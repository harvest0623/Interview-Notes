## 1. 虚拟内存与地址转换

**每个进程看到的是独立的虚拟地址空间，CPU 通过 MMU 把虚拟地址翻译成物理地址，翻译依据是页表，页表的缓存是 TLB。虚拟内存带来的不是「更大的内存」，而是隔离、按需分配、共享与可换出：进程只能用自己页表里映射过的页，物理页可以延迟分配，同一个文件页可以被多个进程共享。**

1. **地址空间布局**：用户态低地址依次是代码段（text）、只读数据、已初始化/未初始化数据（data/bss）、堆（向高地址增长）、共享库与 `mmap` 区、栈（向低地址增长）；内核映射在高半区，用户态不可访问。
2. **多级页表**：x86-64 的 4 级页表把 48 位虚拟地址拆成 4 个 9 位索引加 12 位页内偏移（页大小 4KB）；每级页表占一页，未使用的地址区间对应页表项为空，从而节省内存。
3. **PTE 标志位**：存在位（P）、读写位（R/W）、用户/超级用户位（U/S）、访问位（A）、脏位（D）、全局位（G）、不可执行位（NX）；缺页处理与页面置换都依赖这些位。
4. **TLB**：缓存「虚拟页号 → 物理页帧号」的翻译结果；命中只需 1 个周期级别，未命中要走页表遍历（page walk），多级页表最多 4 次访存。PCID 让切换地址空间时不必全量刷 TLB。
5. **缺页**：页表项不存在或权限不符时触发 `#PF`，内核判断是「按需分配 / COW / 换入 / 非法访问」，分别处理或投递 `SIGSEGV`。
6. **虚拟内存的收益**：进程隔离、按需调页、文件映射共享、`fork` 写时复制、swap 扩展、`overcommit` 允许申请超过物理内存的地址空间。

**地址转换对性能的影响：**

- TLB 命中时地址转换几乎免费；TLB miss 要走页表，最坏 4 次访存，随机访问大内存时 TLB 是关键瓶颈。
- 大页把 512 个 4KB 页合并成一个 2MB 页，TLB 覆盖范围扩大 512 倍，数据库与虚拟化场景收益明显。
- 缺页把「访问内存」变成「进内核 + 磁盘 IO」，major fault 的延迟比 TLB miss 高几个数量级，工作集应尽量控制在物理内存内。

| 区域 | 典型地址（x86-64） | 内容 | 增长方向 |
| --- | --- | --- | --- |
| text / rodata | `0x00400000` 附近 | 指令、只读常量 | 固定 |
| data / bss | text 之后 | 全局/静态变量 | 固定 |
| heap | data 之后 | `malloc`/`new` 的小块 | 向高地址 |
| mmap 区 | `0x7f...` 附近 | 共享库、文件映射、大块分配 | 由内核挑选空档 |
| stack | `0x7fff...` 附近 | 局部变量、返回地址 | 向低地址 |
| kernel | `0xffff...` | 内核代码与直接映射 | 用户不可见 |

**示例（打印各类变量的地址，Linux + GCC）：**

```c
// gcc addr.c -o addr && ./addr
#include <stdio.h>
#include <stdlib.h>

int global_var = 1;

int main(void) {
    int local = 2;
    int *heap = malloc(sizeof(int));
    printf("main   = %p\n", (void *)main);
    printf("global = %p\n", (void *)&global_var);
    printf("heap   = %p\n", (void *)heap);
    printf("stack  = %p\n", (void *)&local);
    free(heap);
    return 0;
}
```

```text
main   = 0x4011a6
global = 0x404038
heap   = 0x1a2a2a0
stack  = 0x7ffd3c9e5a4c
```

```bash
getconf PAGE_SIZE                 # 4096
cat /proc/self/maps               # 当前进程的虚拟地址区间与权限
pmap <pid>                        # 按区间汇总，含 RSS 与共享页
cat /proc/<pid>/status | grep -E 'VmSize|VmRSS|VmSwap'
```

**与业务/后端的联系：**

- `VmSize`（VSZ）是虚拟地址预留，`VmRSS` 是真正占用的物理页；Go、JVM 会预留大块虚拟空间，VSZ 很高但 RSS 正常，不能据此判断内存泄漏。
- 容器内存限额看的是 RSS 与 page cache 等实际用量，不是 VSZ；`docker stats` 的 MEM USAGE 与 `VmRSS` 口径接近但包含 cache。
- 大量 `mmap`/`munmap` 会造成页表与 TLB 抖动，长期运行的服务应复用缓冲区或使用对象池，而不是频繁申请释放大块内存。
- 数据库、消息队列常用 `mmap` 读写文件，把 page cache 直接映射进用户空间，省掉一次内核到用户的拷贝。

**面试怎么答：** 先讲「虚拟地址 → 页表 → 物理地址」这条主线，说明 MMU 与 TLB 的角色。再讲多级页表为什么省内存，以及 PTE 的关键标志位。然后讲缺页的四种来源（按需、COW、换入、非法）。最后补工程视角：VSZ 与 RSS 的区别、虚拟内存带来的隔离与共享。

**易错点：**

- 认为虚拟地址就是物理地址；只有内核的直接映射区才近似相等，用户态地址必须翻译。
- 把 VSZ 当成内存占用；虚拟地址预留不等于物理页已分配。
- 认为 TLB 未命中必须走 4 次访存；实际可能命中中间级页表的缓存，且大页能显著减少遍历层数。
- 忘记页表本身也占内存：进程越多、地址空间越分散，页表开销越大。

## 2. 分页与分段

**分页把地址空间切成固定大小的页（通常 4KB），解决了外部碎片，代价是最后一页可能有内部碎片；分段按程序的逻辑结构切分（代码段、数据段、栈段），便于共享与保护，但会产生外部碎片。x86-64 的 Linux 实际上以分页为主，段寄存器仍然存在但基址基本为 0，所谓「平坦模型」；大页（2MB/1GB）用来减少页表项与 TLB 压力。**

1. **分页术语**：虚拟地址被拆成「页号 + 页内偏移」，物理内存对应「页帧号 + 页内偏移」；页表保存页号到页帧号的映射，页大小决定偏移位数（4KB 对应 12 位）。
2. **分段术语**：逻辑地址是「段号 + 段内偏移」，段表保存段基址与段界限；访问时先查段表再做越界检查，然后加上基址得到线性地址。
3. **段页式**：先分段再分页，兼具逻辑保护与无外部碎片，x86 历史上支持，现代 Linux 简化成平坦分段 + 分页。
4. **内部碎片 vs 外部碎片**：分页的最后一个页可能只用一部分，是内部碎片；分段按需分配不等长区域，释放后留下不连续空洞，是外部碎片。
5. **大页**：x86-64 支持 2MB（PMD 级）与 1GB（PUD 级）大页；一个 2MB 页只需要一个 TLB 条目，能显著降低 TLB miss；THP（透明大页）由内核自动合并，`always`/`madvise`/`never` 三种模式。
6. **代价**：大页会放大 COW 与内存回收的粒度，Redis、JVM 等延迟敏感服务常把 THP 设为 `madvise` 或关闭，避免单次复制 2MB。

**分段与保护的关系：**

- x86 的段描述符带 DPL（特权级）与类型字段，历史上用于实现用户态/内核态隔离；现代 Linux 改用页表的 U/S 位做隔离。
- 「段错误」这个名字来自分段机制，但今天触发它的通常是页表权限检查或非法地址，而不是段界限越界。
- 平坦模型下 `CS`/`DS` 的基址为 0、界限为全地址空间，段寄存器主要保留特权级与 `FS`/`GS` 的 TLS 基址用途。

| 维度 | 分页 | 分段 |
| --- | --- | --- |
| 划分依据 | 固定大小（硬件决定） | 程序逻辑（编译器/程序员决定） |
| 地址 | 页号 + 页内偏移 | 段号 + 段内偏移 |
| 碎片 | 内部碎片（最后一页） | 外部碎片（空洞） |
| 保护与共享 | 以页为粒度 | 以段为粒度，更贴合逻辑 |
| 现代 Linux | 主要机制 | 平坦模型，基址 0，仅保留权限检查 |

**示例（查看页大小、大页与 THP 配置）：**

```bash

# 4096

grep -E 'HugePages_Total|Hugepagesize' /proc/meminfo
# HugePages_Total:       0
# Hugepagesize:       2048 kB

# [always] madvise never

cat /sys/kernel/mm/transparent_hugepage/defrag
# [always] madvise never

grep -i huge /proc/<pid>/smaps | head
```

**显式申请大页（需要预先分配 `vm.nr_hugepages`）：**

```c

               MAP_PRIVATE | MAP_ANONYMOUS | MAP_HUGETLB, -1, 0);
```

```bash
sysctl vm.nr_hugepages        # 查看/设置预留的大页数量（需 root）
```

**与业务/后端的联系：**

- Redis 官方建议把 THP 设为 `madvise` 或 `never`：`fork` 做 RDB 时 COW 以 2MB 为单位复制，会放大延迟与内存占用。
- JVM 的堆常用 `-XX:+UseLargePages` 配大页，减少 TLB miss；但需要预先预留，且 NUMA 机器要配 `numactl`。
- 数据库 buffer pool 用大页能提升随机访问性能，代价是启动时要预留连续物理内存，容器里往往不可用。
- 容器与云主机的内存统计以 4KB 页为基本单位，但内核可能合并相同页（KSM），导致 RSS 看起来偏小。

**面试怎么答：** 先讲分页解决外部碎片、分段贴合逻辑结构，再说段页式如何结合两者。然后指出 x86-64 Linux 是「平坦分段 + 多级分页」，段寄存器主要用于权限。最后补大页与 THP：减少 TLB miss，但放大 COW 与回收粒度，延迟敏感服务要谨慎。

**易错点：**

- 说「分页没有碎片」；分页消除外部碎片，但存在内部碎片。
- 认为现代 Linux 完全不用分段；段寄存器仍在，只是基址为 0、主要用于特权级与兼容。
- 认为大页总是更快；随机小内存访问、COW 频繁、内存紧张时大页可能更慢。
- 把 THP 的 `always` 当成「总是分配大页」；它依赖内存整理，分配失败会回退到 4KB 页。

## 3. 页面置换算法（LRU / Clock）

**页面置换解决「物理页不够时换出谁」。OPT 是理论最优但需要预知未来；FIFO 实现简单却会出现 Belady 异常（增加页帧反而缺页更多）；LRU 用「最近最久未使用」近似程序的局部性，是栈式算法不会出现 Belady 异常，但精确实现需要哈希表 + 双向链表；Clock 用访问位做 LRU 的廉价近似，是操作系统实际常用的方案。**

1. **OPT（最佳置换）**：淘汰未来最长时间不会再被访问的页；缺页率最低，但无法实现，只作为衡量其他算法的上界。
2. **FIFO**：淘汰最早进入内存的页；实现只需一个队列，但会把「常驻的热页」误淘汰，且存在 Belady 异常。
3. **LRU**：淘汰最久没有被访问的页；利用时间局部性，缺页率接近 OPT；精确 LRU 每次访问都要更新链表，开销大。
4. **Clock（二次机会）**：页排成环形，每页一个访问位；缺页时从指针位置扫描，访问位为 1 就清零并跳过，为 0 就淘汰。它把「最近访问过」的页给一次豁免，是 LRU 的近似。
5. **改进 Clock**：同时看访问位与脏位，优先淘汰「未访问且未修改」的页，避免把脏页换出时还要写回磁盘。
6. **工程近似**：Redis 的 `allkeys-lru` 是随机采样若干 key 后挑最久未用的，不是精确 LRU；MySQL InnoDB 用改进 LRU，新页插入 midpoint，避免全表扫描冲掉热数据。

| 算法 | 是否需要预知未来 | Belady 异常 | 实现开销 | 近似目标 |
| --- | --- | --- | --- | --- |
| OPT | 是 | 无 | 不可实现 | 理论下界 |
| FIFO | 否 | 有 | 低（队列） | 无 |
| LRU | 否 | 无（栈式算法） | 高（哈希 + 双向链表） | 时间局部性 |
| Clock | 否 | 可能有 | 低（环形 + 访问位） | 近似 LRU |
| 改进 Clock | 否 | 可能有 | 低 | 近似 LRU + 减少写回 |

**示例（Go 模拟 FIFO 与 LRU 的缺页次数，Go 1.21+）：**

```go
// go run page.go
package main

import "fmt"

func fifo(ref []int, frames int) int {
    mem := []int{}
    faults := 0
    for _, p := range ref {
        hit := false
        for _, v := range mem {
            if v == p { hit = true; break }
        }
        if hit {
            continue
        }
        faults++
        if len(mem) < frames {
            mem = append(mem, p)
        } else {
            mem = append(mem[1:], p)      // 淘汰最早进入的页
        }
    }
    return faults
}

func lru(ref []int, frames int) int {
    mem := []int{}                        // 头部最久未使用，尾部最近使用
    faults := 0
    for _, p := range ref {
        idx := -1
        for i, v := range mem {
            if v == p { idx = i; break }
        }
        if idx >= 0 {
            mem = append(append(mem[:idx], mem[idx+1:]...), p)   // 命中后移到尾部
            continue
        }
        faults++
        if len(mem) < frames {
            mem = append(mem, p)
        } else {
            mem = append(mem[1:], p)
        }
    }
    return faults
}

func main() {
    ref := []int{7, 0, 1, 2, 0, 3, 0, 4, 2, 3, 0, 3, 2, 1, 2, 0, 1, 7, 0, 1}
    fmt.Println("FIFO 缺页:", fifo(ref, 3))
    fmt.Println("LRU  缺页:", lru(ref, 3))
    fmt.Println("OPT  缺页: 9（理论值）")
}
```

```text
FIFO 缺页: 15
LRU  缺页: 12
OPT  缺页: 9（理论值）
```

```bash
sar -B 1 5          # 需要 sysstat：pgpgin/s、pgpgout/s、fault/s、majflt/s
```

**与业务/后端的联系：**

- Redis 的 `maxmemory-policy` 选 `allkeys-lru` 时是采样近似，采样数由 `maxmemory-samples` 控制，增大采样更接近精确 LRU 但更耗 CPU。
- InnoDB 的 buffer pool 用改进 LRU：新页进入 midpoint，防止一次性全表扫描把热数据全部淘汰，这是「LRU 工程化」的经典案例。
- 操作系统层的缺页率看 `majflt/s`：频繁 major fault 说明工作集超过内存，正在 swap 或反复读文件。
- 缓存系统不能只用 LRU：带扫描型访问时会污染缓存，需要结合 LFU、TinyLFU 或分段 LRU。

**面试怎么答：** 先讲 OPT 是上界、FIFO 简单但有 Belady 异常、LRU 利用局部性且不会 Belady、Clock 用访问位近似 LRU。再给缺页率对比：同一引用串下 OPT < LRU < FIFO。最后讲工程实现：精确 LRU 要哈希 + 双向链表做到 O(1)，操作系统更爱 Clock，Redis/InnoDB 用采样或改进 LRU。

**易错点：**

- 认为 FIFO 和 LRU 都满足栈式算法；只有 LRU（以及 OPT）满足，FIFO 会出现 Belady 异常。
- 实现 LRU 只用数组扫描：功能对但复杂度 O(n)，面试要能说出「哈希表 + 双向链表」的 O(1) 结构。
- 把 Clock 当成精确 LRU；它只是给访问位一次机会，指针扫过的页可能被重复豁免。
- 统计缺页次数时忘记「初始空帧也计一次缺页」，或者把命中后的链表更新漏掉。

## 4. 缺页中断与 swap

**缺页不是错误，而是虚拟内存的正常工作方式：页表项为空时，内核在缺页处理中分配物理页、从文件或 swap 读入数据、建立映射，然后重新执行那条指令。缺页分 minor（不需要磁盘 IO，如首次访问匿名页、COW）与 major（需要读磁盘或 swap）；major fault 的延迟是毫秒级，是性能分析里要重点盯的指标。**

1. **触发**：CPU 翻译地址时发现 PTE 不存在（P=0）或权限不符（写只读页、用户态访问内核页），抛出 `#PF`，切换到内核的缺页处理程序。
2. **分类**：匿名页首次访问（minor，分配零页）、文件页首次访问（major，读 page cache 或磁盘）、COW（minor，复制一页）、swap 换入（major）、非法地址（投递 `SIGSEGV`）。
3. **处理步骤**：根据 `cr2` 得到出错地址 → 查 `vma` 判断是否合法 → 分配页帧（可能触发回收/换出）→ 读入数据（文件或 swap）→ 填写 PTE、设置权限 → 返回用户态重新执行指令。
4. **swap**：内存不足时把匿名页写到 swap 分区/文件，换出后 PTE 标记为不在内存；再次访问触发 major fault 换入。swap 不是「扩展内存」，而是把延迟从「OOM」换成「慢」。
5. **zswap/zram**：zswap 在 swap 前先压缩到内存池，zram 用压缩块设备做 swap；两者都用 CPU 换 IO，适合内存紧张但 CPU 有余的场景。
6. **overcommit**：`vm.overcommit_memory=0` 启发式、`1` 总是允许、`2` 严格按 `overcommit_ratio` 限制；允许 overcommit 意味着 `malloc` 成功不代表物理页可用，真正写入时才可能 OOM。

| 类型 | 是否读磁盘 | 典型场景 | 延迟量级 |
| --- | --- | --- | --- |
| minor fault | 否 | 匿名页首次访问、COW、页表项缺失 | 微秒级 |
| major fault | 是 | 文件页未缓存、swap 换入 | 毫秒级 |
| 非法访问 | 否 | 空指针、越界、权限不符 | 立即 `SIGSEGV` |

**示例（mmap 64MB 并逐页写入，统计缺页，Linux + GCC）：**

```c
// gcc fault.c -o fault && /usr/bin/time -v ./fault
#define _GNU_SOURCE
#include <stdio.h>
#include <sys/mman.h>
#include <sys/resource.h>
#include <unistd.h>

int main(void) {
    size_t len = 64UL << 20;                 // 64MB
    char *p = mmap(NULL, len, PROT_READ | PROT_WRITE,
                   MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
    if (p == MAP_FAILED) {
        perror("mmap");
        return 1;
    }
    long ps = sysconf(_SC_PAGESIZE);
    for (size_t i = 0; i < len; i += ps) {
        p[i] = 1;                            // 每页第一次写触发一次 minor fault
    }
    struct rusage ru;
    getrusage(RUSAGE_SELF, &ru);
    printf("minor=%ld major=%ld\n", ru.ru_minflt, ru.ru_majflt);
    munmap(p, len);
    return 0;
}
```

```text
minor=16386 major=0
```

**与业务/后端的联系：**

- 服务刚启动时大量 major fault（冷启动、首次读配置/词典）会造成毛刺；用预热（提前读一遍数据）把 major fault 提前到启动阶段。
- 容器里内存超限时不会「慢慢 swap」，通常直接 OOMKilled（exit 137）；Kubernetes 可以给 Pod 配 `memory.swap.max=0` 明确禁用 swap。
- `swappiness` 默认 60，表示匿名页与文件页回收的相对权重，不是「用到 60% 才 swap」；数据库通常调低到 1-10，减少匿名页被换出。
- JVM/Go 的堆越大，GC 与缺页的交互越明显；堆刚好超过物理内存时会持续 major fault，表现为「CPU 不高但吞吐骤降」。

**面试怎么答：** 先讲缺页处理六步，强调「缺页是正常机制」。再分 minor 与 major，说明 COW 与 swap 换入分别属于哪类。然后讲 swap 的定位：用延迟换空间，不是免费扩容；配合 zswap/zram。最后补 overcommit 与 OOM 的关系：申请成功不等于能写入。

**易错点：**

- 把缺页当成异常/错误；只有非法地址才投递 `SIGSEGV`，正常缺页对用户透明。
- 认为 minor fault 不花时间；它仍要进内核、分配页、填页表，量大时非常可观。
- 认为 `swappiness=0` 就完全不 swap；它只是降低匿名页换出倾向，内存压力大时仍可能换出。
- 把 `vm.overcommit_memory=1` 当成「内存无限」；它只放宽申请检查，物理页不足时照样 OOM。

## 5. 内存碎片与分配器

**碎片分两种：内部碎片是「分配块比请求大，浪费在块内」，外部碎片是「空闲总量够但没有连续的大块」。内核用伙伴系统（buddy）管理物理页、用 slab/slub 管理小对象；用户态 glibc 用 ptmalloc2（arena + bins + tcache），大块直接 `mmap`。碎片不是 bug，而是分配策略的必然产物，工程上靠「对象池、固定大小分配、减少频繁申请释放」来缓解。**

1. **伙伴系统**：把物理页按 2 的幂分成 order 0（1 页）到 order 10（1024 页，4MB）；申请时向上取整到 order，释放时若相邻伙伴也空闲就合并成更高 order，减少外部碎片。
2. **slab/slub**：内核小对象（`task_struct`、`inode`、`dentry`）从 slab 缓存分配，按对象大小建缓存，避免每次都走伙伴系统；slub 是当前默认实现。
3. **ptmalloc2 结构**：每个线程有 arena（默认上限与核数相关），arena 内用 bins 管理空闲 chunk；tcache 是每线程的小块缓存（glibc 2.26+），命中时几乎无锁。
4. **大块分配**：超过 `mmap_threshold`（默认 128KB，动态可上调到 32MB）的请求直接用 `mmap`，释放时 `munmap` 归还内核；小块从 heap（`brk`）分配，释放后不一定归还。
5. **外部碎片来源**：不同大小对象交错分配、长期存活对象夹在中间、线程 arena 各自持有空闲内存；表现为「RSS 不降但空闲块无法复用」。
6. **缓解手段**：固定大小对象池、按大小分级、`malloc_trim`、限制 arena 数量（`MALLOC_ARENA_MAX`）、换用 jemalloc/tcmalloc 的分级缓存。

**分配器选型：**

- glibc ptmalloc2 通用，但多线程下 arena 竞争与碎片明显；jemalloc 用 per-thread cache + size class，Redis 默认用它。
- tcmalloc 以「每线程缓存 + 中央页堆」降低锁竞争，适合短生命周期小对象多的服务；Go 运行时的分配器思路接近 tcmalloc。
- 选型要看分配模式：小对象多、线程多、生命周期混合时，jemalloc/tcmalloc 往往比 ptmalloc 更稳。

| 层级 | 分配器 | 管理单位 | 典型问题 |
| --- | --- | --- | --- |
| 物理页 | buddy | 2 的幂个连续页 | 外部碎片（高阶块缺失） |
| 内核对象 | slab / slub | 固定大小对象 | 缓存膨胀、回收慢 |
| 用户态小块 | ptmalloc2 / tcache | chunk（16B 对齐） | 内部碎片、arena 膨胀 |
| 用户态大块 | `mmap` / jemalloc / tcmalloc | 页或 arena | 频繁 map/unmap 的系统调用 |

**示例（制造空洞并观察 RSS，Linux + GCC）：**

```c
// gcc frag.c -o frag && ./frag
#define _GNU_SOURCE
#include <malloc.h>
#include <stdio.h>
#include <stdlib.h>
#include <sys/resource.h>

int main(void) {
    const int n = 200000;
    void **ptr = malloc(n * sizeof(void *));
    for (int i = 0; i < n; i++) {
        ptr[i] = malloc(96);                 // 小块，走 heap
    }
    for (int i = 0; i < n; i += 2) {
        free(ptr[i]);                        // 每隔一个释放，留下空洞
    }
    void *big = malloc(32UL << 20);          // 大块走 mmap，绕开空洞
    printf("big=%p\n", big);
    free(big);
    for (int i = 1; i < n; i += 2) {
        free(ptr[i]);
    }
    free(ptr);
    malloc_trim(0);                          // 尽量把 heap 顶部归还内核
    struct rusage ru;
    getrusage(RUSAGE_SELF, &ru);
    printf("maxrss=%ld KB\n", ru.ru_maxrss);
    return 0;
}
```

```bash
cat /proc/buddyinfo          # 各 order 的空闲块数量，order 越大越缺说明外部碎片严重
cat /proc/pagetypeinfo       # 按迁移类型统计，Unmovable 多会影响大页分配
grep -E 'Slab|SReclaimable|SUnreclaim' /proc/meminfo
MALLOC_ARENA_MAX=2 ./app     # 限制 arena 数量，降低多线程下的内存膨胀
```

**与业务/后端的联系：**

- Redis 的 `mem_fragmentation_ratio = RSS / used_memory`，大于 1.5 通常说明碎片严重，可开启 `activedefrag`；但它只处理 allocator 层碎片，不处理业务对象泄漏。
- 长期运行的服务 RSS 缓慢上涨但 heap profile 平稳，往往是分配器碎片或线程 arena 缓存，重启能暂时缓解，根治要减少「大小混合 + 频繁申请」。
- 高并发 Java 服务出现 `Native memory` 膨胀，可能是 glibc arena 与 JVM 线程数叠加；`MALLOC_ARENA_MAX=2` 是常见的容器调优项。
- 大页分配失败（`/proc/buddyinfo` 缺少高阶块）会让 THP 退化，数据库启动时预留大页失败多半是物理内存碎片或未预留。

**面试怎么答：** 先区分内部/外部碎片，再讲内核的两级结构：buddy 管页、slab 管对象。然后讲用户态 ptmalloc 的 arena/bins/tcache 与 128KB 的 mmap 阈值。最后给缓解手段：对象池、固定大小、`malloc_trim`、限制 arena、换 jemalloc/tcmalloc。

**易错点：**

- 认为 `free` 会把内存立刻还给操作系统；glibc 只可能 trim 堆顶，中间的空洞无法归还。
- 把「RSS 不下降」等同于内存泄漏；分配器缓存与碎片同样会让 RSS 保持高位。
- 混淆内部碎片与外部碎片；分页/固定大小分配主要产生内部碎片，变长分配主要产生外部碎片。
- 认为换 jemalloc 就能消灭碎片；它只是把碎片控制在 arena 内，长期运行仍会累积。

## 6. 堆与栈的区别

**栈由内核/运行时自动管理，存放函数调用帧（参数、返回地址、局部变量），随函数返回自动弹出，大小有限（Linux 主线程默认 8MB）；堆由程序员或运行时手动管理（`malloc`/`new`/GC），生命周期由代码决定，地址空间大但分配更慢。栈是「后进先出、连续、极快」，堆是「按需分配、离散、需要管理」。**

1. **栈的生长**：x86-64 的栈从高地址向低地址增长，`rsp` 指向栈顶；每次调用压入返回地址与旧 `rbp`，再为局部变量减 `rsp`，形成栈帧。
2. **栈的大小**：`ulimit -s` 默认 8192KB；主线程栈由内核在 `exec` 时建立，子线程栈由 `pthread` 按 `attr` 分配（默认同样 8MB 虚拟空间）；栈底有 guard page，越界访问触发 `SIGSEGV`。
3. **栈的分配**：只移动栈指针，几乎没有分配成本；但栈空间不能跨函数返回后继续使用，返回局部变量的地址是未定义行为。
4. **堆的分配**：`malloc` 走 ptmalloc 的 bins/tcache 或 `mmap`，`free` 归还到分配器；分配需要查空闲链表、可能触发系统调用，成本高于栈。
5. **生命周期**：栈对象随作用域结束销毁；堆对象一直存活到 `free` 或 GC 回收，容易产生泄漏与悬垂指针。
6. **逃逸分析**：Go/Java 会把「可能被外部持有」的对象放到堆，其余留在栈；所以「用了指针就在堆」是错的，栈上也可以有指针。

| 维度 | 栈 | 堆 |
| --- | --- | --- |
| 管理者 | 编译器/运行时自动 | 程序员或 GC |
| 分配方式 | 移动栈指针 | 空闲链表 / bins / mmap |
| 大小 | 默认 8MB，可 `ulimit` 调整 | 受地址空间与物理内存限制 |
| 生长方向 | x86-64 向低地址 | 通常向高地址（`brk`） |
| 分配速度 | 极快（几条指令） | 较慢（查找 + 可能的系统调用） |
| 碎片 | 无 | 有内部/外部碎片 |
| 典型错误 | 栈溢出、返回局部变量地址 | 泄漏、悬垂指针、重复释放 |
| 缓存友好性 | 高（连续、热） | 较低（离散） |

**示例（打印栈/堆地址并观察栈深，Linux + GCC）：**

```c
// gcc heapstack.c -o heapstack && ./heapstack
#include <stdio.h>
#include <stdlib.h>

int global_var;

int depth(int n) {
    char pad[1024];
    pad[0] = (char)n;
    if (n == 0) {
        return pad[0];
    }
    return depth(n - 1) + pad[0];
}

int main(void) {
    int local = 0;
    int *heap = malloc(sizeof(int));
    printf("global=%p heap=%p stack=%p\n",
           (void *)&global_var, (void *)heap, (void *)&local);
    printf("depth(1000)=%d\n", depth(1000));
    free(heap);
    return 0;
}
```

```bash
ulimit -s                     # 8192，单位 KB
cat /proc/<pid>/maps | grep -E 'stack|heap'
# 7ffd...-7ffd... rw-p [stack]
# 01a2...-01a2... rw-p [heap]
ulimit -s 512 && ./heapstack  # 栈变小后，深递归更容易崩溃
```

**与业务/后端的联系：**

- 递归解析深嵌套 JSON/XML 时，栈溢出会让进程直接 `SIGSEGV`；要么限制深度，要么改用显式栈迭代。
- 在栈上开大数组（如 `char buf[1MB]`）会迅速耗尽 8MB 栈；大缓冲区应放堆或复用池。
- 线程数乘以栈大小是虚拟地址开销：1000 个线程约 8GB 虚拟空间，虽然大多未触达，但在 32 位或受限环境会先撞墙。
- Go 的 goroutine 栈按需增长，递归过深会触发 `morestack`；`debug.SetMaxStack` 可调上限，但真正的问题通常是递归没有终止条件。

**面试怎么答：** 先给一句话：栈自动、连续、快、小；堆手动、离散、慢、大。再讲栈帧与 `rsp` 的移动、guard page 与栈溢出；堆讲 `malloc`/`free` 与碎片。最后补逃逸分析：对象放栈还是堆由编译器决定，不由 `new` 决定。

**易错点：**

- 说「栈在低地址、堆在高地址」；x86-64 用户态通常栈在高地址、堆在低地址，栈向低增长。
- 返回局部变量的地址；函数返回后栈帧失效，指针指向已释放区域，属于未定义行为。
- 认为栈一定比堆快很多；小对象在 tcache 命中时也很快，真正的差别在分配机制与缓存局部性。
- 把「栈大小 8MB」当成物理内存占用；它是虚拟空间预留，按需触达才占物理页。

## 7. 零拷贝（sendfile / mmap）

**零拷贝不是「一次拷贝都没有」，而是「消除 CPU 在用户态与内核态之间的数据搬运」。传统 `read` + `write` 要 4 次拷贝、4 次上下文切换；`sendfile` 让数据从 page cache 直接 DMA 到网卡，只剩 2 次 DMA 拷贝、2 次上下文切换；`mmap` + `write` 省掉内核到用户的拷贝，但仍有 3 次拷贝与缺页开销。真正的收益是减少 CPU 占用与内存带宽，而不是消灭所有拷贝。**

1. **传统路径**：`read` 把磁盘数据 DMA 到内核缓冲区，再 CPU 拷贝到用户缓冲区；`write` 把用户缓冲区 CPU 拷贝到 socket 缓冲区，再 DMA 到网卡。共 4 次拷贝（2 次 DMA + 2 次 CPU）、4 次模式切换（两次系统调用，每次进出各一次）。
2. **mmap + write**：`mmap` 把 page cache 映射到用户空间，省掉「内核缓冲区 → 用户缓冲区」的 CPU 拷贝，剩 3 次拷贝、4 次切换；代价是缺页、TLB 压力与映射管理。
3. **sendfile**：数据不经过用户态，内核直接从 page cache 把数据送到 socket；若网卡支持 scatter-gather DMA，连 socket 缓冲区的 CPU 拷贝也省掉，只剩 2 次 DMA 拷贝、2 次切换。
4. **splice**：借助 pipe 在两个 fd 之间移动数据，内核态完成，适合 socket 到 socket、文件到 socket 的转发；需要至少一个 fd 是 pipe。
5. **DMA 与 scatter-gather**：DMA 负责内存与外设之间的搬运，CPU 不参与；scatter-gather 让网卡直接读取分散的页，避免为连续发送而拼接缓冲区。
6. **限制**：`sendfile` 只能「文件 → socket」，不能在用户态修改内容；启用 TLS 时数据需要加密，普通 `sendfile` 不可用，要靠 kTLS 或回退到用户态拷贝。

| 方式 | 拷贝次数 | 上下文切换 | CPU 拷贝 | 适用 |
| --- | --- | --- | --- | --- |
| `read` + `write` | 4 | 4 | 2 次 | 通用，需用户态处理数据 |
| `mmap` + `write` | 3 | 4 | 1 次 | 大文件、可接受缺页开销 |
| `sendfile` | 2 | 2 | 0 次（支持 SG 时） | 静态文件、文件转发 |
| `splice` | 2 | 2 | 0 次 | 管道中转、代理转发 |

**示例（sendfile 拷贝文件，Linux + GCC）：**

```c
// gcc sendfile_demo.c -o sendfile_demo && ./sendfile_demo
#define _GNU_SOURCE
#include <fcntl.h>
#include <stdio.h>
#include <sys/sendfile.h>
#include <sys/stat.h>
#include <unistd.h>

int main(void) {
    int in = open("data.bin", O_RDONLY);
    int out = open("copy.bin", O_WRONLY | O_CREAT | O_TRUNC, 0644);
    if (in < 0 || out < 0) {
        perror("open");
        return 1;
    }
    struct stat st;
    fstat(in, &st);
    off_t off = 0;
    ssize_t n = sendfile(out, in, &off, st.st_size);
    printf("sendfile copied %zd bytes\n", n);
    close(in);
    close(out);
    return 0;
}
```

**Go 的等价路径：**

```go
// io.Copy 在 *os.File 到 net.Conn 时会走 ReadFrom，Linux 上落到 sendfile
n, err := io.Copy(conn, file)
```

**与业务/后端的联系：**

- Nginx 的静态文件服务用 `sendfile`（`sendfile on`），大文件下载的 CPU 占用明显低于逐块 `read/write`。
- Kafka 把日志段发送给消费者时用 `sendfile`，消息不经过 JVM 堆，减少 GC 压力与拷贝。
- 代理/网关转发大响应体时可用 `splice`，避免在用户态拼接缓冲区；但需要处理半包、超时与 TLS。
- 小文件、需要内容改写（压缩、加密、加水印）的场景不适合 `sendfile`，用户态处理后再发反而更简单。

**面试怎么答：** 先画传统 `read` + `write` 的 4 次拷贝与 4 次切换，再讲 `sendfile` 如何把「内核 → 用户 → 内核」这两段砍掉，只剩 DMA。接着对比 `mmap`：省一次 CPU 拷贝但引入缺页与 TLB 开销。最后补限制：只能文件到 socket、不能改内容、TLS 下需要 kTLS 或回退。

**易错点：**

- 把零拷贝说成「零次拷贝」；DMA 拷贝仍然存在，省掉的是 CPU 参与的拷贝。
- 认为 `mmap` 一定比 `read` 快；小文件、随机访问、缺页频繁时可能更慢。
- 在需要修改内容的链路里硬套 `sendfile`；它不支持用户态加工，必须回退到缓冲区方案。
- 忽略 `sendfile` 的 offset 语义：传入 `NULL` 会从文件当前偏移读，传入指针会更新偏移，循环发送时要用对。

## 8. IO 模型：阻塞、非阻塞与多路复用

**一次网络 IO 分两个阶段：等数据就绪（网卡收到包、内核缓冲区可读）和把数据从内核拷贝到用户空间。阻塞 IO 两个阶段都等；非阻塞 IO 第一阶段轮询、第二阶段仍阻塞；IO 多路复用先用 `select`/`poll`/`epoll` 等「哪一个就绪」，再对就绪的 fd 做拷贝；信号驱动靠 `SIGIO` 通知；异步 IO 则由内核完成拷贝后再通知，真正做到了「发起后不管」。**

1. **阻塞 IO**：`read` 一直睡到有数据，期间线程不能做别的；每连接一线程的模型就是这么来的，连接数上去后线程与栈开销爆炸。
2. **非阻塞 IO**：fd 设 `O_NONBLOCK`，没数据时 `read` 立即返回 `-1` 并置 `EAGAIN`/`EWOULDBLOCK`；必须配合事件通知或轮询，纯轮询会烧 CPU。
3. **IO 多路复用**：一个线程用 `epoll_wait` 同时盯成千上万个 fd，返回就绪列表；就绪后仍需自己调用 `read`/`write` 完成拷贝，所以它是「同步 IO」。
4. **信号驱动 IO**：fd 就绪时内核发 `SIGIO`，应用在信号处理里读；信号处理限制多、易丢失，实际很少用于高并发。
5. **异步 IO**：应用发起 `aio_read`/`io_uring` 后立即返回，内核完成「等数据 + 拷贝」再通知；Linux 传统 POSIX AIO 只对部分场景有效，`io_uring`（5.1+）才是通用方案。
6. **两阶段视角**：阻塞/非阻塞描述第一阶段，同步/异步描述第二阶段由谁完成；「多路复用」只优化了第一阶段。

| 模型 | 第一阶段（等数据） | 第二阶段（拷贝） | 典型接口 |
| --- | --- | --- | --- |
| 阻塞 IO | 阻塞 | 阻塞 | `read`/`write` |
| 非阻塞 IO | 立即返回 `EAGAIN` | 阻塞 | `O_NONBLOCK` + 轮询 |
| IO 多路复用 | 阻塞在 `epoll_wait` | 阻塞 | `select`/`poll`/`epoll` |
| 信号驱动 IO | 立即返回，`SIGIO` 通知 | 阻塞 | `fcntl(F_SETFL, O_ASYNC)` |
| 异步 IO | 立即返回 | 内核完成，通知应用 | `io_uring`、IOCP |

**示例（非阻塞读，处理 `EAGAIN`，Linux + GCC）：**

```c
// gcc nonblock.c -o nonblock && ./nonblock
#include <errno.h>
#include <fcntl.h>
#include <stdio.h>
#include <unistd.h>

int main(void) {
    int fd = open("/dev/tty", O_RDONLY | O_NONBLOCK);
    if (fd < 0) {
        perror("open");
        return 1;
    }
    char buf[256];
    for (;;) {
        ssize_t n = read(fd, buf, sizeof(buf));
        if (n > 0) {
            printf("read %zd bytes\n", n);
            break;
        }
        if (n == 0) {
            printf("EOF\n");
            break;
        }
        if (errno == EAGAIN || errno == EWOULDBLOCK) {
            usleep(1000);       // 真实场景应交给 epoll，而不是忙等
            continue;
        }
        if (errno == EINTR) {
            continue;           // 被信号打断，重试
        }
        perror("read");
        break;
    }
    close(fd);
    return 0;
}
```

```bash
strace -e trace=read,poll,epoll_wait,epoll_ctl ./app

```

**与业务/后端的联系：**

- Redis 单线程 + epoll 就能支撑高 QPS，因为命令处理很快，瓶颈在网络等待而不是计算；慢命令会阻塞整个事件循环。
- Go 的 netpoller 把 `epoll` 封装在运行时，开发者写「阻塞式」`conn.Read`，实际由调度器把 goroutine 挂起，不占线程。
- Java 传统 `InputStream.read` 是阻塞的，每连接一线程；Netty 用多 reactor + 非阻塞 channel 解决 C10K/C100K。
- 数据库驱动如果只有同步接口，放在协程里会阻塞线程；要么用异步驱动，要么丢进线程池，别在事件循环里直接调用。

**面试怎么答：** 先讲两阶段模型，这是区分所有 IO 模型的钥匙。再逐个说：阻塞两阶段都等；非阻塞第一阶段轮询；多路复用统一等就绪再拷贝；信号驱动靠信号；异步 IO 由内核完成拷贝。最后强调「多路复用仍是同步 IO」，真正的异步在 Linux 上主要看 `io_uring`。

**易错点：**

- 把 `epoll` 当成异步 IO；它只告诉你「可读/可写」，拷贝仍由应用完成。
- 非阻塞 `read` 返回 0 当成 `EAGAIN`；返回 0 是 EOF，`EAGAIN` 才是「暂时没数据」。
- 忽略 `EINTR`：被信号打断的系统调用要重试，否则会误判为错误。
- 非阻塞 fd 上直接 `write` 大块数据；可能只写入一部分，必须循环写并处理 `EAGAIN`。

## 9. select、poll、epoll 对比

**三者都是「等多个 fd 就绪」，差别在数据结构与通知方式：`select` 用位图、fd 数受 `FD_SETSIZE`（通常 1024）限制，每次调用都要把集合从用户态拷到内核态并线性扫描；`poll` 用数组、没有 1024 限制，但仍是 O(n) 扫描；`epoll` 在内核用红黑树维护关注的 fd、用就绪链表返回事件，`epoll_wait` 只处理就绪的 fd，适合海量连接。**

1. **select**：`fd_set` 是位图，最大 fd 受 `FD_SETSIZE` 限制；每次调用要重置并拷贝三个集合，返回后还要遍历所有 fd 判断谁就绪；时间复杂度 O(n)。
2. **poll**：`pollfd` 数组，无固定上限（受 `RLIMIT_NOFILE` 约束），但仍要把整个数组拷进内核并线性扫描，返回后逐个检查 `revents`。
3. **epoll**：`epoll_create1` 创建实例，`epoll_ctl` 增删改关注的 fd（内核红黑树），fd 就绪时通过回调挂到就绪链表，`epoll_wait` 只取就绪链表；单次复杂度与就绪数相关，而非总 fd 数。
4. **LT 与 ET**：LT（水平触发）只要缓冲区还有数据就持续通知，编程简单；ET（边缘触发）只在状态变化时通知一次，必须把 fd 设为非阻塞并循环读到 `EAGAIN`，否则会漏事件。
5. **多线程细节**：`EPOLLONESHOT` 让一个 fd 的事件只被一个线程处理，处理完要重新 `epoll_ctl` 注册；`EPOLLEXCLUSIVE`（4.5+）让多个进程/线程等同一个 listen fd 时只唤醒一个，缓解惊群。
6. **适用边界**：连接数少且频繁增减时，`epoll_ctl` 的红黑树开销与 `select` 差距不大；海量长连接、事件稀疏时 epoll 优势明显。

| 维度 | select | poll | epoll |
| --- | --- | --- | --- |
| fd 上限 | `FD_SETSIZE`（通常 1024） | 无固定上限，受 `RLIMIT_NOFILE` | 受 `RLIMIT_NOFILE` |
| 数据结构 | 位图 | 数组 | 红黑树 + 就绪链表 |
| 每次调用拷贝 | 拷贝整个集合 | 拷贝整个数组 | 仅 `epoll_ctl` 时注册 |
| 时间复杂度 | O(n) | O(n) | O(就绪数) |
| 触发模式 | 仅 LT | 仅 LT | LT / ET |
| 跨平台 | POSIX | POSIX | Linux（BSD 用 kqueue） |

**示例（epoll 监听一个 pipe，Linux + GCC）：**

```c
// gcc epoll_demo.c -o epoll_demo && ./epoll_demo
#define _GNU_SOURCE
#include <stdio.h>
#include <sys/epoll.h>
#include <unistd.h>

int main(void) {
    int p[2];
    if (pipe(p) == -1) {
        perror("pipe");
        return 1;
    }
    int efd = epoll_create1(0);
    struct epoll_event ev = {0}, evs[4];
    ev.events = EPOLLIN;                  // 默认 LT
    ev.data.fd = p[0];
    epoll_ctl(efd, EPOLL_CTL_ADD, p[0], &ev);

    write(p[1], "hello", 5);
    int n = epoll_wait(efd, evs, 4, -1);
    for (int i = 0; i < n; i++) {
        char buf[16] = {0};
        read(evs[i].data.fd, buf, sizeof(buf) - 1);
        printf("ready fd=%d data=%s\n", evs[i].data.fd, buf);
    }
    close(efd);
    close(p[0]);
    close(p[1]);
    return 0;
}
```

```bash
cat /proc/sys/fs/file-max        # 系统级 fd 上限
ulimit -n                        # 进程级 fd 上限
ss -s                            # 当前 socket 数量概览
```

**与业务/后端的联系：**

- Redis、Nginx、Memcached 都以 epoll 为核心；Redis 单线程事件循环，Nginx 每 worker 一个 epoll。
- Netty 在 Linux 上用 epoll 原生传输（`EpollEventLoopGroup`），比 JDK NIO 的 poll 封装少一层拷贝与对象分配。
- 网关/Acceptor 多进程共享 listen fd 时，用 `EPOLLEXCLUSIVE` 或 `SO_REUSEPORT` 避免惊群，后者让每个进程有独立监听队列。
- ET 模式常见于高性能服务器，但必须配合非阻塞 + 读干净；业务代码里若有一次读不完就返回，容易造成连接「假死」。

**面试怎么答：** 先讲三者演进：select 位图 + 1024 限制 + O(n)；poll 数组 + 无上限 + 仍 O(n)；epoll 红黑树注册 + 就绪链表 + O(1) 取事件。再讲 LT/ET 的区别与 ET 的三个要求：非阻塞、循环读到 `EAGAIN`、必要时 `EPOLLONESHOT`。最后补适用边界：连接少时 epoll 未必更快，跨平台要用 kqueue/IOCP。

**易错点：**

- 认为 `poll` 完全没有 fd 上限；它受进程 `RLIMIT_NOFILE` 限制，只是不受 `FD_SETSIZE` 限制。
- ET 模式不把 fd 设为非阻塞：最后一次 `read` 会一直阻塞，拖死事件循环。
- `epoll_wait` 返回 0 当成出错；返回 0 表示超时（timeout 到期），`-1` 才是错误（`EINTR` 要重试）。
- 忘记 `epoll_ctl` 的 `EPOLL_CTL_DEL`：关闭 fd 前不注销，LT 下可能反复收到事件，甚至操作已关闭的 fd。

## 10. Reactor 与 Proactor 模式

**Reactor 是「就绪事件驱动」：内核告诉你 fd 可读/可写，由应用自己完成 `read`/`write` 与业务处理；Proactor 是「完成事件驱动」：应用发起异步操作，内核把数据拷贝完后再通知你「已完成」。前者是同步非阻塞 IO 的经典封装（epoll/kqueue），后者依赖真正的异步 IO（Windows IOCP、Linux `io_uring`）。**

1. **Reactor 组成**：事件多路复用器（epoll）、事件分发器（dispatch）、事件处理器（handler）；循环是「等事件 → 分发 → 处理 → 回到等事件」。
2. **单 Reactor 单线程**：所有 accept、读写、业务都在一个线程，Redis 就是这种模型；优点是零锁、简单，缺点是一个慢操作阻塞全局。
3. **单 Reactor + 工作线程池**：IO 在 reactor 线程，业务丢给线程池；要注意共享状态与回写线程安全。
4. **多 Reactor 多线程（主从）**：主 reactor 只负责 accept，把连接分给多个子 reactor，每个子 reactor 一个线程跑自己的事件循环；Netty 的主从 `EventLoopGroup`、Nginx 的 per-worker 循环都是这个思路。
5. **Proactor 流程**：应用调用异步读 → 内核把数据从设备读到用户缓冲区 → 完成后投递完成事件 → 应用在回调里处理；应用不参与拷贝。
6. **Linux 现状**：POSIX AIO 在 glibc 里对普通文件支持有限，网络 IO 长期靠 Reactor；`io_uring`（5.1+）提供提交/完成环形队列，支持真正的异步读写与网络操作，是现代高性能存储与代理的热点。

**Reactor 处理一个连接的典型步骤：**

1. `epoll_wait` 返回 `EPOLLIN`，从事件里取出 fd 与注册时绑定的事件处理器。
2. 非阻塞 `read` 把数据读进缓冲区；若返回 `EAGAIN` 说明已读干净，回到事件循环。
3. 解析协议、处理业务；需要写回时把数据放入该连接的写缓冲区。
4. 尝试 `write`，若返回 `EAGAIN` 则注册 `EPOLLOUT`，等可写事件再继续发送。
5. 处理完毕回到 `epoll_wait`，全程不阻塞、不睡眠。

| 维度 | Reactor | Proactor |
| --- | --- | --- |
| 关注点 | 就绪（readable/writable） | 完成（read/write done） |
| 谁做数据拷贝 | 应用调用 `read`/`write` | 内核完成 |
| 通知时机 | 可以操作时 | 操作完成时 |
| 典型实现 | epoll、kqueue、select | IOCP、`io_uring` |
| 编程复杂度 | 事件循环 + 非阻塞状态机 | 异步 API + 回调/协程 |
| 常见问题 | handler 阻塞、状态机复杂 | 回调地狱、内核支持有限 |

**示例（Go 的 TCP 服务，底层是 runtime netpoll 的 Reactor 式实现）：**

```go
// go run server.go
package main

import (
    "fmt"
    "io"
    "net"
)

func main() {
    ln, err := net.Listen("tcp", "127.0.0.1:9000")
    if err != nil {
        panic(err)
    }
    fmt.Println("listen on", ln.Addr())
    for {
        conn, err := ln.Accept()
        if err != nil {
            return
        }
        go func(c net.Conn) {          // 每个连接一个 goroutine，由 netpoll 挂起/唤醒
            defer c.Close()
            io.Copy(c, c)
        }(conn)
    }
}
```

```bash

strace -f -e trace=epoll_wait,epoll_ctl,accept4 -p $(pgrep -f server) 2>&1 | head
printf 'hello' | nc 127.0.0.1 9000
# Go 运行时在 Linux 上使用 epoll：等事件、唤醒对应 goroutine，再执行 read/write
```

**与业务/后端的联系：**

- Netty 默认「主从 Reactor」：boss 线程只 accept，worker 线程处理读写；业务里的阻塞调用必须切到业务线程池，否则卡住 worker。
- Redis 单 Reactor 单线程的前提是「命令都是内存操作」；一旦有慢命令（大 key、`keys *`），整个实例卡住。
- Nginx 每个 worker 是独立 Reactor，进程间无共享，靠 `SO_REUSEPORT` 或共享 listen fd 分配连接。
- 高性能存储、代理开始用 `io_uring` 做 Proactor 式批处理，减少系统调用与拷贝；但内核版本、容器 seccomp 限制要提前确认。

**面试怎么答：** 先给一句话：Reactor 等「就绪」，Proactor 等「完成」。再讲 Reactor 的三种线程模型：单线程、单 reactor + 线程池、主从多 reactor，并各举一个代表（Redis、Netty、Nginx）。然后讲 Proactor 依赖内核异步能力，Linux 上传统 AIO 弱、`io_uring` 是补充。最后提醒：Reactor 里任何阻塞调用都会拖垮整个循环。

**易错点：**

- 把 Reactor 说成「异步 IO」；它是同步非阻塞 + 事件通知，拷贝仍由应用完成。
- 在 Reactor 线程里做数据库查询、文件读写等阻塞操作；这会卡住所有连接。
- 认为 Proactor 一定比 Reactor 快；`io_uring` 有提交/完成队列开销，低并发下未必占优。
- 忽略「半包/粘包」：Reactor 只保证可读，应用仍需自己处理消息边界与状态机。

## 11. 文件系统与 page cache

**`write` 成功只代表数据进了 page cache（内核页缓存），不代表落盘；真正的持久化要等回写线程把脏页写到磁盘，或用 `fsync` 强制等待。page cache 让读命中不碰磁盘、写合并成更大的 IO，是文件系统性能的核心；代价是内存被缓存占用、掉电可能丢最近写入、以及「RSS 没涨但 Cached 很大」的监控困惑。**

1. **VFS 抽象**：Linux 用 superblock（文件系统实例）、inode（文件元数据）、dentry（目录项缓存）、file（打开的文件）四类对象屏蔽 ext4/xfs/overlayfs 的差异。
2. **读路径**：`read` 先在 page cache 查页；命中直接拷贝到用户缓冲区；未命中触发缺页，从磁盘读入（可能触发 readahead 预读），再拷贝。
3. **写路径**：`write` 把用户数据拷到 page cache 对应页，标记 dirty，更新 inode 时间，然后返回；后台 flusher 按阈值与时间把脏页回写。
4. **回写参数**：`dirty_background_ratio` 默认 10%，达到后后台开始回写；`dirty_ratio` 默认 20%，达到后写进程被强制同步回写；`dirty_expire_centisecs` 默认 3000（30 秒），`dirty_writeback_centisecs` 默认 500（5 秒）。
5. **持久化语义**：`fsync` 等待文件数据与元数据落盘；`fdatasync` 只等数据（元数据中影响读取的部分仍需写）；`O_SYNC` 每次写都同步；`O_DIRECT` 绕过 page cache，直接对块设备读写，要求偏移与长度对齐。
6. **预读与回收**：readahead 默认按块设备的 `read_ahead_kb`（常见 128KB）预取后续页；内存紧张时 page cache 属于可回收页，优先被回收，不会直接触发 OOM。

**文件系统类型与容器：**

- ext4 是多数发行版的默认选择，带 journal（默认 `data=ordered`），元数据一致性靠日志恢复；xfs 更适合大文件与高并发写。
- overlayfs 把只读镜像层与可写层叠加，容器的每次写会触发 copy-up，第一次写大文件有明显延迟。
- tmpfs 把文件放在内存与 swap 中，`/dev/shm`、`/run` 都是 tmpfs；写入不落盘，重启即失。
- 网络文件系统（NFS/CephFS）的 `fsync` 语义与本地盘不同，延迟更高，数据库不应把数据目录放在上面。

| 概念 | 含义 | 观察方式 |
| --- | --- | --- |
| page cache | 文件数据的内存缓存 | `/proc/meminfo` 的 `Cached` |
| dirty page | 已修改但未回写的页 | `/proc/meminfo` 的 `Dirty` |
| writeback | 正在回写的页 | `/proc/meminfo` 的 `Writeback` |
| fsync | 强制等待落盘 | 系统调用耗时、`iostat` 的 `fdatasync/s` |
| O_DIRECT | 绕过 page cache | 应用自行管理对齐与缓存 |

**示例（对比 write 返回与真正落盘，Linux + Shell）：**

```bash
# 不带 fsync：write 只保证进了 page cache，命令很快返回
dd if=/dev/zero of=test.bin bs=1M count=256
# 带 fsync：等待数据真正写到磁盘，耗时明显变长
dd if=/dev/zero of=test2.bin bs=1M count=256 conv=fsync

cat /proc/meminfo | grep -E 'Cached|Dirty|Writeback'
# Cached:    很大（page cache）
# Dirty:     刚写完时上升，回写后下降
# Writeback: 正在回写的量

iostat -x 1 5          # 观察 %util、w/s、fdatasync/s
sync                   # 手动触发全部脏页回写
```

```bash
cat /proc/sys/vm/dirty_background_ratio    # 默认 10
cat /proc/sys/vm/dirty_ratio               # 默认 20
cat /proc/sys/vm/dirty_expire_centisecs    # 默认 3000
cat /sys/block/sda/queue/read_ahead_kb     # 预读大小
```

**与业务/后端的联系：**

- 数据库的 WAL 必须 `fsync` 才算提交；把 `fsync` 省掉能提升吞吐，但崩溃会丢最近事务，这是持久性与性能的直接取舍。
- Kafka 依赖 page cache 做「零拷贝 + 批量刷盘」，同时用 `flush` 策略控制丢数据窗口；不要既开 `fsync` 又逐条刷。
- 容器里 `Cached` 也被计入 memory cgroup，page cache 太多会挤压应用内存；可通过 `memory.high` 或主动 `posix_fadvise(DONTNEED)` 释放。
- 监控「内存泄漏」时先分清 anon RSS 与 page cache：`Cached` 可回收，`Anon` 才是应用真正持有的内存。

**面试怎么答：** 先讲 `write` 只写 page cache、`fsync` 才落盘，这是最容易被追问的点。再讲读写路径与回写阈值（10%/20%、30 秒）。然后讲 `O_DIRECT`、`fdatasync` 的差异与适用场景。最后补监控：`Cached` 不是泄漏，`Dirty` 高说明回写跟不上，`iostat` 的 `%util` 与 `fdatasync/s` 能定位磁盘瓶颈。

**易错点：**

- 认为 `write` 返回成功数据就安全落盘；掉电可能丢失 page cache 中的脏页。
- 用 `fsync` 的频率过高；每次提交都刷盘会让吞吐受限于磁盘 IOPS，应批量提交。
- 把 page cache 当成内存泄漏；它是可回收缓存，内存压力下会被释放。
- `echo 3 > /proc/sys/vm/drop_caches` 只丢干净页，不处理脏页；而且需要 root，生产环境慎用，会人为制造冷缓存。

## 12. 内存泄漏与 OOM Killer

**内存泄漏是「申请了但永远不再释放，且不再被使用」的内存；有 GC 的语言也会泄漏，因为 GC 只回收不可达对象，管不了「一直可达但无限增长」的集合、缓存与协程。OOM Killer 是内核在内存耗尽时的最后手段：按 `oom_score` 选一个进程杀掉，容器里则由 cgroup 的 `memory.max` 触发，进程通常收到 `SIGKILL`，退出码 137。**

1. **常见泄漏源**：全局 map/切片只增不减、缓存没有淘汰策略、goroutine/线程泄漏、`time.Ticker` 未 `Stop`、注册的回调未注销、连接/文件描述符未关闭、native 内存（JNI、CGO）未释放。
2. **确认是否泄漏**：观察 RSS/anon 是否持续上涨且 GC 后不回落；用 heap profile 看对象分布；用 `pmap`/`smem` 区分 anon、file、shared。
3. **Go 排查**：`pprof` 的 heap/goroutine profile，`runtime.ReadMemStats` 看 `HeapInuse`/`HeapReleased`，`GODEBUG=gctrace=1` 看 GC 后堆是否仍上涨；`GOMEMLIMIT`（Go 1.19+）给运行时设软上限。
4. **C/C++ 排查**：Valgrind `--leak-check=full`、ASan `-fsanitize=address`、`mtrace`；生产环境用 jemalloc 的 `stats.print` 或 `malloc_info`。
5. **OOM 选择**：`oom_score` 由进程实际占用（RSS + swap + 页表）计算，`oom_score_adj`（-1000 到 1000）可调整；分数最高者优先被杀，`-1000` 表示尽量不杀。
6. **容器 OOM**：cgroup v2 的 `memory.max` 触发 memcg OOM，`memory.oom.group=1` 会杀整个 cgroup；Kubernetes 里表现为 `OOMKilled`、退出码 137（128 + 9）。

| 工具 | 适用 | 能回答的问题 |
| --- | --- | --- |
| `ps`/`top` 的 RSS | 通用 | 哪个进程占用在涨 |
| `pmap`/`smaps` | 通用 | anon、file、shared 各占多少 |
| Go `pprof` heap | Go | 哪些类型/调用路径在涨 |
| Go `pprof` goroutine | Go | 协程是否泄漏、卡在哪 |
| Valgrind / ASan | C/C++ | 哪次分配没有释放 |
| `dmesg` | 系统 | 谁被 OOM Killer 杀了、当时内存多少 |

**排查顺序（从粗到细）：**

1. 看曲线：RSS/anon 是否单调上涨、GC 后是否回落；先排除 page cache 与分配器碎片。
2. 看构成：`pmap -x <pid>` 或 `/proc/<pid>/smaps_rollup` 区分 anon、file、shared、swap。
3. 看对象：Go 用 heap/goroutine profile，Java 用 `jcmd GC.heap_info` 与 heap dump，C/C++ 用 Valgrind/ASan。
4. 看系统：`dmesg` 确认是否 OOM，`/proc/<pid>/oom_score` 确认优先级，cgroup 的 `memory.events` 看 `oom` 计数。

**示例（Go 构造一个可复现的堆泄漏并抓取 profile，Go 1.21+）：**

```go
// go run leak.go
package main

import (
    "net/http"
    _ "net/http/pprof"
    "time"
)

var cache = map[int][]byte{}

func main() {
    go func() {
        for i := 0; ; i++ {
            cache[i] = make([]byte, 1<<20)   // 每秒 1MB，key 永不删除
            time.Sleep(time.Second)
        }
    }()
    http.ListenAndServe("127.0.0.1:6060", nil)
}
```

```bash
go tool pprof -http=:8080 http://127.0.0.1:6060/debug/pprof/heap
curl -s http://127.0.0.1:6060/debug/pprof/heap > heap.pprof
go tool pprof -top heap.pprof
GODEBUG=gctrace=1 go run leak.go     # 看 GC 后堆是否持续上涨
```

```bash
cat /proc/<pid>/status | grep -E 'VmRSS|VmSwap|VmSize'
cat /proc/<pid>/oom_score
cat /proc/<pid>/oom_score_adj
dmesg -T | grep -i -E 'out of memory|killed process'
# Out of memory: Killed process 12345 (java) total-vm:..., anon-rss:..., file-rss:...
```

**与业务/后端的联系：**

- 容器内存 limit 应略高于应用峰值并留出 page cache 余量；limit 太小会频繁 OOMKilled，太大则故障时影响同节点其他服务。
- Go 服务在容器里应设 `GOMEMLIMIT`（如 limit 的 80%），让 GC 更早回收；JVM 用 `-XX:MaxRAMPercentage` 让堆随容器 limit 缩放。
- 缓存必须有上限与淘汰策略（LRU/LFU/TTL）；「只加不删」的本地 map 是最常见的泄漏，压测时不容易暴露，跑几天才炸。
- OOM 排查要看「谁被杀」与「当时谁在涨」：被杀的往往不是泄漏者，而是占用最大的无辜进程，需要结合 `oom_score_adj` 与监控曲线定位。

**面试怎么答：** 先定义泄漏：不可达或可达但无限增长；强调 GC 语言也会泄漏。再给排查路径：RSS 曲线 → `pmap` 分 anon/file → heap profile/goroutine profile → 定位分配点。然后讲 OOM Killer：`oom_score` 由占用计算、`oom_score_adj` 可调、容器由 `memory.max` 触发、退出码 137。最后给治理手段：缓存限额、对象池、`GOMEMLIMIT`/`MaxRAMPercentage`、资源监控与告警。

**易错点：**

- 把 RSS 上涨一律当泄漏；page cache、分配器碎片、native 内存、线程栈都会让 RSS 涨。
- 认为 Go/Java 有 GC 就不会泄漏；全局集合、缓存、协程、`Ticker`、监听器注册都是典型泄漏点。
- 认为 OOM Killer 会杀「泄漏的那个进程」；它按 `oom_score` 选占用最大者，常常误伤正常服务。
- 把容器退出码 137 当成应用主动退出；137 = 128 + 9，表示被 `SIGKILL`，先查 `dmesg` 与 `OOMKilled` 事件。
