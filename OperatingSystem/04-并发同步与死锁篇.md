## 1. 竞态条件与临界区

**原理：** 竞态条件（race condition）指**程序的正确性依赖多个线程的执行时序**。只要同时满足三个条件就会出问题：存在共享状态、至少一个线程写、访问没有同步。临界区（critical section）是访问共享状态的那段代码，同步的本质就是让临界区串行执行。

`i++` 看起来是一条语句，编译后是三步：读内存到寄存器、寄存器加一、写回内存。两条指令流交错时就会出现丢失更新：

```text
线程 A: load  counter(0) → reg=0
线程 B: load  counter(0) → reg=0
线程 A: add   reg+1 → 1
线程 B: add   reg+1 → 1
线程 A: store 1 → counter=1
线程 B: store 1 → counter=1     预期是 2，实际是 1
```

```c
/* 共享计数器：无同步版本在有竞争时必然少计数 */
static int counter = 0;
static pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER;

void *worker_racy(void *arg) {
    for (int i = 0; i < 1000000; i++) {
        counter++;                       /* 读改写，非原子 */
    }
    return NULL;
}

void *worker_safe(void *arg) {
    for (int i = 0; i < 1000000; i++) {
        pthread_mutex_lock(&lock);
        counter++;
        pthread_mutex_unlock(&lock);
    }
    return NULL;
}
```

**典型并发场景：**

| 场景 | 竞态点 | 后果 |
| --- | --- | --- |
| 库存扣减 | 先查库存再减（check-then-act） | 超卖 |
| 单例初始化 | 判断为空再创建 | 创建两个实例 |
| 缓存更新 | 读未命中再回源写 | 旧值覆盖新值 |
| 文件写入 | 判断文件存在再创建 | 抛异常或覆盖他人内容 |
| 转账 | 读余额再加再写 | 金额丢失或凭空多出 |

**防护手段（按优先级）：**

1. **消除共享**：线程封闭（栈变量、`ThreadLocal`）、消息传递（channel、Actor），无共享就没有竞态。
2. **不可变化**：共享对象设为只读，用新对象替换旧对象。
3. **原子操作**：单变量读改写用 CAS 或原子指令（第 9 题）。
4. **加锁**：临界区必须包含**所有**对共享状态的访问，读也要锁（否则读到中间态）。
5. **事务**：数据库层用事务与行锁，把 check-then-act 合并成一条带条件的 `UPDATE`。

**怎么验证：**

```bash
# C/C++：ThreadSanitizer 能在运行期报告数据竞争（需要 -fsanitize=thread 编译）
gcc -fsanitize=thread -g -O1 counter.c -o counter -lpthread && ./counter

# Go：内置竞态检测器
go test -race ./...

# Java：用 jconsole 观察线程状态，或用 stress 工具放大交错窗口
for i in $(seq 1 100); do ./counter 8; done
```

**临界区设计的三个原则：**

| 原则 | 含义 | 反例 |
| --- | --- | --- |
| 互斥 | 任一时刻最多一个线程在临界区 | 只锁写不锁读 |
| 前进 | 没有线程在临界区时，想进入的线程应能尽快进入 | 用一把全局大锁把所有请求串行 |
| 有限等待 | 线程不能无限期被挡在临界区外 | 非公平锁配长任务 |

**读改写与原子性对照：**

```text
counter++       读 → 改 → 写，三步，非原子
counter = 5     单次写本身原子，但与判断组合成 check-then-act 就不安全
x = counter     单次读，32 位平台上读 64 位 long 仍可能读到撕裂值
```

**最小复现思路：** 8 个线程各自增 100 万次，无锁版本的结果几乎必然小于 800 万；加锁版本应精确等于 800 万。这个实验说明竞态不是「概率问题」，而是「必然问题」。

**面试怎么答：** 先给出「共享 + 并发 + 写」三要素，再举 `i++` 的汇编三步说明为什么单条语句也不安全，最后给防护手段的优先级：无共享 > 不可变 > 原子操作 > 加锁。

**易错点：** 只给写加锁、读不加锁仍然会读到撕裂的中间值；把 `volatile` 当成锁（它只保证可见性与有序性，不保证复合操作原子性）。

## 2. 互斥锁与自旋锁

**原理：** 两者都用于保证临界区互斥，区别在**拿不到锁时的行为**。

- **互斥锁（mutex）**：抢不到锁就进入阻塞态，让出 CPU，由操作系统在锁释放时唤醒。现代实现通常是「快路径 CAS 抢锁 + 慢路径 futex 睡眠」，无竞争时几乎没有系统调用开销。适合临界区长、竞争激烈的场景。
- **自旋锁（spinlock）**：抢不到锁就循环重试（忙等），线程始终占用 CPU。适合临界区极短（几十条指令）、多核环境；单核上自旋没有意义，因为持有者根本没机会被调度。

```c
/* 基于 atomic_flag 的自旋锁，test-and-test-and-set 写法减少总线流量 */
typedef struct {
    atomic_flag flag;
} spinlock_t;

void spin_lock(spinlock_t *s) {
    while (atomic_flag_test_and_set_explicit(&s->flag, memory_order_acquire)) {
        /* 已失败一次，改为只读探测，避免持续写缓存行 */
        while (atomic_load_explicit(&s->flag, memory_order_relaxed)) {
            __builtin_ia32_pause();          /* x86 提示超线程让出流水线 */
        }
    }
}

void spin_unlock(spinlock_t *s) {
    atomic_flag_clear_explicit(&s->flag, memory_order_release);
}
```

```c
/* 互斥锁：同样的临界区，竞争时线程睡眠，不浪费 CPU */
static pthread_mutex_t mtx = PTHREAD_MUTEX_INITIALIZER;

void critical_section(void) {
    pthread_mutex_lock(&mtx);
    /* 临界区：允许包含 IO、内存分配、可能阻塞的调用 */
    pthread_mutex_unlock(&mtx);
}
```

**对比：**

| 维度 | 互斥锁 | 自旋锁 |
| --- | --- | --- |
| 等待方式 | 阻塞睡眠，让出 CPU | 忙等，占用 CPU |
| 切换开销 | 两次上下文切换（微秒级） | 无切换，失败重试（纳秒级） |
| 适用临界区 | 长、可能阻塞 | 极短，绝不可阻塞 |
| 适用核数 | 单核、多核均可 | 仅多核 |
| 典型位置 | 用户态业务代码 | 内核中断上下文、驱动 |

**典型并发场景与坑：**

- **内核中断上下文不能用 mutex**：中断处理不能睡眠，只能用自旋锁；且持锁期间必须关本地中断（`spin_lock_irqsave`），否则中断重入会死锁。
- **优先级反转**：低优先级线程持锁、高优先级线程自旋等待，中优先级线程抢占 CPU，导致高优先级被无限拖住。解法是优先级继承（`PTHREAD_PRIO_INHERIT`）。
- **自旋锁内做 IO**：持锁线程被调度出去或等磁盘，其他核全部空转烧 CPU，`%sy` 飙升但吞吐下降。
- **锁粗化与细化**：临界区太小则锁开销占比高，太大则并发度低；常见做法是先粗后细，用压测确认收益。

**mutex 的快慢路径：**

```text
pthread_mutex_lock
    快路径：一条 CAS 把 state 从 0 改成 1，成功即返回，无系统调用
    慢路径：CAS 失败 → 进入 futex 等待队列 → 内核调度睡眠
pthread_mutex_unlock
    无等待者：一条 CAS 把 state 归零
    有等待者：futex_wake 唤醒一个，可能伴随一次上下文切换
```

**自旋锁的退避策略：**

| 策略 | 做法 | 适用 |
| --- | --- | --- |
| 纯自旋 | 持续 CAS | 临界区只有几条指令 |
| test-and-test-and-set | 先只读探测，减少缓存行争抢 | 通用 |
| pause / yield | 插入 `pause` 或 `sched_yield` | 超线程、稍长的临界区 |
| 自适应自旋 | 先自旋若干次，失败再阻塞 | JVM 轻量级锁膨胀 |

**面试怎么答：** 一句话点出「阻塞等待 vs 忙等」的本质差异，再给选择依据（临界区长度、核数、是否可阻塞），最后补「自旋锁不能嵌套、持锁不能睡眠」。

**易错点：** 认为自旋锁一定更快——无竞争时确实更快，但竞争激烈时自旋会浪费大量 CPU；自旋锁不是可重入锁，同一线程重复加锁会永久自旋。

## 3. 读写锁与乐观锁

**原理：**

- **读写锁**：同一时刻允许多个读者并发，写者独占。核心是区分「共享访问」与「排他访问」，适合读多写少。代价是内部维护读者计数，实现比 mutex 复杂、开销更大，临界区极短时反而更慢。
- **乐观锁**：假设冲突很少，不加锁直接操作，在**提交时**校验数据是否被别人改过（版本号、时间戳或 CAS）。冲突则重试或失败返回。适合冲突率低的场景；冲突率高时大量重试会退化得比悲观锁更差。

```c
/* 读写锁：读并发、写独占 */
static pthread_rwlock_t rw = PTHREAD_RWLOCK_INITIALIZER;

void *reader(void *arg) {
    pthread_rwlock_rdlock(&rw);
    read_config();                       /* 多个读者可同时进入 */
    pthread_rwlock_unlock(&rw);
    return NULL;
}

void *writer(void *arg) {
    pthread_rwlock_wrlock(&rw);
    update_config();                     /* 写者独占 */
    pthread_rwlock_unlock(&rw);
    return NULL;
}
```

```sql
-- 乐观锁：版本号校验，冲突时 affected rows 为 0
UPDATE stock
   SET quantity = quantity - 1, version = version + 1
 WHERE id = 1001
   AND version = 5
   AND quantity >= 1;

-- 悲观锁：先锁行再操作，适合冲突率高的扣减
SELECT quantity FROM stock WHERE id = 1001 FOR UPDATE;
```

**典型并发场景：**

| 场景 | 选型 | 理由 |
| --- | --- | --- |
| 配置读多写极少 | 读写锁 / 不可变对象 | 读者并发，写者极少阻塞 |
| 商品详情缓存 | 读写锁 | 命中读多，回源写少 |
| 库存扣减 | 悲观锁或数据库条件更新 | 冲突率高，乐观锁重试成本大 |
| 用户资料更新 | 乐观锁（版本号） | 同一用户并发编辑概率低 |
| 秒杀库存 | 预扣减 + 消息队列串行 | 彻底消除热点行竞争 |

**三种并发控制对比：**

| 方案 | 何时加锁 | 冲突代价 | 适用 |
| --- | --- | --- | --- |
| 悲观锁 | 访问前加锁 | 阻塞等待 | 冲突率高、临界区长 |
| 乐观锁 | 提交时校验 | 重试或失败返回 | 冲突率低、读多写少 |
| 无锁（CAS） | 不加锁，靠原子指令 | 自旋重试 | 单变量、临界区极短 |

**读写锁的适用性判断：** 读临界区要足够长（如毫秒级的复杂计算），读者计数的开销才划算；如果读只是取一个字段，mutex 甚至原子读更快。

**读写锁的三个坑：**

1. **写饥饿**：读优先实现下，源源不断的读者会让写者永远等不到。`pthread_rwlockattr_setkind_np` 可设 `PTHREAD_RWLOCK_PREFER_WRITER_NONRECURSIVE_NP`，但读者递归加锁会死锁。
2. **锁升级会死锁**：持有读锁再申请写锁，两个读者同时升级就互相等待。标准库不提供升级，正确做法是释放读锁再申请写锁，或改用 mutex 保护「读-判断-写」整体。
3. **锁降级可行**：持写锁时再取读锁，然后释放写锁，是允许的（写者唯一，不会与他人互等）。

**乐观锁的 ABA 与重试：**

- 版本号只能发现「改过」，发现不了「改回原值」，但对业务通常足够；无锁数据结构里需要 `AtomicStampedReference` 这类带标记的方案。
- 重试要设上限并加退避，否则高冲突时会形成活锁（见第 8 题）。
- 乐观锁不是「无锁」：它仍需要数据库或 CAS 提供原子提交语义。

**面试怎么答：** 先讲读写锁的「共享读、排他写」和适用条件，再讲乐观锁的「提交时校验」，最后给选型依据：读多写少且临界区长用读写锁，冲突率低用乐观锁，冲突率高用悲观锁。

**易错点：** 在读锁内修改共享数据（读者之间并不互斥，等于没锁）；认为读写锁一定比 mutex 快，实际小临界区下 mutex 更快。

## 4. 信号量与条件变量

**原理：**

- **信号量（semaphore）**：一个带原子计数的整数，`P`（wait）减一，计数为 0 时阻塞；`V`（post）加一，唤醒等待者。计数大于 1 时可用于**限流**（控制并发数），也可用于生产者消费者。二元信号量能当互斥锁用，但它没有「所有权」概念，允许一个线程 wait、另一个线程 post。
- **条件变量（condition variable）**：本身不保存状态，只提供「等待某个条件成立」的能力，必须与一把 mutex 配合。`wait` 会原子地释放锁并睡眠，被唤醒后重新加锁返回；因此**判断条件必须放在 while 循环里**，以应对虚假唤醒与条件再次失效。

```c
/* 有界缓冲区：条件变量 + mutex 的标准写法 */
#define CAP 8
static int buf[CAP];
static int head = 0, tail = 0, count = 0;
static pthread_mutex_t mtx = PTHREAD_MUTEX_INITIALIZER;
static pthread_cond_t not_empty = PTHREAD_COND_INITIALIZER;
static pthread_cond_t not_full = PTHREAD_COND_INITIALIZER;

void put(int v) {
    pthread_mutex_lock(&mtx);
    while (count == CAP) {                       /* 必须 while，不是 if */
        pthread_cond_wait(&not_full, &mtx);      /* 原子释放锁并睡眠 */
    }
    buf[tail] = v;
    tail = (tail + 1) % CAP;
    count++;
    pthread_cond_signal(&not_empty);             /* 唤醒一个消费者 */
    pthread_mutex_unlock(&mtx);
}

int get(void) {
    int v;
    pthread_mutex_lock(&mtx);
    while (count == 0) {
        pthread_cond_wait(&not_empty, &mtx);
    }
    v = buf[head];
    head = (head + 1) % CAP;
    count--;
    pthread_cond_signal(&not_full);
    pthread_mutex_unlock(&mtx);
    return v;
}
```

```c
/* 信号量做并发限流：同时最多 4 个任务访问下游 */
static sem_t slots;

void init_limit(void) {
    sem_init(&slots, 0, 4);                      /* 第二个参数 0 表示线程间共享 */
}

void call_downstream(void) {
    sem_wait(&slots);
    do_request();
    sem_post(&slots);
}
```

**典型并发场景与坑：**

- **丢失唤醒**：生产者先 `signal` 后消费者才 `wait`，信号会丢失。条件变量不保存状态，必须用共享变量（`count`）作为谓词，且在锁内检查。
- **虚假唤醒**：POSIX 允许 `wait` 无故返回，`if` 判断会让消费者在缓冲区仍空时继续执行，导致越界读。
- **信号量计数泄漏**：异常路径漏掉 `post`，计数永久减一，最终所有线程阻塞；用 RAII 或 `try/finally` 保证配对。
- **惊群**：`pthread_cond_broadcast` 唤醒全部等待者，只有一个能推进，其余重新睡眠；只在需要唤醒多个（如状态整体变化）时用 `broadcast`。
- **持锁做耗时操作**：`signal` 前后持锁执行慢操作会放大等待时间，正确做法是先在锁内改状态，再在锁外做实际工作。

**条件变量与信号量对比：**

| 维度 | 条件变量 | 信号量 |
| --- | --- | --- |
| 是否保存状态 | 不保存，必须配共享谓词 | 保存计数 |
| 是否绑定锁 | 必须与 mutex 配合 | 独立使用 |
| 唤醒是否会丢失 | 会（先 signal 后 wait） | 不会（计数已加） |
| 典型用途 | 等待「某个状态成立」 | 限流、生产者消费者计数 |

```c
/* 限流也可以带超时，避免下游故障时无限堆积 */
struct timespec ts;
clock_gettime(CLOCK_REALTIME, &ts);
ts.tv_sec += 3;
if (sem_timedwait(&slots, &ts) != 0) {
    return TIMEOUT;                      /* 超时后要重新检查业务状态，不能直接当失败 */
}
```

**面试怎么答：** 条件变量回答三个关键词——「必须配 mutex」「wait 原子释放锁」「while 循环防虚假唤醒」；信号量回答「计数、P/V、可用于限流」，并点出「信号量保存状态，条件变量不保存状态」。

**易错点：** 用条件变量当计数器（它不存值，睡了就错过）；先 `signal` 再改状态（唤醒者看到旧状态又睡回去）。

## 5. 死锁的四个必要条件

**原理：** 死锁是多个进程/线程互相持有对方需要的资源并永久等待。Coffman 条件四个同时成立才会死锁：

1. **互斥**：资源同一时刻只能被一个持有者占用。
2. **占有并等待**：持有至少一个资源，同时等待其他被占用的资源。
3. **不可抢占**：资源只能由持有者主动释放，不能被强行剥夺。
4. **循环等待**：存在一个等待环 `T1 → T2 → ... → Tn → T1`。

四个条件是**必要条件**而非充分条件：全部满足也可能不死锁（比如等待环之外还有资源可用），但破坏任意一个就能消除死锁。

```c
/* 最经典的死锁：两个线程以相反顺序获取同一组锁 */
static pthread_mutex_t lock_a = PTHREAD_MUTEX_INITIALIZER;
static pthread_mutex_t lock_b = PTHREAD_MUTEX_INITIALIZER;

void *thread_ab(void *arg) {
    pthread_mutex_lock(&lock_a);
    usleep(10000);                     /* 放大交错窗口，真实场景由调度或 IO 造成 */
    pthread_mutex_lock(&lock_b);       /* 等 B，而 B 在等 A */
    /* 临界区 */
    pthread_mutex_unlock(&lock_b);
    pthread_mutex_unlock(&lock_a);
    return NULL;
}

void *thread_ba(void *arg) {
    pthread_mutex_lock(&lock_b);
    usleep(10000);
    pthread_mutex_lock(&lock_a);
    /* 临界区 */
    pthread_mutex_unlock(&lock_a);
    pthread_mutex_unlock(&lock_b);
    return NULL;
}
```

**典型死锁场景：**

| 场景 | 环的形成方式 |
| --- | --- |
| 转账 | 事务 1 锁 A 再锁 B，事务 2 锁 B 再锁 A |
| 数据库事务 | 两条 `UPDATE` 语句更新多行的顺序不一致 |
| 连接池 | 线程持有一个连接再申请第二个，池已耗尽 |
| 嵌套锁 | 锁 A 的回调里申请锁 B，另一路径反向 |
| 文件锁 | 两个进程以不同顺序 `flock` 两个文件 |
| 协程/通道 | 两个 goroutine 互相等待对方先发消息 |

**最小复现与验证：**

```bash
# 死锁发生后进程不会退出，用 gdb 看两个线程各自停在哪把锁上
gdb -p <PID> -batch -ex 'thread apply all bt' | grep -E 'Thread|pthread_mutex_lock'

# 用 strace 观察 futex 调用长期不返回，也是一种信号
strace -f -p <PID> -e trace=futex | head -n 20
```

**四个条件与常见误解：**

- 单线程重复加同一把非递归锁，是**自我死锁**，不构成循环等待，但仍会永久阻塞。
- 两个线程等待同一把锁不构成环，只会让其中一个排队，最终仍能推进。
- 循环等待是四个条件中最容易在工程上破坏的一个，因此「全局锁序」是最常用的预防手段。

**定位信号：**

```bash
# Java：JVM 自己会检测并打印 Found one Java-level deadlock
jstack -l <PID> | grep -A 30 'Found one Java-level deadlock'

# C/C++：用 gdb 挂上去看所有线程栈，找同时停在 pthread_mutex_lock 的线程
gdb -p <PID> -batch -ex 'thread apply all bt' | grep -B 2 pthread_mutex_lock

# Go：运行时检测到全部 goroutine 睡眠时直接 panic
# fatal error: all goroutines are asleep - deadlock!
```

**面试怎么答：** 先完整背出四个条件，再举「反序加锁」的最小复现例子，最后点明「四个条件是必要不充分」，以及「破坏任一条件即可预防」。

**易错点：** 认为满足四个条件就一定死锁；把「等待同一个锁」当成循环等待（单把锁只会饿死，不会形成环）。

## 6. 死锁的检测与恢复

**原理：** 不做任何预防时，系统允许死锁发生，靠**检测 + 恢复**兜底。

- **单实例资源**（每类资源只有一个）：维护**等待图**（wait-for graph），节点是进程，边 `Ti → Tj` 表示 `Ti` 等待 `Tj` 持有的资源。图中出现环即死锁，检测复杂度 `O(V + E)`。
- **多实例资源**：等待图不再充分，需要类似银行家算法的矩阵检测，判断是否存在一个无法完成的进程集合。
- **工程手段**：锁超时（`pthread_mutex_timedlock`、`tryLock(timeout)`）、看门狗定时扫描、请求超时后回滚。

```text
# 等待图环检测（DFS 三色标记）
detect_cycle(wait_for):
    color = {node: WHITE}                  # WHITE 未访问，GRAY 在栈上，BLACK 已完成
    for u in nodes:
        if color[u] == WHITE and dfs(u, color, wait_for) != NONE:
            return "deadlock"
    return "ok"

dfs(u, color, wait_for):
    color[u] = GRAY
    for v in wait_for[u]:
        if color[v] == GRAY:               # 指向当前递归栈上的节点，成环
            return v
        if color[v] == WHITE and dfs(v, color, wait_for) != NONE:
            return v
    color[u] = BLACK
    return NONE
```

**恢复手段：**

| 手段 | 做法 | 代价 |
| --- | --- | --- |
| 全部终止 | 杀掉环上所有进程 | 计算成果全部丢失 |
| 逐个终止 | 每次杀一个并重新检测，直到无环 | 需要可重启、可回滚 |
| 资源抢占 | 剥夺资源并回滚到检查点 | 需要检查点机制，实现复杂 |
| 超时放弃 | 等锁超时后释放已持有的锁并重试 | 可能反复失败，需退避 |
| 人工介入 | 保留现场，dump 栈后重启 | 有服务中断 |

**检测方式对比：**

| 方式 | 原理 | 开销 | 适用 |
| --- | --- | --- | --- |
| 等待图环检测 | DFS 找环 | 每次 O(V+E) | 单实例资源、低频巡检 |
| 矩阵检测 | 类似银行家安全性检查 | O(n²m) | 多实例资源 |
| 锁超时 | 等待超过阈值即失败 | 无额外开销 | 应用层最常用 |
| 看门狗 | 定时检查任务是否有进展 | 低 | 批处理、长任务 |

**恢复时的顺序：**

1. 先冻结现场（dump 线程栈、保存日志），否则重启后无法定位根因。
2. 选择代价最小的牺牲者（事务小、可重试、无副作用）。
3. 释放其持有的资源并回滚，重新检测是否还有环。
4. 重试要带退避与限次，避免立刻再次死锁形成活锁。

```bash
# Java：导出线程栈后离线分析，避免只看到「卡住」而不知道卡在哪
jstack -l <PID> > /tmp/jstack_$(date +%s).txt
grep -c 'java.lang.Thread.State: BLOCKED' /tmp/jstack_*.txt
```

**生产实践：**

- 数据库（如 InnoDB）会定期做等待图检测，选中「代价最小」的事务回滚，所以业务方看到的是 `Deadlock found when trying to get lock; try restarting transaction`，正确做法是**捕获后整事务重试**。
- 应用层更实用的是「锁超时 + 重试」而不是精确检测：`tryLock(3, TimeUnit.SECONDS)` 失败就放弃并告警，把死锁转化为可观测的超时。
- 检测本身有开销，不能每一步都做；通常是低频巡检（如每分钟）或只在请求超时后触发现场 dump。

**面试怎么答：** 单实例讲等待图 + DFS 找环，多实例讲矩阵检测；恢复讲「终止、抢占、回滚、超时」四类，最后落到生产：「与其精确检测，不如用超时与重试把死锁降级成失败」。

**易错点：** 死锁恢复要与幂等性配合，回滚后重试可能重复扣款；只在环上杀一个进程并不能保证解除死锁，需要重新检测。

## 7. 死锁预防与避免（银行家算法）

**原理：** 两个层次：

- **预防（prevention）**：静态地破坏四个必要条件之一，从结构上让死锁不可能发生。
- **避免（avoidance）**：允许四个条件存在，但每次分配前判断「分配后系统是否仍处于安全状态」，不安全就拒绝或推迟分配。银行家算法是典型代表，它要求每个进程**预先声明最大资源需求**。

**破坏四个条件的手段：**

| 条件 | 破坏方式 | 工程做法 |
| --- | --- | --- |
| 互斥 | 资源可共享 | 只读副本、写时复制 |
| 占有并等待 | 一次性申请全部资源 | 启动时预分配；或申请新锁前先释放已有锁 |
| 不可抢占 | 允许抢占 | `trylock` 失败就释放已持有的锁并回退重试 |
| 循环等待 | 全局锁序 | 所有代码按同一顺序加锁；资源编号后按序申请 |

```text
# 银行家算法：安全性检查
n = 进程数, m = 资源种类数
Available[m]        当前可用
Max[n][m]           每个进程声明的最大需求
Allocation[n][m]    已分配
Need[n][m] = Max - Allocation

safe_check():
    Work = copy(Available)
    Finish = [false] * n
    safe_seq = []
    while 存在 i 满足 Finish[i] == false 且 Need[i] <= Work:
        Work = Work + Allocation[i]      # 该进程能跑完并归还资源
        Finish[i] = true
        safe_seq.append(i)
    if all(Finish):
        return SAFE, safe_seq
    return UNSAFE, None

request(i, req[m]):
    if req > Need[i]: return ERROR                  # 超出声明，拒绝
    if req > Available: return WAIT                 # 暂时不够，等待
    试探性分配：Available -= req, Allocation[i] += req, Need[i] -= req
    if safe_check() == SAFE:
        return GRANT
    else:
        回滚试探性分配
        return WAIT                                 # 会让系统进入不安全状态
```

**典型并发场景：**

- 银行家算法需要预先知道最大需求，通用业务系统无法提供，实际几乎不用，只在操作系统课程与特定调度器中出现。
- 工程上真正落地的是**全局锁序**：给所有锁编号（如按资源 ID 升序），任何路径都按序加锁，循环等待在结构上不可能出现。
- 「一次性申请」在分布式场景等价于「按固定顺序批量获取」，比如批量转账先按账户 ID 排序再逐个加锁。
- `trylock` + 超时是把「不可抢占」变成「可放弃」，代价是需要可回滚的业务设计。

**全局锁序的落地写法：**

```c
/* 给每个资源一个单调递增的 id，任何路径都按 id 升序加锁 */
static void lock_two(pthread_mutex_t *m1, int id1, pthread_mutex_t *m2, int id2) {
    if (id1 < id2) {
        pthread_mutex_lock(m1);
        pthread_mutex_lock(m2);
    } else {
        pthread_mutex_lock(m2);
        pthread_mutex_lock(m1);
    }
}
```

锁序必须写进文档与代码规范，并在评审中用静态检查兜住；只要有一条路径反序加锁，循环等待就又可能出现。

**面试怎么答：** 先说预防的四条对应关系，再讲银行家算法的「安全状态」定义与 `Need <= Work` 的判定，最后补一句「工程上主要用锁序与超时，银行家算法因需预知最大需求而少用」。

**易错点：** 把「安全状态」等同于「不会死锁」——安全状态一定不死锁，不安全状态只是**可能**死锁；锁序方案必须全代码统一，遗漏一处反向加锁就前功尽弃。

## 8. 活锁与饥饿

**原理：**

- **活锁（livelock）**：线程没有被阻塞，一直在执行动作，但系统状态无法推进。典型是「互相谦让」或「冲突后一起重试」。
- **饥饿（starvation）**：某个线程长期拿不到资源，虽然资源一直在被别人使用。典型是不公平锁、优先级过低、读写锁的写者饥饿、短任务不断插队。

区别：死锁是静态等待，活锁是动态空转（CPU 高但无进展），饥饿是「有人一直在前进，只是轮不到我」。

```c
/* 活锁：两个线程都检测到冲突就释放并重试，结果同时让路又同时重试 */
void *polite_worker(void *arg) {
    while (1) {
        pthread_mutex_lock(&lock_a);
        if (pthread_mutex_trylock(&lock_b) != 0) {
            pthread_mutex_unlock(&lock_a);       /* 谦让：先放开，等对方也让 */
            continue;                            /* 立即重试，节奏与对方同步 */
        }
        /* 临界区 */
        pthread_mutex_unlock(&lock_b);
        pthread_mutex_unlock(&lock_a);
        break;
    }
    return NULL;
}

/* 打破活锁：随机退避，让双方的重试节奏错开 */
void *worker_with_backoff(void *arg) {
    unsigned seed = (unsigned)time(NULL) ^ (unsigned)pthread_self();
    while (1) {
        pthread_mutex_lock(&lock_a);
        if (pthread_mutex_trylock(&lock_b) == 0) {
            /* 临界区 */
            pthread_mutex_unlock(&lock_b);
            pthread_mutex_unlock(&lock_a);
            break;
        }
        pthread_mutex_unlock(&lock_a);
        usleep(rand_r(&seed) % 1000);            /* 0~1ms 随机退避 */
    }
    return NULL;
}
```

**典型并发场景：**

| 现象 | 类型 | 处理 |
| --- | --- | --- |
| 两个事务反复回滚重试，CPU 很高但订单一直不成功 | 活锁 | 随机退避 + 限次 + 按 ID 排序加锁 |
| 高冲突下 CAS 自旋一直失败 | 活锁 | 退避、分段计数（LongAdder）、改用锁 |
| 消息重发碰撞，两台机器同时重试 | 活锁 | 幂等 + 分布式锁 + 抖动 |
| 低优先级线程长期拿不到 CPU | 饥饿 | 提高优先级或公平调度 |
| 读写锁下写者永远等不到 | 饥饿 | 写优先的读写锁或分段 |
| 固定线程池 + 无界队列，短任务不断插队 | 饥饿 | 公平队列、按优先级分池 |

**判定方法：**

```bash
# 活锁：线程状态是 RUNNABLE，CPU 高，但业务指标（成功率、队列长度）不改善
top -H -p <PID>
jstack <PID> | grep -A 5 'java.lang.Thread.State: RUNNABLE'

# 饥饿：线程长期处于 BLOCKED/WAITING，且等待时间单调增长
jstack <PID> | grep -c 'java.lang.Thread.State: BLOCKED'
```

**饥饿的常见来源与解法：**

| 来源 | 表现 | 解法 |
| --- | --- | --- |
| 非公平锁 | 后来的线程反复插队 | 公平锁（FIFO 队列），代价是吞吐下降 |
| 优先级固定 | 低优先级长期得不到 CPU | 优先级老化，等待越久优先级越高 |
| 读写锁读优先 | 写者永远排队 | 写优先的读写锁或读写分段 |
| 线程池任务插队 | 长任务永远排不上 | 公平队列、优先级队列、任务分池 |

```java
// 公平锁：按等待顺序授予，避免饥饿，但每次唤醒都有额外调度成本
ReentrantLock fairLock = new ReentrantLock(true);
fairLock.lock();
try {
    // 临界区
} finally {
    fairLock.unlock();
}
```

**面试怎么答：** 先把三者区分开（死锁静止、活锁空转、饥饿不公），再给活锁的解法「打破对称性：随机退避或固定顺序」，给饥饿的解法「公平性：FIFO 锁、优先级老化、配额」。

**易错点：** 把活锁当死锁去重启进程，重启后很快复现；用 `synchronized` 时默认是非公平锁，高并发下低优先级线程可能长期饥饿。

## 9. CAS 与原子操作

**原理：** CAS（Compare-And-Swap）是一条 CPU 原子指令（x86 的 `cmpxchg` 配合 `lock` 前缀，ARM 的 `LDREXR/STREXR` 循环），语义是「如果内存值等于期望值，就写入新值，否则返回失败并告诉调用方当前值」。它把「读-比较-写」三步合成一个不可分割的操作，是无锁算法的基础。

```java
/* Java：AtomicInteger 的自增就是 CAS 重试循环 */
public final int incrementAndGet() {
    for (;;) {
        int current = get();
        int next = current + 1;
        if (compareAndSet(current, next)) {      /* 底层是 cmpxchg */
            return next;
        }
        /* 失败说明被别人改过，重新读取后重试 */
    }
}
```

```c
/* C11 原子操作：weak 版本允许伪失败，适合放在循环里 */
int cas_increment(atomic_int *v) {
    int expected = atomic_load(v);
    while (!atomic_compare_exchange_weak(v, &expected, expected + 1)) {
        /* 失败时 expected 已被硬件刷新为最新值，可直接重试 */
    }
    return expected + 1;
}
```

**ABA 问题：** 线程 1 读到 `A`，线程 2 把 `A` 改成 `B` 又改回 `A`，线程 1 的 CAS 仍然成功，但它基于的假设（「没人动过」）已被破坏。在计数器上无害，在无锁栈/链表上会导致节点被重复释放或数据丢失。

```c
/* 带版本号的 CAS：把「值 + 版本」打包成一个 64 位字，或用 hazard pointer 管理回收 */
typedef struct {
    uint32_t value;
    uint32_t version;
} versioned_t;
```

**典型并发场景：**

- **计数器**：`AtomicLong` 高并发下 CAS 失败率上升，JDK 8 引入 `LongAdder` 分段累加，吞吐显著提升。
- **状态机**：用 CAS 做 `RUNNING → STOPPING` 的单向状态迁移，失败即说明别人已改，直接返回。
- **无锁栈**：`push` 用 CAS 换 `top`，必须解决 ABA 与内存回收（hazard pointer、epoch、引用计数）。
- **单次初始化**：`AtomicBoolean.compareAndSet(false, true)` 保证只有一个线程执行初始化。
- **复合操作**：`check-then-act`（如「不存在则插入」）单靠 CAS 无法完成，需要 `ConcurrentHashMap.putIfAbsent` 这类整体原子 API。

**性能与坑：**

| 坑 | 说明 |
| --- | --- |
| 高竞争退化 | 大量线程同时 CAS 同一变量，失败重试会形成活锁，吞吐反而不如锁 |
| 伪共享 | 多个原子变量落在同一缓存行（64 字节），互相失效缓存，用 `@Contended` 或填充对齐 |
| 只保证单变量 | 两个变量的更新不是原子的，需要整体打包或加锁 |
| 内存序默认最强 | Java 的 `compareAndSet` 是 `volatile` 语义，C 的 `memory_order_seq_cst` 开销最大，可按需降级 |

**原子类与适用边界：**

| 工具 | 保证 | 不保证 |
| --- | --- | --- |
| `AtomicInteger` | 单变量读改写原子 | 多变量组合原子 |
| `LongAdder` | 高并发计数吞吐 | 精确的即时快照（`sum()` 非原子） |
| `AtomicReference` | 引用替换原子 | 对象内部字段的并发修改 |
| `compareAndSet` | 一次比较并交换 | 后续业务逻辑的原子性 |

高并发计数优先 `LongAdder`：它把累加分散到多个 Cell，读取时求和，牺牲实时精确性换取吞吐。

**CAS 的三个语义层次：**

```text
原子性：单条指令不可分割，不会看到中间状态
可见性：成功写入后，其他线程的后续读取能看到新值
有序性：CAS 本身是 full barrier，前后操作不会被重排
```

**面试怎么答：** 先讲 CAS 的语义与硬件指令，再讲「无锁 = 循环 CAS + 失败重试」，然后主动提 ABA、高竞争退化、伪共享三个坑，最后给替代方案（分段、`LongAdder`、必要时回到锁）。

**易错点：** 认为无锁一定比锁快（低竞争才快，高竞争更慢）；用 CAS 实现「读两个字段再一起更新」，中间仍可能被插入。

## 10. 内存屏障与可见性

**原理：** 一个线程写的值，另一个线程不一定马上能看到，原因有三层：

1. **编译器重排**：编译器在不改变单线程语义的前提下调整指令顺序。
2. **CPU 乱序执行**：处理器可以乱序执行，只要最终结果符合单线程语义。
3. **存储缓冲与缓存**：写先进入 store buffer，尚未刷到缓存/内存；不同核心的缓存通过 MESI 协议同步，存在时间差。

内存屏障（memory barrier/fence）就是告诉编译器和 CPU「这条线前后的内存操作不能越过」。四种基本类型：

| 屏障 | 约束 |
| --- | --- |
| `LoadLoad` | 前面的读先于后面的读完成 |
| `StoreStore` | 前面的写先于后面的写完成 |
| `LoadStore` | 前面的读先于后面的写完成 |
| `StoreLoad` | 前面的写对后续读可见（最重，通常伴随刷新 store buffer） |

**语言层的对应：**

- Java 的 `volatile`：写操作前插 `StoreStore`、后插 `StoreLoad`；读操作后插 `LoadLoad`/`LoadStore`。它保证可见性与有序性，但**不保证复合操作原子性**。
- C++ 的 `memory_order`：`relaxed`（只保证原子性）、`acquire`（读后不能重排到读前）、`release`（写前不能重排到写后）、`acq_rel`、`seq_cst`（全局单一顺序，最贵）。

```java
/* 双重检查锁：没有 volatile 时，构造函数的写可能被重排到引用赋值之前，
   其他线程会看到「非空但未初始化完成」的对象 */
public class Singleton {
    private static volatile Singleton instance;

    public static Singleton getInstance() {
        if (instance == null) {
            synchronized (Singleton.class) {
                if (instance == null) {
                    instance = new Singleton();   /* 分配、初始化、赋值三步可能重排 */
                }
            }
        }
        return instance;
    }
}
```

```cpp
/* 生产者-消费者：release/acquire 配对，保证 data 的写在 ready 之前可见 */
std::atomic<bool> ready{false};
int data = 0;

void producer() {
    data = 42;
    ready.store(true, std::memory_order_release);   /* 之前的写不能跑到 store 之后 */
}

void consumer() {
    while (!ready.load(std::memory_order_acquire)) {
        /* 自旋等待 */
    }
    assert(data == 42);                             /* acquire 保证能看到 42 */
}
```

**典型并发场景：**

- **双重检查锁**：JDK 5 之前 `volatile` 语义不完整，DCL 是著名错误写法；现在必须写 `volatile`。
- **标志位控制循环**：`while (!stop)` 中 `stop` 不加 `volatile`，JIT 可能把它优化成死循环。
- **无锁队列**：入队用 `release` 发布节点，出队用 `acquire` 读取，缺一不可（第 11 题）。
- **x86 的错觉**：x86 是强内存模型，`LoadLoad`/`StoreStore` 基本不需要，但 `StoreLoad` 仍需 `mfence` 或 `lock` 指令，不能想当然地「x86 不用管」。

**硬件与语言的对应：**

| 语义 | x86 指令 | ARM 指令 | Java / C++ |
| --- | --- | --- | --- |
| LoadLoad | 天然有序（少数情况除外） | `dmb ishld` | `acquire` 读 |
| StoreStore | 天然有序 | `dmb ishst` | `release` 写 |
| LoadStore | 天然有序 | `dmb ish` | `acquire` |
| StoreLoad | `mfence` 或 `lock addl` | `dmb ish` | `volatile` 写、`seq_cst` |

**happens-before 的几条实用规则：**

- 程序顺序：同一线程内，前面的操作先行于后面的操作。
- 监视器锁：解锁先行于后续对同一把锁的加锁。
- `volatile`：对同一变量的写先行于后续的读。
- 线程启动：`Thread.start()` 先行于该线程内的所有操作。
- 传递性：A 先行于 B、B 先行于 C，则 A 先行于 C。

**面试怎么答：** 从「为什么看不到」的三层原因讲起，再给四种屏障与 `volatile`/`memory_order` 的对应关系，最后用 DCL 或生产者消费者举例说明「没有屏障会看到什么错误现象」。

**易错点：** 认为 `volatile` 能保证 `i++` 原子（它只保证每次读写直达内存）；认为加了 `volatile` 就不需要锁——多线程复合操作仍然需要。

## 11. 无锁队列

**原理：** 无锁队列用原子操作与内存序维护队头/队尾指针，避免线程阻塞。按生产者/消费者数量分四类，实现难度依次上升：

| 类型 | 典型实现 | 关键点 |
| --- | --- | --- |
| SPSC（单生产单消费） | 环形数组 + head/tail | 最简单，只需 acquire/release |
| MPSC（多生产单消费） | Michael-Scott 变体 | 入队 CAS 换 tail，需要处理中间态 |
| SPMC | 环形数组 + 原子计数 | 消费者竞争同一位置 |
| MPMC | Michael-Scott 队列 | 需要 ABA 与安全回收（hazard pointer） |

```cpp
/* SPSC 环形队列：容量必须是 2 的幂，head/tail 分居不同缓存行避免伪共享 */
template <typename T, size_t N>
class SpscQueue {
    static_assert((N & (N - 1)) == 0, "capacity must be power of two");
public:
    bool push(const T &v) {
        size_t head = head_.load(std::memory_order_relaxed);
        size_t next = (head + 1) & (N - 1);
        if (next == tail_.load(std::memory_order_acquire)) {
            return false;                              /* 队列已满 */
        }
        buf_[head] = v;                                /* 先写数据 */
        head_.store(next, std::memory_order_release);  /* 再发布 head */
        return true;
    }

    bool pop(T &v) {
        size_t tail = tail_.load(std::memory_order_relaxed);
        if (tail == head_.load(std::memory_order_acquire)) {
            return false;                              /* 队列为空 */
        }
        v = buf_[tail];                                /* 先读数据 */
        tail_.store((tail + 1) & (N - 1), std::memory_order_release);
        return true;
    }

private:
    T buf_[N];
    alignas(64) std::atomic<size_t> head_{0};          /* 与 tail 分开缓存行 */
    alignas(64) std::atomic<size_t> tail_{0};
};
```

```text
# Michael-Scott 队列入队（多生产者），核心是 CAS 推进 tail
enqueue(node):
    while true:
        tail = T.load(acquire)
        next = tail.next.load(acquire)
        if next == NULL:
            if CAS(tail.next, NULL, node):     # 先挂到链尾
                CAS(T, tail, node)             # 再推进 tail，失败也无妨
                return
        else:
            CAS(T, tail, next)                 # tail 落后了，帮忙推进（协作）
```

**典型并发场景：**

- 日志采集、指标上报用 SPSC 环形队列，写入几乎无锁开销，消费端批量刷盘。
- 订单撮合、事件总线用 MPMC 无锁队列，靠批量 CAS 降低竞争。
- 内存回收是 MPMC 的真正难点：节点出队后何时可以 `delete`，需要 hazard pointer、epoch-based reclamation 或引用计数，否则会出现 use-after-free。

**性能与坑：**

| 坑 | 说明 |
| --- | --- |
| 无锁不等于更快 | 高竞争下 CAS 失败重试、缓存行来回失效，吞吐可能低于一把 mutex |
| 内存序写错 | `relaxed` 发布 head，消费者可能先看到指针后看到数据，读到未初始化内容 |
| 容量取模 | 非 2 的幂要用除法取模，成本高；2 的幂用位与 `(N - 1)` |
| 伪共享 | head/tail 在同一缓存行，生产与消费互相拖慢，必须填充对齐 |
| 满/空判定 | 环形队列通常牺牲一个槽位来区分满与空，或额外维护计数 |

**无锁队列与有锁队列的取舍：**

| 维度 | 无锁队列 | 有锁队列 |
| --- | --- | --- |
| 低竞争延迟 | 更低，无上下文切换 | 略高 |
| 高竞争吞吐 | 可能急剧下降 | 相对稳定 |
| 实现复杂度 | 高（内存序、节点回收） | 低 |
| 调试难度 | 极难复现 | 容易定位 |

压测时必须同时看吞吐与 P99：无锁队列在 2 线程下往往领先，线程数超过物理核数后可能被 mutex 版本反超。

**内存回收是 MPMC 的真正门槛：** 节点被 `pop` 之后，其他线程可能仍持有它的指针（正在 CAS 或读 `next`），立即 `delete` 会造成 use-after-free。生产实现通常用引用计数、hazard pointer 或 epoch 回收，而不是简单的 `delete`。

**面试怎么答：** 先按 SPSC/MPSC/MPMC 分类说明难度差异，再讲 SPSC 的 `release/acquire` 发布语义与伪共享填充，最后主动讲 ABA 与内存回收，说明「无锁队列的难点不在指针操作，而在安全回收」。

**易错点：** 只考虑指针 CAS 而忽略节点的生命周期；用 `relaxed` 写指针、用 `relaxed` 读数据，导致读到半成品。

## 12. 分布式锁与本地锁的区别

**原理：** 本地锁（`mutex`/`synchronized`/`ReentrantLock`）依赖**进程内的内存与 CPU 原子指令**，作用域是单机单进程，失效方式是进程崩溃（锁随进程消失）。分布式锁依赖**外部存储的原子操作**，作用域是跨进程、跨机器，本质是「带租约（TTL）的互斥 + 网络通信」，因此必然面临三个本地锁不存在的问题：网络分区、超时与时钟、锁的续期。

| 维度 | 本地锁 | 分布式锁 |
| --- | --- | --- |
| 作用域 | 单进程（或同机共享内存） | 跨机器、跨进程 |
| 实现基础 | CAS、futex、监视器 | Redis/etcd/数据库的原子命令 |
| 获取代价 | 纳秒到微秒 | 毫秒级，含一次网络往返 |
| 失效方式 | 进程退出即释放 | 依赖 TTL 与心跳续期 |
| 一致性 | 强（同一块内存） | 最终一致，存在误判与脑裂 |
| 典型问题 | 死锁、锁粒度 | 锁超时、误删他人锁、网络分区 |

```lua
-- Redis 释放锁：必须比对持有者标识，避免删掉别人的锁（GET + DEL 要原子）
if redis.call('GET', KEYS[1]) == ARGV[1] then
    return redis.call('DEL', KEYS[1])
else
    return 0
end
```

```go
// Redis 加锁：SET NX PX 是原子命令，token 为本次请求的唯一标识
token := uuid.NewString()
ok, err := rdb.SetNX(ctx, "lock:order:1001", token, 30*time.Second).Result()
if err != nil || !ok {
    return errors.New("lock busy")
}
defer func() {
    // 用 Lua 脚本比对 token 后删除，避免业务超时后误删新持有者的锁
    releaseScript.Run(ctx, rdb, []string{"lock:order:1001"}, token)
}()
```

**典型并发场景与坑：**

- **锁超时小于业务耗时**：锁已过期，第二个线程进入，两个线程同时操作共享资源。解法是续期（watchdog 每 `TTL/3` 续一次），或把 TTL 设为业务 P99 的数倍并监控超时。
- **误删他人锁**：A 超时后锁被 B 获取，A 执行完直接 `DEL`，把 B 的锁删了。必须比对 token，且比对与删除在同一个 Lua 脚本里完成。
- **不可重入**：同一线程再次加锁会失败或把自己锁死，需要按「线程标识 + 重入计数」实现。
- **单点与脑裂**：Redis 主从异步复制，主节点宕机时锁可能丢失；要求强一致时用 etcd 的 lease + txn，或接受「锁只是降低冲突概率」的定位。
- **Redlock 的争议**：多节点投票方案在时钟漂移与网络分区下仍被质疑；工程上更常见的是「单 Redis + TTL + 幂等兜底」。
- **锁粒度**：锁整个账户不如锁 `order:1001`，粒度越细并发越高，但要防止死锁与时序问题。

**选型建议：**

| 需求 | 选择 |
| --- | --- |
| 单机多线程共享状态 | 本地锁（mutex / `ReentrantLock`） |
| 多实例防重复执行定时任务 | 分布式锁（Redis/etcd）+ 幂等 |
| 缓存击穿保护 | 分布式锁或单飞（singleflight） |
| 库存扣减 | 数据库行锁/条件更新，而非分布式锁 |
| 强一致互斥（选主、配置变更） | etcd lease + txn，必要时配合 fencing token |

**主流实现对比：**

| 方案 | 加锁语义 | 优点 | 风险 |
| --- | --- | --- | --- |
| Redis `SET NX PX` | 单实例原子 | 性能好、实现简单 | 主从切换可能丢锁 |
| Redis Redlock | 多节点多数派 | 容忍单点故障 | 时钟与分区下存在争议 |
| etcd lease + txn | 强一致、可监听 | 支持租约与 watch | 性能较低，依赖 Raft |
| 数据库行锁 | 事务内互斥 | 与业务数据同库，天然一致 | 锁持有时间长，易拖库 |
| ZooKeeper 临时节点 | 会话断开自动释放 | 天然避免死锁 | 运维成本高 |

**fencing token：** 每次加锁返回单调递增的令牌，写资源时带上令牌，存储层拒绝比已见令牌更小的写入，从根本上防住「旧持有者超时后仍然写入」。

**面试怎么答：** 先讲作用域与实现基础的差异，再讲分布式锁独有的三个问题（TTL、误删、分区），最后给「锁 + 幂等 + fencing token」的组合，强调「分布式锁只能降低并发冲突概率，不能替代幂等」。

**易错点：** 用 `SET NX` 加锁却用裸 `DEL` 释放；把 TTL 设得很短导致并发穿透；认为加了分布式锁就不会有并发问题，忽略了锁失效窗口。
