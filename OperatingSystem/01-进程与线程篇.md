## 1. 进程与线程的区别

**进程是资源分配的单位，线程是 CPU 调度的单位。进程拥有独立的虚拟地址空间、文件描述符表和信号处理表；同一进程内的线程共享地址空间、堆和已打开的文件，只独享栈、寄存器上下文与线程局部存储（TLS）。在 Linux 里两者都由 `task_struct` 表示，差别只在 `clone()` 传了哪些 `CLONE_*` 标志，所以「线程是轻量级进程」不是比喻，而是实现事实。**

1. **资源归属**：进程的 `mm_struct`（地址空间）、`files_struct`（fd 表）、`fs_struct`（工作目录）、`sighand_struct`（信号处理）都是私有的；线程通过 `CLONE_VM`、`CLONE_FILES`、`CLONE_FS`、`CLONE_SIGHAND` 共享它们。
2. **独享部分**：每个线程有自己的 `task_struct`、内核栈、`thread_info`、用户栈、寄存器上下文、`errno`、TLS、`setjmp` 环境；进程内的全局变量与堆对所有线程可见。
3. **隔离与故障域**：进程间一个崩溃（段错误）不会影响另一个；线程内一个段错误会让整个进程退出，因为共享地址空间。
4. **创建与切换成本**：`fork()` 要复制页表（现代实现用写时复制）并建立新的 `mm_struct`；`pthread_create()` 只需新建一个 task 与栈。切换时跨进程要换 CR3 并影响 TLB，同进程线程切换则不换地址空间。
5. **通信方式**：进程间必须走 IPC（管道、消息队列、共享内存、信号、socket）；线程间直接读写共享内存，代价是必须自己做同步。
6. **调度地位**：内核调度器不区分进程与线程，CFS 的调度实体都是 task；线程并不会因为「同进程」而获得免费的切换。

| 维度 | 进程 | 线程 |
| --- | --- | --- |
| 地址空间 | 独立 `mm_struct` | 共享同一 `mm_struct` |
| 文件描述符 | 独立 fd 表（fork 后是副本） | 共享 fd 表 |
| 栈 | 独立用户栈 + 内核栈 | 独立用户栈 + 内核栈 |
| 全局变量 / 堆 | 私有副本 | 共享 |
| 创建原语 | `fork` / `clone(SIGCHLD)` | `pthread_create` / `clone(CLONE_THREAD...)` |
| 切换开销 | 换栈、换寄存器、换 CR3、TLB 受影响 | 换栈、换寄存器，不换 CR3 |
| 隔离性 | 强 | 弱（共享地址空间） |
| 通信 | IPC | 共享内存 + 同步原语 |
| 典型数量级 | 几十到几百 | 几百到几千（受栈与调度限制） |

**示例（Linux + GCC，验证线程与进程对全局变量的可见性差异）：**

```c
// gcc -pthread share.c -o share && ./share
#include <pthread.h>
#include <stdio.h>
#include <sys/wait.h>
#include <unistd.h>

int counter = 0;

void *add(void *arg) {
    counter += 100;              // 线程直接修改进程内的全局变量
    return NULL;
}

int main(void) {
    pthread_t t;
    pthread_create(&t, NULL, add, NULL);
    pthread_join(t, NULL);
    printf("after thread: counter=%d pid=%d\n", counter, getpid());
    fflush(stdout);              // fork 前清空缓冲区，避免子进程继承后重复输出

    pid_t pid = fork();
    if (pid == 0) {
        counter += 100;          // 子进程改的是 fork 出来的私有副本
        printf("child:        counter=%d pid=%d\n", counter, getpid());
        _exit(0);                // 用 _exit 避免刷新父进程继承下来的缓冲区
    }
    wait(NULL);
    printf("parent:       counter=%d pid=%d\n", counter, getpid());
    return 0;
}
```

```text
after thread: counter=100 pid=12345
child:        counter=200 pid=12346
parent:       counter=100 pid=12345
```

**查看一个进程里的线程：**

```bash
ps -T -p <pid>          # SPID 列即线程 ID
ls /proc/<pid>/task | wc -l
top -H -p <pid>         # 按线程显示 CPU 占用
```

**与业务/后端的联系：**

- 服务端通常是「一进程多线程/多协程」：进程负责隔离与资源限额（容器、cgroup），线程或协程负责并发。Nginx 用多进程 + 每进程单线程事件循环，Redis 主线程单线程处理命令，都是刻意规避共享状态。
- 线程栈默认 8MB 只是虚拟地址预留，但线程数上千时仅栈的地址空间与内核 task 开销就不可忽略；高并发 IO 场景应选协程或事件循环。
- 需要强隔离的插件、多租户、批处理任务适合多进程；需要低延迟共享大缓存的场景适合多线程，但必须配好同步与伪共享防护。

**面试怎么答：** 先给一句话定义「进程管资源、线程管调度」，再用「共享什么、独享什么」展开：地址空间、fd、全局变量共享，栈和寄存器独享。接着补 Linux 实现，说明两者都是 `task_struct`，`clone` 的标志位决定共享粒度，所以线程切换仍要进内核、仍要保存寄存器。最后落到选型：隔离选进程、共享选线程、海量 IO 选协程。

**易错点：**

- 「线程共享栈」是错的：栈是线程私有的，共享的是堆和全局区；说反了会被直接追问。
- 「进程切换一定比线程切换慢很多」要加限定：跨进程要换 CR3、影响 TLB，同进程线程切换不换地址空间，但仍需保存浮点/SIMD 与寄存器状态。
- `fork()` 在多线程程序里只复制调用 fork 的那个线程，子进程只有一条执行流；fork 与 exec 之间只能调用 async-signal-safe 函数。
- 线程不是越多越快：线程数超过可运行任务数只会增加切换与缓存失效，CPU 密集型任务的收益上限是物理核数。

## 2. 进程的状态与切换

**进程在生命周期里只有三种核心处境：占着 CPU 在跑、可跑但没轮到、等事件不能跑。Linux 用 `task_struct.state` 编码这些处境，`ps` 的 STAT 列把它们映射成 `R`、`S`、`D`、`T`、`Z` 等字母。切换分两层：同进程线程切换只换执行上下文，跨进程切换还要换地址空间，后者才是「贵」的来源。**

1. **新建**：`fork()` 复制出 task，进入可运行队列。
2. **就绪（R）**：`TASK_RUNNING` 同时表示「正在 CPU 上」和「在 runqueue 里排队」，Linux 不区分 running 与 ready。
3. **运行**：时间片用完、被更高优先级抢占、主动让出（`sched_yield`）、等事件，都会离开 CPU。
4. **阻塞（S / D）**：`TASK_INTERRUPTIBLE` 可被信号唤醒；`TASK_UNINTERRUPTIBLE` 不响应信号，通常卡在磁盘、NFS 等 IO 上，`kill -9` 也杀不掉。
5. **停止（T）**：收到 `SIGSTOP`/`SIGTSTP` 或被调试器跟踪，可用 `SIGCONT` 恢复。
6. **终止（Z / X）**：已 `exit` 但父进程还没 `wait`，保留 pid 与退出码，即僵尸；`X` 是正在被回收的瞬态。

| 五状态模型 | Linux 状态 | `ps` STAT | 说明 |
| --- | --- | --- | --- |
| 新建 | `TASK_NEW` | — | `fork` 过程中 |
| 就绪 / 运行 | `TASK_RUNNING` | `R` | 在跑或在 runqueue |
| 阻塞（可中断） | `TASK_INTERRUPTIBLE` | `S` | 等 IO、锁、定时器，可被信号打断 |
| 阻塞（不可中断） | `TASK_UNINTERRUPTIBLE` | `D` | 等硬件 IO，不可被信号打断 |
| 停止 | `__TASK_STOPPED` | `T` | 被信号或调试器暂停 |
| 终止 | `EXIT_ZOMBIE` / `EXIT_DEAD` | `Z` / `X` | 等待父进程回收 |

**一次切换的步骤：**

1. 触发点：时间片耗尽、阻塞（`wait_event`）、唤醒抢占、信号投递、显式让出。
2. 保存用户态现场到内核栈的 `pt_regs`：`rip`、`rsp`、`rflags`、通用寄存器。
3. 调度器选下一个 task：CFS 取红黑树最左的 `vruntime`，实时任务取优先级队列。
4. `switch_to` 切换内核栈指针与 callee-saved 寄存器（`rbx`、`rbp`、`r12`-`r15`、`rsp`）。
5. 若跨进程，切换 `mm_struct` 并写 CR3；TLB 失效或依赖 PCID 打标签保留部分条目。
6. 返回用户态，恢复 `pt_regs`，继续执行。

**示例（观察 S 与 R 状态、上下文切换计数）：**

```bash
sleep 300 &
sleep_pid=$!
while :; do :; done &
spin_pid=$!

ps -o pid,stat,pcpu,comm -p "$sleep_pid" "$spin_pid"
#   S 表示可中断睡眠；R 表示正在运行或在队列里

cat "/proc/$sleep_pid/status" | grep -E 'State|ctxt_switches'
# State:  S (sleeping)
# voluntary_ctxt_switches:      1
# nonvoluntary_ctxt_switches:   0

kill "$sleep_pid" "$spin_pid"
```

```bash
ps -eo stat | sort | uniq -c     # 统计各状态的进程数量
```

**与业务/后端的联系：**

- 负载均值（load average）统计的是 `R` 加 `D` 的任务数，所以磁盘或 NFS 卡住时 load 会飙升而 CPU 空闲，看 `top` 的 `%Cpu(s)` 会被误导。
- 线上「进程杀不掉」先看 STAT 是否为 `D`：此时 `kill -9` 无效，要查 `iostat -x 1`、`dmesg`、挂载点是否失联，必要时重启或恢复存储。
- 大量 `S` 且 `cs`（上下文切换）很高，说明线程在等锁或等 IO，属于「忙等型」抖动，应减少锁粒度或改异步模型。

**面试怎么答：** 先背五状态模型，再映射到 Linux 的 `R/S/D/T/Z`，特别点出 `R` 同时代表就绪与运行。切换流程按「触发 → 保存现场 → 选 next → 切栈和寄存器 → 换 CR3/影响 TLB → 返回用户态」讲。最后补一个实战点：`D` 状态不可中断，是排查磁盘故障的关键信号。

**易错点：**

- 把「就绪」和「运行」当成 Linux 的两个状态；Linux 的 `TASK_RUNNING` 两者都算。
- 认为 `kill -9` 一定能杀掉进程；`D` 状态和僵尸进程都杀不掉，前者等 IO 返回，后者等父进程 `wait`。
- 忽略 `T` 状态：`SIGSTOP` 与 `SIGTSTP` 都能暂停进程，但前者不可被捕获，后者可以被程序忽略。
- 跨进程切换才换 CR3；把「线程切换也要换页表」说成必然，是常见错误。

## 3. 进程间通信的六种方式

**进程之间默认不共享地址空间，所有通信都要么由内核中转（管道、消息队列、socket），要么由内核建立共享映射（共享内存），要么只传递一个事件（信号）。选型的核心是三件事：数据量、是否需要跨主机、是否需要同步。大数据同机优先共享内存，跨机只能 socket，简单的父子通知用管道或信号。**

| 方式 | 载体 | 方向 | 跨主机 | 典型 API | 特点 |
| --- | --- | --- | --- | --- | --- |
| 匿名管道 | 内核缓冲区 | 半双工 | 否 | `pipe()` | 只能用于有亲缘关系的进程，随进程销毁 |
| 有名管道 FIFO | 文件系统中的特殊文件 | 半双工 | 否 | `mkfifo()` + `open()` | 无亲缘关系也能用，仍在同一台机器 |
| 消息队列 | 内核中的消息链表 | 双向 | 否 | `msgget/msgsnd/msgrcv`（System V）或 `mq_open`（POSIX） | 有边界、可带类型，按类型收取 |
| 共享内存 | 同一块物理页映射到两个地址空间 | 双向 | 否 | `shmget/shmat` 或 `shm_open + mmap` | 最快，零拷贝；必须配信号量或锁做同步 |
| 信号量 | 内核计数器 | 同步原语 | 否 | `semget/semop` 或 `sem_open` | 不传数据，只做互斥与计数 |
| 信号 | 内核投递的事件编号 | 单向通知 | 否 | `kill()`、`sigaction()` | 信息量极小，异步、可丢失（标准信号不排队） |
| socket | 内核 socket 缓冲区 | 双向 | 是 | `socket/bind/connect/send/recv` | 最通用，支持 Unix domain 与 TCP/UDP |

> 严格说信号与 socket 让「六种」有不同数法；面试常把「管道、FIFO、消息队列、共享内存、信号量、信号、socket」并列，答「七种」也不错，只要能说清各自定位。

**示例（匿名管道 + fork，Linux + GCC）：**

```c
// gcc pipe.c -o pipe && ./pipe
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/wait.h>
#include <unistd.h>

int main(void) {
    int fd[2];
    if (pipe(fd) == -1) {
        perror("pipe");
        exit(1);
    }
    pid_t pid = fork();
    if (pid == 0) {
        close(fd[0]);                       // 子进程只写
        const char *msg = "hello from child";
        write(fd[1], msg, strlen(msg));
        close(fd[1]);
        _exit(0);                           // 必须关闭写端，父进程的 read 才会返回
    }
    close(fd[1]);                           // 父进程只读
    char buf[64] = {0};
    ssize_t n = read(fd[0], buf, sizeof(buf) - 1);
    printf("parent got %zd bytes: %s\n", n, buf);
    close(fd[0]);
    wait(NULL);
    return 0;
}
```

```bash
ipcs -m          # 查看共享内存段
ipcs -q          # 查看消息队列
ipcs -s          # 查看信号量
ls -l /dev/shm   # POSIX 共享内存对象
ss -lx           # Unix domain socket
```

**共享内存的关键点：**

- `shm_open` 创建的对象位于 `/dev/shm`（tmpfs），`fork` 后父子进程 `mmap` 同一对象即可共享；进程退出不会自动删除，要 `shm_unlink`。
- 共享内存本身不提供同步，必须配 `PTHREAD_PROCESS_SHARED` 的互斥量、信号量或文件锁，否则读到的是撕裂数据。
- System V 的 `shmget` 段有 `SHMALL`/`SHMMAX` 限制，可用 `ipcs -l` 查看；容器里常因 `/dev/shm` 默认 64MB 导致共享内存型应用异常。

**与业务/后端的联系：**

- 父子进程传递配置或短消息用管道；Nginx 的 master/worker 通过 socketpair 传递控制命令。
- 本地大缓存（如图片、特征向量）在多进程间共享，用共享内存避免重复加载，但要处理一致性、生命周期与版本升级。
- 跨机器或跨容器一律 socket；本机高性能 RPC 可用 Unix domain socket，省掉 TCP 协议栈开销。
- 信号只适合「通知」不适合「传数据」：`SIGHUP` 重载配置、`SIGTERM` 优雅退出，业务数据不要塞进信号。

**面试怎么答：** 先给分类框架：内核中转（管道、FIFO、消息队列）、共享映射（共享内存）、事件通知（信号）、通用通道（socket）。再逐个说特点与限制：管道半双工且有亲缘限制，FIFO 解除了亲缘限制，消息队列有类型和边界，共享内存最快但要自己同步，信号信息量最小，socket 能跨主机。最后给选型结论：大数据同机用共享内存，跨机用 socket，简单通知用信号。

**易错点：**

- 匿名管道是半双工，不是双向；要双向通信得开两根管道或使用 `socketpair`。
- 共享内存不是「自动同步」的，多个进程同时写同一块内存仍然需要锁或原子操作。
- 消息队列有容量上限（`msgmax`、`msgmnb`），写满时 `msgsnd` 会阻塞或返回 `EAGAIN`，不是无限缓存。
- 标准信号不排队：连续发多个 `SIGUSR1` 可能只收到一次；需要可靠计数用实时信号或信号量。

## 4. 线程同步机制（互斥量 / 条件变量 / 信号量）

**三者的分工不是互相替代：互斥量保护临界区，保证同一时刻只有一个线程进入；条件变量用于「等某个条件成立」，必须与互斥量配合，且等待要放在 `while` 循环里防止虚假唤醒；信号量是一个带计数的闸门，既能做互斥（初值 1）也能做「资源计数 / 生产者消费者」（初值 N），还可以跨进程使用。**

1. **互斥量（mutex）**：加锁失败时线程阻塞并被放入等待队列，解锁时由内核或 futex 唤醒。默认 `PTHREAD_MUTEX_NORMAL` 不可重入，同一线程重复加锁会自死锁；需要重入要用 `PTHREAD_MUTEX_RECURSIVE`。
2. **条件变量（condition variable）**：本身不保存「条件」，只提供等待队列。调用 `pthread_cond_wait` 会原子地「解锁 + 入睡」，被唤醒后重新加锁，因此判断条件必须用 `while` 而不是 `if`。
3. **信号量（semaphore）**：`sem_wait` 把计数减一，减到负数就阻塞；`sem_post` 加一并唤醒。它没有「所有者」概念，任何线程都可以 post，这一点与 mutex 不同。
4. **选择**：只保护共享数据用 mutex；需要「等条件成立」用 condvar + mutex；需要限制并发数量或跨进程同步用 semaphore。
5. **底层**：glibc 的 mutex 在无竞争时是用户态原子操作（futex 快速路径），有竞争才进内核排队，所以「锁一定很慢」不成立，竞争才是成本。
6. **死锁四条件**：互斥、持有并等待、不可抢占、循环等待；工程上最有效的是「固定加锁顺序」和「`trylock` + 超时」。

| 机制 | 初值 / 状态 | 是否有所有者 | 主要用途 | 能否跨进程 |
| --- | --- | --- | --- | --- |
| mutex | 未锁 / 已锁 | 是（谁锁谁解） | 保护临界区 | 可以（`PTHREAD_PROCESS_SHARED`） |
| condvar | 无计数 | 否 | 等待条件成立 | 可以（需配共享 mutex） |
| semaphore | 计数 N | 否 | 限流、计数、互斥 | 可以（`sem_open` 或 `sem_init` 共享） |

**示例（mutex + condvar 实现单生产者单消费者，Linux + GCC）：**

```c
// gcc -pthread pc.c -o pc && ./pc
#include <pthread.h>
#include <stdio.h>

#define N 4
int buf[N];
int head = 0, tail = 0, count = 0;
pthread_mutex_t mu = PTHREAD_MUTEX_INITIALIZER;
pthread_cond_t not_empty = PTHREAD_COND_INITIALIZER;
pthread_cond_t not_full = PTHREAD_COND_INITIALIZER;

void *producer(void *arg) {
    for (int i = 0; i < 10; i++) {
        pthread_mutex_lock(&mu);
        while (count == N) {                 // 必须 while：唤醒后重新检查
            pthread_cond_wait(&not_full, &mu);
        }
        buf[tail] = i;
        tail = (tail + 1) % N;
        count++;
        pthread_cond_signal(&not_empty);
        pthread_mutex_unlock(&mu);
    }
    return NULL;
}

void *consumer(void *arg) {
    for (int i = 0; i < 10; i++) {
        pthread_mutex_lock(&mu);
        while (count == 0) {
            pthread_cond_wait(&not_empty, &mu);
        }
        int v = buf[head];
        head = (head + 1) % N;
        count--;
        pthread_cond_signal(&not_full);
        pthread_mutex_unlock(&mu);
        printf("consume %d\n", v);
    }
    return NULL;
}

int main(void) {
    pthread_t p, c;
    pthread_create(&p, NULL, producer, NULL);
    pthread_create(&c, NULL, consumer, NULL);
    pthread_join(p, NULL);
    pthread_join(c, NULL);
    return 0;
}
```

**POSIX 信号量（跨进程示例骨架）：**

```c
sem_t *s = sem_open("/mysem", O_CREAT, 0644, 1);
sem_wait(s);        // P 操作
/* 临界区，可能操作共享内存 */
sem_post(s);        // V 操作
sem_close(s);
sem_unlink("/mysem");
```

**与业务/后端的联系：**

- 连接池、限流器本质是信号量：许可数就是并发上限，`tryAcquire` 失败快速返回比阻塞更适合网关。
- 生产者消费者用「mutex + 两个 condvar」而不是轮询，避免空转烧 CPU；有界队列满时阻塞生产者是最自然的背压。
- 条件变量误用会导致「丢失唤醒」或「唤醒后条件已失效」，线上表现为偶发卡死，必须用 `while` 重检条件。
- 跨进程共享内存配 `PTHREAD_PROCESS_SHARED` 互斥量时，要确保互斥量本身位于共享段内，否则锁的是各自的副本。

**面试怎么答：** 先说定位：mutex 管互斥、condvar 管等待、semaphore 管计数。再讲 condvar 的三个铁律：必须配 mutex、等待用 `while`、修改条件后要 signal/broadcast。信号量则强调「没有所有者、可跨进程、初值决定语义」。最后补 futex 快速路径，说明无竞争时锁的开销只是几条原子指令。

**易错点：**

- 用 `if` 而不是 `while` 包 `pthread_cond_wait`，遇到虚假唤醒或竞争唤醒就会读到错误状态。
- 忘记在 `pthread_cond_wait` 前持有 mutex，行为未定义；也别忘了它返回时已重新持锁。
- `pthread_cond_signal` 只唤醒一个等待者，多消费者场景可能唤醒错的对象；不确定时用 `broadcast`。
- 把 mutex 当信号量用（初值 1 的信号量确实能互斥，但没有所有权，别的线程可以 post，容易破坏临界区语义）。

## 5. 用户态与内核态、系统调用

**CPU 用特权级把「能执行特权指令」和「只能执行普通指令」分开：x86-64 的 ring 3 是用户态，ring 0 是内核态。用户程序要读文件、发网络包、申请内存，必须通过系统调用这条唯一合法入口切到内核；一次系统调用至少包含「模式切换 + 参数校验 + 内核处理 + 返回」四段，这就是它比普通函数调用贵的原因。**

1. **特权级**：ring 0 可执行 `hlt`、改 CR3、访问全部内存与 IO 端口；ring 3 执行这些会触发 `#GP` 异常。Linux 只用 ring 0 与 ring 3，ring 1/2 不使用。
2. **隔离手段**：页表 PTE 的 U/S 位标记页面是否允许用户态访问；内核页映射在用户态不可读，`SMAP`/`SMEP` 进一步阻止内核误用用户指针。
3. **入口**：x86-64 用 `syscall` 指令（32 位时代是 `sysenter`/`int 0x80`），跳转地址来自 `MSR_LSTAR`，同时把 `CS`、`SS` 切到 ring 0。
4. **传参约定**：系统调用号放 `rax`，参数依次放 `rdi`、`rsi`、`rdx`、`r10`、`r8`、`r9`（注意第 4 个是 `r10` 不是 `rcx`），返回值放 `rax`；超过 6 个参数用指针传结构体。
5. **内核侧**：`entry_SYSCALL_64` 保存寄存器、切到内核栈，按 `rax` 查 `sys_call_table`，执行后 `sysretq` 返回；出错用负的 `-errno` 表示，glibc 再转成 `errno`。
6. **常见规避**：`vDSO` 让 `clock_gettime`、`gettimeofday` 在用户态读完共享数据就返回；`io_uring` 用共享环形队列批量提交，减少系统调用次数。

| 维度 | 用户态（ring 3） | 内核态（ring 0） |
| --- | --- | --- |
| 可执行指令 | 普通指令 | 全部，含特权指令 |
| 内存访问 | 仅本进程用户页 | 全部物理内存与内核页 |
| 栈 | 用户栈 | 内核栈（每 task 一份） |
| 进入方式 | — | 系统调用、中断、异常 |
| 出错后果 | 进程收到信号 | 可能 panic 或 oops |

**示例（直接发起系统调用，并统计开销，Linux + GCC）：**

```c
// gcc syscall.c -o syscall && strace -c ./syscall
#define _GNU_SOURCE
#include <stdio.h>
#include <sys/syscall.h>
#include <unistd.h>

int main(void) {
    long pid = syscall(SYS_getpid);      // 绕过 glibc 包装，直接走 syscall 指令
    printf("pid=%ld\n", pid);

    long sum = 0;
    for (int i = 0; i < 100000; i++) {
        sum += syscall(SYS_getpid);      // 反例：高频系统调用
    }
    printf("sum=%ld\n", sum);
    return 0;
}
```

```bash
#  ...
# 100.00    0.0xxxxx           0.x    100001           getpid
```

```bash
strace -e trace=openat,read,write,close ./app    # 看一次文件读取的真实调用序列
```

**与业务/后端的联系：**

- 高频日志、逐条 `write`、每条消息一次 `send` 都会把时间花在模式切换上；改为批量 `writev`、`sendmmsg`、缓冲聚合，吞吐能明显提升。
- 容器里的「只读文件系统」「权限不足」最终都表现为系统调用返回 `EPERM`/`EACCES`，看 `strace` 比猜代码快。
- 性能分析时 `perf top` 里出现大量 `[kernel]` 符号，往往是系统调用或缺页导致，不要只盯用户态函数。

**面试怎么答：** 先讲「为什么需要两种态」：保护内核与硬件不被用户程序破坏。再讲切换路径：`syscall` 指令 → 查 `MSR_LSTAR` 入口 → 保存现场、切内核栈 → 查表执行 → `sysretq` 返回。最后说开销来源：模式切换、TLB/缓存污染、参数拷贝，并给优化手段：`vDSO`、批量接口、`io_uring`。

**易错点：**

- 系统调用不等于函数调用：它有特权级切换，参数在寄存器/用户内存之间传递，内核还要做 `copy_from_user` 校验。
- x86-64 第 4 个参数用 `r10`，不是 `rcx`；手写汇编时写错会得到莫名其妙的参数。
- `int 0x80` 在 64 位下仍可用，但走的是 32 位系统调用表与 32 位 ABI，系统调用号与参数宽度都不同。
- `syscall` 返回负值表示错误（如 `-EINVAL`），不是「返回 -1 且设置 errno」；那是 glibc 包装后的行为。

## 6. 上下文切换的开销与优化

**上下文切换是把 CPU 从一个执行流交给另一个执行流：保存旧流的寄存器与栈指针，恢复新流的。直接开销是几十到几百条指令，真正贵的是间接开销——切换会让 L1/L2 缓存、分支预测器、TLB 变冷，跨进程还要换 CR3。优化方向不是「把切换写得更快」，而是「减少不必要的切换」和「让切换后仍命中缓存」。**

1. **直接成本**：保存/恢复通用寄存器、浮点/SIMD 寄存器、栈指针、程序计数器；内核还要更新调度统计、runqueue、`task_struct` 状态。
2. **间接成本**：新任务的工作集不在缓存里，前几百微秒都在补缓存；跨进程切换导致 TLB 失效（PCID 可缓解），页表遍历变多。
3. **切换类型**：进程切换（换 `mm_struct` + CR3）、线程切换（同进程，不换 CR3）、模式切换（用户态↔内核态，不算任务切换）、中断切换（打断当前流处理中断）。
4. **常见触发**：时间片耗尽、锁竞争阻塞、IO 等待、`sleep`、高优先级抢占、`sched_yield`、频繁 `poll` 超时。
5. **量化**：`vmstat` 的 `cs` 列是每秒上下文切换次数；`pidstat -w` 分 voluntary（主动阻塞）与 nonvoluntary（被抢占）；`/proc/<pid>/status` 有同样两项累计值。
6. **优化手段**：降低锁竞争（分段锁、无锁结构）、用协程替代大量线程、批量处理减少阻塞唤醒、绑核减少迁移、调大 `sched_latency` 或降低调度频率、避免「唤醒风暴」。

| 指标 | 含义 | 观察命令 |
| --- | --- | --- |
| `cs` | 每秒上下文切换总数 | `vmstat 1` |
| `cswch/s` | 每秒主动切换（等资源） | `pidstat -w 1` |
| `nvcswch/s` | 每秒被动切换（被抢占） | `pidstat -w 1` |
| `context-switches` | 进程级切换计数 | `perf stat -e context-switches ./app` |
| `cpu-migrations` | 跨核迁移次数 | `perf stat -e cpu-migrations ./app` |

**示例（两个线程用条件变量来回让出，放大切换成本，Linux + GCC）：**

```c
// gcc -O2 -pthread pingpong.c -o pingpong && ./pingpong
#include <pthread.h>
#include <stdio.h>
#include <time.h>

#define N 200000
pthread_mutex_t mu = PTHREAD_MUTEX_INITIALIZER;
pthread_cond_t cv = PTHREAD_COND_INITIALIZER;
int turn = 0;

void *worker(void *arg) {
    int id = *(int *)arg;
    for (int i = 0; i < N; i++) {
        pthread_mutex_lock(&mu);
        while (turn != id) {
            pthread_cond_wait(&cv, &mu);   // 每次等待都触发一次阻塞/唤醒
        }
        turn = 1 - id;
        pthread_cond_signal(&cv);
        pthread_mutex_unlock(&mu);
    }
    return NULL;
}

int main(void) {
    pthread_t a, b;
    int id0 = 0, id1 = 1;
    struct timespec t0, t1;
    clock_gettime(CLOCK_MONOTONIC, &t0);
    pthread_create(&a, NULL, worker, &id0);
    pthread_create(&b, NULL, worker, &id1);
    pthread_join(a, NULL);
    pthread_join(b, NULL);
    clock_gettime(CLOCK_MONOTONIC, &t1);
    double ms = (t1.tv_sec - t0.tv_sec) * 1000.0 + (t1.tv_nsec - t0.tv_nsec) / 1e6;
    printf("%d 次往返切换耗时 %.1f ms，单次约 %.2f us\n", N, ms, ms * 1000 / (2 * N));
    return 0;
}
```

```bash
vmstat 1 5          # cs 列
pidstat -w 1 5      # 每进程主动/被动切换
perf stat -e context-switches,cpu-migrations,cache-misses ./pingpong
```

**与业务/后端的联系：**

- 线程池不是越大越好：线程数远超核数时，锁与队列竞争会让 `cs` 暴涨，吞吐反而下降；CPU 密集型线程数取核数附近，IO 密集型按「核数 × 阻塞系数」估算。
- 大量短连接服务把线程当连接用时，切换成本会压过业务逻辑；改用事件循环或协程，把「每连接一线程」降为「每核一循环」。
- 微服务间的超时重试、频繁 `sleep(1ms)` 轮询都会制造切换；改成事件驱动或指数退避能显著降低 `cs`。

**面试怎么答：** 先区分直接开销与间接开销，强调后者（缓存与 TLB）才是主因。再区分进程切换、线程切换、模式切换，指出只有跨进程才换 CR3。然后给观测命令 `vmstat`、`pidstat -w`、`perf stat`。最后给优化清单：减少锁竞争、协程化、批量、绑核、避免忙等与唤醒风暴。

**易错点：**

- 把「系统调用」算成上下文切换；模式切换不更换 task，两者不是一回事。
- 只看 `cs` 高低就下结论：切换多可能是正常的 IO 等待，要结合 `%CPU`、`cswch/s` 与 `nvcswch/s` 判断。
- 认为绑核一定提速：绑核减少迁移但可能造成负载不均，且 NUMA 机器上绑错节点反而更慢。
- 忽略「唤醒风暴」：一个锁释放唤醒几十个线程，只有一个能拿到锁，其余继续睡，切换成本白付。

## 7. fork 与 exec 的语义

**`fork` 复制出一个新进程，`exec` 用新程序替换当前进程的地址空间。两者常常成对使用，但职责完全不同：`fork` 负责「造出一个进程」，`exec` 负责「换掉这个进程里的程序」。`fork` 成功后返回两次（父进程得到子进程 pid，子进程得到 0），`exec` 成功后不返回——因为原来的代码已经被覆盖了。**

1. **fork 的资源复制**：复制 `task_struct`、页表（现代内核用写时复制，父子共享物理页并标记只读，任一方写入才真正复制）、fd 表、信号处理表；子进程继承父进程的 `pid` 之外的一切身份信息，但 `pid` 是新的。
2. **fork 的返回值**：父进程得到子进程 pid（大于 0），子进程得到 0，失败返回 -1 并设置 `errno`。所以代码必须 `if (pid == 0) { 子进程逻辑 }`。
3. **exec 的替换过程**：解析路径 → 打开 ELF → 校验格式与架构 → 释放旧 `mm_struct`、建立新地址空间 → 映射代码段/数据段/栈 → 设置入口 `_start` → 重置信号处理（被捕获的信号恢复默认，被忽略的仍忽略）→ 保留 pid、fd（未设 `FD_CLOEXEC` 的）、进程组、会话。
4. **exec 成功不返回**：原进程的代码、堆、栈都已不存在，返回地址无处可回；失败才返回 -1，常见错误是 `ENOENT`、`EACCES`、`ENOEXEC`。
5. **vfork 与 posix_spawn**：`vfork` 让子进程共享父进程地址空间并阻塞父进程，子进程必须立刻 `exec` 或 `_exit`；`posix_spawn` 在 glibc 里用 `clone(CLONE_VM | CLONE_VFORK)` 实现，避免复制页表，适合「fork 后马上 exec」的场景。
6. **多线程下的 fork**：只复制调用 `fork` 的那个线程，其他线程在子进程里不存在；子进程可能继承已被其他线程持有的锁（处于锁定状态且无解锁者），因此 fork 与 exec 之间只能调用 async-signal-safe 函数（如 `write`、`execve`、`_exit`），不要 `malloc`、`printf`。

| 操作 | 是否创建新进程 | pid 变化 | 地址空间 | 成功返回值 |
| --- | --- | --- | --- | --- |
| `fork` | 是 | 子进程获得新 pid | 复制（写时复制） | 父得子 pid，子得 0 |
| `vfork` | 是 | 子进程获得新 pid | 共享父进程地址空间 | 父得子 pid，子得 0 |
| `execve` | 否，替换当前进程映像 | 不变 | 完全替换 | 不返回 |
| `posix_spawn` | 是 | 子进程获得新 pid | 新建并立即 exec | 返回 0 表示 spawn 成功 |

**示例（fork + exec 执行外部命令，Linux + GCC）：**

```c
// gcc forkexec.c -o forkexec && ./forkexec
#include <stdio.h>
#include <sys/wait.h>
#include <unistd.h>

int main(void) {
    pid_t pid = fork();
    if (pid < 0) {
        perror("fork");
        return 1;
    }
    if (pid == 0) {
        execlp("echo", "echo", "child exec ok", (char *)NULL);
        perror("execlp");       // 只有 exec 失败才会走到这里
        _exit(127);
    }
    int status = 0;
    waitpid(pid, &status, 0);
    if (WIFEXITED(status)) {
        printf("parent: child exited with %d\n", WEXITSTATUS(status));
    }
    return 0;
}
```

```text
child exec ok
parent: child exited with 0
```

```bash
strace -f -e trace=clone,execve,wait4 ./forkexec
# clone(...)  = 子进程
# execve("/usr/bin/echo", ["echo", "child exec ok"], ...) = 0
```

**与业务/后端的联系：**

- Shell 执行一条命令就是 `fork` + `exec` + `wait`；容器启动进程、CI 跑脚本、`subprocess` 调外部工具都是同一套语义。
- 需要「父进程继续服务、子进程干脏活」时用 fork；需要「换掉自身程序」时用 exec，例如 supervisor 拉起新版本二进制。
- 多线程服务里不要随便 fork 后调用非 async-signal-safe 函数；更安全的做法是 `posix_spawn` 或先 fork 一个干净的子进程再 exec。
- 子进程继承的 fd 会让文件或 socket 的生命周期被意外延长，创建时记得设 `FD_CLOEXEC`（`O_CLOEXEC`）。

**面试怎么答：** 先讲「fork 造进程、exec 换程序」，强调 fork 返回两次、exec 成功不返回。再讲写时复制：fork 不立刻复制物理页，而是共享只读页，写入触发缺页再复制。然后补 exec 保留什么（pid、未设 CLOEXEC 的 fd、进程组）与重置什么（捕获的信号处理）。最后补多线程 fork 的陷阱与 `posix_spawn` 的替代。

**易错点：**

- 认为 `exec` 会创建新进程；它只是替换当前进程的映像，pid 不变。
- 忘记 fork 前的 `printf` 缓冲区会被子进程继承，子进程 `exit` 时重复输出；应使用 `_exit` 或先 `fflush`。
- 认为 fork 立即复制全部内存；实际是写时复制，但页表本身仍要复制，所以大内存进程 fork 依然有成本。
- fork 失败最常见的原因是 `EAGAIN`（进程数或内存超限）与 `ENOMEM`，不是「代码写错了」。

## 8. 僵尸进程与孤儿进程

**僵尸进程是「已经退出、但父进程还没回收」的进程：它释放了地址空间和文件描述符，只保留 `task_struct`、pid 和退出码，等待父进程 `wait`。孤儿进程是「父进程先退出、自己还活着」的进程：它被 `init`（pid 1）或最近的 subreaper 收养，正常运行，退出后由养父回收。两者不是一回事，但都跟「谁负责 wait」有关。**

1. **退出流程**：`exit` 关闭 fd、释放 `mm_struct`、把退出状态写入 `task_struct`，向父进程发 `SIGCHLD`，然后进入 `EXIT_ZOMBIE`，等父进程调用 `wait`/`waitpid` 后才真正释放 pid。
2. **僵尸的代价**：不占内存（地址空间已释放），但占一个 pid 和一个 `task_struct`；pid 数量有限（`/proc/sys/kernel/pid_max` 默认 32768，可调至 4194304），僵尸堆积最终导致无法创建新进程。
3. **回收方式**：`wait()` 阻塞等任一子进程；`waitpid(pid, &status, 0)` 等指定子进程；`waitpid(pid, &status, WNOHANG)` 非阻塞轮询；`waitid` 更精细。
4. **自动回收**：把 `SIGCHLD` 的处理设为 `SIG_IGN`，内核会在子进程退出时自动回收（POSIX 语义，Linux 支持）；注意「默认忽略」与「显式忽略」不同，默认忽略仍然会产生僵尸。
5. **孤儿收养**：父进程退出后，子进程被 reparent 到 pid 1（或通过 `prctl(PR_SET_CHILD_SUBREAPER, 1)` 指定的 subreaper）；收养后仍是活进程，只有它自己退出且养父未回收时才变僵尸。
6. **容器场景**：容器里的 pid 1 如果是应用本身且不回收子进程，就会不断产生僵尸；常见做法是加一个 tiny init（如 `tini`）或让应用显式 `wait`。

| 对比项 | 僵尸进程 | 孤儿进程 |
| --- | --- | --- |
| 定义 | 子进程已退出，父进程未 wait | 父进程已退出，子进程还活着 |
| 是否占资源 | 占 pid 与 task_struct，不占内存 | 占完整资源，正常运行 |
| 状态字母 | `Z` | `R/S/D` 等正常状态 |
| 由谁回收 | 父进程（或 init） | 养父（init 或 subreaper） |
| 危害 | 堆积耗尽 pid | 一般无害，但可能失去父进程的管理 |

**示例（制造并回收一个僵尸，Linux + GCC）：**

```c
// gcc zombie.c -o zombie && ./zombie
#include <stdio.h>
#include <sys/wait.h>
#include <unistd.h>

int main(void) {
    pid_t pid = fork();
    if (pid == 0) {
        _exit(7);                    // 子进程立即退出
    }
    sleep(3);                        // 这 3 秒内子进程是 Z 状态
    int status = 0;
    waitpid(pid, &status, 0);        // 回收后僵尸消失
    printf("reaped, exit code = %d\n", WEXITSTATUS(status));
    return 0;
}
```

```bash
./zombie &
ps -o pid,ppid,stat,comm -p <child_pid>
#   Z     <defunct>
cat /proc/<child_pid>/status | grep State
```

```bash
ps -eo pid,ppid,stat,comm | awk '$3 ~ /^Z/ {print}'    # 找出所有僵尸
ps -eo pid,ppid,stat,comm | awk '$2 == 1'              # 查看被 init 收养的进程
```

**与业务/后端的联系：**

- 服务端用 `subprocess`、`os/exec`、`fork` 拉起外部命令时，必须 `wait` 或设置 `SIGCHLD` 处理，否则长期运行会积累僵尸，最终 `fork` 返回 `EAGAIN`。
- 容器编排里若应用是 pid 1，要确保它回收所有子进程；否则 `docker ps` 看到容器还在，但内部已经无法创建进程。
- 守护进程常用「双 fork」：第一次 fork 后父进程退出，子进程被 init 收养，从而脱离终端会话；第二次 fork 确保不会再获得控制终端。
- 排查「进程数暴涨」时先数僵尸：`ps -eo stat | grep -c Z`，再看父进程是谁，修复父进程的回收逻辑才是根治。

**面试怎么答：** 先用一句话区分：僵尸是「死了没埋」，孤儿是「没爹但活着」。再讲退出与回收流程：`exit` 释放资源但保留 task_struct 与退出码，父进程 `wait` 后才释放 pid。然后给处理手段：`waitpid`、`SIGCHLD` 显式 `SIG_IGN`、双 fork、容器加 init。最后补危害：僵尸占 pid 不占内存，堆积会耗尽 pid 表。

**易错点：**

- 认为僵尸占用大量内存；地址空间已经释放，主要占用 pid 与内核 task 结构。
- 试图用 `kill -9` 杀僵尸；僵尸已经不在运行，信号无效，只能让父进程 `wait`。
- 把孤儿当成僵尸；孤儿是正常运行的进程，只是父进程变成了 init。
- 认为「没有处理 SIGCHLD 就不会有僵尸」；默认行为是忽略通知但保留退出状态，僵尸照样产生。

## 9. 协程与线程的关系

**协程是用户态或运行时层面的执行流，线程是内核调度实体。一个线程可以承载成千上万个协程，协程的切换由程序自己完成（保存少量寄存器与栈指针），不进入内核，因此比线程切换便宜一到两个数量级。代价是协程不能自动利用多核，需要运行时把大量协程分配到多个线程上（M:N 模型），并且一个阻塞调用可能拖住整个线程。**

1. **栈**：线程栈由内核/glibc 分配，默认 8MB 虚拟空间；协程栈由运行时管理，Go 的 goroutine 初始只有几 KB，按需增长（上限默认 1GB，可用 `debug.SetMaxStack` 调整）。Python 的 `async` 协程是无栈协程，状态保存在堆上的状态机对象里。
2. **切换**：线程切换要进内核、保存完整寄存器与浮点状态、可能换 CR3；协程切换只保存 callee-saved 寄存器与栈指针，通常在几十纳秒级。
3. **调度**：线程由内核抢占式调度；协程由运行时协作式调度，在 `await`、channel 阻塞、`yield` 等点让出。
4. **并行能力**：单个线程上的协程不能并行，只能并发；Go 用 G-M-P 模型把 goroutine 分到多个 P（逻辑处理器）上，P 的数量由 `GOMAXPROCS` 决定，默认等于 CPU 核数（Go 1.25 起会参考 cgroup 的 CPU 限额）。
5. **阻塞的处理**：Go 1.14 起支持异步抢占，长循环不会永久霸占 P；但阻塞式系统调用仍会让 M 阻塞，运行时会创建新的 M 接管 P。Python asyncio 里调用同步阻塞函数会卡住整个事件循环，必须用线程池包起来。
6. **泄漏**：协程没有「join」就退出会泄漏栈与引用；Go 里常见是向无缓冲 channel 发送但无人接收，或 `for { select {} }` 永不退出。

| 维度 | 线程 | 协程 |
| --- | --- | --- |
| 调度者 | 内核 | 语言运行时 / 事件循环 |
| 栈 | 默认 8MB（`ulimit -s`） | 几 KB 起，按需增长 |
| 切换成本 | 微秒级，进内核 | 纳秒级，用户态 |
| 并行 | 多核真并行 | 单线程内并发，靠多线程/多 P 并行 |
| 抢占 | 时间片抢占 | 协作式（Go 1.14+ 有异步抢占） |
| 数量级 | 几百到几千 | 几万到百万 |
| 阻塞影响 | 只阻塞当前线程 | 可能阻塞整个事件循环/线程 |

**示例（Go，观察协程数量与调度，Go 1.21+）：**

```go
// go run main.go
// GODEBUG=schedtrace=1000 go run main.go 可每秒打印调度器状态
package main

import (
    "fmt"
    "runtime"
    "sync"
    "time"
)

func main() {
    fmt.Println("GOMAXPROCS =", runtime.GOMAXPROCS(0), "NumCPU =", runtime.NumCPU())
    const n = 20000
    var wg sync.WaitGroup
    start := time.Now()
    for i := 0; i < n; i++ {
        wg.Add(1)
        go func(id int) {
            defer wg.Done()
            if id%100 == 0 {
                time.Sleep(time.Millisecond)   // 模拟 IO：让出 P，其他协程继续跑
            }
        }(i)
    }
    wg.Wait()
    fmt.Println(n, "goroutines done in", time.Since(start))
}
```

```text
GOMAXPROCS = 8 NumCPU = 8
20000 goroutines done in 12.3ms
```

```bash
# gomaxprocs=8 idleprocs=... threads=... runqueue=...
go tool trace ./trace.out      # 需要先 runtime/trace.Start
```

**与业务/后端的联系：**

- 高并发网关、IM、推送服务的连接数远大于核数，用「每连接一线程」会因栈与切换成本崩掉；Go 的 netpoller + goroutine、Java 21 的虚拟线程、Python 的 asyncio 都是同一思路。
- 协程适合 IO 密集，不适合 CPU 密集：CPU 密集任务要限制并发数（信号量或 worker pool），否则大量协程只是在 runqueue 里排队。
- 协程泄漏比线程泄漏更隐蔽：内存缓慢上涨、`goroutine` 数只增不减，用 `pprof` 的 goroutine profile 定位阻塞点。
- 在协程里调用同步阻塞库（数据库驱动、文件 IO）会拖住线程；Go 靠运行时 handoff 缓解，Python 必须显式 `run_in_executor`。

**面试怎么答：** 先给定义：协程是用户态/运行时的执行流，线程是内核调度实体。再对比切换成本与栈大小，说明协程便宜的原因是不进内核、只保存少量上下文。然后讲 M:N 模型与 `GOMAXPROCS`，指出协程本身不能并行，必须跑在多线程上。最后补两个坑：阻塞调用拖住线程、协程泄漏。

**易错点：**

- 说「协程比线程轻所以可以无限创建」；内存与调度队列仍有成本，且泄漏会累积。
- 认为协程能自动利用多核；单线程事件循环里的协程始终只用一个核，Python 的计算密集型协程不会变快。
- 把 Go 的 goroutine 当成「无栈协程」；goroutine 是有栈协程，栈会动态增长。
- 忽略 `GOMAXPROCS` 与容器 CPU limit 的关系：早期版本默认取宿主机核数，容器里会过度并行，Go 1.25 起才默认感知 cgroup 配额。

## 10. 进程调度算法

**调度的目标是在「吞吐量、响应时间、公平性、优先级」之间取舍，不存在全能算法。批处理看周转时间，交互式看响应时间，实时任务看截止期。Linux 通用进程用 CFS（6.6 起默认 EEVDF），实时进程用 `SCHED_FIFO`/`SCHED_RR`，两者走完全不同的调度类与优先级体系。**

1. **FCFS（先来先服务）**：按到达顺序执行，非抢占。实现最简单，但短任务排在长任务后面会产生「护航效应」，平均等待时间差。
2. **SJF / SPN（短作业优先）**：每次选预计运行时间最短的任务，非抢占版本叫 SJF，抢占版本叫 SRTF。平均等待时间最优，但需要预知运行时间，且长任务可能饿死。
3. **RR（时间片轮转）**：每个任务最多跑一个时间片，用完排到队尾。时间片太大退化为 FCFS，太小则切换开销占比过高，通常取 10-100ms 量级。
4. **优先级调度**：按优先级选任务，高优先级可抢占。问题是低优先级饿死，解决办法是「老化」（等待越久优先级越高）。
5. **MLFQ（多级反馈队列）**：多个不同时间片的队列，新任务进高优先级队列，用完时间片就降级；短任务在高队列快速完成，长任务逐步下沉，兼顾响应与吞吐，但需要防止「 gaming」。
6. **CFS / EEVDF**：CFS 用 `vruntime` 记录虚拟运行时间，总选 `vruntime` 最小者，红黑树维护；`vruntime` 增速与权重成反比，nice 值越低权重越大、跑得越多。Linux 6.6 起默认改为 EEVDF，在 `vruntime` 基础上加入「虚拟截止期」，改善延迟公平性。

| 算法 | 抢占 | 优点 | 缺点 | 适用 |
| --- | --- | --- | --- | --- |
| FCFS | 否 | 简单、无饥饿 | 护航效应，平均等待差 | 批处理 |
| SJF / SRTF | 可选 | 平均等待最优 | 需预知 burst，长任务饿死 | 批处理（可估算） |
| RR | 是 | 响应快、公平 | 时间片难调，切换开销 | 分时系统 |
| 优先级 | 是 | 可表达业务重要性 | 低优先级饥饿 | 实时/关键任务 |
| MLFQ | 是 | 兼顾响应与吞吐 | 参数多，可能被绕过 | 通用 OS |
| CFS / EEVDF | 是 | 公平、低延迟、权重可调 | 实现复杂，参数多 | Linux 通用进程 |

**关键指标：**

- 周转时间 = 完成时间 − 到达时间。
- 等待时间 = 周转时间 − 运行时间。
- 响应时间 = 首次被调度的时间 − 到达时间。
- 吞吐量 = 单位时间完成的任务数；CPU 利用率 = 忙碌时间 / 总时间。

**示例（Go 计算 FCFS 与 SJF 的平均等待时间）：**

```go
// go run sched.go
package main

import (
    "fmt"
    "sort"
)

type proc struct {
    name  string
    burst int
}

func fcfs(ps []proc) float64 {
    t, wait := 0, 0
    for _, p := range ps {
        wait += t
        t += p.burst
    }
    return float64(wait) / float64(len(ps))
}

func sjf(ps []proc) float64 {
    left := append([]proc(nil), ps...)
    sort.Slice(left, func(i, j int) bool { return left[i].burst < left[j].burst })
    t, wait := 0, 0
    for _, p := range left {
        wait += t
        t += p.burst
    }
    return float64(wait) / float64(len(left))
}

func main() {
    ps := []proc{{"P1", 8}, {"P2", 4}, {"P3", 9}, {"P4", 5}}
    fmt.Printf("FCFS 平均等待 = %.2f\n", fcfs(ps))
    fmt.Printf("SJF  平均等待 = %.2f\n", sjf(ps))
}
```

```text
FCFS 平均等待 = 10.25
SJF  平均等待 = 7.50
```

**调整调度策略与优先级：**

```bash
chrt -f 10 ./app          # SCHED_FIFO，优先级 10（1-99，需 CAP_SYS_NICE）
chrt -r 10 ./app          # SCHED_RR
nice -n 10 ./app          # 普通进程降低优先级（-20 最高，19 最低）
renice -n 5 -p <pid>
taskset -c 0-3 ./app      # 绑定 CPU 0-3
```

**与业务/后端的联系：**

- 在线服务要低延迟：把核心服务设为较高 nice 或 `SCHED_FIFO`（谨慎，实时任务跑飞会饿死系统），并给日志、备份等离线任务降优先级。
- 容器里用 cgroup 的 `cpu.weight`/`cpu.max` 做配额，比在进程内调 nice 更可靠；Kubernetes 的 requests/limits 最终落到 cgroup。
- 线程池的任务粒度影响调度：过细的任务让调度开销占比升高，过粗则响应变差，通常按「几十微秒到几毫秒」切分。
- 实时音视频、交易系统关注的是「最坏延迟」而不是平均延迟，需要结合 `SCHED_DEADLINE`、CPU 隔离（`isolcpus`）与中断亲和性。

**面试怎么答：** 先给取舍框架：吞吐、响应、公平、截止期。再按算法讲核心思想与缺点：FCFS 的护航效应、SJF 的最优但不现实、RR 的时间片权衡、优先级饥饿与老化、MLFQ 的多级反馈。最后落到 Linux：CFS 用 `vruntime` + 红黑树，权重由 nice 决定，6.6 起默认 EEVDF；实时任务用 FIFO/RR。

**易错点：**

- 说 SJF 一定最好；它只在「已知运行时间且非抢占」的模型下平均等待最优，现实里无法准确预知。
- 把 RR 的时间片设得越小越好；太小会让切换开销吞掉吞吐，太大则退化为 FCFS。
- 认为 nice 值是「绝对优先级」；CFS 里 nice 只决定权重比例，且普通进程的优先级不影响实时任务。
- 忽略优先级反转：低优先级任务持有锁、高优先级任务等锁，需要优先级继承（`PTHREAD_PRIO_INHERIT`）或临界区设计来缓解。

## 11. 多进程 / 多线程 / 多协程选型

**选型先看任务类型：CPU 密集型要的是「真并行」，进程或线程都行，但进程隔离更好；IO 密集型要的是「同时挂起大量等待」，协程或事件循环最省资源；需要共享大状态又要求低延迟，才轮到多线程加锁。语言运行时是第二层约束：Python 有 GIL，CPU 密集必须多进程；Go 原生协程，默认选 goroutine。**

1. **CPU 密集型**：任务大部分时间在算，线程数超过核数没有收益。多进程能绕过 GIL、隔离故障、利用多核；多线程共享内存方便但锁竞争会拖慢。
2. **IO 密集型**：任务大部分时间在等网络/磁盘。线程模型简单但每线程 8MB 栈与内核切换成本高；协程模型用几 KB 承载一个等待，适合万级以上连接。
3. **共享状态**：多进程需要序列化或共享内存，跨进程锁更重；多线程直接共享，但必须设计同步，稍不注意就是竞态与死锁。
4. **隔离与稳定性**：多进程一个崩溃不影响其他，适合插件、批处理、不可信代码；多线程一个段错误全进程退出，适合内部可信代码。
5. **语言约束**：Python 的 GIL 让多线程无法并行执行字节码，CPU 密集用 `multiprocessing`；Go 的 goroutine 由运行时调度，默认「每任务一协程」；Java 21 有虚拟线程，可把「每请求一线程」重新变成可行方案；Node.js 单线程事件循环，CPU 密集要用 `worker_threads` 或 `cluster`。
6. **成本量化**：线程创建约几十微秒、栈虚拟内存 8MB；进程创建要复制页表，毫秒级；协程创建纳秒到微秒级。切换成本同样依次递减。

| 维度 | 多进程 | 多线程 | 多协程 |
| --- | --- | --- | --- |
| 并行能力 | 真并行 | 真并行（受 GIL 等运行时限制） | 需绑定多线程才能并行 |
| 隔离性 | 强 | 弱 | 弱 |
| 共享数据 | 需 IPC / 共享内存 | 直接共享 | 直接共享（同线程内） |
| 创建成本 | 毫秒级 | 几十微秒 | 纳秒到微秒 |
| 内存占用 | 每进程独立地址空间 | 每线程约 8MB 栈虚拟空间 | 每协程几 KB 起 |
| 适合场景 | CPU 密集、批处理、插件隔离 | 中等并发、共享缓存 | 高并发 IO、网关、长连接 |
| 典型代表 | Nginx worker、Python multiprocessing | Java 线程池、C++ 线程池 | Go goroutine、Python asyncio |

**选型步骤：**

1. 先判断瓶颈：`perf top`/`pprof` 显示用户态计算占主导 → CPU 密集；显示 `read`/`write`/`epoll_wait` 占主导 → IO 密集。
2. CPU 密集：核数决定并行度，进程或线程池大小取 `NumCPU` 附近；需要隔离或绕过 GIL 选进程。
3. IO 密集：估算并发连接数与单次等待时长，优先协程/事件循环；存量同步库多的项目用线程池更稳。
4. 需要共享大缓存：线程或协程；跨进程共享则用共享内存 + 锁，注意一致性与生命周期。
5. 需要强隔离/可独立重启：进程；容器本身就是进程级隔离的延伸。

**示例（Go worker pool，CPU 密集型限制并行度）：**

```go
// go run pool.go
package main

import (
    "fmt"
    "runtime"
    "sync"
)

func worker(jobs <-chan int, results chan<- int, wg *sync.WaitGroup) {
    defer wg.Done()
    for j := range jobs {
        sum := 0
        for i := 0; i < j; i++ {
            sum += i * i
        }
        results <- sum
    }
}

func main() {
    workers := runtime.NumCPU()
    jobs := make(chan int, 100)
    results := make(chan int, 100)
    var wg sync.WaitGroup
    for i := 0; i < workers; i++ {
        wg.Add(1)
        go worker(jobs, results, &wg)
    }
    for i := 1; i <= 200; i++ {
        jobs <- i
    }
    close(jobs)
    wg.Wait()
    close(results)
    total := 0
    for r := range results {
        total += r
    }
    fmt.Println("workers =", workers, "total =", total)
}
```

**与业务/后端的联系：**

- API 网关、IM、推送：连接数上万、每连接大部分时间在等，选协程或事件循环；每连接一线程会在内存与切换上先崩。
- 图片转码、视频抽帧、加密解密：CPU 密集，选多进程或固定大小线程池，进程数取核数，避免超配。
- 有大量共享缓存的推荐服务：单进程多线程 + 分片锁，或 Go 单进程多协程 + `sync.Map`/分片 map；跨进程共享要考虑一致性与热更新。
- Python 数据管道：CPU 密集用 `multiprocessing`/`concurrent.futures.ProcessPoolExecutor`，IO 密集用 `ThreadPoolExecutor` 或 asyncio；不要用多线程跑纯计算。

**面试怎么答：** 先给判断维度：任务类型、共享状态、隔离要求、语言运行时。再给结论：CPU 密集用进程或核数规模的线程池，IO 密集用协程/事件循环，共享大状态用线程/协程加锁。然后补语言约束：Python GIL、Go goroutine、Java 虚拟线程、Node 单线程。最后补成本数字：进程毫秒级、线程几十微秒、协程纳秒级。

**易错点：**

- 「多线程一定比多进程快」：创建与切换线程更便宜，但共享内存的锁竞争、伪共享、缓存一致性可能让吞吐更差。
- 忽略 Python GIL：多线程跑 CPU 密集不会提速，甚至因切换更慢；必须用多进程或原生扩展释放 GIL。
- 协程里调用阻塞库：Go 会让 M 阻塞并 handoff，Python 会卡死整个事件循环，必须用线程池包装。
- 线程池大小拍脑袋：CPU 密集取核数附近，IO 密集按「核数 × (1 + 等待时间/计算时间)」估算，且要压测验证。

## 12. 并发与并行的区别（Amdahl 定律）

**并发是「多个任务在重叠的时间段内推进」，并行是「多个任务在同一时刻真正同时执行」。单核也能并发（时间片轮转），并行必须有多个执行单元。Amdahl 定律给出并行化的上限：若程序中不可并行的比例为 `1-p`，则无论加多少核，加速比都不会超过 `1/(1-p)`；这解释了为什么优化串行段往往比堆机器更有效。**

1. **并发（Concurrency）**：结构问题，指程序能把多个任务组织成互相交错的执行流；目标是「不阻塞」，典型手段是协程、事件循环、非阻塞 IO。
2. **并行（Parallelism）**：执行问题，指同一时刻有多个物理执行单元在跑；目标是「更快」，前提是任务可分解且硬件有多核。
3. **Amdahl 定律**：固定问题规模，`S(N) = 1 / ((1-p) + p/N)`，其中 `p` 是可并行部分占比，`N` 是并行度；`N→∞` 时上限为 `1/(1-p)`。
4. **Gustafson 定律**：固定时间而非问题规模，`S(N) = (1-p) + p·N`，说明问题规模随核数扩大时，并行收益可以持续增长；两定律不矛盾，前提不同。
5. **超线性加速**：理论上不应超过 `N`，但缓存变大、工作集缩小、IO 并行化可能带来少量超线性，不能当作常态。
6. **现实损耗**：线程创建/切换、锁竞争、内存带宽、伪共享、NUMA 远程访问、负载不均，都会让实测加速比低于公式值。

| 并行部分 p | N=2 | N=4 | N=8 | N=16 | N=64 | 上限 1/(1-p) |
| --- | --- | --- | --- | --- | --- | --- |
| 0.50 | 1.33 | 1.60 | 1.78 | 1.88 | 1.97 | 2.00 |
| 0.90 | 1.82 | 3.08 | 4.71 | 6.40 | 8.77 | 10.00 |
| 0.95 | 1.90 | 3.48 | 5.93 | 9.14 | 15.42 | 20.00 |
| 0.99 | 1.98 | 3.88 | 7.48 | 13.91 | 39.26 | 100.0 |

**示例（Go 计算不同并行度下的理论加速比，Go 1.21+）：**

```go
// go run amdahl.go
package main

import "fmt"

func speedup(p float64, n int) float64 {
    return 1 / ((1 - p) + p/float64(n))
}

func main() {
    ps := []float64{0.5, 0.9, 0.95, 0.99}
    ns := []int{2, 4, 8, 16, 64}
    fmt.Printf("%-6s", "N")
    for _, p := range ps {
        fmt.Printf("%9.0f%%", p*100)
    }
    fmt.Println()
    for _, n := range ns {
        fmt.Printf("%-6d", n)
        for _, p := range ps {
            fmt.Printf("%9.2f", speedup(p, n))
        }
        fmt.Println()
    }
    fmt.Println("N=64 时 p=0.99 的加速比 =", speedup(0.99, 64))
    fmt.Println("p=0.99 的理论上限 =", speedup(0.99, 1<<30))
}
```

```text
N           50%       90%       95%       99%
2          1.33      1.82      1.90      1.98
4          1.60      3.08      3.48      3.88
8          1.78      4.71      5.93      7.48
16         1.88      6.40      9.14     13.91
64         1.97      8.77     15.42     39.26
```

**验证并行是否真的生效：**

```bash
perf stat -e task-clock,cpu-migrations,cycles,instructions ./app
# task-clock 的 msec 数 × 核数 才是「CPU 时间」，看 wall time 才能算加速比
time ./app            # 实际耗时
```

**与业务/后端的联系：**

- 服务响应时间由「串行段」决定：一次请求里数据库单次查询、全局锁、串行日志都可能成为 `1-p`。堆核之前先用 profile 找串行热点。
- 压测时 CPU 利用率上不去但 QPS 也不涨，通常是锁竞争或串行资源（连接池、单例）限制，属于 Amdahl 的串行部分。
- 把「每请求一线程」改成协程，提升的是并发能力（同一时刻挂起更多等待），不是单请求的计算速度；两者要分开度量。
- 分布式系统里 Amdahl 依然成立：协调节点、全局锁、中心化存储就是串行段，扩展 worker 的收益会被它们吃掉。

**面试怎么答：** 先一句话区分：并发是「交替推进」，并行是「同时执行」，单核可并发不可并行。写出 Amdahl 公式 `S = 1/((1-p)+p/N)`，说明上限是 `1/(1-p)`，并举 p=0.9 时最多 10 倍的例子。再提 Gustafson 定律说明「扩大问题规模」时结论不同。最后落到工程：先优化串行段，再横向扩展，并用 profile 验证。

**易错点：**

- 把「并发」和「并行」混用：Go 的 goroutine 提供并发，能否并行取决于 `GOMAXPROCS` 与核数。
- 认为「加核就能线性提速」：Amdahl 的上限由串行比例决定，且锁竞争、内存带宽会让实测更低。
- 用 CPU 时间除以墙钟时间算加速比时单位不统一；应统一用 `time` 的 real 值或 `perf` 的 `task-clock`。
- 忽略超线程：逻辑核不等于物理核，计算密集型任务的 `N` 应按物理核估算，SMT 对 IPC 的提升有限。
