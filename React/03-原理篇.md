## 1. Fiber 是什么？解决了什么问题？

**Fiber** 是 React 16 引入的**新的协调引擎（reconciliation engine）**，也是一套**链表式的数据结构**。

**Fiber 节点结构（简化）：**

```js
{
  type,          // 组件类型
  key,
  stateNode,     // 对应的 DOM / 组件实例
  return,        // 父 Fiber
  child,         // 第一个子 Fiber
  sibling,       // 下一个兄弟 Fiber
  alternate,     // 指向另一棵树的对应节点（双缓存）
  memoizedState, // Hooks 链表
  flags,         // 副作用标记（增/删/改）
  lanes,         // 优先级
  ...
}
```

**解决的问题：**

- 旧的 Stack Reconciler 基于**递归**，一旦开始无法中断，大型组件树会**长时间阻塞主线程**，导致掉帧、卡顿。
- Fiber 把递归改为**可中断的循环（工作单元 + 链表遍历）**，让渲染可以被**暂停、恢复、丢弃、赋予优先级**。

**是否可中断：**

```
Stack（旧）：递归调用栈 —— 无法中断，一次到底
Fiber（新）：workLoop 循环 —— 每处理完一个 Fiber 检查是否该让出主线程
```

**要点：**

- Fiber 通过 `child`/`sibling`/`return` 三指针把树变成**链表**，从而用**循环**代替递归。
- 每个 Fiber 是一个**工作单元**，处理完可检查剩余时间，实现**时间切片**。
- 是并发特性（`useTransition`、Suspense）的基础。

## 2. React 的渲染流程（render 与 commit 两阶段）

React 的更新分为两个阶段：

**① Render 阶段（协调 / Reconciliation）——可中断**

- 从根 Fiber 开始遍历，为每个节点计算新的 props/state，执行组件的 `render`，生成 **workInProgress 树**。
- **纯计算，不操作 DOM**。
- 可被高优先级任务打断，中断后丢弃重来（因此**不能在 render 阶段产生副作用**）。

**② Commit 阶段（提交）——不可中断**

- 把 workInProgress 树的变更**一次性同步应用**到真实 DOM。
- 分为三个子阶段：
  - **before mutation**：DOM 变更前（`getSnapshotBeforeUpdate`）。
  - **mutation**：执行 DOM 增删改、`componentWillUnmount`。
  - **layout**：DOM 变更后（`componentDidMount`/`componentDidUpdate`、`useLayoutEffect`）。

```
触发更新 → Render 阶段（可中断，算出差异）→ Commit 阶段（同步，应用 DOM）→ 浏览器绘制 → useEffect
```

**要点：**

- `componentWillMount` / `componentWillUpdate` 等被废弃，正是因为 render 阶段可执行多次。
- `useLayoutEffect` 在 layout 子阶段**同步**执行（绘制前），`useEffect` 在绘制**之后**异步执行。

## 3. React 的 Diff 算法与三大策略

React 的 Diff 是**启发式 O(n)** 算法（通用树 Diff 是 O(n³)，不可接受），基于三条假设：

**① 跨层级比较策略：同层比较，不跨层移动**

- 只比较**同一层级**的节点；若节点类型不同，直接**销毁整棵子树并重建**。

```jsx
// div 变成 span：整棵子树重建
<div><Child /></div>
<span><Child /></Child></span>
```

**② 类型比较策略：类型不同则重建**

- 元素类型（`type`）不同 → 卸载旧节点、挂载新节点，不尝试复用。
- 类型相同 → 复用 DOM，只更新属性。

**③ 列表比较策略：用 `key` 标识同一元素**

- 列表 Diff 通过 `key` 匹配新旧节点，决定移动/复用/删除。
- 无 `key` 时会退化为按索引比较，性能差且易出错。

**列表 Diff 的过程：**

- React 用**两个指针**（新列表头尾、旧列表头尾）配合 `key` 的映射表，寻找可复用节点，生成最小移动操作。
- 常见判断：头头相同、尾尾相同、交叉比较；都匹配不上则查 map 复用。

```jsx
// 有 key：插入头部时旧项可复用
<ul>{items.map((i) => <li key={i.id}>{i.text}</li>)}</ul>
```

**要点：** Diff 只做**同层比较**，所以「把节点跨层移动」的代价很高（会被重建）；保持稳定的 `key` 与稳定的组件结构是性能关键。

## 4. 虚拟 DOM 是什么？有什么优缺点？

**虚拟 DOM（Virtual DOM）**：用 **JS 对象**描述真实 DOM 结构，React 在内存中计算差异后，只把必要变更应用到真实 DOM。

```js
// 真实 DOM 的 JS 描述
{ type: 'div', props: { className: 'box', children: [/* ... */] } }
```

**工作流程：**

```
JSX → React 元素 → 虚拟 DOM 树 → Diff 比较 → 最小 DOM 操作
```

**优点：**

- **减少 DOM 操作**：批量计算最小变更，避免频繁直接操作 DOM。
- **跨平台**：同一套虚拟 DOM 可渲染到 Web、Native、Canvas。
- **声明式**：开发者只描述 UI 状态，无需手工操作 DOM。
- **性能可预测**：把更新收敛到 Diff + 提交两个可控阶段。

**缺点 / 争议：**

- **有额外开销**：维护虚拟 DOM 树、Diff 计算本身需要内存与时间。
- **并非总是更快**：对**静态、极少更新**的页面，直接操作 DOM 可能更快；虚拟 DOM 的优势在于**中大型、频繁更新的复杂 UI**。
- **极端优化场景**可用 Svelte（编译期）或 SolidJS（细粒度响应式）替代。

**要点：** 虚拟 DOM 的核心价值是**抽象与批量更新**，而非单纯的「更快」。

## 5. React 的调度机制（Scheduler）与时间切片

**为什么需要调度？** 单线程 JS 与浏览器渲染共用一个主线程，长任务会阻塞渲染导致掉帧。

**时间切片（Time Slicing）**：把长任务拆成 5ms 左右的小片段，每执行完一段就**让出主线程**，让浏览器有机会响应输入、绘制，再继续。

**Scheduler 的核心机制：**

- 维护**任务队列**（按优先级：Immediate / UserBlocking / Normal / Low / Idle）。
- 用**宏任务**让出主线程：优先 `MessageChannel`（不触发渲染、开销小），降级用 `setTimeout`。
- 每处理完一个工作单元，检查当前帧的**剩余时间**：够就继续，不够就 `yield`。

```js
// 简化示意
function workLoop(deadline) {
  while (nextUnitOfWork && deadline.timeRemaining() > 1) {
    nextUnitOfWork = performUnitOfWork(nextUnitOfWork); // 处理一个 Fiber
  }
  if (nextUnitOfWork) scheduleCallback(workLoop); // 还有剩余 → 下一帧继续
}
```

**与 requestIdleCallback 的关系：** 早期考虑过 `requestIdleCallback`，但因其兼容性与 20ms 时间精度问题，React 自研了 Scheduler，用 `MessageChannel` + `performance.now()` 实现。

**要点：**

- 时间切片让 **Render 阶段**可中断，避免长任务阻塞；**Commit 阶段**不可中断（保证 DOM 一致性）。
- 只有**并发渲染**（如 `createRoot` + `useTransition`）才会真正体现可中断调度。

## 6. 优先级与 Lanes 模型

**Lanes 模型（React 18）** 用 **31 位二进制位**表示不同的优先级车道，可表达「多个优先级并存、可批处理」的复杂情况。

```js
// 简化：每条车道是一个二进制位
SyncLane            = 0b00001;   // 同步（离散输入如点击）
InputContinuousLane = 0b00010;   // 连续输入（拖拽、滚动）
DefaultLane         = 0b00100;   // 默认（数据请求回来）
TransitionLane      = 0b01000;   // 过渡（useTransition）
IdleLane            = 0b10000;   // 空闲
```

**位运算的好处：**

- **合并**：`lanes | otherLanes`（一个更新可属于多个优先级）。
- **判断**：`lanes & SyncLane`（是否包含某优先级）。
- **批量**：一次渲染可处理多条车道。

**优先级高低与抢占：**

- 高优先级（如用户输入）可**打断**低优先级（如过渡更新）的渲染，先渲染高优先级的部分。
- 被打断的低优先级任务之后**重新开始**（因为 render 阶段无副作用，可丢弃重算）。

**演进：**

```
React 15：无优先级
React 16：expirationTime（过期时间，递增数字）
React 17/18：lanes（位掩码，更灵活）
```

**要点：** 能说清「Lanes 用位运算表示优先级，支持合并/判断/批处理，配合 Scheduler 实现高优先级抢占低优先级」即可。

## 7. 批量更新机制（batching）

**批量更新**：把同一个事件循环中的多次状态更新**合并为一次渲染**，提升性能。

**React 17 及以前：**

- **只在 React 事件处理与生命周期中**自动批量。
- `setTimeout`、Promise、原生事件中**不批量**（会同步触发多次渲染）。

```jsx
setTimeout(() => {
  setA(1);
  setB(2);  // React 17：两次渲染
}, 0);
```

**React 18 起（Automatic Batching）：**

- 所有场景**自动批量**，包括 `setTimeout`、Promise、原生事件。

```jsx
setTimeout(() => {
  setA(1);
  setB(2);  // React 18：合并为一次渲染
}, 0);
```

**需要「不批量」时用 `flushSync`：**

```jsx
import { flushSync } from 'react-dom';

flushSync(() => setA(1)); // 立即同步刷新
flushSync(() => setB(2));
```

**原理：** React 维护一个「执行上下文」，进入批次时把更新入队，批次结束时统一调度；`flushSync` 会强制提前冲刷。

**要点：**

- 批量的本质是「**延迟到批次结束再统一渲染**」，因此 `setState` 后立刻读到的仍是旧值。
- 即使批量，多个更新也会**按顺序依次应用于新状态**（用函数式更新可链式累加）。

## 8. 双缓存机制（current 与 workInProgress）

React 在内存中同时维护**两棵 Fiber 树**：

| 树 | 说明 |
| --- | --- |
| **current 树** | 当前屏幕上显示的树 |
| **workInProgress 树** | 正在构建、准备替换的树 |

- 两棵树的节点通过 `alternate` 互相指向。
- 更新时在 workInProgress 上构建，**不改动 current**；构建完成后在 commit 阶段**一次性切换** `root.current` 指向新树。

```js
fiber.alternate === workInProgressFiber; // 互为 alternate
```

**好处：**

- **避免渲染中间态**：用户始终看到完整一致的 UI，不会看到「构建了一半」的界面。
- **可中断与丢弃**：render 阶段被打断时，直接丢弃 workInProgress 重来，current 不受影响。
- **复用节点**：下次更新可以复用上一次的 alternate，减少内存分配。

**类比：** 类似「双缓冲绘图」——在后台缓冲区画好整帧再切换显示，避免撕裂。

## 9. setState 与 useState 的更新原理与 updateQueue

**类组件 `setState`：**

1. 创建一条 **update 对象**（含 `payload`、优先级 `lane`），入队到该 Fiber 的 `updateQueue`（**环形链表**）。
2. 调度该 Fiber 的更新，进入 Render 阶段。
3. Render 时从 `updateQueue` **依次取出并合并**所有 update，计算新 state。

```js
// update 对象（简化）
{
  event: 'update',
  lane,               // 优先级
  payload,            // 新状态或函数
  next,               // 指向下一个 update（环形）
}
```

**函数组件 `useState`：**

- 每个 Hook 对应 `memoizedState` 链表上的一个节点，节点上的 `queue` 保存 update 环形链表。
- `dispatch`（即 setState）创建 update 入队 → 调度渲染 → 渲染时按顺序执行 update 计算新值。

**为什么多次 `setCount(count + 1)` 只 +1，而函数式可以 +2？**

- 对象式 update 的 `payload` 是**固定值**，多个相同的固定值合并后仍是该值。
- 函数式 update 的 `payload` 是**函数**，会**依次执行**，实现累加。

```jsx
setCount(count + 1);      // payload = 0+1 = 1
setCount(count + 1);      // payload = 0+1 = 1  → 最终 1

setCount((c) => c + 1);   // 依次执行 → 0→1→2
setCount((c) => c + 1);
```

**要点：** 更新以「队列 + 优先级」的形式存储，渲染时**批量合并**，这是「批量更新」与「函数式更新」存在的根本原因。

## 10. React 18 的并发特性（Concurrent Rendering）

**并发渲染**：渲染过程可被**中断、暂停、恢复甚至放弃**，让高优先级更新优先完成，保持 UI 响应。

**启用方式：** 用 `createRoot` 替代 `ReactDOM.render`。

```jsx
import { createRoot } from 'react-dom/client';
createRoot(document.getElementById('root')).render(<App />);
```

| 特性 | 作用 |
| --- | --- |
| **Automatic Batching** | 所有场景自动批量更新 |
| **Transitions** | `startTransition` / `useTransition` 标记非紧急更新 |
| **Suspense 增强** | 支持 SSR 流式渲染、`useDeferredValue`、并发特性下的加载态 |
| **useDeferredValue** | 延迟某值的更新 |
| **StrictMode 增强** | 开发环境双调用 effect，暴露问题 |
| **SSR 流式渲染** | `renderToPipeableStream`，支持选择性水合 |

**注意：并发渲染不是「多线程」**，而是**单线程下的可中断调度**（基于 Fiber + Scheduler + Lanes）。

**Suspense 与并发：**

```jsx
<Suspense fallback={<Spinner />}>
  <LazyComponent />
</Suspense>
```

- 组件「挂起」时展示 `fallback`，不阻塞其他部分渲染。
- 配合 `lazy` 实现代码分割。

## 11. React 19 主要新特性

| 特性 | 说明 |
| --- | --- |
| **Actions** | 用 `action` 处理表单提交，自动管理 pending/error/乐观更新 |
| **`useActionState`** | 管理表单 action 的状态 |
| **`useFormStatus`** | 子组件读取父表单提交状态 |
| **`useOptimistic`** | 乐观更新（先展示预期结果，失败再回滚） |
| **`use` API** | 在组件中读取 Promise / Context，可**条件调用** |
| **`ref` 作为 prop** | 函数组件可直接接收 `ref`，`forwardRef` 不再必需 |
| **文档元数据** | 组件内直接写 `<title>`、`<meta>`、`<link>`，自动提升到 `<head>` |
| **样式与脚本** | `<style>` / `<script>` 支持 `precedence`、去重、自动提升 |
| **资源预加载** | `preload`、`preinit`、`prefetchDNS` 等 API |
| **改进的 hydration** | 更精确的错误提示与恢复 |
| **Context 作为 Provider** | 可直接 `<Context>` 代替 `<Context.Provider>` |
| **支持自定义元素** | 对 Web Components 的属性/事件支持更完善 |

```jsx
// ref 作为 prop（React 19）
function Input({ ref, ...props }) {
  return <input ref={ref} {...props} />;
}

// Context 直接作为 Provider
<ThemeContext value="dark">
  <App />
</ThemeContext>
```

**要点：** React 19 的重心是**表单与数据交互**（Actions 系列）与**开发体验**（文档元数据、ref、`use`），并发特性继续沿用 18 的架构。

## 12. React 与 Vue 的 Diff 与响应式对比

| | React | Vue 3 |
| --- | --- | --- |
| 响应式原理 | **不可变 + 显式 setState** 触发重渲染 | **Proxy 依赖收集**，自动精确更新 |
| 更新粒度 | 组件级（重渲染整个组件子树） | 组件级 + 编译优化细粒度 |
| Diff 复杂度 | 启发式 O(n)，同层比较 | 编译期优化 + 双端比较 |
| 优化手段 | `memo`、`useMemo`、`useCallback` | 编译时静态提升、`PatchFlag`、Block Tree |
| 模板 | JSX（JS 表达能力完整） | 模板（编译期可做更多优化） |
| 心智模型 | 数据不可变，手动优化 | 响应式，自动追踪依赖 |

**Vue 3 的编译期优化：**

- **静态提升（Hoist Static）**：静态节点提升到渲染函数外，只创建一次。
- **补丁标志（PatchFlag）**：编译时标记动态部分，Diff 时只比较动态节点。
- **Block Tree**：把动态节点收集为数组，跳过静态节点遍历。

**要点：**

- React 靠**运行时** Diff + 手写优化（`memo` 等）；Vue 靠**编译时**信息减少 Diff 开销。
- React 的「不可变数据 + 显式更新」更利于大型应用的可预测性；Vue 的响应式更省心、上手更快。

## 13. React 的 StrictMode 做了什么？

**`StrictMode`** 是开发环境的辅助检查工具，**不渲染任何 UI**，只在开发模式下**故意暴露问题**。

```jsx
<React.StrictMode>
  <App />
</React.StrictMode>
```

**会做的事：**

| 检查 | 说明 |
| --- | --- |
| **组件双调用** | 开发环境下函数组件、`render`、`shouldComponentUpdate` 等会被**调用两次**，检查是否有副作用（React 18） |
| **Effect 双执行** | 挂载 → 卸载 → 再挂载，检查清理函数是否完整（React 18） |
| **检测过时 API** | 提示使用 `UNSAFE_` 生命周期、旧 Context API 等 |
| **检测意外副作用** | 暴露在 render 阶段修改外部状态的问题 |

**为什么双调用？** 并发渲染下 render 可能被多次执行，StrictMode 通过双调用来**提前暴露**不纯的组件（如 render 里发请求、改全局变量）。

**要点：**

- **只在开发环境生效**，生产构建无影响。
- 双调用**不是 bug**，是刻意设计；若出现数据请求发两次，说明副作用位置不对（应放 effect 中并做好清理/幂等）。
- 可以局部包裹子树以缩小检查范围。

## 14. React 组件的更新是如何触发的（重渲染原因）

**组件重渲染（re-render）的常见触发原因：**

| 原因 | 说明 | 优化手段 |
| --- | --- | --- |
| **自身 state 变化** | `setState` / `useState` 更新 | `useState` 值相同时跳过 |
| **父组件重渲染** | 默认会**递归重渲染所有子组件** | `React.memo` |
| **props 变化** | 父传入的 props 引用或值变化 | `memo` + 稳定引用 |
| **Context 变化** | Provider 的 `value` 变化 | 拆分 Context、稳定 value |
| **自定义 Hook 内 state** | Hook 内的 state 变化 | 关注点拆分 |
| **`forceUpdate`** | 类组件强制更新 | 尽量避免 |
| **`useReducer` 的 dispatch** | 状态变化 | 合理划分状态 |

**关键概念：**

- **Render ≠ DOM 更新**：重渲染只是重新执行组件函数、生成新虚拟 DOM，Diff 后**没有变化就不会改 DOM**。
- 父组件重渲染会**默认带动所有子组件重渲染**（不管 props 是否变化），这是 `React.memo` 的用武之地。

```jsx
// 父重渲染时，Child 默认也会重渲染
function Parent() {
  const [count, setCount] = useState(0);
  return (
    <>
      <button onClick={() => setCount(count + 1)}>{count}</button>
      <Child />   {/* count 变化会带动 Child 重渲染 */}
    </>
  );
}

// 用 memo 阻断
const Child = React.memo(function Child() {
  return <div>static</div>;
});
```

**要点：**

- 「**状态提升**不当」会导致大面积重渲染，应把状态放在**最接近使用处**。
- `children` 作为 props 传入可避免重渲染（因为 `children` 元素引用未变）：

  ```jsx
  // 优化：把不变的部分作为 children 传入
  <Wrapper><ExpensiveTree /></Wrapper>
  ```

**面试总结一句话：** 更新由 **state/props/Context 变化**触发，**父组件重渲染会默认带动子组件**，可用 `memo`、稳定引用、状态就近、`children` 透传等手段控制渲染范围。
