## 1. Web 框架对比与选型

**核心结论：所有 Go Web 框架最终都实现 `http.Handler`，差别只在路由树与请求上下文的封装。**

1. **标准库**：`net/http` 负责连接、HTTP/2、TLS、超时与 `ServeMux`；Go 1.22 起支持 `GET /user/{id}` 的方法 + 路径参数模式，简单服务无需框架。
2. **Gin**：基数树路由，`*gin.Context` 打包请求、响应、参数与中间件链；生态最大，但 handler 签名不是标准 `http.Handler`。
3. **Echo**：性能与 Gin 同级，Binder/Validator/Renderer 均为可替换接口，整体仍实现 `http.Handler`。
4. **Fiber**：基于 `fasthttp`，微基准最快，但**不兼容 `net/http`**，pprof、promhttp、gRPC-Gateway 等标准生态无法直接复用。
5. **Chi**：纯标准库风格，中间件就是 `func(http.Handler) http.Handler`，适合长期维护、与标准生态深度集成的服务。

| 维度 | net/http | Gin | Echo | Fiber | Chi |
| --- | --- | --- | --- | --- | --- |
| 路由 | ServeMux（1.22 支持通配符） | 基数树 | 基数树 | 自研基数树 | 前缀树 |
| 上下文 | `*http.Request` | `*gin.Context`（池化） | `echo.Context` | `*fiber.Ctx`（池化） | `*http.Request` |
| 中间件签名 | `func(http.Handler) http.Handler` | `gin.HandlerFunc` | `echo.MiddlewareFunc` | `fiber.Handler` | 同标准库 |
| 兼容 net/http | 原生 | 部分（`WrapH` 桥接） | 是 | **否** | 完全 |
| 生态 | 标准库 | 最大 | 大 | 中 | 中 |
| 路由基准 | 基准线 | 高 | 高 | 最高 | 高 |

> 路由基准差距通常在几十纳秒，而一次 DB 查询是毫秒级；用 benchmark 决定架构，是用 0.1% 的耗时决定 100% 的选型。

**选型维度：**团队熟悉度（迁移成本最高）> 生态兼容（pprof/promhttp/Gateway）> 功能完备（绑定、校验、错误渲染）> 性能（只有网关/代理敏感）> 可维护性。

**不该用框架：**1~3 个内部接口、健康检查、Webhook 用 `net/http` 足够；反向代理与边车用 `httputil.ReverseProxy` 或 Chi（Fiber 的 fasthttp 语义有兼容坑）；需要 hijack/WebSocket/HTTP2 底层能力或二进制体积敏感时，标准库更合适。

```go
package main

import (
	"context"
	"errors"
	"log"
	"net/http"
	"time"

	"github.com/gin-gonic/gin"
)

func createOrder(ctx context.Context, sku string) error {
	select {
	case <-ctx.Done():
		return ctx.Err()
	case <-time.After(50 * time.Millisecond):
		return nil
	}
}

func healthz(w http.ResponseWriter, r *http.Request) { _, _ = w.Write([]byte(`{"status":"ok"}`)) }

func main() {
	r := gin.New()        // New 不带默认中间件，行为可控
	r.Use(gin.Recovery()) // 只加必需的 panic 兜底
	r.GET("/healthz", gin.WrapH(http.HandlerFunc(healthz)))

	r.POST("/orders", func(c *gin.Context) {
		var req struct {
			SKU string `json:"sku" binding:"required"`
		}
		if err := c.ShouldBindJSON(&req); err != nil {
			c.JSON(http.StatusBadRequest, gin.H{"error": err.Error()})
			return // c.JSON 不会中断 handler，必须 return
		}
		// 超时挂在请求 ctx 上，客户端断开或超时能一路传到下游
		ctx, cancel := context.WithTimeout(c.Request.Context(), 2*time.Second)
		defer cancel()
		if err := createOrder(ctx, req.SKU); err != nil {
			if errors.Is(err, context.DeadlineExceeded) {
				c.JSON(http.StatusGatewayTimeout, gin.H{"error": "下游超时"})
				return
			}
			c.JSON(http.StatusInternalServerError, gin.H{"error": "创建失败"})
			return
		}
		c.JSON(http.StatusCreated, gin.H{"ok": true})
	})

	srv := &http.Server{Addr: ":8080", Handler: r, ReadHeaderTimeout: 5 * time.Second}
	// ErrServerClosed 是正常关闭信号，不能当致命错误
	if err := srv.ListenAndServe(); err != nil && !errors.Is(err, http.ErrServerClosed) {
		log.Fatal(err)
	}
}
```

**易错点：**

- Fiber 不兼容 `net/http`，接入标准中间件或 gRPC-Gateway 只能重写入口层，选型先看兼容性。
- `c.JSON` 只写响应、**不终止**函数，不 `return` 会重复写 header。
- 路由冲突（`/user/:id` 与 `/user/new`）在启动注册时直接 panic。
- `gin.Default()` 隐式挂载 Logger 与 Recovery，叠加自定义日志会打两份。
- 框架 benchmark 多只测空 handler 路由，不覆盖 JSON 序列化、绑定反射与中间件链。

## 2. Gin 的中间件原理

**核心结论：中间件是一条 `[]HandlerFunc` 链，由 `Context.index` 游标驱动；`c.Next()` 推进游标，`c.Abort()` 把游标跳到终点。**

1. **入口**：`Engine.ServeHTTP` 匹配路由后，把「全局 + 分组 + 业务 handler」合并为 `c.handlers`，`c.index = -1`，再调一次 `c.Next()`。
2. **洋葱模型**：`Next()` 是 `for c.index < len(c.handlers)` 循环；`Next()` **之前**是入栈，**之后**是出栈，形成 A→B→handler→B→A。
3. **终止**：`Abort()` 把 `c.index` 设为 `abortIndex`（63），循环立即结束；但当前函数 `Abort()` 之后的代码**仍会执行**。
4. **Context 池化**：`gin.Context` 由 `sync.Pool` 复用，请求结束 `reset()` 清空 `Keys`、`handlers`、writer；异步持有原 `c` 会读到下一个请求的数据。
5. **与标准库差异**：标准库包装 handler、无共享游标、天然可组合；Gin 共享同一 Context，能在 `Next()` 前后改状态，也更容易写错顺序。

```go
// gin.Context.Next 的核心逻辑（v1.10）
func (c *Context) Next() {
	c.index++
	for c.index < int8(len(c.handlers)) {
		c.handlers[c.index](c)
		c.index++
	}
}

func (c *Context) Abort() { c.index = abortIndex } // abortIndex = 63
```

| 写法 | 后续 handler | 当前函数剩余代码 |
| --- | --- | --- |
| `c.Next()` | 执行 | 等后续全部返回后继续 |
| `c.Abort()` | **不执行** | **仍执行** |
| `c.Abort(); return` | 不执行 | 不执行 |
| 直接 `return` | **仍执行** | 不执行 |

> 鉴权失败只写 `c.JSON(401)` 而不 `Abort`，请求会继续进入业务 handler，这是 Gin 项目最常见的安全漏洞。

**顺序：**`Recovery` 最外层兜 panic，`RequestID` 尽早生成供日志关联，`AccessLog` 记录耗时，分组 `Auth` 只对 `/api` 生效；`group.Use` 只影响**之后**注册的路由。

```go
package middleware

import (
	"context"
	"log/slog"
	"net/http"
	"time"

	"github.com/gin-gonic/gin"
	"github.com/google/uuid"
)

func RequestID() gin.HandlerFunc {
	return func(c *gin.Context) {
		id := c.GetHeader("X-Request-ID") // 优先复用网关传入的 ID
		if id == "" {
			id = uuid.NewString()
		}
		c.Set("request_id", id)
		c.Writer.Header().Set("X-Request-ID", id)
		c.Next()
	}
}

func AccessLog() gin.HandlerFunc {
	return func(c *gin.Context) {
		start := time.Now()
		c.Next() // 返回时业务已执行完
		slog.Info("access", "path", c.Request.URL.Path, "status", c.Writer.Status(),
			"cost_ms", time.Since(start).Milliseconds(), "rid", c.GetString("request_id"))
	}
}

// 失败必须 Abort + return，否则会继续进入业务 handler
func Auth() gin.HandlerFunc {
	return func(c *gin.Context) {
		if c.GetHeader("Authorization") == "" {
			c.AbortWithStatusJSON(http.StatusUnauthorized, gin.H{"error": "缺少凭证"})
			return
		}
		c.Next()
	}
}

// 异步任务必须 Copy，且不能复用会随请求取消的 ctx
func AsyncAudit() gin.HandlerFunc {
	return func(c *gin.Context) {
		cp := c.Copy()
		go audit(context.WithoutCancel(cp.Request.Context()), cp.GetString("request_id"))
		c.Next()
	}
}
```

| 维度 | `net/http` | Gin |
| --- | --- | --- |
| 形态 | 高阶函数包装 `http.Handler` | `[]gin.HandlerFunc` 顺序执行 |
| 共享状态 | `context.WithValue` | `c.Set/c.Get` |
| 中断 | 不调用 `next.ServeHTTP` | `c.Abort()` 跳过剩余 handler |
| 善后 | `next.ServeHTTP` 返回后 | `c.Next()` 返回后 |
| 复用风险 | 无 | Context 池化，异步必须 `Copy()` |

**易错点：**

- `Abort()` 后忘记 `return`，函数继续写响应，出现「已 Abort 却仍返回业务数据」。
- 中间件里直接 `go func(){ c.GetString(...) }()`，请求结束 Context 被复用，数据串到别的请求。
- `c.Copy()` 复制出的 Writer 不可用，异步任务只能读数据、做日志/审计，不能写响应。
- `gin.Recovery()` 只捕获**当前 goroutine** 的 panic，子 goroutine 仍需自己 recover。

## 3. gRPC 与 Protobuf

**核心结论：Protobuf 用「字段编号 + 二进制编码」替代「字段名 + 文本」，gRPC 把「方法调用」映射为 HTTP/2 的一条流。**

1. **TLV**：字段编码为 `tag + value`，`tag = (field_number << 3) | wire_type`；编号越小 tag 越短，1~15 号留给高频字段。
2. **Varint**：整数按 7 位一组、最高位表示是否继续，小数值只占 1 字节；`sint*` 先做 ZigZag 把负数映射成正数。
3. **Length-delimited**：`string`、`bytes`、嵌套 message、packed repeated 先写长度再写内容。
4. **默认值不编码**：proto3 零值字段直接省略，「未设置」与「设为 0」无法区分，需要区分时用 `optional`（生成指针）。
5. **兼容性**：字段编号发布后**不能改、不能复用**；删字段用 `reserved` 占住编号与名字；新增字段必须可选。

wire type 共四类：0 Varint（整数、bool、enum）、1 64-bit（`fixed64`、`double`）、2 Length-delimited（`string`、`bytes`、嵌套 message、packed repeated）、5 32-bit（`fixed32`、`float`）。

**为什么比 JSON 小：**字段名不进报文（只传编号）、整数变长编码、无引号逗号等分隔符；代价是可读性差。

四种通信模式：Unary（`rpc F(Req) returns (Resp)`，查询/下单）、Server Streaming（返回 `stream Resp`，大结果集/订阅，循环 `Recv`）、Client Streaming（入参 `stream Req`，批量上报，`Send` 后 `CloseAndRecv`）、Bidirectional（双向流，实时通信）。

**HTTP/2 能力：**单连接多路复用多个 stream，消除 HTTP/1.1 队头阻塞；HPACK 压缩头部；内置流量控制。gRPC 用 trailers 传 `grpc-status`，所以 HTTP 状态码永远是 200，业务错误要看 trailer。

```bash
go install google.golang.org/protobuf/cmd/protoc-gen-go@latest
go install google.golang.org/grpc/cmd/protoc-gen-go-grpc@latest

# paths=source_relative 让输出目录与 proto 目录一一对应
protoc -I api --go_out=. --go_opt=paths=source_relative \
  --go-grpc_out=. --go-grpc_opt=paths=source_relative api/order/v1/order.proto
```

生成物中 `CreateOrderRequest` 的字段编号（`sku=1`、`quantity=2`、`request_id=3`）一旦发布不能改，`request_id` 用作幂等键。

```go
package main

import (
	"context"
	"log"
	"net"
	"time"

	"google.golang.org/grpc"
	"google.golang.org/grpc/codes"
	"google.golang.org/grpc/credentials/insecure"
	"google.golang.org/grpc/metadata"
	"google.golang.org/grpc/status"

	orderv1 "example.com/shop/api/order/v1"
)

type server struct {
	orderv1.UnimplementedOrderServiceServer // 必须嵌入，新增方法时才不会编译失败
}

func (s *server) CreateOrder(ctx context.Context, req *orderv1.CreateOrderRequest) (*orderv1.CreateOrderReply, error) {
	if req.GetSku() == "" {
		return nil, status.Error(codes.InvalidArgument, "sku 不能为空")
	}
	_, _ = metadata.FromIncomingContext(ctx) // metadata 走 header，别塞大对象
	// 客户端 deadline 经 grpc-timeout 传到服务端，服务端必须继续向下传递
	if _, ok := ctx.Deadline(); !ok {
		return nil, status.Error(codes.DeadlineExceeded, "缺少超时设置")
	}
	return &orderv1.CreateOrderReply{OrderId: "o-1001"}, nil
}

// Unary 拦截器：统一记日志与耗时
func loggingInterceptor(ctx context.Context, req any, info *grpc.UnaryServerInfo, handler grpc.UnaryHandler) (any, error) {
	start := time.Now()
	resp, err := handler(ctx, req)
	st, _ := status.FromError(err)
	log.Printf("grpc method=%s code=%s cost=%s", info.FullMethod, st.Code(), time.Since(start))
	return resp, err
}

func main() {
	lis, _ := net.Listen("tcp", ":9090")
	// 多个拦截器必须用 Chain，重复传 UnaryInterceptor 只有最后一个生效
	s := grpc.NewServer(grpc.ChainUnaryInterceptor(loggingInterceptor))
	orderv1.RegisterOrderServiceServer(s, &server{})
	go func() { _ = s.Serve(lis) }()
	defer s.GracefulStop() // 等待在途 RPC 结束，比 Stop 温和

	// v1.63+ 用 grpc.NewClient（懒连接，不需要 WithBlock）
	conn, _ := grpc.NewClient("127.0.0.1:9090", grpc.WithTransportCredentials(insecure.NewCredentials()))
	defer conn.Close()
	ctx, cancel := context.WithTimeout(context.Background(), 800*time.Millisecond)
	defer cancel()
	ctx = metadata.AppendToOutgoingContext(ctx, "x-tenant-id", "t-1")

	_, err := orderv1.NewOrderServiceClient(conn).CreateOrder(ctx,
		&orderv1.CreateOrderRequest{Sku: "sku-1", Quantity: 2})
	// InvalidArgument 重试没有意义，DeadlineExceeded 才降级或重试
	if st, _ := status.FromError(err); st.Code() == codes.DeadlineExceeded {
		log.Println("下游超时，可降级")
	}
}
```

| 维度 | gRPC + Protobuf | REST + JSON |
| --- | --- | --- |
| 契约 | `.proto` 强类型，多语言 stub | OpenAPI 需额外维护 |
| 性能 | 二进制、体积小、多路复用 | 文本、体积大 |
| 流式 | 原生四种模式 | 需 SSE/WebSocket |
| 浏览器 | 需 gRPC-Web 或网关 | 原生 |
| 适用 | 内部服务、低延迟、强契约 | 开放 API、前端直连 |

**易错点：**

- 修改已发布字段编号或复用被删编号会让新旧版本解析出错；删字段必须 `reserved 3;`。
- proto3 无法区分「未传」与「零值」，需要区分时加 `optional`，不要靠 `0` 或 `""` 猜。
- 客户端不设 deadline，下游卡死会一直占用 goroutine 与连接。
- 流式 handler 忘记处理 `io.EOF` 或 `ctx.Done()`，连接断开后 goroutine 永久阻塞。
- `grpc-status` 在 trailer 里，HTTP 层永远 200，通用 HTTP 监控会把失败显示成成功。

## 4. 微服务架构实践

**核心结论：边界按「业务能力 + 数据所有权」划，而不是按技术分层划；拆分换来决定独立演进，代价是分布式复杂度。**

1. **拆分**：以 DDD 限界上下文为单位，一个上下文 = 一个服务 + 一套数据 + 一个团队；判据是能否独立变更、部署、扩容。
2. **数据私有**：服务独占库表，跨服务只走 API 或事件；共享数据库就是分布式单体。
3. **注册发现**：Consul/etcd 是客户端发现（SDK 拿实例列表负载均衡）；K8s Service + CoreDNS 是服务端发现（IPVS 转发），对代码零侵入。
4. **可观测**：日志、指标、链路追踪；跨服务传 W3C `traceparent`，MQ 消息头也要带 context。
5. **治理**：超时、重试、熔断、限流、隔离成对出现；只加超时不加重试预算会打得更死。

| 维度 | 单体 | 微服务 |
| --- | --- | --- |
| 部署 | 一个制品 | 每服务独立流水线 |
| 事务 | 本地事务，强一致 | Saga/TCC/Outbox，最终一致 |
| 调用 | 进程内函数 | 网络调用，需超时与序列化 |
| 数据 | 一个库，JOIN 随意 | 数据私有，跨服务组装 |
| 扩容 | 整体扩容 | 按热点服务扩容 |
| 排障 | 单一日志 | 需 trace id 串全链路 |

**发现方案：**Consul（CP/Raft，主动探测，适合跨云多语言）、etcd（CP/Raft，Lease keepalive，Go 生态友好）、K8s Service（依赖 apiserver 与 kubelet 探针，对代码零侵入）。

**常见误区：**共享库表的分布式单体、一个 CRUD 拆五个服务的过度拆分、每层都重试 3 次导致流量放大 27 倍。纠正方向是数据私有、异步解耦、只在一层重试。

```go
package main

import (
	"context"
	"log"
	"net/http"
	"time"

	"go.opentelemetry.io/contrib/instrumentation/net/http/otelhttp"
	"go.opentelemetry.io/otel"
	"go.opentelemetry.io/otel/attribute"
	"go.opentelemetry.io/otel/codes"
	"go.opentelemetry.io/otel/exporters/otlp/otlptrace/otlptracehttp"
	"go.opentelemetry.io/otel/propagation"
	"go.opentelemetry.io/otel/sdk/resource"
	sdktrace "go.opentelemetry.io/otel/sdk/trace"
)

func initTracer(ctx context.Context) (func(context.Context) error, error) {
	exp, err := otlptracehttp.New(ctx) // 默认读 OTEL_EXPORTER_OTLP_ENDPOINT
	if err != nil {
		return nil, err
	}
	tp := sdktrace.NewTracerProvider(
		sdktrace.WithBatcher(exp, sdktrace.WithBatchTimeout(5*time.Second)),
		sdktrace.WithSampler(sdktrace.ParentBased(sdktrace.TraceIDRatioBased(0.1))),
		sdktrace.WithResource(resource.NewWithAttributes("", attribute.String("service.name", "order"))),
	)
	otel.SetTracerProvider(tp)
	// W3C TraceContext + Baggage：跨服务、跨网关都能透传
	otel.SetTextMapPropagator(propagation.NewCompositeTextMapPropagator(
		propagation.TraceContext{}, propagation.Baggage{}))
	return tp.Shutdown, nil
}

func handleCreateOrder(w http.ResponseWriter, r *http.Request) {
	ctx, span := otel.Tracer("order").Start(r.Context(), "CreateOrder")
	defer span.End()

	// Transport 自动注入 traceparent，并生成 client span
	client := &http.Client{Timeout: 2 * time.Second, Transport: otelhttp.NewTransport(http.DefaultTransport)}
	req, _ := http.NewRequestWithContext(ctx, http.MethodGet, "http://inventory:8080/stock", nil)
	resp, err := client.Do(req)
	if err != nil {
		span.RecordError(err)
		span.SetStatus(codes.Error, err.Error())
		http.Error(w, "internal error", http.StatusInternalServerError)
		return
	}
	defer resp.Body.Close() // 漏掉会泄漏连接
	w.WriteHeader(http.StatusCreated)
}

func main() {
	shutdown, err := initTracer(context.Background())
	if err != nil {
		log.Fatal(err)
	}
	defer func() { _ = shutdown(context.Background()) }() // 退出前 flush，否则最后一批 span 丢失

	mux := http.NewServeMux()
	mux.HandleFunc("/orders", handleCreateOrder)
	// 入口自动提取 traceparent 并创建 server span
	_ = http.ListenAndServe(":8080", otelhttp.NewHandler(mux, "order-http"))
}
```

> 异步链路不会自动传 context：生产者把 `traceparent` 写进消息 header，消费者用 `otel.GetTextMapPropagator().Extract(...)` 重建父 span，否则链路在 MQ 处断掉。

**易错点：**

- 服务拆了但共用一个库，任何表结构变更都要多服务联合发布。
- 只在最外层设超时，内层 RPC 不继承 ctx deadline，外层超时后内层还在跑。
- 重试不加退避、不限次数、不区分幂等，故障时流量成倍放大。
- trace context 只在 HTTP 头里传，MQ 与定时任务链路断开，无法还原调用路径。

## 5. 限流与熔断

**核心结论：限流保护自己不被流量打垮，熔断保护自己不被下游拖垮；重试只有在限流与熔断都生效时才安全。**

| 算法 | 原理 | 突发 | 复杂度 | 典型实现 |
| --- | --- | --- | --- | --- |
| 固定窗口 | 每周期一个计数器，到点清零 | 边界可打 2 倍 | 低，O(1) | 本地计数、Redis INCR |
| 滑动窗口 | 分桶统计最近 N 个桶 | 较平滑 | 中，O(桶数) | Sentinel、Redis ZSET |
| 漏桶 | 请求入队，恒定速率流出 | **不允许** | 中，需队列 | uber-go/ratelimit |
| 令牌桶 | 按速率放令牌，桶容量即突发上限 | 允许 `burst` | 低，O(1) | `x/time/rate` |

**`x/time/rate`：**`rate.NewLimiter(rate.Limit(100), 200)` 表示每秒 100 个令牌、允许瞬时 200 的突发；`Allow()` 非阻塞，`Wait(ctx)` 阻塞并在 ctx 到期返回错误，`WaitN` 在 `n > burst` 时直接报错；`Reserve()` 返回 `*Reservation`，用 `Delay()` 判断等待时间、`Cancel()` 归还令牌。限流器是**进程内**的，多副本实际阈值 = 单机阈值 × 副本数。

**熔断三态：**closed 放行并统计失败；连续失败达到阈值进入 open，直接拒绝并降级；`Timeout` 后进入 half-open，只放行 `MaxRequests` 个试探，全部成功回 closed，任一失败回 open。

**重试：**只对幂等且可重试的错误（超时、连接失败、5xx）重试，指数退避 + jitter 防重试风暴，总时长受 ctx deadline 约束。

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"log"
	"math/rand"
	"time"

	"github.com/sony/gobreaker"
	"golang.org/x/time/rate"
)

var limiter = rate.NewLimiter(rate.Limit(100), 200) // 100 rps，允许 200 突发

// 熔断器按「下游依赖」实例化，不要所有依赖共用一个
var paymentBreaker = gobreaker.NewCircuitBreaker(gobreaker.Settings{
	Name:        "payment",
	MaxRequests: 5,                // half-open 最多放 5 个试探请求
	Interval:    10 * time.Second, // closed 状态统计清零周期
	Timeout:     30 * time.Second, // open 持续多久转 half-open
	ReadyToTrip: func(c gobreaker.Counts) bool { return c.ConsecutiveFailures >= 10 },
})

// 入口限流：Reserve 不阻塞，Delay() > 0 直接 429 并回填 Retry-After
func allow() bool {
	r := limiter.Reserve()
	if !r.OK() {
		return false
	}
	if r.Delay() > 0 {
		r.Cancel() // 不等，归还令牌
		return false
	}
	return true
}

func callPayment(ctx context.Context, orderID string) (string, error) {
	v, err := paymentBreaker.Execute(func() (any, error) {
		var lastErr error
		for i := 0; i < 3; i++ {
			// 每次从上游 ctx 派生超时，保证总耗时受控
			attemptCtx, cancel := context.WithTimeout(ctx, 300*time.Millisecond)
			id, err := doPay(attemptCtx, orderID)
			cancel()
			if err == nil {
				return id, nil
			}
			lastErr = err
			if !isRetryable(err) {
				break
			}
			// 指数退避 + jitter：100ms、200ms、400ms 附近随机
			base := time.Duration(1<<i) * 100 * time.Millisecond
			jitter := time.Duration(rand.Int63n(int64(base/2 + 1)))
			select {
			case <-ctx.Done():
				return nil, ctx.Err()
			case <-time.After(base + jitter):
			}
		}
		return nil, lastErr
	})
	if errors.Is(err, gobreaker.ErrOpenState) || errors.Is(err, gobreaker.ErrTooManyRequests) {
		return "", fmt.Errorf("支付服务熔断: %w", err) // 走降级，如落本地待支付队列
	}
	if err != nil {
		return "", err
	}
	return v.(string), nil
}

func doPay(ctx context.Context, orderID string) (string, error) {
	select {
	case <-ctx.Done():
		return "", ctx.Err()
	case <-time.After(80 * time.Millisecond):
		return "pay-" + orderID, nil
	}
}

func isRetryable(err error) bool {
	return errors.Is(err, context.DeadlineExceeded) || errors.Is(err, context.Canceled)
}
```

**易错点：**

- `rate.NewLimiter` 第一个参数是 `rate.Limit`（每秒事件数），写成 `100*time.Second` 是类型错误。
- 忽略 `Wait(ctx)` 的返回值，ctx 超时后请求仍继续执行，等于没限流。
- 每个请求 `NewLimiter` 相当于每次桶都是满的，限流完全失效。
- 熔断器全局共用一个，支付故障会把库存、用户服务一起熔断。
- 重试次数与超时相乘失控：3 次 × 2s = 6s，超过上游 deadline 后全是无效请求。

## 6. 优雅关闭

**核心结论：先摘流量，再停止接收新请求，等在途请求结束，最后按逆序释放资源。**

1. `http.Server.Shutdown(ctx)` 关闭所有 `Listener`（`Accept` 返回 `ErrServerClosed`），关闭 idle 的 keep-alive 连接，等待活跃请求完成或 ctx 超时。
2. 返回 `ctx.Err()`（通常是 `DeadlineExceeded`）时说明没等完，应调用 `srv.Close()` 强制断开兜底。
3. `Shutdown` **不等待** hijacked 连接（WebSocket）和自行启动的 goroutine，需要连接注册表或 `RegisterOnShutdown`。
4. `SIGTERM`（`docker stop`、K8s 删除 Pod）可捕获；`SIGKILL` 不可捕获，超过 grace period 直接强杀。
5. 关闭顺序：停收流量 → 停消息消费（处理完在途消息并提交位点）→ 等后台 goroutine → flush 生产者 → 关 Redis/DB。

| 方法 | 新连接 | 在途请求 | 适用 |
| --- | --- | --- | --- |
| `Shutdown(ctx)` | 拒绝 | 等待完成 | 正常发布、缩容 |
| `Close()` | 拒绝 | **直接中断** | Shutdown 超时兜底 |
| `os.Exit` / `log.Fatal` | 进程消失 | 全部丢失 | 仅初始化失败 |

```go
package main

import (
	"context"
	"database/sql"
	"errors"
	"fmt"
	"log"
	"net/http"
	"os/signal"
	"syscall"
	"time"

	"github.com/redis/go-redis/v9"
	"golang.org/x/sync/errgroup"
)

func main() {
	// 收到 SIGTERM/SIGINT 时 ctx 被取消；defer stop 恢复默认信号行为
	ctx, stop := signal.NotifyContext(context.Background(), syscall.SIGINT, syscall.SIGTERM)
	defer stop()

	db, err := sql.Open("mysql", "user:pass@tcp(127.0.0.1:3306)/shop?parseTime=true")
	if err != nil {
		log.Fatal(err)
	}
	db.SetMaxOpenConns(50)
	rdb := redis.NewClient(&redis.Options{Addr: "127.0.0.1:6379", PoolSize: 50})

	srv := &http.Server{
		Addr:              ":8080",
		Handler:           http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) { w.WriteHeader(http.StatusOK) }),
		ReadHeaderTimeout: 5 * time.Second,
	}
	g, gctx := errgroup.WithContext(ctx)

	g.Go(func() error {
		if err := srv.ListenAndServe(); err != nil && !errors.Is(err, http.ErrServerClosed) {
			return fmt.Errorf("http serve: %w", err)
		}
		return nil
	})
	g.Go(func() error {
		<-gctx.Done()
		// 超时时间必须小于 K8s terminationGracePeriodSeconds
		shutdownCtx, cancel := context.WithTimeout(context.Background(), 20*time.Second)
		defer cancel()
		if err := srv.Shutdown(shutdownCtx); err != nil {
			_ = srv.Close() // 超时兜底，避免进程卡死
			return fmt.Errorf("http shutdown: %w", err)
		}
		return nil
	})
	if err := g.Wait(); err != nil {
		log.Printf("shutdown with error: %v", err)
	}

	// 资源逆序关闭：连接池最后关，避免在途请求用到已关闭的 DB
	_ = rdb.Close()
	_ = db.Close()
	log.Println("bye")
}
```

**K8s 配合：**`terminationGracePeriodSeconds` 必须大于 `preStop` 与 `Shutdown` 超时之和；`preStop` 里 `sleep 8` 用于等 Endpoints 摘除和 kube-proxy/Ingress 规则同步，避免关闭期间仍有新流量打进来。

**易错点：**

- 用 `os.Exit` 或 `log.Fatal` 处理信号，defer 全部跳过：消息未提交、连接未 flush、日志未落盘。
- 把 `http.ErrServerClosed` 当错误 `Fatal`，每次正常发布都打出致命日志。
- 先关 DB 再等在途请求，运行中的事务报 `sql: database is closed`。
- `terminationGracePeriodSeconds` 小于 `preStop + Shutdown`，Pod 被 SIGKILL，优雅关闭白做。

## 7. 缓存与 Redis 的使用

**核心结论：缓存的核心不是「存」，而是「未命中时如何保护下游」与「更新时如何收敛不一致」。**

| 问题 | 触发条件 | 解决方案 |
| --- | --- | --- |
| 缓存穿透 | 查询**不存在**的数据，缓存永不命中 | 空值缓存（短 TTL）、布隆过滤器、参数校验 |
| 缓存击穿 | **单个热点 key** 过期瞬间 | 互斥重建（singleflight/分布式锁）、逻辑过期 |
| 缓存雪崩 | 大量 key 同时过期，或 Redis 故障 | TTL 随机抖动、多级缓存、熔断降级、集群 |

| 策略 | 读 | 写 | 缺点 |
| --- | --- | --- | --- |
| Cache-Aside | 读缓存，未命中读 DB 回填 | 更新 DB 后**删**缓存 | 存在短暂不一致窗口 |
| Read-Through | 缓存层负责回源 | 同上 | 依赖缓存组件能力 |
| Write-Through | 同 Cache-Aside | 同步写缓存与 DB | 写放大，冷数据占内存 |
| Write-Behind | 同 Cache-Aside | 只写缓存，异步刷 DB | 宕机丢数据 |

**为什么删缓存而不是更新：**并发写的到达顺序可能与 DB 相反，导致缓存长期停留旧值；很多写操作不需要该缓存；删除幂等，失败可安全重试。**一致性**上先更新 DB 再删缓存，仍有「读在删除前读到旧值、删除后回填旧值」的窗口，用**延迟双删**（写后 500ms~1s 再删）或 **binlog/CDC** 兜底。

**多级缓存：**L1 本地（ristretto/bigcache，TTL 1~5s）挡热点读并抗 Redis 抖动；L2 Redis 跨实例共享；L3 DB 是事实来源。本地缓存靠短 TTL 或 pub/sub 广播失效，并保留兜底 TTL。

```go
package cache

import (
	"context"
	"encoding/json"
	"errors"
	"fmt"
	"log"
	"math/rand"
	"time"

	"github.com/redis/go-redis/v9"
	"golang.org/x/sync/singleflight"
)

type User struct {
	ID   int64  `json:"id"`
	Name string `json:"name"`
}

var (
	rdb = redis.NewClient(&redis.Options{
		Addr: "127.0.0.1:6379", PoolSize: 50, MinIdleConns: 10,
		DialTimeout: time.Second,
		// 必须设置读写超时，否则 Redis 抖动会挂住业务 goroutine
		ReadTimeout: 300 * time.Millisecond, WriteTimeout: 300 * time.Millisecond,
	})
	sf          singleflight.Group
	errNotFound = errors.New("user not found")
)

func GetUser(ctx context.Context, id int64) (*User, error) {
	key := fmt.Sprintf("user:%d", id)
	if u, err := getFromCache(ctx, key); err == nil {
		return u, nil
	} else if errors.Is(err, errNotFound) {
		return nil, errNotFound
	} else if !errors.Is(err, redis.Nil) {
		log.Printf("redis get %s: %v", key, err) // 降级读 DB，入口必须限流
	}

	// 同进程相同 key 只回源一次；跨副本仍需分布式锁或逻辑过期
	v, err, _ := sf.Do(key, func() (any, error) {
		u, err := loadFromDB(ctx, id)
		if errors.Is(err, errNotFound) {
			_ = rdb.Set(ctx, key, "null", 30*time.Second).Err() // 空值挡穿透，TTL 要短
			return nil, errNotFound
		}
		if err != nil {
			return nil, err
		}
		ttl := 10*time.Minute + time.Duration(rand.Intn(120))*time.Second // 抖动防雪崩
		if err := rdb.Set(ctx, key, mustJSON(u), ttl).Err(); err != nil {
			log.Printf("redis set %s: %v", key, err) // 回填失败不影响主流程
		}
		return u, nil
	})
	if err != nil {
		return nil, err
	}
	return v.(*User), nil
}

func getFromCache(ctx context.Context, key string) (*User, error) {
	raw, err := rdb.Get(ctx, key).Result()
	if err != nil {
		return nil, err // redis.Nil 表示 key 不存在
	}
	if raw == "null" {
		return nil, errNotFound
	}
	var u User
	if err := json.Unmarshal([]byte(raw), &u); err != nil {
		_ = rdb.Del(ctx, key).Err()
		return nil, err
	}
	return &u, nil
}

func loadFromDB(ctx context.Context, id int64) (*User, error) {
	// 真实实现：db.QueryRowContext(ctx, "SELECT id,name FROM users WHERE id=?", id).Scan(...)
	if id <= 0 {
		return nil, errNotFound
	}
	return &User{ID: id, Name: "alice"}, nil
}

func mustJSON(v any) string { b, _ := json.Marshal(v); return string(b) }
```

**更新流程：**`updateDB` → `DEL key` → 异步延迟 500ms 再 `DEL` 一次；删除失败投递重试队列或依赖 binlog 补偿。批量操作用 `Pipeline` 合并 RTT，但它**不是原子操作**，需要原子性时用 Lua。

**易错点：**

- 先删缓存再更新 DB，中间读请求会把旧值回填，造成长期不一致。
- 回填不设 TTL 会让脏数据永存；所有 key 同一 TTL 会在整点集体过期。
- `singleflight` 只在单进程生效，多副本下热点 key 仍会回源 N 次。
- Redis 超时未设置或过长，抖动时业务 goroutine 全部堆积。
- 用 `KEYS *` 或百万元素的大 key 清理，会阻塞 Redis 单线程。

## 8. 消息队列的使用

**核心结论：MQ 换来解耦、削峰、异步，代价是重复、乱序、积压；业务必须按「至少一次投递」设计。**

| 维度 | Kafka | RabbitMQ | NATS JetStream |
| --- | --- | --- | --- |
| 模型 | 分区日志，拉取 | AMQP 队列，推送 | 主题/流，推拉结合 |
| 吞吐 | 十万级/秒 | 万级/秒 | 十万级/秒 |
| 顺序 | **分区内**有序 | 单队列有序 | 单 subject 有序 |
| 语义 | 至少一次；事务可接近精确一次 | 至少一次（手动 ack） | 至少一次 + 去重窗口 |
| Go 客户端 | sarama、kafka-go、franz-go | amqp091-go | nats.go |
| 场景 | 日志、埋点、流处理 | 复杂路由、任务分发 | 云原生事件总线 |

| 语义 | 实现 | 风险 |
| --- | --- | --- |
| 至多一次 | 先提交位点再处理 | 崩溃**丢消息** |
| 至少一次 | 先处理再提交位点 | 重平衡/崩溃导致**重复** |
| 恰好一次 | 幂等生产者 + 事务 + `read_committed` | 消费侧外部副作用仍需幂等 |

> 「恰好一次」只在 Kafka 事务边界内成立。消费逻辑一旦写外部 DB 或调下游，就必须自己做幂等，业界称 **effectively-once**。

**幂等消费：**首选业务表唯一索引 `(biz_type, msg_id)`，与业务写入放在同一本地事务；其次去重表、Redis SETNX（先写后处理会丢消息）、状态机。

**顺序与积压：**同一业务键作为 partition key 保证分区内有序；一个分区在消费组内只被一个消费者处理。积压先看 consumer lag，再扩容消费者（不超过分区数）或转投更多分区的新 topic。

```go
package main

import (
	"context"
	"errors"
	"strconv"

	"github.com/segmentio/kafka-go"
)

var (
	retryWriter = &kafka.Writer{Addr: kafka.TCP("127.0.0.1:9092"), Topic: "order.retry",
		Balancer: &kafka.Hash{}, RequiredAcks: kafka.RequireAll}
	dlqWriter = &kafka.Writer{Addr: kafka.TCP("127.0.0.1:9092"), Topic: "order.dlq",
		RequiredAcks: kafka.RequireAll}
)

func consume(ctx context.Context) error {
	r := kafka.NewReader(kafka.ReaderConfig{
		Brokers: []string{"127.0.0.1:9092"}, GroupID: "order-worker", Topic: "order.created",
		MinBytes: 1, MaxBytes: 10e6, CommitInterval: 0, // 0 = 只手动提交
	})
	defer r.Close()

	for {
		m, err := r.FetchMessage(ctx)
		if err != nil {
			if errors.Is(err, context.Canceled) {
				return nil // 优雅关闭：不再拉取
			}
			return err
		}
		if err := handle(ctx, m); err != nil {
			// 失败转重试主题，超过 3 次进 DLQ，避免毒消息阻塞分区
			target := retryWriter
			if attempt(m) >= 3 {
				target = dlqWriter
			}
			if err := forward(ctx, target, m, attempt(m)+1); err != nil {
				return err // 转发失败不提交，等下次重投
			}
		}
		// 处理成功或已转交重试/DLQ 后才提交位点
		if err := r.CommitMessages(ctx, m); err != nil {
			return err
		}
	}
}

func handle(ctx context.Context, m kafka.Message) error {
	// 幂等：业务表唯一索引 (biz_type, msg_id)，与业务写入同事务
	return nil
}

func attempt(m kafka.Message) int {
	for _, h := range m.Headers {
		if h.Key == "x-attempt" {
			n, _ := strconv.Atoi(string(h.Value))
			return n
		}
	}
	return 0
}

// 转发时保留 key，重试消息仍落原分区，顺序不被打乱
func forward(ctx context.Context, w *kafka.Writer, m kafka.Message, n int) error {
	return w.WriteMessages(ctx, kafka.Message{Key: m.Key, Value: m.Value,
		Headers: []kafka.Header{{Key: "x-attempt", Value: []byte(strconv.Itoa(n))}}})
}
```

**配置：**`RequireAll` 等 ISR 全部落盘；生产端开幂等；关闭自动提交；一次拉取量按处理能力设置；消费者并发不超过分区数。

**易错点：**

- 开启自动提交且在处理前提交位点，进程崩溃直接丢消息。
- 只做至少一次却假设不会重复，重平衡、超时重投、生产者重试都会重复。
- 多 goroutine 并发处理后各自提交 offset，会跳过尚未完成的消息。
- 毒消息无限重试会卡住整个分区，必须有重试上限与 DLQ。
- 增加分区数会改变 key 的分区映射，历史 key 的顺序保证被打破。

## 9. 分布式锁的实现

**核心结论：分布式锁 = 原子「抢占 + 过期」+ 带身份校验的释放 + 足够续期；任何方案都不能替代下游幂等与 fencing 校验。**

| 维度 | Redis（`SET NX PX`） | etcd | ZooKeeper |
| --- | --- | --- | --- |
| 一致性 | 主从异步，切换可能丢锁 | Raft 强一致 | ZAB 强一致 |
| 性能 | 最高 | 中 | 中 |
| 释放 | TTL + Lua 校验删除 | Lease 到期自动删 | 会话断开删临时节点 |
| 公平性 | 需自行排队 | Revision 天然有序 | 顺序临时节点天然公平 |
| 适用 | 高并发短临界区 | 强一致、选主 | 传统 Java 体系 |

1. **为什么不能 `SETNX` + `EXPIRE`**：两条命令不原子，`SETNX` 成功后进程崩溃，`EXPIRE` 未执行，锁永不过期形成死锁。正确写法是一条 `SET lock:order:1001 <token> NX PX 30000`。
2. **value 必须是唯一标识**（UUID + 实例 ID）：否则 A 的锁过期后 B 拿到锁，A 处理完直接 `DEL` 会删掉 B 的锁。
3. **释放必须 Lua 比较后删除**：`GET` 与 `DEL` 分开写同样有竞态。
4. **看门狗**：按 `TTL/3` 续期，续期前校验 token，锁已易主立即停止，解锁时停掉协程。
5. **Redlock 争议**：5 个 master 取多数派，但依赖「时钟漂移有界 + 无长 GC 暂停」；STW 超过 TTL 仍可能双持有。敏感场景用 etcd/ZK，或加 **fencing token**（下游拒绝更小的版本号）。

```go
package lock

import (
	"context"
	"errors"
	"sync"
	"time"

	"github.com/google/uuid"
	"github.com/redis/go-redis/v9"
)

var ErrLockLost = errors.New("锁已失效或已被他人持有")

type Lock struct {
	client *redis.Client
	key    string
	token  string // 唯一标识，释放与续期都要校验
	ttl    time.Duration
	stop   chan struct{}
	once   sync.Once
}

func NewLock(client *redis.Client, key string, ttl time.Duration) *Lock {
	return &Lock{client: client, key: key, token: uuid.NewString(), ttl: ttl, stop: make(chan struct{})}
}

// SET NX PX 一条命令完成「不存在才设置 + 过期时间」
func (l *Lock) TryLock(ctx context.Context) (bool, error) {
	ok, err := l.client.SetNX(ctx, l.key, l.token, l.ttl).Result()
	if err != nil || !ok {
		return false, err
	}
	go l.renew()
	return true, nil
}

var renewScript = redis.NewScript(`if redis.call("GET",KEYS[1])==ARGV[1] then return redis.call("PEXPIRE",KEYS[1],ARGV[2]) end return 0`)

func (l *Lock) renew() {
	ticker := time.NewTicker(l.ttl / 3)
	defer ticker.Stop()
	for {
		select {
		case <-l.stop:
			return
		case <-ticker.C:
			ctx, cancel := context.WithTimeout(context.Background(), l.ttl/3)
			// 只有 value 仍是自己的 token 才续期，避免给新持有者续命
			n, err := renewScript.Run(ctx, l.client, []string{l.key}, l.token, l.ttl.Milliseconds()).Int()
			cancel()
			if err != nil || n == 0 {
				return // 续期失败：业务应尽快中止
			}
		}
	}
}

var unlockScript = redis.NewScript(`if redis.call("GET",KEYS[1])==ARGV[1] then return redis.call("DEL",KEYS[1]) end return 0`)

func (l *Lock) Unlock(ctx context.Context) error {
	l.once.Do(func() { close(l.stop) }) // 停掉看门狗，避免 goroutine 泄漏
	n, err := unlockScript.Run(ctx, l.client, []string{l.key}, l.token).Int()
	if err != nil {
		return err
	}
	if n == 0 {
		return ErrLockLost
	}
	return nil
}
```

**etcd 写法：**`concurrency.NewSession(client, WithTTL(10))` 建租约，`concurrency.NewMutex(session, "/lock/order/1001")` 后 `Lock(ctx)` 阻塞排队；会话断开节点自动删除，强一致且天然公平。

**可重入与 TTL：**可重入用 Hash 存 `token -> 重入次数`，计数归零才删 key；严格公平排队用 etcd 有序节点。TTL 应大于业务 P99，业务本身再设 `TTL/2` 超时；续期只延长持有时间，弥补不了「业务已超时却仍在跑」。

**易错点：**

- `SETNX` 与 `EXPIRE` 分开执行，中间崩溃留下永不过期的锁。
- 释放不校验 value，会删掉锁过期后别人刚拿到的锁。
- 续期脚本不校验 token，会给新持有者「续命」。
- 业务耗时超过 TTL 又无续期，临界区重叠，锁形同虚设。
- Redlock 不能替代 fencing token，GC STW 与网络分区下仍可能双持有。

## 10. 定时任务

**核心结论：单机定时靠 `Timer/Ticker/cron`，多副本靠「选主、分片或外部调度」保证同一时刻只有一个执行者，且执行逻辑必须幂等。**

| 方案 | 精度 | 形态 | 适用 | 注意 |
| --- | --- | --- | --- | --- |
| `time.Timer` | 纳秒 | 单机 | 一次性延迟、超时 | 用完 `Stop`，注意 channel 排空 |
| `time.Ticker` | 纳秒 | 单机 | 固定间隔采集、心跳 | 必须 `Stop`，否则泄漏 |
| `robfig/cron` v3 | 秒 | 单机进程内 | 报表、清理、对账 | 默认 5 段、默认 `time.Local` |
| K8s CronJob | 分钟 | 集群 | 离线批处理 | 需 `concurrencyPolicy: Forbid` |
| 分布式调度 | 秒 | 集群 | 多副本只跑一次 | 选主/锁/分片 + 幂等 |

**cron v3：**默认 5 段（分 时 日 月 周），写秒要加 `WithSeconds()` 变 6 段；默认时区 `time.Local`，容器通常是 UTC，必须 `WithLocation`；`WithChain` 挂 `Recover` 与 `SkipIfStillRunning`；`Stop()` 返回的 context 在所有 job 结束后关闭。

**分布式四种做法：**Leader Election（etcd/K8s Lease 选主，只有 leader 启动 cron）、分布式锁（执行前 `SET NX PX`）、任务分片（`hash(taskID) % 副本数`）、外部调度（XXL-JOB、Airflow 触发 HTTP）。

```go
package main

import (
	"context"
	"log/slog"
	"time"

	"github.com/redis/go-redis/v9"
	"github.com/robfig/cron/v3"
)

var rdb = redis.NewClient(&redis.Options{Addr: "127.0.0.1:6379"})

func main() {
	loc, err := time.LoadLocation("Asia/Shanghai") // 容器内需 tzdata，或设置 TZ
	if err != nil {
		panic(err)
	}
	c := cron.New(
		cron.WithLocation(loc),
		cron.WithSeconds(), // 6 段：秒 分 时 日 月 周
		cron.WithChain(
			cron.Recover(cron.DefaultLogger),            // 单个任务 panic 不影响调度器
			cron.SkipIfStillRunning(cron.DefaultLogger), // 上一轮没跑完就跳过
		),
	)
	// 每天 02:00:00 执行日终结算
	if _, err := c.AddFunc("0 0 2 * * *", func() {
		ctx, cancel := context.WithTimeout(context.Background(), 30*time.Minute)
		defer cancel()
		if err := settleDaily(ctx); err != nil {
			slog.Error("日终结算失败", "err", err) // 失败靠补偿任务兜底
		}
	}); err != nil {
		panic(err)
	}

	c.Start()
	<-c.Stop().Done() // 等待在途任务结束
}

// 多副本下用分布式锁保证同一业务日只执行一次
func settleDaily(ctx context.Context) error {
	bizDate := time.Now().In(time.FixedZone("CST", 8*3600)).Format("2006-01-02")
	lockKey := "cron:settle:" + bizDate
	token := time.Now().Format("20060102150405.000000") + "-worker-1"

	// TTL 40 分钟 > 任务超时 30 分钟
	ok, err := rdb.SetNX(ctx, lockKey, token, 40*time.Minute).Result()
	if err != nil || !ok {
		return err // 未抢到锁说明其它实例在跑，直接跳过
	}
	defer func() {
		// 释放必须校验 token，避免误删他人的锁
		script := redis.NewScript(`if redis.call("GET",KEYS[1])==ARGV[1] then return redis.call("DEL",KEYS[1]) end return 0`)
		_ = script.Run(context.Background(), rdb, []string{lockKey}, token).Err()
	}()

	// 幂等：执行表唯一键 (task_name, biz_date, shard)，插入失败即视为已跑
	return doSettlement(ctx, bizDate)
}

func doSettlement(ctx context.Context, bizDate string) error { return nil }
```

**幂等与补偿：**执行表唯一键防重复；`running` 状态加心跳/超时，启动时扫描超时记录重跑；补偿任务扫描「应有但未成功」的日期；长任务分片并记录 checkpoint。时区上存储用 UTC、展示用本地时区，业务日切分必须显式指定时区。

**易错点：**

- `time.Ticker` 不 `Stop()`，timer 与 goroutine 都无法回收。
- 循环里用 `time.After` 会不断新建 timer，到期前全部堆积；应复用 `NewTimer` + `Reset`。
- cron v3 默认只解析 5 段，写 6 段却不加 `WithSeconds()` 会解析失败。
- 多副本各自启动 cron，任务执行 N 次；必须选主/加锁/分片，且业务仍要幂等。
- 锁 TTL 小于任务耗时，执行到一半锁过期，另一个实例并发进入。

## 11. 容器化部署

**核心结论：Go 服务的最优解是「静态编译 + 多阶段构建 + 最小运行镜像」，配合探针与资源限制形成完整的运行时契约。**

| 基底 | 体积（约） | 含 shell | 含 CA 证书/时区 | 适用 |
| --- | --- | --- | --- | --- |
| `golang:1.23` | 800MB+ | 是 | 是 | 仅构建阶段 |
| `alpine:3.20` | 7MB | 是（busybox） | 需 `apk add` | 需要 shell 调试 |
| `distroless/static` | 2MB | 否 | 是 | 生产首选，攻击面小 |
| `scratch` | 0 | 否 | **否** | 极致体积，需自行拷证书/时区 |

| 构建参数 | 作用 |
| --- | --- |
| `CGO_ENABLED=0` | 关闭 cgo，生成静态二进制，才能放进 scratch/distroless |
| `GOOS=linux GOARCH=amd64` | 明确目标平台，避免构建出 Darwin 二进制 |
| `-trimpath` | 去掉构建机绝对路径，产物可复现 |
| `-ldflags "-s -w"` | 去符号表与调试信息，体积通常减少 25%~30% |
| `-tags netgo,osusergo` | 纯 Go 的 DNS 解析与用户查询，避免依赖 libc |

```dockerfile
# ---------- 构建阶段 ----------
FROM golang:1.23-alpine AS builder
WORKDIR /src

# 先拷依赖清单并下载，利用层缓存：业务代码变更不会重新下载依赖
COPY go.mod go.sum ./
RUN go mod download
COPY . .

# 静态编译：产物不依赖 libc，才能运行在 scratch/distroless
RUN CGO_ENABLED=0 GOOS=linux GOARCH=amd64 \
    go build -trimpath -tags netgo,osusergo \
    -ldflags "-s -w" -o /out/server ./cmd/server

# ---------- 运行阶段 ----------
FROM gcr.io/distroless/static-debian12:nonroot
COPY --from=builder /out/server /server
EXPOSE 8080
ENTRYPOINT ["/server"]
```

> 用 `scratch` 必须拷贝 `/etc/ssl/certs/ca-certificates.crt` 与 `/usr/share/zoneinfo`，否则 HTTPS 与 `LoadLocation` 都会失败。

**探针分工：**`startupProbe` 判断是否完成启动（失败重启，给足阈值防慢启动被杀）；`livenessProbe` 判断进程是否死锁（失败**重启容器**，不要检查 DB/Redis）；`readinessProbe` 判断能否接流量（失败摘除 Endpoints，可检查关键依赖与预热）。

```yaml
apiVersion: apps/v1
kind: Deployment
metadata: { name: order }
spec:
  replicas: 3
  strategy:
    rollingUpdate: { maxSurge: 1, maxUnavailable: 0 }  # 先起新 Pod 再停旧 Pod
  template:
    metadata: { labels: { app: order } }
    spec:
      terminationGracePeriodSeconds: 40  # > preStop(8s) + Shutdown(20s)
      containers:
        - name: order
          image: registry.example.com/order:v1.2.3
          env:
            - { name: TZ, value: "Asia/Shanghai" }
            - { name: GOMEMLIMIT, value: "720MiB" }  # 约为 memory limit 的 90%
          resources:
            requests: { cpu: "200m", memory: "256Mi" }
            limits:   { cpu: "1",    memory: "800Mi" }
          startupProbe:  { httpGet: { path: /healthz, port: 8080 }, periodSeconds: 2, failureThreshold: 30 }
          readinessProbe: { httpGet: { path: /readyz, port: 8080 }, periodSeconds: 5 }
          livenessProbe:  { httpGet: { path: /healthz, port: 8080 }, periodSeconds: 10, failureThreshold: 3 }
          lifecycle:
            preStop: { exec: { command: ["sh", "-c", "sleep 8"] } }  # 等 Endpoints 摘除
          securityContext: { runAsNonRoot: true, readOnlyRootFilesystem: true }
```

**运行时参数：**`GOMEMLIMIT` 设为容器 limit 的 80%~90%，作为软限制促使 GC 提前工作；内存紧张可调低 `GOGC` 换更低峰值；`GOMAXPROCS` 在 Go 1.25 起默认感知 cgroup CPU limit，更早版本用 `automaxprocs`，避免按宿主机核数开 P。

**易错点：**

- 忘记 `CGO_ENABLED=0`，二进制动态链接 libc，放进 scratch 后报 `no such file or directory`。
- 只拷二进制不拷 CA 证书，HTTPS 调用报 `x509: certificate signed by unknown authority`。
- 没有 tzdata 且未设 `TZ`，容器内是 UTC，业务日期与日志时间偏移 8 小时。
- `livenessProbe` 检查 DB/Redis，依赖抖动时所有 Pod 同时重启，小故障放大成雪崩。
- `GOMEMLIMIT` 高于 `limits.memory`，Go 认为有余量不回收，结果被内核 OOMKilled。

## 12. Go 常见陷阱

**核心结论：Go 的坑集中在「变量复用、nil 语义、共享底层数组、资源未释放」四类，多数能被 `go vet`、`-race` 与静态检查提前发现。**

| 陷阱 | 错误写法 | 正确写法 | 说明 |
| --- | --- | --- | --- |
| range 循环变量 | Go ≤1.21 闭包直接捕获 `v` | Go 1.22+ 每轮独立；旧版 `v := v` | 1.22 起每轮创建新变量 |
| nil map 写入 | `var m map[string]int; m["k"]=1` | `m := make(map[string]int)` | nil map 可读可 range，写入 panic |
| typed nil 接口 | nil 指针装入接口后 `i != nil` | 避免装入，或用反射判断 | 取决于动态类型 |
| defer 参数 | `defer f(x)` 后修改 x 无效 | `defer func(){ f(x) }()` | 参数注册时求值 |
| slice 共享数组 | `s2 := s1[:2]; s2 = append(s2, 9)` | `slices.Clone` 或三索引切片 | cap 足够时复用原数组 |
| append 未赋值 | `append(s, x)` 丢弃返回值 | `s = append(s, x)` | 可能返回新 header |
| goroutine 泄漏 | 无缓冲 channel 发送无人接收 | 带 ctx、带缓冲或确保关闭 | 发送方永久阻塞 |
| `time.After` 循环 | 循环里反复 `time.After` | `time.NewTimer` + `Reset` | 堆积未到期 timer |
| map 并发写 | 多 goroutine 写同一 map | 加锁、`sync.Map`、分片 map | `fatal error`，recover 无效 |
| 错误忽略 | `_ = doSomething()` | 处理、包装或记录 | 故障被静默吞掉 |

```go
package main

import (
	"errors"
	"fmt"
	"sync"
)

type MyError struct{}

func (*MyError) Error() string { return "my error" }

func typedNil() {
	var p *MyError
	var err error = p // 动态类型 *MyError，值为 nil
	fmt.Println("接口是否为 nil:", err == nil) // false
	var target *MyError
	fmt.Println("errors.As 能否提取:", errors.As(err, &target)) // true
}

func sliceShare() {
	s1 := []int{1, 2, 3, 4}
	s2 := s1[:2]        // len=2, cap=4，与 s1 共享底层数组
	s2 = append(s2, 99) // cap 足够，直接写回 s1[2]
	fmt.Println("s1 被污染:", s1) // [1 2 99 4]

	s3 := s1[:2:2] // 三索引切片：限制 cap=2，append 会重新分配
	s3 = append(s3, 100)
	fmt.Println("s1 未被污染:", s1) // [1 2 99 4]
}

func loopCapture() {
	var wg sync.WaitGroup
	for i := 0; i < 3; i++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			fmt.Print(i, " ") // Go 1.22+ 输出 0 1 2；1.21 及更早通常是 3 3 3
		}()
	}
	wg.Wait()
	fmt.Println()
}

func main() {
	typedNil()
	sliceShare()
	loopCapture()
}
```

> 循环变量语义在 ≤1.21 时整个循环共用一个变量，≥1.22 时每轮创建新变量；变化只在**模块 `go` 指令 ≥ 1.22** 时生效。升级工具链但 `go.mod` 仍写 `go 1.21`，行为不会变，这是「本地没问题、CI 有问题」的常见原因。

**易错点：**

- 升级 Go 1.22 但 `go.mod` 的 `go` 版本没改，循环变量仍是旧语义，闭包 bug 依旧存在。
- `var m map[string]int` 只声明未初始化，读不 panic、写 panic；结构体的 map 字段同样要显式初始化。
- 判断接口是否为 nil 时，只要曾装入带类型的 nil 指针，`err != nil` 就永远成立。
- `defer` 参数注册时求值，想读最终值必须用闭包。
- 并发写 map 触发 `fatal error: concurrent map writes`，属于运行时 throw，`recover` 接不住。

## 13. 内存泄漏排查

**核心结论：Go 的「内存泄漏」几乎都不是对象没被 GC，而是「仍有引用」或「goroutine 没退出」；排查靠 profile 对比，而不是盯 RSS。**

| 类型 | 成因 | 现象 | 定位 |
| --- | --- | --- | --- |
| goroutine 泄漏 | channel 阻塞、ctx 未取消、Ticker 未 Stop | goroutine 数只涨不跌 | goroutine profile（`debug=2`） |
| 堆增长 | 全局 map 只增不减、缓存无淘汰、子切片保留大数组 | GC 后 `inuse_heap` 仍上升 | heap profile（`inuse_space`） |
| 连接泄漏 | `rows`/`resp.Body` 未关闭 | 连接数打满，请求卡在等连接 | 连接池指标、`ss` |
| timer 堆积 | 循环 `time.After`、Ticker 未 Stop | 内存缓慢上涨 | heap + `NumGoroutine` |
| 全局 map 膨胀 | key 无上限、指标 label 基数爆炸 | 阶梯式上升 | heap diff |

常用 profile：`goroutine`（`debug=1` 按栈聚合，`debug=2` 看完整栈）、`heap`（`inuse_space` 当前占用、`alloc_space` 累计分配）、`block`（阻塞在 channel/锁上的栈）、`profile?seconds=30`（CPU 热点）。

```go
package main

import (
	"context"
	"log"
	"net/http"
	"net/http/pprof"
	"runtime"
	"time"
)

// 错误示范：无缓冲 channel 没有接收者，goroutine 永久阻塞
func leakSend() {
	ch := make(chan int)
	go func() { ch <- 1 }()
}

// 错误示范：Ticker 不 Stop，goroutine 永远阻塞在 t.C
func leakTicker() {
	for i := 0; i < 100; i++ {
		go func() {
			t := time.NewTicker(time.Second)
			for range t.C { // 没有退出条件
			}
		}()
	}
}

// 正确：defer Stop + ctx 退出
func worker(ctx context.Context) {
	t := time.NewTicker(time.Second)
	defer t.Stop()
	for {
		select {
		case <-ctx.Done():
			return
		case <-t.C:
		}
	}
}

func main() {
	ctx, cancel := context.WithCancel(context.Background())
	defer cancel()

	// pprof 挂独立管理端口，只监听内网；绝不能暴露到公网
	mux := http.NewServeMux()
	mux.HandleFunc("/debug/pprof/", pprof.Index)
	mux.Handle("/debug/pprof/heap", pprof.Handler("heap"))
	mux.Handle("/debug/pprof/goroutine", pprof.Handler("goroutine"))
	go func() { _ = http.ListenAndServe("127.0.0.1:6060", mux) }()

	leakSend()
	leakTicker()
	go worker(ctx)

	// 周期性上报 goroutine 数，接入 Prometheus 后可对持续上涨告警
	go func() {
		t := time.NewTicker(30 * time.Second)
		defer t.Stop()
		for {
			select {
			case <-ctx.Done():
				return
			case <-t.C:
				log.Printf("goroutines=%d", runtime.NumGoroutine())
			}
		}
	}()
	time.Sleep(time.Minute) // 观察一分钟，对比采集前后的 goroutine 数
}
```

```bash
go tool pprof http://127.0.0.1:6060/debug/pprof/goroutine?debug=1   # 聚合栈
curl -s 'http://127.0.0.1:6060/debug/pprof/goroutine?debug=2'      # 完整栈
go tool pprof -http=:8081 http://127.0.0.1:6060/debug/pprof/heap   # 交互式分析
go tool pprof -diff_base=heap-t1.pb.gz heap-t2.pb.gz               # 对比两个时间点
GODEBUG=gctrace=1 ./server                                         # GC 轨迹
```

**gctrace 解读：**`120->123->80 MB` 分别是 GC 开始堆、结束堆、存活堆，存活堆持续上涨说明引用未释放；`goal` 逼近 `GOMEMLIMIT` 说明内存压力大。

**排查流程：**现象（RSS、goroutine 数、P99、OOMKilled）→ 采集（heap 两时间点、`debug=2`、gctrace）→ 定位（`top` 看类型、`list` 看行、diff 看新增）→ 修复（补 ctx 退出、Stop ticker、Close 资源）→ 验证（压测对照 + 观察 24h）。

**易错点：**

- heap profile 默认按 512KB 采样，小对象泄漏可能看不到；用 `-diff_base` 或临时调低 `runtime.MemProfileRate`。
- `inuse_space` 是当前存活，`alloc_space` 是累计分配；前者高说明泄漏，后者高只说明分配频繁。
- goroutine profile 只反映采集瞬间，短生命周期 goroutine 抓不到，需多次采集对比。
- `resp.Body.Close()` 前没有读干，连接无法复用；应先 `io.Copy(io.Discard, body)`。
- pprof 暴露公网等于泄露堆栈、命令行参数甚至内存敏感数据，必须只绑内网或加鉴权。

## 14. Go 项目结构

**核心结论：目录结构服务于「依赖方向」与「可测试性」，不是为好看；小项目过度分层比不分层更糟。**

```text
.
├── cmd/
│   ├── api/main.go            # HTTP 入口：只做装配、启动、优雅关闭
│   └── worker/main.go         # 消费者入口：复用 internal 的领域代码
├── internal/
│   ├── order/                 # 按领域组织，而不是按技术层
│   │   ├── handler.go         # 适配层：参数转换与错误映射
│   │   ├── service.go         # 用例编排：事务边界、领域规则
│   │   ├── repository.go      # 仓储接口：由消费方（service）定义
│   │   └── repo_mysql.go      # 仓储实现：依赖 database/sql
│   ├── payment/
│   └── platform/              # 基础设施：config、logger、db、redis、tracing
├── api/order/v1/order.proto   # 对外契约，与实现分离
├── pkg/                       # 真正可被外部复用的库（可选，别放业务代码）
├── configs/  migrations/  test/
└── go.mod
```

| 组织方式 | 结构 | 优点 | 缺点 | 适用 |
| --- | --- | --- | --- | --- |
| 按技术分层 | `handler/`、`service/`、`repo/` 各大包 | 新人直观 | 改一个业务横跨多包，易循环依赖 | 小型、纯 CRUD |
| 按领域分层 | `internal/order/{handler,service,repository}.go` | 边界清晰、可独立演进 | 需先想清领域边界 | 中大型 |
| 混合 | `internal/<domain>` + `internal/platform` | 兼顾边界与复用 | 对规范要求高 | 大多数服务 |

1. **依赖单向**：`handler → service → repository（接口）`，实现在 `repo_mysql` 并指向 `platform/db`；接口定义在**消费方**，单测可用内存实现替换 DB。
2. **internal 由工具链强制**：只有 `internal` 的父目录及其子目录能导入，外部模块无法引用。
3. **领域层不 import platform**：不直接持有 `*gorm.DB`，否则业务逻辑无法脱离数据库测试。
4. **注入方案**：手工装配（中小项目首选，调用链显式）、`google/wire`（编译期生成、零反射）、`uber-go/fx`（生命周期钩子，但依赖反射）。
5. **启动流程**：加载配置 → 校验失败即退出 → logger/tracing → 连接 DB/Redis（Ping + 有限重试）→ 装配 → 启动服务 → 等信号优雅关闭。

```go
// cmd/api/wire.go：装配关系集中声明，wire 生成 wire_gen.go
//go:build wireinject

func InitApp() (*App, error) {
	wire.Build(
		provideConfig, platform.ProvideLogger, platform.ProvideDB, platform.ProvideRedis,
		order.NewRepository, order.NewService, order.NewHandler,
		newHTTPServer, newApp,
	)
	return nil, nil
}

// cmd/api/main.go：main 只负责启动与退出，依赖由 InitApp 注入
func main() {
	app, err := InitApp()
	if err != nil {
		log.Fatal(err)
	}
	if err := app.Run(); err != nil { // Run 内部启动 HTTP、监听信号并 Shutdown
		log.Printf("exit: %v", err)
	}
}
```

**可测试性：**service 依赖接口而非 `*sql.DB`；不要包级 `var db`；`init()` 不做 IO；注入 `Clock` 与 HTTP client。

**小项目不要过度分层：**只有 3~5 个接口时单个 `main.go` + `handlers.go` 足够；没有独立部署需求不需要 `cmd/` 多入口；没有外部复用不需要 `pkg/`；领域边界未定时先模块化再拆包。

**易错点：**

- 把所有结构体塞进 `models` 包，变成人人依赖的上帝包，改一行触发全量重编译。
- 误以为建了 `internal` 就安全：它只对**父目录**生效，放错层级等于没有限制。
- 领域层直接 import `platform` 或持有 `*gorm.DB`，业务与数据库绑死，无法单测。
- 接口定义在实现方包里，调用方被迫依赖具体实现包，接口失去解耦意义。
- 小项目照搬「四层架构 + wire + pkg」，模板代码比业务代码还多。
- 在 `init()` 里连接数据库或注册全局单例，测试无法替换，启动顺序也不可控。
