## 1. Go 语言的特点

**Go 是静态类型、编译型、自带垃圾回收、原生支持并发的通用编程语言**，设计哲学是「少即是多（Less is more）」：用少量语言特性覆盖服务端主要场景，把复杂度交给标准库和工具链，而不是语法本身。

**核心特点：**

1. **编译为单个二进制**：默认静态链接（cgo 等除外），启动快、无虚拟机预热，适合容器化；可交叉编译。
2. **静态类型 + 类型推导**：类型错误在编译期暴露，`:=` 保持简洁；**没有隐式数值转换**，`int` 与 `int32` 必须显式转换。
3. **自动垃圾回收**：并发三色标记 + 混合写屏障，Go 1.14 起 STW 亚毫秒级；代价是失去释放时机的完全控制。
4. **原生并发原语**：goroutine 与 channel 是语言级设施，倡导 CSP 的「通过通信共享内存」。
5. **极简语法**：25 个关键字，无类/继承/异常；组合代替继承，`error` 代替异常，接口隐式实现。
6. **工程化内建**：`gofmt`、`go mod`、`go test`/`pprof`/`race` 开箱即用，降低协作成本。

| 维度 | Go | Java | Python | C++ |
| --- | --- | --- | --- | --- |
| 执行方式 | 机器码 | 字节码 + JVM | 解释执行 | 机器码 |
| 类型系统 | 静态、强类型、结构化接口 | 静态、强类型、名义接口 | 动态、强类型 | 静态、弱类型 |
| 内存管理 | GC（并发标记清除） | GC（分代 + 多收集器） | 引用计数 + 分代 GC | 手动（RAII / 智能指针） |
| 并发模型 | goroutine + channel（M:N） | 线程池 / 虚拟线程 | GIL 限制的多线程 | 线程 + 协程库 |
| 错误处理 | 显式返回 `error` | 异常 | 异常 | 异常 + 错误码 |
| 泛型 | Go 1.18+ 类型参数 | 有（类型擦除） | 动态类型 | 模板 |
| 编译速度 | 极快（依赖图 + 增量） | 中等 | 无需编译 | 较慢 |
| 部署形态 | 单二进制 | JAR + JRE | 源码 + 解释器 | 二进制 + 动态库 |
| 典型场景 | 云原生、网关、中间件 | 企业级后端 | 脚本、AI | 游戏、高频交易 |

```go
package main

import (
	"fmt"
	"runtime"
	"sync"
)

func main() {
	// 编译期就确定的信息：版本与目标平台
	fmt.Printf("Go %s, 目标平台 %s/%s\n", runtime.Version(), runtime.GOOS, runtime.GOARCH)

	// 静态类型：取消注释会编译失败，而不是运行时才报错
	// var n int = "hello" // cannot use "hello" (untyped string constant) as int value

	// 原生并发：8 个 goroutine 并行计算，用 channel 汇总
	const workers = 8
	ch := make(chan int, workers)
	var wg sync.WaitGroup
	for i := 0; i < workers; i++ {
		wg.Add(1)
		go func(id int) {
			defer wg.Done()
			ch <- id * id
		}(i)
	}
	wg.Wait()
	close(ch)

	sum := 0
	for v := range ch {
		sum += v
	}
	fmt.Println("平方和:", sum) // 0+1+4+...+49 = 140
	fmt.Println("GOMAXPROCS:", runtime.GOMAXPROCS(0))

	// go build -o demo main.go                    → 单个可执行文件
	// GOOS=linux GOARCH=amd64 go build -o demo    → 交叉编译
}
```

**Go 的取舍哲学：**

- 用「没有继承」换「组合 + 隐式接口」：解耦更彻底，但需要适应「小接口」思维。
- 用「显式 error」换「没有异常栈展开」：控制流清晰，代价是 `if err != nil` 反复出现。
- 用「GC」换「开发效率」：把内存安全交给 runtime，需要极致性能时再用 `sync.Pool`、对象复用、`unsafe` 优化。
- 用「语言特性少」换「学习成本低、风格统一」，因此泛型直到 1.18 才以最小可用形态加入。

**易错点：**

- Go 是**编译型**语言，`go run` 只是「编译 + 执行」的封装，不要当成解释执行。
- Go 有方法与接口，但**没有类与继承**；`type MyInt int` 是定义新类型，不是继承 `int`。
- 有 GC 不代表不会泄漏：goroutine 泄漏、全局 map 只增不减、子串驻留大对象都会导致内存上涨。
- 编译快不等于运行快：反射、接口动态派发、频繁 `[]byte`/`string` 转换都是常见热点。
- 静态链接不是绝对的：使用 cgo 会链接 libc，`net` 包在某些配置下走动态 DNS 解析。

## 2. 变量、常量与 iota

**`var` 声明变量并赋予零值，`:=` 是函数内的短变量声明，`const` 声明编译期常量，`iota` 是 `const` 块内的行计数器（从 0 开始、每行自增 1）**。理解这四者的边界，是读懂 Go 代码的第一步。

**逐项拆解：**

1. **`var` 与零值**：`var x int` 得到 `0`，`var s string` 得到 `""`，`var p *T` 得到 `nil`。包级变量统一置零，初始化按依赖关系拓扑排序。
2. **短变量声明 `:=`**：只能在函数内；左侧**至少有一个新变量**；同名变量在不同作用域会**遮蔽（shadow）**，内层赋值不影响外层。
3. **常量必须是编译期可确定的值**：字面量、其他常量、`len`/`cap`/`unsafe.Sizeof` 等；不能是函数调用结果，也不能是 slice/map。
4. **无类型常量**：`const A = 1` 没有固定类型，精度至少 256 位，赋值或运算时才确定类型。默认类型：整数 `int`、浮点 `float64`、字符 `rune`、字符串 `string`、布尔 `bool`。
5. **`iota` 的表达式复用**：`const` 块中省略右侧表达式会**原样重复上一行**（`iota` 取当前行号）；`_` 可跳值；新 `const` 块重新从 0 开始。
6. **位掩码惯用法**：`1 << iota` 生成 1、2、4、8……配合 `|` 组合、`&` 判断，是标准库（如 `os.FileMode`）的常见写法。

| 声明方式 | 可用位置 | 类型 | 初值 | 典型用途 |
| --- | --- | --- | --- | --- |
| `var x T` | 包级 / 函数内 | 显式 | 零值 | 需要零值语义 |
| `var x = v` | 包级 / 函数内 | 推导 | `v` | 包级变量 |
| `x := v` | 仅函数内 | 推导 | `v` | 局部变量，最常用 |
| `const C = v` | 包级 / 函数内 | 无类型或显式 | 编译期常量 | 枚举、位掩码 |
| `new(T)` | 任意 | `*T` | 指向零值 | 需要指针 |
| `make(T, ...)` | 任意 | slice/map/chan | 已初始化 | 创建引用类型 |

```go
package main

import "fmt"

type Weekday int

const (
	Sunday Weekday = iota // 0
	Monday                // 1：省略右侧表达式，复用上一行的 iota
	_                     // 2：跳过该值
	Wednesday             // 3
)

const (
	FlagRead  = 1 << iota // 1 << 0 = 1
	FlagWrite             // 1 << 1 = 2
	FlagExec              // 1 << 2 = 4
)

const (
	_  = iota             // 丢弃 0
	KB = 1 << (10 * iota) // 1 << 10
	MB                    // 1 << 20
	GB                    // 1 << 30
)

const Big = 1 << 62 // 无类型常量：精度至少 256 位，不会在声明时溢出

func main() {
	fmt.Println(Sunday, Monday, Wednesday)     // 0 1 3
	fmt.Println(FlagRead|FlagWrite, FlagExec)  // 3 4：按位或组合权限
	fmt.Printf("KB 的类型是 %T\n", KB)          // int

	var x int64 = Big // 赋值时才确定类型
	fmt.Println(x > 0) // true

	var f float64 = 3           // 3 在上下文中被当作 float64
	fmt.Printf("%T %v\n", f, f) // float64 3

	// 常量溢出在编译期报错：
	// var y int8 = 200 // cannot use 200 (untyped int constant) as int8 value

	// 短变量声明要求至少一个新变量
	a, b := 1, 2
	b, c := 3, 4                // b 是赋值，c 是新变量
	fmt.Println(a, b, c)        // 1 3 4

	// 作用域遮蔽：内层 err 与外层无关
	err := fmt.Errorf("outer")
	if true {
		err := fmt.Errorf("inner")
		_ = err
	}
	fmt.Println(err) // outer
}
```

**易错点：**

- `iota` 按**行**自增：一行声明多个常量时它们的 `iota` 相同（如 `A, B = iota, iota+1`）。
- 省略右侧是「文本复用」：下一行重复同一表达式，而不是复制上一行的计算结果。
- `:=` 左侧必须有一个新变量且只能在函数内；`if`/`for` 初始化语句中声明的变量只在该语句块可见。
- 无类型常量不是无限制：赋值给具体类型时必须能表示，`var u uint8 = -1` 编译失败。
- 常量不能取地址（`&KB` 非法），需要指针时先赋给变量。

## 3. 值类型与引用类型

**Go 中只有值传递：赋值和函数调用永远是「拷贝」**。所谓「引用类型」只是习惯叫法——它们的值本身是包含指针的描述符（slice header、指向 hmap 的指针等），拷贝的是描述符，因此拷贝后仍指向同一份底层数据。

**为什么这么说：**

1. **值类型**：`int`、`float64`、`bool`、`complex`、`array`、`struct`。赋值或传参时**整个数据被复制**，函数内修改副本不影响调用方。
2. **引用类型（行为上）**：`slice`、`map`、`channel`、`pointer`、`function`、`interface`。slice 是 `{ptr, len, cap}`（24 字节），map 是指向 `hmap` 的指针（8 字节），channel 是指向 `hchan` 的指针（8 字节），interface 是 `{type/itab, data}`（16 字节）；拷贝后仍指向同一份数据。
3. **string 是特殊的值类型**：`{ptr, len}`（16 字节），拷贝这两个字段，底层字节数组**只读共享**。
4. **函数传参**：形参是实参的副本。传 slice 时拷贝 header，所以「修改元素」调用方可见，而「`append` 后修改 len/cap」调用方不可见。
5. **map 没有 len 副本问题**：header 里只有指针，`m[k] = v` 直接落到共享的 `hmap`，函数内插入对调用方可见。

| 类型 | `unsafe.Sizeof`（64 位） | 赋值/传参拷贝的内容 | 函数内修改是否影响调用方 |
| --- | --- | --- | --- |
| `int` | 8 | 整个数值 | 否 |
| `[3]int` | 24 | 整个数组 | 否 |
| `struct{X, Y int}` | 16 | 整个结构体 | 否 |
| `string` | 16 | ptr + len（字节只读共享） | 否（不可变） |
| `[]int` | 24 | ptr + len + cap | 改元素是；改 len/cap 否 |
| `map[string]int` | 8 | 指向 hmap 的指针 | 是 |
| `chan int` | 8 | 指向 hchan 的指针 | 是（发送/关闭） |
| `*T` | 8 | 指针地址 | 是（通过解引用） |
| `interface{}` | 16 | 类型指针 + 数据指针 | 取决于内部值 |

```go
package main

import (
	"fmt"
	"unsafe"
)

type Point struct{ X, Y int }

func changeInt(n int)            { n = 100 }
func changeStruct(p Point)       { p.X = 100 }
func changeSlice(s []int)        { s[0] = 100 } // 改底层数组，调用方可见
func growSlice(s []int)          { s = append(s, 7) } // 只改副本 header
func changeMap(m map[string]int) { m["a"] = 100 }

func main() {
	fmt.Println(unsafe.Sizeof(int(0)))           // 8
	fmt.Println(unsafe.Sizeof([3]int{}))         // 24
	fmt.Println(unsafe.Sizeof(Point{}))          // 16
	fmt.Println(unsafe.Sizeof(""))               // 16：ptr + len
	fmt.Println(unsafe.Sizeof([]int{}))          // 24：ptr + len + cap
	fmt.Println(unsafe.Sizeof(map[string]int{})) // 8：指向 hmap 的指针
	fmt.Println(unsafe.Sizeof(make(chan int)))   // 8：指向 hchan 的指针
	fmt.Println(unsafe.Sizeof(any(nil)))         // 16：类型指针 + 数据指针

	n := 1
	changeInt(n)
	fmt.Println(n) // 1

	p := Point{X: 1}
	changeStruct(p)
	fmt.Println(p.X) // 1

	s := []int{1, 2, 3}
	changeSlice(s)
	fmt.Println(s) // [100 2 3]

	s2 := []int{1, 2, 3}
	growSlice(s2)
	fmt.Println(len(s2), s2) // 3 [1 2 3]：append 结果没有回传

	m := map[string]int{}
	changeMap(m)
	fmt.Println(m["a"]) // 100
}
```

**易错点：**

- 「引用类型」不等于「引用传递」：传 map 也是拷贝了一个指针值，Go 没有引用传递。
- 传 slice 想修改长度必须 `return` 新 slice 或传 `*[]T`，只 `append` 形参是无效操作。
- `string` 内部含指针，但语义上不可变，函数内无法修改原字符串内容。
- 含 `sync.Mutex` 的结构体复制会复制锁状态，方法必须用指针接收者（见第 10 题）。
- `interface{}` 是 16 字节而非 8 字节，高频路径上大量装箱会增加分配与拷贝。

## 4. 数组与切片的区别

**数组是长度固定、长度属于类型的一部分的值类型；切片是「指向底层数组的指针 + 长度 + 容量」的三元组描述符**，本质是一个 24 字节的结构体值，只是编译器对它做了特殊处理。

**关键机制：**

1. **长度是类型的一部分**：`[3]int` 与 `[4]int` 是不同类型，不能互相赋值；数组长度必须是编译期常量（或 `[...]T` 由元素推导）。
2. **数组是值语义**：赋值、传参、作为结构体字段都整体拷贝；可比较（逐元素 `==`），可作 map key。
3. **切片是描述符**：`s := arr[1:3]` 得到 `ptr = &arr[1]`、`len = 2`、`cap = len(arr)-1`。`cap` 是从起始位置到底层数组末尾的距离。
4. **共享底层数组**：同一数组范围内的切片修改元素会互相影响；`append` 在 `cap` 足够时直接写入原数组，可能覆盖其他切片「视为己有」的元素。
5. **传参语义**：修改 `s[i]` 影响调用方；`s = s[1:]` 或 `append` 只改形参 header，调用方看不到。
6. **切片只能与 `nil` 比较**：判断相等要用 `slices.Equal`（Go 1.21+）或手写循环；`nil` slice 与 `[]T{}` 的 JSON 结果分别是 `null` 与 `[]`。

| 维度 | 数组 `[N]T` | 切片 `[]T` |
| --- | --- | --- |
| 长度 | 编译期固定，属于类型 | 运行时可变 |
| 内存布局 | 连续的元素本身 | 24 字节 header，指向独立数组 |
| 赋值/传参 | 整体拷贝 | 拷贝 header，共享底层数组 |
| 可比较性 | 元素可比较则可 `==` | 只能与 `nil` 比较 |
| 作为 map key | 可以 | 不可以 |
| 扩容 | 不支持 | `append` 触发扩容 |
| 零值 | 元素全为零值 | `nil`（len=cap=0） |
| 典型用途 | 固定大小缓冲区、矩阵 | 绝大多数集合场景 |

```go
package main

import "fmt"

func modifyElem(s []int) { s[0] = 99 } // 改底层数组，调用方可见
func modifyLen(s []int)  { s = append(s, 7); fmt.Println("函数内:", s, len(s)) }

func main() {
	arr := [5]int{1, 2, 3, 4, 5}
	cp := arr // 数组是值类型：整体拷贝
	cp[0] = 100
	fmt.Println(arr[0], cp[0]) // 1 100

	s := arr[1:3]               // ptr=&arr[1], len=2, cap=4
	fmt.Println(len(s), cap(s)) // 2 4

	s = append(s, 88) // cap 还有空位，直接写入 arr[3]
	fmt.Println(arr)  // [1 2 3 88 5]：原数组被改写

	s = append(s, 77, 66) // 超出 cap=4，分配新数组并拷贝
	s[0] = -1
	fmt.Println(arr)              // [1 2 3 88 5]：已脱钩
	fmt.Println(s, len(s), cap(s)) // [-1 3 88 77 66] 5 8

	modifyElem(s)
	fmt.Println(s[0]) // 99

	modifyLen(s)
	fmt.Println(len(s)) // 5：形参的 append 不影响外层 header

	full := arr[1:3:3]                 // 三索引切片：把 cap 限制为 2
	fmt.Println(len(full), cap(full))  // 2 2
	full = append(full, 1)             // cap 已满，必然复制，不会覆盖 arr[3]
	fmt.Println(arr[3], full[2])       // 88 1

	// range 拿到的是元素副本，修改 v 不会改原切片
	for _, v := range s {
		v = 0
		_ = v
	}
	fmt.Println(s[0]) // 99

	var nilSlice []int
	emptySlice := []int{}
	fmt.Println(nilSlice == nil, emptySlice == nil, len(emptySlice)) // true false 0
	nilSlice = append(nilSlice, 1)                                  // nil slice 可以 append
	fmt.Println(nilSlice)                                            // [1]
}
```

**易错点：**

- `s := arr[1:3]` 的 `cap` 是 `len(arr)-1`，不是 2；append 容易「越界写入」原数组，必要时用三索引切片 `arr[1:3:3]`。
- 切片作为参数时，`append` 若未扩容会修改共享数组、但调用方 `len` 不变，这种「半生效」最容易埋 bug。
- 大数组作为值传递会整体拷贝（如 `[1<<20]byte` 一次拷 1MB），应传指针或改用切片。
- `range` 遍历数组/切片拿到的是元素副本；要修改元素必须用索引 `for i := range s { s[i] = ... }`。
- `nil` slice 与空 slice 在 `append`、`len`、`range` 上一致，但在 JSON、反射、`== nil` 上不同，API 返回值要统一约定。

## 5. 切片的扩容机制

**`append` 在容量足够时原地追加并返回同一个底层数组；容量不足时会分配更大的新数组、拷贝旧元素，并返回指向新数组的新 slice**。因此 `append` 的返回值必须重新赋值，不能丢弃。

**扩容策略（Go 1.18 起）：**

1. **先确定所需容量 `newLen`**：`newLen = oldLen + 追加元素个数`。若 `newLen > 2*oldCap`，直接取 `newLen`，一次性追加很多元素时不做过度增长。
2. **旧容量小于 256**：直接翻倍（`newcap = 2 * oldCap`），让小切片快速增长、减少拷贝次数。
3. **旧容量大于等于 256**：按 `newcap += (newcap + 3*256) / 4` 循环增长，直到不小于 `newLen`。增长比例从接近 2 倍平滑过渡到约 1.25 倍，避免大切片一次增长过多造成浪费。
4. **内存对齐取整**：`newcap` 乘以元素大小后，再用 `roundupsize` 向上取整到 Go 的内存分配 size class，所以实际 `cap` 往往比公式值更大（例如 832 个 `int` 可能拿到 848）。
5. **拷贝与返回**：只拷贝 `oldLen` 个元素（不是 `oldCap`），新 slice 的 `len` 为 `newLen`，此后与原数组完全脱钩。

| 版本 / 条件 | 增长规则 | 说明 |
| --- | --- | --- |
| Go 1.17 及以前，`cap < 1024` | 翻倍 | 老策略，阈值 1024 |
| Go 1.17 及以前，`cap >= 1024` | 1.25 倍 | 每次增加 25% |
| Go 1.18+，`newLen > 2*oldCap` | 直接取 `newLen` | 一次 append 多个元素 |
| Go 1.18+，`oldCap < 256` | 翻倍 | 阈值下调到 256 |
| Go 1.18+，`oldCap >= 256` | `newcap += (newcap+768)/4`，循环至足够 | 约 1.25~2 倍平滑过渡 |
| 所有版本 | 再经 `roundupsize` 对齐 | 实际 cap 常大于计算值 |

```go
package main

import (
	"fmt"
	"slices"
)

func main() {
	// 观察 []int 的容量序列（Go 1.18+，64 位）
	var s []int
	prev := -1
	for i := 0; i < 900; i++ {
		s = append(s, i)
		if cap(s) != prev {
			fmt.Printf("len=%-4d cap=%-4d\n", len(s), cap(s))
			prev = cap(s)
		}
	}
	// 典型输出（随版本与元素大小略有差异）：
	// len=1 cap=1 → 2 → 4 → 8 → 16 → 32 → 64 → 128 → 256
	// len=257 cap=512   ：256 以内仍然翻倍
	// len=513 cap=848   ：超过 256 后约 1.25 倍增长并对齐
	// len=849 cap=1280 左右

	// 容量足够时 append 复用底层数组
	a := make([]int, 2, 4)
	b := append(a, 3)
	b[0] = 99
	fmt.Println(a[0], b[0], len(a), cap(a)) // 99 99 2 4：共享数组

	// 容量不足时复制，此后互不影响
	c := make([]int, 2, 2)
	d := append(c, 3)
	d[0] = 99
	fmt.Println(c[0], d[0]) // 0 99：已脱钩

	// 预分配可以避免多次拷贝
	e := make([]int, 0, 1000)
	for i := 0; i < 1000; i++ {
		e = append(e, i)
	}
	fmt.Println(len(e), cap(e)) // 1000 1000

	// Go 1.21+ 可以用 slices.Grow 预留空间
	g := []int{1, 2, 3}
	g = slices.Grow(g, 20)     // 保证还能再放下 20 个元素
	fmt.Println(len(g), cap(g)) // 3 >= 23

	// 为什么必须 s = append(s, x)：
	// 若扩容，append 返回新 header；只写 append(s, x) 会丢掉它，
	// 调用方看到的仍是旧 len/cap，数据看似「没加进去」。
}
```

**易错点：**

- `append` 可能返回新 slice，**必须接收返回值**；`append(s, x)` 单独一行是无效操作。
- 未扩容的 `append` 会写入共享底层数组，可能覆盖其他切片的元素，跨函数传递时尤其危险。
- 「约 1.25 倍」是 Go 1.18+ 且容量 ≥256 时的近似值，不要背成所有版本都如此。
- 扩容后旧数组不会立刻释放；若仍有其他切片引用它，两份数据会同时驻留内存。
- `make([]T, n)` 与 `make([]T, 0, n)` 不同：前者 `len=n`（n 个零值元素），后者更适合配合 `append` 预分配。

## 6. map 的底层实现

**Go 的 map 是哈希表，底层由 `hmap`（表头）和若干 `bmap`（桶）组成**：每个桶固定 8 个键值对，用键哈希的低 `B` 位选桶、高 8 位（`tophash`）快速过滤，冲突时挂溢出桶，扩容采用渐进式搬迁。

**核心设计：**

1. **`hmap` 字段**：`count`（元素数，即 `len`）、`B`（桶数 = `2^B`）、`buckets`（桶数组指针）、`oldbuckets`（扩容期间的旧桶）、`hash0`（随机种子，抵御哈希碰撞攻击）、`noverflow`（溢出桶近似数量）、`flags`（写标志、扩容标志）。
2. **桶内 8 个槽位**：`bmap` 以 `tophash [8]uint8` 开头，之后是 8 个 key、8 个 value、一个 overflow 指针。key 与 value **分区连续存放**（而非交替），减少不同类型对齐造成的 padding。
3. **`tophash` 过滤**：查找先比较 1 字节的 `tophash`，不匹配直接跳过，避免频繁调用 key 的相等比较（对字符串很有价值）。
4. **装载因子 6.5**：`count > 6.5 * 2^B` 时翻倍扩容（`B+1`）。6.5 是空间与查找效率的折中，8 个槽位留空位以降低溢出桶概率。
5. **溢出桶与等量扩容**：桶满后挂溢出桶形成链表；若溢出桶过多而元素不多（大量删除后），触发 `B` 不变的等量扩容，把元素紧凑重排。
6. **渐进式迁移**：扩容不一次性搬完，旧桶挂在 `oldbuckets`，之后每次写/删搬迁 1~2 个桶；查找时若落在旧桶范围，会先去旧桶找。遍历时随机选择起始桶与槽位，因此顺序每次都不同。

| 操作 | 流程 |
| --- | --- |
| 查找 | 计算哈希 → 低 `B` 位定位桶 → 比较 `tophash` → 比较 key → 查溢出桶 → 扩容中还需查 `oldbuckets` |
| 插入 | 查找是否存在 → 存在则更新 → 不存在则找空槽位（含溢出桶）→ 必要时新建溢出桶 → `count++` → 判断是否扩容 |
| 删除 | 查找槽位 → 清空 key/value（指针置 nil 便于 GC）→ 设置空槽标记 → `count--` |
| 扩容 | 翻倍或等量扩容 → 分配新桶 → 标记 `oldbuckets` → 后续操作逐步 `evacuate` |

| 扩容类型 | 触发条件 | 新桶数量 | 目的 |
| --- | --- | --- | --- |
| 翻倍扩容 | `count > 6.5 * 2^B` | `2^(B+1)` | 降低装载因子，恢复查找效率 |
| 等量扩容 | 溢出桶过多（`noverflow` 超标） | `2^B`（不变） | 清理大量删除造成的碎片 |

```go
package main

import "fmt"

func main() {
	m := make(map[string]int, 8) // 预分配 hint，减少扩容；桶数仍是 2^B
	for _, k := range []string{"a", "b", "c", "d", "e"} {
		m[k] = len(k)
	}

	// 遍历顺序随机：runtime 随机选择起始桶与槽位
	for i := 0; i < 3; i++ {
		for k := range m {
			fmt.Print(k, " ")
		}
		fmt.Println()
	}
	// 典型输出（三次顺序通常都不同）：
	// c a e b d
	// b d a c e

	fmt.Println(len(m)) // 5：len 读取 hmap.count，O(1)

	delete(m, "c")
	fmt.Println(len(m)) // 4：删除不会缩容，桶内存仍保留

	// 装载因子 6.5：count > 6.5*2^B 时翻倍扩容
	// 大量删除后溢出桶过多则触发等量扩容

	// 大量增删后建议重建 map，才能真正释放桶内存
	for i := 0; i < 10000; i++ {
		m[fmt.Sprint("key", i)] = i
	}
	for i := 0; i < 9990; i++ {
		delete(m, fmt.Sprint("key", i))
	}
	fmt.Println(len(m)) // 14，但内存仍接近 10000 个元素的水平

	// key 必须可比较：slice、map、func 不能作 key
	type Key struct{ A int; B string }
	nested := map[Key][]int{{A: 1, B: "x"}: {1, 2, 3}}
	fmt.Println(nested[Key{1, "x"}]) // [1 2 3]
}
```

**易错点：**

- 遍历顺序**不确定且每次不同**，依赖顺序就是 bug；需要顺序时先取 key 排序。
- `len(m)` 是 O(1)，但遍历是 O(桶数 + 元素数)，空桶也要扫描。
- 删除不缩容，长期只增不减的 map 会持续占用内存，可定期重建。
- 扩容期间新旧桶并存，内存会短暂翻倍，大 map 可能出现明显尖峰。
- 只有可比较类型才能作 key；`[]byte` 常用 `string(b)` 转换（编译器对 map 查找有优化，不一定分配）。

## 7. map 的并发安全

**原生 map 不是并发安全的：并发读写或并发写会被 runtime 检测到并直接 `throw`，输出 `fatal error: concurrent map writes`，进程立即终止，`recover` 无法拦截**。这不是普通 panic，而是运行时致命错误。

**要点：**

1. **检测机制**：`hmap.flags` 中有 `hashWriting` 标志，写操作开始时置位、结束时清除；若发现已有写者，调用 `throw` 而不是 `panic`。**检测是概率性的**——没崩不代表代码安全。
2. **并发读是安全的**（没有写的前提下）；「一写多读」「多写」都必须同步。
3. **`sync.RWMutex` + 普通 map** 是最通用方案：读多写少时 `RLock` 可并行，写时独占；注意锁粒度与 `defer Unlock` 配对。
4. **`sync.Map`** 用「只读 `read` + 脏 `dirty` + 未命中计数 + 互斥锁」做读写分离，多数读操作无锁。适合**读远多于写、key 集合基本稳定**的场景，如配置缓存、连接注册表。
5. **`sync.Map` 不适合**：写多、需要精确 `len`、需要一致性遍历、`LoadOrStore` 之外的组合原子操作。
6. **分片锁**：把 key 哈希到 N 个「`RWMutex` + map」上降低单锁竞争，适合超高并发；跨分片操作需额外聚合。

| 方案 | 适用场景 | 优点 | 代价 |
| --- | --- | --- | --- |
| `sync.Mutex` + map | 读写都频繁、逻辑复杂 | 简单、语义清晰 | 读也串行 |
| `sync.RWMutex` + map | 读多写少 | 读可并行 | 写饥饿风险、锁开销 |
| `sync.Map` | 读远多于写、key 稳定 | 常见读路径无锁 | 写与删除较慢、无 `len` |
| 分片锁 | 超高并发读写 | 竞争分散 | 实现复杂、跨分片难 |
| 第三方 concurrent map | 需要更多原子操作 | 功能丰富 | 引入外部依赖 |

```go
package main

import (
	"fmt"
	"sync"
)

// RWMutex 保护普通 map，读写都加锁
type SafeMap struct {
	mu sync.RWMutex
	m  map[string]int
}

func NewSafeMap() *SafeMap { return &SafeMap{m: make(map[string]int)} }

func (s *SafeMap) Get(k string) (int, bool) {
	s.mu.RLock()
	defer s.mu.RUnlock()
	v, ok := s.m[k]
	return v, ok
}

func (s *SafeMap) Set(k string, v int) {
	s.mu.Lock()
	defer s.mu.Unlock()
	s.m[k] = v
}

func main() {
	sm := NewSafeMap()
	var wg sync.WaitGroup
	for i := 0; i < 1000; i++ {
		wg.Add(1)
		go func(i int) {
			defer wg.Done()
			key := fmt.Sprint("k", i)
			sm.Set(key, i)
			sm.Get(key)
		}(i)
	}
	wg.Wait()
	fmt.Println(len(sm.m)) // 1000

	// sync.Map：零值即可用，适合读多写少
	var cache sync.Map
	cache.Store("config", "v1")
	if v, ok := cache.Load("config"); ok {
		fmt.Println(v.(string)) // v1
	}
	actual, loaded := cache.LoadOrStore("config", "v2")
	fmt.Println(actual, loaded) // v1 true

	// 下面这段会直接终止进程，仅作反例：
	// bad := map[int]int{}
	// go func() { for { bad[1] = 1 } }()
	// go func() { for { bad[2] = 2 } }()
	// 输出：fatal error: concurrent map writes，defer recover 也拦不住
}
```

**易错点：**

- `fatal error: concurrent map read and map write` 同样无法 `recover`，不要指望兜底。
- 并发检测有随机性：压测没复现不代表安全，必须用 `go test -race` 或 `go run -race` 验证。
- `sync.Map` 没有 `len` 方法，`Range` 也不保证一致性快照；需要这些语义就选 RWMutex + map。
- 不要复制已使用的 `sync.Map`/`sync.RWMutex`（函数传参要传指针），复制锁会导致状态错乱。
- 分片锁要保证同一个 key 永远落在同一分片，且跨分片统计需额外聚合。

## 8. 字符串的不可变性

**Go 的字符串是只读的字节序列**，底层是 `{ptr *byte, len int}` 两个字段（16 字节）。不可变性带来安全共享、可作 map key、编译期常量池等好处，代价是任何「修改」都必须产生新字符串。

**机制与影响：**

1. **不可变语义**：`s[0] = 'H'` 编译失败，`s[i]` 返回 `byte` 副本。不可变使字符串可被多个 goroutine 安全共享，无需加锁。
2. **常量池与编译期拼接**：字面量存放在只读数据段，相同字面量通常指向同一地址；`"a" + "b"` 在编译期折叠，无运行时开销。
3. **`string` ↔ `[]byte` 默认拷贝**：`string` 不可变而 `[]byte` 可变，转换必须复制才能保证语义安全；编译器对 `m[string(b)]` 等少数场景有优化，但不要依赖。
4. **拼接性能**：`+` 每次分配新串，循环内 `s += x` 是 O(n²)；`strings.Builder` 预分配 + 追加，`String()` 零拷贝，是首选；`strings.Join` 适合已有切片；`fmt.Sprintf` 因格式化开销通常最慢。
5. **子串共享底层数组**：`s[7:12]` 不复制字节，只调整 ptr/len。原串很大而子串很小且长期持有时，整个底层数组都无法被 GC 回收。截至 Go 1.21 子串仍共享；`strings.Clone`（Go 1.18+）可强制复制。
6. **`strings.Builder` 不可复制**：内部有 `addr` 自检，复制后使用会 panic；`String()` 之后继续 `Write` 可以，但不要依赖其内存稳定性。

| 维度 | `string` | `[]byte` |
| --- | --- | --- |
| 可变性 | 只读 | 可修改 |
| 底层结构 | ptr + len（16 字节） | ptr + len + cap（24 字节） |
| 比较 | 可用 `==`、可作 map key | 只能与 nil 比较 |
| 转换成本 | 与 `[]byte` 互转需拷贝 | 同左 |
| 拼接 | `+` 产生新串 | `append` 可原地扩容 |
| 适用 | 文本、日志、key | 二进制、编解码、频繁修改 |

```go
package main

import (
	"fmt"
	"strings"
	"unsafe"
)

func main() {
	s := "hello, world"
	sub := s[7:12] // "world"，不复制底层字节

	base := uintptr(unsafe.Pointer(unsafe.StringData(s))) // Go 1.20+
	subBase := uintptr(unsafe.Pointer(unsafe.StringData(sub)))
	fmt.Println(subBase-base)     // 7：子串指针落在原串内部，证明共享底层数组
	fmt.Println(len(s), len(sub)) // 12 5

	clone := strings.Clone(sub) // Go 1.18+：强制复制，断开与原串的联系
	fmt.Println(unsafe.StringData(clone) == unsafe.StringData(sub)) // false

	// 字符串不可变：取消注释会编译失败
	// s[0] = 'H' // cannot assign to s[0] (neither addressable nor a map index expression)

	// 循环内 += 是 O(n²)
	out := ""
	for i := 0; i < 3; i++ {
		out += fmt.Sprint(i)
	}
	fmt.Println(out) // 012

	// strings.Builder：预分配 + 原地追加，String() 不额外拷贝
	var b strings.Builder
	b.Grow(16)
	b.WriteString("hello")
	b.WriteString(", world")
	fmt.Println(b.String(), b.Len()) // hello, world 12

	// strings.Join 适合已有切片
	parts := []string{"a", "b", "c"}
	fmt.Println(strings.Join(parts, "-")) // a-b-c

	// []byte 与 string 互转都会拷贝
	bs := []byte(s)
	bs[0] = 'H'
	fmt.Println(s, string(bs)) // hello, world Hello, world
}
```

**易错点：**

- 子串共享底层数组：从 1MB 响应体中截几个字段长期缓存，会导致整个响应体无法回收；跨请求缓存前先 `strings.Clone`。
- `s += x` 在循环里是 O(n²)，大文本拼接必须用 `strings.Builder`。
- `strings.Builder` 不能复制、不能并发写；复制后使用会 panic。
- `[]byte(s)` 与 `string(b)` 都发生拷贝，热路径反复转换是常见性能问题；用 `unsafe` 零拷贝必须保证不修改只读内存。
- 字符串长度是**字节数**不是字符数，中文按 UTF-8 占 3 字节；按字符处理要用 `utf8.RuneCountInString` 或 `[]rune(s)`。

## 9. 结构体嵌入与组合

**结构体嵌入（anonymous embedding）是把一个类型作为匿名字段放进另一个结构体，从而「提升（promote）」其字段和方法**。它实现的是**组合（has-a）**与行为复用，而不是面向对象里的继承（is-a），Go 没有虚函数表和多态继承。

**规则与细节：**

1. **匿名字段**：`type Derived struct { Base }`，字段名就是类型名 `Base`（去掉包名前缀）。可用 `d.Base` 显式访问，也可 `d.ID` 直接访问提升字段。
2. **方法提升**：嵌入类型的方法提升到外层类型的方法集。外层定义同名方法时外层优先（覆盖），被覆盖的方法仍可通过 `d.Base.Describe()` 调用。
3. **选择器深度**：查找按「深度最浅优先」；同一深度出现同名成员会编译错误（`ambiguous selector`），必须显式限定。
4. **方法集规则**：嵌入 `T` 时，`S` 的方法集包含 `T` 的值接收者方法，`*S` 包含 `T` 与 `*T` 的全部方法；嵌入 `*T` 时，`S` 与 `*S` 都包含 `T` 与 `*T` 的方法。这决定外层类型能否满足某个接口。
5. **与继承的区别**：嵌入不建立子类型关系，`Derived` 不能赋给 `Base` 变量（除非通过接口）；没有运行时动态派发，`d.Describe()` 在编译期就确定调用哪个方法。
6. **嵌入接口**：可以把接口嵌入结构体，实现「部分实现 + 可替换」的装饰器模式；若嵌入的接口是 nil，调用其方法会 panic。嵌入指针字段同理，零值是 nil，调用提升方法可能 nil 解引用。

| 维度 | 结构体嵌入（组合） | 面向对象继承 |
| --- | --- | --- |
| 关系 | has-a（拥有一个 Base） | is-a（是一个 Base） |
| 类型关系 | 无子类型，不能向上转型 | 子类可赋给父类 |
| 方法复用 | 提升（编译期确定） | 继承 + 虚函数动态派发 |
| 覆盖 | 外层同名方法遮蔽内层 | override + 多态调用 |
| 多态 | 通过接口隐式实现 | 通过继承体系 |
| 耦合度 | 低，可自由组合 | 高，父类改动影响子类 |

```go
package main

import "fmt"

type Base struct{ ID int }

func (b Base) Describe() string { return fmt.Sprintf("Base(%d)", b.ID) }
func (b *Base) SetID(id int)    { b.ID = id }

type Derived struct {
	Base // 匿名嵌入，字段名为 Base
	Name string
}

// 同名方法覆盖提升来的 Describe
func (d Derived) Describe() string { return "Derived:" + d.Name }

func main() {
	d := Derived{Base: Base{ID: 1}, Name: "x"}
	fmt.Println(d.ID)              // 1：提升字段，等价于 d.Base.ID
	fmt.Println(d.Describe())      // Derived:x：外层方法优先
	fmt.Println(d.Base.Describe()) // Base(1)：显式访问被覆盖的方法

	d.SetID(2)        // 提升的指针方法：编译器自动取址 &d.Base
	fmt.Println(d.ID) // 2

	// 嵌入指针字段的零值是 nil，直接调用提升方法会 panic
	type PtrEmbed struct{ *Base }
	var p PtrEmbed
	// fmt.Println(p.Describe()) // panic: nil pointer dereference
	if p.Base != nil {
		fmt.Println(p.Describe())
	}
	p.Base = &Base{ID: 3}
	fmt.Println(p.Describe()) // Base(3)：初始化后可正常调用

	// 同深度同名成员会编译错误：
	// type A struct{ X int }
	// type B struct{ X int }
	// type C struct{ A; B }
	// _ = C{}.X // ambiguous selector C{}.X

	// 接口组合是嵌入思想的另一面：小接口拼成大接口
	type Reader interface{ Read(p []byte) (int, error) }
	type Writer interface{ Write(p []byte) (int, error) }
	type ReadWriter interface {
		Reader
		Writer
	}
	var rw ReadWriter
	_ = rw // 任何同时实现 Read 与 Write 的类型都满足
}
```

**易错点：**

- 嵌入不是继承：`Derived` 不是 `Base` 的子类型，不能传给需要 `Base` 的函数；需要多态时用接口。
- 嵌入指针字段默认是 `nil`，直接调用提升方法可能 panic，构造时必须初始化。
- 同深度同名字段/方法导致 `ambiguous selector`，需显式写 `c.A.X`。
- 嵌入 `T` 与嵌入 `*T` 的方法集不同，直接影响接口实现；不确定时优先嵌入值类型并初始化。
- 嵌入接口时零值接口是 nil，任何方法调用都会 panic；要提供默认实现或构造校验。

## 10. 方法接收者：值接收者与指针接收者

**值接收者 `func (t T) M()` 在调用时拿到接收者的副本，指针接收者 `func (t *T) M()` 拿到地址**。更关键的是：接收者类型决定**方法集**，进而决定该类型能否满足某个接口。

**规则与推导：**

1. **自动取址与解引用**：`x` 可寻址时，`x.M()` 在 `M` 为指针接收者时被编译为 `(&x).M()`；`p` 是指针时，`p.M()` 在 `M` 为值接收者时被编译为 `(*p).M()`（解引用后拷贝）。
2. **不可寻址的值不能调用指针方法**：map 元素、函数返回值、常量都不满足「可寻址」，编译器直接报错。典型场景是 `m["a"].Inc()`。
3. **方法集规则**：类型 `T` 的方法集 = 所有值接收者方法；类型 `*T` 的方法集 = 值接收者方法 + 指针接收者方法。因此 `*T` 总能满足 `T` 能实现的接口，反之不成立。
4. **接口赋值的坑**：`var i I = T{}` 只有在 `I` 的方法都由值接收者实现时才合法；若某个方法是 `func (t *T) M()`，必须写 `var i I = &T{}`。
5. **拷贝成本**：值接收者每次调用都复制整个结构体。结构体越大（例如含 `[1024]byte`），开销越明显，应改用指针接收者；小结构体值接收者的拷贝成本可忽略。
6. **一致性**：同一类型的方法应统一接收者类型。含 `sync.Mutex` 的结构体**必须**用指针接收者，否则复制锁会导致互斥失效。

| 接收者声明 | `T` 的方法集 | `*T` 的方法集 | `var i I = T{}` | `var i I = &T{}` |
| --- | --- | --- | --- | --- |
| `func (t T) M()` | 包含 `M` | 包含 `M` | 合法 | 合法 |
| `func (t *T) M()` | 不包含 | 包含 `M` | **编译错误** | 合法 |

```go
package main

import "fmt"

type Counter struct{ n int }

func (c Counter) IncByValue() { c.n++ } // 值接收者：拿到副本
func (c *Counter) Inc()       { c.n++ } // 指针接收者：修改原对象

type Incer interface{ Inc() }

type Big struct{ buf [1024]byte }

func (b Big) ValueSize() int { return len(b.buf) } // 每次调用拷贝 1KB
func (b *Big) PtrSize() int  { return len(b.buf) } // 只拷贝 8 字节指针

func main() {
	c := Counter{}
	c.IncByValue()
	fmt.Println(c.n) // 0

	c.Inc() // 编译器自动改写为 (&c).Inc()
	fmt.Println(c.n) // 1

	// Counter 不满足 Incer，只有 *Counter 满足
	var i Incer = &c
	i.Inc()
	fmt.Println(c.n) // 2

	// var j Incer = c
	// 编译错误：Counter does not implement Incer (method Inc has pointer receiver)

	// map 元素不可寻址，不能直接调用指针方法
	m := map[string]Counter{"a": {}}
	// m["a"].Inc() // cannot call pointer method Inc on Counter
	v := m["a"]
	v.Inc()
	m["a"] = v
	fmt.Println(m["a"].n) // 1

	// 函数返回值不可寻址，也不能调用指针方法
	// func newCounter() Counter { return Counter{} }
	// newCounter().Inc() // cannot call pointer method Inc on Counter

	cv := c
	cv.Inc()
	fmt.Println(cv.n, c.n) // 3 2：副本自增，原对象不变

	// 大结构体：值接收者会产生明显拷贝
	b := Big{}
	fmt.Println(b.ValueSize(), b.PtrSize())
	// go build -gcflags=-m ./... 可观察接收者拷贝与逃逸
}
```

**易错点：**

- `var i I = T{}` 报「does not implement」时，先检查方法是不是指针接收者，而不是怀疑接口写错。
- map 元素、函数返回值不可寻址，无法调用指针方法；必须取出到局部变量、修改后再写回。
- 值接收者方法里修改字段只改副本，`c.IncByValue()` 后原值不变，这种「看起来生效」的写法最坑。
- 含 `sync.Mutex`/`sync.RWMutex` 的结构体用值接收者会复制锁，互斥完全失效，`go vet` 可能提示 copylocks。
- 不要为了「省拷贝」无脑用指针接收者：小对象取址可能造成逃逸，反而增加 GC 压力。

## 11. 接口与空接口

**接口是一组方法签名的集合，描述「能做什么」而不是「是什么」**。Go 的接口是**隐式实现**的：只要类型的方法集包含接口的全部方法，就自动满足，无需 `implements` 声明。空接口 `interface{}`（Go 1.18 起可用别名 `any`）不含任何方法，因此**所有类型都满足它**。

**底层与要点：**

1. **`iface`（非空接口）**：两个机器字，`tab *itab` + `data unsafe.Pointer`。`itab` 含 `inter`（接口类型）、`_type`（动态类型）、`hash`、`fun [1]uintptr`（方法地址表）。
2. **`eface`（空接口）**：同样是 16 字节，但第一字是 `_type`（动态类型）、第二字是 `data`（动态值），没有方法表。空接口调用方法必须先断言出具体类型。
3. **动态派发**：通过接口调用方法时，runtime 从 `itab.fun` 取函数地址间接跳转；同一「接口 + 动态类型」组合的 `itab` 会缓存复用，但调用仍比直接调用慢。
4. **判 nil 的陷阱**：接口为 nil 的条件是**类型信息与数据都为 nil**。把 `(*T)(nil)` 赋给接口后类型信息非 nil，接口整体**不等于 nil**。
5. **接口比较**：两个接口相等要求动态类型相同且值相等；若动态类型不可比较（slice、map、func），比较会 panic。
6. **用途与设计**：解耦调用方与实现、多态、测试 mock、标准库抽象（`io.Reader`/`error`）。接口应**由使用方按需定义**，越小越容易实现与组合，`io.ReadWriter` 就是小接口拼成的。

| 维度 | `iface`（非空接口） | `eface`（空接口 `any`） |
| --- | --- | --- |
| 方法信息 | `itab` 内含方法表 | 无 |
| 第一字 | `*itab` | `*_type` |
| 第二字 | `data` | `data` |
| 大小 | 16 字节 | 16 字节 |
| 方法调用 | 通过 `itab.fun` 间接跳转 | 必须先类型断言 |
| 典型声明 | `io.Reader`、`error` | `interface{}`、`any` |
| 断言开销 | 比较 `itab`/类型 | 比较 `_type` |

```go
package main

import (
	"fmt"
	"unsafe"
)

type MyErr struct{ msg string }

// 指针接收者，并对 nil 接收者做了保护
func (e *MyErr) Error() string {
	if e == nil {
		return "<nil *MyErr>"
	}
	return e.msg
}

func returnErr() error {
	var p *MyErr // 类型是 *MyErr，值是 nil
	return p     // 装入接口：类型信息非 nil，数据为 nil
}

func main() {
	var e error
	fmt.Println(e == nil) // true：itab 与 data 都为 nil

	e = returnErr()
	fmt.Println(e == nil) // false：类型是 *MyErr，值是 nil —— 经典 typed nil
	fmt.Println(e)        // <nil *MyErr>

	fmt.Println(unsafe.Sizeof(e)) // 16：itab + data

	var x any = 42
	fmt.Println(unsafe.Sizeof(x)) // 16：_type + data

	// 判断「内部值是否为 nil」必须先用断言拿到具体类型
	if p, ok := e.(*MyErr); ok {
		fmt.Println(p == nil) // true
	}

	// 接口比较：动态类型与值都相等才相等
	var a any = 1
	var b any = 1
	var c any = int64(1)
	fmt.Println(a == b, a == c) // true false（类型不同）

	// 动态类型不可比较时，接口比较会 panic
	// var s1 any = []int{1}
	// var s2 any = []int{1}
	// fmt.Println(s1 == s2) // panic: comparing uncomparable type []int
}
```

**易错点：**

- 函数返回 `error` 时不要返回具体类型的 nil 指针，否则调用方 `err != nil` 永远成立；要么返回字面量 `nil`，要么保证指针非 nil。
- 空接口不是「无类型」：任何具体类型的 nil 值装入接口后，接口本身都不等于 nil。
- 接口调用有动态派发开销，极热路径可考虑泛型或具体类型特化。
- 不要定义「大而全」的接口；接口应由使用方按需定义。
- 接口内保存的是值的副本（或指针），把大结构体直接赋给接口会触发拷贝/装箱分配。

## 12. 类型断言与类型转换

**类型断言 `x.(T)` 用于「接口值」在运行时检查并取出动态类型；类型转换 `T(x)` 用于编译期在兼容类型之间转换**。前者可能失败（单值形式失败会 panic），后者类型不兼容时直接编译报错。

**两种语法：**

1. **单值断言**：`v := x.(T)`，失败时 panic：`interface conversion: interface {} is string, not int`。只在确信类型时使用。
2. **comma-ok 断言**：`v, ok := x.(T)`，失败时 `v` 为 `T` 的零值、`ok` 为 false，不 panic；生产代码应优先使用。
3. **`T` 可以是具体类型或另一个接口**：断言到接口时检查动态类型是否实现了目标接口的方法集，成功后获得更强能力视图（能力探测）。
4. **type switch**：`switch v := x.(type)` 按顺序匹配；`case nil` 匹配「接口本身为 nil」，`case SomeInterface` 匹配实现了该接口的动态类型。
5. **类型转换的本质**：编译器知道两种类型的内存表示并生成转换指令，如 `int32 → int64` 符号扩展、`[]byte ↔ string` 拷贝。**不兼容类型（如 `int` 与 `string`）不能直接转换**。
6. **断言实现**：runtime 比较接口的 `itab`/`_type` 与目标类型；目标是接口时还需检查方法集。断言开销不大，但频繁断言通常意味着抽象层次有问题。

| 维度 | 类型断言 `x.(T)` | 类型转换 `T(x)` |
| --- | --- | --- |
| 作用对象 | 接口值 | 任意兼容类型 |
| 检查时机 | 运行时 | 编译期（不兼容直接报错） |
| 失败行为 | 单值 panic / comma-ok 返回零值 | 编译失败 |
| 典型用途 | 从 `any` 取具体值、能力探测 | 数值转换、`string↔[]byte`、具名类型转换 |
| 性能 | 运行时类型比较 | 几条指令或一次拷贝 |
| 是否改变动态类型 | 是（提取） | 否（改变静态类型/表示） |

```go
package main

import "fmt"

type Shape interface{ Area() float64 }
type Named interface{ Name() string }

type Circle struct{ R float64 }

func (c Circle) Area() float64 { return 3.14159 * c.R * c.R }
func (c Circle) Name() string  { return "circle" }

func describe(v any) {
	switch x := v.(type) {
	case nil:
		fmt.Println("nil 接口")
	case Shape:
		fmt.Printf("Shape, area=%.2f\n", x.Area())
	case string:
		fmt.Printf("string, len=%d\n", len(x))
	case int, int64:
		fmt.Printf("整数: %v (%T)\n", x, x)
	default:
		fmt.Printf("未知类型 %T\n", x)
	}
}

func main() {
	var s Shape = Circle{R: 2}

	// 断言到具体类型
	c, ok := s.(Circle)
	fmt.Println(c.R, ok) // 2 true

	// 断言到另一个接口：Circle 同时实现了 Named，成功
	n, ok := s.(Named)
	fmt.Println(n.Name(), ok) // circle true

	var a any = "hi"
	// 单值断言失败会 panic，仅在确定类型时使用
	// num := a.(int)
	// panic: interface conversion: interface {} is string, not int

	if num, ok := a.(int); ok {
		fmt.Println(num)
	} else {
		fmt.Println("不是 int") // 走这里
	}

	describe(nil)          // nil 接口
	describe(Circle{R: 1}) // Shape, area=3.14
	describe("go")         // string, len=2
	describe(3)            // 整数: 3 (int)

	// 类型转换发生在编译期，与接口无关
	var i32 int32 = 100
	i64 := int64(i32)        // 数值扩展
	b := []byte("abc")       // string → []byte，拷贝
	str := string(b)         // []byte → string，拷贝
	fmt.Println(i64, b, str) // 100 [97 98 99] abc
}
```

**易错点：**

- 对 `nil` 接口做单值断言会 panic（`interface conversion: interface is nil, not int`），断言前先判空或用 comma-ok。
- type switch 的 `case nil` 只匹配「接口本身为 nil」，不匹配「接口内装了一个 nil 指针」。
- 类型断言不能用于具体类型之间（`int` 断言 `int64` 无意义），那是类型转换的职责。
- 断言到接口时检查的是**方法集**：`T` 与 `*T` 不同，指针接收者方法可能导致断言失败。
- 频繁用 `any` + 断言模拟泛型会带来装箱、动态派发和可读性成本，Go 1.18+ 优先考虑类型参数。

## 13. defer 的执行顺序与原理

**`defer` 把函数调用推迟到当前函数返回前执行，多个 defer 按 LIFO（后进先出）执行；defer 的参数和接收者在注册时就求值**。它不是「延迟求值」，而是「延迟调用」。

**执行模型：**

1. **返回值不是原子操作**：`return x` 分为「给返回值赋值 → 执行 defer → 跳转返回」三步（命名返回值时更明显），因此 defer 可以读取并修改**命名返回值**。
2. **LIFO**：`defer A(); defer B(); defer C()` 的执行顺序是 C、B、A，常用于资源释放、解锁、计时。
3. **注册时求值**：`defer fmt.Println(x)` 在注册那一刻就把 `x` 的当前值拷贝进 defer 记录；`defer func(){ fmt.Println(x) }()` 捕获变量本身，执行时才读取最新值。
4. **panic 时的 defer**：栈展开过程中会执行当前 goroutine 的所有已注册 defer，这是 `recover` 生效的前提；但 `os.Exit` 直接终止进程，**不会执行 defer**。
5. **实现演进**：
   - **Go 1.13 之前**：每次 `defer` 在堆上分配 `_defer` 结构并挂到 goroutine 链表，返回时由 `deferreturn` 逐个执行，开销约几十纳秒。
   - **Go 1.13 起**：**open-coded defer（开放编码）**把 defer 调用内联到函数尾部，用位图记录待执行项，多数场景零分配、开销降到几纳秒；条件是 defer 不在循环中、数量不超过 8 个，否则回退到堆分配。
   - **Go 1.14** 扩大了开放编码的适用范围，官方称 defer 开销已接近普通函数调用。
6. **循环里的 defer**：defer 注册在当前函数上，循环多少次就积累多少个，直到函数返回才执行；循环里打开文件/连接会导致句柄耗尽。

| 维度 | Go 1.13 之前 | Go 1.13 及以后 |
| --- | --- | --- |
| 实现方式 | `_defer` 链表 + `deferreturn` | open-coded 内联 + 位图 |
| 内存分配 | 每次 defer 堆分配（有缓存复用） | 多数场景零分配 |
| 执行方式 | 返回时遍历链表 | 直接在函数尾部按序调用 |
| 开销 | 几十纳秒 | 几纳秒（接近普通调用） |
| 回退条件 | 无 | 循环中的 defer、超过 8 个等 |

```go
package main

import "fmt"

func order() {
	for i := 0; i < 3; i++ {
		defer fmt.Print(i, " ") // 参数此时求值：0 1 2
	}
	fmt.Print("body ")
}

func named() (n int) {
	defer func() { n++ }() // 在 return 赋值之后执行，修改命名返回值
	return 10
}

func argEval() {
	x := 1
	defer fmt.Println("defer 看到 x =", x) // 注册时拷贝 x=1
	x = 2
	fmt.Println("main 看到 x =", x)
}

func closureCapture() {
	x := 1
	defer func() { fmt.Println("闭包看到 x =", x) }() // 捕获变量本身
	x = 2
}

func main() {
	order()
	fmt.Println() // body 2 1 0

	fmt.Println(named()) // 11

	argEval()
	// main 看到 x = 2
	// defer 看到 x = 1

	closureCapture()
	// 闭包看到 x = 2

	// 循环里正确释放资源：用匿名函数包一层，让 defer 每轮执行
	// for _, name := range names {
	//     func() {
	//         f, err := os.Open(name)
	//         if err != nil { return }
	//         defer f.Close()
	//     }()
	// }

	// 性能观察：go test -bench=. -benchmem 对比 defer 与直接调用
	// Go 1.13+ 的 open-coded defer 通常不产生额外堆分配
}
```

**易错点：**

- `defer fmt.Println(x)` 打印注册时的值，不是返回时的值；要读最新值必须用闭包。
- defer 修改返回值只对**命名返回值**有效；`return r` 前的 defer 修改局部变量 `r` 不影响返回值。
- 循环里 defer 会累积到函数结束，文件、连接、锁都可能因此耗尽或长期不释放。
- `os.Exit`、`log.Fatal` 不会执行 defer；`runtime.Goexit` 会执行 defer（但不会返回）。
- defer 开销虽低，热循环里仍应避免；也不要为「省 defer」而漏掉 `Unlock`/`Close`。

## 14. panic 与 recover

**`panic` 用于报告不可恢复的错误并开始栈展开，`recover` 只能在 `defer` 修饰的函数中直接调用，用于捕获当前 goroutine 的 panic 并恢复执行**。业务错误应当用 `error` 返回，`panic` 只留给「程序已无法继续」的场景。

**传播与恢复：**

1. **传播**：`panic(v)` 后当前函数停止正常执行，先执行已注册的 defer，再逐层向上展开栈；若一直没被 recover，程序打印 panic 值与完整栈并退出（退出码 2）。
2. **recover 的有效条件**：必须**直接在 defer 函数中调用**。`defer recover()` 无效（返回值被丢弃）；在 defer 里再嵌套一层函数调用也无效。
3. **返回值**：发生 panic 时返回 panic 值，没有 panic 时返回 `nil`；惯用写法是 `if r := recover(); r != nil { ... }`。
4. **跨 goroutine 无效**：每个 goroutine 有独立栈，子 goroutine 的 panic 不会被父 goroutine 捕获，未恢复时整个进程崩溃。
5. **recover 后**：不会回到 panic 点继续执行，而是**正常返回调用方**；命名返回值可在 defer 中赋值，否则调用方拿到零值。
6. **使用边界**：panic 适合程序 bug（越界、nil 解引用、断言失败）和初始化致命错误；库代码应返回 `error`。Web 服务通常在中间件统一 recover。Go 1.21 起 `panic(nil)` 会被转换为 `*runtime.PanicNilError`。

| 维度 | `panic` | `error` |
| --- | --- | --- |
| 语义 | 不可恢复的程序错误 | 可预期的业务/运行时错误 |
| 传播方式 | 栈展开，逐层执行 defer | 显式返回值，调用方判断 |
| 是否强制处理 | 否（不 recover 就崩溃） | 编译器不强制，但规范要求 |
| 性能 | 展开栈开销大 | 普通返回值，开销小 |
| 适用 | 断言失败、初始化失败、不可达分支 | I/O 失败、参数校验、下游错误 |
| 跨 goroutine | 不会被外部 recover 捕获 | 可正常返回给调用方 |

| 场景 | recover 是否有效 | 原因 |
| --- | --- | --- |
| `defer func(){ recover() }()` | 有效 | 直接在 defer 函数中调用 |
| `defer recover()` | 无效 | 返回值被丢弃，且不是 defer 函数体内调用 |
| defer 中再调用另一个函数执行 recover | 无效 | 不在 panic 展开的直接 defer 中 |
| 父 goroutine 的 defer 捕获子 goroutine panic | 无效 | 栈独立，panic 只展开当前 goroutine |
| 普通函数（非 defer）中调用 recover | 无效 | 没有正在展开的 panic 上下文 |

```go
package main

import (
	"fmt"
	"net/http"
)

// HTTP 中间件兜底：单个请求 panic 不应打挂整个服务
func recoverMiddleware(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		defer func() {
			if rec := recover(); rec != nil {
				fmt.Printf("panic: %v\n", rec)
				http.Error(w, "internal server error", http.StatusInternalServerError)
			}
		}()
		next.ServeHTTP(w, r)
	})
}

// 命名返回值 + recover：把 panic 转换成 error 返回
func safeDiv(a, b int) (res int, err error) {
	defer func() {
		if rec := recover(); rec != nil {
			err = fmt.Errorf("recovered: %v", rec)
		}
	}()
	return a / b, nil
}

func childPanic() <-chan struct{} {
	done := make(chan struct{})
	go func() {
		defer close(done)
		defer func() { // 子 goroutine 必须自己 recover
			if r := recover(); r != nil {
				fmt.Println("子 goroutine 捕获:", r)
			}
		}()
		panic("child boom")
	}()
	return done
}

func main() {
	fmt.Println(safeDiv(6, 3)) // 2 <nil>
	fmt.Println(safeDiv(1, 0)) // 0 recovered: runtime error: integer divide by zero
	fmt.Println("main 继续执行")

	<-childPanic() // 输出：子 goroutine 捕获: child boom

	// 反例：在 defer 里再嵌套一层函数调用 recover，无效，panic 会继续展开
	// defer func(){ func(){ _ = recover() }() }()
}
```

**易错点：**

- `defer recover()` 看似简洁，实际**完全无效**，必须写成 `defer func(){ recover() }()`。
- recover 只能处理当前 goroutine 的 panic；每个自建 goroutine 都应自带兜底，尤其是常驻后台任务。
- recover 后函数不会「原地复活」：panic 点之后的代码不会执行，调用方拿到 defer 中设置的返回值（否则零值）。
- 不要用 panic 做普通错误控制流：性能差、可读性差，调用方容易忘记 recover。
- `log.Fatal`/`os.Exit` 不会触发 defer，常导致缓冲区未 flush、锁未释放；服务退出要走优雅关闭。

## 15. 函数与闭包

**Go 的函数是一等公民（first-class citizen）**：可以赋值给变量、作为参数、作为返回值、存入切片或 map。**闭包是「函数 + 它捕获的自由变量环境」**，捕获的是变量本身（引用），而不是创建时的值快照。

**机制与用法：**

1. **函数类型**：`func(int) int` 是一种类型，可声明变量 `var f func(int) int`。函数值本质是「代码指针 + 环境指针」，nil 函数值调用会 panic。
2. **闭包捕获**：闭包引用外层局部变量时，该变量会**逃逸到堆上**；多个闭包可共享同一变量，互相可见对方的修改。
3. **循环变量捕获（版本差异，必答）**：
   - **Go 1.22 之前**：循环变量全程只有一份，所有闭包共享它，循环结束后都读到最终值；经典写法是 `i := i` 或传参。
   - **Go 1.22 起**：每次迭代创建新变量（per-iteration variable），闭包捕获当轮变量，可直接使用；由 `go.mod` 的 `go` 指令控制，`go 1.22` 及以上才生效。
   - `range` 同样适用新语义，`k, v` 每轮都是新变量。
4. **闭包与逃逸**：闭包返回后仍要访问的变量必须堆分配，`go build -gcflags=-m` 会输出 `moved to heap`；大量创建闭包会增加 GC 压力。
5. **常见模式**：计数器/状态封装、函数选项（functional options）、中间件/装饰器、柯里化、延迟求值、测试 stub/mock。
6. **内存驻留**：闭包持有捕获变量的引用，若捕获大对象（大 slice、buffer）并长期存活，会导致对象无法回收；可只捕获必要字段，或使用完后解除引用。

| 维度 | Go 1.21 及以前 | Go 1.22 及以后 |
| --- | --- | --- |
| 循环变量 | 整个循环共用一个 | 每轮迭代创建新变量 |
| 闭包捕获 `i` | 都读到循环结束后的值 | 每个闭包读到当轮的值 |
| 经典输出 | `3 3 3` | `0 1 2` |
| 规避写法 | `i := i` 或传参 | 直接使用 |
| 生效条件 | 一直如此 | `go.mod` 的 `go` 指令 ≥ 1.22 |

```go
package main

import "fmt"

// 返回闭包：n 被捕获，逃逸到堆上，生命周期与闭包一致
func newCounter() func() int {
	n := 0
	return func() int {
		n++
		return n
	}
}

// 函数作为参数：装饰器，给任意 int→int 函数加日志
func logger(fn func(int) int) func(int) int {
	return func(x int) int {
		r := fn(x)
		fmt.Printf("call(%d) = %d\n", x, r)
		return r
	}
}

// 柯里化：先固定一个参数，返回接收剩余参数的函数
func adder(base int) func(int) int {
	return func(x int) int { return base + x }
}

func main() {
	c1 := newCounter()
	c2 := newCounter()
	fmt.Println(c1(), c1(), c2()) // 1 2 1：两个闭包各自持有独立的 n

	double := logger(func(x int) int { return x * 2 })
	fmt.Println(double(5)) // call(5) = 10 → 10

	add10 := adder(10)
	fmt.Println(add10(3)) // 13

	// 闭包捕获的是变量本身，不是快照
	x := 1
	f := func() { fmt.Println("x =", x) }
	x = 2
	f() // x = 2

	// Go 1.22+（go.mod 的 go >= 1.22）：每轮循环变量都是新变量
	var funcs []func()
	for i := 0; i < 3; i++ {
		funcs = append(funcs, func() { fmt.Print(i, " ") })
	}
	for _, fn := range funcs {
		fn() // Go 1.22+ 输出 0 1 2；Go 1.21 及以前输出 3 3 3
	}
	fmt.Println()

	// go build -gcflags=-m ./... 可看到 "moved to heap: n"
}
```

**易错点：**

- 闭包捕获的是**变量**不是值：闭包创建后修改变量，执行时看到的是新值；需要快照就显式拷贝一份。
- 讨论循环变量必须带版本：Go 1.22 改变了语义，但只在 `go.mod` 的 `go` 指令 ≥ 1.22 时生效。
- 闭包导致变量逃逸到堆，高频创建闭包（如每次请求构造多个中间件）会增加分配；可复用或改为显式传参。
- 闭包持有大对象引用会造成内存驻留；只捕获必要字段，或在使用完后解除引用。
- nil 函数值调用会 panic（`invalid memory address`），声明函数类型变量后要先赋值再调用。
