## 1. goroutine 与线程的区别

**goroutine** 是 Go 运行时（runtime）管理的**用户态轻量级协程**，由 Go 调度器在少量操作系统线程上复用执行，属于 **M:N 调度**（M 个 goroutine 映射到 N 个内核线程）。**线程**是操作系统内核的调度单位，由内核负责创建、切换和抢占。

**goroutine 的核心特点：**

1. **栈很小且可增长**：初始栈只有 2KB（Go 1.4 起），按需扩缩，64 位平台上限约 1GB；线程栈通常固定 1~8MB。
2. **创建与切换廉价**：创建只需在堆上分配一个小结构，切换发生在用户态、只保存少量寄存器，不陷入内核。
3. **由 runtime 调度**：调度点由编译器插入（函数调用、channel 阻塞等），Go 1.14 起还支持基于信号的异步抢占。
4. **没有对外暴露的 goroutine ID**：刻意不提供 `Goid`，避免退化成线程局部存储式的设计。
5. **推荐用 channel 通信**：CSP 模型「通过通信共享内存」，而不是「通过共享内存通信」。
6. **无法从外部杀死**：只能通过 `context`、`done` channel 等协作式退出，`runtime.Goexit` 也只能在自身内部调用。

| 维度 | goroutine | 操作系统线程 |
| --- | --- | --- |
| 管理方 | Go runtime（用户态） | 操作系统内核 |
| 初始栈大小 | 2KB，可动态扩缩 | 通常 1~8MB，固定 |
| 栈上限 | 约 1GB（64 位） | 由系统/线程库决定 |
| 创建成本 | 约几百纳秒 | 微秒级，需系统调用 |
| 切换成本 | 约几十纳秒，用户态 | 约 1~2 微秒，需陷入内核 |
| 调度方式 | 协作式 + 异步抢占，M:N | 内核时间片抢占，1:1 |
| 单机数量级 | 十万到百万 | 数千 |
| 标识 | 无 goroutine ID | 有 TID |
| 阻塞代价 | 只挂起 G，M 可继续跑别的 G | 整个内核线程被阻塞 |
| 通信方式 | channel（首选）/ 共享内存加锁 | 共享内存 + 锁 / 条件变量 |

```go
package main

import (
	"fmt"
	"runtime"
	"sync"
	"time"
)

func main() {
	const n = 100000
	var wg sync.WaitGroup
	wg.Add(n)

	start := time.Now()
	for i := 0; i < n; i++ {
		go func(id int) {
			defer wg.Done()
			_ = id * 2 // 模拟极轻量的业务逻辑
		}(i)
	}
	wg.Wait()

	var m runtime.MemStats
	runtime.ReadMemStats(&m)
	fmt.Printf("goroutine 数量: %d\n", runtime.NumGoroutine())
	fmt.Printf("堆内存: %.2f MB\n", float64(m.HeapAlloc)/(1<<20))
	fmt.Printf("创建 %d 个 goroutine 耗时: %v\n", n, time.Since(start))
	// 预期输出（数值随机器变化）：
	// goroutine 数量: 1 左右（只剩主 goroutine）
	// 堆内存: 约 3~6 MB
	// 创建 100000 个 goroutine 耗时: 约 20~80 ms
	// 同样的数量换成操作系统线程，通常会直接耗尽内存或触发线程数上限
}
```

**易错点：**

- `main` 函数返回时整个进程结束，**不会等待其他 goroutine**，所以必须用 `WaitGroup`、channel 等同步手段。
- goroutine 泄漏后不会自动回收，长期运行的服务会因 `runtime.NumGoroutine()` 持续增长而 OOM。
- 「goroutine 比线程轻」指的是栈和切换成本，**不代表可以无限制创建**；每个 G 仍有约 2KB 起的栈和调度开销。
- 不要用 `runtime.Gosched()` 或 `time.Sleep` 当作同步手段，它们只影响调度时机，不建立 happens-before 关系。

## 2. GMP 调度模型

Go 调度器由三个角色组成：**G（goroutine）、M（machine，内核线程）、P（processor，逻辑处理器）**。早期是 GM 模型，所有 G 放在一把全局锁保护的队列里，调度开销大、扩展性差；引入 P 之后形成了现在的 GMP 模型。

**G：待执行的任务**

- 保存 goroutine 的栈（stack）、指令指针与栈指针（通过 `gobuf`）、所属的 M、状态等。
- 常见状态：`_Gidle`（刚分配）、`_Grunnable`（在队列中等待）、`_Grunning`（正在 M 上执行）、`_Gsyscall`（执行系统调用）、`_Gwaiting`（因 channel、锁、timer 等阻塞）、`_Gdead`（可复用）。
- G 的栈可以扩容（`morestack`），扩容后旧栈内容会被拷贝到新栈。

**M：真正干活的线程**

- 对应一个操作系统线程，负责执行 G 的代码。
- 每个 M 有一个 `g0` 栈，专门运行调度器代码（`schedule`、`findRunnable` 等），业务 G 跑在用户栈上。
- M 想执行 Go 代码，**必须先绑定一个 P**；没有 P 的 M 只能阻塞或休眠。

**P：执行 Go 代码所需的资源**

- P 的数量由 `GOMAXPROCS` 决定，默认等于逻辑 CPU 数（Go 1.25 起在 Linux 上会考虑 cgroup 的 CPU 配额）。
- 每个 P 持有：**本地运行队列**（最多 256 个 G）、`mcache`（内存分配缓存）、空闲 G 链表、per-P 的 timer 等。
- P 是「并行度」的直接来源：同一时刻最多有 `GOMAXPROCS` 个 G 在真正执行。

**三种队列与 work stealing：**

1. **本地队列（LRQ）**：每个 P 一个，无锁访问，绝大多数调度都发生在这里。
2. **全局队列（GRQ）**：所有 P 共享，需要加锁；当本地队列满（256）时，新 G 连同一批 G 被挪到全局队列。
3. **work stealing**：P 本地队列为空时，先取全局队列；还没有就去**其他 P 的本地队列偷一半**，最多尝试 4 个 victim；最后检查网络轮询器（netpoller）里是否有已就绪的 G。
4. **sysmon**：独立的后台线程，负责回收长时间系统调用占用的 P、触发异步抢占、推进 GC 等。

```text
                全局队列 GRQ（加锁，容量不限）
                     ▲            │
        本地队列满时移入 │            │ 本地队列空时来取
                     │            ▼
   ┌────────────┐  ┌────────────┐  ┌────────────┐
   │     P0     │  │     P1     │  │     P2     │   P 的数量 = GOMAXPROCS
   │  LRQ: G G  │  │  LRQ: G G  │  │  LRQ: 空   │   每个 LRQ 最多 256 个 G
   │  mcache    │  │  mcache    │  │  mcache    │
   └─────┬──────┘  └─────┬──────┘  └─────┬──────┘
         │               │               │
   ┌─────▼──────┐  ┌─────▼──────┐  ┌─────▼──────┐
   │     M0     │  │     M1     │  │     M2     │   M 是内核线程，数量可多于 P
   │  (运行 G)  │  │  (运行 G)  │  │  (运行 G)  │
   └────────────┘  └────────────┘  └────────────┘
                                        │
              P2 空闲：去 P0/P1 的 LRQ 偷一半 G（work stealing）
```

**`GOMAXPROCS` 的含义：**

- 它是 **P 的数量**，限制的是「同一时刻能并行执行 Go 代码的 M 数」，而不是线程总数，也不是 goroutine 总数。
- 即使 `GOMAXPROCS=1`，程序依然可以并发（多个 G 交替执行），只是**没有多核并行**。
- CPU 密集型任务调大 `GOMAXPROCS` 能提升吞吐（不超过物理核数）；IO 密集型任务受限于 IO 而非 P 数。
- Go 1.25 起，Linux 上默认会读取 cgroup 的 CPU 带宽限制并据此设置 `GOMAXPROCS`，并在运行期周期性调整，容器里不必再手动设置。

```go
package main

import (
	"fmt"
	"runtime"
	"sync"
	"time"
)

func cpuWork(n int) int {
	s := 0
	for i := 0; i < n; i++ {
		s += i % 7
	}
	return s
}

func bench(p, workers int) time.Duration {
	runtime.GOMAXPROCS(p)
	start := time.Now()
	var wg sync.WaitGroup
	wg.Add(workers)
	for i := 0; i < workers; i++ {
		go func() {
			defer wg.Done()
			cpuWork(20_000_000)
		}()
	}
	wg.Wait()
	return time.Since(start)
}

func main() {
	fmt.Println("逻辑 CPU 数:", runtime.NumCPU())
	for _, p := range []int{1, 2, 4} {
		d := bench(p, 4)
		fmt.Printf("GOMAXPROCS=%d，4 个 CPU 密集 goroutine 耗时: %v\n", p, d)
	}
	// 预期输出（8 核机器，数值仅供参考）：
	// 逻辑 CPU 数: 8
	// GOMAXPROCS=1，4 个 CPU 密集 goroutine 耗时: 约 200ms
	// GOMAXPROCS=2，4 个 CPU 密集 goroutine 耗时: 约 100ms
	// GOMAXPROCS=4，4 个 CPU 密集 goroutine 耗时: 约 50ms
	// 说明：P 越多，CPU 密集任务越能并行；P 超过核数后不再有收益。
	fmt.Println("当前 GOMAXPROCS:", runtime.GOMAXPROCS(0)) // 传 0 表示只读取不改写
}
```

**易错点：**

- `GOMAXPROCS` 不是「最多创建多少个 goroutine」，创建一百万个 goroutine 也没问题，只是同一时刻只有 P 个在跑。
- goroutine 在**系统调用中阻塞**时，M 会被占用，runtime 会创建或唤醒新的 M 来接管 P，线程数可能因此上涨。
- 本地队列是 256 个，满了会批量转移到全局队列，所以「G 一定先进本地队列」并不绝对。
- `runtime.NumCPU()` 拿到的是逻辑核数（含超线程），不是物理核数。

## 3. goroutine 的调度时机与抢占

**调度点（safe point）**：goroutine 只有在特定位置才允许被换下，这些位置称为安全点。常见的调度时机：

| 调度时机 | 说明 |
| --- | --- |
| `go` 语句 | 新 G 被放入当前 P 的本地队列（或全局队列），可能触发 `wakep` 唤醒空闲 P |
| channel 收发阻塞 | 当前 G 挂到 `sendq`/`recvq` 并 `gopark`，M 转而执行其他 G |
| `select` 阻塞 | 所有 case 都未就绪时挂起，被唤醒后重新竞争 |
| 锁 / 信号量阻塞 | `sync.Mutex`、`WaitGroup.Wait`、`time.Sleep` 等都会 park 当前 G |
| 系统调用 | `entersyscall` 让 M 进入系统调用状态，阻塞较久时 P 会被 sysmon 收回交给其他 M |
| 函数调用（栈检查） | 函数序言检查 `stackguard0`，需要扩栈或标记为抢占时进入 `morestack`，顺带让出 |
| GC | STW 阶段停止所有 G；并发标记阶段通过安全点让 G 配合 |
| 主动让出 | `runtime.Gosched()` 把当前 G 放回全局队列，让其他 G 先跑 |
| 异步抢占（Go 1.14+） | sysmon 发现 G 连续运行超过约 10ms，发信号强制中断 |

**Go 1.14 之前的协作式抢占：**

- 只在**函数调用**的栈检查处检查抢占标志（把 `stackguard0` 设为 `stackPreempt`）。
- 如果一个 goroutine 执行 `for {}` 或没有函数调用的紧循环，它**永远不会主动让出 P**，会导致其他 goroutine 饿死、GC 无法推进（STW 等待它到达安全点）。
- 这就是历史上「死循环拖垮整个程序」问题的根源。

**Go 1.14 引入的基于信号的异步抢占：**

1. sysmon 定期扫描，发现某个 G 在 P 上连续运行超过约 10ms，调用 `preemptM`。
2. 通过 `signalM` 向该 M 发送 `SIGURG` 信号（选它是因为应用几乎不用）。
3. M 的信号处理函数 `doSigPreempt` 在**异步安全点**（任意用户指令处，能安全扫描栈和寄存器）把 G 标记为可抢占。
4. 信号返回后，G 在下一次调度检查时被换下，放回队列。
5. 限制：汇编函数、`cgo` 调用、以及运行在系统栈上的代码不能异步抢占（只能等协作式安全点）。

```go
package main

import (
	"fmt"
	"runtime"
	"time"
)

func main() {
	go func() {
		// 这是一个没有任何函数调用的死循环。
		// Go 1.13 及以前：只能在函数调用处抢占，它会一直霸占 P，
		// 导致 main 永远得不到执行，GC 也会被拖住。
		// Go 1.14 起：sysmon 发送 SIGURG 异步抢占，main 能正常被调度。
		for {
		}
	}()

	time.Sleep(50 * time.Millisecond)
	fmt.Println("main 仍然被调度到了（Go 1.14+ 异步抢占生效）")
	fmt.Println("GOMAXPROCS =", runtime.GOMAXPROCS(0))
	// 预期输出：
	// main 仍然被调度到了（Go 1.14+ 异步抢占生效）
	// GOMAXPROCS = <逻辑 CPU 数>
	// 注意：这个死循环 goroutine 会一直泄漏到进程退出，仅用于演示
}
```

**主动让出的正确姿势：**

```go
// 在长耗时、纯计算的循环里，可以定期让出，降低其他 goroutine 的延迟
for i := 0; i < 1e9; i++ {
	if i%1e6 == 0 {
		runtime.Gosched()
	}
	// 业务计算
}
```

**易错点：**

- 异步抢占解决的是「能不能被换下」，**不保证实时性**；抢占仍有约 10ms 的检测周期，硬实时场景不能依赖它。
- `runtime.Gosched()` 只是把当前 G 放到全局队列尾部，**不保证立刻切换**，也不能替代锁或 channel 的同步语义。
- `GOMAXPROCS=1` 时，一个死循环 goroutine 依然可能让其他 goroutine 长时间得不到执行，只是时间片被限制在毫秒级。
- 讨论抢占要区分版本：Go 1.14 是分水岭，面试时最好明确指出「1.14 之前协作式，1.14 之后基于信号的异步抢占」。

## 4. channel 的底层原理

channel 是 Go 中 goroutine 之间通信的管道，底层由 runtime 的 `hchan` 结构体表示。

```go
// runtime/chan.go 中的 hchan（简化版，字段名与源码一致）
type hchan struct {
	qcount   uint           // 缓冲区中当前元素个数
	dataqsiz uint           // 环形缓冲区的容量，即 make(chan T, n) 的 n
	buf      unsafe.Pointer // 指向容量为 dataqsiz 的环形数组；无缓冲时为 nil
	elemsize uint16         // 单个元素的大小
	closed   uint32         // 关闭标志，0 表示未关闭
	elemtype *_type         // 元素类型，用于赋值与 GC 扫描
	sendx    uint           // 下一个写入位置的下标
	recvx    uint           // 下一个读取位置的下标
	recvq    waitq          // 等待接收的 goroutine 队列（sudog 链表）
	sendq    waitq          // 等待发送的 goroutine 队列（sudog 链表）
	lock     mutex          // 保护 hchan 所有字段的互斥锁
}
```

| 字段 | 作用 |
| --- | --- |
| `qcount` / `dataqsiz` | 当前元素数 / 缓冲区容量，对应 `len(ch)` 与 `cap(ch)` |
| `buf` | 环形缓冲区首地址；无缓冲 channel 为 `nil` |
| `sendx` / `recvx` | 环形队列的写指针与读指针，移动到末尾后取模回绕 |
| `recvq` / `sendq` | 因读/写而阻塞的 G 的等待队列，元素是 `sudog`（包含 G、元素地址、channel 等） |
| `closed` | 关闭标记；关闭后的读、写行为都由它决定 |
| `lock` | 一把内部互斥锁，发送、接收、关闭都要先加锁 |

**环形缓冲区的工作方式（有缓冲时）：**

- 发送：把元素拷贝到 `buf[sendx]`，`sendx = (sendx + 1) % dataqsiz`，`qcount++`。
- 接收：从 `buf[recvx]` 拷贝出元素，`recvx = (recvx + 1) % dataqsiz`，`qcount--`。
- 因为容量固定且指针回绕，所以叫「环形队列」，写入和读取都是 O(1)。

**发送流程（`chansend`）：**

1. 若 channel 为 `nil`，当前 G 永久阻塞（`gopark`），永远醒不来。
2. 加锁；如果 channel 已关闭，直接 `panic: send on closed channel`。
3. 如果 `recvq` 非空，说明有接收者在等：取出一个 `sudog`，**跳过缓冲区，直接把数据拷贝到接收者的目标地址**，唤醒接收者，解锁返回。
4. 否则若缓冲区有空位（`qcount < dataqsiz`），把数据拷进 `buf[sendx]`，更新指针与 `qcount`，解锁返回。
5. 否则（无缓冲，或缓冲区已满）构造 `sudog` 挂到 `sendq`，`gopark` 让出 M；被唤醒后数据已被取走，直接返回。

**接收流程（`chanrecv`）：**

1. 若 channel 为 `nil`，永久阻塞。
2. 加锁；若 channel 已关闭且缓冲区为空，返回**元素类型的零值**，`ok=false`。
3. 如果 `sendq` 非空（且缓冲区已满或为无缓冲），取出等待的发送者，直接把它的数据拷贝给接收者，必要时把发送者的数据补进缓冲区，唤醒发送者。
4. 否则若缓冲区非空，从 `buf[recvx]` 取出，`qcount--`，解锁返回。
5. 否则阻塞：构造 `sudog` 挂到 `recvq`，`gopark`；被发送者直接交接后唤醒。

**关闭流程（`closechan`）：**

- 加锁，若已关闭则 `panic: close of closed channel`；若为 `nil` 则 `panic: close of nil channel`。
- 设置 `closed = 1`。
- 把 `recvq` 中所有等待者出队并唤醒：它们会读到零值，`ok=false`。
- 把 `sendq` 中所有等待者出队并唤醒：它们醒来后发现 channel 已关闭，`panic: send on closed channel`。

| 操作 | nil channel | 已关闭 channel | 正常 channel |
| --- | --- | --- | --- |
| 发送 `ch <- v` | 永久阻塞 | panic | 阻塞或成功 |
| 接收 `<-ch` | 永久阻塞 | 立即返回零值，`ok=false` | 阻塞或成功 |
| `close(ch)` | panic | panic（重复关闭） | 成功 |
| `len(ch)` / `cap(ch)` | 0 / 0 | 缓冲区剩余数 / 容量 | 当前数量 / 容量 |
| `for v := range ch` | 永久阻塞 | 读完缓冲后自动结束 | 持续接收 |

```go
package main

import "fmt"

func main() {
	ch := make(chan int, 3)
	fmt.Printf("cap=%d len=%d\n", cap(ch), len(ch)) // cap=3 len=0

	ch <- 1
	ch <- 2
	fmt.Printf("写入 2 个后 len=%d\n", len(ch)) // 2

	close(ch)

	// 关闭后仍可把缓冲区里的数据读完，读完后循环结束
	for v := range ch {
		fmt.Println("读到:", v) // 1、2
	}

	// 读空的已关闭 channel：立即返回零值，ok=false
	v, ok := <-ch
	fmt.Printf("v=%d ok=%v\n", v, ok) // v=0 ok=false

	// 向已关闭的 channel 发送会 panic
	defer func() {
		if r := recover(); r != nil {
			fmt.Println("panic:", r) // panic: send on closed channel
		}
	}()
	ch <- 3
}
```

**易错点：**

- **关闭 channel 是发送方的职责**，接收方不要关；多方发送时需要一个协调者来关，否则容易重复关闭。
- 关闭后缓冲区内剩余数据仍可正常读取，只有读空后才返回零值；`ok` 是判断「是否还有数据」的依据。
- `len(ch)` 是瞬时快照，并发场景下立刻就会过期，不能用来做流程控制。
- 无缓冲 channel 的 `buf` 为 `nil`，但**仍然有 `sendq`/`recvq`**，「无缓冲」不等于「没有队列」。
- channel 传的是**值的拷贝**（指针类型则拷贝指针），大结构体走 channel 有拷贝成本，必要时传指针。

## 5. 无缓冲与有缓冲 channel 的区别

**无缓冲 channel**：`make(chan T)`，容量为 0。发送与接收必须**同时就绪**才能完成，是一次**同步交接（rendezvous）**。发送方在接收方接收之前会一直阻塞。

**有缓冲 channel**：`make(chan T, n)`，容量为 n。发送方只要缓冲区未满就立即返回，接收方只要缓冲区非空就立即返回，二者解耦。

| 维度 | 无缓冲 channel | 有缓冲 channel |
| --- | --- | --- |
| 创建方式 | `make(chan T)` | `make(chan T, n)` |
| 缓冲区 | 无（`buf == nil`，`dataqsiz == 0`） | 有环形缓冲区 |
| 发送返回条件 | 必须有接收者正在等待 | 缓冲区未满即可返回 |
| 接收返回条件 | 必须有发送者正在等待 | 缓冲区非空即可返回 |
| 同步语义 | **强同步**：发送完成意味着接收方已拿到数据 | 只保证入队，不保证对方已处理 |
| 是否可能阻塞 | 双方没有同时就绪就阻塞 | 满/空时才阻塞 |
| 适用场景 | 信号通知、严格握手、保证时序 | 生产消费削峰、解耦、控制吞吐 |

```go
package main

import (
	"fmt"
	"time"
)

func main() {
	// 无缓冲：发送与接收必须「碰面」，是一次同步交接
	unbuffered := make(chan string)
	go func() {
		fmt.Println("接收方: 准备接收")
		fmt.Println("接收方: 收到", <-unbuffered) // 阻塞，直到发送方就绪
	}()

	time.Sleep(100 * time.Millisecond)
	fmt.Println("发送方: 开始发送")
	unbuffered <- "hello" // 直到接收方准备好才返回
	fmt.Println("发送方: 发送完成")

	// 有缓冲：只要缓冲区没满，发送立即返回
	buffered := make(chan int, 2)
	buffered <- 1
	buffered <- 2
	fmt.Printf("缓冲通道 len=%d cap=%d，两次发送均未阻塞\n", len(buffered), cap(buffered))

	// 缓冲区满了之后再发送才会阻塞
	done := make(chan struct{})
	go func() {
		buffered <- 3 // 阻塞，直到 main 取走一个元素
		close(done)
	}()

	time.Sleep(50 * time.Millisecond)
	fmt.Println("main: 取走", <-buffered) // 1
	<-done
	fmt.Println("发送方: 缓冲区腾出空间后完成发送")
	// 预期输出（「收到 hello」与「发送完成」的先后可能互换）：
	// 接收方: 准备接收
	// 发送方: 开始发送
	// 接收方: 收到 hello
	// 发送方: 发送完成
	// 缓冲通道 len=2 cap=2，两次发送均未阻塞
	// main: 取走 1
	// 发送方: 缓冲区腾出空间后完成发送
}
```

**易错点：**

- 无缓冲 channel 的发送完成建立了 **happens-before** 关系（发送前的写对接收后的读可见）；有缓冲 channel 则依赖「入队 / 出队」的同步点。
- 缓冲区大小不是越大越好：过大会掩盖消费能力不足的问题，也会增加内存与延迟；过小则退化成几乎同步。
- 用 `cap(ch)` 判断是否「有缓冲」不可靠（无缓冲 cap 为 0，但有缓冲容量为 0 的写法本身就等价于无缓冲）。
- 不要用「有缓冲」来逃避关闭与取消逻辑，通道最终仍需有人关闭或由 GC 回收。

## 6. select 多路复用

`select` 用于同时等待多个 channel 操作，语义类似 IO 多路复用，但是 Go 语言层面的语法。

**核心规则：**

1. 每个 `case` 必须是一个 channel 的发送或接收操作。
2. 所有 case 都阻塞时，`select` 挂起当前 goroutine，直到**至少一个** case 就绪。
3. 多个 case 同时就绪时，**随机选一个**（runtime 会打乱顺序，避免饥饿）。
4. 有 `default` 时，若没有 case 就绪则立即执行 `default`，实现非阻塞操作。
5. `nil` channel 上的收发**永远阻塞**，对应的 case 永远不就绪，可用于动态「关闭」某个分支。
6. 一次 `select` 只执行一个 case，不会并发执行多个。
7. `select {}` 会永久阻塞；若没有其他 goroutine 能唤醒它，runtime 会报 `all goroutines are asleep - deadlock!`。

| 写法 | 行为 | 典型用途 |
| --- | --- | --- |
| `select` + 多个 channel | 阻塞直到任一就绪 | 多路事件合并 |
| `select` + `default` | 非阻塞尝试 | 快速判断「有没有数据」 |
| `select` + `time.After` | 超时控制 | 防止无限等待 |
| `select` + `<-ctx.Done()` | 取消控制 | 优雅退出 |
| `select {}` | 永久阻塞 | 让 main 不退出（少见） |
| `case <-nilChan` | 永远不就绪 | 动态禁用分支 |

**实现要点（`runtime.selectgo`）：**

- 把所有 case 编译成 `scase` 数组，生成两个顺序：`pollorder`（打乱，用于随机选择）与 `lockorder`（按 channel 地址排序，用于按序加锁，避免死锁）。
- 先按 `lockorder` 依次锁住所有涉及的 channel，再按 `pollorder` 轮询是否有就绪的 case。
- 若都不就绪，为当前 G 创建 `sudog` 挂到所有 channel 的等待队列，然后 `gopark`。
- 被某个 channel 唤醒后，从 `sudog` 中拿到就绪的 case 序号，解锁所有 channel，清理其他队列上的 `sudog`，执行对应分支。

```go
package main

import (
	"fmt"
	"time"
)

func main() {
	a := make(chan string)
	b := make(chan string)
	close(a)
	close(b)

	// 多个 case 同时就绪时，select 随机选一个
	count := map[string]int{}
	for i := 0; i < 1000; i++ {
		select {
		case <-a:
			count["a"]++
		case <-b:
			count["b"]++
		}
	}
	fmt.Printf("随机选择结果: a=%d b=%d（两者应接近 500）\n", count["a"], count["b"])

	// default：所有 case 都未就绪时走 default，实现非阻塞
	ch := make(chan int)
	select {
	case v := <-ch:
		fmt.Println("收到", v)
	default:
		fmt.Println("没有数据，走 default（非阻塞）")
	}

	// 超时控制
	slow := make(chan int)
	go func() {
		time.Sleep(200 * time.Millisecond)
		slow <- 42
	}()
	select {
	case v := <-slow:
		fmt.Println("收到结果:", v)
	case <-time.After(50 * time.Millisecond):
		fmt.Println("超时，放弃等待")
	}

	// 把 channel 置为 nil，可以让这个 case 永远不就绪（动态关闭分支）
	var disabled chan int
	select {
	case v := <-disabled: // nil channel 上的收发永远阻塞，该 case 不会被选中
		fmt.Println("永远不会打印", v)
	default:
		fmt.Println("nil channel 的 case 被跳过")
	}
	// 预期输出：
	// 随机选择结果: a=约 500 b=约 500（两者应接近 500）
	// 没有数据，走 default（非阻塞）
	// 超时，放弃等待
	// nil channel 的 case 被跳过
}
```

**易错点：**

- `select` **不会按书写顺序优先**，不要假设第一个 case 一定先执行；需要优先级时要嵌套 `select`（先非阻塞尝试高优先级，再进入阻塞 select）。
- `select` + `default` 放进 `for` 里会变成忙轮询，必须配合 `time.Sleep`、阻塞 channel 或限流。
- `time.After` 每次调用都会创建一个定时器；Go 1.23 起未被引用的定时器可被 GC 回收，但高频循环里仍建议复用 `time.Timer`。
- 空 `select{}` 会让当前 goroutine 永久阻塞；若这是最后一个可运行的 goroutine，程序会 panic 报死锁。
- 在 `select` 的 case 里执行耗时操作会阻塞其他分支的处理，长时间任务应交给独立 goroutine。

## 7. sync.Mutex 与 RWMutex

**`sync.Mutex`** 是一把不可重入的互斥锁，内部只有两个字段：

```go
type Mutex struct {
	state int32 // 锁状态：是否加锁、是否有唤醒者、是否饥饿、等待者数量
	sema  uint32 // 信号量，用于阻塞和唤醒等待者
}

const (
	mutexLocked     = 1 << iota // 第 0 位：是否已加锁
	mutexWoken                  // 第 1 位：是否有等待者已被唤醒
	mutexStarving               // 第 2 位：是否处于饥饿模式
	mutexWaiterShift = iota     // 第 3 位起：等待者数量
)
```

**加锁流程：**

1. **快路径**：CAS 把 `state` 从 0 改成 `mutexLocked`，成功即获得锁，代价只有一次原子操作。
2. **慢路径**：进入 `lockSlow`，先尝试**自旋**若干次（最多 4 次），期待锁很快释放。
3. 自旋失败则通过信号量排队休眠；等待时间超过阈值后切换到**饥饿模式**。
4. 解锁时若无等待者直接释放；有等待者则唤醒队首，或按饥饿模式直接移交锁。

**自旋的条件（不满足就直接排队）：**

- 多核（`GOMAXPROCS > 1`）且至少有一个正在运行的 P。
- 当前锁**未处于饥饿模式**。
- 自旋次数未超过 4 次（`active_spin = 4`）。
- 等待队列里没有等待者，或有等待者但 `GOMAXPROCS > 1` 且有空闲 P（认为很快能拿到锁）。

**正常模式与饥饿模式：**

| 维度 | 正常模式（normal） | 饥饿模式（starvation） |
| --- | --- | --- |
| 竞争方式 | 新来的 goroutine 可以和队首等待者抢锁（插队） | 锁直接从解锁者**移交给队首等待者** |
| 公平性 | 不公平，但吞吐高 | 严格 FIFO，保证不饿死 |
| 自旋 | 允许 | 禁止，新来者直接排队到队尾 |
| 进入条件 | 默认状态 | 某等待者等待时间超过 **1ms**（`starvationThresholdNs = 1e6`） |
| 退出条件 | 被切换到饥饿模式 | 队首等待者获得锁时，发现自己是最后一个等待者，或等待时间已小于 1ms |
| 设计目标 | 减少上下文切换、提高吞吐 | 解决高竞争下的长尾延迟 |

**`sync.RWMutex`：**

- 内部维护 `readerCount`（读者计数，同时作为「是否有写者」的标志）与 `readerWait`（写者需等待的读者数）。
- 读锁：`RLock` 对 `readerCount` 原子加 1；若结果为负说明有写者在等，则阻塞。多个读者可同时持有读锁。
- 写锁：`Lock` 先把 `readerCount` 减去一个很大的常量（`rwmutexMaxReaders = 1 << 30`），阻止新的读者进入，然后等待已有读者全部释放（`readerWait` 归零）再独占。
- 写者优先：一旦有写者在等待，后续新读者会被阻塞，避免写者饥饿；但也意味着**读多写少**才是它的优势场景。
- Go 1.18 起提供 `TryLock` / `TryRLock` 非阻塞尝试。

| 维度 | Mutex | RWMutex |
| --- | --- | --- |
| 并发粒度 | 读写都互斥 | 读读并发，读写/写写互斥 |
| 开销 | 较小 | 较大（读者计数、写者等待逻辑） |
| 适用场景 | 读写都频繁、临界区短 | **读多写少**，如配置、缓存 |
| 是否可重入 | 否 | 否（读锁递归也可能死锁） |
| 饥饿处理 | 1ms 后进入饥饿模式 | 写者优先，避免写饥饿 |
| 额外风险 | 复制已使用的锁、忘记解锁 | 写者等待时递归 `RLock` 会死锁 |

```go
package main

import (
	"fmt"
	"sync"
	"sync/atomic"
)

type Counter struct {
	mu sync.Mutex
	n  int
}

func (c *Counter) Inc() {
	c.mu.Lock()
	defer c.mu.Unlock()
	c.n++
}

func (c *Counter) Get() int {
	c.mu.Lock()
	defer c.mu.Unlock()
	return c.n
}

func main() {
	var wg sync.WaitGroup
	c := &Counter{}
	for i := 0; i < 1000; i++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			c.Inc()
		}()
	}
	wg.Wait()
	fmt.Println("Mutex 计数:", c.Get()) // 1000

	// RWMutex：多个读者可以同时持锁，写者独占
	var rw sync.RWMutex
	data := map[string]string{"go": "goroutine"}
	var readOps int64
	var readers sync.WaitGroup
	for i := 0; i < 100; i++ {
		readers.Add(1)
		go func() {
			defer readers.Done()
			rw.RLock()
			_ = data["go"] // 读读并发
			rw.RUnlock()
			atomic.AddInt64(&readOps, 1)
		}()
	}
	readers.Wait()

	rw.Lock()
	data["go"] = "gmp" // 写写/读写互斥
	rw.Unlock()

	fmt.Println("读操作次数:", atomic.LoadInt64(&readOps)) // 100
	fmt.Println("写后读到:", data["go"])                  // gmp
}
```

**易错点：**

- **Mutex 不可重入**：同一个 goroutine 重复 `Lock` 会死锁，不要写出递归加锁的代码。
- 锁必须与它保护的数据绑定在同一个对象上；结构体按值传递会**复制锁**，等于两把不同的锁，保护失效。`go vet` 会提示「copies lock value」。
- `RWMutex` 的读锁**不能升级**为写锁（先 `RUnlock` 再 `Lock`），在有写者等待时递归 `RLock` 也可能死锁。
- 临界区里不要做 IO、不要调用可能阻塞很久的函数，否则会把锁竞争放大成排队。
- 不要用 `defer` 包裹超大临界区后中途 `return` 前还有大量计算，锁的持有时间会变长。

## 8. WaitGroup 的使用与陷阱

`sync.WaitGroup` 用于等待一组 goroutine 完成，内部维护一个计数器和一个信号量：

```go
// 简化示意
type WaitGroup struct {
	state1 [3]uint32 // 打包了计数器 counter 与等待者数量 waiter
	// state() 返回 counter、waiter 指针，semap 返回信号量地址
}
```

- `Add(delta)`：计数器加 delta；若计数器变为 0，唤醒所有等待者。
- `Done()`：等价于 `Add(-1)`。
- `Wait()`：若计数器大于 0，则把当前 goroutine 挂起，直到被唤醒。

**使用规则：**

1. `Add` 必须在 `Wait` 之前发生（通常是在启动 goroutine 之前调用）。
2. 计数器为 0 时并发调用 `Add` 与 `Wait` 是**误用**，可能触发 `panic: sync: WaitGroup is reused before previous Wait has returned`。
3. `Wait` 返回后可以复用同一个 WaitGroup，但必须等上一轮全部结束。
4. `Done` 要放在 `defer` 里，保证 panic 路径也能减计数。
5. WaitGroup 不可复制，传参必须传指针。

| 写法 | 结果 |
| --- | --- |
| 先 `wg.Add(1)`，再 `go f(&wg)`，`f` 中 `defer wg.Done()` | 正确 |
| 在 goroutine 内部 `wg.Add(1)` | 错误：`Wait` 可能先返回，或计数为 0 时 Add 触发 misuse |
| 按值传递 `wg` 给函数 | 错误：复制的是计数器的副本，`Done` 作用不到原对象 |
| `Done` 写在函数末尾而无 `defer` | 有 panic 时不会执行，`Wait` 永久阻塞 |
| 重复 `Done` | `panic: sync: negative WaitGroup counter` |

```go
package main

import (
	"fmt"
	"sync"
)

func worker(id int, wg *sync.WaitGroup) {
	defer wg.Done() // 无论正常返回还是 panic，都会减计数
	fmt.Println("worker", id, "done")
}

func main() {
	var wg sync.WaitGroup
	for i := 1; i <= 3; i++ {
		wg.Add(1) // 必须在启动 goroutine 之前 Add
		go worker(i, &wg)
	}
	wg.Wait()
	fmt.Println("全部完成")
	// 预期输出（worker 顺序不固定）：
	// worker 1 done
	// worker 3 done
	// worker 2 done
	// 全部完成
}
```

> 提示：Go 1.25 新增了 `WaitGroup.Go(f)`，等价于 `wg.Add(1); go func() { defer wg.Done(); f() }()`；低于该版本时按上面的写法手写即可。

**错误示范（不要这样写）：**

```go
// Add 放在 goroutine 里：main 可能在所有 Add 执行前就 Wait 完毕
var wg sync.WaitGroup
for i := 0; i < 3; i++ {
	go func() {
		wg.Add(1) // 与 Wait 并发，可能 panic 或提前返回
		defer wg.Done()
	}()
}
wg.Wait()
```

**易错点：**

- `WaitGroup` 适合「已知任务数量」的等待；数量动态、需要收集错误时优先用 `golang.org/x/sync/errgroup`。
- 同一个 WaitGroup 多轮复用时，必须在上一轮 `Wait` 返回之后再开始下一轮 `Add`。
- `Add` 的 delta 可以为负，但计数器不能为负，否则直接 panic。
- Go 1.25 的 `go vet` 新增了 `waitgroup` 检查器，能静态发现部分错位的 `Add` 调用。

## 9. sync.Once 与 sync.Pool

**`sync.Once`** 保证某个函数在**整个进程生命周期内只执行一次**，常用于单例、全局配置、一次性初始化。

```go
type Once struct {
	done atomic.Uint32 // 0 表示未执行，1 表示已执行
	m    Mutex
}

func (o *Once) Do(f func()) {
	if o.done.Load() == 0 { // 快路径：一次原子读
		o.doSlow(f)
	}
}

func (o *Once) doSlow(f func()) {
	o.m.Lock()
	defer o.m.Unlock()
	if o.done.Load() == 0 { // 双重检查
		defer o.done.Store(1)
		f()
	}
}
```

- 快路径只有一次原子读，开销极小；只有第一次调用才会加锁。
- `f` 返回后设置 `done=1`；**即使 `f` panic，`defer` 仍会执行**，Once 视为已完成，后续调用不会重试。
- Go 1.21 新增 `sync.OnceFunc`、`OnceValue`、`OnceValues`，省去手写包装。

**`sync.Pool`** 是可复用的临时对象池，用于**降低 GC 压力**（注意：不是连接池）。

- 每个 P 有一个私有槽（private）和一个共享链（shared），`Get` 优先取私有槽，其次共享链，最后其他 P，仍没有则调用 `New`。
- 对象可能在任何一次 GC 时被清理，**不能假设 Put 进去的对象一定能 Get 回来**。
- Go 1.13 起采用「victim cache」两代缓存：GC 时当前池降级为 victim，victim 中的对象还能存活一个 GC 周期，减少命中率抖动。
- 放回前应 `Reset`，避免把脏数据带给下一个使用者。
- 适合生命周期短、创建成本高的对象：`bytes.Buffer`、`strings.Builder`、临时编码缓冲区、`json` 解码中间对象。

| 维度 | sync.Once | sync.Pool |
| --- | --- | --- |
| 目的 | 保证初始化只执行一次 | 复用临时对象，减少分配 |
| 生命周期 | 进程级，永久有效 | 对象随时可能被 GC 回收 |
| 并发语义 | 阻塞等待第一次执行完成 | 无状态保证，Get 可能拿到 nil |
| 典型用法 | 单例、配置加载、注册表 | Buffer、临时结构体、序列化缓冲 |
| 常见误用 | 在 `Do` 里加锁后再调用同一 Once | 把 Pool 当连接池 / 依赖其中对象一定存在 |

```go
package main

import (
	"bytes"
	"fmt"
	"sync"
)

func main() {
	// Once：多个 goroutine 并发调用，初始化只执行一次
	var once sync.Once
	var wg sync.WaitGroup
	for i := 0; i < 5; i++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			once.Do(func() {
				fmt.Println("初始化只执行一次")
			})
		}()
	}
	wg.Wait()
	// 预期输出：初始化只执行一次（仅一行）

	// OnceFunc（Go 1.21+）更简洁
	initDB := sync.OnceFunc(func() {
		fmt.Println("连接数据库")
	})
	initDB()
	initDB() // 不再执行
	// 预期输出：连接数据库（仅一行）

	// Pool：复用 bytes.Buffer，避免反复分配
	var bufPool = sync.Pool{
		New: func() any { return new(bytes.Buffer) },
	}
	for i := 0; i < 2; i++ {
		buf := bufPool.Get().(*bytes.Buffer)
		buf.WriteString("hello ")
		buf.WriteString(fmt.Sprint(i))
		fmt.Println(buf.String())
		buf.Reset() // 放回前必须清理，避免脏数据被下一个使用者读到
		bufPool.Put(buf)
	}
	// 预期输出：
	// hello 0
	// hello 1
}
```

**易错点：**

- `Once.Do` 内部不要再调用同一个 `once.Do`（会死锁），也不要在 `Do` 的函数里等待依赖该初始化的其他 goroutine。
- `f` panic 后 Once 依旧标记为完成，若初始化必须可重试，需要自己额外管理状态。
- `Pool.Get` 返回的是 `any`，必须类型断言；池为空且未设置 `New` 时返回 `nil`。
- 不要把带状态的对象直接放回池中（忘记 `Reset`），会造成数据串用。
- `sync.Pool` 的对象在 GC 后可能全部消失，**绝不能**用它保存有业务价值、必须存在的数据。

## 10. context 的作用与用法

`context.Context` 用于在**调用链之间传递取消信号、截止时间和请求级元数据**，是 Go 并发控制的标准入口。

```go
type Context interface {
	Deadline() (deadline time.Time, ok bool) // 截止时间；没有则 ok=false
	Done() <-chan struct{}                   // 取消时关闭的 channel；永不取消时返回 nil
	Err() error                              // Done 关闭后返回 Canceled 或 DeadlineExceeded
	Value(key any) any                       // 取请求级元数据
}
```

| 方法 | 语义 | 注意 |
| --- | --- | --- |
| `Deadline` | 返回截止时间与是否存在 | 用于向下游传递超时预算 |
| `Done` | 返回只读的取消信号 channel | `Background`/`TODO` 返回 `nil`，`select` 时该 case 永久阻塞 |
| `Err` | 返回取消原因 | `context.Canceled` / `context.DeadlineExceeded`；未取消返回 `nil` |
| `Value` | 读取键值 | 只用于请求级元数据，不用于传可选参数 |

**四种实现：**

| 类型 | 创建方式 | 作用 |
| --- | --- | --- |
| `emptyCtx` | `context.Background()` / `context.TODO()` | 根节点，永不取消，无值 |
| `cancelCtx` | `context.WithCancel(parent)` | 手动取消，取消会向下传播 |
| `timerCtx` | `context.WithTimeout` / `WithDeadline` | 到时自动取消 |
| `valueCtx` | `context.WithValue(parent, k, v)` | 携带一个键值对，逐层向上查找 |

**选用原则：**

- 需要手动控制生命周期：`WithCancel`。
- 需要「最多等多久」：`WithTimeout`；需要绝对时间点：`WithDeadline`。
- 需要透传 trace id、用户身份、租户信息：`WithValue`，key 用**自定义未导出类型**，避免字符串冲突。
- 上游取消必须能传导到下游：所有阻塞操作都要 `select` 监听 `ctx.Done()`。
- 每个 `WithXxx` 都会返回 `cancel`，**必须调用**（通常 `defer cancel()`），否则会泄漏定时器和子节点，直到父 context 取消。
- 取消是**单向向下传播**的：父取消 → 子取消；子取消不影响父。
- Go 1.20 增加 `WithCancelCause` / `Cause`，Go 1.21 增加 `WithoutCancel`、`AfterFunc`。

```go
package main

import (
	"context"
	"fmt"
	"time"
)

type ctxKey struct{} // 未导出的 key 类型，避免与其他包的 key 冲突

func slowWork(ctx context.Context) (string, error) {
	select {
	case <-time.After(200 * time.Millisecond):
		return "结果", nil
	case <-ctx.Done():
		return "", ctx.Err() // DeadlineExceeded 或 Canceled
	}
}

func main() {
	ctx := context.Background()
	ctx = context.WithValue(ctx, ctxKey{}, "trace-123")
	fmt.Println("透传的值:", ctx.Value(ctxKey{})) // trace-123

	timeoutCtx, cancel := context.WithTimeout(ctx, 50*time.Millisecond)
	defer cancel() // 即使提前返回也要调用，释放定时器与子节点

	res, err := slowWork(timeoutCtx)
	fmt.Printf("res=%q err=%v\n", res, err)
	// 预期输出：
	// 透传的值: trace-123
	// res="" err=context deadline exceeded

	// 父 context 被取消后，所有子 context 一并取消
	parent, cancelParent := context.WithCancel(context.Background())
	child, cancelChild := context.WithCancel(parent)
	defer cancelChild()

	cancelParent()
	<-child.Done()
	fmt.Println("子 context 的 Err:", child.Err()) // context canceled
}
```

**易错点：**

- 忘记调用 `cancel` 是最常见的泄漏源；即使设置了超时，也应 `defer cancel()`，让定时器尽早释放。
- 不要把 `context.Context` 存进结构体字段，应作为函数的**第一个参数**显式传递（命名约定 `ctx`）。
- 不要用 `context.WithValue` 传业务参数或可选配置，它会让依赖关系隐式化、类型不安全。
- key 不要用内置的 `string` 类型，容易与第三方库冲突；用 `type ctxKey struct{}` 这类未导出类型。
- 判断取消原因用 `errors.Is(err, context.DeadlineExceeded)`，不要直接比较字符串。
- `Done()` 可能返回 `nil`（如 `Background`），此时 `select` 中该分支永远阻塞，反而安全；但不能对它做 `close`。

## 11. 原子操作与 atomic 包

`sync/atomic` 提供对单个变量的**不可分割**读写，避免加锁的开销，是实现无锁数据结构与轻量计数的基础。

| API（函数式） | 作用 |
| --- | --- |
| `atomic.LoadT` | 原子读取 |
| `atomic.StoreT` | 原子写入 |
| `atomic.AddT` | 原子加减（仅整型、无符号整型） |
| `atomic.SwapT` | 原子交换，返回旧值 |
| `atomic.CompareAndSwapT` | CAS：旧值等于期望值时才写入 |
| `atomic.Value` | 存储任意类型的「整体快照」，读写都原子 |
| `atomic.Pointer[T]` | 泛型原子指针（Go 1.19+） |

Go 1.19 起还提供了类型化的原子类型：`atomic.Int32`、`atomic.Int64`、`atomic.Uint64`、`atomic.Bool`、`atomic.Pointer[T]` 等，使用 `Load/Store/Add/Swap/CompareAndSwap` 方法，避免手写函数名与对齐问题。

**内存模型：**

- `sync/atomic` 的操作具有**顺序一致性**语义，可以建立 happens-before 关系：对变量 X 的原子写，被另一个 goroutine 原子读到后，写之前的操作对该 goroutine 可见。
- 但原子操作**只保护它自己操作的那个变量**，多个字段之间的一致性仍需锁或其它同步手段。
- Go 1.19 修订了内存模型文档，明确了原子操作、channel、Mutex、Once 的同步语义。

| 维度 | atomic | Mutex |
| --- | --- | --- |
| 保护粒度 | 单个变量 | 一段临界区 / 多个字段 |
| 开销 | 一条 CPU 原子指令 | 原子操作 + 可能的休眠唤醒 |
| 可组合性 | 差，多字段一致性难保证 | 好，天然支持复合不变量 |
| 阻塞 | 不阻塞（CAS 失败需重试） | 会阻塞 |
| 适用场景 | 计数器、标志位、指针快照 | 复合结构、临界区较长、逻辑复杂 |

**CAS 循环模式：**

```go
for {
	old := x.Load()
	newVal := f(old)
	if x.CompareAndSwap(old, newVal) {
		break
	}
	// 失败说明被别人改过，重新读取再试
}
```

- CAS 存在 **ABA 问题**：值从 A 改成 B 又改回 A，CAS 会误以为没变过。带版本号的结构（如 `{value, version}` 打包成一个整数或用指针）可以缓解。
- 高竞争时 CAS 自旋会浪费 CPU，此时 Mutex 反而更划算。

```go
package main

import (
	"fmt"
	"sync"
	"sync/atomic"
)

func main() {
	// 原子计数
	var counter atomic.Int64
	var wg sync.WaitGroup
	for i := 0; i < 1000; i++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			counter.Add(1)
		}()
	}
	wg.Wait()
	fmt.Println("计数:", counter.Load()) // 1000

	// CAS 循环：无锁地更新最大值
	var max atomic.Int64
	updateMax := func(v int64) {
		for {
			old := max.Load()
			if v <= old || max.CompareAndSwap(old, v) {
				return
			}
		}
	}
	var wg2 sync.WaitGroup
	for _, v := range []int64{3, 9, 2, 7} {
		wg2.Add(1)
		go func(v int64) {
			defer wg2.Done()
			updateMax(v)
		}(v)
	}
	wg2.Wait()
	fmt.Println("最大值:", max.Load()) // 9

	// atomic.Value：整体替换配置快照，读路径无锁
	var cfg atomic.Value
	cfg.Store(map[string]string{"mode": "dev"})
	fmt.Println("配置:", cfg.Load().(map[string]string)["mode"]) // dev
}
```

**易错点：**

- 在 32 位平台上，64 位原子操作要求变量**8 字节对齐**；结构体首字段或全局变量通常满足，放在结构体中间可能 panic。使用 `atomic.Int64` 类型可规避。
- 原子类型**不能被复制**（`go vet` 会报错），包含它的结构体也不要按值传递。
- `atomic.Value` 要求所有 `Store` 的类型**完全一致**，否则 panic；也不能 `Store(nil)`。
- 普通变量的 `x++` 不是原子操作，即使它看起来只有一行。
- 原子操作保证的是单个变量的原子性，不保证「先检查再修改」的复合逻辑，这类逻辑要么用 CAS 循环，要么用锁。

## 12. 常见并发模式

| 模式 | 作用 | 关键点 | 常见坑 |
| --- | --- | --- | --- |
| fan-out | 一个输入分发给多个 worker 并行处理 | 多个 goroutine 读同一个 channel | worker 数量与下游消费能力不匹配 |
| fan-in | 多个输入合并到一个输出 | 用 WaitGroup 等所有生产者结束再 close | 忘记 close 导致 range 永不结束 |
| worker pool | 固定数量 worker 消费任务队列 | 任务 channel + 结果 channel + 关闭信号 | 任务无人关闭、worker 泄漏 |
| pipeline | 多阶段串联，每阶段一个 goroutine | 每阶段自己关闭输出 channel | 上游出错后下游永久阻塞，需要取消 |
| semaphore | 限制同时进行的任务数 | 带缓冲 channel 当令牌桶 | 令牌未释放导致永久阻塞 |
| rate limit | 限制单位时间内的请求数 | `time.Ticker` + `select` | Ticker 未 Stop |

**原则：**

1. **谁写谁关**：向 channel 发送数据的一方负责关闭；接收方只读。
2. **每阶段自己关闭输出**：pipeline 中每个 stage 在 `defer close(out)`，下游 `range` 才能正常结束。
3. **关闭是广播**：close 会让所有接收者立即解除阻塞，适合做「全部停止」的信号。
4. **取消要能传导**：长时间运行的模式都应接收 `ctx`，在 `ctx.Done()` 时退出。

**① fan-out + fan-in + worker pool：**

```go
package main

import (
	"fmt"
	"sync"
)

func producer(nums ...int) <-chan int {
	out := make(chan int)
	go func() {
		defer close(out) // 生产完由生产者关闭
		for _, n := range nums {
			out <- n
		}
	}()
	return out
}

func worker(id int, in <-chan int, out chan<- string, wg *sync.WaitGroup) {
	defer wg.Done()
	for n := range in { // in 关闭后循环自动结束
		out <- fmt.Sprintf("worker%d: %d*2=%d", id, n, n*2)
	}
}

func main() {
	in := producer(1, 2, 3, 4, 5, 6, 7, 8)

	// fan-out：3 个 worker 同时消费同一个 channel
	const workers = 3
	out := make(chan string)
	var wg sync.WaitGroup
	for i := 1; i <= workers; i++ {
		wg.Add(1)
		go worker(i, in, out, &wg)
	}

	// fan-in：等所有 worker 结束后关闭结果 channel
	go func() {
		wg.Wait()
		close(out)
	}()

	for s := range out {
		fmt.Println(s)
	}
	// 预期输出：共 8 行，worker 编号与顺序不固定，例如：
	// worker1: 1*2=2
	// worker2: 2*2=4
	// worker3: 3*2=6
	// worker1: 4*2=8
	// （其余 4 行同理）
}
```

**② pipeline（流水线）：**

```go
package main

import "fmt"

func gen(nums ...int) <-chan int {
	out := make(chan int)
	go func() {
		defer close(out)
		for _, n := range nums {
			out <- n
		}
	}()
	return out
}

func square(in <-chan int) <-chan int {
	out := make(chan int)
	go func() {
		defer close(out) // 每个阶段负责关闭自己的输出
		for n := range in {
			out <- n * n
		}
	}()
	return out
}

func main() {
	for v := range square(square(gen(1, 2, 3, 4))) {
		fmt.Println(v)
	}
	// 预期输出（顺序固定）：
	// 1
	// 16
	// 81
	// 256
}
```

**③ 信号量限流 + 固定速率限流：**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"time"
)

func main() {
	const (
		tasks      = 10
		concurrent = 3
	)
	sem := make(chan struct{}, concurrent) // 缓冲区大小 = 最大并发数
	var wg sync.WaitGroup
	var mu sync.Mutex
	running, peak := 0, 0

	for i := 0; i < tasks; i++ {
		wg.Add(1)
		sem <- struct{}{} // 获取令牌；已有 3 个在跑时这里阻塞
		go func(id int) {
			defer wg.Done()
			defer func() { <-sem }() // 释放令牌

			mu.Lock()
			running++
			if running > peak {
				peak = running
			}
			mu.Unlock()

			time.Sleep(20 * time.Millisecond) // 模拟任务耗时

			mu.Lock()
			running--
			mu.Unlock()
		}(i)
	}
	wg.Wait()
	fmt.Println("峰值并发:", peak) // 3

	// 固定速率限流：每 10ms 放行一次
	ctx, cancel := context.WithCancel(context.Background())
	defer cancel()
	limiter := time.NewTicker(10 * time.Millisecond)
	defer limiter.Stop()

	count := 0
	start := time.Now()
	for count < 5 {
		select {
		case <-ctx.Done():
			return
		case <-limiter.C:
			count++
		}
	}
	fmt.Printf("5 次放行耗时约 %v\n", time.Since(start).Round(10*time.Millisecond))
	// 预期输出：
	// 峰值并发: 3
	// 5 次放行耗时约 50ms
}
```

**易错点：**

- fan-in 汇总多个 channel 时，**必须等所有生产者结束后再 close 输出**，否则会向已关闭的 channel 发送而 panic。
- worker 数量并非越多越快：超过下游承载能力后只会增加上下文切换和内存占用。
- `range` 一个永远不关闭的 channel 会永久阻塞，是泄漏的常见来源；一定要有明确的关闭者或 `ctx` 退出路径。
- 用 channel 做信号量时，令牌获取与释放必须**成对**；`panic` 路径要用 defer 释放，否则永久占坑。
- 限流用 `time.Ticker` 记得 `Stop()`；循环内用 `time.After` 会不断创建定时器。

## 13. 数据竞争与 race detector

**数据竞争（data race）**：两个 goroutine 并发访问**同一块内存**，其中**至少一个是写**，且**没有同步措施**。满足以下三条即构成数据竞争：

1. 两个访问发生在不同 goroutine 中。
2. 访问同一内存地址。
3. 至少一次是写，且访问之间没有 happens-before 关系。

**数据竞争 ≠ 竞态条件（race condition）：**

| 概念 | 定义 | 是否一定被 race detector 发现 |
| --- | --- | --- |
| 数据竞争 | 未同步的并发读写同一内存 | 是（只要实际执行到） |
| 竞态条件 | 逻辑正确性依赖执行时序，如「先检查后执行」 | 不一定，可能完全由锁保护却没有数据竞争 |

**Go 内存模型中的 happens-before 来源：**

- 同一个 goroutine 内的语句按程序顺序。
- channel 的发送 happens-before 对应接收完成；关闭 channel happens-before 接收零值。
- `Mutex`/`RWMutex` 的解锁 happens-before 后续加锁。
- `WaitGroup` 的 `Done` happens-before `Wait` 返回。
- `sync.Once` 的 `Do` 返回 happens-before 任意 `Do` 返回。
- `atomic` 操作之间按顺序一致性建立同步。

**race detector 的使用：**

```bash
# 运行程序时检测
go run -race main.go

# 运行测试时检测（最常用）
go test -race ./...

# 构建带检测的二进制
go build -race -o app-race .
```

- 基于 **ThreadSanitizer**，通过在编译期插桩记录每次内存访问与同步事件，判断是否存在 happens-before 关系。
- 开销：CPU 约 5~10 倍，内存约 5~10 倍，因此只在测试/预发使用，不要用于生产。
- 局限：**只能发现实际执行到的竞争**；没跑到的分支、低概率时序可能漏报。

**有竞争的错误版本：**

```go
// racy.go
// 运行：go run -race racy.go
package main

import "fmt"

func main() {
	counter := 0
	done := make(chan struct{})
	for i := 0; i < 1000; i++ {
		go func() {
			counter++ // 未同步的并发写：数据竞争
			done <- struct{}{}
		}()
	}
	for i := 0; i < 1000; i++ {
		<-done
	}
	fmt.Println(counter)
	// 预期：通常小于 1000，且每次不同
	// go run -race 会输出类似：
	// WARNING: DATA RACE
	// Write at 0x... by goroutine N:
	//   main.main.func1()
	// Previous write at 0x... by goroutine M:
	//   main.main.func1()
}
```

**加锁修复后：**

```go
package main

import (
	"fmt"
	"sync"
)

func main() {
	var mu sync.Mutex
	counter := 0
	var wg sync.WaitGroup
	for i := 0; i < 1000; i++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			mu.Lock()
			counter++
			mu.Unlock()
		}()
	}
	wg.Wait()
	fmt.Println(counter) // 1000
}
```

**避免数据竞争的三条路径：**

1. **不共享**：把数据通过 channel 传递所有权，或每个 goroutine 持有自己的副本。
2. **共享但加同步**：`Mutex` 保护复合状态，`atomic` 保护单变量。
3. **不可变**：初始化完成后只读，不再写入（如全局配置快照）。

**易错点：**

- 用 `time.Sleep` 等待 goroutine 完成**不是同步**，不能建立 happens-before，`-race` 依然会报错。
- `map` 的并发读写不仅数据竞争，还会直接触发 `fatal error: concurrent map read and map write`，必须加锁或用 `sync.Map`。
- race detector 报的是**实际发生**的竞争，跑通一次没报错不代表没有竞争，CI 应长期开启 `-race`。
- 只读共享变量不需要同步，但前提是**初始化完成后绝不再写**，否则仍可能竞争。

## 14. 死锁与 goroutine 泄漏

**死锁**：两个或多个 goroutine 互相等待对方持有的资源，导致全部无法推进。

**死锁的四个必要条件：**

1. **互斥**：资源同一时刻只能被一个 goroutine 持有。
2. **占有且等待**：持有资源的同时等待其他资源。
3. **不可抢占**：资源只能由持有者主动释放。
4. **循环等待**：存在一个等待环。

**Go 运行时的检测**：当所有 goroutine 都处于阻塞状态、且没有任何可运行的 goroutine（包括 sysmon 也无法推进）时，runtime 会输出 `fatal error: all goroutines are asleep - deadlock!`。注意：只要还有任意一个 goroutine 能运行，runtime 就**不会**报死锁，程序只是「看起来卡住」。

**常见死锁形态：**

| 形态 | 示例 | 修复 |
| --- | --- | --- |
| 锁顺序不一致 | 两个 goroutine 以相反顺序锁 `mu1`、`mu2` | 全局统一加锁顺序 |
| 自锁 | 同一 goroutine 重复 `Lock` 不可重入的 Mutex | 拆锁或改用可重入设计 |
| channel 自等待 | 无缓冲 channel 上先发后收，且在同一 goroutine | 先启动接收方，或用缓冲 |
| `select {}` 空阻塞 | main 永久挂起且无其他可运行 G | 改用真正的等待或退出条件 |
| WaitGroup 误用 | `Wait` 时计数为 0，之后再 `Add` | 先 `Add` 再启动 goroutine |

**goroutine 泄漏**：goroutine 永久阻塞且没有任何路径能唤醒它，导致栈、引用对象和 runtime 结构都无法释放。

| 泄漏形态 | 典型代码 | 修复方式 |
| --- | --- | --- |
| 发送方永久阻塞 | 向无缓冲 channel 发送，但无人接收 | 保证有接收方，或使用容量为 1 的缓冲 |
| 接收方永久阻塞 | 等待一个永远不会关闭/发送的 channel | 用 `ctx.Done()` 退出 |
| 未取消的 context | `WithCancel` 后忘记 `cancel()` | `defer cancel()` |
| channel 未关闭 | `for v := range ch` 等不到结束 | 由发送方在结束时 close |
| 上游提前返回 | 下游 goroutine 还在往 channel 写 | 用 ctx 通知下游退出 |
| 锁等待 | 等待一把永不放开的锁 | 检查锁的持有与释放路径 |
| timer / ticker 未停 | 循环里创建定时器 | 复用 Timer 或 `defer Stop()` |

**排查方法：**

1. `runtime.NumGoroutine()`：观察数量是否随请求量单调增长且不回落。
2. `net/http/pprof` 的 goroutine profile：
   ```bash
   curl http://localhost:6060/debug/pprof/goroutine?debug=1   # 按栈聚合计数
   curl http://localhost:6060/debug/pprof/goroutine?debug=2   # 完整栈
   go tool pprof http://localhost:6060/debug/pprof/goroutine
   ```
3. `runtime/pprof.Lookup("goroutine").WriteTo(os.Stdout, 1)` 在信号或定时任务中打印。
4. 测试中使用 `go.uber.org/goleak`，在 `TestMain` 结束后检查是否有残留 goroutine。
5. 查看堆 profile 中 `runtime.gopark`、`chan.send`、`chan.recv`、`sync.(*Mutex).Lock` 的占比，定位阻塞点。

**泄漏示例与修复：**

```go
package main

import (
	"context"
	"fmt"
	"runtime"
	"time"
)

func leak() {
	ch := make(chan int) // 无缓冲，且没有接收方
	go func() {
		ch <- 42 // 永久阻塞在这里，goroutine 泄漏
	}()
}

func fixed(ctx context.Context) {
	ch := make(chan int, 1) // 缓冲为 1：即使暂时没人接收，发送也能完成
	go func() {
		select {
		case ch <- 42:
		case <-ctx.Done(): // 上游取消时退出
		}
	}()
	<-ch
}

func main() {
	base := runtime.NumGoroutine()

	for i := 0; i < 100; i++ {
		leak()
	}
	time.Sleep(100 * time.Millisecond) // 等 goroutine 都跑起来
	fmt.Println("泄漏后 goroutine 数:", runtime.NumGoroutine(), "基线:", base)
	// 预期：约 101（100 个泄漏 + main）

	ctx, cancel := context.WithCancel(context.Background())
	defer cancel()
	before := runtime.NumGoroutine()
	for i := 0; i < 100; i++ {
		fixed(ctx)
	}
	time.Sleep(50 * time.Millisecond)
	fmt.Println("修复后新增 goroutine:", runtime.NumGoroutine()-before)
	// 预期：0（任务完成后都已退出）
}
```

**死锁示例（会触发运行时检测）：**

```go
package main

import "sync"

func main() {
	var mu1, mu2 sync.Mutex

	// 两个 goroutine 以相反顺序加锁，形成循环等待
	go func() {
		mu1.Lock()
		defer mu1.Unlock()
		mu2.Lock()
		defer mu2.Unlock()
	}()

	go func() {
		mu2.Lock()
		defer mu2.Unlock()
		mu1.Lock()
		defer mu1.Unlock()
	}()

	select {} // 主 goroutine 永久阻塞
	// 预期输出：
	// fatal error: all goroutines are asleep - deadlock!
}
```

**易错点：**

- 有缓冲 channel 只能延缓泄漏，不能根治：缓冲写满后同样会阻塞，必须配套取消机制。
- `context.WithCancel` 的 `cancel` 忘记调用，即使 goroutine 早已结束，子 context 仍挂在父节点上，造成内存与定时器泄漏。
- 只在测试里跑一次没发现泄漏不代表安全，泄漏往往在异常分支（超时、错误返回）才出现。
- 线上排查优先看**阻塞栈聚合**（`debug=1`），它能直接告诉你「有多少个 goroutine 卡在同一个位置」，比逐个看栈高效。
- 修复死锁的根本手段是**统一资源获取顺序**、**缩小临界区**、**避免在持锁时调用外部代码**。
