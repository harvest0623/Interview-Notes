## 1. 内存分配与逃逸分析

**Go 采用「每 P 缓存 + 大小分级」的 TCMalloc 式分配：小对象在 mcache 上无锁分配，缓存不足时才逐级向 mcentral、mheap 申请。对象落在栈还是堆由编译期逃逸分析决定，而不是由 `new`、`&` 或「是不是指针」决定。栈分配零成本、随栈帧回收；堆分配要付出分配与 GC 扫描的代价，所以减少逃逸是最直接的优化手段。**

1. **三级结构**：`mcache`（每 P 私有，无锁）→ `mcentral`（每种 size class 一个，全局加锁）→ `mheap`（全局堆，管理 span 与 arena）→ 操作系统。
2. **mspan 与 spanClass**：堆按 8KB 页管理，若干连续页组成一个 `mspan`，只服务一种大小规格；`spanClass` 由 size class 编号与 `noscan` 标志组成，`noscan` 表示该 span 不含指针，GC 可整块跳过。
3. **size class 与 tiny 对象**：8B~32KB 共 67 档（8、16、24、32、48 … 32768），申请字节数向上取整到最近档位，因此有内部碎片；小于 16B 且不含指针的对象走 `mcache.tiny`，多个 tiny 对象塞进同一个 16B 块的不同偏移。
4. **分配路径**：tiny 路径 → mcache 对应档位 → 超过 32KB 的大对象直接由 mheap 按页分配，走全局锁。
5. **逃逸分析**：编译器在 IR 阶段分析引用去向，若地址可能被函数外部持有就分配到堆，否则留在栈上。编译器的 `maxStackVarSize` 为 10MB、隐式临时变量上限 64KB，超过阈值即使不逃逸也放堆。
6. **逃逸场景**：返回局部变量地址、闭包捕获、装箱进 interface、赋给全局变量、发送指针到 channel、动态大小的 `make([]T, n)`、map 扩容、反射间接持有、对象过大。

| 对象情况 | 分配来源 | 是否加锁 |
| --- | --- | --- |
| 无指针且 < 16B | `mcache.tiny` | 否 |
| ≤ 32KB（含指针或 ≥ 16B） | `mcache` 对应 size class 的 mspan，不足时向 mcentral 补货 | 否（补货时加锁） |
| > 32KB 大对象 | 直接从 `mheap` 按页分配 | 是（堆锁） |
| 逃逸的栈变量 | 编译器插入 `newobject`，走同样路径 | 取决于大小 |
| 未逃逸变量 | 当前 goroutine 栈 | 否，无 GC 开销 |

```go
package main

import "fmt"

type Point struct{ X, Y int }

func newPoint() *Point {
	return &Point{X: 1, Y: 2} // 地址被返回：逃逸到堆
}

func sum(a, b int) int {
	p := Point{X: a, Y: b} // 只在函数内用：留在栈上
	return p.X + p.Y
}

func counter() func() int {
	x := 0
	return func() int { // 闭包捕获 x：x 逃逸
		x++
		return x
	}
}

func box() any {
	v := 42 // 装箱进 interface：v 逃逸
	return v
}

func main() {
	fmt.Println(*newPoint(), sum(1, 2), counter()(), box())
}
```

```bash
# -m 打印结论，-m -m 打印推导链（flow、leaking param）
go build -gcflags="-m -m" main.go
# ./main.go:8:9:  &Point{...} escapes to heap
# ./main.go:12:2: p does not escape
# ./main.go:17:2: moved to heap: x
# ./main.go:23:2: v escapes to heap
go build -gcflags="-m -m" ./...   # 覆盖依赖包
```

**`-m` 输出解读：**

| 片段 | 含义 |
| --- | --- |
| `escapes to heap` | 该值必须在堆上分配 |
| `moved to heap: x` | 变量 x 本身被搬到堆 |
| `does not escape` | 未逃逸，可留在栈上 |
| `leaking param content: s` | 参数指向的内容被外部持有（如返回其底层数组） |

**优化手段：**

- 用 `-gcflags="-m"` 定位热点路径的意外逃逸，优先修循环内的逃逸。
- 小对象按值返回通常可留在栈上，且更利于内联；预分配容量、复用对象（`sync.Pool`、`strings.Builder`）。
- 减少热点路径的接口抽象与 `map[string]interface{}`，它们既阻止内联又让参数装箱逃逸。

**易错点：**

- 「用了指针就一定在堆上」是错的：`p := &T{}` 若不逃逸，T 可以放栈上；返回指针也不绝对逃逸，内联后可能落在调用方栈帧。
- 逃逸分析是编译器优化，不属于语言规范，升级 Go 版本后结论可能变化，不要依赖它保证正确性。
- `fmt.Println(x)` 会让 x 装箱进 `interface{}`，热点循环里应避免。

## 2. Go 的垃圾回收机制

**Go 使用并发的、非分代、非压缩的标记清扫收集器：三色标记找存活对象，混合写屏障保证并发正确，清扫阶段惰性回收未标记的 span。整个周期只有两次极短的 STW，标记与清扫绝大部分时间与业务代码并发。它不是引用计数，因此没有循环引用问题，代价是需要 STW 与写屏障。**

1. **非分代、非压缩**：每次 GC 扫描整个堆，不区分新生代/老年代；对象地址终生不变，栈上指针无需在 GC 时修正，但堆会产生外部碎片，靠 size class 缓解。
2. **并发标记**：由后台 mark worker 与用户 goroutine 共同完成；分配过快时触发 mutator assist，由分配者帮忙标记。
3. **两次 STW**：`mark setup`（开启写屏障）与 `mark termination`（关闭写屏障、收尾标记）各停一次，Go 1.14+ 都只有几十微秒。
4. **触发条件**：堆达到 GOGC 计算的目标、距上次 GC 超过 2 分钟（`forcegcperiod`）、手动 `runtime.GC()`、Go 1.19 起的软内存限制。
5. **标记清扫 ≠ 引用计数**：标记从根集合出发遍历可达对象，天然处理循环引用，但回收有延迟；引用计数在赋值时维护计数，归零即回收，需要额外的循环检测。
6. **清扫是惰性的**：GC 结束后并不立刻归还全部内存，分配时才清扫对应 span，空闲页由 scavenger 渐进还给 OS。

| 阶段 | 是否 STW | 主要工作 |
| --- | --- | --- |
| sweep termination | 是（极短） | 结束上一轮未扫完的清扫 |
| mark setup | 是（极短） | 开启混合写屏障，启动 mark worker |
| concurrent mark | 否，与业务并发 | 从栈、全局变量、寄存器出发做三色标记；分配过快时 assist |
| mark termination | 是（极短） | 关闭写屏障，完成剩余标记，统计存活堆与下次目标 |
| concurrent sweep | 否，惰性执行 | 清扫未标记 span，空闲页归还 mheap |

```text
  STW①           并发标记（与业务代码同时进行）          STW②        并发清扫
  sweep term. → mark setup → mark workers + assist → mark term. → sweep
   几十微秒      开启写屏障      三色标记推进            关闭写屏障     惰性回收
```

```go
package main

import (
	"fmt"
	"runtime"
	"time"
)

func alloc(n int) []byte {
	b := make([]byte, n)
	for i := range b {
		b[i] = byte(i)
	}
	return b
}

func main() {
	var before, after runtime.MemStats
	runtime.ReadMemStats(&before)

	keep := make([][]byte, 0, 64)
	for i := 0; i < 64; i++ {
		keep = append(keep, alloc(1<<20)) // 保留 64MB 存活堆，制造 GC 压力
	}

	runtime.GC() // 手动触发完整 GC，线上不要在请求路径调用
	runtime.ReadMemStats(&after)

	fmt.Printf("GC 次数: %d -> %d\n", before.NumGC, after.NumGC)
	fmt.Printf("堆对象数: %d -> %d\n", before.HeapObjects, after.HeapObjects)
	fmt.Printf("存活堆: %.1f MB\n", float64(after.HeapAlloc)/(1<<20))
	fmt.Printf("GC 累计暂停: %v\n", time.Duration(after.PauseTotalNs))
	fmt.Printf("下次目标: %.1f MB\n", float64(after.NextGC)/(1<<20))
	_ = keep
}
```

```bash
# 每个 GC 周期打印一行，可直接观察频率与停顿
GODEBUG=gctrace=1 go run main.go
# gc 1 @0.003s 0%: 0.006+0.12+0.003 ms clock, 0.048+0.10/0.06/0.001+0.024 ms cpu, 4->4->3 MB, 6 MB goal, 0 B (forced), 8 P
```

**Go 1.24 的改进**：引入按尺寸特化的新小对象分配器（size-specialized malloc），降低小对象的元数据与碎片开销。

**易错点：**

- `runtime.GC()` 会阻塞等整个周期结束，线上不要在请求路径调用；`debug.FreeOSMemory()` 同样带来明显停顿。
- 即使没有内存压力，也可能因 2 分钟强制 GC 被触发，不能假设「不分配就不会 GC」。
- 并发标记 ≠ 没有停顿：`mark setup` 与 `mark termination` 依然是 STW，只是极短。
- `MemStats.PauseTotalNs` 是历史累计值，不是上一次停顿。

## 3. 三色标记法与写屏障

**三色标记把对象分成白、灰、黑，从根集合出发把可达对象逐步染黑，剩下的白色即为垃圾。并发标记期间用户代码会改指针，可能破坏「黑对象不直接指向白对象」的不变式，于是需要写屏障在赋值时补一次标记。Go 1.8 起使用混合写屏障（插入 + 删除），并约定「GC 开始后新建的栈对象一律标黑」，使标记结束阶段不必重新扫描所有栈，把 STW 压到几十微秒。**

1. **白色**：尚未访问，标记结束时仍为白的对象会被回收。
2. **灰色**：自身已访问、子对象未扫描完，是待处理队列。
3. **黑色**：自身与子对象都扫描完毕，确定存活。

**漏标的两个条件（必须同时满足）：**

1. 黑色对象**新增**了指向白色对象的引用（标记器不会回头再扫黑对象）。
2. 该白色对象**失去**了所有从灰色对象出发的可达路径（被删除引用）。

破坏任一条件即可避免漏标，这就是两类写屏障的出发点。

| 不变式 | 表述 | 实现手段 |
| --- | --- | --- |
| 强三色不变式 | 黑色对象不允许直接指向白色对象 | 插入写屏障（Dijkstra） |
| 弱三色不变式 | 黑指向的白对象，必须存在一条从灰经白到达它的路径 | 删除写屏障（Yuasa） |

```text
// 插入写屏障：新引用的目标直接标灰，破坏条件 1
writePointer(slot, ptr):
    shade(ptr)
    *slot = ptr

// 删除写屏障：被覆盖的旧值标灰，破坏条件 2
writePointer(slot, ptr):
    shade(*slot)
    *slot = ptr

// Go 1.8 混合写屏障：两者都做
writePointer(slot, ptr):
    shade(*slot)   // 删除屏障
    shade(ptr)     // 插入屏障
    *slot = ptr
```

**Go 1.8 混合写屏障解决了什么：**

- Go 1.8 之前只用插入写屏障（Dijkstra），而**栈上的指针写不开启屏障**（栈写太频繁）；所以标记结束必须重扫所有 goroutine 的栈，这段是 STW 的，栈越多停得越久。
- 混合写屏障配合「GC 开始后新建的栈对象一律标黑、栈上已有对象指向的目标也标黑」，栈上不会出现「黑指向白」，标记结束**无需重扫栈**。
- 结果：STW 从与 goroutine 数量相关的毫秒级降到几十微秒，代价是每个指针写多做一次标记。

**屏障开销：**

- 屏障由编译器插在**指针写**处，读写数值、字符串、非指针字段不触发。
- 每个指针写多几条指令（判断阶段、把对象入灰队列），典型代价是个位数百分比；只在标记阶段真正生效。

```bash
# 在汇编中观察写屏障调用（amd64）
go tool compile -S main.go | grep -A2 "gcWriteBarrier"
#   LEAQ    type:int(SB), AX
#   CALL    runtime.gcWriteBarrier2(SB)
# 一次指针写被展开为「写屏障 + 真正写入」两步
```

```go
package main

import "fmt"

type Node struct {
	next *Node // 指针字段：赋值会触发写屏障，GC 需沿它扫描
	val  int
}

func main() {
	a := &Node{val: 1}
	b := &Node{val: 2}
	a.next = b // 标记阶段这一行会走混合写屏障
	fmt.Println(a.next.val)
}
```

**易错点：**

- 「三色」是逻辑抽象，对象没有颜色字段，颜色编码在 span 的 mark bits 与 gcWork 队列里。
- 写屏障只对指针类型的写生效，且只在标记阶段有意义；栈上不开启写屏障是设计选择，靠「新栈对象标黑」保证正确性。
- 混合写屏障同时做插入与删除，灰队列比单一屏障略大，是用少量 CPU 换 STW。

## 4. GC 调优与 GOGC

**GOGC 控制「堆涨多少比例后触发下一次 GC」，默认 100 表示堆达到上次存活堆的 2 倍时触发。调大减少 GC 次数、提高吞吐但增加内存；调小相反。Go 1.19 的 GOMEMLIMIT 提供软内存上限，可以理解为「在内存预算内尽量少 GC」，容器场景比单纯调 GOGC 更稳。调优顺序永远是：先减少分配，再谈参数。**

1. **GOGC 的计算**：目标堆 ≈ 本轮存活堆 × (1 + GOGC/100)。存活 100MB、GOGC=100 时目标约 200MB，GOGC=50 时约 150MB。
2. **GOGC=off**：关闭比例触发，只剩 2 分钟强制 GC 与手动触发；适合批处理或配合 GOMEMLIMIT。
3. **GOMEMLIMIT（Go 1.19+）**：软限制，可写 `4GiB` 这类单位，也可用 `debug.SetMemoryLimit` 运行期调整；接近上限时 GC 更早更频繁，但**不保证不超限**（栈、cgo 内存不完全受控）。
4. **平衡点**：GC 太频繁会吃掉 CPU、增加延迟抖动；GC 太少则堆膨胀、单次标记变长、可能 OOM。
5. **容器场景**：GOGC 只看堆比例，容易在限额边缘反复横跳；通常把 GOMEMLIMIT 设为容器 limit 的 80%~90%，GOGC 保持默认或适当调大。
6. **两者的关系**：GOMEMLIMIT 不是替代 GOGC，而是叠加约束。运行时每轮都取「按 GOGC 算出的目标」与「内存上限对应的目标」中更小的那个，所以到限后即使堆没翻倍也会 GC。

| 配置 | 行为 | 适用场景 |
| --- | --- | --- |
| 默认 GOGC=100 | 存活堆翻倍时触发 | 大多数服务 |
| GOGC=50 | 更早触发，省内存、费 CPU | 内存敏感、延迟不敏感 |
| GOGC=200~400 | 更晚触发，吞吐更高、峰值更大 | 吞吐优先、内存充足 |
| GOGC=off | 只靠 2 分钟强制 GC 与手动触发 | 批处理、配合 GOMEMLIMIT |
| GOGC=off + GOMEMLIMIT | 到限才 GC，尽量少停顿 | 容器内长驻服务（需实测） |

**读懂 gctrace 的一行输出：**

```text
gc 12 @3.421s 4%: 0.021+2.145+0.003 ms clock, 0.168+1.02/1.90/0.002+0.024 ms cpu, 120->245->130 MB, 260 MB goal, 0 B (forced), 8 P
```

| 字段 | 含义 |
| --- | --- |
| `gc 12` | 第 12 次 GC |
| `@3.421s` | 程序启动后 3.421 秒发生 |
| `4%` | 到目前为止 GC 占用的 CPU 时间比例 |
| `0.021+2.145+0.003 ms clock` | 墙钟：STW① + 并发标记 + STW② |
| `0.168+1.02/1.90/0.002+0.024 ms cpu` | assist + 后台标记（专用/空闲/分数 worker）+ STW② |

```go
package main

import (
	"fmt"
	"runtime/debug"
)

func main() {
	old := debug.SetGCPercent(200) // 等价于 GOGC=200，返回旧值
	fmt.Println("旧的 GOGC:", old)

	// 软内存限制（Go 1.19+），单位字节
	debug.SetMemoryLimit(3 << 30) // 3GiB

	// 读出当前限制，便于日志核对配置是否生效
	fmt.Println("当前内存上限:", debug.SetMemoryLimit(-1))
}
```

**GC 频繁的排查思路：**

1. **看分配速率**：`alloc_space` 曲线陡峭说明分配快，GC 只是结果。
2. **找 top 分配点**：按 `alloc_objects` 排序，常能发现循环里的小对象（`fmt.Sprintf`、临时切片）。
3. **检查逃逸**：确认热点函数是否意外逃逸（装箱、闭包、返回指针）。
4. **降低分配量**：预分配、`sync.Pool`、`strings.Builder`、避免 `[]byte` 与 `string` 反复转换。
5. **减少存活与指针密度**：无上限缓存会让存活堆与 GC 目标一起抬高，表现为内存只涨不降；`map[string]*T` 换成 `map[string]T` 可缩短扫描队列。
6. **最后调参数**：分配量合理后再调 GOGC，或用 GOMEMLIMIT 兜底。

**易错点：**

- GOGC 是百分比，不是内存绝对值，`GOGC=100` 不是「堆最多 100MB」。
- GOMEMLIMIT 是软限制，超限只会让 GC 更激进，不会阻塞分配，仍可能 OOM。
- 调大 GOGC 会让单次标记的存活堆更大、扫描更久，STW 未必变短；`SetGCPercent` 传负数等价于关闭 GC。

## 5. interface 的底层结构

**接口固定占两个字长（64 位 16 字节）：空接口 `eface` 是「类型指针 + 数据指针」，带方法的接口 `iface` 是「itab 指针 + 数据指针」。itab 把接口方法集与动态类型的方法地址绑定，接口调用是查表后的间接跳转，因此无法内联、比直接调用慢；类型断言是运行期类型比较。装箱可能引发堆分配，typed-nil 则让「接口不为 nil」成为经典陷阱。**

1. **eface**：`interface{}`（即 `any`）只有 `_type` 与 `data`。`_type` 描述动态类型（大小、对齐、kind、方法集），`data` 指向数据；动态类型是指针宽度时，`data` 直接存该值。
2. **iface 与 itab**：非空接口是 `tab *itab` + `data`；itab 含接口类型 `inter`、动态类型 `_type`、哈希 `hash` 与变长方法地址数组 `fun [1]uintptr`，长度由接口方法数决定。
3. **itab 的生成与缓存**：赋值时调用 `getitab`，先查全局 `itabTable`（开放寻址哈希表）；命中复用，未命中则校验方法集，成功则新建并缓存，失败则 panic（`interface conversion: ... is not ...`），失败组合不缓存。
4. **调用开销**：`s.Area()` 编译为「取 `itab.fun[k]` → 间接 CALL」，多两次内存加载和一次间接跳转；间接调用点无法内联，因此小方法用接口抽象会明显变慢。
5. **类型断言**：`v, ok := i.(T)` 对空接口比较 `_type`，对非空接口比较 itab；`switch i.(type)` 按 case 顺序比较，case 越多越慢。
6. **接口嵌入与转换**：接口之间可以直接赋值（如 `io.ReadWriter` 赋给 `io.Reader`），运行时只需换 itab；但具体类型指针与接口之间的转换每次都要查表。
7. **装箱是否分配**：通常需要一份稳定副本，可能逃逸到堆；若接口值本身不逃逸、类型是小整数（0~255 由运行时静态数组复用）或本身是指针，则可能不产生新分配。

| 对比项 | eface（`any`） | iface（带方法） |
| --- | --- | --- |
| 运行时结构 | `_type` + `data` | `itab` + `data` |
| 大小（64 位） | 16 字节 | 16 字节 |
| 类型信息来源 | 直接读 `_type` | 通过 `itab._type` |
| 能否直接调方法 | 不能，必须断言 | 能，走 `itab.fun[i]` |
| 赋值成本 | 写类型指针 + 数据 | 先 `getitab` 查表/建表，再写数据 |

```go
package main

import "fmt"

type Shape interface{ Area() float64 }

type Rect struct{ W, H float64 }

func (r Rect) Area() float64 { return r.W * r.H }

type MyErr struct{ code int }

func (e *MyErr) Error() string { return "my err" } // 不解引用 e，避免 nil panic

func newErr() error {
	var p *MyErr // p 本身是 nil
	return p     // 装进 iface：tab 非空，data 为 nil
}

func main() {
	var s Shape = Rect{W: 2, H: 3}
	fmt.Println(s.Area()) // 通过 itab.fun[0] 间接调用，接收者被复制

	var v any = 42
	if n, ok := v.(int); ok { // 断言失败不 panic，返回零值 + false
		fmt.Println(n)
	}
	if _, ok := v.(string); !ok {
		fmt.Println("不是 string")
	}

	err := newErr()
	fmt.Println(err == nil) // false：接口带有类型信息
	if err != nil {
		fmt.Println("err:", err) // err: my err
	}
}
```

```bash
# 观察接口调用被编译成间接跳转
go tool compile -S main.go | grep -E "CALL.*AX|CALL.*\(.*\)"
# 检查接口参数是否发生装箱逃逸
go build -gcflags="-m" main.go 2>&1 | grep "escapes to heap"
# 观察接口调用的汇编：CALL 的目标来自 itab，无法内联
go tool objdump -s "main.main" app | grep CALL
# 量化「接口调用 vs 直接调用」差距
go test -bench=. -benchmem -run=^$ ./...
```

**易错点：**

- `var p *T = nil; var i any = p` 之后 `i != nil` 为 true，判空要看「类型 + 数据」是否都为空。
- 返回 `error` 时不要返回具体类型的 nil 指针，应显式 `return nil`，否则调用方 `err != nil` 恒成立。
- 接口方法集按「值接收者方法属于 T 和 *T，指针接收者方法只属于 *T」计算，`*T` 能装入的接口 `T` 未必能装入。
- 热点路径不要滥用接口解耦：接口调用既阻止内联，又可能让参数装箱逃逸；大结构体装箱还会整体复制一份，应改存指针。
- `any` 与 `interface{}` 完全等价，不存在性能差异。

## 6. 反射的原理与使用

**反射是在运行时绕过编译期类型系统操作值，入口是 `reflect.TypeOf` 与 `reflect.ValueOf`，参数会先装箱进接口。`reflect.Type` 描述类型，`reflect.Value` 描述具体值（含数据指针与标志位）。只有「可寻址且可导出」的 Value 才能被修改，这就是 `ValueOf(x).SetInt()` 必然 panic 的原因。反射灵活但慢，工程上应优先用代码生成、泛型或显式类型分支替代。**

1. **Type 与 Value**：`TypeOf(i)` 返回 `reflect.Type`（底层是运行时的 `*rtype`）；`ValueOf(i)` 返回 `reflect.Value`（含 `typ`、`ptr`、`flag`）。Value 是值语义，复制它不影响原值。
2. **Kind 与 Type**：Type 是具体类型，Kind 是底层分类。`type MyInt int` 的 Name 是 `MyInt`，Kind 是 `reflect.Int`；归类判断用 Kind，具体类型用 Type 或类型断言。
3. **可寻址（CanAddr）**：`ValueOf(x)` 拿到副本，不可寻址；`ValueOf(&x).Elem()` 指向 x，可寻址。只有可寻址的 Value 才可能被修改。
4. **可设置（CanSet）**：可寻址且字段可导出才为 true。未导出字段带 `flagRO` 标记，即使通过 `Elem()` 拿到也不能 Set，强设会 panic。
5. **StructField 与 Tag**：`Type.Field(i)` 返回 `StructField`，含 `Name`、`Type`、`Tag`、`Offset`、`Index`、`Anonymous`；`encoding/json` 正是读字段与 `json` tag 并缓存后序列化。
6. **性能与替代**：反射包含装箱、类型检查与动态分派，通常慢一到两个数量级，`FieldByName` 还要做字符串匹配。替代方案：`go generate` 代码生成（easyjson、stringer、msgp）、泛型、缓存 Type 与字段索引。

```go
package main

import (
	"fmt"
	"reflect"
)

type User struct {
	Name string `json:"name"`
	Age  int    `json:"age,omitempty"`
	mail string // 未导出字段
}

func main() {
	u := User{Name: "gopher", Age: 18}
	t := reflect.TypeOf(u)
	v := reflect.ValueOf(u)

	fmt.Println(t.Name(), t.Kind(), t.NumField()) // User struct 3
	fmt.Println(v.FieldByName("Age").Int())       // 18
	fmt.Println(v.FieldByName("Age").CanSet())    // false：Value 是副本

	// 修改：必须通过指针拿到可寻址的 Value
	pv := reflect.ValueOf(&u).Elem()
	fmt.Println(pv.CanAddr(), pv.CanSet()) // true true
	pv.FieldByName("Name").SetString("alice")

	// 未导出字段：可寻址也不可设置
	f := pv.FieldByName("mail")
	fmt.Println(f.CanAddr(), f.CanSet()) // true false
	// f.SetString("x") // panic: ... using value obtained using unexported field

	// Tag 解析：序列化库的核心依赖
	sf, _ := t.FieldByName("Age")
	fmt.Println(sf.Tag.Get("json")) // age,omitempty
	fmt.Println(sf.Offset)          // 16：Name 是 string，占 16 字节

	fmt.Println(u) // {alice 18 }
}
```

| 实现方式 | 相对性能 | 适用场景 |
| --- | --- | --- |
| 直接字段访问 | 1x | 已知类型的业务代码 |
| 类型断言 / 类型 switch | 数倍 | 类型集合有限且稳定 |
| 反射（缓存 Type 与字段索引） | 数十倍 | 通用库、ORM、序列化 |
| 反射（每次 `FieldByName`） | 上百倍 | 不推荐用于热点路径 |
| 代码生成 / 泛型 | 接近直接访问 | 性能敏感的序列化、校验 |

```bash
# 量化反射开销：两组 benchmark 对比 ns/op 与 allocs/op
go test -bench='Reflect|Direct' -benchmem -run=^$ ./...
# 确认反射路径上的装箱逃逸
go build -gcflags="-m" ./... 2>&1 | grep "escapes to heap"
# 生成代码与反射的对比（如 easyjson 生成 MarshalJSON）
go generate ./...
```

**易错点：**

- `reflect.ValueOf(nil)` 返回零 Value，`Kind()` 是 `Invalid`，调用 `Interface()` 会 panic。
- `CanSet` 为 false 时不要硬调 `Set*`，先判断 `CanAddr && CanSet`。
- 反射拿到的 Value 是副本，修改它不影响原变量，除非来自指针的 `Elem()`。
- 未导出字段不能 `Interface()`，JSON 序列化也会跳过；反射把编译期错误变成运行期 panic。
- 反射无法绕过类型系统做不安全转换，那是 `unsafe` 的领域；ORM 类库要限制可用字段，避免能力外泄。

## 7. unsafe.Pointer 的使用

**`unsafe.Pointer` 是唯一能在任意指针类型间转换的通用指针，且和普通指针一样被 GC 追踪。它受四条转换规则约束，最关键的是：`unsafe.Pointer` 与 `uintptr` 的互转必须写在同一个表达式里。因为 `uintptr` 只是整数，GC 不会把它当指针，一旦单独存进变量，对象就可能被回收。它适合零拷贝转换、读取结构体布局、与 C 交互；滥用会直接破坏内存安全。**

**四条转换规则：**

1. 任意 `*T` 可转 `unsafe.Pointer`。
2. `unsafe.Pointer` 可转任意 `*T`（不要求与原类型相同）。
3. `uintptr` 可转 `unsafe.Pointer`。
4. `unsafe.Pointer` 可转 `uintptr`。

> 规则 3、4 的附加约束：互转必须出现在**同一个表达式**中。写成 `u := uintptr(p); q := unsafe.Pointer(u)` 是未定义行为，因为中间没有任何东西让 GC 知道 `p` 还活着。

```text
安全（一行内完成）：
    p := (*T)(unsafe.Pointer(uintptr(base) + offset))

不安全（中间存了 uintptr）：
    u := uintptr(unsafe.Pointer(p))   // p 已无人引用
    runtime.GC()                      // 对象可能被回收
    q := (*T)(unsafe.Pointer(u))      // 悬垂指针
```

| 函数 | 作用 | 返回值性质 |
| --- | --- | --- |
| `unsafe.Sizeof(x)` | 类型占用的字节数（不含堆数据） | 编译期常量 |
| `unsafe.Alignof(x)` | 类型要求的对齐字节数 | 编译期常量 |
| `unsafe.Offsetof(s.f)` | 字段相对结构体起始的偏移 | 编译期常量 |
| `unsafe.String(ptr, len)` | 指针 + 长度构造 string（Go 1.20+） | 不复制 |
| `unsafe.StringData(s)` | 取 string 底层数据指针（Go 1.20+） | 只读 |
| `unsafe.Slice(ptr, len)` | 指针 + 长度构造切片（Go 1.17+） | 不复制 |
| `unsafe.SliceData(s)` | 取切片底层数组指针（Go 1.20+） | 可写 |
| `unsafe.Add(ptr, len)` | 指针偏移，替代 uintptr 运算（Go 1.17+） | 保持指针语义 |

```go
package main

import (
	"fmt"
	"runtime"
	"unsafe"
)

// []byte -> string：零拷贝，与 b 共享内存
func bytesToString(b []byte) string {
	return unsafe.String(unsafe.SliceData(b), len(b)) // Go 1.20+
}

// string -> []byte：零拷贝，只可读
func stringToBytes(s string) []byte {
	return unsafe.Slice(unsafe.StringData(s), len(s)) // Go 1.20+
}

func main() {
	b := []byte("hello")
	s := bytesToString(b)
	b[0] = 'H'
	fmt.Println(s) // Hello —— 修改 b 会“穿透”到 s，证明不是副本

	raw := stringToBytes("world")
	fmt.Println(len(raw)) // 5；写 raw[0] 是禁止的：字面量在只读段，可能直接段错误

	type S struct {
		A int32
		B int64
	}
	var x S
	fmt.Println(unsafe.Sizeof(x))     // 16：4 字节 + 4 字节 padding + 8 字节
	fmt.Println(unsafe.Alignof(x))    // 8
	fmt.Println(unsafe.Offsetof(x.B)) // 8

	// uintptr 不是指针，GC 不追踪
	p := new(int)
	*p = 42
	u := uintptr(unsafe.Pointer(p))
	runtime.GC()                   // p 已无引用，可能在此被回收
	_ = *(*int)(unsafe.Pointer(u)) // 未定义行为
	runtime.KeepAlive(p)           // 正确做法：让 p 活到这里

	// 安全的指针运算：一行内完成
	arr := [4]int{10, 20, 30, 40}
	q := (*int)(unsafe.Add(unsafe.Pointer(&arr[0]), unsafe.Sizeof(arr[0])))
	fmt.Println(*q) // 20
}
```

**版本差异**：Go 1.17 引入 `unsafe.Add`、`unsafe.Slice`；Go 1.20 引入 `unsafe.String`、`unsafe.StringData`、`unsafe.SliceData`，`reflect.SliceHeader` 的旧用法退出历史；需要独立副本时应用 `strings.Clone`（Go 1.18+）。

**易错点：**

- `unsafe.Pointer` 与 `uintptr` 互转必须一行完成，中间存进变量就是悬垂指针。
- 零拷贝得到的 string 内容不稳定：原 `[]byte` 被复用后（`sync.Pool` 归还、buffer 重置），字符串内容会跟着变。
- `stringToBytes` 的切片绝对不能写、也不能 append；`unsafe.Sizeof(f())` 不会调用 f，只按类型求值。

## 8. 编译与链接过程

**`go build` 是一条依赖图驱动的并行流水线：先解析 import 得到包依赖 DAG，再按拓扑序并发编译每个包，命中构建缓存则直接复用；单包内部经历词法分析、语法分析、类型检查、IR 降糖、内联与逃逸分析、SSA 优化、机器码生成；最后由链接器做符号解析与重定位。内联与逃逸分析都在中端 IR 上完成，链接器只关心符号与段布局。**

```text
go build .
   ├─ 1. 解析 import，构建包依赖 DAG，检测循环依赖
   ├─ 2. 按拓扑序并发编译各包；命中 GOCACHE 直接复用
   │      词法分析 scanner → 语法分析 parser（AST）
   │      → 类型检查 types2（含泛型实例化）
   │      → IR 降糖 walk（range、闭包、defer、panic 展开）
   │      → 内联 inline → 逃逸分析 escape
   │      → SSA 优化（常量传播、边界检查消除、寄存器分配）
   │      → 生成机器码，写入目标文件
   ├─ 3. 打包归档（.a）：导出数据 + 目标代码
   └─ 4. 链接 cmd/link：符号解析、重定位、段合并 → 可执行文件
```

| 阶段 | 主要工作 | 观测手段 |
| --- | --- | --- |
| 前端 | 词法、语法、类型检查 | 编译错误、`gofmt`、`go vet` |
| 中端 | 降糖、内联、逃逸分析 | `-gcflags="-m"`、`-gcflags="-l"` 关闭内联 |
| 后端 | SSA 优化、机器码生成 | `-gcflags="-S"`、`go tool objdump` |
| 链接 | 符号解析、重定位、段布局 | `go tool nm`、`-ldflags`、`go version -m` |
| 缓存 | 按内容寻址复用编译产物 | `go env GOCACHE`、`go clean -cache` |

1. **词法与语法**：`scanner` 切 token，`parser` 产出 AST，语法错误在这一步报出。
2. **类型检查**：`types2` 做类型推导、接口实现检查、泛型实例化，是编译期错误的主要来源。
3. **降糖**：`range`、`defer`、`select`、闭包、`go` 语句被展开为更基础的形式，例如 `defer` 转成 `deferproc`/`deferreturn`，闭包转成带捕获变量的结构体。
4. **内联**：在 IR 阶段按函数体节点数（默认预算 80）决定是否展开；内联后调用方会重新做逃逸分析，所以「内联消除逃逸」很常见。Go 1.20 引入 PGO，Go 1.21 起 `-pgo=auto` 默认开启，读取 main 包目录的 `default.pgo`。
5. **SSA 与机器码**：常量传播、冗余消除、边界检查消除、寄存器分配，最终由各架构后端生成汇编。
6. **链接**：合并目标文件、解析符号、完成重定位，按目标格式（ELF/Mach-O/PE）写出可执行文件；只有 main 包触发链接。
7. **构建缓存**：每个包的编译输入（源码、编译器版本、flags、依赖的导出数据）算一个哈希，产物按哈希存放，命中即免编译；哈希基于内容而非时间戳。
8. **为什么二进制大**：静态链接运行时（GC、调度器、类型信息），且默认保留符号表与 DWARF；剥离后典型可减 25%~30%。

```bash
go build -x -work ./...            # 打印执行的命令，保留临时目录
go env GOCACHE GOOS GOARCH CGO_ENABLED
go clean -cache                    # 清空构建缓存（排查可疑的陈旧产物）
go build -a ./...                  # 忽略缓存强制重建
go tool compile -S main.go         # 只编译不链接，输出汇编
go build -gcflags="-m" ./... 2>&1 | grep "can inline"
go build -gcflags="-l" ./...       # 关闭内联，对比二进制体积与基准结果
go build -trimpath -ldflags "-s -w -X main.version=1.2.3" -o app .
go tool nm app | grep "main.main"
go version -m app                  # 读取 buildinfo（模块、依赖、构建参数）
GOOS=linux GOARCH=amd64 CGO_ENABLED=0 go build -o app-linux .
go tool dist list | grep linux     # 查看支持的 GOOS/GOARCH 组合
go list -deps ./... | wc -l        # 统计依赖包数量，依赖越多编译越慢
go build -pgo=auto ./...           # Go 1.21+ 默认值，等价于显式开启 PGO
go build -buildvcs=false ./...     # 不写入 VCS 信息，提升可复现性
go build -gcflags="-d=ssa/check_bce/debug=1" ./...   # 查看边界检查消除情况
```

| 维度 | `CGO_ENABLED=0` | `CGO_ENABLED=1` |
| --- | --- | --- |
| 依赖 | 只需 Go 工具链 | 需要 C 编译器与头文件 |
| 产物 | 完全静态，可放入 scratch 镜像 | 动态链接 libc |
| 交叉编译 | 直接指定 GOOS/GOARCH | 需要交叉工具链 |
| 编译速度 | 快 | 慢（cgo 预处理 + C 编译） |
| 运行时开销 | 无额外切换 | cgo 调用有栈切换与调度开销 |
| DNS 解析 | 纯 Go 解析器 | 默认走 libc 解析器 |

**可复现构建的要点：**

- 加 `-trimpath` 去掉绝对路径，避免不同机器编出的二进制哈希不同。
- 固定工具链与依赖：`go.mod` 声明 `toolchain`、`go.sum` 校验、`GOFLAGS=-mod=readonly` 防止构建偷偷改 `go.mod`。
- 构建信息会写进二进制，用 `go version -m app` 审计；介意体积时加 `-buildvcs=false`。

**易错点：**

- `-ldflags "-s -w"` 去掉符号表与 DWARF 信息，panic 仍能显示行号（依赖 pclntab），但源码级调试受影响。
- 构建缓存是内容寻址的，改了 `-ldflags`、`-tags` 或 Go 版本都会失效，不是缓存坏了。
- 内联不是越多越好，过度内联增大体积、恶化 instruction cache；`//go:noinline` 可用于对照。
- 用 `-gcflags` 时漏掉 `./...` 就只看当前包，看不到依赖包的输出。
- `-trimpath` 会移除构建路径，`runtime.Caller` 返回的文件路径随之变化，日志与监控不要硬编码绝对路径。
- `go build` 默认只处理当前目录的包，`./...` 才遍历子目录；脚本里漏写是「改了没生效」的常见原因。

## 9. 程序启动流程

**Go 的真正入口不是 `main.main`，而是链接器指定的 `runtime.rt0_go` 汇编入口。它建立 g0 栈与 TLS，调用 `args`、`osinit`、`schedinit` 完成运行时初始化，再用 `newproc` 创建 `runtime.main` 这个 goroutine，由 `mstart` 进入调度。`runtime.main` 依次启动 sysmon、开启 GC、执行所有包的 init，最后调用 `main.main`；`main.main` 返回后进程立即退出，不等待其他 goroutine。**

```text
ELF 入口 _rt0_amd64_linux
   ↓
runtime.rt0_go（汇编）
   ├─ 分配 g0 栈，把 g 指针写入 TLS
   ├─ runtime.args / osinit（CPU 数、物理页大小）
   ├─ runtime.schedinit
   │    ├─ mallocinit     初始化 mheap 与 size class
   │    ├─ mcommoninit    登记 m0
   │    ├─ gcinit         初始化 GC（尚未开启）
   │    └─ procresize     按 GOMAXPROCS 创建 P
   ├─ runtime.newproc     创建 runtime.main 对应的 G
   └─ runtime.mstart → schedule → runtime.main
        ├─ newm(sysmon)     启动后台监控线程
        ├─ gcenable()       开启 GC
        ├─ doInit(runtime)  运行时 init
        ├─ doInit(main)     所有包的 init（依赖优先）
        └─ main.main        返回后 exit(0)
```

1. **入口由链接器决定**：可执行文件的入口符号是平台相关的 `_rt0_amd64_linux`（Windows 上是 `_rt0_amd64_windows`），它只做少量寄存器设置就跳到 `runtime.rt0_go`，所以调试器里第一段「Go 代码」其实是运行时汇编。
2. **schedinit**：初始化栈与内存分配器、登记 m0、初始化模块数据、初始化 GC（只准备不开启），并按 `GOMAXPROCS` 创建 P 列表。
3. **创建 main goroutine**：`rt0_go` 末尾用 `newproc` 以 `runtime.main` 为函数创建 G，随后 `mstart` 进入 `schedule`，这个 G 被调度执行。
4. **init 顺序**：被依赖的包先初始化；同一包内包级变量先于 `init`，多个 `init` 按源文件名字典序执行；包级变量之间按依赖关系排序，所以 `var b = a + 1` 一定在 `a` 之后。
5. **退出**：`main.main` 返回后 `runtime.main` 调用 `exit(0)`，其他 goroutine 被强杀，它们的 defer 不会执行；`os.Exit` 同样跳过所有 defer。
6. **m0 与 g0**：`m0` 是主线程对应的 M，`g0` 是它的调度栈（不是用户 goroutine）；每个 M 都有一个 g0，负责执行调度、GC、morestack 等运行时逻辑。
7. **栈上限**：`runtime.main` 会把自己的栈上限设为 `maxstacksize`（64 位默认 1GB），同时创建 `forcegc` goroutine，保证 2 分钟无 GC 时也能强制触发。

| 初始化形式 | 执行时机 | 典型用途 |
| --- | --- | --- |
| 包级变量初始化 | 最早，按依赖排序 | 构造配置、注册表 |
| `func init()` | 变量之后，同包按文件名序 | 注册驱动、校验配置 |
| `main.main` | 所有 init 之后 | 业务入口 |
| `sync.Once` / 懒加载 | 首次使用时 | 避免启动变慢、规避 init 依赖不确定 |

```go
package main

import "fmt"

var a = initA() // 包级变量：先于 init 执行

func initA() int {
	fmt.Println("1. 变量 a 初始化")
	return 1
}

func init() {
	fmt.Println("2. init 函数执行")
}

func main() {
	fmt.Println("3. main.main 执行")
	defer fmt.Println("4. main 中的 defer 在 main 返回时执行")
}
```

```bash
GODEBUG=inittrace=1 ./app   # 观察各包 init 的耗时与分配
# init internal/bytealg @0.008 ms, 0 ms clock, 0 bytes, 0 allocs
# init main @0.021 ms, 0 ms clock, 16 bytes, 1 allocs

go tool nm app | grep -E "rt0_go|main\.main|runtime\.main"
go build -ldflags "-X main.buildTime=$(date -u +%Y-%m-%dT%H:%M:%SZ)" -o app .
```

**易错点：**

- `main` 返回时其他 goroutine 会被直接杀掉，需要优雅退出必须自己同步。
- 不要依赖跨文件的 init 顺序，同包内按文件名排序，重命名文件就可能改变行为。
- `init` 不能被显式调用或取地址；一个包可以有多个 `init`，按出现顺序执行。
- `init` 里启动的 goroutine 不保证在 `main` 之前跑完，只保证已创建。
- `import _ "pkg"` 的唯一作用是触发该包的变量初始化与 `init`（如注册驱动）。

## 10. 栈与栈扩容

**goroutine 栈是连续栈，Go 1.4 起取代了分段栈。每个 goroutine 初始只有 2KB，函数序言用 stack guard 检查剩余空间，不足时由 `morestack` 分配两倍大小的新栈，把旧栈整块拷过去并修正所有指向旧栈的指针；GC 时若栈使用不足 1/4 还会缩回一半。扩容是「拷贝 + 指针修正」而非链式追加，所以栈上对象地址会变化，这也是不能把栈指针长期交给 C 保存的根本原因。**

1. **分段栈 → 连续栈**：Go 1.3 及以前溢出时挂新栈段、返回时摘除，跨段调用与「热分裂」开销明显；Go 1.4 改为连续栈，扩容即整块拷贝，访问始终连续。
2. **初始大小与上限**：`runtime._StackMin = 2048` 字节；64 位平台默认上限 1GB，32 位约 250MB；可用 `debug.SetMaxStack` 调整。
3. **栈检查**：非叶子函数序言比较 `SP` 与 `g.stackguard0`，小于则跳到 `morestack`；guard 预留了 `StackGuard` 余量，保证扩容代码本身不再超栈。
4. **扩容过程（`newstack`）**：新栈大小为旧栈的 2 倍（超上限则 `fatal error: stack overflow`）；按帧拷贝旧栈，用编译器生成的 stack map 找出帧内指针并改为指向新栈对应位置，最后释放旧栈。
5. **栈收缩**：GC 扫描栈时若已用空间不足 1/4，缩到一半（不低于 2KB），同样是拷贝。
6. **栈上分配**：未逃逸对象直接放栈帧，随栈拷贝、随栈回收，这是栈分配零 GC 成本的来源。
7. **栈帧布局**：栈从高地址向低地址增长，每个帧含返回地址、调用者的 BP、局部变量与溢出参数区；扩容时按帧信息（frame size、args size、stack map）搬运，所以帧布局必须由编译器精确描述。
8. **为什么不能把栈指针交给 C**：cgo 调用期间 goroutine 可能被调度到别的 M，栈也可能扩容搬移；Go 因此规定 C 代码不得长期保存 Go 指针，`cgo.Handle` 就是为此提供的间接层。

| 对比项 | 分段栈（Go ≤ 1.3） | 连续栈（Go ≥ 1.4） |
| --- | --- | --- |
| 扩容方式 | 挂接新栈段，链表式 | 分配 2 倍新栈，整块拷贝 |
| 访问连续性 | 跨段不连续 | 始终连续 |
| 主要问题 | 热分裂、跨段调用开销 | 扩容拷贝成本 O(n) |

| 常见报错 | 触发原因 |
| --- | --- |
| `fatal error: stack overflow` | 无限递归或单帧过大，超过栈上限，`recover` 无效 |
| `fatal error: concurrent stack copy` | 运行时 bug 或 `unsafe` 破坏了栈信息 |
| `signal SIGSEGV` 于小地址 | 常见于 C 侧保存了已搬移的 Go 栈指针 |

```go
package main

import (
	"fmt"
	"runtime"
	"runtime/debug"
)

func depth(n int) int {
	if n == 0 {
		return 0
	}
	var buf [64]byte // 放大栈帧，加快触发扩容
	buf[0] = byte(n)
	return depth(n-1) + int(buf[0])
}

func main() {
	debug.SetMaxStack(64 << 20) // 把单 goroutine 上限降到 64MB，便于观察

	var before, after runtime.MemStats
	runtime.ReadMemStats(&before)
	fmt.Println("递归结果:", depth(200000)) // 经历 2KB→4KB→8KB… 多次扩容
	runtime.ReadMemStats(&after)

	fmt.Printf("StackInuse: %d KB -> %d KB\n", before.StackInuse>>10, after.StackInuse>>10)
	fmt.Println("默认初始栈 2KB，64 位平台默认上限 1GB")
}
```

```bash
# 在汇编里观察栈检查与扩容调用
go build -gcflags="-S" main.go | grep -B2 -A2 "morestack"
#   CMPQ SP, 16(R14)    ; 与 g.stackguard0 比较
#   JLS  morestack      ; 空间不足则扩容
#   CALL runtime.morestack_noctxt(SB)

# 统计函数中出现栈检查的次数（每个非叶子函数至少一次）
go build -gcflags="-S" main.go | grep -c "morestack"
# 每次扩容都翻倍，所以扩容次数是 O(log n)，代价集中在单次拷贝
# 观察各 goroutine 的栈占用与数量
go tool pprof -http=:8080 http://127.0.0.1:6060/debug/pprof/goroutine
# 查看当前 goroutine 的栈大小
go tool pprof -top http://127.0.0.1:6060/debug/pprof/goroutine
```

**易错点：**

- 栈地址不稳定，扩容与收缩都会搬移；不要把栈变量地址存进全局或交给 C 长期持有。
- 「初始 2KB」不等于「只占 2KB」，泄漏的 goroutine 会长期占住整块栈内存。
- `//go:nosplit` 的函数不做栈检查，只能用于运行时底层代码，业务代码不要用。
- 栈溢出是 fatal error 而非 panic，`recover` 无效；大数组局部变量会显著放大栈帧，深递归应改写为迭代。

## 11. 内存对齐

**CPU 以字为单位访问内存，一次读取要求地址落在自然边界：未对齐可能跨越缓存行、需要两次访存，某些架构上甚至直接 fault。Go 编译器保证每个字段偏移是其对齐值的整数倍，结构体对齐取字段最大对齐值，大小再向上取整到该对齐值的倍数——多出来的就是 padding。字段顺序因此直接影响结构体大小，按对齐值从大到小排列通常最省内存。**

1. **对齐规则**：字段偏移必须是该字段对齐值的倍数；结构体对齐 = 字段最大对齐；结构体大小必须是结构体对齐的倍数（尾部 padding）。
2. **为什么不能紧凑**：`int64` 落在偏移 1 时，每次读写跨两个 8 字节字，需要两次访存再拼接；ARM 等平台可能直接异常。
3. **字段重排**：大对齐字段放前面、小字段放后面可消除大量内部 padding，但只有热点结构体值得为此牺牲可读性。
4. **空结构体**：`struct{}` 大小为 0、对齐为 1；作字段本身不占空间，但落在结构体末尾时编译器会补 1 字节，避免 `&s.f` 指向分配块之外，随后再按对齐取整。
5. **伪共享**：两个高频写入的变量落在同一条 64 字节缓存行，会因缓存行在核间反复失效而变慢；用填充字段隔开到不同缓存行即可。

| 类型 | 大小（64 位） | 对齐值 |
| --- | --- | --- |
| `bool` / `int8` / `uint8` | 1 | 1 |
| `int16` / `uint16` | 2 | 2 |
| `int32` / `rune` / `float32` | 4 | 4 |
| `int64` / `float64` / 任意指针 | 8 | 8 |
| `string` | 16（指针 + 长度） | 8 |
| `slice` | 24（指针 + len + cap） | 8 |
| `interface` | 16（类型 + 数据） | 8 |
| `map` / `chan` / `func` | 8（指针） | 8 |
| `struct{}` | 0 | 1 |

```go
package main

import (
	"fmt"
	"unsafe"
)

type A struct { // 顺序不佳
	B bool  // 偏移 0
	I int64 // 偏移 8（1~7 是 padding）
	C bool  // 偏移 16
} // 大小 24（尾部补 7 字节）

type B struct { // 按对齐值重排
	I int64 // 偏移 0
	B bool  // 偏移 8
	C bool  // 偏移 9
} // 大小 16（尾部补 6 字节）

type WithEmpty struct {
	I int64
	E struct{} // 落在末尾：补 1 字节后再按 8 对齐
}

// 伪共享：两个计数器共享同一条缓存行
type Shared struct {
	A int64
	B int64
}

// 填充到 64 字节，让 A、B 分处不同缓存行
type Padded struct {
	A int64
	_ [56]byte
	B int64
}

func main() {
	var a A
	var b B
	fmt.Println(unsafe.Sizeof(a), unsafe.Alignof(a))         // 24 8
	fmt.Println(unsafe.Sizeof(b), unsafe.Alignof(b))         // 16 8
	fmt.Println(unsafe.Offsetof(a.I), unsafe.Offsetof(a.C))  // 8 16
	fmt.Println(unsafe.Sizeof(WithEmpty{}))                  // 16
	fmt.Println(unsafe.Sizeof(Shared{}), unsafe.Sizeof(Padded{})) // 16 72
}
```

```bash
# 官方分析器直接给出重排建议
go install golang.org/x/tools/go/analysis/passes/fieldalignment/cmd/fieldalignment@latest
fieldalignment ./...
# main.go:8:9: struct with 24 pointer bytes could be 16

go test -bench=Sharing -benchmem -run=^$ ./...   # 对比伪共享与填充后的 ns/op
```

**易错点：**

- `unsafe.Sizeof` 不含指针指向的堆数据，`string` 的 16 字节也不含字符内容。
- 结构体大小不等于字段大小之和，`bool + int64 + bool` 是 24 而不是 10。
- 字段重排会影响依赖布局的序列化、`unsafe` 偏移计算与 cgo 结构体映射。
- 伪共享的填充要与缓存行大小（常见 64 字节）对齐，随意填几个字节可能仍同行。

## 12. 零值与可比较性

**Go 的变量声明后一定处于确定的零值状态，不存在未初始化的野值。零值让很多类型开箱即用：nil slice 可直接 append，nil map 可读、可 range、可 delete；但 nil map 写入会 panic，nil channel 的收发会永久阻塞。可比较性由类型的静态结构决定——slice、map、function 不可比较；interface 的相等性看「动态类型 + 动态值」，动态类型不可比较时运行期 panic。**

1. **零值由类型决定**：数值 0、bool false、string 空串 `""`（不是 nil）、数组与结构体逐元素取零值、指针/切片/映射/通道/函数/接口为 nil。
2. **nil slice 与空 slice**：len 与 cap 都是 0，但前者底层数组指针为 nil，后者非 nil；二者都能 append、len、range，但 JSON 结果分别是 `null` 与 `[]`，`DeepEqual` 也判为不等。
3. **nil map**：读不存在的 key 返回零值，len 为 0，range 不迭代，delete 安全；赋值会 panic（`assignment to entry in nil map`）。
4. **nil channel**：收发永久阻塞，`select` 中对应 case 永不选中，`close(nil)` panic；这也是「动态禁用某个 select 分支」的技巧。
5. **可比较类型**：布尔、数值、字符串、指针、channel、interface、数组（元素可比较）、结构体（所有字段可比较）；slice、map、function 只能与 nil 比较。
6. **interface 比较**：先比动态类型（必须完全相同），再比动态值；两个 nil 接口相等；装着不可比较类型时比较会 panic（`comparing uncomparable type []int`）。Go 1.20 起普通接口也能满足 `comparable` 约束，但运行期仍可能 panic。

| 类型 | 零值 | 可比较 |
| --- | --- | --- |
| `bool` | `false` | 是 |
| 数值类型 | `0` | 是 |
| `string` | `""`（非 nil） | 是 |
| 数组 | 元素各自零值 | 元素可比较则可比较 |
| struct | 字段各自零值 | 所有字段可比较则可比较 |
| slice | `nil` | 否，只能与 nil 比较 |
| map | `nil` | 否，只能与 nil 比较 |
| channel | `nil` | 是（同一实例） |
| func | `nil` | 否，只能与 nil 比较 |
| 指针 | `nil` | 是（地址比较） |
| interface | `nil` | 是（可能 panic） |

```go
package main

import (
	"encoding/json"
	"fmt"
	"reflect"
)

type Item struct {
	Tags []string // 含不可比较字段 → Item 不可比较
}

func main() {
	var s1 []int         // nil slice
	s2 := []int{}        // 空 slice，底层数组非 nil
	fmt.Println(s1 == nil, s2 == nil)                        // true false
	fmt.Println(len(s1), cap(s1), reflect.DeepEqual(s1, s2)) // 0 0 false

	b1, _ := json.Marshal(s1)
	b2, _ := json.Marshal(s2)
	fmt.Println(string(b1), string(b2)) // null []

	var m map[string]int        // nil map
	fmt.Println(m["x"], len(m)) // 0 0，读取安全
	// m["x"] = 1               // panic: assignment to entry in nil map
	m = make(map[string]int)
	m["x"] = 1

	// 不可比较类型
	// fmt.Println(s1 == s2) // 编译错误：slice can only be compared to nil
	// _ = Item{} == Item{}  // 编译错误：struct containing []string cannot be compared

	// interface：动态类型不同即不相等
	var a, b any = 1, int64(1)
	fmt.Println(a == b) // false

	// 动态类型不可比较 → 运行期 panic
	var c, d any = []int{1}, []int{1}
	// fmt.Println(c == d) // panic: comparing uncomparable type []int
	_, _ = c, d // 占位，避免“声明未使用”

	seen := map[[2]int]bool{} // 数组可作 key
	seen[[2]int{1, 2}] = true
	fmt.Println(seen, equalAny(1, 1)) // map[[1 2]:true] true
}

func equalAny[T comparable](a, b T) bool { return a == b }
```

```bash
go run main.go   # 去掉注释后可见 panic: comparing uncomparable type []int
go vet ./...     # 提前发现可疑比较（自比较、恒真比较）
go build ./...   # 让 Item 作 map key 会编译失败：invalid map key type
```

**易错点：**

- nil slice 与空 slice 业务上常等价，但 JSON（`null` vs `[]`）与 `DeepEqual` 结果不同，对外接口要统一。
- nil map 可以读、range、delete，唯独不能写；「nil map 什么都不能做」是错的。
- interface 比较要求动态类型完全一致，`int(1)` 与 `int64(1)` 装进接口后不相等。
- 浮点 `NaN != NaN` 恒成立，用 NaN 作 map key 会「取不出来」；数组比较是逐元素值比较，代价 O(n)。

## 13. 深拷贝与浅拷贝

**Go 的赋值与传参永远是值复制，但复制的深度取决于类型：数组、结构体逐字段复制；slice 只复制 header（指针 + len + cap），map 只复制一个指针。所谓浅拷贝，就是复制了 header 却仍共享底层数据；深拷贝则递归复制所有间接引用的数据。理解这一点，既能解释「改了副本原对象也变了」，也能解释「截取一小段字符串却拖住一整块内存」。**

1. **赋值与传参**：复制的是值的全部内容；对 slice/map/channel/指针来说，这个内容只是描述符，指向的数据没有复制。
2. **slice 浅拷贝**：`s2 := s1` 共享底层数组，改元素互相可见；append 未超 cap 也写同一数组，超过 cap 才新建数组——但元素若是指针，新数组里仍是同一批指针。
3. **map 浅拷贝**：`m2 := m1` 复制同一个 hmap 指针，增删改与 len 完全同步，独立副本必须手动遍历复制。
4. **结构体含引用字段**：`u2 := u1` 会复制 string header（共享字符数据，但 string 不可变所以安全），而 slice、map 字段仍共享。
5. **深拷贝手段**：手写 Clone 最可靠；JSON/gob 往返省事但丢未导出字段、把接口退化成 `map[string]any` 且慢；`deepcopy`、`copystructure` 用反射递归复制，要处理循环引用。`copy` 只按元素赋值，元素含指针仍是浅拷贝。

| 操作 | 是否深拷贝 | 说明 |
| --- | --- | --- |
| `b := a`（数组 / 无引用字段的 struct） | 是 | 完全独立 |
| `b := a`（slice） | 否 | 共享底层数组，只复制 24 字节 header |
| `b := a`（map） | 否 | 同一个 hmap，互相可见 |
| `copy(dst, src)` | 元素级 | 元素含指针时仍是浅拷贝 |
| JSON / gob 往返 | 是 | 丢未导出字段与类型信息，性能差 |
| 手写 `Clone` / deepcopy | 是 | 最可控，需处理循环引用 |

```go
package main

import (
	"fmt"
	"strings"
)

type User struct {
	Name string
	Tags []string
	Meta map[string]string
}

func shallow(u User) User { return u } // 只复制结构体，Tags/Meta 仍共享

func deep(u User) User {
	c := User{Name: u.Name}
	c.Tags = append([]string(nil), u.Tags...) // 新的底层数组
	c.Meta = make(map[string]string, len(u.Meta))
	for k, v := range u.Meta {
		c.Meta[k] = v
	}
	return c
}

func main() {
	orig := User{Name: "a", Tags: []string{"x"}, Meta: map[string]string{"k": "v"}}

	s := shallow(orig)
	s.Tags[0] = "changed"
	fmt.Println(orig.Tags[0]) // changed：共享底层数组

	d := deep(orig)
	d.Tags[0] = "deep"
	d.Meta["k"] = "deep"
	fmt.Println(orig.Tags[0], orig.Meta["k"]) // changed v：深拷贝互不影响

	// 切片截取：小切片拖住大内存
	big := strings.Repeat("x", 1<<20) // 1MB
	small := big[:10]                 // 仍引用 1MB 底层数组
	cloned := strings.Clone(small)    // Go 1.18+：独立副本
	fmt.Println(len(big), len(small), len(cloned)) // 1048576 10 10

	// copy 不是深拷贝
	src := [][]int{{1, 2}}
	dst := make([][]int, len(src))
	copy(dst, src)
	dst[0][0] = 99
	fmt.Println(src[0][0]) // 99：内层切片仍共享
}
```

**易错点：**

- `copy(dst, src)` 只复制元素，元素是指针、slice、map 时依旧共享，不算深拷贝。
- JSON 往返会丢未导出字段、`time.Time` 的单调时钟信息与具体类型（接口变成 map）。
- 深拷贝有环对象图会无限递归，手写 Clone 必须记录已访问节点。
- 用 `big[:n]` 取子串后长期持有会阻止整个底层数组回收，是典型的内存泄漏；浅拷贝在并发下同样共享数据。

## 14. 值传递与引用传递

**Go 只有值传递：调用时实参被复制给形参，函数内操作的是副本。所谓「slice、map、channel 是引用传递」是误称——它们本身就是值，只是这个值内部含有指向底层数据的指针（slice header、hmap 指针、hchan 指针），复制后仍指向同一份数据，看起来像传了引用。指针参数同样是值传递，复制的是地址本身。**

1. **值传递的定义**：形参是实参的副本，函数内重新赋值不影响调用方；能否改到调用方的数据，取决于副本里是否含指针。
2. **slice 为什么像引用**：slice 是 24 字节 header（数据指针 + len + cap）。按值传递复制 header，`s[0] = x` 改共享数组，调用方可见；但 `s = append(...)` 只改本地 header，调用方 len 不变。
3. **map 与 channel**：传递的是指针（8 字节），副本与原值指向同一个 hmap/hchan，增删改、收发、关闭互相可见；但 `m = make(...)` 只影响本地变量。
4. **指针参数**：复制的是地址，`*p = x` 能改调用方对象，`p = &other` 不影响调用方。
5. **数组与结构体**：按值传递整体复制，大结构体（如 8KB 数组）复制成本高，还可能因参数逃逸分配到堆。
6. **接收者选择**：需要修改、结构体较大、需要 nil 语义时用指针接收者；小类型、只读、天然 header 类型用值接收者；同一类型的方法要保持一致，否则方法集分裂。
7. **接口参数也是值**：接口占 16 字节（类型 + 数据），传参复制这两个字段，底层数据仍共享，所以通过接口方法修改对象能被调用方看到。

| 传参形式 | 复制的内容 | 能改调用方变量本身 | 能改其指向/底层数据 |
| --- | --- | --- | --- |
| `func f(v T)`（数组/struct） | T 的完整值 | 否 | 仅当 T 含指针字段 |
| `func f(s []T)` | slice header（24B） | 否（len/cap 不变） | 可以（元素共享） |
| `func f(m map[K]V)` | 指针（8B） | 否 | 可以（增删改） |
| `func f(ch chan T)` | 指针（8B） | 否 | 可以（收发、关闭） |
| `func f(p *T)` | 地址（8B） | 可以（`*p = ...`） | 可以 |
| `func f(fn func())` | 函数指针（8B） | 否 | 可以（调用它） |
| `func f(i any)` | 类型 + 数据（16B） | 否 | 底层数据共享 |

```go
package main

import "fmt"

type Big struct {
	Data [1 << 10]int64 // 8KB，按值传递会整体复制
}

func byValue(b Big)    { b.Data[0] = 1 } // 只改副本
func byPointer(b *Big) { b.Data[0] = 2 } // 改原对象

func modifySlice(s []int) {
	s[0] = 100         // 可见：共享底层数组
	s = append(s, 200) // 不可见：只改了本地 header
}

func main() {
	b := Big{}
	byValue(b)
	fmt.Println(b.Data[0]) // 0
	byPointer(&b)
	fmt.Println(b.Data[0]) // 2

	arr := make([]int, 1, 2)
	modifySlice(arr)
	fmt.Println(arr[0], len(arr)) // 100 1

	// 数组是纯值类型：赋值即整体复制
	a1 := [3]int{1, 2, 3}
	a2 := a1
	a2[0] = 9
	fmt.Println(a1[0], a2[0]) // 1 9

	// range 复制元素，修改 v 不影响原切片
	for _, v := range a1 {
		v = 0
	}
	fmt.Println(a1) // [1 2 3]
}
```

```bash
# 对比大结构体按值/按指针传递的分配与耗时
go test -bench='Value|Pointer' -benchmem -run=^$ ./...
# 看是否因取地址而逃逸到堆
go build -gcflags="-m" main.go 2>&1 | grep -E "escapes to heap|does not escape"
```

**易错点：**

- 「Go 有引用传递」是错误说法，Go 规范没有引用类型概念；只有值传递，只是某些值内部含指针。
- 值接收者方法无法修改原对象，且每次调用都复制整个接收者；指针接收者方法只属于 `*T`，接口要求时只有 `*T` 能满足。
- 传指针不一定更快：被取地址的值可能因此逃逸到堆，反而增加 GC 压力。
- `for _, v := range s` 修改 v 不影响元素，要改必须用下标 `s[i]`。
