## 1. 主题切换与暗色模式（避免首屏闪烁）

**结论先行：** 首屏闪烁的本质是**「主题状态在 JS 执行时才确定，而浏览器已经用默认配色画了第一帧」**。要根治，必须让主题在**首次绘制之前**就落到 DOM 上：在 `<head>` 里放一段同步内联脚本，读 `localStorage` / `prefers-color-scheme` 并给 `<html>` 打上 `data-theme`。放在 React/Vue 挂载后设置，必然晚一帧。

**方案对比：**

| 方案 | 原理 | 首屏闪烁 | 优点 | 缺点 |
| --- | --- | --- | --- | --- |
| 纯 `prefers-color-scheme` | CSS 媒体查询 | 无 | 零 JS、跟随系统 | 无法手动切换 |
| CSS 变量 + `data-theme` | 属性选择器切换变量 | 取决于脚本时机 | 灵活、可扩展多主题 | 需要处理首屏脚本 |
| Tailwind `dark:` class | 根节点加 `dark` 类 | 同上 | 与原子类配合好 | 颜色散落在 class 中，语义弱 |
| CSS-in-JS ThemeProvider | JS 注入变量 | 通常有闪烁 | 与组件体系贴合 | 首屏依赖 JS，SSR 需注水一致 |
| 浏览器强制暗色 | `forced-colors` / 扩展 | 不可控 | 无需开发 | 效果不可预期 |

**三态设计：`light` / `dark` / `system`**

用户选的「跟随系统」必须单独存，不能简单存成当前的 `light` 或 `dark`，否则系统切换时页面不跟随：

```ts
type ThemeMode = 'light' | 'dark' | 'system';

function resolveTheme(mode: ThemeMode): 'light' | 'dark' {
  if (mode !== 'system') return mode;
  return matchMedia('(prefers-color-scheme: dark)').matches ? 'dark' : 'light';
}

// 监听系统变化，只在 mode === 'system' 时生效
matchMedia('(prefers-color-scheme: dark)').addEventListener('change', () => {
  if (getMode() === 'system') applyTheme(resolveTheme('system'));
});
```

**首屏脚本：必须同步、必须尽早**

```html
<!DOCTYPE html>
<html lang="zh-CN">
  <head>
    <meta name="color-scheme" content="light dark" />
    <script>
      (function () {
        try {
          var mode = localStorage.getItem('theme') || 'system';
          var dark = mode === 'dark' ||
            (mode === 'system' && matchMedia('(prefers-color-scheme: dark)').matches);
          document.documentElement.dataset.theme = dark ? 'dark' : 'light';
          document.documentElement.style.colorScheme = dark ? 'dark' : 'light';
        } catch (e) {
          document.documentElement.dataset.theme = 'light';
        }
      })();
    </script>
    <!-- 样式表放在脚本之后也可以，关键是脚本先于 body 渲染 -->
  </head>
  <body>
    <div id="app"></div>
  </body>
</html>
```

三个要点：

- **不要等 DOMContentLoaded**，脚本要在 `<head>` 中同步执行，否则浏览器可能已经画了白底。
- **加 `try/catch`**：隐私模式下 `localStorage` 可能直接抛异常，不能让主题脚本把整个页面搞崩。
- **同时设置 `color-scheme`**：它决定滚动条、表单控件、默认背景色，只设 `data-theme` 会出现「页面是暗的、滚动条还是白的」。

**SSR 场景：主题要从 Cookie 带到服务端**

服务端渲染时，内联脚本仍会在客户端执行，但**首屏 HTML 已经由服务端输出**，如果服务端不知道主题，就会先输出浅色再被脚本改掉。做法是把主题存 Cookie（不只是 localStorage），服务端读取后直接渲染 `<html data-theme="dark">`，客户端注水时读取同一个值，避免 hydration mismatch。

**颜色体系：用语义变量，不要直接用色值**

```css
:root,
[data-theme='light'] {
  --color-bg-page: #ffffff;
  --color-bg-elevated: #ffffff;
  --color-text-primary: #1f2329;
  --color-text-secondary: #646a73;
  --color-border: #dee0e3;
  --color-brand: #3370ff;
}

[data-theme='dark'] {
  --color-bg-page: #17181a;
  --color-bg-elevated: #232427;
  --color-text-primary: #e8e9eb;
  --color-text-secondary: #a6a8ad;
  --color-border: #35373b;
  --color-brand: #4e83fd;   /* 暗色下品牌色通常要提亮一档 */
}

body {
  background: var(--color-bg-page);
  color: var(--color-text-primary);
}
```

业务代码只用 `--color-text-primary` 这类**语义变量**，不要在组件里写 `#fff` 或 `bg-white`。否则新增一套主题时要把所有组件翻一遍。暗色不是简单反色：品牌色、阴影、图片遮罩、图表配色都要单独调，且正文对比度要满足 WCAG AA（4.5:1）。

**切换动画：别给全局加 transition**

```ts
function applyTheme(next: 'light' | 'dark') {
  const root = document.documentElement;
  // 只在切换的瞬间开启过渡，避免影响日常交互
  root.classList.add('theme-transition');
  root.dataset.theme = next;
  setTimeout(() => root.classList.remove('theme-transition'), 300);
}
```

```css
.theme-transition,
.theme-transition * {
  transition: background-color 0.25s ease, color 0.25s ease, border-color 0.25s ease !important;
}
```

如果直接给 `*` 常态加 `transition`，列表滚动、hover、弹窗都会变慢，还会在低端机上掉帧。更现代的做法是用 View Transition API 做圆形扩散切换，但要检测支持度并保留降级。

**第三方内容也要同步：**

- `iframe` 内的页面收不到父页面的 CSS 变量，需要通过 `postMessage` 通知主题。
- Canvas/图表（ECharts）要在主题变化时 `dispose` 重建或调用 `setOption` 更新配色。
- 富文本编辑器、代码高亮、地图瓦片（暗色地图）都要单独适配。
- 图片在暗色下过亮时，可用 `filter: brightness(0.85)` 做轻度压制，但不要用在需要准确色彩的商品图上。

**边界情况与坑：**

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 刷新时白屏闪一下 | 主题在 React 挂载后才设置 | `<head>` 内联脚本 |
| 滚动条仍是白色 | 只设了 `data-theme`，没设 `color-scheme` | 同时设置 `style.colorScheme` |
| 切换「跟随系统」后不跟随 | 把 system 解析成了具体值存储 | 存 mode 而不是 resolved theme |
| 系统主题变化时页面不变 | 没有监听 `matchMedia change` | 加监听，仅在 system 模式下应用 |
| SSR 注水报错 | 服务端与客户端主题不一致 | 主题放 Cookie，两端读同一来源 |
| 切换时整页卡顿 | 全局 `* { transition }` | 只在切换瞬间加过渡类 |
| 弹窗/下拉没变色 | 挂载到 body 的 portal 没继承变量 | 变量定义在 `:root`，portal 自然继承；若用了独立文档需单独注入 |
| 暗色下图片刺眼 | 图片没有暗色适配 | 加遮罩或提供暗色素材，商品图不要滤镜 |

**面试怎么答：** 先给结论「闪烁只能靠首屏前执行的内联脚本解决」，再讲三态模型（light/dark/system）与 `matchMedia` 监听，然后讲变量分层（基础色 → 语义色 → 组件只消费语义色），最后补 `color-scheme`、SSR Cookie、第三方内容同步和切换动画这几个细节。

**易错点：**

- 说「在 `useEffect` 里设置 `document.body.className`」，这一定会闪。
- 把「跟随系统」存成当前解析值，系统切换后失效。
- 只改背景和文字色，忘了滚动条、表单控件、图表、iframe。
- 用 `filter: invert(1)` 做暗色，图片和品牌色全毁。

## 2. 国际化 i18n 方案与文案管理

**结论先行：** i18n 的难点不在「查表替换」，而在三件事：**文案的组织与协作**（谁维护、怎么校验）、**语言相关的格式**（复数、日期、货币、数字）、**运行时加载**（语言包怎么拆、切换要不要刷新）。方案上，React 选 `react-i18next`、Vue 选 `vue-i18n` 最稳，格式化统一交给原生 `Intl`。

**方案对比：**

| 方案 | 框架 | 优点 | 缺点 | 适用 |
| --- | --- | --- | --- | --- |
| `react-i18next` | React | 生态成熟、命名空间懒加载、`Trans` 支持富文本 | 配置项多 | 中大型 React 项目 |
| `vue-i18n` | Vue | 与模板集成好、支持复数与日期 | 大语言包要手动拆分 | Vue 项目 |
| `FormatJS`（react-intl） | React | ICU 语法标准、格式化强 | 文案写法偏重、编译步骤 | 强 i18n 规范团队 |
| 自研 `t()` | 任意 | 体积极小、完全可控 | 复数/RTL/插值都要自己实现 | 文案少、语言固定 |

**文案 key 的设计：**

```
模块.页面.元素        例：order.list.exportButton、user.profile.saveSuccess
```

三条规则：

- **按语义命名，不按文案内容命名**：`common.confirm` 而不是 `common.确定`，否则改文案就要改 key。
- **key 不能带业务变量**：`order.status.${status}` 这种动态拼接会让静态扫描失效，应显式列出 `order.status.paid`。
- **一个 key 一个含义**：同一个「确定」在不同语境下可能需要不同翻译（例如按钮 vs 标题），不要为了复用强行合并。

**语言包组织与懒加载：**

```
locales/
  zh-CN/
    common.json
    order.json
    user.json
  en-US/
    common.json
    order.json
    user.json
```

按**页面/领域拆命名空间**，路由切换时只加载当前页面需要的包：

```ts
i18n.use(initReactI18next).init({
  lng: detectLanguage(),          // 优先级：用户设置 > 浏览器 > 默认
  fallbackLng: 'zh-CN',
  ns: ['common'],
  defaultNS: 'common',
  resources: { 'zh-CN': { common: zhCommon } },
  interpolation: { escapeValue: false },  // React 已做 XSS 转义
});

// 进入订单页时再加载
await i18n.loadNamespaces(['order']);
```

首屏只加载 `common`，能把语言包体积从几百 KB 降到几十 KB。缺点是切页时有一次加载等待，用骨架或 Suspense 兜住即可。

**格式化统一用 `Intl`，不要手写模板：**

```ts
const amount = new Intl.NumberFormat(locale, {
  style: 'currency',
  currency: 'CNY',
}).format(1234.5);                       // ￥1,234.50

const date = new Intl.DateTimeFormat(locale, {
  year: 'numeric', month: '2-digit', day: '2-digit',
  timeZone: 'Asia/Shanghai',
}).format(new Date());

const plural = new Intl.PluralRules(locale).select(3);  // other
```

复数是最容易出错的地方：中文没有复数变化，英文有 `one/other`，俄语有 `one/few/many/other`。不要写 `count > 1 ? 'items' : 'item'`，直接用 i18next 的复数能力（底层也是 `Intl.PluralRules`）：

```json
{
  "cart.items": "{{count}} 件商品",
  "cart.items_plural": "{{count}} 件商品"
}
```

**插值与富文本：**

```json
{
  "welcome": "欢迎，{{name}}",
  "agreement": "我已阅读并同意<1>《用户协议》</1>"
}
```

```tsx
<Trans i18nKey="agreement" components={{ 1: <a href="/terms" /> }} />
```

**不要用字符串拼接**（`t('hello') + name + t('suffix')`）：不同语言的语序不同，拼接必然出问题。链接、加粗这类富文本也不能把 HTML 直接塞进 JSON 再 `dangerouslySetInnerHTML`，要用 `Trans` 的组件插槽。

**切换语言的两种模式：**

| 模式 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 不刷新 | 切换 `i18n.language`，依赖响应式重渲染 | 体验顺滑 | 需要所有文案都走 `t()`；已缓存的接口数据不会翻译 |
| 刷新页面 | 把语言写入 URL/Cookie 后 `location.reload()` | 状态干净、SEO 友好 | 有白屏；未保存的表单会丢 |

工程上常见做法：**界面文案不刷新，接口返回的多语言字段随请求头 `Accept-Language` 重新拉取**。如果当前页有未保存表单，切换语言前要提示。

**文案管理与协作：**

- 语言包放仓库，走 Code Review；翻译平台的导出结果用脚本回写，避免人工复制。
- CI 加一条校验：**各语言 key 集合必须一致**，缺 key 直接失败；同时扫描代码里 `t('...')` 的静态字面量，发现未定义 key 报警。
- 开发期用「伪翻译」（把中文替换成带重音的变体）检查是否有硬编码文案遗漏。
- 文案长度要有约束：德语、俄语通常比中文长 30% 到 50%，按钮和表格列宽要按最长语言设计。

**RTL（阿拉伯语、希伯来语）：**

```css
[dir='rtl'] .card { margin-inline-start: 16px; }   /* 用逻辑属性代替 left/right */
```

用 `margin-inline-start`、`padding-inline-end`、`inset-inline-start` 代替物理方向属性；图标（箭头、返回）要能镜像翻转；数字和代码保持 LTR。`<html dir="rtl" lang="ar">` 要在切换语言时同步更新。

**边界情况与坑：**

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 切换语言后部分文案没变 | 组件里硬编码中文，或用了非响应式变量 | 统一 `t()`，避免模块顶层缓存翻译结果 |
| 缺失 key 直接显示 key 名 | 没有 fallback | 配 `fallbackLng` + 开发环境显式告警 |
| 日期差一天 | 时区不同 | `Intl.DateTimeFormat` 显式指定 `timeZone` |
| 金额小数位不对 | 手写 `toFixed(2)` | 用 `Intl.NumberFormat`，不同币种小数位不同 |
| 语言包越来越大 | 全量打包 | 按命名空间懒加载、按路由拆包 |
| 复数翻译错误 | 手写 `count > 1` | 用 `Intl.PluralRules` / i18next 复数后缀 |
| 切换后页面布局错乱 | 文案变长 | 弹性布局、避免固定宽度、按最长语言验收 |
| SEO 抓不到多语言 | 纯前端切换 | 每种语言独立 URL + `hreflang` 标注 |

**面试怎么答：** 先讲 key 规范与按命名空间懒加载，再讲三类格式化（数字/日期/复数）必须用 `Intl`，接着讲插值与富文本要用 `Trans` 而不是拼接/`innerHTML`，最后补文案协作（CI 校验 key 一致）、语言切换模式（不刷新 + 接口重拉）、RTL 与 SEO。

**易错点：**

- 用「中文文案」当 key，改文案就得改代码。
- 字符串拼接组装句子，语序一变就错。
- 手动判断复数、手动 `toFixed`、手动拼日期。
- 只翻译界面，忘了接口返回的数据、错误码、邮件模板也要多语言。

## 3. 多页签与路由缓存（keep-alive 式需求在 React/Vue 中怎么做）

**结论先行：** 多页签需求拆开是四件事：**页签列表管理**（打开/关闭/切换/右键菜单）、**组件实例缓存**（切走不销毁）、**滚动与表单状态恢复**、**刷新后恢复页签**。Vue 有 `keep-alive`，是原生解法；React 没有，只能在「状态外置」「隐藏而不销毁」「第三方库」三条路里选，且每条都有代价。

**需求拆解：**

| 能力 | 说明 | 难点 |
| --- | --- | --- |
| 打开页签 | 路由跳转时新增/激活页签 | 同一路由不同参数是否算两个页签 |
| 切换 | 点击页签恢复页面 | 组件实例与滚动位置都要恢复 |
| 关闭 | 关闭当前/其他/左侧/右侧 | 关闭时要清理缓存，避免内存泄漏 |
| 刷新 | 重载当前页签 | 要同时清理该页的缓存 |
| 持久化 | 浏览器刷新后页签仍在 | 存 path、title、query，不存组件状态 |
| 固定页签 | 首页/工作台不可关闭 | 与权限、默认路由联动 |

**Vue：`keep-alive` + `include` + 动态 key**

```vue
<template>
  <router-view v-slot="{ Component, route }">
    <keep-alive :include="cachedNames" :max="20">
      <component :is="Component" :key="route.fullPath" />
    </keep-alive>
  </router-view>
</template>
```

```ts
// 页签 store：name 必须是组件内 defineOptions({ name: 'OrderList' }) 的名字
const cachedNames = computed(() =>
  tabs.value.filter((t) => t.keepAlive).map((t) => t.name)
);

function addTab(route: RouteLocationNormalized) {
  if (tabs.value.some((t) => t.fullPath === route.fullPath)) return;
  tabs.value.push({
    fullPath: route.fullPath,
    name: route.name as string,
    title: route.meta.title as string,
    keepAlive: route.meta.keepAlive !== false,
  });
}

function closeTab(fullPath: string) {
  tabs.value = tabs.value.filter((t) => t.fullPath !== fullPath);
  // 从 include 移除后，Vue 会销毁对应实例并触发 deactivated → unmounted
}
```

三个关键点：

- `include` 匹配的是**组件 name**，不是路由 name。用 `<script setup>` 时必须显式 `defineOptions({ name: 'OrderList' })`，否则缓存永远不生效。
- `:key` 用 `fullPath` 时，同一路由不同参数会各缓存一份；用 `path` 则共用一份实例（切换参数时不会重新 `created`）。**这是业务语义选择，不是性能选项**。
- 关闭页签要从 `include` 里移除，实例才会真正销毁；只从页签数组删除，组件仍活在缓存里。

**React：没有 keep-alive，三条路**

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 状态外置 | 表单/列表状态放 store 或 URL，组件正常卸载 | 无额外运行时、内存干净 | 改造成本高；滚动位置、第三方组件内部状态难恢复 |
| 隐藏不销毁 | 所有打开过的页面都渲染，用 `display: none` 切换 | 行为最接近 keep-alive | DOM 数量增长、副作用不停止、内存上涨 |
| 第三方库 | `react-activation` / `keepalive-for-react` | 接入快、API 接近 Vue | 依赖 React 内部实现，升级有风险 |

**「隐藏不销毁」的最小实现：**

```tsx
function KeepAliveOutlet({ tabs, activeKey }: Props) {
  return (
    <>
      {tabs.map((tab) => (
        <div
          key={tab.key}
          style={{ display: tab.key === activeKey ? 'block' : 'none' }}
          // 隐藏容器不参与布局，但组件仍在运行
        >
          <RouteView route={tab.route} />
        </div>
      ))}
    </>
  );
}
```

这条路必须额外处理：

- **副作用不会暂停**：页面里的 `setInterval`、WebSocket 订阅、`IntersectionObserver` 在隐藏后仍在跑，要在 `useEffect` 里监听可见性并暂停。
- **DOM 膨胀**：打开 30 个页签就是 30 棵 DOM 树，低端机会明显变卡，要给页签数量设上限（如 15 个）并提示。
- **弹窗/Portal**：`display: none` 的容器里的 `position: fixed` 弹窗会跟随隐藏，需要把弹窗挂到 body 并手动控制显隐。

**滚动位置恢复：**

```ts
// 缓存每个页签的滚动容器位置
const scrollMap = new Map<string, number>();

function saveScroll(key: string) {
  const el = document.querySelector('[data-scroll-root]');
  if (el) scrollMap.set(key, el.scrollTop);
}

function restoreScroll(key: string) {
  requestAnimationFrame(() => {
    const el = document.querySelector('[data-scroll-root]');
    if (el) el.scrollTop = scrollMap.get(key) ?? 0;
  });
}
```

Vue 的 `keep-alive` 只缓存组件实例，**不缓存滚动位置**（除非滚动容器本身在组件内且没被销毁）。React 隐藏方案天然保留 DOM，滚动位置自动保留。

**页签持久化：**

```ts
// 只持久化「页签描述」，不持久化组件状态
localStorage.setItem('tabs', JSON.stringify(tabs.map(({ fullPath, name, title }) => ({
  fullPath, name, title,
}))));
```

刷新后恢复页签，再按当前路由激活对应项。不要试图序列化组件状态：函数、DOM 引用、第三方实例都无法序列化，硬做只会得到一堆脏数据。

**边界情况与坑：**

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 页签切换后表单被清空 | 组件被销毁 | Vue 用 `keep-alive`，React 用隐藏或状态外置 |
| `keep-alive` 不生效 | `include` 与组件 name 不匹配 | `<script setup>` 显式声明 name |
| 同一路由不同参数互相覆盖 | `key` 用了 `path` | 需要独立状态时用 `fullPath` |
| 关闭页签后内存没降 | 只删了页签数组 | 同步从 `include` 移除，或卸载隐藏容器 |
| 关掉当前页签后空白 | 没计算「关闭后激活哪个」 | 优先右侧，其次左侧，最后回首页 |
| 刷新当前页签后仍是旧数据 | 缓存实例还在 | 先移出 `include`，`nextTick` 后再加回 |
| 页签越开越多 | 没有上限与去重 | 按 `fullPath` 去重，设最大数量 |
| 隐藏页面的定时器还在跑 | `display: none` 不停止 JS | 监听可见性暂停副作用 |
| 右键菜单关闭「其他」后路由错乱 | 把当前页也关了 | 先判断当前页是否在关闭集合内 |

**面试怎么答：** 先把需求拆成「页签管理 / 实例缓存 / 状态恢复 / 持久化」四块，再讲 Vue 的 `keep-alive + include + key` 三件套（重点说 include 匹配组件 name、key 用 path 还是 fullPath 的语义差异），然后讲 React 的三条路与各自代价，最后补滚动恢复、关闭清理、页签上限这些工程细节。

**易错点：**

- 认为 Vue 的 `keep-alive` 会自动缓存滚动位置。
- React 里用「隐藏不销毁」却不处理定时器、订阅和 DOM 膨胀。
- 关闭页签只删数组，不清理缓存。
- 把组件状态序列化进 localStorage 做恢复。

## 4. 低代码/配置化渲染的实现思路

**结论先行：** 低代码平台的内核是**「协议 + 渲染器 + 物料 + 配置器」**四件套：JSON Schema 描述页面，递归渲染器把 Schema 变成组件树，物料库提供可配置组件，配置器负责可视化编辑。真正的难点不是渲染，而是**协议设计、联动表达式、版本兼容与适用边界**。

**三类低代码，别混为一谈：**

| 类型 | 典型产品 | 核心 | 适用 | 不适合 |
| --- | --- | --- | --- | --- |
| 表单/表格驱动 | 动态表单、审批流 | Schema → 表单控件 | 后台 CRUD、审批 | 强交互页面 |
| 页面搭建 | 活动页、落地页、大屏 | 拖拽 + 物料 + 自由布局 | 营销页、可视化大屏 | 复杂业务逻辑 |
| 逻辑编排 | 流程引擎、规则引擎 | 节点图 + 执行器 | 审批流、自动化 | 实时交互 |

**Schema 协议设计（示意）：**

```json
{
  "version": "1.0",
  "type": "Page",
  "children": [
    {
      "id": "form1",
      "type": "Form",
      "props": { "layout": "vertical" },
      "children": [
        {
          "id": "name",
          "type": "Input",
          "props": { "label": "姓名", "placeholder": "请输入" },
          "rules": [{ "required": true, "message": "姓名必填" }]
        },
        {
          "id": "city",
          "type": "Select",
          "props": {
            "label": "城市",
            "options": { "source": "dict", "key": "city" }
          },
          "visibleOn": "{{ form.country === 'CN' }}"
        }
      ]
    }
  ]
}
```

协议要提前定好四类字段：**结构**（type/children）、**属性**（props）、**行为**（events）、**约束**（rules/visibleOn/disabledOn）。不要一开始就设计得无比灵活，字段越多，渲染器和配置器的组合复杂度是指数级上升的。

**递归渲染器：**

```tsx
const registry: Record<string, React.ComponentType<any>> = {
  Page, Form, Input, Select, Button,
};

function renderNode(node: SchemaNode, ctx: RenderContext): React.ReactNode {
  const Comp = registry[node.type];
  if (!Comp) return <Unknown type={node.type} />;

  // 条件渲染：表达式在沙箱里求值
  if (node.visibleOn && !evaluate(node.visibleOn, ctx)) return null;

  const props = resolveProps(node.props ?? {}, ctx);   // 解析数据源、表达式
  const children = node.children?.map((c) => (
    <Fragment key={c.id}>{renderNode(c, ctx)}</Fragment>
  ));

  return (
    <Comp key={node.id} {...props} node={node} ctx={ctx}>
      {children ?? node.text}
    </Comp>
  );
}
```

要点：

- **组件必须来自白名单 registry**，不能根据 Schema 里的字符串动态 `import()` 任意模块，否则等于远程代码执行。
- `id` 用于稳定 `key`、定位与联动，必须唯一且持久。
- 渲染器不承担业务逻辑，只做「解析 + 组装」，业务逻辑通过事件/数据源外挂。

**联动与表达式：安全沙箱是红线**

常见做法是把表达式编译成函数：

```ts
function compile(expr: string) {
  // 只允许读取作用域内的变量，禁用全局对象
  const fn = new Function('scope', `with (scope) { return (${expr}); }`);
  return (scope: Record<string, unknown>) => fn(scope);
}
```

`with` + `new Function` 能实现「`form.country === 'CN'`」这类写法，但它**不是安全沙箱**：用户仍可能通过 `constructor` 链拿到全局对象。生产环境应使用：

- AST 白名单解析（只允许变量、比较、逻辑、三元、算术、少量函数），自己解释执行。
- 或 `expr-eval` / `jsep` 这类解析器 + 白名单函数。
- 表达式来源若完全可信（只由开发者在仓库里写），风险可接受；如果支持运营在后台编辑，必须做沙箱。

**联动实现：依赖收集 + 最小重渲染**

```ts
// 字段变化 → 只重算依赖该字段的 visible/disabled/options
const deps = new Map<string, Set<string>>();  // field -> 依赖它的节点 id

function onFieldChange(field: string, value: unknown) {
  ctx.form[field] = value;
  for (const nodeId of deps.get(field) ?? []) {
    recomputeNode(nodeId);
  }
}
```

不要在任何一个字段变化时重渲染整棵 Schema，字段一多就会卡。把每个节点的可见性、禁用、选项做成独立订阅，或者把节点拆成 `React.memo` 的单元。

**数据源与事件：**

- 数据源统一抽象成 `{ source: 'api' | 'dict' | 'context', ... }`，渲染器只负责调用，不关心具体实现。
- 事件（`onClick`、`onChange`）在 Schema 里描述为「动作链」：`setField`、`request`、`navigate`、`toast`，由执行器按顺序执行。
- 出码（生成源码）适合「需要二次开发」的场景，但要接受「生成的代码不可再回编」的单向性。

**性能与规模：**

| 问题 | 处理 |
| --- | --- |
| Schema 层级深、节点多 | 扁平化 + 虚拟化；只渲染可视区 |
| 每个字段变化都全量重算 | 依赖收集 + memo + 局部状态 |
| 配置器与渲染器双份逻辑 | 共用同一份 registry 与属性描述 |
| 大 Schema 首屏慢 | 按区块懒加载、Schema 分片下发 |

**适用边界（这是加分项）：**

低代码适合**结构重复、变化频繁、由非开发者维护**的场景（表单、审批、活动页、大屏）。不适合：强定制交互（拖拽画布、复杂动画）、性能敏感页面、需要深度调试的复杂状态流。硬套低代码的结果往往是「配置器越来越复杂，最后比写代码还慢」。

**边界情况与坑：**

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| Schema 升级后老页面崩 | 协议不兼容 | `version` 字段 + 迁移函数 + 渲染器向后兼容 |
| 表达式把页面搞崩 | 沙箱不严或异常未捕获 | AST 白名单 + try/catch + 超时保护 |
| 配置器与运行时表现不一致 | 两套渲染实现 | 共用 registry 和同一套属性解析 |
| 组件库升级后 Schema 失效 | props 语义变化 | 物料版本化，Schema 绑定物料版本 |
| 页面越配越慢 | 全量重渲染 | 依赖收集 + memo + 虚拟化 |
| 运营配置出 XSS | 直接渲染 HTML 字符串 | 禁止 `dangerouslySetInnerHTML`，富文本走白名单清洗 |
| 回滚困难 | 没有版本与发布记录 | Schema 存版本、支持灰度与回滚 |

**面试怎么答：** 先给「协议 + 渲染器 + 物料 + 配置器」四件套，再按三类低代码说明适用场景；渲染器讲递归 + registry 白名单 + 条件渲染；联动讲依赖收集与最小重渲染；安全讲表达式沙箱（`new Function` 不是沙箱）；最后讲版本兼容与适用边界，明确「不是所有页面都该低代码」。

**易错点：**

- 把低代码等同于「拖拽生成页面」，忽略协议与运行时。
- 用 `eval` / `new Function` 执行运营输入的表达式并称之为沙箱。
- 让 Schema 里的 type 直接决定动态 import 路径，留下远程代码执行风险。
- 任何字段变化都重渲染整页，字段一多就卡死。
- 不做 Schema 版本管理，协议一改老页面全废。

## 5. PDF 预览与前端打印

**结论先行：** PDF 预览有两条路：**交给浏览器内置查看器**（`iframe`/`embed`，零代码但不可控）和**自己渲染**（`pdf.js`，可控但要做分页、缩放、文本层）。前端打印的核心不是 `window.print()`，而是**打印样式（`@media print`）与分页控制**；把 HTML 转成 PDF（html2canvas + jsPDF）通常是最后手段，清晰度和分页都容易翻车。

**预览方案对比：**

| 方案 | 实现 | 优点 | 缺点 | 适用 |
| --- | --- | --- | --- | --- |
| `iframe` / `embed` / `object` | 直接给 PDF URL | 零依赖、功能全 | 样式不可控、移动端体验差、跨域受限 | 内部系统、快速上线 |
| `pdf.js` | Canvas 逐页渲染 | 完全可控、可加水印/选区/自定义工具栏 | 需要 worker、包体较大、文本层要单独做 | 需要深度定制的 C 端 |
| 服务端转图片 | 后端渲染成 PNG 列表 | 前端极简、防下载 | 失去文本与缩放清晰度、成本高 | 只读展示、防复制 |
| 第三方 SaaS | 嵌入厂商 viewer | 功能全、省开发 | 成本、数据合规 | 商业文档场景 |

**pdf.js 的关键配置：**

```ts
import * as pdfjsLib from 'pdfjs-dist';
import workerUrl from 'pdfjs-dist/build/pdf.worker.min.mjs?url';

pdfjsLib.GlobalWorkerOptions.workerSrc = workerUrl;

async function renderPdf(url: string, canvas: HTMLCanvasElement, pageNo = 1) {
  const pdf = await pdfjsLib.getDocument({
    url,
    cMapUrl: '/cmaps/',          // 中文等 CJK 字体映射，缺了会乱码
    cMapPacked: true,
  }).promise;

  const page = await pdf.getPage(pageNo);
  const viewport = page.getViewport({ scale: 1 });
  const dpr = window.devicePixelRatio || 1;
  const scale = (canvas.clientWidth / viewport.width) * dpr;

  const scaled = page.getViewport({ scale });
  canvas.width = scaled.width;
  canvas.height = scaled.height;
  canvas.style.width = `${scaled.width / dpr}px`;

  await page.render({
    canvasContext: canvas.getContext('2d')!,
    viewport: scaled,
  }).promise;
}
```

要点：

- **必须配 worker**，否则主线程解析大 PDF 会卡死；worker 文件要走构建工具处理路径（Vite 用 `?url`）。
- **按 DPR 放大 Canvas**，否则高分屏上文字发虚。
- **只渲染当前页/可视页**，百页 PDF 一次性渲染会直接 OOM；翻页时销毁旧页的 render task。
- **中文乱码**多半是缺 `cMapUrl` 与标准字体资源。
- 需要选中复制文字时，要额外渲染 text layer（`pdfjs-dist` 的 `TextLayer`），Canvas 本身没有文本。

**打印：先把打印样式做对**

```css
@media print {
  @page {
    size: A4;
    margin: 12mm;
  }

  .no-print { display: none !important; }
  .page-break { break-after: page; }
  .avoid-break { break-inside: avoid; }

  /* 表格跨页时重复表头 */
  thead { display: table-header-group; }
  tr { break-inside: avoid; }

  /* 背景色默认不打印，需要显式开启 */
  .print-bg {
    -webkit-print-color-adjust: exact;
    print-color-adjust: exact;
  }
}
```

几个高频问题：

| 问题 | 原因 | 处理 |
| --- | --- | --- |
| 打印出来没有背景色 | 浏览器默认省墨 | `print-color-adjust: exact` |
| 表格跨页断在行中间 | 没有分页控制 | `tr { break-inside: avoid }` + `thead` 重复 |
| 图表被截断 | Canvas 尺寸与纸张比例不匹配 | 打印前按 A4 比例重绘，或转图片 |
| 打印出侧边栏/按钮 | 没有隐藏非内容区 | `.no-print` + 打印专用布局 |
| 分页位置不可控 | 依赖浏览器自动分页 | 用固定高度的分页容器主动切页 |

**只打印局部区域：**

```ts
function printElement(el: HTMLElement) {
  const iframe = document.createElement('iframe');
  iframe.style.cssText = 'position:fixed;right:0;bottom:0;width:0;height:0;border:0;';
  document.body.appendChild(iframe);

  const doc = iframe.contentDocument!;
  doc.open();
  doc.write(`<!doctype html><html><head>${collectStyles()}</head><body>${el.outerHTML}</body></html>`);
  doc.close();

  iframe.onload = () => {
    iframe.contentWindow!.focus();
    iframe.contentWindow!.print();
    setTimeout(() => iframe.remove(), 1000);   // 打印对话框是异步的，不能立刻删
  };
}
```

`collectStyles()` 要把当前页的 `<link rel="stylesheet">` 和 `<style>` 复制进去，否则打印出来没有样式。直接对 `document.body` 加 `print-only` 类再 `window.print()` 也可以，但会受全局布局影响，iframe 方案更隔离。

**html2canvas + jsPDF 的坑：**

- 本质是「截图 → 塞进 PDF」，**文字变成位图**，放大模糊、无法选中、文件体积大。
- 长页面要手动分页，按 canvas 高度切片，容易出现「一行字被切成两半」。
- 跨域图片会污染 canvas，必须 `crossOrigin` + 服务端 CORS。
- 自定义字体、阴影、渐变、`filter` 支持不完整。
- 只适合「导出凭证/海报」这类短页面；正式报表优先让后端生成 PDF。

**边界情况与坑：**

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 移动端 iframe 里 PDF 不显示 | 部分 WebView 不支持内置 PDF | 改用 pdf.js 渲染 |
| 跨域 PDF 加载失败 | 服务端未允许跨域/需要鉴权 | 后端代理或签名 URL |
| 大 PDF 首屏很慢 | 一次性解析全部页 | 只加载当前页，按需 `getPage` |
| 打印按钮点了没反应 | 在异步回调里调用，丢失用户手势 | 在点击同步链路里触发 |
| 打印内容空白 | iframe 尚未 load 就 print | 在 `onload` 后打印 |
| 打印预览与页面不一致 | 屏幕样式依赖视口宽度 | 打印样式用固定 mm/pt 单位 |
| 页码/页眉缺失 | 浏览器自动页眉页脚 | `@page` 只能控制边距，页码需自己排版或用后端生成 |

**面试怎么答：** 先按「内置 viewer / pdf.js / 服务端转图」给选型，再讲 pdf.js 的三个关键点（worker、DPR、按页渲染）和中文 cMap；打印部分讲 `@media print` 的分页、表头重复、背景色、局部打印的 iframe 方案；最后明确 html2canvas 方案只适合短页面，正式报表走后端。

**易错点：**

- 用 `iframe` 预览跨域 PDF，没考虑鉴权与 X-Frame-Options。
- pdf.js 不配 worker，大文件直接把主线程卡住。
- 打印时忘了 `print-color-adjust`，品牌色全丢。
- 用 html2canvas 导出几十页报表，文字模糊且分页错乱。

## 6. 二维码生成与识别

**结论先行：** 生成是「把字符串编码成矩阵图」，识别是「从图像里定位三个定位符并解码」。工程上生成用 `qrcode` 之类的库直接出 Canvas/SVG；识别优先用原生 `BarcodeDetector`，不支持时退回 `jsQR`/`zxing-wasm`。真正的坑在**容错等级、尺寸与对比度、摄像头抽帧性能**。

**生成方案对比：**

| 方案 | 输出 | 优点 | 缺点 |
| --- | --- | --- | --- |
| `qrcode` | Canvas / DataURL / SVG | 通用、API 简单 | 不支持 logo、样式定制 |
| `qrcode.react` | React 组件（SVG/Canvas） | 声明式、随状态更新 | 仅 React |
| `qrcode-generator` | 矩阵数据 | 可完全自绘 | 要自己画模块 |
| 服务端生成 | 图片 URL | 不占前端、可带 logo | 多一次请求、难实时改 |

**生成与关键参数：**

```ts
import QRCode from 'qrcode';

await QRCode.toCanvas(canvas, 'https://example.com/login?t=abc', {
  width: 240,
  margin: 2,                 // 静区，至少 4 个模块，太小会扫不出
  errorCorrectionLevel: 'M', // L/M/Q/H，越高越抗遮挡、容量越小
  color: { dark: '#000000', light: '#ffffff' },
});
```

| 参数 | 建议 | 说明 |
| --- | --- | --- |
| `errorCorrectionLevel` | 一般 `M`；带 logo 用 `H` | H 可恢复约 30% 破损，但模块更密 |
| `margin`（静区） | 至少 4 个模块 | 四周留白不足是最常见的扫不出原因 |
| 尺寸 | 物理尺寸 ≥ 2cm，模块 ≥ 4px | 屏幕像素不等于打印尺寸 |
| 对比度 | 深色码点 + 浅色底 | 反色（白码黑底）很多扫描器不支持 |
| 内容长度 | 越短越好 | 长 URL 会让版本升高、模块变小 |

带 logo 时，logo 面积不要超过码面 20%，并放在中心；容错等级用 `H`。二维码内容建议用**短链**，而不是把长参数直接编码进去。

**识别：优先原生，降级 wasm/JS**

```ts
async function scanWithBarcodeDetector(video: HTMLVideoElement) {
  const detector = new (window as any).BarcodeDetector({ formats: ['qr_code'] });
  const loop = async () => {
    if (video.readyState >= 2) {
      const codes = await detector.detect(video);
      if (codes[0]?.rawValue) return codes[0].rawValue;
    }
    requestAnimationFrame(loop);
  };
  return loop();
}
```

`BarcodeDetector` 在 Chrome/Edge/Android 可用，Safari 与 Firefox 支持不全；降级用 `jsQR`：

```ts
import jsQR from 'jsqr';

function scanFrame(video: HTMLVideoElement, canvas: HTMLCanvasElement) {
  const ctx = canvas.getContext('2d', { willReadFrequently: true })!;
  canvas.width = video.videoWidth;
  canvas.height = video.videoHeight;
  ctx.drawImage(video, 0, 0);
  const imageData = ctx.getImageData(0, 0, canvas.width, canvas.height);
  return jsQR(imageData.data, imageData.width, imageData.height, {
    inversionAttempts: 'dontInvert',   // 只认深码浅底，性能更好
  });
}
```

**摄像头扫码的完整流程：**

```ts
async function startScan(onResult: (text: string) => void) {
  const stream = await navigator.mediaDevices.getUserMedia({
    video: { facingMode: 'environment', width: { ideal: 1280 } },
  });
  video.srcObject = stream;
  await video.play();

  let raf = 0;
  let last = 0;
  const tick = (ts: number) => {
    // 每 100ms 解一帧即可，逐帧解码会吃满 CPU
    if (ts - last > 100) {
      last = ts;
      const code = scanFrame(video, canvas);
      if (code) {
        stop();
        return onResult(code.data);
      }
    }
    raf = requestAnimationFrame(tick);
  };
  raf = requestAnimationFrame(tick);

  const stop = () => {
    cancelAnimationFrame(raf);
    stream.getTracks().forEach((t) => t.stop());   // 必须关，否则摄像头指示灯常亮
  };
}
```

要点：

- **必须 HTTPS**（`localhost` 例外），否则 `getUserMedia` 不可用。
- 用 `facingMode: 'environment'` 优先后置摄像头，失败时要能切前置。
- 抽帧节流（8 到 12 帧/秒）比逐帧解码稳定得多。
- 识别成功后立刻停止轨道，否则手机耗电且隐私指示灯不灭。
- 从相册选图识别时，用 `File` → `createImageBitmap` → Canvas → `jsQR`，注意压缩后的图片可能已损坏二维码。

**边界情况与坑：**

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 生成的码扫不出 | 静区太小/模块不足 4px | 加 `margin`、放大尺寸 |
| 带 logo 后扫不出 | 遮挡超过容错能力 | 用 `H` 级，logo ≤ 20% |
| 暗色主题下二维码失效 | 背景透明或反色 | 始终给浅色底，不要透明背景 |
| iOS 不识别 | 用了反色或低对比度 | 深码浅底、提高对比度 |
| 扫码很卡 | 逐帧解码 + 高分辨率 | 降低分辨率、抽帧、`willReadFrequently` |
| 页面切后台摄像头仍开 | 没监听 `visibilitychange` | 切后台停止轨道，回前台重启 |
| 权限被拒后无提示 | 没捕获 `NotAllowedError` | 展示引导文案与重新授权入口 |
| Canvas 截图识别失败 | 图片跨域污染 | 同源或 CORS + `crossOrigin` |

**面试怎么答：** 先分生成与识别两块：生成讲容错等级、静区、尺寸与对比度，识别讲 `BarcodeDetector` 优先、`jsQR` 降级、抽帧与轨道释放；再补 HTTPS、权限、相册识别这些工程点。

**易错点：**

- 给二维码设透明背景，暗色页面下直接失效。
- 内容过长导致模块过密，打印或远距离扫不出。
- 逐帧全分辨率解码，手机发烫且识别率反而下降。
- 识别成功后不 `stop()` 轨道，摄像头一直开着。

## 7. 剪贴板 API 与富文本复制粘贴

**结论先行：** 剪贴板分「写」和「读」两条链路，各有不同限制：写入需要**安全上下文 + 用户手势**，读取还需要**权限**；富文本复制要靠 `ClipboardItem` 同时写 `text/html` 与 `text/plain`，粘贴则必须**清洗 HTML**（防 XSS）并处理图片、表格等特殊内容。

**能力对比：**

| 能力 | API | 前提 | 兼容性 |
| --- | --- | --- | --- |
| 写纯文本 | `navigator.clipboard.writeText` | HTTPS + 用户手势 | 现代浏览器全支持 |
| 写富文本/图片 | `navigator.clipboard.write([ClipboardItem])` | HTTPS + 用户手势 + 权限 | Chromium 较全，Safari 部分支持 |
| 读纯文本 | `navigator.clipboard.readText` | HTTPS + 权限（Safari 会弹确认） | 现代浏览器 |
| 读任意类型 | `navigator.clipboard.read` | 权限 | Chromium |
| 监听粘贴 | `paste` 事件 + `clipboardData` | 无 | 全支持 |
| 旧版写入 | `document.execCommand('copy')` | 选中内容 | 已废弃但兼容性好 |

**写入纯文本与降级：**

```ts
async function copyText(text: string) {
  try {
    await navigator.clipboard.writeText(text);
    return true;
  } catch {
    // 降级：创建不可见 textarea + execCommand
    const ta = document.createElement('textarea');
    ta.value = text;
    ta.style.cssText = 'position:fixed;opacity:0;pointer-events:none;';
    document.body.appendChild(ta);
    ta.select();
    const ok = document.execCommand('copy');
    ta.remove();
    return ok;
  }
}
```

**必须在用户手势的同步调用链里触发**。如果在 `await fetch(...)` 之后再调 `writeText`，Safari 会认为不是用户触发的而拒绝。正确做法是：先拿到数据再让用户点「复制」，或点击时立刻写入一个占位内容。

**复制富文本：同时给 HTML 和纯文本**

```ts
async function copyRich(html: string, plain: string) {
  const item = new ClipboardItem({
    'text/html': new Blob([html], { type: 'text/html' }),
    'text/plain': new Blob([plain], { type: 'text/plain' }),
  });
  await navigator.clipboard.write([item]);
}
```

只给 `text/html` 时，粘贴到纯文本编辑器（记事本、终端）会得到空内容；只给 `text/plain` 则丢失格式。**两个都给**才是正确姿势，`text/plain` 一般是 HTML 的降级文本。

**复制当前选区（保留原有格式）：**

```ts
document.addEventListener('copy', (e) => {
  const selection = window.getSelection();
  if (!selection || selection.isCollapsed) return;
  const container = document.createElement('div');
  container.appendChild(selection.getRangeAt(0).cloneContents());

  // 自定义剪贴板内容
  e.clipboardData?.setData('text/html', container.innerHTML);
  e.clipboardData?.setData('text/plain', selection.toString());
  e.preventDefault();   // 阻止浏览器默认行为，使用我们写入的内容
});
```

这个方式的好处是能**在复制时追加来源信息、去除敏感内容或改写链接**（例如给复制的正文自动加上原文地址）。

**粘贴：默认行为与自定义**

```ts
editor.addEventListener('paste', async (e) => {
  const html = e.clipboardData?.getData('text/html');
  const text = e.clipboardData?.getData('text/plain');
  const files = Array.from(e.clipboardData?.files ?? []);

  // 图片粘贴：截图后直接上传
  const image = files.find((f) => f.type.startsWith('image/'));
  if (image) {
    e.preventDefault();
    return insertImage(await upload(image));
  }

  if (html) {
    e.preventDefault();
    return insertHtml(sanitize(html));   // 关键：白名单清洗
  }
  // 纯文本走默认行为即可
});
```

**粘贴清洗是安全红线：** 从 Word/网页复制的内容可能带 `<script>`、`onerror`、`javascript:` 链接、外部追踪像素。必须用白名单清洗（`DOMPurify` 或自研规则），只保留允许的标签与属性，并移除所有事件属性。直接 `innerHTML = clipboardHtml` 等于给自己开了一个 XSS 入口。

**表格粘贴：**

从 Excel 复制到网页表格，`text/plain` 是 TSV（`\t` 分列、`\n` 分行），`text/html` 是 `<table>`。优先解析 HTML 更能保留合并单元格；解析 TSV 更简单稳定。粘贴到富文本编辑器时，通常要把 `<table>` 转成编辑器支持的表格节点，而不是原样插入。

**边界情况与坑：**

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| `navigator.clipboard` 是 undefined | HTTP 环境或旧浏览器 | 降级 `execCommand`，并提示需 HTTPS |
| 写剪贴板报 `NotAllowedError` | 非用户手势/iframe 权限策略 | 在点击回调里同步调用，检查 `allow="clipboard-write"` |
| Safari 复制失败 | 异步后丢失用户手势 | 先准备数据再点击，或点击时用 `ClipboardItem` 同步写入 Promise |
| 粘贴后格式全乱 | 直接插入原始 HTML | 白名单清洗 + 样式内联化 |
| 粘贴带脚本 | 未清洗 | DOMPurify，禁止事件属性与 `javascript:` |
| 图片粘贴无效 | 只看 `text/plain` | 读 `clipboardData.files` / `items` |
| 复制到 Excel 不分列 | 只给了 HTML 或分隔符不对 | 同时给 `text/plain` 的 TSV |
| 复制内容带隐藏水印/追踪 | 源 HTML 自带 | 清洗时移除 `<img>` 外链与不可见元素 |

**面试怎么答：** 先讲写入的三个前提（安全上下文、用户手势、权限），再讲富文本必须同时写 `text/html` 和 `text/plain`；粘贴侧重点讲**清洗**（XSS 红线）、图片与表格的处理；最后补 Safari 的异步手势限制与 `execCommand` 降级。

**易错点：**

- 在 `await` 之后调用 `writeText`，Safari 直接拒绝。
- 只写 HTML 不写纯文本，粘到记事本变空。
- 粘贴时直接 `innerHTML`，引入 XSS。
- 忘了图片在 `clipboardData.files` 里，而不是文本字段。

## 8. 离线可用与 PWA 落地

**结论先行：** PWA 的三件套是 **HTTPS + Web App Manifest + Service Worker**。离线能力的核心是 Service Worker 的缓存策略：**静态资源预缓存（precache）、接口按场景选策略（CacheFirst / NetworkFirst / StaleWhileRevalidate）、导航请求回退到 `index.html`**。真正难的是**版本更新**：缓存策略写错，用户会长期停留在旧版本。

**能力清单与现实边界：**

| 能力 | 依赖 | 说明 |
| --- | --- | --- |
| 可安装 | Manifest + HTTPS + SW | Chrome/Edge 支持；iOS 需手动「添加到主屏幕」 |
| 离线访问 | SW 缓存 | 首次访问必须联网，之后才可离线 |
| 离线数据 | IndexedDB | localStorage 容量小且同步阻塞 |
| 后台同步 | Background Sync | 仅 Chromium 系，iOS 不支持 |
| 推送 | Web Push + VAPID | iOS 16.4+ 且必须已添加到主屏 |
| 版本更新 | SW 生命周期 | 必须显式处理 `skipWaiting` 与刷新提示 |

**Manifest 最小配置：** 必备字段是 `name` / `short_name` / `start_url` / `scope` / `display: "standalone"` / `theme_color`，以及 192 与 512 两个尺寸的 PNG 图标（Android 安装横幅的硬性要求），另加一张 `purpose: "maskable"` 的自适应图标避免被裁成奇怪形状。`scope` 决定 SW 的控制范围，`start_url` 要是用户真实入口，否则从桌面图标进入会落到错误页面。

**缓存策略选型：**

| 资源 | 策略 | 理由 |
| --- | --- | --- |
| JS/CSS/字体（带 hash） | CacheFirst / precache | 内容不变，命中即用 |
| `index.html` | NetworkFirst | 必须尽快拿到新版本入口 |
| 列表/详情接口 | NetworkFirst（短超时） | 优先新鲜数据，弱网回缓存 |
| 配置/字典 | StaleWhileRevalidate | 先用旧值，后台更新 |
| 图片/静态媒体 | CacheFirst + 过期清理 | 省流量 |
| 用户私有接口 | 不缓存或按用户分区 | 防串号与隐私泄漏 |

**Workbox 配置（构建期注入）：**

```ts
// sw.ts
import { precacheAndRoute, cleanupOutdatedCaches } from 'workbox-precaching';
import { registerRoute, NavigationRoute } from 'workbox-routing';
import { NetworkFirst, CacheFirst, StaleWhileRevalidate } from 'workbox-strategies';
import { ExpirationPlugin } from 'workbox-expiration';

cleanupOutdatedCaches();
precacheAndRoute(self.__WB_MANIFEST);   // 构建时注入带 hash 的产物列表

registerRoute(
  ({ request }) => request.mode === 'navigate',
  new NetworkFirst({ cacheName: 'pages', networkTimeoutSeconds: 3 })
);

registerRoute(
  ({ request }) => ['style', 'script', 'font'].includes(request.destination),
  new CacheFirst({ cacheName: 'assets' })
);

registerRoute(
  ({ url }) => url.pathname.startsWith('/api/config'),
  new StaleWhileRevalidate({ cacheName: 'config' })
);

registerRoute(
  ({ request }) => request.destination === 'image',
  new CacheFirst({
    cacheName: 'images',
    plugins: [new ExpirationPlugin({ maxEntries: 100, maxAgeSeconds: 7 * 24 * 3600 })],
  })
);

// 登出时清理私有数据缓存，避免串号
async function clearUserCaches() {
  await Promise.all(['pages', 'config'].map((c) => caches.delete(c)));
}
```

SPA 必须处理**导航回退**：刷新 `/order/123` 时服务器没有这个文件，SW 要返回缓存的 `index.html`，再由前端路由接管。Workbox 的 `NetworkFirst` 对 navigate 请求会自动回退到 precache 的 `index.html`。

**版本更新：最容易翻车的地方**

Service Worker 的默认行为是「新的 waiting，旧的继续控制页面」，直到所有标签页关闭。这会导致用户长时间用旧版本。标准流程：

```ts
// 注册与更新提示
navigator.serviceWorker.register('/sw.js').then((reg) => {
  reg.addEventListener('updatefound', () => {
    const worker = reg.installing;
    worker?.addEventListener('statechange', () => {
      if (worker.state === 'installed' && navigator.serviceWorker.controller) {
        showUpdateToast(() => {
          worker.postMessage({ type: 'SKIP_WAITING' });
        });
      }
    });
  });
});

// 新 SW 接管后刷新一次
navigator.serviceWorker.addEventListener('controllerchange', () => {
  location.reload();
});
```

```ts
// sw.ts
self.addEventListener('message', (e) => {
  if (e.data?.type === 'SKIP_WAITING') self.skipWaiting();
});
```

注意：`controllerchange` 里直接 `reload()` 可能造成刷新循环，要加一个标志位只刷新一次。另外，**不要默认 `skipWaiting`**：新 SW 立刻接管会让正在提交表单的页面资源版本错乱，应该由用户确认后更新。

**离线数据与后台同步：**

```ts
// 离线时把待提交操作写入 IndexedDB
async function saveOfflineAction(action: OfflineAction) {
  const db = await openDB();
  await db.add('outbox', { ...action, id: crypto.randomUUID(), ts: Date.now() });
}

// 联网后按顺序补发（Background Sync 不可用时用 online 事件兜底）
window.addEventListener('online', async () => {
  const db = await openDB();
  for (const action of await db.getAll('outbox')) {
    await api.submit(action);          // 服务端按 action.id 幂等
    await db.delete('outbox', action.id);
  }
});
```

要点：离线队列必须**幂等**（带客户端生成的 id），否则重发会重复下单；要按时间顺序发送；冲突策略（服务端为准 / 客户端为准 / 合并）必须提前定义。

**安装与推送：**

```ts
let deferredPrompt: any;

window.addEventListener('beforeinstallprompt', (e) => {
  e.preventDefault();
  deferredPrompt = e;               // 必须存下来，等用户点「安装」时再 prompt
});

installButton.onclick = async () => {
  if (!deferredPrompt) return;
  deferredPrompt.prompt();
  await deferredPrompt.userChoice;
  deferredPrompt = null;            // 只能调用一次，用完即弃
};
```

iOS 没有 `beforeinstallprompt`，只能引导用户「分享 → 添加到主屏幕」；Web Push 在 iOS 也要求已添加到主屏，且权限必须由用户手势触发。

**边界情况与坑：**

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 改了代码用户还是旧版 | SW 缓存了旧入口，未更新 | `NetworkFirst` 处理 HTML + 更新提示 + `cleanupOutdatedCaches` |
| 更新后白屏 | 新旧资源 hash 混用 | 预缓存全量新产物，旧缓存清理；入口走网络优先 |
| 离线时刷新 404 | 没做导航回退 | navigate 请求回退 `index.html` |
| 缓存无限增长 | 没有过期与上限 | `ExpirationPlugin` + 容量监控 |
| 私有数据串号 | 接口缓存没按用户分区 | 登出时清空相关缓存 |
| `getUserMedia`/推送不可用 | 非 HTTPS | 全站 HTTPS（localhost 除外） |
| SW 不生效 | `scope` 与注册路径不匹配 | `sw.js` 放根路径或设置 `Service-Worker-Allowed` |
| 开发环境缓存旧代码 | SW 在 dev 也生效 | 只在生产注册，dev 主动 `unregister` |
| 双标签页互相刷新 | 两个页面都监听 `controllerchange` | 只让主标签页 reload，或加一次性标志 |

**面试怎么答：** 先给三件套与能力边界（尤其 iOS），再讲缓存策略按资源类型分开（预缓存、HTML 网络优先、图片 CacheFirst），重点讲**版本更新流程**（waiting → 提示 → skipWaiting → controllerchange 刷新）与导航回退，最后补离线队列幂等、缓存清理、私有数据不缓存。

**易错点：**

- 认为「注册了 SW 就能离线」，其实首次访问必须联网完成预缓存。
- 默认调用 `skipWaiting`，导致旧页面加载新资源而报错。
- 把接口响应全量缓存，造成隐私泄漏与脏数据。
- 只在开发环境测试，没验证 HTTPS、scope、iOS 的安装路径。
