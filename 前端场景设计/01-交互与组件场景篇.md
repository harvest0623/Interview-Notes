## 1. 如何实现一个高性能虚拟列表（固定高度与不定高度）

**结论先行：** 虚拟列表的本质是**只渲染可视区内的节点**，用「占位高度 + 绝对定位/transform」伪造完整滚动空间。固定高度是纯数学问题（除法即可）；不定高度是**测量 + 前缀和 + 二分查找 + 滚动锚点补偿**的问题。两者都必须解决同一件事：**滚动条长度必须真实**，否则会出现「滚到底部还在加载」的错觉。

**选型对比（先说清楚用什么，再说怎么写）：**

| 方案 | 适用场景 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 自己实现 | 面试手写、结构特殊的列表（聊天流、瀑布流） | 完全可控、便于做业务定制 | 边界多，测量与锚点补偿要自己处理 |
| `react-window` | 固定高/等宽网格、海量简单行 | 体积小（约 6KB）、API 简单 | 动态高度支持弱（需 `VariableSizeList` + 手动重置缓存） |
| `react-virtualized` | 老项目、需要 Table/Grid/Masonry 全家桶 | 功能最全 | 体积大、维护低频、API 陈旧 |
| `@tanstack/virtual` | 动态高度、横向/纵向、框架无关 | 支持 `measureElement` 动态测量、头less | 需要自己写 DOM 结构 |
| `vue-virtual-scroller` | Vue 2/3 动态列表 | 开箱即用、支持动态尺寸 | 深度定制不如手写灵活 |

**固定高度：一次除法就能定位**

```ts
const ITEM_H = 48;
const OVERSCAN = 3; // 上下各多渲染几条，抵消快速滚动的白屏

function getRange(scrollTop: number, viewportH: number, total: number) {
  const rawStart = Math.floor(scrollTop / ITEM_H);
  const start = Math.max(0, rawStart - OVERSCAN);
  const visible = Math.ceil(viewportH / ITEM_H) + 1;
  const end = Math.min(total, rawStart + visible + OVERSCAN);
  return { start, end, offsetY: start * ITEM_H };
}
```

渲染结构的关键是**三层**：

```
外层容器（固定高度，overflow-y: auto，负责产生滚动条）
  └─ 占位层（height = total * ITEM_H，把滚动空间撑出来）
       └─ 渲染层（transform: translateY(offsetY)，只放 start~end 的节点）
```

用 `transform` 而不是 `top`，因为 `transform` 只触发合成，不触发布局；同时给渲染层加 `will-change: transform` 可以减少滚动时的重绘（但不要滥用到每个子项上，会吃显存）。

**不定高度：三个必须解决的问题**

1. **未测量时怎么占位**：给一个 `estimatedHeight`（估算值），先按估算值排布，测量后再修正。
2. **怎么根据 `scrollTop` 找到起始索引**：维护 `offsets` 前缀和数组，用二分查找代替线性遍历（几万条数据时差距是毫秒级 vs 几十毫秒）。
3. **测量后高度变化导致内容跳动**：如果用户已经往下滚了，上方某条变高会把当前内容「顶下去」，必须补偿 `scrollTop`（锚点补偿）。

```ts
// 前缀和 + 二分：返回 scrollTop 对应的行索引
function findStart(offsets: number[], scrollTop: number) {
  let lo = 0, hi = offsets.length - 1;
  while (lo <= hi) {
    const mid = (lo + hi) >> 1;
    if (offsets[mid] <= scrollTop) lo = mid + 1;
    else hi = mid - 1;
  }
  return Math.max(0, hi);
}

// 测量并写回：只对「已渲染」的节点测量，未渲染的仍是估算值
const ro = new ResizeObserver((entries) => {
  let delta = 0;
  for (const entry of entries) {
    const el = entry.target as HTMLElement;
    const index = Number(el.dataset.index);
    const h = entry.borderBoxSize[0].blockSize;
    const old = heights[index];
    if (Math.abs(h - old) > 0.5) {
      heights[index] = h;
      delta += h - old;
      // 只有「变化发生在可视区上方」才需要补偿，否则会平白滚动
      if (index < startIndex) deltaAbove += h - old;
    }
  }
  rebuildOffsets();               // 重算前缀和（O(n)，可优化成树状数组）
  if (deltaAbove) {
    scroller.scrollTop += deltaAbove; // 锚点补偿：视觉位置不变
    deltaAbove = 0;
  }
});
```

**几个经常被追问的实现细节：**

- **滚动事件用 `requestAnimationFrame` 合并**：`scroll` 事件触发频率可能高于帧率，直接在回调里 `setState` 会掉帧。用 rAF 节流，一帧只更新一次区间。
- **`ResizeObserver` 优于每次渲染后读 `offsetHeight`**：后者会强制同步布局（layout thrashing），几十行就是几十次重排。
- **列表总高度用「估算 + 已测」混合**：全部测量完之前总高度是动态变化的，滚动条会轻微抖动，这是正常代价；成熟的库会把未测量项按平均值估算来减小抖动。
- **快速拖动滚动条时的白屏**：`overscan` 只能缓解，根治要靠「滚动期间显示占位块/骨架」而不是等测量完成。
- **吸底场景（聊天）**：新消息插入时要判断用户是否在底部，在底部才自动 `scrollToBottom`，否则保持当前位置（否则用户翻历史会被强行拽回底部）。

**边界情况与坑：**

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 列表空白但滚动条很长 | 占位层高度没算对（用了渲染条数而不是总数） | 总高度必须基于 `total` 计算 |
| 滚动到某处内容突然跳一下 | 上方行测量后变高，未补偿 `scrollTop` | 记录 `deltaAbove` 并补偿 |
| 移动端惯性滚动时闪白 | 渲染速度跟不上滚动速度 | 提高 `overscan`、降低单行渲染成本、必要时用 `content-visibility` |
| 键盘 Tab 焦点丢失 | 焦点元素被移出渲染区导致 DOM 卸载 | 记住焦点索引，滚动到该索引后再聚焦 |
| 屏幕阅读器读不全 | 虚拟化天然只暴露部分 DOM | 提供「表格视图/导出」等替代路径，或使用 `aria-rowcount` 声明总数 |
| 容器 `display: none` 时初始化 | `clientHeight` 为 0，算出可视条数为 0 | 用 `ResizeObserver` 等容器有尺寸后再计算 |

**轻量替代方案：** 如果只是「几屏长、结构简单」的列表，`content-visibility: auto` + `contain-intrinsic-size` 可以让浏览器跳过屏外内容的渲染，代码量几乎为零；但它不减少 DOM 数量，节点上万时内存仍然吃紧，不能替代虚拟化。

**面试怎么答：** 先讲「渲染裁剪 + 占位撑高 + transform 定位」三件套，再分固定/不定两种讲索引计算，重点强调不定高度的三个难点（估算、二分、锚点补偿），最后补一句选型（简单场景用 `react-window`/`@tanstack/virtual`，聊天流这类结构特殊的自己写）。

**易错点：**

- 把虚拟列表说成「懒加载」——懒加载是延迟**请求**，虚拟列表是延迟**渲染**，两件事。
- 只渲染可视区却忘了撑高容器，滚动条会变成「只有一屏」。
- 不定高度场景直接用 `scrollTop / 估算高度` 算索引，测量后必然错位。
- 在 `scroll` 回调里同步读 `offsetHeight`，等于每帧强制重排，性能比不优化还差。

## 2. 无限滚动与分页加载（IntersectionObserver 方案与坑）

**结论先行：** 无限滚动的核心不是「监听滚动」，而是**用一个哨兵元素 + `IntersectionObserver` 判断「快到尽头了」，再用一个显式状态机控制请求**。多数线上事故不是 IO 用错，而是**没有状态机**：重复请求、并发覆盖、加载失败后无法恢复、到底了还在请求。

**三种加载模式对比（先选型再实现）：**

| 模式 | 交互 | 优点 | 缺点 | 适用 |
| --- | --- | --- | --- | --- |
| 传统分页 | 点页码/上一页下一页 | 定位明确、可分享 URL、可回跳 | 操作成本高 | 后台管理、需要精确跳转 |
| 点击加载更多 | 手动点按钮 | 可控、可访问性好、省流量 | 多一次点击 | 移动端信息流、弱网 |
| 自动无限滚动 | 滚到底自动加载 | 沉浸、转化率高 | 难以回到之前位置、SEO 差 | 社交/内容流 |

> 工程上常见做法是**混合**：自动加载为主，同时保留「加载更多」按钮作为兜底（IO 不支持、加载失败、用户想手动触发时都能用）。

**`IntersectionObserver` 的正确用法：**

```ts
const io = new IntersectionObserver(
  (entries) => {
    if (entries[0].isIntersecting) loadMore();
  },
  {
    root: scrollContainer,   // 关键：不传则以视口为准，容器内滚动不触发
    rootMargin: '0px 0px 400px 0px', // 提前 400px 触发，减少等待感
    threshold: 0,
  }
);
io.observe(sentinelRef.current!);
```

`rootMargin` 的方向语义容易被记反：**底部预加载要写在下边**（`0 0 400px 0`），因为它是「把观察区域的边界向外扩」。

**状态机（这是答题的加分项）：**

```
idle ──触发──> loading ──成功且有数据──> idle（hasMore=true）
                    │
                    ├─成功但空数组──> finished（不再请求）
                    └─失败──> error（展示重试，或退避后自动重试 1 次）
```

对应到代码，至少要四个字段：`status`、`page/cursor`、`hasMore`、`requestId`。

```ts
type Status = 'idle' | 'loading' | 'error' | 'finished';

async function loadMore() {
  if (statusRef.current !== 'idle' || !hasMoreRef.current) return; // 并发锁
  statusRef.current = 'loading';
  const seq = ++seqRef.current;
  try {
    const res = await api.list({ cursor: cursorRef.current, size: 20 });
    if (seq !== seqRef.current) return;        // 丢弃过期响应，防竞态
    cursorRef.current = res.nextCursor;
    hasMoreRef.current = res.list.length > 0 && !!res.nextCursor;
    setList((prev) => [...prev, ...res.list]);
    statusRef.current = hasMoreRef.current ? 'idle' : 'finished';
    // 首屏不足一屏时 IO 不会再触发，需要主动补一次
    requestAnimationFrame(() => {
      if (scrollContainer.scrollHeight <= scrollContainer.clientHeight) loadMore();
    });
  } catch (e) {
    statusRef.current = 'error';
  }
}
```

**为什么用 cursor 而不是 page+offset：** 信息流在头部插入新数据时，`offset` 会整体后移，导致第二页重复返回第一页末尾的几条。后端用「上一页最后一条的排序键」作为 `cursor` 可以天然避免漂移；如果后端只能给 offset，前端要按业务主键去重。

**常见坑（按出现频率排序）：**

| 坑 | 表现 | 原因与解法 |
| --- | --- | --- |
| 一次触发多次请求 | 同一页数据重复追加 | IO 回调可能在布局变化时连续触发，必须用 `loading` 锁 |
| 到底后仍在请求 | 空数组反复拉取 | 用 `hasMore` 或 `finished` 状态终止，并 `io.disconnect()` |
| 容器内滚动不触发 | 滚到底没反应 | `root` 没指向滚动容器 |
| 首屏不满一屏 | 不继续加载 | IO 初始就会回调一次，若首屏数据不足需主动补拉 |
| 加载后哨兵仍在视口内 | 连续触发 | 说明数据没撑满，属于预期，应继续加载直到撑满或 `finished` |
| 容器被 `display: none` | 切回页签后不触发 | IO 对不可见元素不产生交叉，切回时手动检测一次 |
| 列表重排后位置丢失 | 从详情返回时回到顶部 | 缓存 `scrollTop` 与已加载数据，返回时恢复（配合 keep-alive 更自然） |
| 重复 observe 同一元素 | 回调执行多次 | 组件卸载时 `io.unobserve`，且不要在多处 observe 同一哨兵 |
| 手势惯性滚动过快 | 直接越过触发区 | `rootMargin` 加大，必要时同时监听 `scroll` 做兜底 |

**竞态问题要单独讲清楚：** 用户快速切换筛选条件时，旧请求可能晚于新请求返回，把旧数据拼到新列表里。除了 `seq` 自增校验，更稳妥的是在筛选条件变化时**重置状态机并 `AbortController.abort()` 掉在途请求**。

**可访问性与 SEO：** 无限滚动对键盘用户和爬虫都不友好。可访问性上要给列表加 `role="feed"`、给「加载更多」按钮真实可聚焦；SEO 上要么首屏直出，要么提供分页 URL 供爬虫抓取（这也是很多内容站保留 `?page=n` 的原因）。

**面试怎么答：** 先给三种模式对比并说明为什么选自动加载 + 按钮兜底，再讲 IO 的三个参数（尤其 `root` 与 `rootMargin`），然后重点讲状态机（并发锁、结束条件、错误恢复、竞态），最后讲 offset 漂移和位置恢复这两个业务坑。

**易错点：**

- 把「加载中」当成 `isLoading` 一个布尔值，无法区分「失败」和「已结束」，必然出现死循环请求。
- 用 `scrollTop + clientHeight >= scrollHeight` 判断触底：在移动端惯性滚动与图片异步撑高时经常误判，且每次都要读布局，性能差。
- 忘了 `io.disconnect()`，组件卸载后回调仍会执行并对已卸载组件 `setState`。
- 没处理「首屏不足一屏」，用户看到的是空白页而不是加载中。

## 3. 如何实现拖拽排序（HTML5 Drag and Drop 与 Pointer Events 两套方案）

**结论先行：** 两套方案的分界线是**设备与自由度**。HTML5 Drag and Drop 是「原生拖放协议」，桌面端零依赖、能拖到外部应用，但**移动端完全不支持**、拖拽影像不可定制、事件语义反直觉；Pointer Events 是「自己算坐标」的方案，鼠标/触屏/触控笔统一，能做出丝滑的插入动画，代价是所有交互（阈值、自动滚动、碰撞检测）都要手写。

**选型对比：**

| 维度 | HTML5 DnD | Pointer Events | 成熟库（SortableJS / dnd-kit） |
| --- | --- | --- | --- |
| 触屏支持 | 不支持（移动端无 drag 事件） | 原生支持 | 支持 |
| 拖拽预览 | 只能用 `setDragImage` 截一张图 | 完全自定义（可加缩放、阴影、倾斜） | 可定制 |
| 跨窗口/跨应用 | 支持（与系统文件拖放同一套） | 不支持 | 不支持 |
| 事件模型 | `dragstart/dragover/drop`，需成对 `preventDefault` | 一条 `pointerdown→move→up` 流 | 已封装 |
| 实现成本 | 低（列表排序约 50 行） | 中（排序 + 动画约 200 行） | 低（引入即用） |
| 典型用途 | 文件上传区、跨区域搬运 | 移动端排序、看板拖拽 | 生产项目首选 |

### 方案一：HTML5 Drag and Drop

三个必须记住的规则：

1. **`dragover` 必须 `preventDefault()`**，否则浏览器认为该区域不接受放置，`drop` 永远不会触发。这是最高频的「拖了没反应」原因。
2. **`dragstart` 里必须 `dataTransfer.setData()`**，Firefox 下不设置数据则不会启动拖拽。
3. **`dragenter/dragleave` 会在子元素间冒泡**，直接切换高亮会闪烁，要用计数器或判断 `relatedTarget`。

```ts
function onDragStart(e: DragEvent, index: number) {
  e.dataTransfer!.effectAllowed = 'move';
  e.dataTransfer!.setData('text/plain', String(index)); // Firefox 必需
  e.dataTransfer!.setDragImage(customGhost, 20, 20);    // 可选：自定义拖拽影像
  dragIndex = index;
}

function onDragOver(e: DragEvent, index: number) {
  e.preventDefault();                 // 关键：不加则无法 drop
  e.dataTransfer!.dropEffect = 'move';
  if (index !== hoverIndex) hoverIndex = index; // 只做插入指示线，不实时换位
}

function onDrop(e: DragEvent, index: number) {
  e.preventDefault();
  const from = Number(e.dataTransfer!.getData('text/plain'));
  if (from !== index) reorder(from, index);
  reset();
}
```

**为什么推荐「松手才换位」而不是「dragover 实时换位」：** 实时换位会让被拖元素在 DOM 中移动，而 DOM 移动会中断原生拖拽（Chrome 下表现为拖拽直接取消）。如果要实时预览，正确做法是**用 transform 做视觉位移**，数据顺序等 `drop` 时再提交。

**HTML5 DnD 的坑：**

- 移动端 Safari/Chrome 均不触发 `dragstart`，必须做 Pointer Events 降级或直接用库。
- `dragstart` 后修改被拖节点的样式无效（浏览器已经截了图），要改 `setDragImage`。
- 拖拽过程中 `mousemove` 不触发，无法做「拖到边缘自动滚动」，只能用 `dragover` 的坐标 + 定时器模拟。
- 从外部拖入文件时，`dataTransfer.types` 包含 `Files`，可据此区分内部排序与文件上传。

### 方案二：Pointer Events

核心是四步：**按下记录起点 → 移动超过阈值才进入拖拽 → 用 transform 跟随手指 → 根据中点判断插入位置**。

```ts
function onPointerDown(e: PointerEvent, index: number) {
  if (e.button !== 0 && e.pointerType === 'mouse') return;
  el.setPointerCapture(e.pointerId);   // 关键：指针移出元素甚至移出窗口仍能收到事件
  startY = e.clientY;
  dragIndex = index;
  moved = false;
}

function onPointerMove(e: PointerEvent) {
  const dy = e.clientY - startY;
  if (!moved && Math.abs(dy) < 5) return; // 5px 阈值：避免与点击冲突
  moved = true;
  ghost.style.transform = `translateY(${dy}px)`;

  // 碰撞检测：遍历同级项，比较「指针位置」与「每项垂直中点」
  const items = [...listEl.children] as HTMLElement[];
  const pointerY = e.clientY;
  let target = dragIndex;
  items.forEach((item, i) => {
    if (i === dragIndex) return;
    const rect = item.getBoundingClientRect();
    const mid = rect.top + rect.height / 2;
    if (i < dragIndex && pointerY < mid) target = Math.min(target, i);
    if (i > dragIndex && pointerY > mid) target = Math.max(target, i);
  });
  if (target !== dragIndex) showIndicator(target);
}

function onPointerUp() {
  el.releasePointerCapture(e.pointerId);
  if (moved && target !== dragIndex) reorder(dragIndex, target);
  reset();
}
```

配套的三件小事，决定了手感：

1. **`touch-action: none`**：不加的话移动端一按就变成页面滚动，`pointermove` 会被浏览器接管并触发 `pointercancel`。
2. **边缘自动滚动**：指针距离容器上下边缘小于 60px 时，用 `requestAnimationFrame` 持续 `scrollTop += speed`，速度随距离线性变化。
3. **FLIP 动画**：换位后先用 `getBoundingClientRect` 记录旧位置，改 DOM 后再读取新位置，对位移差做反向 `transform` 再过渡到 0，才能有「其他项平滑让位」的效果。

**为什么坐标判断用「中点」而不是「边界」：** 用中点判断等价于「指针越过目标项一半才交换」，符合直觉且不会在边界处来回抖动；用边界会在相邻项之间高频切换。

**边界情况：**

| 场景 | 处理 |
| --- | --- |
| 拖拽中页面滚动 | 监听 `scroll` 重新计算目标索引，或锁定滚动 |
| 列表项高度不一 | 必须用每项的实时 `rect`，不能用 `index * itemHeight` |
| 拖拽时点击被误触发 | 移动超过阈值后，在 `pointerup` 里阻止一次 `click` |
| 多指触控 | 只认第一个 `pointerId`，其余忽略 |
| 拖拽到列表外松手 | `pointercancel` 与 `pointerup` 都要做复位 |
| 键盘用户 | 提供「上移/下移」按钮或 `Alt + 方向键` 的排序方式 |

**库的选择：** `SortableJS` 兼容性好、API 简单，适合老项目；`dnd-kit` 基于 Pointer Events、可访问性与自定义能力强，适合 React 新项目；两者都支持虚拟列表联动（拖到边缘滚动加载），但都需要额外处理「拖拽项脱离虚拟渲染区」的问题。

**面试怎么答：** 先给「DnD 适合桌面 + 跨应用，Pointer 适合全端 + 自定义动画」的结论，再分别讲三条关键规则（DnD 的 `dragover` preventDefault、`setData`；Pointer 的 `setPointerCapture`、`touch-action`、阈值），然后说实时换位会中断原生拖拽这个反直觉点，最后补自动滚动与 FLIP。

**易错点：**

- 说「HTML5 拖拽移动端也能用」，实际移动端没有 `drag` 事件。
- 在 `dragover` 里忘记 `preventDefault`，导致 `drop` 不触发。
- Pointer 方案没设 `touch-action: none`，移动端变成滚动。
- 拖拽中直接 `appendChild` 移动节点，导致原生拖拽中断或动画丢失。

## 4. 富文本编辑器的技术选型与实现要点

**结论先行：** 富文本编辑器的分水岭是**「HTML 是不是数据源」**。直接用 `contenteditable` + `execCommand` 看起来最省事，但它把浏览器渲染结果当数据，各浏览器产出的 DOM 结构不一致，撤销、协同、序列化全部不可控。正经编辑器的做法是：**维护一棵结构化文档树，HTML 只是它的视图**，输入事件先转成文档操作，再由渲染层同步到 DOM。

**选型对比：**

| 方案 | 数据模型 | 协同能力 | 体积 | 上手成本 | 适用 |
| --- | --- | --- | --- | --- | --- |
| 原生 `contenteditable` | 无（DOM 即数据） | 几乎不可做 | 0 | 低 | 只读展示、极简输入 |
| `Quill` | Delta（线性操作流） | 需接 OT/CRDT | 中 | 低 | 评论、富文本留言 |
| `ProseMirror` | 不可变文档树 + 事务 | 强（接 y-prosemirror） | 较大 | 高 | 专业编辑器、协作文档 |
| `TipTap` | 基于 ProseMirror 封装 | 强 | 中 | 中 | 业务侧快速落地 |
| `Slate` | 纯 JSON 文档树 | 中（需自行接协同） | 中 | 中 | React 技术栈定制 |
| `Lexical` | 节点树 + 编辑器状态 | 中（官方协作示例） | 中 | 中 | React、追求性能 |
| `wangEditor` | JSON | 弱 | 小 | 低 | 中文场景、后台系统 |

> 选型顺序：先问「要不要协同、要不要自定义节点（@提及、表格、代码块）」，再看团队技术栈。只做评论框，`Quill` 或 `wangEditor` 足够；要长期演进、做协作文档，直接上 `ProseMirror`/`TipTap`，不要自己从 `contenteditable` 起步。

**原生 `contenteditable` 的五个硬伤：**

| 问题 | 表现 | 处理 |
| --- | --- | --- |
| DOM 结构不一致 | 回车在 Chrome 生成 `<div>`，Firefox 生成 `<br>` | 监听 `beforeinput` 自己接管，或统一归一化 |
| `execCommand` 已废弃 | `document.execCommand('bold')` 逐步移除 | 用 `document.execCommand` 只作兜底，主逻辑走 Range 操作 |
| 光标位置漂移 | 重新渲染后光标跳到开头 | 渲染前后保存/恢复 `Range`，或用编辑器框架托管 |
| 粘贴带脏样式 | Word/网页的 `<span style>` 层层嵌套 | 粘贴时白名单清洗，只保留标签语义 |
| 输入法打断 | 中文输入过程中触发 `input`，组合串被拆开 | 监听 `compositionstart/end`，组合期间不重渲染 |

**最小可用实现（粘贴清洗 + 输入法保护）：**

```ts
const editor = document.querySelector<HTMLDivElement>('[contenteditable]')!;
let composing = false;

editor.addEventListener('compositionstart', () => (composing = true));
editor.addEventListener('compositionend', () => (composing = false));

editor.addEventListener('paste', (e) => {
  e.preventDefault();
  const html = e.clipboardData?.getData('text/html');
  const text = e.clipboardData?.getData('text/plain') ?? '';
  // 有 HTML 就清洗后插入，否则按纯文本插入（避免把纯文本当 HTML 解析）
  editor.insertAdjacentHTML('insertHTML', html ? sanitize(html) : escapeHtml(text));
});

// 输入时不回写整段 HTML，只在 compositionend / 失焦时序列化
editor.addEventListener('input', () => {
  if (composing) return;
  scheduleSync();      // 防抖 300ms，避免每个字符都触发一次状态更新
});
```

**文档模型与选区：**

- 数据结构建议 `{ type: 'doc', children: [{ type: 'paragraph', children: [{ type: 'text', text: '…', marks: ['bold'] }] }] }`。所有编辑操作都是「对树的变换」，便于撤销（保存操作栈）与协同（变换可交换）。
- 选区不要存裸 `Range`：DOM 重渲染后节点引用会失效。存「路径 + 偏移」（如 `[2, 0, 5]`）或字符偏移，渲染后再映射回 `Range`。
- 撤销栈用「操作 + 反向操作」而不是整篇快照：整篇快照在长文档下内存会迅速膨胀。

**协同编辑的取舍（面试常追问）：**

| 方案 | 冲突处理 | 优点 | 缺点 |
| --- | --- | --- | --- |
| OT（Operational Transform） | 服务端变换操作序列 | 结果确定、历史成熟 | 服务端要维护状态、实现复杂 |
| CRDT（Yjs/Automerge） | 数据结构本身可合并 | 支持离线、去中心化 | 内存开销大、文档结构受限 |

工程上多用 `Yjs` + `y-prosemirror`/`y-quill`：它把「离线编辑、断线重连、多端合并」都封装好了，前端只需要把编辑器状态和 `Y.Doc` 绑定。注意协同场景必须处理**光标位置冲突**（远程光标用装饰节点绘制）和**版本快照**（历史回滚）。

**边界情况与坑：**

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 中文输入被截断 | 组合输入期间重渲染 | `compositionstart/end` 期间跳过同步 |
| 粘贴后格式全乱 | 直接插入源 HTML | 白名单清洗 + 样式内联化 |
| 粘贴带 XSS | 未过滤 `script`、`onerror` | `DOMPurify`，禁止事件属性 |
| 光标跳到开头 | 受控重渲染替换了 DOM | 渲染后恢复选区，或用 `key` 稳定节点 |
| 长文越编辑越卡 | 每次输入序列化整棵树 | 防抖 + 局部更新 + 只重渲染变化节点 |
| 图片粘贴丢失 | 只读 `text/html` | 读 `clipboardData.files` 单独上传 |
| 撤销把协同内容也撤了 | 本地栈包含远程操作 | 只把本地操作入栈，远程操作走独立历史 |
| 移动端键盘遮挡光标 | 视口缩放/固定定位 | `scrollIntoView({ block: 'nearest' })` |

**面试怎么答：** 先给「HTML 不是数据源」这个核心判断，再讲选型维度（协同、自定义节点、技术栈），然后讲 `contenteditable` 的五个硬伤与对应解法（`beforeinput`、选区保存、`composition`、粘贴清洗），最后补文档模型、撤销栈与 OT/CRDT 的取舍。

**易错点：**

- 认为 `execCommand` 还能长期使用，不知道它已被废弃。
- 把 `innerHTML` 当编辑器数据源，导致每次渲染都丢失光标。
- 忽略中文输入法的 `composition` 事件，输入过程中内容被重置。
- 协同场景用「整篇覆盖」同步，后写的人会覆盖先写的人。

## 5. 图片上传预览与前端压缩

**结论先行：** 预览的关键是**不要用 base64**：`URL.createObjectURL` 生成的是内存引用，几乎零成本，base64 会把图片体积按 1.33 倍塞进字符串并常驻内存。压缩的关键是**按「最大边 + 质量」缩放后再编码**，并且必须处理 **EXIF 方向**，否则手机竖拍的照片会横过来。

**预览方案对比：**

| 方式 | 内存/性能 | 生命周期 | 适用 |
| --- | --- | --- | --- |
| `URL.createObjectURL(file)` | 极低（仅引用） | 需手动 `revokeObjectURL` | 上传前预览首选 |
| `FileReader.readAsDataURL` | 高（base64 字符串常驻） | 随变量回收 | 需要把图片存进 localStorage/JSON 时 |
| `createImageBitmap(file)` | 中（解码为位图） | 需 `close()` 释放 | 需要像素数据做压缩/裁剪 |
| `<img src={blobUrl}>` + `decode()` | 低 | 同 objectURL | 需要确保渲染完成再取尺寸 |

**压缩方案对比：**

| 方案 | 原理 | 优点 | 缺点 |
| --- | --- | --- | --- |
| Canvas `toBlob` | 绘制到 canvas 再编码 | 兼容性好、可控质量 | 主线程解码大图会卡顿 |
| `createImageBitmap` + `OffscreenCanvas` | 在 Worker 内解码缩放 | 不阻塞主线程 | 兼容性较好但实现复杂 |
| 原生 `canvas.toDataURL('image/webp')` | 换编码格式 | 体积可再降 30% | Safari 早期不支持 webp 编码 |
| WASM（squoosh/mozjpeg） | 专业编码器 | 质量与体积最优 | 包体大、加载慢 |
| 服务端压缩 | 后端处理 | 前端零负担 | 上传流量已经产生，弱网体验差 |

**预览 + 压缩的实现：**

```ts
async function compress(file: File, maxEdge = 1600, quality = 0.8) {
  // imageOrientation: 'from-image' 会自动应用 EXIF 方向，避免手机照片横躺
  const bitmap = await createImageBitmap(file, { imageOrientation: 'from-image' });
  const scale = Math.min(1, maxEdge / Math.max(bitmap.width, bitmap.height));
  const w = Math.round(bitmap.width * scale);
  const h = Math.round(bitmap.height * scale);

  const canvas = document.createElement('canvas');
  canvas.width = w;
  canvas.height = h;
  canvas.getContext('2d')!.drawImage(bitmap, 0, 0, w, h);
  bitmap.close();                    // 及时释放位图内存

  const blob = await new Promise<Blob | null>((r) =>
    canvas.toBlob(r, 'image/jpeg', quality)
  );
  if (!blob) throw new Error('encode failed');
  return blob.size < file.size ? blob : file;   // 压缩反而变大时用原图
}

function preview(file: File) {
  const url = URL.createObjectURL(file);
  // 组件卸载或换图时必须释放，否则 Blob 常驻内存
  return { url, revoke: () => URL.revokeObjectURL(url) };
}
```

**按目标体积迭代压缩（更贴近业务）：**

```ts
async function compressToSize(file: File, targetKB = 500) {
  let quality = 0.9;
  let blob = await compress(file, 1600, quality);
  // 二分或等比降质，最多重试 4 次，避免无限循环
  for (let i = 0; i < 4 && blob.size > targetKB * 1024; i++) {
    quality = Math.max(0.4, quality - 0.15);
    blob = await compress(file, 1600, quality);
  }
  return blob;
}
```

**上传前必须做的校验：**

- **类型**：不要只信 `file.type`（可伪造），服务端要按文件头（magic number）校验；前端可用前几个字节做一次粗筛。
- **尺寸**：用 `createImageBitmap` 拿宽高，拒绝超长图（如 20000px），否则 Canvas 编码会失败或吃掉巨量内存。
- **数量与并发**：多图上传限制并发（3 到 4 个），并给每张图单独的进度与失败重试。
- **命名**：浏览器不给原始路径，只能拿到 `file.name`；服务端要重新生成存储名，避免路径穿越与重名覆盖。

**边界情况与坑：**

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 手机竖拍照片横躺 | EXIF Orientation 未应用 | `createImageBitmap(..., { imageOrientation: 'from-image' })` |
| 压缩后反而更大 | 原图已高度压缩，重新编码膨胀 | 比较体积，取更小的那个 |
| 连续换图后内存暴涨 | 没 `revokeObjectURL` | 换图/卸载时释放旧 URL |
| 大图压缩时页面卡死 | 主线程解码 + 绘制 | 降到 Worker/OffscreenCanvas，或先限制最大边 |
| 透明背景变黑 | 输出 JPEG 丢失 alpha | PNG 或 WebP，或先铺白底 |
| GIF 动图只剩第一帧 | Canvas 只取首帧 | 动图不做 Canvas 压缩，直接上传 |
| HEIC 无法预览 | 浏览器不支持该编码 | 提示用户转换，或后端转码 |
| 截图粘贴的图没有文件名 | `File` 来自剪贴板 | 生成 `paste-${Date.now()}.png` |
| 压缩后图片模糊 | 缩放质量差（多次缩放） | 只缩放一次，用高质量插值 |

**面试怎么答：** 先讲预览用 `createObjectURL` 而不是 base64（内存与体积），再讲压缩的三要素（最大边、质量、编码格式）和 EXIF 方向，然后讲按目标体积迭代压缩与 Worker 卸载主线程压力，最后补上传前校验（类型、尺寸、并发）与内存释放。

**易错点：**

- 用 base64 做预览，几十张图直接把内存打满。
- 压缩只调质量不缩尺寸，大图依然很大。
- 忘了 EXIF 方向，手机上预览和上传后都是横的。
- 只校验 `file.type`，伪造扩展名即可绕过。

## 6. Canvas 实现图片/页面水印

**结论先行：** 水印有两条路：**DOM/CSS 覆盖**（文字水印，便宜但可被删）和 **Canvas 生成水印图**（可倾斜、平铺、带 logo，成本略高）。真正的难点不是画，而是**防篡改**（用户删节点、改样式）和**不干扰交互**（`pointer-events: none`）。要强调：前端水印只能提高成本，**不能真正防截图**。

**方案对比：**

| 方案 | 实现 | 优点 | 缺点 | 适用 |
| --- | --- | --- | --- | --- |
| CSS 重复背景 | `background-image` + `repeat` | 零 JS、性能最好 | 只能纯色文字 | 后台管理系统 |
| Canvas 生成瓦片 | 画一张 tile → `toDataURL` → 设为背景 | 可倾斜、透明、带图标 | 生成时有一次性开销 | 大多数场景 |
| SVG 背景 | `data:image/svg+xml` | 矢量清晰、体积小 | 部分浏览器导出/打印兼容性一般 | 需要高清打印 |
| 服务端加水印 | 后端合成到图片 | 真正防下载 | 无法覆盖整页、成本高 | 图片版权保护 |

**Canvas 水印瓦片的实现：**

```ts
function createWatermark(text: string, opts = {}) {
  const { width = 240, height = 140, fontSize = 14, rotate = -20, color = 'rgba(0,0,0,0.12)' } = opts;
  const dpr = window.devicePixelRatio || 1;

  const canvas = document.createElement('canvas');
  canvas.width = width * dpr;
  canvas.height = height * dpr;
  const ctx = canvas.getContext('2d')!;
  ctx.scale(dpr, dpr);                 // 按 DPR 放大，避免高分屏发虚
  ctx.translate(width / 2, height / 2);
  ctx.rotate((rotate * Math.PI) / 180);
  ctx.font = `${fontSize}px sans-serif`;
  ctx.fillStyle = color;
  ctx.textAlign = 'center'; ctx.textBaseline = 'middle';
  ctx.fillText(text, 0, 0);

  return canvas.toDataURL('image/png');   // tile 越小，重复越密
}

function applyWatermark(container: HTMLElement, text: string) {
  const url = createWatermark(text);
  container.style.backgroundImage = `url(${url})`;
  container.style.backgroundRepeat = 'repeat';
  container.style.pointerEvents = 'none'; // 水印层不能挡住点击
}
```

**水印层的三种挂法：**

| 挂法 | 说明 | 注意 |
| --- | --- | --- |
| 容器背景 | 直接把 tile 设为内容容器背景 | 内容有白底会盖住水印 |
| 独立覆盖层 | 绝对定位铺满 + `pointer-events: none` | 要处理 `z-index` 与滚动容器 |
| 伪元素 | `::after { background: url(...) }` | 不可被 JS 轻易删除，但可被 CSS 覆盖 |

**防篡改（提高成本，不是绝对安全）：**

- `MutationObserver` 监听水印节点被删除/样式被改，检测到就重建。注意别监听整个 body，只观察水印节点及其 `style`、`class` 属性。
- 用 `IntersectionObserver`/定时器做二次校验（例如每 2 秒检查 `getComputedStyle(el).backgroundImage` 是否为空）。
- 容器加 `user-select: none` 防整体复制；更彻底的是把水印直接画进业务内容（如报表导出图），但要权衡遮挡。

```ts
function guardWatermark(el: HTMLElement, rebuild: () => void) {
  const mo = new MutationObserver(() => {
    const bg = getComputedStyle(el).backgroundImage;
    if (!bg || bg === 'none') rebuild();     // 被移除就重建
  });
  mo.observe(el, { attributes: true, attributeFilter: ['style', 'class'], childList: true });
  return () => mo.disconnect();              // 组件卸载时必须断开
}
```

**图片水印：先加载再画**

```ts
async function watermarkImage(file: File, text: string) {
  const bitmap = await createImageBitmap(file);
  const canvas = Object.assign(document.createElement('canvas'), {
    width: bitmap.width, height: bitmap.height,
  });
  const ctx = canvas.getContext('2d')!;
  ctx.drawImage(bitmap, 0, 0);

  const size = Math.max(14, bitmap.width * 0.03);   // 字号随图片宽度缩放
  ctx.font = `${size}px sans-serif`; ctx.fillStyle = 'rgba(255,255,255,0.35)';
  ctx.rotate((-25 * Math.PI) / 180);                // 对角线平铺
  for (let y = -bitmap.height; y < bitmap.height * 2; y += size * 6)
    for (let x = -bitmap.width; x < bitmap.width * 2; x += size * 12) ctx.fillText(text, x, y);
  bitmap.close();
  return new Promise<Blob>((r) => canvas.toBlob((b) => r(b!), 'image/jpeg', 0.9));
}
```

**边界情况与坑：**

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 高分屏水印模糊 | Canvas 没按 DPR 放大 | `canvas.width = w * dpr` 并 `ctx.scale(dpr, dpr)` |
| 水印挡住按钮点击 | 覆盖层没有 `pointer-events: none` | 加该属性，或把水印放到内容下层 |
| 滚动后水印错位 | 固定定位相对视口而非容器 | 水印挂在滚动内容容器上，随内容滚动 |
| 水印被一键删除 | 只加 DOM 节点 | `MutationObserver` 重建 + 伪元素兜底 |
| 图片水印把原图压糊 | 重复编码 JPEG | 只编码一次，质量不低于 0.9 |

**面试怎么答：** 先分「页面水印」与「图片水印」，页面水印讲 Canvas 生成瓦片 + 平铺 + `pointer-events: none` + DPR，防篡改讲 `MutationObserver` 与伪元素兜底；图片水印讲 `createImageBitmap` 先解码、按宽度缩放字号、平铺角度；最后明确水印只能提高截图成本，真正防泄漏要靠服务端与权限。

**易错点：**

- 声称前端水印能防截图，忽略 DevTools 可直接删节点。
- tile 不按 DPR 放大，高分屏上文字发虚。
- 覆盖层挡住交互，用户点不到下面的按钮。
- 只画一层水印且不做任何监测，删掉就完全失效。

## 7. 骨架屏的实现与首屏体验

**结论先行：** 骨架屏解决的是**「加载期的布局稳定 + 等待感知」**，不是「好看」。它必须满足三个条件才有价值：**结构尺寸与真实内容一致**（否则加载完会跳一下，CLS 反而更大）、**首屏骨架内联在 HTML 里**（等 JS 挂载再显示骨架，等于白屏换成灰屏）、**有延迟显示阈值**（请求 80ms 就返回时还闪一下骨架，体验更差）。

**方案对比：**

| 方案 | 实现 | 优点 | 缺点 | 适用 |
| --- | --- | --- | --- | --- |
| 手写骨架组件 | 按页面结构写占位块 | 尺寸最贴合、可控 | 页面改版要同步改 | 核心页面 |
| 组件库 Skeleton | `antd`/`Element` 的 Skeleton | 开箱即用 | 结构与真实内容常有偏差 | 通用列表、卡片 |
| 自动生成插件 | 构建期分析页面生成骨架 HTML | 省人力 | 生成结果僵硬、维护成本转移 | 多页面后台 |
| SSR 内联骨架 | 服务端直出骨架 HTML | 首屏最快、无闪烁 | 需要 SSR/预渲染 | C 端首屏 |
| 真实内容占位 | 保留容器尺寸 + `content-visibility` | 无额外 DOM | 仍然要等数据 | 长列表分块渲染 |

**核心实现：延迟显示 + 最短展示**

```tsx
function useSkeleton(loading: boolean, delay = 200, minDuration = 300) {
  const [visible, setVisible] = useState(false);
  const shownAt = useRef(0);

  useEffect(() => {
    if (!loading) {
      // 已经展示的骨架至少停留 minDuration，避免「闪一下」的割裂感
      const rest = Math.max(0, minDuration - (Date.now() - shownAt.current));
      const t = setTimeout(() => setVisible(false), rest);
      return () => clearTimeout(t);
    }
    // 200ms 内返回的请求不展示骨架，直接出内容
    const t = setTimeout(() => {
      shownAt.current = Date.now();
      setVisible(true);
    }, delay);
    return () => clearTimeout(t);
  }, [loading, delay, minDuration]);

  return visible;
}
```

这套「延迟 + 最短时长」是骨架屏体验的关键：**延迟**避免快请求的闪烁，**最短时长**避免骨架只出现一帧造成的跳动。

**尺寸必须对齐：**

```css
.skeleton-line {
  height: 16px;              /* 与正文行高一致 */
  margin-bottom: 12px;
  border-radius: 4px;
  background: linear-gradient(90deg, #f2f3f5 25%, #e9ebef 37%, #f2f3f5 63%) 0 0 / 400% 100%;
  animation: shimmer 1.4s ease infinite;
}

@keyframes shimmer {
  0% { background-position: 100% 50%; } 100% { background-position: 0 50%; }
}

@media (prefers-reduced-motion: reduce) {
  .skeleton-line { animation: none; }   /* 尊重系统的减弱动效设置 */
}
```

对齐的三个层次，从易到难：

1. **块级尺寸**：头像 40×40、标题行高 24、正文三行 16，和真实组件用同一套设计令牌（间距、圆角、字号）。
2. **数量与布局**：列表骨架默认 3 到 5 条（不要按「可能的最大条数」渲染），左右分栏与卡片间距必须复刻真实布局，只换内容不换结构。

**首屏骨架要「先于 JS」出现：**

```html
<!-- index.html：服务端或构建时直接内联首屏骨架，JS 加载后替换 -->
<div id="app">
  <div class="skeleton-page" aria-busy="true">
    <div class="skeleton-line" style="width: 40%"></div>
    <div class="skeleton-line"></div>
    <div class="skeleton-line" style="width: 70%"></div>
  </div>
</div>
```

如果骨架由 React/Vue 渲染，那么「下载 JS → 执行 → 挂载 → 发请求 → 显示骨架」这条链路里，前几步都是白屏，骨架只覆盖了最后一段。把它内联进 HTML，才能从 FCP 开始就有内容。

**骨架屏与性能指标的关系：**

- 骨架屏**不改善 LCP**：LCP 统计的是最大内容元素，骨架块本身可能被算作 LCP 元素，导致指标看起来「变好了」但用户实际等待没变。要在骨架里避免放超大色块，或给骨架加 `aria-hidden` 并接受它是过渡内容。
- 骨架屏**改善的是感知等待与 CLS**：结构稳定、无跳动，用户不会觉得页面「乱跳」。
- 无障碍：容器加 `aria-busy="true"`，加载完改为 `false`；给读屏用户提供「正在加载」的文本，骨架本身 `aria-hidden="true"`。

**边界情况与坑：**

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 加载完页面跳一下 | 骨架高度与真实内容不一致 | 用固定高度/最小高度，骨架与内容共用设计令牌 |
| 骨架只闪一帧 | 请求太快 | 200ms 延迟显示 + 300ms 最短展示 |
| 首屏仍白屏 | 骨架等 JS 挂载后才渲染 | 骨架内联进 HTML / SSR 直出 |
| 骨架屏很多但很卡 | 骨架 DOM 过重、动画过多 | 骨架控制在几十个节点内，用背景渐变而非多层 div |
| 列表骨架条数过多 | 按最大页大小渲染 | 用默认页大小或固定 3 到 5 条 |
| 切换 Tab 每次都闪骨架 | 没有缓存已加载数据 | 首次加载用骨架，之后用局部 loading |

**面试怎么答：** 先纠正「骨架屏是为了好看」，讲它的两个真实目标（布局稳定、感知等待），再讲延迟与最短时长这两个开关，然后讲尺寸对齐（设计令牌）和首屏内联（否则只覆盖最后一段），最后补 CLS/LCP 的关系与 `aria-busy`。

**易错点：**

- 骨架与真实内容尺寸不一致，加载完反而更晃。
- 没有延迟阈值，快请求时骨架闪一下。
- 用 JS 渲染骨架，白屏时间一点没减少。
- 把骨架屏当成性能优化指标，声称它能提升 LCP。

## 8. 大表格的性能优化（分页、虚拟化、冻结列）

**结论先行：** 大表格要分三层优化：**数据层**（分页/游标、服务端排序筛选，别把十万行拉到前端）、**渲染层**（行虚拟化 + 列虚拟化）、**交互层**（冻结列、列宽拖拽、多选、编辑）。其中**冻结列与虚拟化的冲突**是本题的核心难点：`position: sticky` 需要列真实存在于 DOM 中，而列虚拟化会把屏外列移出 DOM，两者必须配合「固定列常驻、中间列虚拟」的设计。

**方案对比：**

| 方案 | 数据量 | 优点 | 缺点 | 适用 |
| --- | --- | --- | --- | --- |
| 传统分页 | 任意（服务端分页） | 实现简单、定位明确、可分享 | 跨页对比困难 | 后台管理默认方案 |
| 无限滚动 | 万级 | 浏览连续 | 回到原位置难、内存增长 | 日志、信息流 |
| 全量虚拟化 | 十万级（内存允许） | 滚动流畅、可全量排序 | 首屏要拉全量数据 | 本地数据分析 |
| 服务端虚拟化 | 百万级 | 只取可视区数据 | 滚动时频繁请求、要处理占位 | 超大数据集 |

**表格库选型：**

| 库 | 虚拟化 | 冻结列 | 体积 | 说明 |
| --- | --- | --- | --- | --- |
| `AG Grid` | 行/列都支持 | 原生支持 | 大 | 功能最全，企业版收费 |
| `TanStack Table` | 头less，需配虚拟化 | 自己用 sticky 实现 | 小 | 灵活、适合自研 |
| `antd Table` | 支持 `virtual` | 支持 `fixed` | 中 | 中后台快速落地 |
| `vxe-table` | 行/列虚拟化 | 支持 | 中 | Vue 生态、表格能力强 |
| `Element Plus Table` | 需第三方虚拟滚动 | 支持 `fixed` | 中 | Vue 中后台常见 |

**冻结列的实现要点：**

```css
.table { position: relative; overflow: auto; }
.table th, .table td { box-sizing: border-box; }

/* 左固定：left 偏移需要按前面所有固定列的宽度累加 */
.col-fixed-left { position: sticky; left: 0; z-index: 2; background: #fff; }
.col-fixed-left-2 { position: sticky; left: 120px; z-index: 2; background: #fff; }

/* 右固定 */
.col-fixed-right { position: sticky; right: 0; z-index: 2; background: #fff; }

/* 阴影提示「下面还有内容」，滚动到边界时用 JS 去掉 */
.col-fixed-left.is-shadow { box-shadow: 6px 0 8px -6px rgba(0, 0, 0, 0.15); }
```

四个必须处理的问题：

1. **固定列必须不透明**：`sticky` 只是改变定位，不解决层叠。固定列背景透明时，横向滚动的内容会从它下面透出来。
2. **`left` 要累加**：两列都写 `left: 0` 会叠在一起，第二列的 `left` 等于前面固定列宽度之和；列宽可拖拽时要动态计算。
3. **`z-index` 分层**：固定列 > 普通列，表头 > 表体；表头本身也要 `sticky top: 0`，两个方向的 sticky 叠加时层级容易乱。
4. **滚动阴影**：滚动到最左/最右时要隐藏阴影，否则会误导用户「还有内容」。

**列虚拟化与固定列的配合：**

```ts
function getVisibleColumns(columns: Column[], scrollLeft: number, viewportW: number) {
  const fixedLeft = columns.filter((c) => c.fixed === 'left');
  const fixedRight = columns.filter((c) => c.fixed === 'right');
  const scrollable = columns.filter((c) => !c.fixed);

  // 固定列永远渲染；只对中间列做虚拟化，否则 sticky 元素会消失
  let acc = 0;
  const rest = scrollable.filter((c) => {
    acc += c.width;
    return acc > scrollLeft && acc - c.width < scrollLeft + viewportW;
  });
  return [...fixedLeft, ...rest, ...fixedRight];
}
```

行虚拟化可以直接复用第 1 题的思路；列虚拟化还要额外维护**列宽前缀和**，并用 `colgroup` 或固定宽度的 `div` 保证未渲染列的宽度仍然占位，否则表头与表体列会错位。

**数据层与选中状态：**

- 排序、筛选、分页一律交给服务端，前端只保留当前页数据；否则「第 3 页按金额排序」会变成对 20 条数据排序，结果完全错误。
- 多选状态用 `Set<rowId>` 保存在组件外部（store 或 ref），**跨页选择才不会丢**；「全选」要区分「选中当前页」与「选中全部筛选结果」。
- 排序/筛选变化后，选中项要按 id 重新映射，不能按索引保留。

**边界情况与坑：**

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 固定列下面透出内容 | `sticky` 元素背景透明 | 给固定列不透明背景，并置于更高 `z-index` |
| 两列固定列重叠 | `left` 偏移没累加 | 按前面固定列宽度动态计算 |
| 横向滚动时列错位 | 列虚拟化后总宽度变化 | 未渲染列用固定宽度占位 |
| 行高不一致导致滚动跳动 | 用了固定行高估算 | 动态测量 + 锚点补偿（见第 1 题） |
| 表头与表体不对齐 | 表头独立滚动容器 | 共用一个滚动容器，或用滚动同步 |
| 跨页选择丢失 | 选中状态按索引存 | 用 rowId 的 `Set`，并在数据加载后回填 |
| 排序后选中错行 | 按位置匹配选中 | 始终按主键匹配 |
| 拖拽列宽后固定列偏移失效 | `left` 是写死的 | 列宽变化后重算偏移 |
| 编辑态滚动出屏后输入丢失 | 虚拟化卸载了编辑行 | 编辑行强制渲染，或把编辑值提到外部状态 |

**面试怎么答：** 先分三层（数据、渲染、交互），强调「十万行不该拉全量」；渲染层讲行虚拟化 + 列虚拟化，重点说**固定列必须常驻、只虚拟中间列**，否则 `sticky` 失效；再讲固定列的四个细节（不透明、偏移累加、层级、阴影）；最后补跨页选中、服务端排序、编辑态与虚拟化的冲突。

**易错点：**

- 前端拉全量数据再排序筛选，数据量一大直接崩。
- 列虚拟化把固定列也移出 DOM，`sticky` 完全失效。
- 固定列背景透明，滚动时内容穿透。
- 多选按索引存，翻页或排序后选中全乱。

## 9. Schema 驱动的动态表单与表单联动

**结论先行：** Schema 驱动表单的本质是**「把表单结构、校验、联动从代码里抽成数据」**。要落地好，必须解决四件事：**字段描述**（类型、props、布局）、**值的存取**（扁平 path，避免深层对象重建）、**校验**（规则与触发时机）、**联动**（依赖图，而不是全量重算）。联动做不好，字段一多就会卡。

**方案对比：**

| 方案 | 描述方式 | 联动能力 | 上手成本 | 适用 |
| --- | --- | --- | --- | --- |
| 手写表单 | JSX/模板 | 随意但散落 | 低 | 字段少、一次性页面 |
| 组件库 Form | `Form.Item` + rules | 需手写 `shouldUpdate`/`watch` | 低 | 常规后台表单 |
| `Formily` | JSON Schema + 响应式 | 强（依赖自动收集） | 高 | 复杂联动、低代码平台 |
| `react-hook-form` + `zod` | 注册式 + schema 校验 | 中（`watch`） | 中 | React 性能敏感表单 |
| `vee-validate` + `yup` | Vue 校验库 | 中 | 低 | Vue 项目 |

**Schema 的结构：**

```json
{
  "fields": [
    { "name": "type", "type": "select", "label": "类型", "options": [
      { "label": "企业", "value": "company" }, { "label": "个人", "value": "person" }] },
    { "name": "companyName", "type": "input", "label": "企业名称", "visibleWhen": "type === 'company'",
      "rules": [{ "required": true, "message": "请填写企业名称" }] },
    { "name": "idCard", "type": "input", "label": "身份证号", "visibleWhen": "type === 'person'",
      "rules": [{ "pattern": "^\\d{17}[\\dXx]$", "message": "身份证号格式不正确" }] }
  ]
}
```

三个设计决定：

- **扁平 `name`**：`user.company.name` 用 path 读写，避免每次输入重建整棵 values 树。
- **联动用表达式 + 依赖声明**：`visibleWhen` 里的字段名即依赖，渲染器扫描后建立「字段 → 依赖节点」索引；布局与字段分离，`layout`（栅格/分组/分步）单独描述，否则 Schema 会膨胀成页面描述语言。

**递归渲染与依赖收集：**

```tsx
function SchemaForm({ schema, value, onChange }: Props) {
  const deps = useMemo(() => buildDeps(schema.fields), [schema]);   // field -> 依赖节点
  const [touched, setTouched] = useState<Record<string, boolean>>({});

  const visible = (field: Field) =>
    !field.visibleWhen || evaluate(field.visibleWhen, value);       // 沙箱内求值

  return (
    <form>
      {schema.fields.map((field) => {
        if (!visible(field)) return null;                            // 隐藏即卸载
        return (
          <Field
            key={field.name}
            field={field}
            value={get(value, field.name)}
            error={touched[field.name] ? validateField(field, value) : undefined}
            onChange={(v) => onChange(set(clone(value), field.name, v))}
            onBlur={() => setTouched((t) => ({ ...t, [field.name]: true }))}
          />
        );
      })}
    </form>
  );
}
```

**联动性能的关键：只重算受影响的字段**

```ts
// 字段 → 依赖它的节点：type 变化时只重算 visibleWhen 里引用了 type 的字段
function buildDeps(fields: Field[]) {
  const map = new Map<string, Set<string>>();
  for (const { name, visibleWhen = '' } of fields)
    for (const dep of extractIdentifiers(visibleWhen))
      (map.get(dep) ?? map.set(dep, new Set()).get(dep)!).add(name);
  return map;
}
```

如果每个字段变化都重渲染整张表单，50 个字段的表单每敲一个字都会卡。更彻底的做法是把每个 `Field` 用 `React.memo` 包起来，值通过订阅（如 `useSyncExternalStore` 或 Formily 的响应式）单独获取，父组件不随值变化重渲染。

**校验的时机与策略：**

| 时机 | 体验 | 适用 |
| --- | --- | --- |
| `onChange` 实时 | 反馈快，但用户还没输完就报错 | 格式类（手机号、邮箱）可在失焦后 |
| `onBlur` | 平衡，最常见的默认 | 大多数字段 |
| 联动校验 | 依赖字段变化时重校验 | 确认密码、起止日期 |

提交时要做「全量校验 + 定位到第一个错误 + 聚焦」，并且**隐藏字段不参与校验**（否则用户看不到错误却提交不了）。

**边界情况与坑：**

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 切换类型后旧值残留提交 | 字段被卸载但值还在 | 明确策略：卸载即清空，或保留在 `hiddenValues` 里但不提交 |
| 联动死循环 | A 依赖 B、B 又依赖 A，互相 set | 单向依赖 + 变化检测（值相同不触发） |
| 动态增减字段校验丢失 | 规则挂在已卸载组件上 | 校验由 Schema 驱动，不依赖组件实例 |
| 表达式注入 | `visibleWhen` 用 `new Function` | AST 白名单或受控解析器 |
| 数组字段（明细表）性能差 | 每行都是完整表单实例 | 行级订阅、虚拟化、只校验可见行 |

**面试怎么答：** 先讲 Schema 要解决的四个问题（结构、取值、校验、联动），再讲扁平 path 与依赖图这两个性能关键点，然后讲校验时机与隐藏字段策略，最后补联动死循环、数组字段、表达式沙箱这些真实坑。

**易错点：**

- 把联动写成「任何字段变化就重算全部」，字段一多就卡。
- 隐藏字段卸载后值仍被提交，造成脏数据。
- 用 `new Function` 执行运营配置的表达式，还认为是沙箱。
- 校验逻辑绑在组件实例上，字段一卸载规则就丢了。

## 10. 可编辑表格的实现与编辑态管理

**结论先行：** 可编辑表格的复杂度不在「能输入」，而在**编辑态的生命周期**：进入编辑、暂存草稿、校验、提交、失败回滚、焦点在单元格间流转。设计时先定三个策略：**提交粒度**（单元格/行/整表）、**触发方式**（失焦/Enter/Tab）、**冲突处理**（乐观更新 + 版本号）。这三条决定了后面所有代码结构。

**方案对比：**

| 方案 | 交互 | 优点 | 缺点 | 适用 |
| --- | --- | --- | --- | --- |
| 行内编辑 | 点单元格变输入框 | 快、上下文不丢失 | 校验与焦点管理复杂 | 批量改少量字段 |
| 弹窗/抽屉编辑 | 点行弹出表单 | 校验集中、字段多也不乱 | 打断浏览、多一步操作 | 字段多、校验重 |
| 全表可编辑（Excel 式） | 所有单元格可直接输入 | 录入效率最高 | 实现成本最高（选区、复制、撤销） | 数据录入、财务 |
| 只读 + 批量编辑模式 | 切换模式后整表可改 | 明确、可整体保存 | 模式切换有学习成本 | 配置类表格 |

**编辑态状态机：**

```
idle ─聚焦/双击→ editing ─输入→ dirty ─提交→ saving ─成功→ idle；Esc/失焦→ idle（丢弃或提交），失败→ error（保留草稿）
```

对应到数据结构：

```ts
type CellKey = `${string}:${number}`;       // rowId:field
type EditState = {
  editing: CellKey | null;
  drafts: Map<CellKey, unknown>;            // 草稿值，未提交
  errors: Map<CellKey, string>;
  saving: Set<CellKey>;
};
```

**核心实现：草稿外置 + 失焦提交**

```tsx
function EditableCell({ rowId, field, value, state, dispatch, save }: CellProps) {
  const key = `${rowId}:${field}` as CellKey;
  const isEditing = state.editing === key;
  const draft = state.drafts.get(key);
  const current = draft === undefined ? value : draft;

  if (!isEditing) {
    return <div onDoubleClick={() => dispatch({ type: 'start', key, value })}>{String(current ?? '')}</div>;
  }

  return (
    <input
      autoFocus
      value={String(current ?? '')}
      onChange={(e) => dispatch({ type: 'draft', key, value: e.target.value })}
      onBlur={() => commit(key)}
      onKeyDown={(e) => {
        // 中文输入法选词时按 Enter 不应提交
        if (e.key === 'Enter' && !e.nativeEvent.isComposing) {
          e.preventDefault(); commit(key); focusNextCell(rowId, field);  // 提交后跳到下一格
        }
        if (e.key === 'Escape') dispatch({ type: 'cancel', key });
        if (e.key === 'Tab') { e.preventDefault(); focusNextCell(rowId, field); }
      }}
    />
  );
}
```

**提交粒度：** 单元格级（失焦即 `PATCH /cell`）冲突小、失败只影响一格，但请求多；行级一致性好但要用户记得点保存；整表级可批量校验，失败回滚复杂。工程上常用**单元格即时保存 + 整表批量兜底**，并保留「未保存草稿」提示防止网络丢数据。

**批量保存：用 dirty map 而不是逐格请求**

```ts
async function saveBatch(dirty: Map<CellKey, unknown>) {
  const res = await api.batchUpdate(groupByRow(dirty));            // 按 rowId 聚合成 [{ id, patch }]
  for (const item of res.failed) markError(item.key, item.reason); // 只回滚失败格，成功保留
}
```

**虚拟化与编辑态的冲突：**

- 行虚拟化会卸载滚出可视区的行，编辑态值若只存在组件内 `useState`，一滚动就丢：必须把**草稿值提到表格级状态**（上面的 `drafts`）。
- 正在编辑的行与列要强制渲染（滚出视口也保留 DOM），否则失焦可能不触发、滚回来输入框已消失。

**键盘导航与选区：**

- `Tab` 向右、`Shift+Tab` 向左、`Enter` 向下（最后一行回车新增一行），这套是 Excel 用户的肌肉记忆。
- 方向键在非编辑态用于移动当前单元格（`tabIndex` + `focus({ preventScroll: true })`），进入编辑态后归输入框所有；`paste` 可解析 TSV 批量填充并一次性标脏。

**边界情况与坑：**

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 中文输入法回车误提交 | 选词时按 Enter 触发 `keydown` | 判断 `event.nativeEvent.isComposing` |
| 滚动后输入内容丢失 | 行虚拟化卸载了编辑行 | 草稿外置到表格状态，编辑行强制渲染 |
| 失焦提交重复请求 | `blur` 与「保存」按钮同时触发 | 提交时加 `saving` 锁，按 key 去重 |
| 保存失败后数据错乱 | 乐观更新未回滚 | 失败只回滚对应单元格并保留草稿 |
| 快速点两格输入串行 | 前一次提交未完成就切换 | 编辑切换前先 flush 当前草稿 |
| 整行校验不通过仍保存 | 只校验了当前格 | 行级保存前跑整行规则 |
| 删除行后草稿残留 | 草稿 key 未清理 | 删除行时清掉该行所有 `CellKey` |

**面试怎么答：** 先给编辑态状态机（idle/editing/dirty/saving/error），再讲三个策略选择（提交粒度、触发方式、冲突处理），然后讲草稿外置、批量保存按单元格回滚、IME 的 `isComposing`、虚拟化下编辑行常驻这几个实现要点，最后补键盘导航与复制粘贴。

**易错点：**

- 把编辑值放在单元格组件的 `useState` 里，虚拟化一滚动就丢。
- 不判断 `isComposing`，中文输入选词时回车直接提交半截内容。
- 批量保存「一条失败全部回滚」，用户几十条修改白做。
- 只校验当前单元格，整行数据仍然不合法就提交了。
