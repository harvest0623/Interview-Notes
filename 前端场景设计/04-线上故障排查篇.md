## 1. 线上白屏的排查路径

**结论先行：** 白屏不是一种故障，而是**链路上任意一环断掉后的共同表现**。排查必须从「用户侧现象」往「代码侧根因」倒推：先确认影响面与版本，再依次验证 HTML 是否到达、资源是否加载、JS 是否执行、渲染是否发生。**先止损（回滚/降级）、再定位、后修复**，是线上问题的第一原则。

**排查路径（按顺序）：**

1. **确认影响面**：全量还是灰度？单一机型、单一地区、单一网络？按 UV 看，不要只看错误数。
2. **对齐版本与时间**：白屏开始时间是否与发布记录吻合；回滚后是否恢复。若恢复，直接定性为发布引入。
3. **确认 HTML 是否到达**：`curl -I` 看状态码与 `content-type`；返回错误页说明问题在 DNS、网关或服务端。
4. **确认主文档是否完整**：`curl -s URL | head -n 50`，检查 `<!DOCTYPE html>`、挂载点、`<script src>` 是否还在，常见是网关注入或压缩中间件截断。
5. **确认资源是否加载**：Network 过滤 JS/CSS，看 404、pending、`net::ERR_*`；核对 `document.scripts.length`。
6. **确认 JS 是否执行**：Console 的第一条报错往往就是根因；`SyntaxError` 多为产物损坏或降级失败，`ReferenceError` 多为依赖缺失。
7. **确认是否渲染**：挂载点有无子节点、`body` 高度是否为 0、是否被 `display:none` 或浮层遮挡。
8. **确认运行时环境**：内核版本、WebView 版本、代理/广告 SDK 注入、弱网。

**分层判断表（先定位层，再谈修复）：**

| 层级 | 白屏特征 | 快速判断 | 典型原因 |
| --- | --- | --- | --- |
| 网络 / DNS | 一直转圈，无 HTML | `curl -I` 超时 | DNS 劫持、CDN 节点故障、运营商劫持 |
| 网关 / 服务端 | 返回 502 或空白 HTML | body 不含挂载点 | 上游超时、WAF 拦截、灰度路由配错 |
| 资源层 | HTML 有，JS 红色 404 | Network 面板 | 产物未上传、CDN 未刷新、`publicPath` 配错 |
| 执行层 | 资源 200 但页面空 | Console 有报错 | 语法不兼容、依赖循环、初始化抛错 |
| 渲染层 | 有 DOM 但不可见 | 挂载点有子节点 | CSS 高度 0、`display:none`、层级被盖 |
| 环境层 | 仅特定机型 | UA 维度分布 | 低版本内核不支持 ES2020、WebView 白名单 |

**关键命令：**

```bash
# 看状态码、响应头、是否命中 CDN
curl -sI https://example.com/ | grep -Ei 'HTTP/|content-type|age|x-cache|cache-control'

# 抓 HTML 首屏，确认挂载点与脚本是否完整
curl -s https://example.com/ | head -n 40

# 检查关键静态资源是否存在（替换成实际产物名）
curl -sI https://cdn.example.com/static/js/main.3f2a1b.js | head -n 5

# 指定解析绕过本地 DNS，对比不同 CDN 节点
curl -sI --resolve example.com:443:1.2.3.4 https://example.com/
```

**浏览器侧的关键检查：**

```js
// 在 Console 或远程调试中逐项排除
const root = document.querySelector('#root');
console.table({
    htmlLength: document.documentElement.outerHTML.length,
    hasRoot: !!root,
    rootChildren: root ? root.children.length : -1,
    scripts: document.scripts.length,
    inlineScripts: [...document.scripts].filter((s) => !s.src).length,
    bodyHeight: document.body.getBoundingClientRect().height,
});

// 加载失败或跨域无耗时的资源（transferSize、decodedBodySize 均为 0）
performance.getEntriesByType('resource')
    .filter((r) => r.transferSize === 0 && r.decodedBodySize === 0)
    .forEach((r) => console.warn('可疑资源:', r.name));
```

**验证手段：**

- 外网与办公网各 `curl` 一次，排除本地代理差异。
- 无痕窗口并禁用全部扩展复现，排除用户侧插件注入。
- DevTools 勾选 Disable cache + Slow 3G，复现弱网下的白屏时机。
- 回滚后观察 5 分钟监控曲线，确认错误率与 PV 同时恢复，而不是只看单点。
- 真机远程调试：iOS 用 Safari Web Inspector，Android 用 `chrome://inspect`。

**边界与坑：**

| 坑 | 说明 |
| --- | --- |
| 只看错误数不看 PV | JS 挂了可能连上报都发不出去，错误数反而下降 |
| 直接怀疑业务代码 | 大量白屏根因在网关、CDN、DNS，代码只是背锅 |
| 忽略「局部白屏」 | 单个懒加载 chunk 404 只影响一个模块，不是整页故障 |
| 忽视缓存 | 旧 HTML 配新 JS，哈希对不上是发布后白屏的高发原因 |
| 清理现场 | 复现前就清缓存、重发布，证据永久丢失 |

**面试怎么答：** 先讲「先止损再定位」，再按网络 → 网关 → 资源 → 执行 → 渲染 → 环境六层给顺序，每层配一个可执行动作（curl、Network、Console、DOM 检查），最后补一句「白屏率要按 UV 与机型维度监控，错误日志不是唯一信号」。

**易错点：**

- 上来就说「看 Console 报错」，但资源 404、HTML 截断这类白屏根本没有 Console 输出。
- 把白屏等同于 JS 报错，忽略「HTML 没回来」这一最常见原因。
- 不区分首屏白屏与交互后白屏，后者多为运行时异常而非加载问题。

## 2. 首屏加载慢（8s 降到 2s）的定位与优化

**结论先行：** 8s 降到 2s 不是靠堆优化手段，而是**先把 8s 拆成可归因的几段，再按 ROI 排序打掉最大的一块**。典型拆解是 DNS/连接、TTFB、内容下载、JS 解析执行、首次渲染五段；多数 To C 页面的主矛盾是**主包体积 + 串行请求 + 首屏依赖无关资源**，而移动端还叠加 CPU 解析瓶颈。

**排查路径（按顺序）：**

1. **先统一口径**：首屏是 FCP、LCP 还是业务自定义「关键内容可见」？指标必须按 p75/p95 看，平均值会掩盖长尾。
2. **拉真实用户数据（RUM）**：从 `PerformanceObserver` 或现成 SDK 取分段耗时，按机型、网络、地区分组。
3. **抓瀑布图**：看关键请求链是否串行（A 的响应里才发现 B 的地址），串行是首屏杀手。
4. **拆分段耗时**：用 Navigation Timing 把总时长拆成上面五段，确认是网络慢还是执行慢。
5. **分析包体积**：`webpack-bundle-analyzer` / `vite --profile`，列出 Top 10 模块与重复依赖。
6. **分析主线程**：Performance 面板看 JS 执行与长任务，确认解析执行占比。
7. **归因排序**：服务端 TTFB 是否可优化、资源能否并行/预加载、首屏是否加载了非首屏代码。
8. **灰度验证**：按 5% → 50% 放量，同时看性能指标与业务指标，防止优化伤转化。

**优化手段与收益对比（按投入产出排序）：**

| 手段 | 预期收益 | 成本 | 风险 |
| --- | --- | --- | --- |
| 路由级代码分割 + 首屏按需 | 主包常降 40%~60% | 低 | 拆得过细会产生大量小请求 |
| 关键资源 `preconnect` / `preload` / `modulepreload` | 省 200~500ms | 低 | 预加载过多会抢占带宽 |
| 依赖替换（lodash → lodash-es、moment → dayjs） | 省 100~300KB | 低 | 行为差异需回归 |
| 图片 WebP/AVIF + 正确尺寸 + 首屏外懒加载 | LCP 常降 30%+ | 中 | 兼容性与画质 |
| CDN + `immutable` 长缓存 + 文件指纹 | 二次访问接近秒开 | 低 | 缓存与回滚策略要配套 |
| 服务端渲染 / 预渲染 | FCP 可到 1s 内 | 高 | 运维复杂度、缓存一致性 |
| 第三方脚本延后 / 异步化 | 省 300ms~1s | 中 | 业务方可能不接受 |
| HTTP/2 或 HTTP/3 + br 压缩 | 省 10%~30% 传输 | 中 | 基础设施改造 |

**分段计时与资源优先级：**

```js
// 上报首屏分段耗时（在页面加载完成后采集）
window.addEventListener('load', () => {
    const nav = performance.getEntriesByType('navigation')[0];
    const paint = performance.getEntriesByType('paint');
    const fcp = paint.find((p) => p.name === 'first-contentful-paint');
    const segments = {
        redirect: nav.redirectEnd - nav.redirectStart,
        dns: nav.domainLookupEnd - nav.domainLookupStart,
        tcp: nav.connectEnd - nav.connectStart,
        ttfb: nav.responseStart - nav.requestStart,
        download: nav.responseEnd - nav.responseStart,
        domParse: nav.domContentLoadedEventEnd - nav.responseEnd,
        fcp: fcp ? fcp.startTime : 0,
    };
    navigator.sendBeacon('/rum', JSON.stringify(segments));
});

// 首屏关键接口提前发起，不等路由挂载完成
const critical = fetch('/api/home/feed');
```

```html
<!-- 关键资源提示：只对首屏必需资源使用 -->
<link rel="preconnect" href="https://cdn.example.com" crossorigin>
<link rel="preload" as="image" href="/hero.webp" fetchpriority="high">
<link rel="modulepreload" href="/static/js/vendor.js">
```

**验证手段：**

- 实验室数据用 Lighthouse（移动端模拟 + 4G 节流）对比优化前后 FCP/LCP/TBT。
- 真实数据用 RUM 的 p75/p95 对比，至少观察一个完整业务周期。
- 灰度分组做 A/B，确认首屏耗时下降同时跳出率、转化率不恶化。
- 用 `webpack-bundle-analyzer` 的产物快照做体积门禁，防止下次回涨。
- 弱网（Slow 3G）+ 低端机（CPU 4x 降速）复测，这是线上长尾的真实条件。

**边界与坑：**

| 坑 | 说明 |
| --- | --- |
| 只优化实验室指标 | Lighthouse 分数好看但线上 p75 没降，多为网络与机型差异 |
| 预加载滥用 | 首屏 preload 十几个资源，反而挤占关键请求带宽 |
| SSR 一上就万事大吉 | 首屏 HTML 变快，但 hydration 的 JS 没减，交互仍然卡 |
| 缓存策略与发布冲突 | 长缓存 + HTML 也缓存，会导致新版本永远拿不到 |
| 忽略 TTFB | 客户端优化到极限也补不回 1.5s 的服务端响应 |
| 只做一次优化 | 没有体积与性能门禁，两个迭代后体积回涨 |

**面试怎么答：** 先给「先量化再优化」的立场，再讲五段拆解方法和 p75 口径，然后按 ROI 说三到四个手段（代码分割、关键资源提示、图片与缓存、第三方延后），最后讲灰度验证与性能门禁，避免「优化完没有基线」。

**易错点：**

- 把首屏慢直接归因为「包太大」，不做分段就下结论。
- 用平均值汇报优化效果，掩盖低端机与弱网用户的长尾。
- 只做代码分割却不改首屏依赖，主包小了但首屏请求数暴增。
- 上线长缓存却不做文件指纹与回滚预案。

## 3. 页面卡顿与长任务排查

**结论先行：** 卡顿的本质是**主线程在单帧预算内没干完活**。60Hz 下每帧只有 16.7ms（120Hz 只有 8.3ms），超过 50ms 的任务会被浏览器记为 Long Task，期间输入、滚动、动画全部排队。定位卡顿不是「感觉哪里慢」，而是**用火焰图找到占用主线程的那几段代码**，再区分是脚本执行、样式重算、布局还是 GC。

**排查路径（按顺序）：**

1. **定义卡顿场景**：加载期卡、滚动卡、点击后卡、定时卡（周期性）、还是随机卡。不同场景的嫌疑代码完全不同。
2. **确认设备与复现条件**：只有低端机卡，说明是 CPU 瓶颈；只有大数据量卡，说明是算法或渲染量问题。
3. **Performance 面板录制**：录制 10 秒包含一次完整操作，勾选 Screenshots 与 Memory。
4. **看 Frames 轨道**：出现红色长条即掉帧，记下掉帧时刻对应的操作。
5. **看 Main 轨道**：找超过 50ms 的黄色长任务块，展开看调用栈最顶部的业务函数。
6. **看 Bottom-Up / Call Tree**：按 Self Time 排序，找出真正耗时的函数，而不是只看最外层。
7. **检查样式与布局**：Layout 次数多、`Recalculate Style` 频繁，通常是读写布局交替（layout thrashing）。
8. **检查 DOM 规模**：`document.getElementsByTagName('*').length`，上万节点时任何样式变更都会放大。
9. **检查 GC**：Minor GC 频繁说明短命对象过多，Major GC 出现即全线程停顿。
10. **检查第三方与埋点**：很多卡顿来自 SDK 的同步调用、频繁上报、深层对象克隆。

**卡顿类型与对策对照：**

| 类型 | 表现 | 常见原因 | 主要手段 |
| --- | --- | --- | --- |
| 脚本执行型 | 点击后白屏几百毫秒 | 大循环、深拷贝、复杂计算 | 时间切片、Worker、算法降复杂度 |
| 渲染型 | 滚动掉帧 | 节点过多、重排重绘、阴影滤镜 | 虚拟列表、`transform`、`content-visibility` |
| 布局抖动型 | 交互时卡一下 | 循环中读 `offsetHeight` 后写样式 | 批量读、批量写，或用 `ResizeObserver` |
| GC 型 | 周期性顿挫 | 每帧创建大量临时对象 | 复用对象、减少闭包与字符串拼接 |
| 输入阻塞型 | 输入框打字延迟 | 受控输入触发整页重渲染 | 局部状态、防抖、`useDeferredValue` |
| 第三方型 | 无业务操作也卡 | 广告/统计 SDK 定时扫描 DOM | 延后加载、隔离、限制调用 |

**定位长任务与切分：**

```js
// 采集长任务，定位到具体归因（需在页面早期注册）
new PerformanceObserver((list) => {
    for (const entry of list.getEntries()) {
        console.warn('长任务', Math.round(entry.duration), 'ms', entry.attribution);
    }
}).observe({ type: 'longtask', buffered: true });

// 时间切片：把大循环拆到多帧，保证每帧不超过 5ms
async function runInSlices(items, handler, budget = 5) {
    let i = 0;
    while (i < items.length) {
        const start = performance.now();
        while (i < items.length && performance.now() - start < budget) {
            handler(items[i++]);
        }
        await new Promise((resolve) => requestAnimationFrame(resolve));
    }
}
```

```js
// 批量读写，避免强制同步布局
// 反例：每次循环都读一次布局
for (const el of nodes) {
    el.style.width = el.offsetWidth + 10 + 'px';
}

// 正例：先集中读，再集中写
const widths = nodes.map((el) => el.offsetWidth);
nodes.forEach((el, i) => {
    el.style.width = widths[i] + 10 + 'px';
});
```

**验证手段：**

- Performance 录制前后各一次，对比 Frames 掉帧数与 Long Task 总时长。
- 观察 INP（Interaction to Next Paint），这是交互卡顿最直接的线上指标。
- DevTools 的 Rendering 面板开启 Paint Flashing 与 FPS meter，确认重绘区域是否收敛。
- 用 CPU 4x/6x 降速模拟低端机，只有在降速下仍流畅才算过关。
- 上线后看 RUM 的 INP p75 与长任务数量，避免「开发机不卡、线上卡」。

**边界与坑：**

| 坑 | 说明 |
| --- | --- |
| 只看总耗时不看调用栈 | 外层函数耗时高，真正元凶是里面反复调用的工具函数 |
| 用 `setTimeout(fn, 0)` 切片 | 定时器最小间隔被 clamp 到 4ms 以上，切片反而更慢，优先 `rAF` 或 `scheduler` |
| 把动画写成 JS 逐帧改样式 | 应交给 CSS 动画或 Web Animations，走合成线程 |
| 加 `will-change` 就以为能提速 | 滥用会创建大量合成层，显存暴涨，低端机直接崩 |
| 只优化首屏 | 长稳运行后的卡顿多来自定时器、轮询、未清理的监听器 |
| 忽略受控输入成本 | 每次按键都触发整棵表单重渲染，是后台系统最常见的卡顿 |

**面试怎么答：** 先给「帧预算 + 长任务」的定义，再讲 Performance 面板的定位顺序（Frames → Main → Bottom-Up → Layout），然后按脚本、渲染、布局抖动、GC 四类给对策，最后落到 INP 与真机降速验证，体现「能定位」而不是「会背优化清单」。

**易错点：**

- 把卡顿笼统归因为「代码写得不好」，说不出是脚本、渲染还是 GC。
- 不看调用栈的 Self Time，误判外层函数为根因。
- 用加 `debounce` 掩盖问题，实际阻塞依旧存在。
- 只在开发机上验证，忽略线上低端机与复杂 DOM。

## 4. 内存持续上涨与页面崩溃（OOM）

**结论先行：** 内存上涨分两种：**真泄漏**（对象被意外引用，GC 收不掉）与**假上涨**（缓存/池化/未触顶的堆增长，GC 后能回落）。判断标准只有一个：**强制 GC 后 `usedJSHeapSize` 是否仍持续抬升**。移动端 WebView 还有进程级上限，泄漏最终表现为整页白屏或「页面已崩溃，是否重新加载」。

**排查路径（按顺序）：**

1. **确认现象**：是长时间停留缓慢上涨，还是每次操作后台阶式上涨。
2. **建立基线**：打开页面，触发一次 GC，记录 `usedJSHeapSize` 作为基线。
3. **重复操作 N 次**：同一业务动作重复 50~100 次，每 10 次强制 GC 一次并记录。
4. **看曲线形状**：锯齿整体向上即泄漏；锯齿持平只是正常分配。
5. **抓三次快照**：基线、操作后、再操作后，用 Comparison 视图对比新增对象。
6. **筛 Detached DOM**：快照搜索 `Detached`，看是否有已卸载但被 JS 引用的节点。
7. **追引用链**：选中可疑对象看 Retainers，一路追到全局变量、闭包、事件监听或定时器。
8. **排查常见持有者**：全局缓存 Map、事件总线、未清理的 `setInterval`、`ResizeObserver`、Worker、iframe。
9. **修复后长稳验证**：30 分钟或 1000 次循环，堆曲线必须回到基线附近。

**泄漏类型对照：**

| 类型 | 典型代码 | 识别方式 | 修复 |
| --- | --- | --- | --- |
| 全局缓存无上限 | `const cache = new Map()` 只写不删 | 快照中 Map 体积随操作增长 | LRU + 容量上限 + TTL |
| 事件监听未解绑 | `window.addEventListener('resize', fn)` | Retainers 指向 `window` | `removeEventListener` 或用 `AbortController` |
| 定时器未清除 | `setInterval` 在组件卸载后仍跑 | 定时器数量持续增加 | 卸载时 `clearInterval` |
| 闭包持有大对象 | 回调里引用了整份列表数据 | Retainers 指向闭包作用域 | 只捕获必要字段，用完置空 |
| Detached DOM | 移除节点但变量仍引用 | 快照出现 Detached 节点 | 引用置空，避免缓存 DOM |
| 观察器未断开 | `ResizeObserver` 未 `disconnect` | 快照中观察器实例增长 | 卸载时 `disconnect` |
| Worker / iframe 未销毁 | 每次打开都新建 Worker | 线程与文档数递增 | `terminate()`、移除 iframe 并置空 |
| 订阅未取消 | 全局 store 订阅未退订 | 订阅者数组只增不减 | 返回并调用 unsubscribe |

**泄漏示例与修复：**

```js
// 泄漏：组件卸载后监听器仍持有组件实例与大数组
function mountPanel(data) {
    const handler = () => render(data);   // 闭包捕获整个 data
    window.addEventListener('resize', handler);
    return () => {
        // 缺失 removeEventListener，卸载后 handler 与 data 都无法回收
    };
}

// 修复：用 AbortController 一次性解绑，并只捕获必要字段
function mountPanelFixed(data) {
    const controller = new AbortController();
    const total = data.length;             // 只保留需要的值
    const handler = () => render(total);
    window.addEventListener('resize', handler, { signal: controller.signal });
    return () => controller.abort();
}
```

```js
// 采样堆内存（performance.memory 仅 Chromium 支持，需做能力判断）
function sampleHeap() {
    if (!performance.memory) return null;
    return {
        used: performance.memory.usedJSHeapSize,
        total: performance.memory.totalJSHeapSize,
        limit: performance.memory.jsHeapSizeLimit,
    };
}

// DevTools Console 中强制 GC 后取值（需开启 Console 的 GC 按钮或 CDP）
// HeapProfiler.collectGarbage → 再读 performance.memory.usedJSHeapSize
```

**验证手段：**

- 三次快照 Comparison，确认新增对象的构造函数与保留大小（Retained Size）可解释。
- 长稳脚本：Playwright 循环打开/关闭页面 100 次，记录堆曲线与 DOM 节点数。
- 真机低端机（内存 4GB 以下）连续使用 30 分钟，观察是否触发系统回收。
- 监控侧上报 `usedJSHeapSize / jsHeapSizeLimit` 比值，超过 70% 预警。
- 修复后回归同一路径，确认曲线由「持续上升」变为「锯齿持平」。

**边界与坑：**

| 坑 | 说明 |
| --- | --- |
| 只看任务管理器内存 | 浏览器进程内存包含缓存与预留，不等于 JS 堆泄漏 |
| 不强制 GC 就下结论 | 未回收的垃圾会被误判为泄漏 |
| 只抓一次快照 | 没有对比就没有新增对象，定位不到根因 |
| 用 `performance.memory` 当标准 | 非标准 API，Safari/Firefox 不支持，且值有精度限制 |
| 忽略 DOM 节点数 | 节点泄漏往往比 JS 对象泄漏更致命 |
| 修完不验证长稳 | 泄漏常是多处叠加，改一处曲线仍会上升 |

**面试怎么答：** 先区分真泄漏与假上涨，给出「强制 GC 后是否回落」的判定标准，再讲三步快照法与 Detached DOM / Retainers 的用法，最后列出高频持有者（全局缓存、监听器、定时器、观察器、Worker）与修复方式，收尾讲长稳验证与堆占比监控。

**易错点：**

- 把内存上涨一律当成泄漏，忽略了缓存与池化的合理增长。
- 只说「用 Chrome 的 Memory 面板」，讲不清 Comparison 与 Retainers 怎么用。
- 修复时只清定时器，遗漏同一组件里的事件监听与观察器。
- 不做线上堆占比监控，等用户反馈崩溃才发现。

## 5. 接口 502/504 与跨域报错的定位

**结论先行：** 这两类问题经常被混为一谈，但责任层完全不同：**502/504 是网关与上游服务的问题**（前端只能止损与反馈），**跨域报错是浏览器的同源策略表现**（服务端响应头配置或预检失败）。定位第一步永远是**看响应头与状态码的来源**，而不是先改前端代码。

**排查路径（按顺序）：**

1. **确认错误归属**：Network 面板看状态码与 `Server`、`Via`、`X-Request-Id`，判断是 CDN、网关还是应用返回。
2. **区分 502 与 504**：502 是上游返回了无效响应（进程挂了、端口不通、协议错），504 是网关等待上游超时。
3. **确认范围**：全站所有接口还是单接口；全量用户还是单环境/单地域；是否与发布或扩容时间吻合。
4. **看请求特征**：是否大 body、大 header、慢查询、批量导出；是否只有带鉴权的请求失败。
5. **看预检请求**：跨域且非简单请求时，浏览器先发 `OPTIONS`，预检失败会在 Console 报 CORS 错误而业务请求根本没发出。
6. **核对 CORS 响应头**：`Access-Control-Allow-Origin`、`-Methods`、`-Headers`、`-Credentials`、`Max-Age` 是否齐全且匹配。
7. **检查凭据模式**：带 `credentials: 'include'` 时，`Allow-Origin` 不能为 `*`，且必须 `Allow-Credentials: true`。
8. **检查协议与证书**：HTTPS 页面请求 HTTP 接口会被拦截（混合内容）；自签证书会导致请求直接失败。
9. **对齐网关配置**：`proxy_read_timeout`、`client_max_body_size`、上游健康检查与重试次数。
10. **拿 Trace ID 找后端**：用 `X-Request-Id` 查上游日志，确认是超时、崩溃还是被限流。

**现象与归因对照：**

| 现象 | 含义 | 常见原因 | 定位方式 |
| --- | --- | --- | --- |
| 502 Bad Gateway | 网关拿到无效响应 | 上游进程崩溃、端口错、协议不匹配 | 查上游存活与网关 error log |
| 504 Gateway Timeout | 网关等待超时 | 慢 SQL、下游串行调用、超时配置过短 | 查上游耗时与超时配置 |
| CORS 报错但无请求 | 预检被拒 | `OPTIONS` 未返回 2xx、缺 Allow 头 | Network 看 OPTIONS 响应 |
| CORS 报错且有请求 | 响应缺 Allow 头 | 网关覆盖了上游头、错误页无 CORS 头 | 看实际响应头 |
| `blocked by CORS policy` + 200 | 错误页被当业务响应 | 401/500 页面未带 CORS 头 | 服务端统一错误页加头 |
| Mixed Content | HTTPS 页请求 HTTP | 接口地址写死 http | Console 明确提示 |
| `net::ERR_FAILED` 无详情 | 证书或连接被中断 | 证书过期、TLS 版本不匹配 | `curl -v` 看握手 |

**关键命令：**

```bash
# 复现预检请求，重点看返回的状态码与 Allow 系列头
curl -i -X OPTIONS 'https://api.example.com/user/profile' \
    -H 'Origin: https://www.example.com' \
    -H 'Access-Control-Request-Method: PUT' \
    -H 'Access-Control-Request-Headers: content-type,authorization'

# 带凭据的实际请求，确认响应头是否回显 Origin
curl -i 'https://api.example.com/user/profile' \
    -H 'Origin: https://www.example.com' \
    -H 'Cookie: sid=abc'

# 看 TLS 握手与证书链
curl -vI https://api.example.com/ 2>&1 | grep -Ei 'SSL|TLS|subject|expire'
```

```nginx
# 网关侧统一补齐 CORS 头，注意回显 Origin 以支持多域名与凭据
location /api/ {
    if ($http_origin ~* "^https://(www\.)?example\.com$") {
        add_header Access-Control-Allow-Origin $http_origin always;
        add_header Access-Control-Allow-Credentials true always;
        add_header Access-Control-Allow-Methods 'GET,POST,PUT,DELETE,OPTIONS' always;
        add_header Access-Control-Allow-Headers 'Content-Type,Authorization,X-Request-Id' always;
        add_header Access-Control-Max-Age 86400 always;
    }
    if ($request_method = OPTIONS) {
        return 204;
    }
    proxy_read_timeout 30s;
    client_max_body_size 20m;
    proxy_pass http://app_upstream;
}
```

**验证手段：**

- `curl -v` 完整链路复现，排除浏览器缓存与插件干扰；对比浏览器 Network 的预检结果。
- 用 `X-Request-Id` 串联前端、网关、上游日志，确认超时发生在哪一跳。
- 在网关 error log 中确认 `upstream timed out` 还是 `connect() failed`。
- 跨域修复后分别验证「简单请求」与「预检请求」，以及带 Cookie 的场景。
- 让后端在错误页（401/403/500）也统一输出 CORS 头，这是最容易被忽略的一环。

**边界与坑：**

| 坑 | 说明 |
| --- | --- |
| 把 504 当成前端超时 | 前端 `axios timeout` 只是客户端放弃，服务端可能仍在执行 |
| 前端加 `Access-Control-Allow-Origin` | 这是响应头，前端设置无效，必须服务端输出 |
| `Allow-Origin: *` 配 `credentials` | 浏览器直接拒绝，必须回显具体 Origin |
| 只给 2xx 加 CORS 头 | 401/500 错误页没有头，前端只能看到 CORS 报错，掩盖真实错误 |
| 网关覆盖上游头 | 上游已加 CORS，网关 `add_header` 未用 `always` 或重复设置导致丢失 |
| 预检缓存过长 | `Max-Age` 太大时改了配置客户端仍用旧结果，排障时先禁用缓存 |

**面试怎么答：** 先把两类问题分层（网关/上游 vs 浏览器策略），再分别给排查顺序：502/504 看响应头与 Trace ID 定位到哪一跳；跨域先看预检是否发出、再看 Allow 系列头与凭据模式，最后强调「错误页也要带 CORS 头」这个高频坑。

**易错点：**

- 看到跨域报错就让前端改代码，实际问题在服务端响应头。
- 不区分「预检失败」与「实际请求失败」，两种修法完全不同。
- 忽略带 Cookie 时 `*` 不合法，配了也无效。
- 只看前端 Network 面板，不拿 Trace ID 去对齐后端日志。

## 6. 发布后大面积 JS 报错与紧急回滚

**结论先行：** 发布后大面积报错几乎都是**变更引入的兼容性问题**，高发三类：构建产物与环境不匹配（语法/API 不支持）、缓存版本错配（旧 HTML 配新 JS）、依赖或接口契约变更。处置顺序是**先止损（回滚或关开关）、再保留现场、最后定位根因**，任何先分析后止损的做法都会放大故障时长。

**排查路径（按顺序）：**

1. **判断是否与发布相关**：把错误趋势的时间轴与发布记录对齐，误差在几分钟内即可基本定性。
2. **按版本维度看**：上报里带 `appVersion` / 产物哈希，确认是「新版本专属」还是「全版本」。
3. **定级**：影响 UV 占比、核心链路（登录、支付、下单）是否不可用，决定回滚还是灰度止血。
4. **立即止损**：回滚镜像 / 切回旧版路由 / 关闭引发问题的功能开关，三选一，优先最快的那条。
5. **保留现场**：抽 10 条错误样本（堆栈、UA、URL、版本、用户操作路径），并把对应版本的 sourcemap 归档。
6. **归类报错**：`SyntaxError` 看兼容，`TypeError: Cannot read properties of undefined` 看契约，`ChunkLoadError` 看资源发布，`NetworkError` 看网关。
7. **检查版本一致性**：页面 HTML 里的版本号与运行时加载的 JS 哈希是否匹配，这是缓存错配的直接证据。
8. **检查构建目标**：`browserslist` 与 `build.target` 是否覆盖了线上最低内核；是否漏了 polyfill。
9. **检查依赖**：是否升级了大版本、是否出现同一库的两个实例（Context/单例失效）。
10. **灰度验证修复**：1% → 5% → 全量，每档观察错误率与核心接口成功率。

**报错类型与处置对照：**

| 报错特征 | 根因 | 处置 |
| --- | --- | --- |
| `SyntaxError: Unexpected token '?'` | 产物含可选链，低版本内核不支持 | 降级构建目标 + 补 polyfill，或对该机型下发旧包 |
| `ChunkLoadError` / `Loading chunk failed` | 新 HTML 引用了未发布的 chunk，或旧 HTML 引用了已删除的 chunk | 先发资源后发 HTML，保留上一版本产物，捕获后自动刷新一次 |
| `xxx is not a function` 集中爆发 | 依赖大版本升级、API 改名 | 回滚依赖或加兼容层 |
| `Cannot read properties of undefined` | 接口字段变更/为空，前端未兜底 | 回滚接口契约或加可选链与默认值 |
| `Multiple instances of xxx` | 依赖重复打包 | 统一版本、配置 `resolve.alias` 或 externals |
| 仅 iOS 报错 | Safari 对某 API 支持较晚 | 特性检测 + 降级实现，避免 UA 判断 |
| 报错量随 PV 同比上升 | 新版本全量放量 | 立即回滚，不做线上调试 |

**版本一致性检查与上报：**

```html
<!-- 页面注入版本号，运行时可比对，也便于排障 -->
<meta name="app-version" content="2026.11.03-1">
<script>
    window.__APP_VERSION__ = '2026.11.03-1';
</script>
```

```js
// 启动时校验：主包哈希与 HTML 版本是否属于同一次发布
const expected = document.querySelector('meta[name="app-version"]')?.content;
const actual = window.__BUILD_HASH__;
if (expected && actual && expected !== actual) {
    // 典型缓存错配：上报并提示刷新，不要静默继续运行
    report('version_mismatch', { expected, actual });
}

// 全局兜底：捕获未处理异常与资源加载失败
window.addEventListener('error', (e) => {
    const target = e.target;
    if (target && target.tagName === 'SCRIPT') {
        report('script_load_error', { src: target.src });
        return;
    }
    report('js_error', {
        message: e.message,
        stack: e.error && e.error.stack,
        version: window.__APP_VERSION__,
        ua: navigator.userAgent,
    });
}, true);

window.addEventListener('unhandledrejection', (e) => {
    report('promise_rejection', { reason: String(e.reason) });
});
```

**回滚与止血命令：**

```bash
# Kubernetes：回滚到上一个 ReplicaSet，并确认滚动状态
kubectl rollout undo deployment/web-frontend -n prod
kubectl rollout status deployment/web-frontend -n prod

# 回滚到指定历史版本（先查历史）
kubectl rollout history deployment/web-frontend -n prod
kubectl rollout undo deployment/web-frontend -n prod --to-revision=3

# 静态资源站点：切回上一版本目录（软链方式）
ln -sfn /srv/web/releases/20261102-2 /srv/web/current
```

**验证手段：**

- 回滚后对比错误率曲线，5 分钟内应明显下降；同时看 PV 是否恢复（防止只是上报失败）。
- 灰度机群用固定 UA/固定用户命中，验证修复版本在目标内核可用。
- 用 `npx browserslist` 打印实际覆盖的浏览器清单，确认与线上 UA 分布一致。
- 构建产物做 diff，确认没有意外新增的高版本语法（可用 `es-check` 校验）。
- 复盘时补「发布前检查项」：版本一致性、最低内核真机冒烟、上一版本产物保留。

**边界与坑：**

| 坑 | 说明 |
| --- | --- |
| 先分析后止损 | 大面积故障每多一分钟都是业务损失，回滚永远优先 |
| 回滚不彻底 | 只回滚应用不回滚配置/开关，问题依旧 |
| 删除旧产物 | 用户浏览器还持有旧 HTML，会请求已删除的 chunk |
| 只看错误数 | 错误 SDK 自身挂了会导致「错误数下降」的假象 |
| 用 UA 判断能力 | UA 可伪造且版本混乱，必须特性检测 |
| 修复不做灰度 | 二次发布再次全量翻车，故障叠加 |

**面试怎么答：** 先亮出「止损优先」的原则与三种止血手段，再按「版本一致性 → 构建目标 → 依赖 → 接口契约」给排查顺序，重点讲 `ChunkLoadError` 与低版本语法这两类高频事故，最后讲灰度验证与发布前的产物保留、真机冒烟。

**易错点：**

- 把大面积报错当成单点 bug 去修，错过回滚窗口。
- 忽略「旧 HTML + 新资源」的缓存错配，只盯着代码找原因。
- 回滚后不验证 PV，误把上报丢失当成故障恢复。
- 发布流程不保留上一版本产物，导致回滚也失败。

## 7. CDN 缓存污染与资源 404

**结论先行：** 这两件事通常是同一个根因的两面：**缓存粒度和发布顺序没设计好**。缓存污染指错误内容（404 页、错误 JSON、他人响应）被边缘节点缓存并按 key 扩散；资源 404 指 HTML 与静态资源版本不一致，或回源路径错误。核心解法是**HTML 不缓存或极短缓存、静态资源带内容指纹长缓存、先发资源后发 HTML**。

**排查路径（按顺序）：**

1. **看缓存命中信息**：响应头里的 `Age`、`X-Cache`、`CF-Cache-Status`、`Via`，判断是边缘直接返回还是回源。
2. **多节点对比**：用 `--resolve` 指定不同边缘 IP 请求同一 URL，若结果不一致即为节点间不同步或污染。
3. **确认 HTML 是否被缓存**：`Cache-Control` 是否为 `no-cache`；被缓存会导致新版本长时间不可见。
4. **确认缓存 key**：CDN 是否忽略 query string（导致带版本参数的请求命中旧对象）；是否正确处理 `Vary`。
5. **确认发布顺序**：是否先上传静态资源再更新 HTML；反过来必然出现短暂 404。
6. **确认路径与 `publicPath`**：构建时的 `base`/`publicPath` 是否与 CDN 目录一致，是否少了前导斜杠。
7. **看回源结果**：绕过 CDN 直接请求源站，若源站 404 则问题在上传，不是缓存。
8. **看 MIME 与压缩**：`content-type` 错误会导致浏览器拒绝执行（严格 MIME 检查），压缩损坏会导致解析失败。
9. **刷新与预热**：对受污染的 URL 执行 purge，再对新版本资源做预热。
10. **加固**：静态资源加内容哈希、HTML 短缓存、发布后自动刷新目录首页。

**现象与根因对照：**

| 现象 | 根因 | 处理 |
| --- | --- | --- |
| 部分用户看到旧页面，部分看到新页面 | HTML 被 CDN 缓存且未刷新 | HTML 设 `no-cache`，发布后刷新 |
| 新版本 JS 404 | 先发 HTML 后发资源 / 旧产物被删 | 调整发布顺序，保留上一版产物 |
| 同一 URL 不同地区返回不同内容 | 边缘节点缓存不同步 | purge 全节点，检查缓存 key |
| 带 `?v=xxx` 仍返回旧资源 | CDN 忽略 query 作为缓存 key | 开启 query 保留或改用路径指纹 |
| 返回 200 但内容是 404 页 | 源站软 404 + CDN 缓存错误页 | 源站返回真实 404，CDN 不缓存非 2xx |
| 图片/字体跨域被拒 | 缺 `Access-Control-Allow-Origin` | CDN 侧统一加 CORS 头 |
| 浏览器报 MIME 错误 | `content-type` 与实际不符 | 修正源站 MIME 映射 |

**缓存策略配置：**

```nginx
# HTML：不缓存，保证版本即时生效
location ~* \.html$ {
    add_header Cache-Control "no-cache, no-store, must-revalidate";
    add_header Pragma "no-cache";
    expires -1;
}

# 带内容指纹的静态资源：长缓存 + immutable
location ~* \.(js|css|woff2|png|webp|avif)$ {
    add_header Cache-Control "public, max-age=31536000, immutable";
    add_header Access-Control-Allow-Origin "*";
    try_files $uri =404;
}
```

```bash
# 手动清除缓存（Fastly 等支持 PURGE 方法的 CDN）
curl -X PURGE https://cdn.example.com/static/js/main.3f2a1b.js

# 校验刷新结果：MISS 表示已清除，HIT 表示仍在边缘
curl -sI https://cdn.example.com/index.html | grep -Ei 'age|x-cache|cache-control'

# 预热新版本资源，避免首批用户回源
for f in main.3f2a1b.js vendor.9c81de.css; do
    curl -s -o /dev/null -w "%{http_code} $f\n" "https://cdn.example.com/static/$f"
done
```

**验证手段：**

- 连续三次 `curl -sI` 同一 URL，看 `Age` 是否递增、`X-Cache` 是否 HIT，确认缓存行为符合预期。
- 用多个地域的探测节点（或 `--resolve` 不同 IP）验证一致性。
- 发布后自动巡检：抓 HTML 中所有 `script[src]` 与 `link[href]`，逐个 HEAD 请求断言 200。
- 监控侧对静态资源 404 率单独建告警，比总错误率更早发现问题。
- 发布流水线里加「资源先上传并预热成功，再切 HTML」的串行门禁。

**边界与坑：**

| 坑 | 说明 |
| --- | --- |
| 给 HTML 设长缓存 | 新版本发布后用户长期停留在旧页面，且无法回滚生效 |
| 用 query 做版本号 | 部分 CDN 忽略 query，版本号形同虚设，优先用文件名哈希 |
| 删除上一版本产物 | 旧 HTML 仍在用户浏览器中，回滚与平滑过渡都会 404 |
| 缓存错误页 | 源站软 404 返回 200，错误页被缓存后大面积扩散 |
| 只 purge 首页 | 受污染的是具体资源 URL，必须按 URL 精确清除 |
| 忽略 `Vary` | 按 `Accept-Encoding` 区分 br/gzip 时缺失会导致乱码 |

**面试怎么答：** 先讲「HTML 不缓存 + 资源指纹长缓存 + 先资源后 HTML」这三条铁律，再给排查顺序（响应头 → 多节点 → 缓存 key → 发布顺序 → 回源），最后用自动巡检与 404 率告警说明怎么防止复发。

**易错点：**

- 把资源 404 归因为「CDN 挂了」，实际是发布顺序或路径配置问题。
- 用 query 参数当版本号，却没确认 CDN 的缓存 key 规则。
- 出问题只会刷新首页，不知道要按 URL purge。
- 发布时删旧产物，导致回滚窗口内旧页面白屏。

## 8. 移动端 WebView 兼容与白屏

**结论先行：** WebView 白屏的本质是**运行环境比浏览器更不可控**：内核版本碎片化（系统 WebView、X5、WKWebView）、宿主注入 JSBridge、证书与存储受限。排查必须先拿到**内核版本与真实 UA**，再按「JS 语法 → CSS 特性 → 注入环境 → 网络证书 → 存储」五类逐一排除，而不是凭机型猜测。

**排查路径（按顺序）：**

1. **拿环境信息**：UA、`navigator.appVersion`、内核版本（Android 可通过 UA 中的 `Chrome/xx` 推断，X5 内核有 `TBS/xxx` 标识）。
2. **开启远程调试**：Android 用 `chrome://inspect`（需 App 打开 WebView 调试开关），iOS 用 Safari 的 Web Inspector。
3. **看 Console 首错**：白屏时第一条报错基本就是根因，常见 `SyntaxError`、`undefined is not an object`。
4. **验证 JS 语法**：检查产物是否含可选链、空值合并、class fields、顶层 await，低版本内核会整包解析失败。
5. **验证 CSS 特性**：`:is()`、`:where()`、`gap`（flex 场景）、`dvh`、`aspect-ratio`、`backdrop-filter` 在旧内核无效。
6. **验证注入环境**：宿主可能注入 JSBridge 并改写 `window`、`document`，或用 `Object.defineProperty` 抢占全局。
7. **验证网络与证书**：低版本 Android 不信任新根证书（如 Let's Encrypt 新链），表现为所有 HTTPS 请求失败。
8. **验证存储**：隐私模式或宿主清理导致 `localStorage` 抛异常，初始化代码未兜底即白屏。
9. **验证路由与容器**：`history.pushState` 在部分容器有兼容问题；返回键行为与 H5 路由不一致。
10. **降级验证**：用 `@supports` 与特性检测提供兜底实现，再在目标机型回归。

**兼容问题对照：**

| 能力 | 最低可用环境 | 检测方式 | 降级方案 |
| --- | --- | --- | --- |
| 可选链 `?.` | Chrome 80 / iOS 13.4 | 构建期 `es-check` | 降级构建，转译为 ES2017 |
| `flex` 的 `gap` | Chrome 84 / iOS 14.1 | `CSS.supports('gap', '1px')` | margin 负值或 `space-between` |
| `:is()` / `:where()` | Chrome 88 / iOS 14 | `CSS.supports('selector(:is(a))')` | 展开为并列选择器 |
| `dvh` 单位 | Chrome 108 / iOS 15.4 | `CSS.supports('height', '100dvh')` | `100vh` + JS 修正 |
| `ResizeObserver` | Chrome 64 / iOS 13.4 | `'ResizeObserver' in window` | `resize` 事件 + 轮询兜底 |
| `IntersectionObserver` | Chrome 51 / iOS 12.2 | 同上 | `scroll` + `getBoundingClientRect` |
| `localStorage` | 宿主允许且非隐私模式 | try/catch 探测 | 内存降级 + 提示 |

**边界与坑：**

| --- | --- |

**面试怎么答：** 先讲 WebView 环境的三类不确定性（内核、注入、证书），再给「内核版本 → 远程调试 → JS/CSS 特性 → 注入 → 证书/存储」的排查顺序，最后用 browserslist + 特性检测 + `@supports` 说明怎么系统性兼容，并强调真机矩阵与线上 UA 维度监控。

**易错点：**

- 一遇 WebView 白屏就说是「App 的问题」，不拿日志与内核信息。
- 用 UA 做能力判断，忽略特性检测才是可靠方式。
- 只在构建期降级语法，忘了 CSS 特性也需要兜底。
- 兼容修复后不做存量机型回归，问题在下一批用户中复现。

## 9. 偶现问题的复现与日志埋点

**结论先行：** 偶现问题的本质是**触发条件稀缺 + 现场信息缺失**。正确姿势不是「等它再出现」，而是**先把不可复现变成可观测**：补齐确定性上下文（版本、设备、网络、路由、操作序列、并发时序），用环形缓冲保留事发前的一段日志，用 traceId 把一次会话串起来，再用构造条件把它变成必现。

**排查路径（按顺序）：**

1. **收集用户侧信息**：精确到秒的时间、操作步骤、页面、账号、设备型号、App/浏览器版本、网络环境。
2. **按 traceId 检索日志**：查该会话的上报、接口调用、路由切换与错误，优先看事发前 30 秒。
3. **找共性条件**：是固定机型、固定版本、固定数据量，还是固定时段（定时任务、缓存过期、跨天）。
4. **提出可验证假设**：例如「并发请求乱序」「时区导致日期偏移」「浮点精度」「接口返回空数组」。
5. **补临时埋点**：在关键分支打印入参摘要、分支走向、耗时、时序编号，先定位再删。
6. **构造复现条件**：网络节流、并发压测、篡改系统时间/时区、构造边界数据、降低采样率放大问题。
7. **最小修复**：优先加防御（去重、幂等、超时、兜底值），避免大范围重构引入新风险。
8. **转长期监控**：把该场景做成固定埋点与告警，防止同类问题再次静默发生。

**偶现类型与构造方式：**

| 类型 | 典型例子 | 构造方法 | 关键埋点 |
| --- | --- | --- | --- |
| 竞态 | 快速切换筛选，旧响应覆盖新数据 | 人为打乱响应顺序、加随机延迟 | 请求 seq、发起/返回时间 |
| 时序 | 组件先渲染后拿配置导致取值 undefined | 调整初始化顺序、延迟配置下发 | 各阶段时间戳、初始化状态 |
| 缓存 | 第二次进入页面读到脏缓存 | 手动写入旧版本缓存再进入 | 缓存 key、版本、命中结果 |
| 边界数据 | 空数组/超长文本/emoji 导致渲染异常 | Mock 极端数据 | 数据长度、类型、样本哈希 |
| 环境差异 | 仅某机型、某时区、某语言出错 | 系统时间与语言切换、真机矩阵 | 时区、locale、UA、内核 |
| 并发 | 双击提交产生两笔订单 | 并发触发、去掉按钮禁用 | 点击序号、请求 id、幂等键 |
| 资源 | 弱网下 chunk 加载失败 | 网络节流 + 断点续传失败 | 资源 URL、重试次数、耗时 |
| 概率 | 抽样命中某分支才出错 | 降低采样阈值、强制命中 | 随机种子、分支标识 |

**环形缓冲与上下文采集：**

```js
// 只保留最近 N 条日志，出错时整段上报，解决「事发前的现场丢失」
class RingBuffer {
    constructor(limit = 50) {
        this.limit = limit;
        this.items = [];
    }

    push(entry) {
        this.items.push({ ts: Date.now(), ...entry });
        if (this.items.length > this.limit) this.items.shift();
    }

    dump() {
        return this.items.slice();
    }
}

const buffer = new RingBuffer(50);

function logStep(step, detail) {
    buffer.push({ step, detail, traceId: window.__TRACE_ID__ });
}

// 错误发生时带上前置日志一起上报
window.addEventListener('error', (e) => {
    navigator.sendBeacon('/log/error', JSON.stringify({
        message: e.message,
        stack: e.error && e.error.stack,
        traceId: window.__TRACE_ID__,
        version: window.__APP_VERSION__,
        route: location.pathname + location.search,
        recent: buffer.dump(),
    }));
}, true);
```

```js

async function simulateRace() {

        fetch('/api/list?filter=A'),
        fetch('/api/list?filter=B'),

    // 人为让第一个请求更晚返回
```

- 用 Playwright 并行跑 20 个上下文，配合路由拦截随机延迟，稳定复现竞态。
- DevTools 的 Network 节流与「离线」开关，验证超时、重试与降级分支。
- 用 `page.clock` 或改系统时间/时区，验证跨天、夏令时、时区偏移类问题。
- 修复后观察同 traceId 的完整链路，确认分支走向符合预期。
- 上线后看该场景的固定埋点计数，连续一周为 0 才算闭环。

**边界与坑：**

| 坑 | 说明 |
| --- | --- |
| 只加日志不加 traceId | 日志散落各处，无法还原一次完整会话 |
| 日志不打码 | 手机号、身份证进入日志，带来合规风险 |
| 采样率过高 | 偶现问题本就稀少，采样会直接丢掉样本 |
| 只修表象不加防御 | 下次换个入口同样复现 |
| 埋点不删 | 临时日志长期保留，噪声淹没真实信号还增加体积 |
| 用「无法复现」结案 | 没有转成监控项，问题会以更高成本再次出现 |

**面试怎么答：** 先给「偶现 = 条件稀缺 + 观测缺失」的判断，再讲三步：补齐上下文（traceId + 环形缓冲）、找共性条件、构造必现环境；最后强调修复要加防御性代码，并把场景沉淀成埋点与告警。

**易错点：**

- 反复让用户「再试一次」，却不补充任何埋点。
- 日志只记错误不记上下文，拿到堆栈也无法还原操作路径。
- 不考虑采样与上报丢失，误以为「没日志就没发生」。
- 修复只改一处调用，不做幂等、去重、超时等通用防御。

## 10. 第三方脚本导致的性能与故障

**结论先行：** 第三方脚本是**不可控依赖**：代码不在你的仓库、发布时间不由你决定、出错也常无堆栈。它们会阻塞渲染、抢占主线程、污染全局、淹没自家错误。治理思路是**默认异步、超时熔断、失败降级、必要时隔离到 iframe，并用 CSP/SRI 限制来源与完整性**。

**排查路径（按顺序）：**

1. **盘点全部第三方**：`script`、`link`、`iframe`、像素图、字体，逐个记录域名、用途、负责人。
2. **看加载方式**：同步脚本会阻塞解析；`async` 不保证顺序；`defer` 在 DOM 解析后按序执行。
3. **看资源瀑布**：Performance 面板按域名分组，确认第三方是否处于关键路径、是否串行。
4. **做屏蔽对照**：本地 hosts 或 DevTools 请求拦截屏蔽该域名，对比 LCP、TBT、长任务数量。
5. **查全局污染**：对比加载前后 `Object.keys(window)`，看是否覆盖原生方法或注入同名变量。
6. **查长任务归属**：`longtask` 的 `attribution` 会给出容器与来源，确认卡顿是否来自第三方。
7. **查错误来源**：错误堆栈里的资源 URL 可判断归属；第三方报错应单独归类，不混入业务错误率。
8. **制定策略**：延后到首屏后加载、加超时放弃、隔离到沙箱、或改为服务端代理自建。

**第三方类型与风险对照：**

| 类型 | 主要风险 | 治理策略 |
| --- | --- | --- |
| 统计/埋点 SDK | 主线程计算、频繁上报、深拷贝 | 异步加载、首屏后初始化、限制上报频率 |
| 客服/IM 组件 | 大体积、创建 iframe、定时轮询 | 点击后再加载、iframe 隔离 |
| 广告脚本 | 同步阻塞、改写 DOM、不可控网络 | 异步 + 超时 + 容器隔离，禁止进入关键路径 |
| 地图/图表库 | 大包、WebGL 显存 | 按需加载、动态 import、限制实例数 |
| 支付/风控 SDK | 强依赖顺序、全局回调 | 保留同步但收敛到支付页，单独监控 |
| 字体/图标 CDN | 阻塞文本渲染、跨域 | `font-display: swap`、自建或预连接 |

**加载、超时与隔离：**

```js
// 动态加载第三方脚本：超时即放弃，不阻塞首屏与主流程
function loadScript(src, timeout = 3000) {
    return new Promise((resolve, reject) => {
        const s = document.createElement('script');
        s.src = src;
        s.async = true;
        const timer = setTimeout(() => {
            s.remove();
            reject(new Error('third-party timeout: ' + src));
        }, timeout);
        s.onload = () => {
            clearTimeout(timer);
            resolve();
        };
        s.onerror = () => {
            clearTimeout(timer);
            reject(new Error('third-party failed: ' + src));
        };
        document.head.appendChild(s);
    });
}

// 失败只降级，不影响业务
loadScript('https://third.example.com/sdk.js').catch((err) => {
    report('third_party_error', { msg: err.message });
    window.__THIRD_PARTY_READY__ = false;
});
```

**验证手段：**

- 屏蔽第三方域名前后各跑一次 Lighthouse，对比 LCP、TBT 与长任务数量。
- 用 `longtask` 的 `attribution` 统计各来源贡献，量化「谁在占主线程」。
- 校验 SRI：给关键第三方脚本加 `integrity`，升级时校验失败即阻断。
- 打开 CSP Report-Only 收集一周违规，确认收紧策略不会误杀。
- 用 `Object.keys(window)` 快照对比，检查是否被注入或覆盖原生方法。

**边界与坑：**

| 坑 | 说明 |
| --- | --- |
| 第三方失败导致整页报错 | 未做 try/catch 与降级，一个 SDK 挂了全站不可用 |
| 用 `async` 又依赖执行顺序 | 异步脚本顺序不保证，业务初始化可能先于 SDK |
| 沙箱给 `allow-scripts` + `allow-same-origin` | 两者同时给等于没有沙箱，可自行移除 sandbox |
| 只做性能优化不做隔离 | DOM 污染与样式冲突无法靠异步解决 |
| 第三方错误算进业务错误率 | 告警被噪声淹没，真实故障被忽略 |
| 没有第三方清单 | 上线多年后无人知道页面上跑了哪些脚本 |

**面试怎么答：** 先把第三方定义为不可控依赖，再讲治理四件套：异步加载与超时熔断、失败降级、iframe 沙箱隔离、CSP/SRI 约束；排查上强调「屏蔽对照 + 长任务归因 + 全局污染检查」，最后说监控要按来源分开统计。

**易错点：**

- 认为「脚本加了 async 就不阻塞」，忽略其执行仍占主线程。
- 用 iframe 隔离却给足同源权限，等于白做。
- 只在上线前测一次，第三方脚本会随时变更内容。
- 把第三方报错和业务报错混在一个错误率里做告警。

## 11. 灰度发布与监控告警体系

**结论先行：** 灰度解决「**爆炸半径**」，告警解决「**发现速度**」，两者必须共用同一套指标口径，否则灰度看着正常、告警却在响。一个可用的体系包含：稳定的分流标识、分层指标门禁、自动回滚阈值、按影响面分级的告警与去噪策略。

**排查路径（按顺序）：**

1. **确认告警真实性**：先看告警对应的指标曲线与样本量，排除采集故障与口径变更。
2. **确认影响面**：按灰度批次、地域、机型、版本切片，判断是新版本还是全量问题。
3. **对齐变更**：最近是否有发布、配置变更、开关切换、依赖升级、CDN 刷新。
4. **判断是否触发门禁**：错误率、白屏率、接口成功率、LCP/INP 是否超过阈值。
5. **决定动作**：单批次异常则暂停放量；多批次异常则整体回滚；指标轻微劣化则观察。
6. **定位到层**：前端错误、接口 5xx、网关、CDN、第三方，按告警维度分流到对应负责人。
7. **保留现场**：冻结发布、保存日志与 sourcemap、记录时间线。
8. **恢复验证**：回滚或关闭开关后，确认指标回到基线且持续稳定 10 分钟以上。

**灰度策略对比：**

| 维度 | 适用场景 | 优点 | 风险 |
| --- | --- | --- | --- |
| 用户 ID 哈希 | 功能灰度、AB 实验 | 同一用户稳定命中，体验一致 | 哈希不均需校验分布 |
| 比例随机 | 快速验证 | 实现简单 | 同一用户可能忽新忽旧 |
| 白名单 | 内部先验、重点客户 | 可控、可指定 | 样本不代表线上 |
| 地域/机房 | 基础设施变更 | 隔离网络风险 | 地域差异干扰结论 |
| 设备/版本 | 客户端兼容验证 | 精准覆盖目标机型 | 版本分布可能过窄 |
| 分层灰度 | 大版本发布 | 先 1% 再 5%/20%/50% | 周期长，需要自动化门禁 |

**分流与曝光标记：**

```js
// 稳定的灰度分流：同一用户 + 同一实验始终落在同一桶
function bucketOf(uid, salt, buckets = 100) {
    let hash = 2166136261;
    const key = uid + ':' + salt;
    for (let i = 0; i < key.length; i++) {
        hash ^= key.charCodeAt(i);
        hash = Math.imul(hash, 16777619);
    }
    return Math.abs(hash) % buckets;
}

const inGray = bucketOf(userId, 'checkout-v2', 100) < 10; // 10% 灰度
report('gray_exposure', {
    experiment: 'checkout-v2',
    bucket: bucketOf(userId, 'checkout-v2', 100),
    hit: inGray,
    version: window.__APP_VERSION__,
});
```

```yaml

        rules:
            -   alert: HighJSErrorRate
```

**验证手段：**

- 灰度前用历史数据回放，确认分流比例与目标一致（卡方检验或简单分布对比）。
- 每档灰度设置观察窗口（建议 ≥ 30 分钟），指标达标才继续放量。
- 做故障注入演练：人为提高某版本错误率，验证告警在 5 分钟内触发并自动暂停放量。
- 校验告警去噪：确认同比/环比与持续时长条件能过滤发布期的正常波动。
- 复盘统计 MTTD（发现时长）与 MTTR（恢复时长），作为体系有效性的量化指标。

**边界与坑：**

| 坑 | 说明 |
| --- | --- |
| 灰度只看错误率 | 性能与业务指标（转化、下单）同样要进门禁 |
| 分流标识不稳定 | 未登录用户用随机数，刷新就换桶，体验割裂 |
| 告警阈值照搬 | 不同页面基线差异大，必须按页面/版本分别设阈值 |
| 告警无分级 | 全部 P0 会导致狼来了，最终无人响应 |
| 自动回滚无冷却 | 抖动触发回滚，反而制造二次故障 |
| 灰度样本太小 | 1% 流量在低峰期可能只有几十个 UV，结论不可信 |

**面试怎么答：** 先区分灰度与告警的职责，再讲分流维度与稳定性要求，然后给「指标门禁 + 自动回滚」的具体设计，最后强调告警要分级、持续时长去噪，并用 MTTD/MTTR 与演练验证体系有效性。

**易错点：**

- 把灰度当成「发一部分机器」，不设计用户维度的稳定分流。
- 只配错误率告警，不配白屏率、接口成功率与性能指标。
- 告警一响就回滚，不做影响面判断与灰度批次切片。
- 灰度比例与观察窗口随意设定，样本不足就下结论。

## 12. 线上问题复盘模板与应急流程

**结论先行：** 应急的核心是**缩短「发现 → 止损」的时间**，复盘的核心是**把一次事故变成一条流程约束**。没有止损纪律的团队，事故时长取决于运气；没有闭环改进的复盘，同一类问题会以不同面貌重复出现。复盘对事不对人，但改进项必须有 owner 与 deadline。

**排查路径（按顺序）：** 以下顺序同时就是应急响应流程。

1. **确认与定级**：核实告警真实性，按影响面（用户比例、核心链路、资损风险）定为 P0/P1/P2。
2. **拉起应急群**：明确一个指挥者（Incident Commander），避免多人并行操作互相覆盖。
3. **先止损**：回滚、切流、关闭开关、降级页面，四选一，5 分钟内必须有一个动作。
4. **同步信息**：固定节奏（每 15 分钟）对外通报现状、影响面、下一步，避免重复问询。
5. **并行定位**：一人查监控与日志、一人查变更记录、一人对接后端/运维，不串行等待。
6. **修复验证**：小流量验证后再全量，验证指标为错误率、白屏率、核心接口成功率。
7. **恢复确认**：指标稳定 10 分钟以上，PV 恢复，才宣布恢复并解除应急。
8. **保留证据**：冻结发布窗口，保存日志、sourcemap、监控截图、操作记录。
9. **24 小时内出复盘**：时间线、根因、影响量化、改进项，一周内跟踪闭环。

**事故分级与响应要求：**

| 级别 | 判定标准 | 首次响应 | 止损时限 | 通报范围 |
| --- | --- | --- | --- | --- |
| P0 | 核心链路不可用或资损 | 5 分钟 | 10 分钟 | 全公司 + 相关负责人 |
| P1 | 部分用户/部分地区功能异常 | 10 分钟 | 30 分钟 | 业务线 + 技术负责人 |
| P2 | 非核心功能异常、体验劣化 | 30 分钟 | 当天 | 团队内部 |
| P3 | 单点问题、可自助恢复 | 次日 | 按排期 | 团队内部 |

**边界与坑：**

| 坑 | 说明 |
| --- | --- |
| 复盘变成追责会 | 信息被隐藏，真正根因永远查不出来 |
| 只有时间线没有根因 | 记录很详细，但没有任何流程改变 |
| 改进项没有 owner | 复盘文档写完即封存，问题必然复发 |
| 影响面靠估算 | 无量化就无优先级，也无法评估止损效果 |

| 应急时多人同时操作 | 互相覆盖变更，故障被二次放大 |

**面试怎么答：** 先给应急顺序（定级 → 拉起 → 止损 → 通报 → 定位 → 验证 → 保留证据），强调「5 分钟内必须有止损动作」；再给复盘模板的四要素（时间线、根因、影响量化、带 owner 的改进项），最后用 MTTD/MTTR 与演练说明体系如何被验证。

**易错点：**

- 把复盘写成「问题描述 + 责任人」，缺少根因与流程改进。
- 应急时先定位后止损，错过最佳恢复窗口。
- 改进项只写「加强测试」，不可执行、不可验收。
- 不做演练，真实故障时才发现告警没人看、回滚脚本跑不通。
