## 1. 设计一个组件库

**结论先行：** 组件库不是「把重复组件抽出来」，而是一套**受控的设计系统**：Token 定义视觉语言，组件 API 定义使用契约，构建产物定义接入方式，文档与测试定义可维护性。先划边界（服务几个业务、是否跨框架、是否对外开放），再决定投入，否则很容易做成一个无人维护的私有仓库。

**需求拆解：**

| 维度 | 需要明确的问题 | 本方案的取值 |
| --- | --- | --- |
| 使用者 | 内部几个业务线？是否对外？ | 内部 5 条业务线，不对外 |
| 技术栈 | 单框架还是多框架？ | React 18 为主，不追求跨框架 |
| 组件范围 | 基础组件、业务组件、布局组件 | 只做基础 + 布局，业务组件留在业务包 |
| 主题能力 | 是否多品牌、暗色、密度切换 | 支持 Token 级主题与暗色 |

**核心模块：**

1. **Design Token**：颜色、字体、间距、圆角、阴影、动效曲线，全部以 CSS 变量输出，主题切换只换变量层。
2. **样式方案**：CSS Modules + CSS 变量，避免运行时开销；组件内不使用全局选择器。
3. **组件分层**：基础组件（Button/Input/Table）→ 组合组件（Form/Modal）→ 布局组件（Grid/Space），禁止跨层反向依赖。
4. **API 规范**：统一 `size`、`variant`、`disabled`、`loading` 命名；受控与非受控双模式；复合组件用 Context 传递状态。
5. **构建产物**：ESM + CJS + `.d.ts`，`sideEffects` 标记便于 tree-shaking，样式单独可引入。
6. **文档与示例**：每个组件有可运行示例、API 表、可访问性说明、设计稿链接。
7. **测试体系**：单元测试（逻辑）+ 交互测试（Testing Library）+ 视觉回归（截图比对）+ a11y 扫描。
8. **发布与治理**：Changesets 管理版本与 changelog，语义化版本，破坏性变更走 RFC 与迁移指南。

**技术选型对比：**

| 方案 | 运行时开销 | 主题能力 | 包体积 | 适用 |
| --- | --- | --- | --- | --- |
| CSS Modules + CSS 变量 | 无 | 强（换变量即可） | 小 | 推荐，主流选择 |
| CSS-in-JS（styled-components/emotion） | 有（序列化与插入样式） | 强 | 中 | 需要极致动态样式 |

| 环节 | 推荐工具 | 理由 |
| --- | --- | --- |
| 构建 | Vite library mode 或 tsup | 配置简单，产出 ESM/CJS/d.ts |
| 文档 | Storybook | 生态成熟，支持交互测试与视觉回归 |
| 版本 | Changesets | 与 monorepo 配合好，自动生成 changelog |
| 测试 | Vitest + Testing Library + Playwright | 逻辑、交互、视觉三层覆盖 |

**关键实现：**

```tsx
// 受控 + 非受控双模式：对外 API 保持一致
import styles from './Input.module.css';

interface InputProps {
    value?: string;
    defaultValue?: string;
    onChange?: (value: string) => void;
    size?: 'sm' | 'md' | 'lg';
    disabled?: boolean;
}

export function Input({ value, defaultValue, onChange, size = 'md', disabled }: InputProps) {
    const [inner, setInner] = useState(defaultValue ?? '');
    const controlled = value !== undefined;
    const current = controlled ? value : inner;

    const handleChange = (e: React.ChangeEvent<HTMLInputElement>) => {
        if (!controlled) setInner(e.target.value);
        onChange?.(e.target.value);
    };

    return (
        <input
            className={`${styles.input} ${styles[size]}`}
            value={current}
            disabled={disabled}
            onChange={handleChange}
        />
    );
}
```

**扩展点：**

- **主题插件**：业务方传入自定义 Token 覆盖，无需改组件源码。
- **表单适配层**：提供与 React Hook Form / Formik 的受控适配，避免每个业务重复写胶水代码。

**风险与边界：**

| 风险 | 说明 | 缓解 |
| --- | --- | --- |
| 版本碎片 | 各业务锁定不同版本，修复无法下沉 | 定期升级专项，提供 codemod |
| 样式污染 | 全局样式泄漏到宿主页面 | 全部 CSS Modules，禁止全局选择器 |
| 破坏性变更 | 改 API 导致大面积返工 | semver + RFC + 迁移指南 + 双版本共存期 |

**面试怎么答：** 先划边界（内部/外部、单框架/多框架、基础/业务），再讲四层结构：Token → 组件 API → 构建产物 → 文档测试；然后给样式与构建的选型理由，最后讲版本治理与破坏性变更的处理，体现「库是长期资产」的意识。

**易错点：**

- 上来就讲目录结构，不讲服务对象与边界，容易设计出过度工程。
- 只做组件不做 Token，主题定制时只能改源码。
- 用 CSS-in-JS 却不说运行时成本与 SSR 影响。

## 2. 设计一个前端监控平台

**结论先行：** 监控平台的难点不在「收集错误」，而在**成本、时效、可定位性三者的平衡**。完整链路是：SDK 采集（错误/性能/行为/白屏）→ 上报（可靠且低开销）→ 服务端符号化与聚合 → 存储与查询 → 告警与归因。设计时必须先定「采什么、采多少、留多久」，否则数据量会把预算吃光。

**需求拆解：**

| 维度 | 需要明确的问题 | 本方案的取值 |
| --- | --- | --- |
| 采集范围 | 错误、性能、接口、资源、白屏、行为 | 错误 + 性能 + 接口 + 白屏 |
| 数据量 | 日均 PV 与错误量 | 千万 PV，错误全采、性能采样 10% |
| 定位能力 | 是否需要还原到源码行 | 需要，SourceMap 私有化管理 |

**核心模块：**

1. **SDK**：错误捕获（`error`、`unhandledrejection`、框架钩子）、性能采集（PerformanceObserver）、接口采集（包装 fetch/XHR）、白屏检测、上下文（版本、路由、设备、traceId）。
2. **上报层**：优先 `sendBeacon`，降级 `fetch keepalive`；批量 + 采样 + 失败重试；页面卸载前 flush。
3. **处理层**：SourceMap 符号化、错误指纹聚合（同因归并）、指标预聚合。
4. **存储层**：明细入列式存储，指标入时序库，SourceMap 入对象存储。
5. **查询与看板**：按版本/机型/路由/错误指纹多维下钻，支持样本查看。
6. **告警**：阈值 + 同比 + 持续时长，分级通知，支持静默与值班表。
7. **SourceMap 管理**：构建时上传、按版本索引、访问鉴权、定期清理。

**技术选型对比：**

| 方案 | 优点 | 缺点 | 适用 |
| --- | --- | --- | --- |
| 自建 | 成本可控、数据自主、可深度定制 | 投入大、要维护存储与符号化 | 中大型团队 |
| Sentry 自建 | 开箱即用、符号化完善 | 资源消耗大、定制受限 | 想快速上线 |
| 云厂商 APM | 接入快、与后端链路打通 | 按量计费、数据在外部 | 中小团队 |

**关键实现：**

```js
// SDK 初始化：采样 + 上下文 + 批量上报
const config = {
    sampleRate: 1,          // 错误全采
    perfSampleRate: 0.1,    // 性能采样 10%
    flushInterval: 5000,
    maxBatch: 20,
};

const queue = [];

function report(type, payload) {
    queue.push({
        type,
        ts: Date.now(),
        traceId: window.__TRACE_ID__,
        version: window.__APP_VERSION__,
        route: location.pathname,
        ua: navigator.userAgent,
        ...payload,
    });
    if (queue.length >= config.maxBatch) flush();
}

function flush() {
    if (!queue.length) return;
    const body = JSON.stringify(queue.splice(0, config.maxBatch));
    if (navigator.sendBeacon) {
        navigator.sendBeacon('/monitor/collect', body);
    } else {
        fetch('/monitor/collect', { method: 'POST', body, keepalive: true });
    }
}

setInterval(flush, config.flushInterval);
window.addEventListener('pagehide', flush);
```

```js
// 错误指纹：把「同一根因」归并，避免告警被同一 bug 刷爆
function fingerprint(error) {
    const stack = (error && error.stack) || '';
    // 去掉行列号与内存地址，只保留函数名与文件
    const normalized = stack
        .split('\n')
        .slice(0, 5)
        .map((line) => line.replace(/:\d+:\d+/g, '').replace(/0x[0-9a-f]+/g, '0x?'))
        .join('|');
    return hash(normalized + '|' + error.message);
}
```

**扩展点：**

- **会话回放**：采集 DOM 变更与输入事件（需严格脱敏），用于复现偶现问题。
- **告警联动**：与发布系统打通，错误率超阈值自动暂停灰度。

**风险与边界：**

| 风险 | 说明 | 缓解 |
| --- | --- | --- |
| 成本失控 | 明细全量存储，费用指数增长 | 采样 + 分级存储 + TTL |
| 上报丢失 | 页面崩溃/卸载前未发送 | `sendBeacon` + `pagehide` flush |
| 隐私合规 | 采集了手机号、身份证 | 字段白名单 + 脱敏 + 合规评审 |
| SourceMap 泄露 | map 随产物公开 | `hidden-source-map` + 上传鉴权 |

**面试怎么答：** 先讲「采什么、采多少、留多久」三个前置决策，再给五段链路（SDK → 上报 → 处理 → 存储 → 查询告警），然后说清符号化与错误指纹这两个关键能力，最后讲成本控制与隐私合规，体现平台视角。

**易错点：**

- 只讲错误捕获，不讲性能、接口与白屏，平台能力不完整。
- 忽略上报可靠性，崩溃前的最后一条日志永远收不到。
- 不做指纹聚合，一个 bug 产生上万条告警。

## 3. 设计一个低代码平台

**结论先行：** 低代码的本质是**把「页面结构 + 数据 + 交互」抽象成可序列化的协议**，然后用渲染器把它变成真实页面。成败不在编辑器多炫，而在**协议是否稳定、物料是否够用、边界是否清晰**。如果场景是「少量固定模板的活动页」，自研轻量方案即可；如果是「复杂中后台 + 多人协作」，投入产出比要重新评估。

**需求拆解：**

| 维度 | 需要明确的问题 | 本方案的取值 |
| --- | --- | --- |
| 目标场景 | 活动页、中后台表单、还是任意页面 | 运营活动页 + 简单表单页 |
| 使用者 | 运营、产品还是开发 | 运营为主，开发提供物料 |
| 产出形态 | JSON 协议、可执行代码 | JSON 协议 + 运行时解释 |
| 交互复杂度 | 是否需要逻辑编排 | 支持简单条件与接口联动 |
| 安全 | 是否允许自定义 JS | 不允许，只允许声明式配置 |

**核心模块：**

1. **协议（Schema）**：页面 → 组件树 → 物料 props → 数据源 → 交互规则，全部 JSON 可序列化，带 `version` 字段。
2. **物料库**：每个物料有 `name`、`propsSchema`、默认 props、渲染组件、设计态缩略图，开发通过注册接入。
3. **编辑器**：画布（拖拽定位）、大纲树、属性面板（由 `propsSchema` 自动生成）、预览与撤销重做。
4. **渲染引擎**：递归渲染组件树，解析数据源与联动规则，做 props 校验与默认值兜底。
5. **沙箱**：设计态与运行态隔离，避免物料样式或全局变量污染编辑器。
6. **发布与版本**：每次发布生成不可变快照，支持回滚、灰度与多环境。
7. **出码（可选）**：把 Schema 编译成可维护的工程代码，用于需要二次开发的场景。

**技术选型对比：**

| 维度 | 方案 A | 方案 B | 取舍 |
| --- | --- | --- | --- |
| 引擎 | 自研轻量渲染器 | 阿里低代码引擎 lowcode-engine | 场景简单选自研，复杂编辑器选成熟引擎 |
| 画布隔离 | 同层渲染（同 DOM） | iframe 隔离 | 物料可信选同层，第三方物料选 iframe |
| 执行方式 | 解释 Schema | 出码后编译 | 运营频繁改选解释，交付给开发选出码 |
| 属性面板 | 手写 | 由 JSON Schema 生成 | 物料多时生成，物料少时手写更快 |
| 状态管理 | 局部状态 | 全局 store + 命令模式 | 需要撤销重做时用命令模式 |

```tsx
// 渲染器：递归 + 物料查找 + 未知物料兜底
const registry = new Map<string, Component>();

function RenderNode({ node }: { node: SchemaNode }) {
    const Comp = registry.get(node.component);
    if (!Comp) {
        return <div data-unknown={node.component}>未知组件：{node.component}</div>;
    }
    if (!node.children || node.children.length === 0) {
        return <Comp {...node.props} />;
    }
    return (
        <Comp {...node.props}>
            {node.children.map((child) => (
                <RenderNode key={child.id} node={child} />
            ))}
        </Comp>
    );
}
```

**扩展点：**

- **物料市场**：物料独立发版，平台按需加载，避免主包膨胀。
- **逻辑编排**：以节点图描述「请求 → 判断 → 赋值 → 跳转」，比纯 JSON 条件更可读。
- **多端出码**：同一 Schema 输出 H5/小程序，差异放在渲染适配层。
- **AI 生成**：自然语言生成 Schema 草稿，人工在编辑器里调整，注意生成结果必须走同一套校验。

**风险与边界：**

| 风险 | 说明 | 缓解 |
| --- | --- | --- |
| 复杂度失控 | 用户要求支持任意逻辑，最终做成 IDE | 明确不做复杂交互，超出的走开发 |
| 性能劣化 | 组件树过深、数据源重复请求 | 渲染缓存、请求去重、懒加载 |
| 调试困难 | 线上问题无法定位到 Schema 节点 | 渲染时注入节点 id，错误上报带路径 |
| 版本不兼容 | 协议升级导致老页面渲染错乱 | Schema 带 version，渲染器多版本共存 |
| 安全 | 允许自定义 JS 导致 XSS | 只支持声明式配置，禁用 `eval` |
| 物料生态 | 物料不够用，运营不愿用 | 先覆盖 Top 20 高频组件，再逐步扩 |

**面试怎么答：** 先给「协议 + 物料 + 编辑器 + 渲染器 + 沙箱」五件套，再强调边界：只解决高频、结构化场景，复杂逻辑交回开发；然后讲隔离与版本兼容，最后讲出码与解释执行的选择依据。

**易错点：**

- 把低代码等同于「拖拽生成页面」，忽略协议与物料体系。
- 不做沙箱，第三方物料直接污染编辑器与宿主页面。
- 允许任意 JS，埋下 XSS 与不可维护的隐患。
- 不设计版本兼容，协议一升级历史页面全挂。

## 4. 设计一个 IM 前端

**结论先行：** IM 的难点是**消息的可靠性**：不丢、不重、不乱序，且在弱网、切后台、多端登录下都成立。核心设计是把「连接」和「消息」分成两层：连接层负责可达（心跳、重连、多端），消息层负责正确（seq、ack、去重、状态机），渲染层只消费已确认顺序的消息列表。

**需求拆解：**

| 维度 | 需要明确的问题 | 本方案的取值 |
| --- | --- | --- |
| 场景 | 社交单聊、群聊、还是客服 | 单聊 + 500 人群聊 |
| 消息类型 | 文本、图片、文件、语音、撤回 | 文本 + 图片 + 文件 + 系统消息 |
| 可靠性 | 是否允许丢消息 | 不允许，必须有 ack 与补拉 |
| 规模 | 同时在线与消息量 | 万级在线，单群 500 人 |

**核心模块：**

1. **连接层**：WebSocket + 应用层心跳（30s 发一次，2 次无 pong 判定断开）+ 指数退避重连 + 前后台切换检测。
2. **消息层**：服务端分配单调递增 `seq`，客户端维护 `localMaxSeq`；发送侧本地临时 id + 状态机；接收侧按 seq 去重与补齐。
3. **本地存储**：IndexedDB 存会话与消息，按 `conversationId + seq` 建索引，限制单会话缓存条数。
4. **会话列表**：未读数、最后一条消息、置顶/免打扰，更新要幂等。
5. **渲染层**：虚拟列表 + 消息气泡 + 时间分隔 + 已读回执。
6. **富媒体**：先上传拿到 URL 再发消息，进度与失败重传独立于消息状态。

**技术选型对比：**

| 维度 | 方案 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 传输 | WebSocket | 双向、低延迟 | 需自建心跳与重连 |
| 传输 | SSE | 服务端实现简单、自动重连 | 只能服务端推，发送要走 HTTP |
| 存储 | IndexedDB | 容量大、支持索引与事务 | API 复杂，需封装 |
| 存储 | localStorage | 简单 | 容量 5MB、同步阻塞 |
| 排序 | 服务端 seq | 全局有序、易补拉 | 依赖服务端可靠分配 |
| 排序 | 客户端时间戳 | 实现简单 | 多端时钟不一致必然乱序 |

**关键实现：**

```js
// 消息状态机：发送中 → 已送达 → 已读，失败可重试
const MessageStatus = {
    SENDING: 'sending',
    SENT: 'sent',
    DELIVERED: 'delivered',
    READ: 'read',
    FAILED: 'failed',
};

// 发送：先插入本地临时消息，收到服务端 ack 后替换为真实 seq
async function sendMessage(convId, content) {
    const tempId = 'tmp_' + Date.now() + '_' + Math.random().toString(36).slice(2);
    const local = { tempId, convId, content, status: MessageStatus.SENDING, ts: Date.now() };
    store.appendLocal(local);
    try {
        const res = await api.send({ convId, content, tempId });
        store.replaceTemp(tempId, { ...res.message, status: MessageStatus.SENT });
    } catch (e) {
        store.updateStatus(tempId, MessageStatus.FAILED);
    }
}
```

```js
// 接收：按 seq 去重 + 缺口补拉，保证不乱序
const received = new Set();

async function onIncoming(msg) {
    if (received.has(msg.seq)) return;          // 重复推送直接丢弃
    received.add(msg.seq);

    const expected = store.localMaxSeq(convIdOf(msg)) + 1;
    if (msg.seq > expected) {
        // 中间有缺口，先补拉再插入，避免列表出现空洞
        const missing = await api.history({ convId: convIdOf(msg), from: expected, to: msg.seq - 1 });
        missing.forEach((m) => store.insertOrdered(m));
    }
    store.insertOrdered(msg);                    // 内部按 seq 排序
}
```

```js
// 重连：指数退避 + 抖动，避免服务端恢复瞬间被大量客户端压垮
let retry = 0;

function connect() {
    const ws = new WebSocket(WS_URL);
    ws.onopen = () => {
        retry = 0;
        syncAfterReconnect();   // 按 lastSeq 补拉断连期间的消息
    };
    ws.onclose = () => {
        const delay = Math.min(30000, 1000 * Math.pow(2, retry++)) + Math.random() * 500;
        setTimeout(connect, delay);
    };
    ws.onmessage = (e) => handle(JSON.parse(e.data));
}
```

**扩展点：**

- **已读与撤回**：都作为「控制消息」走同一套 seq 通道，避免额外接口造成状态不一致。
- **消息搜索**：本地索引 + 服务端全文检索，注意权限过滤。
- **多端同步**：以「每端 lastSeq」做增量同步，已读用最大已读 seq 合并。

**风险与边界：**

| 风险 | 说明 | 缓解 |
| --- | --- | --- |
| 消息乱序 | 客户端时间戳排序、多端并发 | 一律用服务端 seq |
| 消息重复 | 重连补拉与实时推送重叠 | 按 seq 去重集合 |
| 消息丢失 | 断连期间未补拉 | lastSeq 增量拉取 + ack |
| 弱网体验 | 发送一直转圈 | 本地先落库 + 失败重试 + 明确状态 |

**面试怎么答：** 先讲「连接层保可达、消息层保正确」的分层，再给 seq + ack + 去重 + 补拉这四件套，然后讲重连退避与本地存储，最后讲已读、撤回、多端同步如何复用同一通道，体现对可靠性的系统理解。

**易错点：**

- 用客户端时间戳排序，多端必然乱序。
- 只做重连不做补拉，断网期间的消息永久丢失。
- 心跳用 WebSocket 协议层 ping（浏览器端无法直接发），必须发应用层消息等 pong。

## 5. 设计一个可视化大屏

**结论先行：** 大屏的核心约束是**固定比例 + 长时间运行 + 数据实时**。设计要解决三件事：等比适配（不同分辨率不变形）、图表性能（几十个图不卡）、长稳（几周不崩不泄漏）。视觉炫技是表层，工程稳定性才是面试考点。

**需求拆解：**

| 维度 | 需要明确的问题 | 本方案的取值 |
| --- | --- | --- |
| 分辨率 | 固定 1920×1080 还是自适应 | 设计稿 1920×1080，等比缩放 |
| 屏幕形态 | 单屏、拼接屏、超宽屏 | 单屏 + 超宽屏兼容 |
| 图表数量 | 10 个还是 50 个 | 30 个左右，含 3 个实时刷新 |
| 数据实时性 | 秒级、分钟级 | 核心指标 5s，其余 30s |
| 运行时长 | 是否 7×24 常开 | 7×24，需要内存与连接治理 |
| 交互 | 是否需要点击下钻 | 支持点击下钻与轮播 |

**核心模块：**

1. **适配层**：以设计稿为基准做 `scale` 变换，保持宽高比，居中留黑边；超宽屏单独断点。
2. **布局层**：栅格 + 绝对定位混合，模块化卡片，支持配置化摆放。
3. **图表层**：统一封装 ECharts 实例（初始化、主题、resize、dispose），按需引入图表类型。
4. **数据层**：轮询与 WebSocket 统一成数据源接口，做请求去重、失败重试、断线降级。
5. **动效层**：数字滚动、轮播、切换动画，统一用 CSS/WAAPI，避免 JS 逐帧。
6. **性能与长稳**：图表实例回收、定时器清理、页面不可见时暂停刷新。

**技术选型对比：**

| 图表库 | 优势 | 劣势 | 适用 |
| --- | --- | --- | --- |
| ECharts | 图表全、文档好、社区大 | 包体较大，需按需引入 | 大屏首选 |
| AntV G2/G6 | 语法化、图形能力强 | 学习成本高 | 复杂关系图、定制视觉 |
| D3 | 完全自由 | 开发成本高、需自己封装 | 特殊可视化 |
| 轻量 Canvas 自绘 | 体积小、性能可控 | 功能少 | 简单仪表盘、极简场景 |

| 适配方案 | 原理 | 优点 | 缺点 |
| --- | --- | --- | --- |
| `transform: scale` | 按设计稿整体缩放 | 实现简单、完全等比 | 字体缩放可能模糊 |
| `rem` + 动态根字号 | 按宽度换算 | 布局弹性好 | 比例可能失真 |
| `vw/vh` | 视口单位 | 无需 JS | 极端比例下布局难控 |
| 响应式断点 | 多套布局 | 各分辨率都精细 | 开发量大 |

**关键实现：**

```js
// 等比缩放：以 1920×1080 为基准，居中留边，避免拉伸变形
function applyScale() {
    const designW = 1920;
    const designH = 1080;
    const scale = Math.min(window.innerWidth / designW, window.innerHeight / designH);
    const stage = document.querySelector('#stage');
    stage.style.transform = `scale(${scale})`;
    stage.style.transformOrigin = 'left top';
    stage.style.left = (window.innerWidth - designW * scale) / 2 + 'px';
    stage.style.top = (window.innerHeight - designH * scale) / 2 + 'px';
}

window.addEventListener('resize', debounce(applyScale, 200));
applyScale();
```

**面试怎么答：** 先讲三条约束（等比适配、图表性能、长稳），再给适配方案对比与选择理由，然后讲图表封装（按需引入、resize、dispose）与数据层统一，最后讲 7×24 场景下的定时刷新、可见性暂停与内存监控。

**易错点：**

- 只讲视觉与图表配置，不提实例销毁与内存泄漏。
- 用 `rem` 强行拉伸，导致宽高比失真。
- 每个图表单独建轮询，几十个定时器同时打接口。
- 忽略长时间运行，浏览器几天后必然卡死或崩溃。

## 6. 设计一个权限中台

**结论先行：** 权限中台的价值是**把「谁能做什么」从各业务系统里抽出来，变成统一的模型与鉴权服务**。设计要点：模型要能表达组织、角色、资源与数据范围；前端只做体验层过滤，**真正的安全边界永远在服务端**；权限变更要能快速失效缓存，否则会出现「已撤权但仍可操作」。

**需求拆解：**

| 维度 | 需要明确的问题 | 本方案的取值 |
| --- | --- | --- |
| 租户 | 单租户还是 SaaS 多租户 | 多租户，租户间数据隔离 |
| 授权模型 | RBAC、ABAC 还是关系型 | RBAC 为主，数据权限用规则表达式 |
| 权限粒度 | 菜单、页面、按钮、接口、数据 | 四层：菜单 / 按钮 / 接口 / 数据行 |
| 组织 | 是否按部门继承 | 支持部门树继承与岗位角色 |
| 变更时效 | 授权后多久生效 | 秒级，靠缓存失效广播 |
| 审计 | 是否需要操作留痕 | 需要，授权与鉴权均记录 |

**核心模块：**

1. **权限模型**：租户 → 用户 → 组织/岗位 → 角色 → 权限点；数据权限用「资源 + 范围 + 规则」表达。
2. **权限点管理**：统一命名（`模块.资源.动作`），由各业务注册，避免字符串散落。
3. **鉴权服务**：登录后返回用户权限集合与数据范围，提供批量校验接口。
4. **前端 SDK**：`hasPermission(code)`、`hasDataScope(resource)`、路由守卫、按钮包装组件。
5. **动态路由**：按权限过滤静态路由表，未命中的路由不注册，避免直接输入 URL 进入。
6. **缓存与失效**：权限集合按用户缓存，授权变更通过消息广播使各节点失效。
7. **审计**：记录「谁在何时授予/回收了什么权限」以及关键操作的鉴权结果。

**技术选型对比：**

| 模型 | 表达能力 | 复杂度 | 适用 |
| --- | --- | --- | --- |
| RBAC | 角色 → 权限，够用且直观 | 低 | 大多数中后台 |
| ABAC | 属性组合，细粒度动态 | 高（规则引擎） | 风控、跨维度授权 |
| ReBAC | 关系图谱（如文档协作者） | 中高 | 协同类产品、社交关系 |
| RBAC + 数据规则 | 功能用角色，数据用表达式 | 中 | 推荐，覆盖绝大多数场景 |

**关键实现：**

- 把「前端隐藏按钮」当成权限控制，忽略接口可被直接调用。

- 数据权限让前端传部门 ID，等于把越权入口交给客户端。
- 授权变更不失效缓存，用户投诉「权限改了没用」。

## 7. 设计协同编辑（OT 与 CRDT）

**结论先行：** 协同编辑的核心问题是**多人在并发编辑时如何合并操作而不破坏文档**。两条主流路线：OT（操作变换，需要中心服务端定序）与 CRDT（无冲突复制数据类型，可去中心化）。选型不是「哪个更先进」，而是看**是否需要中心服务端、是否要离线、文档规模与运维能力**。

**需求拆解：**

| 维度 | 需要明确的问题 | 本方案的取值 |
| --- | --- | --- |
| 文档类型 | 纯文本、富文本、表格、白板 | 富文本 + 评论 |
| 并发规模 | 单文档几人同时编辑 | 单文档 20 人，读多写少 |
| 离线 | 是否允许离线编辑后合并 | 需要，弱网可继续编辑 |
| 历史 | 是否需要版本回溯 | 需要，按操作日志回溯 |
| 冲突体验 | 是否允许自动合并 | 自动合并，冲突区域标记 |
| 部署 | 是否有中心服务端 | 有，但希望客户端可离线 |

**核心模块：**

1. **文档模型**：文本用字符序列或块结构；富文本建议块级模型，降低变换复杂度。
2. **操作定义**：`insert(pos, content)`、`delete(pos, len)`、`retain(n)`、`format(range, attrs)`，必须可序列化、可逆。
3. **同步协议**：客户端发送本地操作 + 版本号，服务端定序后广播；或 CRDT 直接合并。
4. **冲突解决**：OT 做变换矩阵，CRDT 用逻辑时钟与唯一 ID 保证可交换。
5. **快照与持久化**：定期生成快照 + 增量日志，避免加载时重放全部操作。
6. **Awareness**：光标、选区、在线状态，属于临时态，不进入文档历史。
7. **权限与审计**：按文档/段落控制编辑权，记录操作来源。

**技术选型对比：**

| 维度 | OT | CRDT |
| --- | --- | --- |
| 拓扑 | 需要中心服务端定序 | 可 P2P、可离线 |
| 冲突处理 | 变换函数，需针对操作类型穷举 | 数据结构自带可交换合并 |
| 实现复杂度 | 中（变换规则易错） | 高（算法与内存） |
| 离线支持 | 弱，需补操作队列 | 强，天然支持 |
| 内存占用 | 低（只存文档与操作） | 高（保留历史元数据） |
| 典型实现 | ShareDB、ot.js | Yjs、Automerge |
| 适用 | 在线文档、强中心化 | 离线优先、多端同步 |

**关键实现：**

```js
// OT 的核心：把「对方已应用的操作」变换到「自己的操作」上
// 以纯文本插入/删除为例，仅示意位置变换的关键分支
function transform(op, against) {
    if (op.type === 'insert' && against.type === 'insert') {
        // 对方在自己之前插入，自己的位置要后移
        if (against.pos <= op.pos) return { ...op, pos: op.pos + against.text.length };
        return op;
    }
    if (op.type === 'insert' && against.type === 'delete') {
        if (against.pos + against.len <= op.pos) {
            return { ...op, pos: op.pos - against.len };
        }
        if (against.pos >= op.pos) return op;
        // 删除区间覆盖了插入点，插入位置收敛到删除起点
        return { ...op, pos: against.pos };
    }
    if (op.type === 'delete' && against.type === 'insert') {
        if (against.pos >= op.pos + op.len) return op;
        if (against.pos <= op.pos) return { ...op, pos: op.pos + against.text.length };
        return { ...op, len: op.len + against.text.length };
    }
    return op;
}
```

- **版本回溯**：OT 保留操作日志可重放；CRDT 用快照 + 增量，回溯成本更高。
- **多端离线**：CRDT 天然适配，OT 需要为每个客户端维护待确认队列。
- **导出与打印**：服务端用同一份模型渲染，避免前端 DOM 与文档模型不一致。

**风险与边界：**

| 风险 | 说明 | 缓解 |
| --- | --- | --- |
| 合并错误 | OT 变换分支遗漏，文档结构损坏 | 变换规则单测 + 随机操作序列测试 |
| 内存膨胀 | CRDT 保留大量历史元数据 | 定期快照 + 压缩 + 文档拆分 |
| 离线冲突 | 长时间离线后大量操作合并 | 限制离线操作数 + 冲突提示 |
| 包体积 | 协同库较重 | 仅编辑页动态加载 |
| 服务端单点 | OT 依赖中心定序 | 服务端高可用 + 操作幂等 |
| 权限绕过 | 客户端直接改共享文档 | 服务端校验操作来源与权限 |

**面试怎么答：** 先讲「并发合并」这个核心问题，再对比 OT 与 CRDT 的拓扑、复杂度、离线能力与内存代价，然后给选型结论（有中心服务端且在线为主选 OT，离线优先选 CRDT），最后讲快照、Awareness 与权限校验。

**易错点：**

- 把 CRDT 说成「没有冲突」，它只是让冲突可自动合并，不等于没有语义冲突。
- 忽略 OT 需要中心服务端定序这一前提。
- 把光标位置存进文档历史，导致版本回溯出现幽灵光标。
- 只做合并不做快照，文档变大后加载极慢。

## 8. 设计多端统一的状态与数据层

**结论先行：** 多端统一的难点不是「共用一份代码」，而是**把平台差异收敛到一个薄适配层**，让状态与数据逻辑可以复用。正确分层是：领域模型与数据请求（复用）→ 状态管理（复用，少量平台分支）→ 平台适配（Storage、网络、导航、生命周期）→ UI（各端独立）。抽象一旦越过 UI，就会变成难维护的「万能框架」。

**需求拆解：**

| 维度 | 需要明确的问题 | 本方案的取值 |
| --- | --- | --- |
| 平台 | Web、小程序、RN、鸿蒙 | Web + 小程序 + RN |
| 状态类型 | UI 状态、业务状态、服务端缓存 | 三类分开管理 |
| 数据一致性 | 是否需要离线与乐观更新 | 需要乐观更新 + 离线队列 |
| 缓存策略 | 内存、持久化、TTL | 内存 + 持久化 + 按资源失效 |
| 包体积 | 小程序有严格限制 | 适配层与领域层按需引入 |

**核心模块：**

1. **领域层**：实体类型、DTO 转换、业务规则，纯 TS，不依赖任何平台 API。
2. **数据请求层**：统一 `request` 接口、拦截器、重试、取消、错误归一化。
3. **服务端缓存层**：按 key 缓存、失效策略、乐观更新、并发去重。
4. **UI 状态层**：只存当前界面的临时状态，不做跨页面共享。
5. **持久化层**：统一 KV 接口，Web 用 localStorage/IndexedDB，小程序用 `wx.getStorage`，RN 用 AsyncStorage。
6. **平台适配层**：Storage、网络、导航、生命周期、日志，各端各实现一份。
7. **离线队列**：写操作排队，恢复网络后按序重放，需幂等键防重复。

**技术选型对比：**

| 能力 | 方案 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 状态管理 | Zustand | 轻、无 Provider 嵌套 | 生态小于 Redux |
| 状态管理 | Redux Toolkit | 规范、DevTools 完善 | 样板代码多 |
| 状态管理 | Pinia（Vue） | 类型友好、API 简洁 | 仅 Vue |
| 服务端缓存 | TanStack Query | 缓存/失效/重试开箱即用 | 概念较多，需团队学习 |
| 服务端缓存 | SWR | 轻量、API 简单 | 复杂失效场景要自己补 |
| 服务端缓存 | 自研 | 完全贴合业务 | 重复造轮子，边界多 |

**关键实现：**

| --- | --- | --- |

| 过度抽象 | 为了复用 UI 造「万能组件」 | 只复用逻辑层，UI 各端独立 |
| 包体积 | 适配层与领域层全量引入 | 按端裁剪入口 + tree-shaking |
| 缓存不一致 | 多端缓存各自为政 | 统一 key 规范与失效事件 |
| 离线重放重复 | 网络抖动导致重复提交 | 幂等键 + 服务端去重 |
| 调试困难 | 抽象层掩盖真实错误 | 统一日志与 traceId 透传 |

**面试怎么答：** 先给四层结构（领域 → 数据 → 适配 → UI），强调「逻辑复用、UI 独立」，再讲服务端缓存与乐观更新、离线队列的幂等设计，最后讲抽象边界：适配层只暴露能力，不暴露平台对象，避免抽象泄漏。

**易错点：**

- 追求「一套代码跑所有端」，把 UI 也强行抽象，最后无法维护。
- 业务代码直接调用 `localStorage`/`wx.*`，换端时大面积改动。
- 乐观更新不做回滚，接口失败后界面与后端永久不一致。
- 离线队列没有幂等键，恢复网络后重复下单。

## 9. 设计微前端架构

**结论先行：** 微前端的本质是**用技术手段解决组织协作问题**，不是性能方案。它把一个大应用拆成可独立开发、独立部署的子应用，代价是**隔离、通信、依赖、调试复杂度全面上升**。如果团队只有一个、发布节奏一致，微前端往往是负收益；决定拆分前必须先说清「按什么维度拆」。

**需求拆解：**

| 维度 | 需要明确的问题 | 本方案的取值 |
| --- | --- | --- |
| 拆分维度 | 按团队、按业务域、按技术栈 | 按业务域 + 团队边界 |
| 技术栈 | 是否允许异构（React/Vue） | 允许，但限制在 2 种 |
| 隔离级别 | 样式、JS 全局、路由、DOM | JS 沙箱 + 样式隔离，不强求 DOM 隔离 |
| 通信 | 是否频繁跨应用调用 | 少量，走事件总线与 props |
| 路由 | 主应用统一还是子应用自管 | 主应用统一分发 |
| 部署 | 是否独立发布 | 独立发布，主应用只维护注册表 |
| 性能 | 首屏是否加载多个子应用 | 按路由懒加载，同一时刻只挂载一个 |

**核心模块：**

1. **主应用（基座）**：统一布局、登录鉴权、路由分发、子应用注册表、全局错误兜底。
2. **加载器**：按 `entry` 拉取子应用资源（HTML Entry 或 JS Entry），解析并执行。
3. **JS 沙箱**：用 Proxy 拦截 `window` 读写，记录副作用，卸载时还原；或快照式沙箱。
4. **样式隔离**：CSS Modules/前缀、Shadow DOM、或运行时给选择器加作用域。
5. **路由**：主应用按 `activeRule` 决定激活哪个子应用，子应用内部路由需与基座路由前缀对齐。
6. **通信**：初始化 props、全局事件总线、共享状态（谨慎使用），约定事件命名规范。
7. **依赖共享**：React/Vue 等基础库通过 externals 或 Module Federation 共享，避免重复加载。
8. **治理**：子应用注册表版本化、灰度发布、健康检查、加载失败的降级页面。

**技术选型对比：**

| 方案 | 隔离能力 | 接入成本 | 性能 | 适用 |
| --- | --- | --- | --- | --- |
| iframe | 最强（天然隔离） | 低 | 较差（独立上下文、通信麻烦） | 强隔离、老系统集成 |
| qiankun | JS 沙箱 + 样式隔离 | 中 | 中 | React/Vue 主流场景 |
| micro-app | Web Components + 沙箱 | 低 | 中 | 想少改子应用 |
| Module Federation | 运行时共享模块 | 中高（需构建改造） | 好 | 同技术栈、依赖共享 |
| Web Components | 组件级隔离 | 中 | 好 | 组件级复用，不是整页拆分 |

**关键实现：**


**扩展点：**

- **独立灰度**：子应用自己控制版本发布，基座注册表按用户命中不同 `entry`。
- **统一登录**：基座负责 token，子应用通过 props 或 Cookie 获取，避免各自实现。
- **跨应用通信规范**：事件名带域前缀，禁止直接读写其他子应用的 store。
- **可观测**：每个子应用独立上报，错误带 `appName`，便于归因。

**风险与边界：**

| 风险 | 说明 | 缓解 |
| --- | --- | --- |
| 样式冲突 | 全局样式与选择器互相污染 | 严格样式隔离 + 前缀约束 |
| 重复依赖 | 每个子应用各打一份 React | 共享依赖 + 版本对齐 |
| 性能下降 | 首屏加载多个包、沙箱开销 | 路由懒加载 + 预取策略 |
| 调试困难 | 跨应用调用链断裂 | 统一 traceId + 分应用日志 |
| 版本失控 | 子应用升级导致基座不兼容 | 注册表版本锁定 + 契约测试 |
| 通信耦合 | 事件总线滥用，形成隐形依赖 | 限制事件清单 + 文档化 |

**面试怎么答：** 先讲「微前端解决组织问题而非性能问题」的定位，再给拆分维度与三种隔离手段，然后对比 iframe/qiankun/Module Federation 的适用边界，最后讲通信规范、依赖共享与独立发布的治理方式。

**易错点：**

- 单团队、单发布节奏也强行上微前端，徒增复杂度。
- 认为 qiankun 能解决一切隔离，忽略 `window` 污染与样式泄漏仍需治理。
- 子应用 `unmount` 不清理副作用，切换几次后定时器成倍增长。
- 不做依赖共享，页面里同时存在两份 React，Context 完全失效。

## 10. 设计前端灰度与 AB 实验平台

**结论先行：** 灰度与 AB 实验共享同一套「分流 + 曝光 + 指标」基础设施，但目标不同：**灰度关注风险控制（指标不能变差），AB 关注因果推断（差异是否显著）**。设计的关键是**分流单元稳定、实验分层正交、曝光准确、指标口径统一**，否则结论不可信。

**需求拆解：**

| 维度 | 需要明确的问题 | 本方案的取值 |
| --- | --- | --- |
| 分流单元 | 用户、设备、会话 | 登录用户用 userId，未登录用 deviceId |
| 分流位置 | 客户端还是服务端 | 客户端 SDK 为主，关键实验服务端分流 |
| 实验规模 | 同时跑几个实验 | 几十个，需分层正交 |
| 指标类型 | 点击、转化、性能 | 业务指标 + 性能护栏指标 |
| 显著性 | 是否需要统计检验 | 需要，比例类用卡方/双样本比例检验 |
| 配置时效 | 变更多久生效 | 分钟级，SDK 定时拉取 + 本地缓存 |
| 合规 | 是否需要用户同意 | 需要，敏感场景可关闭实验 |

**核心模块：**

1. **分流 SDK**：稳定哈希分桶、实验配置缓存、默认值兜底、曝光上报。
2. **配置中心**：实验定义（层、流量、人群、变体、起止时间）、版本化发布、回滚。
3. **曝光埋点**：命中且真正展示时才曝光，避免「分配了但没看到」污染指标。
4. **指标计算**：按变体聚合，输出转化率、均值、置信区间与显著性。
5. **实验管理**：创建、审批、互斥检查、流量分配、一键停止。
6. **护栏指标（Guardrail）**：错误率、白屏率、LCP 变差则自动停止实验。
7. **SRM 检测**：校验实际分流比例是否符合预期，避免分流实现有 bug。

**技术选型对比：**

| 维度 | 客户端分流 | 服务端分流 |
| --- | --- | --- |
| 生效速度 | 快（本地计算） | 受接口与缓存影响 |
| 一致性 | 多端可能不一致 | 全局一致 |
| 适用范围 | UI/文案/交互 | 算法、接口、数据 |
| 安全性 | 配置暴露在前端 | 逻辑不暴露 |
| 实现成本 | 低 | 中（需网关与服务支持） |

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| Unleash 自建 | 开源、特性开关完善 | AB 统计能力弱 |
| LaunchDarkly 等 SaaS | 能力强、开箱即用 | 成本高、数据出境 |
| 自研 | 完全贴合业务指标 | 投入大，需统计能力 |

**关键实现：**

```js
// 分层分流：不同实验层用不同 salt，保证层间正交、层内互斥
function hashToBucket(unitId, salt, buckets = 10000) {
    let h = 2166136261;
    const key = unitId + ':' + salt;
    for (let i = 0; i < key.length; i++) {
        h ^= key.charCodeAt(i);
        h = Math.imul(h, 16777619);
    }
    return Math.abs(h) % buckets;
}

function assign(unitId, experiment) {
    const bucket = hashToBucket(unitId, experiment.layer + ':' + experiment.key);
    let acc = 0;
    for (const variant of experiment.variants) {
        acc += variant.weight;              // 权重为万分比
        if (bucket < acc) return variant.key;
    }
    return experiment.variants[0].key;      // 兜底：默认变体
}

const variant = assign(userId, {
    key: 'checkout-button',
    layer: 'ui-layer-1',
    variants: [
        { key: 'control', weight: 5000 },
        { key: 'test', weight: 5000 },
    ],
});
```

```js
// 曝光：只有真正渲染到用户面前才上报，避免「分配即曝光」的偏差
function exposeWhenVisible(el, payload) {
    const io = new IntersectionObserver((entries) => {
        if (entries[0].isIntersecting) {
            report('experiment_exposure', payload);
            io.disconnect();
        }
    });
    io.observe(el);
}
```

**扩展点：**

- **正交实验**：多层各用独立 salt，同一用户可同时进入多个不冲突实验。
- **互斥组**：同一模块的实验放入同一互斥组，避免两个变体同时改动同一按钮。
- **多因素实验**：正交数组降低样本需求，但分析复杂度上升。
- **自动决策**：护栏指标达标且显著性达成后自动放量，仍需人工确认上线。

**风险与边界：**

| 风险 | 说明 | 缓解 |
| --- | --- | --- |
| 分流不均（SRM） | 哈希实现或缓存导致比例偏差 | 每日 SRM 检测 + 告警 |
| 指标污染 | 曝光时机不对、跨实验叠加 | 分层 salt + 曝光规范化 |
| 缓存导致不生效 | 配置缓存过长 | 短 TTL + 版本号 + 强制刷新 |
| 样本不足 | 小流量实验提前下结论 | 预估样本量 + 固定实验周期 |
| 实验长期不关 | 代码里堆满分支 | 实验生命周期管理 + 到期提醒 |
| 合规风险 | 未获同意参与实验 | 敏感场景开关 + 隐私评审 |

**面试怎么答：** 先区分灰度（控风险）与 AB（求因果），再讲分流单元、分层 salt、曝光时机三个基础设计，然后给指标与显著性方法，最后讲 SRM、护栏指标与实验生命周期管理，体现「结论可信」比「功能齐全」更重要。

**易错点：**

- 用 `Math.random()` 分流，同一用户每次刷新都换组，数据完全不可用。
- 分配即曝光，用户没看到也算进实验组，指标被稀释。
- 不做 SRM 检测，分流代码有 bug 却当成实验结论。
- 实验结束后分支代码不清理，半年后无人知道某个 `if` 是干什么的。
