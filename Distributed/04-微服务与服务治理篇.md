## 1. 微服务拆分原则

**结论：拆分的目的是「缩小变更的影响范围、让团队能独立交付」，不是「让服务数量变多」。合理的边界来自业务能力与领域模型，而不是技术分层；拆错方向的微服务，比单体更难维护。**

**四条可落地的拆分依据：**

| 依据 | 含义 | 落地方法 |
| --- | --- | --- |
| 业务能力（Business Capability） | 一个服务对应一项完整业务能力 | 按「订单、库存、支付、履约」切，而不是按「Controller、Service、DAO」切 |
| DDD 限界上下文 | 同一个上下文内的模型、术语、事务放在一起 | 找出聚合根（订单、商品），聚合根边界即服务边界 |
| AKF 扩展原则 | X 轴水平复制、Y 轴功能拆分、Z 轴数据分片 | 先做 X 轴无状态复制，扛不住再拆 Y 轴，最后才分库分表 |
| 康威定律 | 系统结构反映组织沟通结构 | 一个服务对应一个可独立负责的团队，跨团队强耦合就是拆分信号 |

**常见拆分维度对比：**

| 维度 | 示例 | 优点 | 风险 |
| --- | --- | --- | --- |
| 按业务能力 | 交易、库存、营销 | 边界稳定，团队自治 | 需要清晰的领域模型 |
| 按技术分层 | 接入层、逻辑层、数据层 | 初期改造快 | 一次业务变更横跨三层，等于没拆 |
| 按变更频率 | 高频变动的促销独立 | 隔离变更影响 | 边界随业务漂移 |
| 按读写 | 命令侧与查询侧分离（CQRS） | 读写各自优化 | 最终一致，复杂度上升 |
| 按团队 | 一个团队一个服务 | 责任清晰 | 组织调整会撕裂系统 |

**必须避免的三个反模式：**

1. 分布式单体：服务拆开了，但每次需求仍要同时改 5 个服务、一起发版，耦合只是从代码变成了网络调用。
2. 贫血领域模型：每个服务只有一张表的 CRUD，业务逻辑全堆在上层编排服务，领域能力被掏空。
3. 共享数据库：多个服务直连同一个库同一批表，数据库成为事实上的耦合点，拆分失去意义。

**代码示例（Java，用 ArchUnit 把拆分规则固化成测试，4 空格缩进）：**

```java
@AnalyzeClasses(packages = "com.example.order")
public class ModuleBoundaryTest {

    // 规则一：订单域不得直接依赖库存域的内部实现，只能通过防腐层接口
    @ArchTest
    static final ArchRule order_must_not_touch_inventory_internal =
        noClasses()
            .that().resideInAPackage("com.example.order..")
            .should().dependOnClassesThat()
            .resideInAPackage("com.example.inventory.internal..");

    // 规则二：领域层不得依赖 Spring Web，保证领域模型可独立测试
    @ArchTest
    static final ArchRule domain_must_not_depend_on_web =
        noClasses()
            .that().resideInAPackage("com.example.order.domain..")
            .should().dependOnClassesThat()
            .resideInAnyPackage("org.springframework.web..");

    // 规则三：跨域只能通过 api 包（对外契约）通信
    @ArchTest
    static final ArchRule cross_domain_only_via_api =
        classes()
            .that().resideInAPackage("com.example.order..")
            .should().onlyDependOnClassesThat()
            .resideInAnyPackage("com.example.order..", "com.example.inventory.api..");
}
```

**拆分后的数据一致性方案（必须提前想清楚）：**

```text
    同一聚合根内的强一致   → 留在同一个服务、同一个库、同一个本地事务
    跨服务的最终一致       → 本地消息表 / 事务消息 + 消费幂等 + 对账补偿
    跨服务的实时查询       → 同步调用 + 缓存，接受级联失败
    跨服务的统计与分析     → 事件流（CDC/binlog）到数仓，禁止直连业务库
```

**故障场景与兜底：**

- 拆得过细导致调用链过长：一次下单串行调用 8 个服务，P99 累积超时。合并过细粒度的服务，或改为并行调用 + 聚合层。
- 拆分后跨服务事务丢失：原本一个本地事务变成 3 个服务，必须补上本地消息表与补偿任务，否则出现「扣了库存没生成订单」。
- 共享库无法拆：先做「逻辑隔离」（独立 schema、禁止跨域 join），再逐步迁数据，不要一步到位物理分库。
- 团队与边界不匹配：一个服务被两个团队同时高频修改，说明边界切在了业务能力中间，应按团队职责重新划界。

**面试怎么答：** 先纠正「微服务＝拆得细」的误解，明确目的是隔离变更与团队自治；再给四条依据（业务能力、DDD 限界上下文、AKF、康威定律），每条配一个具体切法；然后讲三个反模式，尤其是分布式单体和共享数据库，这两个最能体现是否真做过拆分；最后讲拆分后的一致性方案，按「同聚合根用本地事务、跨服务用最终一致」分层回答。

**易错点：**

- 按技术分层拆（Controller 一个服务、DAO 一个服务）：每次需求都要全链路改，是最典型的伪微服务。
- 只拆应用不拆数据：共享库让服务之间仍然强耦合，数据库变更依然要同步发布。
- 忽略团队规模：3 个人维护 20 个服务，运维成本直接压垮交付。
- 用「一个表一个服务」做拆分：贫血领域模型，业务逻辑无处安放。
- 拆分时不设计幂等与补偿：跨服务写操作一旦失败就没有回滚路径。

## 2. 服务注册与发现

**结论：注册中心解决的是「实例地址会变」这个问题：服务启动时把自己注册进去，调用方按服务名订阅实例列表，再由负载均衡挑选一个实例。核心是三件事——注册、心跳（健康判定）、变更通知。**

**主流注册中心对比：**

| 组件 | 一致性模型 | 健康判定 | 变更通知 | 特点 |
| --- | --- | --- | --- | --- |
| Nacos 2.x | AP（Distro 协议），可切 CP | 临时实例心跳 + 长连接断连摘除 | 推送 + 客户端定时拉取 | 注册与配置一体，国内主流 |
| Eureka | AP | 30 秒续约，90 秒未续约剔除 | 客户端每 30 秒拉取增量 | 自我保护机制，适合纯注册场景 |
| Consul | CP（Raft） | 主动健康检查（脚本/HTTP/TCP） | 阻塞查询（long polling） | 多数据中心，服务网格能力强 |
| ZooKeeper | CP（ZAB） | 会话 + 临时节点 | Watch 事件 | 强一致，但 Watch 一次性、易丢事件 |
| etcd | CP（Raft） | Lease + 定期续租 | Watch | 云原生底座，K8s 生态 |

**AP 与 CP 的取舍：** 注册中心本质是「发现服务」，可用性优先。注册中心短时间不可用时，调用方应继续使用本地缓存的实例列表；如果为了强一致而让注册中心整体不可写，反而会导致新实例无法上线。

**推与拉的组合（生产标准做法）：**

```text
    启动时      ：主动注册（自注册）或由注册中心扫描（第三方注册）
    运行期间    ：客户端本地缓存实例列表 + 定时全量拉取（兜底）
    变更发生时  ：注册中心推送或客户端长轮询，立即刷新缓存
    实例下线    ：优雅下线先摘除流量，等待在途请求结束再注销
```

**代码示例（Spring Cloud + Nacos，YAML 与 Java，4 空格缩进）：**

```yaml
spring:
    application:
        name: order-service
    cloud:
        nacos:
            discovery:
                server-addr: 10.0.0.31:8848,10.0.0.32:8848
                namespace: prod
                # 临时实例：靠心跳维持，断连自动摘除
                ephemeral: true
                # 元数据，便于按版本、机房做流量路由
                metadata:
                    version: 20261103
                    zone: sh-a
        loadbalancer:
            cache:
                # 实例列表本地缓存，注册中心故障时仍可服务
                ttl: 35s
```

```java
@Service
public class InventoryCaller {

    private final DiscoveryClient discoveryClient;
    private final RestClient restClient;

    public InventoryCaller(DiscoveryClient discoveryClient, RestClient restClient) {
        this.discoveryClient = discoveryClient;
        this.restClient = restClient;
    }

    public int query(String sku) {
        List<ServiceInstance> instances = discoveryClient.getInstances("inventory-service");
        if (instances.isEmpty()) {
            // 注册中心无实例时降级到本地快照，避免整条链路直接失败
            instances = LocalSnapshot.get("inventory-service");
        }
        ServiceInstance target = RoundRobin.pick(instances);
        return restClient.get()
            .uri(target.getUri() + "/stock?sku=" + sku)
            .retrieve()
            .body(Integer.class);
    }
}
```

**健康检查必须分三层，不能只看心跳：**

| 层次 | 判定内容 | 失败后的动作 |
| --- | --- | --- |
| 进程存活 | 进程在、端口通 | 摘除流量，重启实例 |
| 应用就绪 | 依赖的 DB、缓存、配置已加载 | 暂不接流量，但不重启 |
| 业务健康 | 核心接口成功率、队列积压 | 告警 + 灰度摘流，通常不自动摘除 |

**故障场景与兜底：**

- 注册中心整体不可用：调用方靠本地缓存与快照继续服务，新实例暂时无法上线，恢复后自动补齐。
- 网络分区导致「幽灵实例」：实例已死但注册中心仍认为健康，调用方持续超时。需要应用层主动探测 + 熔断兜底。
- 优雅下线缺失：实例直接 kill，注册中心还没摘除，流量继续打到死实例。下线流程必须是「先置为下线状态 → 等待一个心跳周期 → 停止接流量 → 处理完在途请求 → 退出」。
- 心跳间隔过长：实例故障后最长要等一个完整过期周期才摘除（Eureka 是 90 秒），期间持续报错。

**面试怎么答：** 先说注册中心解决的是「地址动态变化」，再讲注册、心跳、变更通知三件事；然后对比 Nacos、Eureka、Consul、ZooKeeper 的一致性模型与健康判定方式，点明「注册中心应当 AP 优先」；最后讲本地缓存兜底与优雅下线两个工程细节。能说出「Eureka 30 秒续约、90 秒剔除」和「先摘流量再停机」，说明真运维过。

**易错点：**

- 注册即健康：进程起来了但 DB 连不上，流量打进去全是 500，必须区分就绪与存活。
- 把 ZooKeeper 当 AP 注册中心用：ZK 是 CP，选举期间整个注册不可用。
- 调用方不做本地缓存：注册中心一抖动，全站调用失败。
- 心跳间隔与摘除阈值不匹配：心跳 30 秒、阈值 35 秒，网络抖动就误摘。
- 下线直接 kill：注册中心仍保留实例，上游持续超时几十秒。

## 3. API 网关

**结论：API 网关是所有外部流量的统一入口，把鉴权、限流、熔断、路由、协议转换、灰度、日志这些「与业务无关但每个服务都要做」的能力收敛到一层，让业务服务只关心业务。**

**网关的职责边界：**

| 应该做 | 不应该做 |
| --- | --- |
| 路由转发、负载均衡、协议转换 | 复杂业务编排、跨服务数据聚合 |
| 统一鉴权、签名校验、防重放 | 业务级权限判断（下放到服务） |
| 全局限流、黑白名单、防爬 | 精确到字段的业务校验 |
| 灰度分流、A/B 实验入口 | 长耗时任务、文件转码 |
| 访问日志、TraceId 注入、指标 | 状态存储、业务缓存 |

**主流网关对比：**

| 网关 | 技术栈 | 配置方式 | 性能 | 适用 |
| --- | --- | --- | --- | --- |
| Spring Cloud Gateway | WebFlux + Reactor | Java 代码 + YAML 路由 | 中，单机数万 QPS | Java 体系、需要写自定义过滤器 |
| Kong | OpenResty + Lua | Admin API + 声明式 | 高 | 插件生态丰富、多语言团队 |
| APISIX | OpenResty + etcd | etcd 动态配置、插件热加载 | 高 | 动态路由、国内使用广 |
| Nginx + Lua | C 模块 + Lua | 配置文件 reload | 极高 | 只做转发与简单鉴权 |
| Envoy | C++ | xDS 动态配置 | 极高 | 服务网格数据面、云原生 |

**代码示例（Spring Cloud Gateway 路由与全局过滤器，YAML + Java，4 空格缩进）：**

```yaml

        gateway:
            routes:
                - id: order-route
                  uri: lb://order-service
                  predicates:
                      - Path=/api/order/**
                  filters:

                      - name: RequestRateLimiter
                        args:

                            redis-rate-limiter.burstCapacity: 2000
                  metadata:
                      connect-timeout: 200
                      response-timeout: 2500
                - id: canary-route
                  uri: lb://order-service-v2
                  predicates:
                      - Path=/api/order/**
```

```java
@Component
public class AuthGlobalFilter implements GlobalFilter, Ordered {
    private final TokenVerifier verifier;

    public AuthGlobalFilter(TokenVerifier verifier) {
        this.verifier = verifier;
    }

    @Override
    public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
        String path = exchange.getRequest().getURI().getPath();
        if (path.startsWith("/actuator/health")) {
            return chain.filter(exchange);
        }
        String token = exchange.getRequest().getHeaders().getFirst("Authorization");
        if (token == null || !verifier.verify(token)) {
            exchange.getResponse().setStatusCode(HttpStatus.UNAUTHORIZED);
            return exchange.getResponse().setComplete();
        }
        // 网关注入用户标识与 TraceId，下游不再重复解析令牌
        ServerHttpRequest request = exchange.getRequest().mutate()
            .header("X-User-Id", verifier.userId(token))
            .header("X-Trace-Id", TraceIdGenerator.next())
            .build();
        return chain.filter(exchange.mutate().request(request).build());
    }

    @Override
    public int getOrder() {
        return -100;
    }
}
```

**网关的性能与容量注意点：**

- 每经过一层网关，延迟增加 1 到 3 毫秒，链路中不要串联多个网关。
- 网关自身的连接数与并发是瓶颈：响应式网关（WebFlux/Envoy）用少量线程扛高并发，阻塞式网关需要按「QPS × RT」配线程。
- 网关超时必须小于上游 SLA，且要能向下游传递截止时间。

**故障场景与兜底：**

- 网关成为单点：必须多实例 + 前置 LB，且配置中心与注册中心故障时网关要能使用本地缓存路由。
- 路由配置推错：一条错误路由可能把全部流量打到错误服务。灰度发布路由配置 + 版本回滚 + 变更审计是必需的。
- 鉴权在网关做了缓存：权限变更无法即时生效，用户被越权访问。鉴权结果只缓存极短时间，或把细粒度权限下放到服务。
- 网关做聚合导致扇出：一个入口请求打 10 个下游，网关线程被占满，故障面反而扩大。

**面试怎么答：** 先给网关的定位——统一入口 + 横切能力收敛；再用一张表划清「该做/不该做」的边界，特别强调不做业务编排；然后对比 Spring Cloud Gateway、Kong、APISIX、Envoy 的技术栈与适用场景；最后讲延迟开销、单点、路由配置错误三个运维问题。能说出「网关超时要小于上游 SLA 并向下传递」，说明考虑过全链路。

**易错点：**

- 把业务逻辑塞进网关：网关变成新的单体，且无法独立扩缩容。
- 在网关做全局限流但不区分租户：一个客户打满全站配额。
- 网关不注入 TraceId：跨服务链路从这里断掉。
- 网关串联多级（外部网关 → 业务网关 → 服务网关）：每层都加延迟与故障点。

## 4. 配置中心

**结论：配置中心的价值不是「把配置放到远端」，而是「变更可灰度、可回滚、可审计、可即时生效」。配置是运行时行为的一部分，一次错误的配置推送等同于一次全量故障发布。**

**主流方案对比：**

| 方案 | 存储 | 生效机制 | 灰度能力 | 适用 |
| --- | --- | --- | --- | --- |
| Nacos | 内置 DB + Distro/Raft | 长轮询（默认 30 秒挂起）+ 推送 | 按 namespace/group 分组，灰度较弱 | 注册与配置一体，中小团队 |
| Apollo | MySQL | HTTP 长轮询（默认 60 秒） | 按集群/namespace/灰度规则发布 | 权限、审计、灰度要求高 |
| Spring Cloud Config | Git / JDBC / Vault | Bus 消息广播 + 定时刷新 | 靠 Git 分支，弱 | 配置即代码，随应用发布 |
| etcd | etcd | Watch 事件，毫秒级 | 无原生灰度 | 云原生、K8s 体系 |

**长轮询为什么比轮询好：** 客户端发起请求后服务端不立即返回，而是挂起（Nacos 约 30 秒、Apollo 约 60 秒）；期间若有配置变更立即返回，否则超时后客户端重新发起。这样既保证秒级生效，又把请求量从「每秒一次」降到「每分钟一到两次」。

**配置的三类分层（决定安全等级）：**

| 类型 | 示例 | 生效方式 | 安全要求 |
| --- | --- | --- | --- |
| 静态配置 | 端口、线程池大小、连接串 | 启动时加载，重启生效 | 变更走发布流程 |
| 动态开关 | 降级开关、灰度比例、限流阈值 | 运行时刷新，秒级生效 | 需要审计与到期时间 |
| 敏感配置 | 密钥、证书、数据库密码 | 加密存储 + 运行时解密 | 禁止明文、禁止进代码库 |

**代码示例（Nacos 动态配置 + 本地快照兜底，Java 与 YAML，4 空格缩进）：**

**灰度发布的正确姿势（配置中心的核心价值）：**

```text
    1. 先在 1 个实例 / 1 个集群灰度，观察 10 分钟核心指标
    2. 灰度期间保留旧值，随时一键回滚到上一版本
    3. 全量前做「配置差异对比」，避免把测试环境的键带到生产
    4. 每条动态开关都必须有 owner 与到期时间，到期自动失效
```

**故障场景与兜底：**

- 配置推错导致全站故障：这是配置中心最典型的事故。必须灰度 + 版本回滚 + 变更审计 + 关键配置双人复核。
- 配置中心不可用时应用无法启动：本地快照是必需项，不能只依赖远端。
- `@RefreshScope` 不生效：字段是 `static`/`final`、Bean 未被代理、刷新未开启，三者任一都会导致配置不更新。
- Bean 重建引发状态丢失：`@RefreshScope` 会销毁并重建 Bean，若 Bean 持有连接池或本地缓存，重建后状态清零，应把配置收敛到独立的配置 Bean。
- 配置项无默认值：老实例收到新增配置项时启动失败，所有配置必须有代码侧默认值。

**面试怎么答：** 先给一句定位——配置变更等于一次发布，所以必须灰度、回滚、审计；再对比 Nacos、Apollo、Spring Cloud Config、etcd 的存储与生效机制；重点讲长轮询为什么能把「秒级生效」和「低请求量」兼顾；然后讲配置分层（静态、动态、敏感）与本地快照兜底。能说出 `@RefreshScope` 对 static/final 无效，说明踩过坑。

**易错点：**

- 配置中心只做存储不做灰度：一次推送影响全量实例，和直接发版没区别。
- 敏感配置明文存放：密钥进配置中心也必须加密，且要做访问审计。
- 没有本地快照：配置中心挂掉，新实例起不来，扩缩容直接失败。
- 用配置中心存业务数据：配置是低频变更的元数据，不是数据表。
- 动态开关不设到期时间：临时降级开关变成永久行为，无人清理。

## 5. 服务调用（RPC 与 REST）

**结论：内部服务之间追求性能与强契约，用 RPC（Dubbo、gRPC）；对外开放、跨团队、跨语言、要求可读与通用性，用 REST。二者不是新旧替代关系，而是两种契约风格。**

**核心差异对比：**

| 维度 | RPC（Dubbo / gRPC） | REST（HTTP + JSON） |
| --- | --- | --- |
| 传输协议 | Dubbo 私有协议 / gRPC 基于 HTTP/2 | HTTP/1.1 或 HTTP/2 |
| 序列化 | Hessian2 / Protobuf，二进制 | JSON，文本 |
| 报文体积 | 小，Protobuf 通常比 JSON 小 3 到 5 倍 | 大，字段名重复传输 |
| 连接模型 | 长连接 + 多路复用，连接复用率高 | 短连接或连接池，HTTP/2 可复用 |
| 契约 | 强，IDL / 接口 JAR，编译期校验 | 弱，OpenAPI 文档，运行期校验 |
| 性能 | 高，单机可达数万 QPS | 中，序列化与 Header 开销大 |
| 可调试性 | 需专用工具，抓包不直观 | 极好，curl 即可 |
| 适用 | 内部高频同步调用 | 对外开放、第三方集成、前后端 |

**gRPC 的四个关键特性：**

1. 基于 HTTP/2：多路复用（一个连接并发多个请求）、Header 压缩（HPACK）、服务端推送。
2. Protobuf 序列化：字段编号而非字段名传输，体积小、解析快、支持向前向后兼容。
3. 四种调用方式：一元、服务端流、客户端流、双向流。
4. Deadline 传播：`context` 中的截止时间会随调用链传递，下游可感知上游已放弃。

**代码示例（gRPC，proto 与 Go 服务端，4 空格缩进）：**

```protobuf
syntax = "proto3";

package inventory.v1;

service InventoryService {
    rpc QueryStock(QueryStockRequest) returns (QueryStockResponse);
    rpc WatchStock(QueryStockRequest) returns (stream QueryStockResponse);
}

message QueryStockRequest {
    string sku_id = 1;
    // 预留字段编号，删除字段时禁止复用编号
    reserved 4, 5;
}

message QueryStockResponse {
    string sku_id = 1;
    int32 available = 2;
}
```

```go
func (s *inventoryServer) QueryStock(ctx context.Context, req *pb.QueryStockRequest) (*pb.QueryStockResponse, error) {
    // 下游继承上游 deadline，若剩余时间不足直接快速失败
    if deadline, ok := ctx.Deadline(); ok {
        if time.Until(deadline) < 50*time.Millisecond {
            return nil, status.Error(codes.DeadlineExceeded, "insufficient time budget")
        }
    }
    stock, err := s.repo.Query(ctx, req.SkuId)
    if err != nil {
        return nil, status.Error(codes.Internal, "query stock failed")
    }
    return &pb.QueryStockResponse{SkuId: req.SkuId, Available: int32(stock)}, nil
}
```

**Dubbo 3 的关键变化（面试常问）：**

| 维度 | Dubbo 2.x | Dubbo 3.x |
| --- | --- | --- |
| 协议 | Dubbo 私有协议 | Triple（兼容 gRPC 风格，基于 HTTP/2） |
| 注册 | ZooKeeper / Nacos | 应用级服务发现，注册中心只存元数据 |
| 地址发现 | 接口级，实例多时注册中心压力大 | 应用级，按应用聚合，支持大规模集群 |
| 跨语言 | 弱 | Triple 协议支持多语言 |

**故障场景与兜底：**

- 序列化不兼容：新增字段用了已删除的编号，或枚举值顺序变化，导致老客户端解析失败。Protobuf 中删除字段必须 `reserved`，枚举新增只能追加。
- 长连接假死：TCP 连接存在但服务端已无响应，连接池里的连接全部不可用。必须配心跳（keepalive）与最小空闲检测。
- 内部高频调用用 REST：JSON 序列化 + 短连接建立开销占了一半 RT，QPS 上不去。内部调用应换 RPC 或至少启用 HTTP/2 与连接池。
- RPC 接口无版本：接口签名一变，全部调用方必须同步升级。接口必须有版本号或兼容策略。
- 默认超时过长：Feign 默认连接超时 10 秒、读超时 60 秒，一个下游挂死会拖住整个线程池。

**面试怎么答：** 先给判断标准——内部高频强契约用 RPC，对外开放弱契约用 REST；再用一张表对比协议、序列化、连接模型、契约强度、可调试性；然后讲 gRPC 的 HTTP/2 多路复用与 deadline 传播、Dubbo 3 的 Triple 协议与应用级发现；最后讲序列化兼容、长连接假死、默认超时三个坑。能说清「Protobuf 删字段要 reserved」是硬细节。

**易错点：**

- 认为 REST 一定比 RPC 先进：两者是契约风格差异，内部高频调用 REST 反而更慢。
- RPC 接口直接暴露给外部：外部依赖内部接口签名，任何重构都是破坏性变更。
- 忽略序列化兼容：上线新版本后老客户端大面积解析失败。
- 连接池不设上限：下游变慢时连接数暴涨，把下游连接数打满。
- 只配读超时不配连接超时：连接建立阶段挂住，线程永久阻塞。

## 6. 服务网格 Service Mesh

**结论：Service Mesh 把「重试、超时、熔断、mTLS、流量切分、可观测」这些治理能力从业务 SDK 下沉到 Sidecar 或 eBPF 层，业务代码零侵入，且天然跨语言。**

**两种实现路径：**

| 路径 | 代表 | 原理 | 侵入性 |
| --- | --- | --- | --- |
| Sidecar 代理 | Istio（Envoy）、Linkerd | 每个 Pod 注入一个代理，iptables/eBPF 劫持流量 | 零代码侵入，有资源与延迟开销 |
| SDK 内嵌 | Spring Cloud Alibaba、Dubbo | 治理逻辑在应用进程内 | 需要改依赖，跨语言弱 |
| eBPF | Cilium | 内核层拦截，无 Sidecar | 延迟最低，能力受内核版本限制 |

**Istio 核心资源对象：**

| 对象 | 作用 |
| --- | --- |
| VirtualService | 定义路由规则、超时、重试、故障注入、流量权重 |
| DestinationRule | 定义目标子集（subset）、负载均衡策略、熔断（outlierDetection）、mTLS |
| Gateway | 入口网关，替代传统 Ingress 的部分职责 |
| PeerAuthentication | 定义 mTLS 模式（STRICT / PERMISSIVE / DISABLE） |

**代码示例（Istio 路由 + 熔断 + 灰度，YAML，4 空格缩进）：**

```yaml
apiVersion: networking.istio.io/v1beta1
kind: VirtualService
metadata:
    name: order-service
spec:
    hosts:
        - order.internal
    http:
        - match:
              - uri:
                    prefix: /api/order
          route:
              - destination:
                    host: order-service
                    subset: v1
                weight: 90
              - destination:
                    host: order-service
                    subset: v2
                weight: 10
          timeout: 2500ms
          retries:
              attempts: 2
              perTryTimeout: 800ms
              retryOn: 5xx,reset,connect-failure
---
apiVersion: networking.istio.io/v1beta1
kind: DestinationRule
metadata:
    name: order-service
spec:
    host: order-service
    trafficPolicy:
        loadBalancer:
            simple: LEAST_REQUEST
        outlierDetection:
            consecutive5xxErrors: 5
            interval: 30s
            baseEjectionTime: 60s
            maxEjectionPercent: 30
        tls:
            mode: ISTIO_MUTUAL
    subsets:
        - name: v1
          labels:
              version: v1
        - name: v2
          labels:
              version: v2
```

**Sidecar 的真实成本（必须回答）：**

- 延迟：每次调用多两跳本地代理，通常增加 1 到 2 毫秒。
- 资源：每个 Pod 一个 Envoy，内存约几十 MB，集群规模大时总量可观。
- 复杂度：流量劫持依赖 iptables 规则，排障要看 Sidecar 日志与 Envoy 配置转储。
- 控制面故障：istiod 挂掉不影响已有数据面配置生效，但无法下发新规则（这是设计上的优点，要能说清）。

**故障场景与兜底：**

- Sidecar 未就绪导致流量被劫持但无代理处理：必须保证 Sidecar 与应用同生命周期启动，或用 `holdApplicationUntilProxyStarts`。
- 与 SDK 治理重复：应用内又配了 Ribbon 重试、Sentinel 熔断，与网格策略叠加，重试次数相乘。治理只能在一处生效。
- mTLS 证书轮换失败：证书过期后服务间全部调用失败，必须有到期告警与自动轮换。
- 网格策略全集群统一：所有服务共用一套超时，慢接口被误杀。策略要按服务粒度覆盖。

**面试怎么答：** 先讲 Mesh 的本质——治理能力下沉、业务零侵入、跨语言；再对比 Sidecar、SDK、eBPF 三种路径的侵入性与开销；然后讲 Istio 的 VirtualService（路由、超时、重试、权重）与 DestinationRule（subset、负载均衡、熔断、mTLS）各管什么；最后讲 Sidecar 的 1 到 2 毫秒开销、与 SDK 治理重复、控制面故障不影响数据面三个关键点。

**易错点：**

- 认为上了 Mesh 就不用管超时：网格的默认超时不一定匹配业务 SLA，必须按服务覆盖。
- 网格与应用内都配重试：重试次数相乘，故障时流量放大数倍。
- 忽略 Sidecar 资源：几百个 Pod 就是几百个 Envoy，内存与 CPU 都要计入容量。
- 把 Mesh 当银弹：它解决的是横切治理，解决不了服务边界设计与数据一致性。
- 排障时不看 Sidecar：请求在应用日志里根本没有，实际卡在代理层。

## 7. 链路追踪与日志聚合

**结论：追踪回答「这次请求慢在哪一跳」，日志回答「这一跳到底发生了什么」，两者靠 TraceId 关联。生产可观测体系的最小闭环是「TraceId 全链路透传 + 结构化日志 + 集中采集 + 按 TraceId 一键检索」。**

**采集与存储架构：**

```text
    应用日志（JSON）→ 采集 agent（Filebeat / Fluent Bit / Promtail）
        → 缓冲（Kafka，削峰与解耦）
        → 存储（Elasticsearch / Loki / ClickHouse）
        → 查询（Kibana / Grafana）
    链路数据（Span）→ OTel Collector → Jaeger / SkyWalking / Tempo
```

**方案对比：**

| 方案 | 存储模型 | 成本 | 查询能力 | 适用 |
| --- | --- | --- | --- | --- |
| ELK（Elasticsearch） | 倒排索引，全文检索强 | 高，存储与内存开销大 | 最强，支持聚合分析 | 需要复杂检索与聚合 |
| Loki | 只索引标签，日志块压缩存储 | 低 | 按标签 + 关键字，聚合弱 | 成本敏感、以检索为主 |
| ClickHouse | 列式存储 | 中 | 大规模聚合快 | 日志分析、指标明细 |
| SkyWalking | ES/MySQL + 专用 UI | 中 | 调用链、拓扑、告警 | Java 体系、无侵入 |
| Jaeger / Tempo | ES/Cassandra/对象存储 | 中 | 调用链查询 | OTel 标准体系 |

**日志规范（比选型更重要）：**

| 字段 | 示例 | 作用 |
| --- | --- | --- |
| `ts` | 2026-11-03T10:12:33.482+08:00 | 精确到毫秒，统一时区 |
| `level` | INFO / WARN / ERROR | 分级，ERROR 必须可告警 |
| `trace_id` / `span_id` | 32 位 / 16 位十六进制 | 串联全链路 |
| `service` / `host` | order-service / pod-xxx | 定位实例 |
| `msg` | 固定文案 + 变量分离 | 便于聚合统计 |
| `biz_key` | 订单号、用户 ID | 按业务维度检索 |

**代码示例（Logback 结构化输出 + MDC，Java 与 XML，4 空格缩进）：**

```xml
<configuration>
    <appender name="JSON" class="ch.qos.logback.core.ConsoleAppender">
        <encoder class="net.logstash.logback.encoder.LogstashEncoder">
            <includeMdcKeyName>trace_id</includeMdcKeyName>
            <includeMdcKeyName>span_id</includeMdcKeyName>
            <customFields>{"service":"order-service"}</customFields>
        </encoder>
    </appender>
    <!-- 异步 appender 必须有界队列，否则日志会拖垮业务线程 -->
    <appender name="ASYNC" class="ch.qos.logback.classic.AsyncAppender">
        <queueSize>8192</queueSize>
        <discardingThreshold>0</discardingThreshold>
        <neverBlock>true</neverBlock>
        <appender-ref ref="JSON"/>
    </appender>
    <root level="INFO">
        <appender-ref ref="ASYNC"/>
    </root>
</configuration>
```

**采集配置（Fluent Bit，YAML，4 空格缩进）：**

```yaml
pipeline:
    inputs:
        - name: tail
          path: /var/log/app/*.log
          parser: json
          # 记录文件读取位点，重启后从断点续采
          db: /var/lib/fluent-bit/state.db
          read_from_head: false
    filters:
        - name: record_modifier
          record:
              cluster: sh-a
        - name: grep
          # 采集侧丢弃 DEBUG，避免把存储打爆
          exclude: level ^DEBUG$
    outputs:
        - name: kafka
          brokers: 10.0.0.41:9092
          topic: app-log
          format: json
```

**故障场景与兜底：**

- 日志同步写导致接口变慢：磁盘抖动时业务 RT 直接翻倍，必须异步 + 有界队列 + `neverBlock`。
- 日志量打爆存储：一次线上 DEBUG 忘了关，一天写满集群。采集侧过滤 + 应用侧分级 + 存储侧 ILM 滚动删除三者都要有。
- Loki 标签基数爆炸：把 `trace_id`、`user_id` 当标签，索引条目无限增长，Loki 直接不可用。高基数字段只能放日志内容，不能做标签。
- TraceId 在异步与 MQ 中丢失：日志无法串联。异步用 `TaskDecorator`，MQ 在消息 Header 里携带。
- ES 分片过多：默认 5 分片 × 每天一个索引，几个月后上千分片，集群元数据压力大。按大小滚动或使用 ILM。

**面试怎么答：** 先区分追踪与日志的职责，再说二者靠 TraceId 关联；然后讲采集链路（应用 → agent → Kafka → 存储 → 查询）每段的作用，强调 Kafka 是为了削峰解耦；再对比 ELK、Loki、ClickHouse 的成本与查询能力；最后讲日志规范六个字段与三个坑（同步写、量失控、高基数标签）。能说出「trace_id 不能做 Loki 标签」是硬细节。

**易错点：**

- 日志里打全量请求体：包含手机号、身份证等敏感信息，合规风险极高。
- 用 `System.out` 或同步 appender：无级别、无结构，且阻塞业务线程。
- 采样只做链路不做日志：日志全量、链路采样，两者对不上账。
- 日志保留期照抄「永久保留」：成本失控，且从未被查询过。
- 只按服务名检索：没有 TraceId 就没有跨服务串联，排障只能靠猜。

## 8. 灰度与蓝绿发布

**结论：蓝绿是「两套完整环境整体切换」，回滚最快但资源翻倍；灰度（金丝雀）是「按比例或按维度逐步放量」，风险最小；滚动发布是「逐批替换实例」，资源最省但发布期间新旧版本共存。**

**四种发布方式对比：**

| 方式 | 资源开销 | 回滚速度 | 风险 | 适用 |
| --- | --- | --- | --- | --- |
| 蓝绿 | 2 倍 | 秒级，切回旧环境 | 中，切换瞬间全量 | 核心服务、需要极速回滚 |
| 金丝雀 / 灰度 | 略增 | 分钟级，调权重到 0 | 低，先小流量验证 | 大多数生产发布 |
| 滚动 | 几乎不增 | 慢，需再滚一轮 | 中，新旧版本共存 | K8s 默认、无状态服务 |
| 全量替换 | 无 | 靠重新部署 | 高 | 非核心、内网工具 |

**灰度维度的选择（决定灰度是否有效）：**

| 维度 | 做法 | 注意 |
| --- | --- | --- |
| 流量比例 | 网关注入权重，5% → 20% → 50% → 100% | 必须有真实流量，且样本量足够 |
| 用户白名单 | 指定 UID / 设备 ID 进新版本 | 适合内部先验，但流量不代表真实分布 |
| 地域 / 机房 | 单机房先全量 | 能快速暴露区域性依赖问题 |
| 接口维度 | 只放开只读接口 | 写接口最后放量，避免数据污染 |

**代码示例（K8s 双 Deployment + Service 切流量，YAML，4 空格缩进）：**

```yaml
apiVersion: apps/v1
kind: Deployment
```

**发布流程（必须写进 SOP）：**

```text
    1. 发布前：数据库变更必须「先兼容后切换」（加字段、双写、回填、再删旧字段）
    2. 灰度 5%：观察 10 分钟，看错误率、P99、核心业务指标
    3. 灰度 30%：观察 30 分钟，对比新旧版本的业务转化
    4. 全量：保留旧版本实例与镜像至少 24 小时
    5. 回滚：切流量权重 + 回滚镜像，数据库变更需独立回滚方案
```

**故障场景与兜底：**

- 新旧版本共用数据库不兼容：新版本写了老版本读不懂的字段，回滚后数据错乱。数据库变更必须向前向后都兼容。
- 灰度流量不真实：内部白名单用户集中在小城市、低并发时段，灰度通过但全量出事。灰度必须按真实流量比例。
- 回滚依赖重新构建镜像：回滚耗时 10 分钟以上，错过止损窗口。必须保留上一版本镜像并支持秒级切流。
- 只灰度读流量：写接口直接全量，数据一旦写错无法回滚。
- 缺少灰度观测：只看机器指标不看业务指标（下单成功率、支付转化），故障发现滞后。

**面试怎么答：** 先给四种发布方式的对比，明确「蓝绿换环境、灰度换比例、滚动换实例」；再讲灰度维度怎么选，强调按真实流量比例而不是内部白名单；然后讲数据库变更的兼容原则——加字段、双写、回填、删旧字段四步；最后讲回滚预案与观测指标。能说出「数据库变更要向前向后兼容」是分水岭。

**易错点：**

- 把灰度当蓝绿：只切了一次 50%，没有渐进放量与观察窗口。
- 数据库变更不可逆却直接全量：回滚代码回滚不了数据。
- 灰度只看技术指标：错误率没涨但下单量跌了一半，同样是事故。
- 全量后立刻删旧版本：出问题时无镜像可回。
- 灰度实例数与流量比例不匹配：2 个实例承担 50% 流量，先被压垮。

## 9. 容器化与 K8s 基础

**结论：K8s 的核心抽象是「Pod 是最小调度单元、Deployment 管无状态副本、Service 提供稳定访问入口、Ingress 提供七层路由」。生产可用的关键不在会写 YAML，而在探针、资源限制、优雅停机、滚动策略这四项。**

**核心对象对照：**

| 对象 | 职责 | 关键点 |
| --- | --- | --- |
| Pod | 最小调度单元，可含多个容器 | 同 Pod 内容器共享网络与存储卷 |
| Deployment | 管理无状态 Pod 副本与滚动更新 | 不直接创建 Pod，依靠 ReplicaSet |
| StatefulSet | 有状态服务，稳定网络标识与存储 | 有序启停，PVC 模板 |
| Service | 为一组 Pod 提供稳定 ClusterIP 与负载均衡 | ClusterIP / NodePort / LoadBalancer |
| Ingress | 七层 HTTP 路由 | 依赖 Ingress Controller 实现 |
| ConfigMap / Secret | 配置与敏感信息注入 | Secret 默认只做 base64，不是加密 |
| HPA | 按 CPU/内存/自定义指标扩缩容 | 默认每 15 秒同步一次 |

**探针的正确用法（最容易被追问）：**

| 探针 | 回答的问题 | 失败动作 | 典型配置 |
| --- | --- | --- | --- |
| `startupProbe` | 是否启动完成 | 重启容器 | 慢启动应用必配，失败阈值放宽 |
| `livenessProbe` | 是否还活着 | 重启容器 | 只检查进程与死锁，不检查外部依赖 |
| `readinessProbe` | 是否能接流量 | 从 Endpoints 摘除，不重启 | 检查依赖可用性与初始化完成 |

**代码示例（生产级 Deployment，YAML，4 空格缩进）：**

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
    name: order-service
spec:
    replicas: 4
    strategy:
        type: RollingUpdate
        rollingUpdate:
            maxSurge: 25%
            maxUnavailable: 25%
    minReadySeconds: 10
    selector:
        matchLabels:
            app: order-service
    template:
        metadata:
            labels:
                app: order-service
        spec:
            terminationGracePeriodSeconds: 40
            containers:
                - name: order
                  image: registry.example.com/order-service:20261103-1
                  ports:
                      - containerPort: 8080
                  resources:
                      requests:
                          cpu: 500m
                          memory: 768Mi
                      limits:
                          cpu: 1000m
                          memory: 1Gi
                  startupProbe:
                      httpGet:
                          path: /actuator/health/liveness
                          port: 8080
                      failureThreshold: 30
                      periodSeconds: 5
                  livenessProbe:
                      httpGet:
                          path: /actuator/health/liveness
                          port: 8080
                      periodSeconds: 10
                      failureThreshold: 3
                  readinessProbe:
                      httpGet:
                          path: /actuator/health/readiness
                          port: 8080
                      periodSeconds: 5
                      failureThreshold: 2
                  lifecycle:
                      preStop:
                          exec:
                              # 先从 Endpoints 摘除，再等待在途请求结束
                              command: ["sh", "-c", "sleep 15"]
```

**资源与 QoS 的关系：**

```text
    requests = limits（CPU 与内存都相等）→ Guaranteed，最稳，适合核心服务
    只设 requests 或 limits 不等      → Burstable，弹性好，可能被驱逐
    两者都不设                        → BestEffort，最先被驱逐，禁止用于生产
```

**故障场景与兜底：**

- OOMKilled：`limits.memory` 小于应用真实堆外内存（Netty 直接内存、Metaspace），容器被内核杀掉。Java 应用必须显式设置 `-XX:MaxRAMPercentage` 并留出堆外空间。
- 探针导致重启循环：`livenessProbe` 检查了数据库连接，DB 抖动时全部实例被判死并重启，故障被放大。存活探针只检查自身。
- 优雅停机丢请求：直接 kill 导致在途请求中断。`preStop` 先摘流量再等待，`terminationGracePeriodSeconds` 要大于最长请求耗时。

**面试怎么答：** 先讲四个核心抽象（Pod、Deployment、Service、Ingress）各自解决什么；再重点讲三种探针的差异，强调「存活探针不能查外部依赖」；然后讲 requests/limits 与 QoS 的关系，以及 Java 容器的 OOM 陷阱；最后讲滚动策略与优雅停机（preStop + grace period）。这四点说出来，基本可以确认真在 K8s 上跑过生产。

**易错点：**

- 把 `livenessProbe` 写成依赖检查：下游一抖动，整个服务被重启。
- 只设 limits 不设 requests：调度器无法正确分配，且 QoS 降级。
- 内存 limit 不考虑堆外：Java 应用频繁 OOMKilled 却查不到原因。
- 忘记 `preStop`：滚动更新期间 5xx 上升，误判为新版本有 bug。

## 10. 服务依赖与雪崩

**结论：雪崩不是「某个下游挂了」，而是「下游变慢或不可用后，调用方的线程、连接、队列被逐步占满，故障沿调用链向上蔓延，最终全站不可用」。治理雪崩是一组组合拳，缺任何一环都会留下放大路径。**

**放大链路（典型全过程）：**

```text
    DB 慢查询 → 库存服务 RT 从 20ms 涨到 2s
        → 订单服务线程池被占满（线程都在等库存）
        → 订单服务所有接口变慢，包括不依赖库存的接口
        → 上游网关超时 → 上游开始重试（流量 ×3）
        → 库存服务压力再翻倍 → 彻底不可用
        → 缓存击穿 → DB 压力再上一层 → 全站雪崩
```

**治理手段与副作用：**

| 手段 | 阻断哪一环 | 副作用 |
| --- | --- | --- |
| 超时 | 线程被无限占用 | 超时过短会误杀正常请求 |
| 熔断 | 持续调用已知不可用的依赖 | 可能误判，需要 HALF_OPEN 试探 |
| 隔离（舱壁） | 一个依赖占满共享线程池 | 线程数上升，成本增加 |
| 降级 | 非核心功能拖垮核心链路 | 用户体验下降，需产品确认 |
| 限流 | 请求量超过下游容量 | 误伤正常用户，需精细化维度 |
| 缓存 | DB 被重复查询打穿 | 数据一致性下降，需防击穿 |
| 异步化 | 同步调用链过长 | 一致性变最终一致，需补偿 |

**强弱依赖必须显式梳理：**

| 依赖类型 | 定义 | 故障策略 |
| --- | --- | --- |
| 强依赖 | 缺了它业务无法成立（库存、支付） | 快速失败 + 明确错误码，不降级 |
| 弱依赖 | 缺了它体验下降但业务可完成（推荐、评价、积分） | 降级 + 兜底数据 |
| 可异步依赖 | 不要求实时结果（短信、推送、积分入账） | 异步化 + 重试 + 死信 |

**代码示例（Java，超时 + 熔断 + 隔离 + 降级组合，4 空格缩进）：**

```java
@Service
public class OrderCreateService {

    private final CircuitBreaker inventoryBreaker;
    private final ThreadPoolExecutor inventoryExecutor;
    private final InventoryClient inventoryClient;
    private final CouponClient couponClient;

    public OrderCreateService(CircuitBreakerRegistry registry,
                              @Qualifier("inventoryExecutor") ThreadPoolExecutor inventoryExecutor,
                              InventoryClient inventoryClient,
                              CouponClient couponClient) {
        this.inventoryBreaker = registry.circuitBreaker("inventory");
        this.inventoryExecutor = inventoryExecutor;
        this.inventoryClient = inventoryClient;
        this.couponClient = couponClient;
    }

    public OrderVO create(OrderCommand command) {
        // 强依赖：超时 + 熔断 + 独立线程池，失败直接返回明确错误
        int stock = queryStockWithGuard(command.getSkuId());
        // 弱依赖：失败降级，不影响下单
        BigDecimal discount = queryDiscountSafely(command.getCouponId());
        return buildOrder(command, stock, discount);
    }

    private int queryStockWithGuard(String skuId) {
        try {
            Future<Integer> future = inventoryExecutor.submit(
                CircuitBreaker.decorateSupplier(inventoryBreaker, () -> inventoryClient.query(skuId))::get);
            return future.get(300, TimeUnit.MILLISECONDS);
        } catch (TimeoutException e) {
            futureCancel();
            throw new BizException("库存查询超时，请稍后重试");
        } catch (CallNotPermittedException e) {
            // 熔断打开：不要再重试，直接快速失败
            throw new BizException("库存服务暂不可用");
        } catch (Exception e) {
            throw new BizException("库存查询失败");
        }
    }

    private BigDecimal queryDiscountSafely(String couponId) {
        try {
            return couponClient.discount(couponId);
        } catch (Exception e) {
            // 降级必须返回合法值，不能返回 null
            return BigDecimal.ZERO;
        }
    }
}
```

**故障场景与兜底：**

- 只加熔断不加超时：熔断统计窗口内请求仍然要等满超时，线程照样被占满。
- 强依赖被当弱依赖降级：库存查不到就按「有货」处理，直接超卖。
- 重试与熔断不联动：熔断已打开，上游还在重试 3 次，把拒绝放大 3 倍。
- 依赖图不清：没人知道「评价服务」还依赖「用户服务」，故障时排查方向全错。

**面试怎么答：** 先完整复述一条雪崩放大链路（DB 慢 → 线程占满 → 上游超时重试 → 缓存击穿），这条链路本身就是答案；再给治理手段表，说明每个手段阻断哪一环、有什么副作用；然后讲强弱依赖梳理，强调「强依赖不能降级成默认值」；最后讲缓存穿透、击穿、雪崩的防护思路，以及「熔断与重试必须联动」。能画出放大链路，比背七个手段更有说服力。

**易错点：**

- 认为加了熔断就万事大吉：没有超时，线程依然被慢请求占满。
- 降级返回默认值给强依赖：库存默认 0 会误杀正常订单，默认有货会超卖。
- 所有依赖共用线程池：一个慢依赖拖垮全部接口，舱壁模式形同虚设。
- 忽略缓存击穿：雪崩往往发生在下游刚恢复、缓存又失效的那一刻。

## 11. 多集群与容灾

**结论：容灾能力由 RPO（能丢多少数据）与 RTO（多久能恢复）定义，而不是由「有几个机房」定义。同城双活解决机房级故障，异地多活解决城市级灾难，代价是数据一致性与路由复杂度指数上升。**

**容灾模式对比：**

| 模式 | 数据同步 | RPO | RTO | 成本 | 适用 |
| --- | --- | --- | --- | --- | --- |
| 单机房 + 冷备 | 定期备份 | 小时级 | 小时级 | 低 | 内部系统 |
| 同城双活（双集群） | 同步/半同步复制 | 接近 0 | 分钟级 | 中 | 核心交易 |
| 两地三中心 | 同城同步 + 异地异步 | 秒级 | 分钟到小时 | 高 | 金融级 |
| 异地双活（单元化） | 单元内闭环，单元间异步 | 秒级（同单元内 0） | 秒到分钟 | 极高 | 超大规模、跨地域 |
| 异地多活 | 多单元 + 双向同步 | 取决于冲突处理 | 秒级 | 极高 | 全球化业务 |

**多活必须解决的三件事：**

1. 流量路由：谁决定一个用户去哪个单元？通常按 UID 哈希或地域。
2. 数据归属：一个用户的数据只能有一个「写单元」，避免双写冲突。
3. 故障切换：单元故障时，把该单元的用户整体迁到备用单元，并处理数据追平。

**代码示例（Java，单元化路由，4 空格缩进）：**

```java
@Component
public class UnitRouter {

    private static final int UNIT_COUNT = 4;
    private final UnitHealthChecker healthChecker;

    public UnitRouter(UnitHealthChecker healthChecker) {
        this.healthChecker = healthChecker;
    }

    public String route(long uid) {
        int index = (int) (Math.floorMod(uid, UNIT_COUNT));
        String unit = "unit-" + index;
        if (healthChecker.isHealthy(unit)) {
            return unit;
        }
        // 故障单元整体切到备用单元，注意备用单元要能承接整份数据
        return healthChecker.backupOf(unit);
    }
}
```

**流量调度与健康检查（GSLB 配置思路，YAML，4 空格缩进）：**

```yaml
gslb:
    domain: api.example.com
    ttl: 60
    policies:
        - name: primary
          unit: sh-a
          weight: 100
          health-check:
              path: /actuator/health/readiness
              interval: 10s
              timeout: 3s
              unhealthy-threshold: 3
        - name: standby
          unit: sh-b
          weight: 0
          # 备用单元平时不接流量，切换时改权重
          promote-on-failure: true
```

**数据同步的关键约束：**

- 异步复制必然有 RPO，声称 RPO=0 就必须是同步复制，而同步复制会放大写延迟。
- 双向同步必须定义冲突解决策略（最后写入获胜、版本号、业务字段合并），否则数据会被随机覆盖。
- 跨单元查询尽量避免实时 join，改为数据冗余或异步汇总。
- 数据库切换必须验证「回切」路径，只做单向切换演练是不完整的。

**故障场景与兜底：**

- 脑裂：两个单元都认为自己是主，同时接受写入，数据分叉。必须有仲裁（第三方节点或多数派）决定归属。
- DNS TTL 过长：故障切换要等 TTL 过期，实际 RTO 被 DNS 拖到几分钟以上。关键入口用短 TTL + 多级调度。
- 单元容量按平均分配：一个单元挂掉后，剩余单元要承接全部流量，必须按「N-1」容量设计。
- 从未演练切换：真实故障时发现数据没追平、配置没同步、证书不匹配。容灾必须定期真实演练。
- 跨城延迟被忽略：一次请求跨城调用增加 10 到 30 毫秒，链路里跨城调用多了直接超 SLA。

**面试怎么答：** 先给 RPO 与 RTO 的定义，明确「容灾能力是被这两个指标定义的」；再给容灾模式对比表，从冷备到异地多活说明成本与一致性代价；然后讲多活三件事（流量路由、数据归属、故障切换），强调「一个用户只能有一个写单元」；最后讲脑裂、DNS TTL、N-1 容量、切换演练四个关键点。能说出「按 N-1 设计容量」，说明真做过容灾规划。

**易错点：**

- 把冷备叫双活：备用机房平时不接流量、数据落后几小时，切过去就是事故。
- 声称 RPO=0 但用异步复制：数据库 crash 时必然丢最后一批事务。
- 双写两个单元：冲突策略没定义，同一订单在两个单元状态不同。
- 只做单向切换演练：回切时发现反向数据没同步。
- 忽略跨城调用延迟：多活之后 P99 直接翻倍，SLA 反而更差。

## 12. 单体与微服务选型

**结论：微服务不是默认答案。团队小、领域边界不清、缺少自动化运维能力时，模块化单体是更优解；只有在「多个团队需要独立交付、领域边界稳定、运维体系成熟」三个条件同时成立时，拆分才划算。**

**三种形态对比：**

| 维度 | 单体 | 模块化单体 | 微服务 |
| --- | --- | --- | --- |
| 部署单元 | 1 个 | 1 个（模块内高内聚） | N 个 |
| 事务一致性 | 本地事务，天然强一致 | 本地事务 | 需最终一致 + 补偿 |
| 开发效率（小团队） | 高 | 高 | 低，跨服务联调成本高 |
| 独立交付 | 否 | 否 | 是 |
| 排障 | 简单，一个进程 | 简单 | 复杂，需要链路追踪 |
| 弹性扩缩 | 整体扩容 | 整体扩容 | 按服务扩容 |
| 技术异构 | 难 | 较难 | 容易 |
| 适用规模 | 小团队、早期业务 | 中等团队、边界渐清晰 | 多团队、大规模 |

**选型判断清单（满足 3 条以上才考虑拆）：**

```text
    1. 有 3 个以上团队需要同时高频修改同一代码库，合并冲突成为日常
    2. 不同模块的扩缩容需求差异巨大（如秒杀模块与后台管理）
    3. 存在明确且稳定的领域边界，且已被业务验证半年以上
    4. 已有自动化发布、链路追踪、集中日志、配置中心等治理设施
    5. 能够接受跨服务最终一致，并愿意投入补偿与对账
```

**演进路径：绞杀者模式（Strangler Fig），而不是一次性重写：**

```text
    第 1 步：在单体前面加网关，所有流量经过网关
    第 2 步：挑一个边界清晰、变更频繁的模块，独立实现为新服务
    第 3 步：网关把该模块的流量逐步切到新服务（5% → 100%）
    第 4 步：单体中该模块代码下线，数据通过同步或双写迁移
    第 5 步：重复以上步骤，直到单体只剩核心骨架
```

**代码示例（Gradle 多模块的模块化单体骨架，Kotlin DSL，4 空格缩进）：**

```kotlin
// settings.gradle.kts
rootProject.name = "mall"

include(
    ":order-domain",
    ":order-application",
    ":inventory-domain",
    ":payment-domain",
    ":web-api"
)

// 模块间只允许单向依赖：web-api → application → domain，禁止反向
project(":order-application").projectDir = file("order/application")
```

```kotlin
// order/application/build.gradle.kts
dependencies {
    implementation(project(":order-domain"))
    // 跨域只能依赖对方的 api 模块，不能依赖 internal
    implementation(project(":inventory-api"))
    implementation("org.springframework.boot:spring-boot-starter")
}
```

**拆分的成本清单（面试时主动说出来，非常加分）：**

| 成本项 | 具体表现 |
| --- | --- |
| 运维成本 | N 个服务的部署、监控、告警、证书、扩缩容 |
| 一致性成本 | 分布式事务、幂等、对账、补偿任务 |
| 排障成本 | 跨服务链路追踪、日志聚合、依赖拓扑 |
| 联调成本 | 接口版本管理、契约测试、环境隔离 |
| 组织成本 | 服务 owner、SLA、跨团队协作流程 |

**故障场景与兜底：**

- 过早拆分：业务模型还在快速变化，边界每季度重画一次，服务反复合并拆分。先做模块化单体，等边界稳定再拆。
- 分布式单体：拆完仍要一起发布，只是把方法调用换成了网络调用，性能更差、故障更多。必须做到独立发布才算拆成功。
- 拆分后事务丢失：跨服务写操作没有补偿，出现数据不一致。必须先落地本地消息表与对账。
- 治理设施缺失：没有链路追踪就拆服务，线上出问题连调用链都拼不出来。治理设施应先于拆分建设。

**面试怎么答：** 先反直觉地表态「微服务不是默认答案」，再给三种形态对比，说明模块化单体在小团队反而更高效；然后给选型判断清单（多团队冲突、扩缩容差异、边界稳定、治理设施、可接受最终一致）；再讲绞杀者模式的演进路径，强调不要一次性重写；最后主动列拆分成本清单。这套答法体现的是架构判断力，而不是背概念。

**易错点：**

- 把「拆分」当成技术能力的证明：拆得越多不代表越先进，只代表运维成本越高。
- 用微服务解决代码耦合：代码耦合靠模块化与依赖约束解决，拆服务只是把耦合搬到网络。
- 一次性重写：新老系统并行开发半年，期间需求两边都要改，几乎必然失败。
- 拆完不做契约管理：接口随意变更，调用方被动升级。
- 忽略组织因素：康威定律决定了服务边界必须与团队边界对齐，否则拆完仍然互相阻塞。
