## 1. 幂等的设计层次

**结论：幂等是「同一请求被执行多次，业务效果与执行一次相同」的保证。它不是某一层的功能，而是一条贯穿协议、接入、应用、存储、消息的防线，任何单层方案都存在漏洞。**

**为什么单层不够：** 网关能拦住重复点击，但拦不住消息重投；唯一索引能拦住重复写入，但拦不住重复扣减内存余额；分布式锁能拦住并发，但拦不住锁过期后的第二次执行。幂等必须「多层设防、最后一层兜底」。

**分层手段对比：**

| 层次 | 典型手段 | 改造成本 | 能解决什么 | 遗留问题 |
| --- | --- | --- | --- | --- |
| 协议层 | 明确 GET/PUT/DELETE 的幂等语义，POST 不重试 | 低 | 客户端重试不产生副作用 | POST 天然不幂等，无法覆盖下单类接口 |
| 接入层 | 网关按 requestId 去重、按钮防抖、前端防重复提交 | 中 | 快速拦截同一请求的并发重复 | 网关内存去重重启即失效，跨实例不共享 |
| 应用层 | 幂等键 + 状态机 + 分布式锁 | 高 | 业务级唯一，能返回首次结果 | 处理中状态悬挂，需要超时与对账 |
| 存储层 | 唯一索引、乐观锁 version、条件更新 CAS | 低 | 最终拦截脏写与重复写 | 只能防「写」，防不住重复的旁路副作用（短信、积分） |
| 消息层 | 消费去重表、业务唯一键、offset 与业务同事务 | 中 | 重复投递不重复消费 | 去重表需要保留期与清理策略 |

**判断一个接口要不要幂等，看三个特征：**

1. 会写状态（扣库存、改余额、建订单），必须幂等。
2. 会被重试（RPC 超时重试、MQ 重投、用户连点），必须幂等。
3. 有外部副作用（发短信、发券、调三方），必须幂等，否则重复成本直接是钱。

**代码示例（Java，应用层状态机式幂等组件）：**

```java
public enum IdempotentStatus {
    PROCESSING, SUCCESS, FAILED
}

@Component
public class IdempotentExecutor {

    private static final Duration PROCESSING_TTL = Duration.ofSeconds(60);
    private final StringRedisTemplate redis;
    private final IdempotentRecordMapper recordMapper;

    public IdempotentExecutor(StringRedisTemplate redis, IdempotentRecordMapper recordMapper) {
        this.redis = redis;
        this.recordMapper = recordMapper;
    }

    public <T> T execute(String bizKey, Supplier<T> action) {
        // 第一步：抢占执行权，value 记录状态，必须带超时防止崩溃后永久悬挂
        Boolean acquired = redis.opsForValue().setIfAbsent(
            "idem:" + bizKey, IdempotentStatus.PROCESSING.name(), PROCESSING_TTL);
        if (Boolean.FALSE.equals(acquired)) {
            String status = redis.opsForValue().get("idem:" + bizKey);
            if (IdempotentStatus.SUCCESS.name().equals(status)) {
                // 已成功，直接返回首次结果，不再执行业务
                return recordMapper.selectResult(bizKey);
            }
            throw new IdempotentProcessingException("请求正在处理中，请稍后查询结果");
        }
        try {
            T result = action.get();
            // 第二步：落库结果并置为成功，数据库唯一索引是最后一道防线
            recordMapper.insertSuccess(bizKey, toJson(result));
            redis.opsForValue().set("idem:" + bizKey, IdempotentStatus.SUCCESS.name(), Duration.ofHours(24));
            return result;
        } catch (DuplicateKeyException e) {
            // 并发下另一个线程已写入，按成功处理
            return recordMapper.selectResult(bizKey);
        } catch (RuntimeException e) {
            redis.delete("idem:" + bizKey);
            throw e;
        }
    }
}
```

**幂等键的选取原则（决定这套方案是否成立）：**

- 优先用业务唯一号：`订单号 + 操作类型`，例如 `ORDER_PAY:202611030001`。
- 其次用客户端生成的 requestId，同一业务动作重试时保持不变。
- 禁止用消息 ID、UUID、时间戳、自增 ID 作为幂等键，重试后必然变化。
- 键的粒度要等于「业务动作」，退款和支付共用订单号会互相误判。

**故障场景与兜底：**

- 进程在处理中崩溃，Redis 里停留在 `PROCESSING`：靠 60 秒 TTL 自然过期，同时落一张处理日志表，由对账任务扫描超过阈值仍为处理中的记录，人工或自动重放。
- Redis 整体不可用：降级为「只依赖数据库唯一索引」，宁可返回失败让上游重试，也不要放行重复写。
- 唯一索引冲突但业务确实需要再次执行（例如同一订单多次部分退款）：说明幂等键粒度错了，必须把动作序号纳入键，而不是放弃幂等。
- 幂等记录表无限增长：按业务保留期分区，例如只保留 30 天，过期后由归档任务清理。

**面试怎么答：** 先给一句定义，再强调「幂等是分层的，不是加个注解就完事」；按协议、接入、应用、存储、消息五层各说一个手段和它的遗留问题；然后落到幂等键怎么选（业务唯一号优先，禁止 UUID）；最后主动补充处理中悬挂、Redis 故障降级、去重表清理三个工程细节，这三点点到即说明真落地过。

**易错点：**

- 以为加了 `@Transactional` 就幂等：事务只保证原子性，不保证重复执行的效果。
- 先查后插判断重复：并发下两个请求都查到不存在，必须靠唯一索引或原子 setIfAbsent 兜底。
- 幂等键用过就删：锁释放了但业务已成功，下一次重复请求仍会再执行一遍。
- 只做写幂等，漏掉旁路副作用：短信、积分、推送重复发放同样是事故。
- 把幂等和去重混为一谈：去重是「丢弃重复请求」，幂等是「重复请求返回同一结果」，用户重试时期望的是后者。

## 2. 幂等键与去重表

**结论：幂等键是「业务动作的唯一标识」，去重表是「幂等键的持久化账本」。生产上最可靠的结构是「Redis 抢锁做快速失败 + 数据库唯一索引做最终兜底 + 结果表支持重复请求直接返回」。**

**幂等键的三种来源：**

| 来源 | 示例 | 优点 | 风险 |
| --- | --- | --- | --- |
| 客户端请求号 | Header `X-Request-Id` | 重试可复用，语义清晰 | 客户端可能每次生成新值 |
| 业务唯一号 | 订单号 + 动作类型 + 序号 | 天然唯一，可回溯 | 需要业务模型支持 |
| 内容摘要 | 参数排序后 SHA-256 | 无需客户端配合 | 参数含时间戳时摘要会变 |

**去重表三种实现对比：**

| 方案 | 原子性 | 性能 | 结果复用 | 适用 |
| --- | --- | --- | --- | --- |
| 数据库唯一索引 + insert ignore | 强，由数据库保证 | 中，每次一次写 | 需再查一次结果表 | 金额、订单等强一致场景 |
| Redis SETNX + 状态值 | 强，单命令原子 | 高 | 可在 value 中存结果 | 高并发、可接受最终一致 |
| 状态机表（PROCESSING/SUCCESS） | 强，条件更新 | 中 | 支持「处理中」语义 | 长耗时业务，如调用三方 |
| 布隆过滤器 | 弱，有假阳性 | 极高 | 不支持 | 只做前置拦截，不能单独使用 |

**表结构设计（关键字段缺一不可）：**

```sql
CREATE TABLE idempotent_record (
    id            BIGINT       NOT NULL AUTO_INCREMENT,
    biz_key       VARCHAR(128) NOT NULL COMMENT '业务唯一键',
    biz_type      VARCHAR(64)  NOT NULL COMMENT '业务类型，便于分治与清理',
    status        TINYINT      NOT NULL COMMENT '0处理中 1成功 2失败',
    result_data   TEXT         NULL COMMENT '首次执行结果，用于重复请求返回',
    created_at    DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at    DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    PRIMARY KEY (id),
    UNIQUE KEY uk_biz_key (biz_key),
    KEY idx_type_time (biz_type, created_at)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4;
```

**代码示例（Java，唯一索引 + 条件更新，可复用的去重逻辑）：**

```java
@Service
public class OrderPayService {

    private final IdempotentRecordMapper recordMapper;
    private final OrderMapper orderMapper;

    @Transactional(rollbackFor = Exception.class)
    public PayResult pay(String orderNo, BigDecimal amount) {
        String bizKey = "ORDER_PAY:" + orderNo + ":" + amount.stripTrailingZeros().toPlainString();
        IdempotentRecord record = new IdempotentRecord();
        record.setBizKey(bizKey);
        record.setBizType("ORDER_PAY");
        record.setStatus(0);

        try {
            recordMapper.insert(record);
        } catch (DuplicateKeyException e) {
            IdempotentRecord exist = recordMapper.selectByBizKey(bizKey);
            if (exist.getStatus() == 1) {
                return PayResult.fromJson(exist.getResultData());
            }
            if (exist.getStatus() == 0) {
                throw new BizException("支付处理中，请勿重复提交");
            }
            throw new BizException("上次支付失败，请更换支付方式");
        }

        // 只在这里执行真正的扣款，且必须与去重记录在同一事务
        PayResult result = doPay(orderNo, amount);
        recordMapper.markSuccess(bizKey, result.toJson());
        return result;
    }
}
```

**Redis 版本的原子写法（Lua，4 空格缩进）：**

```lua
-- KEYS[1] = 幂等键，ARGV[1] = 状态值，ARGV[2] = 过期秒数
-- 返回 1 表示抢到执行权，0 表示重复请求
local ok = redis.call('SET', KEYS[1], ARGV[1], 'NX', 'EX', tonumber(ARGV[2]))
if ok then
    return 1
end
return 0
```

**故障场景与兜底：**

- 去重记录写入成功但业务事务回滚：记录与业务必须在同一本地事务，否则会出现「记录说成功、实际没扣款」，这是最隐蔽的资损来源。
- 状态长期停留在「处理中」：设置超时判定（例如 5 分钟），超时后置为失败并允许重试，同时记录告警。
- 同一订单分多笔支付：幂等键必须带金额或支付流水序号，否则第二笔会被误判为重复。
- 分库分表后唯一索引失效：唯一索引必须落在同一分片，按订单号分片即可保证。

**面试怎么答：** 先说幂等键的三类来源和选取优先级，再说「Redis 快失败 + 唯一索引兜底 + 结果表复用」的组合结构，然后讲表结构里必须有 status 与 result_data 两个字段，最后讲「去重记录与业务同事务」这个最容易踩的坑。如果能补充「同一订单多笔支付要用金额或流水号做键」，基本可以判断做过支付类业务。

**易错点：**

- 把去重表放在另一个库或另一个事务里：原子性丢失，出现记录与业务不一致。
- 用 `select` 判断是否存在再 `insert`：并发下双写，必须依赖唯一约束捕获异常。
- Redis 去重不加过期时间：键无限增长，且业务成功后重复请求仍被拒绝。
- 只存「已处理」标记不存结果：用户重试拿不到首次结果，体验与一致性都差。
- 忽略去重表的清理：单表过亿后写入变慢，必须按时间分区或定期归档。

## 3. 令牌桶与漏桶

**结论：令牌桶是「按固定速率往桶里放令牌，请求取令牌才能通过」，桶容量决定允许的突发量；漏桶是「请求先入桶，桶以固定速率流出」，输出速率绝对平滑。需要允许突发用令牌桶，需要绝对平滑用漏桶。**

**本质差异：** 令牌桶限制的是「平均速率 + 突发上限」，短期内可以一次性消耗积累的令牌；漏桶限制的是「流出速率」，无论进来多少，出去永远是恒定速率，超出容量的请求被丢弃或排队。

**算法对比：**

| 维度 | 令牌桶 | 漏桶 |
| --- | --- | --- |
| 控制对象 | 平均速率，允许突发 | 流出速率，绝对平滑 |
| 突发流量 | 允许，上限为桶容量 | 不允许，超出即排队或丢弃 |
| 实现复杂度 | 中，需要惰性补充令牌 | 低，队列 + 定时消费 |
| 典型实现 | Guava `RateLimiter`、`golang.org/x/time/rate` | Nginx `limit_req`、Sentinel 匀速排队 |
| 适用场景 | 对外 API 限流、保护下游 | 削峰填谷、保护脆弱的下游存储 |

**关键参数：** Guava `RateLimiter.create(100)` 表示每秒 100 个许可，内部 `SmoothBursty` 的 `maxBurstSeconds` 默认 1.0，即最大可存储 1 秒的令牌（100 个），所以瞬时最多放行 100 个请求。`SmoothWarmingUp` 用于冷启动预热，构造时指定 `warmupPeriod`，预热期内速率逐步爬升到设定值。

**代码示例（Java，Guava 令牌桶 + 手写漏桶）：**

```java
public class RateLimitConfig {

    // 令牌桶：每秒 200 个许可，允许 1 秒突发，即瞬时最多 200 个
    private final RateLimiter apiLimiter = RateLimiter.create(200.0);

    // 预热模式：每秒 200 个，预热 3 秒，适合刚启动时缓存为空的下游
    private final RateLimiter warmupLimiter = RateLimiter.create(200.0, 3, TimeUnit.SECONDS);

    public void acquireOrReject() {
        // tryAcquire 不阻塞，拿不到令牌立即返回 false，用于快速失败
        if (!apiLimiter.tryAcquire(50, TimeUnit.MILLISECONDS)) {
            throw new RateLimitException("请求过于频繁");
        }
    }
}
```

```java
public class LeakyBucket {

    private final int capacity;
    private final int ratePerSecond;
    private final Deque<Long> queue = new ArrayDeque<>();
    private long lastLeakTime = System.currentTimeMillis();

    public LeakyBucket(int capacity, int ratePerSecond) {
        this.capacity = capacity;
        this.ratePerSecond = ratePerSecond;
    }

    public synchronized boolean tryAcquire() {
        long now = System.currentTimeMillis();
        // 按经过时间流出，最多把桶漏空
        long leaked = (now - lastLeakTime) * ratePerSecond / 1000;
        if (leaked > 0) {
            for (int i = 0; i < leaked && !queue.isEmpty(); i++) {
                queue.pollFirst();
            }
            lastLeakTime = now;
        }
        if (queue.size() >= capacity) {
            return false;
        }
        queue.addLast(now);
        return true;
    }
}
```

**Go 版本（官方扩展库，生产首选）：**

```go
limiter := rate.NewLimiter(rate.Limit(200), 100)
// Wait 阻塞直到拿到令牌或 context 取消，适合后台任务
if err := limiter.Wait(ctx); err != nil {
    return err
}
// Allow 不阻塞，适合 HTTP 入口快速拒绝
if !limiter.Allow() {
    http.Error(w, "too many requests", http.StatusTooManyRequests)
    return
}
```

**故障场景与兜底：**

- 单机限流 × 集群实例数：10 台机器各限 200 QPS，集群实际放行 2000 QPS，远超下游容量。必须把总阈值按实例数分摊，或用集中式限流。
- 桶容量设置过大：突发放行量等于容量，下游瞬间被打满，等于没限流。容量应按下游能承受的瞬时峰值设定，通常不超过 1 秒的许可数。
- 预热模式用于已预热的热点接口：前几秒大量请求被拒，属于参数误用。
- 限流后没有降级：被拒请求直接 500，应返回 429 并带 `Retry-After`，同时前端做退避。

**面试怎么答：** 先用一句话说清「令牌桶控平均速率且允许突发，漏桶控流出速率且绝对平滑」，再举 Guava `RateLimiter` 的 `maxBurstSeconds=1` 说明突发量从哪来，然后讲单机限流在集群下失效这个坑，最后给出「总阈值按实例分摊或集中式」的解法。能主动提 `tryAcquire` 与 `acquire` 的阻塞差异，说明真用过。

**易错点：**

- 把 Guava `RateLimiter` 当分布式限流用：它只在单 JVM 内有效。
- 认为令牌桶能限制总并发：它限制速率，不限制正在处理中的请求数，并发要靠信号量。
- 漏桶实现里用定时任务消费队列：定时精度差且线程开销大，应按时间差惰性计算。
- 忘记桶容量与速率是两个独立参数：只调速率不调容量，突发行为不会改变。
- 限流阈值照抄压测值：压测是单接口满负载，生产是混合流量，阈值应留 30% 余量。

## 4. 滑动窗口限流

**结论：固定窗口在窗口边界会放行接近 2 倍的流量，滑动窗口通过「窗口随时间滑动」消除边界突变。工程上主流是滑动窗口计数（分桶近似），精度要求极高时用滑动窗口日志（ZSET 精确记录）。**

**固定窗口的边界问题：** 限制每分钟 100 次，在第 59 秒打满 100 次，第 61 秒（新窗口）又能打满 100 次，实际 2 秒内放行了 200 次，是阈值的 2 倍。

**三种窗口方案对比：**

| 方案 | 精度 | 存储成本 | 实现 | 适用 |
| --- | --- | --- | --- | --- |
| 固定窗口 | 低，边界 2 倍 | 极低，一个计数器 | Redis INCR + EXPIRE | 粗粒度配额、非核心 |
| 滑动窗口日志 | 精确到请求级 | 高，每个请求一条记录 | Redis ZSET，按时间戳删旧 | 低频、强精度场景 |
| 滑动窗口计数 | 近似，误差随分桶数下降 | 中，每个小窗口一个计数 | 分桶计数 + 加权求和 | 高并发主流方案 |

**滑动窗口计数的估算公式：** 把 1 分钟切成 6 个 10 秒桶，当前滑动窗口的计数 = 上一个完整桶 + 部分当前桶，按时间比例加权。桶越多越精确，通常 10 到 60 个桶即可。

**代码示例（Lua，Redis ZSET 精确滑动窗口，4 空格缩进）：**

```lua
-- KEYS[1] = 限流 key，ARGV[1] = 当前时间戳(毫秒)，ARGV[2] = 窗口毫秒，ARGV[3] = 阈值
local key = KEYS[1]
local now = tonumber(ARGV[1])
local window = tonumber(ARGV[2])
local limit = tonumber(ARGV[3])

-- 1. 移除窗口外的旧请求
redis.call('ZREMRANGEBYSCORE', key, 0, now - window)

-- 2. 统计窗口内请求数
local count = redis.call('ZCARD', key)
if count >= limit then
    return 0
end

-- 3. member 必须唯一，否则同一毫秒的请求会互相覆盖
redis.call('ZADD', key, now, ARGV[4])
-- 4. 过期时间略大于窗口，避免 key 永久存在
redis.call('PEXPIRE', key, window)

return limit - count - 1
```

**Java 调用侧：**

```java
public boolean tryAcquire(String userId) {
    String key = "rate:slide:" + userId;
    long now = System.currentTimeMillis();
    // member 用 UUID，保证同一毫秒多请求不会被 ZADD 覆盖
    String member = now + ":" + UUID.randomUUID();
    Long remain = redis.execute(SLIDE_SCRIPT, List.of(key),
        String.valueOf(now), "60000", "100", member);
    return remain != null && remain >= 0;
}
```

**滑动窗口计数版本（分桶，适合超大流量）：**

```java
public boolean tryAcquireByBucket(String key, int limit, int windowSeconds, int bucketCount) {
    long now = System.currentTimeMillis() / 1000;
    int bucketSize = windowSeconds / bucketCount;
    long currentBucket = now / bucketSize;
    long offsetInBucket = now % bucketSize;

    String currentKey = key + ":" + currentBucket;
    String lastKey = key + ":" + (currentBucket - 1);

    Long current = redis.opsForValue().increment(currentKey);
    redis.expire(currentKey, Duration.ofSeconds(windowSeconds * 2L));
    Long last = Optional.ofNullable(redis.opsForValue().get(lastKey))
        .map(Long::valueOf).orElse(0L);

    // 上一个桶按剩余时间比例计入，近似还原滑动窗口
    double estimated = current + last * (1 - (double) offsetInBucket / bucketSize);
    return estimated < limit;
}
```

**故障场景与兜底：**

- ZSET 变成大 key：单 key 记录整个窗口的每个请求，10 万 QPS 下就是 600 万成员，内存与 CPU 双爆。高流量必须改用分桶计数或令牌桶。
- member 使用纯时间戳：同一毫秒的并发请求互相覆盖，实际放行数偏少，限流失真。
- 客户端时钟不一致：多实例传入各自时间，窗口判断错乱。时间戳应由 Redis `TIME` 或统一时间源提供。
- 限流 key 不带用户维度：一个热点用户打满全局限额，其他用户被误伤，需按 IP、用户、接口多维分 key。

**面试怎么答：** 先讲固定窗口的边界 2 倍问题，这是引出滑动窗口的唯一理由；再给三种方案对比，明确「生产用分桶近似，精确场景才用 ZSET」；然后说 ZSET 大 key 和 member 唯一性两个坑；最后给时间源统一的解法。能说出「桶数决定精度」比背算法名更有价值。

**易错点：**

- 用滑动窗口日志做全局限流：QPS 上万时 Redis 直接被拖垮。
- `ZREMRANGEBYSCORE` 用 `-inf` 到 `now-window` 却忘了 `PEXPIRE`，key 永久残留。
- member 用请求 ID 但忘记去重意义：ZSET 本身按 member 去重，member 必须全局唯一。
- 分桶计数里当前桶不做 `expire`，历史桶无限增长。
- 认为滑动窗口能解决集群限流：它仍是单 key 维度，跨实例还是各算各的。

## 5. 分布式限流

**结论：单机限流只能保护「本实例」，保护不了「下游总容量」。分布式限流要解决的是全局配额分配，主流有三类：集中式（Redis/Lua 原子计数）、集群流控（Sentinel Token Server）、配额下发（按实例分摊 + 本地令牌桶）。**

**三类方案对比：**

| 方案 | 一致性 | 性能开销 | 可用性风险 | 适用 |
| --- | --- | --- | --- | --- |
| Redis + Lua 集中计数 | 强，单 key 原子 | 每次限流一次网络往返 | Redis 故障即限流失效 | 中小规模、调用频次可控 |
| Sentinel 集群流控 | 强，Token Server 统一发令牌 | 一次 RPC，可批量 | Token Server 需高可用 | 大规模、需要动态规则 |
| 配额下发 + 本地限流 | 最终一致，允许少量偏差 | 极低，本地内存 | 配额发放延迟 | 超高 QPS、可容忍偏差 |
| 网关层统一限流 | 强，入口唯一 | 网关成为瓶颈 | 网关需集群化 | 南北向流量、多租户 |

**核心原则：限流点要尽量靠前（网关），限流维度要尽量细（用户/IP/接口/租户），限流阈值要按「下游真实容量」反推，而不是按「上游希望放行多少」拍脑袋。**

**代码示例（Redis + Lua 分布式令牌桶，4 空格缩进）：**

```lua
-- KEYS[1] = 桶 key
-- ARGV[1] = 速率(个/秒)，ARGV[2] = 桶容量，ARGV[3] = 当前时间(毫秒)，ARGV[4] = 本次请求令牌数
local rate = tonumber(ARGV[1])
local capacity = tonumber(ARGV[2])
local now = tonumber(ARGV[3])
local requested = tonumber(ARGV[4])

local bucket = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
local tokens = tonumber(bucket[1])
local ts = tonumber(bucket[2])
if tokens == nil then
    tokens = capacity
    ts = now
end

-- 惰性补充：按时间差补令牌，最多补到容量上限
local delta = math.max(0, now - ts)
local filled = math.min(capacity, tokens + delta * rate / 1000)

local allowed = 0
if filled >= requested then
    filled = filled - requested
    allowed = 1
end

redis.call('HMSET', KEYS[1], 'tokens', filled, 'ts', now)
-- 桶空了以后 key 可以过期，过期时间按补满所需时间计算
redis.call('PEXPIRE', KEYS[1], math.ceil(capacity / rate * 1000))

return allowed
```

**Java 调用与降级策略：**

**Sentinel 集群流控配置（Java，4 空格缩进）：**

**故障场景与兜底：**

- Redis 故障导致限流全部失效：必须显式选择 fail-open（保业务，可能打垮下游）或 fail-close（保下游，业务受损），核心交易通常 fail-open + 本地兜底限流。
- 热点 key：单 key 承载全部流量，Redis 单分片 CPU 打满。按用户 ID 哈希打散，或把全局配额拆成多 key 汇总。
- 每次请求一次网络往返：限流本身增加 0.5 到 2 毫秒延迟，超高 QPS 场景应改为「批量领令牌」，一次领 100 个在本地消费。
- 实例数变化导致总阈值漂移：配额按注册实例动态下发，实例下线后要及时回收配额。

**面试怎么答：** 先点明单机限流的总量失控问题，再给四类方案对比并说明各自的一致性、性能、可用性代价；然后讲「限流点前移、维度细化、阈值按下游容量反推」三条原则；最后重点讲 Redis 故障时的 fail-open 与 fail-close 取舍，以及热点 key 打散。能说出「批量领令牌」说明考虑过性能。

**易错点：**

- 用 `INCR` + `EXPIRE` 两条命令做限流：非原子，高并发下计数与过期都会错。
- Lua 脚本里用 `redis.call('TIME')`：部分托管 Redis 禁用，应由客户端传时间。
- 只按接口维度限流：单个用户刷接口仍能打满，必须叠加用户维度。
- 限流阈值等于压测峰值：没有余量，正常波动就触发限流。
- 分布式限流不做降级：Redis 一抖动，全站 429，故障面被放大。

## 6. 熔断器设计

**结论：熔断器是「当下游错误率或慢调用比例超过阈值时，快速失败一段时间，给下游恢复窗口」的状态机，核心是 CLOSED、OPEN、HALF_OPEN 三态与滑动窗口统计。**

**三态语义：**

| 状态 | 行为 | 进入条件 | 退出条件 |
| --- | --- | --- | --- |
| CLOSED | 正常放行，统计结果 | 初始状态 / HALF_OPEN 试探成功 | 错误率或慢调用率超阈值且样本足够 |
| OPEN | 直接拒绝，不调用下游 | CLOSED 达阈值 | 等待时长结束 |
| HALF_OPEN | 放行少量试探请求 | OPEN 等待期结束 | 试探成功回 CLOSED，失败回 OPEN |

**主流实现对比：**

| 组件 | 统计方式 | 特点 | 现状 |
| --- | --- | --- | --- |
| Resilience4j | 环形缓冲区滑动窗口，计数或时间 | 轻量、函数式、Spring Boot 3 首选 | 活跃维护 |
| Sentinel | 秒级滑动窗口，错误率/慢调用比例/异常数 | 规则动态推送、带控制台 | 国内主流 |
| Hystrix | 滑动窗口 + 线程池隔离 | 功能全但已停止维护 | 不推荐新项目 |
| gobreaker | 计数窗口 | 简单、Go 生态常用 | 活跃维护 |

**Resilience4j 关键默认值（必须记准）：**

| 参数 | 默认值 | 含义 |
| --- | --- | --- |
| `slidingWindowSize` | 100 | 统计窗口内保留的调用次数 |
| `minimumNumberOfCalls` | 100 | 达到该样本量才开始计算失败率 |
| `failureRateThreshold` | 50 | 失败率百分比阈值 |
| `slowCallRateThreshold` | 100 | 慢调用比例阈值，默认等于不生效 |
| `slowCallDurationThreshold` | 60s | 判定慢调用的耗时门槛 |
| `waitDurationInOpenState` | 60s | OPEN 持续时长 |
| `permittedNumberOfCallsInHalfOpenState` | 10 | HALF_OPEN 允许的试探数 |
| `automaticTransitionFromOpenToHalfOpenEnabled` | false | 是否自动进入 HALF_OPEN |

**代码示例（Resilience4j，YAML + Java，4 空格缩进）：**

```yaml

        instances:
            inventory:
                sliding-window-size: 100
                minimum-number-of-calls: 50
                failure-rate-threshold: 50

                slow-call-rate-threshold: 80
```

```java
@Service

    private final CircuitBreaker breaker;
    private final InventoryClient client;

    public InventoryService(CircuitBreakerRegistry registry, InventoryClient client) {
        this.breaker = registry.circuitBreaker("inventory");
        this.client = client;
    }

    public int queryStock(String sku) {
        // 业务异常不计入失败率，只有超时、网络异常才计入
        return breaker.executeSupplier(() -> client.queryStock(sku));
    }
}
```

**故障场景与兜底：**

- 熔断与重试叠加：熔断 OPEN 后上游重试 3 次，等于把拒绝放大 3 倍，还会拖长线程占用。熔断打开时必须关闭该依赖的重试。
- HALF_OPEN 放行过多：`permittedNumberOfCallsInHalfOpenState` 设为 100，下游还没恢复就被再次打挂。通常设为并发量的 5% 到 10%。
- 统计窗口内样本不足：`minimumNumberOfCalls` 设得过大，低流量接口永远不熔断；设得过小，偶发一次失败就熔断。
- 熔断只统计异常不统计超时：下游「慢而不死」是最常见的故障形态，必须开启慢调用比例统计。
- 熔断后没有降级：直接抛异常给用户，应返回兜底数据或排队提示。

**面试怎么答：** 先画三态转换并说明每态的判定条件，再讲滑动窗口统计「失败率 + 慢调用比例」两个指标，然后给一组生产参数（窗口 100、最少样本 50、失败率 50%、OPEN 30 秒、HALF_OPEN 5 个），最后讲熔断与重试叠加、HALF_OPEN 放行量两个坑。参数说得具体，可信度立刻不同。

**易错点：**

- 把熔断当限流：熔断看「错误比例」，限流看「请求速率」，目标完全不同。
- 业务异常也计入失败率：参数校验失败会把熔断器误触发，必须 ignore。
- OPEN 状态直接永久拒绝：没有 HALF_OPEN 试探，下游恢复了也回不去。
- 熔断阈值按单实例统计却共享状态：集群下每个实例各自熔断，行为不一致。
- 只配熔断不配超时：没有超时，请求会一直挂到熔断统计窗口外，慢调用根本统计不到。

## 7. 降级与兜底

**结论：降级是「在依赖不可用或容量不足时，主动放弃非核心功能，保住核心链路」；兜底是「降级时给用户一个可接受的替代结果」。降级是策略，兜底是数据，两者必须成对设计。**

**降级手段分类：**

| 类型 | 做法 | 示例 | 风险 |
| --- | --- | --- | --- |
| 功能降级 | 关闭非核心功能 | 大促关闭商品推荐、评价展示 | 用户体验下降，需产品确认 |
| 读降级 | 读缓存/读副本/读本地快照 | 库存查缓存、商品详情读静态页 | 数据可能过期 |
| 写降级 | 异步化、排队、写本地消息表 | 下单转异步、积分延迟到账 | 一致性变为最终一致 |
| 流量降级 | 限流、排队、剔除低优先级流量 | 非会员请求排队 | 可能误伤正常用户 |
| 数据兜底 | 返回默认值、空列表、历史快照 | 推荐位返回运营配置兜底 | 兜底数据本身要能扛住 |

**触发方式对比：**

| 触发方式 | 说明 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 手动开关 | 配置中心一键切换 | 可控、可回滚 | 依赖人工发现 |
| 自动熔断触发 | 熔断 OPEN 时自动走降级分支 | 秒级生效 | 可能误判 |
| 阈值触发 | 错误率、RT、队列水位超阈值 | 可量化 | 阈值调优成本高 |
| 定时降级 | 大促前预设降级预案 | 确定性高 | 不适用于突发故障 |

**代码示例（Java，多级兜底，4 空格缩进）：**

```java
@Service
public class ProductDetailService {

    private final ProductClient productClient;
    private final RedisTemplate<String, String> redis;
    private final DegradeSwitch degradeSwitch;

    public ProductDetailVO detail(String sku) {
        // 第一级：降级开关打开时，直接走缓存兜底
        if (degradeSwitch.isOn("product.detail.cacheOnly")) {
            return fromCache(sku);
        }
        try {
            ProductDetailVO vo = productClient.detail(sku);
            redis.opsForValue().set("product:detail:" + sku, toJson(vo), Duration.ofMinutes(10));
            return vo;
        } catch (Exception e) {
            // 第二级：实时接口失败，回读缓存
            ProductDetailVO cached = fromCache(sku);
            if (cached != null) {
                return cached;
            }
            // 第三级：缓存也没有，返回最小可用信息，绝不返回 null
            return ProductDetailVO.builder()
                .sku(sku)
                .title("商品信息加载中")
                .available(false)
                .build();
        }
    }

    private ProductDetailVO fromCache(String sku) {
        String json = redis.opsForValue().get("product:detail:" + sku);
        return json == null ? null : fromJson(json);
    }
}
```

**降级开关配置（YAML，4 空格缩进）：**

```yaml

    switches:
        product.detail.cacheOnly:
            enabled: false
            owner: product-team
            effective-time: "2026-11-11 20:00:00"
        order.create.async:
            enabled: false
            owner: trade-team
            max-qps: 2000
    # 开关必须带自动恢复与到期提醒，避免遗忘
    auto-recover:
        enabled: true
        max-duration: 2h
```

**故障场景与兜底：**

- 兜底数据本身过期或为空：缓存击穿时降级路径直接返回 null，引发 NPE。兜底必须保证「一定返回一个合法对象」。
- 降级开关忘记关闭：大促结束后仍在降级，用户长期看到旧数据。必须设置最长生效时长与到期告警。
- 降级路径从未被压测：真正故障时才发现缓存 QPS 扛不住，降级反而制造新故障。
- 降级范围过大：把核心的库存校验也降级，导致超卖，降级清单必须由业务确认「可放弃」的部分。
- 降级与重试冲突：降级分支里还在重试原依赖，等于没降级。

**面试怎么答：** 先区分降级（放弃功能）与兜底（给替代结果），再按功能、读、写、流量、数据五类各举一例；然后讲触发方式，强调「手动开关 + 自动熔断」双通道；最后讲三个工程细节：兜底不能返回 null、开关要有到期自动恢复、降级路径必须压测。这三点是区分「知道概念」和「做过预案」的关键。

**易错点：**

- 降级返回 null 或空对象：调用方没做判空，故障从下游扩散到上游。
- 把降级写成 try-catch 吞异常：异常被吞掉但没记录，故障不可见。
- 降级开关存在本地内存：多实例状态不一致，部分机器降级部分不降。
- 只降级不监控：降级期间业务指标变化没人看，等于掩盖故障。
- 降级预案没有优先级：所有功能一起降，核心链路也被波及。

## 8. 隔离舱与舱壁模式

**结论：舱壁模式（Bulkhead）是把不同依赖的调用隔离开，各自使用独立的线程池、连接池、信号量，避免一个慢依赖耗尽共享资源，拖垮所有接口。**

**要隔离的四类资源：**

| 资源 | 不隔离的后果 | 隔离手段 | 开销 |
| --- | --- | --- | --- |
| 线程 | 慢依赖占满 Tomcat 线程，全站无可用线程 | 每个下游独立线程池 + 有界队列 | 线程数增加，上下文切换 |
| 连接 | 一个下游的连接池被打满，其他下游拿不到连接 | 按下游拆连接池 | 连接数增加 |
| 信号量 | 并发无上限，下游被打挂 | 每个依赖独立 Semaphore | 极低 |
| 部署 | 一个服务拖垮整机资源 | 独立容器 + 资源 limit | 运维成本 |

**线程池隔离 vs 信号量隔离：**

| 维度 | 线程池隔离 | 信号量隔离 |
| --- | --- | --- |
| 是否异步 | 是，调用方线程立即释放 | 否，仍在调用方线程执行 |
| 超时控制 | 支持，Future.get 带超时 | 不支持，靠下游超时 |
| 上下文传递 | 需要显式传递 TraceId、用户上下文 | 天然在同一线程，无丢失 |
| 开销 | 线程切换 + 队列 | 几乎为零 |
| 适用 | 强依赖、需要快速失败 | 轻量调用、线程模型不适合异步 |

**代码示例（Java，按下游隔离线程池 + 信号量，4 空格缩进）：**

```java
@Configuration
public class BulkheadConfig {

    // 库存查询：核心链路，线程池较大，队列有界，拒绝策略抛异常快速失败
    @Bean("inventoryExecutor")
    public ThreadPoolExecutor inventoryExecutor() {
        return new ThreadPoolExecutor(
            32, 64, 60, TimeUnit.SECONDS,
            new ArrayBlockingQueue<>(200),
            new ThreadPoolExecutor.AbortPolicy());
    }

    // 推荐服务：非核心，线程池小，满了直接降级
    @Bean("recommendExecutor")
    public ThreadPoolExecutor recommendExecutor() {
        return new ThreadPoolExecutor(
            8, 16, 60, TimeUnit.SECONDS,
            new ArrayBlockingQueue<>(50),
            new ThreadPoolExecutor.CallerRunsPolicy());
    }
}
```

```java
@Service
public class RecommendService {

    private final ThreadPoolExecutor recommendExecutor;
    private final Semaphore recommendSemaphore = new Semaphore(20);

    public RecommendService(@Qualifier("recommendExecutor") ThreadPoolExecutor recommendExecutor) {
        this.recommendExecutor = recommendExecutor;
    }

    public List<String> recommend(String userId) {
        // 信号量先做并发闸门，拿不到立刻降级，不占用线程
        if (!recommendSemaphore.tryAcquire()) {
            return Collections.emptyList();
        }
        try {
            Future<List<String>> future = recommendExecutor.submit(() -> client.recommend(userId));
            return future.get(200, TimeUnit.MILLISECONDS);
        } catch (Exception e) {
            futureCleanup();
            return Collections.emptyList();
        } finally {
            recommendSemaphore.release();
        }
    }
}
```

**线程池容量估算（Little 定律）：**

```text
    所需线程数 = QPS × 平均响应时间(秒) × 冗余系数
    例：QPS 500，平均 RT 20ms，冗余 2 倍
        线程数 = 500 × 0.02 × 2 = 20，队列按 5 到 10 倍 RT 的排队量设置
```

**故障场景与兜底：**

- 线程池隔离导致线程数暴涨：20 个下游各配 50 线程，单机 1000 线程，GC 与切换开销反噬。必须按「QPS × RT」精算，并设总数上限。
- 队列无界：慢依赖时任务无限堆积，内存 OOM 且延迟无限增长。队列必须有界，且拒绝策略要明确（抛异常、降级、丢弃）。
- 信号量与线程池重复限流：两层都设很小，实际并发被压到最低，需明确谁是主闸门。
- 隔离后监控缺失：每个池的活跃线程、队列长度、拒绝次数都要上报，否则无法判断隔离是否生效。

**面试怎么答：** 先讲「共享线程池导致一个慢依赖拖垮全站」这个典型故障，引出舱壁模式；再列线程、连接、信号量、部署四类隔离资源；然后对比线程池隔离与信号量隔离的取舍（超时能力 vs 上下文传递）；最后给线程池容量公式和「队列必须有界」两个硬结论。

**易错点：**

- 只隔离线程池不隔离连接池：线程没打满但连接耗尽，故障依旧。
- 队列用 `LinkedBlockingQueue` 无参构造：默认容量 `Integer.MAX_VALUE`，等于无界。
- 拒绝策略用 `DiscardPolicy`：静默丢任务，调用方永远等不到结果。
- 隔离线程池不传 TraceId：异步后链路断掉，排障成本剧增。
- 线程数按「下游个数 × 固定值」拍脑袋，不做压测校准。

## 9. 重试策略与退避

**结论：重试只应对「瞬时故障 + 幂等操作」，必须配指数退避与随机抖动，并设最大次数和总时限。无脑重试是把局部故障放大成全局雪崩的最快方式。**

**哪些错误可以重试：**

| 错误类型 | 示例 | 是否重试 |
| --- | --- | --- |
| 网络瞬时异常 | 连接重置、连接超时 | 是 |
| 下游过载 | HTTP 429、503 | 是，且必须退避 |
| 下游明确不可用 | 连接拒绝 | 是，短次数 |
| 业务错误 | 参数非法、余额不足、401/403 | 否 |
| 非幂等写操作 | 下单、扣款未做幂等 | 否 |
| 数据库唯一键冲突 | DuplicateKey | 否，按幂等成功处理 |

**退避策略对比：**

| 策略 | 第 n 次等待 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 固定间隔 | 固定 500ms | 简单 | 重试风暴时同时冲击 |
| 线性退避 | n × 500ms | 稍平滑 | 大次数下等待过长 |
| 指数退避 | 500ms × 2^(n-1) | 快速让出资源 | 后期等待过长，需上限 |
| 指数退避 + 抖动 | 上值 × random(0.5, 1.5) | 打散重试时刻，避免共振 | 实现稍复杂 |

**代码示例（Resilience4j Retry，YAML + Java，4 空格缩进）：**

```yaml

                max-attempts: 3
```

**Go 版本（指数退避 + 抖动）：**

```go
func callWithBackoff(ctx context.Context, fn func() error) error {
    backoff := 300 * time.Millisecond
    for attempt := 1; attempt <= 3; attempt++ {
        err := fn()
        if err == nil {
            return nil
        }
        if !isRetryable(err) || attempt == 3 {
            return err
        }
        // 加 0.5 到 1.5 倍随机抖动，避免所有客户端同一时刻重试
        jitter := time.Duration(rand.Int63n(int64(backoff)))
        select {
        case <-time.After(backoff/2 + jitter):
            backoff *= 2
        case <-ctx.Done():
            return ctx.Err()
        }
    }
    return nil
}
```

**参数取值经验：**

- 最大次数 2 到 3 次，超过 3 次成功率提升有限，流量却成倍放大。
- 首次等待 200 到 500 毫秒，指数倍率 2，总等待不超过上游超时的 1/3。

**故障场景与兜底：**

- 重试风暴：下游刚恢复，积压的重试同时涌入再次打挂。靠抖动、最大次数、熔断三者共同抑制。
- 重试放大流量：1 次失败 × 3 次重试，峰值流量变为 4 倍，容量规划必须把这部分算进去。
- 非幂等接口重试：重复下单、重复扣款。重试前必须确认接口幂等或带幂等键。
- 重试嵌套：A 重试 3 次调 B，B 重试 3 次调 C，C 收到 9 倍流量。重试只能在一层做。

**面试怎么答：** 先明确「只重试瞬时故障且必须幂等」，再给四类退避策略对比并说明抖动的作用；然后给一组生产参数（3 次、300ms 起、倍率 2、总时限为上游超时的 1/3）；最后讲重试风暴、流量放大、重试嵌套三个放大效应。强调「重试是放大器不是修复器」，观点立刻清晰。

**易错点：**

- 对 4xx 业务错误重试：永远失败，白白消耗 3 倍资源。
- 重试不加抖动：同一批请求同时重试，形成周期性冲击波。
- 只限次数不限总时长：单次超时 5 秒 × 3 次 = 15 秒，用户早已离开。
- 多层都配重试：流量按层数相乘放大。
- 重试与熔断不联动：熔断已打开还在重试，等于持续打一个已知不可用的依赖。

## 10. 超时与重试的传递

**结论：超时必须逐层递减，上游超时要大于下游「单次超时 × 重试次数 + 退避总时长」，并且要用 deadline 向下传递，让下游在调用方放弃后主动停止计算。**

**超时设置的典型错误：**

| 错误 | 后果 |
| --- | --- |
| 只设连接超时不设读超时 | 下游挂死时线程永久阻塞 |
| 各层超时相同（都是 3 秒） | 上游先超时，下游仍在跑，线程与连接被浪费 |
| 上游超时小于下游总耗时 | 上游已返回失败，下游仍在写数据，产生脏数据 |
| 用默认超时 | Feign 默认读超时 60 秒，Dubbo 默认 1000 毫秒，量级完全不同 |
| 超时后不取消下游 | 下游继续执行，资源泄漏，重试叠加 |

**超时预算分配示例（总预算 3000 毫秒）：**

```text
    网关          3000ms（对外承诺）
      └ 订单服务  2500ms（预留 500ms 给网关自身与网络）
          └ 库存服务 800ms × 2 次 + 300ms 退避 = 1900ms
          └ 优惠服务 600ms × 1 次 = 600ms
    剩余预算 = 2500 - 1900 - 600 = 0，必须并发调用而不是串行
```

**代码示例（Go，context deadline 逐层传递）：**

```go
func (s *OrderService) CreateOrder(ctx context.Context, req *CreateOrderRequest) (*Order, error) {
    // 入口统一收敛超时，下游全部继承这个 deadline
    ctx, cancel := context.WithTimeout(ctx, 2500*time.Millisecond)
    defer cancel()

    var wg sync.WaitGroup
    var stockErr, couponErr error

    wg.Add(2)
    go func() {
        defer wg.Done()
        // 子调用超时不得大于父 deadline，WithTimeout 会自动取更小值
        subCtx, subCancel := context.WithTimeout(ctx, 800*time.Millisecond)
        defer subCancel()
        stockErr = s.stock.Deduct(subCtx, req.SkuID, req.Count)
    }()
    go func() {
        defer wg.Done()
        subCtx, subCancel := context.WithTimeout(ctx, 600*time.Millisecond)
        defer subCancel()
        couponErr = s.coupon.Lock(subCtx, req.CouponID)
    }()
    wg.Wait()

    if stockErr != nil {
        return nil, stockErr
    }
    if couponErr != nil {
        return nil, couponErr
    }
    return s.repo.Save(ctx, req)
}
```

**故障场景与兜底：**

- 上游超时短于下游写操作：上游返回失败并重试，下游第一次请求其实成功了，产生重复数据。写接口必须幂等，且下游要在超时后检查状态。
- 超时后不 cancel：Go 里忘记 `defer cancel()` 会泄漏 context 与 goroutine；Java 里 `Future` 不 cancel 会持续占用线程。
- 重试的总时长超过上游超时：上游早已返回，下游还在重试，形成「幽灵流量」。
- 下游没有超时只有上游有：下游内部串行调用多个依赖，累计耗时不可控。
- 超时值写死在代码里：不同部署环境网络差异大，必须可配置。

**面试怎么答：** 先讲「超时预算」的概念：对外承诺一个总时长，按调用树逐层分配，子调用之和必须小于父预算，串行放不下就改并发。再讲 deadline 传递的意义——不只是限制自己，还要让下游知道「调用方已经不等了」。然后给一组具体数字（网关 3 秒、订单 2.5 秒、库存 800 毫秒 × 2 次），最后讲超时后不 cancel 导致的幽灵流量。

**易错点：**

- 各层超时都设成同一个值：等于没有分层预算，最慢的一层决定全部。
- 只在上游设超时：下游自己还会重试，实际耗时是上游的几倍。
- 超时时间小于下游 P99：正常请求也被大量超时，错误率虚高。
- 超时后立刻重试同一个实例：下游可能只是短暂抖动，应换实例或退避。
- 忘记 `defer cancel()`：Go 里是最常见的资源泄漏来源。

## 11. 链路追踪

**结论：链路追踪的本质是「为一次请求生成全局唯一的 TraceId，并在每次跨线程、跨进程、跨消息传递时携带 SpanId 与父 SpanId，最终拼成一棵调用树」。它解决的是「一个请求慢在哪一跳」，而不是「哪个服务挂了」。**

**三个核心概念：**

| 概念 | 含义 | 作用 |
| --- | --- | --- |
| TraceId | 一次完整请求的全局 ID，32 位十六进制 | 串起所有日志与 Span |
| SpanId | 单个操作（一次 RPC、一次 DB 查询）的 ID | 定位具体哪一跳耗时 |
| ParentSpanId | 父 Span 的 ID | 还原调用树与父子关系 |

**方案对比：**

| 方案 | 侵入性 | 存储 | 特点 |
| --- | --- | --- | --- |
| OpenTelemetry + Jaeger | 低，SDK 或 agent | ES/Cassandra | 标准协议，厂商中立，云原生首选 |
| SkyWalking | 极低，Java agent 无侵入 | ES/H2/MySQL | 国内主流，支持拓扑与告警 |
| Zipkin | 低 | ES/MySQL | 轻量，功能相对简单 |
| 自研 TraceId + ELK | 中，需改日志框架 | ES | 成本低，只有日志级串联，无调用树 |

**W3C 标准透传头（跨语言互通的关键）：**

```text
    traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
                 版本 trace-id(32位)            parent-id(16位)  flags
```

**代码示例（Java，MDC + 拦截器 + 异步透传，4 空格缩进）：**

```java
@Component
public class TraceFilter implements Filter {

    private static final String TRACE_ID = "traceId";
    private static final String SPAN_ID = "spanId";

    @Override
    public void doFilter(ServletRequest request, ServletResponse response, FilterChain chain)
            throws IOException, ServletException {
        HttpServletRequest req = (HttpServletRequest) request;
        String traceId = req.getHeader("X-Trace-Id");
        if (traceId == null || traceId.isEmpty()) {
            traceId = UUID.randomUUID().toString().replace("-", "");
        }
        MDC.put(TRACE_ID, traceId);
        MDC.put(SPAN_ID, shortId());
        try {
            ((HttpServletResponse) response).setHeader("X-Trace-Id", traceId);
            chain.doFilter(request, response);
        } finally {
            // 必须清理，线程池复用会污染下一个请求
            MDC.clear();
        }
    }
}
```

```java
public class TraceTaskDecorator implements TaskDecorator {

    @Override
    public Runnable decorate(Runnable runnable) {
        // 提交线程的 MDC 快照，在子线程中恢复，否则异步后 TraceId 丢失
        Map<String, String> context = MDC.getCopyOfContextMap();
        return () -> {
            if (context != null) {
                MDC.setContextMap(context);
            }
            try {
                runnable.run();
            } finally {
                MDC.clear();
            }
        };
    }
```

**采样策略（决定成本，必须回答）：**

| 策略 | 说明 | 适用 |
| --- | --- | --- |
| 头部采样 | 入口按比例决定是否采集整条链路 | 高流量、成本敏感 |
| 尾部采样 | 全量收集后按「慢请求/错误」筛选保留 | 需要保留所有异常链路 |
| 按比例 + 错误必采 | 正常流量 1% 到 10%，错误与慢调用 100% | 生产最常用 |

**故障场景与兜底：**

- 异步线程池丢失 TraceId：日志里出现大量无 TraceId 的记录，链路断裂。必须用 `TaskDecorator` 或 `TransmittableThreadLocal`。
- MQ 消费端不继承 TraceId：生产与消费链路断开，需要用消息 Header 显式传递。
- 采样率 100% 且流量大：存储与采集端被打爆，甚至影响业务。必须分层采样。
- TraceId 由客户端传入且不校验：恶意用户可伪造 TraceId 污染数据，需做格式校验或重新生成。
- 只用 TraceId 不记 SpanId：只能按请求聚合，无法看出是哪个子调用慢。

**面试怎么答：** 先讲 TraceId、SpanId、ParentSpanId 三件套和「拼成调用树」的目标；再讲跨线程、跨进程、跨 MQ 三种传递方式，强调异步与消息是重灾区；然后给 W3C `traceparent` 标准头说明跨语言互通；最后讲采样策略——正常流量比例采样、错误与慢调用全采。能说出「尾部采样」是加分项。

**易错点：**

- 只在 HTTP 入口生成 TraceId，不往下传：下游各自生成，链路断成多段。
- 用 `ThreadLocal` 存 TraceId 却不清理：线程池复用导致串号，日志张冠李戴。
- 采样率写死 100%：上线一周后存储告警。
- TraceId 用自增数字：跨服务重复，且暴露业务量。
- 认为有 TraceId 就等于有链路追踪：没有 Span 与耗时，仍然定位不到慢在哪一跳。

## 12. 容量评估与压测

**结论：容量评估 = 用 Little 定律估算资源需求 + 用压测找拐点 + 留冗余水位。核心输出不是「能扛多少 QPS」，而是「在 P99 延迟和错误率约束下能扛多少 QPS，以及第一个瓶颈在哪里」。**

**Little 定律与常用公式：**

```text
    并发数   = QPS × 平均响应时间(秒)
    线程数   = 并发数 × 冗余系数(1.5 到 2)
    连接数   = 并发数（短连接需乘以 QPS × 建立连接耗时）
    带宽     = QPS × 平均响应体大小 × 8
    存储     = 日增数据量 × 保留天数 × 副本数 × 1.3（索引与碎片）
```

**必须观测的指标：**

| 类别 | 指标 | 健康水位 |
| --- | --- | --- |
| 延迟 | P50 / P95 / P99 / P999 | P99 小于 SLA 的 80% |
| 吞吐 | QPS / TPS | 压测峰值的 70% 以内 |
| 错误率 | 5xx、超时率 | 小于 0.1% |
| 资源 | CPU、内存、GC 次数、磁盘 IO、网络 | CPU 小于 70%，GC 停顿小于 200ms |
| 依赖 | 下游 RT、连接池使用率、队列长度 | 连接池小于 70%，队列不持续增长 |

**压测类型对比：**

| 类型 | 目的 | 做法 |
| --- | --- | --- |
| 基准压测 | 单接口极限 | 逐步加压直到拐点 |
| 容量压测 | 混合场景下的承载 | 按生产流量比例构造请求 |
| 稳定性压测 | 长时间运行是否泄漏 | 70% 压力跑 8 到 24 小时 |
| 破坏性压测 | 依赖故障时的表现 | 拔掉 Redis、MQ、下游 |

**代码示例（k6 压测脚本，4 空格缩进）：**

```javascript
import http from 'k6/http';
import { check, sleep } from 'k6';
import { Rate } from 'k6/metrics';

const errorRate = new Rate('business_error');

export const options = {
    scenarios: {
        ramp: {
            executor: 'ramping-arrival-rate',
            startRate: 50,
            timeUnit: '1s',
            preAllocatedVUs: 200,
            maxVUs: 2000,
            stages: [
                { target: 500, duration: '2m' },
                { target: 1000, duration: '2m' },
                { target: 2000, duration: '5m' },
                { target: 2000, duration: '10m' },
            ],
        },
    },
    thresholds: {
        http_req_duration: ['p(99)<300'],
        http_req_failed: ['rate<0.001'],
    },
};

export default function () {
    const res = http.get('http://gateway/order/detail?orderNo=202611030001', {

```

**故障场景与兜底：**

- 压测环境与生产差异大：机器规格、数据量、依赖部署都不同，压测结论不可迁移。至少保证「同规格机器 + 近似数据量 + 相同依赖配置」。
- 压测打的是生产库：直接造成真实数据污染与锁竞争。压测必须使用影子库或脱敏副本。
- 只压单接口：真实流量是混合的，单接口 5000 QPS 不代表混合场景能扛 5000。
- 忽略下游：本服务压到 3000 QPS 没问题，但下游库存服务只能扛 800，瓶颈在下游。
- 没有稳定性压测：内存泄漏、连接泄漏只有跑几小时才暴露。

**面试怎么答：** 先给 Little 定律的公式，说明并发、线程、连接怎么算；再讲「压测的目标是找拐点而不是找最大值」，拐点即 QPS 上升但 P99 陡增、错误率上升的那个点；然后讲压测四类型与必须观测的指标；最后强调「预留 30% 到 50% 余量、瓶颈可能在下游、必须做稳定性压测」。给出具体水位（CPU 70%、P99 小于 SLA 80%）比空谈方法论更可信。

**易错点：**

- 只看平均 RT：P99 已经是 SLA 的 3 倍，平均值依然很好看。
- 压测时不限制并发模型：用同步阻塞客户端，压不上去却以为服务到顶。
- 把压测峰值当容量：没有冗余，正常业务波动就打满。
- 忽略 GC 与连接池：QPS 没到瓶颈，Full GC 先到了。
- 压测报告不给瓶颈分析：只说「能扛 3000」，说不清先崩的是 CPU、连接池还是下游。
