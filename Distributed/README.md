## 核心速查表

**MQ 选型对比**

```text
    Kafka        ：高吞吐日志与事件流；分区内有序；无原生延迟消息；生态最好
    RabbitMQ     ：路由灵活（direct/fanout/topic/headers）；低延迟；quorum queue 保可靠
    RocketMQ     ：事务消息、延迟消息、严格顺序；电商与金融业务首选
    Pulsar       ：存算分离、多租户、原生延迟；运维复杂度高
    Redis Stream ：轻量异步；持久化与可靠性偏弱，适合非核心链路
```

**分布式事务方案对比**

```text
    2PC/XA      ：强一致、适合短事务；同步阻塞、协调者单点、提交阶段可能部分成功
    TCC         ：资源预占、性能好；需处理空回滚、悬挂、幂等
    Saga        ：长流程、逆序补偿；无隔离性，需语义锁与 Saga 日志
    本地消息表   ：业务与消息同库同事务；轮询投递，最终一致，通用性最强
    事务消息     ：RocketMQ 半消息 + 本地事务 + 回查；依赖 MQ 能力
    最大努力通知 ：跨企业回调 + 阶梯重试 + 对账；不保证送达，靠查询兜底
```

**限流算法**

```text
    固定窗口   ：实现简单；窗口边界可能放行约 2 倍流量
    滑动窗口   ：细粒度计数，边界更平滑；存储与计算成本较高
    漏桶       ：恒定速率流出，削峰平滑；无法应对合理突发
    令牌桶     ：按速率发放令牌，允许一定突发；Guava RateLimiter 常用
    分布式限流 ：Redis + Lua 原子计数或令牌桶；注意热点 key、时钟与网络开销
```

**Kafka 可靠性三件套**

```text
    Producer ：acks=all + enable.idempotence=true + 充足 retries
    Broker   ：replication.factor=3 + min.insync.replicas=2 + 禁止 unclean 选举
    Consumer ：enable.auto.commit=false + 处理成功后手动提交 + 业务幂等
```

**分布式锁选型**

```text
    Redis     ：SET NX PX + 唯一 token + Lua 释放；性能高，主从切换有丢锁风险
    Redisson  ：可重入 + 看门狗续期；显式 leaseTime 时看门狗不生效
    ZooKeeper ：临时顺序节点 + watch 前驱；CP，会话结束自动释放
    etcd      ：Lease + 事务；CP，云原生场景常用
    兜底      ：fencing token（单调版本号）+ 业务幂等，防止过期持有者继续写
```

## 易错点清单

```text
    1. 以为 Kafka 全局有序：只保证分区内有序，跨分区无序
    2. 以为 acks=all 就不丢：ISR 可能缩小，必须配合 min.insync.replicas
    3. 先提交 offset 再处理消息：进程崩溃直接丢消息
    4. 用消息 ID 做幂等键：重试后消息 ID 可能变化，应使用业务唯一键
    5. 把 Kafka 事务当分布式事务：它不覆盖数据库写入
    6. 以为 RabbitMQ 消息级 TTL 独立生效：队头长 TTL 会阻塞后面的短 TTL
    7. 认为 RocketMQ 死信永久保存：%DLQ% 有保留期限，需及时处理
    8. 认为 3PC 解决了分区问题：它只降低阻塞概率，仍可能部分提交
    9. TCC 的 Try 写成真实扣减：Confirm 会重复扣款
    10. Saga 忽略隔离性：中间态被读到，产生超卖或重复支付
    11. 本地消息表与业务表不在同一事务：原子性失效
    12. 分布式锁 SETNX 后再 EXPIRE：不是原子操作，可能死锁
    13. Redis 锁不校验 token：可能误删他人的锁
    14. 用 UUID 做主键：无序导致 B+ 树分裂与索引膨胀
    15. 一致性哈希不设虚拟节点：节点少时严重倾斜
    16. 把 Redis Cluster 说成一致性哈希：它使用 16384 个哈希槽
```

## 使用建议

1. 先按分册顺序过一遍，建立「MQ 可靠性 → 分布式一致性 → 高并发防护 → 服务治理」的整体链路。
2. 每道题不要背原文，重点记住「结论 + 一张表 + 一个真实故障场景」。
3. 回答分布式事务时，先问清业务对一致性、时延、改造成本的容忍度，再给方案，不要直接背 TCC。
4. 回答 MQ 可靠性时，按 Producer、Broker、Consumer 三段拆开，每段给出配置与兜底。
5. 结合自己的项目准备一个「消息重复/积压/事务不一致」的排查案例，比背概念更有说服力。
