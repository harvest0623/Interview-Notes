## 1. CAP 与 BASE

**CAP 指出一致性（Consistency）、可用性（Availability）、分区容错性（Partition tolerance）三者无法同时满足；由于网络分区在分布式系统中不可避免，真正的架构选择是「分区发生时保 C 还是保 A」**。BASE 是对 AP 路线的工程化延伸：接受短暂不一致，通过补偿与对账达到最终一致。

**三个字母的准确含义：**

| 字母 | 含义 | 常见误解 |
| --- | --- | --- |
| C（Consistency） | 所有读都能看到最近一次成功写入，等价于线性一致性 | 不是「数据不丢」或「事务 ACID 的 C」 |
| A（Availability） | 每个请求都能在有限时间内得到非错误响应 | 不保证返回最新数据 |
| P（Partition tolerance） | 网络分区时系统仍能继续运行 | 不是「永不分區」，而是分区后如何取舍 |

**为什么不能选 CA：** 分布式系统跨机房、跨机器，网络分区、丢包、延迟抖动是客观事实。放弃 P 意味着分区发生时系统整体不可用，这在工程上不成立。因此只有 CP 与 AP 两种现实路线：

| 路线 | 分区时的行为 | 典型系统 | 适用场景 |
| --- | --- | --- | --- |
| CP | 少数派节点拒绝服务，保证不返回旧数据 | ZooKeeper、etcd、MySQL MGR | 配置、选主、元数据、金融核心 |
| AP | 所有节点继续服务，允许读到旧数据 | Eureka、Cassandra、Redis 主从 | 商品列表、社交 Feed、会话 |

**一致性不是二值，而是一个光谱：**

```text
线性一致（最强） → 顺序一致 → 因果一致 → 最终一致（最弱）
```

- 线性一致：任何时刻读到的都是最近一次写，代价是同步与阻塞。
- 因果一致：只保证有因果关系的操作有序，适合协作类场景。
- 最终一致：允许多个副本短暂不同，收敛时间取决于复制与补偿机制。

**BASE 的真实含义：**

| 字母 | 含义 | 工程落地 |
| --- | --- | --- |
| Basically Available | 基本可用：允许降级、限流、部分功能不可用 | 熔断、降级页、读写分离 |
| Soft state | 软状态：允许中间状态存在 | 订单「支付中」、库存「预占」 |
| Eventually consistent | 最终一致：经过一段时间后所有副本收敛 | 重试、对账、补偿、CDC |

**取舍示例（伪代码）：**

```java
// 分区发生时只能在 C 与 A 之间取舍，不存在真正的“CA”
if (networkPartitionDetected()) {
    if (strongConsistencyRequired) {
        rejectWrite();        // CP：宁可不可用，也不返回旧数据
    } else {
        serveStaleRead();     // AP：继续服务，接受短暂不一致
    }
}
```

```sql
-- Cassandra 把取舍下放到单次请求：R + W > N 偏 CP，W=1 偏 AP
CONSISTENCY QUORUM;
CONSISTENCY ONE;
```

**常见系统归类（带前提）：**

- ZooKeeper/etcd：CP，写需多数派确认，分区时少数派不可写。
- Eureka：AP，节点间异步复制，可能读到旧的服务列表。
- Kafka：不是固定标签，`acks=all` + `min.insync.replicas=2` 偏 CP，`acks=1` + 允许 unclean 选举偏 AP。
- Redis 主从/Sentinel：偏 AP，异步复制可能丢失最后写入。
- MySQL 主从：偏 AP（异步复制）；MGR 多数派模式偏 CP。

**故障场景与兜底：**

- 分区期间强一致写入失败：上层要能降级、排队或提示稍后重试，不能无限重试打满线程池。
- AP 系统读到旧数据：读己之写场景用会话粘滞、版本号校验或短时间读主。
- 分区恢复后副本冲突：需要版本向量、最后写入胜出或业务对账来收敛。
- 跨机房双写：优先单元化（同一用户固定机房），而不是依赖双向同步。

**面试怎么答：** 先准确解释 C/A/P，指出 P 在分布式系统中不可放弃，所以不是「三选二」而是「分区时选 C 或 A」；再举 CP/AP 的真实系统；然后讲一致性光谱与 BASE 的三个字母；最后结合业务说明哪些数据必须 CP（余额、库存），哪些可以 AP（商品描述、评论）。

**易错点：**

- 说「我们系统是 CA」：跨网络部署时不存在 CA。
- 把 CAP 的 C 等同于 ACID 的 C：前者是一致性读，后者是事务约束。
- 认为 AP 就是「不要一致性」：AP 只是把一致性问题推迟到收敛阶段。
- 把 BASE 当成「不保证」：最终一致仍需要在有限时间内收敛。
- 给 Kafka、Redis 贴固定 CP/AP 标签：它们的语义高度依赖配置。

## 2. 2PC 与 3PC

**2PC（两阶段提交）把一次分布式事务拆成「准备」与「提交」两个阶段，由事务协调者统一驱动所有参与者**；它能保证强一致，但存在同步阻塞、协调者单点、提交阶段故障后状态不确定三大问题。3PC 在 2PC 前插入 `CanCommit` 并用超时减少阻塞，但仍无法解决网络分区下的共识问题。

**2PC 角色：**

| 角色 | 职责 |
| --- | --- |
| TM（Transaction Manager） | 协调者，发起 Prepare/Commit，维护事务状态 |
| RM（Resource Manager） | 参与者，通常是数据库，执行本地事务并反馈 |
| XA | 数据库层面的两阶段提交接口规范，MySQL、Oracle 均支持 |

**2PC 流程：**

```text
协调者                     参与者 A              参与者 B
    |  Prepare  -------------> |                     |
    | <---- Yes/No ----------- |                     |
    |  Prepare  -----------------------------------> |
    | <----------------------------- Yes/No --------- |
    |                                                 |
    |  全部 Yes：Commit ------> |  Commit  ---------> |
    |  任一 No ：Rollback ----> |  Rollback --------> |
```

1. 准备阶段：协调者向所有参与者发送 Prepare，参与者执行本地事务但不提交，锁定资源并返回 Yes/No。
2. 提交阶段：全部 Yes 则发送 Commit，任一 No 则发送 Rollback。
3. 参与者执行后释放锁并返回 ACK；协调者记录事务日志。

**故障窗口：**

| 故障点 | 后果 | 处理 |
| --- | --- | --- |
| Prepare 阶段参与者超时 | 协调者回滚，已 Prepare 的参与者需回滚 | 依赖协调者指令或超时自动回滚 |
| Commit 阶段协调者宕机 | 参与者已 Prepare 但不知道该提交还是回滚，资源长期锁定 | 需要协调者日志恢复，期间阻塞 |
| Commit 指令丢失 | 部分参与者已提交，部分未提交，数据不一致 | 重发指令或人工介入 |
| 参与者提交后宕机 | 重启后按本地日志继续完成 | 需要本地事务日志 |

**3PC 的三阶段：**

1. `CanCommit`：只询问参与者是否具备提交条件，不锁资源。
2. `PreCommit`：预留资源并执行本地事务，类似 2PC 的 Prepare。
3. `DoCommit`：正式提交；若 PreCommit 超时，参与者可自行回滚；若 DoCommit 超时，参与者倾向于提交。

```text
CanCommit → PreCommit → DoCommit
    （询问）    （预留）    （提交）
```

3PC 通过超时把「无限阻塞」变成「有限阻塞」，并让参与者在 DoCommit 超时后有明确的默认动作，但：

- 网络分区下仍可能出现「一部分参与者提交、另一部分回滚」。
- 多了一次网络往返，性能比 2PC 更差。
- 工程上很少单独使用，更多出现在理论题中。

**MySQL XA 示例：**

```sql
-- 参与者本地执行，不提交
XA START 'tx-order-001';
UPDATE stock SET count = count - 1 WHERE sku_id = 'SKU-1';
INSERT INTO order_item (order_id, sku_id) VALUES ('O-1', 'SKU-1');
XA END 'tx-order-001';
XA PREPARE 'tx-order-001';

-- 协调者确认全部 Prepare 成功后
XA COMMIT 'tx-order-001';

-- 异常时回滚
-- XA ROLLBACK 'tx-order-001';

-- 崩溃恢复后查看悬挂事务
XA RECOVER;
```

**故障场景与兜底：**

- 协调者单点：用高可用协调者（如 Seata Server 集群）并持久化事务日志。
- 长时间锁资源：控制事务时长，避免跨远程调用，设置超时与告警。
- 悬挂事务：定时扫描 `XA RECOVER`，按日志补偿提交或回滚。
- 数据库不支持 XA 或性能无法接受：改用 TCC、Saga、本地消息表等柔性方案。
- 跨服务调用超时：不要让 Prepare 阶段包含不可控的远程调用。

**面试怎么答：** 先讲 TM/RM 与 Prepare/Commit 两阶段，再列三个经典问题（阻塞、单点、提交阶段不确定）；然后讲 3PC 增加的 CanCommit 与超时默认动作，说明它只是缓解而非根治；最后给 MySQL XA 的落地方式与适用边界（短事务、同库或支持 XA 的数据源）。

**易错点：**

- 认为 2PC 能保证 100% 一致：协调者在提交阶段崩溃会出现部分提交。
- 把 2PC 当高性能方案：同步阻塞 + 两次网络往返，吞吐明显下降。
- 在 Prepare 阶段做远程 RPC：超时会让整个事务长期悬挂。
- 以为 3PC 解决了分区问题：它只降低了阻塞概率。
- 忘记 `XA RECOVER` 与悬挂事务处理，导致资源长期不释放。

## 3. TCC

**TCC 是「Try 预留资源、Confirm 确认、Cancel 取消」的业务层两阶段协议**：它把锁资源这件事从数据库层上移到业务层，用业务字段记录预占状态，因此没有长事务锁，性能更好，但需要业务实现三个方法并处理空回滚、悬挂、幂等三个经典问题。

**三个阶段：**

| 阶段 | 职责 | 示例（下单） |
| --- | --- | --- |
| Try | 检查并预留资源，不真正扣减 | 冻结库存、冻结余额、创建订单为「待确认」 |
| Confirm | 使用预留资源，完成最终业务 | 扣减冻结库存、扣款、订单改为「已支付」 |
| Cancel | 释放预留资源，回滚 Try | 解冻库存、解冻余额、订单关闭 |

**与 2PC 的差异：**

| 维度 | 2PC/XA | TCC |
| --- | --- | --- |
| 资源锁定 | 数据库行锁/事务锁 | 业务字段预占，无长事务 |
| 性能 | 低，锁持有时间长 | 高，Try 后即释放数据库锁 |
| 侵入性 | 低，数据库透明 | 高，每个服务实现三个方法 |
| 一致性 | 强一致 | 最终一致，依赖 Confirm/Cancel 成功 |
| 中间状态 | 对外不可见 | 对外可见（冻结、待确认） |

**三个必须解决的问题：**

1. **空回滚**：Try 未执行（或未成功），却收到了 Cancel。常见于 Try 超时但请求未到达。解决：Cancel 时先查事务状态，若没有 Try 记录，插入一条「已取消」记录后直接返回成功。
2. **悬挂**：Cancel 先到，Try 后到。若 Cancel 已把资源释放，迟到的 Try 又会冻结资源，导致资源永久占用。解决：Try 执行前检查事务状态，若已取消则拒绝执行。
3. **幂等**：Confirm/Cancel 可能被重复调用（网络重试、协调器重发）。解决：用事务状态表 + 唯一键，状态机只允许一次终态迁移。

**事务状态表：**

```sql
CREATE TABLE tcc_transaction (
    tx_id VARCHAR(64) NOT NULL,
    biz_key VARCHAR(128) NOT NULL,
    status TINYINT NOT NULL,       -- 1 TRYING 2 CONFIRMED 3 CANCELLED
    amount DECIMAL(18, 2) NOT NULL,
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    PRIMARY KEY (tx_id),
    UNIQUE KEY uk_biz_key (biz_key)
) ENGINE = InnoDB;
```

**代码示例（Java，Seata TCC 注解）：**

```java
@LocalTCC
public interface OrderTccService {
    @TwoPhaseBusinessAction(name = "tryCreateOrder",
            commitMethod = "confirmOrder", rollbackMethod = "cancelOrder")
    boolean tryCreateOrder(
            @BusinessActionContextParameter(paramName = "orderId") String orderId);

    boolean confirmOrder(BusinessActionContext context);

    boolean cancelOrder(BusinessActionContext context);
}
```

```java
@Override
public boolean tryCreateOrder(String orderId) {
    int inserted = transactionMapper.insertTry(orderId, "TRYING");
    if (inserted == 0) {
        return true;                      // 已 Try 过，幂等返回
    }
    return stockService.freeze(orderId);
}

@Override
public boolean cancelOrder(BusinessActionContext context) {
    String orderId = (String) context.getActionContext("orderId");
    int updated = transactionMapper.markCancelled(orderId);
    if (updated == 0) {
        transactionMapper.insertCancelled(orderId);   // 空回滚兜底
        return true;
    }
    return stockService.unfreeze(orderId);
}
```

**故障场景与兜底：**

- Try 成功但 Confirm 一直失败：资源停留在冻结态，需要定时任务扫描 `TRYING` 超时记录并重试 Confirm，或转人工。
- Cancel 失败：同样需要重试队列与告警，不能假设一次成功。
- Try 超时：调用方不能直接判定失败，应以事务状态表为准。
- 服务宕机：状态表与业务表必须同库同事务，重启后可恢复。
- 跨多个服务：由事务协调器（Seata Server）驱动，协调器本身要集群化。

**面试怎么答：** 先讲 Try/Confirm/Cancel 三段与「业务预占」的核心思想；再对比 2PC 说明性能优势与侵入性代价；重点展开空回滚、悬挂、幂等三个问题及状态表解法；最后补 Confirm/Cancel 失败的重试与人工兜底。

**易错点：**

- 把 Try 写成真正的扣减：Confirm 再扣一次就重复扣款。
- Cancel 不查状态直接释放：空回滚会把别人的资源解冻。
- Try 不检查已取消状态：悬挂导致资源永久冻结。
- 状态表与业务表分库：本地事务无法保证原子性。
- 以为 TCC 一定强一致：它仍是最终一致，Confirm/Cancel 可能延迟完成。

## 4. Saga

**Saga 把长事务拆成一串本地事务，每个正向操作都配一个补偿操作，任一步失败就逆序执行已完成的补偿**。它适合流程长、跨多个服务、无法长时间锁资源的业务，代价是没有隔离性，中间状态对外可见。

**两种编排方式：**

| 方式 | 说明 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 编排式（Orchestration） | 中央协调器按状态机依次调用服务 | 流程集中、易观测、易补偿 | 协调器复杂，可能成为瓶颈 |
| 协同式（Choreography） | 各服务监听事件自行推进 | 去中心、松耦合 | 流程分散、难追踪、易循环依赖 |

**执行模型：**

```text
T1 → T2 → T3 → T4
失败于 T3：
执行 C2 → C1（逆序补偿），T3 自身若有本地事务则先回滚
```

**关键设计：**

| 设计点 | 要求 |
| --- | --- |
| 补偿幂等 | 同一补偿可能被多次调用，结果必须一致 |
| 补偿可交换 | 某些场景下补偿顺序不严格，需保证最终状态正确 |
| 语义锁 | 用状态字段（如 `PENDING`）标记中间态，防止其他事务读到半成品 |
| 超时 | 每一步设置超时，避免长时间悬挂 |
| 持久化 | Saga 日志必须落库，重启后能继续或补偿 |
| 版本号 | 用聚合根版本防止并发 Saga 覆盖 |

**代码示例（Java 伪代码，编排式）：**

```java
public class CreateOrderSaga {
    private final SagaLogRepository sagaLogRepository;

    public void execute(Order order) {
        String sagaId = sagaLogRepository.start(order.getId());
        try {
            orderService.create(order);              // T1
            sagaLogRepository.record(sagaId, "T1");

            inventoryService.reserve(order);         // T2
            sagaLogRepository.record(sagaId, "T2");

            paymentService.charge(order);            // T3
            sagaLogRepository.record(sagaId, "T3");

            sagaLogRepository.complete(sagaId);
        } catch (Exception e) {
            compensate(sagaId, order);
            throw e;
        }
    }

    private void compensate(String sagaId, Order order) {
        List<String> completed = sagaLogRepository.completedSteps(sagaId);
        for (String step : reverse(completed)) {
            switch (step) {
                case "T3" -> paymentService.refund(order);
                case "T2" -> inventoryService.release(order);
                case "T1" -> orderService.cancel(order);
                default -> throw new IllegalStateException("unknown step: " + step);
            }
        }
        sagaLogRepository.compensated(sagaId);
    }
}
```

**语义锁示例：**

```sql
-- 中间态对外不可见：查询只返回 PAID 及之后的状态
UPDATE orders SET status = 'PENDING_PAYMENT', version = version + 1
WHERE order_id = 'O-1' AND status = 'CREATED' AND version = 3;
```

**与 TCC 的对比：**

| 维度 | TCC | Saga |
| --- | --- | --- |
| 资源预留 | 显式 Try 冻结 | 无预留，直接执行本地事务 |
| 隔离性 | 较好（冻结字段） | 无隔离，需要语义锁 |
| 侵入性 | 高，三方法 | 中，正向 + 补偿 |
| 适用 | 短流程、强资源控制 | 长流程、跨多服务 |
| 失败处理 | Cancel 释放预留 | 逆序补偿已完成的步骤 |

**故障场景与兜底：**

- 补偿失败：必须重试并告警，补偿日志保证不会漏掉。
- 进程崩溃：从 Saga 日志恢复，按「已完成步骤」继续正向或补偿。
- 并发冲突：同一订单同时发起两个 Saga，用版本号或分布式锁串行化。
- 补偿不可逆：如已发短信、已出票，需要人工工单或业务侧可逆设计。
- 中间态被读到：查询接口过滤中间态，或返回「处理中」。

**面试怎么答：** 先讲「本地事务链 + 逆序补偿」的执行模型，再区分编排式与协同式；重点说明 Saga 没有隔离性，需要用语义锁/状态字段防脏读；然后对比 TCC 的预占模型；最后讲 Saga 日志、补偿幂等与失败重试。

**易错点：**

- 把 Saga 当成「失败就全部回滚」：它只补偿已完成的步骤，且补偿可能失败。
- 忽略隔离性：中间态被其他请求读取，产生超卖或重复支付。
- 补偿操作不幂等：重试时重复退款。
- 不持久化 Saga 日志：进程崩溃后不知道执行到哪一步。
- 补偿顺序错误：必须逆序，且要跳过未完成的步骤。

## 5. 本地消息表

**本地消息表（Outbox Pattern）把「业务写入」与「待发送消息」放在同一个本地数据库事务里，再由后台任务轮询消息表投递到 MQ**。它不依赖 MQ 的事务能力，落地简单、适用面广，是业务系统实现最终一致最常用的方案。

**执行流程：**

```text
1. 本地事务：写业务表 + 写 outbox 消息表（同一 DB，同一事务）
2. 定时任务扫描 outbox 中 status=待发送 的记录
3. 发送到 MQ，成功后把记录标记为已发送
4. 发送失败按退避策略重试，超过阈值告警
5. 消费端幂等消费，失败进入重试/死信
6. 定时对账，修复漏发与漏消费
```

**表结构：**

```sql
CREATE TABLE outbox_message (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    biz_key VARCHAR(128) NOT NULL,
    topic VARCHAR(128) NOT NULL,
    payload TEXT NOT NULL,
    status TINYINT NOT NULL DEFAULT 0,      -- 0 待发送 1 已发送 2 失败
    retry_count INT NOT NULL DEFAULT 0,
    next_retry_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    UNIQUE KEY uk_biz_key_topic (biz_key, topic),
    KEY idx_status_retry (status, next_retry_at)
) ENGINE = InnoDB;
```

**代码示例（Java，同事务写入）：**

```java
@Transactional
public void createOrder(Order order) {
    orderRepository.save(order);
    outboxRepository.save(OutboxMessage.pending(
            order.getId(), "order-created", order.toJson()));
}
```

```java
@Scheduled(fixedDelay = 1000)
public void relay() {
    List<OutboxMessage> messages = outboxRepository.lockPending(100);
    for (OutboxMessage message : messages) {
        try {
            kafkaTemplate.send(message.getTopic(), message.getBizKey(),
                    message.getPayload()).get(3, TimeUnit.SECONDS);
            outboxRepository.markSent(message.getId());
        } catch (Exception e) {
            outboxRepository.markRetry(message.getId(), e.getMessage());
        }
    }
}
```

```sql
-- 多实例抢占：MySQL 8.0 支持 SKIP LOCKED，避免重复扫描同一条
SELECT id, biz_key, topic, payload
FROM outbox_message
WHERE status = 0 AND next_retry_at <= NOW()
ORDER BY id
LIMIT 100
FOR UPDATE SKIP LOCKED;
```

**为什么不用「先写库再发 MQ」：**

- 写库成功后进程崩溃，消息没发出，下游永远不知道。
- 先发 MQ 再写库，MQ 成功但数据库回滚，下游收到一条不存在的业务事件。
- 本地事务能保证「业务 + 消息记录」原子落库，消息投递则通过重试达到最终成功。

**优缺点：**

| 优点 | 缺点 |
| --- | --- |
| 不依赖 MQ 事务特性，任何 MQ 可用 | 消息表与业务库同库，增加写压力 |
| 实现简单、可观测、可重放 | 投递有延迟（轮询间隔） |
| 与业务事务强绑定，不漏消息 | 消息表会膨胀，需要归档 |
| 失败可重试、可人工补偿 | 多实例扫描要处理并发与顺序 |

**故障场景与兜底：**

- 轮询任务宕机：多实例部署 + 数据库抢占，单实例故障不影响投递。
- 消息表积压：监控 `status=0` 的数量与最老记录时间，扩容轮询或提高批量。
- 重复投递：发送成功后标记前宕机，重启会再发一次，消费端必须幂等。
- 消息顺序：同一业务键的消息按 id 顺序发送，或由消费端按版本号排序。
- 消息表无限增长：按时间分区，已发送记录定期归档或删除。
- 大事务：消息体过大拖慢业务事务，payload 只存关键字段或引用。

**面试怎么答：** 先讲「业务表 + 消息表同事务」这个核心，说明它解决了「写库与发消息」的原子性；再讲轮询投递、失败重试、消费幂等、对账兜底四步；然后对比事务消息（依赖 RocketMQ）与本地消息表（通用）的差异；最后补多实例抢占、消息表清理与顺序问题。

**易错点：**

- 业务表与消息表不在同一数据库或同一事务：原子性失效。
- 发送成功但标记失败：重启后重复发送，消费端必须幂等。
- 轮询任务单实例：任务挂了消息就停发。
- 不做消息表清理：表越来越大，扫描越来越慢。
- 把本地消息表当成强一致：它只保证最终一致，存在投递延迟。

## 6. 最大努力通知

**最大努力通知是「尽最大努力把结果告知对方，但不保证一定送达」的柔性方案**，通常用于跨企业、跨平台的异步结果通知（如支付回调、物流状态推送）。它靠「多次重试 + 通知记录 + 对方主动查询/对账」来收敛，而不是靠事务保证。

**与 MQ 方案的区别：**

| 维度 | 最大努力通知 | MQ 消息 |
| --- | --- | --- |
| 目标 | 通知外部系统 | 系统内部解耦 |
| 可靠性 | 尽力而为，可能丢 | 通常至少一次 |
| 重试 | 按计划多次 HTTP 重试 | MQ 自身重投 |
| 兜底 | 对方主动查询 + 对账 | 死信 + 补偿 |
| 耦合 | 依赖对方接口 | 依赖 MQ 集群 |

**典型流程：**

```text
1. 业务完成后记录通知任务（notify_log，状态待通知）
2. 按计划发起 HTTP 回调：立即、1m、5m、10m、30m、1h、2h、6h...
3. 对方返回成功 → 标记已通知
4. 对方返回失败/超时 → 记录失败原因，进入下一次重试
5. 超过最大次数 → 标记失败，告警并进入人工/对账
6. 提供查询接口，对方可主动拉取最终状态
7. 日终对账，修复双方状态差异
```

**通知记录表：**

```sql
CREATE TABLE notify_log (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    biz_key VARCHAR(128) NOT NULL,
    target_url VARCHAR(512) NOT NULL,
    payload TEXT NOT NULL,
    status TINYINT NOT NULL DEFAULT 0,      -- 0 待通知 1 成功 2 失败
    retry_count INT NOT NULL DEFAULT 0,
    next_retry_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    last_error VARCHAR(512),
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    UNIQUE KEY uk_biz_key (biz_key),
    KEY idx_status_retry (status, next_retry_at)
) ENGINE = InnoDB;
```

**代码示例（Java，按计划重试）：**

```java
private static final int[] DELAY_SECONDS = {0, 60, 300, 600, 1800, 3600, 7200};

@Scheduled(fixedDelay = 1000)
public void notifyLoop() {
    List<NotifyLog> logs = notifyRepository.lockDue(100);
    for (NotifyLog log : logs) {
        try {
            NotifyResponse response = httpClient.post(log.getTargetUrl(), log.getPayload());
            if (response.isSuccess()) {
                notifyRepository.markSuccess(log.getId());
            } else {
                retryOrFail(log, "http status " + response.getStatus());
            }
        } catch (Exception e) {
            retryOrFail(log, e.getMessage());
        }
    }
}

private void retryOrFail(NotifyLog log, String error) {
    int next = log.getRetryCount() + 1;
    if (next >= DELAY_SECONDS.length) {
        notifyRepository.markFailed(log.getId(), error);
        alertService.notify("notify failed: " + log.getBizKey());
        return;
    }
    notifyRepository.markRetry(log.getId(), next, DELAY_SECONDS[next], error);
}
```

**接收方的义务：**

- 必须幂等：同一 `biz_key` 重复通知只处理一次。
- 必须快速返回：先落库再异步处理，避免回调超时触发重试。
- 必须校验签名与来源，防止伪造通知。
- 必须提供查询接口，供对方在通知丢失时主动补偿。

**故障场景与兜底：**

- 对方长期不可用：达到最大次数后标记失败，转入对账与人工处理。
- 通知重复：接收方按业务键幂等，返回成功即可停止重试。
- 通知丢失且对方无感知：日终对账 + 主动查询接口兜底。
- 回调地址变更：通知记录保存地址快照，变更需平滑切换。
- 重试风暴：退避 + 抖动 + 限流，避免把对方打垮。
- 中间状态不确定：对方查询接口必须返回明确终态，不能返回「处理中」无限循环。

**面试怎么答：** 先说明它适用于「跨组织、无法控制对方」的场景，本质是尽力而为；再讲通知记录、阶梯重试、查询接口、日终对账四件套；然后对比 MQ 方案，强调它不保证送达但保证可发现、可修复；最后补接收方幂等与安全校验。

**易错点：**

- 把最大努力通知当成可靠消息：它可能永久丢失，必须有对账。
- 只重试不记录：无法判断哪些通知失败，也无法人工补偿。
- 接收方不做幂等：重复回调导致重复发货或重复记账。
- 回调里做重业务：超时触发更多重试，形成雪崩。
- 没有查询接口：对方无法主动确认最终状态。

## 7. 分布式事务选型对比

**没有一种方案能同时满足强一致、高性能、低侵入、高可用，选型的本质是按业务对一致性、时延、改造成本的容忍度做取舍**。常见组合是「核心资金链路用 TCC/事务消息，普通业务用本地消息表/最大努力通知，跨行长流程用 Saga」。

**方案总览：**

| 方案 | 一致性 | 性能 | 侵入性 | 隔离性 | 依赖 | 适用场景 |
| --- | --- | --- | --- | --- | --- | --- |
| 2PC/XA | 强一致 | 低 | 低 | 强 | 支持 XA 的数据库 | 同库/短事务、传统金融 |
| TCC | 最终一致 | 高 | 高 | 较好 | 事务协调器 | 资金、库存等资源预占 |
| Saga | 最终一致 | 高 | 中 | 无 | 状态机/协调器 | 长流程、跨多服务 |
| 本地消息表 | 最终一致 | 高 | 低 | 无 | 任意 MQ | 业务事件通知、通用 |
| 事务消息 | 最终一致 | 高 | 中 | 无 | RocketMQ | 电商订单、支付回调 |
| 最大努力通知 | 最终一致 | 高 | 低 | 无 | HTTP + 对账 | 跨企业通知 |

**决策路径：**

```text
需要强一致且事务短、数据源支持 XA？
    是 → 2PC/XA
    否 → 是否核心资源需要预占（库存、余额）？
        是 → TCC
        否 → 流程是否很长、跨多个服务？
            是 → Saga
            否 → 是否能接受依赖 RocketMQ？
                是 → 事务消息
                否 → 本地消息表
    跨企业、无法控制对方 → 最大努力通知 + 对账
```

**Seata AT 模式示例（适合大多数业务）：**

```java
@GlobalTransactional(timeoutMills = 300000, name = "create-order")
public void createOrder(Order order) {
    orderService.create(order);
    inventoryService.deduct(order.getSkuId(), order.getCount());
    accountService.debit(order.getUserId(), order.getAmount());
}
```

Seata AT 模式通过解析 SQL 生成前后镜像，自动完成回滚，侵入性低；但依赖全局锁与 undo_log，性能不如 TCC，且跨服务调用需要传递 XID。

**混合使用的真实架构：**

- 下单：本地事务写订单 + 本地消息表，异步通知库存与积分。
- 支付：TCC 冻结余额，Confirm 扣款，Cancel 解冻。
- 退款：Saga 编排「退款申请 → 渠道退款 → 记账 → 通知」，失败逆序补偿。
- 对外商户：最大努力通知 + 日终对账。

**故障场景与兜底：**

- 选型过重：普通通知用 TCC，开发与运维成本极高，收益有限。
- 选型过轻：资金链路只用最大努力通知，丢消息直接资损。
- 协调器单点：Seata Server、Saga 编排器都要集群与持久化。
- 跨服务 XID 丢失：Feign/Dubbo 调用要透传事务上下文。
- 没有对账：任何最终一致方案都可能漏，必须有日终对账兜底。

**面试怎么答：** 先给一张按「一致性、性能、侵入性、隔离性、依赖」维度的对比表；再给决策路径：强一致短事务选 XA，资源预抢占 TCC，长流程选 Saga，通用事件选本地消息表，依赖 RocketMQ 选事务消息，跨企业选最大努力通知；最后用一个真实业务链路说明多种方案可以混合使用。

**易错点：**

- 追求「强一致」而忽略性能与可用性，把核心链路做成串行同步。
- 认为本地消息表一定可靠：它只保证不漏发，不保证不重复。
- 用 TCC 却只实现 Try：Confirm/Cancel 缺失，资源永久冻结。
- 忽略隔离性：Saga 与本地消息表都可能被读到中间态。
- 不做对账：最终一致方案没有对账就等于没有兜底。

## 8. 最终一致性与补偿

**最终一致性不是「不管了」，而是「允许中间态存在，但必须在有限时间内通过重试、补偿、对账收敛到正确状态」**。工程上要同时具备四件事：幂等、可重试、可补偿、可对账，缺一不可。

**正向与反向补偿：**

| 类型 | 含义 | 示例 |
| --- | --- | --- |
| 正向补偿（重试） | 继续尝试未完成的操作直到成功 | 支付回调失败重试、消息重投 |
| 反向补偿（回滚） | 对已完成操作执行逆操作 | 退款、解冻库存、取消订单 |
| 对账修复 | 定期比对双方状态，修正差异 | 日终对账、差错工单 |

**收敛的五个前提：**

1. **幂等**：同一操作执行多次结果一致，通常用业务唯一键 + 状态机。
2. **可重试**：失败可被识别并重新驱动，不能静默吞掉。
3. **可补偿**：每个正向操作都有对应的逆操作，且逆操作本身幂等。
4. **可观测**：中间态、失败次数、最老未完成记录都要有监控。
5. **可对账**：与权威数据源比对，发现漏发、漏处理、状态不一致。

**状态机示例：**

```java
public enum OrderStatus {
    CREATED, PENDING_PAYMENT, PAID, SHIPPED, COMPLETED, REFUNDING, REFUNDED, CANCELLED
}

public boolean canTransit(OrderStatus from, OrderStatus to) {
    return switch (from) {
        case CREATED -> to == PENDING_PAYMENT || to == CANCELLED;
        case PENDING_PAYMENT -> to == PAID || to == CANCELLED;
        case PAID -> to == SHIPPED || to == REFUNDING;
        case SHIPPED -> to == COMPLETED || to == REFUNDING;
        case REFUNDING -> to == REFUNDED;
        default -> false;
    };
}

@Transactional
public void transit(String orderId, OrderStatus target) {
    Order order = orderRepository.lock(orderId);
    if (!canTransit(order.getStatus(), target)) {
        return;                     // 重复消息或非法迁移，幂等返回
    }
    orderRepository.updateStatus(orderId, target, order.getVersion());
}
```

**Outbox + CDC 方案：**

```text
业务事务写 orders + outbox
        ↓ binlog
Debezium 捕获 outbox 变更 → 投递 Kafka
        ↓
下游消费（幂等）→ 更新自己的状态
```

相比轮询消息表，CDC 延迟更低、对业务库压力更小，但引入了 Debezium、Kafka Connect 等运维组件。

**补偿设计原则：**

- 补偿必须是「业务逆操作」，不是简单地把状态改回去；退款要走渠道退款，不能只改订单状态。
- 补偿要考虑部分成功：批量扣款中部分失败，需要按明细逐笔补偿。
- 补偿要有上限与人工兜底：无限重试会拖垮系统，也可能造成重复退款。
- 补偿要与原操作使用同一业务键，便于幂等与追踪。
- 补偿的最终状态要可查询、可审计。

**故障场景与兜底：**

- 重试次数用尽仍失败：转人工工单，保留上下文与失败原因。
- 补偿本身失败：补偿也要有重试队列与死信，不能假设一定成功。
- 中间态长期不收敛：设置超时阈值，超时后强制查询权威源并修正。
- 对账发现差异：自动修复可重入的差异，资损类差异必须人工复核。
- 消息乱序：按业务键 + 版本号处理，旧版本消息直接丢弃。

**面试怎么答：** 先定义「最终一致 = 有限时间内收敛」，再讲正向重试、反向补偿、对账三层机制；然后给五个前提（幂等、可重试、可补偿、可观测、可对账）；最后用状态机 + Outbox/CDC 举例，说明如何避免中间态被误读。

**易错点：**

- 把「最终一致」当成「不需要一致」，不做对账也不做补偿。
- 补偿只改状态不执行真实逆操作，账目对不上。
- 重试没有上限与退避，失败消息拖垮下游。
- 状态机允许任意迁移，重复消息把已完成订单改回中间态。
- 忽略部分成功：批量操作失败后整批重试，造成重复扣款。

## 9. 分布式 ID

**分布式 ID 要在多节点并发下保证「全局唯一、趋势递增、高性能、高可用」，同时尽量不暴露业务量**。常见方案从 UUID、数据库号段、Redis 自增到雪花算法，选择取决于是否需要有序、是否容忍时钟回拨、以及运维复杂度。

**方案对比：**

| 方案 | 唯一性 | 有序性 | 性能 | 依赖 | 缺点 |
| --- | --- | --- | --- | --- | --- |
| UUID | 高 | 无序 | 高（本地生成） | 无 | 太长、索引碎片、可读性差 |
| 数据库自增 | 高 | 严格递增 | 低（单库瓶颈） | 数据库 | 单点、扩容难 |
| 数据库号段 | 高 | 趋势递增 | 高 | 数据库 | 号段浪费、需双 buffer |
| Redis INCR | 高 | 递增 | 高 | Redis | 持久化与单点风险 |
| 雪花算法 | 高 | 趋势递增 | 很高（本地） | 时钟 + workerId | 时钟回拨、workerId 分配 |
| Leaf | 高 | 趋势递增 | 高 | 号段 + ZooKeeper | 组件较多 |
| TinyID | 高 | 递增 | 高 | 号段服务 | 依赖服务可用性 |

**雪花算法位分配（64 位）：**

```text
0 | 41 bit 时间戳（毫秒） | 5 bit 数据中心 | 5 bit 机器 | 12 bit 序列号
```

- 41 位毫秒时间戳可用约 69.7 年。
- 10 位工作机标识最多 1024 个节点。
- 12 位序列号表示单节点每毫秒最多 4096 个 ID。
- 理论上单节点约 409.6 万 ID/秒。

**代码示例（Java，雪花算法核心）：**

```java
public class SnowflakeIdGenerator {
    private static final long EPOCH = 1704067200000L;      // 2024-01-01
    private static final long WORKER_BITS = 5L;
    private static final long DATACENTER_BITS = 5L;
    private static final long SEQUENCE_BITS = 12L;
    private static final long MAX_SEQUENCE = ~(-1L << SEQUENCE_BITS);
    private static final long WORKER_SHIFT = SEQUENCE_BITS;
    private static final long DATACENTER_SHIFT = SEQUENCE_BITS + WORKER_BITS;
    private static final long TIMESTAMP_SHIFT = SEQUENCE_BITS + WORKER_BITS + DATACENTER_BITS;
    private final long datacenterId;
    private final long workerId;
    private long sequence = 0L;
    private long lastTimestamp = -1L;
    public SnowflakeIdGenerator(long datacenterId, long workerId) {
        this.datacenterId = datacenterId;
        this.workerId = workerId;
    }
    public synchronized long nextId() {
        long now = System.currentTimeMillis();
        if (now < lastTimestamp) {
            throw new IllegalStateException("clock moved backwards");
        }
        if (now == lastTimestamp) {
            sequence = (sequence + 1) & MAX_SEQUENCE;
            if (sequence == 0) {
                now = waitNextMillis(lastTimestamp);
            }
        } else {
            sequence = 0L;
        }
        lastTimestamp = now;
        return ((now - EPOCH) << TIMESTAMP_SHIFT)
                | (datacenterId << DATACENTER_SHIFT)
                | (workerId << WORKER_SHIFT)
                | sequence;
    }
    private long waitNextMillis(long last) {
        long now = System.currentTimeMillis();
        while (now <= last) {
            now = System.currentTimeMillis();
        }
        return now;
    }
}
```
**时钟回拨的处理：**

| 策略 | 说明 | 风险 |
| --- | --- | --- |
| 直接抛异常 | 拒绝生成，等待时钟追平 | 短时间不可用 |
| 等待追平 | 自旋到 `lastTimestamp` 之后 | 回拨较大时阻塞久 |
| 备用位 | 用扩展位记录回拨次数 | 实现复杂 |
| 切换 workerId | 换一个节点继续生成 | 需要额外分配机制 |

**workerId 分配：**

- 启动时向 ZooKeeper/etcd 注册临时顺序节点，取序号作为 workerId。
- 或由配置中心/数据库分配，配合心跳续约。
- 容器化环境不要用 IP 末位，Pod 重启后 IP 会变化，容易冲突。

**故障场景与兜底：**

- 时钟回拨：抛出异常并告警，或等待追平；不能生成可能重复的 ID。
- workerId 冲突：两台机器生成重复 ID，必须有注册与续约机制。
- 号段耗尽：双 buffer 预加载，剩余阈值触发异步取下一段。
- Redis 宕机：号段模式本地缓存可撑一段时间，UUID 可本地生成不受影响。
- ID 暴露业务量：对外展示用混淆或独立公开 ID，内部主键不直接暴露。

**面试怎么答：** 先列需求（唯一、有序、性能、可用、安全），再对比 UUID、数据库、Redis、雪花、Leaf；重点讲雪花算法的位分配与 4096/毫秒的容量，以及时钟回拨和 workerId 分配两个工程难题；最后说明趋势递增对数据库索引友好，严格递增通常不需要。

**易错点：**

- 用 UUID 做主键：无序导致 B+ 树频繁分裂，写入与存储成本高。
- 雪花算法直接用机器 IP 当 workerId：容器漂移后冲突。
- 忽略时钟回拨：NTP 校准或虚拟机迁移会导致重复 ID。
- 数据库自增单表：并发稍高就成为瓶颈。
- 认为 ID 必须严格连续：趋势递增即可，连续会暴露业务量且难以分片。

## 10. 一致性哈希

**一致性哈希把节点和 key 都映射到一个 0 到 2^32-1 的环上，key 顺时针找到的第一个节点即归属节点**。它的价值在于「增删节点只影响相邻的一段数据」，而取模哈希在节点数变化时几乎全部 key 都要迁移。

**与取模哈希的对比：**

| 维度 | 取模哈希 | 一致性哈希 |
| --- | --- | --- |
| 扩容影响 | 约 (N-1)/N 的 key 迁移 | 约 1/N 的 key 迁移 |
| 实现复杂度 | 低 | 中 |
| 数据倾斜 | 较均匀 | 节点少时易倾斜，需虚拟节点 |
| 典型场景 | 分库分表、固定分片 | 缓存集群、负载均衡 |

**环与虚拟节点：**

```text
        0 / 2^32
            |
    Node C  |  Node A
            |     key1 → 顺时针命中 Node A
    Node B  |
            |
        2^31
```

- 物理节点少时，哈希落点不均，可能一个节点承担大部分流量。
- 每个物理节点映射多个虚拟节点（通常 100~200 个），让落点均匀。
- 增加节点时，只从环上相邻节点接管一段 key。

**代码示例（Java，TreeMap 实现）：**

```java
public class ConsistentHash<T> {
    private final TreeMap<Long, T> ring = new TreeMap<>();
    private final int virtualNodes;

    public ConsistentHash(int virtualNodes) {
        this.virtualNodes = virtualNodes;
    }

    public void addNode(T node) {
        for (int i = 0; i < virtualNodes; i++) {
            ring.put(hash(node.toString() + "#" + i), node);
        }
    }

    public void removeNode(T node) {
        for (int i = 0; i < virtualNodes; i++) {
            ring.remove(hash(node.toString() + "#" + i));
        }
    }

    public T getNode(String key) {
        Map.Entry<Long, T> entry = ring.ceilingEntry(hash(key));
        return entry == null ? ring.firstEntry().getValue() : entry.getValue();
    }

    private long hash(String value) {
        byte[] digest = md5(value);
        return ((long) (digest[3] & 0xFF) << 24)
                | ((long) (digest[2] & 0xFF) << 16)
                | ((long) (digest[1] & 0xFF) << 8)
                | (digest[0] & 0xFF);
    }

    private byte[] md5(String value) {
        try {
            MessageDigest md = MessageDigest.getInstance("MD5");
            return md.digest(value.getBytes(StandardCharsets.UTF_8));
        } catch (NoSuchAlgorithmException e) {
            throw new IllegalStateException(e);
        }
    }
}
```

**虚拟节点数量怎么选：**

- 节点少、流量大：虚拟节点多一些（如 200），降低倾斜。
- 节点多：虚拟节点可少一些，减少环的维护开销。
- 上线前用实际 key 分布做压测，观察最大节点占比，通常要求不超过均值的 1.5 倍。

**常见误用：**

- **Redis Cluster 不是一致性哈希**：它用 16384 个哈希槽（`CRC16(key) mod 16384`），槽可以迁移，扩容按槽重新分配。
- **Dubbo 的 ConsistentHashLoadBalance** 默认每个服务提供者 160 个虚拟节点，按方法参数哈希。
- **分库分表** 多用固定分片 + 取模/号段，因为需要稳定的路由与可控的扩容流程，一致性哈希反而增加迁移复杂度。

**故障场景与兜底：**

- 节点宕机：原本落在该节点的 key 顺时针转移到下一节点，可能造成下一节点热点。
- 热点 key：一致性哈希无法拆分单个 key，需要本地缓存、key 拆分或副本。
- 虚拟节点过少：数据倾斜严重，扩缩容前先评估分布。
- 环为空：`getNode` 要做空判断，避免 NPE。
- 节点权重不同：按性能给不同数量的虚拟节点，而不是平均分配。

**面试怎么答：** 先讲取模哈希扩容的迁移问题，再画环、讲「顺时针第一个节点」；然后说明虚拟节点解决倾斜，增删节点只迁移 1/N；最后对比 Redis Cluster 的槽机制，指出一致性哈希适合缓存与负载均衡，不适合需要精细迁移控制的分库分表。

**易错点：**

- 把 Redis Cluster 说成一致性哈希：它是哈希槽。
- 不设虚拟节点：三节点集群很容易出现 80% 流量落在一个节点。
- 认为一致性哈希能解决热点 key：同一 key 永远落同一节点。
- 节点权重相同：异构机器应按容量分配虚拟节点。
- 忽略环为空与哈希碰撞的边界处理。

## 11. Paxos 与 Raft

**Paxos 与 Raft 都是「多数派共识算法」，用于在存在故障的分布式系统中就某个值达成一致**。Paxos 是理论鼻祖，抽象难懂；Raft 以「Leader 选举 + 日志复制 + 成员变更」三段式降低了工程实现难度，成为 etcd、Consul、Kafka KRaft 的主流选择。

**Paxos 角色与两阶段：**

| 角色 | 职责 |
| --- | --- |
| Proposer | 提出提案（编号 + 值） |
| Acceptor | 对提案投票，多数派接受即通过 |
| Learner | 学习已通过的值 |

```text
Phase 1（Prepare）：
    Proposer → Acceptor：Prepare(n)
    Acceptor → Proposer：Promise(n, 当前最大已接受提案)

Phase 2（Accept）：
    Proposer → Acceptor：Accept(n, value)
    Acceptor → Proposer：Accepted(n)
    多数派 Accepted 后，值被选定
```

- 提案编号必须全局单调递增。
- 多数派 = `2f + 1` 中的 `f + 1`，可容忍 f 个节点故障。
- Basic Paxos 一次只能对一个值达成共识；Multi-Paxos 通过选举 Leader 跳过 Phase 1，提升吞吐。
- Paxos 只保证「值一旦被选定就不会被覆盖」，不保证实时性，也不处理拜占庭故障。

**Raft 的三个子问题：**

| 子问题 | 机制 |
| --- | --- |
| Leader 选举 | 任期 term + 随机选举超时 + 多数派投票 |
| 日志复制 | Leader 追加日志，Follower 按序复制，多数派确认后提交 |
| 成员变更 | 联合共识（Joint Consensus）或单节点变更 |

**Raft 选举流程：**

1. 所有节点初始为 Follower，心跳超时后变为 Candidate。
2. Candidate 递增 term，向其他节点发送 `RequestVote`。
3. 获得多数派投票则成为 Leader，否则等待下一轮随机超时重试。
4. Leader 定期发送 `AppendEntries` 作为心跳，维持领导地位。
5. 选举超时加入随机抖动，避免多个 Candidate 同时竞选导致选票分裂。

**日志复制与提交：**

```text
Leader:    [idx 1][idx 2][idx 3][idx 4]
FollowerA: [idx 1][idx 2][idx 3]
FollowerB: [idx 1][idx 2][idx 3]
多数派确认 idx 3 → commitIndex = 3，之前日志不可回退
```

- 只有 Leader 能提交日志，Follower 只能追加。
- Leader 崩溃后，新 Leader 必须拥有旧 Leader 已提交的全部日志。
- 日志条目包含 term 与 index，冲突时从分歧点截断后重放。

**Raft 伪代码（投票）：**

```text
on RequestVote(term, candidateId, lastLogIndex, lastLogTerm):
    if term < currentTerm:
        return false
    if term > currentTerm:
        currentTerm = term
        votedFor = null
    if votedFor == null and candidateLogUpToDate(lastLogIndex, lastLogTerm):
        votedFor = candidateId
        return true
    return false

on AppendEntries(term, prevIndex, entries, leaderCommit):
    if term < currentTerm:
        return false
    if prevIndex 不匹配:
        return false, 期望的 nextIndex
    追加 entries，更新 commitIndex = min(leaderCommit, lastIndex)
    return true
```

**Paxos 与 Raft 对比：**

| 维度 | Paxos | Raft |
| --- | --- | --- |
| 抽象 | 提案/投票，理论简洁 | 工程化三段式，易实现 |
| Leader | Multi-Paxos 才有 | 强 Leader |
| 日志 | 不强调 | 明确日志复制与提交规则 |
| 成员变更 | 较复杂 | 有标准流程 |
| 典型实现 | ZooKeeper（ZAB 近似）、Paxos Made Simple | etcd、Consul、TiKV、KRaft |

**故障场景与兜底：**

- 网络分区：多数派一侧继续服务，少数派停止写入，分区恢复后按日志收敛。
- 选举风暴：随机化选举超时，必要时引入 Pre-Vote 防止频繁切换。
- 日志冲突：新 Leader 从冲突点截断 Follower 日志，不能直接覆盖已提交日志。
- 磁盘损坏：节点丢失日志后不能直接加入集群，需要重新同步或快照恢复。
- 性能瓶颈：Raft 的提交受 Leader 串行限制，高吞吐场景用批量与多 Raft Group 分片。

**面试怎么答：** 先讲共识算法的目标与多数派原理，再讲 Paxos 的 Prepare/Promise、Accept/Accepted 两阶段；然后重点讲 Raft 的 Leader 选举、日志复制、提交规则三件事，说明 term 与随机超时如何避免脑裂；最后对比 Paxos 与 Raft 的工程差异，并举例 etcd、KRaft。

**易错点：**

- 认为 Paxos 能保证强实时一致：它只保证安全性与最终收敛。
- 把 Raft 的 Leader 当成单点：Leader 崩溃会重新选举。
- 以为多数派写入就立即持久：还需落盘与快照策略配合。
- 忽略 term：跨 term 的日志不能简单比较 index。
- 认为 ZAB 就是 Paxos：ZAB 是 ZooKeeper 专用协议，细节不同。

## 12. 分布式锁

**分布式锁要在多进程/多节点间提供互斥，必须同时满足「互斥、不死锁、可重入（可选）、高可用、性能可接受」**。工程上没有完美锁，只有「锁 + 超时 +  fencing token + 幂等」的组合；能用无锁方案（唯一索引、状态机、乐观锁）时优先不用分布式锁。

**方案对比：**

| 方案 | 互斥 | 死锁风险 | 性能 | 一致性 | 适用 |
| --- | --- | --- | --- | --- | --- |
| 数据库唯一键 | 是 | 需手动清理 | 低 | 强 | 低频、简单场景 |
| Redis SET NX PX | 是 | 靠过期时间 | 高 | 主从异步复制有风险 | 高频、短临界区 |
| Redisson | 是 | 看门狗续期 | 高 | 同上 | 需要可重入、等待队列 |
| ZooKeeper | 是 | 临时节点自动释放 | 中 | CP | 强一致、低频 |
| etcd | 是 | Lease 自动过期 | 中 | CP | 强一致、云原生 |

**Redis 锁的最小实现：**

```java
String token = UUID.randomUUID().toString();
Boolean ok = redis.opsForValue()
        .setIfAbsent("lock:order:" + orderId, token, Duration.ofSeconds(30));
if (Boolean.FALSE.equals(ok)) {
    return;                       // 获取失败，快速返回或排队
}
try {
    doBusiness();
} finally {
    String script = "if redis.call('get', KEYS[1]) == ARGV[1] then "
            + "return redis.call('del', KEYS[1]) else return 0 end";
    redis.execute(new DefaultRedisScript<>(script, Long.class),
            List.of("lock:order:" + orderId), token);
}
```

要点：

- 必须设置过期时间，否则进程崩溃后死锁。
- value 必须是唯一 token，释放时用 Lua 比对，避免误删别人的锁。
- 业务时间可能超过锁过期时间：需要续期（看门狗）或把临界区做短。
- 加锁与设置过期必须原子：`SET key value NX PX 30000`。

**Redisson 看门狗：**

```java
RLock lock = redisson.getLock("lock:order:" + orderId);
lock.lock();                       // 不指定 leaseTime，启用看门狗
try {
    doBusiness();
} finally {
    lock.unlock();
}
```

- 默认锁过期 30 秒，看门狗每 10 秒续期一次（约为租期的 1/3）。
- 显式指定 `leaseTime` 时看门狗不生效，业务必须保证在租期内完成。
- 可重入通过 Hash 结构记录「锁名 + 线程 ID + 重入次数」。

**ZooKeeper 锁：**

```java
String path = zkClient.createEphemeralSequential("/lock/order-", orderId);
// 获取 /lock/order- 下所有子节点并按序号排序
// 若自己不是最小节点，watch 前一个节点；前一个节点删除后重新判断
// 拿到锁后执行业务，最后删除自己的临时节点
```

- 临时顺序节点在会话结束后自动删除，避免死锁。
- Watch 前驱节点而不是所有节点，避免「羊群效应」。
- 缺点：依赖 ZK 可用性，写操作有延迟，性能不如 Redis。

**Redlock 与争议：**

- Redlock 在 5 个独立 Redis 节点上依次加锁，多数派成功且总耗时小于租期才算成功。
- 争议点：GC 停顿、时钟漂移、网络延迟可能让客户端在锁已失效后继续写。
- 更稳妥的做法：单 Redis + 足够短的临界区 + fencing token（单调递增版本号），数据库写入时校验 token，拒绝过期持有者的写。

**故障场景与兜底：**

- 锁过期但业务未完成：另一个线程进入临界区，产生并发写；用 fencing token 或延长租期。
- 误删他人锁：释放前比对 token，使用 Lua 原子删除。
- Redis 主从切换丢锁：异步复制下主库宕机可能丢锁；核心场景用 Redlock 或 ZK/etcd。
- GC/网络停顿：客户端暂停超过租期，恢复后继续写；必须用 fencing token 兜底。
- 锁粒度过粗：按订单号加锁而不是全局锁，降低竞争。
- 死锁：所有锁都必须有超时与自动释放机制。

**面试怎么答：** 先讲锁的五个要求，再对比数据库、Redis、ZK、etcd；重点讲 Redis 的 `SET NX PX` + 唯一 token + Lua 释放 + 看门狗续期；然后指出 Redis 主从异步复制的丢锁风险与 Redlock 的争议，给出 fencing token 兜底；最后强调优先用幂等、状态机、唯一索引替代分布式锁。

**易错点：**

- `SETNX` 后再 `EXPIRE` 两条命令：不是原子操作，中间宕机就死锁。
- 释放锁不校验 token：可能删掉别人刚获得的锁。
- 业务执行时间超过锁租期：看门狗只在未指定 `leaseTime` 时生效。
- 认为 Redis 锁绝对安全：主从切换与 GC 停顿都可能破坏互斥。
- 锁粒度过大或到处加锁：性能下降，还会引入新的死锁路径。
