## 1. 消息队列的作用与选型

**消息队列的本质是「在生产者与消费者之间加一个可持久化的缓冲区」，用异步与解耦换取吞吐和弹性，代价是一致性、复杂度与运维成本**。它解决的是「流量在时间上不均匀、系统在空间上强耦合」的问题，而不是所有架构问题的万能药。

**四大核心作用：**

| 作用 | 说明 | 典型场景 |
| --- | --- | --- |
| 解耦 | 生产者只依赖 MQ，不依赖下游实现 | 订单创建后通知库存、积分、风控 |
| 异步 | 主链路只做核心动作，旁路异步执行 | 注册后发短信、发券、写日志 |
| 削峰 | 把瞬时洪峰缓冲到队列，下游按能力消费 | 秒杀、抢购、批量导入 |
| 广播 | 一条消息被多个消费组各自消费 | 配置变更、缓存失效、事件总线 |

补充作用：分区内顺序保障、配合事务消息实现最终一致、积压量本身就是可观测的容量指标。

**引入 MQ 的代价：**

- 可用性从「A 调 B」变成「A → MQ → B」，MQ 成为新的单点，必须做集群、副本与容灾。
- 一致性从同步调用变成最终一致，需要幂等、重试、对账、补偿一整套机制。
- 排障链路变长：消息去哪了、为什么重复、为什么积压，都需要额外工具链。
- 延迟增加：一次网络跳转 + 落盘 + 消费调度，通常多几毫秒到几十毫秒。

**选型对比（重点）：**

| 维度 | Kafka | RabbitMQ | RocketMQ | Pulsar |
| --- | --- | --- | --- | --- |
| 模型 | 分区日志、拉取 | AMQP、推送 | 队列 + CommitLog | 存算分离、分层存储 |
| 吞吐 | 极高（百万级/秒） | 中（万级/秒） | 高（十万级/秒） | 高 |
| 延迟 | 毫秒级 | 微秒到毫秒级 | 毫秒级 | 毫秒级 |
| 路由 | 简单（Topic/Partition） | 非常灵活（4 种交换机） | 较简单（Tag/Key） | 较灵活 |
| 顺序 | 分区内有序 | 单队列有序 | 队列内严格有序 | 分区内有序 |
| 延迟消息 | 无原生支持 | TTL + DLX 或插件 | 原生支持 | 原生支持 |
| 事务消息 | 仅流处理 EOS | 无 | 原生半消息事务 | 无 |
| 运维 | 中（KRaft 后简化） | 低 | 中 | 高 |
| 生态 | 最好（Flink/Spark） | 好 | 国内较好 | 一般 |

**选型决策：**

1. 日志采集、流式计算、海量事件 → Kafka，吞吐与生态首选。
2. 业务消息、复杂路由、低延迟、中小规模 → RabbitMQ，上手快、路由灵活。
3. 电商/金融业务消息，需要事务消息、延迟消息、严格顺序 → RocketMQ。
4. 多租户、存算分离、消息与流一体 → Pulsar，但运维复杂度高。
5. 只是轻量异步且已有 Redis → Redis Stream，需接受持久化与可靠性偏弱。

**不该用 MQ 的场景：**

- 必须强一致、同步返回结果的核心链路，例如扣款结果、库存扣减结果。
- 调用关系简单、QPS 很低，引入 MQ 只是多了一个故障点。
- 要求亚毫秒级延迟且流量不大，直接 RPC 更合适。

**代码示例（Java，解耦 + 异步的典型写法）：**

```java
@Service
public class OrderService {
    private final KafkaTemplate<String, String> kafkaTemplate;

    public OrderService(KafkaTemplate<String, String> kafkaTemplate) {
        this.kafkaTemplate = kafkaTemplate;
    }

    @Transactional
    public void createOrder(Order order) {
        orderRepository.save(order);
        // 发送失败不阻塞主流程，由本地消息表或补偿任务兜底重发
        kafkaTemplate.send("order-created", order.getId(), order.toJson());
    }
}
```

**故障场景与兜底：**

- MQ 集群整体不可用：主链路降级为「写本地库 + 本地消息表」，恢复后由补偿任务重发。
- 消息发送成功但下游消费失败：依赖重试与死信队列，超过阈值转人工或补偿。
- 下游消费能力不足：先扩容消费者，再考虑分区扩容与降级非核心消息。
- 消息重复：消费端必须幂等，不能假设 MQ 只投递一次。

**面试怎么答：** 先给一句话定义「可持久化的异步缓冲区」，再讲解耦、异步、削峰、广播四个作用，每个作用配一个真实场景；然后主动说代价（可用性、一致性、排障、延迟），最后按吞吐、路由、延迟消息、事务消息、运维成本几个维度对比 Kafka/RabbitMQ/RocketMQ，并说明你们项目为什么选它。

**易错点：**

- 把 MQ 当成「银弹」：强一致、低延迟、简单调用场景引入 MQ 反而更糟。
- 只说优点不说代价：面试官通常追问「引入 MQ 后一致性问题怎么解决」。
- 选型只看吞吐：RabbitMQ 的路由能力、RocketMQ 的事务消息都是业务侧的关键差异。
- 忽略消费端幂等：任何 MQ 都只能保证至少一次或尽力而为，重复是常态。
- 以为 Kafka 支持任意延迟消息：Kafka 本身没有延迟队列语义。

## 2. Kafka 架构与核心概念

**Kafka 是「以分区为单位、以日志文件为存储、以消费者组为并行单位」的分布式提交日志**：消息追加写入分区，分区内严格有序，分区之间无序；每个分区有多个副本，由 Leader 对外提供读写，Follower 只负责同步。

**核心组件：**

| 组件 | 职责 |
| --- | --- |
| Broker | 单个 Kafka 服务节点，负责存储分区、处理读写 |
| Topic | 逻辑消息类别，物理上由多个 Partition 组成 |
| Partition | 有序、追加写的日志分段，是并行与顺序的基本单位 |
| Replica | 分区的副本，分为 Leader 与 Follower |
| Producer | 按分区策略写入，可批量、压缩、重试 |
| Consumer | 以拉模式消费，按 offset 记录进度 |
| Consumer Group | 组内分区互斥分配，实现并行消费与负载均衡 |
| Controller | 管理分区 Leader 选举、副本状态与集群元数据 |
| Coordinator | Group Coordinator 负责 rebalance 与位点，Transaction Coordinator 负责事务 |

**存储结构：**

- 每个分区是一个追加写日志，切成多个 Segment（默认 `log.segment.bytes=1GB`）。
- Segment 由 `.log`（数据）、`.index`（偏移索引）、`.timeindex`（时间索引）组成。
- 保留策略默认按时间 `log.retention.hours=168`（7 天），也可按大小；`cleanup.policy=compact` 用于 changelog 类主题做键级压缩。

**读写流程：**

1. Producer 计算分区：有 key 按 key 哈希，无 key 在 2.4+ 采用粘性分区器尽量写满一个分区再切换。
2. 消息进入客户端缓冲区，按 `batch.size`、`linger.ms` 聚合成批后发送。
3. Broker 追加写入 Leader 的 Page Cache 并建立索引，按副本机制同步给 Follower。
4. Consumer 以 `poll` 拉取，按 `fetch.min.bytes`、`max.poll.records` 控制批量。
5. 消费完成后提交 offset 到 `__consumer_offsets`（默认 50 分区、副本 3）。

**关键默认值：**

| 配置 | 默认值 | 说明 |
| --- | --- | --- |
| `num.partitions` | 1 | 新建 Topic 默认分区数，生产环境需按吞吐规划 |
| `default.replication.factor` | 1 | 新建 Topic 默认副本数，生产环境通常设为 3 |
| `log.retention.hours` | 168 | 默认保留 7 天 |
| `log.segment.bytes` | 1073741824 | 单 Segment 1GB |
| `offsets.topic.num.partitions` | 50 | 位点主题分区数 |
| `auto.create.topics.enable` | true | 建议生产关闭，避免脏 Topic |

**代码示例（建 Topic 与 Java 生产/消费）：**

```bash
kafka-topics.sh --bootstrap-server 10.0.0.11:9092 \
    --create --topic order-created \
    --partitions 12 --replication-factor 3 \
    --config min.insync.replicas=2
```

```java
Properties props = new Properties();
props.put(ProducerConfig.BOOTSTRAP_SERVERS_CONFIG, "10.0.0.11:9092,10.0.0.12:9092");
props.put(ProducerConfig.KEY_SERIALIZER_CLASS_CONFIG, StringSerializer.class);
props.put(ProducerConfig.VALUE_SERIALIZER_CLASS_CONFIG, StringSerializer.class);
props.put(ProducerConfig.ACKS_CONFIG, "all");
props.put(ProducerConfig.ENABLE_IDEMPOTENCE_CONFIG, "true");
props.put(ProducerConfig.LINGER_MS_CONFIG, "5");
props.put(ProducerConfig.COMPRESSION_TYPE_CONFIG, "lz4");

KafkaProducer<String, String> producer = new KafkaProducer<>(props);
producer.send(new ProducerRecord<>("order-created", orderId, payload));
```

```java
Properties consumerProps = new Properties();
consumerProps.put(ConsumerConfig.BOOTSTRAP_SERVERS_CONFIG, "10.0.0.11:9092");
consumerProps.put(ConsumerConfig.GROUP_ID_CONFIG, "order-consumer");
consumerProps.put(ConsumerConfig.ENABLE_AUTO_COMMIT_CONFIG, "false");
consumerProps.put(ConsumerConfig.AUTO_OFFSET_RESET_CONFIG, "earliest");
consumerProps.put(ConsumerConfig.MAX_POLL_RECORDS_CONFIG, "100");
consumerProps.put(ConsumerConfig.KEY_DESERIALIZER_CLASS_CONFIG, StringDeserializer.class);
consumerProps.put(ConsumerConfig.VALUE_DESERIALIZER_CLASS_CONFIG, StringDeserializer.class);

KafkaConsumer<String, String> consumer = new KafkaConsumer<>(consumerProps);
consumer.subscribe(List.of("order-created"));
while (running) {
    ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(500));
    for (ConsumerRecord<String, String> record : records) {
        handle(record);
    }
    consumer.commitSync();
}
```

**故障场景与兜底：**

- 分区数不足导致消费并行度上不去：只能扩分区或新建更多分区的 Topic 做迁移。
- 单分区热点：检查 key 分布，必要时加随机后缀打散，但会牺牲该 key 的顺序。
- Broker 磁盘写满：设置保留策略与配额，磁盘水位告警，避免整机不可写。
- Controller 切换：KRaft 模式下由 Controller Quorum 选举，客户端会自动重连。

**面试怎么答：** 先画「Producer → Topic → Partition/Replica → Consumer Group」的结构，讲清分区是并行与有序的单位、副本是可靠性的单位、消费者组是并行消费的单位；再补充 Segment 存储、offset 与 `__consumer_offsets`、Controller 与 Coordinator 的职责，最后说明分区数与副本数的规划依据。

**易错点：**

- 以为 Topic 的消息全局有序：Kafka 只保证分区内有序。
- 把副本数当成分区数：副本是同一分区的冗余，不增加写并行度。
- 忽略 `default.replication.factor=1`，生产建 Topic 不显式指定副本数导致单副本。
- 消费者数超过分区数后多余消费者闲置，扩消费者前先看分区数。
- 以为 offset 存在 Broker 本地文件：消费者位点存放在 `__consumer_offsets` 主题中。

## 3. Kafka 的副本与 ISR

**Kafka 用「Leader/Follower 副本 + ISR 集合 + HW 水位」保证单分区的高可用与一致性**：所有读写都走 Leader，Follower 持续拉取 Leader 的日志；只有追得上 Leader 的副本才留在 ISR，Leader 挂掉后从 ISR 中选新 Leader，从而把「已确认写入」的丢失概率降到最低。

**副本角色与位点：**

| 概念 | 含义 |
| --- | --- |
| Leader | 唯一对外提供读写的副本，维护分区日志 |
| Follower | 只读拉取 Leader 日志，不对外服务 |
| LEO | Log End Offset，副本下一条待写入位置 |
| HW | High Watermark，ISR 中最小 LEO，消费者最多读到 HW |
| ISR | In-Sync Replicas，与 Leader 同步在阈值内的副本集合 |
| `replica.lag.time.max.ms` | 判定不同步的时间阈值，默认 10000 毫秒 |
| `min.insync.replicas` | 写入成功所需的最小 ISR 数量，默认 1 |
| `unclean.leader.election.enable` | 是否允许非 ISR 副本当选，默认 false |

**写入与确认流程：**

1. Producer 发送到 Leader，Leader 追加本地日志，LEO 前移。
2. Leader 把消息分发给 ISR 中的 Follower。
3. Follower 追加成功后，LEO 前移；Leader 更新 HW 为 ISR 内最小 LEO。
4. 当 `acks=all` 时，Leader 等到 ISR 中除自己外的副本都追上（满足 `min.insync.replicas`）才向 Producer 返回成功。
5. 消费者只能读到 HW 之前的消息，避免读到尚未同步完成的数据。

**副本配置建议（RF=3）：**

```properties
# broker 端
default.replication.factor=3
min.insync.replicas=2
unclean.leader.election.enable=false
replica.lag.time.max.ms=10000
auto.leadership.rebalance.enable=true
```

```properties
# producer 端
acks=all
enable.idempotence=true
retries=2147483647
max.in.flight.requests.per.connection=5
```

**运维命令：**

```bash
# 查看分区、Leader、副本与 ISR
kafka-topics.sh --bootstrap-server 10.0.0.11:9092 --describe --topic order-created

# 触发首选 Leader 均衡
kafka-leader-election.sh --bootstrap-server 10.0.0.11:9092 \
    --election-type preferred --all-topic-partitions

# 分区副本重分配
kafka-reassign-partitions.sh --bootstrap-server 10.0.0.11:9092 \
    --reassignment-json-file reassign.json --execute
```

**Leader 选举规则：**

- Leader 崩溃后，Controller 从 ISR 中挑选新 Leader，通常优先与原 Leader 同机架的副本。
- 若 ISR 为空且开启 unclean 选举，可能选出一个严重落后的副本，造成数据回退。
- 关闭 unclean 选举时，如果 ISR 数量小于 `min.insync.replicas`，`acks=all` 的写入会直接失败（`NOT_ENOUGH_REPLICAS`），这是「宁可不可写，也不丢数据」的取舍。

**故障场景与兜底：**

- 单 Broker 宕机：ISR 中仍有 2 个副本，选主后继续服务，但写入吞吐下降。
- 两副本同时宕机：ISR 只剩 1 个，小于 `min.insync.replicas=2`，写入失败；应尽快恢复副本。
- 副本同步落后：检查网络、磁盘 IO 与 `replica.lag.time.max.ms`，避免副本被踢出 ISR 后反复进出。
- 脑裂与数据回退：禁止 unclean 选举，配合机架感知与跨 AZ 部署。
- 分区倾斜：部分分区 Leader 集中在一台 Broker，用首选 Leader 均衡或重分配修复。

**面试怎么答：** 先讲 Leader/Follower、LEO/HW、ISR 三个概念，再讲一次写入从 Leader 到 Follower 再到 HW 推进的过程；重点说明 `acks=all` + `min.insync.replicas=2` + `unclean=false` 这组配置如何在「丢数据」和「可用性」之间取舍，最后补 Leader 选举与 ISR 收缩的运维手段。

**易错点：**

- 以为 `acks=all` 就等于强一致：它只保证所有 ISR 副本收到，ISR 本身可能已经缩小。
- 忽略 `min.insync.replicas` 默认是 1：RF=3 但 min ISR=1 时，仍可能在只剩一个副本时继续写。
- 把 HW 与 LEO 混为一谈：HW 是消费者可见边界，LEO 是副本写入末尾。
- 认为 Follower 也提供读：Kafka 的读默认只走 Leader（副本读是有限特性）。
- 副本数越多越好：副本增加同步开销与存储成本，3 副本通常是可靠性与成本的平衡点。

## 4. Kafka 如何保证不丢不重

**Kafka 的「不丢」需要 Producer、Broker、Consumer 三段各自兜底，「不重」则依赖幂等生产者与事务，端到端精确一次只在特定配置下成立**。任何一段缺失，都会出现消息丢失或重复，因此面试要按链路分段回答，而不是一句「acks=all」。

**三段可靠性：**

| 环节 | 丢失原因 | 解决手段 |
| --- | --- | --- |
| Producer | `acks=0/1`、缓冲区未 flush 就退出、重试关闭、超时过短 | `acks=all`、幂等、重试、`delivery.timeout.ms`、发送后 `flush` 或同步等待 |
| Broker | 单副本、未落盘、unclean 选举、磁盘损坏 | RF=3、`min.insync.replicas=2`、`unclean=false`、跨机架/跨 AZ |
| Consumer | 自动提交早于处理、处理失败后仍提交、rebalance 丢位点 | 关闭自动提交、处理成功后手动提交、幂等消费 |

**Producer 侧关键配置：**

```properties
acks=all
enable.idempotence=true
retries=2147483647
max.in.flight.requests.per.connection=5
delivery.timeout.ms=120000
request.timeout.ms=30000
linger.ms=5
batch.size=16384
compression.type=lz4
```

- 3.0 起 `acks` 默认已改为 `all`、`enable.idempotence` 默认已改为 `true`，但显式声明更安全。
- 幂等生产者通过 PID + 分区级 sequence number 去重，重试不会产生重复消息。
- `max.in.flight.requests.per.connection` 在幂等模式下可以保持 5，因为序列号能纠正乱序重试。

**Broker 侧关键配置：**

```properties
default.replication.factor=3
min.insync.replicas=2
unclean.leader.election.enable=false
log.flush.interval.messages=9223372036854775807
log.flush.interval.ms=null
```

- Kafka 默认依赖 OS Page Cache，不在每条消息后 fsync；单机掉电可能丢最近未刷盘数据，但副本仍有一份。
- 真正要防的是「副本也没收到就确认」，因此副本数与 min ISR 比 `log.flush` 更重要。

**Consumer 侧关键配置：**

```properties
enable.auto.commit=false
auto.offset.reset=earliest
max.poll.records=100
max.poll.interval.ms=300000
session.timeout.ms=45000
heartbeat.interval.ms=3000
```

```java
while (running) {
    ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(500));
    for (ConsumerRecord<String, String> record : records) {
        process(record);          // 必须幂等，失败抛出进入重试
    }
    consumer.commitSync();        // 全部处理成功后再提交
}
```

**精确一次（EOS）：**

- 生产者幂等只解决「重试导致的重复」，解决不了「业务处理 + 位点提交」的原子性。
- 事务生产者：设置 `transactional.id`，`initTransactions` → `beginTransaction` → 发送 → `sendOffsetsToTransaction` → `commitTransaction`。
- 消费者设置 `isolation.level=read_committed`，只读已提交事务的消息，未提交的读不到。
- Kafka Streams 可设 `processing.guarantee=exactly_once_v2`，把「处理 + 状态 + 位点」放进同一事务。

```java
producer.initTransactions();
try {
    producer.beginTransaction();
    producer.send(new ProducerRecord<>("order-created", orderId, payload));
    producer.sendOffsetsToTransaction(offsets, consumerGroupId);
    producer.commitTransaction();
} catch (Exception e) {
    producer.abortTransaction();
    throw e;
}
```

**故障场景与兜底：**

- 发送超时但 Broker 已写入：幂等生产者用序列号去重，避免重试产生两条。
- 消费者处理成功但提交前宕机：重启后重复消费，靠业务幂等表兜底。
- rebalance 期间位点未提交：使用协作式 rebalance 与较短的处理时间，避免超过 `max.poll.interval.ms`。
- 跨系统精确一次：Kafka 事务只管 Kafka 内部，业务库与消息的一致性要用本地消息表或事务消息。

**面试怎么答：** 按 Producer、Broker、Consumer 三段讲丢失点与对策，明确「acks=all + 幂等 + 手动提交」只能做到至少一次；再讲事务生产者如何把「发送」和「位点提交」放进同一事务，消费者用 `read_committed` 实现 Kafka 内部的精确一次；最后强调跨库场景仍需业务幂等或本地消息表。

**易错点：**

- 以为 `acks=all` 一定不丢：ISR 可能只剩一个副本，必须配合 `min.insync.replicas`。
- 以为开启幂等就不会重复：幂等只对 Producer 重试有效，消费端重复仍需自己处理。
- 先提交 offset 再处理消息：进程崩溃会直接丢消息。
- 把 Kafka 事务当成分布式事务：它不覆盖数据库写入。
- 忽略 `delivery.timeout.ms` 必须大于 `request.timeout.ms` 与 `linger.ms` 之和。

## 5. RabbitMQ 的模型与交换机

**RabbitMQ 基于 AMQP 0-9-1，核心是「Producer → Exchange → Binding → Queue → Consumer」的投递模型**：生产者不直接发队列，而是发给交换机，交换机按绑定规则把消息路由到一个或多个队列；路由的灵活性来自四种交换机类型。

**核心概念：**

| 概念 | 说明 |
| --- | --- |
| Virtual Host | 逻辑隔离单元，拥有独立的交换机、队列与权限 |
| Connection | TCP 连接，成本高，应复用 |
| Channel | 连接内的轻量会话，绝大多数操作在 Channel 上完成 |
| Exchange | 接收生产者消息并按规则路由，不存储消息 |
| Binding | 交换机与队列之间的路由规则，可带 routing key |
| Queue | 实际存储消息的实体，竞争消费 |
| Consumer | 订阅队列，支持手动/自动确认 |

**四种交换机：**

| 类型 | 路由规则 | 典型场景 |
| --- | --- | --- |
| direct | routing key 完全匹配 | 按错误级别、按订单类型分发 |
| fanout | 忽略 routing key，广播到所有绑定队列 | 配置刷新、全量通知 |
| topic | `*` 匹配一个单词，`#` 匹配零或多个单词，以 `.` 分隔 | `order.created.*`、`log.error.#` |
| headers | 按消息头键值匹配，`x-match=all/any` | 复杂多维条件路由 |

默认交换机 `""` 是 direct 类型，routing key 直接等于队列名，适合点对点。

**可靠性三件套：**

1. 交换机持久化：`exchangeDeclare(name, type, durable=true)`。
2. 队列持久化：`queueDeclare(name, durable=true, exclusive=false, autoDelete=false)`。
3. 消息持久化：`deliveryMode=2`，同时配合 Publisher Confirm 确认 Broker 已接收。
4. 消费端手动 ACK：处理成功后 `basicAck`，失败 `basicNack` 并决定是否重回队列。
5. 设置 `basicQos(prefetchCount)` 控制预取，避免一个消费者囤积过多消息。

**代码示例（Java，声明、绑定、手动 ACK）：**

```java
ConnectionFactory factory = new ConnectionFactory();
factory.setHost("10.0.0.10");
factory.setUsername("app");
factory.setPassword("***");

try (Connection connection = factory.newConnection();
        Channel channel = connection.createChannel()) {
    channel.exchangeDeclare("order.exchange", "topic", true);
    Map<String, Object> args = new HashMap<>();
    args.put("x-dead-letter-exchange", "order.dlx");
    args.put("x-queue-type", "quorum");
    channel.queueDeclare("order.created.queue", true, false, false, args);
    channel.queueBind("order.created.queue", "order.exchange", "order.created.#");
    channel.basicQos(10);

    channel.basicConsume("order.created.queue", false, (tag, delivery) -> {
        try {
            handle(delivery.getBody());
            channel.basicAck(delivery.getEnvelope().getDeliveryTag(), false);
        } catch (Exception e) {
            channel.basicNack(delivery.getEnvelope().getDeliveryTag(), false, false);
        }
    }, tag -> { });
}
```

**Publisher Confirm：**

```java
channel.confirmSelect();
channel.addConfirmListener((sequence, ack) -> {
    if (!ack) {
        log.warn("message {} not confirmed", sequence);
    }
}, (sequence, cause) -> log.error("confirm failed", cause));
channel.basicPublish("order.exchange", "order.created.paid", props, body);
channel.waitForConfirmsOrDie(5000);
```

**故障场景与兜底：**

- 消息不可路由：开启 `mandatory` 并注册 `ReturnListener`，否则消息会被静默丢弃。
- Broker 内存/磁盘告警：触发流控甚至阻塞生产者，需设置水位与告警。
- 单节点故障：使用 quorum queue（3.8+，基于 Raft，至少 3 节点），4.0 起不再推荐经典队列镜像。
- 消费者异常退出：手动 ACK 未确认的消息会重回队列，必须保证消费幂等。
- 毒消息无限重投：`basicNack` 时 `requeue=false` 进入死信队列，而不是反复重回。

**面试怎么答：** 先讲 Exchange、Binding、Queue、Channel、VHost 五个概念，强调「生产者只认交换机」；再对比 direct/fanout/topic/headers 的路由差异；然后讲可靠性三件套（持久化、Confirm、手动 ACK）与 prefetch 的意义；最后补 quorum queue 与死信队列的运维实践。

**易错点：**

- 只声明队列持久化，却忘了交换机持久化或消息 `deliveryMode`，宕机后仍会丢。
- 开了自动 ACK：消费者收到即确认，处理失败就永久丢消息。
- `basicNack(requeue=true)` 处理业务错误：会形成死循环重投，应转入死信。
- 以为 topic 的 `*` 能匹配多层：`*` 只匹配一个单词，多层要用 `#`。
- 一个 Connection 上开大量 Channel 且不关闭，导致句柄泄漏；Channel 不是线程安全的。

## 6. RocketMQ 架构

**RocketMQ 是「NameServer 管路由、Broker 存消息、Producer/Consumer 按组协作」的队列型消息中间件**，在事务消息、延迟消息、严格顺序和堆积能力上更贴近电商与金融业务；存储上采用 CommitLog + ConsumeQueue 的两级结构，兼顾顺序写与按队列消费。

**4.x 核心组件：**

| 组件 | 职责 |
| --- | --- |
| NameServer | 无状态路由注册中心，Broker 每 30 秒心跳注册，客户端每 30 秒拉取路由 |
| Broker | 存储与投递核心，分 Master/Slave，`brokerId=0` 为 Master |
| Producer Group | 生产者组，用于事务消息回查等场景 |
| Consumer Group | 消费者组，集群模式下组内分摊队列 |
| Topic | 逻辑主题，默认自动创建 4 个队列（`defaultTopicQueueNums=4`） |
| Message Queue | 分区单位，决定顺序与并行度 |

**存储结构：**

- CommitLog：所有 Topic 的消息按到达顺序追加写，顺序写磁盘，吞吐高。
- ConsumeQueue：按 Topic + Queue 建立的索引，记录消息在 CommitLog 的物理偏移、大小与 tag hash。
- IndexFile：按消息 key 建立索引，支持按 key 查询。
- 刷盘：`flushDiskType=ASYNC_FLUSH` 默认异步刷盘；`SYNC_FLUSH` 同步刷盘更可靠但更慢。
- 主从：`brokerRole=ASYNC_MASTER` 默认异步复制；`SYNC_MASTER` 等 Slave 确认，可靠性更高。

**5.x 变化：**

- 增加 Proxy 层，支持 gRPC 与多语言客户端，NameServer 仍保留。
- 支持任意时间延迟消息（基于时间轮），不再局限于 18 个固定档位。
- 支持 Controller 模式（基于 DLedger/Raft）做自动主备切换，减少人工运维。

**发送与消费流程：**

1. Producer 从 NameServer 获取 Topic 路由，选择可写 Broker 与队列。
2. 消息写入 CommitLog，异步构建 ConsumeQueue 与 IndexFile。
3. 消费者拉取 ConsumeQueue，按偏移从 CommitLog 读取消息体。
4. 集群消费模式下，位点保存在 Broker；广播模式保存在客户端本地。
5. 消费失败进入 `%RETRY%消费组` 重试主题，超过次数进入 `%DLQ%消费组` 死信主题。

**代码示例（Java，同步发送与集群消费）：**

```java
DefaultMQProducer producer = new DefaultMQProducer("order-producer");
producer.setNamesrvAddr("10.0.0.21:9876;10.0.0.22:9876");
producer.setRetryTimesWhenSendFailed(2);
producer.start();

Message message = new Message("OrderTopic", "Pay", orderId,
        payload.getBytes(StandardCharsets.UTF_8));
SendResult result = producer.send(message);
log.info("send status={}, msgId={}", result.getSendStatus(), result.getMsgId());
producer.shutdown();
```

```java
DefaultMQPushConsumer consumer = new DefaultMQPushConsumer("order-consumer");
consumer.setNamesrvAddr("10.0.0.21:9876");
consumer.subscribe("OrderTopic", "Pay || Refund");
consumer.setConsumeMode(ConsumeMode.CONCURRENTLY);
consumer.registerMessageListener((MessageListenerConcurrently) (messages, context) -> {
    for (MessageExt message : messages) {
        handle(message);
    }
    return ConsumeConcurrentlyStatus.CONSUME_SUCCESS;
});
consumer.start();
```

**故障场景与兜底：**

- NameServer 全挂：客户端仍可用本地缓存路由一段时间，但新 Topic 无法发现，应至少部署 2 台。
- Master 宕机：4.x 需手动切换或依赖 DLedger 主备；5.x Controller 模式可自动选主。
- 异步刷盘掉电：Page Cache 中未刷盘消息可能丢失，核心业务用 `SYNC_FLUSH`。
- 异步复制主库故障：Slave 可能缺少最后一批消息，核心业务用 `SYNC_MASTER`。
- 消费堆积：优先扩消费者（不超过队列数），必要时增加队列或临时转发到新 Topic。

**面试怎么答：** 先讲 NameServer、Broker、Producer、Consumer 四角色与「Broker 向 NameServer 注册、客户端拉路由」的弱一致设计；再讲 CommitLog + ConsumeQueue 的存储结构为什么能兼顾顺序写与随机消费；最后对比 4.x 与 5.x（Proxy、任意延迟、Controller 自动切换），并说明同步刷盘/同步复制的可靠性取舍。

**易错点：**

- 以为 NameServer 强一致：它是 AP 设计，路由可能短暂过期，客户端需容忍重试。
- 把 ConsumeQueue 当成消息存储：消息体在 CommitLog，ConsumeQueue 只是索引。
- 默认异步刷盘 + 异步复制就宣称「金融级可靠」，需要显式改为同步。
- 消费者数量超过队列数，多余消费者空转；扩队列对已有 key 的顺序有影响。
- 广播模式误用集群位点：广播模式位点存客户端本地，换机器会重复消费。

## 7. 消息顺序性

**消息队列只能保证「局部有序」，全局有序的代价是单队列单消费者，吞吐会急剧下降**。工程上的正确做法是「按业务主键选分区/队列，让同一业务实体的消息进入同一分区，并在消费端对同一分区串行处理」。

**三种语义：**

| 语义 | 含义 | 实现代价 |
| --- | --- | --- |
| 分区内有序 | 同一分区/队列内按写入顺序消费 | 低，常规做法 |
| 业务键有序 | 同一订单/用户的消息有序，不同键可并行 | 中，需要按 key 路由 |
| 全局有序 | 所有消息严格 FIFO | 极高，单分区单消费者 |

**各 MQ 的实现：**

| MQ | 顺序手段 | 注意事项 |
| --- | --- | --- |
| Kafka | 消息带 key → 同一分区；消费者单线程处理该分区 | 扩分区会改变 key 的落点，历史顺序无法跨分区保证 |
| RocketMQ | 发送时用 `MessageQueueSelector` 按业务键选队列；消费用 `MessageListenerOrderly` | 顺序消费会加队列锁，消费能力受限 |
| RabbitMQ | 单队列单消费者；或用 consistent hash exchange 按 key 路由 | 多消费者竞争同一队列即失去顺序 |

**Kafka 生产端按 key 路由：**

```java
ProducerRecord<String, String> record =
        new ProducerRecord<>("order-events", orderId, payload);
producer.send(record);
```

同一 `orderId` 会哈希到同一分区；只要分区数不变，该订单的事件就保持顺序。

**Kafka 消费端串行处理：**

```java
// 单分区单线程：最稳妥，但吞吐受限于单线程
while (running) {
    ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(500));
    for (ConsumerRecord<String, String> record : records) {
        processInOrder(record);
    }
    consumer.commitSync();
}
```

若要多线程，必须按 key 再哈希到固定工作线程，且同一 key 不能被两个线程同时处理：

```java
ExecutorService[] workers = new ExecutorService[8];
for (int i = 0; i < workers.length; i++) {
    workers[i] = Executors.newSingleThreadExecutor();
}
for (ConsumerRecord<String, String> record : records) {
    int slot = Math.floorMod(record.key().hashCode(), workers.length);
    workers[slot].submit(() -> processInOrder(record));
}
```

**RocketMQ 顺序发送与顺序消费：**

```java
// 生产端：按订单号选择同一个队列
SendResult result = producer.send(message, (queues, msg, arg) -> {
    int index = Math.floorMod(arg.hashCode(), queues.size());
    return queues.get(index);
}, orderId);
```

```java
// 消费端：顺序消费，失败时挂起当前队列而不是跳过
consumer.registerMessageListener((MessageListenerOrderly) (messages, context) -> {
    for (MessageExt message : messages) {
        if (!handle(message)) {
            return ConsumeOrderlyStatus.SUSPEND_CURRENT_QUEUE_A_MOMENT;
        }
    }
    return ConsumeOrderlyStatus.SUCCESS;
});
```

**故障场景与兜底：**

- 消费者多线程乱序：按 key 分派到固定线程，或退回单分区单线程。
- 消费失败跳过：顺序消费必须挂起当前队列重试，不能返回成功继续消费后面的消息。
- 分区扩容：同一 key 可能迁到新分区，扩容窗口内顺序被打断，应选择低峰并接受重放。
- 重试消息乱序：重试队列与主队列分离，重试成功后可能晚于后续消息，需业务状态机兜底。
- 跨服务顺序：下游多实例并发处理，仍需按业务键做串行化（如分布式锁或状态机）。

**面试怎么答：** 先明确「只有局部有序」，再讲「业务主键 → 分区/队列 → 单线程或按 key 串行」这条主线；对比 Kafka、RocketMQ、RabbitMQ 的具体手段；最后说明顺序与吞吐的取舍，以及扩分区、重试、下游并发都会破坏顺序，需要状态机或幂等兜底。

**易错点：**

- 认为 Kafka 设置一个分区就能全局有序且高吞吐：单分区写入与消费都会成为瓶颈。
- 消费者开了线程池却按消息逐条提交：同一 key 被并发处理，顺序失效。
- RocketMQ 顺序消费失败后返回 `CONSUME_SUCCESS`：后面的消息会越过失败消息。
- 扩分区后仍假设同一 key 落原分区：分区数变化会改变哈希取模结果。
- 忽略下游服务的并发：MQ 内有序不代表端到端有序。

## 8. 消息积压处理

**积压的本质是「生产速率持续大于消费速率」，处理顺序应是「先止血、再定位、后治理」**：先保证线上不被拖垮（扩容、降级、转发），再查清是流量突增、消费变慢、分区倾斜还是毒消息，最后补上容量规划与监控。

**先定位：**

| 现象 | 可能原因 | 排查手段 |
| --- | --- | --- |
| 所有分区 lag 均匀上涨 | 流量突增或消费者整体变慢 | 对比生产 TPS 与消费 TPS、看 GC 与下游 RT |
| 少数分区 lag 极高 | key 倾斜或单分区热点 | `kafka-consumer-groups.sh --describe` 看分区 lag |
| 消费 TPS 为 0 | 消费者挂掉、rebalance 卡住、毒消息阻塞 | 看消费线程栈、rebalance 日志、重试次数 |
| 反复 rebalance | 处理超时超过 `max.poll.interval.ms` | 调小 `max.poll.records`、缩短单批处理时间 |
| 下游超时 | DB/HTTP 瓶颈 | 看下游监控、连接池、慢查询 |

```bash
kafka-consumer-groups.sh --bootstrap-server 10.0.0.11:9092 \
    --describe --group order-consumer
# 关注 CURRENT-OFFSET、LOG-END-OFFSET、LAG 以及分区分布
```

**应急处置手段：**

| 手段 | 适用 | 代价 |
| --- | --- | --- |
| 扩消费者 | 消费者数小于分区数 | 最直接，受分区数上限约束 |
| 扩分区 | 长期容量不足 | 只对新消息生效，破坏 key 顺序 |
| 新建大分区 Topic + 转发 | 紧急消化历史积压 | 需要转发程序，期间可能重复 |
| 批量消费 + 异步化 | 单条处理 RT 高 | 要保证幂等与提交语义 |
| 降级非核心消息 | 流量洪峰 | 业务有损，需提前约定 |
| 丢弃/归档低价值消息 | 日志类数据 | 不可恢复，谨慎 |
| 提升下游能力 | DB/HTTP 瓶颈 | 成本高，需联动 |

**消费者扩容的边界：**

- Kafka 的有效并行度 = 分区数；消费者数超过分区数后，多余实例处于空闲。
- RocketMQ 的有效并行度 = 队列数；顺序消费还会进一步受队列锁限制。
- RabbitMQ 单队列多消费者可提升吞吐，但顺序性会丢失。

**代码示例（Kafka 提升单批处理能力）：**

```properties
max.poll.records=500
fetch.min.bytes=65536
fetch.max.wait.ms=500
max.partition.fetch.bytes=1048576
```

```java
// 批量入库替代逐条写库，显著降低消费 RT
ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(500));
List<OrderEvent> batch = new ArrayList<>(records.count());
for (ConsumerRecord<String, String> record : records) {
    batch.add(parse(record));
}
orderRepository.saveAll(batch);   // 需保证 upsert 幂等
consumer.commitSync();
```

**紧急转发程序（伪代码）：**

```text
1. 新建 topic `order-created-v2`，分区数扩大为原来的 4 倍
2. 启动转发消费者：从旧 topic 消费，不执行业务，只写入新 topic
3. 转发程序按 key 写入，保证同一业务键仍有序
4. 新 topic 上部署 N 倍消费者并行消化
5. 积压清零后，切回正常消费逻辑，旧 topic 下线
```

**故障场景与兜底：**

- 盲目扩消费者超过分区数：新增实例空转，浪费资源且不提升吞吐。
- 直接扩分区：key 的哈希落点变化，历史顺序与幂等假设可能失效。
- 批量消费后整批提交：部分失败会导致整批重放，必须做幂等或逐条状态记录。
- 消费线程池打满：`max.poll.interval.ms` 超时触发 rebalance，形成恶性循环。
- 毒消息反复重试：设置最大重试次数并转入死信，避免阻塞整个分区。

**面试怎么答：** 按「监控 lag → 判断是突增还是变慢 → 扩容/降级止血 → 定位根因 → 长期治理」的顺序讲；强调 Kafka 的并行度上限是分区数，扩容前先看分区分布与倾斜；再给紧急转发方案（新 Topic 扩分区 + 转发程序）与批量消费、异步化、死信兜底等细节。

**易错点：**

- 一上来就扩分区：历史消息仍在旧分区，且会破坏 key 顺序。
- 消费者数量超过分区数：多出来的实例不会消费任何消息。
- 只扩消费者不看下游：DB 或第三方接口先被打垮。
- 批量处理失败后整批重试：没有幂等会导致重复写。
- 忽略 rebalance：单批处理时间超过 `max.poll.interval.ms` 会不断触发再平衡。

## 9. 延迟消息

**延迟消息是「消息在指定时间之后才可被消费」的语义，常用于订单超时取消、支付超时、定时提醒与失败重试**。不同 MQ 的支持程度差异很大：RocketMQ 原生支持，RabbitMQ 需要 TTL + 死信或插件，Kafka 没有原生语义，必须借助外部调度。

**实现方案对比：**

| 方案 | 精度 | 规模 | 说明 |
| --- | --- | --- | --- |
| RocketMQ 固定档位 | 秒级，18 档 | 大 | 默认 `1s 5s 10s 30s 1m ... 2h`，超出按档位取整 |
| RocketMQ 5.x 任意时间 | 秒级 | 大 | 基于时间轮，支持指定时刻 |
| RabbitMQ TTL + DLX | 秒级 | 中 | 队列级 TTL 可靠，消息级 TTL 只在队头生效 |
| RabbitMQ delayed 插件 | 毫秒级 | 中 | `x-delayed-message` 交换机，依赖插件与单点存储 |
| Kafka + 外部调度 | 取决于调度 | 大 | 落库/Redis ZSet，扫描到期后投递 |
| Pulsar | 毫秒级 | 大 | 原生 delayed delivery |
| Redis ZSet | 毫秒级 | 中 | `ZADD` + 定时扫描，需处理持久化与多实例竞争 |

**RabbitMQ：TTL + 死信队列**

```java
Map<String, Object> args = new HashMap<>();
args.put("x-message-ttl", 30000);                       // 队列级 TTL，30 秒
args.put("x-dead-letter-exchange", "order.delay.dlx");  // 到期转入死信交换机
args.put("x-dead-letter-routing-key", "order.timeout");
channel.queueDeclare("order.delay.30s", true, false, false, args);
channel.queueBind("order.delay.30s", "order.delay.exchange", "order.created");
```

注意：**消息级 TTL 只有在消息到达队头时才会被检查**，如果队列里有更长的 TTL 消息阻塞，短 TTL 消息不会先过期。需要不同延迟粒度时，按档位拆多个队列。

**RabbitMQ delayed 插件：**

```java
Map<String, Object> args = new HashMap<>();
args.put("x-delayed-type", "direct");
channel.exchangeDeclare("order.delayed.exchange", "x-delayed-message", true, false, args);
AMQP.BasicProperties props = new AMQP.BasicProperties.Builder()
        .headers(Map.of("x-delay", 30000))
        .deliveryMode(2)
        .build();
channel.basicPublish("order.delayed.exchange", "order.timeout", props, body);
```

**RocketMQ：**

```java
Message message = new Message("OrderDelayTopic", body.getBytes(StandardCharsets.UTF_8));
// 18 个固定档位：1s 5s 10s 30s 1m 2m 3m 4m 5m 6m 7m 8m 9m 10m 20m 30m 1h 2h
message.setDelayTimeLevel(3);
producer.send(message);

// 5.x 支持指定时间戳（毫秒），精度到秒
Message timedMessage = new Message("OrderDelayTopic", body.getBytes(StandardCharsets.UTF_8));
timedMessage.setDelayTimeMs(30_000L);
producer.send(timedMessage);
```

**Kafka 的替代方案（Redis ZSet + 调度器）：**

```text
1. 下单时写入 ZSet：ZADD delay:order <deadline> <orderId>
2. 调度器每秒执行 ZRANGEBYSCORE delay:order 0 now LIMIT 0 100
3. 用 Lua 原子地 ZREM + 投递 Kafka，保证只有一个实例处理
4. 消费端按 orderId 幂等取消订单，已支付的直接忽略
```

**故障场景与兜底：**

- 延迟精度要求高但用了固定档位：只能取整到最近档位，业务要接受误差。
- RabbitMQ 消息级 TTL 被队头阻塞：按延迟档位拆队列，或改用插件。
- 调度器单点：多实例抢占需要分布式锁或 Lua 原子操作，避免重复投递。
- 消息到期时业务已处理：消费端必须做状态判断，延迟消息只是「提醒」而非「命令」。
- 服务重启丢失内存时间轮：延迟任务必须持久化，重启后重建。
- 超长延迟（几天/几周）：不要放在 MQ 里空等，落库后由调度系统扫描。

**面试怎么答：** 先给业务场景，再对比 RocketMQ、RabbitMQ、Kafka 的支持差异；重点讲 RabbitMQ 的 TTL + DLX 与「消息级 TTL 只在队头生效」这个坑，以及 RocketMQ 的 18 档与 5.x 任意时间；最后给 Kafka 场景下的外部调度方案（DB/Redis ZSet + 定时扫描 + 幂等）。

**易错点：**

- 以为 RabbitMQ 每条消息的 TTL 都独立生效：队列中前面有长 TTL 消息会阻塞后面的短 TTL。
- 把延迟消息当时钟：延迟消息可能晚到，业务要用状态机判断是否还需要执行。
- 用内存时间轮做延迟任务：重启即丢，必须持久化。
- RocketMQ 固定档位差一档：`delayTimeLevel` 从 1 开始，对应 1s。
- Kafka 上自己 pause 分区实现延迟：会阻塞该分区所有消息，不适合生产。

## 10. 事务消息

**事务消息解决的是「本地数据库事务」与「消息发送」的原子性**：要么本地事务成功且消息最终被投递，要么本地事务回滚且消息不投递。RocketMQ 用「半消息 + 本地事务 + 回查」实现，Kafka 的事务则是流处理内部的精确一次，两者不是一回事。

**RocketMQ 事务消息流程：**

```text
Producer                Broker                 Local DB
    |  1. 发送半消息 --------> |                       |
    | <---- 写入成功（对消费者不可见）                   |
    |  2. 执行本地事务 ------------------------------> |
    |  3. commit / rollback --> |                       |
    |                          |  4. 未收到结果则回查    |
    | <---- 回查本地事务状态 ---- |                       |
    |  5. 再次 commit / rollback                       |
    |                          |  6. 可见后投递给消费者  |
```

1. 生产者先发「半消息」，Broker 持久化但不允许消费者可见。
2. 半消息成功后执行本地事务（写订单库）。
3. 本地事务成功则 `COMMIT_MESSAGE`，失败则 `ROLLBACK_MESSAGE`。
4. 若生产者宕机未返回结果，Broker 定时回查生产者的本地事务状态。
5. 回查超过最大次数仍未知，消息会被丢弃或转入死信，需要告警与人工补偿。

**关键参数：**

| 参数 | 默认值 | 说明 |
| --- | --- | --- |
| `transactionTimeOut` | 60000 毫秒 | 半消息超过该时间未确认则触发回查 |
| `transactionCheckInterval` | 30000 毫秒 | 回查间隔 |
| `transactionCheckMax` | 15 | 最大回查次数 |

**代码示例（Java）：**

```java
public class OrderTransactionListener implements TransactionListener {
    @Override
    public LocalTransactionState executeLocalTransaction(Message msg, Object arg) {
        try {
            orderService.createOrder((Order) arg);
            return LocalTransactionState.COMMIT_MESSAGE;
        } catch (Exception e) {
            return LocalTransactionState.ROLLBACK_MESSAGE;
        }
    }

    @Override
    public LocalTransactionState checkLocalTransaction(MessageExt msg) {
        boolean exists = orderService.exists(msg.getKeys());
        if (exists) {
            return LocalTransactionState.COMMIT_MESSAGE;
        }
        return LocalTransactionState.UNKNOW;
    }
}
```

```java
TransactionMQProducer producer = new TransactionMQProducer("order-tx-producer");
producer.setNamesrvAddr("10.0.0.21:9876");
producer.setTransactionListener(new OrderTransactionListener());
producer.start();

Message message = new Message("OrderTopic", "Create", orderId,
        payload.getBytes(StandardCharsets.UTF_8));
SendResult result = producer.sendMessageInTransaction(message, order);
```

**与本地消息表、TCC 的区别：**

| 方案 | 原子性来源 | 依赖 | 一致性 |
| --- | --- | --- | --- |
| 事务消息 | MQ 半消息 + 回查 | RocketMQ | 最终一致 |
| 本地消息表 | 业务库与消息表同库同事务 | 任意 MQ | 最终一致 |
| TCC | 业务层 Try/Confirm/Cancel | 事务协调器 | 最终一致，隔离性更好 |

**Kafka 事务的边界：**

- Kafka 事务把「多条消息发送 + 消费位点提交」放在同一事务，用于流处理 EOS。
- 它不能把「写 MySQL」纳入事务，因此不能替代业务侧的分布式事务方案。
- 消费者需设置 `isolation.level=read_committed`，否则会读到未提交事务的消息。

**故障场景与兜底：**

- 本地事务成功但 commit 失败：Broker 回查后补 commit，消费者最终能收到。
- 本地事务回滚但 commit 消息丢失：回查返回 UNKNOW，超过次数后丢弃，业务需对账。
- 回查实现有误（查不到订单就返回 ROLLBACK）：可能把已成功的订单消息回滚，必须按「存在即 commit，不确定即 UNKNOW」处理。
- 消费者重复收到：事务消息仍是至少一次投递，消费端必须幂等。
- 事务消息堆积：半消息也占存储，需监控与告警。

**面试怎么答：** 先讲要解决的问题「本地事务与发消息的原子性」，再画半消息 → 本地事务 → commit/rollback → 回查的流程，强调半消息对消费者不可见；然后说明回查的作用与「UNKNOW 不能随意返回 ROLLBACK」；最后对比本地消息表、TCC，并指出 Kafka 事务只覆盖 Kafka 内部。

**易错点：**

- 把 Kafka 事务当成跨数据库的分布式事务。
- 回查时查不到记录就返回 ROLLBACK：可能是主从延迟或事务未提交，正确做法是 UNKNOW 继续回查。
- 以为事务消息能保证「消息只投一次」：它保证最终投递，不保证不重复。
- 本地事务里做了远程调用：远程超时会让本地事务状态与消息状态不一致。
- 忽略 `transactionCheckMax`：超过次数后消息会被丢弃，必须有对账兜底。

## 11. 消息幂等消费

**在至少一次投递语义下，重复消息是常态而不是异常，消费端必须做到「同一条消息执行多次，业务结果与执行一次相同」**。幂等的关键不是识别「同一条消息」，而是识别「同一个业务动作」，因此业务唯一键比消息 ID 更可靠。

**重复的来源：**

| 来源 | 场景 |
| --- | --- |
| 生产端重试 | 发送超时但 Broker 已写入，重试产生两条 |
| Broker 重投 | 消费者未 ACK、连接断开、消费超时 |
| 消费端重放 | 处理成功但提交位点前宕机 |
| rebalance | 位点未提交，分区转交给新消费者后从头消费 |
| 人为补偿 | 重放工具、对账修复重复投递 |

**幂等方案对比：**

| 方案 | 实现 | 适用 | 注意 |
| --- | --- | --- | --- |
| 唯一索引 | 业务表加唯一键，重复插入报冲突 | 创建类操作 | 捕获重复键异常并视为成功 |
| 去重表 | 独立表记录 `biz_key` 与状态 | 通用 | 与业务操作同事务，注意清理 |
| Redis SETNX | `SET key value NX EX` | 高频、可容忍丢失 | 过期后可能重复，需持久化兜底 |
| 状态机 | 只允许合法状态迁移 | 订单、支付 | 重复消息落在同一状态直接返回 |
| 乐观锁 | `UPDATE ... WHERE version = ?` | 更新类操作 | 冲突需重试或放弃 |
| 分布式锁 | 按业务键加锁 | 并发重复 | 锁只是串行化，不是幂等本身 |

**推荐组合：** 唯一索引/去重表做最终兜底，状态机做业务语义判断，Redis 做前置快速过滤（可选）。

**代码示例（Java，去重表 + 本地事务）：**

```java
@Transactional
public void handle(OrderPaidEvent event) {
    int inserted = dedupMapper.insertIgnore(event.getEventId(), "order-paid");
    if (inserted == 0) {
        return;                       // 已处理过，直接返回
    }
    orderRepository.markPaid(event.getOrderId());
    accountRepository.addPoints(event.getUserId(), event.getPoints());
}
```

```sql
CREATE TABLE consume_dedup (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    dedup_key VARCHAR(128) NOT NULL,
    status TINYINT NOT NULL DEFAULT 0,
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    UNIQUE KEY uk_dedup_key (dedup_key)
) ENGINE = InnoDB;
```

**代码示例（Redis 前置过滤）：**

```java
String key = "consume:order-paid:" + event.getEventId();
Boolean first = redis.opsForValue().setIfAbsent(key, "1", Duration.ofHours(24));
if (Boolean.FALSE.equals(first)) {
    return;
}
try {
    handleInTransaction(event);
} catch (Exception e) {
    redis.delete(key);            // 失败释放，允许重试
    throw e;
}
```

**业务唯一键怎么选：**

- 优先用业务主键 + 动作，例如 `orderId:PAY`、`userId:REGISTER`。
- 不要用 MQ 的 `messageId`：重试或重新发送后可能变化，且跨 Topic 不唯一。
- 事件类消息可用「聚合根 ID + 版本号」，版本号天然防重与防乱序。

**故障场景与兜底：**

- 去重表与业务表不在同一事务：业务成功但去重记录未写，重试会重复执行。
- Redis 被淘汰或宕机：前置过滤失效，必须靠数据库唯一键兜底。
- 去重表无限增长：按时间分区或定期归档，保留窗口要覆盖最大重试周期。
- 并发重复消息：两个线程同时通过前置检查，最终仍要靠唯一索引或 `INSERT IGNORE`。
- 副作用不可逆：发短信、扣款等操作要查状态或使用业务流水号，不能只靠「标记已处理」。

**面试怎么答：** 先说明「至少一次 → 必然重复」，再讲重复的五个来源；然后按「业务唯一键 → 去重表/唯一索引 → 状态机 → 前置 Redis 过滤」分层给出方案，强调去重记录必须与业务操作同事务；最后补清理策略、并发场景与不可逆副作用的处理。

**易错点：**

- 用消息 ID 做幂等键：重试后消息 ID 可能变化，跨 Topic 也不唯一。
- 先查 Redis 再处理：检查与处理不是原子操作，并发下仍会重复。
- 去重表和业务表分属不同库或不同事务：无法保证原子性。
- 认为「消费成功就幂等」：成功但位点未提交，重启后还会再消费。
- 忽略 TTL：去重记录过期早于最大重试窗口，会导致重复执行。

## 12. 死信队列与重试

**死信队列（DLQ）是「消息多次重试仍无法被正确处理」的最终容器，重试策略的核心是「区分可重试与不可重试错误，限制次数、退避、隔离毒消息」**。没有死信的消费系统，遇到毒消息要么无限重投拖垮分区，要么直接丢弃造成数据丢失。

**重试设计要点：**

| 要点 | 做法 |
| --- | --- |
| 错误分类 | 网络超时、限流、下游 5xx 可重试；参数错误、业务规则拒绝不可重试 |
| 最大次数 | 按业务设定，通常 3~16 次，超过转死信 |
| 退避 | 指数退避 + 随机抖动，避免重试风暴 |
| 幂等 | 每次重试都可能重复执行，必须幂等 |
| 隔离 | 毒消息不能阻塞正常消息，转入重试队列或死信 |
| 可观测 | 重试次数、死信量、原因分布都要有监控与告警 |
| 可回放 | 死信修复后能按原顺序或指定时间重放 |

**RabbitMQ：DLX + 重试队列**

```java
// 业务队列绑定死信交换机
Map<String, Object> args = new HashMap<>();
args.put("x-dead-letter-exchange", "order.dlx");
args.put("x-dead-letter-routing-key", "order.failed");
channel.queueDeclare("order.queue", true, false, false, args);

// 死信交换机再把消息路由到死信队列
channel.exchangeDeclare("order.dlx", "direct", true);
channel.queueDeclare("order.dlq", true, false, false, null);
channel.queueBind("order.dlq", "order.dlx", "order.failed");
```

消费失败时 `basicNack(tag, false, false)` 且不重回原队列，消息进入 DLX；若要延迟重试，可让 DLX 指向一个带 TTL 的重试队列，到期后再回到业务交换机。

**Kafka：没有原生死信，需要框架或自建**

```java
@RetryableTopic(
        attempts = "4",
        backoff = @Backoff(delay = 1000, multiplier = 2.0, maxDelay = 10000),
        autoCreateTopics = "false",
        dltTopicSuffix = ".dlt")
@KafkaListener(topics = "order-created", groupId = "order-consumer")
public void consume(OrderEvent event) {
    handle(event);
}

@DltHandler
public void onDeadLetter(OrderEvent event) {
    deadLetterRepository.save(event);
    alertService.notify("order-created dlt", event);
}
```

Spring Kafka 的 `@RetryableTopic` 会创建重试主题与 `.dlt` 死信主题；也可以手动实现「失败后写入 `xxx.dlq` 主题，再由补偿任务处理」。

**RocketMQ：内置重试主题与死信主题**

- 消费失败返回 `RECONSUME_LATER`，消息进入 `%RETRY%消费组`。
- 默认最多重试 16 次，按延迟档位逐级拉长间隔。
- 超过次数进入 `%DLQ%消费组`，只保留有限时间，需要订阅该主题做告警与人工处理。

```java
consumer.registerMessageListener((MessageListenerConcurrently) (messages, context) -> {
    try {
        for (MessageExt message : messages) {
            handle(message);
        }
        return ConsumeConcurrentlyStatus.CONSUME_SUCCESS;
    } catch (RetryableException e) {
        return ConsumeConcurrentlyStatus.RECONSUME_LATER;
    } catch (NonRetryableException e) {
        // 不可重试：记录后直接确认，避免进入死信
        return ConsumeConcurrentlyStatus.CONSUME_SUCCESS;
    }
});
```

**故障场景与兜底：**

- 无限重试：毒消息反复回队，阻塞分区；必须设最大次数并转入 DLQ。
- 重试风暴：所有失败消息同时重试打垮下游；用指数退避与抖动。
- 死信无人处理：DLQ 只进不出，磁盘与积压持续上涨；要有告警与回放工具。
- 重放顺序错乱：批量重放可能早于原消息；按业务键与版本号做状态判断。
- 不可重试错误进入死信：参数错误重试无意义，应在第一次就记录并告警。
- 死信队列本身故障：DLQ 也要高可用与持久化，不能是临时队列。

**面试怎么答：** 先讲「为什么需要死信」：毒消息、下游长期不可用、不可重试错误；再讲重试的三要素（分类、次数、退避），然后分别说 RabbitMQ 的 DLX、Kafka 的 `@RetryableTopic`/自建 DLQ、RocketMQ 的 `%RETRY%` 与 `%DLQ%`；最后强调死信的可观测、可回放与幂等。

**易错点：**

- `basicNack(requeue=true)` 处理所有失败：同一队列内无限循环。
- 不区分错误类型：参数错误也重试十几次，浪费资源且延迟告警。
- 以为 RocketMQ 死信会永久保存：`%DLQ%` 有保留期限，需要及时处理。
- Kafka 直接丢弃失败消息：没有 DLQ 就没有补偿入口。
- 死信重放不做幂等：修复后重放会造成二次脏数据。
