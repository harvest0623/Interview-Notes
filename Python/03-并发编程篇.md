## 1. 进程、线程、协程的区别

**三者不是同一层级的替代品，而是三种不同粒度的「并发单位」：**

- **进程（Process）**：操作系统进行**资源分配**的最小单位。每个进程拥有独立的虚拟地址空间、文件描述符表、信号处理、全局变量；进程之间默认**不共享内存**，要通信必须走 IPC（管道、队列、共享内存、socket）。
- **线程（Thread）**：操作系统进行 **CPU 调度**的最小单位，是进程内的一条执行流。同一进程内的线程**共享**代码段、堆、全局变量、文件描述符，但各自拥有独立的**栈**与寄存器上下文、线程局部存储（TLS）。
- **协程（Coroutine）**：**用户态**的轻量级「线程」，由程序（事件循环）而非操作系统调度，切换不陷入内核，因此开销极小。协程不是操作系统概念，是语言与运行时层面的抽象。

**层级关系一句话：**

> 进程 ⊃ 线程 ⊃ 协程。前两者由**操作系统调度**（抢占式），协程由**程序自己调度**（协作式，在 `await` / `yield` 处主动让出）。

**从进程到协程的演进逻辑：**

| 阶段 | 想解决的问题 | 付出的代价 |
| --- | --- | --- |
| 多进程 | CPU 真并行、内存隔离 | 创建/切换贵，共享数据要序列化 |
| 多线程 | 更轻、共享数据方便 | 共享带来竞态需加锁；受 GIL 限制无法并行计算 |
| 协程 | 单线程内支撑超高并发 IO | 无法利用多核做计算；依赖非阻塞生态 |

**完整对比表（面试核心）：**

| 维度 | 进程 | 线程 | 协程 |
| --- | --- | --- | --- |
| 归属 | 操作系统 | 操作系统 | 语言 / 运行时（用户态） |
| 资源分配 | 独立地址空间、独立资源 | 共享进程资源，独享栈 | 共享线程资源，独享极少上下文 |
| 创建开销 | 大（MB 级，要建页表） | 中（KB~MB，内核对象） | 极小（KB 级，纯 Python 对象） |
| 切换成本 | 最贵（切页表、进内核） | 较贵（内核态上下文切换） | 极便宜（用户态，无系统调用） |
| 切换方式 | 时间片 / 优先级，抢占式 | 时间片，抢占式 | 主动让出，协作式 |
| 能否真并行 | 能（多核） | 受 GIL 限制，计算不并行 | 单线程，计算不并行 |
| 隔离性 | 强（一个崩不影响其他） | 弱（一个线程段错误，全进程亡） | 弱（同一线程内） |
| 通信方式 | Queue / Pipe / 共享内存 / socket | 共享内存 + Lock / Queue | `await`、共享变量（同线程） |
| 数据共享 | 需序列化（pickle 传输） | 直接共享，须同步 | 直接共享，无需加锁 |
| 数量级 | 几十 ~ 几百 | 几百 ~ 几千 | 成千上万（可 10 万+ 连接） |
| 受 GIL 影响 | 不受 | **受**（同进程同时只跑一个线程的字节码） | 受（也在同一线程内） |
| 典型场景 | CPU 密集、需要隔离 | IO 密集、简单共享 | 超高并发网络 IO |

**通信 / 共享方式的对照：**

| 方式 | 适用对象 | 说明 |
| --- | --- | --- |
| `queue.Queue` | 线程间 | 内存队列，内部自带锁 |
| `multiprocessing.Queue` | 进程间 | 数据 pickle 序列化后经管道传输 |
| `multiprocessing.Pipe` | 进程间 | 双向或单向管道 |
| `Value` / `Array` | 进程间 | 共享内存（`Value` 自带锁） |
| `Manager` | 进程间 | 代理对象（dict / list / Queue），使用方便但较慢 |
| 全局变量 | 线程 / 协程间 | 直接共享，须警惕竞态 |

**三件套的最小可运行示例：**

```python
# ---------- 多进程：计算真并行 ----------
import multiprocessing as mp

def cpu_task(n: int) -> int:
    return sum(i * i for i in range(n))

if __name__ == "__main__":                 # Windows 上必须加保护
    with mp.Pool(4) as pool:
        print(pool.map(cpu_task, [10 ** 6] * 4))   # 4 个核同时算

# ---------- 多线程：IO 密集并发 ----------
import threading, time

def io_task(name: str) -> None:
    time.sleep(1)                           # 等待期间释放 GIL
    print(f"{name} 完成")

threads = [threading.Thread(target=io_task, args=(f"t{i}",)) for i in range(3)]
for t in threads:
    t.start()
for t in threads:
    t.join()                                # 总耗时约 1 秒，而非 3 秒

# ---------- 协程：单线程高并发 IO ----------
import asyncio

async def fetch(name: str) -> None:
    await asyncio.sleep(1)                  # 非阻塞，主动让出事件循环
    print(f"{name} 完成")

async def main() -> None:
    await asyncio.gather(*(fetch(f"c{i}") for i in range(3)))

asyncio.run(main())                         # 总耗时同样约 1 秒
```

> 观察点：多线程和协程在这里都能「1 秒跑完 3 个任务」，因为它们都在**等待时让出执行权**；区别在于线程由操作系统抢占式切换，协程由事件循环在 `await` 处协作式切换。

**易错点：**

- 「协程比线程快」不严谨：协程快在**切换开销与内存占用**，但在**纯计算**上不会比单线程更快（依然受 GIL 约束）。
- 线程隔离性差：某个线程触发的段错误（C 扩展写坏内存）会让整个进程崩溃；进程之间则互不影响。
- 协程的本质是「**单线程内的并发**」而非并行；想用多核仍须配合多进程。
- 常被追问：在 `asyncio` 里调用阻塞函数（`time.sleep`、`requests.get`）会**卡死整个事件循环**，应改用 `await asyncio.sleep()` 或 `loop.run_in_executor`。

## 2. 多线程与 threading

Python 的多线程由 `threading` 模块提供。它适合 **IO 密集型**任务：因为线程阻塞在 IO 时会**释放 GIL**，其他线程可以趁机执行。

**① 基本用法**

```python
import threading, time

def worker(name: str, n: int) -> None:
    print(f"[{name}] 开始")
    time.sleep(n)
    print(f"[{name}] 结束")

# 方式一：target + args
t = threading.Thread(target=worker, args=("A", 1), name="worker-A")
t.start()          # 启动新线程，交操作系统调度，最终执行 run()
t.join()           # 主线程阻塞，等待 t 结束

# 方式二：继承 Thread，重写 run()
class MyThread(threading.Thread):
    def __init__(self, n: int) -> None:
        super().__init__()
        self.n = n

    def run(self) -> None:          # 注意是 run 不是 start
        print(f"{self.n} 的平方 = {self.n ** 2}")

m = MyThread(5)
m.start()          # 会在新线程里调用 run()
m.join()
```

**② `start()` 与 `run()` 的区别（高频追问）**

| 方法 | 行为 | 是否开新线程 |
| --- | --- | --- |
| `start()` | 创建新线程并调用 `run()`，由 OS 调度 | **是** |
| `run()` | 只是普通方法，直接在当前线程里执行线程体 | 否 |

> 直接调用 `t.run()` 不报错，但等于「同步执行」，多线程效果完全失效，是常见错误。

**③ 守护线程 `daemon`**

守护线程会随主线程退出而**强制结束**（不等待它跑完），适合做后台监控、心跳之类的工作。

```python
import threading, time

def background() -> None:
    while True:
        time.sleep(0.5)
        print("心跳...")

t = threading.Thread(target=background, daemon=True)   # 必须在 start 之前设置
t.start()
time.sleep(1.5)
print("主线程结束，守护线程随之退出")    # 程序不会因为它在死循环而卡住
```

**④ `threading.local`：线程局部存储**

每个线程各自持有一份独立副本，天然避免数据串扰，常用于 Web 框架保存「当前请求上下文」。

```python
import threading

local_data = threading.local()

def process(name: str) -> None:
    local_data.name = name                      # 只在本线程可见
    print(f"{threading.current_thread().name} -> {local_data.name}")

threads = [threading.Thread(target=process, args=(f"user{i}",)) for i in range(3)]
for t in threads:
    t.start()
for t in threads:
    t.join()
```

**⑤ `threading` 常用成员速查**

| 成员 | 作用 |
| --- | --- |
| `current_thread()` | 当前线程对象 |
| `main_thread()` | 主线程对象 |
| `active_count()` / `enumerate()` | 存活线程数 / 列表 |
| `Thread` | 线程类（`start` / `join` / `is_alive`） |
| `Timer` | 延时执行一次的线程 |
| `Lock` / `RLock` / `Semaphore` / `Event` / `Condition` / `Barrier` | 同步原语（见下一题） |

**易错点：**

- 忘记 `join()`：主线程可能在子线程完成前就退出，数据没写完、日志没落盘。
- `daemon` 必须在 `start()` **之前**设置，否则抛 `RuntimeError: cannot set daemon status of active thread`。
- 多线程共享可变对象一定要加锁，`list.append` 虽在 CPython 下多为原子，但 `+=`、`dict` 复合操作并非原子。
- `t.join()` 只是等待，**不会**帮你把异常传播出来；子线程异常默认只打印堆栈，不影响主线程，需要自己收集（如放进 `queue`）。

## 3. 多进程与 multiprocessing

`multiprocessing` 通过**多进程**绕开 GIL，实现真正的多核并行，适合 **CPU 密集型**任务；同时它提供了与 `threading` 极为相似的 API，并以 Queue / Pipe / 共享内存等方式解决进程间通信。

**① Process 与 Pool**

```python
import multiprocessing as mp
import os

def task(n: int) -> int:
    print(f"进程 {os.getpid()} 处理 {n}")
    return n * n

if __name__ == "__main__":               # Windows / macOS 必须加保护
    # ---- 直接创建进程 ----
    p = mp.Process(target=task, args=(5,))
    p.start()                            # 新建进程并执行
    p.join()                             # 等待结束

    with mp.Pool(processes=4) as pool:   # 进程池，复用 4 个 worker
        print(pool.map(task, [1, 2, 3, 4]))          # 阻塞，按顺序返回全部结果
        for r in pool.imap(task, range(5)):          # 迭代器，边完成边取（仍按顺序）
            print("imap:", r)
        for r in pool.imap_unordered(task, range(5)):  # 谁先完成谁先返回
            print("unordered:", r)
        res = pool.apply_async(task, (10,))          # 异步提交，返回 AsyncResult
        print("apply_async:", res.get(timeout=5))    # get 阻塞取结果
```

| 方法 | 返回 | 特点 |
| --- | --- | --- |
| `map` | 列表 | 阻塞，结果**按输入顺序** |
| `imap` | 迭代器 | 有进度感，结果**按输入顺序** |
| `imap_unordered` | 迭代器 | 谁先完成谁先出，**不保证顺序** |
| `apply` | 结果 | 同步，一次一个任务 |
| `apply_async` | `AsyncResult` | 异步提交，`get()` 取结果 |

**② 进程间通信：Queue 与 Pipe**

```python
import multiprocessing as mp

def producer(q: mp.Queue) -> None:
    for i in range(3):
        q.put(i)
    q.put(None)                  # 结束信号

def consumer(q: mp.Queue) -> None:
    while True:
        item = q.get()
        if item is None:
            break
        print("收到:", item)

if __name__ == "__main__":
    q = mp.Queue()
    p1 = mp.Process(target=producer, args=(q,))
    p2 = mp.Process(target=consumer, args=(q,))
    p1.start(); p2.start()
    p1.join();  p2.join()
```

```python
import multiprocessing as mp

def sender(conn: mp.connection.Connection) -> None:
    conn.send(["hello", 42, {"k": "v"}])
    conn.close()

if __name__ == "__main__":
    parent_conn, child_conn = mp.Pipe()     # 双向管道，返回两端
    p = mp.Process(target=sender, args=(child_conn,))
    p.start()
    print("父进程收到:", parent_conn.recv())
    p.join()
```

**③ 共享内存 Value / Array 与 Manager**

```python
import multiprocessing as mp

def inc(v, arr) -> None:
    with v.get_lock():          # Value 自带锁，改值要加锁
        v.value += 1
    arr[0] = 99                 # Array 支持下标赋值

if __name__ == "__main__":
    v = mp.Value("i", 0)                    # 'i' 表示 int
    arr = mp.Array("i", [0, 0, 0])          # 共享内存数组
    ps = [mp.Process(target=inc, args=(v, arr)) for _ in range(5)]
    for p in ps: p.start()
    for p in ps: p.join()
    print(v.value, list(arr))
```

```python
import multiprocessing as mp

def put_item(m, k) -> None:
    m[k] = k * k

if __name__ == "__main__":
    with mp.Manager() as manager:
        d = manager.dict()                  # 代理对象，可跨进程读写
        ps = [mp.Process(target=put_item, args=(d, i)) for i in range(3)]
        for p in ps: p.start()
        for p in ps: p.join()
        print(dict(d))
```

**通信方式对比：**

| 方式 | 速度 | 灵活性 | 适用 |
| --- | --- | --- | --- |
| `Queue` | 中 | 高 | 多生产者多消费者 |
| `Pipe` | 快 | 低（一般两端） | 点对点通信 |
| `Value` / `Array` | 最快 | 低（同类型定长） | 数值型共享状态 |
| `Manager` | 慢 | 最高 | dict / list / 自定义代理 |

**④ Windows 上的 `spawn` 与 `if __name__ == "__main__"`**

| 启动方式 | 平台默认 | 特点 |
| --- | --- | --- |
| `fork` | Linux（部分） | 复制父进程内存，快，但多线程下不安全 |
| `spawn` | **Windows / macOS** | 全新解释器，重新 import 主模块，**必须加 `if __name__ == "__main__"` 保护** |
| `forkserver` | 可指定 | 先起一个干净服务进程再 fork |

> Windows 采用 `spawn`：子进程会重新导入主模块，若把 `mp.Process(...)` 写在模块顶层，就会**无限递归创建进程**并报 `RuntimeError`。所有多进程代码都应放在 `if __name__ == "__main__":` 里。

**易错点：**

- 传给子进程的参数与返回值必须能被 **pickle 序列化**，lambda、局部函数、打开的 file 对象都会失败。
- `Pool.map` 会一次性把可迭代对象**物化**提交，超大输入要用 `imap` 或分批。
- 进程间不共享内存，改全局变量在子进程里**不会**影响父进程。
- `Pool` 要 `close()` + `join()` 或直接用 `with`，否则可能泄漏子进程。

## 4. 线程同步与锁

**为什么需要锁？** 因为 `counter += 1` 并非原子操作，它至少包含「读 → 加 → 写」三步字节码。GIL 虽然保证**同一时刻只有一个线程执行字节码**，但完全可能在任意两步之间切换线程。

```python
import threading

counter = 0

def add() -> None:
    global counter
    for _ in range(100_000):
        counter += 1        # 非原子：LOAD → ADD → STORE，中途可能被切换

ts = [threading.Thread(target=add) for _ in range(5)]
for t in ts: t.start()
for t in ts: t.join()
print(counter)              # 往往小于 500000，这就是竞态
```

**加锁修复（推荐 `with` 写法）：**

```python
import threading

lock = threading.Lock()
counter = 0

def add() -> None:
    global counter
    for _ in range(100_000):
        with lock:          # 进入自动 acquire，退出（含异常）自动 release
            counter += 1

ts = [threading.Thread(target=add) for _ in range(5)]
for t in ts: t.start()
for t in ts: t.join()
print(counter)              # 稳定输出 500000
```

**同步原语一览：**

| 原语 | 语义 | 典型用途 |
| --- | --- | --- |
| `Lock` | 互斥锁，一次只允许一个线程进入 | 保护共享变量 |
| `RLock` | 可重入锁，同线程可多次 `acquire` | 递归函数、嵌套调用 |
| `Semaphore` | 计数信号量，允许 N 个线程同时进入 | 限制并发数（连接池、限流） |
| `BoundedSemaphore` | 带上限的信号量，超量 `release` 报错 | 防止 release 次数写错 |
| `Event` | 事件标志，`wait` / `set` / `clear` | 线程间「通知/等待」 |
| `Condition` | 条件变量，`wait` / `notify` / `notify_all` | 生产者消费者、队列内部实现 |
| `Barrier` | 屏障，等 N 个线程全部到齐再一起放行 | 分阶段同步（如多阶段计算） |

**Event：一对多的通知**

```python
import threading, time

event = threading.Event()

def waiter(name: str) -> None:
    print(f"{name} 等待信号")
    event.wait()                      # 阻塞直到 event 被 set
    print(f"{name} 收到，继续执行")

def setter() -> None:
    time.sleep(1)
    print("发信号")
    event.set()                       # 唤醒所有等待者

ts = [threading.Thread(target=waiter, args=(f"w{i}",)) for i in range(3)]
ts.append(threading.Thread(target=setter))
for t in ts: t.start()
for t in ts: t.join()
```

**Semaphore：限制并发数**

```python
import threading, time

sem = threading.Semaphore(3)          # 最多 3 个线程同时进入

def access(i: int) -> None:
    with sem:
        print(f"任务 {i} 占用槽位")
        time.sleep(1)

ts = [threading.Thread(target=access, args=(i,)) for i in range(6)]
for t in ts: t.start()                # 6 个任务分两批，每批 3 个
for t in ts: t.join()
```

**RLock 可重入的意义**

```python
import threading

lock = threading.RLock()

def outer() -> None:
    with lock:
        inner()                   # 同一线程再次请求锁

def inner() -> None:
    with lock:                    # RLock 允许；换成 Lock 会在这里死锁
        print("可重入成功")

outer()
```

> `Lock` 在同一线程里第二次 `acquire` 会**永久阻塞**（它不记录持有者）。当代码存在「加锁的方法调用另一个加锁的方法」时，必须用 `RLock`。

**易错点：**

- 用 `lock.acquire()` 却不 `release()`（尤其异常路径），导致其他线程永久等待；**优先用 `with lock`**。
- `Condition.wait()` 必须在**已持有该 Condition 关联锁**的状态下调用，否则抛 `RuntimeError`。
- 锁粒度太粗会退化性能，太细又容易漏加导致竞态；应只包裹「共享数据的读写区间」。
- 多把锁嵌套时务必约定统一顺序，否则可能死锁（详见第 11 题）。

## 5. 线程池与进程池

`concurrent.futures` 提供统一的 `Executor` 抽象：`ThreadPoolExecutor` 用于 IO 密集，`ProcessPoolExecutor` 用于 CPU 密集。它们**复用**工作单位，避免频繁创建销毁的开销。

**① 两种池的使用（接口一致）**

```python
from concurrent.futures import ThreadPoolExecutor, ProcessPoolExecutor, as_completed
import time

def task(n: int) -> int:
    time.sleep(0.5)
    return n * n

# ---------- 线程池：IO 密集 ----------
with ThreadPoolExecutor(max_workers=4) as pool:
    # map：阻塞，按输入顺序返回全部结果
    print(list(pool.map(task, range(6))))

    # submit + as_completed：谁先完成谁先被处理
    futures = {pool.submit(task, i): i for i in range(6)}
    for fut in as_completed(futures):
        n = futures[fut]
        try:
            print(f"{n} -> {fut.result()}")
        except Exception as e:
            print(f"{n} 出错: {e}")

# ---------- 进程池：CPU 密集，注意 Windows 上须放在 __main__ 保护内 ----------
if __name__ == "__main__":
    with ProcessPoolExecutor(max_workers=4) as pool:
        print(list(pool.map(task, range(6))))
```

**② Future 对象的方法**

| 方法 | 说明 |
| --- | --- |
| `result(timeout=None)` | 阻塞取返回值；任务内部异常会在此**重新抛出** |
| `exception(timeout=None)` | 取任务抛出的异常（无异常返回 `None`） |
| `done()` | 是否已完成（正常结束或被取消） |
| `cancel()` | 取消任务；**仅在尚未开始时**才成功 |
| `cancelled()` | 是否已成功取消 |
| `running()` | 是否正在执行（不可取消） |
| `add_done_callback(fn)` | 完成时回调 |

```python
from concurrent.futures import ThreadPoolExecutor

with ThreadPoolExecutor(2) as pool:
    f = pool.submit(lambda x: x + 1, 1)   # 注意：进程池里不能用 lambda
    print(f.result())                     # 2
    print(f.exception())                  # None
    print(f.done())                       # True
```

**③ 池大小如何定（高频）**

| 任务类型 | 经验公式 / 建议 |
| --- | --- |
| CPU 密集 | `workers = CPU 核数 (+1)`，超过核数只是徒增切换开销 |
| IO 密集 | `workers = 核数 × (1 + 等待时间 / 计算时间)`，或按并发目标直接设几十 ~ 上百 |
| 进程池 | 一般 = 核数；过多会争抢内存与 CPU 缓存 |

```python
import os
cpu = os.cpu_count() or 4

# CPU 密集：进程池 ≈ 核数
cpu_workers = cpu

# IO 密集：等待占比越大，线程数越多
wait_ratio = 9                 # 等待 9 份时间，计算 1 份
io_workers = cpu * (1 + wait_ratio)   # 例如 4 核 → 40
```

> 注意：这两个公式只是**起点**，真实最优值要靠压测。协程场景下则根本不用池——用 `asyncio` 直接并发，或者用 `run_in_executor` 调用阻塞库。

**易错点：**

- 在 `with` 块**外**调用 `future.result()` 可能拿不到已完成的结果（池已关闭），也可能因异常没被取出而静默失败——所有 `result()` 都应放进 `try/except`。
- 进程池里 `submit` 的**函数与参数必须可 pickle**：`lambda`、闭包、实例方法在某些场景会失败。
- `map` 是**阻塞**且按顺序的；要「先完成先处理」必须用 `submit + as_completed`。
- 不要为了「看起来快」把线程数调到几百，上下文切换反而拖慢整体。

## 6. asyncio 与事件循环

`asyncio` 是 Python 的**异步 IO 框架**，核心是**事件循环（Event Loop）**：它在单线程内轮转调度大量协程，某个协程遇到 IO 时用 `await` 交出控制权，循环立即去跑其他就绪任务。因此它能用极低的内存支撑**海量并发连接**。

**核心概念：**

| 概念 | 说明 |
| --- | --- |
| 协程（coroutine） | `async def` 定义的函数，调用后返回协程对象，**不立即执行** |
| 事件循环（Event Loop） | 调度器，负责驱动协程、处理 IO、定时器 |
| Task | 对协程的封装，创建后**立即排入**事件循环开始调度 |
| Future | 更底层的「结果占位符」，表示一个尚未完成的异步操作 |

**① `asyncio.run` 与并发执行**

```python
import asyncio, time

async def fetch(name: str, delay: float) -> str:
    print(f"{name} 开始")
    await asyncio.sleep(delay)         # 非阻塞等待，交还控制权给事件循环
    print(f"{name} 结束")
    return name

async def main() -> None:
    start = time.perf_counter()
    results = await asyncio.gather(    # 并发执行，结果按传入顺序返回
        fetch("A", 1),
        fetch("B", 0.5),
        fetch("C", 0.8),
    )
    print(results, f"总耗时 {time.perf_counter() - start:.2f}s")

asyncio.run(main())                    # 创建事件循环 → 运行 main → 关闭循环
```

**② 直接 `await` vs `create_task`（最容易踩的坑）**

```python
async def main() -> None:
    # 直接 await：串行，A 跑完才跑 B，约 2 秒
    await fetch("A", 1)
    await fetch("B", 1)

    # create_task：先包装成 Task 立即调度，再 await，约 1 秒
    t1 = asyncio.create_task(fetch("A", 1))
    t2 = asyncio.create_task(fetch("B", 1))
    await t1
    await t2
```

> `await fetch(...)` 只是「等这个协程跑完」；`create_task` 才是「把它排进事件循环开始并发」。想并发，必须先 `create_task`（或交给 `gather` / `wait`）。

**③ gather / wait / as_completed 三种等待**

```python
import asyncio

async def main() -> None:
    # gather：并发跑完所有任务，返回结果列表（可选 return_exceptions=True 避免一个失败全崩）
    res = await asyncio.gather(*[fetch(n, 0.5) for n in "ABC"])

    # wait：等待一组任务，可指定「先完成一个就返回」
    tasks = [asyncio.create_task(fetch(n, 1)) for n in "XYZ"]
    done, pending = await asyncio.wait(tasks, return_when=asyncio.FIRST_COMPLETED)
    print("先完成:", [t.result() for t in done])
    for t in pending:
        t.cancel()                     # 取消剩余任务

    # as_completed：谁先完成谁先取出，适合「边完成边处理」
    tasks2 = [asyncio.create_task(fetch(n, 1)) for n in "UVW"]
    for fut in asyncio.as_completed(tasks2):
        print(await fut)
```

| 函数 | 返回 | 何时用 |
| --- | --- | --- |
| `gather` | 结果列表（按传入顺序） | 需要全部结果，最常用 |
| `wait` | `(done, pending)` 两个集合 | 需要「先完成先处理」或超时取消 |
| `as_completed` | 结果迭代器（完成即出） | 完成顺序有意义（如抓取进度） |

**④ `run_in_executor`：把阻塞调用丢进线程池**

事件循环里**绝对不要**直接调用阻塞函数（`time.sleep`、`requests.get`、文件 IO），否则整个循环卡死。用 `run_in_executor` 把它委托给线程池。

```python
import asyncio, time

def blocking_io() -> str:              # 阻塞函数，例如 requests.get / 读大文件
    time.sleep(1)
    return "done"

async def main() -> None:
    loop = asyncio.get_running_loop()
    result = await loop.run_in_executor(None, blocking_io)   # None = 用默认线程池
    print(result)

asyncio.run(main())
```

**易错点：**

- `await asyncio.sleep(1)` 与 `time.sleep(1)` 天差地别：前者让出循环，后者阻塞**整个事件循环**。
- 忘记持有 Task 引用：`asyncio.create_task(...)` 的返回值若没被变量接收，任务可能被 GC 回收而中途消失。
- `gather` 默认一个任务抛异常会让整体抛异常（其余任务仍在跑）；想容错要 `return_exceptions=True`。
- 事件循环是**单线程**的：CPU 密集代码放进协程不会更快，反而饿死其他协程，应交给进程池。

## 7. async 与 await 原理

**核心事实：`async def` 函数调用后不会执行函数体，而是返回一个协程对象。**

协程对象是可暂停、可恢复的执行单元：它实现了 `send` / `throw` / `close`，并在 `await` 处「挂起」，把控制权交还给驱动它的**事件循环**。

**① 调用 async 函数不执行任何代码**

```python
import asyncio
from inspect import iscoroutine

async def hello() -> None:
    print("hello")

coro = hello()                 # 只创建协程对象，函数体一行都没跑
print(type(coro))              # <class 'coroutine'>
print(iscoroutine(coro))       # True

asyncio.run(coro)              # 交给事件循环真正驱动，才打印 hello
```

**② `await` 做的事：挂起当前协程，交还控制权**

```python
import asyncio

async def sub() -> int:
    print("sub 开始")
    await asyncio.sleep(1)      # 挂起：把控制权交回事件循环，1 秒后再恢复
    print("sub 结束")
    return 42

async def main() -> None:
    result = await sub()        # await 会驱动 sub 直到它挂起或返回
    print("拿到:", result)

asyncio.run(main())
```

`await expr` 的语义可以拆成三步（等价于 `yield from` 的现代版本）：

1. 求值 `expr`，得到一个 **awaitable**（协程 / Task / Future）。
2. 把当前协程**挂起**，控制权交回事件循环；事件循环转去执行其他就绪任务。
3. 等 `expr` 产生结果后，事件循环**恢复**当前协程，把结果作为 `await` 表达式的值。

**③ Future 与 Task**

```python
import asyncio

async def main() -> None:
    loop = asyncio.get_running_loop()

    # Future：底层结果占位符，需手动 set_result
    fut = loop.create_future()
    loop.call_later(1, fut.set_result, "future-ok")

    # Task：包装协程并自动排入事件循环调度
    task = asyncio.create_task(asyncio.sleep(1, "task-ok"))

    print(await fut, await task)
```

| 对象 | 层次 | 谁创建 | 能否被 await |
| --- | --- | --- | --- |
| 协程对象 | 最上层 | `async def` 调用 | 能 |
| `Task` | 中间 | `create_task` / `ensure_future` | 能 |
| `Future` | 最底层 | `loop.create_future` / 库内部 | 能 |
| 自定义 awaitable | 任意 | 实现 `__await__` | 能 |

**④ 用 `send` 手动驱动一个协程（理解机制）**

```python
import asyncio

async def add(a: int, b: int) -> int:
    return a + b            # 没有 await，执行即结束

c = add(1, 2)
print(hasattr(c, "send"), hasattr(c, "throw"), hasattr(c, "__await__"))  # True True True

try:
    c.send(None)            # 启动协程
except StopIteration as e:
    print("返回:", e.value) # 返回: 3   —— 返回值通过 StopIteration.value 传出
```

> 这说明 await 与生成器的 `yield from` 在机制上同源：**事件循环用 `send()` 驱动协程、用 `throw()` 注入异常、用 `StopIteration.value` 取返回值**。

**易错点：**

- 只调用不 await，会出现 `RuntimeWarning: coroutine 'xxx' was never awaited`，代码静默不生效。
- `await` 只能出现在 `async def` 内部；在普通函数里用会 `SyntaxError`。
- `await` 一个非 awaitable（如 `await 1`）抛 `TypeError`。
- `async def` 里若长时间做 CPU 计算且不 `await`，会阻塞整个事件循环——因为协程本质仍是**单线程**执行。

## 8. 协程与生成器的关系

**历史脉络：协程是从生成器「长出来」的。**

- 生成器（`yield`）最初用于**惰性产出**序列，是单向的「生产者」。
- PEP 342 给生成器加了 `send()` / `throw()`，让它能**接收外部值**，于是成了「协程雏形」。
- PEP 380 引入 `yield from`，可把执行「委托」给子生成器，似乎有了协程的调用链。
- Python 3.4 用 `@asyncio.coroutine` + `yield from` 写异步。
- Python 3.5 起引入 **native coroutine（`async def` / `await`）**，语法更清晰，拦截了「误把生成器当协程」的歧义。

**① 生成器作为协程雏形：`send` 双向通信**

```python
def echo():
    while True:
        received = yield          # 挂起并把外部 send 的值赋给 received
        print("收到:", received)

g = echo()
next(g)                        # 启动：跑到第一个 yield，返回 None
g.send("hello")                # 恢复执行并传入 "hello" → 打印 收到: hello
g.send("world")                # → 打印 收到: world
```

**② `yield from`：委托给子生成器**

```python
def sub_gen():
    yield 1
    yield 2
    return "sub-done"             # 子生成器的返回值

def delegating():
    result = yield from sub_gen() # 把产出/接收都委托给子生成器，并拿到其 return 值
    print("子生成器返回:", result)
    yield 99

print(list(delegating()))         # [1, 2, 99] 并打印 子生成器返回: sub-done
```

**③ 历史写法：`@asyncio.coroutine`（已废弃）**

```python
import asyncio

@asyncio.coroutine               # Python 3.4 时代 —— 现已被删除
def old_style():
    yield from asyncio.sleep(1)  # 用 yield from 等待
    return "done"
```

**④ 原生协程（现代写法）**

```python
import asyncio

async def new_style():
    await asyncio.sleep(1)        # 用 await 等待
    return "done"
```

**⑤ 用 `inspect` 区分两者**

```python
import inspect

def gen_func():
    yield 1

async def coro_func():
    return 1

g = gen_func()
c = coro_func()
print(inspect.isgenerator(g), inspect.isgeneratorfunction(gen_func))    # True True
print(inspect.iscoroutine(c), inspect.iscoroutinefunction(coro_func))   # True True
print(inspect.isawaitable(c))                                           # True
print(inspect.isawaitable(g))                                           # False（生成器不是 awaitable）
```

**生成器 vs 原生协程对比：**

| 维度 | 生成器 | 原生协程（async def） |
| --- | --- | --- |
| 关键语法 | `yield` | `async def` / `await` |
| 类型 | `generator` | `coroutine` |
| 通信 | `send` / `throw`（双向） | `await`（单向等待） |
| 调度者 | 手动 `next` / `send`，或 for 循环 | 事件循环 |
| 是否 awaitable | 否 | 是 |
| 典型用途 | 惰性迭代、流式处理 | 异步 IO 并发 |

> 事件循环与协程之间其实是**双工通信**：循环用 `send()` 把「恢复信号 / 结果」送进去，协程用 `yield` 把「我等待的 Future」抛出来，一来一回构成调度。

**易错点：**

- `yield` 既是**挂起点**又是**接收点**：`x = yield y` 中，`y` 是产出，`x` 是 `send` 进来的值。
- 生成器用 `return` 会触发 `StopIteration`，值藏在 `.value` 里，`yield from` 会替你把它取出来。
- 原生协程**不能**用 `send()` 随意驱动（虽然语法上可以），正确方式是交给事件循环；`asyncio.iscoroutine` 会被标记废弃，改用 `inspect.iscoroutine`。

## 9. CPU 密集型与 IO 密集型

**判别方法（面试常问「你怎么区分」）：**

- **CPU 密集型**：时间主要花在计算上，CPU 使用率高、几乎不等待。例子：大量数值计算、图像处理、加密解密、正则回溯。
- **IO 密集型**：时间主要花在等待外部资源上，CPU 大量空闲。例子：网络请求、数据库查询、文件读写、`socket.recv`。
- 实测手段：用 `cProfile` / `line_profiler` 看热点，或在代码里打点测量「计算时间 vs 等待时间」的占比。

| 维度 | CPU 密集型 | IO 密集型 |
| --- | --- | --- |
| 瓶颈 | CPU 指令周期 | 网络 / 磁盘 / 外部服务延迟 |
| CPU 使用率 | 接近 100% | 很低（通常在等） |
| GIL 影响 | 多线程**无法并行**，甚至更慢 | 等待时释放 GIL，多线程有效 |
| 推荐方案 | **多进程** / C 扩展 / numpy | **多线程** / asyncio |
| 并发上限 | ≈ CPU 核数 | 几十 ~ 上万个 |
| 提速来源 | 多核并行 | 把「等待时间」重叠起来 |

```python
import time, threading

def cpu_bound() -> int:              # CPU 密集：纯计算
    return sum(i * i for i in range(10 ** 7))

def io_bound() -> None:              # IO 密集：用 sleep 模拟等待
    time.sleep(1)

# 结论演示（详见第 13 题）：
# CPU 密集：4 线程耗时 ≈ 单线程（受 GIL 限制，无法并行）
# IO 密集 ：4 线程耗时 ≈ 单个的 1 倍（等待被重叠，接近线性加速）
```

**为什么两者结论相反？**

> 关键在 **GIL 的释放时机**：线程执行**纯计算**时不会主动释放 GIL，导致同一时刻只有一个线程在跑，多核用不上；而一旦线程**进入 IO 等待**（网络、磁盘、`time.sleep`），CPython 会释放 GIL，其他线程立即接手，从而真正并发。

**用剖析工具量化判别：**

```python
import cProfile, pstats, io, time

def task() -> int:
    total = sum(i * i for i in range(2 * 10 ** 6))   # 计算部分
    time.sleep(0.2)                                   # 等待部分
    return total

profiler = cProfile.Profile()
profiler.enable()
task()
profiler.disable()

buf = io.StringIO()
pstats.Stats(profiler, stream=buf).sort_stats("cumulative").print_stats(5)
print(buf.getvalue())
# 判读：若 sleep / 系统调用占比高 → IO 密集；若纯 Python 函数占比高 → CPU 密集
```

**常见任务的归类参考：**

| 常见任务 | 类型 | 说明 |
| --- | --- | --- |
| 网络请求 / 爬虫 | IO | 大部分时间在等响应 |
| 数据库查询 | IO | 等 DB 返回结果 |
| 文件批量读写 | IO（大文件含 CPU） | 磁盘等待为主 |
| 数值 / 矩阵计算 | CPU | `numpy` 例外（C 层释放 GIL） |
| 图像 / 视频处理 | CPU | 逐像素计算 |
| 加密 / 压缩 | CPU（部分释放 GIL） | `hashlib` / `zlib` 会释放 GIL |
| 大对象 JSON 序列化 | CPU | 纯 Python 解析 |

> 实践建议：先**测**再**选**。用 `cProfile` 或简单打点测出「计算时间 : 等待时间」的比值，比值远大于 1 就是 CPU 密集，反之是 IO 密集。

**易错点：**

- 用「有没有 sleep」来判别过于粗糙：很多库（如 `numpy`、`hashlib`、`zlib`）在 C 层**主动释放 GIL**，即使看着像 CPU 密集也可能受益于多线程。
- 混合型任务（既计算又等待）要**分层处理**：计算部分交进程池，等待部分交协程/线程。
- 「IO 密集一定能提速」有前提：如果线程间有**锁竞争**（如都抢同一个全局锁），加速效果会被吃掉。

## 10. 并发场景下的选择策略

**决策表（背下来）：**

| 场景 | 首选方案 | 备选 | 理由 |
| --- | --- | --- | --- |
| IO 密集（网络 / DB / 文件） | `asyncio` 协程 或 线程池 | 多线程 | 等待时可让出，不占 CPU |
| CPU 密集（计算 / 图像 / 加密） | **多进程** / `ProcessPoolExecutor` | C 扩展、numpy | 绕开 GIL，用满多核 |
| 海量长连接（1 万 + 并发） | **asyncio** | - | 协程内存开销极小，能扛住连接数 |
| 简单任务并行 / 批处理 | `concurrent.futures` | - | 统一 API，最省心 |
| 需要强隔离 / 稳定性 | 多进程 | - | 一个崩溃不影响其他 |
| 既有 IO 又有 CPU（如爬虫解析） | **协程 + 进程池混合** | 线程 + 进程 | 各取所长 |

**核心判断口诀：**

> **等待 → 并发（线程/协程）；计算 → 并行（多进程）。**

**选型三问：**

1. 任务是**等**多还是**算**多？（决定协程/线程 vs 多进程）
2. 并发量多大？几百以内用线程池即可，上万连接必须协程。
3. 现成库是同步还是异步的？（同步库多就先用线程池，改造异步成本高）

**把决策逻辑写成代码（示意）：**

```python
def choose_concurrency(task_kind: str, concurrency: int) -> str:
    """根据任务类型与并发量推荐并发方案（示意，非生产代码）"""
    if task_kind == "cpu":
        return "多进程 / ProcessPoolExecutor（或 numpy、C 扩展）"
    if task_kind == "io":
        if concurrency > 1000:            # 海量长连接
            return "asyncio（协程）"
        return "ThreadPoolExecutor（线程池）"
    return "协程做 IO + 进程池做计算（混合）"

print(choose_concurrency("cpu", 4))       # 多进程
print(choose_concurrency("io", 20))       # 线程池
print(choose_concurrency("io", 5000))     # asyncio
print(choose_concurrency("mixed", 100))   # 混合
```

**混合方案：协程负责 IO，进程池负责计算**

```python
import asyncio
from concurrent.futures import ProcessPoolExecutor

def cpu_heavy(n: int) -> int:            # CPU 密集：交给进程池
    return sum(i * i for i in range(n))

async def main() -> None:
    loop = asyncio.get_running_loop()
    with ProcessPoolExecutor(max_workers=4) as pool:
        # 计算任务丢进程池（用 run_in_executor 不阻塞事件循环）
        results = await asyncio.gather(
            loop.run_in_executor(pool, cpu_heavy, 10 ** 6),
            loop.run_in_executor(pool, cpu_heavy, 10 ** 6),
        )
        print(results)

asyncio.run(main())
```

**常见技术栈的选型参考：**

| 场景 | 推荐 |
| --- | --- |
| Flask / Django（同步 WSGI） | 线程池 / 多进程（gunicorn workers） |
| FastAPI（异步 ASGI） | `asyncio` + 必要的 `run_in_executor` |
| 大批量数据计算 | `multiprocessing.Pool` / `ProcessPoolExecutor` |
| 采集 / 爬虫 | `asyncio` + aiohttp（高并发）或线程池 + requests |
| 定时批处理 | `multiprocessing` + 任务队列（Celery） |

**易错点：**

- 盲目上 `asyncio`：如果中间夹杂大量同步阻塞库（requests、pymysql），只会把事件循环卡死，反而不如多线程。
- CPU 密集用线程池：看起来「用了池」，实际因 GIL 毫无提速，还多了调度开销。
- 已经在 Web 框架的多进程模型下又开多进程池，容易**进程嵌套爆炸**，要评估总进程数。
- 选型必须结合**部署环境**：容器里 `cpu_count()` 可能返回宿主核数而非配额，需显式配置 worker 数。

## 11. 死锁与避免

**死锁：多个线程/进程互相持有对方需要的资源，且都不释放，导致全部永久阻塞。**

**死锁的四个必要条件（缺一不可，破坏任一即可避免）：**

| 条件 | 含义 | 破坏手段 |
| --- | --- | --- |
| 互斥 | 资源同一时刻只能被一个执行流占用 | 尽量用无锁结构 / 只读共享 |
| 占有并等待 | 持有资源的同时又等待其他资源 | 一次性申请全部资源 |
| 不可抢占 | 资源不能被强行夺走 | 允许超时放弃、回退重试 |
| 循环等待 | 存在等待环 | **统一加锁顺序**（最实用） |

**Python 死锁示例（两把锁交叉获取）**

```python
import threading, time

lock_a = threading.Lock()
lock_b = threading.Lock()

def task1() -> None:
    with lock_a:
        time.sleep(0.1)          # 放大竞态窗口，让 task2 先拿到 lock_b
        with lock_b:             # 等 task2 释放 lock_b
            print("task1 完成")

def task2() -> None:
    with lock_b:
        time.sleep(0.1)
        with lock_a:             # 等 task1 释放 lock_a —— 双方互等，死锁
            print("task2 完成")

t1 = threading.Thread(target=task1)
t2 = threading.Thread(target=task2)
t1.start(); t2.start()
t1.join();  t2.join()            # 程序永远卡在这里
print("这行永远不会打印")
```

**避免手段（三种可运行方案）：**

```python
import threading

lock_a = threading.Lock()
lock_b = threading.Lock()

# 方案一：统一加锁顺序 —— 所有线程都按「同一顺序」拿锁
def ordered() -> None:
    first, second = sorted((lock_a, lock_b), key=id)   # 按内存地址排序
    with first:
        with second:
            print("按序加锁，不会死锁")

# 方案二：带超时获取，失败就放弃并回退，避免永久等待
def with_timeout() -> None:
    got_a = lock_a.acquire(timeout=1)
    got_b = lock_b.acquire(timeout=1) if got_a else False
    if got_a and got_b:
        try:
            print("两把锁都拿到了")
        finally:
            lock_b.release()
            lock_a.release()
    else:
        if got_a:
            lock_a.release()        # 关键：必须释放已持有的一把，避免锁泄漏
        print("获取超时，稍后重试")

# 方案三：用 with 统一管理，保证任何路径（含异常）都会释放
def safe() -> None:
    with lock_a, lock_b:            # 注意这里顺序固定，等价于方案一
        print("with 保证释放")
```

**排查手段：**

- `threading.enumerate()` 看还有哪些线程活着；`sys._current_frames()` 打印各线程调用栈，定位卡在哪个 `acquire`。
- `faulthandler.dump_traceback_later(5, exit=True)` 可在超时后自动导出所有线程栈，是线上排查死锁的利器。
- 进程级死锁用 `py-spy dump --pid <PID>` 直接看栈。

**易错点：**

- 死锁**不能靠复现稳定重现**（依赖调度时序），必须靠**代码审查 + 统一加锁顺序**预防。
- 单把 `Lock` 也能死锁：同一线程对非重入锁二次 `acquire` 会自锁，此时应换 `RLock`。
- 超时方案若忘记释放「已获取到的那把锁」，会变成新的锁泄漏 / 新的死锁源。
- 数据库层面同样有死锁（行锁交叉更新），思路一致：**固定更新顺序 + 缩短事务 + 重试**。

## 12. 队列与生产者消费者模型

队列是线程/进程间**传递数据**的经典结构，天然解耦「生产者」和「消费者」，也是实现限流、缓冲、背压的基础。

**三种队列的区别：**

| 队列 | 所属模块 | 线程安全 | 跨进程 | 内部实现 |
| --- | --- | --- | --- | --- |
| `queue.Queue` | `queue` | 是 | 否 | `Lock` + `Condition` |
| `multiprocessing.Queue` | `multiprocessing` | 是 | **是** | 管道 + pickle 序列化 |
| `asyncio.Queue` | `asyncio` | 单线程内无需锁 | 否 | 基于事件循环的 Future |

**`queue.Queue` 的内部原理**

它内部维护一个 `deque` 与一个 `Condition`：

- `put`：若队列已满（`maxsize` 达到），阻塞等待 `not_full` 条件；成功后 `notify` 唤醒消费者。
- `get`：若队列为空，阻塞等待 `not_empty` 条件；成功后 `notify` 唤醒生产者。

**常用方法：**

| 方法 | 说明 |
| --- | --- |
| `put(item, block=True, timeout=None)` | 入队，满时阻塞 |
| `get(block=True, timeout=None)` | 出队，空时阻塞 |
| `put_nowait` / `get_nowait` | 不阻塞，满/空直接抛异常 |
| `task_done()` | 声明「刚取出的那项已处理完毕」 |
| `join()` | 阻塞直到**所有已入队的任务都 `task_done`** |
| `qsize` / `empty` / `full` | 状态查询（多线程下仅供参考） |

**生产者消费者（线程版）**

```python
import queue, threading, time

q = queue.Queue(maxsize=10)          # 有界队列：满了生产者会阻塞，形成背压

def producer() -> None:
    for i in range(5):
        q.put(i)                     # 满时阻塞等待消费者取走
        print(f"生产 {i}")
        time.sleep(0.1)
    q.put(None)                      # 结束信号（哨兵）

def consumer() -> None:
    while True:
        item = q.get()
        if item is None:
            q.task_done()
            break
        print(f"消费 {item}")
        q.task_done()                # 每处理完一项就通知队列

p = threading.Thread(target=producer)
c = threading.Thread(target=consumer)
p.start(); c.start()
p.join()
q.join()                             # 等所有 put 进来的任务都被 task_done
c.join()
print("全部完成")
```

> `q.join()` 的语义是「队列里所有已入队任务都完成了 `task_done`」，**不是**「消费者线程结束」。`task_done` 调用次数必须与 `put` 次数一致，否则 `join` 永不返回。

**生产者消费者（协程版）**

```python
import asyncio

async def main() -> None:
    q = asyncio.Queue(maxsize=5)

    async def producer() -> None:
        for i in range(5):
            await q.put(i)            # 满时 await 挂起，不阻塞事件循环
            await asyncio.sleep(0.1)
        await q.put(None)

    async def consumer() -> None:
        while True:
            item = await q.get()      # 空时 await 挂起
            if item is None:
                break
            print("消费", item)

    await asyncio.gather(producer(), consumer())

asyncio.run(main())
```

**跨进程版本（把 `queue.Queue` 换成 `mp.Queue`）**

```python
import multiprocessing as mp

def producer(q: mp.Queue) -> None:
    for i in range(5):
        q.put(i)
    q.put(None)

def consumer(q: mp.Queue) -> None:
    while True:
        item = q.get()
        if item is None:
            break
        print("消费", item)

if __name__ == "__main__":
    q = mp.Queue()
    p1 = mp.Process(target=producer, args=(q,))
    p2 = mp.Process(target=consumer, args=(q,))
    p1.start(); p2.start()
    p1.join();  p2.join()
```

**易错点：**

- 忘记调用 `task_done()`：`q.join()` 会永远阻塞（这是最常见的 `join` 卡死原因）。
- `multiprocessing.Queue` 传输的每个对象都要 pickle，传大对象/大批量性能差，此时应改用共享内存或 `Manager`。
- `asyncio.Queue` 只能在**同一事件循环 / 同一线程**内使用，跨线程要用 `queue.Queue` + `run_in_executor`。
- `qsize()` / `empty()` 在多线程下是**近似值**：查询完的那一刻状态就可能变了，不能用它做「等空再继续」的逻辑。

## 13. 多线程实际能不能提速

**先给结论：**

| 任务类型 | 多线程能否提速 | 原因 |
| --- | --- | --- |
| **IO 密集型** | **能**，接近线性 | 等待 IO 时释放 GIL，其他线程可跑 |
| **CPU 密集型** | **不能**，甚至更慢 | GIL 保证同一时刻只有一个线程执行字节码，多核用不上，还多切换开销 |

**GIL 的释放时机（关键细节）：**

| 时机 | 说明 |
| --- | --- |
| 每执行若干字节码 | CPython 3.2+ 基于**时间片**检查（默认约 5 毫秒），主动让出 |
| 遇到 IO 阻塞 | 进入 `socket` / 文件读写等系统调用时**释放 GIL** |
| `time.sleep()` | 睡眠期间释放 GIL |
| C 扩展主动释放 | 如 `numpy`、`hashlib`、`zlib` 内部会 `Py_BEGIN_ALLOW_THREADS` |

**用实验证明（思路 + 代码）**

```python
import time, threading

def cpu_work() -> int:              # CPU 密集
    n = 0
    for i in range(5 * 10 ** 6):
        n += i
    return n

def io_work() -> None:              # IO 密集（用 sleep 模拟等待）
    time.sleep(0.5)

def run(target, count: int) -> float:
    start = time.perf_counter()
    if count == 1:
        target()
    else:
        ts = [threading.Thread(target=target) for _ in range(count)]
        for t in ts: t.start()
        for t in ts: t.join()
    return time.perf_counter() - start

print("CPU 单线程:", round(run(cpu_work, 1), 3))
print("CPU 4 线程:", round(run(cpu_work, 4), 3))   # ≈ 单线程（甚至更慢）
print("IO  单线程:", round(run(io_work, 1), 3))    # ≈ 0.5s
print("IO  4 线程:", round(run(io_work, 4), 3))    # ≈ 0.5s（几乎不增加时间）
```

> 观察：4 个 IO 任务用 4 个线程后，总耗时依然只是**一个任务的时长**（0.5s），说明等待被完全重叠；而 4 个 CPU 任务用 4 个线程，总耗时约等于**串行执行**，GIL 没有让计算并行。

**CPU 密集的替代方案（怎么真的提速）：**

| 方案 | 说明 |
| --- | --- |
| 多进程 | `multiprocessing` / `ProcessPoolExecutor`，直接绕开 GIL 用满多核 |
| `numpy` / `pandas` | 底层 C 实现且**释放 GIL**，向量化远快于 Python 循环 |
| C 扩展 / Cython / numba | 把计算下沉到 C / JIT 编译，同时可释放 GIL |
| 换解释器 | PyPy（JIT）、Python 3.13+ 的 free-threaded 版本（可选禁用 GIL） |
| 下沉到外部系统 | 交给数据库、缓存、向量库做计算 |

**易错点：**

- 「多线程能提速」要看**是否真正并发在等**：如果任务里有共享锁，线程会互相排队，加速被吃掉。
- 线程数不是越多越好：IO 密集也有上限，过多线程带来内存与切换开销。
- `GIL` 是 CPython 的实现细节，不是 Python 语言规范；Jython / PyPy / 无 GIL 构建的表现可能不同。
- `numpy` 能提速常被误解为「多线程变快了」，实际是**向量化 + 释放 GIL**共同作用。

## 14. 异步与多线程的对比

`asyncio` 与多线程都能实现「并发」，但**编程模型与适用边界完全不同**。

| 维度 | 异步（asyncio） | 多线程（threading） |
| --- | --- | --- |
| 调度者 | 事件循环（**协作式**，靠 `await` 让出） | 操作系统（**抢占式**，时间片切换） |
| 编程模型 | 回调 / 协程 / `async-await` | 同步顺序代码 + 共享状态 |
| 并发度 | 极高（单线程可 10 万+ 连接） | 受限（几百 ~ 几千线程） |
| 切换开销 | 极低（用户态，无系统调用） | 较高（内核态上下文切换） |
| 数据共享 | 单线程内执行，**无需加锁** | 共享内存，**必须加锁** |
| 阻塞调用 | **危险**：一阻塞就卡死整个循环 | 只阻塞当前线程，其他线程照跑 |
| 生态兼容 | 需异步库（aiohttp / asyncpg / httpx） | 兼容一切同步库 |
| 调试难度 | 高（调用栈被展开、漏 `await` 静默失效） | 中（竞态问题难复现，但栈直观） |
| CPU 计算 | **无提速**（仍单线程） | **无提速**（受 GIL） |
| 最适场景 | 超高并发网络 IO、长连接、爬虫 | 中等并发 IO、需要复用同步库 |

**同一任务的两种写法：**

```python
# ---------- 多线程 + 线程池：复用同步库 ----------
from concurrent.futures import ThreadPoolExecutor
import requests

def fetch_sync(url: str) -> int:
    return len(requests.get(url, timeout=5).text)

urls = [f"https://example.com/page/{i}" for i in range(50)]
with ThreadPoolExecutor(max_workers=20) as pool:
    results = list(pool.map(fetch_sync, urls))
print("线程版完成", len(results))
```

```python
# ---------- asyncio + aiohttp：单线程高并发 ----------
import asyncio, aiohttp

async def fetch_async(session: aiohttp.ClientSession, url: str) -> int:
    async with session.get(url, timeout=5) as resp:
        text = await resp.text()
        return len(text)

async def main() -> None:
    urls = [f"https://example.com/page/{i}" for i in range(50)]
    async with aiohttp.ClientSession() as session:
        results = await asyncio.gather(*(fetch_async(session, u) for u in urls))
    print("协程版完成", len(results))

asyncio.run(main())
```

**关键澄清：为什么「异步不能加速 CPU 计算」**

> 因为 `asyncio` 的全部任务都在**同一个线程**里跑，事件循环一次只能推进一个协程。协程只在 `await`（IO 等待）时让出，**计算期间没有任何让出点**，所以 10 万个协程做计算，仍是串行。异步擅长的是**把等待重叠**，不是**把计算并行**。要并行计算，必须上多进程。

**选型建议：**

- 项目已大量使用同步库（`requests`、`pymysql`、`psycopg2`）、并发量不高 → **多线程 / 线程池**更划算，改造成本低。
- 面向「高并发网络 IO / 长连接 / 网关」且能用异步库（FastAPI、httpx、asyncpg）→ **asyncio** 更合适。
- 既有 IO 又有计算 → **协程 + 进程池**混合，各取所长。

**易错点：**

- 在异步代码里调用同步阻塞函数（`requests.get`、`time.sleep`、同步 DB 驱动）会让整个服务串行化，务必换成异步库或用 `run_in_executor`。
- 多线程共享状态若不加锁可能「偶尔出错」，而 async 单线程内几乎不用锁——但这也意味着**一个协程里的长计算会拖垮所有协程**。
- 两者都不解决 CPU 密集：任何「异步/多线程能把 CPU 计算变快」的说法都是错的。
- 异步的异常传播更隐蔽：漏 `await`、Task 未持有、`gather` 未 `return_exceptions` 都可能让错误静默丢失。
