## 1. ESLint 的工作原理

**ESLint** 是一个基于 **AST（抽象语法树）** 的 JS/TS 静态代码分析工具，用来发现语法错误、潜在 bug、风格问题和危险写法。它的工作可以拆成三个阶段：

**① 解析（Parsing）—— 源码转 AST**

- 用**解析器**把源码字符串解析成 AST（一棵描述代码结构的树）。
- 默认解析器是 **espree**（实现 ESTree 规范的语法树格式）。
- TS 项目换成 `@typescript-eslint/parser`（内部用 TypeScript 编译器产出 ESTree 兼容 AST）；Vue 单文件组件用 `vue-eslint-parser`。
- 解析失败（语法错误）会直接上报，后面阶段不再执行。

**② 遍历（Traversal）—— 深度优先访问节点并执行规则**

- ESLint 用 `estraverse` 做**深度优先遍历**，进入节点（`enter`）和离开节点（`exit`）时都会派发事件。
- 每条**规则**本质是一份「节点监听器」：声明自己关心哪类节点（如 `Identifier`、`CallExpression`、`VariableDeclaration`）。
- 规则函数从 `context` 拿到配置、源码文本、作用域信息，发现问题时调用 `context.report()` 上报。

**③ 报告（Reporting）—— 输出结果与自动修复**

- 上报的问题带位置、消息、严重级别（`warn`/`error`）、是否可修复。
- 带 `--fix` 时，规则通过 `fixer` 返回「文本区间替换」的修复补丁，ESLint 按区间应用。
- 默认 formatter 是 stylish，`--format json` 可输出结构化结果给 CI 解析。

**配置的分层模型（面试常问「extends/plugins/rules 的区别」）：**

| 配置项 | 作用 | 说明 |
| --- | --- | --- |
| `extends` | 复用他人配置 | 取共享预设：`eslint:recommended`、`airbnb`、`@typescript-eslint/recommended` |
| `plugins` | 引入规则集 | **只是加载**插件（提供规则），不会自动启用任何规则 |
| `rules` | 逐条开关规则 | `off`/`warn`/`error`，可带参数：`["error", { ... }]` |
| `parser` | 指定解析器 | TS/Vue 必须替换，否则解析失败 |
| `parserOptions` | 解析选项 | `ecmaVersion`、`sourceType`、`project`（类型感知规则需要） |
| `env` / `globals` | 声明全局变量 | 避免 `window`、`process` 被报 `no-undef` |
| `overrides` | 按文件覆盖 | 对不同目录/后缀用不同规则，如测试文件放宽 |
| `ignorePatterns` | 忽略文件 | 一般忽略 `dist`、`node_modules`、`coverage` |

> 一句话：`extends` 决定「继承哪些规则集」，`plugins` 决定「有哪些规则可用」，`rules` 决定「每条规则的具体开关」。

**ESLint 9 的 flat config（`eslint.config.js`）：**

ESLint 9 默认使用新的扁平配置，取代了旧版 `.eslintrc.*` 的「级联查找 + extends 字符串」模型。

```js
// eslint.config.js（ESLint 9 扁平配置）
import js from '@eslint/js';
import ts from 'typescript-eslint';
import globals from 'globals';

export default [
  // 忽略目录（扁平配置里用独立对象声明）
  { ignores: ['dist/**', 'node_modules/**', 'coverage/**'] },
  // 基础推荐规则
  js.configs.recommended,
  // TS 推荐规则
  ...ts.configs.recommended,
  {
    files: ['**/*.{js,ts,vue}'],
    languageOptions: {
      ecmaVersion: 2022,
      sourceType: 'module',
      globals: { ...globals.browser, ...globals.node },
    },
    rules: {
      'no-console': ['warn', { allow: ['warn', 'error'] }],
      'no-unused-vars': 'off', // 交给 TS 版本
      '@typescript-eslint/no-unused-vars': ['error', { argsIgnorePattern: '^_' }],
    },
  },
];
```

```json
// 旧版 .eslintrc.json（ESLint 8 及以前，仍常见于老项目）
{
  "root": true,
  "env": { "browser": true, "es2022": true },
  "parser": "@typescript-eslint/parser",
  "parserOptions": { "ecmaVersion": 2022, "sourceType": "module" },
  "plugins": ["@typescript-eslint"],
  "extends": ["eslint:recommended", "plugin:@typescript-eslint/recommended"],
  "rules": {
    "no-console": "warn",
    "@typescript-eslint/no-explicit-any": "off"
  },
  "overrides": [
    { "files": ["*.test.ts"], "rules": { "no-console": "off" } }
  ]
}
```

**写一条自定义规则的骨架（理解规则为何是「监听器」）：**

```js
export default {
  meta: {
    type: 'problem',
    fixable: 'code',
    messages: { noVar: '不要使用 var，请用 let/const' },
  },
  create(context) {
    return {
      // 访问 VariableDeclaration 节点，kind 为 var 就报错
      VariableDeclaration(node) {
        if (node.kind === 'var') {
          context.report({
            node,
            messageId: 'noVar',
            fix(fixer) {
              return fixer.replaceText(node, 'let ' + context.sourceCode.getText(node).slice(4));
            },
          });
        }
      },
    };
  },
};
```

**执行流程串起来：** 读取配置 → 逐个文件用 parser 解析成 AST → 遍历 AST 触发所有规则 → 汇总上报 → 应用 fix → 输出。

**易错点：**

- `plugins` 只加载不启用：只写 `"plugins": ["react"]` 却不写 `"rules"`，规则根本不会生效。
- 类型感知规则（如 `@typescript-eslint/no-floating-promises`）必须配 `parserOptions.project`，否则报错或失效。
- 扁平配置没有「级联向上查找」，一个目录只能有一份 `eslint.config.js`；`extends` 由 JS 的数组展开代替，写法完全不同。
- `eslint .` 与 `eslint src` 的默认忽略规则不同，CI 里明确指定路径更可控。
- 规则优先级：`rules` 覆盖 `extends` 里的同名规则；`overrides` 再按文件覆盖。

## 2. ESLint 与 Prettier 的区别与配合

两者都是「代码规范工具」，但职责完全不同，面试高频点是「为什么会冲突、怎么配合」。

| 维度 | ESLint | Prettier |
| --- | --- | --- |
| 定位 | **代码质量**检查（潜在 bug、坏习惯） | **代码格式**统一（排版） |
| 关注点 | 逻辑：未使用变量、隐式 any、危险写法 | 外观：缩进、换行、引号、分号、行宽 |
| 是否可自动修复 | 部分规则可 `--fix` | **几乎全部可自动格式化** |
| 配置风格 | 规则逐条开关，可辩论 | 「少数派哲学」，几乎不给选项 |
| 对代码的语义理解 | 基于 AST，理解语义 | 部分格式仅处理文本（如 Markdown、CSS） |
| 冲突可能 | 有（格式类规则与 Prettier 结论不一致） | 无（它不检查逻辑） |

**为什么会冲突？** ESLint 里有一批「格式类规则」（`indent`、`quotes`、`semi`、`comma-dangle`、`max-len` 等），它们和 Prettier 的排版结论可能不同。若同时开启，会出现「ESLint 想加换行、Prettier 想合成一行」的来回打架。

**方案 A（推荐）：分离职责 —— Prettier 管格式，ESLint 管质量**

用 `eslint-config-prettier` **关掉所有与 Prettier 冲突的 ESLint 格式规则**，格式化交给 `prettier` 命令（编辑器和 lint-staged 各跑各的）。

```json
// .eslintrc.json —— extends 里 prettier 必须放在最后，才能覆盖前面的格式规则
{
  "extends": [
    "eslint:recommended",
    "plugin:@typescript-eslint/recommended",
    "prettier"
  ]
}
```

```js
// eslint.config.js（扁平配置）：用 eslint-config-prettier 关闭冲突规则
import js from '@eslint/js';
import prettier from 'eslint-config-prettier';

export default [
  js.configs.recommended,
  prettier, // 放在末尾，禁用所有与 Prettier 冲突的规则
];
```

```json
// .prettierrc.json
{
  "semi": true,
  "singleQuote": true,
  "printWidth": 100,
  "trailingComma": "all",
  "arrowParens": "always",
  "tabWidth": 2
}
```

```bash
# 格式化单独跑
prettier --write "src/**/*.{js,ts,css,json,md}"
```

**方案 B：把 Prettier 当成 ESLint 规则跑 —— `eslint-plugin-prettier`**

用 `eslint-plugin-prettier` 让「格式不一致」直接变成一条 ESLint 报错，配合 `eslint-config-prettier`（`plugin:prettier/recommended` 已内置）。

```json
// .eslintrc.json
{
  "extends": [
    "eslint:recommended",
    "plugin:prettier/recommended"  // = eslint-plugin-prettier + eslint-config-prettier
  ]
}
```

| 对比 | 方案 A（分离职责） | 方案 B（plugin-prettier） |
| --- | --- | --- |
| 命令入口 | 两条：`eslint` + `prettier` | 一条：`eslint` |
| 报错可读性 | 质量与格式问题分开，清晰 | 格式差异也显示为 ESLint error，消息较啰嗦 |
| 性能 | 更快（各跑各的） | 较慢（每行都过 Prettier） |
| 编辑器 | 需同时装两个插件 | 只装 ESLint 即可 |
| 后果 | 需保证两条命令都被执行 | 容易「只跑 eslint 忘了格式化」也一致 |
| 推荐度 | **现代主流推荐** | 老项目/追求单一入口时可用 |

> 结论：**两者都要求安装 `eslint-config-prettier`**（关掉冲突规则），差别只在「格式检查是否复用 ESLint 的通道」。多数团队选方案 A。

**易错点：**

- `prettier` 在 `extends` 数组里**必须放最后**，否则前面的格式规则会覆盖它，冲突依旧。
- 只装 `eslint-plugin-prettier` 不装 `eslint-config-prettier`，冲突规则不会关闭。
- Prettier 不检查逻辑，别指望它发现未使用变量；ESLint 也不该管缩进，职责要分清。
- Stylelint 同理：CSS/SCSS 用 `stylelint-config-standard` + `stylelint-config-prettier`（新版 `stylelint-config-prettier` 已并入 stylelint 15+ 的 `stylelint-config-standard`，样式排序规则改用 `stylelint-config-recess-order` 或 `stylelint-order`）。

## 3. Husky 与 lint-staged

**目标**：在 `git commit` 时自动拦截「不合规的代码」，把问题挡在提交之前，而不是等 CI 才失败。

**① Git Hooks 是底层机制**

Git 在仓库的 `.git/hooks/` 目录下有一批可执行的钩子脚本，在特定动作前后触发（如 `pre-commit`、`commit-msg`）。但 `.git` 目录**不随仓库提交**，团队里每个人都要手动装 —— 于是有了 **Husky**。

**② Husky 的作用**

- 把钩子脚本纳入**版本管理**（放在 `.husky/` 目录）并自动安装到 `.git/hooks/`。
- Husky 9+ 的用法：`npm install husky -D` 后执行 `npx husky init` 初始化（会自动加 `prepare` 脚本并生成 `.husky/pre-commit`）。
- 钩子脚本里可以直接写命令，Husky 会负责注入运行时与执行。

**③ lint-staged 的作用**

直接 `pre-commit` 里跑 `eslint .` 是**全量检查**，项目大了每次提交要等好几秒甚至几十秒。**lint-staged** 只对**本次暂存区（staged）的文件**执行任务，速度提升显著，也是它能流行的核心原因。

| 对比 | 全量检查（`eslint .`） | lint-staged |
| --- | --- | --- |
| 作用范围 | 整个项目所有文件 | 仅 `git add` 过的暂存文件 |
| 耗时 | 慢，随项目增长 | 快，与改动量相关 |
| 是否会误报旧问题 | 会（历史文件的老问题也阻断提交） | 不会（只查你改的） |
| 适用场景 | CI 门禁、定期检查 | 本地提交前 |

**配置示例：**

```bash
# 安装并初始化
npm install -D husky lint-staged
npx husky init
```

```bash
# .husky/pre-commit —— 提交前跑 lint-staged
npx lint-staged
```

```json
// package.json 中配置 lint-staged
{
  "scripts": {
    "prepare": "husky"
  },
  "lint-staged": {
    "*.{js,ts,vue,jsx,tsx}": ["eslint --fix", "prettier --write"],
    "*.{css,scss,less}": ["stylelint --fix", "prettier --write"],
    "*.{json,md,yml}": ["prettier --write"]
  }
}
```

```ini
# 或用独立的 .lintstagedrc / lint-staged.config.js
```

```js
// lint-staged.config.js —— 需要动态构造命令时用函数形式
export default {
  '*.{js,ts,vue}': (files) => {
    // 文件名可能含空格，需转义
    const list = files.map((f) => `"${f}"`).join(' ');
    return [`eslint --fix ${list}`, `prettier --write ${list}`];
  },
};
```

**执行链路：** `git commit` → 触发 `.husky/pre-commit` → `lint-staged` 取暂存文件 → 按 glob 匹配跑对应任务 → 若 `eslint --fix` 改了内容，需重新 `git add`（lint-staged 会自动把修改后的文件重新加入暂存区）→ 有未修复的 error 则**中断本次提交**。

**易错点：**

- lint-staged 默认会**自动 `git add`** 修复后的文件；若某任务不返回文件修改，则无影响。
- 首次克隆仓库后需要执行 `npm install`（触发 `prepare` 脚本）才会装好钩子；CI 上加 `--ignore-scripts` 会跳过。
- `eslint --fix` 未修复的**剩余 error** 仍会让提交失败，这是设计意图；想只警告可用 `--max-warnings` 控制。
- 钩子可以用 `git commit --no-verify` 绕过，因此**不要只依赖本地钩子**，CI 必须有同样的检查兜底。
- Husky 9 废弃了 `husky install` 的手动调用，改为 `husky`（在 `prepare` 里）。

## 4. commitlint 与 Git 提交规范

**① Conventional Commits（约定式提交）**

提交信息统一成固定格式，既可读，又能被工具解析，用于**自动生成 changelog 和语义化版本号**。

```text
<type>(<scope>): <subject>

<body>

<footer>
```

- `type`：**必填**，提交类型。
- `scope`：可选，影响范围（如 `router`、`user`、`deps`）。
- `subject`：必填，简短描述，动词原形、不加句号。
- `body`：可选，详细说明。
- `footer`：可选，如 `BREAKING CHANGE:` 声明破坏性变更。

**常用 type：**

| type | 含义 | 是否影响版本号（semantic-release 语义） |
| --- | --- | --- |
| `feat` | 新增功能 | MINOR |
| `fix` | 修复 bug | PATCH |
| `perf` | 性能优化 | PATCH |
| `refactor` | 重构（不改行为） | 不影响 |
| `docs` | 文档变更 | 不影响 |
| `style` | 格式调整（不影响逻辑） | 不影响 |
| `test` | 测试相关 | 不影响 |
| `build` | 构建/依赖变更 | 不影响 |
| `ci` | CI 配置变更 | 不影响 |
| `chore` | 杂项（工具、配置） | 不影响 |
| `revert` | 回滚某次提交 | 不影响 |
| 任意 type + `!` 或 `BREAKING CHANGE` | 破坏性变更 | **MAJOR** |

**② commitlint 的接入**

commitlint 在 **commit-msg 钩子**里校验提交信息是否符合规范，不符则拒绝提交。

```bash
npm install -D @commitlint/cli @commitlint/config-conventional
```

```js
// commitlint.config.js
export default {
  extends: ['@commitlint/config-conventional'],
  rules: {
    'type-enum': [
      2,
      'always',
      ['feat', 'fix', 'perf', 'refactor', 'docs', 'style', 'test', 'build', 'ci', 'chore', 'revert'],
    ],
    'subject-empty': [2, 'never'],
    'subject-full-stop': [2, 'never', '.'], // 标题结尾不许加句号
    'header-max-length': [2, 'always', 72],
    'scope-case': [2, 'always', 'kebab-case'],
  },
};
```

```bash
# .husky/commit-msg —— 校验提交信息
npx --no -- commitlint --edit "$1"
```

```bash
# 手动校验一条信息（CI 里可用）
echo "feat(router): 支持嵌套路由" | npx commitlint
echo "update something" | npx commitlint   # 会报错：type 不合法
```

**③ 交互式生成提交信息（可选）**

```bash
npm install -D commitizen cz-git
```

```json
// package.json
{
  "scripts": { "commit": "cz" },
  "config": {
    "commitizen": { "path": "node_modules/cz-git" }
  }
}
```

```bash
npm run commit   # 交互式选择 type/scope/描述，自动拼出规范信息
```

> 这套链路（commitlint + Conventional Commits）是「changelog 自动化」和「自动升版本号」的**前置条件**——没有规范提交，工具就无从解析。

**易错点：**

- commitlint 只校验**提交信息**，不校验代码；代码质量仍需 lint-staged。
- `subject-full-stop` 与 `header-max-length` 是最容易踩的规则：标题别以句号结尾、别超长。
- 破坏性变更必须显式声明 `!` 或 footer 里的 `BREAKING CHANGE:`，否则 semantic-release 不会升 MAJOR。
- 团队已有历史提交不规范时，commitlint 只对**新提交**生效，历史提交无法追溯（除非配合 `--from` 手工检查）。
- scope 名字要统一（如全用 kebab-case），否则 changelog 分组会散乱。

## 5. Git Hooks 有哪些？

Git Hooks 是 Git 在特定动作前后自动执行的脚本，分**客户端**（本地，随 `.git/hooks`）与**服务端**（远端，`pre-receive` 等，如 GitLab/GitHub 的校验集中在这里）。

**常用客户端钩子：**

| Hook | 触发时机 | 常见用途 |
| --- | --- | --- |
| `pre-commit` | `git commit` 执行前，生成提交对象前 | lint-staged、格式化、跑单测 |
| `prepare-commit-msg` | 生成默认提交信息后、编辑器打开前 | 自动插入 issue 号/模板 |
| `commit-msg` | 提交信息编辑完成后 | commitlint 校验格式 |
| `post-commit` | 提交完成之后 | 通知、统计、触发本地任务 |
| `pre-rebase` | rebase 开始前 | 阻止对已推送分支 rebase |
| `post-checkout` | `git checkout`/`git switch` 后 | 自动装依赖、切换环境 |
| `post-merge` | merge 完成后 | 依赖变更时提示 `npm install` |
| `pre-push` | `git push` 前 | 跑完整测试、类型检查（比 pre-commit 更重） |
| `post-rewrite` | 被 `commit --amend`/`rebase` 重写后 | 同步元数据 |
| `applypatch-msg` / `pre-applypatch` | `git am` 相关 | 打补丁时校验 |

**服务端钩子：**

| Hook | 触发时机 | 用途 |
| --- | --- | --- |
| `pre-receive` | 推送到达、尚未更新引用前 | 统一门禁（拒绝不规范提交/大文件） |
| `update` | 每个分支引用更新前 | 分支级策略（如保护分支） |
| `post-receive` | 引用更新后 | 触发部署、通知、CI |

```bash
# 原生写法：.git/hooks/pre-commit（需 chmod +x，且不入版本库）
#!/bin/sh
npm run lint-staged
```

```bash
# Husky 写法：.husky/pre-commit（入版本库，团队共享）
npx lint-staged
```

```bash
# .husky/pre-push —— 推送前跑更重的检查
npm run type-check
npm test
```

**为什么推荐 Husky 而不是手写 `.git/hooks`：**

- `.git/hooks` **不入版本库**，新同事克隆后没有钩子，需要手动装。
- Husky 把脚本放到 `.husky/`（属于工作区，会提交），并通过 `prepare` 自动安装，保证团队一致。

**易错点：**

- 钩子脚本**没有执行权限**（Windows 尤其明显）或首行 shebang 缺失，会导致静默不执行；Husky 生成的脚本已处理好。
- 客户端钩子可用 `--no-verify` 跳过，**安全关键校验必须放服务端钩子或 CI**。
- `post-merge`/`post-checkout` 里跑 `npm install` 会拖慢操作，建议只在 lock 变化时提醒而非自动装。
- 服务端钩子运行在服务端环境，脚本依赖（如 Node 版本）需按服务端配置，不能假设与本地一致。

## 6. Git 工作流有哪些？

**Git 工作流**指「团队如何用分支协作、如何合并、如何发布」的一套约定。主流有四种。

| 工作流 | 核心分支 | 发布方式 | 适用团队 | 优点 | 缺点 |
| --- | --- | --- | --- | --- | --- |
| **Git Flow** | `main`/`develop`/`feature`/`release`/`hotfix` | 计划式、版本化发布 | 有明确版本周期的产品 | 分支职责清晰，适合多版本并行维护 | 分支多、流程重、合并频繁、不适合持续交付 |
| **GitHub Flow** | `main` + 短命 `feature` 分支 | PR 合并即部署 | 持续交付的 Web 团队 | 简单、配合 PR/CI 天然顺畅 | 缺少发布分支，难处理多版本并行 |
| **Trunk Based** | 只有 `main`（主干） | 小步提交，随时可发 | 高成熟度、强 CI 团队 | 冲突少、集成快、天然持续交付 | 对自动化测试与特性开关要求极高 |
| **GitLab Flow** | `main` + 环境分支（如 `staging`/`production`） | 代码随环境分支流转 | 需要多环境部署的团队 | 兼顾简单与多环境，支持 cherry-pick 回补 | 需要管理环境分支与回补流程 |

**Git Flow 分支模型：**

```text
main     ──●───────────────●───────────────●──→   只放「已发布」的稳定版本，打 tag
            \             / \             /
release       ●───●───●       ●───●───●           发布准备分支，只修 bug，验收后并入 main+develop
            /               /
develop  ──●───────●───────●───────────────●──→   集成分支，汇聚所有已完成功能
            \     /         \     /
feature       ●─●            ●───●                功能分支，从 develop 切出，完成后并回 develop
                  \
hotfix             ●───●  ─────→ 从 main 切出，紧急修复，同时并回 main 与 develop
```

**GitHub Flow 流程：**

```text
main ──●──────────────────●──────────●──→  始终可部署
        \                /          /
feature  ●───●───●───●──●            ●───●   每个改动一条短命分支，开 PR，CI 通过后合并部署
```

**GitLab Flow（环境分支）：**

```text
main ──────●──────●──────────●──→
            \      \          \
staging      ●──────●          \     预发布环境
                    \          \
production           ●──────────●    生产环境（由 staging 或 main 推进）
```

**选型建议：**

- **持续交付的 Web 产品** → GitHub Flow 或 GitLab Flow（简单、贴合 PR/CI）。
- **成熟的工程团队、自动化完备** → Trunk Based（最少分支、最快集成）。
- **多版本并行、有固定发版节奏的客户端/库** → Git Flow（或它的简化：GitHub Flow + release 分支）。

> 面试要点：**没有最好的工作流，只有最适合团队自动化水平与发布节奏的工作流**。分支越多，合并成本越高；能否高频集成，取决于 CI 与测试是否足够可靠。

**易错点：**

- Git Flow 最大的痛点是 `develop` 长期落后于 `main`，合并冲突多、release 分支生命周期长。
- Trunk Based 必须配合**特性开关（Feature Flag）**：功能未完成也能进主干，只是默认关闭。
- 别把「分支命名规范」（如 `feature/xxx`、`hotfix/xxx`）当成工作流本身，它只是约定。
- 跨环境推进时（GitLab Flow），注意「回补」：环境分支上直接改的 hotfix 要 cherry-pick 回 main，否则下次发布会被覆盖。

## 7. merge 与 rebase 的区别？

两者都能把一个分支的改动「并入」另一个分支，但**历史形态**与**是否改写提交**不同。

| 维度 | merge | rebase |
| --- | --- | --- |
| 历史形态 | **非线性**，保留分叉与合并点 | **线性**，提交像排队一样接在目标分支后 |
| 是否产生新提交 | 产生一个 **merge commit** | 不产生 merge commit，**改写原提交**（新 hash） |
| 提交 ID | 原分支提交 hash 不变 | 原提交被复制成新 hash |
| 是否改写历史 | 不改写 | **改写**（危险点在共享分支） |
| 冲突处理 | 一次性在合并点解决 | **可能每个提交都冲突**，逐个解决 |
| 适用 | 集成到公共分支、保留真实协作轨迹 | 本地整理提交、同步上游、保持线性 |
| 可回退性 | 合并点清晰，`git revert -m 1` 可回退整体 | 线性但无合并点，回退需按提交处理 |

**merge 的两种形态：**

```bash
git checkout main
git merge feature     # 默认：若 main 有新提交，会生成一个 merge commit（非线性）
git merge --ff-only feature   # 仅允许快进，不能快进就报错
git merge --no-ff feature     # 强制生成 merge commit（即使能快进）
```

```text
# merge（--no-ff）历史：
main    A───B───────M
             \     /
feature       C───D
# M 是合并节点，保留了两条线的分叉

# rebase 历史（线性）：
main    A───B───C'───D'
# C、D 被「重放」到 B 之后，hash 变成 C'、D'，看不出曾经分叉
```

**rebase 的用法：**

```bash
# 把当前分支的改动「重放」到最新的 main 之上
git checkout feature
git rebase main

# 交互式整理本地提交（合并、改写、删除、排序）
git rebase -i HEAD~3
```

```bash
# 解决 rebase 冲突后继续
git add <文件>
git rebase --continue
# 放弃本次 rebase，回到开始前的状态
git rebase --abort
```

**黄金法则（面试必答）：**

> **不要对「已经被别人拉取过 / 已推送到公共远端」的分支做 rebase。** rebase 会改写提交 hash，别人的本地分支与你远端分支会对不上，强行同步会造成重复提交或历史灾难。

- 本地**私有的** `feature` 分支：可以随便 rebase 整理。
- 公共的 `main`/`develop`/`release`：**只允许 merge，不允许 rebase**。
- 已推送的私有分支要 rebase，只能用 `git push --force-with-lease`（比 `--force` 更安全，会先校验远端是否被别人更新过）。

**易错点：**

- `git pull` 默认行为受 `pull.rebase` 配置影响：`git config pull.rebase true` 才能让 `git pull` 用 rebase（否则默认 merge，产生多余的 merge commit）。
- rebase 冲突可能反复出现（每个提交一次），大分支上比 merge 更耗精力。
- rebase 后原提交的 hash 变了，若这些 hash 已被别的分支/CI 记录，会失效。
- 用 `--force` 覆盖远端是**危险操作**；优先 `--force-with-lease`，并确认没有队友在你之后推送。

## 8. reset 与 revert 的区别？

两者都用于「撤销」，但一个**改写历史**，一个**追加反向提交**。

| 维度 | `git reset` | `git revert` |
| --- | --- | --- |
| 本质 | 移动 `HEAD`/分支指针，**丢弃或退回**提交 | 生成一个**反向提交**来抵消目标提交 |
| 是否改写历史 | **改写**（已推送会与远端冲突） | **不改写**（在原历史后面追加） |
| 安全性 | 低（可能丢提交） | 高（可安全用于公共分支） |
| 适用 | 本地尚未推送的提交 | **已推送到公共分支**的错误提交 |
| 回退粒度 | 回到某个提交状态（可丢多个） | 精确抵消某一个提交 |
| 典型命令 | `reset --soft/--mixed/--hard <commit>` | `revert <commit>` |

**`git reset` 的三种模式（重点）：**

| 模式 | 分支指针 | 暂存区（index） | 工作区 | 效果 |
| --- | --- | --- | --- | --- |
| `--soft` | 回退 | **保留** | 保留 | 撤销提交，改动回到**暂存区**，可立即重新提交 |
| `--mixed`（默认） | 回退 | **重置** | 保留 | 撤销提交并取消暂存，改动留在**工作区** |
| `--hard` | 回退 | 重置 | **重置** | 提交、暂存、工作区**全部丢弃**（危险） |

```bash
# 撤销最近一次提交，但把改动放回暂存区（想改完重新提交）
git reset --soft HEAD~1

# 撤销最近一次提交并取消暂存（改动还在工作区，可继续改）
git reset HEAD~1

# 彻底回退到某个提交，丢弃此后的所有改动（危险！）
git reset --hard HEAD~3

# 找回被 reset/删掉提交（reflog 是你的安全网）
git reflog
git reset --hard HEAD@{2}
```

**`git revert`：**

```bash
# 抵消某个提交，生成一个新提交（不改写历史）
git revert a1b2c3d
# 撤销一连串提交
git revert --no-commit HEAD~3..HEAD   # 先不自动提交，攒到一起再提交
# 回退一个 merge 提交，需指定保留哪一侧（-m 1 表示保留第一父，即主分支侧）
git revert -m 1 <merge-commit>
```

**选择判断：**

```text
提交还没 push，只在自己本地      → git reset（干净利落，改写历史无妨）
提交已经 push，别人可能已拉取    → git revert（不改写历史，最安全）
只是想让自己本地少几个提交        → reset --soft/--mixed 保留改动
已经把改动弄丢想找回              → git reflog + reset
```

**易错点：**

- `git reset --hard` 会**永久丢弃未提交的工作区改动**，执行前务必确认（可用 `git stash` 先保存）。
- 忘记「默认是 `--mixed`」：很多人以为 `git reset HEAD~1` 也删了改动，其实改动还在工作区。
- 公共分支上 `reset` 后 `push --force` 会改写远端历史，队友的提交会「消失」，除非团队约定否则禁止。
- `revert` 一个 merge 提交时**必须给 `-m` 参数**，否则 Git 不知道保留哪个父提交。
- 被 revert 抵消的提交，若之后又 merge 回来，需要先 revert 掉那次 revert（否则改动不会重新生效）。

## 9. 单元测试框架与写法

**① 主流框架与选择**

| 框架 | 特点 | 适用 |
| --- | --- | --- |
| **Jest** | 生态最成熟，内置 mock/快照/覆盖率，开箱即用 | 老项目、React（CRA）、大量现有资料 |
| **Vitest** | 基于 Vite，速度极快，API 与 Jest 兼容度高，原生 ESM/TS | Vite 项目、现代工程化首选 |
| **Mocha + Chai + Sinon** | 灵活、组装式（断言/桩各自独立） | 需要高度定制、Node 项目 |
| **@testing-library/react** | 组件测试，面向用户行为而非实现 | React 组件 |
| **Vitest + @vue/test-utils** | Vue 组件测试组合 | Vue 项目 |

| 维度 | Jest | Vitest |
| --- | --- | --- |
| 底层转换 | 自带 babel/ts-jest | 复用 Vite（esbuild/rollup） |
| ESM 支持 | 需额外配置（`extensionsToTreatAsEsm` 等） | **原生支持** |
| 速度 | 较慢（尤其冷启动） | **快**（复用 Vite 依赖预构建与缓存） |
| 与构建配置 | 需单独维护 transform | **复用 `vite.config.ts`** |
| mock 能力 | 强（`jest.mock`） | 兼容（`vi.mock`） |
| 覆盖率 | Istanbul（默认）

/V8 | V8（默认）/ Istanbul |

**② 核心写法（`describe` / `it` / `expect`）**

```ts
// math.ts
export const add = (a: number, b: number) => a + b;
export const divide = (a: number, b: number) => {
  if (b === 0) throw new Error('除数不能为 0');
  return a / b;
};

// math.test.ts（Vitest 语法，Jest 基本一致，把 vi 换成 jest 即可）
import { describe, it, expect, beforeEach, vi } from 'vitest';
import { add, divide } from './math';

describe('math 模块', () => {
  // 每个用例前执行
  beforeEach(() => {
    vi.clearAllMocks();
  });

  it('add 应正确相加', () => {
    expect(add(1, 2)).toBe(3);
  });

  it('divide 遇到 0 应抛错', () => {
    expect(() => divide(1, 0)).toThrow('除数不能为 0');
  });

  it('异步函数应 resolve 出期望值', async () => {
    await expect(Promise.resolve(add(2, 3))).resolves.toBe(5);
  });
});
```

**常用匹配器：**

| 匹配器 | 含义 |
| --- | --- |
| `toBe` | 严格相等（`Object.is`），用于原始值 |
| `toEqual` | 递归结构相等，用于对象/数组 |
| `toContain` | 数组/字符串包含 |
| `toThrow` | 抛出异常（可带消息） |
| `resolves` / `rejects` | 断言 Promise 成功/失败 |
| `toMatchSnapshot` | 快照比对 |
| `toBeCalledWith` | mock 被以指定参数调用 |

**③ mock（隔离依赖）**

```ts
import { vi } from 'vitest';
import * as userApi from './api';
import { getUserName } from './user';

// 桩掉整个模块
vi.mock('./api');

it('getUserName 应调用接口并返回名字', async () => {
  // 让 mock 函数在本次用例返回指定值
  vi.mocked(userApi.fetchUser).mockResolvedValue({ id: 1, name: '张三' });

  await expect(getUserName(1)).resolves.toBe('张三');
  expect(userApi.fetchUser).toHaveBeenCalledWith(1);
});
```

```ts
// 只桩一个函数，保留其余实现
import { vi } from 'vitest';
const spy = vi.spyOn(console, 'log').mockImplementation(() => {});
console.log('hi');
expect(spy).toHaveBeenCalledWith('hi');
spy.mockRestore();
```

**定时器与快照：**

```ts
import { vi } from 'vitest';

it('假定时器可加速时间相关逻辑', () => {
  vi.useFakeTimers();
  const fn = vi.fn();
  setTimeout(fn, 1000);
  vi.advanceTimersByTime(1000);
  expect(fn).toHaveBeenCalled();
  vi.useRealTimers();
});

it('渲染结构快照', () => {
  expect({ a: 1, b: [2, 3] }).toMatchSnapshot(); // 首次生成 .snap，之后比对
});
```

**易错点：**

- 快照测试**不要盲目 `-u` 更新**：`vitest -u`/`jest -u` 全量刷新会把真实问题一起覆盖，应逐个 review  diff。
- mock 后忘记 `restore`/`clear`：`vi.restoreAllMocks()` 与 `vi.clearAllMocks()` 语义不同（前者恢复原实现，后者只清调用记录）。
- `toBe` 与 `toEqual` 混用：对象必须用 `toEqual`，`toBe` 会因引用不同而失败。
- 异步断言要 `await`，否则用例可能在断言执行前就结束而「假通过」。
- 测试要**独立**：用例之间不能有顺序依赖（`beforeEach` 清理状态）。

## 10. 测试覆盖率与测试策略

**① 覆盖率的四个指标**

| 指标 | 含义 | 举例说明漏测点 |
| --- | --- | --- |
| **Statements** 语句覆盖率 | 被执行到的语句占比 | `if` 里某句没跑到 |
| **Branches** 分支覆盖率 | `if/else`、`?:`、`&&`、`\|\|` 各分支被执行占比 | `else` 分支从未覆盖 |
| **Functions** 函数覆盖率 | 被调用的函数占比 | 某工具函数从未被测试调用 |
| **Lines** 行覆盖率 | 被执行的源码行占比 | 与语句接近，但多行语句计算方式不同 |

```ts
// 例子：函数与分支覆盖的关系
export function grade(score: number) {
  if (score >= 90) return 'A';   // 分支 1
  if (score >= 60) return 'B';   // 分支 2
  return 'C';                    // 分支 3
}
// 只测 grade(95) → 语句覆盖 100%（3 条语句都「可能」被执行）？
// 实际：只跑一条路径，分支覆盖率只有 33%，漏测 B 与 C。
```

> 关键认知：**行/语句覆盖率 100% 不代表没 bug**，分支覆盖率更能反映逻辑完整度；但覆盖率是「测了多少」，不是「测得对不对」。

**② 配置覆盖率门槛（以 Vitest 为例）**

```ts
// vitest.config.ts
import { defineConfig } from 'vitest/config';

export default defineConfig({
  test: {
    environment: 'jsdom',
    coverage: {
      provider: 'v8', // 或 'istanbul'
      reporter: ['text', 'html', 'lcov'], // lcov 供 CI/Codecov 使用
      include: ['src/**/*.{ts,tsx,vue}'],
      exclude: ['src/**/*.d.ts', 'src/main.ts', '**/*.test.ts'],
      thresholds: {
        statements: 80,
        branches: 75,
        functions: 80,
        lines: 80,
      },
    },
  },
});
```

```json
// package.json
{
  "scripts": {
    "test": "vitest",
    "coverage": "vitest run --coverage"
  }
}
```

**③ 测试金字塔（测试策略）**

```text
        /\        E2E（端到端）
       /  \       少而精、慢、贵（Playwright / Cypress）
      /----\      验证真实用户流程
     /      \
    /  集成  \    中等数量（组件 + 接口联调）
   /----------\   验证模块间协作
  /            \
 /   单元测试   \ 数量最多、快、便宜
/________________\ 验证单个函数/组件逻辑（Vitest / Jest）
```

| 层级 | 数量 | 速度 | 成本 | 关注点 | 工具 |
| --- | --- | --- | --- | --- | --- |
| 单元 | 多 | 快 | 低 | 函数/组件内部逻辑 | Vitest、Jest |
| 集成 | 中 | 中 | 中 | 模块协作、接口、状态流转 | Vitest + Testing Library、MSW |
| E2E | 少 | 慢 | 高 | 真实用户路径、跨页流程 | Playwright、Cypress |

**④ 测试策略原则**

- **测试行为，不测实现**：断言「用户看到什么」，避免耦合内部私有方法，否则重构就碎。
- **优先测核心逻辑与边界**：纯函数、工具、状态管理、关键分支；UI 渲染细节交给集成/E2E。
- **覆盖率作为门槛而非目标**：设合理阈值（如 80%），禁止「为刷覆盖率而写无意义断言」。
- **CI 中跑 `run` 模式**：本地开发用 watch（`vitest`），CI 用单次运行（`vitest run`）避免挂起。

**易错点：**

- 覆盖率 100% 仍可能有 bug（分支组合、边界外输入、并发、副作用未被断言）。
- 把 `environment` 设成 `node` 却测组件：DOM 相关 API 不存在会直接失败，需 `jsdom`/`happy-dom`。
- 排除文件写太宽会「虚高」：把核心业务文件也 exclude 掉，覆盖率就失去意义。
- E2E 用例过多会拖慢流水线且易 flaky；核心路径稳定后再扩。
- 覆盖率报告要区分「本次新增代码的覆盖率」，全量覆盖率会被历史代码稀释。

## 11. TypeScript 类型检查接入工程

**① 类型检查与「编译产物」是两件事**

- `tsc` 既做类型检查，又输出 JS；
- 而 Vite/webpack 用 esbuild/SWC/Babel 做的是**转译**（去类型），**不做类型检查**（为了快）。
- 所以现代工具链里，**类型检查必须单独跑**，否则改错类型也能打包成功。

| 方式 | 命令 | 说明 |
| --- | --- | --- |
| 仅类型检查 | `tsc --noEmit` | 不产出文件，只报类型错误（CI 常用） |
| Vue 项目 | `vue-tsc --noEmit` | 识别 `.vue` 文件里的 `<script setup>` 类型 |
| 构建时检查 | `vue-tsc --noEmit && vite build` | 类型不过不构建（推荐） |
| ESLint 内 | `@typescript-eslint` 的类型感知规则 | 补充 lint 层面的类型问题 |

**② tsconfig.json 关键配置**

```json
{
  "compilerOptions": {
    "target": "ES2020",
    "module": "ESNext",
    "moduleResolution": "Bundler",     // 现代打包器解析方式
    "strict": true,                     // 开启全套严格检查（强烈建议）
    "noUnusedLocals": true,             // 未使用局部变量报错
    "noUnusedParameters": true,
    "noImplicitOverride": true,
    "noFallthroughCasesInSwitch": true,
    "verbatimModuleSyntax": true,       // 明确区分 import type
    "skipLibCheck": true,               // 跳过 .d.ts 检查，提速
    "isolatedModules": true,            // 每个文件可独立转译（Vite/Babel 需要）
    "esModuleInterop": true,
    "resolveJsonModule": true,
    "baseUrl": ".",
    "paths": { "@/*": ["src/*"] }       // 路径别名
  },
  "include": ["src/**/*.ts", "src/**/*.tsx", "src/**/*.vue"],
  "exclude": ["node_modules", "dist"]
}
```

**③ 接入到脚本与 CI**

```json
// package.json
{
  "scripts": {
    "type-check": "vue-tsc --noEmit",
    "build": "npm run type-check && vite build",
    "lint": "eslint . --fix"
  }
}
```

```yaml
# CI 中的质量门禁：类型检查与 lint 各跑一步
jobs:
  quality:
    steps:
      - run: npm ci
      - run: npm run type-check
      - run: npm run lint
      - run: npm run coverage
```

**④ ESLint 的类型感知规则**

```js
// eslint.config.js
import tseslint from 'typescript-eslint';

export default [
  ...tseslint.configs.recommendedTypeChecked,
  {
    languageOptions: {
      parserOptions: {
        projectService: true, // 让规则能读取 tsconfig 的类型信息
        tsconfigRootDir: import.meta.dirname,
      },
    },
    rules: {
      '@typescript-eslint/no-floating-promises': 'error', // 需要类型信息
      '@typescript-eslint/no-misused-promises': 'error',
    },
  },
];
```

**易错点：**

- 以为 Vite 能报类型错误：**它不能**，只有 `vue-tsc`/`tsc --noEmit` 才做类型检查。
- `skipLibCheck: true` 会跳过第三方 `.d.ts` 的错误，能提速，但可能掩盖依赖类型问题。
- 路径别名 `paths` 只影响类型检查与 IDE，**打包器还需单独配 `resolve.alias`**（或通过 `vite-tsconfig-paths` 桥接）。
- `isolatedModules`：`const enum`、仅 re-export 的类型等单文件无法处理的写法会被禁用，需改写。
- 类型检查耗时随项目增大，可在 CI 中用 `tsc --incremental`（配合 `tsBuildInfoFile`）加速。

## 12. Code Review 与 PR 规范

**① 标准 PR 流程**

```text
1. 从 main 切出特性分支（命名规范：feat/xxx、fix/xxx）
2. 本地开发 + 自测（lint / test / type-check 通过）
3. 提交并推送，发起 PR（描述清楚「为什么改、怎么改、怎么验证」）
4. CI 自动门禁：lint / 单测 / 类型检查 / 构建
5. 指定 Reviewer（至少 1 人，核心模块 2 人）
6. 逐个处理 review 意见，push 增量提交（不改写已 review 的历史）
7. 至少 1 人 approve + CI 全绿 → 合并（Squash/合并策略见下）
8. 关联 issue 自动关闭，必要时回滚方案准备好
```

**② Review 的关注点（按优先级）**

| 优先级 | 关注点 | 具体内容 |
| --- | --- | --- |
| 高 | 正确性 | 逻辑是否满足需求、边界与异常、并发/时序 |
| 高 | 安全性 | 注入、XSS、鉴权、密钥是否泄漏、依赖风险 |
| 中 | 可维护性 | 命名、职责单一、重复代码、复杂度 |
| 中 | 测试 | 新增/修改逻辑是否有对应测试，测试是否有效 |
| 中 | 性能 | 不必要的重渲染、大循环、内存泄漏、包体增量 |
| 低 | 风格 | 交给 lint/Prettier 自动处理，人不必纠结 |

**③ 如何写出好的 Review 意见**

```text
先说结论、再给理由、最后给建议：

✗ 「这里写得不对」            （没有信息量，让人无从下手）
✓ 「这个函数同时在改 state 和发请求，职责混在一起。建议拆成纯函数，
   副作用放外面，这样也能单独测试。」

区分「必须改」与「建议」：
- [blocking] 这个判断会漏掉 null 的情况，会抛错，需修复
- [nit] 建议换个变量名，非阻塞
- [question] 为什么这里用轮询而不是订阅？想了解背景而非挑错

对事不对人；肯定做得好的地方；一次说清而非反复来回。
```

**④ 自动化门禁（把机器能判的都交给机器）**

```yaml
# .github/workflows/ci.yml
name: CI
on: [pull_request]
jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20, cache: pnpm }
      - run: pnpm install --frozen-lockfile
      - run: pnpm lint
      - run: pnpm type-check
      - run: pnpm test -- --run --coverage
      - run: pnpm build
```

```text
CI 应拦住的：lint 错误、类型错误、单测失败、覆盖率低于阈值、
             构建失败、包体超预算、依赖漏洞（audit/dependabot）
人该看的：  设计是否合理、命名与抽象、测试是否有意义、是否有更简单的方案
```

**⑤ 合并策略**

| 策略 | 结果 | 适用 |
| --- | --- | --- |
| Merge commit | 保留全部提交 + 合并节点 | 想保留协作轨迹 |
| Squash merge | 把 PR 压成一个提交 | 迭代中提交琐碎、要求主干线性（**多数团队首选**） |
| Rebase merge | 把 PR 提交线性重放到主干 | 要求线性且想保留独立提交 |

**⑥ PR 描述模板**

```markdown
## 背景 / 目的
（为什么做这个改动，关联 issue：#123）

## 改动内容
- xxx
- xxx

## 验证方式
- [ ] 本地跑了 lint / type-check / 单测
- [ ] 手动验证了 xxx 场景

## 风险与回滚
- 风险：xxx
- 回滚：revert 本 PR 即可 / 需要回退数据迁移
```

**易错点：**

- **超大的 PR 是 review 的天敌**：控制在几百行内、单一主题，大改动拆成多个 PR 顺序合并。
- Review 不该纠结格式：把格式问题交给 lint/Prettier，人的注意力留给设计与正确性。
- 「PR 描述写一句『修了个 bug』」等于没写：Reviewer 无法判断上下文与验证方式。
- 合并后才发现 CI 门禁没生效（如 required checks 配错），等于没门禁。
- 用 `--force push` 覆盖已 review 的提交会让 diff 失效，应追加新提交。

## 13. 版本发布与 changelog 自动化

**核心前提：Conventional Commits + 语义化版本 + 自动生成 changelog。**

**① 原理链路**

```text
规范的提交信息（feat/fix/BREAKING CHANGE）
   │
   ├─ 解析：工具读取自上个 tag 以来的所有提交，按 type 分类
   │
   ├─ 计算版本号：
   │     fix/perf        → PATCH（1.2.3 → 1.2.4）
   │     feat            → MINOR（1.2.3 → 1.3.0）
   │     BREAKING CHANGE → MAJOR（1.2.3 → 2.0.0）
   │
   └─ 产出：更新 package.json 版本、生成/更新 CHANGELOG.md、打 git tag、发布
```

**② 方案对比：semantic-release vs changesets**

| 维度 | semantic-release | changesets |
| --- | --- | --- |
| 触发方式 | 每次 push 到发布分支自动推断版本并发布 | 开发者用命令**手动记录**变更意图（changeset） |
| 版本决定 | 全自动，从提交推断 | 半自动，由提交者指定 bump 类型与说明 |
| 适合场景 | 单一包、持续发布 | **Monorepo / 多包**，需要灵活控制各包版本 |
| changelog | 自动生成 | 发版时汇总各 changeset 生成 |
| 控制力 | 低（约定优先） | 高（可精确指定受影响包与类型） |
| 学习成本 | 低（配置好即可） | 中（需理解 changeset 工作流） |

**③ semantic-release 配置示例**

```json
// package.json
{
  "scripts": {
    "release": "semantic-release"
  },
  "devDependencies": {
    "semantic-release": "^24.0.0"
  }
}
```

```js
// release.config.js
export default {
  branches: ['main'],
  plugins: [
    '@semantic-release/commit-analyzer',   // 分析提交，决定版本号
    '@semantic-release/release-notes-generator', // 生成 release notes
    '@semantic-release/changelog',         // 写 CHANGELOG.md
    '@semantic-release/npm',               // 发布到 npm
    ['@semantic-release/git', {            // 提交回版本号与 changelog
      assets: ['package.json', 'CHANGELOG.md'],
      message: 'chore(release): ${nextRelease.version} [skip ci]',
    }],
    '@semantic-release/github',            // 创建 GitHub Release
  ],
};
```

```yaml
# 在 CI 上发布（提交信息规范是唯一前提）
- run: npx semantic-release
  env:
    GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
    NPM_TOKEN: ${{ secrets.NPM_TOKEN }}
```

**④ changesets 工作流（Monorepo 首选）**

```bash
# 1. 改完代码，记录一个 changeset
npx changeset
#   交互式选择：受影响的包 + bump 类型（patch/minor/major）+ 描述
#   生成 .changeset/xxx.md

# 2. 累积多个 changeset 后，进入「版本阶段」
npx changeset version   # 汇总所有 changeset，升版本号 + 生成 CHANGELOG

# 3. 发布
npx changeset publish
```

```markdown
<!-- .changeset/funny-cats-dance.md —— changeset 文件内容 -->
---
'@scope/ui': minor
'@scope/utils': patch
---

新增 Button 组件的 loading 态；修复 utils 的日期格式化在时区上的问题。
```

```json
// .changeset/config.json 关键字段
{
  "commit": false,
  "access": "public",
  "baseBranch": "main",
  "updateInternalDependencies": "patch",
  "ignore": []
}
```

**⑤ 版本与发布的关系速记**

```text
feat            → MINOR
fix / perf      → PATCH
BREAKING CHANGE → MAJOR
docs/style/refactor/test/build/ci/chore → 不发版（或仅进 changelog）
```

**易错点：**

- semantic-release **强依赖**规范的提交信息，历史提交不规范会导致版本判断错误或漏发。
- 自动提交回 `package.json`/`CHANGELOG.md` 时要加 `[skip ci]`，否则触发无限构建循环。
- changeset 的 bump 类型与提交 type 无关，它由**开发者显式指定**，别指望自动推断。
- Monorepo 里各包版本与依赖引用要同步升级（`updateInternalDependencies`），否则内部依赖会指向旧版本。
- 首次接入时，确保仓库已有 git tag（否则工具会从第一个提交算起，误判大版本）。

## 14. 前端质量保障体系包含哪些环节？

**质量保障**不是「上线前跑一次测试」，而是一条**贯穿开发到线上的闭环**，每个环节都有对应工具与门禁。

**① 全流程视角（按代码生命周期）**

| 阶段 | 目标 | 手段/工具 |
| --- | --- | --- |
| 编码 | 提前发现低级错误 | ESLint、Prettier、Stylelint、TypeScript（编辑器实时提示） |
| 提交 | 挡住不合规的本地改动 | Husky + lint-staged、commitlint |
| 构建 | 保证产物可用、类型正确 | `tsc --noEmit` / `vue-tsc`、构建成功门禁 |
| 测试 | 验证逻辑与流程正确 | 单元（Vitest/Jest）、集成、E2E（Playwright） |
| 集成（CI） | 自动化统一门禁 | lint + 类型 + 测试 + 覆盖率阈值 + 构建 |
| 评审（Review） | 人判断设计与正确性 | PR 流程、Code Review 规范、自动化检查 |
| 部署 | 小步、可回滚 | CD、灰度/金丝雀、特性开关 |
| 运行（线上） | 发现并定位真实问题 | Sentry 监控、埋点、告警、日志 |
| 反馈 | 持续改进 | 缺陷复盘、完善测试用例、补充 lint 规则 |

**② 分层模型（按「机器能判 vs 人判断」分）**

```text
┌──────────────────────────────────────────────────────────┐
│  静态层（Pre-commit / CI）                                  │
│  ESLint + Prettier + Stylelint + TypeScript —— 机器全自动    │
├──────────────────────────────────────────────────────────┤
│  测试层（CI）                                               │
│  单元 → 集成 → E2E，配合覆盖率阈值，作为构建门禁               │
├──────────────────────────────────────────────────────────┤
│  流程层（提交 → PR → 合并 → 发布）                            │
│  commitlint + Husky + Code Review + 分支保护 + 自动化发布      │
├──────────────────────────────────────────────────────────┤
│  运行层（线上兜底）                                          │
│  错误监控（Sentry）+ 性能监控 + 灰度发布 + 快速回滚            │
└──────────────────────────────────────────────────────────┘
```

**③ 门禁清单（一个健康的工程化仓库应具备）**

```text
本地：
  [x] 编辑器保存自动格式化（Prettier / EditorConfig）
  [x] 保存/提交时 lint 自动修复（ESLint --fix）
  [x] pre-commit 只检查暂存文件（lint-staged）
  [x] commit-msg 校验提交信息（commitlint）
  [x] pre-push 跑类型检查与关键测试（可选，成本高）

CI（合并前必须全绿）：
  [x] lint / stylelint
  [x] type-check（tsc/vue-tsc --noEmit）
  [x] 单元测试 + 覆盖率阈值
  [x] 构建产物成功
  [x] 依赖安全审计（audit / Dependabot）
  [x] 包体预算检查（可选）

发布：
  [x] 自动化版本号与 changelog（semantic-release / changesets）
  [x] 灰度 / 金丝雀 + 可一键回滚

线上：
  [x] 错误监控与告警（Sentry）
  [x] 性能指标采集（Web Vitals）
  [x] 缺陷复盘并补充回归测试
```

**④ 面试答题结构建议**

```text
先给一个总纲（贯穿「编码 → 提交 → 构建 → 测试 → 评审 → 部署 → 运行」）
再分层展开（静态检查 / 测试 / 流程 / 线上监控）
最后落到「门禁 + 闭环」：机器能自动判的都自动化，人只做机器做不了的判断，
且线上问题要能反向补充测试与规则，形成持续改进。
```

> 一句话总结：**质量保障 = 规范（约定）+ 自动化（工具与门禁）+ 监控（线上兜底）+ 反馈（持续改进）**。

**易错点：**

- 只做「上线前测试」，没有提交门禁与 CI，问题会大量堆到后期，修复成本成倍上升。
- 把 lint/格式化当质量核心：它们只挡风格与低级问题，**正确性靠测试，设计靠 Review**。
- 门禁配置了但没“required”，PR 挂了也能强合并，等于没有门禁。
- 只做静态检查不做线上监控：上线后的真实错误（接口异常、性能退化）无法及时发现。
- 质量项要与团队规模匹配：小团队先上 lint + CI + 单测，大团队再补 E2E、监控、灰度。
