## 1. 什么是前端工程化？

**前端工程化**是指：把软件工程的**方法与工具**引入前端开发，用**规范化、模块化、组件化、自动化**的手段，解决「开发效率、代码质量、团队协作、交付上线」这几类问题。

一句话概括：**把「手工作坊」变成「流水线生产」。**

**它要解决的问题与对应的手段：**

| 问题 | 手段 | 常见工具 |
| --- | --- | --- |
| 代码怎么组织 | 模块化、组件化 | ESM、Monorepo |
| 语法/资源浏览器不认 | 编译、构建 | Webpack、Vite、Babel、TypeScript |
| 依赖怎么装、怎么管 | 包管理 | npm、yarn、pnpm |
| 团队代码风格不一致 | 规范化 | ESLint、Prettier、Stylelint |
| 提交信息混乱 | 流程约束 | Husky、commitlint |
| 每次发版都靠手工 | 自动化 | CI/CD、GitHub Actions |
| 产物大、加载慢 | 构建优化 | Tree Shaking、代码分割、CDN |
| 上线出问题无法定位 | 监控 | Sentry、埋点 |

**四个核心维度（面试可按此结构作答）：**

1. **模块化/组件化**：解决「如何拆分与复用」。
2. **规范化**：解决「多人协作的一致性」（命名、目录、提交、代码风格）。
3. **自动化**：解决「重复劳动」（构建、测试、部署、发布）。
4. **性能与稳定性**：解决「用户体验与线上质量」（构建产物优化、监控、灰度）。

> 面试答题建议：先给定义，再按「模块化 → 规范化 → 自动化 → 性能/监控」四条线铺开，最后补一句「工程化的目标是提效、保质、可协作」。

## 2. 前端模块化规范有哪些？

| 规范 | 全称 | 运行环境 | 加载方式 | 是否静态 | 典型写法 |
| --- | --- | --- | --- | --- | --- |
| **CommonJS** | CommonJS | Node.js | 运行时同步 `require` | 否 | `const a = require('a')` |
| **AMD** | Asynchronous Module Definition | 浏览器 | 异步 `define`/`require` | 否 | `define(['a'], function (a) {})` |
| **CMD** | Common Module Definition | 浏览器（SeaJS） | 就近依赖、延迟执行 | 否 | `define(function (require) { require('a') })` |
| **UMD** | Universal Module Definition | 通用 | 运行时判断环境 | 否 | 兼容 CJS + AMD + 全局 |
| **ES Module** | ECMAScript Module | 浏览器 / Node（`.mjs`） | 静态 `import` | **是** | `import a from 'a'` |

**发展脉络：** 全局变量（`window.jQuery`）→ 命名空间 → IIFE → AMD/CMD → CommonJS（Node）→ **ES Module（统一标准）**。

```js
// AMD：依赖前置，异步加载
define(['./a', './b'], function (a, b) {
    return { sum: a.value + b.value };
});

// CMD：就近依赖，用到才加载（SeaJS）
define(function (require, exports, module) {
    const a = require('./a'); // 执行到这一行才加载
    module.exports = { value: a.value };
});

// UMD：打包库时常用，兼容三种环境
(function (root, factory) {
    if (typeof define === 'function' && define.amd) {
        define(['b'], factory);
    } else if (typeof module === 'object' && module.exports) {
        module.exports = factory(require('b'));
    } else {
        root.myLib = factory(root.b);
    }
})(typeof self !== 'undefined' ? self : this, function (b) {
    return { value: b.value };
});
```

**ESM 的两个硬性特征（面试重点）：**

- **静态结构**：`import`/`export` 只能出现在顶层，不能在 `if` 里动态引入，所以构建工具能在**编译期**分析出依赖图。
- **实时绑定（live binding）**：导入的是「变量的引用」而非值的拷贝，导出方变了，导入方也变。

> 现状：浏览器与 Node 都已原生支持 ESM；AMD/CMD 基本退出历史舞台，只在老项目或某些库的 UMD 产物中见到。

## 3. CommonJS 与 ES Module 的区别？

| 维度 | CommonJS | ES Module |
| --- | --- | --- |
| 语法 | `require` / `module.exports` | `import` / `export` |
| 加载时机 | **运行时**（代码执行到才加载） | **编译时**确定依赖，运行时求值 |
| 加载方式 | 同步加载 | 异步加载（浏览器）/ 先解析再求值 |
| 导出内容 | **值的拷贝**（对象快照） | **值的引用**（live binding 实时绑定） |
| 能否 Tree Shaking | 不能 | 能 |
| 顶层 `this` | `module.exports` | `undefined` |
| 顶层 `await` | 不支持 | 支持（Top-level await） |
| 动态导入 | 天然支持（`require` 可写在任意处） | 需 `await import()` |
| 扩展名 | `.js` / `.cjs` | `.mjs` / `"type": "module"` |
| 循环依赖 | 返回**未完成**的导出对象 | 靠提升与实时绑定，更可控 |

**1）值拷贝 vs 实时绑定（最经典的对比）**

```js
// ---------- CommonJS ----------
// counter.js
let count = 0;
const add = () => { count++; };
module.exports = { count, add };

// main.js
const { count, add } = require('./counter');
add();
console.log(count); // 0 ← 拿到的是快照，不会跟着变

// ---------- ES Module ----------
// counter.mjs
export let count = 0;
export const add = () => { count++; };

// main.mjs
import { count, add } from './counter.mjs';
add();
console.log(count); // 1 ← 实时绑定，能读到最新值
```

> 注意：ESM 中导入的变量是**只读视图**，直接 `count = 10` 会报错；只能用导出方提供的方法去改。

**2）动态性对比**

```js
// CJS 可以做条件引入
if (process.env.NODE_ENV === 'development') {
    require('./devtools');
}

// ESM 静态导入不行，但可以用动态 import()
if (import.meta.env.DEV) {
    const mod = await import('./devtools');
}
```

**3）互相引用时的现实问题**

- 用打包器时：`ESM 文件` 可以 `import` 一个 CJS 文件（构建工具会做转换，默认导出通常映射为 `module.exports`）。
- 在 Node 中：CJS 可以通过 `require()` 加载 ESM 吗？**Node 22 起支持 `require(esm)`**（要求该 ESM 无顶层 await）；早期版本会报 `ERR_REQUIRE_ESM`。
- 反向：ESM 里 `import` CJS 时，默认导入拿到 `module.exports`，具名导入依赖 Node 的静态分析（cjs-module-lexer），**不一定成功**。

**易错点：**

- `type: "module"` 后，`.js` 文件会以 ESM 解析，项目里老代码可能直接报 `require is not defined`。
- ESM 中不能使用 `__dirname` / `__filename`（需用 `import.meta.url` 转换）。
- CJS 的 `require` 会**缓存**结果，重复 `require` 拿到同一个对象引用。

## 4. 为什么 ESM 能 Tree Shaking 而 CommonJS 不行？

**Tree Shaking**（摇树）指在打包时**删除没有被用到的导出代码**，减小产物体积。

**核心原因：ESM 的依赖关系是「静态可分析」的。**

| 条件 | ESM | CommonJS |
| --- | --- | --- |
| 导入导出位置 | 必须顶层，语法固定 | `require` 是普通函数调用，可写在任意位置 |
| 导入名称 | 编译期就能确定是哪个名字 | 常写成 `const _ = require('./utils')`，用哪个属性要运行时才知道 |
| 值的性质 | 引用绑定，可追踪 | 对象属性访问，可能被动态改写 |
| 结论 | 能标记未使用导出并安全删除 | 无法静态确定，只能保守全保留 |

```js
// utils.js —— ESM：只有 add 被引用，minus 可被摇掉
export const add = (a, b) => a + b;
export const minus = (a, b) => a - b;

// main.js
import { add } from './utils';
console.log(add(1, 2));

// ---------- 同样功能用 CJS ----------
// utils.js
exports.add = (a, b) => a + b;
exports.minus = (a, b) => a - b;

// main.js —— 打包器无法确定你到底用不用 minus
const utils = require('./utils');
console.log(utils.add(1, 2));
```

**光用 ESM 还不够，还要满足：**

1. 打包器支持并开启（`mode: 'production'`，或用 Vite/Rollup 默认开启）。
2. `package.json` 的 `sideEffects` 声明，告诉打包器「哪些文件有副作用不能删」。

```json
{
  "sideEffects": false
}
```

```json
{
  "sideEffects": ["*.css", "./src/polyfill.js"]
}
```

> 反面理解：`sideEffects: false` 表示「这个包里所有模块删除后都不影响外部行为」，打包器才敢删未使用模块；若包里有「导入即注册」的代码（如 `import './reset.css'`、`import './polyfill'`），必须显式列出，否则会被误删。

**易错点：**

- 只写 `exports.add = ...` 的库无法让使用者摇树（CJS 产物）——所以现在库一般会同时提供 `module` / `exports.import` 指向 ESM 产物。
- 类的静态方法/未使用的类字段也可能被保留，因为无法确定是否有反射式调用。
- 摇树只对「库的导出」有效，业务代码里的死代码主要靠压缩器（Terser/esbuild）消除。

## 5. ESM 的加载过程

ESM 的加载分为**三个阶段**，这是理解「为什么 ESM 支持循环依赖」和「为什么 `import` 有提升」的关键。

**① 构造（Construction）—— 解析模块，生成模块记录**

- 根据入口文件递归解析 `import` 语句，找到每个模块的 URL（浏览器需发请求下载）。
- 每个模块生成一个 **Module Record**，记录导入项、导出项、代码。
- 最终形成一颗**模块依赖图（Module Graph）**。
- 这个阶段**不执行任何代码**。

**② 实例化（Instantiation）—— 建立绑定**

- 为所有模块创建「环境记录」，把每个导出**绑定到内存中的位置（binding）**。
- 处理 `import`：让导入方的标识符**指向导出方的位置**（而不是复制值）→ 这就是 live binding 的由来。
- 此时函数声明已被提升，但函数体、`const`/`let` 都**尚未执行/初始化**（暂时处于 TDZ）。

**③ 求值（Evaluation）—— 执行代码**

- 从叶节点开始，**深度优先、后序遍历**模块图依次执行模块体（依赖先执行）。
- 执行过程中填充各绑定的值；有 Top-level await 的模块会让求值变为异步。

```js
// 观察执行顺序（Node 中 node main.mjs）
// a.mjs
console.log('a 开始');
// b.mjs
console.log('b 开始');
// main.mjs
import './a.mjs';
import './b.mjs';
console.log('main 结束');
// 输出：a 开始 → b 开始 → main 结束（依赖先执行）
```

**与 CommonJS 的对比：** CJS 是「加载 → 执行 → 返回 `module.exports`」一步到位，同步且边加载边执行；ESM 是「先全部解析完 → 再建立绑定 → 最后才执行」，因此能做到**静态分析**。

**易错点：**

- `import` 会被**提升**到模块顶部执行（先于同位置的普通语句），因此 `console.log` 在 import 之前也无效。
- 导出 `const` 在 TDZ 期间被访问会抛 `ReferenceError`（和 `let` 一致）。

## 6. 循环依赖怎么处理？

**循环依赖**：A 依赖 B，B 又依赖 A，形成环。

**① CommonJS 下的表现：拿到「不完整的导出对象」**

```js
// a.js
exports.done = false;
const b = require('./b.js');   // 此时 b 还没执行完 a，拿到的是 a 的半成品
console.log('在 a 中，b.done =', b.done);
exports.done = true;           // 赋值发生在 require 之后
console.log('a 执行完毕');

// b.js
exports.done = false;
const a = require('./a.js');   // a 未执行完，a.done 还是 false
console.log('在 b 中，a.done =', a.done);
exports.done = true;
console.log('b 执行完毕');

// main.js
require('./a.js');
// 输出：
// 在 b 中，a.done = false
// 在 a 中，b.done = true
// b 执行完毕
// a 执行完毕
```

原理：CJS 的 `require` 遇到「正在加载中」的模块，会**直接返回当前已构建的部分 `module.exports`**（内存中已存在的对象引用），而不是等待执行完成。所以后执行的模块拿到的是**半成品**，可能出现 `undefined`。

**② ESM 下的表现：靠实时绑定 + 提升「存活」**

```js
// a.mjs
import { b } from './b.mjs';
export const a = 'a';
console.log('a 中读到 b =', b);   // 若 b 是 function 声明则可用；const 未初始化会报错

// b.mjs
import { a } from './a.mjs';
export const b = 'b';
```

因为绑定在**实例化阶段**就建立好了，只要不在 TDZ 期间访问，就能拿到最终值；但**函数声明会被提升**，所以循环依赖中「互相调用函数」通常能正常工作，而「互相读取 `const` 变量」容易踩 TDZ 报错。

```js
// 常见可用形态：互相调用函数
// a.mjs
import { fromB } from './b.mjs';
export function fromA() { return 'A'; }
export function callB() { return fromB(); }

// b.mjs
import { fromA } from './a.mjs';
export function fromB() { return 'B' + fromA(); }
```

**③ 如何避免/解决：**

1. **重构依赖方向**：抽出公共模块 C，让 A、B 都依赖 C（最根本的方案）。
2. **延迟引入**：CJS 中使用「函数内 `require`」；ESM 中使用动态 `import()`。
3. **只依赖类型/接口**：TS 中 `import type` 不产生运行时依赖。
4. **注意副作用顺序**：把「执行代码」从模块顶层挪进函数，避免加载期互相调用。

**易错点：**

- 循环依赖往往是「功能能跑但偶发 `undefined`」的隐形炸弹，配合 `madge --circular`、ESLint `import/no-cycle` 可以检测。
- 打包器处理循环依赖时结果可能与 Node 不完全一致，不要依赖其「恰好能跑通」。

## 7. npm、yarn、pnpm 的区别？

| 维度 | npm | yarn（v1 Classic） | pnpm |
| --- | --- | --- | --- |
| 出现时间 | 2010（Node 自带） | 2016（Facebook） | 2017 |
| `node_modules` 结构 | 提升/扁平化 | 提升/扁平化 | **符号链接 + 全局 store** |
| 重复依赖存储 | 每个项目独立拷贝 | 每个项目独立拷贝 | **全局内容寻址存储，硬链接复用** |
| 安装速度 | 较慢 | 较快（并行） | **快**（复用 + 硬链接） |
| 磁盘占用 | 大 | 大 | **小**（同一版本只存一份） |
| 幽灵依赖 | **有** | **有** | **没有**（严格依赖） |
| lock 文件 | `package-lock.json` | `yarn.lock` | `pnpm-lock.yaml` |
| Monorepo 支持 | workspaces | workspaces | **workspaces（最完善）** |
| 默认严格性 | 宽松 | 宽松 | **严格（不开 hoist）** |

```bash
# 常用命令对照
npm install            # yarn            # pnpm install
npm install axios      # yarn add axios  # pnpm add axios
npm install -D vite    # yarn add -D     # pnpm add -D vite
npm uninstall axios    # yarn remove     # pnpm remove axios
npm run build          # yarn build      # pnpm build
npm ci                 # yarn install --frozen-lockfile  # pnpm install --frozen-lockfile
```

**选型建议：**

- **新项目首选 pnpm**：省磁盘、装得快、依赖严格（能提前暴露「幽灵依赖」问题）、Monorepo 体验最好。
- **老项目/CI 环境已固化**：跟随现有 lock 文件，不要随意切换包管理器（切换会重建 lock，可能引入版本漂移）。
- **yarn 的现代版本（v2+/Berry）** 走 PnP（Plug'n'Play，不生成 `node_modules`），生态兼容性需评估，多数团队仍停留在 v1 或已迁到 pnpm。

**易错点：**

- **同一个仓库只用一个包管理器**：混用会产生两份 lock 文件，导致依赖版本不一致（可在 `preinstall` 里用 `only-allow` 强制）。
- 用 `npm i` 而不是 `npm ci` 装 CI 依赖，会**改写 lock 文件**，破坏可复现性。
- pnpm 下 `node_modules` 里看到的多是软链接，`rm -rf node_modules` 不会删掉全局 store（这是特性，不是 bug）。

## 8. 什么是幽灵依赖与依赖提升？

**依赖提升（hoisting）**：npm/yarn 为了让「子依赖能被找到」，会把依赖尽可能**平铺到 `node_modules` 根目录**。如果版本冲突，才把冲突的版本嵌套进该依赖自己的 `node_modules`。

**幽灵依赖（phantom dependency）**：你的项目**没有在 `package.json` 声明**某个包，却因为「依赖提升」把它平铺到了根目录，于是你在代码里能 `import` 到它——本质是**在依赖别人没有承诺的东西**。

```js
// package.json 里只声明了 one-package
// one-package 内部依赖 lodash
import _ from 'lodash';        // 运行正常！
// 但根目录能访问 lodash 只是「提升」的副作用
```

```text
// npm/yarn 提升后的 node_modules 结构
node_modules/
├── one-package/          ← 你声明的
└── lodash/               ← 你没声明，却被提升上来了（幽灵依赖）
```

**危害：**

1. **版本漂移**：`one-package` 哪天升级/换掉 lodash 版本，你的代码可能直接崩。
2. **升级即报错**：某次重装依赖后 lodash 不再被提升，构建突然失败，且很难定位。
3. **隐性耦合**：团队成员原地开发没问题，换台机器/换 CI 就挂。

**pnpm 的做法：**

```text
node_modules/
├── .pnpm/                ← 所有依赖的真实存放地（含嵌套结构）
│   ├── lodash@4.17.21/node_modules/lodash
│   └── one-package@1.0.0/node_modules/
│       ├── one-package
│       └── lodash  → 软链到 ../../lodash@4.17.21/node_modules/lodash
└── one-package  → 软链到 .pnpm/one-package@1.0.0/node_modules/one-package
    (lodash 不会出现在顶层，所以 import 'lodash' 直接报错)
```

只有 `package.json` 里**显式声明**的依赖才会被链接到顶层 `node_modules`，未声明的无法解析 → **把问题提前暴露，而不是上线才炸**。

**如果确实需要临时放宽：**

```ini
# .npmrc：允许把某些包提升到根目录（不推荐，仅迁移期过渡）
public-hoist-pattern[]=*lodash*
shamefully-hoist=true
```

**易错点：**

- 「项目里能跑」不代表依赖声明正确；可通过 `npx depcheck` 扫描「已声明未使用」与「已使用未声明」的依赖。
- 从 npm/yarn 迁移到 pnpm 时，最常见的报错就是补全这些幽灵依赖。

## 9. pnpm 的原理

pnpm 之所以又快又省空间，依赖三样东西：**内容寻址存储（store）+ 硬链接（hard link）+ 符号链接（symlink）**。

**① 全局内容寻址存储（Content-Addressable Store）**

- 所有依赖包的文件按**内容哈希**存放在全局 store（如 `~/.pnpm-store/v3`）。
- 同一个版本的文件在磁盘上**只存一份**，多个项目共享。
- 曾出现过的「同一文件内容」也会被去重（相同内容 → 同一哈希 → 同一文件）。

**② 硬链接到虚拟目录 `.pnpm`**

- 安装时先把包「硬链接」到项目的 `node_modules/.pnpm/<name>@<version>/node_modules/<name>`。
- 硬链接不复制文件内容，只增加一个目录项（inode 复用），**几乎不占额外空间、也不耗时**。

**③ 符号链接组织依赖树**

- `node_modules/` 顶层只放 `package.json` 声明的依赖，且都是**软链接**，指向 `.pnpm` 中的真实位置。
- `.pnpm` 内部按「谁依赖谁」建立软链，形成**非扁平的、严格的依赖树**。

```text
node_modules/
├── .pnpm/
│   ├── lodash@4.17.21/node_modules/lodash/(硬链接→store)
│   └── axios@1.7.0/node_modules/
│       ├── axios/(硬链接→store)
│       └── follow-redirects → ../../follow-redirects@1.15.6/node_modules/follow-redirects
└── axios → .pnpm/axios@1.7.0/node_modules/axios   (软链接)
```

**带来的收益：**

| 收益 | 说明 |
| --- | --- |
| 省磁盘 | 同一版本全局只存一份，硬链接复用 |
| 装得快 | 本地已有内容直接链接，无需重新下载/解压 |
| 依赖严格 | 未声明的依赖无法访问，避免幽灵依赖 |
| 无版本冲突 | 每个包只看到「自己声明的版本」，不再靠目录层级抢占 |
| 支持 Monorepo | workspace 间用软链互相引用，天然支持增量 |

**其他要点：**

- `pnpm-lock.yaml` 记录精确版本与依赖关系；`--frozen-lockfile`（CI 默认）禁止改写 lock。
- store 是跨项目、跨版本的，可以安全地删掉项目的 `node_modules` 而不影响 store。

**易错点：**

- **硬链接的局限**：跨文件系统（不同磁盘分区）无法硬链接，此时 pnpm 会退化为复制，失去部分收益。
- 某些老工具不解析软链接（如部分 IDE 索引、`jest` 默认配置），需 `node-linker=hoisted` 或加配置。
- 看到 `node_modules` 里全是箭头别慌，这是正常结构。

## 10. package.json 中的版本号与 semver

**语义化版本（Semantic Versioning）**：`MAJOR.MINOR.PATCH`，即 `主版本.次版本.修订号`。

| 位置 | 含义 | 变化时机 |
| --- | --- | --- |
| MAJOR | 主版本 | **不兼容**的 API 变更 |
| MINOR | 次版本 | 向后兼容的**功能新增** |
| PATCH | 修订号 | 向后兼容的**问题修复** |

**常见范围符号：**

| 写法 | 允许的更新范围 | 含义 |
| --- | --- | --- |
| `1.2.3` | 只装 `1.2.3` | 精确锁定 |
| `~1.2.3` | `>=1.2.3 <1.3.0` | 只允许 PATCH 升级 |
| `^1.2.3` | `>=1.2.3 <2.0.0` | 允许 MINOR/PATCH 升级（默认） |
| `^0.2.3` | `>=0.2.3 <0.3.0` | **0.x 版本视为不稳定**，`^` 只锁 MINOR |
| `1.x` / `1.*` | `>=1.0.0 <2.0.0` | 等价于 `^1.0.0` |
| `*` / `latest` | 任意版本 | 危险，禁止用于生产依赖 |
| `>=1.2.3` | 大于等于 | 不设上限，危险 |

```json
{
  "dependencies": {
    "vue": "^3.4.0",
    "lodash-es": "~4.17.21",
    "some-lib": "1.0.0"
  }
}
```

**`dependencies` / `devDependencies` / `peerDependencies`：**

| 字段 | 用途 | 是否随包安装 |
| --- | --- | --- |
| `dependencies` | 运行时需要 | 是 |
| `devDependencies` | 仅开发/构建/测试需要 | 否（作为依赖被安装时不装） |
| `peerDependencies` | 宿主环境应提供的（如插件要求 `vue`） | 由使用者提供 |
| `optionalDependencies` | 可选依赖，装失败不报错 | 尝试安装 |

**预发布版本：** `1.0.0-alpha.1` < `1.0.0-beta.1` < `1.0.0-rc.1` < `1.0.0`。标识符按「数字按数值比较、字符串按字典序」排序，因此 `1.0.0-alpha.10 > 1.0.0-alpha.9`。

**易错点：**

- `^` 在 `0.x` 下**不是**升 MINOR，而是升 PATCH（`^0.2.3` → `<0.3.0`），很多人答错。
- 版本范围只影响「能否装上」，实际装到哪个版本以 **lock 文件**为准。
- `peerDependencies` 在 npm 7+ 会**自动安装**，容易造成「重复的 vue 实例」等隐性问题，库作者应写清 `peerDependenciesMeta`。

## 11. lock 文件的作用是什么？

lock 文件（`package-lock.json` / `yarn.lock` / `pnpm-lock.yaml`）记录了**本次安装最终确定的完整依赖树**，包括：

1. **每个依赖的精确版本**（不是 `^1.2.3` 这种范围）。
2. **依赖之间的层级关系**（谁依赖谁、谁被提升到哪一层）。
3. **完整性校验值（integrity hash）**，防止包内容被篡改。

**为什么必须提交到 Git：**

| 作用 | 说明 |
| --- | --- |
| 可复现安装 | 团队/CI/生产装出的依赖树**完全一致**，消除「我这儿能跑」 |
| 规避版本漂移 | 上游发布新版本不会影响你（因为版本已锁定） |
| 安全校验 | `integrity` 校验包内容哈希，防供应链篡改 |
| 加速安装 | 已解析好的树，跳过版本求解 |

```bash
# CI 中应使用「只按 lock 安装、禁止改写」
npm ci
# 或
pnpm install --frozen-lockfile
```

**`npm ci` 与 `npm install` 的区别：**

| | `npm install` | `npm ci` |
| --- | --- | --- |
| 读取 lock | 会更新 lock | **严格按 lock 安装，不一致直接失败** |
| node_modules | 增量更新 | **先整体删除再安装** |
| 速度 | 较慢 | 快 |
| 适用 | 本地开发 | **CI / 发布环境** |

**易错点：**

- lock 文件冲突时**不要手改、不要删了重装**：应以某一侧为准重装，或在 Git 中选一侧后运行安装命令重新生成。
- 只在 `.gitignore` 忽略 lock（尤其 npm 时代的库项目）会导致下游使用者的依赖树不确定；**应用项目必须提交 lock，库项目也建议提交**。
- 改了 `package.json` 后忘记安装，lock 与实际不一致 → `npm ci` 直接报错。

## 12. npm run 与 npx、生命周期脚本

**① `npm run` 的本质**

- `npm run xxx` 会执行 `package.json` 中 `scripts.xxx` 对应的 shell 命令。
- 执行前会把 `node_modules/.bin` **临时加入 `PATH`**，所以脚本里可以直接写 `vite`、`eslint`，无需 `./node_modules/.bin/vite`。

```json
{
  "scripts": {
    "dev": "vite",
    "build": "vue-tsc --noEmit && vite build",
    "lint": "eslint . --fix",
    "commit": "cz"
  }
}
```

**② 生命周期钩子（按执行顺序）**

| 时机 | 钩子 |
| --- | --- |
| 安装前 | `preinstall` |
| 安装后 | `install` → `postinstall` |
| 发布前 | `prepublish` / `prepublishOnly` / `prepack` |
| 发布后 | `postpublish` |
| 运行脚本前后 | `pre<script>` → `post<script>`（如 `predev`、`postbuild`） |

```json
{
  "scripts": {
    "predev": "node scripts/check-env.js",
    "dev": "vite",
    "postbuild": "node scripts/upload-cdn.js"
  }
}
```

**③ `npx` 是什么**

- `npx xxx` 会**先在本地 `node_modules/.bin` 查找**，找不到再临时下载并执行（执行完即弃），避免全局安装污染。
- 适合一次性工具：`npx depcheck`、`npx create-vite@latest`。

```bash
npx create-vite my-app        # 创建项目
npx depcheck                  # 扫描无用/未声明依赖
npx only-allow pnpm           # 强制使用 pnpm（放在 preinstall）
```

**④ 常用命令补充**

```bash
npm run              # 列出所有可用脚本（不带参数）
npm run dev -- --port 8080   # -- 之后的参数透传给脚本
npm pkg set scripts.dev=vite # 直接改 package.json 字段
npm version patch -m "chore: release"   # 升版本号并打 tag
```

**易错点：**

- `npm run dev --port 8080` 参数会丢，必须写成 `npm run dev -- --port 8080`。
- `npm run` 无参数只列脚本，**不会执行**任何内容（与 `npm run nonexistent` 报错要区分）。
- 钩子脚本在 CI 安装时也会跑，若有副作用（改文件、上传）要注意 `--ignore-scripts`。

## 13. 什么是 Monorepo？

**Monorepo（单一仓库）**：把多个项目/包放在**同一个 Git 仓库**中管理；相对的 **Multirepo** 是每个包一个仓库。

| 维度 | Monorepo | Multirepo |
| --- | --- | --- |
| 代码复用 | 直接引用，改完立即生效 | 需发版、装包才能用 |
| 依赖管理 | 统一版本，可强制一致 | 各仓库独立，容易版本分裂 |
| 原子提交 | 一次 commit 改多个包 | 需跨仓库协调 |
| 工具链 | 统一配置（lint/build/test） | 各仓库重复配置 |
| 权限控制 | **粒度粗**（整个仓库） | 细（仓库级） |
| CI 成本 | 需要「只构建受影响的包」（增量） | 天然隔离 |
| 仓库体积 | 大，克隆慢 | 小 |

**主流工具：**

| 工具 | 定位 |
| --- | --- |
| **pnpm workspaces** | 提供 workspace 软链与依赖管理（基础能力） |
| **Turborepo** | 任务编排 + 缓存（配置少，Go 实现，快） |
| **Nx** | 全功能：任务图、插件生态、代码生成、影响分析（重） |
| **Lerna** | 老牌发布工具，v7 起已交由 Nx 驱动 |

**pnpm workspaces 示例：**

```yaml
# pnpm-workspace.yaml
packages:
  - 'packages/*'
  - 'apps/*'
```

```json
// 根 package.json
{
  "name": "my-monorepo",
  "private": true,
  "scripts": {
    "build": "pnpm -r --filter ./packages/* build",
    "dev": "pnpm --filter web dev"
  },
  "devDependencies": {
    "typescript": "^5.5.0"
  }
}
```

```text
my-monorepo/
├── pnpm-workspace.yaml
├── package.json
├── packages/
│   ├── ui/            (@scope/ui)
│   └── utils/         (@scope/utils)
└── apps/
    └── web/           (依赖 @scope/ui，通过 workspace:* 软链)
```

```json
// apps/web/package.json —— 用 workspace: 协议引用本地包
{
  "dependencies": {
    "@scope/ui": "workspace:*",
    "@scope/utils": "workspace:*"
  }
}
```

**关键概念：`workspace:*` 协议**

- 本地开发时软链到源码目录，**改完即时生效**，无需发版。
- 发布时 pnpm 会自动把 `workspace:*` 替换成实际版本号（如 `^1.2.3`），保证发布出去可用。

**Turborepo 的任务流水线：**

```json
// turbo.json
{
  "tasks": {
    "build": {
      "dependsOn": ["^build"],   // 先构建依赖的包
      "outputs": ["dist/**"]
    },
    "test": { "dependsOn": ["build"] }
  }
}
```

```bash
turbo run build   # 按依赖拓扑执行，并命中本地/远程缓存
```

**易错点：**

- Monorepo 的最大成本是 **CI 与权限**：必须支持「只对受影响的包执行任务」，否则每次改一行都要全量构建。
- 依赖版本应尽量在根统一（用 `pnpm.overrides` 强制），否则各包版本分裂，打包会重复引入。
- 不要把无关项目硬塞进一个仓库；Monorepo 适合**强关联、需要频繁同步改动**的包集合。

## 14. 如何发布自己的 npm 包？

**① 必要字段**

```json
{
  "name": "@your-scope/my-lib",
  "version": "0.1.0",
  "description": "一句话描述",
  "type": "module",
  "main": "./dist/index.cjs",
  "module": "./dist/index.mjs",
  "types": "./dist/index.d.ts",
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.mjs",
      "require": "./dist/index.cjs"
    },
    "./style.css": "./dist/style.css"
  },
  "files": ["dist", "README.md"],
  "sideEffects": false,
  "peerDependencies": {
    "vue": "^3.3.0"
  },
  "publishConfig": {
    "registry": "https://registry.npmjs.org/"
  }
}
```

| 字段 | 作用 |
| --- | --- |
| `name` | 包名；带 `@scope/` 表示作用域包（默认私有） |
| `main`/`module`/`types` | 老工具的入口约定（CJS / ESM / 类型） |
| `exports` | **现代入口映射**，可按 `import`/`require`/`types` 分流，还支持子路径 |
| `files` | **白名单**：只发布列出的文件/目录（比 `.npmignore` 更安全） |
| `sideEffects` | 声明是否有副作用，决定使用者能否 Tree Shaking |
| `peerDependencies` | 声明宿主依赖，避免重复实例 |
| `publishConfig` | 指定发布源（如私有 registry、`access: public`） |

> 注意：`files` 是白名单，`.npmignore` 是黑名单；两者同时存在时 `files` 优先。**推荐 `files`**，避免把测试、源码、`.env` 误发出去。

**② 发布流程**

```bash
# 1. 登录（首次）
npm login

# 2. 构建产物（务必在发布前执行）
npm run build

# 3. 本地自测：打包出 tarball 看内容对不对
npm pack --dry-run

# 4. 升版本（自动改 package.json 并打 git tag）
npm version patch    # 或 minor / major

# 5. 发布
npm publish --access public
```

**③ 私有源与其他要点**

```bash
# 发布到私有 registry
npm publish --registry https://your-registry.com/

# 用 .npmrc 固化 registry
echo "registry=https://your-registry.com/" > .npmrc
```

- **版本号一经发布不可覆盖**（同版本重复发布会报错），撤销需 `npm unpublish`（有 24 小时限制，且已下载的无法收回），正确姿势是**发新版本**。
- 使用 **`dist-tags`** 管理预发布：

```bash
npm publish --tag beta      # 发到 beta 标签，不影响 latest
npm install my-lib@beta     # 使用者按 tag 安装
```

**④ CI 自动发布（用 Token 而非密码）**

```yaml
# .github/workflows/publish.yml
name: Publish
on:
  push:
    tags: ['v*']
jobs:
  publish:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      id-token: write      # 用于 npm provenance（可信发布）
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          registry-url: https://registry.npmjs.org
      - run: npm ci
      - run: npm run build
      - run: npm publish --provenance --access public
        env:
          NODE_AUTH_TOKEN: ${{ secrets.NPM_TOKEN }}
```

**易错点：**

- `files` 漏写 `README.md`、`LICENSE` 会导致页面信息缺失（这两个文件默认总会发布，其余需显式声明）。
- 未配置 `exports` 时，`import` 与 `require` 混用会踩「入口不一致」的坑；要保证 ESM/CJS 双产物齐全且 `types` 正确。
- 未声明 `peerDependencies` 而直接打包进 `dependencies`，会导致使用者的框架出现**多实例**（如两个 Vue、两个 React），引发 `inject`/hooks 报错。
- 发布前务必跑 `npm pack --dry-run` 检查内容，避免把源码、测试、密钥一起发出去。
