## 1. Tree Shaking 是什么？为什么没生效？

**Tree Shaking（摇树优化）**：打包时根据「谁被真正引用」的关系，**删除模块中没有被用到的导出代码**，从而减小产物体积。

名字来自「摇树，把枯叶（无用代码）抖落」。它最早由 **Rollup** 提出并实现，后成为 Webpack、Vite（Rollup）、esbuild 的通用能力。

**它的原理分三步：**

1. **建图**：从入口出发，依据**静态的 `import`/`export`** 递归解析出模块依赖图。
2. **标记（mark）**：分析每个模块的导出是否被其他模块引用，标记「已使用 / 未使用」。
3. **删除（shake）**：把未被引用的导出及相关代码整段移除；最后交给压缩器（Terser / esbuild）做第二轮消除。

**与「死代码消除（DCE）」的区别：**

| 维度 | Tree Shaking | 死代码消除（DCE） |
| --- | --- | --- |
| 作用对象 | **模块之间**未被引用的导出 | **函数内部**不可达的代码 |
| 依据 | 静态 `import`/`export` 关系 | 控制流分析（如 `if (false)`、`return` 之后的代码） |
| 执行者 | Rollup / Webpack / Vite | Terser / esbuild / SWC |
| 范围 | 跨文件（跨模块） | 单文件（单作用域） |

> 两者是**互补**的：Tree Shaking 先删掉整块未使用的导出，压缩器再在剩下的代码里做局部死代码消除。

**Tree Shaking 生效的最小条件：**

```js
// utils.js —— 必须是 ESM：导出可被静态分析
export const add = (a, b) => a + b;
export const minus = (a, b) => a - b;
export const multiply = (a, b) => a * b;

// main.js —— 只用了 add，minus / multiply 应被摇掉
import { add } from './utils.js';
console.log(add(1, 2));
```

**为什么没生效？排查清单（面试高频）：**

| 排查项 | 典型现象 | 解决方式 |
| --- | --- | --- |
| 产物不是 ESM（CJS / UMD） | 整个包全部被保留 | 库提供 `module` / `exports.import` 指向 ESM 产物 |
| Babel 把 ESM 转成了 CJS | `import` 变成 `require`，静态分析失效 | `@babel/preset-env` 设 `modules: false` |
| 未开启压缩 / minifier | 代码被标记但没被删除 | 用 `mode: 'production'`，确保 Terser/esbuild 开启 |
| 代码存在副作用 | 删除会改变行为，工具不敢删 | 把副作用代码抽离或在 `sideEffects` 中显式声明 |
| `sideEffects` 误设为 `false` | 有副作用的文件被误删（bug） | 精确列出有副作用的文件 |
| 使用了命名空间导入 / 动态属性访问 | 无法确定用到哪些属性 | 改为具名导入 |
| 编译器无法识别库 | `export 'xxx' was not found` 只能保守保留 | 梳理 `exports` 入口映射 |

**① 关键配置一：让 Babel 保留 ESM 语法**

```js
// babel.config.js
module.exports = {
  presets: [
    // modules: false 表示「不要把 import/export 转成 CJS」，保留给打包器做摇树
    ['@babel/preset-env', { modules: false }]
  ]
};
```

如果用 `tsc` 编译，同理要把 `module` 设为 `ESNext`（而不是 `CommonJS`）：

```json
// tsconfig.json
{
  "compilerOptions": {
    "module": "ESNext",
    "target": "ES2020"
  }
}
```

**② 关键配置二：声明 `sideEffects`**

```json
// 库的 package.json —— 声明本包所有模块都无副作用，可放心摇树
{
  "name": "@scope/pure-lib",
  "sideEffects": false,
  "module": "./dist/index.mjs",
  "exports": {
    ".": { "import": "./dist/index.mjs", "require": "./dist/index.cjs" }
  }
}
```

```json
// 有副作用的包 —— 白名单方式，只有列出的文件算「有副作用」
{
  "sideEffects": ["*.css", "./src/polyfill.js", "./src/register.js"]
}
```

```js
// 反面案例：包里有「导入即执行副作用」的代码
import './reset.css';          // 有副作用：插入样式
import './tracker';            // 有副作用：上报注册
// 若 sideEffects 写成 false，这两行会被当成无用代码删除 → 页面样式丢失 / 埋点失效
```

**③ 关键配置三：标记纯函数（PURE 注释）**

当工具无法判断某个函数调用是否「纯」时，会保守保留。可用魔法注释告诉它「这次调用没有副作用，返回值没用就可以删」：

```js
// 通过 /*#__PURE__*/ 标注：若返回值未被使用，则整个调用可被删除
const style = /*#__PURE__*/ makeStyleObject({ color: 'red' });
```

**④ Webpack / Vite 中开启摇树的开关**

```js
// webpack.config.js（Webpack 5 生产模式默认已开启，可显式确认）
module.exports = {
  mode: 'production',
  optimization: {
    usedExports: true,       // 标记哪些导出被使用（摇树的核心）
    providedExports: true,   // 分析每个模块提供了哪些导出
    sideEffects: true,       // 结合 package.json 的 sideEffects 字段判断副作用
    minimize: true           // 开启压缩，真正把标记的代码删掉
  }
};
```

```js
// vite.config.js —— Rollup 默认会做摇树，通常无需配置
import { defineConfig } from 'vite';

export default defineConfig({
  build: {
    rollupOptions: {
      treeshake: true // 默认 true，这里显式写出方便排查
    }
  }
});
```

**易错点：**

- 只写了 `exports.add = ...` 的 CJS 库，**使用者无论如何都摇不动它**，所以现代库都会同时产出 ESM（`module` / `exports.import`）。
- `sideEffects: false` 不是「越纯越好」：漏标 CSS 导入、polyfill、注册类副作用，会删掉功能代码，产生「样式丢了 / 埋点没了」这类线上事故。
- 摇树主要作用于「库的导出」，业务代码里的死分支还是靠压缩器；两者别混为一谈。
- `import * as utils from './utils'` 这种命名空间导入会让工具更难判定，尽量用具名导入。
- 类的方法、被反射调用的函数（如字符串拼接调用的方法名）可能被保守保留，属正常现象。

## 2. 代码分割（Code Splitting）

**代码分割**：把一个「大产物」拆成多个 **chunk（分块）**，让浏览器**按需下载**，而不是首屏一次性加载所有 JS。它是首屏优化的第一手段。

**为什么要分割：** 单包体积越大，下载 + 解析 + 执行越慢；很多页面用不到的功能（后台管理、图表库、弹窗组件）没必要进首屏。

**三种典型切法（面试答题骨架）：**

| 切法 | 手段 | 适用场景 | 效果 |
| --- | --- | --- | --- |
| **入口分割** | 多 `entry` / 多页应用 | 后台多页、多端 | 天然隔离，各页独立 |
| **按路由分割** | 路由懒加载 `import()` | SPA 路由 | 首屏只加载当前页 |
| **按组件分割** | `React.lazy` / `defineAsyncComponent` | 重组件（地图、编辑器、图表） | 用户触发才加载 |
| **按体积/依赖分割** | `SplitChunks` / `manualChunks` | 抽离第三方库、公共模块 | 复用 + 缓存友好 |

**① Webpack：`splitChunks`（chunks + cacheGroups）**

```js
// webpack.config.js
module.exports = {
  optimization: {
    splitChunks: {
      chunks: 'all',           // 对同步 + 异步 chunk 都生效（async 只处理动态导入）
      minSize: 20000,          // 拆分出的 chunk 最小体积（字节），太小就不拆
      maxSize: 244000,         // 单个 chunk 超过它会尝试继续拆（0 表示不限制）
      minChunks: 1,            // 至少被引用几次才拆（1 = 只要被引用就拆公共块）
      cacheGroups: {
        // 抽离 node_modules 里的第三方库
        vendors: {
          test: /[\\/]node_modules[\\/]/,
          name: 'vendors',
          priority: -10         // 优先级越高越先匹配
        },
        // 被两个及以上入口共享的业务代码
        common: {
          minChunks: 2,
          name: 'common',
          priority: -20,
          reuseExistingChunk: true // 能复用的已存在 chunk 直接复用
        }
      }
    },
    // 把运行时（runtime）单独抽出来，避免它变化带动其它 chunk 的 hash
    runtimeChunk: 'single',
    // 用确定性 id，保证内容不变时 hash 稳定
    moduleIds: 'deterministic'
  }
};
```

**② Vite：`manualChunks`（Rollup 风格）**

```js
// vite.config.js
import { defineConfig } from 'vite';
import react from '@vitejs/plugin-react';

export default defineConfig({
  plugins: [react()],
  build: {
    rollupOptions: {
      output: {
        // 按依赖来源手动分包，便于长期缓存与体积控制
        manualChunks(id) {
          if (id.includes('node_modules')) {
            if (id.includes('lodash')) return 'vendor-lodash';
            if (id.includes('echarts')) return 'vendor-echarts';
            return 'vendor'; // 其余三方库统一进 vendor
          }
        },
        chunkFileNames: 'assets/[name]-[hash].js',
        entryFileNames: 'assets/[name]-[hash].js',
        assetFileNames: 'assets/[name]-[hash][extname]'
      }
    }
  }
});
```

**③ 路由懒加载：React.lazy + Suspense**

```jsx
// App.jsx
import React, { Suspense, lazy } from 'react';
import { BrowserRouter, Routes, Route } from 'react-router-dom';

// 动态 import() 返回 Promise，React.lazy 据此生成异步组件
const Home = lazy(() => import('./pages/Home'));
const Dashboard = lazy(() => import('./pages/Dashboard')); // 只有访问 /dashboard 才加载

export default function App() {
  return (
    <BrowserRouter>
      <Suspense fallback={<div>加载中…</div>}>
        <Routes>
          <Route path="/" element={<Home />} />
          <Route path="/dashboard" element={<Dashboard />} />
        </Routes>
      </Suspense>
    </BrowserRouter>
  );
}
```

**④ 路由懒加载：Vue Router + defineAsyncComponent**

```js
// router/index.js
import { createRouter, createWebHistory, defineAsyncComponent } from 'vue-router';

const routes = [
  { path: '/', component: () => import('../views/Home.vue') },
  { path: '/about', component: () => import('../views/About.vue') }
];

// 也可用于「重组件」的局部懒加载
const HeavyChart = defineAsyncComponent(() => import('../components/HeavyChart.vue'));

export default createRouter({ history: createWebHistory(), routes });
```

**⑤ Webpack 魔法注释：给 chunk 起名 / 指定加载方式**

```js
// webpackChunkName 指定产物名（便于排查）；webpackPrefetch 让浏览器空闲时预取
import(
  /* webpackChunkName: "editor" */
  /* webpackPrefetch: true */
  './Editor'
).then(({ Editor }) => { /* ... */ });

// webpackPreload：与父 chunk 并行加载，适合「马上要用」的资源
import(/* webpackPreload: true */ './CriticalModal');
```

**`prefetch` 与 `preload` 的区别：**

| 指令 | 时机 | 优先级 | 适合 |
| --- | --- | --- | --- |
| `preload` | 与父资源**并行**下载 | 高 | 当前页面马上要用的关键资源 |
| `prefetch` | **浏览器空闲**时下载 | 低 | 下一个页面可能用到的资源 |

**易错点：**

- 动态 `import()` 的路径必须**静态可分析**：`import(/* 变量拼接 */ path)` 在 Vite/Rollup 里会报警告，因为无法确定拆分粒度。
- 切得太碎会导致请求数量暴涨、反而变慢：一般单 chunk 控制在 20KB～244KB，公共库合并成 `vendor`。
- `chunks: 'async'`（默认）只处理动态导入产生的异步 chunk，同步代码不会拆；想共享业务代码要设 `'all'`。
- 抽离 `runtimeChunk` 很关键：否则主包 hash 一变，运行时也会变，缓存全失效（详见第 6 题）。

## 3. 打包体积分析

优化前必须先**量化**：搞清楚「哪个包最大、为什么大、能不能摇掉」。

**主流三件套对比：**

| 工具 | 生态 | 可视化形式 | 特点 |
| --- | --- | --- | --- |
| `webpack-bundle-analyzer` | Webpack | 交互式矩形树图 | 展示 parsed / gzip 体积、模块占比 |
| `rollup-plugin-visualizer` | Vite / Rollup | 树图 / 桑基图 | 支持开关摇树前后对比、多种图 |
| `source-map-explorer` | 任意（需 sourcemap） | 树图 | 从 sourcemap 反推，可分析非 Webpack 产物 |

**① webpack-bundle-analyzer**

```js
// webpack.config.js
const { BundleAnalyzerPlugin } = require('webpack-bundle-analyzer');

module.exports = {
  plugins: [
    new BundleAnalyzerPlugin({
      analyzerMode: 'server',       // 打开浏览器页面；也可 'static' 生成 HTML
      openAnalyzer: true,
      reportFilename: 'report.html',
      defaultSizes: 'parsed'        // 默认按解析后体积；也可 'gzip'
    })
  ]
};
```

```json
// package.json：用一个独立脚本触发，避免日常构建都跑它
{
  "scripts": {
    "build": "vite build",
    "analyze": "cross-env ANALYZE=1 vite build"
  }
}
```

**② rollup-plugin-visualizer（Vite 推荐）**

```js
// vite.config.js
import { defineConfig } from 'vite';
import { visualizer } from 'rollup-plugin-visualizer';

export default defineConfig({
  plugins: [
    // 只有显式开启分析时才生成报告，避免污染正常构建
    process.env.ANALYZE &&
      visualizer({
        filename: 'dist/stats.html',
        open: true,
        gzipSize: true,        // 显示 gzip 后体积
        template: 'treemap'    // treemap / sunburst / network
      })
  ].filter(Boolean)
});
```

**③ source-map-explorer（基于 sourcemap）**

```bash
# 先开启 sourcemap 构建，再对产物分析
npm run build   # 构建配置里需打开 build.sourcemap = true
npx source-map-explorer 'dist/assets/*.js'
```

**如何解读报告（面试追问点）：**

1. **看 gzip 后体积，而不是原始体积**：线上传的是压缩产物，1MB 的未压缩 JS 压缩后可能只有 200KB。
2. **看「大头」模块的占比**：一般是 moment、lodash、echarts、@ant-design/icons 这类库。
3. **看是否有重复依赖**：同一个库出现多个版本（如 lodash 与 lodash-es 并存），说明版本分裂。
4. **看是否引入了不该进业务包的东西**：如把整个组件库、整个图标集打进了主包。

```js
// 常见优化动作示例
// 1) 按需引入图标，而不是整包引入
import { SearchOutlined } from '@ant-design/icons'; // 好
// import * as Icons from '@ant-design/icons';      // 差：全量

// 2) moment 只保留中文并去掉未用语言包
import moment from 'moment';
import 'moment/locale/zh-cn'; // 配合 IgnorePlugin / 语言包裁剪
```

```js
// webpack：忽略 moment 的本地化目录（配合上面的显式引入）
const webpack = require('webpack');
module.exports = {
  plugins: [
    new webpack.IgnorePlugin({ resourceRegExp: /^\.\/locale$/, contextRegExp: /moment$/ })
  ]
};
```

**易错点：**

- 报告里的体积是「打包体积」，**不等于运行时解析/执行耗时**；体积小不等于快，还要看解析成本与执行逻辑。
- 分析插件**不要**常驻生产构建流程，它本身会拖慢构建、生成大文件。
- 只开 `openAnalyzer` 本地看，注意 `report.html` 别误提交到仓库（建议加入 `.gitignore` 或输出到临时目录）。

## 4. 构建速度优化有哪些手段？

构建速度优化的核心思路：**少干活、并行干、缓着干**。即「缩小处理范围、多线程/原生工具加速、缓存复用结果」。

**优化清单与收益对比：**

| 类别 | 手段 | 收益 | 代价 / 注意 |
| --- | --- | --- | --- |
| 缩小范围 | `resolve.extensions` 明确、`alias`、`include/exclude` | 减少无谓查找 | 需维护 alias 一致 |
| 缓存 | Webpack `cache: { type: 'filesystem' }`、Vite `optimizeDeps` | 二次构建极快 | 缓存目录要纳入 CI 缓存 |
| 并行 | `thread-loader`、Terser `parallel`、esbuild/swc | 多核加速 | thread 通信有开销，小项目反而变慢 |
| 换引擎 | Babel → SWC / esbuild；ts-loader → esbuild-loader | 数倍提速 | 少数语法/插件不兼容 |
| 跳过类型检查 | `transpileOnly`、`fork-ts-checker-webpack-plugin` | 构建与检查解耦 | 类型错误需另跑 `tsc --noEmit` |
| 关掉重活 | 关闭生产 `sourceMap`、选轻量 `devtool` | 立竿见影 | 影响线上问题定位 |
| 老方案 | DLL、`noParse`、`cache-loader` | 预编译不常变依赖 | 配置繁琐，Webpack 5 已被 filesystem cache 取代 |

**① Webpack 5 持久化缓存（最有效的一招）**

```js
// webpack.config.js
module.exports = {
  cache: {
    type: 'filesystem',       // 把构建结果缓存到磁盘，二次构建快很多
    buildDependencies: {
      config: [__filename]    // 配置文件变化时使缓存失效
    },
    version: 'v1'             // 手动改这里可强制清空旧缓存
  },
  resolve: {
    extensions: ['.ts', '.tsx', '.js'],  // 明确后缀，避免逐个尝试
    alias: { '@': require('path').resolve(__dirname, 'src') },
    modules: ['node_modules']            // 限制搜索目录，别让模块向上乱找
  },
  module: {
    rules: [
      {
        test: /\.tsx?$/,
        include: require('path').resolve(__dirname, 'src'), // 只处理源码
        exclude: /node_modules/,                            // 排除依赖
        use: ['thread-loader', 'babel-loader']              // 多线程转译
      }
    ]
  }
};
```

**② 用 esbuild / SWC 替换 Babel**

```js
// webpack.config.js：esbuild-loader 转译 + 压缩，速度是 Babel+Terser 的数倍
const { ESBuildMinifyPlugin } = require('esbuild-loader');

module.exports = {
  module: {
    rules: [
      {
        test: /\.[jt]sx?$/,
        loader: 'esbuild-loader',
        options: { target: 'es2015' }  // 指定目标语法，交给 esbuild 转译
      }
    ]
  },
  optimization: {
    minimizer: [new ESBuildMinifyPlugin({ target: 'es2015' })]
  }
};
```

```js
// babel.config.js：若保留 Babel，用 swc 插件替换慢的部分
// 或直接切换到 @swc/core 的 swc-loader
```

**③ TypeScript：构建与类型检查分离**

```js
// webpack.config.js
module.exports = {
```

```json
// package.json：把类型检查作为独立脚本（CI 中务必执行）
{
  "scripts": {

    "typecheck": "vue-tsc --noEmit"
```

**④ Vite 的构建优化**

```js
// vite.config.js
import { defineConfig } from 'vite';

export default defineConfig({
  esbuild: {
    drop: ['console', 'debugger'] // 生产环境移除 console 与 debugger
  },
  build: {
    sourcemap: false,            // 生产不开 sourcemap，提速并减小产物
    reportCompressedSize: false, // 跳过额外计算 gzip 体积的耗时（默认 true 会拖慢构建）
    chunkSizeWarningLimit: 1000
  },
  optimizeDeps: {
    include: ['lodash-es', 'echarts'] // 预构建常用依赖，减少首启的反复扫描
  }
});
```

> Vite 本身用 esbuild 做预构建与压缩，速度已经很快；它的瓶颈常出现在**插件**（如体积分析、自定义 AST 处理）与**依赖预构建**上。

**易错点：**

- `thread-loader` 对**小项目无收益**：线程启动与通信有开销，只有当转译耗时占比高时才值得。
- 关掉生产 `sourcemap` 会让线上报错堆栈变成「混淆代码」，通常要配合「上传 sourcemap 到监控平台但不随包发布」。
- `transpileOnly` 提速的前提是**类型检查必须另跑**（CI 里加 `tsc --noEmit`），否则类型错误被静默放过。
- 缓存的失效依赖「配置指纹」：改了配置却忘记让缓存失效，会出现「改了没生效」的诡异现象。

## 5. 构建缓存

**构建缓存**要区分两个层面：① **构建工具自身的缓存**（重复构建复用中间产物）；② **CI 层面的缓存**（跨流水线复用 `node_modules`、构建缓存目录）。

**① Webpack 5 持久化缓存（filesystem）**

```js
// webpack.config.js
module.exports = {
  cache: {
    type: 'filesystem',
    cacheDirectory: require('path').resolve(__dirname, 'node_modules/.cache/webpack'),
    name: 'prod-cache',   // 不同构建目标用不同 name，避免互相污染
    maxAge: 7 * 24 * 60 * 60 * 1000, // 缓存有效期（毫秒）
    buildDependencies: {
      config: [__filename],
      // 若用环境变量驱动构建，变化时也应让缓存失效
      tsconfig: [require('path').resolve(__dirname, 'tsconfig.json')]
    }
  }
};
```

- 相比旧的 `cache-loader`（进程级、内存级）与 **DLL**（预先打包不常变的依赖），filesystem cache 把结果落到磁盘，**二次构建几乎是增量**。
- Webpack 4 时代的 DLL 方案（`DllPlugin` + `DllReferencePlugin`）配置繁琐，Webpack 5 一般不再需要。

**② Vite 的缓存**

```text
node_modules/.vite/          # 依赖预构建（optimizeDeps）的缓存目录
  ├── deps/                  # 预构建后的 ESM 依赖
  └── _metadata.json         # 指纹，依赖或配置变化时自动失效
```

```bash
# 强制重新预构建（依赖异常时常用来「清缓存」）
npx vite --force
# 或直接删除缓存目录后重启
```

**③ CI 层面的缓存对比：**

| 缓存对象 | 平台/工具 | 命中后收益 | 注意 |
| --- | --- | --- | --- |
| `node_modules` | `actions/cache` / `actions/setup-node` `cache: 'pnpm'` | 省去重复下载、安装 | 以 lock 文件哈希为 key |
| 包管理器 store | pnpm store / npm cache | 跨项目复用 | 与 lock 绑定 |
| 构建缓存目录 | `node_modules/.cache`、`.vite` | 增量构建 | 缓存目录要固定路径 |
| 构建产物 | `actions/upload-artifact` / `download-artifact` | 跨 job 复用产物 | 大文件注意存储成本 |

**④ 缓存实现的底层逻辑：内容指纹**

```text
缓存 key = 输入内容的哈希（源码 + 依赖版本 + 配置）
     ↓
key 命中  → 直接复用上次结果
key 未命中 → 重新计算，并写入缓存
```

因此「改了源码但没重新构建」的根因通常是**指纹没被正确计算**（如配置被忽略、环境变量未纳入）。

**易错点：**

- 缓存目录（`node_modules/.cache`、`.vite`）应加入 `.gitignore`，不要提交。
- CI 缓存 key 一定要绑定 **lock 文件哈希**；不绑定会导致「依赖升级了但缓存还是旧的」。
- 缓存不是万能的：第一个构建（冷缓存）一定慢，所以「构建提速」要区分冷启动与增量两类指标。
- 环境变量（如 `API_BASE_URL`）参与构建时，也要作为缓存失效因子，否则不同环境的产物可能混用。

## 6. 产物缓存策略与 contenthash

线上部署后，**浏览器如何复用旧文件、只在内容变化时才重新下载**，靠的是「文件名带内容哈希 + HTTP 缓存头」的配合。

**① 三种 hash 的区别（经典考点）：**

| 类型 | 计算范围 | 特点 | 适用 |
| --- | --- | --- | --- |
| `hash` | 整个构建（一次编译） | 任一文件变，全部文件名变 | 已不推荐 |
| `chunkhash` | 单个 chunk | 同一 chunk 内变则变；但受 runtime 影响 | 入口级 |
| `contenthash` | **文件内容本身** | 内容不变则 hash 不变 | **JS/CSS 产物首选** |

```js
// webpack.config.js
module.exports = {
  output: {
    // contenthash：文件内容决定文件名，缓存最精准
    filename: '[name].[contenthash:8].js',
    chunkFilename: '[name].[contenthash:8].js',
    assetModuleFilename: 'assets/[name].[contenthash:8][ext]'
  },
  optimization: {
    // 把 runtime（管理模块加载的胶水代码）单独抽出来
    runtimeChunk: 'single',
    moduleIds: 'deterministic',   // 模块 id 稳定，避免无关变化带动 hash
    chunkIds: 'deterministic',
    splitChunks: { chunks: 'all' }
  }
};
```

**为什么要抽离 runtime：** runtime 里记录了「模块 id → 加载逻辑」。若它和业务代码在同一 chunk，**任何业务文件的变化都会改写 runtime，进而带动全包 hash 变化**，导致缓存连锁失效。拆出 `runtimeChunk` 后就互不影响了。

**② 强缓存 vs 协商缓存：**

| 维度 | 强缓存 | 协商缓存 |
| --- | --- | --- |
| 相关头 | `Cache-Control: max-age` / `Expires` | `ETag` / `Last-Modified` |
| 是否发请求 | **不发**，直接用本地副本 | **发请求**，服务端判断是否 304 |
| 返回码 | `200 (from cache)` | `304 Not Modified` |
| 优先级 | 高（同时存在时优先 `Cache-Control`） | 低 |
| 适用 | 带 hash 的静态资源 | `index.html` 等不能长期缓存的资源 |

```nginx
# nginx.conf：带 hash 的静态资源强缓存一年；index.html 不缓存
location ~* \.(?:js|css|png|jpg|jpeg|gif|svg|woff2?|ttf)$ {
    # immutable：告诉浏览器在这一年内即使刷新也不要发起校验请求
    add_header Cache-Control "public, max-age=31536000, immutable";
}

location = /index.html {
    # 入口 HTML 必须每次校验，保证用户拿到最新版本的资源引用
    add_header Cache-Control "no-cache, no-store, must-revalidate";
}
```

> 关键点：**带 contenthash 的资源可以用「一年强缓存」**，因为它内容变了文件名就变了；而 `index.html` 的文件名固定，必须走「不缓存 / 协商缓存」，否则用户永远停留在旧版本。

**③ 完整链路是怎么工作的：**

```text
1. 用户访问 https://site.com/ → 请求 index.html（no-cache，每次校验）
2. index.html 内引用 app.a1b2c3.js、vendor.d4e5f6.js（带 contenthash）
3. 浏览器请求带 hash 的 JS → 命中一年强缓存，直接本地读取
4. 发版后 index.html 引用变成 app.9f8e7d.js → 浏览器视为新文件，重新下载
5. 旧版本文件仍在缓存里，不影响新版本加载
```

**④ Vite 产物命名**

```js
// vite.config.js
export default defineConfig({
  build: {
    rollupOptions: {
      output: {
        entryFileNames: 'assets/[name]-[hash].js',
        chunkFileNames: 'assets/[name]-[hash].js',
        assetFileNames: 'assets/[name]-[hash][extname]'
      }
    }
  }
});
```

**易错点：**

- 用 `hash` 而非 `contenthash`：随便改一个文件，全量资源文件名都变，缓存几乎全失效。
- **不抽离 runtime** 会让缓存「连锁失效」，是面试常考的原理题。
- `index.html` 一定不能设长 `max-age`；但也不宜完全 `no-store`（会让每次都重新下载），`no-cache`（允许存但每次校验）是常用折中。
- `immutable` 只对**文件名带 hash** 的资源使用；对 `index.html` 用它会导致用户「永远看不到新版本」。
- CDN 上一般还要**配置忽略 URL 查询串**或配合「回源刷新」，否则旧缓存可能被带参数的 URL 命中。

## 7. CDN 与静态资源部署

**CDN（Content Delivery Network，内容分发网络）**：通过部署在各地的**边缘节点**就近响应用户请求，把静态资源分发到离用户最近的节点，降低延迟、提升下载速度、分担源站压力。

**工作原理：**

```text
用户请求 → DNS 解析（智能调度，就近选点）→ 边缘节点
     ├── 命中缓存 → 直接返回（最快）
     └── 未命中 → 回源到源站 → 拉取并缓存到边缘 → 返回
```

**① 构建时正确配置资源前缀（publicPath / base）**

```js
// webpack.config.js：让产物里的资源引用指向 CDN 域名
module.exports = {
  output: {
    publicPath: 'https://cdn.example.com/static/v1.2.3/',
    filename: '[name].[contenthash:8].js'
  }
};
```

```js
// vite.config.js
export default defineConfig({
  // 也可用环境变量按环境注入不同域名
  base: process.env.CDN_BASE || 'https://cdn.example.com/static/v1.2.3/'
});
```

```html
<!-- 产物内的资源引用会被前缀替换为 -->
<script src="https://cdn.example.com/static/v1.2.3/assets/index-a1b2c3.js"></script>
```

**② 上传产物到 CDN（构建后脚本）**

```json
// package.json
{
  "scripts": {
    "build": "vite build",
    "deploy:cdn": "node scripts/upload-cdn.js"
  }
}
```

```js
// scripts/upload-cdn.js（示意：用对象存储 SDK 同步 dist 到 CDN 源站桶）
const OSS = require('ali-oss');
const path = require('path');
const fs = require('fs');

const client = new OSS({
  region: process.env.OSS_REGION,
  accessKeyId: process.env.OSS_KEY_ID,
  accessKeySecret: process.env.OSS_KEY_SECRET,
  bucket: process.env.OSS_BUCKET
});

async function walk(dir) {
  const entries = fs.readdirSync(dir, { withFileTypes: true });
  for (const e of entries) {
    const full = path.join(dir, e.name);
    if (e.isDirectory()) await walk(full);
    else {
      const key = `static/v1.2.3/${path.relative('dist', full).replace(/\\/g, '/')}`;
      await client.put(key, full); // 上传后由 CDN 回源读取
    }
  }
}

walk('dist').then(() => console.log('CDN 上传完成'));
```

**③ CDN 部署的几个关键策略：**

| 策略 | 说明 |
| --- | --- |
| 版本化路径 | 用 `static/v1.2.3/` 区分版本，回滚只需切路径 |
| 多域名 / 域名哈希 | 突破浏览器「同域并发连接数」限制，如 `cdn1`、`cdn2` |
| 缓存刷新 | 更新 `index.html` 后需**主动刷新** CDN 缓存（或依赖版本化路径规避） |
| 回源策略 | 缓存未命中才回源；可设「回源鉴权」防止被直接刷源站 |
| HTTPS | 全站 HTTPS，避免混合内容拦截 |

**④ 常见问题排查：**

```text
Q: 发版后用户还是看到旧页面？
A: ① index.html 缓存未刷新（需 CDN 刷缓存）；② 预览时被运营商/代理缓存；③ 未做版本化路径导致同名文件被旧缓存命中。
```

**易错点：**

- `publicPath` / `base` 配置错会导致**资源 404 或白屏**，这是部署最常见的事故来源。
- CDN 缓存的是**源站内容**：只更新了源站却没刷新 CDN，用户仍拿旧文件（CDN 的 TTL 决定刷新延迟）。
- 带版本号路径（`v1.2.3/`）能规避刷新问题，但要记得清理历史版本，避免存储无限膨胀。
- 跨域资源要在 CDN 侧配置 `Access-Control-Allow-Origin`，否则字体、Canvas 图片等会因跨域失败（如 `woff2` 字体加载失败）。

## 8. 环境变量与多环境配置

前端项目通常要在「开发 / 测试 / 预发 / 生产」多套环境间切换后端地址、开关功能。核心是**用构建期注入的环境变量**（而非运行时读取服务器环境）。

**① Vite 的环境变量机制**

```bash
# .env               所有环境都会加载（提交仓库）
VITE_APP_TITLE=示例应用

# .env.development   仅 dev 模式（vite dev）加载
VITE_API_BASE=/api

# .env.production    仅 build 模式加载
VITE_API_BASE=https://api.example.com

# .env.local         本地私有覆盖（加入 .gitignore，不提交）
VITE_API_BASE=http://127.0.0.1:3000
```

```js
// src/config.js —— 通过 import.meta.env 读取（Vite 特有）
export const config = {
  // 只有以 VITE_ 开头的变量才会被注入到客户端
  apiBase: import.meta.env.VITE_API_BASE,
  mode: import.meta.env.MODE,      // 'development' | 'production' | 自定义
  isDev: import.meta.env.DEV,      // 布尔
  isProd: import.meta.env.PROD     // 布尔
};
```

**Vite 文件加载优先级（从低到高，后者覆盖前者）：**

| 优先级 | 文件 | 是否提交 |
| --- | --- | --- |
| 1（最低） | `.env` | 提交 |
| 2 | `.env.local` | **不提交**（私有） |
| 3 | `.env.[mode]` | 提交 |
| 4（最高） | `.env.[mode].local` | **不提交** |

> 规则：**具体模式 > 通用；`.local` 优先级最高**。已被 `.env` 定义过的变量，同一层里 `[mode]` 会覆盖它。

**② 自定义模式（多环境）**

```bash
# .env.staging
VITE_API_BASE=https://staging-api.example.com
```

```json
// package.json：用 --mode 指定加载哪个 .env.[mode]
{
  "scripts": {
    "dev": "vite",
    "build:staging": "vite build --mode staging",
    "build": "vite build --mode production"
  }
}
```

**③ Vite 只暴露 `VITE_` 前缀的原因**

```js
// 危险：若把任意变量都暴露，可能把服务端密钥打进客户端代码
// Vite 用「VITE_ 前缀白名单」防止误注入
const secret = import.meta.env.DB_PASSWORD; // undefined —— 未被注入

// 自定义前缀（谨慎使用）
// vite.config.js
export default defineConfig({
  envPrefix: 'APP_' // 此时 APP_XXX 才会被暴露
});
```

**④ Webpack 的做法：`DefinePlugin`**

```js
// webpack.config.js —— 构建期把变量「文本替换」进代码
const webpack = require('webpack');

module.exports = {
  plugins: [
    new webpack.DefinePlugin({
      // 注意：值会被当作代码片段注入，字符串必须再包一层 JSON.stringify
      'process.env.API_BASE': JSON.stringify(process.env.API_BASE),
      'process.env.NODE_ENV': JSON.stringify('production'),
      __DEV__: JSON.stringify(false)
    })
  ]
};
```

```js
// 代码里则写作
const base = process.env.API_BASE; // 构建后会被替换成字符串字面量
if (__DEV__) { console.log('dev only'); } // false 分支会被压缩器消除
```

**⑤ 运行时配置 vs 构建时配置：**

| 方式 | 注入时机 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 构建时（env、DefinePlugin） | 打包时写死 | 简单、可被压缩器优化 | 换环境要重新构建 |
| 运行时（请求 `/config.json`、挂 `window.__CONFIG__`） | 页面加载时 | 同一份产物可部署多环境 | 多一次请求、无法静态优化 |

```html
<!-- 运行时配置示例：镜像构建一次，部署时替换 config.json -->
<script src="/config.js"></script>
<script>
  window.__APP_CONFIG__ = { apiBase: 'https://api.example.com' };
</script>
```

**易错点：**

- 环境变量会被**打进产物**：把密钥写进 `VITE_` 变量等于把密钥公开给用户（前端没有真正的秘密）。
- `.env.local*` 必须加入 `.gitignore`，否则本地私有地址会被上传、覆盖团队配置。
- Vite 中**不是** `process.env` 而是 `import.meta.env`；老代码里用 `process.env.XXX` 在 Vite 下会报 `undefined`。
- `DefinePlugin` 的值不是字符串字面量而写错（漏了 `JSON.stringify`）时，会注入成裸变量名导致运行时 ReferenceError。
- 同一份产物要部署到多环境时，应改用运行时配置，而不是为每个环境各构建一份。

## 9. CI/CD 与前端流水线

**CI（持续集成）**：频繁把代码合并到主干，自动执行「安装依赖 → 检查 → 测试 → 构建」；**CD（持续交付/部署）**：把构建产物自动发布到目标环境。

**前端流水线的标准环节：**

| 阶段 | 做什么 | 工具示例 |
| --- | --- | --- |
| 检出 | 拉取代码、切分支 | `actions/checkout` |
| 环境准备 | 装 Node、包管理器，恢复缓存 | `actions/setup-node` |
| 安装依赖 | `npm ci` / `pnpm install --frozen-lockfile` | pnpm / npm |
| 静态检查 | ESLint、Stylelint、类型检查、commitlint | eslint、tsc |
| 测试 | 单元 / 集成 / 覆盖率 | Vitest / Jest |
| 构建 | 产物构建 | vite build |
| 制品 | 归档产物供后续 job 使用 | `actions/upload-artifact` |
| 部署 | 上传 CDN / 服务器、刷新缓存 | ossutil、rsync、kubectl |
| 通知 | 成功/失败通知 | Slack / 飞书机器人 |

**完整 GitHub Actions 示例：**

```yaml
# .github/workflows/deploy.yml
name: Build & Deploy

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

# 同一分支的并发构建，后一次取消前一次，避免重复部署
concurrency:
  group: deploy-${{ github.ref }}
  cancel-in-progress: true

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - name: 检出代码
        uses: actions/checkout@v4

      - name: 安装 pnpm
        uses: pnpm/action-setup@v4
        with:
          version: 9

      - name: 安装 Node 并缓存 pnpm store
        uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: pnpm          # 自动按 pnpm-lock.yaml 生成缓存 key

      - name: 安装依赖（严格按 lock，禁止改写）
        run: pnpm install --frozen-lockfile

      - name: 代码检查
        run: pnpm run lint

      - name: 类型检查
        run: pnpm run typecheck

      - name: 单元测试
        run: pnpm run test -- --run

      - name: 构建
        run: pnpm run build
        env:
          VITE_API_BASE: ${{ secrets.VITE_API_BASE }}

      - name: 归档构建产物
        uses: actions/upload-artifact@v4
        with:
          name: dist
          path: dist/
          retention-days: 7

  deploy:
    needs: build            # 依赖 build 成功后才部署
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    environment: production
    steps:
      - name: 下载构建产物
        uses: actions/download-artifact@v4
        with:
          name: dist
          path: dist/

      - name: 上传到对象存储并刷新 CDN
        run: |
          pnpm dlx ossutil cp -r dist/ oss://my-bucket/static/${{ github.sha }}/
          # 刷新 index.html 缓存，保证用户拿到新版本
          pnpm dlx ossutil cdn-refresh --url https://cdn.example.com/index.html
        env:
          OSS_ACCESS_KEY_ID: ${{ secrets.OSS_ACCESS_KEY_ID }}
          OSS_ACCESS_KEY_SECRET: ${{ secrets.OSS_ACCESS_KEY_SECRET }}
```

**缓存加速（`actions/cache` 的作用与原理）：**

```yaml
- name: 缓存构建中间产物
  uses: actions/cache@v4
  with:
    path: node_modules/.cache      # 例如 Webpack filesystem cache
    key: ${{ runner.os }}-build-${{ hashFiles('**/lock.yaml') }}
    restore-keys: |
      ${{ runner.os }}-build-
```

- `key` 命中 → 直接复用；未命中 → 用 `restore-keys` 找最近可用的旧缓存（部分复用）。
- `key` 建议包含 **lock 文件哈希**：依赖一变，缓存自动失效。

**易错点：**

- CI 里必须用 `npm ci` / `--frozen-lockfile`：用 `install` 会改写 lock，破坏可复现性。
- 用 `secrets` 注入敏感变量，**绝不能**把密钥写死在 workflow 文件里。
- 部署要设置 `environment` 保护与环境级审批，避免误推生产。
- `upload-artifact` 会在平台留存文件，注意 `retention-days` 与敏感信息；产物不要包含 `.env` / 源码。
- 构建环境（Node 版本、包管理器版本）要与本地一致，否则可能出现「本地能构建、CI 失败」。

## 10. Nginx 部署 SPA 的常见配置

SPA 的产物是「一个 `index.html` + 若干静态资源」，路由由前端接管。用 Nginx 托管时，**核心是「资源直接命中、找不到的路径一律回退给 `index.html`」**，否则刷新子路由会 404。

**① SPA 回退（最关键的配置）**

```nginx
# nginx.conf
server {
    listen 80;
    server_name example.com;

    # 产物目录（容器部署时通常指向 /usr/share/nginx/html）
    root /usr/share/nginx/html;
    index index.html;

    location / {
        # 依次尝试：精确文件 → 同名目录 → 最终回退到 /index.html
        try_files $uri $uri/ /index.html;
    }
}
```

**② 静态资源长缓存 + gzip 压缩**

```nginx
# gzip 压缩（对文本类资源效果显著，图片/字体无需压缩）
gzip on;
gzip_vary on;
gzip_comp_level 6;              # 1~9，6 是速度与压缩率的折中
gzip_min_length 1024;           # 小于 1KB 不压缩（收益低）
gzip_types text/plain text/css application/json application/javascript
           application/xml text/xml application/xml+rss image/svg+xml;

server {
    # 带 hash 的资源：强缓存一年（详见第 6 题）
    location ~* \.(?:js|css|png|jpg|jpeg|gif|svg|ico|woff2?|ttf|eot)$ {
        expires 1y;
        add_header Cache-Control "public, max-age=31536000, immutable";
        access_log off;          # 静态资源不打访问日志，省 IO
    }

    # 入口 HTML：绝不长缓存，保证能拿到最新资源引用
    location = /index.html {
        add_header Cache-Control "no-cache, must-revalidate";
    }
}
```

**③ 如果预先压缩好 `.gz` 产物，用 `gzip_static` 直接下发（零 CPU 开销）**

```nginx
gzip_static on;   # 存在 index.html.gz 时优先发送它，无需运行时压缩
```

**④ 后端接口反向代理（解决跨域 / 统一入口）**

```nginx
location /api/ {
    proxy_pass http://backend-service:8080/;   # 注意结尾斜杠会改写路径
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;

    # 若上游是跨域服务，也可在此补 CORS 头（但通常放在后端更清晰）
    add_header Access-Control-Allow-Origin $http_origin always;
    add_header Access-Control-Allow-Credentials true always;
}
```

**⑤ `location` 匹配优先级（理解它才能写出正确配置）：**

| 优先级 | 写法 | 含义 |
| --- | --- | --- |
| 1（最高） | `location = /path` | 精确匹配，命中即停 |
| 2 | `location ^~ /path/` | 前缀匹配，命中后**不再尝试正则** |
| 3 | `location ~ /\.js$/` | 正则匹配（区分大小写） |
| 4 | `location ~* \.js$` | 正则匹配（不区分大小写） |
| 5（最低） | `location /path/` | 普通前缀匹配，取**最长**前缀 |

```text
匹配顺序要点：先找「精确 = 」，再看「^~ 前缀」，然后按「正则」从上到下，最后才是普通前缀。
正则一旦命中就停止；普通前缀则取最长的那条。
```

**易错点：**

- 忘记 `try_files ... /index.html` 会出现「能进首页，刷新子路由 404」，这是 SPA 部署最经典的问题。
- `proxy_pass` 结尾带不带 `/` 会影响路径拼接：`proxy_pass http://host/;` 会**替换** `location` 匹配的前缀。
- `index.html` 若被设了长缓存，发版后用户会一直停留在旧版本（引用旧的、已删除的资源 → 白屏）。
- `gzip` 不要对 `image/*`、`video/*` 等已压缩格式开启，纯属浪费 CPU。
- 用 `root` 还是 `alias` 容易混淆：`alias` 会替换整个匹配路径，写错同样导致 404。

## 11. Docker 部署前端应用

用 Docker 部署前端，本质是「用 Nginx 镜像托管构建产物」。关键实践是**多阶段构建**：构建阶段装依赖、跑打包，运行阶段只保留产物 + Nginx，**镜像因此极小**。

**单阶段 vs 多阶段构建对比：**

| 维度 | 单阶段 | 多阶段 |
| --- | --- | --- |
| 阶段数 | 1（构建 + 运行同镜像） | ≥2（builder + runner） |
| 镜像体积 | 大（含 Node、源码、依赖、构建工具） | **小**（只含 Nginx + dist） |
| 构建工具泄露 | 会留在镜像里（安全隐患） | 不会 |
| 复用 | 差 | 构建与运行解耦，可分别替换 |
| 适用 | 内部临时调试 | **生产环境首选** |

**① 多阶段 Dockerfile**

```dockerfile
# ---------- 阶段一：builder，负责构建 ----------
FROM node:20-alpine AS builder

WORKDIR /app

# 先只拷贝依赖清单，利用 Docker 层缓存：依赖不变则不重复安装
COPY package.json pnpm-lock.yaml ./
RUN corepack enable && pnpm install --frozen-lockfile

# 再拷贝源码并构建
COPY . .
RUN pnpm run build

# ---------- 阶段二：runner，只放产物与 Nginx ----------
FROM nginx:1.27-alpine AS runner

# 覆盖默认配置（见第 10 题的 nginx.conf）
COPY deploy/nginx.conf /etc/nginx/conf.d/default.conf

# 只从 builder 里拿构建产物，Node 与源码不进最终镜像
COPY --from=builder /app/dist /usr/share/nginx/html

EXPOSE 80
CMD ["nginx", "-g", "daemon off;"]
```

**② `.dockerignore`（避免把无用文件塞进构建上下文）**

```text
# .dockerignore
node_modules
dist
.git
.github
.vscode
.idea
*.log
.env
.env.local
Dockerfile
docker-compose.yml
README.md
```

> 作用：构建上下文越小，`docker build` 越快；同时避免把 `node_modules`（宿主机编译、可能不兼容）覆盖进镜像。

**③ 镜像体积优化清单：**

| 手段 | 效果 |
| --- | --- |
| 多阶段构建 | 去掉 Node、源码、构建工具，通常可压到几十 MB |
| 用 `alpine` 基础镜像 | 基础层从上百 MB 降到几 MB |
| `.dockerignore` | 缩小构建上下文、避免宿主 `node_modules` 混入 |
| 合并 `RUN` 指令 | 减少镜像层数 |
| 依赖层单独拷贝 + 缓存 | 依赖不变时不重复安装 |
| 清理缓存（`pnpm store prune`、删 `.cache`） | 减少构建阶段残留 |

**④ 常用构建与运行命令**

```bash
# 构建镜像（带版本 tag，便于回滚，见第 13 题）
docker build -t my-frontend:1.2.3 .

# 运行
docker run -d --name my-frontend -p 8080:80 my-frontend:1.2.3

# 查看镜像体积
docker images my-frontend
```

**易错点：**

- 单阶段镜像会**把构建工具和源码一起打包**，体积大且有信息泄露风险，生产不建议。
- 顺序写错（先 `COPY . .` 再装依赖）会导致「改一行代码就要重装依赖」，白丢层缓存。
- `.dockerignore` 漏写 `node_modules`：宿主机依赖会被拷进镜像，可能出现平台架构不匹配的报错。
- Nginx 容器默认配置**不带 SPA 回退**，必须替换配置，否则刷新子路由 404。
- 版本 tag 要唯一且可追溯（用语义版本或 git sha），不要只用 `latest`，否则无法回滚。

## 12. 打包产物的首屏优化

首屏优化的目标：让用户**尽快看到有意义的内容**。对应指标通常是 **FCP（首次内容绘制）**、**LCP（最大内容绘制）**、**TTI（可交互时间）**。

**优化手段与作用：**

| 手段 | 作用 | 说明 |
| --- | --- | --- |
| 代码分割 + 按需加载 | 减少首屏 JS 体积 | 见第 2 题 |
| `preload` 关键资源 | 提前并行下载 | 首屏必需字体、关键 CSS |
| `prefetch` 后续页资源 | 空闲预取 | 下个路由可能用的 chunk |
| 骨架屏 | 提升「感知速度」 | 首帧就有内容，缓解白屏 |
| 关键 CSS 内联 | 避免 CSS 阻塞渲染 | 首屏样式内联进 `<head>` |
| 资源压缩与图片优化 | 减少传输体积 | gzip/brotli、WebP/AVIF、响应式图片 |
| 字体优化 | 避免字体闪烁（FOIT/FOUT） | `font-display: swap`、子集化 |
| SSR / 预渲染 | 首屏直出 HTML | 内容型页面提升明显 |
| 减少主线程阻塞 | 降低 TTI | 长任务拆分、`requestIdleCallback` |

**① 资源预加载指令（Vite / 手动均可）**

```html
<!-- preload：当前页面马上要用，最高优先级并行下载 -->
<link rel="preload" href="/assets/font.woff2" as="font" type="font/woff2" crossorigin>
<link rel="preload" href="/assets/main.css" as="style">

<!-- prefetch：空闲时预取，为「下一步」做准备 -->
<link rel="prefetch" href="/assets/dashboard-a1b2.js">

<!-- 预连接：提前建连/TLS 握手，减少后续请求的等待 -->
<link rel="preconnect" href="https://cdn.example.com">
<link rel="dns-prefetch" href="https://api.example.com">
```

**② 关键 CSS 内联 + 其余样式异步加载**

```html
<head>
  <!-- 首屏关键样式内联，避免渲染阻塞 -->
  <style>
    .hero { display: flex; align-items: center; height: 60vh; }
  </style>

  <!-- 非关键样式异步加载：onload 后切换为正常样式表 -->
  <link rel="preload" href="/assets/app.css" as="style"
        onload="this.onload=null;this.rel='stylesheet'">
  <noscript><link rel="stylesheet" href="/assets/app.css"></noscript>
</head>
```

**③ 字体优化**

```css
/* font-display: swap —— 字体未就绪时先用系统字体渲染，避免文字长时间不可见（FOIT） */
@font-face {
  font-family: 'MyFont';
  src: url('/assets/myfont.woff2') format('woff2');
  font-display: swap;
  unicode-range: U+4E00-9FFF; /* 只加载实际用到的字符子集 */
}
```

```html
<!-- 预加载首屏字体，减少字形切换 -->
<link rel="preload" href="/assets/myfont.woff2" as="font" type="font/woff2" crossorigin>
```

**④ 图片优化**

```html
<!-- 响应式图片 + 现代格式：让浏览器选最合适的资源 -->
<picture>
  <source srcset="/img/hero.avif" type="image/avif">
  <source srcset="/img/hero.webp" type="image/webp">
  <img src="/img/hero.jpg" alt="首屏大图" width="800" height="450"
       loading="eager" fetchpriority="high">
</picture>

<!-- 首屏外的图片懒加载，减少初始请求 -->
<img src="/img/lazy.jpg" alt="" loading="lazy" decoding="async">
```

**⑤ 骨架屏思路（示意）**

```jsx
// 首屏数据未就绪时先渲染骨架，避免白屏，提升感知性能
function Page() {
  const { data, loading } = useRequest(fetchHome);
  if (loading) return <Skeleton />; // 结构占位，视觉上「已经有内容了」
  return <Content data={data} />;
}
```

**易错点：**

- `preload` 滥用会**抢带宽**，反而拖慢真正关键的资源；务必只用于「首屏必需」的一两项。
- `preload` 字体时必须带 `crossorigin`，否则会**重复下载**（无 CORS 的预加载与真正的字体请求被当作两次）。
- `font-display: swap` 会出现字体闪烁（FOUT），是「可用优先」的取舍；品牌诉求强时可考虑子集化后内联。
- 懒加载图片要留好宽高占位，否则加载时布局抖动（CLS 指标变差）。
- 首屏优化务必用真实网络（弱网、慢速 4G）与真实设备验证，别只看本地 `localhost` 的理想数据。

## 13. 灰度发布与版本回滚

**灰度发布（金丝雀发布）**：新版本先只推给**一部分用户**，观察指标正常后再逐步放量到全量；出问题能**快速回滚**。

**常见灰度方案对比：**

| 维度 | 按比例 | 按用户 | 按白名单 |
| --- | --- | --- | --- |
| 划分依据 | 随机 / 权重（如 5%） | 用户 ID 哈希 | 指定用户/内部账号 |
| 一致性 | 同一用户可能一会儿新一会儿旧 | **同一用户始终一致** | 仅指定人群可见 |
| 实现 | 网关 / CDN 权重 | 网关按 ID 取模分流 | 配置中心开关 |
| 适用 | 快速验证稳定性 | 需要体验一致的业务 | 内测、预发验证 |

**实现方式对比：**

| 层级 | 手段 | 特点 |
| --- | --- | --- |
| 网关层 | 按 header/token/IP 分流到不同后端版本 | 通用、与前端解耦 |
| 前端资源层 | 部署多份产物，按 Cookie 下发不同版 `index.html` | 前端主导、粒度细 |
| 配置中心 | 开关（feature flag）控制新功能显隐 | 无需重新部署，回滚最快 |

**① 基于前端资源的灰度（多版本产物并存）**

```nginx
# 用 Cookie 决定返回哪个版本的 index.html
map $cookie_app_version $index_file {
    default        "/index.html";         # 默认发布版
    "canary"       "/index-canary.html";  # 灰度版
}

server {
    location = / {
        # 通过内部重定向返回对应版本的入口 HTML
        rewrite ^ /$index_file last;
    }
    location /v1/ { root /usr/share/nginx/html; }
    location /v2/ { root /usr/share/nginx/html; }
}
```

**② 基于配置中心的开关（feature flag）**

```js
// 运行时读取配置中心下发的开关，控制新功能是否启用
async function bootstrap() {
  // 例如从远端拉取灰度配置（可缓存 + 降级）
  const resp = await fetch('/api/feature-flags', { credentials: 'include' });
  const flags = await resp.json();

  if (flags.newCheckout) {
    // 新流程
    return import('./pages/CheckoutNew'); // 也可以懒加载新版本代码
  }
  return import('./pages/CheckoutOld');
}
```

**回滚策略对比：**

| 策略 | 做法 | 回滚速度 | 注意 |
| --- | --- | --- | --- |
| 旧版本保留 | 同时保留多个版本目录/镜像 | 极快（切流量） | 需额外存储 |
| 镜像回退 | K8s 回滚到上一镜像 tag | 快 | 依赖镜像 tag 唯一可追溯 |
| CDN 立即刷新 | 刷新 `index.html` 缓存 | 中（有传播延迟） | 带 hash 资源无需刷 |
| 配置开关回退 | 关闭 flag | **最快**（秒级） | 需事前设计好开关 |

```bash
# K8s 回滚到上一版本的示例
kubectl rollout history deployment/frontend          # 查看历史版本
kubectl rollout undo deployment/frontend             # 回滚上一版本
kubectl rollout undo deployment/frontend --to-revision=3  # 回滚到指定版本
```

**易错点：**

- 灰度用户要**粘性**（同一用户始终命中同一版本），否则前端状态/本地缓存可能错乱，难以复现问题。
- 前端资源是**静态的**：同一个 `index.html` 会引用固定 hash 的资源，所以「部分用户新版本」需要**多份入口 + 资源并存**，不能只靠一份产物。
- 回滚时若有 `index.html` 缓存，务必**立即刷新 CDN**，否则回滚不生效。
- 灰度必须有**明确的观测指标与自动止损**（错误率、转化率），否则只是「随机放量」，不叫灰度。
- 多版本产物并存时，注意清理历史版本目录，避免磁盘/存储无限增长。

## 14. 前端监控与异常上报

线上的问题（白屏、报错、卡顿）**不可复现、不可调试**，因此必须靠一套监控体系：**采集 → 上报 → 聚合 → 告警 → 定位**。

**错误类型与捕获方式：**

| 错误类型 | 捕获方式 | 说明 |
| --- | --- | --- |
| JS 运行时错误 | `window.onerror` / `addEventListener('error')` | 同步异常 |
| Promise 未处理拒绝 | `unhandledrejection` | 异步链路的常被忽略处 |
| 资源加载错误 | `addEventListener('error', handler, true)` 捕获阶段 | img/script/link 加载失败 |
| 框架内异常 | `errorHandler`（Vue）/ ErrorBoundary（React） | 组件级错误边界 |
| 接口异常 | 请求库拦截器（axios interceptor） | 业务/网络错误 |
| 性能指标 | Performance API / PerformanceObserver | FCP/LCP/CLS 等 |

**① 核心采集代码**

```js
// monitor.js —— 统一异常采集与上报
const report = (type, payload) => {
  // 用 sendBeacon 不阻塞页面卸载；失败再降级为同步请求
  const data = JSON.stringify({ type, payload, ts: Date.now() });
  if (navigator.sendBeacon) {
    navigator.sendBeacon('/api/monitor', data);
  } else {
    const img = new Image();
    img.src = `/api/monitor?data=${encodeURIComponent(data)}`; // 降级方案
  }
};

// 1. 同步运行时错误
window.onerror = (message, source, lineno, colno, error) => {
  report('error', {
    message,
    source,
    line: lineno,
    column: colno,
    stack: error?.stack
  });
  return false; // 不阻止默认行为
};

// 2. 未处理的 Promise 拒绝
window.addEventListener('unhandledrejection', (e) => {
  report('unhandledrejection', {
    reason: String(e.reason),
    stack: e.reason?.stack
  });
});

// 3. 资源加载错误（注意：资源错误不会冒泡，要用捕获阶段）
window.addEventListener(
  'error',
  (e) => {
    const target = e.target;
    if (target && (target.tagName === 'IMG' || target.tagName === 'SCRIPT' || target.tagName === 'LINK')) {
      report('resource', {
        tag: target.tagName,
        url: target.src || target.href
      });
    }
  },
  true // 关键：true 表示在捕获阶段监听
);
```

**② 框架级错误边界**

```jsx
// React：用 ErrorBoundary 兜住组件渲染错误，避免整页白屏
import React from 'react';
import { report } from './monitor';

class ErrorBoundary extends React.Component {
  state = { hasError: false };
  static getDerivedStateFromError() {
    return { hasError: true };
  }
  componentDidCatch(error, info) {
    report('react', { error: error.stack, info });
  }
  render() {
    return this.state.hasError ? <div>页面出错了</div> : this.props.children;
  }
}
```

```js
// Vue：全局错误处理钩子
import { report } from './monitor';

  report('vue', { error: err?.stack, info });
};
```

**③ 性能指标采集**

```js
// 用 PerformanceObserver 采集 LCP / FCP 等核心指标
const observer = new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    if (entry.name === 'largest-contentful-paint') {
      report('perf', { lcp: entry.startTime });
    } else if (entry.name === 'first-contentful-paint') {
      report('perf', { fcp: entry.startTime });
    } else if (entry.entryType === 'layout-shift' && !entry.hadRecentInput) {
      report('perf', { cls: entry.value }); // 累积布局偏移
    }
  }
});
observer.observe({ type: 'largest-contentful-paint', buffered: true });
observer.observe({ type: 'layout-shift', buffered: true });

// 首屏加载相关（navigation timing）
window.addEventListener('load', () => {
  const nav = performance.getEntriesByType('navigation')[0];
  report('perf', {
    dns: nav.domainLookupEnd - nav.domainLookupStart,
    ttfb: nav.responseStart - nav.requestStart,
    domReady: nav.domContentLoadedEventEnd - nav.startTime
  });
});
```

**④ 上报策略：采样与节流（避免监控本身拖垮页面/打爆服务端）**

```js
// 采样：只上报 10% 的用户，减少服务端压力与带宽
const SAMPLING_RATE = 0.1;
const shouldSample = Math.random() < SAMPLING_RATE;

// 节流：同类错误短时间内只上报一次，避免循环报错刷屏
const reportedKeys = new Set();
function reportThrottled(key, payload) {
  if (reportedKeys.has(key)) return;
  reportedKeys.add(key);
  if (shouldSample) report('error', payload);
}

window.onerror = (msg, src, line) => {
  reportThrottled(`${msg}@${src}:${line}`, { message: msg, source: src, line });
};
```

**⑤ 接入 Sentry 的思路（一般不自研时选它）**

```js
// 初始化：捕获未处理异常、收集面包屑、自动附带 sourcemap 还原堆栈
import * as Sentry from '@sentry/browser';

Sentry.init({
  dsn: 'https://xxx.ingest.sentry.io/xxx',
  environment: 'production',
  tracesSampleRate: 0.1,          // 性能追踪采样率
  beforeSend(event) {
    // 上报前过滤：如忽略已知的第三方脚本错误
    if (event.exception?.values?.[0]?.value?.includes('ResizeObserver')) return null;
    return event;
  }
});
```

```bash
# 关键：构建时生成 sourcemap 并上传给 Sentry，才能把压缩后的堆栈还原成源码
npx @sentry/cli sourcemaps upload --org my-org --project my-app ./dist
```

**易错点：**

- 资源错误**不冒泡**，用 `window.onerror` 抓不到，必须 `addEventListener('error', fn, true)` 在捕获阶段监听。
- 生产环境不开 sourcemap，上报的堆栈全是混淆后的代码，**等于拿不到有效信息**；正确做法是「上传 sourcemap 到监控平台，但不随产物发布」。
- 监控上报本身要有**采样与节流**，否则「监控导致的性能问题」会变成新的故障源。
- `sendBeacon` 更可靠（页面卸载也能发出），但容量有限（约 64KB），大 payload 要拆分。
- 「采集到错误」不等于「能定位」：至少带上用户标识、页面路径、版本号、浏览器信息，才能聚合与复现。
