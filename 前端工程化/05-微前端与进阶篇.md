## 1. 什么是微前端？

**微前端（Micro Frontends）**：借鉴微服务思想，把一个大型 Web 应用按**业务域**拆分成多个可以**独立开发、独立测试、独立部署、独立运行**的「子应用」，再由一个**主应用（容器 / 基座）**负责加载、路由与整合，最终在主应用的框架内呈现为一个整体。

它解决的不是「代码怎么复用」，而是**「组织怎么协作、系统怎么演进」**——技术只是承载物。

**要解决的问题（四个典型场景）：**

1. **多团队并行**：多个团队维护同一个巨型前端，代码冲突、发布排队、互相阻塞；拆分后各团队自治、独立发布。
2. **技术栈异构**：历史项目用 Vue2 + Webpack，新项目想用 Vue3/React + Vite；不可能一次全量迁移，只能**渐进式**共存。
3. **渐进式重构**：老系统（如 JSP、jQuery、旧 Vue）以子系统为单位逐步替换，而不是「推倒重来」。
4. **独立部署与灰度**：某个模块可以单独上线、单独回滚、单独灰度，不受其他模块牵制。

**核心特征（面试可以背）：**

- **应用级**而非模块级拆分（对比 npm 包的模块级复用）。
- **运行时组合**而非构建时合并（对比 Monorepo 一次构建）。
- **技术栈无关**、独立部署。
- 主应用负责整体框架、路由、登录、导航。

**它带来的代价（一定要说代价，否则答案不完整）：**

| 维度 | 代价 |
| --- | --- |
| 复杂度 | 多仓库、多构建、多版本、多环境，工程链路变长 |
| 通信 | 主子应用、子子应用之间数据传递要设计统一规范 |
| 隔离 | 样式冲突、全局变量污染、事件与定时器副作用 |
| 性能 | 重复依赖（多个 Vue/React 实例）、额外请求、公共库无法共享 |
| 调试 | 多个应用、多层沙箱/iframe，断点定位困难 |
| 体验 | 跨应用跳转、状态保持、弹窗层级、路由同步容易出现割裂感 |
| 治理 | 版本兼容、公共依赖升级、权限与监控需要统一约束 |

**何时不该用：** 团队规模小、应用体量不大、模块间耦合紧密、无法承担额外工程复杂度时，拆分反而增加成本。微前端的收益来自「组织规模」，不是「技术先进」。

```bash
# 典型微前端仓库/部署形态
main-app/                     # 主应用：导航、路由分发、登录、全局状态
  src/App.vue
micro-apps/
  order-app/                  # 子应用 1：Vue3 + Vite，独立仓库、独立 CI
  user-app/                   # 子应用 2：React + Webpack
  old-legacy/                 # 子应用 3：Vue2 老系统，渐进式下线
```

```js
// 主应用的核心动作：按路由把某个子应用「装载」到指定容器里
const routes = [
  { path: '/order', entry: '//order.example.com/entry.html', container: '#sub-view' },
  { path: '/user',  entry: '//user.example.com/entry.html',  container: '#sub-view' },
];
// 主应用只关心「哪个地址挂到哪个容器」，子应用的技术栈完全透明
```

> 面试答题建议：定义 → 四大痛点 → 四大特征 → 代价清单 → 适用边界，最后补一句「微前端本质是组织架构问题在前端架构上的投射」。

**易错点：**

- 微前端不是「把页面拆成多个 Vue 组件」，那是组件化；它是**运行时的应用级组合**。
- 「独立部署」是硬指标：如果子应用必须跟着主应用一起发版，就没有真正拆开。
- 拆分粒度应按**业务域**（团队边界 / 交付边界）而不是按技术分层；按「一个页面一个应用」容易过度拆分。

## 2. 微前端的主流方案对比

按**整合手段**分，主流方案可以归为四类。

**① iframe（最原始、隔离最好）**

- 天然隔离：JS 作用域、CSS、DOM、历史记录、沙箱全部由浏览器保证，最彻底。
- 缺点：URL 主应用无法感知、弹窗/遮罩无法覆盖父页面、滚动与全屏受限、通信要走 `postMessage`、每次切换重新加载导致体验与状态保持差。

**② 路由分发式（single-spa / qiankun）**

- 主应用注册子应用，劫持路由，根据 URL 匹配激活子应用，加载其 HTML 入口并挂载。
- 子应用可复用现有代码，改造小；这是目前**应用级微前端**最常见的一类。

**③ Web Components 增强（micro-app、wujie）**

- micro-app 用 CustomElement 把子应用包成 `<micro-app>` 标签，并结合自研沙箱；接入近乎零改造。
- wujie 用 iframe 承载子应用（隔离），但把 DOM 渲染到主应用文档流（解决弹窗层级问题），相当于「iframe 隔离 + 主文档渲染」。

**④ 模块联邦（Module Federation）**

- 构建期/运行时暴露与共享**模块**（组件、工具函数），不是整个应用；适合「组件级共享、要共享依赖单例」的场景。

| 方案 | 隔离能力 | 通信成本 | 技术栈无关 | 依赖共享 | 接入成本 | 弹窗/层级 | 典型代表 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| **iframe** | 最强（原生沙箱） | 高（postMessage） | 强 | 不能 | 低 | **差** | 传统方案 |
| **路由分发（qiankun）** | 中（沙箱 + 样式隔离） | 中 | 强 | 弱 | 中（子应用需导出生命周期） | 好 | qiankun、single-spa |
| **Web Components（micro-app）** | 中（自研沙箱） | 中 | 强 | 弱 | 低（近乎零改造） | 好 | micro-app、wujie |
| **Module Federation** | 无（模块级） | 低（直接 import） | 需同构建工具 | **强（shared 单例）** | 中 | 好 | Webpack 5、Rspack |
| **原生 Custom Element** | 弱（需自行隔离） | 中 | 中 | 无 | 中 | 好 | 自研组件级 |
| **npm 包 / Monorepo** | 不适用 | 无 | 需统一构建 | 强 | 低 | 好 | 模块级复用（非运行时） |

```html
<!-- ① iframe：隔离彻底，但 URL/层级/通信都有坑 -->
<iframe src="//order.example.com" id="order-frame"></iframe>
```

```js
// ② qiankun：注册 + 启动（路由分发式）
import { registerMicroApps, start } from 'qiankun';
registerMicroApps([
  { name: 'order', entry: '//order.example.com', container: '#sub-view', activeRule: '/order' },
]);
start();
```

```html
<!-- ③ micro-app：一行标签接入，接近零改造 -->
<micro-app name="order" url="http://order.example.com/" baseroute="/order"></micro-app>
```

```js
// ④ Module Federation：从远程应用直接 import 组件（模块级）
const RemoteButton = React.lazy(() => import('orderApp/Button'));
```

**选型思路：**

- 需要**绝对隔离**、页面较独立（如后台工具页）：iframe 或 wujie。
- 需要**应用级拆分成体系**、子应用可复用现有代码：qiankun / micro-app。
- 需要**组件级共享、共享依赖单实例**、统一构建体系：Module Federation。
- 只是代码复用、不涉及独立部署：Monorepo + npm 包，别上微前端。

**易错点：**

- qiankun 与 Module Federation 不是替代关系：前者是**应用级**组合，后者是**模块级**共享，实践中常组合使用。
- micro-app / wujie 的隔离依赖各自的自研沙箱，与 qiankun 实现细节不同，不能混着讲。
- 「技术栈无关」不等于「谁都不用改」：qiankun 要求子应用导出 `bootstrap / mount / unmount`。

## 3. qiankun 的原理

qiankun 是**基于 single-spa 的应用级微前端框架**，在 single-spa 之上补上了 **HTML Entry、JS 沙箱、CSS 隔离、资源预加载** 四块能力。

**① 路由劫持与应用调度（来自 single-spa）**

- 重写 `history.pushState / replaceState`，监听 `popstate`、`hashchange`。
- 每次 URL 变化后，按每个应用注册的 `activeRule` 判断「激活 / 卸载」，调用对应生命周期。
- 核心是「**URL 是唯一事实来源**」，主应用负责路由分发。

**② HTML Entry（`import-html-entry`）**

- 传统 single-spa 要求子应用提供一个 JS Entry（把所有资源打包成一个 JS），接入改造大。
- qiankun 改为让子应用提供一个 **HTML 入口**（就是它自己的 `index.html`）；框架用 `fetch` 拉取该 HTML，用正则解析出：
  - `template`：去掉 script/style 后的 DOM 模板；
  - `scripts`：外部脚本与内联脚本的内容/地址；
  - `styles`：样式链接与内联样式。
- 好处：子应用**几乎零改造**（保持自己 `index.html` 即可），且能自动识别它引入了哪些资源。

**③ 资源加载与执行**

- 框架按需 `fetch` 各个脚本，在 `window.execScript`（本质是 `eval`）中执行，并用沙箱包裹 `window`。
- 样式被注入到子应用容器范围，或做前缀处理。
- 支持 `excludeAssetFilter`、`getPublicPath`、资源预加载等能力。

**④ JS 沙箱（重点）**

| 维度 | 快照沙箱（SnapshotSandbox） | Proxy 沙箱（ProxySandbox） |
| --- | --- | --- |
| 原理 | 记录 `window` 快照，激活时写入、卸载时还原 | 用 `Proxy` + `with` 拦截对 `window` 的读写 |
| 是否污染真实 window | 会（短暂写入后还原） | 不污染，写入落到「代理的假 window」 |
| 多实例 | **不支持** | **支持** |
| 实现复杂度 | 低 | 中 |
| 浏览器要求 | 都行 | 需支持 `Proxy` |

- **快照沙箱**：`activate` 时遍历 `window` 属性存一份「修改前快照」，子应用运行期间对 `window` 的新增/修改被记录，`deactivate` 时把差异还原回去。问题：同一时刻只能跑一个应用。
- **Proxy 沙箱**：把子应用的全局作用域替换为 `new Proxy(window, handler)`，代码在 `with (proxyWindow) {}` 中执行；`get` 时优先从「子应用自己的属性池」取，取不到再落到真实 `window`；`set` 时写进属性池，`window` 无感知。因此多个子应用可**同时**运行互不干扰。
- Vue3 的 `effectScope` / `reactive` 与沙箱思想类似，但 qiankun 是用 `Proxy` 代理「全局对象」而非普通对象。

**⑤ CSS 隔离**

| 配置 | 做法 | 效果 | 代价 |
| --- | --- | --- | --- |
| `strictStyleIsolation: true` | 子应用容器挂 `Shadow DOM`，样式只作用于 shadow 内 | 隔离最彻底 | 部分第三方弹窗（挂到 body）失效、通信受限 |
| `experimentalStyleIsolation: true` | 给子应用所有选择器加前缀 `div[data-qiankun="name"]`，运行时改写 `<style>` | 隔离较彻底，能访问真实 DOM | 仍是实验性，动态插入的样式可能漏掉 |
| 都不开（默认） | 不做隔离，靠命名约定（BEM / CSS Modules） | 无额外成本 | 依赖团队自觉，易冲突 |

**⑥ 资源预加载与启动配置**

```js
start({
  prefetch: 'all',                        // 'all' | 'major' | true | 函数
  singular: false,                        // 是否单实例模式
  sandbox: { strictStyleIsolation: false, experimentalStyleIsolation: true },
  // 预加载的时机：首个应用 mount 之后，用浏览器空闲时间加载其他子应用资源
  // 预加载只下载资源、不执行，避免提前污染
});
```

- `prefetch: 'all'`：首个应用挂载后预取所有子应用资源（不执行），切换时更快。
- `'major'`：只在浏览器空闲时预取。
- 也可以传函数自定义预取策略，加速切换。

**⑦ `loadMicroApp`：手动加载（不依赖路由）**

```js
import { loadMicroApp } from 'qiankun';

const app = loadMicroApp({
  name: 'order',
  entry: '//order.example.com',
  container: '#sub-view',
  props: { user: currentUser },
});
// 需要时手动卸载
app.unmount();
```

**⑧ 子应用要导出的生命周期**

```js
// 子应用入口（Vue3）
let instance = null;
let router = null;

function render(props = {}) {
  const { container } = props;
  router = createRouter({ history: createWebHistory('/order'), routes });
  instance = createApp(App).use(router);
  instance.mount(container ? container.querySelector('#app') : '#app');
}

// 独立运行时直接渲染，被 qiankun 接管时等待通知
if (!window.__POWERED_BY_QIANKUN__) {
  render();
}

export async function bootstrap() { console.log('子应用 bootstrap'); }
export async function mount(props) { render(props); }
export async function unmount() {
  instance?.unmount();
  instance = null;
  router = null;
}
// 可选：update（仅 loadMicroApp 手动加载且配置了时才触发）
```

**易错点：**

- 子应用路由要用 `base` 前缀（如 `createWebHistory('/order')`），否则主应用地址会串到子应用路由。
- 子应用应配置 `output.libraryTarget: 'umd'`、`publicPath` 为绝对地址，否则资源 404。
- 快照沙箱遇到「多个子应用同时存在」会互相踩踏，需要 `Proxy` 沙箱（qiankun 会按浏览器能力自动选择）。
- `strictStyleIsolation` 下子应用挂到 `document.body` 的弹窗不会被 shadow 覆盖，很多组件库弹窗会「跑出去」。

## 4. Module Federation 的原理

**Module Federation（模块联邦）** 是 Webpack 5 引入的**运行时模块共享**机制：让一个构建产物在运行时**动态加载另一个独立构建、独立部署**的应用所暴露的模块，并可共享公共依赖。

**三个核心配置：**

| 配置 | 作用 | 关键点 |
| --- | --- | --- |
| **`exposes`** | 本应用**暴露**出去给别人用的模块 | 如 `{ './Button': './src/components/Button.jsx' }` |
| **`remotes`** | 本应用**消费**的远程应用 | 如 `{ orderApp: 'orderApp@//order.example.com/remoteEntry.js' }` |
| **`shared`** | 多应用共用的依赖（如 react） | 保证**单实例**：`singleton: true` + `requiredVersion` |

**运行时机制：**

1. 消费方在代码里 `import('orderApp/Button')`，运行时 Webpack 会先加载 `orderApp` 的 `remoteEntry.js`（即 `filename` 指向的容器入口）。
2. `remoteEntry.js` 里包含一个**容器模块**，提供两个方法：`init(scope, sharedScope)` 与 `get(module, getScope)`。
3. 消费方调用 `init` 注入自己的 `shared` 作用域，再 `get('./Button')` 取出远程模块的工厂函数并执行，得到模块。
4. `shared` 依赖在 `init` 阶段协商：若已存在满足 `requiredVersion` 的实例则复用（单例），否则加载自己那份。

```js
// 远程应用（order）的 webpack.config.js —— 暴露模块
const { ModuleFederationPlugin } = require('webpack').container;

module.exports = {
  output: { publicPath: '//order.example.com/', uniqueName: 'orderApp' },
  plugins: [
    new ModuleFederationPlugin({
      name: 'orderApp',
      filename: 'remoteEntry.js',
      exposes: {
        './Button': './src/components/Button.jsx',   // 对外暴露的模块
        './utils': './src/utils/index.js',
      },
      shared: {
        react: { singleton: true, requiredVersion: '^18.2.0', eager: false },
        'react-dom': { singleton: true, requiredVersion: '^18.2.0' },
      },
    }),
  ],
};
```

```js
// 消费方（main）的 webpack.config.js —— 消费远程模块
new ModuleFederationPlugin({
  name: 'mainApp',
  remotes: {
    orderApp: 'orderApp@//order.example.com/remoteEntry.js',
  },
  shared: {
    react: { singleton: true, requiredVersion: '^18.2.0' },
    'react-dom': { singleton: true, requiredVersion: '^18.2.0' },
  },
});
```

```jsx
// 消费方使用：像本地模块一样 import，实际是运行时远程加载
import React, { Suspense, lazy } from 'react';
const RemoteButton = lazy(() => import('orderApp/Button'));

export default function App() {
  return (
    <Suspense fallback={<div>加载中…</div>}>
      <RemoteButton />
    </Suspense>
  );
}
```

```ts
// Vite 生态：@originjs/vite-plugin-federation
// vite.config.ts（远程方）
import federation from '@originjs/vite-plugin-federation';

export default {
  plugins: [
    federation({
      name: 'orderApp',
      filename: 'remoteEntry.js',
      exposes: { './Button': './src/components/Button.vue' },
      shared: ['vue'],
    }),
  ],
};
```

**与 qiankun 的区别（常考）：**

| 维度 | qiankun | Module Federation |
| --- | --- | --- |
| 拆分粒度 | **应用级**（整个页面/子应用） | **模块级**（组件/函数） |
| 运行时耦合 | 松（子应用自主路由、独立技术栈） | 较紧（需约定模块协议、同构建体系） |
| 是否管路由 | 是（路由分发是核心） | 否 |
| 依赖共享 | 弱（各自打包，易多实例） | **强**（`shared` 保证单例） |
| 隔离 | 有沙箱与样式隔离 | 无隔离概念（同一运行时） |
| 典型诉求 | 多团队、异构技术栈、独立部署 | 组件复用、跨应用共享依赖 |

**实践要点：**

- `shared` 的 `singleton: true` 是解决「两个 React / 两个 Vue」的关键；`requiredVersion` 不匹配会告警甚至加载失败。
- `eager: true` 会把该依赖打进初始包（体积变大但避免额外请求），一般只在「主机应用必用」的依赖上开。
- 远程地址可以**运行时动态指定**：把 `remotes` 写成占位，运行时通过 `window.orderAppUrl` 或环境变量注入，便于多环境部署。

**易错点：**

- 远程应用必须把 `publicPath` 配成**绝对地址**（含域名），否则 `remoteEntry.js` 里的相对路径会 404。
- 生产环境要用 **`uniqueName`** 避免多个 Webpack 运行时的 chunk 冲突（每个 chunk 名会带 `uniqueName` 前缀）。
- 版本不匹配的 `shared` 依赖可能导致「加载两份」或「用错版本」，必须显式声明 `requiredVersion` 并做兼容。
- MF 与 qiankun 混用时，注意 qiankun 沙箱代理的 `window` 可能影响 MF 的全局运行时查找。

## 5. 微前端的 CSS 隔离与 JS 沙箱

微前端把多个应用塞进同一个 `document` 与同一个 `window`，**隔离**是绕不开的问题，分「样式隔离」与「JS 沙箱」两条线。

**样式（CSS）隔离方案对比：**

| 方案 | 做法 | 隔离程度 | 优点 | 缺点 |
| --- | --- | --- | --- | --- |
| **Shadow DOM** | 容器 `attachShadow({ mode: 'open' })`，样式只作用于 shadow 内部 | 最强 | 原生、无需改写选择器 | body 级弹窗逃逸、第三方库兼容差 |
| **命名空间前缀** | 构建时/运行时给选择器加前缀（`postcss-prefix-selector`） | 较强 | 不改组件代码、能覆盖真实 DOM | 前缀长、动态插入样式可能漏 |
| **CSS Modules** | 类名编译为唯一哈希（`styles.title`） | 中 | 自然、局部作用域 | 只对用它的代码生效，第三方库无效 |
| **BEM / 命名约定** | 类名前缀（`order__button`） | 弱 | 零成本 | 全靠自觉、易冲突 |
| **iframe** | 独立文档 | 最强 | 彻底 | 通信、层级、性能问题 |
| **scoped（Vue SFC）** | 编译加 `data-v-xxx` 属性选择器 | 中 | 组件内自动生效 | 只作用于本组件样式 |

```js
// ① Shadow DOM 隔离（qiankun strictStyleIsolation 就是这种思路）
const shadow = container.attachShadow({ mode: 'open' });
shadow.innerHTML = subAppHtml;   // 子应用渲染在 shadow 内，外部样式进不来
```

```js
// ② 命名空间前缀：postcss-prefix-selector（构建期给所有选择器加前缀）
// postcss.config.js
module.exports = {
  plugins: {
    'postcss-prefix-selector': {
      prefix: '#sub-app-order',        // 所有选择器前加该前缀
      // 让 :root / html / body 这类选择器也能被正确处理
      transform(prefix, selector, prefixedSelector) {
        if (selector === ':root' || selector === 'html' || selector === 'body') {
          return prefix;
        }
        return prefixedSelector;
      },
    },
  },
};
```

```vue
<!-- ③ Vue scoped：编译后转换成带属性选择器的规则 -->
<style scoped>
.title { color: red; }
</style>
<!-- 输出：.title[data-v-7ba5bd90] { color: red; } -->
```

**JS 沙箱：**

**为什么需要**：子应用可能改写 `window` 全局变量、注册未清理的定时器/事件监听/`requestAnimationFrame`、改写 `history`/`location` 等。若不隔离，切换应用后会「串味」、内存泄漏。

| 类型 | 原理 | 多实例 | 说明 |
| --- | --- | --- | --- |
| **快照沙箱** | 激活时快照 `window`，卸载时 diff 还原 | 否 | 实现简单，只能单实例 |
| **Proxy 沙箱** | `with` + `Proxy(window)` 拦截读写 | **是** | 主流，写落到假 window |
| **无沙箱** | 不做隔离，靠代码规范 | — | 性能最好但风险高 |

```js
// 快照沙箱（简化实现）：记录并还原 window 差异
class SnapshotSandbox {
  constructor() {
    this.modifiedProps = {};
    this.windowSnapshot = {};
  }
  active() {
    // 1. 先给真实 window 拍快照
    for (const key in window) this.windowSnapshot[key] = window[key];
    // 2. 把上次运行残留的修改重新写回
    Object.keys(this.modifiedProps).forEach((key) => { window[key] = this.modifiedProps[key]; });
  }
  inactive() {
    for (const key in window) {
      if (window[key] !== this.windowSnapshot[key]) {
        this.modifiedProps[key] = window[key];   // 记录差异
        window[key] = this.windowSnapshot[key];  // 还原
      }
    }
  }
}
```

```js
// Proxy 沙箱（简化实现）：用 with + Proxy 把读写劫持到「假 window」
class ProxySandbox {
  constructor() {
    const rawWindow = window;
    const fakeWindow = Object.create(null);   // 子应用自己的属性池
    this.proxy = new Proxy(fakeWindow, {
      get: (target, key) => (key in target ? target[key] : rawWindow[key]),
      set: (target, key, value) => { target[key] = value; return true; },
      // 关键：全局变量写入 fakeWindow，真实 window 不受影响
    });
  }
}

// 用 Function 包裹执行子应用脚本，with 的全局对象被换成代理
const script = `with (window) { console.log('这里的 window 是代理对象'); }`;
new Function('window', script)(sandbox.proxy);
```

**副作用清理（比沙箱更重要）：** 沙箱能拦住「写 window」，但拦不住**定时器、事件监听、订阅**：

```js
// 子应用应自己在 unmount 生命周期里清理
let timer = null;
let onResize = () => { /* ... */ };

export function mount() {
  timer = setInterval(poll, 3000);
  window.addEventListener('resize', onResize);
}
export function unmount() {
  clearInterval(timer);
  window.removeEventListener('resize', onResize);
  store.destroy();          // 清理订阅
}
```

**易错点：**

- Shadow DOM 隔离下，挂到 `document.body` 的弹窗、`document.createElement('div')` 追加到文档的节点**不受 shadow 约束**，UI 组件库弹窗容易逃逸。
- `strictStyleIsolation` 与 `experimentalStyleIsolation` 一般**只开一个**，同时开会互相干扰。
- 快照沙箱在「同时激活两个子应用」时会互相还原，产生难以复现的 bug，应使用 Proxy 沙箱。
- 沙箱防不住对 `document` 的全局操作，页面级隔离仍要谨慎。

## 6. 微前端的通信方案

通信要明确两个问题：**方向（谁给谁）** 与 **时机（何时同步）**。总体原则是「**主应用下发、子应用订阅**」，避免子应用反向控制主应用。

| 方案 | 方向 | 耦合度 | 适用场景 | 缺点 |
| --- | --- | --- | --- | --- |
| **props 传参** | 主 → 子 | 低 | 初始化时的用户、token、路由信息 | 只能初始化传，动态更新要配合状态方案 |
| **全局状态（initGlobalState）** | 双向可订阅 | 中 | 跨应用共享的登录态、主题、语言 | 需主子应用都遵守同一套 API |
| **CustomEvent / 事件总线** | 双向 | 低 | 松耦合的「发生了某事」通知 | 事件名易冲突、难追踪 |
| **URL / query / 路由参数** | 双向 | 最低 | 页面级参数传递、分享链接 | 不适合大数据、易暴露 |
| **localStorage / sessionStorage** | 跨页面 | 低 | 持久的用户偏好、登录态 | 需监听 `storage` 事件、同步问题 |
| **框架内置 API** | 主 → 子 | 低 | micro-app 的 `data`、qiankun 的 props | 依赖具体框架 |

**① props：主应用在注册/加载时下发给子应用**

```js
// 主应用注册时传 props
import { registerMicroApps } from 'qiankun';
registerMicroApps([
  {
    name: 'order',
    entry: '//order.example.com',
    container: '#sub-view',
    activeRule: '/order',
    props: { user: currentUser, tenantId: 't-001', onLogout: () => logout() },
  },
]);
```

```js
// 子应用 mount 时接收
export async function mount(props) {
  const { user, tenantId, onLogout } = props;
  // 把主应用下发的能力接到子应用内部
}
```

**② 全局状态：qiankun 的 `initGlobalState`**

```js
// 主应用：初始化全局状态（只做一次）
import { initGlobalState } from 'qiankun';
const actions = initGlobalState({ user: null, theme: 'light' });

actions.onGlobalStateChange((state, prevState) => {
  // 主应用订阅状态变化
  console.log('主应用收到:', state, '上一次:', prevState);
}, true);   // 第二参数 true 表示立即触发一次

actions.setGlobalState({ theme: 'dark' });  // 修改状态 → 会同步给所有子应用
```

```js
// 子应用：在 mount 的 props 里拿到 actions，订阅并（必要时）修改
export async function mount(props) {
  props.onGlobalStateChange((state) => {
    document.body.dataset.theme = state.theme;   // 子应用响应状态
  }, true);

  // qiankun 推荐子应用尽量避免直接改主应用状态，改为通知主应用
  props.setGlobalState({ lastVisited: '/order/list' });
}
```

**③ 事件总线：发布订阅（跨应用松耦合）**

```js
// 用 mitt 做轻量事件总线，主 / 子应用都共享同一个实例
import mitt from 'mitt';
export const bus = mitt();   // 实践中常由主应用创建并挂到全局或通过 props 下发

// 子应用 A 发布
bus.emit('order:created', { id: 1024 });

// 子应用 B 订阅
const handler = (payload) => console.log('收到订单创建:', payload);
bus.on('order:created', handler);

// 组件卸载时取消订阅，避免内存泄漏
bus.off('order:created', handler);
```

**④ CustomEvent：利用浏览器原生事件机制**

```js
// 子应用派发（挂在共同可访问的 window 上）
window.dispatchEvent(new CustomEvent('app:theme-change', { detail: { theme: 'dark' } }));

// 主应用监听
window.addEventListener('app:theme-change', (e) => {
  console.log(e.detail.theme);
});
```

**⑤ micro-app 的内置通信**

```js
// 主应用给子应用下发数据，并监听子应用数据变化
const microApp = document.querySelector('micro-app[name="order"]');
microApp.setData({ user });
microApp.addEventListener('datachange', (e) => console.log(e.detail.data));
```

**易错点：**

- `initGlobalState` 只能在**主应用**初始化一次；子应用只订阅、不重复初始化。
- 事件总线如果每个子应用引入各自实例，会「各说各话」；必须共享同一个实例（或通过主应用 props 下发）。
- 子应用卸载时必须 `off` 掉订阅与监听，否则下次挂载会重复触发。
- 全局状态只管「共享的少量数据」（用户、主题、权限），页面数据尽量走各自的后端接口，避免全局状态成为新的耦合点。

## 7. 如何实现一个脚手架 CLI

脚手架的职责：**把「新建项目 / 新增模块」的重复劳动自动化**——询问、取模板、渲染、安装依赖、初始化 Git。

**核心原理：**

1. **`bin` 字段 + shebang**：让 npm 在安装后把命令链接到 `node_modules/.bin`，并指明用 node 执行。

```json
{
  "name": "@scope/create-my-app",
  "version": "1.0.0",
  "type": "module",
  "bin": {
    "create-my-app": "./bin/index.js"
  }
}
```

```js
#!/usr/bin/env node
// 文件第一行必须是 shebang，否则 CLI 无法被直接执行
console.log('CLI 启动');
```

2. **参数解析（`commander`）**：支持 `create-my-app my-app --template vue-ts --no-install`。
3. **交互式询问（`inquirer`）**：让用户选择模板、是否装依赖、是否初始化 Git。
4. **拉取模板（`download-git-repo` / `degit`）**：从 GitHub/GitLab 或私有仓库下载模板；`degit` 只拉最新快照、不带 `.git`。
5. **模板渲染（`ejs` / `handlebars`）**：把项目名、作者、描述等变量填进模板文件。
6. **收尾**：`fs-extra` 复制与清理、`ora` 进度提示、`chalk` 颜色、自动 `pnpm install`、`git init`。

```js
#!/usr/bin/env node
// bin/index.js —— 完整可运行示例
import { Command } from 'commander';
import inquirer from 'inquirer';
import download from 'download-git-repo';
import path from 'node:path';
import fs from 'fs-extra';
import ejs from 'ejs';
import ora from 'ora';
import chalk from 'chalk';

const program = new Command();

program
  .name('create-my-app')
  .description('创建一个前端项目')
  .version('1.0.0')
  .argument('[projectName]', '项目名称')
  .option('-t, --template <name>', '模板名称')     // 不给默认值，未指定时走交互
  .option('--no-install', '不自动安装依赖')
  .action(async (projectName, options) => {
    // 1. 项目名：命令行没给就交互询问
    if (!projectName) {
      const res = await inquirer.prompt([
        { type: 'input', name: 'projectName', message: '请输入项目名称：', default: 'my-app' },
      ]);
      projectName = res.projectName.trim();
    }

    // 2. 模板选择：命令行没指定时让用户选
    const templates = {
      'vue-ts': 'your-org/template-vue-ts#main',
      'react-ts': 'your-org/template-react-ts#main',
      lib: 'your-org/template-lib#main',
    };
    if (!options.template || !templates[options.template]) {
      const res = await inquirer.prompt([
        {
          type: 'list',
          name: 'template',
          message: '请选择模板：',
          choices: [
            { name: 'Vue3 + TS + Vite', value: 'vue-ts' },
            { name: 'React + TS + Vite', value: 'react-ts' },
            { name: 'Vue3 组件库', value: 'lib' },
          ],
        },
      ]);
      options.template = res.template;
    }

    const targetDir = path.join(process.cwd(), projectName);

    // 3. 拉取模板：owner/repo#branch，可指向私有仓库
    const spinner = ora('正在下载模板…').start();
    await new Promise((resolve, reject) => {
      download(templates[options.template], targetDir, { clone: false }, (err) =>
        err ? reject(err) : resolve(),
      );
    });
    spinner.succeed(chalk.green('模板下载完成'));

    // 4. 渲染模板：把项目名等变量写进文件
    const pkgPath = path.join(targetDir, 'package.json');
    const pkg = await fs.readJson(pkgPath);
    pkg.name = projectName.toLowerCase();
    await fs.writeJson(pkgPath, pkg, { spaces: 2 });

    const readmeTpl = await fs.readFile(path.join(targetDir, 'README.ejs'), 'utf-8');
    await fs.writeFile(
      path.join(targetDir, 'README.md'),
      ejs.render(readmeTpl, { projectName, author: process.env.USER || 'unknown' }),
    );
    await fs.remove(path.join(targetDir, 'README.ejs'));

    // 5. 初始化 Git（可选）
    const { initGit } = await inquirer.prompt([
      { type: 'confirm', name: 'initGit', message: '是否初始化 Git？', default: true },
    ]);
    if (initGit) {
      const { execa } = await import('execa');
      await execa('git', ['init'], { cwd: targetDir });
    }

    // 6. 提示后续命令
    console.log(chalk.cyan(`\n项目已创建：${targetDir}`));
    console.log(`\n  cd ${projectName}`);
    if (options.install !== false) console.log('  pnpm install');
    console.log('  pnpm dev\n');
  });

program.parse();
```

```bash
# 本地调试：把当前包 link 到全局，直接测试命令
npm link
create-my-app demo --template react-ts

# 发布
npm publish --access public
# 用户使用
npx create-my-app@latest my-app
```

**关键设计点：**

- 模板仓库与 CLI 分离：模板更新不需要发新版本 CLI，只需 `git push`。
- 用 `degit`（`npx degit owner/repo#branch target`）可避免拉取完整 Git 历史，更快、更干净。
- 交互库 `inquirer` 的 `prompt` 是异步的，注意 `await` 与错误处理。
- 支持 `--template`、`--no-install` 等参数，让 CLI 既能交互也能被 CI 静默调用。

**易错点：**

- Windows 下 `download-git-repo` 依赖本机 `git` 命令，需保证环境已安装 Git；`clone: false` 的 tarball 方式在部分私有源不可用。
- 忘记 shebang 时，用 `node bin/index.js` 测试正常、安装后执行却报错（权限 / CRLF）。
- 项目名与 npm 包名规则不一致：目录名要校验（不能含大写、空格），`package.json` 的 `name` 还要小写化。
- 目标目录已存在时应先询问是否覆盖，避免误删用户文件。

## 8. 组件库的工程化实践

组件库工程化要解决四件事：**怎么构建、怎么分发、怎么按需引入、怎么保证质量与文档**。

**① 构建：库模式 + 多入口**

```ts
// vite.config.ts —— 组件库构建配置
import { defineConfig } from 'vite';
import vue from '@vitejs/plugin-vue';
import dts from 'vite-plugin-dts';
import path from 'node:path';

export default defineConfig({
  plugins: [
    vue(),
    dts({ insertTypesEntry: true, include: ['src'], outputDir: 'dist/types' }),  // 生成 .d.ts
  ],
  build: {
    lib: {
      entry: path.resolve(__dirname, 'src/index.ts'),   // 总入口
      name: 'MyUI',
      fileName: (format) => `my-ui.${format}.js`,        // es / umd
      formats: ['es', 'umd'],
    },
    rollupOptions: {
      // 关键：把框架交给宿主，不要打进产物
      external: ['vue', 'vue-router'],
      output: { globals: { vue: 'Vue' } },               // UMD 下映射到全局变量
    },
  },
});
```

**为什么必须 `external` + `peerDependencies`：** 组件库若把自己用到的 `vue` 打包进去，使用者的应用会出现**两个 Vue 实例**，导致 `provide/inject`、响应式、插件全部失效。正确做法是把 `vue` 声明为 `peerDependencies`，构建时 `external` 掉。

```json
{
  "name": "@scope/my-ui",
  "version": "0.1.0",
  "main": "./dist/my-ui.umd.js",
  "module": "./dist/my-ui.es.js",
  "types": "./dist/types/index.d.ts",
  "exports": {
    ".": {
      "types": "./dist/types/index.d.ts",
      "import": "./dist/my-ui.es.js",
      "require": "./dist/my-ui.umd.js"
    },
    "./style.css": "./dist/style.css"
  },
  "files": ["dist"],
  "sideEffects": ["**/*.css"],
  "peerDependencies": { "vue": ">=3.3.0" }
}
```

**② 按需引入**

| 方案 | 原理 | 适用 |
| --- | --- | --- |
| **每个组件独立入口** | `exports` 暴露 `./button` 子路径，使用者 `import '@scope/my-ui/button'` | 通用、最稳 |
| **`unplugin-vue-components`** | 编译期自动 import 组件 + 样式（Vite 插件） | Vue 项目，零手工 import |
| **`babel-plugin-import`** | 转换 `import { Button } from 'my-ui'` → 按路径引入 | 老项目 / 非 Vite |
| **全量注册** | `app.use(MyUI)`，体积大 | 内部系统、不关心体积 |

```ts
// 使用者：Vite + unplugin-vue-components 自动按需引入
import Components from 'unplugin-vue-components/vite';
import { MyUIResolver } from '@scope/my-ui/resolver';   // 组件库提供的解析器

export default {
  plugins: [
    Components({
      resolvers: [MyUIResolver()],   // 用到 <MyButton> 时自动引入组件和样式
    }),
  ],
};
```

**③ 类型声明**

- 用 `vite-plugin-dts` / `rollup-plugin-dts` 从源码生成 `.d.ts`；Vue SFC 需配合 `vue-tsc`。
- 入口 `index.d.ts` 要 `export` 所有组件与类型，`exports.types` 要指对。
- 可提供 `GlobalComponents` 声明，让使用者模板里获得组件名与 props 补全。

**④ 文档与示例（VitePress / Storybook）**

- VitePress：适合「中文文档 + API 表格 + 可运行示例」的组件库官网。
- Storybook：适合组件开发时逐个调试、视觉回归与交互测试。

```md
<!-- docs/components/button.md -->
# Button 按钮

常用操作按钮。

## 基础用法

<preview path="./demos/button/basic.vue" />

## API

| 属性 | 说明 | 类型 | 默认值 |
| --- | --- | --- | --- |
```

## 9. SSR 的工程化实现

**SSR（Server-Side Rendering）**：在同一份前端代码上，服务端**先渲染出 HTML 字符串**返回给浏览器（解决首屏白屏与 SEO），浏览器拿到后**再「水合」**接管为可交互的客户端应用。核心词是**同构（Isomorphic / Universal）**：同一份业务代码，两端都能跑。

| 维度 | CSR（客户端渲染） | SSR（服务端渲染） | SSG（静态生成） | ISR（增量静态再生） |
| --- | --- | --- | --- | --- |
| 首屏 | 慢（白屏等 JS） | **快**（直接有 HTML） | 最快（预生成静态文件） | 快 |
| SEO | 差 | **好** | 好 | 好 |
| 服务器成本 | 低（纯静态） | 高（每次请求都要渲染） | 极低（CDN 分发） | 中（定时/按需再生） |
| 数据实时性 | 每次请求实时 | 每次请求实时 | 构建时固定 | 定时/按需更新 |
| 适用 | 后台、强交互应用 | 电商、资讯、需 SEO | 博客、文档、营销页 | 内容会更新但无需实时 |
| 框架/方案 | 纯 SPA | Nuxt / Next | VitePress / Astro | Next.js 的 ISR |

**① 项目结构（同构）**

```text
my-ssr-app/
├── index.html                # 模板，含 <!--app-html--> 占位
├── src/
│   ├── main.ts               # 创建应用（两端共用）
│   ├── App.vue
│   ├── entry-client.ts       # 客户端入口：hydrate + 挂载
│   └── entry-server.ts       # 服务端入口：导出 render 函数
├── server.js                 # Express：把渲染结果拼进 HTML 返回
└── vite.config.ts            # 用 Vite 分别构建 client / server 两套产物
```

**② 两端入口**

```ts
// src/main.ts —— 两端共用的应用工厂
import { createSSRApp } from 'vue';
import { createRouter } from './router.js';
import App from './App.vue';

export function createApp() {
  const app = createSSRApp(App);      // SSR 版本的应用实例
  const router = createRouter();
  app.use(router);
  return { app, router };
}
```

```ts
// src/entry-client.ts —— 客户端：水合而非重新挂载
import { createApp } from './main.js';

const { app, router } = createApp();
router.isReady().then(() => {
  app.mount('#app');   // SSR 产物已存在，这里是「水合」，复用服务端 DOM
});
```

```ts
// src/entry-server.ts —— 服务端：输出 HTML 字符串
import { renderToString } from 'vue/server-renderer';
import { createApp } from './main.js';

export async function render(url) {
  const { app, router } = createApp();
  await router.push(url);                    // 按请求地址定位路由
  await router.isReady();
  const html = await renderToString(app);    // 渲染为 HTML 字符串
  return html;
}
```

**③ 服务端把 HTML 拼起来返回**

```js
// server.js（Express）
import express from 'express';
import fs from 'node:fs';
import { render } from './src/entry-server.js';

const app = express();
// 读取构建产物中的模板
let template = fs.readFileSync('./dist/client/index.html', 'utf-8');

app.get('*', async (req, res) => {
  try {
    const appHtml = await render(req.originalUrl);   // 关键：把 URL 传进渲染
    const html = template.replace('<!--app-html-->', appHtml);
    res.status(200).set({ 'Content-Type': 'text/html' }).end(html);
  } catch (e) {
    // 降级：SSR 出错时退回纯 CSR 模板，保证页面不 500
    res.status(200).set({ 'Content-Type': 'text/html' }).end(template);
  }
});

app.listen(3000);
```

**④ 数据预取：SSR 的核心难点**

客户端渲染时，数据是「挂载后请求」；SSR 必须**在服务端就拿到数据并渲染进 HTML**，否则首屏仍是空的。

```ts
// entry-server.ts —— 服务端预取数据并注入初始状态
export async function render(url) {
  const { app, router, store } = createApp();
  await router.push(url);
  await router.isReady();

  // 找出当前匹配的组件，调用其自定义的 asyncData / prefetch
  const matched = router.currentRoute.value.matched;
  const preloads = matched
    .map((record) => record.components?.default?.asyncData)
    .filter(Boolean);
  await Promise.all(preloads.map((fn) => fn({ store, route: router.currentRoute.value })));

  const html = await renderToString(app);
  // 把状态序列化，随 HTML 一起下发；客户端水合时读取并复用，避免二次请求
  return { html, state: JSON.stringify(store.state) };
}
```

```html
<!-- index.html 模板中注入初始状态（由服务端替换占位与状态） -->
<script>window.__INITIAL_STATE__ = /* 服务端注入 */</script>
```

```ts
// entry-client.ts —— 客户端读取服务端下发的状态
const { store } = createApp();
store.replaceState(window.__INITIAL_STATE__);   // 复用服务端数据，不再重复请求
```

**⑤ 流式渲染（大页面优化）**

```ts
// React：renderToPipeableStream，边渲染边输出，比 renderToString 更快出首屏
import { renderToPipeableStream } from 'react-dom/server';
import App from './App';

app.get('*', (req, res) => {
  const { pipe } = renderToPipeableStream(<App url={req.url} />, {
    onShellReady() {          // 外壳就绪即刻响应，后面的内容流式补齐
      res.setHeader('Content-Type', 'text/html');
      pipe(res);
    },
    onError(err) { console.error(err); },
  });
});
```

| API | 特点 | 场景 |
| --- | --- | --- |
| `renderToString` | 同步、字符串一次性返回，最简单 | 中小页面 |
| `renderToPipeableStream` | 流式，外壳先返回，可配 `Suspense` | 大页面、React 18+ |
| `renderToStaticMarkup` | 不生成水合标记，纯静态 | 邮件、非交互页 |

**⑥ 常见难题与对策**

| 难题 | 对策 |
| --- | --- |
| 服务端没有 `window`/`document` | 只在 `onMounted` 等生命周期内访问；用 `typeof window !== 'undefined'` 守卫 |
| 水合不匹配（Hydration mismatch） | 两端渲染结果必须一致：避免随机数、当前时间、`localStorage` 参与首屏渲染 |
| 样式收集 | 用 `ssrContext.modules` 或 Vite 的 `assets` 收集 CSS 一并注入 |
| 性能与缓存 | 页面级缓存（Redis/CDN）、接口层缓存、只对有 SEO 需求的页面开启 SSR |
| 第三方库不支持 SSR | 动态 `import()` 客户端专属库，或用 `<ClientOnly>` 包裹 |

```ts
// 处理 window 不存在的守卫
const isServer = typeof window === 'undefined';
if (!isServer) {
  // 只有客户端才执行的逻辑
  window.addEventListener('resize', onResize);
}
```

**易错点：**

- 水合不匹配是 SSR 最常见的线上 bug：服务端渲染的内容与客户端首次渲染不一致，Vue 会丢弃重渲染、React 会告警并降级为客户端渲染，造成闪烁与性能损失。
- SSR 并没有让「接口变快」，它只是把「首屏数据请求」提前到服务端；客户端的水合仍然要跑一遍 JS。
- 不是所有页面都值得 SSR：强交互后台用 CSR 更简单；只有首屏/SEO 关键页开 SSR，其余可走 CSR 或 SSG。
- Nuxt / Next 是「约定式 SSR 框架」，它们把入口、数据预取、路由、缓存都封装好了；手写 SSR 更应理解其原理而非重复造轮子。

## 10. 跨端与多端工程化方案

「跨端」指用**一套代码**覆盖多个运行环境（H5 / 小程序 / App / 桌面）。核心矛盾是：**复用率越高，性能与原生能力越受限**。

| 方案 | 技术栈/语法 | 覆盖端 | 渲染方式 | 性能 | 生态成熟度 | 典型适用 |
| --- | --- | --- | --- | --- | --- | --- |
| **uni-app** | Vue（含 Vue3） | H5 / 小程序（全集）/ App / 快应用 | 编译为各端原生组件 | 中 | 高（国内） | 多端小程序、快速铺开 |
| **Taro** | React / Vue | H5 / 小程序 / RN | 编译 + 各端适配层 | 中 | 高 | React 团队、多端小程序 |
| **React Native** | React | iOS / Android | 原生组件 + JS 逻辑 | 高 | 高 | 原生体验的 App |
| **Flutter** | Dart | iOS / Android / Web / 桌面 | 自绘引擎（Skia / Impeller） | 很高 | 高 | 追求一致性 UI 的 App |
| **Electron** | 任意 Web 技术 | Windows / macOS / Linux | 内嵌 Chromium | 中（体积大） | 高 | 桌面应用（VSCode 类） |
| **Tauri** | Web + Rust | 桌面 | 系统 WebView + Rust 后端 | 高（体积小） | 中 | 轻量桌面应用 |

**① uni-app：一份 Vue 代码编译到多端**

```vue

    <!-- #endif -->
  </view>
</template>

<script setup>

// #ifdef APP-PLUS

// #endif
</script>
```

**④ 选型要点：**

- **只要小程序 + H5**：uni-app 或 Taro，不必引入 RN / Flutter。
- **要原生体验的 App**：RN（Web 团队容易上手）或 Flutter（UI 一致性好、性能强）。
- **桌面端**：Electron 生态最成熟但体积大；Tauri 体积小、性能好，但需要 Rust、生态较新。
- **多端不等于一套代码跑全部**：业务逻辑可复用，但每个平台都会有条件编译与适配层，需预留人力。

**易错点：**

- 跨端的性能瓶颈往往在**列表长滚动、复杂动画、大数据渲染**，这些是各方案差异最大的地方。
- 小程序有包体积限制，跨端框架的运行时和适配层会占掉一部分，拆分主包/分包要提前规划。
- uni-app / Taro 编译到 App 本质是「原生渲染 + JS 桥」，与 Flutter 的自绘路线完全不同，性能模型不可类比。
- Electron 体积大主要来自 Chromium；用 Tauri 可显著减小，但要接受各平台系统 WebView 的差异。

## 11. 依赖治理与私有 registry

依赖治理解决三类问题：**环境一致性（Node / 包管理器版本）、依赖来源（私有源）、依赖安全与更新（版本锁定与自动升级）**。

## 12. 前端供应链安全

前端供应链攻击的典型路径：**你安装了被投毒的依赖，它在你本地 / CI 执行恶意代码，或窃取环境中的密钥**。

**① 常见攻击面**

| 攻击类型 | 说明 | 例子 |
| --- | --- | --- |
| **投毒 / 抢注（typosquatting）** | 包名与知名包相似，诱导装错 | `crossenv` vs `cross-env`、`lodahs` |
| **依赖混淆（dependency confusion）** | 私有包名撞上公共包，公共源的高版本被优先装上 | 公司私有包名被攻击者抢注同版本号 |
| **`postinstall` 脚本** | 安装时自动执行任意脚本，可窃取 token、挖矿 | `preinstall` / `postinstall` 中的恶意代码 |
| **锁文件篡改** | 篡改 `lock` 中的 `resolved` 地址或 `integrity` | 指向攻击者自建 registry |
| **维护者账号被盗** | 正规包被注入恶意版本 | `event-stream`、`ua-parser-js` 事件 |
| **构建产物注入** | CI 中被污染的环境变量或缓存 | 密钥泄露到打包产物 |

**② 防护手段**

```bash
# 1. 安装时忽略所有生命周期脚本（最有效的第一道防线）
npm install --ignore-scripts
# 全局默认关闭（写进 .npmrc）：
echo "ignore-scripts=true" >> .npmrc
```

```bash
# 2. CI 严格按 lock 安装，禁止改写，拒绝人为干预
npm ci
pnpm install --frozen-lockfile

# 3. 强制校验 integrity（npm 默认开启），并锁定 registry
npm config set registry https://npm.your-company.com/
npm config set strict-ssl true
```

```bash
# 4. 依赖漏洞扫描与 SBOM 生成
npx osv-scanner --lockfile=pnpm-lock.yaml
# 生成 CycloneDX 格式 SBOM（软件物料清单）
npx @cyclonedx/cyclonedx-npm --output-file sbom.json
```

```yaml
# 5. npm provenance（可信发布）：GitHub Actions 中带 --provenance 发布
- run: npm publish --provenance --access public
  env:
    NODE_AUTH_TOKEN: ${{ secrets.NPM_TOKEN }}
```

**为什么 `provenance` 有用：** 它把「这个包由哪个仓库、哪次提交、哪条 CI 流水线构建出来」以**加密签名**的形式附在包上（Sigstore），使用者可以验证包的真实来源，而不是只信任 registry 上的一段文本。

**③ 防御清单（可当答案收尾）**

1. **最小化依赖**：能不引入的库就不引入，减少攻击面。
2. **锁定来源**：统一 registry、`--frozen-lockfile`、校验 `integrity`。
3. **关闭脚本**：`ignore-scripts=true`；确需脚本时手动执行白名单依赖。
4. **持续扫描**：`npm audit` / `osv-scanner` / SCA 工具接入 CI。
5. **可信发布**：`npm provenance`、发布用 OIDC Token 而非长期密钥、开启 2FA。
6. **审计与告警**：关注镜像源同步延迟、CI 中密钥最小权限、产物中禁止明文密钥。
7. **物料清单**：生成 SBOM，出问题能快速定位「哪个版本、哪个包受影响」。

**易错点：**

- `ignore-scripts=true` 会同时禁掉 `esbuild`、`sharp`、`husky` 等依赖的安装后脚本，可能导致它们不可用；团队需要评估并给白名单。
- 私有源的 `@scope` 包要确保**同名公共包无法覆盖**，把 `@scope:registry` 配到私有源并校验来源。
- `npm audit` 只覆盖已知漏洞库，对新出现的投毒包（尚未进入漏洞库）无效，必须靠「来源可信 + 脚本关闭」等策略兜底。

## 13. 现代前端工具链趋势

核心趋势可以概括为三句话：**编译/构建工具用原生语言重写、开发期不打包、工具链走向一体化**。

**① 用 Rust / Go 重写热点工具**

| 工具 | 语言 | 定位 | 说明 |
| --- | --- | --- | --- |
| **SWC** | Rust | JS/TS 编译器 | Babel 的高性能替代，主打转译与压缩 |
| **esbuild** | Go | 打包 / 转译 | 极快，Vite 依赖它做依赖预构建与转译 |
| **Rspack** | Rust | Webpack 兼容打包器 | API 兼容 Webpack 5，迁移成本低，速度大幅提升 |
| **Turbopack** | Rust | 增量打包器 | Next.js 官方主推，增量与缓存能力强 |
| **oxc / oxlint** | Rust | 解析器 + Lint | 面向 JS/TS 的解析与 Lint，速度对标 Rust 生态 |
| **Rolldown** | Rust | Rollup 的 Rust 版 | Vite 未来统一的打包内核 |
| **Biome** | Rust | Lint + Format | 一站式替代 ESLint + Prettier 的方向 |

**② 开发期「不打包」与原生 ESM**

- Vite 的思路：开发时**按需编译**（基于浏览器原生 ESM，一个模块一个请求），冷启动几乎与项目规模无关；生产构建再交给 Rollup / Rolldown。
- 对比 Webpack 的「先打包成 bundle 再启动 dev server」，规模越大启动越慢。
- 代价：浏览器请求数变多，需依赖预构建（把 CJS / 大量内部文件合并）来优化。

**③ Vite 生态一体化**

| 工具 | 定位 |
| --- | --- |
| **Vite** | 开发服务器 + 构建工具 |
| **Rolldown / rolldown-vite** | Rust 打包内核，替换 Rollup，进一步提升构建速度 |
| **Vitest** | 复用 Vite 配置的测试框架，与开发环境一致 |
| **VitePress** | 基于 Vite 的静态站点生成器（文档站） |
| **unplugin 系列** | 跨 Vite / webpack / Rollup 的统一插件写法 |

**④ WebContainer：浏览器里的 Node**

- WebContainer 让 Node.js 运行在浏览器内（不用远程容器 / VM），可直接在页面里跑 `npm install`、`vite dev`。
- 典型用途：在线 IDE（如 StackBlitz）、文档里的「可运行示例」。
- 限制：纯前端运行，性能受限于浏览器，不适合重负载或需要系统能力的场景。

**⑤ 趋势小结**

| 趋势 | 表现 | 收益 |
| --- | --- | --- |
| 原生语言重写 | Rust / Go 实现编译器、打包器、Lint | 十倍量级的启动 / 构建提速 |
| 按需编译 | 开发期不打包、原生 ESM | 冷启动与项目规模解耦 |
| 一体化 | 构建、测试、文档共用一个内核与配置 | 减少配置割裂与工具重复 |
| 平台化 | WebContainer、Nx / Turborepo 等编排 | 统一浏览器内或大仓库中的开发体验 |

```bash
# 体验新的 Rust 工具链
npx @rspack/cli build              # Webpack 兼容的 Rust 打包器
npx rolldown-vite build            # 用 Rolldown 内核的 Vite
npx oxlint                         # Rust 实现的 Lint
```

```js
// Rspack 的配置几乎与 Webpack 一致（迁移成本低的体现）
module.exports = {
  mode: 'production',
  entry: './src/index.js',
  output: { path: __dirname + '/dist', filename: 'main.js' },
  module: {
    rules: [{ test: /\.js$/, use: 'builtin:swc-loader' }],   // 用 SWC 转译
  },
};
```

**易错点：**

- 「Rust 工具」并不意味着生态立刻完整：兼容性、插件生态、社区方案仍需时间，迁移要评估。
- Vite 开发快不等于生产构建快：生产仍要打包（Tree Shaking、代码分割、压缩），速度取决于内核。
- 不要为了「追新」频繁更换构建工具；工具链稳定性与团队熟悉度优先于单纯的性能数字。
