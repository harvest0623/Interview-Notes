## 1. Redis 为什么快？单线程为什么还能高并发

**Redis 快不是某一个单点的功劳，而是「纯内存 + 高效数据结构 + IO 多路复用 + 单线程无锁 + 简单协议」的组合结果。所谓单线程，准确说是「命令的执行」由一个主线程串行完成；连接管理、网络读写、持久化、异步释放等环节并不只有一个线程。单线程反而带来了无锁、无上下文切换、命令天然原子这三个好处，使它能用一条事件循环把大量短命令处理到十万级 QPS。**

拆开来看，快的原因有六层：

1. **纯内存访问**：数据放在内存，读写不需要磁盘寻道与页缓存回填，单次访问在百纳秒量级；持久化是旁路行为，不参与命令路径。
2. **数据结构高效**：SDS 取长度为 O(1)，字典查找平均 O(1)，跳表范围查询 O(log N + M)，listpack 把元素放在连续内存里，缓存局部性好。
3. **IO 多路复用**：基于 epoll 的单线程事件循环，一个线程就能监听成千上万个非阻塞 socket，不需要为每个连接开线程。
4. **单线程执行命令**：没有锁竞争、没有线程切换、没有多线程竞态的修复成本；每个命令在执行期间独占数据，天然具备原子性。
5. **协议简单**：RESP 协议是文本 + 长度前缀，解析逻辑轻；客户端还可以用 Pipeline 批量发送，摊薄 RTT。
6. **实现层优化**：对象共享（0~9999 的整数共享对象）、jemalloc 减少碎片、惰性删除、渐进式 rehash，避免一次性大开销。

| 线程 / 进程 | 职责 | 出现版本 |
| --- | --- | --- |
| 主线程 | 事件循环、解析命令、执行命令、处理定时任务 | 全版本 |
| IO 线程 | 分担 socket 的 read/write（不执行命令） | 6.0 起，`io-threads` |
| `bio_close_file` | 异步关闭大文件，避免 `close` 阻塞 | 4.0 起 |
| `bio_aof_fsync` | 后台执行 AOF fsync | 4.0 起 |
| `bio_lazy_free` | `UNLINK`、`FLUSHALL ASYNC` 的内存异步释放 | 4.0 起 |
| fork 子进程 | 生成 RDB、重写 AOF | 全版本 |

```c

    // 3. 可写事件：把 reply buffer 写回客户端（6.0 起可由 IO 线程分担）

    //    call() 在主线程串行执行，执行期间不会插入其他命令
```

```bash
# 查看版本与运行状态
redis-cli INFO server | grep redis_version
redis-cli INFO stats | grep instantaneous_ops_per_sec

# 命令耗时统计：usec_per_call 能看出谁在拖慢主线程

# 更接近真实场景：value 100 字节、Pipeline 每批 16 条、随机 key
```

**压测时容易忽略的变量：**

- `-d` 默认 value 只有 3 字节，测出来的是「极限小包」；真实业务常见 100B~10KB，吞吐会明显下降。
- `-P` 开启 Pipeline 会大幅提高 QPS，但测的是批量吞吐，不是单请求延迟。
- 客户端压测机可能先成为瓶颈：CPU、网卡、连接数、单机端口耗尽都要排除。
- 看 Redis 侧 `instantaneous_ops_per_sec`、`used_cpu_sys`、`used_cpu_user`，确认瓶颈在主线程还是网络。
- 延迟要用 `redis-cli --latency` 或 `--latency-history` 观察，不能只看平均 QPS。

**单线程为什么还能高并发：**

- 并发连接数由 epoll 承担，不需要「一个连接一个线程」，连接多不等于线程多。
- 大多数命令是 O(1) 或 O(log N) 的短任务，单次执行在微秒级，主线程可以快速轮转。
- 没有锁与上下文切换，CPU 几乎都花在真实工作上；多线程版本反而可能因锁竞争变慢。
- 单机不够就横向扩展：主从读写分离、Cluster 分片、代理分片、本地缓存，而不是把单机命令改成多线程。

**面试怎么答：**

先给一句总括「内存 + 数据结构 + epoll + 单线程无锁 + RESP」，再展开三层：单线程指的是命令执行；IO 多路复用负责连接；6.0 的 IO 线程只分担读写。最后补一句瓶颈：慢命令、大 key、单核 CPU、网络与内存带宽，以及横向扩展手段，答案就完整了。

**易错点：**

- 「Redis 是单线程」不准确：主线程之外还有 bio 线程、6.0 的 IO 线程、fork 出的子进程。
- 「单线程所以不会阻塞」是错的：`KEYS *`、大 key 的 `HGETALL`、Lua 死循环都会阻塞整个实例。
- IO 线程不执行命令，也不解决慢命令；`io-threads` 在多数版本需要改配置重启生效。
- 十万 QPS 是数量级描述，真实值取决于命令、value 大小、连接数、Pipeline 与硬件，不能当成固定指标。

## 2. 五种基本数据类型及典型使用场景

**五种基本类型是 String、List、Hash、Set、ZSet。它们的区别不只是「形状」，更在于底层编码与命令复杂度：String 是二进制安全的字节串，List 是有序可重复的双端队列，Hash 是字段级可读写的映射，Set 是无序去重集合，ZSet 是带 score 的有序去重集合。选型的核心是「访问模式」：整存整取用 String，按字段改用 Hash，按位置/顺序用 List，去重与集合运算用 Set，排序与范围用 ZSet。**

| 类型 | 常用命令 | 关键复杂度 | 典型场景 | 注意事项 |
| --- | --- | --- | --- | --- |
| String | `SET` `GET` `MSET` `INCR` `SETEX` `SET NX PX` | 读写 O(1)，`APPEND`/`GETRANGE` 与长度相关 | 缓存对象 JSON、计数器、分布式锁、Bitmap 签到、Session | 大 value 会拖慢网络与 fork；计数器溢出会报错 |
| List | `LPUSH` `RPUSH` `LPOP` `RPOP` `LRANGE` `LTRIM` `BLMOVE` | 头尾插入删除 O(1)，按索引/范围 O(N) | 栈、队列、最新列表、阻塞队列、简易消息队列 | `LRANGE 0 -1` 是 O(N)；消费后删除不具备 ACK |
| Hash | `HSET` `HGET` `HMGET` `HGETALL` `HINCRBY` `HDEL` | 单字段 O(1)，`HGETALL` O(N) | 对象字段部分更新、购物车、配置表、用户属性 | 大 Hash 的 `HGETALL` 会阻塞；不能对字段单独设 TTL |
| Set | `SADD` `SREM` `SISMEMBER` `SINTER` `SUNION` `SRANDMEMBER` | 增删查 O(1)，集合运算 O(N) | 去重、标签、共同关注、抽奖、黑白名单 | `SMEMBERS` 全量返回；大集合运算会阻塞 |
| ZSet | `ZADD` `ZINCRBY` `ZSCORE` `ZRANK` `ZREVRANGE` `ZRANGEBYSCORE` | 增删改 O(log N)，按排名范围 O(log N + M) | 排行榜、延迟队列、范围查询、带权重排序 | score 是 double，超大整数会丢精度；同分按成员字典序 |

```bash
# String：缓存对象（整存整取，配合过期时间）
SET user:1001:profile '{"name":"张三","level":3}' EX 3600
GET user:1001:profile

# String：计数器（INCR 是原子操作）
INCR article:2024:views
INCRBY article:2024:views 10

# String：分布式锁（一条命令保证互斥 + 过期）
SET lock:order:1001 token-abc NX PX 30000

# List：最新 10 条动态（写入后裁剪，避免无限增长）
LPUSH feed:1001 9001
LTRIM feed:1001 0 9
LRANGE feed:1001 0 9

# List：阻塞队列（BRPOP 阻塞等待，超时 0 表示永久）
LPUSH queue:mail 1001
BRPOP queue:mail 5

# Hash：对象字段级更新，只改一个字段不必读改写整个 JSON
HSET user:1001 name 张三 age 28
HINCRBY user:1001 age 1
HMGET user:1001 name age

# Set：标签与共同好友
SADD tag:redis 1001 1002 1003
SADD tag:mysql 1002 1003 1004
SINTER tag:redis tag:mysql

# ZSet：排行榜，score 为分数，成员为用户 ID
ZADD rank:2024:10 980 user:1001 950 user:1002
ZINCRBY rank:2024:10 20 user:1001
ZREVRANGE rank:2024:10 0 9 WITHSCORES

# ZSet：延迟队列，score 为执行时间戳（毫秒）
ZADD delay:queue 1735689600000 task:9001
ZRANGEBYSCORE delay:queue 0 1735689600000 LIMIT 0 10
```

**选型时的三个判断：**

1. **是否需要按字段读写**：整对象读写用 String；频繁只改部分字段用 Hash，避免「读 JSON → 改 → 写回」的并发覆盖。
2. **是否需要顺序/范围**：只需要头尾进出用 List；需要按分数排序、按排名取区间用 ZSet；只需要去重用 Set。
3. **数据规模与访问方式**：元素多、又要全量读取时，任何类型都会变成大 key，应考虑分页、分片或换存储。

**扩展类型（面试加分，不属于五种基本类型）：**

| 类型 | 核心命令 | 底层 | 典型场景 | 注意 |
| --- | --- | --- | --- | --- |
| Bitmap | `SETBIT` `GETBIT` `BITCOUNT` `BITOP` `BITPOS` | String 的位操作 | 签到、活跃用户标记、布隆过滤器 | offset 最大 2^32-1，单 key 上限 512MB |
| HyperLogLog | `PFADD` `PFCOUNT` `PFMERGE` | 概率基数估计 | UV 统计、去重计数 | 标准误差约 0.81%，不精确、不能取成员 |
| GEO | `GEOADD` `GEODIST` `GEOSEARCH` | 基于 ZSet 的 geohash | 附近的人、门店距离 | 精度受 geohash 编码影响 |
| Stream | `XADD` `XREADGROUP` `XACK` `XPENDING` | radix tree + listpack | 轻量消息队列、消费组 | 需要处理 pending 与消息裁剪 |

```bash
# Bitmap：用户 1001 在第 10 天签到，1 表示已签到
SETBIT sign:1001 9 1
BITCOUNT sign:1001
# (integer) 1

# HyperLogLog：统计 UV，固定约 12KB，与基数无关
PFADD uv:20241024 user:1 user:2 user:3
PFCOUNT uv:20241024
# (integer) 3

# GEO：添加门店坐标并查距离（单位 km）
GEOADD shop:beijing 116.397 39.908 shop:1
GEODIST shop:beijing shop:1 shop:2 km

# Stream：写入消息并创建消费组
XADD stream:order '*' order_id 1001
XGROUP CREATE stream:order group:1 0 MKSTREAM
```

**面试怎么答：**

按「类型 → 结构 → 命令 → 场景 → 坑」五步答。不要只背「String 存字符串」，要说明 Hash 适合字段级更新、ZSet 靠 score 排序、List 的 `BLMOVE` 可以替代不安全的 `BRPOPLPUSH`（后者自 6.2 起标记废弃）。最后补一句：所有集合类型的全量命令在大 key 上都是 O(N)，生产要分页或拆分。

**易错点：**

- `HGETALL`、`SMEMBERS`、`LRANGE 0 -1`、`ZRANGE 0 -1` 都是 O(N)，不是「Hash/Set/List 都 O(1)」。
- List 做队列没有 ACK 与消费组，进程崩溃会丢消息；可靠队列应使用 Stream 或专业 MQ。
- Hash 不能给单个 field 设置过期时间，TTL 只能作用于整个 key。
- ZSet 的 score 是 IEEE 754 double，超过 2^53 的整数无法精确表示，订单号、时间戳（毫秒）要注意量级。
- 同一个 key 反复 `DEL` 再创建会改变编码，也可能触发扩容/缩容，不要把它当成「重置」的低成本操作。

## 3. 底层数据结构与编码转换（intset、listpack、quicklist、hashtable）

**Redis 对外只暴露五种类型，对内却有多套编码：小数据用紧凑的连续内存结构（intset、listpack），大数据才升级为 hashtable、skiplist、quicklist。编码由「元素个数 + 单个元素长度」共同决定，升级通常不可逆。Redis 7.0 用 listpack 全面替换 ziplist，7.2 又给 Set 增加了 listpack 编码；面试时要把版本差异说清楚。**

| 类型 | 小数据编码 | 大数据编码 | 触发升级的条件（默认值） |
| --- | --- | --- | --- |
| String | `int`（整数）、`embstr`（≤44 字节） | `raw`（>44 字节） | 长度超过 44 或包含需重新分配的内容 |
| List | `quicklist`（节点内为 listpack） | `quicklist`（节点内为 listpack） | 元素数/节点大小超过 `list-max-listpack-size` 时增加节点，编码仍是 quicklist |
| Hash | `listpack`（7.0+，6.x 为 ziplist） | `hashtable` | 字段数 > 128 或任一字段/值 > 64 字节 |
| Set | `intset`（全整数）、`listpack`（7.2+） | `hashtable` | 整数元素数 > 512；或 listpack 条件不满足 |
| ZSet | `listpack`（7.0+，6.x 为 ziplist） | `skiplist` + `dict` | 元素数 > 128 或任一成员 > 64 字节 |

**各编码的要点：**

- **intset**：有序整数数组，元素按值升序排列，支持二分查找；只存整数，不存字符串。元素超过 `set-max-intset-entries`（默认 512）后转 hashtable。
- **listpack**：连续内存的紧凑列表，每个元素记录自身长度，支持从两端遍历；相比 ziplist 取消了「记录前一节点长度」的字段，避免连锁更新。元素个数与单元素长度都有阈值。
- **quicklist**：由多个 listpack 节点组成的双向链表，兼顾内存与插入性能；`list-compress-depth` 可压缩中间节点（默认 0 不压缩）。
- **hashtable**：拉链法哈希表，负载因子触发扩容/缩容，配合渐进式 rehash 避免一次性搬迁。
- **skiplist**：多层有序链表，ZSet 大时与 dict 组合使用，dict 负责 O(1) 查 score，skiplist 负责排序与范围。

```bash
# 查看某个 key 的实际编码
redis-cli OBJECT ENCODING user:1001
# "listpack" / "hashtable" / "intset" / "quicklist" / "skiplist" / "embstr" / "raw" / "int"

# 查看编码相关阈值（7.x 的配置名）
redis-cli CONFIG GET hash-max-listpack-entries
redis-cli CONFIG GET hash-max-listpack-value
redis-cli CONFIG GET list-max-listpack-size
redis-cli CONFIG GET set-max-intset-entries
redis-cli CONFIG GET set-max-listpack-entries
redis-cli CONFIG GET zset-max-listpack-entries
redis-cli CONFIG GET zset-max-listpack-value

# 6.x 及以前使用 ziplist 命名，配置项也不同
# hash-max-ziplist-entries 128
# hash-max-ziplist-value 64
# zset-max-ziplist-entries 128
# zset-max-ziplist-value 64
```

```bash
# 观察 Hash 编码升级：字段数从 128 到 129
DEL demo:hash
# 写入 128 个短字段，仍是 listpack
EVAL "for i=1,128 do redis.call('hset',KEYS[1],'f'..i,'v') end return redis.call('object','encoding',KEYS[1])" 1 demo:hash
# 输出 "listpack"

HSET demo:hash f129 v
OBJECT ENCODING demo:hash
# 输出 "hashtable"，且删除字段后不会自动退回 listpack

# 观察 Set 的 intset 升级
DEL demo:set
SADD demo:set 1 2 3
OBJECT ENCODING demo:set
# "intset"
SADD demo:set abc
OBJECT ENCODING demo:set
# "hashtable"（7.2 之前；7.2+ 在满足 listpack 条件时可能是 "listpack"）
```

**为什么小数据要用紧凑编码：**

1. **省内存**：listpack/intset 不存指针，元素连续排列，没有每个 entry 的 24 字节 dictEntry 与 SDS 头开销。
2. **缓存友好**：连续内存一次加载多条缓存行，遍历快。
3. **代价**：插入删除可能触发内存搬移，元素多时退化为 O(N)，所以必须设阈值，超过就换成指针结构。

**面试怎么答：**

先画一张「类型 → 编码 → 阈值」表，再解释 listpack 相比 ziplist 解决了连锁更新，quicklist 是「链表套 listpack」，ZSet 大编码是「dict + skiplist」双结构。最后说明升级不可逆、阈值可调但要权衡内存与 CPU，并点出 7.0/7.2 的版本差异。

**易错点：**

- 只记元素个数阈值，漏掉单元素长度阈值：一个 1KB 的 field 就能让 Hash 直接转 hashtable。
- 以为删除元素后编码会自动降级：多数转换是单向的，小数据不会再退回 listpack。
- `list-max-listpack-size` 既可以是正数（元素个数），也可以是负数（按节点大小限制，如 -2 表示 8KB），不要只按「128」理解。
- Redis 7.0 之前 List 的 quicklist 节点是 ziplist，7.0 起才是 listpack；回答时说「ziplist」要补版本。
- `OBJECT ENCODING` 只反映当前编码，不代表性能一定好；128 个元素的 listpack 上做中间插入仍然是 O(N)。

## 4. SDS 与 C 字符串的区别

**Redis 没有直接使用 C 的 `char *`，而是自己实现 SDS（Simple Dynamic String）。SDS 在字符数组前加了 `len`（已用长度）、`alloc`（已分配容量）和 `flags`（头类型），因此取长度是 O(1)、二进制安全、追加前会检查并扩容、不会缓冲区溢出；同时它仍然以 `\0` 结尾，可以直接复用 C 的字符串函数做只读操作。**

SDS 的头结构（简化）：

```c
struct sdshdr8 {
    uint8_t len;       // 已使用字节数，不含结尾 \0
    uint8_t alloc;     // 已分配容量，不含头和结尾 \0
    uint8_t flags;     // 低 3 位表示头类型
    char buf[];        // 柔性数组，实际字符 + 结尾 \0
};
```

Redis 按长度选择 `sdshdr5`、`sdshdr8`、`sdshdr16`、`sdshdr32`、`sdshdr64`，用尽量小的头存长度，避免短字符串浪费内存。`sdshdr5` 没有 `alloc` 字段，只用于创建后不再追加的短字符串。

| 维度 | C 字符串 | SDS |
| --- | --- | --- |
| 取长度 | `strlen` 遍历到 `\0`，O(N) | 读 `len` 字段，O(1) |
| 二进制安全 | 不能存 `\0`，否则被截断 | 按 `len` 读写，可存任意字节（图片、序列化数据） |
| 缓冲区溢出 | `strcat` 不检查目标容量 | 追加前检查 `alloc`，不够则扩容 |
| 内存分配 | 每次修改都可能 `realloc` | 空间预分配 + 惰性释放，减少 `realloc` |
| 结束符 | 必须有 `\0` | 同样以 `\0` 结尾，可传给 `printf`、`strcmp` 等只读函数 |
| 内存开销 | 仅字符 + 1 字节 | 头（1~17 字节，常用 3~9）+ 字符 + 1 字节 |
| 长度上限 | 受地址空间限制 | 单 value 上限 512MB |

**空间预分配规则：**

- 追加后长度 `< 1MB`：`alloc = 2 * len`，即多分配一倍。
- 追加后长度 `>= 1MB`：`alloc = len + 1MB`，每次最多多给 1MB。
- 目的：把连续 N 次追加的 `realloc` 次数从 O(N) 降到 O(log N) 或 O(1) 级别。

**惰性释放：**

- 缩短字符串时（如 `SETRANGE` 覆盖为更短内容、`sdstrim`），SDS 不立即 `free` 多余空间，只改 `len`，保留 `alloc` 供后续追加复用。
- 真正需要释放时调用 `sdsRemoveFreeSpace`，把 `alloc` 收缩到 `len`。
- 这也意味着「删掉内容」不等于「立刻归还内存」，判断内存要结合 `MEMORY USAGE`。

```bash
# 取长度 O(1)，与内容无关
SET msg "hello"
STRLEN msg
# (integer) 5

# 二进制安全：值中可以包含 \0，SET/GET 不受影响
SET bin "\x00\x01\x02"
STRLEN bin
# (integer) 3

# 追加会触发扩容；APPEND 返回追加后的长度
APPEND msg " world"
# (integer) 11

# 覆盖指定区间，不会越界写坏内存
SETRANGE msg 0 "HELLO"
GET msg
# "HELLO world"

# 查看 value 实际占用（包含 SDS 头、redisObject、jemalloc 对齐等）
MEMORY USAGE msg
```

**embstr 与 raw 的区别（常被追问）：**

- `embstr`：`redisObject` 与 SDS 在同一块内存中一次 `malloc` 分配，适合 ≤44 字节的短字符串，创建/释放各一次分配，缓存局部性好。
- `raw`：`redisObject` 与 SDS 分开两次分配，适合长字符串；`APPEND`、`SETRANGE` 等修改会使 `embstr` 转成 `raw`。
- `int`：内容是整数且能用 `long` 表示时，直接把数值存在 `redisObject` 的指针字段里，不额外分配 SDS。

**面试怎么答：**

先给结论「SDS = 长度 + 容量 + 头类型 + 柔性数组」，再对比四点：O(1) 长度、二进制安全、杜绝溢出、预分配减少重分配；最后补「仍然以 `\0` 结尾，兼容 C 函数」和 `embstr`/`raw` 的分配差异。这样既回答了区别，也解释了为什么 Redis 需要自己造字符串。

**易错点：**

- SDS 不是「不以 `\0` 结尾」，它保留结尾符只是为了兼容 C 的只读函数。
- 预分配会浪费内存：短字符串频繁追加后 `alloc` 可能远大于 `len`，`STRLEN` 小不代表占用小。
- `embstr` 是只读的，任何修改都会转成 `raw`，不要以为短字符串永远只有一次分配。
- 单 value 上限是 512MB，不是无限；接近上限的 value 会带来网络、fork、迁移灾难。
- SDS 的 `len` 是字节数，不是字符数；中文等多字节内容用 `STRLEN` 得到的是字节长度。

## 5. 跳表与 ZSet 的实现

**ZSet 需要同时支持「按成员查分数」和「按分数排序/取范围」，单一结构很难两全，所以大数据量时用 `dict + skiplist`：dict 负责 O(1) 的 `ZSCORE`，skiplist 负责 O(log N) 的插入与范围查询。跳表通过多层索引把链表查找从 O(N) 降到期望 O(log N)，每个节点还记录 `span`（跨越的节点数），因此 `ZRANK` 也能在 O(log N) 内算出排名。数据量小时 ZSet 用 listpack，不建跳表。**

核心结构（简化）：

```c
typedef struct zset {
    dict *dict;        // member -> score，支持 O(1) 查分
    zskiplist *zsl;    // 按 score 排序，支持范围与排名
} zset;

typedef struct zskiplistNode {
    sds ele;                       // 成员
    double score;                  // 分数
    struct zskiplistNode *backward; // 后退指针，支持倒序
    struct zskiplistLevel {
        struct zskiplistNode *forward; // 前进指针
        unsigned long span;            // 到下一个节点的跨度
    } level[];                     // 柔性数组，层数随机
} zskiplistNode;
```

**跳表的关键机制：**

1. **随机层数**：插入时不断抛硬币，以 1/4 的概率继续升高，最高 32 层；期望层数约 1.33，空间开销可控。
2. **多层索引**：高层指针跳得远，低层指针跳得细，查找从最高层开始，能往右就往右，不能就往下一层。
3. **插入**：先找到每一层的前驱节点，再按随机层数逐层插入，期望 O(log N)。
4. **删除**：找到节点后逐层摘除指针，期望 O(log N)。
5. **排名**：沿路径累加 `span`，`ZRANK` 是 O(log N)；`ZRANGE start stop` 是 O(log N + M)，M 为返回元素数。
6. **同分排序**：score 相同时按 `ele` 的字典序（`memcmp`）排列，保证顺序稳定。

```text
level 3:  head ──────────────────────────────→ node(50)
level 2:  head ──────────→ node(20) ─────────→ node(50)
level 1:  head → node(5) → node(20) → node(35) → node(50) → node(80)
                      ↑ span 记录每段跨越的底层节点数
```

```bash
# 写入：ZADD 可一次添加多个 member/score 对
ZADD rank:2024:10 980 user:1001 950 user:1002 920 user:1003

# 加分并返回新分数（原子）
ZINCRBY rank:2024:10 20 user:1001
# "1000"

# 按排名取前 10（倒序），WITHSCORES 一并返回分数
ZREVRANGE rank:2024:10 0 9 WITHSCORES

# 查排名：从高到低的名次，O(log N)
ZREVRANK rank:2024:10 user:1002

# 按分数范围取（包含边界），LIMIT 分页
ZRANGEBYSCORE rank:2024:10 900 1000 WITHSCORES LIMIT 0 10

# 删除分数区间内的成员，常用于清理过期榜单
ZREMRANGEBYSCORE rank:2024:10 0 899

# 查看底层编码：元素少时是 listpack，多时是 skiplist
OBJECT ENCODING rank:2024:10
```

**为什么用跳表而不是红黑树/B+ 树：**

| 维度 | 跳表 | 红黑树 | B+ 树 |
| --- | --- | --- | --- |
| 范围查询 | 找到起点后沿底层链表顺序扫，简单 | 需要中序遍历，实现复杂 | 适合磁盘页，内存中节点利用率低 |
| 排名 | `span` 天然支持 O(log N) 排名 | 需额外维护子树大小 | 需额外维护 |
| 实现复杂度 | 无旋转、无变色，插入删除逻辑直观 | 插入删除要多次旋转/变色 | 分裂合并复杂 |
| 并发友好 | 局部指针修改，易于无锁化 | 旋转影响面大 | 页分裂影响面大 |
| 内存 | 平均 1.33 个指针/节点，可控 | 每节点固定指针 + 颜色 | 节点填充率与页管理开销 |

Redis 是内存数据库，不需要 B+ 树为磁盘页优化；跳表在范围查询、排名、实现成本上更合适。虽然 Redis 命令执行是单线程，但跳表结构也为未来/集群场景留下了更好的并发基础。

**面试怎么答：**

先点明 ZSet 是「dict + skiplist」双结构，各自职责；再讲跳表的随机层数、多层索引、`span` 排名；然后解释为什么不用红黑树（范围查询与排名更简单）和为什么不用 B+ 树（内存场景不需要磁盘页）；最后补小数据用 listpack、score 是 double。

**易错点：**

- 跳表查询是「期望 O(log N)」，最坏情况仍是 O(N)，只是概率极低。
- `ZRANGE` 的复杂度是 O(log N + M)，不是纯 O(log N)；一次取全量就是 O(N)。
- `ZINCRBY` 修改分数会先删后插，不是原地改一个数字。
- 同分成员按字典序排，不是按插入顺序；做榜单要接受这个规则或把次序编码进 score。
- 小 ZSet 使用 listpack，此时 `ZRANK` 是 O(N)；不要无条件说 ZSet 所有操作都 O(log N)。

## 6. 字典与渐进式 rehash

**Redis 的字典是「两张哈希表 + 拉链法」：平时只用 `ht[0]`，扩容或缩容时把 `ht[1]` 分配为新的容量，然后通过 `rehashidx` 逐步把桶从 `ht[0]` 搬到 `ht[1]`，而不是一次性搬完。这样把 O(N) 的搬迁摊到每次增删改查与定时任务里，避免大字典在单次操作上阻塞主线程。搬迁期间查找要查两张表，新增只写 `ht[1]`。**

核心结构（简化）：

```c
typedef struct dictEntry {
    void *key;
    union {
        void *val;
        uint64_t u64;
        int64_t s64;
        double d;
    } v;
    struct dictEntry *next;   // 拉链解决冲突
} dictEntry;

typedef struct dictht {
    dictEntry **table;        // 桶数组
    unsigned long size;       // 桶数量，2 的幂
    unsigned long sizemask;   // size - 1，用于 hash & sizemask
    unsigned long used;       // 已有节点数
} dictht;

typedef struct dict {
    dictType *type;
    void *privdata;
    dictht ht[2];             // ht[0] 旧表，ht[1] 新表
    long rehashidx;           // -1 表示未 rehash，否则是当前搬迁的桶下标
    int16_t pauserehash;
} dict;
```

**rehash 的触发条件：**

| 场景 | 条件 | 新容量 |
| --- | --- | --- |
| 扩容 | `used / size >= 1`，且当前没有执行 `BGSAVE`/`BGREWRITEAOF` | 第一个 ≥ `used * 2` 的 2 的幂 |
| 强制扩容 | `used / size > 5`（`dict_force_resize_ratio`） | 同上，即使正在 fork 也执行 |
| 缩容 | `used / size < 0.1` 且 `size > 4` | 第一个 ≥ `used` 的 2 的幂 |

执行 fork 时（RDB、AOF rewrite）会临时关闭自动扩容，因为扩容会修改大量内存页，破坏 Copy-On-Write 的收益；但负载因子超过 5 时仍会强制扩容，防止哈希冲突把查询拖成 O(N)。

**渐进式搬迁的步骤：**

1. 为 `ht[1]` 分配空间，`rehashidx = 0`。
2. 每次字典操作（查找、插入、删除）顺带搬迁 `rehashidx` 桶上的所有节点，然后 `rehashidx++`。
3. 定时任务 `serverCron` 每次最多花 1ms、搬迁约 100 个桶，直到搬完。
4. 搬迁期间：
   - 查找：先查 `ht[0]`，没有再去 `ht[1]`。
   - 新增：直接写入 `ht[1]`，保证 `ht[0]` 只减不增。
   - 删除/更新：两张表都要处理。
   - `SCAN`：`dictScan` 使用反向二进制迭代，能在 rehash 过程中不重不漏地遍历。
5. 全部搬完后释放 `ht[0]`，把 `ht[1]` 赋给 `ht[0]`，`rehashidx = -1`。

```text
初始：ht[0] 容量 4，used 4，负载因子 1 → 触发扩容

ht[0]: [0]→A→C  [1]→B  [2]→D  [3]→E
ht[1]: 容量 8，尚未开始搬

rehashidx=0 时搬桶 0：
ht[0]: [0]空  [1]→B  [2]→D  [3]→E
ht[1]: [0]→C  ...  [4]→A（按新 sizemask 重新计算）

后续每次操作搬一个桶，直到 rehashidx 追上 ht[0].size
```

```bash
# 查看当前 db 的哈希表状态（7.0 起 debug 命令默认禁用）
# 需在 redis.conf 设置 enable-debug-command yes 后重启；该配置是 protected config，不能运行时 CONFIG SET
redis-cli DEBUG HTSTATS 0
# hash table 0 stats (main hash table):
#  size: 4, used: 4
# hash table 1 stats (rehashing target):
#  size: 8, used: 0
#  rehashing in progress, rehashidx: 0

# 生产环境更常用 INFO 与 MEMORY 观察整体，不要依赖 DEBUG
redis-cli INFO memory | grep used_memory
redis-cli MEMORY STATS
```

**为什么不用一次性 rehash：**

- 大字典可能有百万级 key，一次性搬迁会造成几十毫秒甚至更长的停顿，主线程被阻塞，所有客户端超时。
- 摊还后每次只搬少量桶，单次开销可控；总工作量不变，但峰值延迟大幅下降。
- 代价是搬迁期间内存占用约为原来的 1.5~2 倍，且查找可能多一次访问。

**面试怎么答：**

按「结构 → 触发 → 过程 → 期间读写 → 为什么」回答：两张表 + `rehashidx`；负载因子 1 扩容、0.1 缩容、fork 时暂停；每次操作搬一个桶、定时任务搬 100 个桶；查找双表、新增只写新表；最后说这样做是为了避免大 key 字典造成主线程长停顿。

**易错点：**

- rehash 不是后台线程做的，而是主线程在命令与定时任务里「顺手」搬，仍会消耗 CPU。
- 搬迁期间不是「只读旧表」，新增必须写新表，否则永远搬不完旧表。
- `used/size` 是平均负载因子，某个桶可能很长；极端哈希冲突仍会让单次查找退化。
- fork 期间暂停扩容是为了 COW 性能，不是「禁止一切扩容」，超过 5 倍仍会强制扩容。
- 缩容阈值是 0.1，不是 0.5；小字典（size ≤ 4）不会缩容。

**哈希函数与冲突：**

- Redis 使用 SipHash 1-2（3.2 起）计算 key 的哈希，带随机种子，攻击者无法预先构造大量同哈希 key 来把字典退化成链表。
- 桶数量始终是 2 的幂，取模用 `hash & sizemask`，比 `%` 快。
- 冲突用拉链法，新节点通常插在桶头，查找沿 `next` 遍历。
- 单个桶过长时查找退化为 O(N)；负载因子与随机哈希共同保证平均桶长接近 1。
- 这也是「不要用可预测的哈希实现」的原因：早期 MurmurHash 无种子，曾被用于哈希碰撞 DoS。

## 7. 过期删除策略与内存淘汰策略

**过期删除解决「key 到点后怎么删」，内存淘汰解决「内存满了删谁」，两者是不同问题。Redis 用「惰性删除 + 定期删除」组合清理过期 key：访问时检查、后台每 100ms 抽样清理，因此过期 key 不会立刻释放内存。内存达到 `maxmemory` 后，再按 `maxmemory-policy` 淘汰；默认策略是 `noeviction`，写命令会直接报 OOM，而不是自动删数据。**

**过期时间的存储：**

- 每个 db 有一个 `expires` 字典，key 指向过期时间（毫秒时间戳），与主字典分开存储。
- `SET key value EX 60`、`EXPIRE key 60`、`PEXPIRE`、`EXPIREAT` 最终都写入这个字典。
- `PERSIST key` 删除过期时间；`TTL` 返回秒，`PTTL` 返回毫秒，`-1` 表示没有过期时间，`-2` 表示 key 不存在。

| 删除策略 | 触发时机 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 惰性删除 | 每次访问 key 时检查过期时间 | 对 CPU 友好，只处理被访问的 key | 不访问就永不删除，内存可能被撑爆 |
| 定期删除 | `serverCron` 每 100ms 触发一次（`hz 10`） | 能兜底清理冷数据 | 抽样清理，不是全量扫描；过期 key 仍有滞后 |
| 定时删除 | 为每个 key 建定时器 | 到点即删，内存最及时 | 大量定时器消耗 CPU，Redis 未采用 |

**定期删除的具体过程（`activeExpireCycle`）：**

1. 从每个 db 的 `expires` 字典中随机抽取 `ACTIVE_EXPIRE_CYCLE_KEYS_PER_LOOP`（默认 20）个 key。
2. 删除其中已过期的 key。
3. 如果本轮过期比例超过 25%，说明过期 key 还很多，继续抽样下一轮。
4. 每轮受时间上限约束（慢速模式最多占 25% CPU），避免清理拖垮主线程；`active-expire-effort`（1~10，默认 1）越大，清理越积极。

**主从下的过期行为：**

- 从库不会主动删除过期 key，而是等主库删除后同步 `DEL`/`UNLINK`。
- 从库读取到逻辑上已过期的 key 时返回 nil，但内存里仍然保留，直到收到主库的删除命令。
- 因此从库的 `DBSIZE` 与内存可能比主库「多」，这是正常现象。

**内存淘汰的八种策略：**

| 策略 | 候选范围 | 淘汰依据 | 适用场景 |
| --- | --- | --- | --- |
| `noeviction` | 不淘汰 | 写命令返回 OOM 错误 | 数据不能丢、纯数据库式使用 |
| `allkeys-lru` | 所有 key | 最近最少使用（近似） | 通用缓存，最常用 |
| `allkeys-lfu` | 所有 key | 访问频率最低（近似） | 热点明显、长尾访问 |
| `allkeys-random` | 所有 key | 随机 | 访问分布均匀、无热点 |
| `volatile-lru` | 设置了 TTL 的 key | 最近最少使用 | 缓存与持久数据混存 |
| `volatile-lfu` | 设置了 TTL 的 key | 访问频率最低 | 同上，热点明显 |
| `volatile-random` | 设置了 TTL 的 key | 随机 | 同上，无热点 |
| `volatile-ttl` | 设置了 TTL 的 key | 剩余 TTL 最短优先 | 临期数据优先清理 |

**LRU 与 LFU 都是近似实现：**

- Redis 不为每个 key 维护完整链表，而是在 `redisObject` 的 24 位 `lru` 字段里记录信息，淘汰时随机采样 `maxmemory-samples`（默认 5）个 key，挑其中最久未使用的。
- LRU 记录的是 24 位时钟，精度约 1 秒；采样越多越接近真实 LRU，但 CPU 开销更大。
- LFU 把 24 位拆成 16 位「上次衰减时间（分钟）」+ 8 位「访问频率计数器」；计数器不是简单自增，而是概率增长，避免早期热点永久占优；`lfu-decay-time`（默认 1 分钟）控制衰减速度，`lfu-log-factor`（默认 10）控制增长难度。
- `OBJECT FREQ key` 查看 LFU 计数（需要 `allkeys-lfu`/`volatile-lfu`），`OBJECT IDLETIME key` 查看空闲秒数（LRU 模式）。

```conf
# redis.conf 关键配置
maxmemory 4gb                    # 0 表示不限制；生产通常设为物理内存的 60%~75%
maxmemory-policy allkeys-lru     # 默认是 noeviction
maxmemory-samples 5              # 采样数量，越大越精确、越耗 CPU
lfu-decay-time 1                 # LFU 计数器衰减周期（分钟）
lfu-log-factor 10                # LFU 计数器增长因子
hz 10                            # 定时任务频率，影响定期删除的粒度
active-expire-effort 1           # 1~10，越大过期清理越积极
```

```bash
# 设置与查看过期时间
SET session:1001 abc EX 1800
TTL session:1001
# (integer) 1800
PERSIST session:1001
TTL session:1001
# (integer) -1

# 7.0 起 EXPIRE 支持 NX/XX/GT/LT，做「只延长不缩短」
EXPIRE session:1001 3600 XX
EXPIRE session:1001 60 GT

# 查看内存与淘汰情况
redis-cli INFO memory | grep -E "used_memory_human|maxmemory_human|mem_fragmentation_ratio"
redis-cli INFO stats | grep evicted_keys
redis-cli CONFIG GET maxmemory-policy

# 查看 key 的空闲时间与访问频率
redis-cli OBJECT IDLETIME session:1001
redis-cli OBJECT FREQ hot:key

# 手动触发内存碎片整理（7.0+ 支持 active defrag）
redis-cli MEMORY PURGE
redis-cli CONFIG SET activedefrag yes
```

**一次写命令遇到内存上限时的流程：**

1. 执行命令前检查 `used_memory > maxmemory`（`performEvictions`）。
2. 若策略是 `noeviction`，直接返回 OOM 错误，命令不执行。
3. 否则按策略从候选集合中采样，选出「最佳淘汰对象」放入淘汰池。
4. 删除对象并释放内存，重复直到内存降到 `maxmemory` 以下，或达到时间/次数上限。
5. 若仍无法腾出空间（例如 `volatile-*` 但候选集合为空），写命令报 OOM。
6. 淘汰会产生 `evicted_keys` 指标与 `DEL` 传播到从库/AOF；大量淘汰往往意味着容量不足或 TTL 设计不合理。

**容量与策略的取舍：**

- 缓存场景优先 `allkeys-lru` 或 `allkeys-lfu`，不要让缓存 key 与「不可丢数据」共用一个实例。
- 若同一实例既有缓存又有持久数据，用 `volatile-*` 并确保缓存 key 都有 TTL，否则淘汰会「卡住」。
- `maxmemory` 建议留出 20%~30% 余量给 fork COW、复制缓冲区、碎片与客户端缓冲。
- 监控 `evicted_keys` 的增速比看瞬时值更有意义：持续增长说明命中率与容量都在恶化。

**面试怎么答：**

先区分两个问题：过期删除是「时间到了怎么清理」，内存淘汰是「内存满了删谁」。过期删除答「惰性 + 定期抽样，默认 hz=10、每次抽 20 个、过期比例 >25% 继续」；淘汰答「8 种策略、默认 noeviction、LRU/LFU 都是采样近似」。最后补主从不主动过期、`volatile-*` 只淘汰有 TTL 的 key 这两个坑。

**易错点：**

- 过期 key 不会立即释放内存，`DBSIZE` 也可能把逻辑过期的 key 算进去（从库尤其明显）。
- `volatile-lru` 不是「优先淘汰过期 key」，而是「只在有 TTL 的 key 里选」；如果所有 key 都没 TTL，内存满了也不会淘汰，直接 OOM。
- `noeviction` 下读命令仍可用，只有写命令报 `OOM command not allowed when used memory > 'maxmemory'`。
- LRU/LFU 是近似算法，采样 5 个不代表精确顺序；调大 `maxmemory-samples` 是用 CPU 换准确度。
- `maxmemory` 不包含 fork 的 COW、复制缓冲区、内存碎片，实际 RSS 往往高于配置值，容量规划要留余量。
- 修改 `maxmemory-policy` 是运行时命令，但策略切换不会立刻清理已有数据。

## 8. Redis 6.0 的 IO 多线程

**Redis 6.0 引入的是「IO 多线程」，不是「命令多线程」。主线程仍然负责解析命令、执行命令、处理定时任务；额外的 IO 线程只分担 socket 的 `read`/`write` 系统调用与协议数据的搬运。这样在网络成为瓶颈时（大 value、TLS、高连接数）可以用多核分担内核拷贝与读写等待，而命令执行依然无锁、串行、原子。**

**为什么需要 IO 多线程：**

- 单线程执行命令通常不是瓶颈，瓶颈在「把数据从 socket 读到用户态」和「把回复写回 socket」。
- 大 value、TLS 加解密、海量连接会让主线程大量时间耗在 `read`/`write` 上，命令执行反而空闲。
- 多线程只做 IO，不碰共享数据结构，因此不需要给命令加锁，保留了单线程模型的简单性。

**工作流程（简化）：**

1. 主线程通过 epoll 发现可读事件，把待读的客户端分配给 IO 线程。
2. IO 线程并行执行 `read()`，把数据放入各自的 query buffer。
3. 主线程等待所有 IO 线程完成本轮读，然后自己解析 RESP、执行命令。
4. 命令产生回复后，主线程把待写客户端分配给 IO 线程，并行 `write()`。
5. 主线程继续下一轮事件循环。

```conf
# redis.conf
io-threads 4              # 默认 1，表示关闭 IO 多线程；建议 4~8，且不超过 CPU 核数
io-threads-do-reads no    # 默认 no，只对写做多线程；yes 表示读也交给 IO 线程
```

```bash
# 查看当前配置（io-threads 是启动参数，运行时修改通常不生效）
redis-cli CONFIG GET io-threads
redis-cli CONFIG GET io-threads-do-reads

# 对比开关前后的吞吐：固定 100 连接、100 万次 GET
redis-benchmark -h 127.0.0.1 -p 6379 -c 100 -n 1000000 -t get -q
# 开启前：GET: 98000 requests per second
# 开启后：GET: 145000 requests per second（示例值，随硬件与 value 大小变化）
```

| 维度 | Redis 6.0 之前 | Redis 6.0 起 |
| --- | --- | --- |
| 网络读写 | 主线程串行 | 可由 `io-threads` 分担 |
| 命令执行 | 主线程串行 | 仍是主线程串行 |
| 数据结构加锁 | 不需要 | 仍然不需要 |
| 适用场景 | 普通 KV、小 value | 大 value、TLS、多核机器、高连接数 |
| 配置生效 | 无 | 改 `io-threads` 需重启 |

**开启建议与限制：**

- CPU 少于 4 核时收益很小，`io-threads` 设为 1（关闭）即可。
- 线程数不要超过核数，常见 4 或 8；线程过多会增加上下文切换与同步开销。
- 它不会加速 `KEYS`、大 key 的 `HGETALL`、复杂 Lua 等 CPU/阻塞型命令。
- 它也不会让命令并行执行，事务、Lua 的原子性不受影响。
- 官方基准显示，普通小 value 场景提升有限，大 value 或 Pipeline 场景更明显。

**为什么命令执行不做成多线程：**

- 共享数据结构需要加锁，锁竞争、死锁排查、内存模型都会显著增加复杂度。
- 多线程执行会破坏单条命令的原子性，`INCR`、`LPUSH`、ZSet 更新都需要额外同步。
- 命令通常很短，线程切换与同步的开销可能大于并行收益。
- 真正的扩展方式是横向：主从分担读、Cluster 分担写、代理分片、本地缓存，而不是单实例内并行执行命令。
- 需要多核 CPU 时，可以部署多个 Redis 实例分片，每个实例仍是单线程命令模型，运维上更可控。

**面试怎么答：**

一句话：「6.0 多线程的是网络 IO，不是命令执行。」再讲动机（网络读写成为瓶颈）、流程（IO 线程读 → 主线程解析执行 → IO 线程写）、配置（`io-threads` 默认 1，建议 4~8 且不超过核数，需重启）。最后补「命令仍串行、原子性不变、慢命令不受益」，避免把多线程理解成并发执行命令。

**易错点：**

- 「Redis 6.0 变成多线程了」是错的：命令执行依然单线程，多线程只做 socket 读写。
- `io-threads` 不是越大越好，超过核数会因调度与同步变慢。
- `io-threads-do-reads` 默认是 `no`，只开写多线程；读多线程需要显式开启。
- IO 多线程不会解决慢查询与 big key 阻塞，这类问题只能拆分数据或改写命令。
- 该参数通常需要重启生效，不能把它当作在线扩容手段。

## 9. Pipeline、事务与 Lua 脚本

**Pipeline 解决「往返次数多」，事务解决「一组命令连续执行不被穿插」，Lua 解决「一组逻辑在服务端原子执行并可带条件」。三者不是替代关系：Pipeline 只减少 RTT，不保证原子；`MULTI/EXEC` 保证连续执行但不支持回滚；Lua 原子且能读值做判断，但会阻塞主线程，必须控制执行时间。**

| 能力 | Pipeline | MULTI/EXEC 事务 | Lua 脚本 |
| --- | --- | --- | --- |
| 减少网络 RTT | 是，批量发送 | 否，仍需 MULTI/EXEC 两次往返 | 否，一次 EVAL 一次往返 |
| 原子性 | 否，其他客户端命令可能穿插 | 是，EXEC 内命令连续执行 | 是，整个脚本执行期间不处理其他命令 |
| 条件判断 | 否，客户端无法基于中间结果分支 | 有限，需 WATCH 做乐观锁 | 是，可在服务端读值后决定 |
| 失败回滚 | 不涉及 | 不支持，运行时错误继续执行 | 不支持，`redis.call` 报错会中断脚本 |
| 主要开销 | 客户端缓冲与服务端输出缓冲 | 事务队列与 WATCH 冲突重试 | 主线程被占用，长脚本阻塞 |
| 集群限制 | 无，逐条路由 | 所有 key 需同槽 | 所有 key 需同槽 |

**Pipeline 的机制与边界：**

- 客户端一次写入多条命令，不等待逐条回复；服务端按顺序执行后一次性返回所有结果。
- 它减少的是网络往返与系统调用，不减少服务端命令执行时间。
- 不保证原子：服务端可能在两条命令之间处理其他客户端；不要把「Pipeline 内的命令」当成事务。
- 单次 Pipeline 不宜过大：几万条命令会占满客户端与服务端的输出缓冲区，甚至触发 `client-output-buffer-limit` 断开连接。建议按 500~1000 条分批。

```bash
# 用 redis-cli --pipe 批量导入（适合初始化大量 key）
# 生成 RESP 格式的命令流
python3 - <<'PY' > /tmp/commands.txt
for i in range(10000):
    print(f"SET key:{i} value:{i}")
PY
redis-cli --pipe < /tmp/commands.txt

# 普通客户端伪代码：批量发送、统一读取
# pipe = client.pipeline()
# for i in range(1000):
#     pipe.set(f"key:{i}", i)
# results = pipe.execute()   # 一次网络往返，结果按顺序返回
```

**事务的机制与边界：**

```bash
MULTI
SET account:1 100
INCR account:1
EXEC
# 1) OK
# 2) 101

# WATCH：乐观锁，若 key 在 EXEC 前被改动，整个事务放弃
WATCH stock:1001
GET stock:1001
# 客户端基于结果决定是否继续
MULTI
DECR stock:1001
EXEC
# 若 stock:1001 被其他客户端改过，返回 (nil)，需要业务重试

DISCARD   # 放弃事务
UNWATCH   # 取消监视
```

- `MULTI` 后命令进入队列，返回 `QUEUED`，并不立即执行。
- `EXEC` 时按入队顺序连续执行，期间不插入其他客户端命令，因此具备原子性。
- **两类错误要区分**：
  - 入队错误（命令不存在、参数个数不对）：`EXEC` 返回 `EXECABORT`，整个事务不执行。
  - 执行错误（如对 String 执行 `LPUSH`、除零）：错误只影响该条命令，其他命令继续执行，**没有回滚**。
- `WATCH` 是乐观锁：只监视 key 是否被修改，不阻塞；冲突后由客户端重试。`WATCH` 必须在 `MULTI` 之前调用，`EXEC`/`DISCARD` 后自动取消。
- 事务不能嵌套，`MULTI` 内再 `MULTI` 会报错。

**Lua 的机制与边界：**

```bash
# 原子地「读值 + 判断 + 写值」，适合扣库存、发令牌
EVAL "
  local stock = tonumber(redis.call('GET', KEYS[1]))
  if stock == nil or stock <= 0 then
    return -1
  end
  redis.call('DECR', KEYS[1])
  return stock - 1
" 1 stock:1001

# 先加载脚本，后续用 SHA1 调用，节省网络带宽
SCRIPT LOAD "return redis.call('INCR', KEYS[1])"
# 返回脚本的 SHA1，例如 "<sha1>"
EVALSHA <sha1> 1 counter:1

# 检查脚本是否还在缓存中（重启/SCRIPT FLUSH 后会消失）
SCRIPT EXISTS <sha1>
```

- `EVAL script numkeys key [key ...] arg [arg ...]`，`KEYS` 与 `ARGV` 是脚本内的两个数组，key 必须显式声明，便于集群路由。
- 脚本执行期间主线程不处理其他命令，天然原子；也意味着长脚本会阻塞所有客户端。
- `redis.call` 遇到错误会中断脚本并返回错误；`redis.pcall` 会捕获错误，脚本可继续。
- Redis 5.0 起脚本按「效果复制」同步到从库/AOF，Redis 7.0 默认仍是效果复制，因此脚本内使用随机命令不再导致主从不一致；但不应依赖未定义行为。
- `lua-time-limit`（默认 5000ms）只用于在超时后让 Redis 开始返回 `BUSY`，并不会自动杀死脚本；只有脚本尚未写入时才能用 `SCRIPT KILL` 终止，已写入则只能 `SHUTDOWN NOSAVE`。
- Redis 7.0 新增 Function（`FUNCTION LOAD`、`FCALL`），可把脚本作为库持久化，适合复用；普通场景 EVALSHA 足够。

**怎么选：**

1. 只是批量读写、无依赖：用 Pipeline，成本最低。
2. 需要「一组命令不被打断」但不需要读中间值：用 `MULTI/EXEC`；有并发冲突用 `WATCH`。
3. 需要「读值后条件写入」且要求原子：用 Lua；注意 key 同槽、脚本短小。
4. 跨服务、长流程、需要重试与持久化：不要塞进 Lua，改用 Stream/MQ + 业务状态机。

**面试怎么答：**

先给三者定位：Pipeline 省 RTT、事务保连续、Lua 做服务端原子逻辑。再各讲一个关键限制：Pipeline 不原子；事务运行时错误不回滚；Lua 阻塞主线程且集群要求同槽。最后给选型口诀，并补 `WATCH` 乐观锁与 `EVALSHA` 的缓存机制。

**易错点：**

- Pipeline 不是事务，其他客户端命令可能插在两条命令之间。
- `MULTI/EXEC` 不支持回滚：执行期错误不会撤销已执行的命令，不要拿它当关系型事务。
- `WATCH` 监视的是 key 是否被修改，不是值是否变化；任何写操作都会让事务失败。
- Lua 里 `KEYS` 和 `ARGV` 下标从 1 开始，不是 0。
- Lua 脚本中的 key 必须通过 `KEYS` 传入；在集群模式下，所有 key 必须落在同一槽，否则报 `CROSSSLOT`。
- 长 Lua 脚本会让整个实例进入 `BUSY` 状态，生产脚本要限制循环次数与数据量。

## 10. 大 key 与热 key 的危害与治理

**大 key 是「单个 key 的 value 过大或元素过多」，热 key 是「单个 key 的访问 QPS 过高」。前者主要伤害内存、网络与 fork，后者主要伤害单核 CPU 与分片均衡。两者都可能让一个看似正常的 Redis 实例出现延迟抖动、超时甚至雪崩，治理思路分别是「拆小/异步删」与「分散/本地缓存」。**

**阈值没有官方标准，业界常用经验值：**

| 类型 | 大 key 参考阈值 | 说明 |
| --- | --- | --- |
| String | value > 10KB | 超过 10KB 就算偏大，超过 1MB 属于严重大 key |
| Hash / List / Set / ZSet | 元素数 > 5000，或单元素 > 10KB | 元素多与单元素大都要关注 |
| 整体实例 | 单个 key 内存占比 > 1% | 从容量与分片角度判断 |

**大 key 的危害：**

1. **命令阻塞**：`HGETALL`、`LRANGE 0 -1`、`SMEMBERS`、`DEL` 都是 O(N)，百万元素会阻塞主线程数秒。
2. **网络拥塞**：一次返回几十 MB，占满带宽与客户端缓冲区，触发 `client-output-buffer-limit` 断连。
3. **删除阻塞**：`DEL` 大 key 同步释放内存，可能卡住主线程；应使用 `UNLINK` 异步释放。
4. **fork 与 COW**：大 key 所在的内存页在 RDB/AOF fork 后被写入，会复制整页，内存可能翻倍。
5. **集群倾斜**：一个大 key 只落在一个槽、一个节点，造成单节点内存与流量远高于其他节点。
6. **迁移困难**：`MIGRATE` 大 key 会长时间占用源节点与目标节点，扩缩容卡住。
7. **主从延迟**：大 key 的写入/删除同步到从库耗时长，复制缓冲区膨胀。

**热 key 的危害：**

- 单 key 的 QPS 可能占整个实例的一半，单核 CPU 打满，其他请求被拖慢。
- 在 Cluster 中，热点 key 固定落在一个节点，无法靠增加分片分摊。
- 热点 key 过期瞬间可能引发缓存击穿，直接打到数据库。
- 监控上表现为「整体 QPS 不高，但某个节点 CPU 很高、延迟抖动」。

**发现手段：**

```bash
# 1. 扫描大 key：基于 SCAN，不会像 KEYS 那样阻塞，但会消耗 CPU，低峰期执行
redis-cli --bigkeys
# 输出示例：
# Biggest string found 'user:1001:profile' has 5242880 bytes
# Biggest list found 'feed:global' has 1200000 items
# 1 lists with 1200000 items (0.00% of keys, avg size 1200000.00)

# 2. 按内存排序找大 key（需要 MEMORY USAGE 支持）
redis-cli --memkeys

redis-cli MEMORY USAGE feed:global SAMPLES 0

```

**大 key 的治理：**

| 手段 | 做法 | 适用场景 |
| --- | --- | --- |
| 拆分 String | 按块存 `key:0`、`key:1`，读取时并发 `MGET` 再拼接 | 超大 JSON、图片、日志 |
| 拆分集合 | 按业务 ID 取模分桶，如 `cart:{uid}:0` ~ `cart:{uid}:99` | 大 Hash/List/Set/ZSet |
| 压缩 | 业务层 gzip/snappy 压缩后存 String | 文本类大 value |
| 异步删除 | 用 `UNLINK` 代替 `DEL`，或 `FLUSHALL ASYNC` | 删除大 key、清库 |
| 分页读取 | `HSCAN`、`SSCAN`、`ZSCAN`、`LRANGE` 分段 | 必须全量遍历时 |
| 冷热分离 | 大 key 归档到对象存储/ES，Redis 只留摘要 | 历史数据、日志 |
| 控制 TTL | 给大 key 设置合理过期时间，避免永久堆积 | 临时聚合数据 |

**热 key 的治理：**

| 手段 | 做法 | 代价 |
| --- | --- | --- |
| 本地缓存 | 进程内 Caffeine/Guava Cache 缓存热点，设短 TTL | 多实例一致性有延迟 |
| key 复制 | `hot:key:0` ~ `hot:key:N` 写多份，读时随机选 | 写入放大、内存浪费 |
| 读写分离 | 热点读打到多个从库 | 主从延迟、从库数量有限 |
| 请求合并 | 单航班（singleflight）合并并发回源 | 实现复杂，需处理失败 |
| 限流降级 | 对热点接口限流，返回兜底数据 | 影响部分用户体验 |
| 热点探测 | 代理层统计 key 访问频次，动态识别 | 需要额外组件 |

```bash
# 拆分大 Hash：按 uid 分桶，读时只取对应桶
HSET cart:{1001}:0 item:1 2
HSET cart:{1001}:1 item:9001 1
# 注意 {} 内内容相同，保证同槽；分桶编号放在 {} 外

# 异步删除大 key，避免主线程释放内存造成停顿
UNLINK feed:global

# 分页遍历大 Hash，避免 HGETALL
HSCAN user:1001 0 COUNT 100

# 分页读取大 List
LRANGE feed:global 0 99
LRANGE feed:global 100 199
```

**一个排查案例（把方法串起来）：**

某商品详情页接口 P99 从 20ms 涨到 800ms，Redis 整体 QPS 不高：

1. `INFO stats` 看到 `instantaneous_ops_per_sec` 正常，`SLOWLOG` 出现 `HGETALL product:detail:8899`，耗时 120ms。
2. `HLEN` 发现该 Hash 有 12 万个字段，`MEMORY USAGE` 约 80MB，确认是大 key。
3. 业务把「商品属性 + 库存 + 推荐」全塞进一个 Hash，读时 `HGETALL` 全量返回。
4. 治理：拆成 `product:{8899}:base`、`product:{8899}:stock` 等小 Hash，读接口按需 `HMGET`；历史字段归档到 MySQL；删除旧 key 用 `UNLINK`。
5. 同时发现 `product:config` 是热 key，加进程内缓存与 30 秒 TTL，读请求不再全部打到 Redis。
6. 上线后 `SLOWLOG` 不再出现该命令，P99 回到 25ms，单节点 CPU 从 90% 降到 45%。

**面试怎么答：**

先定义：大 key 看「value 大小/元素数量」，热 key 看「访问 QPS」。再分别讲危害：大 key 阻塞命令、网络、fork、迁移；热 key 打满单核、分片倾斜、过期击穿。最后给治理清单：大 key 拆分/压缩/UNLINK/分页，热 key 本地缓存/复制/读写分离/限流，并强调「低峰期用 SCAN 类工具检测，不要用 KEYS」。

**易错点：**

- 大 key 不只是 String 大，一个百万元素的 Hash/List/ZSet 同样是灾难。
- `DEL` 大 key 是同步释放，必须用 `UNLINK`；`UNLINK` 只是把释放交给后台线程，不是「不删」。
- `--bigkeys` 基于 SCAN，仍会消耗 CPU 与内存带宽，生产要在低峰执行。
- `--hotkeys` 依赖 LFU 策略，LRU 模式下结果没有意义。
- 拆分集合时要考虑多 key 命令：`MGET`、`SUNION` 在 Cluster 下要求同槽，分桶 key 要用 hash tag 控制。
- 热 key 复制会放大写入与内存，只适合读多写少的场景。

## 11. key 的设计规范与命名

**key 的命名不是「好看」问题，而是可运维性问题：它决定了排查时能否按业务定位、集群下能否控制同槽、内存是否被 key 本身浪费、以及能否安全地批量清理。推荐「业务域:对象:ID:属性」的分层结构，强制 TTL，控制长度，集群场景用 hash tag 控制同槽，禁止把用户输入直接拼进 key。**

**推荐结构：**

```text
业务域:对象:唯一标识:属性[:版本]
user:profile:1001:basic
order:detail:202410240001
cache:product:8899:v2
lock:order:202410240001
rate:api:1001:202410241200
```

| 规范 | 建议 | 原因 |
| --- | --- | --- |
| 分隔符 | 统一用冒号 `:` | 客户端工具、监控、SCAN 都按前缀识别 |
| 大小写 | 统一小写英文 + 数字 | 避免 `User`/`user` 被当成两个业务 |
| 长度 | 尽量 ≤ 128 字节，短前缀 + 必要 ID | key 本身也占内存，长 key 在百万级下很可观 |
| 可读性 | 见名知意，不用无意义缩写 | 排查、审计、迁移时能定位业务 |
| 唯一性 | 包含业务主键，避免碰撞 | 多业务共用实例时尤其重要 |
| 版本 | 结构变更时加 `:v2` | 支持灰度与回滚，避免新旧格式混读 |
| TTL | 除极少数配置/锁，一律设置过期 | 防止内存无限增长 |
| 特殊字符 | 避免空格、换行、控制字符 | 命令行、日志、URL 中易出错 |
| 用户输入 | 哈希或转义后再拼接 | 防止 key 注入、超长 key、热点构造 |

**Cluster 下的 hash tag：**

- Redis Cluster 用 `CRC16(key) mod 16384` 计算槽；如果 key 含有 `{...}`，只对第一个 `{}` 中的内容做哈希。
- `{user:1001}:profile` 与 `{user:1001}:cart` 落在同一槽，可以一起执行 `MGET`、`SUNION`、Lua。
- `{}` 为空时按整个 key 计算；`{a}{b}` 只取第一个 `{a}`。
- 滥用 hash tag 会让大量 key 挤在同一槽，形成新的热点，必须按「需要一起操作的维度」使用。

```bash
# 好的命名：业务 + 对象 + ID + 属性，带 TTL
SET user:profile:1001:basic '{"name":"张三"}' EX 3600
SET order:detail:202410240001 '{"amount":99.00}' EX 86400

# 需要一起操作的 key 用 hash tag 固定到同一槽
SET {user:1001}:profile '{"name":"张三"}' EX 3600
SET {user:1001}:cart '["item:1"]' EX 3600
MGET {user:1001}:profile {user:1001}:cart

# 用 SCAN 按前缀清理，不要用 KEYS
redis-cli --scan --pattern "cache:product:*" | head -n 100
# 分批删除
redis-cli --scan --pattern "cache:product:*" | xargs -n 100 redis-cli UNLINK

# 查看 key 的内存占用，评估命名长度是否值得
redis-cli MEMORY USAGE user:profile:1001:basic
```

**TTL 设计：**

- 缓存类 key 必须有过期时间，按数据变更频率设置：商品详情 5~30 分钟，用户资料 10~60 分钟，验证码 5 分钟。
- 同一批写入的 key 加随机抖动（如 `EX 3600 + random(0, 600)`），避免同一秒集中过期引发雪崩。
- 锁的 TTL 要略大于业务最长执行时间，并配合续期；不能设成永久。
- 配置类数据可以不过期，但要通过发布系统更新，不能靠人工改 Redis。

**常见命名反例：**

```text
user_1001                    # 分隔符不统一，无法按业务域扫描
User:1001                    # 大小写混用，可能被当成不同 key
cache:1001                   # 看不出缓存的是什么对象
order:202410240001:detail:all:fields:ext:...   # 过长，key 本身浪费内存
tmp:abc                      # 无业务含义，无法判断能否删除
lock:1001                    # 没有业务域，排查时不知道锁的是什么
user:{1001}                  # 单个 key 用 hash tag 没有收益，反而限制分片
```

**面试怎么答：**

按「可读、可控、可清理」三条讲：`业务:对象:ID:属性` 的命名、统一小写与冒号、长度控制、强制 TTL、版本号、hash tag 同槽、禁止用户输入直拼。再补两个运维细节：用 SCAN 而不是 KEYS 清理；key 本身也占内存，长 key 在千万级下不可忽视。

**易错点：**

- 冒号只是约定，没有语法含义；但统一约定能让监控、扫描、权限控制按前缀工作。
- hash tag 只认第一个 `{}`，`{user:1001}:profile:{v2}` 的槽只由 `user:1001` 决定。
- 滥用 hash tag 会把大量 key 压到一个节点，形成热点，反而失去分片意义。
- 给 key 加版本号要同时考虑旧数据迁移与双读，不能只改名字了事。
- 不要把密码、token、身份证号等敏感信息直接放进 key，key 会出现在慢日志、MONITOR、备份中。
- `KEYS pattern` 是 O(N) 且阻塞，生产清理一律用 `SCAN`。

## 12. Redis 与 Memcached 的对比

**两者都是内存 KV，但定位不同：Memcached 是「多线程、纯内存、只存字节」的缓存；Redis 是「单线程执行命令、带数据结构、可持久化、带主从与集群」的数据结构服务器。选 Memcached 通常是为了极简 KV 与多核横向吞吐；选 Redis 是为了丰富的数据操作、持久化、高可用与生态。**

| 维度 | Redis | Memcached |
| --- | --- | --- |
| 数据模型 | String/List/Hash/Set/ZSet/Stream/Bitmap/HyperLogLog 等 | 仅 key-value 字节串 |
| 线程模型 | 命令执行单线程，6.0 起 IO 多线程 | 多线程，命令可并行处理 |
| 持久化 | RDB、AOF、混合持久化 | 不支持，重启即丢 |
| 复制/高可用 | 主从、哨兵、Cluster | 原生不支持，靠客户端分片 |
| 集群 | 服务端 16384 槽分片 | 无服务端集群，客户端一致性哈希 |
| 事务/Lua | MULTI/EXEC、Lua、Function | 无，只有 CAS |
| 过期/淘汰 | 惰性 + 定期删除，8 种淘汰策略 | 惰性过期 + LRU（按 slab 分池） |
| 单 value 上限 | 512MB | 默认 1MB（可调，但大了性能差） |
| 内存分配 | jemalloc，按需分配 | slab allocator，预分配 slab class |
| 协议 | RESP | 文本协议 / 二进制协议 |
| 典型场景 | 缓存、排行榜、锁、队列、会话、计数 | 纯页面/对象缓存、大规模简单 KV |

**Memcached 的特点：**

- **多线程**：worker 线程并行处理请求，能利用多核，简单 KV 场景吞吐高。
- **slab 分配**：内存按固定大小的 chunk 分池，避免碎片，但会产生内部浪费；不同 slab class 之间不能借用内存，容易出现「有的池满、有的池空」。
- **纯内存**：不持久化、不复制，节点宕机数据全丢，需要客户端兜底回源。
- **LRU 是分池的**：每个 slab class 独立 LRU，整体命中率不如全局 LRU。
- **CAS**：`gets` 返回 cas token，`cas` 带 token 更新，能做简单的乐观并发控制。
- **客户端分片**：一致性哈希在多节点间分布 key，扩缩容需要迁移或双写。

**Redis 的特点：**

- **数据结构丰富**：List 做队列、ZSet 做排行榜、Hash 做对象、Set 做去重、Bitmap 做签到、HyperLogLog 做 UV 估算。
- **持久化与复制**：RDB/AOF 可以恢复，主从/哨兵/Cluster 提供高可用，适合不能接受「重启全丢」的场景。
- **单线程命令执行**：单机命令吞吐受单核限制，但无锁、延迟稳定；网络 IO 可用多线程分担。
- **功能多带来复杂度**：大 key、热 key、慢命令、fork 抖动、集群迁移都是额外运维成本。

```bash
# Redis：一个 key 存对象，还能按字段更新、计数、排序
HSET user:1001 name 张三 age 28
HINCRBY user:1001 age 1
ZADD rank:2024 980 user:1001

# Memcached：只有字节串，取出来必须整体反序列化再写回
# set user:1001 0 3600 32
# {"name":"张三","age":28}
# get user:1001
# VALUE user:1001 0 32
# {"name":"张三","age":28}
# END

# Memcached 的 CAS 更新（伪代码）
# gets user:1001        -> 返回 cas token 12345
# cas user:1001 0 3600 32 12345
# 若期间被别人修改，返回 EXISTS，需要重试

# Memcached 查看 slab 与命中率
# stats
# stats items
# stats slabs
```

**怎么选：**

| 场景 | 推荐 | 理由 |
| --- | --- | --- |
| 纯 HTML/对象缓存，KV 简单，追求多核吞吐 | Memcached | 多线程 + slab，简单高效 |
| 需要排行榜、计数器、队列、去重 | Redis | 原生数据结构，不必取回客户端计算 |
| 需要持久化、主从、故障自动切换 | Redis | Memcached 重启即丢、无复制 |
| 需要分布式锁、Lua 原子逻辑 | Redis | Memcached 只有 CAS |
| 单 value 很大、连接数很多 | Redis（配合拆分） | Memcached 默认 1MB，大 value 不友好 |
| 已有 Memcached 且稳定，只做缓存 | 不必迁移 | 迁移收益不足以抵消风险 |

**实际架构中的组合：**

- **Redis 做主缓存 + Memcached 做页面缓存**：两者并存并不冲突，但会增加运维与监控成本，多数团队最终会收敛到 Redis。
- **Redis 做锁/队列/排行榜 + 本地缓存挡热点**：Redis 不直接承受全部读流量，本地缓存承担秒级热点。
- **Memcached 做纯 KV + 数据库兜底**：命中率靠容量与 TTL，节点故障时客户端回源，需要限流防止打垮数据库。
- **迁移方向**：从 Memcached 迁 Redis 时，重点不是命令替换，而是数据结构重设计（Hash 字段、ZSet 排序、TTL 语义）与容量评估。

**面试怎么答：**

先给定位差异：Memcached 是「多线程纯 KV 缓存」，Redis 是「单线程执行、数据结构丰富、可持久化、带高可用」的服务器。再按数据模型、线程、持久化、集群、淘汰、value 上限逐项对比。最后给选型：简单 KV 追求多核吞吐可选 Memcached；需要结构、持久化、锁、排行榜、高可用选 Redis。补一句「Memcached 多线程不等于一定更快，Redis 的瓶颈常在单核与慢命令」。

**易错点：**

- Memcached 多线程是命令级并行，但受 slab 分池与锁影响，不代表任何场景都比 Redis 快。
- Memcached 的 LRU 是每个 slab class 独立，不是全局 LRU；内存池之间不能互相借用。
- Memcached 的过期是惰性 + LRU 驱逐，过期 key 也可能占内存。
- Memcached 没有原生集群与复制，所谓「集群」是客户端一致性哈希。
- Redis 单线程指的是命令执行，6.0 起网络 IO 可以是多线程，不要简单说「Redis 单线程所以比 Memcached 慢」。
- Memcached 默认 value 上限 1MB，超过需要改 `-I`，但大 value 会加剧内存碎片与网络延迟。
- Memcached 的 CAS 只保证单个 key 的原子更新，不能替代跨 key 事务。
- Redis 的持久化不是默认全开：`appendonly` 默认 `no`，只用 RDB 时仍可能丢失最后一次快照后的数据。
- Redis 的「单线程」与 Memcached 的「多线程」是命令执行模型，不代表整体吞吐的绝对高低。
