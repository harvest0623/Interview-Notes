## 1. 缓存穿透及解决方案

**缓存穿透是「查询一个根本不存在的数据」：缓存没有、数据库也没有，于是每次请求都穿过缓存打到数据库。它和击穿的区别是「数据不存在」而不是「热点过期」，和雪崩的区别是「单个/少量恶意 key」而不是「大面积失效」。核心方案是「让不存在也被记住」：缓存空值、布隆过滤器、参数校验与限流。**

**为什么会穿透：**

1. 攻击者构造随机 ID（如 `user:-1`、`product:999999999`）高频查询。
2. 业务查询逻辑是「缓存没有 → 查库 → 查不到 → 不写缓存」，导致每次都不命中。
3. 数据库对不存在的记录也执行了一次查询，QPS 高时连接池被打满。
4. 缓存层没有「不存在」的表示，无法区分「未缓存」与「确实不存在」。

**方案对比：**

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 缓存空值 | 查不到时写入 `null`/占位符，TTL 30~120 秒 | 实现简单，直接拦住重复查询 | 占用内存；数据后续创建时要清理空值 |
| 布隆过滤器 | 启动时/增量把存在的 ID 写入位图，查询前先判断 | 内存小，能拦住绝大多数随机 key | 有假阳性、标准实现不能删除、需要维护 |
| 参数校验 | ID 必须为正数、格式合法、范围合理 | 成本最低，拦住明显非法请求 | 无法拦住「格式合法但不存在」的 ID |
| 限流 | 按 IP/用户/接口限流 | 防止恶意刷接口 | 误伤正常用户，需精细策略 |
| 异步补偿 | 空值缓存 + 数据创建后删除空值 | 兼顾体验与一致性 | 依赖业务写入路径配合 |

**缓存空值的实现要点：**

- 用特殊占位符（如 `__NULL__`）而不是空字符串，避免与真实空值混淆。
- TTL 不要过长（30~120 秒），否则数据创建后长时间仍返回空。
- 数据创建/更新时，主动删除对应的空值 key，或让 TTL 自然过期。
- 空值也要防大 key：不要把大量不存在的 ID 永久缓存。

```bash
# 查询不存在的商品：写入空值占位符，60 秒过期
SET cache:product:999999 __NULL__ EX 60
GET cache:product:999999
# "__NULL__"

# 商品创建后，删除空值缓存，让下一次读回源
DEL cache:product:999999
```

```text
// 读路径伪代码
value = redis.get(key)
if value == "__NULL__":
    return nil
if value != nil:
    return value

value = db.query(key)
if value == nil:
    redis.set(key, "__NULL__", EX=60)   // 防穿透
    return nil
redis.set(key, value, EX=300 + random(0, 60))
return value
```

**布隆过滤器的接入方式：**

```bash
# RedisBloom 模块（需要加载模块，不是原生 Redis 命令）
BF.RESERVE product:bloom 0.01 1000000
# 误判率 1%，预计 100 万个元素

BF.ADD product:bloom 1001
BF.EXISTS product:bloom 1001
# (integer) 1
BF.EXISTS product:bloom 999999
# (integer) 0，一定不存在，直接返回空

# 批量写入
BF.MADD product:bloom 1002 1003 1004
```

- 布隆过滤器只能回答「可能存在」或「一定不存在」，不存在假阴性。
- 写入数据库成功后要同步写布隆；删除数据不能直接删布隆（标准 Bloom 不支持删除），需要重建或使用 Counting Bloom/Cuckoo Filter。
- 布隆的容量要预估，超过容量误判率会上升；扩容需要新建过滤器并逐步迁移。

**面试怎么答：**

先定义「查不存在的数据，缓存和 DB 都没有」，与击穿、雪崩区分。再给方案：缓存空值（短 TTL）、布隆过滤器（前置拦截）、参数校验、限流。最后讲空值 key 的清理与布隆的假阳性/不可删除，说明没有银弹，要组合使用。

**易错点：**

- 缓存空值不是「缓存一个空字符串」，要用独立占位符区分「不存在」与「空值」。
- 空值 TTL 太长会导致数据创建后长时间读不到；太短则防穿透效果有限。
- 布隆过滤器有假阳性，可能把「存在」误判为「不存在」吗？不会，只有「不存在」可能误判为「存在」。
- 标准布隆过滤器不支持删除，数据删除后必须重建或改用 Counting Bloom/Cuckoo。
- 布隆只能拦住「已加入过滤器的 ID 之外」的请求，攻击者用合法但不存在的 ID 仍可能穿透，需要配合空值与限流。
- 只做参数校验不能解决「格式合法但不存在」的穿透。

## 2. 缓存击穿及解决方案

**缓存击穿是「某个热点 key 在过期瞬间，大量并发请求同时未命中，全部去重建缓存/查数据库」。它针对单个热点 key，后果是数据库瞬间被打满。核心方案是「只让一个请求去重建」：互斥锁、逻辑过期 + 异步更新、热点 key 不过期、请求合并。**

**典型过程：**

1. 热点 key `product:8899` 在 12:00:00 过期。
2. 12:00:00 的几千个并发请求同时 `GET` 未命中。
3. 每个请求都去查数据库并回填缓存，数据库 QPS 瞬间放大几千倍。
4. 数据库连接池耗尽，接口超时，用户重试，进一步放大流量。

**方案对比：**

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 互斥锁重建 | `SET lock NX PX` 只有一个请求查库，其他等待/重试 | 实现简单，数据一致 | 等待延迟；锁超时/持有者崩溃需处理 |
| 逻辑过期 | value 内带 `expireAt`，过期后异步重建，先返回旧值 | 无等待，可用性高 | 短期返回旧数据；需要异步线程/队列 |
| 热点不过期 | 热点 key 不设 TTL，后台定时刷新 | 永不击穿 | 内存常驻；需要识别热点与刷新机制 |
| 请求合并 | 单航班/singleflight 合并同 key 请求 | 减少重复回源 | 进程内有效，多实例仍需分布式锁 |
| 本地缓存 | 热点放本地，短 TTL | 延迟最低 | 多实例一致性弱 |

**互斥锁重建的关键点：**

- 用 `SET lock:product:8899 <token> NX PX 3000` 抢锁，抢不到就短暂 sleep 后重试读缓存。
- 拿到锁后要「二次检查」缓存，避免前一个请求已经回填。
- 释放锁用 Lua 比较 token，避免误删别人的锁。
- 锁的过期时间要大于「查库 + 回填」的最长耗时；否则业务没完成锁就失效，仍会击穿。
- 等待方要设置最大重试次数/超时，不能无限等待。

```bash
# 抢重建锁：3 秒过期，token 防误删
SET lock:product:8899 token-abc NX PX 3000
# OK 表示抢到；(nil) 表示别人在重建

# 释放锁：只有 token 匹配才删除
EVAL "
  if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1])
  else
    return 0
  end
" 1 lock:product:8899 token-abc
```

```text
// 互斥重建伪代码
value = redis.get(key)
if value != nil:
    return value

if redis.set(lockKey, token, NX, PX=3000):
    try:
        value = redis.get(key)       // 二次检查
        if value == nil:
            value = db.query(key)
            redis.set(key, value, EX=300 + random(0, 60))
        return value
    finally:
        unlockLua(lockKey, token)
else:
    sleep(50ms)
    return readAgain(maxRetry=3)
```

**逻辑过期的实现：**

- 缓存 value 不设 Redis TTL，或设一个很长的 TTL；value 内部带 `expireAt`。
- 读取时发现 `expireAt` 已过，仍返回旧值，同时投递一个异步重建任务。
- 重建任务用分布式锁保证只有一个实例执行，完成后写入新值。
- 优点是没有等待，热点过期瞬间仍能服务；缺点是一段时间内读到旧数据，需要业务能接受。

```json
{
  "data": {"id": 8899, "name": "商品 A"},
  "expireAt": 1735689600000
}
```

**面试怎么答：**

先定义「单个热点 key 过期，大量并发同时回源」，与穿透（数据不存在）、雪崩（大面积失效）区分。再给方案：互斥锁 + 二次检查、逻辑过期 + 异步重建、热点不过期、请求合并。最后讲锁的 token、超时、等待上限，以及逻辑过期的旧数据窗口。

**易错点：**

- 只用 `SETNX` 不加过期时间，锁持有者崩溃会导致死锁。
- 拿到锁后不二次检查，可能重复查库。
- 释放锁不校验 token，可能删掉其他请求的锁。
- 锁的 TTL 小于业务耗时，锁提前失效仍会击穿。
- 逻辑过期返回旧值要评估业务容忍度，金融/库存类数据不能直接用。
- 请求合并只在单实例内有效，多实例仍需要 Redis 分布式锁。

## 3. 缓存雪崩及解决方案

**缓存雪崩是「大量 key 在同一时间失效」或「Redis 整体不可用」，导致请求全部打到数据库，数据库被打垮，进而引发系统级联故障。它与击穿的区别是「面」而不是「点」：击穿是一个热点 key，雪崩是一批 key 或整个缓存层。**

**两类原因：**

| 类型 | 原因 | 表现 |
| --- | --- | --- |
| 同时过期 | 批量预热时给同一批 key 设置了相同 TTL | 到点后大量 key 同时失效 |
| 缓存层故障 | Redis 宕机、主从切换、Cluster 故障、网络分区 | 所有请求直接回源 |
| 热点集中 | 大量请求依赖少数 key，这些 key 同时失效 | 局部雪崩 |
| 重试风暴 | 缓存超时后客户端无限重试 | 放大流量，拖垮 DB |

**解决方案：**

1. **TTL 加随机抖动**：在基础 TTL 上叠加随机值，把过期时间打散。
2. **Redis 高可用**：主从 + 哨兵/Cluster，故障自动切换；多可用区部署。
3. **本地缓存兜底**：热点数据在进程内留一份短 TTL 副本，Redis 挂了仍能顶住部分流量。
4. **熔断与限流**：缓存层故障时，对回源请求限流，超过阈值直接返回兜底/降级。
5. **预热**：大促/发布前把热点数据提前加载，避免冷启动瞬间回源。
6. **多级缓存**：CDN/本地/Redis 分层，单层故障不至于全部穿透。
7. **持久化与快速恢复**：RDB/AOF 让 Redis 重启后快速恢复，缩短不可用时间。
8. **监控告警**：命中率、QPS、延迟、连接数、DB QPS 联动监控。

```text
// TTL 抖动：基础 3600 秒，随机加 0~600 秒
ttl = 3600 + random(0, 600)
redis.set(key, value, EX=ttl)

// 批量预热时也逐 key 设置不同 TTL，避免同一秒过期
for key in hotKeys:
    redis.set(key, load(key), EX=3600 + random(0, 600))
```

```bash
# 查看缓存命中率与 key 数量，评估雪崩风险
redis-cli INFO stats | grep -E "keyspace_hits|keyspace_misses|expired_keys|evicted_keys"
# 命中率 = hits / (hits + misses)

# 查看是否有大量 key 同时过期（抽样 TTL）
redis-cli --scan --pattern "cache:product:*" | head -n 20 | while read k; do
  redis-cli TTL "$k"
done

# 查看 Redis 是否处于故障/切换状态
redis-cli INFO replication
redis-cli -p 26379 SENTINEL get-master-addr-by-name mymaster
redis-cli CLUSTER INFO
```

**降级策略：**

- Redis 超时/不可用时，不再同步回源，而是返回本地缓存、默认值或稍后重试。
- 对数据库设置并发上限（信号量/连接池隔离），缓存故障时只放少量探测流量。
- 使用熔断器（如 Sentinel/Hystrix/Resilience4j）在错误率超阈值时快速失败。
- 降级不是「永久关闭缓存」，要有恢复探测与自动回切。

**面试怎么答：**

先定义「大面积 key 失效或缓存层整体故障」，与击穿、穿透区分。再给原因：同时过期、Redis 故障、热点集中、重试风暴。方案按「预防（TTL 抖动、高可用、预热）+ 兜底（本地缓存、限流、熔断、降级）+ 恢复（持久化、监控）」三层回答。

**易错点：**

- 只做 TTL 抖动不能解决 Redis 整体宕机，必须配合高可用与降级。
- 缓存故障时「全部回源」是最危险的操作，必须限流，否则 DB 会被打垮。
- 本地缓存 TTL 太长会导致长期脏数据，太短则兜底效果有限。
- 重试要加退避与上限，否则缓存超时会变成重试风暴。
- 预热要在低峰执行并限速，避免预热本身把 DB 打满。
- 雪崩不是「缓存命中率低」的同义词，命中率低可能是容量不足或 key 设计问题。

## 4. 缓存与数据库的一致性（旁路缓存、延迟双删、binlog 订阅）

**缓存与数据库的一致性本质是「两个存储的更新不是原子的」。最常用的是 Cache-Aside（旁路缓存）：读时先查缓存、未命中查库并回填；写时先更新数据库、再删除缓存。它能做到最终一致，但在「删除失败」「读写并发」「主从延迟」下会出现短暂不一致。延迟双删只能缩小窗口，binlog 订阅能把「删缓存」变成可靠、可重试的异步动作，彻底强一致则需要锁/串行化或放弃缓存。**

**Cache-Aside 的标准流程：**

```text
读：GET cache → 命中返回
             → 未命中 → 查 DB → 回填 cache（带 TTL）→ 返回

写：UPDATE DB（提交）
   → DEL cache
   → 失败则重试/投递 MQ/binlog 补偿
```

**为什么是「删缓存」而不是「更新缓存」：**

| 做法 | 并发写 A、B 的结果 | 问题 |
| --- | --- | --- |
| 先更新 DB 再更新缓存 | A 更新 DB=1，B 更新 DB=2；B 先写缓存=2，A 后写缓存=1 | 缓存最终是旧值 1 |
| 先更新 DB 再删缓存 | A、B 都删缓存，下一次读回源得到 DB 当前值 2 | 短暂未命中，但最终一致 |
| 先删缓存再更新 DB | 读请求在删后、更新前回源，把旧值写回缓存 | 缓存长期旧值，除非再有删除 |

删除比更新更安全：删除后下一次读一定回源，能把并发写的顺序问题交给数据库；更新缓存则要求「谁后写缓存」与「谁后写 DB」顺序一致，很难保证。

**不一致的三种典型场景：**

1. **删缓存失败**：DB 更新成功，`DEL` 因网络/超时失败，缓存仍是旧值，直到 TTL 过期。
   - 解决：删除重试、投递 MQ、binlog 订阅补偿、缩短 TTL。
2. **读写并发**：读请求未命中 → 查 DB 得到旧值 → 写请求更新 DB 并删缓存 → 读请求把旧值回填。
   - 解决：延迟双删（写后延迟再删一次）、给缓存加版本号、读写锁/串行化。
3. **主从延迟**：写主库后立即读从库，读到旧值并回填缓存。
   - 解决：关键读走主库、会话粘滞、延迟双删、binlog 按位点消费。

**延迟双删：**

```text
写流程：
1. UPDATE DB
2. DEL cache
3. sleep(D)                   // D 略大于「一次读+回填」的耗时，常见 300~1000ms
4. DEL cache                   // 删掉步骤 2~3 之间可能被回填的旧值
```

- 第一次删除在更新 DB 后，第二次删除在延迟后，目的是覆盖「并发读回填旧值」的窗口。
- 延迟时间没有标准值，要按业务读耗时、主从延迟估算；太短无效，太长影响一致性窗口。
- 延迟双删仍不是强一致：延迟期间仍可能读到旧值，且第二次删除也可能失败。
- 删除失败要有重试/补偿，不能假设 `DEL` 一定成功。

```bash
# 写后删除缓存（伪代码）
redis-cli DEL product:8899
# 返回 0 只表示 key 本就不存在，不算失败；命令报错/超时才投递补偿任务
```

**binlog 订阅（Canal/Debezium）：**

```text
业务写 DB（提交）
   → binlog
   → Canal/Debezium 解析 row change
   → 投递 MQ（可靠、可重试）
   → 缓存消费者按 key 删除/更新
```

- 优点：与数据库提交顺序一致，删除动作可重试、可审计，不依赖业务代码「记得删缓存」。
- 缺点：链路长、延迟（通常毫秒到秒级）、需要维护 Canal/MQ、要处理重复消息（删除是幂等的）。
- 适合多个写入方、跨服务共享缓存的场景；单服务简单写入用 Cache-Aside + 重试即可。
- 消费要按主键删除，不要按业务字段批量删；重复消费最多多删一次，不会造成脏数据。

| 方案 | 一致性 | 复杂度 | 适用场景 |
| --- | --- | --- | --- |
| 先更 DB 再删缓存 | 最终一致，窗口小 | 低 | 大多数业务 |
| 延迟双删 | 最终一致，窗口更小 | 低中 | 读写并发高、主从延迟明显 |
| binlog 订阅 | 最终一致，可靠补偿 | 高 | 多写入方、共享缓存、要求可审计 |
| 读写锁/串行化 | 接近强一致 | 高 | 极少数强一致场景 |
| 不用缓存 | 强一致 | 低 | 数据量小、QPS 低 |

```text
// Cache-Aside 伪代码（含删除重试）
def write(key, value):
    db.update(key, value)
    try:
        redis.delete(key)
    except Exception:
        mq.send("cache:delete", key)   // 异步补偿

def read(key):
    v = redis.get(key)
    if v != nil:
        return v
    v = db.query(key)
    if v != nil:
        redis.set(key, v, EX=300 + random(0, 60))
    return v
```

**面试怎么答：**

先给标准答案「先更新数据库，再删除缓存（Cache-Aside）」，解释为什么删而不是更新。再讲三种不一致场景：删除失败、读写并发、主从延迟，对应延迟双删、重试/MQ、binlog 订阅。最后明确「缓存只能最终一致，强一致要么加锁串行化，要么不用缓存」。

**易错点：**

- 「先删缓存再更新 DB」在并发读下会把旧值回填，通常不推荐。
- 延迟双删的延迟不是固定 500ms，要按业务读写耗时与主从延迟调整。
- 删除缓存失败不能只靠 TTL 兜底，关键数据要重试/补偿。
- binlog 订阅有延迟，消费端要幂等，重复删除是安全的。
- 主从延迟下「写主读从」会读到旧值，缓存会把这个旧值放大。
- 更新缓存比删除缓存更容易出现「后写 DB 的先写缓存」导致长期脏数据。

## 5. 分布式锁（SETNX、看门狗、Redlock）

**Redis 分布式锁的最小正确实现是一条命令：`SET key value NX PX ttl`，value 用唯一 token；解锁必须用 Lua 比较 token 再删除，防止误删别人的锁。业务执行时间不确定时，需要看门狗自动续期；跨多个独立 Redis 实例的强可用场景可以用 Redlock，但它依赖时钟与网络假设，仍有争议，强一致场景应配合 fencing token 或改用 etcd/ZooKeeper。**

**一把合格的分布式锁要满足：**

1. **互斥**：同一时刻只有一个客户端持有锁。
2. **不死锁**：锁必须有过期时间，持有者崩溃后能自动释放。
3. **不误删**：只能释放自己持有的锁，value 用唯一 token。
4. **可重入**（可选）：同一线程/协程可以多次获取。
5. **高可用**：Redis 主从切换后锁语义不被破坏（这是最难的部分）。

**加锁与解锁：**

```bash
# 加锁：NX 保证互斥，PX 保证不会死锁，value 是唯一 token
SET lock:order:1001 8f4a-token NX PX 30000
# OK 表示获取成功；(nil) 表示已被占用

# 解锁：必须比较 token，避免锁过期后被别人持有却删了别人的锁
EVAL "
  if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1])
  else
    return 0
  end
" 1 lock:order:1001 8f4a-token
```

**为什么不能 `SETNX` + `EXPIRE` 两条命令：**

- `SETNX` 成功、`EXPIRE` 之前进程崩溃，锁永不过期，形成死锁。
- 两条命令之间不是原子的，必须用 `SET key value NX PX` 一条命令完成。
- 解锁同理：`GET` 判断后再 `DEL` 不是原子操作，必须用 Lua。

**看门狗（watchdog）：**

- 业务执行时间可能超过锁 TTL，需要后台线程定期续期。
- Redisson 的 `RLock.lock()` 默认 leaseTime 30 秒，看门狗每 10 秒（1/3 周期）续期一次，直到 `unlock()`。
- 若显式指定 `lock(leaseTime, unit)`，则不会启用看门狗，到期自动释放。
- 续期失败（Redis 不可用/网络问题）时，锁到期后其他客户端可获取，业务要能处理「锁已失效」。

```text
// Redisson 伪代码
RLock lock = redisson.getLock("lock:order:1001");
lock.lock();              // 不指定 leaseTime，启用看门狗，默认 30s，每 10s 续期
try {
    // 业务逻辑
} finally {
    lock.unlock();        // 只有持有者能解锁
}

// 指定 leaseTime：不启用看门狗，到期自动释放
lock.lock(10, TimeUnit.SECONDS);
```

**Redlock 算法：**

1. 准备 N 个**相互独立**的 Redis master（通常 5 个，不要求主从）。
2. 客户端记录开始时间，依次向每个实例执行 `SET key token NX PX ttl`。
3. 只有在多数（`N/2 + 1`）实例加锁成功，且总耗时小于 TTL 时，才算获取成功。
4. 获取成功后，锁的有效时间 = TTL - 加锁总耗时 - 时钟漂移。
5. 释放时向所有实例发送 Lua 解锁。
6. 如果失败，向所有实例发送解锁，清理可能的部分加锁。

```text
N=5，需要 3 个成功：
client ──→ Redis1 OK
       ──→ Redis2 OK
       ──→ Redis3 OK   → 成功，有效时间 = TTL - 总耗时 - drift
       ──→ Redis4 失败
       ──→ Redis5 超时
```

**Redlock 的争议：**

- Martin Kleppmann 指出：Redlock 依赖各节点时钟大致同步、网络延迟有上限；进程暂停（GC/STW）或时钟跳变可能导致两个客户端同时持锁。
- 即使 Redlock 加锁成功，如果业务在锁内访问的是「非 Redis 的外部资源」，仍需要 fencing token（单调递增的版本号）让资源侧拒绝旧锁的写入。
- Redis 作者 antirez 认为 Redlock 在合理假设下可用，但承认它不是强一致共识算法。
- 工程结论：普通业务用「单 Redis 主从 + SET NX PX + Lua 解锁 + 看门狗」足够；强一致场景用 etcd/ZooKeeper 或数据库行锁/唯一约束。

| 方案 | 互斥 | 自动释放 | 高可用 | 强一致 | 适用 |
| --- | --- | --- | --- | --- | --- |
| `SET NX PX` 单实例 | 是 | 是 | 依赖主从 | 否 | 大多数业务 |
| Redisson + 看门狗 | 是 | 是 | 依赖主从 | 否 | 长任务、需要续期 |
| Redlock（5 实例） | 多数派 | 是 | 较好 | 仍有争议 | 跨实例、容忍一定风险 |
| etcd/ZooKeeper | 是 | 是（会话） | 强 | 较好 | 强一致、配置/选主 |

**面试怎么答：**

先给最小正确实现：`SET key token NX PX ttl` + Lua 比较 token 解锁。再讲为什么不能 `SETNX` + `EXPIRE`、为什么需要看门狗、Redlock 的多数派流程与争议。最后给选型：普通业务单实例足够，强一致用 etcd/ZooKeeper 或 fencing token。

**易错点：**

- `SETNX` 成功后再 `EXPIRE` 不是原子操作，崩溃会死锁。
- 解锁不校验 token 会误删别人的锁；必须用 Lua。
- 锁 TTL 小于业务耗时，业务还没结束锁就失效，互斥被破坏。
- 看门狗只在「不指定 leaseTime」时生效；显式指定 leaseTime 不会续期。
- Redlock 不是「绝对安全」，时钟漂移、进程暂停、网络分区都可能破坏互斥。
- 主从切换可能丢锁：主库加锁成功但未同步到从库，主库挂后从库没有锁，另一个客户端可再次加锁。
- 锁的 value 不要用固定字符串，必须每次加锁生成唯一 token。

## 6. 基于 Redis 的限流（固定窗口、滑动窗口、令牌桶）

**限流的核心是「在分布式环境下原子地计数/扣减」。Redis 的优势是单线程命令原子、可用 Lua 把「读-判断-写」打包；难点是选对算法：固定窗口简单但有边界突刺，滑动窗口精确但内存高，令牌桶能控制速率并允许一定突发。生产上通常用 Lua 脚本或 Redis Cell 模块，避免多条命令之间的竞态。**

**四种算法对比：**

| 算法 | 实现 | 优点 | 缺点 | 适用 |
| --- | --- | --- | --- | --- |
| 固定窗口 | `INCR` + `EXPIRE` | 简单、内存小 | 窗口边界可能放过 2 倍流量 | 粗粒度限流 |
| 滑动窗口日志 | `ZADD` + `ZREMRANGEBYSCORE` + `ZCARD` | 精确，任意时间窗口 | 每个请求存一条，内存高 | 低频/精确限流 |
| 滑动窗口计数 | 当前窗口 + 上一窗口加权 | 内存小，较平滑 | 近似，仍有误差 | 通用 API 限流 |
| 令牌桶 | 令牌按速率补充，请求取令牌 | 允许突发，速率可控 | 实现稍复杂 | 网关/接口限流 |
| 漏桶 | 请求排队，按固定速率流出 | 输出平滑 | 增加延迟，队列有上限 | 保护下游 |

**固定窗口：**

```lua
-- KEYS[1] = rate:api:1001:202410241200
-- ARGV[1] = 窗口毫秒数，ARGV[2] = 上限
local current = redis.call('INCR', KEYS[1])
if current == 1 then
    redis.call('PEXPIRE', KEYS[1], ARGV[1])
end
if current > tonumber(ARGV[2]) then
    return 0
end
return 1
```

- 窗口 key 可以按分钟/小时拼进 key，也可以让 key 自己过期。
- 边界问题：窗口 1 分钟、上限 100，在第 59 秒来 100 个、第 61 秒来 100 个，实际 2 秒内放了 200 个。
- 解决边界突刺可以用滑动窗口或令牌桶。

**滑动窗口日志：**

```lua
-- KEYS[1] = rate:api:1001
-- ARGV[1] = now(ms)，ARGV[2] = window(ms)，ARGV[3] = limit，ARGV[4] = 唯一 member
redis.call('ZREMRANGEBYSCORE', KEYS[1], 0, tonumber(ARGV[1]) - tonumber(ARGV[2]))
local count = redis.call('ZCARD', KEYS[1])
if count < tonumber(ARGV[3]) then
    redis.call('ZADD', KEYS[1], ARGV[1], ARGV[4])
    redis.call('PEXPIRE', KEYS[1], ARGV[2])
    return 1
end
return 0
```

- 每个请求存一个 member，score 是时间戳；先清理窗口外的，再计数。
- member 必须唯一（UUID 或「时间戳 + 随机数」），否则同一毫秒的重复请求会被 ZADD 覆盖。
- 内存与请求量成正比，适合低频接口；高频接口用滑动窗口计数或令牌桶。

**令牌桶：**

```lua
-- KEYS[1] = rate:token:api:1001
-- ARGV[1] = rate（每秒补充令牌数），ARGV[2] = capacity，ARGV[3] = now(ms)，ARGV[4] = 请求令牌数
local data = redis.call('HMGET', KEYS[1], 'tokens', 'last')
local tokens = tonumber(data[1])
local last = tonumber(data[2])
if tokens == nil then
    tokens = tonumber(ARGV[2])
    last = tonumber(ARGV[3])
end
local delta = math.max(0, tonumber(ARGV[3]) - last)
local refill = delta * tonumber(ARGV[1]) / 1000
tokens = math.min(tonumber(ARGV[2]), tokens + refill)

if tokens >= tonumber(ARGV[4]) then
    tokens = tokens - tonumber(ARGV[4])
    redis.call('HMSET', KEYS[1], 'tokens', tokens, 'last', ARGV[3])
    redis.call('PEXPIRE', KEYS[1], 60000)
    return 1
end
redis.call('HMSET', KEYS[1], 'tokens', tokens, 'last', ARGV[3])
redis.call('PEXPIRE', KEYS[1], 60000)
return 0
```

- 桶容量 `capacity` 决定允许多大的突发，补充速率 `rate` 决定长期平均 QPS。
- 时间用 Redis 服务端时间或客户端时间要统一，避免多实例时钟不一致。
- 也可以用 Redis Cell 模块：`CL.THROTTLE key max burst rate per`，返回是否允许、剩余令牌、重试时间。

```bash
# Redis Cell 示例：每 60 秒最多 100 次，桶容量 200
CL.THROTTLE rate:api:1001 200 100 60
# 1) (integer) 0      # 0 允许，1 拒绝
# 2) (integer) 201    # 总配额（max_burst + 1）
# 3) (integer) 200    # 剩余令牌
# 4) (integer) -1     # 需要等待的秒数，-1 表示无需等待
# 5) (integer) 60     # 重置时间
```

**限流的工程细节：**

- **键的维度**：按 IP、用户 ID、接口、租户组合，避免单维度被绕过。
- **拒绝策略**：返回 429 + `Retry-After`，或排队/降级，不要静默丢弃。
- **Redis 故障**：限流器不可用时是「放行」还是「拒绝」要提前决定；保护下游通常选择本地兜底限流。
- **时钟**：多实例用同一个时间源（Redis `TIME` 或 NTP），不要依赖各自本地时间。
- **原子性**：多条命令必须用 Lua 或事务，避免「读计数 → 判断 → 写」之间插入其他请求。
- **清理**：窗口 key 要设置过期，避免无限增长。

**面试怎么答：**

先给四种算法对比：固定窗口简单但有边界突刺，滑动窗口精确但内存高，令牌桶允许突发、适合网关。再讲 Redis 实现要点：`INCR` + `EXPIRE` 的原子性用 Lua、滑动窗口用 ZSET、令牌桶用 Hash + Lua。最后补工程细节：维度、429、Redis 故障兜底、时钟统一。

**易错点：**

- `INCR` 和 `EXPIRE` 两条命令不是原子的，第一次 `INCR` 后崩溃会导致 key 永不过期。
- 固定窗口在边界可能放过 2 倍流量，不是「严格 N 次/窗口」。
- 滑动窗口的 ZSET member 必须唯一，否则同一时间戳的请求会互相覆盖。
- 令牌桶的 `last` 时间不要用各实例本地时钟，否则补充速率会漂移。
- 限流 key 不设 TTL 会无限增长，尤其是按用户/IP 维度。
- Redis 故障时无限放行会打垮下游，必须本地兜底或快速失败。

## 7. 排行榜与 zset 实战

**排行榜是 ZSet 最典型的场景：`ZADD`/`ZINCRBY` 写入分数，`ZREVRANGE` 取 Top N，`ZREVRANK` 查个人名次，`ZRANGEBYSCORE` 做区间查询。难点不在命令，而在「同分排序、分数精度、周期榜合并、深分页与内存上限」。设计时要先确定榜单规模与更新频率，再决定是「全量 ZSet」还是「只保留 Top N + 个人分数」。**

**基础操作：**

```bash
# 写入/覆盖分数
ZADD rank:2024:10 980 user:1001 950 user:1002 920 user:1003

# 原子加分，返回新分数
ZINCRBY rank:2024:10 20 user:1001
# "1000"

# Top 10（从高到低），带分数
ZREVRANGE rank:2024:10 0 9 WITHSCORES

# 个人排名（从 0 开始，0 表示第一名）
ZREVRANK rank:2024:10 user:1002
# (integer) 1

# 个人分数
ZSCORE rank:2024:10 user:1002
# "950"

# 榜单总人数
ZCARD rank:2024:10

# 分数区间查询（1000 分以上）
ZRANGEBYSCORE rank:2024:10 1000 +inf WITHSCORES
```

**同分排序与分数精度：**

- score 是 IEEE 754 double，尾数 53 位，能精确表示的最大整数是 2^53-1（约 9.007e15）。
- 如果 score 用「积分 × 10^6 + 时间戳」编码，很容易超过 2^53，导致精度丢失、排名错乱。
- 同分时 Redis 按 member 的字典序（`memcmp`）排序，不是按写入时间。
- 需要「同分先达到者靠前」时，可以把时间编码进一个安全范围内的分数，或改用额外字段在应用层排序。
- 更稳妥的做法：score 只存业务分值，同分顺序由业务接受字典序，或把「时间」作为 member 的一部分（但会影响查询）。

```text
// 错误示例：分数 = 积分 * 1e9 + (maxTime - timestamp)
// 积分 1000 万时已经接近 1e16，超过 2^53，double 会丢精度
// 正确做法：控制量级，例如 积分 * 1e4 + (9999 - 秒级时间偏移)，确保 < 2^53
```

**周期榜与合并：**

```bash
# 日榜、周榜、月榜分别用不同 key
ZINCRBY rank:2024:10:day:24 10 user:1001
ZINCRBY rank:2024:10:week:43 10 user:1001
ZINCRBY rank:2024:10:month:10 10 user:1001

# 合并多个榜（权重 1:1，分数相加）
ZUNIONSTORE rank:2024:10:total 2 rank:2024:10:day:24 rank:2024:10:day:25 \
  WEIGHTS 1 1 AGGREGATE SUM

# 给周期榜设置过期，避免无限增长（日榜保留 7 天）
EXPIRE rank:2024:10:day:24 604800
```

- `ZUNIONSTORE` 的 `AGGREGATE` 支持 `SUM`/`MIN`/`MAX`，合并时同 member 按规则聚合。
- 合并大榜是 O(N)，不要在高频请求里做；用定时任务预计算。
- 周期榜要设置 TTL，否则历史榜单会持续占内存。

**只保留 Top N：**

```bash
# 榜单只保留前 10 万名，删除排名 10 万之后的成员
ZREMRANGEBYRANK rank:2024:10 100000 -1

# 统计删除数量
ZCARD rank:2024:10
```

- `ZREMRANGEBYRANK key 0 -(N+1)` 删除最低的成员，保留前 N。
- 被删除的用户再次加分时会重新插入，但历史分数已丢；如果要查「未上榜用户的名次」，就不能裁剪。
- 大榜裁剪后 `ZCARD` 不再等于总参与人数，需要用额外计数（HyperLogLog/数据库）统计参与量。

**分页与深分页：**

```bash
# 第 1 页：0~19
ZREVRANGE rank:2024:10 0 19 WITHSCORES

# 第 100 页：1980~1999
ZREVRANGE rank:2024:10 1980 1999 WITHSCORES
```

- `ZREVRANGE start stop` 的复杂度是 O(log N + M)，M 是返回元素数；翻到很深的位置仍要先跳过前面的元素，但不需要扫描全部。
- 不要一次取 `0 -1`，大榜会返回全部成员并阻塞。
- 前端无限滚动可以用「上一页最后一个 score + member」做游标：`ZREVRANGEBYSCORE key (score -inf WITHSCORES LIMIT 0 20`，避免 offset 漂移。

**热点与分片：**

- 榜单 key 往往是热 key，Top N 可以放本地缓存（短 TTL），减少 Redis 读。
- 超大规模榜单可按业务维度拆（如分区榜、好友榜），避免单个 ZSet 过大。
- 写入用 `ZINCRBY` 是 O(log N)，但高频写入同一 key 仍会集中到单节点；可先本地聚合再批量写。

**面试怎么答：**

先给四条命令：`ZINCRBY` 写、`ZREVRANGE` 取 Top N、`ZREVRANK` 查名次、`ZREVRANGEBYSCORE` 游标分页。再讲三个坑：score 是 double 有精度上限、同分按字典序、裁剪后无法查未上榜名次。最后讲周期榜用 `ZUNIONSTORE` 预计算、榜单加 TTL、热 key 本地缓存。

**易错点：**

- score 不是无限精度，超过 2^53 的整数会丢精度，编码时间戳时要控制量级。
- 同分不是「先到先得」，而是按 member 字典序；需要业务确认能否接受。
- `ZREVRANGE 0 -1` 是 O(N)，大榜会阻塞，必须分页。
- `ZREMRANGEBYRANK` 裁剪后，未上榜用户无法再查真实名次。
- `ZUNIONSTORE` 是 O(N)，不要在高频接口里实时合并大榜。
- 榜单 key 不设 TTL 会永久占内存，周期榜尤其明显。
- 高频 `ZINCRBY` 同一 key 会形成热 key，必要时本地聚合/分片。

## 8. 分布式 Session 与登录态

**分布式 Session 的核心是「把会话从单机内存搬到共享存储」，让任意应用实例都能识别同一个用户。常见做法是用 Redis 存 Session（Spring Session 默认）或自定义 token → userId 映射；登录态还需要处理过期续期、主动注销、多端登录与安全属性。它与 JWT 的取舍是「服务端可撤销」与「无状态」之间的取舍。**

**方案对比：**

| 方案 | 存储 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 粘性 Session | 单机内存 + 负载均衡粘滞 | 简单、无额外存储 | 扩容/故障会丢会话，负载不均 |
| Session 复制 | 各实例互相同步 | 无需共享存储 | 网络与内存开销大，不一致 |
| Redis Session | Redis Hash/String | 共享、可过期、可水平扩展 | 依赖 Redis 高可用，多一次网络 |
| JWT | 客户端保存签名 token | 无状态、易扩展 | 难以主动撤销、体积大、需防泄露 |
| Redis + JWT | JWT 携带身份 + Redis 存黑名单/版本 | 兼顾无状态与可撤销 | 实现复杂，仍有 Redis 依赖 |

**Spring Session 的结构：**

```text
spring:session:sessions:<sessionId>       Hash
  ├─ creationTime
  ├─ lastAccessedTime
  ├─ maxInactiveInterval
  ├─ sessionAttr:userId
  └─ sessionAttr:roles

spring:session:sessions:expires:<sessionId>   String，用于过期触发
spring:session:expirations:<timestamp>        Set，按分钟分组，扫描过期
```

- Spring Session 会给 session key 设置 TTL，并在访问时更新 `lastAccessedTime`。
- 它用额外的 expires/expirations key 处理「过期事件」，避免只依赖 Redis 的惰性删除。
- 序列化默认 JDK，生产建议改为 JSON（如 Jackson）以避免版本兼容问题。

**自定义 token 登录态：**

```bash
# 登录成功：生成随机 token（128 位以上），存 userId，30 分钟过期
SET session:token:8f4a9c2e user:1001 EX 1800

# 每次请求校验：存在且 userId 匹配
GET session:token:8f4a9c2e
# "user:1001"

# 滑动续期：访问时重置 TTL（注意频繁写放大）
EXPIRE session:token:8f4a9c2e 1800

# 退出登录：删除 token
DEL session:token:8f4a9c2e

# 多端登录管理：用户的所有 token 放一个 Set
SADD user:sessions:1001 8f4a9c2e
SMEMBERS user:sessions:1001
```

**过期续期的两种策略：**

| 策略 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 滑动过期 | 每次访问 `EXPIRE` 重置 | 活跃用户不掉线 | 每次请求都写 Redis，放大写压力 |
| 绝对过期 | 登录时定死过期时间，不续期 | 写少、安全边界清晰 | 活跃用户到点也会掉线 |
| 折中 | 剩余 TTL 小于阈值时才续期 | 减少写、兼顾体验 | 实现稍复杂 |

```text
// 折中续期伪代码
ttl = redis.ttl(tokenKey)
if ttl > 0 and ttl < 600:          // 剩余不足 10 分钟才续
    redis.expire(tokenKey, 1800)
```

**主动注销与多端控制：**

- 单端注销：`DEL session:token:<token>`，并从 `user:sessions:<uid>` 中 `SREM`。
- 全端注销：读取 `user:sessions:<uid>` 的所有 token 并逐个删除，或递增 `user:tokenVersion:<uid>`，校验时比对版本。
- JWT 撤销：维护黑名单 `jwt:blacklist:<jti>`，TTL 设为 token 剩余有效期；或按用户版本号失效所有旧 token。
- 修改密码/封号：必须使旧会话失效，不能只依赖 TTL。

**安全要点：**

- token 必须用密码学安全随机数（如 128 位以上），不能自增 ID 或可预测字符串。
- Cookie 设置 `HttpOnly`、`Secure`、`SameSite=Lax/Strict`，降低 XSS/CSRF 风险。
- 登录成功后轮换 session id，防止会话固定攻击。
- 不要在 Redis 里存明文密码、身份证等敏感信息；必要时加密。
- 绑定 IP/UA 要谨慎，移动网络切换会导致误杀。

**面试怎么答：**

先给方案对比：粘性、复制、Redis、JWT、混合。再讲 Redis 结构：Spring Session 的 Hash + expires，或自定义 `session:<token> → userId`。重点讲 TTL 续期（滑动 vs 绝对 vs 折中）、注销与多端控制、安全属性。最后给选型：需要主动撤销用 Redis Session，纯无状态用 JWT，混合用 JWT + 黑名单/版本。

**易错点：**

- Session 存在 Redis 不等于「永不过期」，必须设置 TTL 并处理续期。
- 每次请求都 `EXPIRE` 会放大写压力，高 QPS 下用「剩余 TTL 不足才续」。
- 注销只删 Cookie 不删 Redis，token 仍可被重放。
- JWT 无状态但难以撤销，必须配合黑名单或短过期 + 刷新 token。
- Spring Session 默认 JDK 序列化，跨版本/跨语言可能不兼容。
- Redis 故障时登录态全部失效，需要本地缓存/降级或接受短暂不可用。
- token 放在 URL 参数会进入日志/Referer，应放在 Cookie 或 Authorization 头。

## 9. 用 Stream 做轻量消息队列

**Redis Stream 是 5.0 引入的日志型数据结构：消息按 ID 追加，支持消费组、ACK、pending 列表与消息认领，能做「轻量消息队列」。它比 List 的 `BLPOP` 多了「消费组 + 未确认消息 + 多消费者分摊」，比 Kafka 轻但缺少分区、跨节点复制与长期持久化能力。适合任务量不大、已有 Redis、能接受内存存储的场景。**

**核心概念：**

| 概念 | 说明 |
| --- | --- |
| Stream | 一个只追加的消息日志，每条消息有唯一 ID（`毫秒-序号`） |
| Consumer Group | 消费组，组内多个消费者分摊消息，组维护 last-delivered-id |
| Pending List（PEL） | 已投递但未 ACK 的消息，按消费者分组记录 |
| ACK | 消费者处理成功后确认，消息从 PEL 移除 |
| Claim | 把长时间未 ACK 的消息转移给其他消费者重试 |

**基本命令：**

```bash
# 写入消息，* 表示自动生成 ID
XADD stream:order * order_id 1001 event created
# "1735689600000-0"

# 创建消费组，从 0 开始（$ 表示只消费新消息），MKSTREAM 自动创建 stream
XGROUP CREATE stream:order group:1 0 MKSTREAM

# 消费者读取新消息，> 表示从未投递的消息开始
XREADGROUP GROUP group:1 consumer:1 COUNT 10 BLOCK 5000 STREAMS stream:order >

# 处理成功后 ACK
XACK stream:order group:1 1735689600000-0

# 查看 pending 消息
XPENDING stream:order group:1 - + 10

# 查看 pending 摘要（每个消费者的未确认数量）
XPENDING stream:order group:1

# 认领超过 60 秒未 ACK 的消息给 consumer:2（6.2+）
XAUTOCLAIM stream:order group:1 consumer:2 60000 0-0 COUNT 10

# 查看流与消费组信息
XINFO STREAM stream:order
XINFO GROUPS stream:order
XINFO CONSUMERS stream:order group:1

# 限制 stream 长度，MAXLEN ~ 近似裁剪，性能更好
XADD stream:order MAXLEN ~ 100000 * order_id 1002 event paid
XTRIM stream:order MAXLEN ~ 100000
```

**消费流程：**

```text
生产者 → XADD → stream
                    │
        ┌───────────┴───────────┐
   consumer:1               consumer:2
   XREADGROUP >             XREADGROUP >
        │                        │
   处理成功 → XACK          处理失败/崩溃 → 留在 PEL
        │                        │
   消息移出 PEL          超时后被 XAUTOCLAIM 认领重试
```

- `>` 只返回「从未投递过」的消息；要读取自己的 pending，用具体 ID 或 `0`。
- 消费者崩溃后，消息留在 PEL，其他消费者可用 `XAUTOCLAIM` 认领。
- `XPENDING` 的 delivery count 可以判断重试次数，超过阈值转入死信/人工处理。
- 消费必须幂等：至少一次投递意味着同一条消息可能被处理多次。

**与 List、Kafka 的对比：**

| 维度 | List（BLPOP） | Stream | Kafka |
| --- | --- | --- | --- |
| 消费组 | 无 | 有 | 有 |
| ACK/重试 | 无，弹出即丢 | 有 PEL + 认领 | 有 offset + rebalance |
| 多消费者分摊 | 竞争弹出，无分组 | 组内分摊 | 分区内分摊 |
| 持久化 | Redis 持久化 | Redis 持久化 | 磁盘日志，长期保留 |
| 分区/顺序 | 单 key 顺序 | 单 stream 顺序 | 分区级顺序 |
| 容量 | 内存 | 内存，需 XTRIM | 磁盘，按 retention |
| 适用 | 简单队列 | 轻量任务队列 | 高吞吐、可靠消息 |

**生产要点：**

- **裁剪**：Stream 不会自动删除，必须 `XTRIM`/`MAXLEN` 或按时间 `MINID` 清理，否则内存无限增长。
- **裁剪与 PEL**：裁剪可能删除尚未 ACK 的消息，导致 pending 指向不存在的 ID；要保留足够长度或先确认再裁剪。
- **消费者命名**：consumer 名要稳定且唯一（实例 ID），崩溃重启后能识别自己的 pending。
- **监控**：`XINFO GROUPS` 的 `lag`（未投递数量）、`XPENDING` 的数量与最老消息时间。
- **阻塞**：`BLOCK` 会占用连接，消费者要用独立连接池，避免阻塞普通命令。
- **集群**：Stream 是单 key，Cluster 下落在一个槽；吞吐受单节点限制。

**面试怎么答：**

先讲 Stream 的四个概念：消息 ID、消费组、PEL、ACK。再给命令链路：`XADD` → `XGROUP CREATE` → `XREADGROUP >` → 处理 → `XACK`；失败用 `XPENDING` + `XAUTOCLAIM` 重试。最后对比 List（无 ACK/组）与 Kafka（磁盘、分区），说明 Stream 适合轻量、已有 Redis 的场景，必须做裁剪与幂等。

**易错点：**

- `XREADGROUP` 的 `>` 只读新消息，读 pending 要用具体 ID/`0`。
- 忘记 `XACK` 会让消息永远留在 PEL，越积越多。
- Stream 不自动过期，不 `XTRIM` 会撑爆内存。
- 裁剪可能删掉未 ACK 的消息，pending 变成「悬空 ID」。
- 消费者名不固定会导致重启后无法识别自己的 pending。
- Stream 是至少一次语义，消费必须幂等，不能假设只投递一次。
- Cluster 下 Stream 单 key 落单槽，不能靠加节点提升单个 stream 的吞吐。

## 10. 布隆过滤器的原理与使用

**布隆过滤器用「一个位数组 + k 个哈希函数」表示一个集合：添加元素时把 k 个位置置 1；查询时若有一位为 0，则元素一定不存在；若全为 1，则元素可能存在（可能是其他元素碰巧置位）。它只有假阳性、没有假阴性，空间效率极高，但标准实现不支持删除，容量也需要提前预估。**

**原理：**

```text
m 位的位数组，初始全 0
k = 3 个哈希函数 h1/h2/h3

添加 "user:1001"：
h1 → 位置 2 置 1
h2 → 位置 7 置 1
h3 → 位置 11 置 1

查询 "user:1002"：
h1 → 2（1）、h2 → 5（0）→ 一定不存在
查询 "user:1003"：
h1 → 2（1）、h2 → 7（1）、h3 → 11（1）→ 可能存在（可能是别人的位）
```

**参数估算：**

| 参数 | 公式/关系 | 说明 |
| --- | --- | --- |
| 位数组大小 m | `m = -n * ln(p) / (ln2)^2` | n 为预计元素数，p 为误判率 |
| 哈希函数个数 k | `k = (m/n) * ln2` | 使误判率最低 |
| 误判率 p | 约 `(1 - e^(-kn/m))^k` | 元素越多，误判率越高 |

- 例：n=100 万、p=1%，m ≈ 958 万位 ≈ 1.2MB，k ≈ 7。
- 位数组越长、哈希函数越多，误判率越低，但计算与内存成本上升。
- 实际元素数超过预估容量后，误判率会快速上升，必须提前规划或重建。

**RedisBloom 模块用法：**

```bash
# 创建：误判率 1%，预计 100 万个元素
BF.RESERVE product:bloom 0.01 1000000

# 单个添加/查询
BF.ADD product:bloom 1001
BF.EXISTS product:bloom 1001
# (integer) 1
BF.EXISTS product:bloom 999999
# (integer) 0，一定不存在

# 批量添加/查询
BF.MADD product:bloom 1002 1003 1004
BF.MEXISTS product:bloom 1001 999999
# 1) (integer) 1
# 2) (integer) 0

# 查看容量、已用元素、误判率
BF.INFO product:bloom
```

**用原生 Bitmap 手写（不依赖模块）：**

```bash
# 3 个哈希位置，分别置位；实际项目用 Pipeline 批量执行
SETBIT bloom:product 12345 1
SETBIT bloom:product 67890 1
SETBIT bloom:product 24680 1

# 查询：三个位置都为 1 才「可能存在」
GETBIT bloom:product 12345
GETBIT bloom:product 67890
GETBIT bloom:product 24680
```

- Bitmap 的 offset 最大 2^32-1，即单个 key 最多约 512MB（42 亿位）。
- 手写方案要自己实现多个哈希函数（如 MurmurHash3 加不同种子），并保证 Redis 与业务端算法一致。
- 多个位置用 Pipeline 批量读写，减少 RTT；但不要一次查太多 key，避免阻塞。

**在缓存穿透中的位置：**

```text
请求 → 参数校验 → 布隆过滤器（一定不存在则直接返回）
     → 查缓存 → 命中返回
     → 未命中 → 查 DB → 存在则回填缓存 + 布隆
                      → 不存在则缓存空值（短 TTL）
```

- 布隆过滤器挡在缓存之前，拦截绝大多数随机/非法 ID。
- 布隆通过后仍可能不存在（假阳性），所以还要配合空值缓存。
- 新增数据时要同步 `BF.ADD`，否则新数据会被误判为「一定不存在」。
- 删除数据不能 `BF.DEL`（标准 Bloom 不支持），需要重建或改用 Cuckoo Filter。

**Cuckoo Filter（支持删除）：**

```bash
# RedisBloom 的 Cuckoo Filter
CF.RESERVE product:cf 1000000
CF.ADD product:cf 1001
CF.EXISTS product:cf 1001
CF.DEL product:cf 1001
```

- Cuckoo Filter 支持删除，空间效率略低于 Bloom，误判率也可控。
- 仍不适合「高频删改 + 超大集合」的场景，扩容/重建仍有成本。
- 选择时看是否需要删除：只增不改用 Bloom，需要删除用 Cuckoo/Counting Bloom。

**面试怎么答：**

先讲「位数组 + k 个哈希 + 只有假阳性」的原理，再给参数公式（m、k、p）与例子。然后讲 RedisBloom 命令、与空值缓存的组合、新增同步与删除限制。最后说适用边界：海量存在性判断、能接受误判、不需要删除；否则用 Cuckoo 或直接查库。

**易错点：**

- 布隆过滤器不会把「存在」误判为「不存在」，只会把「不存在」误判为「存在」。
- 标准 Bloom 不支持删除，删除数据后必须重建，否则会留下永久假阳性。
- 容量是按预计元素数设计的，实际超出后误判率会急剧上升。
- 新增数据忘记 `BF.ADD` 会被误判为不存在，导致正常数据被拦截。
- 手写 Bitmap 要注意哈希函数与 offset 范围，offset 超限会报错。
- RedisBloom 是模块，不是原生 Redis 命令；云服务/托管实例未必支持。
- 布隆不能替代空值缓存，假阳性仍会穿透到数据库。

## 11. 热点数据预热与缓存容量规划

**预热是「在流量到来前把热点数据放进缓存」，容量规划是「用可解释的模型估算需要多少内存与多少余量」。两者都服务于命中率与稳定性：预热避免冷启动瞬间回源，容量规划避免频繁淘汰与 OOM。核心不是拍一个数字，而是按「key 数量 × 单 key 开销 × 冗余系数」估算，并留出 fork、复制、碎片的余量。**

**预热的时机与来源：**

| 时机 | 做法 | 注意 |
| --- | --- | --- |
| 发布/重启后 | 启动时批量加载热点 key | 限速，避免启动即打满 DB |
| 大促前 | 按历史访问日志提前加载 Top N | 提前几小时，分批验证 |
| 缓存扩容后 | 新节点预热再切流量 | 先小流量灰度 |
| 热点发现后 | 把突增 key 主动写入并延长 TTL | 配合热点探测 |
| 定时任务 | 每天低峰刷新次日热点 | 避免与业务高峰重叠 |

**预热的实现要点：**

- 数据来源可以是数据库、离线数仓、访问日志、推荐系统；优先用离线结果，避免预热时压 DB。
- 用 Pipeline 批量写入，单批 500~1000 条，控制 RTT 与服务端输出缓冲。
- 预热 QPS 要限速，例如不超过 DB 容量的 20%，并监控 DB 负载。
- TTL 加随机抖动，避免预热数据在同一秒集中过期。
- 预热完成后校验命中率与抽样数据，确认没有大面积写错/漏写。
- 不要把「全量数据」都塞进缓存，只预热可证明的热点。

```bash
# 批量预热（伪代码）：从离线文件读取 key/value，Pipeline 写入
# pipe = redis.pipeline()
# for i, (k, v) in enumerate(hot_items):
#     pipe.set(k, v, ex=3600 + random(0, 600))
#     if i % 500 == 0:
#         pipe.execute()
#         sleep(50ms)   # 限速
# pipe.execute()
```

**单 key 内存开销的构成：**

| 组成 | 估算 | 说明 |
| --- | --- | --- |
| key 的 SDS | 头 3~9B + 字符串长度 + 1B | 长 key 本身也占内存 |
| value 的 SDS/对象 | 头 + 内容 + `redisObject` 16B | 不同类型编码不同 |
| 主字典 entry | `dictEntry` 约 24B + 指针 | 每个 key 都有 |
| 过期字典 entry | 约 24B + 8B 时间戳 | 设置了 TTL 才有 |
| jemalloc 对齐 | 通常 8/16B 对齐，少量浪费 | 小对象碎片更明显 |
| 编码结构 | listpack/intset/skiplist 额外头 | 集合类型有额外开销 |

**容量估算示例：**

```text
场景：100 万个 String key，key 平均 40B，value 平均 100B，全部带 TTL

粗算：
  key SDS + redisObject        ≈ 40 + 16 + 8  = 64B
  value SDS + redisObject      ≈ 100 + 16 + 8 = 124B
  dictEntry（主字典）          ≈ 24B
  expires entry + 时间戳        ≈ 32B
  jemalloc 对齐/碎片            ≈ 20%
合计单 key ≈ (64 + 124 + 24 + 32) × 1.2 ≈ 293B
100 万 key ≈ 293MB

再留 fork COW、复制缓冲、碎片余量 30%：
建议 maxmemory ≈ 293MB / 0.75 ≈ 390MB
```

- 这是数量级估算，真实值用 `MEMORY USAGE key SAMPLES 0` 抽样后外推。
- 集合类型不能只按元素平均大小算，还要加 listpack/skiplist/dict 的结构开销。
- 副本、Cluster 槽迁移、AOF 缓冲都会额外占内存，不能只算主库数据。

```bash
# 抽样单 key 内存
redis-cli MEMORY USAGE user:profile:1001 SAMPLES 0

# 总量与碎片
redis-cli INFO memory
# used_memory_human / used_memory_rss_human / mem_fragmentation_ratio

# key 数量
redis-cli DBSIZE
redis-cli INFO keyspace
# db0:keys=1000000,expires=1000000,avg_ttl=...

# 命中率
redis-cli INFO stats | grep -E "keyspace_hits|keyspace_misses"
```

**maxmemory 与物理内存：**

- `maxmemory` 通常设为物理内存的 60%~75%，不能设成 100%。
- 预留空间给：fork 的 COW（写入密集时可能接近翻倍）、复制缓冲区、客户端输出缓冲、内存碎片、AOF/RDB 缓冲。
- `used_memory_rss` 高于 `used_memory` 是正常的（分配器预留、碎片）；`mem_fragmentation_ratio > 1.5` 要考虑碎片整理或重启。
- `mem_fragmentation_ratio < 1` 往往意味着发生了 swap，性能会严重下降。

**命中率与容量：**

- 命中率 `= keyspace_hits / (keyspace_hits + keyspace_misses)`。
- 缓存容量不是「等于全部数据」，而是「覆盖热点工作集」；常见目标是 90%~95% 命中率。
- 容量不足时 `evicted_keys` 持续增长，命中率下降，DB 压力上升。
- 容量过大则成本高、fork/恢复变慢；按业务增长预留 20%~30% 缓冲，定期复盘。

**面试怎么答：**

预热按「时机 → 来源 → 限速 → 抖动 TTL → 验证」回答；容量按「单 key 组成 → 抽样 `MEMORY USAGE` → 总量 → 冗余系数 → maxmemory 留 25%~30%」回答。最后补命中率目标与 `evicted_keys` 监控，说明容量规划是持续校准，不是一次性计算。

**易错点：**

- 只按 value 大小估算，漏掉 key、dictEntry、过期字典、jemalloc 对齐，实际内存可能高 50% 以上。
- `maxmemory` 设得接近物理内存，fork COW 时容易 OOM 或被系统 kill。
- 预热不限速会把数据库打满，预热本身变成故障。
- 预热数据 TTL 不抖动，会在同一时间集中过期，引发雪崩。
- 命中率高不代表缓存健康，可能是「缓存了大量很少访问的数据」。
- 扩容后新节点没有预热就切流量，会因冷启动把 DB 打高。
- `used_memory` 不含 fork COW 与复制缓冲，容量规划要看 RSS 与峰值。

## 12. 缓存监控与常见线上问题

**Redis 线上问题大多不是「Redis 挂了」，而是「延迟抖动、内存增长、命中率下降、连接耗尽、主从延迟」。排查要按「先看整体指标 → 再定位慢命令/大 key/热 key → 最后看系统层（CPU、内存、磁盘、网络、swap）」的顺序，避免一上来就 `MONITOR` 或 `KEYS` 把问题放大。**

**必看指标：**

| 分类 | 指标 | 异常含义 |
| --- | --- | --- |
| 内存 | `used_memory`、`used_memory_rss`、`mem_fragmentation_ratio` | 增长过快、碎片高、可能 swap |
| 淘汰 | `evicted_keys`、`maxmemory_policy` | 容量不足或策略不当 |
| 命中 | `keyspace_hits`、`keyspace_misses` | 命中率下降，回源压力上升 |
| 吞吐 | `instantaneous_ops_per_sec`、`total_commands_processed` | 突增/突降都可能是异常 |
| 延迟 | `latency`、`SLOWLOG`、`latency_percentiles_usec` | 慢命令、fork、swap、网络 |
| 连接 | `connected_clients`、`blocked_clients`、`rejected_connections` | 连接泄漏、阻塞命令、上限 |
| 复制 | `master_link_status`、`master_repl_offset`、`slave_repl_offset` | 主从断链、延迟扩大 |
| 持久化 | `rdb_last_bgsave_status`、`aof_last_write_status`、`aof_delayed_fsync` | 磁盘满、fsync 阻塞 |
| 集群 | `cluster_state`、`cluster_slots_assigned` | 槽丢失、集群不可用 |
| fork | `latest_fork_usec`、`rdb_last_cow_size` | fork 阻塞、COW 内存膨胀 |

```bash
# 整体状态（按 section 查看，避免一次输出过多）
redis-cli INFO memory
redis-cli INFO stats
redis-cli INFO clients
redis-cli INFO replication
redis-cli INFO persistence
redis-cli INFO keyspace

# 慢查询：默认超过 10ms 记录，最多 128 条
redis-cli CONFIG GET slowlog-log-slower-than
redis-cli CONFIG GET slowlog-max-len
redis-cli SLOWLOG GET 20
redis-cli SLOWLOG LEN
redis-cli SLOWLOG RESET

# 延迟监控：默认 latency-monitor-threshold 为 0（关闭），设为 100 表示记录 >100ms 的事件
redis-cli CONFIG SET latency-monitor-threshold 100
redis-cli LATENCY HISTORY command
redis-cli LATENCY LATEST
redis-cli LATENCY DOCTOR

# 内存诊断
redis-cli MEMORY STATS
redis-cli MEMORY DOCTOR
redis-cli MEMORY USAGE some:key SAMPLES 0

# 连接与客户端
redis-cli CLIENT LIST
redis-cli CLIENT INFO
redis-cli INFO clients | grep -E "connected_clients|blocked_clients"

# 大 key / 热 key（低峰执行）
redis-cli --bigkeys
redis-cli --memkeys
redis-cli --hotkeys

# 实时统计（采样，不要长期开着）
redis-cli --stat
redis-cli --latency
redis-cli --latency-history
```

**常见问题与排查路径：**

| 现象 | 可能原因 | 排查 | 处理 |
| --- | --- | --- | --- |
| CPU 单核打满 | 慢命令、大 key、热 key、Lua 长脚本 | `SLOWLOG`、`COMMANDSTATS`、`--hotkeys` | 拆分 key、改写命令、限流、扩容 |
| 延迟周期性抖动 | fork、AOF fsync、RDB、swap | `latest_fork_usec`、`aof_delayed_fsync`、`vmstat` | 调大内存/关闭 swap、错峰持久化、拆分实例 |
| 内存持续增长 | 无 TTL、大 key、碎片、复制缓冲 | `INFO memory`、`DBSIZE`、`--bigkeys` | 补 TTL、拆分、清理、碎片整理 |
| 命中率下降 | 容量不足、TTL 太短、key 设计错误 | `keyspace_hits/misses`、`evicted_keys` | 扩容、调 TTL、修 key 规范 |
| 连接数暴涨 | 连接泄漏、客户端未复用、阻塞命令 | `CLIENT LIST` 按 IP 统计 | 修连接池、限制客户端、排查 `BLOCK` |
| 主从延迟 | 大 key 写入、网络、从库负载高 | `INFO replication` 的 offset 差 | 拆分大 key、扩容网络、加从库 |
| 写入失败 | 内存满且 `noeviction`、磁盘满、只读从库 | `maxmemory`、`rdb_last_bgsave_status`、`role` | 扩容/淘汰、清磁盘、切主 |
| 集群不可用 | 槽未覆盖、多数派丢失、节点超时 | `CLUSTER INFO`、`CLUSTER NODES` | `--cluster check`、`--cluster fix`、恢复节点 |
| 连接超时但 Redis 正常 | 网络、TLS、客户端 DNS、连接池满 | `--latency`、抓包、客户端指标 | 修网络、调连接池、扩容 |

**几个高频线上坑：**

1. **swap 导致延迟飙升**：`mem_fragmentation_ratio < 1` 或 `used_memory_rss` 远高于预期，检查 `free`/`vmstat`，关闭 swap 或扩容。
2. **透明大页（THP）**：fork 与 COW 变慢，建议 `echo never > /sys/kernel/mm/transparent_hugepage/enabled`。
3. **`KEYS *` / `MONITOR`**：生产禁止；`MONITOR` 会放大流量并泄露所有命令，排查用 `SLOWLOG` 与采样。
4. **大 key 删除**：用 `UNLINK`，不要 `DEL`；`FLUSHALL` 用 `ASYNC`。
5. **AOF fsync 阻塞**：`aof_delayed_fsync` 增长说明磁盘慢，考虑 `everysec` + 更快的盘，或 `no-appendfsync-on-rewrite`。
6. **客户端输出缓冲**：大 value/Pipeline 过大触发 `client-output-buffer-limit` 断连，分批发送。
7. **连接池打满**：Redis 本身连接数正常，但客户端池太小/泄漏，看客户端指标而不是只看 Redis。

**监控与告警建议：**

- 采集 `INFO all` 到 Prometheus（redis_exporter），配置内存、命中率、延迟、连接、复制、持久化、集群状态告警。
- 慢查询按「命令 + 调用方」聚合，定位是哪个业务在拖慢主线程。
- 大 key/热 key 做成定时巡检（低峰），而不是等故障时临时扫描。
- 告警要有分级：内存 80%/90%、延迟 P99、主从断链、`cluster_state:fail` 为高优先级。
- 每次故障复盘要落到「指标 → 根因 → 改进」，否则同类问题会重复发生。

**面试怎么答：**

先给「四层排查法」：整体指标（内存/命中/连接/复制）→ 慢命令与大 key/热 key → 系统层（CPU/内存/磁盘/网络/swap）→ 客户端与网络。再列高频问题：CPU 高、延迟抖动、内存增长、命中率下降、主从延迟、写入失败、集群不可用。最后补禁止项（`KEYS`、`MONITOR`）与告警建设。

**易错点：**

- 只看平均延迟会漏掉 P99 抖动，必须看分位值与 `LATENCY`。
- `mem_fragmentation_ratio < 1` 往往不是「碎片少」，而是发生了 swap。
- `evicted_keys` 增长说明容量不足，不是「淘汰策略工作正常」。
- 命中率高也可能是「缓存了大量冷数据」，要结合 `DBSIZE` 与业务访问分布看。
- `MONITOR` 会显著增加开销并泄露敏感命令，生产禁止长期开启。
- `KEYS` 是 O(N) 阻塞命令，扫描用 `SCAN`/`--scan`。
- 连接超时不一定是 Redis 问题，可能是客户端连接池、DNS、TLS 或网络。
- 主从延迟要看 offset 差与时间，不只看 `master_link_status:up`。
