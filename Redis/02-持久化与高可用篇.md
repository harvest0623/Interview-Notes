## 1. RDB 的原理与触发方式

**RDB 是 Redis 的「某一时刻全量数据快照」：父进程 `fork` 出子进程，子进程把当前内存中的数据序列化成紧凑的二进制文件，父进程继续处理请求，靠 Copy-On-Write 保证子进程看到一致的快照。RDB 文件小、恢复快，适合备份与全量同步，但两次快照之间的数据会丢失，且 fork 与写时复制会带来延迟和内存峰值。**

**核心流程（BGSAVE）：**

1. 父进程检查是否已有子进程在持久化，避免重复 fork。
2. 父进程 `fork()` 出子进程；fork 会复制页表，阻塞时间与内存页表大小相关，不是复制全部数据。
3. 子进程遍历内存，把键值按 RDB 格式写入临时文件。
4. 父进程继续处理客户端请求；期间被修改的内存页由内核复制（Copy-On-Write），父进程与子进程各持一份。
5. 子进程写完临时文件后 `rename` 为 `dump.rdb`，替换旧文件。
6. 父进程通过 `waitpid` 感知完成，更新 `rdb_last_save_time`、`rdb_last_bgsave_status` 等指标。

```text
父进程内存页 ──fork──→ 子进程（共享只读页）
     │                        │
     │ 客户端写入某页          │ 遍历并写 RDB
     ▼                        ▼
  内核复制该页            读到的是 fork 瞬间的旧页
  （COW，内存可能上涨）     写临时文件 → rename
```

**触发方式：**

| 触发方式 | 命令/条件 | 是否阻塞主线程 | 说明 |
| --- | --- | --- | --- |
| 手动同步 | `SAVE` | 是，全程阻塞 | 生产禁用，仅调试/关机前使用 |
| 手动异步 | `BGSAVE` | 仅 fork 瞬间阻塞 | 后台子进程生成快照 |
| 自动 | `save <seconds> <changes>` | 仅 fork 瞬间阻塞 | 满足「N 秒内至少 M 次修改」触发 |
| 主从全量同步 | 复制时主库生成 RDB | 仅 fork 瞬间阻塞 | 可用 diskless 直接发往从库 |
| 正常关闭 | `SHUTDOWN` | 是，退出前保存 | `SHUTDOWN NOSAVE` 可跳过 |
| 调试 | `DEBUG RELOAD` | 是 | 需要开启 debug 命令，生产禁用 |

```conf
# Redis 7.x 默认的自动快照条件
save 3600 1 300 100 60 10000
# 3600 秒内至少 1 次修改，或 300 秒内至少 100 次，或 60 秒内至少 10000 次

dbfilename dump.rdb
dir ./                         # RDB/AOF 的落盘目录，需有写权限与足够空间
rdbcompression yes             # 使用 LZF 压缩字符串，省空间但耗 CPU
rdbchecksum yes                # 文件末尾写 CRC64 校验，加载时校验
stop-writes-on-bgsave-error yes # 最近一次 bgsave 失败时拒绝写命令
rdb-del-sync-files no          # 无盘复制完成后是否删除临时 RDB
```

```bash
# 手动触发并观察状态
redis-cli BGSAVE
# Background saving started

redis-cli INFO persistence
# rdb_bgsave_in_progress:0
# rdb_last_save_time:1735689600
# rdb_last_bgsave_status:ok
# rdb_last_cow_size:1048576

redis-cli LASTSAVE
# (integer) 1735689600，上次成功保存的 Unix 时间戳

# 校验 RDB 文件是否完整
redis-check-rdb /var/lib/redis/dump.rdb

# 关闭自动快照（纯缓存且不依赖 RDB 时）
redis-cli CONFIG SET save ""
```

**RDB 文件格式（了解即可）：**

- 开头是 `REDIS` 魔数与版本号，便于快速识别。
- 之后是辅助字段（`redis-ver`、`redis-bits`、`ctime`、`used-mem` 等）。
- 按 db 分组，每个 db 有 SELECTDB 标记，随后是 key-value 对，value 按类型编码。
- 末尾是 `EOF` 与 CRC64 校验和。
- 因此 RDB 是紧凑的二进制格式，不可读、不可增量修改，只能整体替换。

**RDB 的优缺点：**

| 优点 | 缺点 |
| --- | --- |
| 文件紧凑，适合备份、冷备、跨机房传输 | 两次快照之间的数据会丢，无法做到秒级 RPO |
| 恢复速度快，直接加载二进制，不用重放命令 | fork 会阻塞主线程，内存大时可达数十毫秒 |
| 对主线程影响小，子进程负责写盘 | COW 在写入密集时可能让内存翻倍 |
| 适合主从全量同步的基线 | 快照期间磁盘 IO 高，可能影响其他进程 |

```bash
# 观察 fork 与 COW 成本
redis-cli INFO stats | grep -E "fork|latest_fork_usec"
redis-cli INFO memory | grep -E "used_memory|used_memory_rss|mem_fragmentation_ratio"
redis-cli INFO persistence | grep rdb_last_cow_size

# 系统层面确认 overcommit，避免 fork 失败
# Linux 建议 vm.overcommit_memory = 1
cat /proc/sys/vm/overcommit_memory
```

**面试怎么答：**

先定义「全量快照 + fork + COW」，再讲 BGSAVE 的六步流程与「fork 只复制页表、写时才复制页」。触发方式分手动、自动、主从、关机四类。最后给取舍：RDB 适合备份与快速恢复，不适合低 RPO；fork 与 COW 是主要风险，要监控 `latest_fork_usec` 与 `rdb_last_cow_size`。

**易错点：**

- `fork` 不是复制全部内存，而是复制页表；阻塞时间与页表大小、内存碎片有关。
- COW 不是「写时复制整个实例」，只复制被写的页；但写入量大时最坏可接近 2 倍内存。
- `SAVE` 会阻塞整个 Redis，生产不要用；`BGSAVE` 只在 fork 瞬间阻塞。
- `stop-writes-on-bgsave-error yes` 会在快照失败时拒绝写，可能把「磁盘满」放大成「服务不可写」。
- RDB 文件不是「日志」，不能增量恢复；两次快照之间的写入无法从 RDB 找回。
- 关闭自动快照不等于关闭 RDB：主从全量同步、`SHUTDOWN` 仍可能生成 RDB。

## 2. AOF 的三种刷盘策略与重写

**AOF 记录的是「写命令日志」：每条改变数据的命令按 RESP 追加到文件，重启时从头重放恢复。`appendfsync` 决定什么时候真正 `fsync` 到磁盘：`always` 每条都刷、`everysec` 每秒刷、`no` 交给操作系统。AOF 文件会越来越大，需要重写（rewrite）生成「能恢复当前数据的最小命令集」，Redis 7.0 起使用多 Part AOF，把基线文件与增量文件分开管理。**

**写入链路：**

1. 命令执行后，把写命令追加到 `server.aof_buf`（内存缓冲）。
2. 事件循环的 `beforeSleep` 把 `aof_buf` 写入 AOF 文件（`write` 系统调用）。
3. 根据 `appendfsync` 决定是否调用 `fsync` 刷到磁盘。
4. `everysec` 模式下由后台 bio 线程每秒执行一次 `fsync`，避免主线程被磁盘阻塞。
5. 如果上一次 `fsync` 迟迟未完成且 AOF 缓冲持续增长，Redis 会记录 `aof_delayed_fsync`，并可能短暂阻塞写入；这是 `everysec` 在慢盘上的主要风险。

```conf
appendonly no                 # 默认 no；开启持久化需改为 yes
appendfilename "appendonly.aof"
appenddirname "appendonlydir" # 7.0 起多 Part AOF 的目录名

appendfsync everysec          # always / everysec / no，默认 everysec
no-appendfsync-on-rewrite no  # 重写期间是否暂停 fsync，默认 no
auto-aof-rewrite-percentage 100
auto-aof-rewrite-min-size 64mb
aof-load-truncated yes        # 文件尾部截断时尽量加载，默认 yes
aof-use-rdb-preamble yes      # 重写时用 RDB 作为基线，默认 yes
aof-timestamp-enabled no      # 是否在 AOF 中记录时间戳注释
```

| 策略 | 行为 | 数据丢失窗口 | 性能 | 适用场景 |
| --- | --- | --- | --- | --- |
| `always` | 每条写命令都 `fsync` 后才回复 | 理论最小，仍受磁盘缓存/故障影响 | 最差，受限于磁盘 IOPS | 极小数据量、强持久化要求 |
| `everysec` | 每秒后台 `fsync` 一次 | 通常最多约 1 秒 | 较好，默认推荐 | 大多数生产场景 |
| `no` | 只 `write`，由 OS 决定何时刷 | 可能数十秒，宕机丢失多 | 最好 | 可接受丢数据、追求吞吐 |

**AOF 重写的机制：**

- 触发：手动 `BGREWRITEAOF`；或当前 AOF 大小同时超过 `auto-aof-rewrite-min-size`（64MB）且比上次重写后增长超过 `auto-aof-rewrite-percentage`（100%）。
- 父进程 `fork` 子进程，子进程根据当前内存生成「最小命令集」写入新 AOF。
- 重写期间父进程继续处理写命令，同时把这些命令追加到「AOF 重写缓冲区」。
- 子进程写完后，父进程把重写缓冲区的内容追加到新文件，保证「基线 + 增量」完整。
- 最后原子替换旧文件，更新 manifest（7.0 多 Part）。

```text
时间线：
父进程：处理写命令 ──────────────────────────────→ 追加重写缓冲 → 替换文件
              │ fork
子进程：         └─ 扫描内存，生成最小命令集 ──→ 写完新基线
```

**Redis 7.0 的多 Part AOF：**

| 文件 | 内容 | 作用 |
| --- | --- | --- |
| `appendonly.aof.manifest` | 清单，记录 base 与 incr 文件顺序 | 加载时按清单顺序读取 |
| `appendonly.aof.1.base.rdb` | 基线文件，默认是 RDB 格式 | 快速加载当前全量数据 |
| `appendonly.aof.1.incr.aof` | 增量命令文件 | 记录基线之后的写命令 |
| 多个 incr 文件 | 每次重写产生新的增量段 | 避免单文件无限增长 |

```bash
# 开启 AOF 并观察状态
redis-cli CONFIG SET appendonly yes
redis-cli INFO persistence
# aof_enabled:1
# aof_rewrite_in_progress:0
# aof_last_bgrewrite_status:ok
# aof_last_write_status:ok
# aof_delayed_fsync:0

# 手动重写
redis-cli BGREWRITEAOF
# Background append only file rewriting started

# 查看 AOF 目录结构（7.0+）
ls -lh /var/lib/redis/appendonlydir/
# appendonly.aof.manifest
# appendonly.aof.1.base.rdb
# appendonly.aof.1.incr.aof

# 修复被截断的 AOF（先停服务并备份）
redis-check-aof --fix appendonlydir/appendonly.aof.1.incr.aof
```

**AOF 的优缺点：**

| 优点 | 缺点 |
| --- | --- |
| 数据丢失窗口小，`everysec` 通常 ≤1 秒 | 文件通常比 RDB 大，加载慢 |
| 追加写，顺序 IO，对磁盘友好 | 重写需要 fork 与额外磁盘空间 |
| 命令可读，便于排查（RDB 基线除外） | `always` 严重受限于磁盘延迟 |
| 适合对 RPO 敏感的业务 | 重写期间内存与 IO 压力上升 |

**面试怎么答：**

按「写命令追加 → 缓冲 → write → fsync」讲链路，重点区分三种 `appendfsync` 的丢失窗口与性能。再讲重写：fork 子进程生成最小命令集、父进程用重写缓冲补增量、最后原子替换。最后补 7.0 多 Part AOF 与 `aof-use-rdb-preamble`，说明「AOF 不是纯命令日志，基线可以是 RDB」。

**易错点：**

- `appendonly` 默认是 `no`，不是「Redis 默认开启 AOF」。
- `everysec` 不是「绝对只丢 1 秒」：磁盘阻塞、fsync 延迟、操作系统缓存都会影响。
- `always` 也不是绝对零丢失：磁盘缓存、文件系统、硬件故障仍可能丢，且性能代价很大。
- AOF 重写不是「压缩原文件」，而是根据当前内存重新生成最小命令集；重写期间的新写入靠缓冲区补齐。
- `no-appendfsync-on-rewrite yes` 会在重写期间放弃 fsync，降低阻塞但扩大丢失窗口，默认是 `no`。
- 多 Part AOF 是 7.0 的特性，6.x 及以前是单个 AOF 文件；回答版本差异时要说明。

## 3. RDB 与 AOF 的混合持久化

**混合持久化是「AOF 重写时，先用 RDB 格式写当前全量数据作为基线，再把重写期间的增量命令以 AOF 格式追加在后面」。它结合了 RDB 的「加载快、体积小」与 AOF 的「增量、丢失窗口小」，由 `aof-use-rdb-preamble yes` 控制（5.0 起支持，默认开启）。Redis 7.0 的多 Part AOF 把这种思路进一步拆成 base 文件与 incr 文件。**

**为什么需要混合：**

- 纯 RDB：恢复快，但两次快照之间丢数据。
- 纯 AOF：丢失窗口小，但文件大、重放命令慢，重启可能几十秒到几分钟。
- 混合：基线用 RDB 快速加载，尾部用 AOF 补最近增量，兼顾恢复速度与数据完整性。

**文件结构（单文件时代，5.0~6.x）：**

```text
appendonly.aof
┌──────────────────────────────┐
│ RDB 格式的全量基线（REDIS 魔数） │
├──────────────────────────────┤
│ AOF 格式的增量命令（RESP）       │
└──────────────────────────────┘
```

**Redis 7.0 多 Part 结构：**

```text
appendonlydir/
├── appendonly.aof.manifest          # 清单：base + 若干 incr
├── appendonly.aof.1.base.rdb        # 全量基线（RDB 格式）
├── appendonly.aof.1.incr.aof        # 增量命令
└── appendonly.aof.2.incr.aof        # 下一次重写后的新增量段
```

**加载顺序：**

1. 读取 manifest，确定 base 与 incr 文件顺序。
2. 先加载 base（RDB 格式），快速恢复大部分数据。
3. 再按顺序重放 incr 文件中的命令，补齐基线之后的修改。
4. 若尾部截断且 `aof-load-truncated yes`，加载到截断点并记录警告；否则启动失败。

```conf
# 开启混合持久化（默认即为 yes）
appendonly yes
aof-use-rdb-preamble yes
aof-load-truncated yes
```

```bash
# 触发一次重写，让基线变成 RDB 格式
redis-cli BGREWRITEAOF
redis-cli INFO persistence | grep -E "aof_enabled|aof_last_bgrewrite_status"

# 单文件时代：查看文件头是否为 REDIS
head -c 5 appendonly.aof
# REDIS

# 7.0 多 Part：查看 manifest
cat appendonlydir/appendonly.aof.manifest
# file appendonly.aof.1.base.rdb seq 1 type b
# file appendonly.aof.1.incr.aof seq 1 type i

# 查看基线文件类型与大小
ls -lh appendonlydir/
```

| 方案 | 恢复速度 | 数据丢失窗口 | 文件体积 | 可读性 |
| --- | --- | --- | --- | --- |
| 纯 RDB | 快 | 大（取决于 save 周期） | 小 | 二进制，不可读 |
| 纯 AOF | 慢（重放命令） | 小（everysec 约 1 秒） | 大 | 命令可读 |
| 混合持久化 | 快（RDB 基线 + 少量增量） | 小 | 中等 | 基线不可读，尾部可读 |

**面试怎么答：**

一句话：「AOF 重写时用 RDB 做基线，后面追加增量 AOF。」再讲动机：纯 RDB 丢数据多、纯 AOF 恢复慢；混合让重启先加载 RDB 再重放少量命令。补配置 `aof-use-rdb-preamble yes`（默认）、7.0 多 Part 的 manifest/base/incr 结构，以及「必须开启 AOF 才有混合，纯 RDB 不叫混合」。

**易错点：**

- 混合持久化不是「同时写 RDB 和 AOF 两个文件」，而是 AOF 文件内部用 RDB 作为基线。
- 必须 `appendonly yes` 才涉及混合；只开 RDB 时不存在「混合」。
- 混合 AOF 的基线是 RDB 格式，旧版本 Redis（5.0 之前）无法识别，降级前要重写或关闭。
- `aof-use-rdb-preamble no` 时重写仍生成纯 AOF 基线，恢复会变慢。
- 7.0 多 Part 的 base 与 incr 是一个整体，不能只拷贝其中一个文件做备份。
- 混合持久化不改变 `appendfsync` 的丢失窗口，尾部增量仍按刷盘策略落盘。

## 4. 主从复制的原理与全量/增量同步

**Redis 主从复制是异步的：从库通过 `PSYNC` 带上主库的 `replid` 与偏移量请求同步；主库判断能否只补发缺失的命令（增量），否则执行全量同步——fork 生成 RDB 发给从库，期间的新写入放进复制缓冲区，从库加载完 RDB 后再补放缓冲区。复制是「主库不等待从库」的异步模型，因此故障切换可能丢最后一段数据。**

**建立复制的步骤：**

1. 从库配置 `replicaof <masterip> <masterport>`（5.0 起替代 `slaveof`），或运行时执行 `REPLICAOF`。
2. 从库与主库建立连接，发送 `PING` 确认可达；若配置了 `masterauth`/`masteruser` 则先认证。
3. 从库发送 `REPLCONF listening-port <port>`、`REPLCONF capa eof capa psync2` 等能力声明。
4. 从库发送 `PSYNC <replid> <offset>`：首次同步时 `replid` 为 `?`，`offset` 为 `-1`。
5. 主库若无法增量同步，返回 `+FULLRESYNC <replid> <offset>`，进入全量流程。
6. 主库 `fork` 子进程生成 RDB（可走 diskless），同时把新写入累积到复制缓冲区。
7. 从库清空旧数据、加载 RDB，然后重放复制缓冲区中的命令，进入持续复制状态。
8. 之后主库每执行一条写命令，就异步传播给所有从库；从库更新自己的偏移量。

```text
从库                          主库
 │  PING / AUTH / REPLCONF      │
 │ ───────────────────────────→ │
 │  PSYNC ? -1                  │
 │ ───────────────────────────→ │
 │  +FULLRESYNC <replid> <off>  │
 │ ←─────────────────────────── │
 │  RDB 文件（fork 生成）         │
 │ ←─────────────────────────── │
 │  加载 RDB，期间命令进缓冲区     │
 │  重放缓冲区，进入增量复制       │
 │ ←──── 持续传播写命令 ──────── │
```

**全量同步与增量同步：**

| 维度 | 全量同步 | 增量同步 |
| --- | --- | --- |
| 触发 | 首次复制、replid 不匹配、offset 超出 backlog | replid 匹配且 offset 仍在 backlog 范围内 |
| 主库动作 | fork + 生成 RDB + 缓冲新写入 | 从 backlog 中截取缺失命令 |
| 数据量 | 全量，受内存与网络影响 | 只补缺失部分 |
| 开销 | 大：fork、磁盘/网络、从库清空重载 | 小：只传增量 |
| 命令 | `FULLRESYNC` | `CONTINUE` |

**复制积压缓冲区（backlog）：**

- 主库维护一个环形缓冲区，默认 `repl-backlog-size 1mb`，记录最近传播的写命令与对应偏移量。
- 从库断线重连时，如果它的 `offset` 仍在 backlog 范围内，主库返回 `+CONTINUE`，只补发缺失部分。
- 如果断线时间太长、写入太多，旧数据被环形覆盖，就只能全量同步。
- 高写入量场景要调大 backlog，例如 64MB~256MB，按「断线最长可容忍时间 × 写入速率」估算。

**关键配置：**

```conf
replicaof 10.0.0.1 6379       # 从库指向主库
masterauth yourpassword       # 主库有密码时必填
masteruser default            # 6.0 ACL 用户名，默认 default

replica-read-only yes         # 从库默认只读，防止误写
repl-backlog-size 64mb        # 复制积压缓冲区，默认 1mb，生产建议调大
repl-backlog-ttl 3600         # 从库全部断开后 backlog 保留时间
repl-ping-replica-period 10   # 主库向从库发送 PING 的间隔（秒）
repl-timeout 60               # 复制超时，超过认为连接失效
repl-disable-tcp-nodelay no   # no 表示及时发送小包，延迟低但耗带宽
repl-diskless-sync yes        # 7.x 默认 yes，直接通过 socket 发送 RDB
repl-diskless-sync-delay 5    # 等待更多从库加入后再开始无盘同步
repl-diskless-load disabled   # 从库无盘加载：disabled/on-empty-db/swapdb

min-replicas-to-write 0       # 至少 N 个从库在线才允许写，0 表示不限制
min-replicas-max-lag 10       # 从库延迟超过 N 秒视为不在线
replica-priority 100          # 哨兵选主优先级，越小越优先，0 表示永不提升
```

**复制偏移量与状态：**

```bash
redis-cli INFO replication
# 主库视角：
# role:master
# connected_slaves:2
# slave0:ip=10.0.0.2,port=6379,state=online,offset=123456,lag=0
# master_replid:3f7a...
# master_repl_offset:123456
# 从库视角：
# role:slave
# master_host:10.0.0.1
# master_link_status:up
# slave_repl_offset:123450
# slave_read_only:1

redis-cli ROLE
# 1) "master" / "slave"

# 主动提升从库为主库（故障切换或维护）
redis-cli REPLICAOF NO ONE

# 等待至少 1 个从库确认，最多 100ms（返回确认数量）
redis-cli WAIT 1 100
```

**异步复制与一致性：**

- 主库执行完命令就返回客户端，不等待从库确认；从库的 `slave_repl_offset` 通常落后于主库。
- `WAIT` 可以阻塞等待指定数量的从库确认，但它不是强一致：确认只代表「命令已到达从库缓冲区」，不代表已落盘。
- 主库宕机时，未传播到从库的写入会丢失；哨兵/Cluster 提升从库后，这部分数据就永久丢失。
- 从库默认只读，避免双写；如果需要从库写，必须显式 `replica-read-only no`，并自行处理冲突。
- 从库不会主动过期 key，等主库同步 `DEL`/`UNLINK`；从库读取逻辑过期 key 返回 nil。

**面试怎么答：**

按「PSYNC → 全量/增量 → 缓冲区 → 异步」讲：从库带 replid/offset 请求；主库能增量就 `CONTINUE`，否则 `FULLRESYNC` + fork RDB + 复制缓冲区；最后说异步复制与 `WAIT` 的边界。补 `repl-backlog-size`、`min-replicas-to-write` 与主从延迟监控。

**易错点：**

- 主从复制是异步的，主库写入成功不代表从库已收到，故障切换可能丢数据。
- 全量同步的 RDB 不是「从库自己 bgsave」，而是主库 fork 生成后发送。
- `repl-backlog-size` 太小会导致频繁全量同步；太大则浪费内存。
- 从库默认只读，但 `replica-read-only no` 后写入不会同步回主库，会造成数据分叉。
- `WAIT` 返回的是「确认的从库数」，不是「数据已持久化」，不能当强一致用。
- 级联复制（从库再从库）会增加延迟，故障切换时要考虑层级。

## 5. 哨兵模式的原理与故障转移

**哨兵（Sentinel）是一组独立进程，负责监控主从、判断主库是否下线、在多数哨兵同意后自动选一个从库提升为主库，并通知其他从库与客户端切换。它解决的是「主库挂了谁来接管」，不解决分片与容量扩展。生产至少部署 3 个奇数哨兵，且分布在不同的故障域。**

**哨兵承担的四个职责：**

1. **监控**：每秒向主库、从库、其他哨兵发送 `PING`，每 10 秒发送 `INFO` 获取拓扑，每 2 秒通过 `__sentinel__:hello` 频道交换信息。
2. **通知**：通过发布订阅与事件通知（如 `+switch-master`）告知客户端拓扑变化。
3. **自动故障转移**：主库客观下线后，选举 leader 哨兵，选从库提升，重新配置其他从库。
4. **配置提供者**：客户端启动时向哨兵查询当前主库地址。

**主观下线与客观下线：**

| 概念 | 判定 | 说明 |
| --- | --- | --- |
| SDOWN（主观下线） | 单个哨兵在 `down-after-milliseconds` 内没收到有效 PING 回复 | 只是某个哨兵的判断，可能是网络抖动 |
| ODOWN（客观下线） | 达到 `quorum` 数量的哨兵都认为主库 SDOWN | 哨兵之间通过 `SENTINEL is-master-down-by-addr` 互相询问 |

**quorum 与 majority 不是一回事：**

- `quorum` 只用于「判定主库客观下线」，配置在 `sentinel monitor ... <quorum>`。
- 真正发起故障转移需要选举 leader，必须获得「所有哨兵中的多数（majority）」投票，例如 3 个哨兵需要 2 票。
- 若 `quorum=1`、总共 3 个哨兵：1 个哨兵就能判定 ODOWN，但仍需 2 票才能当选 leader，避免单点误判直接切主。
- 哨兵总数建议为奇数（3、5），且多数部署在不同机房/可用区，避免网络分区导致两边都选不出 leader。

**故障转移的步骤：**

1. 哨兵发现主库 SDOWN，向其他哨兵询问，达到 quorum 后标记 ODOWN。
2. 哨兵之间进行 leader 选举：每个哨兵有当前 epoch，向其他哨兵请求投票，获得多数者成为 leader。
3. leader 从从库中挑选新主：
   - 排除 `replica-priority 0`、断线超时、数据太旧的从库。
   - 按 `replica-priority` 从小到大。
   - 优先级相同看复制偏移量 `slave_repl_offset`，越大越新。
   - 再相同看 `runid` 字典序，最小者优先。
4. 对新主执行 `REPLICAOF NO ONE`，使其成为 master。
5. 向其余从库发送 `REPLICAOF <new-master>`，让它们复制新主。
6. 旧主恢复后，哨兵向其发送 `REPLICAOF <new-master>`，降级为从库。
7. 通过 `+switch-master` 事件通知客户端；客户端刷新主库地址。

```conf
# sentinel.conf
port 26379
sentinel monitor mymaster 10.0.0.1 6379 2
sentinel down-after-milliseconds mymaster 30000
sentinel failover-timeout mymaster 180000
sentinel parallel-syncs mymaster 1
sentinel auth-pass mymaster yourpassword
sentinel deny-scripts-reconfig yes
```

| 参数 | 默认值 | 作用 |
| --- | --- | --- |
| `down-after-milliseconds` | 30000 | 超过该时间无有效回复判 SDOWN |
| `failover-timeout` | 180000 | 故障转移各阶段超时与重试间隔 |
| `parallel-syncs` | 1 | 切换后同时向新主同步的从库数量，越小对主库压力越小 |
| `quorum` | 配置值 | 判定 ODOWN 所需票数 |
| `replica-priority` | 100 | 选主优先级，0 表示不参选 |

```bash
# 查询当前主库地址（客户端常用）
redis-cli -p 26379 SENTINEL get-master-addr-by-name mymaster
# 1) "10.0.0.2"
# 2) "6379"

# 查看哨兵认为的主从拓扑
redis-cli -p 26379 SENTINEL masters
redis-cli -p 26379 SENTINEL replicas mymaster
redis-cli -p 26379 SENTINEL sentinels mymaster

# 检查 quorum 是否足够
redis-cli -p 26379 SENTINEL CKQUORUM mymaster
# OK 3 usable Sentinels. Quorum and failover authorization can be reached

# 手动触发一次故障转移（演练用）
redis-cli -p 26379 SENTINEL FAILOVER mymaster
```

**客户端如何接入：**

- 客户端不能只连哨兵，也不能缓存一次主库地址就永不更新；应订阅 `+switch-master` 或定期查询哨兵。
- 常见客户端库（Lettuce、Jedis、Redisson）支持 Sentinel 模式，传入哨兵地址列表与 master 名称。
- 切换瞬间可能出现短暂写入失败，业务要捕获 `READONLY` 错误并重试/刷新连接。
- 哨兵本身也要高可用：至少 3 个，配置一致，时间同步，避免全部部署在同一台机器。

**面试怎么答：**

先讲四个职责「监控、通知、故障转移、配置提供」，再区分 SDOWN 与 ODOWN、quorum 与 majority。故障转移按「选举 leader → 选从库（priority/offset/runid）→ 提升 → 重配其他从库 → 通知客户端」回答。最后补部署要求：3 个以上奇数、跨故障域、客户端要能刷新主库地址。

**易错点：**

- quorum 是判定 ODOWN 的票数，不是选 leader 的票数；选 leader 需要多数。
- `quorum=1` 不代表可以单哨兵切主，仍需要多数投票。
- 哨兵不存储数据，也不做分片；它只管理一组主从。
- 故障转移是异步复制之上的切换，旧主未同步的写入会丢。
- `parallel-syncs` 不是越大越好，同时全量同步多个从库会压垮新主。
- 旧主恢复后不会自动变回主库，哨兵会把它降级为从库；若网络分区导致它仍被客户端写入，就会产生分叉。

## 6. Cluster 分片与槽位迁移

**Redis Cluster 把整个键空间划分为 16384 个槽（slot），每个 key 用 `CRC16(key) mod 16384` 映射到槽，槽再分配给不同主节点；每个主节点可以带从节点，主节点故障时由集群多数派提升从节点。客户端收到 `MOVED` 后更新路由，槽迁移期间会收到 `ASK` 临时重定向。Cluster 解决分片与水平扩展，但多 key 操作、事务、Lua 都要求 key 在同一槽。**

**为什么是 16384 个槽：**

- 槽位图用位图表示，16384 位 = 2KB，心跳包可以携带完整槽位图；65536 位 = 8KB，心跳开销太大。
- 16384 个槽在几十到上千节点规模下足够均匀，再大也没有明显收益。
- 槽数量固定，扩缩容是「搬槽」，不是重新哈希所有 key。

**key 到槽的计算：**

```text
slot = CRC16(key) mod 16384

# hash tag：只对第一个 {} 中的内容做 CRC16
CRC16("{user:1001}:profile") = CRC16("user:1001")
CRC16("{user:1001}:cart")    = CRC16("user:1001")
# 两个 key 落在同一槽，可以一起 MGET / 事务 / Lua
```

**核心配置：**

```conf
cluster-enabled yes
cluster-config-file nodes.conf       # 节点自动维护，不要手改
cluster-node-timeout 15000           # 节点失联判定时间（毫秒）
cluster-require-full-coverage yes    # 有槽未覆盖时整个集群停止服务
cluster-migration-barrier 1          # 从节点迁移到无副本主节点的门槛
cluster-allow-reads-when-down no     # 集群 fail 时是否允许读
cluster-replica-no-failover no       # 从节点是否禁止自动 failover
```

| 端口 | 用途 |
| --- | --- |
| 6379 | 客户端连接端口 |
| 16379 | 集群总线端口（客户端端口 + 10000），节点间 gossip/心跳/投票 |
| 26379 | 哨兵端口（Cluster 模式不需要哨兵） |

**搭建与查看：**

```bash
# 创建 3 主 3 从集群（--cluster-replicas 1 表示每个主带 1 个从）
redis-cli --cluster create \
  10.0.0.1:6379 10.0.0.2:6379 10.0.0.3:6379 \
  10.0.0.4:6379 10.0.0.5:6379 10.0.0.6:6379 \
  --cluster-replicas 1

# 查看集群状态与槽分配
redis-cli -p 6379 CLUSTER INFO
# cluster_state:ok
# cluster_slots_assigned:16384
# cluster_slots_ok:16384
# cluster_known_nodes:6

redis-cli -p 6379 CLUSTER NODES
# <id> 10.0.0.1:6379@16379 myself,master - 0 0 1 connected 0-5460

redis-cli -p 6379 CLUSTER SLOTS
# 7.0 也可以用 CLUSTER SHARDS 查看更结构化的信息

# 健康检查
redis-cli --cluster check 10.0.0.1:6379
```

**MOVED 与 ASK：**

| 重定向 | 含义 | 客户端动作 |
| --- | --- | --- |
| `MOVED <slot> <host:port>` | 槽已永久归属目标节点 | 更新本地槽映射，后续请求直接发目标 |
| `ASK <slot> <host:port>` | 槽正在迁移，本次 key 已迁到目标 | 先向目标发送 `ASKING`，再发原命令；不更新长期映射 |

**槽迁移的步骤（手动/工具内部）：**

1. 目标节点执行 `CLUSTER SETSLOT <slot> IMPORTING <source-node-id>`。
2. 源节点执行 `CLUSTER SETSLOT <slot> MIGRATING <target-node-id>`。
3. 源节点用 `CLUSTER GETKEYSINSLOT <slot> <count>` 取 key，逐个 `MIGRATE` 到目标。
4. 迁移完成后，向所有节点广播 `CLUSTER SETSLOT <slot> NODE <target-node-id>`。
5. 迁移期间源节点对已迁走的 key 返回 `ASK`，对未迁走的 key 正常处理。

```bash
# 查看某个槽的 key 数量
redis-cli -p 6379 CLUSTER COUNTKEYSINSLOT 100

# 取该槽的 key 列表
redis-cli -p 6379 CLUSTER GETKEYSINSLOT 100 10

# 手动迁移一个 key（目标节点需先 SETSLOT IMPORTING）
redis-cli -p 6379 MIGRATE 10.0.0.2 6379 key:1001 0 5000

# 用官方工具重新分片：从节点 A 搬 1000 个槽到节点 B
redis-cli --cluster reshard 10.0.0.1:6379 \
  --cluster-from <source-id> \
  --cluster-to <target-id> \
  --cluster-slots 1000 \
  --cluster-yes

# 均衡槽位
redis-cli --cluster rebalance 10.0.0.1:6379
```

**集群故障转移：**

- 主节点失联超过 `cluster-node-timeout`，其从节点发起选举。
- 需要获得「多数主节点」的投票（不是所有节点），因此集群至少要有 3 个主节点。
- 从节点按复制偏移量、优先级等排序，数据最新的优先。
- 提升后广播槽位变更，客户端收到 `MOVED` 更新路由。
- 若 `cluster-require-full-coverage yes`，只要有一个槽没有主节点，整个集群 `cluster_state:fail`，所有读写被拒绝。

**多 key 限制：**

- `MGET`、`MSET`、`SUNION`、事务、Lua 脚本中的 key 必须落在同一槽，否则报 `CROSSSLOT Keys in request don't hash to the same slot`。
- 用 hash tag `{...}` 把需要一起操作的 key 固定到同一槽。
- 不要滥用 hash tag，否则大量 key 挤在一个节点，形成热点。
- Cluster 只支持 db 0，不能 `SELECT` 其他 db。

**面试怎么答：**

先讲「16384 槽 + CRC16 + 槽归属节点」，再讲 MOVED/ASK 的区别与迁移步骤，最后讲故障转移需要多数主节点、`cluster-require-full-coverage` 与多 key 同槽限制。补 hash tag 的用法与滥用风险。

**易错点：**

- Cluster 不是一致性哈希，槽是固定数量、显式分配的。
- `MOVED` 是永久重定向，`ASK` 是临时重定向；ASK 后必须发 `ASKING`。
- 槽迁移不是「自动重新哈希所有 key」，而是逐个 `MIGRATE`，大 key 会卡住迁移。
- 集群至少 3 主才能可靠选举；2 主在丢失一个后无法获得多数。
- `cluster-require-full-coverage yes` 会让「一个槽不可用」升级为「整个集群不可用」，可用性与一致性要权衡。
- Cluster 模式不需要哨兵，哨兵与 Cluster 是两套不同的高可用方案。
- `nodes.conf` 由节点自动维护，手改可能导致节点 ID/槽信息错乱。

## 7. 脑裂问题与数据丢失

**脑裂（split-brain）指网络分区后，集群出现「两个都认为自己该服务写入的主节点」：一侧的哨兵/集群多数派把从库提升为新主，另一侧的旧主仍然接受客户端写入。等网络恢复，旧主被降级为从库并执行全量同步，它在隔离期间写入的数据会被覆盖，造成永久丢失。根因是 Redis 异步复制 + 故障检测依赖网络，无法同时满足强一致与高可用。**

**典型时间线（哨兵模式）：**

1. 主库 M 与哨兵、从库之间的网络中断，但 M 与部分客户端仍连通。
2. 哨兵达到 `down-after-milliseconds` 后判定 M 主观下线，达到 quorum 后客观下线。
3. 多数哨兵选出 leader，把从库 R 提升为新主，其他从库改为复制 R。
4. 客户端如果仍连着 M（长连接、未刷新路由），继续向 M 写入数据 A。
5. 网络恢复，哨兵发现 M 仍在，向 M 发送 `REPLICAOF R`，M 降级为从库。
6. M 全量同步 R 的数据，写入 A 被覆盖；如果 A 已经返回客户端成功，就形成「已确认但丢失」。

```text
       网络分区
  ┌───────────────┐
  │               │
[旧主 M] ──x── [哨兵 quorum] ── [从库 R → 新主]
  │                               │
客户端仍写 M（数据 A）          新写入 B
  │                               │
  └──── 网络恢复，M 降级、全量同步 ──→ A 丢失，B 保留
```

**Cluster 模式下是否也会脑裂：**

- Cluster 的故障转移需要「多数主节点」投票，孤立在少数派一侧的旧主无法获得多数，超过 `cluster-node-timeout` 后会标记集群不可用，通常不再接受写入。
- 因此 Cluster 比「单组哨兵 + 客户端直连旧主」更难出现双写，但不是绝对：客户端路由错误、`cluster-require-full-coverage no`、`cluster-allow-reads-when-down yes` 等配置会扩大风险。
- 无论哪种模式，只要旧主在隔离期间接受了写入，这些写入都不在新主的历史里，恢复后就会被覆盖。

**降低数据丢失的手段：**

| 手段 | 配置/做法 | 作用 | 局限 |
| --- | --- | --- | --- |
| 最小从库数 | `min-replicas-to-write 1`、`min-replicas-max-lag 10` | 没有健康从库时拒绝写入，减少旧主继续写 | 降低可用性，网络抖动可能误拒 |
| 同步确认 | `WAIT 1 100` | 等待至少 1 个从库确认 | 只到从库缓冲，不是落盘；增加延迟 |
| 客户端路由 | 只向哨兵/集群查询当前主库 | 避免长期直连旧主 | 切换瞬间仍有短暂错误 |
| fencing | 旧主恢复前强制降级、断网、关机 | 阻止旧主继续服务 | 需要外部编排与运维权限 |
| 多数派 | 哨兵 majority、Cluster 多数主节点 | 防止少数派单方面切主 | 分区两侧都失去多数时整体不可用 |
| 业务幂等 | 写入带业务唯一键、可重放 | 丢失后可补偿 | 不能恢复已丢数据，只能减少影响 |

```conf
# 主库配置：至少 1 个从库、延迟不超过 10 秒才允许写
min-replicas-to-write 1
min-replicas-max-lag 10
```

```bash
# 查看从库数量与延迟
redis-cli INFO replication | grep -E "connected_slaves|slave0|master_repl_offset"

# 写入后等待 1 个从库确认（100ms 超时），返回确认数
redis-cli SET order:1001 paid
redis-cli WAIT 1 100
# (integer) 1

# 故障恢复后确认旧主已被降级
redis-cli -h old-master ROLE
# 1) "slave"
# 2) "10.0.0.2"
# 3) 6379

# 必要时强制断开旧主上的客户端，阻止继续写入
redis-cli -h old-master CLIENT KILL TYPE normal
```

**为什么不能彻底解决：**

- Redis 复制是异步的，主库无法在返回成功前确认「所有从库都已收到」；要强一致就得牺牲写入延迟与可用性（类似 `WAIT` 每次都等）。
- 网络分区时，系统必须在「拒绝服务」与「可能双写」之间选择；Redis 默认偏向可用性（AP）。
- 真正的强一致需要共识协议（Raft/Paxos）或外部锁/ fencing token，Redis 本身不提供。
- 因此工程上通常接受「极小概率丢最后一段数据」，用业务补偿、对账、幂等来兜底。

**面试怎么答：**

先定义脑裂与数据丢失的时间线，点明根因「异步复制 + 分区期间旧主仍可写」。再讲 Sentinel 与 Cluster 的差异：Cluster 靠多数派降低概率，Sentinel 靠客户端正确刷新路由。最后给手段：`min-replicas-to-write`、`WAIT`、fencing、业务幂等，并明确「Redis 无法同时做到强一致与高可用」。

**易错点：**

- 脑裂不是「两个主库同时存在就一定会丢数据」，而是「旧主在隔离期间接受了未同步的写入」才会丢。
- `min-replicas-to-write` 会在从库不足时拒绝写，可能把「部分故障」放大成「整体不可写」，要评估可用性。
- `WAIT` 不能替代持久化，也不能保证从库已落盘；它只降低丢失概率。
- 旧主恢复后是被降级并全量同步，不是「把旧主的数据合并到新主」。
- Cluster 的多数派只能降低脑裂概率，不能解决异步复制本身的丢失窗口。
- 不要用「重启旧主」当作 fencing：重启前它仍可能接受写入，必须先断网/降级/关机。

## 8. 一致性哈希与 Redis Cluster 的区别

**一致性哈希是一种「客户端/代理侧」的数据分布算法：把节点和 key 都哈希到同一个 2^32 环上，key 顺时针找到第一个节点；增删节点只影响相邻区间的 key。Redis Cluster 则是「服务端分片」：固定 16384 个槽，CRC16 映射，槽的归属由集群元数据维护，客户端通过 MOVED/ASK 重定向。两者都能分片，但一致性哈希不是 Redis Cluster 的实现方式。**

**一致性哈希的工作方式：**

1. 把哈希空间组织成 `0 ~ 2^32-1` 的环。
2. 每个物理节点计算哈希，放在环上；通常一个物理节点会映射为多个「虚拟节点」，让分布更均匀。
3. 每个 key 计算哈希，顺时针找到第一个节点，就是它的归属。
4. 增加节点：只把新节点逆时针到前一个节点之间的 key 迁过来，约 `1/N`。
5. 删除节点：只把它负责的 key 交给顺时针下一个节点，约 `1/N`。

```text
            0 / 2^32
              │
       node A ●
          ╱        ╲
   key1 ●          ● node B
        │          │
   key2 ●          ● node C
          ╲        ╱
              │
          key3 ●
# key1 顺时针遇到 node B，归属 B；key3 顺时针遇到 node A，归属 A
```

**虚拟节点的作用：**

- 物理节点少时，哈希环上的分布可能很不均匀，甚至一个节点承担大部分 key。
- 每个物理节点映射 100~1000 个虚拟节点，把负载打散，标准差显著下降。
- 虚拟节点越多，分布越均匀，但元数据与客户端计算开销也越大。
- 节点权重可以通过虚拟节点数量调节（性能强的机器放更多虚拟节点）。

| 维度 | 一致性哈希 | Redis Cluster |
| --- | --- | --- |
| 分片方式 | 哈希环 + 顺时针找节点 | 16384 固定槽 + CRC16 |
| 分布实现 | 客户端/代理计算 | 服务端维护槽归属，客户端缓存路由 |
| 扩容 | 只迁移相邻区间，约 1/N | 显式搬槽，可用工具 rebalance |
| 路由 | 客户端自己算，无重定向 | `MOVED`/`ASK` 重定向 |
| 多 key | 取决于客户端实现，通常要求同节点 | 要求同槽，可用 hash tag |
| 故障转移 | 算法本身不提供，需配合哨兵/代理 | 内置主从与多数派选举 |
| 数据倾斜 | 靠虚拟节点缓解 | 靠槽分配与 rebalance，热点 key 仍会倾斜 |
| 典型实现 | Twemproxy、Codis、客户端分片 | Redis Cluster 原生 |

**Redis Cluster 为什么不用一致性哈希：**

- 槽数量固定，元数据小且确定，节点间可以用 2KB 位图同步槽信息。
- 槽是显式分配的，运维可以精确控制某个业务落在哪个节点，便于隔离与迁移。
- 客户端只需缓存「槽 → 节点」映射，收到 MOVED 更新即可，不需要自己维护哈希环与虚拟节点。
- 故障转移、副本迁移、槽迁移都能在服务端编排，代理/客户端逻辑更简单。
- 代价是扩缩容要搬槽，且多 key 操作受槽限制；一致性哈希的「自动最小迁移」在 Cluster 中需要工具显式完成。

**代理分片与智能客户端：**

- 代理方案（Twemproxy、Codis、Predixy）在客户端与 Redis 之间做一致性哈希/槽路由，客户端像连单机一样使用。
- 代理的缺点是增加一跳网络、需要自身高可用、对事务/Lua/多 key 支持有限。
- 智能客户端（Jedis Cluster、Lettuce Cluster、Redisson）直接维护槽映射，性能更好，但要正确处理 MOVED/ASK 与拓扑刷新。
- 选择时看团队运维能力：想少改客户端可用代理，想吃满性能与原生故障转移用 Cluster。

**面试怎么答：**

先给定义：一致性哈希是环 + 顺时针 + 虚拟节点，扩缩容只影响约 1/N；Redis Cluster 是固定 16384 槽 + CRC16 + 服务端槽归属 + MOVED/ASK。再对比路由、扩容、多 key、故障转移。最后点明「Cluster 不是一致性哈希」，并补代理分片与智能客户端的取舍。

**易错点：**

- Redis Cluster 用的是「槽」，不是一致性哈希环；不要说「Cluster 用一致性哈希」。
- 一致性哈希的「只迁移 1/N」是理想情况，节点少、虚拟节点少时仍会倾斜。
- 虚拟节点不是真实节点，增加虚拟节点只改善均衡，不增加容量。
- Cluster 的槽迁移是显式的，不会因为加节点就自动把 key 搬过去。
- 多 key 操作在 Cluster 下不是「路由到多个节点再合并」，而是直接报 `CROSSSLOT`。
- 代理方案也会遇到多 key、事务、Lua 的限制，不是「透明分片」就没有代价。

## 9. 持久化方案选型（能否当数据库用）

**Redis 能否当数据库，取决于你对 RPO/RTO、强一致、查询能力与成本的要求。它可以做到「重启不丢大部分数据」「主库挂了自动切换」，但它不是关系型数据库：内存成本高、异步复制可能丢最后一段、没有跨节点事务与复杂查询。把 Redis 当「唯一真相源」需要非常严格的持久化、复制、备份与对账体系，多数业务更适合「数据库 + Redis 缓存」。**

**先看 RPO 与 RTO：**

| 方案 | 数据丢失窗口（RPO） | 恢复时间（RTO） | 说明 |
| --- | --- | --- | --- |
| 仅 RDB | 两次快照之间，可能几分钟到几十分钟 | 快，加载二进制 | 适合可重建的缓存、备份 |
| AOF `everysec` | 通常 ≤1 秒 | 较慢，需重放命令 | 大多数持久化场景的默认 |
| AOF `always` | 接近 0，但非绝对 | 慢，文件大 | 写入吞吐受磁盘 IOPS 限制 |
| 混合持久化 | 通常 ≤1 秒 | 快，RDB 基线 + 少量增量 | 兼顾恢复速度与丢失窗口 |
| 主从异步 | 故障切换可能丢未同步部分 | 秒级到几十秒 | 高可用不等于不丢数据 |
| 主从 + `WAIT` | 降低丢失概率 | 增加写入延迟 | 仍不是强一致 |

**Redis 当数据库的硬性条件：**

1. **数据能全部放进内存**，并预留 30% 以上给 fork COW、碎片、复制缓冲。
2. **接受最终一致或可补偿**：主从异步、故障切换、脑裂都可能丢最后一段写入。
3. **没有复杂查询需求**：不支持 SQL、JOIN、二级索引、聚合；只能靠数据结构预先建模。
4. **没有跨分片事务**：Cluster 下事务/Lua 要求同槽，跨业务强一致要靠外部协调。
5. **有完善的持久化与备份**：AOF everysec + 定期 RDB 冷备 + 异地备份 + 恢复演练。
6. **有高可用与容量治理**：哨兵/Cluster、从库、监控、告警、扩缩容预案。
7. **有对账与补偿**：定期比对业务库与 Redis，发现丢失可修复。

```conf
# 偏「数据库式」的持久化配置示例
appendonly yes
appendfsync everysec
aof-use-rdb-preamble yes
auto-aof-rewrite-percentage 100
auto-aof-rewrite-min-size 256mb
save 900 1
save 300 100
save 60 10000
maxmemory-policy noeviction       # 数据不能淘汰，宁可写失败
min-replicas-to-write 1
min-replicas-max-lag 10
```

```bash
# 运行时开启 AOF（会触发一次重写）
redis-cli CONFIG SET appendonly yes
redis-cli INFO persistence
# aof_enabled:1
# aof_last_bgrewrite_status:ok

# 检查当前刷盘策略
redis-cli CONFIG GET appendfsync
# 1) "appendfsync"
# 2) "everysec"

# 写入后等待从库确认
redis-cli SET order:1001 paid
redis-cli WAIT 1 100

# 备份：RDB 冷备 + AOF 目录备份，注意先确保文件完整
redis-cli BGSAVE
redis-cli LASTSAVE
cp /var/lib/redis/dump.rdb /backup/redis/dump-$(date +%F).rdb
```

**推荐选型：**

| 场景 | 持久化 | 高可用 | 说明 |
| --- | --- | --- | --- |
| 纯缓存，可回源 | RDB 或不持久化 | 主从/哨兵 | 丢失可重建，优先性能 |
| 缓存 + 少量不可丢状态 | AOF everysec + RDB | 哨兵/Cluster | 接受秒级丢失，做好补偿 |
| 接近数据库的会话/订单状态 | AOF everysec + 从库 + `WAIT` | Cluster + 定期演练 | 必须有对账与备份 |
| 金融级强一致 | 不建议用 Redis 作为唯一存储 | — | 用关系型/分布式数据库，Redis 只做缓存 |
| 允许丢数据的排行榜/计数 | RDB | 主从 | 可定期从业务库重建 |

**面试怎么答：**

先给结论：「可以做持久化存储，但不是默认的数据库替代品。」再讲 RPO/RTO 表：RDB 丢分钟级、AOF everysec 丢约 1 秒、always 接近 0 但慢、复制是异步的。然后列当数据库的七个条件：内存、最终一致、查询能力、跨分片事务、备份、高可用、对账。最后给场景选型，强调「缓存可以丢，状态要能补偿」。

**易错点：**

- 「开启 AOF 就不会丢数据」是错的：`everysec` 仍可能丢约 1 秒，`always` 也受磁盘与故障影响。
- 「有主从就不会丢」是错的：复制是异步的，故障切换会丢未同步写入。
- 「RDB 是备份，AOF 不是备份」不准确：两者都要异地备份，且备份前要确认文件完整。
- `maxmemory-policy` 在数据库式场景应设为 `noeviction`，否则内存满时数据会被淘汰。
- AOF 文件大时恢复很慢，必须配合混合持久化/重写与恢复演练。
- Redis 的备份不是「拷一个文件就完事」：7.0 多 Part 要拷整个 `appendonlydir` 与 manifest。

## 10. 扩容缩容与数据迁移

**Redis 的扩容分两种：哨兵模式只能加从库做读扩展，写容量仍受单主限制；Cluster 模式通过「加节点 → 搬槽 → 加从库」实现水平扩展。缩容则相反：先把槽迁走，再删节点。整个过程的核心是「槽迁移」，而槽迁移的核心是 `MIGRATE` 与 `ASK` 重定向，必须保证客户端支持重定向、业务能容忍迁移期间的延迟。**

**Cluster 扩容的标准步骤：**

1. **评估**：`redis-cli --cluster check` 看槽分布、副本数、big key；确认新节点内存、磁盘、网络与老节点一致。
2. **启动新节点**：配置 `cluster-enabled yes`、`cluster-config-file`、`cluster-node-timeout`，端口与总线端口（+10000）放通。
3. **加入集群**：`redis-cli --cluster add-node <new> <existing>`，新节点以 master 身份加入，但初始没有槽。
4. **迁移槽**：`redis-cli --cluster reshard` 从老节点搬指定数量的槽到新节点；或按权重 `rebalance`。
5. **加从库**：`redis-cli --cluster add-node <new-replica> <existing> --cluster-slave --cluster-master-id <new-master-id>`。
6. **验证**：`CLUSTER INFO` 的 `cluster_state:ok`、`cluster_slots_assigned:16384`；`--cluster check` 无告警；压测与业务回归。

```bash
# 1. 加入一个新的空 master
redis-cli --cluster add-node 10.0.0.7:6379 10.0.0.1:6379

# 2. 从源节点搬 2000 个槽到新节点（source-id/target-id 从 CLUSTER NODES 获取）
redis-cli --cluster reshard 10.0.0.1:6379 \
  --cluster-from <source-node-id> \
  --cluster-to <target-node-id> \
  --cluster-slots 2000 \
  --cluster-yes

# 3. 为新 master 添加从库
redis-cli --cluster add-node 10.0.0.8:6379 10.0.0.1:6379 \
  --cluster-slave \
  --cluster-master-id <target-node-id>

# 4. 按权重均衡（可选）
redis-cli --cluster rebalance 10.0.0.1:6379 \
  --cluster-weight <node-id>=2 <other-id>=1 \
  --cluster-use-empty-masters

# 5. 健康检查
redis-cli --cluster check 10.0.0.1:6379
```

**槽迁移期间发生了什么：**

- 源节点把槽标记为 `MIGRATING`，目标节点标记为 `IMPORTING`。
- 源节点对「已迁走的 key」返回 `ASK`，客户端需要先发 `ASKING` 再发命令。
- 源节点对「尚未迁走的 key」正常处理；目标节点只接受带 `ASKING` 的请求。
- 迁移完成后，槽归属广播到全集群，客户端收到 `MOVED`，后续请求直接走目标节点。
- 迁移是逐 key `MIGRATE`，大 key、大量 key 会长时间占用源/目标节点的 CPU 与网络。

**缩容的标准步骤：**

1. 先把待删除节点上的槽全部 `reshard` 到其他节点，确保 `CLUSTER COUNTKEYSINSLOT` 为 0。
2. 删除该节点的从库（如果有），再删除主节点：`redis-cli --cluster del-node <host:port> <node-id>`。
3. 确认 `cluster_state:ok`、16384 个槽全部有归属、副本数满足要求。
4. 观察一段时间再下线机器，避免「刚删完就出故障」没有回滚余地。

```bash
# 删除节点前先确认它没有槽
redis-cli -p 6379 CLUSTER NODES | grep <node-id>

# 删除节点（必须先迁走槽与从库）
redis-cli --cluster del-node 10.0.0.1:6379 <node-id>

# 修复集群状态（槽丢失、节点 handshake 等）
redis-cli --cluster fix 10.0.0.1:6379
```

**哨兵模式下的扩展：**

- 写容量无法通过加从库扩展，只能垂直扩容（更强 CPU/内存）或改成 Cluster/业务分片。
- 读容量可以加从库，客户端做读写分离；注意主从延迟与从库数量对主库复制缓冲的压力。
- 加从库：启动新实例，配置 `replicaof <master> <port>` 与 `masterauth`，哨兵会自动发现。
- 缩容：先 `REPLICAOF NO ONE` 摘除从库，再下线；不要直接杀掉正在全量同步的从库。

**迁移前的检查清单：**

| 检查项 | 目的 |
| --- | --- |
| 客户端支持 MOVED/ASK | 否则迁移期间大量请求失败 |
| 业务是否使用多 key/事务/Lua | 跨槽会失败，需要 hash tag 或改造 |
| 是否有大 key | `MIGRATE` 会阻塞，先拆分或异步迁移 |
| 新节点内存/磁盘/网络 | 避免迁入后立刻 OOM 或 RDB 失败 |
| 持久化与备份 | 迁移前做一次完整备份，保留回滚点 |
| 监控与告警 | 迁移期间盯住延迟、错误率、槽状态 |

**面试怎么答：**

先区分哨兵与 Cluster：哨兵只能读扩展，Cluster 才能写扩展。Cluster 扩容按「加空 master → reshard 搬槽 → 加从库 → 验证」回答；缩容按「迁走槽 → 删从库 → 删主节点 → 验证」。再补迁移期间的 ASK/MOVED、大 key 与多 key 限制、客户端必须支持重定向。

**易错点：**

- 新节点加入 Cluster 后默认没有槽，不会自动分担流量，必须显式 reshard。
- `rebalance` 不是「重新哈希所有 key」，而是按槽数量/权重搬槽，仍可能受大 key 影响。
- 缩容前必须确认节点没有槽、没有从库，否则 `del-node` 会失败或留下坏状态。
- 迁移期间客户端不支持 ASK 会读到 `MOVED`/`ASK` 错误，表现为大量失败。
- 多 key 操作在迁移期间更容易触发 `CROSSSLOT`，要提前用 hash tag。
- 迁移不是「零延迟」：`MIGRATE` 会阻塞源节点，最好限速、分批、低峰执行。

## 11. 故障演练与高可用验证

**高可用不能只看架构图，必须通过故障演练验证「检测时间、切换时间、数据丢失量、客户端恢复」四个指标。演练要覆盖主库宕机、网络分区、磁盘满、AOF 损坏、fork 失败、集群少数派等场景，并在隔离环境或低峰期进行，准备好备份、回滚与观测手段。**

**演练矩阵：**

| 场景 | 模拟方式 | 预期行为 | 验证点 |
| --- | --- | --- | --- |
| 主库进程崩溃 | `kill -9 <pid>` 或 `SHUTDOWN NOSAVE` | 哨兵/Cluster 检测并提升从库 | RTO、客户端是否自动重连、丢失写入量 |
| 主库机器断电 | 关机/断网 | 同上，但可能伴随磁盘/网络恢复问题 | 旧主恢复后是否被降级 |
| 网络分区 | `iptables` 封禁主库与哨兵/从库 | 多数派一侧切主，少数派停止写 | 是否双写、恢复后数据是否覆盖 |
| 从库全量同步中断 | 传输中断网/重启从库 | 重连后增量或重新全量 | `master_link_status`、backlog 是否够用 |
| 磁盘写满 | `fallocate` 占满磁盘 | RDB/AOF 写失败，可能触发 `stop-writes-on-bgsave-error` | 告警、写拒绝、恢复后能否继续 |
| AOF 尾部损坏 | 截断 AOF 文件末尾 | `aof-load-truncated yes` 时尽量加载 | 启动日志、丢失范围、是否需要 `--fix` |
| fork 失败 | 限制内存/关闭 overcommit | `BGSAVE`/`BGREWRITEAOF` 失败 | `rdb_last_bgsave_status`、是否影响写入 |
| 集群少数派 | 隔离 1 个主节点 | 多数派提升其从库；少数派停止服务 | `cluster_state`、槽是否完整 |
| 慢命令 | `DEBUG SLEEP`/大 key 操作 | 主线程阻塞，延迟飙升 | 慢日志、超时、是否能快速定位 |

```bash
# 模拟主库崩溃（不保存，最接近断电）
redis-cli -h 10.0.0.1 SHUTDOWN NOSAVE

# 观察哨兵切换
redis-cli -p 26379 SENTINEL get-master-addr-by-name mymaster
redis-cli -p 26379 SENTINEL masters | grep -E "name|flags|num-slaves"

# 观察集群状态
redis-cli -p 6379 CLUSTER INFO
redis-cli -p 6379 CLUSTER NODES
redis-cli --cluster check 10.0.0.1:6379

# 模拟主线程阻塞（7.0 默认禁用 DEBUG）
# 需在 redis.conf 设置 enable-debug-command yes 并重启；protected config 不能运行时 CONFIG SET
redis-cli DEBUG SLEEP 5

# 更安全的暂停方式：暂停写入 5 秒，观察客户端表现
redis-cli CLIENT PAUSE 5000 WRITE

# 查看复制与持久化状态
redis-cli INFO replication
redis-cli INFO persistence
```

**演练要记录的核心指标：**

| 指标 | 含义 | 目标示例 |
| --- | --- | --- |
| 故障检测时间 | 从故障发生到判定下线 | 哨兵 30s 左右，Cluster 15s 左右 |
| 切换时间（RTO） | 从故障到新主可写 | 30s 内 |
| 数据丢失量（RPO） | 故障前未同步的写入 | 0~1 秒（异步复制的极限） |
| 客户端错误率 | 切换期间失败请求占比 | 短暂上升后可恢复 |
| 自动恢复 | 旧主恢复后是否被正确降级 | 不出现双主、不需要人工介入 |

**演练的安全要求：**

- 生产演练必须提前审批、通知业务方、选择低峰期，并准备回滚脚本。
- 先做只读/从库演练，再做主库切换；先单实例，再集群。
- 演练前确认备份可用，演练后做数据对账，确认没有静默丢失。
- 不要在生产直接 `DEBUG SLEEP`、`SHUTDOWN`、`iptables`，这些操作可能被安全策略拦截或放大故障。
- 演练结束要复盘：检测为什么慢、客户端为什么没切换、监控是否漏报。

**面试怎么答：**

先给「四个指标」：检测、RTO、RPO、客户端恢复。再列场景：主库崩溃、网络分区、磁盘满、AOF 损坏、fork 失败、集群少数派。每个场景说「怎么模拟、预期什么、看什么指标」。最后补安全要求：审批、低峰、备份、回滚、对账。

**易错点：**

- 只验证「能切主」不验证「客户端能恢复」，切换成功后业务仍可能大量报错。
- 不验证旧主恢复后的行为，可能留下双主或旧主继续被写入。
- 用 `SHUTDOWN`（默认保存）模拟崩溃不真实，`SHUTDOWN NOSAVE` 或 `kill -9` 更接近断电。
- 7.0 默认禁用 `DEBUG`，演练前要确认 `enable-debug-command`，且生产不建议长期开启。
- 网络分区演练可能影响其他系统，必须在受控网络命名空间/隔离环境做。
- 演练不记录 RPO/RTO，就无法判断高可用方案是否达标。

## 12. 多级缓存架构

**多级缓存是「CDN → 本地缓存 → Redis → 数据库」的分层结构：越靠近用户，速度越快、容量越小、一致性越弱；越往后，容量越大、延迟越高。它的目标不是「所有数据都放 Redis」，而是让热点在更近的层被拦截，降低 Redis 与数据库的压力，同时用 TTL、失效通知与降级策略控制一致性风险。**

**典型读路径：**

```text
请求 → CDN（静态资源） → Nginx/OpenResty 本地缓存
     → 应用进程内缓存（Caffeine/Guava）
     → Redis（分布式缓存）
     → 数据库
     每一层未命中才往下走，回填时逐层写入
```

**典型写路径：**

```text
写请求 → 数据库（提交）
       → 删除 Redis 缓存
       → 发布失效消息（Pub/Sub / MQ / binlog）
       → 各实例删除本地缓存
```

**各层的取舍：**

| 层级 | 典型实现 | 延迟 | 容量 | 一致性 | 适用数据 |
| --- | --- | --- | --- | --- | --- |
| CDN | 云 CDN、边缘节点 | 10~50ms | 大 | 弱，靠 TTL/刷新 | 静态资源、图片、视频 |
| 本地缓存 | Caffeine、Guava、Ehcache | 纳秒~微秒 | 小（单机内存） | 弱，多实例各自一份 | 极热配置、字典、榜单 |
| Redis | 单机/哨兵/Cluster | 亚毫秒~毫秒 | 中大 | 较强（单 key 原子） | 会话、对象缓存、计数、锁 |
| 数据库 | MySQL/PostgreSQL | 毫秒~几十毫秒 | 大 | 强 | 真相源、复杂查询 |

**本地缓存的关键问题：**

- **多实例不一致**：每个实例各有一份，更新后其他实例可能仍是旧值；必须用短 TTL + 失效广播。
- **容量与淘汰**：本地缓存占堆内存，过大会引发 GC 停顿；要给固定上限与淘汰策略（LRU/LFU）。
- **冷启动**：实例刚启动时本地缓存为空，可能瞬间把流量打到 Redis/DB；需要预热或限流。
- **热点漂移**：本地缓存只对「稳定热点」有效，突发热点仍要靠 Redis 与请求合并。

**一致性方案：**

| 方案 | 做法 | 一致性 | 复杂度 |
| --- | --- | --- | --- |
| 短 TTL | 本地缓存 1~5 秒过期 | 最终一致，窗口可控 | 低 |
| Pub/Sub 失效 | 更新后发布 key，实例订阅删除 | 秒级一致，可能丢消息 | 中 |
| MQ 广播 | 用可靠 MQ 替代 Pub/Sub | 更高可靠，仍有延迟 | 中高 |
| binlog 订阅 | Canal/Debezium 解析数据库变更，广播失效 | 与数据库变更对齐 | 高 |
| 版本号 | 缓存值带版本，读取时校验 | 可检测旧值 | 中 |

```bash
# 更新数据库后删除缓存，并发布失效消息
redis-cli DEL product:8899
redis-cli PUBLISH cache:invalidate "product:8899"

# 应用实例订阅失效频道（伪代码）
# subscriber.subscribe("cache:invalidate")
# on_message(channel, key):
#     localCache.invalidate(key)
```

```text
// 读路径伪代码（带空值缓存与互斥重建）
value = localCache.get(key)
if value != nil:
    return value
value = redis.get(key)
if value == EMPTY_PLACEHOLDER:
    return nil
if value == nil:
    if redis.set(lockKey, token, NX, PX=3000):
        value = db.query(key)
        if value == nil:
            redis.set(key, EMPTY_PLACEHOLDER, EX=60)   // 防穿透
        else:
            redis.set(key, value, EX=300 + random(0, 60))
        redis.del(lockKey)
    else:
        sleep(50ms)
        return readAgain()   // 短暂等待后重试，避免大量并发打 DB
localCache.put(key, value, TTL=3s)
return value
```

**故障降级：**

- Redis 整体不可用：本地缓存继续服务热点；未命中的请求走限流 + 数据库，避免打垮 DB。
- 本地缓存失效：直接查 Redis，必要时加单航班合并。
- 数据库不可用：返回兜底数据/默认值，记录日志，禁止无限重试。
- 分层降级要有开关与预案，不能等故障发生才临时改代码。

**容量规划：**

- 本地缓存只放「Top N 热点」，按访问频次与内存预算定，通常几十 MB 到几百 MB。
- Redis 容量按「热点数据量 × 1.2~1.5（副本/碎片/过期未清）」估算，`maxmemory` 留 20%~30% 余量。
- CDN 按流量与回源率评估，缓存规则要区分静态资源与个性化接口。
- 每层都要监控命中率：本地命中率低说明热点不稳定，Redis 命中率低说明容量或 TTL 有问题。

**面试怎么答：**

先画四层「CDN → 本地 → Redis → DB」，说明越靠近用户越快但一致性越弱。再讲读路径逐层回填、写路径「先更库再删缓存 + 广播失效」。重点讲本地缓存的多实例一致性与容量问题，以及 TTL、Pub/Sub、binlog 三种失效方案。最后给降级与容量规划：Redis 挂了本地顶着、DB 要限流、每层看命中率。

**易错点：**

- 多级缓存不是「层数越多越好」：每加一层都增加一致性、容量与运维成本。
- 本地缓存不能用长 TTL，否则多实例长期不一致；也不能没有上限，否则 GC 抖动。
- Pub/Sub 不持久化，实例断线期间的消息会丢；关键业务用 MQ 或 binlog。
- 缓存降级不能「全部放行到 DB」，否则 Redis 故障会迅速变成数据库故障。
- 本地缓存与 Redis 的 key 命名要统一，否则失效消息无法准确删除。
- 多级缓存不能替代缓存穿透/击穿/雪崩的治理，仍然需要布隆过滤器、互斥重建、TTL 抖动。
