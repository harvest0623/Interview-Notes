## 1. 分库分表后的跨表查询

**需求澄清与量级估算：**

- 数据量：订单 10 亿行，按 `user_id` 哈希分 32 库，每库 32 表，共 1024 张表。
- 查询维度：用户查自己的订单、商家查店铺订单、客服按订单号查、运营按时间统计。
- 流量：读 8 万 QPS，其中按 `user_id` 的查询占 70%，按商家与订单号的查询占 25%。
- 约束：分片键只能选一个，跨分片查询不能全表广播，深分页不能把 1024 个分片的结果全拉回内存。
- 结论：分片键决定 70% 的查询效率，剩余 30% 必须用基因法、索引表、异构存储补齐。

**方案对比：**

| 方案 | 适用查询 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 广播所有分片 | 低频运营查询 | 实现简单 | 1024 次查询，尾延迟不可控 |
| 基因法 | 按订单号查 | 无需额外存储 | 只适用于能改造主键的场景 |
| 索引表 | 按商家、订单号查 | 灵活、可控 | 索引表本身要分片与保证一致 |
| 冗余宽表 | 商家后台列表 | 查询简单、性能好 | 写放大，需要同步机制 |
| 异构到 ES | 多条件搜索、模糊查询 | 检索能力强 | 数据同步与一致性成本 |

**核心流程：**

```
按 user_id 查：
    1. 计算 db = hash(user_id) % 32，table = hash(user_id) % 32
    2. 直接路由到唯一分片，单表查询
按 order_no 查：
    3. order_no 中嵌入 user_id 的后 10 位作为基因
    4. 从 order_no 解析基因，反推 db 与 table
按 merchant_id 查：
    5. 先查索引表 order_index 拿到 order_no 列表
    6. 再按 order_no 基因批量回源，或直接读商家冗余表
深分页：
    7. 每个分片只取 offset + size 条，内存归并后截取
    8. 更优方案是用游标：WHERE create_time < lastTime ORDER BY create_time DESC LIMIT size
```

**关键实现：**

订单号基因法把分片信息编码进业务主键，查询时无需索引表：

```java
public String generateOrderNo(long userId, long seq) {
    long gene = userId % 1024;
    long ts = System.currentTimeMillis();
    return String.format("%d%03d%03d", ts, gene, seq % 1000);
}

public int[] parseShard(String orderNo) {
    int gene = Integer.parseInt(orderNo.substring(13, 16));
    return new int[]{gene / 32, gene % 32};
}
```

索引表保存非分片键到分片的路由信息，本身也要按查询维度分片：

```sql
CREATE TABLE order_index (
    order_no     VARCHAR(32) NOT NULL,
    user_id      BIGINT      NOT NULL,
    merchant_id  BIGINT      NOT NULL,
    db_index     SMALLINT    NOT NULL,
    table_index  SMALLINT    NOT NULL,
    created_at   DATETIME    NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (order_no),
    KEY idx_merchant_time (merchant_id, created_at)
) ENGINE = InnoDB;
```

ShardingSphere 5.x 的分片配置，注意分片算法与数据节点必须一致：

```yaml
rules:
    - !SHARDING
      tables:
          t_order:
              actualDataNodes: ds_${0..31}.t_order_${0..31}
              databaseStrategy:
                  standard:
                      shardingColumn: user_id
                      shardingAlgorithmName: db_hash
              tableStrategy:
                  standard:
                      shardingColumn: user_id
                      shardingAlgorithmName: table_hash
      shardingAlgorithms:
          db_hash:
              type: INLINE
              props:
                  algorithm-expression: ds_${user_id % 32}
          table_hash:
              type: INLINE
              props:
                  algorithm-expression: t_order_${user_id % 32}
```

跨分片归并排序不能直接 `ORDER BY ... LIMIT 10000, 10`，否则每个分片都要返回 10010 条：

```sql
-- 每个分片执行，只取前 10010 条
SELECT order_no, create_time, amount
FROM t_order
WHERE user_id = ?
ORDER BY create_time DESC
LIMIT 10010;
```

**失败场景与兜底：**

| 失败点 | 现象 | 兜底策略 |
| --- | --- | --- |
| 分片键选错 | 80% 查询变广播 | 上线前统计查询维度，选覆盖率最高的字段 |
| 索引表不一致 | 按订单号查不到 | 订单写入与索引表同事务，或 binlog 补偿 |
| 深分页 | 内存溢出、响应超时 | 游标分页、限制最大页数、导出走异步任务 |
| 跨分片聚合 | 结果不准或超时 | 预聚合表、数仓、限制时间范围 |
| 分片倾斜 | 单库热点 | 用一致性哈希或提前规划大客户独立分片 |
| 扩容翻倍 | 旧数据路由错 | 用双倍扩容 + 数据迁移，避免取模变化 |

**面试怎么答：** 先问查询维度与占比，再确定分片键。然后按「分片键直查、基因法、索引表、异构 ES、数仓」逐级补齐非分片键查询。重点讲深分页与跨分片聚合的代价，说明分库分表不是「中间件一接就完事」，业务查询必须一起设计。

**易错点：**

- 分片键选 `order_id`，结果 90% 的「我的订单」查询全部广播。
- 用 `user_id % 1024` 分 1024 张表，扩容到 2048 时全量数据要重分布。
- 跨分片 `JOIN`，中间件只能广播或直接不支持。
- 深分页用 `LIMIT 100000, 10`，每个分片都扫十万行。
- 索引表异步更新但没有补偿，数据不一致后无法自查。

## 2. 亿级数据的统计与报表

**需求澄清与量级估算：**

- 数据量：订单明细 10 亿行，日增 300 万，保留 3 年。
- 报表需求：商家日/月 GMV、品类销量 TOP N、小时级订单量、实时大屏 5 分钟延迟。
- 查询量：后台报表 500 QPS，大屏每 10 秒刷新一次。
- 约束：报表查询不能压业务库；T+1 报表允许小时级延迟；实时大屏允许 5 分钟延迟。
- 结论：明细、汇总、应用三层分开，T+1 与实时走两条链路，MySQL 只存结果。

**方案对比：**

| 方案 | 延迟 | 查询能力 | 成本 | 适用 |
| --- | --- | --- | --- | --- |
| MySQL 直接聚合 | 实时 | 弱，大表慢 | 低 | 小数据量 |
| MySQL 预聚合表 | T+1 或小时 | 弱，需预定义维度 | 低 | 固定报表 |
| ClickHouse | 秒级 | 强，适合大宽表 | 中 | 明细分析、大屏 |
| Doris | 秒级 | 强，支持 Join | 中 | 多维分析、实时数仓 |
| Hive + Spark | 小时级 | 最强，成本低 | 低（离线） | T+1 全量报表 |
| Elasticsearch | 秒级 | 全文与聚合 | 高 | 搜索型报表 |

**核心流程：**

```
离线链路：
    1. ODS：业务库 binlog 或每日快照入 Hive
    2. DWD：清洗、去重、维度补全，按日期分区
    3. DWS：按商家、品类、小时预聚合
    4. ADS：面向报表的结果表，同步回 MySQL 供后台查询
实时链路：
    5. 业务库 binlog -> Canal -> Kafka
    6. Flink 按事件时间开 5 分钟窗口聚合
    7. 结果写 Doris/ClickHouse，同时写 Redis 供大屏
查询：
    8. 固定报表查预聚合结果表
    9. 探索式分析查 ClickHouse 明细
    10. 大屏查 Redis，避免每次扫明细
```

**关键实现：**

ClickHouse 用 `SummingMergeTree` 按维度预聚合，后台合并时自动累加数值列：

```sql
CREATE TABLE order_stats (
    stat_date   Date,
    merchant_id UInt64,
    category_id UInt32,
    order_cnt   UInt64,
    gmv         Decimal(18, 2)
) ENGINE = SummingMergeTree()
PARTITION BY toYYYYMM(stat_date)
ORDER BY (stat_date, merchant_id, category_id);
```

每日离线导入只写增量，后台合并完成汇总：

```sql
INSERT INTO order_stats
SELECT
    toDate(create_time) AS stat_date,
    merchant_id,
    category_id,
    count() AS order_cnt,
    sum(amount) AS gmv
FROM order_detail
WHERE toDate(create_time) = '2026-11-02'
GROUP BY stat_date, merchant_id, category_id;
```

报表结果表落到 MySQL，字段与前端查询一一对应，避免运行时聚合：

```sql
CREATE TABLE report_merchant_daily (
    stat_date    DATE         NOT NULL,
    merchant_id  BIGINT       NOT NULL,
    order_cnt    BIGINT       NOT NULL,
    gmv          DECIMAL(18, 2) NOT NULL,
    refund_cnt   BIGINT       NOT NULL,
    updated_at   DATETIME     NOT NULL,
    PRIMARY KEY (stat_date, merchant_id),
    KEY idx_merchant_date (merchant_id, stat_date)
) ENGINE = InnoDB;
```

数据倾斜时先给热点商家加随机盐，再做二阶段聚合：

```sql
-- 第一阶段：加盐打散
SELECT
    merchant_id,
    concat(merchant_id, '_', cast(rand() * 8 AS INT)) AS salt_key,
    sum(amount) AS partial_gmv
FROM order_detail
WHERE stat_date = '2026-11-02'
GROUP BY merchant_id, salt_key;

-- 第二阶段：按商家汇总
SELECT merchant_id, sum(partial_gmv) AS gmv
FROM stage_one
GROUP BY merchant_id;
```

**失败场景与兜底：**

| 失败点 | 现象 | 兜底策略 |
| --- | --- | --- |
| 数据倾斜 | 单个任务卡在 99% | 加盐二阶段聚合、拆分热点 key |
| 迟到数据 | 报表数字偏小 | 事件时间窗口 + 允许延迟，次日重跑 |
| 重复计算 | 同一天数据翻倍 | 按主键幂等写入，分区覆盖而不是追加 |
| 查询扫全表 | 报表超时 | 分区裁剪、预聚合、限制查询时间范围 |
| 实时链路断 | 大屏停更 | 离线结果兜底 + 大屏显示数据时间 |
| 口径不一致 | 报表与业务对不上 | 统一指标定义，落指标字典 |

**面试怎么答：** 先分层：明细层、汇总层、应用层；再分链路：T+1 离线与 5 分钟实时。然后讲引擎选型：固定报表用预聚合，探索分析用 ClickHouse/Doris，全文检索用 ES。最后讲数据倾斜、迟到数据和指标口径，这三点决定报表能不能信。

**易错点：**

- 在 MySQL 上直接 `COUNT(*)` 十亿行，还奇怪为什么慢。
- 用 `COUNT(DISTINCT user_id)` 做超大基数去重，内存直接爆。
- 只建表不分区，查询每次都扫全量。
- 实时与离线两套口径，同一个 GMV 出现两个数字。
- 报表任务失败没有重跑机制，第二天数据永久缺失。

## 3. 主从延迟下的读写策略

**需求澄清与量级估算：**

- 架构：一主两从，写 5000 TPS，读 5 万 QPS，读请求 90% 走从库。
- 延迟：平时 50ms 以内，大促或大事务时可达 2 秒以上。
- 业务影响：用户下单后立即查订单，可能查不到；支付后显示未支付。
- 约束：不能所有读都走主库，否则主库被打爆；也不能假装延迟不存在。
- 结论：区分「读己之写」和「绝对一致」，前者用会话粘滞，后者只能读主。

**方案对比：**

| 方案 | 一致性 | 主库压力 | 复杂度 | 适用 |
| --- | --- | --- | --- | --- |
| 全部读主 | 强 | 极高 | 低 | 极小流量 |
| 全部读从 | 最终 | 低 | 低 | 可容忍延迟的列表页 |
| 半同步复制 | 较强 | 中 | 中 | 不能丢数据的事务 |
| 会话粘滞读主 | 读己之写 | 中 | 中 | 下单后查详情 |
| 延迟阈值切换 | 最终 | 低 | 中 | 从库健康度差异大 |
| GTID 等待 | 强 | 中 | 高 | 必须读到指定位点 |

**核心流程：**

```
写请求：
    1. 写主库，成功后记录 write_ts 与 gtid 到会话或 Redis
    2. 返回给客户端，同时在响应头带一个版本号（可选）
读请求：
    3. 判断是否「读己之写」：同一用户 3 秒内读过自己的写
    4. 是则强制读主库
    5. 否则读从库
从库健康：
    6. 定时采集延迟，超过 1 秒的从库降权或摘除
    7. 延迟恢复后逐步放量，避免瞬间打回
强一致读：
    8. 支付结果、订单详情等关键路径直接读主
    9. 或用 GTID 等待从库追平指定事务
```

**关键实现：**

ShardingSphere 提供强制主库路由的 Hint，适合「写后立即读」的代码块：

```java
public OrderDetail queryAfterCreate(long orderId, long userId) {
    try (HintManager hintManager = HintManager.getInstance()) {
        hintManager.setWriteRouteOnly();
        return orderMapper.selectDetail(orderId, userId);
    }
}
```

用 Redis 记录用户最近写入时间，读请求按时间窗口决定路由：

```java
public void markWrite(long userId) {
    redis.opsForValue().set("rw:lastwrite:" + userId,
        String.valueOf(System.currentTimeMillis()), Duration.ofSeconds(5));
}

public boolean shouldReadMaster(long userId) {
    String ts = redis.opsForValue().get("rw:lastwrite:" + userId);
    if (ts == null) {
        return false;
    }
    return System.currentTimeMillis() - Long.parseLong(ts) < 3000;
}
```

MySQL 半同步复制只能保证「至少一个从库收到 binlog」，不能保证已执行：

```properties
# 主库
rpl_semi_sync_master_enabled=ON
rpl_semi_sync_master_timeout=1000
rpl_semi_sync_master_wait_for_slave_count=1

# 从库
rpl_semi_sync_slave_enabled=ON
```

监控不要只看 `Seconds_Behind_Master`，大事务执行期间它可能显示 0 但实际未追平：

```sql
SHOW REPLICA STATUS\G
-- 关注 Replica_IO_Running、Replica_SQL_Running、Seconds_Behind_Master
-- 更可靠的是 pt-heartbeat 或对比 GTID 集合
```

**失败场景与兜底：**

| 失败点 | 现象 | 兜底策略 |
| --- | --- | --- |
| 写后读从 | 刚创建的订单查不到 | 会话粘滞 3 秒读主，或前端延迟刷新 |
| 主库被打爆 | 所有读切主后雪崩 | 只对关键读切主，其余降级为缓存 |
| 从库延迟突增 | 列表页数据旧 | 延迟阈值摘除 + 告警，不自动全切主 |
| 半同步超时 | 写请求变慢 | 超时后退化为异步，同时告警 |
| 主从切换 | 新主数据缺失 | 切换前确认 GTID 追平，切换后校验 |
| 大事务 | 从库延迟数分钟 | 拆分大事务，开启并行复制 |

**面试怎么答：** 先区分一致性需求：列表页可以读从，订单详情与支付结果必须读主。再讲「读己之写」的实现：会话时间戳、强制主库、GTID 等待。最后讲从库健康管理：延迟监控、摘除降权、半同步与并行复制，强调不能靠 `sleep` 解决。

**易错点：**

- 所有读都走主库，以为能解决延迟，结果主库先挂。
- 用 `Seconds_Behind_Master` 判断延迟，大事务时严重失真。
- 写完 `Thread.sleep(100ms)` 再读，延迟 2 秒时照样读不到。
- 半同步当成强同步，忽略超时降级为异步。
- 从库延迟后直接摘除，没有恢复后的逐步放量。

## 4. 热点 key 与缓存一致性

**需求澄清与量级估算：**

- 场景：商品详情页 50 万 QPS，头部商品单 key 10 万 QPS，库存与价格频繁更新。
- 缓存：Redis 集群 6 主 6 从，本地缓存可选。
- 一致性要求：价格与库存允许秒级延迟，但绝不能长时间读到旧值。
- 热点问题：单 key 打到一个分片，分片 CPU 打满，其他分片空闲。
- 结论：一致性用 Cache Aside + 删除 + 过期兜底；热点用本地缓存 + key 打散。

**方案对比：**

| 方案 | 一致性 | 性能 | 复杂度 | 说明 |
| --- | --- | --- | --- | --- |
| Cache Aside | 中 | 高 | 低 | 主流，读回填、写删除 |
| 双写缓存 | 中 | 高 | 低 | 并发写容易产生脏数据 |
| 延迟双删 | 较高 | 高 | 中 | 降低旧值回填窗口 |
| binlog 订阅删除 | 较高 | 高 | 中 | 解耦业务、最终一致 |
| 本地缓存 + 广播失效 | 中 | 极高 | 中 | 热点 key 首选 |

**核心流程：**

```
读：
    1. 查本地缓存，命中直接返回
    2. 未命中查 Redis，命中则回填本地并返回
    3. Redis 未命中，加互斥锁回源数据库
    4. 回源结果写 Redis，设置随机 TTL，防止同时过期
写：
    5. 先更新数据库，事务提交成功
    6. 删除 Redis key，而不是更新缓存
    7. 发送本地缓存失效广播
    8. 可选：500ms 后再次删除，覆盖并发读回填的旧值
热点：
    9. 单 key 超过阈值时，key 加随机后缀拆成 16 份
    10. 读时随机选一个后缀，写时删除所有后缀
```

**关键实现：**

Cache Aside 的读路径要处理缓存击穿，用互斥锁保证只有一个线程回源：

```java
public Product getProduct(long productId) {
    String key = "product:" + productId;
    Product local = localCache.getIfPresent(key);
    if (local != null) {
        return local;
    }
    String json = redis.opsForValue().get(key);
    if (json != null) {
        Product product = JSON.parseObject(json, Product.class);
        localCache.put(key, product);
        return product;
    }
    return loadWithMutex(key, productId);
}
private Product loadWithMutex(String key, long productId) {
    String lockKey = "lock:" + key;
    boolean locked = redis.opsForValue().setIfAbsent(lockKey, "1", Duration.ofSeconds(10));
    try {
        if (!locked) {
            sleepQuietly(50);
            return getProduct(productId);
        }
        Product product = productMapper.selectById(productId);
        if (product == null) {
            redis.opsForValue().set(key, "NULL", Duration.ofMinutes(2));
            return null;
        }
        long ttl = 1800 + ThreadLocalRandom.current().nextInt(120);
        redis.opsForValue().set(key, JSON.toJSONString(product), Duration.ofSeconds(ttl));
        return product;
    } finally {
        if (locked) {
            redis.delete(lockKey);
        }
    }
}
```

写路径必须先落库再删缓存，顺序反了会长期脏数据：

```java
    productMapper.updatePrice(productId, price);
    afterCommit(() -> {
        redis.delete("product:" + productId);
        redisTemplate.convertAndSend("cache:invalidate", "product:" + productId);
    });
}
```

热点 key 打散，读时随机选后缀，写时全删：

```java

    return "product:" + productId + ":" + ThreadLocalRandom.current().nextInt(HOT_KEY_SPLITS);
}
public void invalidateHot(long productId) {
    for (int i = 0; i < HOT_KEY_SPLITS; i++) {

    }
```

**失败场景与兜底：**

| 失败点 | 现象 | 兜底策略 |
| --- | --- | --- |
| 先删缓存再更新库 | 并发读回填旧值 | 改为先更新库再删缓存 |
| 删除失败 | 缓存长期是旧值 | 重试 + binlog 补偿 + TTL 兜底 |
| 缓存击穿 | 热点 key 失效瞬间打穿 DB | 互斥锁、逻辑过期、预热 |
| 缓存穿透 | 查不存在的数据 | 空值缓存、布隆过滤器、参数校验 |
| 缓存雪崩 | 大量 key 同时过期 | 随机 TTL、多级缓存、限流降级 |
| 热点 key | 单分片 CPU 打满 | 本地缓存 + key 打散 + 读写分离 |

**面试怎么答：** 先明确「缓存一致性是概率问题，不是强一致」。然后讲 Cache Aside 的标准顺序：读回填、写删除、先库后缓存。再讲延迟双删的适用场景与局限，最后讲热点 key 的两种处理：本地缓存挡住读、key 打散拆开写。

**易错点：**

- 更新数据库后更新缓存，并发写导致缓存值互相覆盖。
- 先删缓存再更新数据库，读请求把旧值回填，长期不一致。
- 热点 key 只加本地缓存不广播失效，多实例读到不同价格。

## 5. 大事务拆分与锁等待

**需求澄清与量级估算：**

- 场景：批量导入 10 万用户、批量更新 5 万订单状态、月底结算跑批。
- 现状：单事务执行 30 秒，锁等待报警，从库延迟 2 分钟。
- 数据：单批最多 10 万行，单行更新约 50 字节。
- 约束：不能长时间持有行锁；失败要能断点续跑；不能产生半成品数据。
- 结论：大事务必须拆成「小批事务 + 幂等 + checkpoint」，并能观测进度。

**方案对比：**

| 方案 | 锁持有时间 | 失败恢复 | 复杂度 | 适用 |
| --- | --- | --- | --- | --- |
| 单一大事务 | 长 | 全部回滚 | 低 | 数据量很小 |
| 分批提交 | 短 | 从断点继续 | 中 | 批量导入、批量更新 |
| 异步任务 + 批次表 | 短 | 可重试 | 中高 | 长耗时跑批 |
| 消息队列逐条处理 | 极短 | 天然重试 | 中 | 事件驱动 |
| 数据库游标 | 短 | 需记录位置 | 中 | 大数据量扫描 |

**核心流程：**

```
1. 任务开始时写入 job_progress，记录 total 与 cursor
2. 按主键区间或游标取一批，每批 1000 到 5000 行
3. 每批开启独立事务，执行业务更新
4. 事务成功后更新 cursor，提交进度
5. 失败则重试当前批，超过 3 次标记失败并告警
6. 全部完成后更新任务状态，触发后置动作
7. 定时任务扫描超时未完成的任务，从 cursor 继续
```

**关键实现：**

按主键区间分批，避免 `LIMIT offset` 越翻越慢：

```sql
UPDATE user_profile
SET status = 1, updated_at = NOW()
WHERE id >= 100000
    AND id < 101000
    AND status = 0;
```

Java 侧每批独立事务，游标推进与业务更新分开提交：

```java
long cursor = progressMapper.selectCursor(jobId);
while (true) {
    List<Long> ids = userMapper.selectIdsByCursor(cursor, 1000);
    if (ids.isEmpty()) {
        break;
    }
    transactionTemplate.executeWithoutResult(status -> {
        userMapper.batchUpdate(ids);
        progressMapper.updateCursor(jobId, ids.get(ids.size() - 1));
    });
    cursor = ids.get(ids.size() - 1);
}
```

多实例抢任务时用 `SKIP LOCKED`，避免所有实例锁同一批：

```sql
SELECT id
FROM batch_task
WHERE status = 'PENDING'
ORDER BY id
LIMIT 100
FOR UPDATE SKIP LOCKED;
```

事务内禁止调用 RPC，远程超时会把数据库锁一起拖住：

```java
// 错误：事务内调用远程服务
@Transactional
public void settle(long orderId) {
    orderMapper.updateStatus(orderId, "SETTLED");
    riskClient.check(orderId);
}

// 正确：事务只做本地更新，远程调用放到事务提交后
@Transactional
public void settle(long orderId) {
    orderMapper.updateStatus(orderId, "SETTLED");
}

public void afterSettle(long orderId) {
    riskClient.check(orderId);
}
```

**失败场景与兜底：**

| 失败点 | 现象 | 兜底策略 |
| --- | --- | --- |
| 批次部分成功 | 数据半成品 | 每批幂等，进度与业务同事务提交 |
| 死锁 | 事务被回滚 | 固定加锁顺序、缩短事务、捕获后重试 |
| 锁等待超时 | 请求大量失败 | 降低批大小、错峰执行、调整 `innodb_lock_wait_timeout` |
| 进度丢失 | 重启后重复处理 | 进度表持久化，业务更新幂等 |
| binlog 过大 | 从库延迟 | 拆批、控制单批行数、错峰跑批 |
| 任务卡住 | 长时间无进展 | 超时检测 + 告警 + 支持手动重跑 |

**面试怎么答：** 先讲大事务的四宗罪：锁持有时间长、undo log 膨胀、binlog 过大导致主从延迟、回滚成本高。然后给拆分方案：按主键分批、每批独立事务、进度表 checkpoint、业务幂等。最后讲锁等待与死锁：固定顺序、缩短事务、事务内不调用 RPC。

**易错点：**

- 用 `LIMIT offset, size` 分批，翻到后面每批都要扫描前面的行。
- 批次太大，虽然事务短了但单批仍然锁几秒。
- 进度更新与业务更新不在同一事务，崩溃后重复或漏处理。
- 事务内调用 HTTP/RPC，远程超时导致数据库锁长时间不释放。
- 死锁后不重试也不告警，任务静默失败。

## 6. 数据迁移与双写切换

**需求澄清与量级估算：**

- 数据量：订单主表 2 亿行，约 400GB，日增 300 万行。
- 目标：从旧库迁移到新库，停机窗口不超过 5 分钟，迁移期间业务不能停。
- 约束：不能丢数据、不能重复、任何阶段都能回滚。
- 难点：全量迁移期间仍有增量写入；切读后新旧库可能不一致；回滚时新库数据不能丢。
- 结论：迁移的核心是「可验证、可灰度、可回滚」，双写顺序决定回滚风险。

**方案对比：**

| 方案 | 停机时间 | 风险 | 复杂度 | 适用 |
| --- | --- | --- | --- | --- |
| 停机迁移 | 小时级 | 低 | 低 | 小数据量、可停机 |
| 全量 + 增量 + 双写 | 分钟级 | 中 | 高 | 大型在线业务 |
| CDC 同步 + 读灰度 | 分钟级 | 中 | 高 | 不想改业务代码 |
| 影子库 + 比对 | 分钟级 | 低 | 高 | 金融、账务 |
| 新库双活 | 无 | 最高 | 最高 | 长期并行、容灾 |

**核心流程：**

```
1. 建新表，结构与旧表兼容，索引先不建或只建必要索引
2. 全量迁移：按主键分段导出导入，限速避免拖垮旧库
3. 增量同步：Canal 订阅 binlog，实时写入新库
4. 数据校验：行数、主键集合、金额汇总、抽样全字段比对
5. 开启双写：先写旧库，再写新库，失败落补偿表
6. 读灰度：1% 读新库，逐步放量，同时比对返回结果
7. 切写：新库成为主写，旧库降级为备
8. 观察一个完整业务周期后，停止双写与增量同步
9. 旧库保留只读一段时间，确认无回滚需求后下线
```

**关键实现：**

双写顺序必须是「先旧后新」，这样新库写失败时旧库仍是完整数据，回滚不会丢：

```java
public void saveOrder(Order order) {
    oldOrderRepo.save(order);
    try {
        newOrderRepo.save(order);
    } catch (Exception e) {
        log.error("dual write to new db failed, orderNo={}", order.getOrderNo(), e);
        dualWriteRetryRepo.save(order.getOrderNo(), "NEW_DB", e.getMessage());
    }
}
```

全量迁移按主键区间分段，每段独立事务，避免长事务与锁表：

```sql
SELECT id, order_no, user_id, amount, status, created_at
FROM orders
WHERE id >= 10000000
    AND id < 10001000
ORDER BY id;
```

**失败场景与兜底：**

| 失败点 | 现象 | 兜底策略 |
| --- | --- | --- |
| 全量期间新增数据 | 新库缺一段 | 增量同步补，校验按时间范围对齐 |
| 增量延迟 | 新库读不到最新数据 | 监控消费位点，延迟超阈值暂停切读 |
| 双写失败 | 新旧库不一致 | 补偿表 + 定时重放 + 对账 |
| 校验不一致 | 金额或行数对不上 | 差异池逐条修复，未清零不切写 |
| 切写后回滚 | 新库新数据丢失 | 双写保留旧库，回滚期间继续双写 |
| 迁移限速影响线上 | 旧库 CPU 打满 | 按主键分段 + 限流 + 低峰执行 |

**面试怎么答：** 按「全量、增量、校验、双写、灰度读、切写、下线」七步讲，重点说明每一步的退出条件。然后强调双写顺序与回滚预案：先写旧库保证可回滚，新库失败进补偿表。最后讲校验：行数、金额、抽样全字段，三者缺一不可。

**易错点：**

- 先写新库再写旧库，回滚时新库数据全部丢失。
- 只校验行数，金额与状态字段错乱完全发现不了。
- 全量迁移不限速，把线上旧库 CPU 打满。
- 增量同步延迟还没追平就切读，用户读到旧数据。
- 切写后立刻停双写，发现问题时已经没有回滚数据。

## 7. 多级缓存架构设计

**需求澄清与量级估算：**

- 场景：商品详情 50 万 QPS，Redis 集群安全容量 10 万 QPS，数据库 2 万 QPS。
- 数据特征：头部 1% 商品占 80% 流量，更新频率低但价格与库存敏感。
- 延迟目标：P99 小于 20ms，缓存命中率大于 99%。
- 约束：本地缓存多实例不一致窗口必须可控；Redis 故障不能直接打穿数据库。
- 结论：多级缓存的本质是「用一致性换延迟」，每一层都要有 TTL 与失效广播。

**方案对比：**

| 层级 | 技术 | 命中率 | 一致性 | 作用 |
| --- | --- | --- | --- | --- |
| CDN | 静态资源、详情页 | 高 | 分钟级 | 挡住绝大部分公网流量 |
| 本地缓存 | Caffeine | 极高 | 秒级 | 抗热点 key、降低 Redis 压力 |
| 分布式缓存 | Redis | 高 | 毫秒到秒 | 跨实例共享、容量大 |
| 数据库 | MySQL | 最终来源 | 强 | 回源与最终账本 |

**核心流程：**

```
读：
    1. 请求先到 CDN，静态资源直接返回
    2. 未命中到应用，查本地缓存 Caffeine
    3. 本地未命中查 Redis
    4. Redis 未命中回源数据库，回填 Redis 与本地
写：
    5. 更新数据库并提交事务
    6. 删除 Redis key
    7. 通过 Pub/Sub 广播失效消息
    8. 所有实例收到后删除本地缓存
    9. 本地缓存保留短 TTL，作为广播丢失的兜底
```

**关键实现：**

Caffeine 本地缓存设置较小的容量与短 TTL，避免堆内存膨胀与长期不一致：

```java
private final Cache<String, Product> localCache = Caffeine.newBuilder()
    .maximumSize(10_000)
    .expireAfterWrite(Duration.ofSeconds(10))
    .recordStats()
    .build();
```

Redis 作为第二级，TTL 加随机值，防止大面积同时失效：

```java
public void putRedis(String key, Product product) {
    long ttl = 1800 + ThreadLocalRandom.current().nextLong(0, 120);
    redis.opsForValue().set(key, JSON.toJSONString(product), Duration.ofSeconds(ttl));
}
```

Spring Data Redis 的 Pub/Sub 监听，收到消息后只删本地缓存：

```java
@Bean

    RedisMessageListenerContainer container = new RedisMessageListenerContainer();
    container.setConnectionFactory(factory);
    container.addMessageListener((message, pattern) -> {
        String key = new String(message.getBody(), StandardCharsets.UTF_8);

```

更新后广播失效，注意要在事务提交后发送，否则其他实例可能回源到旧数据：

```java

    TransactionSynchronizationManager.registerSynchronization(new TransactionSynchronization() {
        @Override
        public void afterCommit() {

```

Redis 故障时用本地缓存 + 限流兜底，避免所有请求直接回源：

```java

    Product local = localCache.getIfPresent("product:" + productId);
    if (local != null) {
        return local;
    }
    if (!circuitBreaker.allowRequest()) {
        throw new BizException("CACHE_UNAVAILABLE", "系统繁忙，请稍后重试");
    }
    return loadFromDb(productId);

```

**失败场景与兜底：**

| 失败点 | 现象 | 兜底策略 |
| --- | --- | --- |
| 广播丢失 | 本地缓存长期旧值 | 本地短 TTL + 定时全量刷新版本号 |
| 本地缓存过大 | GC 频繁、内存溢出 | 限制 maximumSize，按热度淘汰 |
| Redis 热 key | 单分片 CPU 打满 | 本地缓存 + key 打散 + 读写分离 |
| Redis 故障 | 全部回源打穿 DB | 熔断 + 限流 + 静态兜底 |
| 缓存穿透 | 大量不存在的 ID | 空值缓存 + 布隆过滤器 |
| 更新与失效乱序 | 旧值覆盖新值 | 先库后删 + 版本号 + 延迟双删 |

**面试怎么答：** 先画四层：CDN、本地、Redis、数据库，说明每层解决什么问题。再讲一致性：更新数据库后删 Redis、广播本地失效、短 TTL 兜底。最后讲故障：Redis 挂了不能直接打 DB，要熔断限流；本地缓存不能无限大，要限制容量。

**易错点：**

- 本地缓存 TTL 设成几小时，多实例价格长期不一致。
- 只删 Redis 不广播本地，热点商品在多个实例读到不同价格。
- 本地缓存无容量上限，热点数据把堆内存撑爆。
- 事务未提交就发失效消息，其他实例回源读到旧值又回填。
- 认为多级缓存能保证强一致，账务类数据也往里塞。

## 8. RAG 召回不准的调优

**需求澄清与量级估算：**

- 数据：10 万篇文档，切分后约 50 万 chunk，平均每篇 5 个 chunk。
- 查询：日均 10 万次问答，TopK 取 5，上下文预算 3000 token。
- 现状：人工抽检 100 条，回答正确率 62%，其中 70% 的错误是「没召回正确文档」。
- 目标：recall@5 从 0.62 提升到 0.85 以上，答案准确率提升到 80%。
- 结论：先判断是召回问题还是生成问题，再分「切分、检索、重排、生成」四层优化。

**问题定位：**

| 现象 | 可能原因 | 验证方法 |
| --- | --- | --- |
| 答案完全无关 | 召回为空或全是噪声 | 看 TopK 文档与问题相关性 |
| 答案部分正确 | 召回有正确文档但排名靠后 | 看正确文档的 rank 与分数 |
| 答案与文档矛盾 | 生成阶段幻觉 | 固定召回结果，只换 prompt |
| 多轮后答错 | query 指代未消解 | 用改写后的 query 再检索 |
| 权限内文档查不到 | 元数据过滤过严 | 检查 ACL 与过滤条件 |

**方案对比：**

| 优化点 | 手段 | 提升幅度 | 成本 |
| --- | --- | --- | --- |
| 切分 | 语义切分、父子块、512 token + overlap | 中 | 低 |
| 查询 | 多 query 改写、HyDE、指代消解 | 中高 | 中 |
| 召回 | 向量 + BM25 混合 | 高 | 中 |
| 融合 | RRF 融合多路结果 | 中 | 低 |
| 重排 | Cross-Encoder rerank | 高 | 中高（延迟） |
| 生成 | 引用约束、拒答策略、上下文压缩 | 中 | 低 |

**核心流程：**

```
离线：
    1. 解析文档，保留标题、章节、生效时间、权限等元数据
    2. 按语义边界切分，单块 512 token，重叠 64 token
    3. 用 embedding 模型生成向量，写入向量库
    4. 同时构建 BM25 倒排索引
在线：
    5. 多轮对话先做指代消解与 query 改写
    6. 向量召回 Top 50，BM25 召回 Top 50
    7. RRF 融合两路结果，取 Top 20
    8. Cross-Encoder rerank，取 Top 5
    9. 按权限与时效过滤，组装带引用的上下文
    10. 生成答案，要求引用文档 ID，无法回答时明确拒答
```

**关键实现：**

混合召回用 RRF 融合，不需要归一化两路分数，工程上最稳：

```python
def hybrid_search(query, top_k=5, rrf_k=60):
    vector_hits = vector_store.search(query, top_k=50)
    bm25_hits = bm25_index.search(query, top_k=50)
    scores = {}
    doc_map = {}
    for rank, doc in enumerate(vector_hits):
        doc_map[doc.id] = doc
        scores[doc.id] = scores.get(doc.id, 0.0) + 1.0 / (rrf_k + rank + 1)
    for rank, doc in enumerate(bm25_hits):
        doc_map[doc.id] = doc
        scores[doc.id] = scores.get(doc.id, 0.0) + 1.0 / (rrf_k + rank + 1)
    candidates = sorted(scores.items(), key=lambda item: item[1], reverse=True)[:20]
    return rerank(query, [doc_map[doc_id] for doc_id, _ in candidates], top_n=top_k)
```

父子块检索：用小块做向量匹配，命中后返回大块给模型，兼顾精度与上下文：

```python
def retrieve_with_parent(query, top_k=5):
    child_hits = vector_store.search(query, top_k=20)
    parent_ids = list({hit.metadata["parent_id"] for hit in child_hits})
    parents = parent_store.get_many(parent_ids)
    ranked = rerank(query, parents, top_n=top_k)
    return ranked
```

**失败场景与兜底：**

| 失败点 | 现象 | 兜底策略 |
| --- | --- | --- |
| 切分断裂 | 答案被切成两半 | 语义切分 + overlap + 父子块 |
| 召回为空 | 模型自由发挥 | 相似度阈值 + 明确拒答 |
| 排序不准 | 正确文档排第 8 | rerank + 提高召回数量 |
| 多轮指代 | 「它」指哪本书不清楚 | query 改写 + 对话摘要 |
| 权限泄漏 | 检索到其他租户文档 | 召回阶段强制 ACL 过滤 |
| 上下文超限 | 截断后丢失关键段 | 压缩上下文 + 按相关性排序 |

**面试怎么答：** 先定位问题：把「召回」和「生成」分开评估，分别看 recall@5 与答案正确率。然后按切分、查询改写、混合召回、rerank、生成约束五层讲优化。最后强调评估集：没有 100 到 200 条标注数据，所有调优都是拍脑袋。

**易错点：**

- 一上来就调 prompt，明明是召回没找到正确文档。
- chunk 切得太大，一个块混多个主题，向量被平均成噪声。
- chunk 切得太小，缺少上下文，模型断章取义。
- 只用向量召回，专有名词与编号查询明显不如 BM25。
- 先召回再按权限过滤，等于把无权文档送进了模型上下文。

## 9. Agent 工具调用失败与超时

**需求澄清与量级估算：**

- 场景：Agent 接入 20 个工具，包括查订单、查物流、退款、发券，单次任务平均 3 到 5 步。
- 流量：日均 10 万次任务，工具调用 50 万次，P99 目标 3 秒。
- 现状：工具失败率 5%，其中超时占 60%，参数错误占 20%，下游 5xx 占 20%。
- 约束：失败不能中断整个任务；非幂等工具不能随便重试；不能无限循环调用。
- 结论：Agent 可靠性等于「工具契约 + 超时重试 + 熔断降级 + 幂等 + 步数上限」。

**方案对比（按失败类型）：**

| 失败类型 | 是否重试 | 策略 | 示例 |
| --- | --- | --- | --- |
| 网络超时 | 是，幂等工具 | 指数退避，最多 2 次 | 查物流 |
| 下游 5xx | 是，幂等工具 | 退避 + 熔断 | 查订单 |
| 参数校验失败 | 否 | 把结构化错误返回给模型修正 | 日期格式错 |
| 权限不足 | 否 | 终止该工具，提示用户授权 | 无退款权限 |
| 业务拒绝 | 否 | 原样返回业务码，让模型解释 | 订单已发货不能退 |
| 非幂等超时 | 不盲目重试 | 先查询执行结果，再决定 | 退款、发券 |

**核心流程：**

```
1. 模型输出 tool_calls，先做 JSON Schema 校验
2. 校验业务参数与用户权限，不通过则把错误返回给模型
3. 调用工具：设置 2 秒超时，记录 trace_id 与幂等键
4. 可重试错误：指数退避重试，最多 2 次
5. 仍失败：返回结构化错误，模型可换工具或换参数
6. 同一工具连续失败 5 次：熔断 30 秒，走备用方案
7. 整个任务最多 10 步，超过则终止并返回已完成部分
8. 全程记录每步输入、输出、耗时、错误码
```

**关键实现：**

工具定义必须用 JSON Schema 约束参数，减少模型瞎编：


带超时与重试的调用封装，只有幂等工具才自动重试：

```python
async def call_tool(name, args, trace_id, user):
    tool = registry[name]
    validate_args(tool.schema, args)
    if not tool.idempotent:
        args["idempotency_key"] = f"{trace_id}:{name}"
    last_error = None
    for attempt in range(3):
        try:
            async with asyncio.timeout(tool.timeout_seconds):
                return await tool.invoke(args, user)
        except (TimeoutError, TransientError) as e:
            last_error = e
            if attempt == 2:
                break
            await asyncio.sleep(0.5 * (2 ** attempt) + random.random() * 0.2)
    raise ToolError(
        code="TOOL_UNAVAILABLE",
        retryable=True,
        message=str(last_error),
        suggestion="请稍后重试，或改用 query_logistics 工具",
    )
```

熔断器避免对已经挂掉的下游持续打请求：

```python
class CircuitBreaker:
    def __init__(self, threshold=5, cooldown=30):
        self.threshold = threshold
        self.cooldown = cooldown
        self.failures = 0
        self.opened_at = 0.0
        self.half_open = False

    def allow(self):
        if self.failures < self.threshold:
            return True
        if time.time() - self.opened_at < self.cooldown:
            return False
        self.half_open = True
        return True

    def record(self, success):
        if success:
            self.failures = 0
            self.half_open = False
        else:
            self.failures += 1
            if self.failures >= self.threshold:
                self.opened_at = time.time()
```

把错误结构化返回给模型，而不是抛一段自然语言，模型才能正确决策。

**失败场景与兜底：**

| 失败点 | 现象 | 兜底策略 |
| --- | --- | --- |
| 工具超时 | 任务卡住 | 单工具 2 秒超时，整体任务 15 秒上限 |
| 非幂等重试 | 重复退款、重复发券 | 幂等键 + 先查执行结果再重试 |
| 无限循环 | 模型反复调用同一工具 | 最大步数 + 相同参数重复检测 |
| 参数错误 | 模型编造订单号 | JSON Schema + 业务校验 + 错误回传 |
| 下游熔断 | 所有调用失败 | 备用工具、缓存结果、转人工 |
| 上下文爆炸 | token 超限、成本飙升 | 截断工具返回、只保留关键字段 |

**面试怎么答：** 先按失败类型分类：可重试、不可重试、需要先查询结果。然后讲四层保护：Schema 校验、超时重试、熔断降级、步数与成本上限。最后强调非幂等工具的幂等键，以及把错误结构化返回给模型，让它自己换路径。

**易错点：**

- 对所有工具统一重试 3 次，退款接口直接重复退款。
- 只设 HTTP 超时，不设模型思考与整体任务超时。
- 工具错误返回一段中文，模型看不懂，继续原样重试。
- 没有最大步数，模型在两个工具之间来回调用直到 token 耗尽。
- 工具返回整个 JSON，几十 KB 塞进上下文，成本和延迟都爆炸。

## 10. 大模型成本与延迟优化

**需求澄清与量级估算：**

- 规模：日均 100 万次调用，平均输入 1500 token，输出 300 token。
- 目标：P95 首 token 小于 1 秒，P95 总延迟小于 3 秒；单位成本下降 40%。
- 现状：80% 请求是简单问答，20% 需要多步推理，但全部走同一个大模型。
- 成本构成：输入 token、输出 token、缓存未命中、重试与无效调用。
- 结论：成本和延迟要分开优化，先路由与缓存，再压缩上下文，最后才考虑换模型。

**方案对比：**

| 手段 | 成本影响 | 延迟影响 | 质量风险 | 实施难度 |
| --- | --- | --- | --- | --- |
| 模型路由 | 高 | 高 | 低 | 中 |
| 精确缓存 | 高 | 高 | 无 | 低 |
| 语义缓存 | 高 | 高 | 中 | 中 |
| Prompt 压缩 | 中 | 中 | 中 | 低 |
| 限制 `max_tokens` | 中 | 中 | 低 | 低 |
| 流式输出 | 无 | 首 token 明显 | 无 | 低 |
| 批处理接口 | 高 | 变慢 | 无 | 低 |
| 蒸馏小模型 | 高 | 高 | 中 | 高 |
| 量化部署 | 高 | 高 | 中 | 高 |

**核心流程：**

```
1. 请求进入后先做意图分类：简单问答、知识检索、多步推理、代码生成
2. 简单问答走小模型，复杂任务走大模型，超长上下文单独计费
3. 先查精确缓存（query + 参数 hash），命中直接返回
4. 未命中查语义缓存，相似度阈值 0.92 以上才复用
5. 组装上下文：只保留相关片段，历史对话做摘要
6. 设置 max_tokens，要求结构化输出，减少废话
7. 流式返回首 token，前端先展示，降低感知延迟
8. 离线任务走批处理接口，非实时场景不占在线配额
9. 监控 token 数、缓存命中率、P95、单请求成本
```

**关键实现：**

按意图路由，不要让所有请求都走最贵的模型：

**失败场景与兜底：**

| 失败点 | 现象 | 兜底策略 |
| --- | --- | --- |
| 小模型质量不够 | 答非所问、格式错 | 置信度低时升级到大模型重试一次 |
| 语义缓存错配 | 答非所问 | 提高阈值、按租户隔离、关键问题禁用 |
| 上下文过长 | 成本高、延迟高 | 检索 TopK 限制、摘要、分段处理 |
| 输出过长 | 成本失控 | `max_tokens` + 结构化输出 + 停止词 |
| 限流 429 | 请求失败 | 队列排队 + 指数退避 + 多供应商切换 |
| 流式中断 | 用户看到半句话 | 前端标记未完成，支持重试与续写 |

**面试怎么答：** 先把成本拆成「输入 token、输出 token、缓存、重试」，把延迟拆成「排队、首 token、生成」。然后按性价比排序讲优化：路由与缓存最先做，Prompt 压缩与 `max_tokens` 次之，蒸馏与量化最后。强调流式只改感知延迟，批处理只适合离线。

**易错点：**

- 只看模型单价，不看输入输出 token 数与平均上下文长度。
- 语义缓存阈值过低，把相似但不同的问题答案复用。
- 为了省成本把 `max_tokens` 设得很小，结果答案被截断。
- 所有请求都上大模型，80% 的简单问答白白多花钱。
- 只优化平均延迟，忽略 P95 与首 token 时间。
