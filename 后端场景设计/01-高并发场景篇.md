## 1. 设计秒杀系统

**需求澄清与量级估算：**

- 业务形态：整点开抢，单 SKU 库存 1000 件，参与用户 100 万，流量集中在开抢后 10 秒。
- 读请求：商品详情与活动状态约 50 万 QPS，其中 90% 可以静态化到 CDN。
- 写请求：下单峰值 10 万 QPS，最终有效订单只有 1000 个，99% 的请求应在靠前层被过滤；不超卖是硬约束，不少卖靠对账修复，一人一单，30 分钟未支付回补。
- 容量结论：Redis 单分片大约 1 万到 2 万 QPS，10 万 QPS 需要 8 到 16 个分片；数据库只承接 1000 次真实写，不能作为第一道扣减。

**方案对比：**

| 方案 | 一致性 | 吞吐 | 复杂度 | 适用场景 |
| --- | --- | --- | --- | --- |
| 数据库行锁扣减 | 强 | 低，单行锁串行 | 低 | 库存少、流量小 |
| 数据库条件更新 | 强 | 中 | 低 | 最终扣减与兜底 |
| Redis 预扣 + MQ 异步下单 | 最终一致 | 高 | 中 | 主流秒杀 |
| 令牌 + 本地库存 | 最终一致 | 极高 | 高 | 超大流量、可接受少卖 |

**核心流程：**

```
活动前 10 分钟：
    1. 库存预热：SET seckill:stock:{skuId} 1000，活动信息写入本地缓存
    2. 详情页静态化推 CDN，接口只暴露活动状态与开始时间
    3. 压测确认 Redis 分片、MQ 分区与消费能力
开抢瞬间：
    4. 网关按 uid 限流 1 次/秒，同时设置全局 10 万 QPS 令牌桶
    5. 校验活动时间、风控黑名单、一人一单
    6. Redis Lua 原子扣减库存并记录购买资格
    7. 扣减成功发送 MQ 消息，立即返回「排队中」与 orderToken
    8. 消费端幂等建单，数据库条件更新作为最终兜底
    9. 30 分钟未支付，延迟消息关单并回补库存
```

**关键实现：**

```lua
-- KEYS[1] = seckill:stock:{skuId}
-- KEYS[2] = seckill:users:{skuId}
-- ARGV[1] = userId
-- ARGV[2] = 扣减数量
if redis.call('EXISTS', KEYS[1]) == 0 then
    return -1
end
if redis.call('SISMEMBER', KEYS[2], ARGV[1]) == 1 then
    return -2
end
local stock = tonumber(redis.call('GET', KEYS[1]))
if stock < tonumber(ARGV[2]) then
    return 0
end
redis.call('DECRBY', KEYS[1], ARGV[2])
redis.call('SADD', KEYS[2], ARGV[1])
return 1
```

Java 侧按返回值区分状态，只有扣减成功才发消息；发送失败必须把资格回补，否则会出现「占了名额却永远不下单」：

```java
public SeckillResult seckill(long skuId, long userId) {
    String stockKey = "seckill:stock:" + skuId;
    String userKey = "seckill:users:" + skuId;
    Long code = redis.execute(
        SECKILL_SCRIPT,
        Arrays.asList(stockKey, userKey),
        String.valueOf(userId),
        "1"
    );
    if (code == null || code == -1L) {
        return SeckillResult.notStarted();
    }
    if (code == -2L) {
        return SeckillResult.duplicated();
    }
    if (code == 0L) {
        return SeckillResult.soldOut();
    }
    String orderToken = UUID.randomUUID().toString().replace("-", "");
    rocketMQTemplate.asyncSend("seckill-order", new SeckillMessage(skuId, userId, orderToken), new SendCallback() {
        @Override
        public void onSuccess(SendResult sendResult) {
            log.info("seckill message sent, userId={}", userId);
        }
        @Override
        public void onException(Throwable e) {
            rollbackQualification(stockKey, userKey, userId);
        }
    });
    return SeckillResult.queued(orderToken);
}
```

消费端不信任 Redis，落库时用唯一索引兜底：

```sql
CREATE TABLE seckill_order (
    id          BIGINT       NOT NULL AUTO_INCREMENT,
    order_no    VARCHAR(32)  NOT NULL,
    user_id     BIGINT       NOT NULL,
    sku_id      BIGINT       NOT NULL,
    status      TINYINT      NOT NULL DEFAULT 0,
    created_at  DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (id),
    UNIQUE KEY uk_user_sku (user_id, sku_id),
    UNIQUE KEY uk_order_no (order_no)
) ENGINE = InnoDB;
```

**失败场景与兜底：**

| 失败点 | 现象 | 兜底策略 |
| --- | --- | --- |
| Redis 分片不可用 | 扣减全部失败 | 入口开关直接返回售罄，绝不把流量放给数据库 |
| MQ 发送失败 | 用户有资格但没有订单 | 同步回补库存与用户集合，返回失败让用户重试 |
| MQ 积压 | 下单延迟数分钟 | 消费端批量处理并扩容消费者，前端展示排队号而不是假成功 |
| 重复消费 | 同一用户出现多条订单 | `uk_user_sku` 捕获 `DuplicateKeyException` 后直接确认消息 |
| 少卖 | Redis 剩余与订单数不符 | 活动结束后按库存流水对账，脚本或人工回补 |
| 未支付占用 | 库存被锁死 | 延迟消息关单，回补前用 CAS 改状态，保证只回补一次 |

**面试怎么答：** 按「分层过滤、原子扣减、异步下单、最终对账」四段讲。先算清楚 10 万 QPS 里只有 1000 个有效请求，设计目标是「用最便宜的方式挡掉 99%」，而不是让数据库扛住 10 万。再说明 Redis 与数据库各承担什么职责、MQ 失败如何回补、少卖如何对账。

**易错点：**

- 用 `GET` 再 `DECR` 两步扣库存，并发下必然超卖，必须用 Lua 或 `DECRBY` 单命令。
- 只在 Redis 扣减就算下单成功，Redis 重启后订单与库存全部对不上。
- 库存预热后没有活动结束清理，第二天活动沿用旧库存。
- 把 MQ 当成绝对可靠，发送失败不回补，直接造成「有资格无订单」的少卖。

## 2. 订单超时自动关闭

**需求澄清与量级估算：**

- 业务规则：下单后 30 分钟未支付自动关闭，关闭时回补库存、退回优惠券、释放积分冻结。
- 数据量：日均订单 100 万，峰值 3000 TPS，30 分钟窗口内约 60 万笔待支付订单。
- 时间精度：允许 30 秒到 1 分钟的误差，不需要精确到秒。
- 核心约束：不能误关已支付订单；不能重复回补；关单失败必须能补偿。
- 估算结论：30 分钟内 60 万条延迟任务，消息队列与 Redis ZSet 都能承受，关键是「到期任务不能丢」。

**方案对比：**

| 方案 | 精度 | 可靠性 | 成本 | 缺点 |
| --- | --- | --- | --- | --- |
| 定时扫表 | 分钟级 | 高 | 低 | 全表扫描压力大，订单量大时扫不完 |
| Redis ZSet | 秒级 | 中 | 低 | 内存占用，Redis 故障会丢任务 |
| MQ 延迟消息 | 秒级 | 高 | 中 | RocketMQ 4.x 只支持固定延迟级别 |
| RabbitMQ TTL + 死信 | 秒级 | 高 | 中 | 队列级 TTL 需要每条消息单独队列，运维复杂 |
| 时间轮 | 毫秒级 | 中 | 低 | 单机内存态，重启恢复要额外设计 |

**核心流程：**

```
下单成功：
    1. 本地事务写订单，同时写一条延迟消息或 ZSet 任务
    2. 消息携带 orderId 与业务超时时间，不携带金额等可变字段
到期消费：
    3. 查询订单当前状态
    4. 仍为 UNPAID 才执行 CAS 关单
    5. CAS 成功后才回补库存、退券、解冻积分
    6. 已支付或已关闭直接确认消息，不做任何回补
兜底：
    7. 每小时扫一次 created_at 在 29 到 31 分钟前的 UNPAID 订单
    8. 对账任务检查「已关闭但库存未回补」的异常单
```

**关键实现：**

RocketMQ 4.x 的延迟级别是固定的 18 档，30 分钟对应级别 16；5.x 才支持任意时间延迟：

```java
Message message = new Message(
    "order-timeout-topic",
    "CLOSE",
    orderId.getBytes(StandardCharsets.UTF_8)
);
// RocketMQ 4.x: 1s 5s 10s 30s 1m 2m 3m 4m 5m 6m 7m 8m 9m 10m 20m 30m 1h 2h
message.setDelayTimeLevel(16);
producer.send(message);
```

关单必须用状态机 CAS，而不是先查再改：

```sql
UPDATE orders
SET status = 'CLOSED',
    closed_at = NOW()
WHERE order_id = ?
    AND status = 'UNPAID';
```

返回受影响行数为 1 才继续回补；为 0 说明已被支付或已被其他实例关闭。回补动作本身也要幂等，库存表用业务单号去重：

```sql
INSERT INTO stock_rollback_log (order_id, sku_id, quantity, created_at)
VALUES (?, ?, ?, NOW());
-- 依赖 UNIQUE KEY uk_order_sku (order_id, sku_id)，重复插入直接失败
```

如果不用 MQ，Redis ZSet 的实现要点是「先移除再处理」，避免多实例重复消费：

```
ZADD order:delay {deadlineTimestamp} {orderId}
ZRANGEBYSCORE order:delay 0 {now} LIMIT 0 100
ZREM order:delay {orderId}
处理成功后再落一条已处理标记，防止进程崩溃后任务丢失
```

**失败场景与兜底：**

| 失败点 | 现象 | 兜底策略 |
| --- | --- | --- |
| 消息丢失 | 订单永远不关闭 | 定时扫表按创建时间补发，扫表频率 5 分钟 |
| 消费失败 | 消息重试多次进入死信 | 死信队列告警 + 人工或脚本重放 |
| 重复消费 | 库存被回补两次 | CAS 关单 + 回补流水唯一键双重幂等 |
| 用户正在支付 | 关单与支付并发 | 支付回调也走 CAS，只有一方能把状态从 UNPAID 改走 |
| 时钟漂移 | 提前或延后关单 | 以服务端时间为准，deadline 写库而不是依赖消费时刻 |
| 大促延迟 | 消息堆积导致超时不准 | 允许延迟，但必须保证最终关闭，不能漏 |

**面试怎么答：** 先给「延迟消息为主、扫表兜底、CAS 保证状态只迁移一次」的骨架，再对比几种延迟方案。重点讲两个并发边界：关单与支付同时到达怎么办、重复消费如何避免重复回补。最后补一句精度要求，30 分钟业务不需要时间轮这种毫秒级方案。

**易错点：**

- 只依赖定时扫表，订单量上来后一次扫描跑不完，任务持续延后。
- 先回补库存再关单，支付回调插入后会出现「已支付但库存被回补」。
- 用 `SELECT` 判断状态再 `UPDATE`，两个实例同时通过检查。
- 延迟消息只发一次，消费失败进死信后没人处理。
- 关单时间用消费端当前时间判断，消息堆积时会把刚下单的订单误关。

## 3. 接口幂等设计

**需求澄清与量级估算：**

- 场景：下单、支付、退款、回调四类写接口，客户端超时重试 3 次，网关也会重试。
- 流量：下单峰值 5000 TPS，重复请求占比约 3%，大促时能到 10%。
- 约束：同一个业务请求无论到达多少次，结果必须一致，且副作用只发生一次。
- 时间窗口：重试通常发生在 24 小时内，幂等记录至少要覆盖业务最长处理时间。
- 关键区分：幂等不是「防重复提交按钮」，而是服务端对重复请求的最终承诺。

**方案对比：**

| 方案 | 实现方式 | 优点 | 缺点 | 适用 |
| --- | --- | --- | --- | --- |
| 唯一索引 | 业务唯一键落库 | 最强兜底、实现简单 | 只能防插入，防不了更新 | 创建类接口 |
| 幂等 token | 先领 token，再带 token 提交 | 能防重复点击 | 多一次交互 | 下单、支付 |
| 状态机 CAS | 带前置状态的条件更新 | 天然幂等、无额外存储 | 只适用于有状态流转 | 订单、支付 |
| Redis SETNX | 请求 ID 占位 | 性能高、TTL 自动清理 | Redis 故障需降级 | 通用写接口 |
| 幂等表 | 单独记录请求与结果 | 可查结果、可审计 | 多一次写、需要清理 | 金额类核心接口 |

**核心流程：**

```
1. 客户端进入页面前先调用 GET /api/idempotent-token 获取 requestId
2. 提交时把 requestId 放在 Header 或业务字段中
3. 服务端 SETNX idem:{scene}:{requestId}，value 先写 PROCESSING，TTL 24 小时
4. 占位成功：执行业务，成功后把结果写回同一个 key
5. 占位失败：读取 value，PROCESSING 返回「处理中」，已有结果直接返回结果
6. 数据库唯一索引作为最后一道防线
7. 业务明确失败时删除 key，允许用户修正参数后重试
```

**关键实现：**

Redis 占位与结果回写要注意「业务失败」和「系统异常」的处理差异：

```java
public OrderResult createOrder(CreateOrderCmd cmd) {
    String key = "idem:order:" + cmd.getRequestId();
    Boolean locked = redis.opsForValue().setIfAbsent(key, "PROCESSING", Duration.ofHours(24));
    if (Boolean.FALSE.equals(locked)) {
        String value = redis.opsForValue().get(key);
        if ("PROCESSING".equals(value)) {
            throw new BizException("ORDER_PROCESSING", "请求处理中，请勿重复提交");
        }
        return JSON.parseObject(value, OrderResult.class);
    }
    try {
        OrderResult result = doCreateOrder(cmd);
        redis.opsForValue().set(key, JSON.toJSONString(result), Duration.ofHours(24));
        return result;
    } catch (BizException e) {
        // 参数类业务失败允许重试，释放占位
        redis.delete(key);
        throw e;
    } catch (Exception e) {
        // 系统异常保留 PROCESSING 由补偿任务处理，避免重复下单
        throw e;
    }
}
```

数据库唯一索引是 Redis 挂掉后的兜底：

```sql
CREATE TABLE order_idempotent (
    scene       VARCHAR(32) NOT NULL,
    biz_no      VARCHAR(64) NOT NULL,
    status      TINYINT     NOT NULL,
    result      JSON        NULL,
    created_at  DATETIME    NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (scene, biz_no),
    KEY idx_created (created_at)
) ENGINE = InnoDB;
```

创建订单时同时写业务唯一键，捕获重复键异常后查询已有结果返回，而不是把异常抛给用户：

```java
try {
    orderMapper.insert(order);
} catch (DuplicateKeyException e) {
    Order existing = orderMapper.selectByOrderNo(order.getOrderNo());
    return OrderResult.from(existing);
}
```

**失败场景与兜底：**

| 失败点 | 现象 | 兜底策略 |
| --- | --- | --- |
| Redis 不可用 | 所有请求都放行 | 降级到数据库唯一索引，同时入口限流保护数据库 |
| 并发同 key | 两个线程都看到 PROCESSING | 后到者快速失败并提示，不阻塞等待 |
| 占位后进程崩溃 | key 永远是 PROCESSING | 记录开始时间，超过阈值允许补偿任务清理 |
| TTL 短于业务耗时 | 处理中 key 过期，重复请求进来 | TTL 必须大于最大处理时间，至少 24 小时 |
| key 生成不稳定 | 同一请求算出不同 key | 用客户端 requestId 或业务唯一号，不要用参数 hash |
| 更新类接口 | 唯一索引防不住重复更新 | 用状态机 CAS 或版本号，不用「先查后改」 |

**面试怎么答：** 先给定义：幂等是「同一请求重复到达，结果一致且副作用只发生一次」。再按「唯一标识、去重存储、业务兜底」三层讲，举下单和支付两个例子分别说明创建类与状态流转类的不同做法。最后强调 Redis 只是性能层，数据库唯一约束才是最终一致性保障。

**易错点：**

- 用请求参数的 MD5 当幂等键，参数顺序、时间戳、空值都会导致同一业务算出不同 key。
- 先执行业务再写幂等记录，进程在中间崩溃后重复请求会再次执行。
- 只在网关做幂等，绕过网关的内部调用仍然重复。
- 业务失败也删除占位，用户连续点三次就产生三笔订单。
- 认为「加了分布式锁就等于幂等」，锁释放后重复请求仍会执行。

## 4. 分布式事务方案选型

**需求澄清与量级估算：**

- 场景：下单需要同时扣库存、锁优惠券、加积分，三个服务各自独立库。
- 流量：峰值 3000 TPS，允许秒级最终一致，不允许少卖、多扣、重复加积分。
- 约束：跨服务无法用本地事务；强一致会显著降低吞吐；必须能对账和人工修复。
- 估算结论：99% 的请求走「最终一致」方案，资金类核心链路才考虑 TCC；XA 不适合高并发。
- 选型原则：能本地事务解决就不要跨服务；必须跨服务时优先「本地消息表 / 事务消息」。

**方案对比：**

| 方案 | 一致性 | 性能 | 侵入性 | 适用场景 |
| --- | --- | --- | --- | --- |
| 2PC / XA | 强一致 | 低，事务期间锁资源 | 低 | 传统银行、低频核心交易 |
| TCC | 强一致（最终） | 中 | 高，每个服务写 Try/Confirm/Cancel | 资金、库存预占 |
| Saga | 最终一致 | 高 | 中，需要补偿接口 | 长流程、跨多服务 |
| 本地消息表 | 最终一致 | 高 | 中 | 订单后置动作 |
| RocketMQ 事务消息 | 最终一致 | 高 | 中 | 已有 RocketMQ 的团队 |
| 最大努力通知 | 最终一致 | 高 | 低 | 外部渠道回调、通知类 |

**核心流程：**

以 RocketMQ 事务消息为例，保证「本地事务成功」与「消息可投递」的一致性：

```
1. 生产者发送 half message，Broker 持久化但不投递
2. Broker 返回成功，生产者执行本地事务（写订单）
3. 本地事务成功：提交 half message，Broker 投递给库存、积分消费者
4. 本地事务失败：回滚 half message，消息不投递
5. 消费者执行本地事务并返回结果，失败则重试
6. Broker 定时回查长时间未决的 half message，生产者按订单是否存在决定提交或回滚
7. 消费仍失败进入死信，由补偿任务或人工处理
```

**关键实现：**

事务消息的生产者需要实现本地事务与回查：

```java
TransactionMQProducer producer = new TransactionMQProducer("order-tx-group");
producer.setNamesrvAddr("rocketmq1:9876;rocketmq2:9876");
producer.setTransactionListener(new TransactionListener() {
    @Override
    public LocalTransactionState executeLocalTransaction(Message msg, Object arg) {
        try {
            orderService.createOrder((CreateOrderCmd) arg);
            return LocalTransactionState.COMMIT_MESSAGE;
        } catch (BizException e) {
            return LocalTransactionState.ROLLBACK_MESSAGE;
        } catch (Exception e) {
            return LocalTransactionState.UNKNOW;
        }
    }

    @Override
    public LocalTransactionState checkLocalTransaction(MessageExt msg) {
        String orderId = msg.getKeys();
        boolean exists = orderService.exists(orderId);
        return exists ? LocalTransactionState.COMMIT_MESSAGE : LocalTransactionState.UNKNOW;
    }
});
producer.start();
```

没有 MQ 时，本地消息表是同一套思路的轻量实现，业务写库与消息记录在同一个本地事务里：

```sql
BEGIN;
INSERT INTO orders (order_id, user_id, amount, status)
VALUES ('ORD202611030001', 1001, 199.00, 'CREATED');
INSERT INTO local_message (biz_no, topic, payload, status, next_retry_at)
VALUES ('ORD202611030001', 'stock-deduct', '{"skuId":1,"count":1}', 'PENDING', NOW());
COMMIT;
```

TCC 的关键是三个接口都要幂等，并处理空回滚与悬挂：

```
Try：    冻结库存，available = available - 1，frozen = frozen + 1
Confirm：确认扣减，frozen = frozen - 1
Cancel： 释放冻结，available = available + 1，frozen = frozen - 1
空回滚： Try 未执行就收到 Cancel，插入一条「已取消」标记，不能再释放
悬挂：   Cancel 先于 Try 到达，Try 看到取消标记后直接返回成功，不冻结
```

**失败场景与兜底：**

| 失败点 | 现象 | 兜底策略 |
| --- | --- | --- |
| 消息发送成功但本地事务失败 | 下游多扣库存 | 事务消息回滚；本地消息表靠状态机避免投递 |
| 本地事务成功但消息丢失 | 下游没扣库存 | 定时扫描待发送消息重投，业务侧对账 |
| 消费失败 | 消息反复重试 | 幂等消费 + 重试上限 + 死信告警 |
| 空回滚 | Cancel 释放了不存在的冻结 | Cancel 幂等并记录空回滚标记 |
| 悬挂 | Cancel 后 Try 又冻结 | Try 检查全局事务状态，已取消则拒绝 |
| 长时间未决 | 订单已建、库存未扣 | 定时对账 + 差异池 + 人工补偿 |

**面试怎么答：** 先问三个问题：跨几个服务、能否接受最终一致、是否有资金强一致要求。然后给选型结论：订单后置动作优先本地消息表或事务消息；库存预占类用 TCC；长流程用 Saga；XA 只在低频强一致场景考虑。最后一定要讲「对账与补偿」，因为任何分布式事务方案都不能保证 100% 成功。

**易错点：**

- 把最终一致说成强一致，面试官追问「消息丢了怎么办」就答不上来。
- TCC 只写 Try/Confirm/Cancel，不处理空回滚与悬挂。
- 事务消息的消费者不幂等，重试导致重复扣库存。
- 在本地事务里调用远程服务，远程成功本地回滚，数据直接不一致。
- 认为 Seata AT 模式没有侵入性，忽略 undo_log 与全局锁带来的性能开销。

## 5. 库存扣减与超卖

**需求澄清与量级估算：**

- 商品：单 SKU 库存 1000 件，活动峰值 10 万 QPS，读多写多。
- 约束：绝对不能超卖；尽量少卖；扣减、回补、查询余额都要有流水可查。
- 数据特征：同一行热点写，单机数据库行锁只能支撑几千 TPS。
- 估算结论：数据库条件更新可支撑约 3000 到 5000 TPS，Redis 预扣可到 1 万以上，需要组合使用。
- 关键决策：DB 是最终账本，Redis 是流量缓冲，二者必须能对账。

**方案对比：**

| 方案 | 超卖风险 | 吞吐 | 复杂度 | 说明 |
| --- | --- | --- | --- | --- |
| `SELECT ... FOR UPDATE` | 无 | 低 | 低 | 行锁串行，热点行排队严重 |
| 乐观锁 version | 无 | 中 | 中 | 冲突高时重试次数爆炸 |
| 条件更新 `stock >= n` | 无 | 中高 | 低 | 推荐作为数据库兜底 |
| Redis Lua 预扣 | 无（Redis 内） | 高 | 中 | 需要回补与对账 |
| 分段库存 | 无 | 很高 | 高 | 段间借还需要额外脚本 |
| 预占 + 确认 | 无 | 中 | 中 | 适合下单锁库存 |

**核心流程：**

```
下单：
    1. Redis Lua 原子预扣，成功才继续
    2. 发送 MQ 异步落库
    3. 数据库条件更新 stock = stock - n WHERE stock >= n
    4. 数据库失败则回补 Redis，并把订单标记为失败
取消或超时：
    5. 订单状态 CAS 改为 CLOSED
    6. 回补 Redis 与数据库，写库存流水
    7. 回补接口按 orderId 幂等，重复调用不重复加库存
对账：
    8. 定时比对 Redis 剩余、数据库库存、有效订单数
    9. 差异写入库存差异表，人工或脚本修复
```

**关键实现：**

数据库条件更新是最稳的兜底，一条 SQL 同时完成判断与扣减：

```sql
UPDATE sku_stock
SET stock = stock - 1
WHERE sku_id = 1001
    AND stock >= 1;
-- affected rows = 1 表示成功，0 表示库存不足
```

不要用「先查再改」：

```sql
-- 错误示范：两个事务都能读到 stock = 1，然后都执行扣减
SELECT stock FROM sku_stock WHERE sku_id = 1001;
UPDATE sku_stock SET stock = stock - 1 WHERE sku_id = 1001;
```

乐观锁版本号适合冲突不高的场景，冲突高时大量重试反而更慢：

```sql
UPDATE sku_stock
SET stock = stock - 1, version = version + 1
WHERE sku_id = 1001
    AND version = 3
    AND stock >= 1;
```

Redis 预扣脚本与秒杀共用，但库存扣减要额外记录流水，方便对账：

```lua
-- KEYS[1] = stock:{skuId}
-- ARGV[1] = 扣减数量
-- ARGV[2] = 业务单号
local stock = tonumber(redis.call('GET', KEYS[1]) or '-1')
if stock < tonumber(ARGV[1]) then
    return 0
end
redis.call('DECRBY', KEYS[1], ARGV[1])
redis.call('HSET', 'stock:ledger:' .. KEYS[1], ARGV[2], ARGV[1])
return 1
```

分段库存把一行热点拆成多行，按 uid 哈希选段：

```java
int segment = Math.floorMod(Long.hashCode(userId), 10);
String key = "stock:" + skuId + ":seg:" + segment;
// 每段 100 件，段内 Lua 扣减；某段不足时从相邻段借，需要单独的借还脚本
```

**失败场景与兜底：**

| 失败点 | 现象 | 兜底策略 |
| --- | --- | --- |
| Redis 扣减成功、DB 失败 | Redis 少、DB 不少 | 回补 Redis，订单失败；定时对账兜底 |
| DB 扣减成功、消息丢失 | 订单未创建但库存已减 | 库存流水关联订单，扫表补建单或回补 |
| 回补重复 | 库存被加回两次 | 回补流水唯一键 `uk_order_sku` |
| 分段不均 | 某段售罄、其他段有货 | 借还脚本或活动前按历史流量分配 |
| Redis 重启 | 预扣数据丢失 | 以 DB 为准重建缓存，活动期间禁止重建 |
| 少卖 | 活动结束仍有库存 | 对账后统一释放，不做实时补救 |

**面试怎么答：** 先说结论：数据库条件更新保证不超卖，Redis 预扣提升吞吐，二者用 MQ 解耦，最后靠对账修少卖。然后对比行锁、乐观锁、条件更新的差异，说明为什么高并发下不用 `SELECT FOR UPDATE`。最后讲回补幂等和分段库存的适用边界。

**易错点：**

- 用 `stock > 0` 判断而不是 `stock >= n`，批量扣减时会扣成负数。
- 先查库存再更新，中间没有锁，典型超卖写法。
- 乐观锁重试没有上限，热点商品下线程全耗在重试。
- 回补没有幂等，用户取消一次、超时关单又一次，库存凭空多出。
- 只对 Redis 做对账，不对数据库与订单数做三方核对。

## 6. 支付与对账

**需求澄清与量级估算：**

- 业务：日订单 100 万，支付单约 120 万（含重复发起），接入 3 家渠道。
- 流量：支付回调峰值 2000 TPS，查单任务每分钟数千次。
- 一致性要求：支付状态不能丢、不能重复入账、金额一分不差。
- 对账要求：T+1 全量对账，日间准实时监控大额差异。
- 估算结论：回调与查单是两条独立链路，对账是最后一道保险，三者缺一不可。

**方案对比：**

| 方案 | 实时性 | 可靠性 | 缺点 |
| --- | --- | --- | --- |
| 只依赖同步返回 | 高 | 低 | 前端可伪造，网络超时无法判断 |
| 只依赖异步回调 | 高 | 中 | 回调可能丢失、重复、乱序 |
| 回调 + 主动查单 | 高 | 高 | 需要处理查单频率与渠道限流 |
| 回调 + 查单 + T+1 对账 | 高 | 最高 | 实现成本高，但对资金场景必需 |
| 渠道账单实时推送 | 高 | 中 | 依赖渠道能力，格式差异大 |

**核心流程：**

```
支付发起：
    1. 生成本地支付单 pay_no，金额单位用分，落库状态 INIT
    2. 调渠道下单，保存渠道返回的 prepay_id 或跳转地址
    3. 前端拿到参数完成支付
回调处理：
    4. 验签，校验商户号、金额、渠道交易号
    5. CAS 更新支付单：INIT/UNPAID -> PAID
    6. 更新订单状态，发送履约消息
    7. 按渠道要求返回成功应答，不能返回自定义 JSON
补偿：
    8. 未收到回调的支付单，按 1 分钟、5 分钟、30 分钟阶梯查单
    9. T+1 下载渠道对账文件，做平台、渠道、账务三方对账
    10. 差异进入差错池，自动冲正或人工处理
```

**关键实现：**

回调验签与金额校验是第一步，任何一项不通过都不能改状态：

```java
public String handleCallback(String channel, String rawBody, Map<String, String> headers) {
    if (!channelClient.verifySign(rawBody, headers)) {
        return "FAIL";
    }
    PayCallback callback = JSON.parseObject(rawBody, PayCallback.class);
    if (!merchantId.equals(callback.getMerchantId())) {
        return "FAIL";
    }
    PaymentOrder order = paymentMapper.selectByPayNo(callback.getPayNo());
    if (order == null || order.getAmount() != callback.getAmount()) {
        log.error("amount mismatch, payNo={}, local={}, channel={}",
            callback.getPayNo(), order == null ? null : order.getAmount(), callback.getAmount());
        return "FAIL";
    }
    markPaid(callback);
    return "SUCCESS";
}
```

状态更新用 CAS，保证重复回调只生效一次：

```sql
UPDATE payment_order
SET status = 'PAID',
    channel_trade_no = ?,
    paid_at = ?,
    callback_at = NOW()
WHERE pay_no = ?
    AND status IN ('INIT', 'UNPAID')
    AND amount = ?;
```

对账 SQL 用 `UNION` 模拟全外连接，分别找「平台有、渠道无」和「渠道有、平台无」：

```sql
SELECT p.pay_no, p.amount AS platform_amount, NULL AS channel_amount, 'PLATFORM_ONLY' AS diff_type
FROM payment_order p
LEFT JOIN channel_bill c ON p.pay_no = c.pay_no
WHERE p.bill_date = '2026-11-02'
    AND c.pay_no IS NULL
UNION
SELECT c.pay_no, NULL AS platform_amount, c.amount AS channel_amount, 'CHANNEL_ONLY' AS diff_type
FROM channel_bill c
LEFT JOIN payment_order p ON p.pay_no = c.pay_no
WHERE c.bill_date = '2026-11-02'
    AND p.pay_no IS NULL;
```

金额一律用 `BIGINT` 存分，禁止 `FLOAT` 与 `DOUBLE`：

```sql
CREATE TABLE payment_order (
    pay_no          VARCHAR(32)  NOT NULL,
    order_no        VARCHAR(32)  NOT NULL,
    amount          BIGINT       NOT NULL COMMENT '单位：分',
    currency        CHAR(3)      NOT NULL DEFAULT 'CNY',
    status          VARCHAR(16)  NOT NULL,
    channel_trade_no VARCHAR(64) NULL,
    paid_at         DATETIME     NULL,
    PRIMARY KEY (pay_no),
    UNIQUE KEY uk_channel_trade (channel_trade_no)
) ENGINE = InnoDB;
```

**失败场景与兜底：**

| 失败点 | 现象 | 兜底策略 |
| --- | --- | --- |
| 回调丢失 | 用户已付款，订单未发货 | 阶梯查单，主动向渠道确认 |
| 回调重复 | 重复发货、重复加积分 | CAS 状态更新 + 下游幂等 |
| 金额篡改 | 少付或多付 | 验签 + 服务端金额比对，绝不信任前端 |
| 渠道掉单 | 渠道无记录、平台已支付 | 对账差异池，冲正或补单 |
| 退款失败 | 用户已退款、平台未退 | 退款单状态机 + 查单 + 人工 |
| 对账文件缺失 | 当日无法对账 | 告警并重试下载，超过 3 天升级人工 |

**面试怎么答：** 按「回调、查单、对账」三层讲，强调回调不可信、必须验签、必须金额比对、必须幂等。然后讲状态机：支付单只允许从 INIT 到 PAID，不允许反向。最后讲对账三方口径与差错处理，说明资金场景为什么不能只靠回调。

**易错点：**

- 信任前端「支付成功」的跳转结果，没有服务端验签与查单。
- 回调里直接 `UPDATE status = 'PAID'`，重复回调重复发货。
- 金额用 `double`，0.1 + 0.2 在对账时永远差一分。
- 对账只对总额，不对明细，单笔错账被总额抹平。
- 把「查单」当成补偿的全部，忽略渠道本身也可能丢单。

## 7. 消息队列削峰填谷

**需求澄清与量级估算：**

- 场景：大促开抢后写请求峰值 5 万/s，持续 10 分钟，下游订单库安全写入能力约 8000/s。
- 消息量：10 分钟约 3000 万条，单条约 2KB，消息体总量约 60GB。
- 延迟要求：允许用户等待 1 到 10 分钟，但不能丢单、不能重复入账。
- 容量换算：5 万/s 涌入、8000/s 消费，积压速度 4.2 万/s，10 分钟积压约 2520 万条；按 8000/s 消费需要约 52 分钟才能追平。
- 结论：削峰的本质是「用可接受的延迟换吞吐」，必须同时具备限流、积压监控和扩容预案。

**方案对比：**

| 方案 | 峰值承载 | 延迟 | 复杂度 | 说明 |
| --- | --- | --- | --- | --- |
| 直接写数据库 | 数据库上限 | 低 | 低 | 峰值必崩，不可行 |
| 同步限流 | 数据库上限 | 低 | 中 | 超限用户直接失败，体验差 |
| MQ 缓冲 + 异步消费 | 很高 | 分钟级 | 中 | 主流削峰方案 |
| MQ + 批量落库 | 很高 | 分钟级 | 中高 | 提升消费吞吐，需处理部分失败 |
| 队列 + 排队页 | 高 | 可感知 | 中 | 用户可见进度，降低焦虑 |

消息中间件选型：

| 中间件 | 吞吐 | 延迟 | 顺序 | 适用 |
| --- | --- | --- | --- | --- |
| Kafka | 十万级 | 毫秒到秒 | 分区内有序 | 日志、海量事件、大数据链路 |
| RocketMQ | 万到十万级 | 毫秒 | 分区内有序，支持事务消息 | 电商交易、需要事务与延迟消息 |
| RabbitMQ | 万级 | 微秒到毫秒 | 队列内有序 | 业务解耦、路由灵活、消息量中等 |

**核心流程：**

```
生产端：
    1. 业务校验通过后写 MQ，key 用 orderId，保证同一订单进入同一分区
    2. 同步发送并设置 acks=all 与 min.insync.replicas=2，确保至少两个副本确认
    3. 发送失败写本地重试表，由定时任务重投
Broker：
    4. 分区数按目标消费能力设计，Kafka 分区只能增加不能减少
    5. 副本数 3，避免单节点故障丢消息
消费端：
    6. 批量拉取，单批 500 条，手动提交 offset
    7. 批量插入数据库，唯一索引保证幂等
    8. 部分失败时拆分重试，不整批回滚
    9. 消费延迟超过阈值触发告警，必要时扩容消费者
```

**关键实现：**

Kafka 消费者关闭自动提交，避免「提交了 offset 但业务没落库」：

```java
Properties props = new Properties();
props.put("bootstrap.servers", "kafka1:9092,kafka2:9092,kafka3:9092");
props.put("group.id", "order-writer");
props.put("enable.auto.commit", "false");
props.put("max.poll.records", "500");
props.put("fetch.min.bytes", "1048576");
props.put("key.deserializer", "org.apache.kafka.common.serialization.StringDeserializer");
props.put("value.deserializer", "org.apache.kafka.common.serialization.StringDeserializer");

KafkaConsumer<String, String> consumer = new KafkaConsumer<>(props);
consumer.subscribe(Collections.singletonList("order-created"));
while (running) {
    ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(500));
    if (records.isEmpty()) {
        continue;
    }
    try {
        orderWriter.batchInsert(records);
        consumer.commitSync();
    } catch (Exception e) {
        log.error("batch insert failed, size={}", records.count(), e);
        // 不提交 offset，让这批消息重新消费；批量接口必须幂等
    }
}
```

RocketMQ 生产端设置同步发送与重试，保证消息不静默丢失：

```java
DefaultMQProducer producer = new DefaultMQProducer("order-producer");
producer.setNamesrvAddr("rocketmq1:9876;rocketmq2:9876");
producer.setRetryTimesWhenSendFailed(2);
producer.start();

Message message = new Message("order-created", "CREATE", orderId, payload.getBytes(StandardCharsets.UTF_8));
SendResult result = producer.send(message, 3000);
if (result.getSendStatus() != SendStatus.SEND_OK) {
    retryTable.save(orderId, payload);
}
```

消费幂等依赖数据库唯一键，而不是「消费前查一次」：

```sql
CREATE TABLE order_consume_log (
    order_id    BIGINT      NOT NULL,
    consumer    VARCHAR(32) NOT NULL,
    consumed_at DATETIME    NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (order_id, consumer)
) ENGINE = InnoDB;
```

**失败场景与兜底：**

| 失败点 | 现象 | 兜底策略 |
| --- | --- | --- |
| 生产端发送失败 | 订单丢失 | 本地重试表 + 定时重投 + 对账 |
| Broker 副本不足 | 单节点宕机丢消息 | `acks=all`、副本数 3、禁止 `acks=0` |
| 消费重复 | 重复建单、重复扣款 | 唯一索引 + 消费日志 |
| 消费积压 | 用户等待时间变长 | 扩容消费者（不超过分区数）、临时降级非核心消费 |
| 顺序错乱 | 同一订单先支付后创建 | 按 orderId 分区 + 单线程消费分区 |
| 死信堆积 | 异常消息无人处理 | 死信队列告警 + 重放工具 + 人工介入 |

**面试怎么答：** 先算清楚「峰值速率、消费速率、积压量、追平时间」四个数，证明为什么必须削峰。再讲生产端可靠发送、Broker 副本、消费端幂等三件事。最后讲积压处理：优先扩容消费者，但 Kafka 受分区数限制，必要时临时降级非核心链路。

**易错点：**

- 开启 `enable.auto.commit=true`，业务异常时 offset 已提交，消息直接丢。
- 认为「加消费者就能解决积压」，忽略分区数上限。
- 顺序消息用多线程消费，同一订单的创建与支付乱序。
- 批量消费一条失败就整批回滚，导致大量重复消费。
- 只监控队列长度，不监控消费延迟与死信数量。

## 8. 灰度发布（蓝绿 / 金丝雀）

**需求澄清与量级估算：**

- 规模：100 台应用实例，日活 100 万，核心接口峰值 2 万 QPS。
- 变更内容：新版本增加订单字段、调整价格计算逻辑、升级依赖版本。
- 约束：任何问题必须在 5 分钟内回滚；同一用户不能在两套逻辑间反复切换。
- 数据兼容：数据库变更必须向前兼容，旧版本代码在新表结构上仍可运行。
- 结论：灰度不是「切流量」一件事，而是流量、数据、监控三位一体。

**方案对比：**

| 方案 | 资源成本 | 回滚速度 | 风险 | 适用 |
| --- | --- | --- | --- | --- |
| 蓝绿部署 | 双倍资源 | 秒级切回 | 低 | 资源充足、版本切换 |
| 金丝雀发布 | 少量额外资源 | 分钟级 | 低 | 核心服务、逐步放量 |
| 滚动发布 | 无额外资源 | 分钟级 | 中 | 无状态服务、K8s 默认 |
| Feature Flag | 低 | 秒级关闭 | 低 | 功能级开关、可按用户维度 |

**核心流程：**

```
发布前：
    1. 数据库加字段必须可空或有默认值，禁止直接改列类型
    2. 新旧代码双写兼容，读路径做版本判断
    3. 缓存 key 加版本前缀，避免旧格式被新代码读到
    4. 准备回滚脚本与回滚开关，确认旧版本仍可启动
放量：
    5. 金丝雀 1% 流量，观察 30 分钟：错误率、P99、GC、DB 连接数
    6. 5%、20%、50%、100% 分阶段，每阶段对比基线
    7. 业务指标同步观察：下单成功率、支付成功率、客单价
异常：
    8. 错误率超过基线 2 倍或 P99 超过 1.5 倍，自动回滚
    9. 回滚只切流量，不回滚数据库，靠向前兼容保证旧代码可用
```

**关键实现：**

Nginx 按用户哈希切 1% 流量，保证同一用户稳定进入金丝雀：

```nginx

}

server {

    location / {
        proxy_pass http://$variant;
        proxy_set_header X-Release-Variant $variant;
    }
}
```

**失败场景与兜底：**

| 失败点 | 现象 | 兜底策略 |
| --- | --- | --- |
| 数据库不兼容 | 旧版本读不到新字段或报错 | 加字段可空、双写、分两次发布 |
| 缓存格式变化 | 旧代码反序列化失败 | key 加版本、双读兼容、过期重建 |
| 用户流量漂移 | 同一用户新旧逻辑来回切 | 按 uid 哈希而不是随机 |
| 回滚不彻底 | 新写入数据旧代码不识别 | 向前兼容、回滚只切流量 |
| 监控缺失 | 出问题靠用户反馈 | 发布前配置错误率、P99、业务指标看板 |
| 依赖未灰度 | 新代码调用旧下游报错 | 下游先行发布，或做接口版本兼容 |

**面试怎么答：** 先区分蓝绿与金丝雀：蓝绿是两套完整环境切流量，回滚快但资源翻倍；金丝雀是小比例引流，逐步放量。然后重点讲「数据兼容」——数据库加字段、双写、缓存版本、回滚不滚数据。最后讲观测指标与自动回滚阈值，体现你真正做过发布。

**易错点：**

- 只切流量不考虑数据库变更，新代码回滚后旧代码直接报错。
- 灰度按机器而不是按用户，同一用户请求在两台机器上结果不同。
- 没有基线指标，出问题说不清「是否变差」。
- 回滚时连数据库一起回滚，新写入的数据全部丢失。
- 功能开关默认打开，配置中心故障时行为不可控。

## 9. 多租户数据隔离

**需求澄清与量级估算：**

- 规模：5000 个租户，大租户单表 1000 万行，小租户几千行，SaaS 平台。
- 流量：整体峰值 1 万 QPS，头部 10 个租户占 60% 流量。
- 合规：部分客户要求数据物理隔离，普通客户接受逻辑隔离。
- 约束：任何查询不能跨租户；租户 ID 不能由前端传入；异步任务也要带租户上下文。
- 结论：隔离级别要按租户分层，不能一刀切用独立库，也不能所有租户挤一张表。

**方案对比：**

| 方案 | 隔离性 | 成本 | 扩展性 | 适用 |
| --- | --- | --- | --- | --- |
| 独立数据库 | 最高 | 最高 | 运维复杂 | 金融、政企、合规客户 |
| 共享库独立 schema | 高 | 中高 | schema 数量多 | 中大客户 |
| 共享表 + tenant_id | 低 | 最低 | 好 | 海量小客户 |
| 共享表 + 按租户分片 | 中 | 中 | 好 | 大租户与长尾混合 |
| 独立库 + 共享表混合 | 按租户 | 中 | 中 | 主流 SaaS 分层方案 |

**核心流程：**

```
1. 网关从 JWT 或 session 解析 tenant_id，禁止从请求参数读取
2. tenant_id 写入 ThreadLocal 与 MDC，日志全链路可追踪
3. 数据访问层统一拦截，所有 SQL 强制带 tenant_id 条件
4. 写操作校验业务对象归属，防止越权修改他人数据
5. 唯一索引必须包含 tenant_id，避免跨租户冲突
6. 定时任务与 MQ 消费从任务参数恢复租户上下文
7. 大租户路由到独立库，长尾租户共享库
```

**关键实现：**

MyBatis 拦截器统一注入租户条件，生产环境应基于 AST 而不是字符串替换：

```java
@Intercepts({
    @Signature(type = Executor.class, method = "query",
        args = {MappedStatement.class, Object.class, RowBounds.class, ResultHandler.class})
})
public class TenantInterceptor implements Interceptor {
    @Override
    public Object intercept(Invocation invocation) throws Throwable {
        MappedStatement ms = (MappedStatement) invocation.getArgs()[0];
        Object param = invocation.getArgs()[1];
        String sql = ms.getBoundSql(param).getSql();
        if (TenantContext.get() == null) {
            throw new IllegalStateException("tenant context missing");
        }
        if (sql.contains(" t_order ") && !sql.contains("tenant_id")) {
            throw new IllegalStateException("sql without tenant_id: " + ms.getId());
        }
        return invocation.proceed();
    }
}
```

PostgreSQL 可以用行级安全策略，把隔离下沉到数据库，应用漏写条件也不会越权：

```sql
ALTER TABLE orders ENABLE ROW LEVEL SECURITY;

CREATE POLICY tenant_isolation ON orders
    USING (tenant_id = current_setting('app.tenant_id')::bigint);

-- 每个请求开始时设置，连接归还前必须重置
SET app.tenant_id = '1001';
```

共享表的核心索引与唯一键必须把 `tenant_id` 放首列：

```sql
CREATE TABLE orders (
    id          BIGINT       NOT NULL AUTO_INCREMENT,
    tenant_id   BIGINT       NOT NULL,
    order_no    VARCHAR(32)  NOT NULL,
    user_id     BIGINT       NOT NULL,
    amount      BIGINT       NOT NULL,
    created_at  DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (id),
    UNIQUE KEY uk_tenant_order (tenant_id, order_no),
    KEY idx_tenant_user_time (tenant_id, user_id, created_at)
) ENGINE = InnoDB;
```

异步任务必须显式传递租户，不能依赖 ThreadLocal：

```java
public void handle(OrderMessage message) {
    TenantContext.set(message.getTenantId());
    try {
        orderService.process(message);
    } finally {
        TenantContext.clear();
    }
}
```

**失败场景与兜底：**

| 失败点 | 现象 | 兜底策略 |
| --- | --- | --- |
| 漏加租户条件 | 查到其他租户数据 | 拦截器校验 + 集成测试 + 数据库 RLS 兜底 |
| 前端传入 tenant_id | 越权访问 | 只信任 token，参数中的租户一律忽略 |
| 唯一索引不带租户 | 两个租户订单号冲突 | 唯一键以 tenant_id 开头 |
| 大租户热点 | 单库单表被打爆 | 大租户独立库或独立分片 |
| 异步任务丢上下文 | 定时任务写到默认租户 | 任务参数携带 tenant_id，消费前校验 |
| 缓存 key 不带租户 | 读到别人的缓存 | 所有 key 前缀 `tenant:{id}:` |

**面试怎么答：** 先问租户规模、合规要求和单租户数据量，再给分层方案：小客户共享表，大客户独立库，超大客户独立实例。然后讲落地细节：tenant_id 从 token 注入、SQL 强制过滤、索引首列、缓存前缀、异步上下文。最后讲越权测试与 RLS 兜底。

**易错点：**

- 从请求参数或 Header 读取 tenant_id，攻击者改一个数字就能查别人数据。
- 只给查询加 tenant_id，更新和删除忘记加。
- 唯一索引是 `(order_no)`，两个租户生成相同订单号直接冲突。
- 定时任务用 ThreadLocal，线程复用导致串租户。
- 缓存 key 只写业务 ID，不同租户读到同一份缓存。

## 10. 热点账户与热点数据

**需求澄清与量级估算：**

- 场景：平台头部商户账户，活动期间单账户入账峰值 1 万 TPS，持续 5 分钟。
- 数据：单账户余额一行，流水表每天新增 300 万条。
- 约束：余额不能错、不能丢流水、查询要能实时看到大致余额。
- 问题本质：不是「缓存读热点」，而是「单行写热点」，缓存解决不了写锁排队。
- 结论：写热点要用「追加流水 + 异步合并」或「拆分子账户」，读热点才用缓存。

**方案对比：**

| 方案 | 写吞吐 | 余额实时性 | 复杂度 | 说明 |
| --- | --- | --- | --- | --- |
| 直接 `UPDATE balance` | 低 | 实时 | 低 | 单行锁串行，1 万 TPS 不可能 |
| 乐观锁重试 | 中 | 实时 | 中 | 冲突高时重试风暴 |
| 追加流水 + 定时汇总 | 高 | 秒级延迟 | 中 | 主流方案 |
| Redis 累加 + 异步落库 | 很高 | 秒级 | 中高 | 需处理 Redis 宕机丢数据 |
| 拆分子账户 | 很高 | 需汇总 | 高 | 适合超大账户 |
| 缓冲记账（内存合并） | 很高 | 有延迟 | 高 | 进程崩溃会丢，需持久化队列 |

**核心流程：**

```
入账：
    1. 校验业务单号，写流水表（只追加，不做更新）
    2. 流水表按 account_id 分表或分区，避免单表膨胀
    3. Redis HINCRBY 更新「未汇总余额」，供实时查询
    4. 立即返回受理成功，不等待余额落库
汇总：
    5. 定时任务每 5 秒扫描未汇总流水
    6. 按 account_id 聚合，批量更新账户余额
    7. 更新成功后标记流水已汇总，保证不重复
查询：
    8. 余额 = 账户表余额 + 未汇总流水合计
    9. 对账任务每天核对流水合计与账户余额
```

**关键实现：**

流水表只追加，天然没有行锁竞争：

```sql
CREATE TABLE account_ledger (
    id          BIGINT      NOT NULL AUTO_INCREMENT,
    account_id  BIGINT      NOT NULL,
    biz_no      VARCHAR(64) NOT NULL,
    amount      BIGINT      NOT NULL COMMENT '单位：分，正数入账，负数出账',
    direction   VARCHAR(8)  NOT NULL,
    settled     TINYINT     NOT NULL DEFAULT 0,
    created_at  DATETIME    NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (id),
    UNIQUE KEY uk_biz_no (biz_no),
    KEY idx_account_settled (account_id, settled, id)
) ENGINE = InnoDB;
```

汇总任务按账户聚合，并用 `settled` 做幂等：

```sql
UPDATE account
SET balance = balance + ?,
    updated_at = NOW()
WHERE account_id = ?;

UPDATE account_ledger
SET settled = 1
WHERE account_id = ?
    AND settled = 0
    AND id <= ?;
```

金额较大的账户拆成 16 个子账户，按业务单号哈希路由：

```java
int shard = Math.floorMod(bizNo.hashCode(), 16);
String redisKey = "account:unsettled:" + accountId + ":" + shard;
redis.opsForHash().increment(redisKey, "balance", amount);
```

实时余额查询把「已落库余额」与「未汇总流水」相加，避免用户看到旧余额：

```sql
SELECT a.balance + COALESCE(
    (SELECT SUM(l.amount) FROM account_ledger l
     WHERE l.account_id = a.account_id AND l.settled = 0), 0
) AS available_balance
FROM account a
WHERE a.account_id = ?;
```

**失败场景与兜底：**

| 失败点 | 现象 | 兜底策略 |
| --- | --- | --- |
| 汇总任务崩溃 | 余额长时间不更新 | 记录 checkpoint，重启后从上次位置继续 |
| 重复汇总 | 余额多加 | `settled` 条件更新 + 汇总批次号唯一 |
| Redis 宕机 | 实时余额丢失 | 以流水表为准，Redis 只做展示加速 |
| 子账户拆分不均 | 某个子账户仍是热点 | 按历史流量分配权重，或增加拆分数 |
| 查询放大 | 每次查余额都聚合流水 | 维护「未汇总余额」缓存，定期校准 |
| 流水表膨胀 | 查询与汇总变慢 | 按日分区，历史流水归档 |

**面试怎么答：** 先纠正常见误区：热点账户是写热点，加缓存没用。然后给两条路径：普通热点用「追加流水 + 定时汇总」，超大热点再「拆分子账户」。最后讲余额实时性怎么保证：账户余额加未汇总流水，配合每日对账。

**易错点：**

- 直接 `UPDATE account SET balance = balance + ?`，高并发下全部排在行锁上。
- Redis 累加后认为余额已经持久化，Redis 重启直接丢账。
- 拆分子账户后查询余额忘记汇总所有子账户。
- 汇总任务没有 checkpoint，重启后从头扫，重复计算。
- 只保证入账幂等，出账与退款没有同一套业务单号体系。

## 11. 限流与排队

**需求澄清与量级估算：**

- 入口：网关整体 10 万 QPS，后端服务安全容量 2 万 QPS，突发流量可达日常 3 倍。
- 维度：全局、接口、用户、IP、租户五个维度，不同维度阈值不同。
- 目标：超限请求快速失败并给出重试时间，核心接口不被非核心流量拖垮。
- 约束：限流组件本身不能成为单点；Redis 故障时要有本地兜底。
- 结论：限流是「保护下游」，排队是「把失败变成等待」，两者解决不同问题。

**方案对比：**

| 算法 | 突发流量 | 实现复杂度 | 缺点 | 适用 |
| --- | --- | --- | --- | --- |
| 固定窗口计数 | 不允许 | 低 | 临界点会放过 2 倍流量 | 粗粒度保护 |
| 滑动窗口 | 允许少量 | 中 | 需要存储请求时间 | 精确 QPS 限制 |
| 漏桶 | 不允许 | 低 | 无法应对合理突发 | 平滑下游压力 |
| 令牌桶 | 允许 | 中 | 需要维护令牌数 | 网关主流 |
| 并发信号量 | 不涉及 | 低 | 只限并发不限速率 | 服务内部隔离 |

排队方案对比：

| 方案 | 用户体验 | 实现 | 适用 |
| --- | --- | --- | --- |
| 直接返回 429 | 立即失败 | 简单 | 非核心接口 |
| 返回排队号 + 轮询 | 可感知进度 | 中 | 秒杀、抢购 |
| MQ 异步 + 202 | 后台处理 | 中 | 允许延迟的任务 |
| 前端排队页 | 等待感低 | 中 | 大促入口 |

**核心流程：**

```
1. CDN/WAF 做 IP 级粗粒度限流，挡住明显攻击流量
2. 网关按 uid、接口、租户三个维度做令牌桶限流
3. 核心接口预留独立配额，不被非核心接口挤占
4. 服务内部用信号量隔离，限制同时处理的请求数
5. 超限返回 429，携带 Retry-After 与限流维度
6. 秒杀类场景改为发放排队号，前端轮询排队进度
7. 排队人数超过上限直接拒绝，避免队列无限增长
```

**关键实现：**

Redis Lua 令牌桶，把「取令牌」做成一次原子操作：

```lua
-- KEYS[1] = limiter:{dimension}:{key}
-- ARGV[1] = capacity, ARGV[2] = rate(个/秒), ARGV[3] = now(毫秒), ARGV[4] = cost
local capacity = tonumber(ARGV[1])
local rate = tonumber(ARGV[2])
local now = tonumber(ARGV[3])
local cost = tonumber(ARGV[4])
local data = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
local tokens = tonumber(data[1]) or capacity
local ts = tonumber(data[2]) or now
local delta = math.max(0, now - ts)
tokens = math.min(capacity, tokens + delta * rate / 1000)
if tokens < cost then
    redis.call('HMSET', KEYS[1], 'tokens', tokens, 'ts', now)
    return 0
end
redis.call('HMSET', KEYS[1], 'tokens', tokens - cost, 'ts', now)
redis.call('PEXPIRE', KEYS[1], math.ceil(capacity / rate * 1000) * 2)
return 1
```

滑动窗口用 ZSet 记录请求时间，适合「60 秒内最多 100 次」这类规则：

```lua
-- KEYS[1] = window:{uid}:{api}
-- ARGV[1] = now(毫秒), ARGV[2] = window(毫秒), ARGV[3] = limit
local now = tonumber(ARGV[1])
local window = tonumber(ARGV[2])
local limit = tonumber(ARGV[3])
redis.call('ZREMRANGEBYSCORE', KEYS[1], 0, now - window)
local count = redis.call('ZCARD', KEYS[1])
if count >= limit then
    return 0
end
redis.call('ZADD', KEYS[1], now, ARGV[4])
redis.call('PEXPIRE', KEYS[1], window)
return 1
```

单机限流用 Guava 的令牌桶，作为 Redis 故障时的本地兜底：

```java
private final RateLimiter localLimiter = RateLimiter.create(2000.0);

public boolean allow() {
    return localLimiter.tryAcquire(1, 50, TimeUnit.MILLISECONDS);
}
```

**失败场景与兜底：**

| 失败点 | 现象 | 兜底策略 |
| --- | --- | --- |
| Redis 故障 | 分布式限流全部失效 | 降级到单机令牌桶，阈值按实例数分摊 |
| 固定窗口临界 | 第 59 秒和第 60 秒各打满一次 | 改用滑动窗口或令牌桶 |
| 限流维度过粗 | 正常用户被误伤 | 按 uid + 接口，IP 只做粗筛 |
| 热点 key | 单分片被打爆 | key 加随机后缀，多分片聚合 |
| 队列无上限 | 排队越久越多，最终雪崩 | 设置最大排队数，超出直接拒绝 |
| 不返回重试时间 | 客户端立即重试，压力更大 | 返回 `Retry-After` 与指数退避建议 |

**面试怎么答：** 先区分限流与排队：限流保护系统，排队改善体验。再讲算法选型：网关用令牌桶允许合理突发，精确规则用滑动窗口，内部用信号量限并发。最后讲分布式实现的两个坑：Redis 单点与热点 key，必须准备本地降级。

**易错点：**

- 用固定窗口计数，临界点两倍流量打穿下游。
- 只做全局限流，某个接口被刷时其他接口一起遭殃。
- 限流 key 用 IP，NAT 环境下误伤大量正常用户。
- 返回 429 但不告诉客户端何时重试，客户端立刻重试形成风暴。
- 排队队列不设上限，流量持续涌入时内存先爆。

## 12. 大促容量评估与压测

**需求澄清与量级估算：**

- 业务：日常 1 万 QPS，大促 0 点预计 10 万 QPS，峰值持续 30 分钟。
- 链路：网关、订单、库存、支付、消息队列、数据库、Redis 共 7 层依赖。
- 目标：峰值下 P99 小于 200ms，错误率小于 0.1%，任一依赖故障可降级。
- 约束：压测不能污染生产数据；压测流量必须可识别、可清理。
- 结论：容量评估是「算、压、观测、预案」四步，任何一步缺失都只是拍脑袋。

**方案对比：**

| 压测方式 | 真实度 | 成本 | 风险 | 适用 |
| --- | --- | --- | --- | --- |
| 单接口压测 | 低 | 低 | 低 | 找单机拐点 |
| 单服务全链路 | 中 | 中 | 中 | 验证服务容量 |
| 生产全链路压测 | 高 | 高 | 高 | 大促前最终验证 |
| 影子库压测 | 高 | 高 | 低 | 需要隔离数据 |
| 线上流量回放 | 最高 | 中 | 中 | 有历史流量样本 |

**核心流程：**

```
1. 业务建模：DAU × 转化率 × 人均行为次数，按小时分布换算成 QPS
2. 拆分读写比、缓存命中率、下游调用次数
3. 单机压测：固定 CPU、内存、连接池，逐步加压找拐点
4. 计算实例数：峰值 QPS ÷ 单机安全 QPS × 1.3 缓冲
5. 全链路压测：影子表、影子库、压测标透传
6. 观察每层指标：CPU、GC、连接池、慢 SQL、MQ 积压、Redis 命中率
7. 找出木桶短板，扩容或限流
8. 准备降级预案：关闭非核心推荐、合并请求、静态兜底
```

**关键实现：**

容量换算公式：

```
峰值 QPS = DAU × 人均请求数 × 峰值集中系数 ÷ 峰值持续秒数
示例：100 万 × 20 × 0.6 ÷ 1800 ≈ 6667 QPS（按业务实际调整）
单机安全 QPS = 压测拐点 QPS × 70%
实例数 = 峰值 QPS ÷ 单机安全 QPS × 1.3
数据库连接数 = 实例数 × 单实例连接池上限，必须小于 DB max_connections
```

压测命令示例，固定并发与持续时间，观察延迟分布：

```bash
wrk -t 8 -c 200 -d 60s \
    -H "Authorization: Bearer $TOKEN" \
    -H "X-Load-Test: true" \
    --latency http://api.example.com/order/create
```

Prometheus 查询 P99，定位哪个接口先劣化：

```
histogram_quantile(
    0.99,
    sum(rate(http_request_duration_seconds_bucket[5m])) by (le, uri)
)
```

    } else {

**失败场景与兜底：**

| 失败点 | 现象 | 兜底策略 |
| --- | --- | --- |
| 压测污染生产 | 真实用户看到测试订单 | 压测标 + 影子库 + 数据清理脚本 |
| 缓存未预热 | 压测直接打穿数据库 | 先预热热点 key，再开始加压 |
| 只压单接口 | 全链路仍崩 | 按真实调用比例编排混合场景 |
| 依赖未压 | 下游先挂 | 逐层压测，记录每层容量 |
| 数据量不对 | 小表跑得飞快，大表慢十倍 | 使用生产同量级数据或按比例构造 |
| 没有降级预案 | 峰值下只能全站挂 | 提前演练限流、降级、开关 |

**面试怎么答：** 先讲估算公式和四个关键数：峰值 QPS、单机拐点、实例数、依赖容量。再讲压测方法：单机找拐点、全链路验证木桶、影子库避免污染。最后讲预案：限流阈值、降级开关、扩容触发条件，并强调压测结论要落到具体数字，而不是「压过了」。

**易错点：**

- 用平均 QPS 做容量规划，忽略峰值集中系数。
- 压测环境用空库，和生产数据量差几个数量级。
- 只压订单接口，忽略库存、支付、MQ 消费的连锁压力。
- 压测流量没有标记，测试订单混入真实订单。
- 算出容量就结束，没有对应的限流与降级预案。
