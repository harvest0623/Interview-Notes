# 后端场景设计面试题

> 本目录收录「后端场景设计」类高频面试题及参考答案。与八股题不同，场景题考察的是**给定业务约束后，你怎么估算、怎么选型、怎么落地、怎么兜底**。默认技术背景为 **MySQL 8.0 / Redis 7 / RocketMQ 5.x / Kafka 3.x / JDK 17 / Spring Boot 3**；AI 场景部分以 **Python 3.11+ 与 OpenAI 兼容接口** 为例，模型名称与价格只作占位，落地时以实际供应商为准。本目录不重复讲 SQL 语法、Redis 数据结构、JVM 调优等基础知识，只讲**具体场景的设计路径与取舍**。

## 学习路径建议

```
高并发场景篇（先把交易链路打通：秒杀 / 库存 / 幂等 / 事务 / 支付）
    ↓
数据库场景篇（数据量上来后的问题：分库分表 / 报表 / 主从 / 缓存 / 迁移）
    ↓
AI 应用场景篇（RAG / Agent / 成本与延迟，重点在评估与兜底）
```

> 面试策略：**秒杀、库存扣减、幂等、分布式事务是硬门槛**，答不出细节说明没真正做过交易；**分库分表跨表查询、主从延迟、缓存一致性是分水岭**，能讲清失败路径才算做过；**RAG 与 Agent 是加分项**，能说清评估指标与降级方案比会调 API 更加分。
>
> 场景题的统一骨架：**先澄清约束与量级（QPS、数据量、延迟、一致性）→ 给方案对比 → 讲核心流程 → 落到关键代码或 SQL → 讲失败场景与兜底 → 说取舍理由**。只贴代码不谈取舍，是这类题最常见的失分点。

## 核心速查表

**秒杀链路**

```
详情页静态化到 CDN
    → 网关限流（uid 1 次/秒 + 全局阈值）
    → 活动时间 / 黑名单 / 一人一单校验
    → Redis Lua 原子扣减（判库存 + 判重 + DECRBY + SADD）
    → 发送 MQ，立即返回排队中与 orderToken
    → 消费端幂等建单（UNIQUE KEY uk_user_sku）
    → 数据库条件更新兜底（UPDATE ... WHERE stock >= n）
    → 30 分钟未支付，延迟消息关单并回补
    → 活动结束三方对账（Redis / DB / 订单数）

容量口径：
    写 QPS 峰值 / Redis 单分片 1~2 万 QPS = 分片数
    有效订单数决定 DB 压力，不按入口 QPS 估 DB
```

**分布式事务对比**

```
XA / 2PC      强一致，性能低，事务期间锁资源；适合低频核心交易
TCC           强一致（最终），Try/Confirm/Cancel 三段；必须处理空回滚、悬挂、幂等
Saga          最终一致，每步有补偿；适合长流程、跨多服务
本地消息表    最终一致，业务与消息同库同事务，定时重投；实现简单、可控
事务消息      half message + 本地事务 + 定时回查；依赖 MQ 可靠性与消费幂等
最大努力通知  最终一致，反复通知 + 对账；适合外部渠道、通知类

选型顺序：
    能本地事务 -> 本地消息表 / 事务消息 -> TCC（资金预占）-> Saga（长流程）-> XA（低频强一致）
    任何方案都必须配对账与补偿，不能假设 100% 成功
```

**缓存一致性方案**

```
读路径：
    本地缓存 -> Redis -> DB 回填（互斥锁防击穿，空值缓存防穿透）
写路径：
    更新 DB -> 事务提交 -> 删除 Redis -> 广播本地缓存失效
兜底：
    随机 TTL（防雪崩）+ 延迟双删 + binlog 订阅补偿
热点：
    本地缓存 + key 打散（如 16 份）+ 读写分离 + 限流
禁止：
    先删缓存再写库、更新缓存而不是删除、所有 key 同一 TTL
```

## 易错点清单

```
1. 秒杀用 GET 再 DECR 扣库存，两步之间被并发穿透，必然超卖
2. 只在 Redis 扣减就返回下单成功，Redis 重启后库存与订单全部对不上
3. 订单超时只靠定时扫表，订单量上来后扫不完，任务持续延后
4. 关单先回补库存再改状态，支付回调插进来就出现「已支付但库存被回补」
5. 幂等键用参数 MD5，参数顺序或时间戳一变就算出不同 key
6. 先执行业务再写幂等记录，进程崩溃后重复请求会再次执行
7. 分布式事务把「最终一致」说成「强一致」，追问消息丢失就答不上来
8. TCC 不处理空回滚与悬挂，Cancel 释放了不存在的冻结
9. 库存回补没有幂等，用户取消一次、超时关单又一次，库存凭空变多
10. 支付只信前端跳转结果，不验签、不查单、不对账
11. 金额用 double 存储，对账时永远差一分
12. 灰度只切流量不改 schema，回滚后旧代码直接报错
13. 多租户从请求参数读 tenant_id，改一个数字就能查别人数据
14. 唯一索引不带 tenant_id，两个租户生成相同订单号直接冲突
15. 热点账户直接 UPDATE balance，高并发全部排在行锁上
16. 限流用固定窗口，临界点放过两倍流量；只按 IP 会误伤整个 NAT 出口
17. 容量评估用平均 QPS，忽略峰值集中系数与下游木桶短板
18. 分库分表选错分片键，80% 查询变成全分片广播
19. 跨分片深分页 LIMIT 100000, 10，每个分片都扫十万行
20. 在 MySQL 上直接 COUNT 十亿行做报表，还奇怪为什么超时
21. 所有读都走主库解决主从延迟，结果主库先被打爆
22. 用 Seconds_Behind_Master 判断延迟，大事务执行期间严重失真
23. 更新 DB 后更新缓存，并发写导致缓存值互相覆盖
24. 本地缓存不广播失效，多实例读到不同价格
25. 大事务里调用 RPC，远程超时把数据库行锁一起拖住
26. 分批任务用 LIMIT offset 翻页，越往后越慢
27. 数据迁移先写新库再写旧库，回滚时新数据全部丢失
28. 迁移只校验行数，不校验金额与关键字段
29. RAG 一上来就调 prompt，实际是召回没找到正确文档
30. RAG 先召回再按权限过滤，无权文档已经进了模型上下文
31. Agent 对所有工具统一重试，退款接口直接重复退款
32. Agent 没有最大步数，模型在两个工具之间循环到 token 耗尽
33. 大模型只按调用次数算成本，不看输入输出 token 与上下文长度
34. 语义缓存阈值过低，把相似但不同的问题答案复用
```
