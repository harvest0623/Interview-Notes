## 1. LangChain 的记忆机制有哪些

**记忆（Memory）** 解决的是「让无状态的 LLM 拥有跨轮次/跨会话的上下文记忆」。LangChain 的记忆可以按三条线拆开看：**作用范围**、**存储载体**、**实现方式**。

**① 按作用范围分两层**

| 层级 | 说明 | 现代实现 |
| --- | --- | --- |
| 短期记忆（Short-term） | 单个会话线程内的历史消息，随对话滚动 | LangGraph `State.messages` + `Checkpointer`；`RunnableWithMessageHistory` |
| 长期记忆（Long-term） | 跨会话、跨线程，按用户/命名空间存取 | LangGraph `Store`（`InMemoryStore` / `PostgresStore`）、向量库做语义记忆 |

**② 按存储载体分（`BaseChatMessageHistory` 家族）**

| 载体 | 类 | 适用场景 |
| --- | --- | --- |
| 内存（进程内） | `InMemoryChatMessageHistory` | 开发调试、单实例小流量 |
| 本地文件 | `FileChatMessageHistory` | 单机脚本、快速验证 |
| SQL 数据库 | `SQLChatMessageHistory`（`langchain-community`） | 中小规模持久化 |
| Redis | `RedisChatMessageHistory` | 高并发、带过期策略的会话 |
| LangGraph Checkpointer | `MemorySaver` / `SqliteSaver` / `PostgresSaver` | **生产首选**，随图状态一起持久化 |

**③ 旧 Memory 类已弃用**

`ConversationBufferMemory`、`ConversationBufferWindowMemory`、`ConversationSummaryMemory`、`ConversationSummaryBufferMemory`、`ConversationEntityMemory` 等属于 0.0.x/0.1.x 时代的「链内记忆」。

- 它们已从主包迁往 `langchain-classic`，官方明确不再作为新项目推荐用法；
- 替代方案：
  - 只需要「消息历史 → 塞进 Prompt」→ **`RunnableWithMessageHistory`**；
  - 需要「持久化 + 可回溯 + 支持人工介入」→ **LangGraph `Checkpointer`**；
  - 需要「自动摘要压缩」→ **Summarization 中间件 / 自建摘要节点**。

**完整可运行示例（现代写法）**

```python
# 依赖：pip install "langchain~=0.3.0" "langchain-openai~=0.3.0"
from langchain_core.chat_history import InMemoryChatMessageHistory
from langchain_core.prompts import ChatPromptTemplate, MessagesPlaceholder
from langchain_core.runnables.history import RunnableWithMessageHistory
from langchain_openai import ChatOpenAI

# 会话历史存储：key 是 session_id，value 是该会话的消息列表
store: dict[str, InMemoryChatMessageHistory] = {}


def get_session_history(session_id: str) -> InMemoryChatMessageHistory:
    """按 session_id 取出（或新建）会话历史。这是 RunnableWithMessageHistory 的约定签名。"""
    if session_id not in store:
        store[session_id] = InMemoryChatMessageHistory()
    return store[session_id]


prompt = ChatPromptTemplate.from_messages(
    [
        ("system", "你是一个简洁的中文助手。"),
        # 历史消息会按顺序填入这里
        MessagesPlaceholder("history"),
        ("human", "{input}"),
    ]
)

chain = prompt | ChatOpenAI(model="gpt-4o-mini", temperature=0)

# 给链挂上「按会话读取/写入历史」的能力
chain_with_history = RunnableWithMessageHistory(
    chain,
    get_session_history,          # 会话历史工厂（必须接收 session_id）
    input_messages_key="input",   # 用户输入在输入字典里的键
    history_messages_key="history",  # 历史消息填入 Prompt 的占位符名
)

config = {"configurable": {"session_id": "user-001"}}

print(chain_with_history.invoke({"input": "你好，我叫小明"}, config=config).content)
# 第二轮会自动带上第一轮的问答
print(chain_with_history.invoke({"input": "我叫什么名字？"}, config=config).content)
```

**LangGraph 的持久化记忆（生产主线）**

```python
from langgraph.checkpoint.memory import MemorySaver
from langgraph.graph import StateGraph, MessagesState, START


def call_model(state: MessagesState):
    # state["messages"] 就是「短期记忆」，由 Checkpointer 自动存取
    reply = ChatOpenAI(model="gpt-4o-mini").invoke(state["messages"])
    return {"messages": [reply]}


builder = StateGraph(MessagesState)
builder.add_node("model", call_model)
builder.add_edge(START, "model")
graph = builder.compile(checkpointer=MemorySaver())  # 换成 SqliteSaver/PostgresSaver 即可持久化

# thread_id 即「会话 ID」，同一 thread_id 的多次调用共享历史
cfg = {"configurable": {"thread_id": "thread-001"}}
graph.invoke({"messages": [("user", "你好")]}, config=cfg)
graph.invoke({"messages": [("user", "我上句说了什么？")]}, config=cfg)
```

**易错点：**

- `ConversationBufferMemory` 这类旧 API 在新文档里已看不到，**面试若答旧写法要主动说明「已弃用，现在用 Checkpointer / RunnableWithMessageHistory」**。
- `RunnableWithMessageHistory` 的历史**不会自动落库**：默认工厂用内存 dict，进程重启即丢；生产必须换成 `SQLChatMessageHistory`、Redis 或直接用 Checkpointer。
- `session_id` 是「会话」而非「用户」；同一用户多标签页应使用不同 `session_id`，否则历史会串。
- LangGraph 0.2.x 中内存 checkpointer 类名为 `MemorySaver`，更新版本已改名为 `InMemorySaver`（`MemorySaver` 作为别名保留），面试提及新旧名称都可，但要说明这是弃用改名而非功能变化。

## 2. 短期记忆与长期记忆的区别

**一句话区分：短期记忆是「这次对话聊了什么」，长期记忆是「这个用户是谁、有什么偏好」。**

| 维度 | 短期记忆（Short-term） | 长期记忆（Long-term） |
| --- | --- | --- |
| 作用范围 | 单个**会话线程** | 跨会话、跨线程 |
| 隔离标识 | `thread_id` / `session_id` | `user_id` + 命名空间（namespace） |
| 存储位置 | LangGraph `State.messages`，随 Checkpointer 持久化 | LangGraph `Store`、向量库、关系型数据库 |
| 生命周期 | 会话期间（可配 TTL 清理） | 长期，需显式写入与删除 |
| 读写方式 | 直接读消息列表，追加新消息 | 语义检索（embedding 相似度）+ 键值查询 |
| 载入 Prompt 的方式 | 全量/裁剪后拼进上下文 | 检索 Top-K 相关条目拼进 Prompt |
| 主要成本 | token 消耗（上下文越长越贵） | 写入时机、检索精度、隐私合规 |
| 典型实现 | `Checkpointer`、`RunnableWithMessageHistory` | `InMemoryStore`、`PostgresStore`、Chroma/pgvector |

**LangGraph 的对应关系：`Checkpointer` 管短期，`Store` 管长期。** 两者可以同时挂载在同一张图上。

```python
from langgraph.checkpoint.memory import MemorySaver
from langgraph.store.memory import InMemoryStore
from langgraph.graph import StateGraph, MessagesState, START


# 长期记忆：按 (namespace, key) 存结构化条目
store = InMemoryStore()
checkpointer = MemorySaver()  # 短期记忆


def call_model(state: MessagesState, config):
    user_id = config["configurable"]["user_id"]

    # 1) 读长期记忆：按用户命名空间做语义检索，取出与当前问题相关的事实
    memories = store.search(("user", user_id), query=state["messages"][-1].content, limit=3)
    facts = "\n".join(m.value["text"] for m in memories)

    system = "以下是与该用户相关的长期信息，请合理利用：\n" + (facts or "（无）")
    messages = [("system", system)] + state["messages"]
    reply = ChatOpenAI(model="gpt-4o-mini").invoke(messages)

    # 2) 写长期记忆：把本轮显式提取出的事实写回（真实系统通常再挂一个抽取节点）
    store.put(("user", user_id), key=f"fact-{len(memories)}", value={"text": "用户偏好简洁回答"})
    return {"messages": [reply]}


builder = StateGraph(MessagesState)
builder.add_node("model", call_model)
builder.add_edge(START, "model")
graph = builder.compile(checkpointer=checkpointer, store=store)

cfg = {"configurable": {"thread_id": "t-1", "user_id": "u-1"}}
graph.invoke({"messages": [("user", "帮我看看这条报错")]}, config=cfg)
```

**面试怎么答：**

1. 先给定义：短期 = 会话内上下文，长期 = 跨会话的用户画像/知识；
2. 再讲实现：短期用 `State.messages` + Checkpointer，长期用 `Store`（或向量库）做语义检索；
3. 最后补实践：**不要把长期记忆全量塞进 Prompt**，应先检索、再裁剪，否则 context 爆炸；长期记忆要有**写入策略**（重要事实才写，避免噪声）。

**易错点：**

- 只做短期记忆的系统，换个会话就"失忆"，这是最常见的产品缺陷；用户说的"你上次答应过我"完全接不住。
- 长期记忆写入需要「去重/更新/删除」，否则同一事实反复累积，检索结果互相冲突。
- `Store` 不是数据库快照：默认 `InMemoryStore` 同样不持久化，生产要换 `PostgresStore`（并调用 `setup()` 建表）。
- 合规：长期记忆涉及个人信息，需支持按用户删除（GDPR 类要求）。

## 3. 如何实现历史消息裁剪

**为什么需要裁剪：** LLM 有上下文窗口上限（如 128K token），历史越长，**成本越高、延迟越大，且关键信息被稀释**（"Lost in the Middle"）。超长时不同模型表现不同：有的直接报 `context_length_exceeded`，有的静默截断。

**三种主流策略：**

| 策略 | 做法 | 优点 | 缺点 | 对应 API |
| --- | --- | --- | --- | --- |
| **滑动窗口** | 只保留最近 N 条消息 / 最近 N token | 实现简单、成本可控 | 早期信息被丢弃 | `trim_messages(strategy="last")` |
| **摘要压缩** | 把旧消息用 LLM 总结成摘要，只保留摘要 + 近期消息 | 保留语义、省 token | 多一次 LLM 调用、摘要可能失真 | Summarization 中间件 / 自建摘要节点 |
| **显式删除** | 从 LangGraph State 中移除指定消息 | 精确控制，可与业务规则联动 | 需自己判断删哪些 | `RemoveMessage` + reducer |

**① `trim_messages`：最常用的裁剪工具（`langchain_core.messages`）**

关键参数：

| 参数 | 含义 |
| --- | --- |
| `max_tokens` | 裁剪后的 token 上限 |
| `strategy` | `"last"` 保留末尾（对话场景默认）、`"first"` 保留开头 |
| `token_counter` | 计数方式：传模型对象按真实 token 计，传函数自定义，传 `len` 则按「消息条数」粗略计 |
| `include_system` | 是否强制保留第一条 System 消息 |
| `allow_partial` | 是否允许把一条长消息截断成半条 |
| `start_on` | 裁剪后首条消息的角色（如 `"human"`），避免出现「连续两条 AI 消息」的非法序列 |

```python
from langchain_core.messages import AIMessage, HumanMessage, SystemMessage, trim_messages
from langchain_openai import ChatOpenAI

llm = ChatOpenAI(model="gpt-4o-mini")

# 保留最近 1500 token，必须包含 System 消息，且裁剪后不能以半条消息开头
trimmer = trim_messages(
    max_tokens=1500,
    strategy="last",            # 从末尾往前保留
    token_counter=llm,          # 用模型自带 tokenizer 精确计数
    include_system=True,        # 系统提示不能被裁掉
    allow_partial=False,        # 不切半条消息
    start_on="human",           # 裁剪后的第一条必须是 human，保证角色交替合法
)

messages = [
    SystemMessage("你是一个严谨的中文技术助手。"),
    HumanMessage("问题一"),
    AIMessage("回答一"),
    HumanMessage("问题二"),
    AIMessage("回答二"),
    # ... 大量历史 ...
    HumanMessage("当前问题"),
]

trimmed = trimmer.invoke(messages)
print([m.type for m in trimmed])  # 系统消息 + 最近若干轮
```

**② 在 LCEL 链里自动裁剪（每次调用前先裁）**

```python
from langchain_core.prompts import ChatPromptTemplate, MessagesPlaceholder
from langchain_core.runnables import RunnableLambda

prompt = ChatPromptTemplate.from_messages(
    [("system", "你是中文助手。"), MessagesPlaceholder("history"), ("human", "{input}")]
)

chain = (
    # 调用前对 history 做一次裁剪，只保留最近的 token 预算
    RunnableLambda(lambda x: {**x, "history": trimmer.invoke(x["history"])})
    | prompt
    | llm
)
```

**③ LangGraph 中用 `RemoveMessage` 主动删消息**

```python
from langchain_core.messages import RemoveMessage


def prune_node(state: MessagesState):
    """只保留最近 10 条消息（外加一条摘要，此处省略摘要生成）。"""
    if len(state["messages"]) <= 10:
        return {}
    # 给每条要删除的消息返回一个 RemoveMessage（带原消息 id），由 reducer 移除
    return {"messages": [RemoveMessage(id=m.id) for m in state["messages"][:-10]]}
```

> 提示：`MessagesState` 用的是 `add_messages` reducer，`RemoveMessage` 是它约定的「删除指令」，必须携带原消息 `id` 才有效。

**④ 摘要压缩（无需保留原始消息时的更优解）**

思路：设置一个 token 阈值，超过阈值时调用一次 LLM，把「被裁掉的消息」总结成一段 `SystemMessage` 摘要，与最近消息一起带着走。LangChain v1 提供 `summarizationMiddleware`，0.3.x 中可自建节点实现同样的逻辑。

**易错点：**

- `strategy="last"` 裁剪后首条可能是 AI 消息，部分模型（尤其 Anthropic、Gemini）会报「必须以 user 消息开头」→ 设 `start_on="human"`。
- `token_counter=len` 时 `max_tokens=100` 其实表示「最多 100 条消息」，**极易误解**，只适合粗略估算。
- 裁剪会丢信息，重要约束（如「必须用 JSON 输出」）应固定写在 System 消息里，并设 `include_system=True`。
- 摘要压缩要**控制摘要本身的长度**并增量更新，否则摘要会越滚越长，等于没压。

## 4. LangServe 的作用

**LangServe** 的作用：把任意 `Runnable`（链 / Agent / 图）**零改动地暴露成 HTTP 服务**，自动生成一套标准的 REST 端点、OpenAPI schema 和在线调试页面，让「LangChain 应用」快速变成「可被前端/其他服务调用的 API」。

**核心能力：**

| 能力 | 说明 |
| --- | --- |
| 一键路由 | `add_routes(app, chain, path="/chat")` 自动注册全部端点 |
| 标准端点集 | `/invoke`、`/batch`、`/stream`、`/stream_log`、`/playground` 等 |
| 自动 Schema | 由 Runnable 的输入输出类型自动推导出 OpenAPI / JSON Schema |
| 调试页面 | `/playground` 提供可视化试调界面，无需自己写前端 |
| 服务端配置 | 支持把常见的 `config`（如 `session_id`）固化成独立端点 |
| 客户端 | `RemoteRunnable("http://host/chat")` 可当作本地 Runnable 直接使用 |

**标准端点对照：**

| 端点 | 方法 | 作用 |
| --- | --- | --- |
| `/chat/invoke` | POST | 单次调用，返回完整结果 |
| `/chat/batch` | POST | 批量输入，内部并行处理 |
| `/chat/stream` | POST | SSE 流式返回最终输出 |
| `/chat/stream_log` | POST | 流式返回**中间步骤**日志（调试链内部非常有用） |
| `/chat/playground` | GET | 自动生成的交互调试页 |
| `/chat/input_schema` `/output_schema` `/config_schema` | GET | 自动生成的 schema |
| `/chat/c/{config_hash}/...` | - | 内置固定配置的等价端点 |

```python
# server.py
# 依赖：pip install "langserve~=0.3.0" fastapi uvicorn sse-starlette
from fastapi import FastAPI
from langchain_core.prompts import ChatPromptTemplate
from langchain_openai import ChatOpenAI
from langserve import add_routes

prompt = ChatPromptTemplate.from_template("用一句话回答：{question}")
chain = prompt | ChatOpenAI(model="gpt-4o-mini")

app = FastAPI(title="LangChain 服务")

# 一行代码把链接入到 /chat 路径下，端点、schema、playground 全部自动生成
add_routes(app, chain, path="/chat")

if __name__ == "__main__":
    import uvicorn

    uvicorn.run(app, host="0.0.0.0", port=8000)
```

```bash
# 启动后即可直接调用
curl -X POST http://localhost:8000/chat/invoke \
  -H "Content-Type: application/json" \
  -d '{"input": {"question": "什么是 LCEL？"}}'

# 流式
curl -X POST http://localhost:8000/chat/stream \
  -H "Content-Type: application/json" \
  -d '{"input": {"question": "什么是 LCEL？"}}'
```

```python
# 客户端：把远端服务当作一个 Runnable 用
from langserve import RemoteRunnable

remote_chain = RemoteRunnable("http://localhost:8000/chat/")
print(remote_chain.invoke({"question": "什么是 LCEL？"}).content)

# 远端也支持流式与批处理，接口与本地一致
for chunk in remote_chain.stream({"question": "什么是 LCEL？"}):
    print(chunk.content, end="", flush=True)
```

**面试怎么答：**「LangServe 是 LangChain 的**部署层**——把 Runnable 直接变成 REST API，自动带 schema 与 playground，省掉手写 FastAPI 样板代码；它解决的是『链写好了怎么让前端/别的服务调用』。」

**现状与局限（重要）：**

- LangServe 目前处于**维护状态（不再积极演进）**，官方对复杂 Agent 应用的推荐路径是 **LangGraph Platform（已更名为 LangSmith Deployment）** 或自建 FastAPI 服务。
- 因此面试时更稳妥的说法是：**LangServe 适合快速把无状态链暴露为 API；需要持久化状态、长任务、人工介入时，用 LangGraph + 自建服务或托管平台。**
- LangServe 的 `config` 传入不直观、流式细节受限、无状态（会话历史要靠外部存储）是它被更复杂方案取代的主因。

**易错点：**

- `add_routes` 时 chain 的输入是**字典**，请求体形如 `{"input": {...}}`，直接平铺字段会 422。
- LangServe 默认只暴露 `invoke` 类端点；要启用 `stream_log` 需要额外配置，且前端要会解析 SSE。
- 不要用 `uvicorn --reload` 上生产；也不要指望 LangServe 帮你管会话（它不内置持久化）。

## 5. LangSmith 如何做追踪与评估

**LangSmith** 是 LangChain 官方的可观测与评估平台，三大块能力：**Trace（追踪）→ Dataset & Experiment（数据集与实验）→ Evaluation（评估）**，另外还有 Monitoring（在线监控）与 Prompt Hub（提示词管理）。

**① 开启追踪：只靠环境变量（零代码改动）**

```bash
# 现代变量名（推荐）
export LANGSMITH_TRACING=true
export LANGSMITH_API_KEY="lsv2_pt_xxxxxxxx"
export LANGSMITH_ENDPOINT="https://api.smith.langchain.com"   # 自建/私有化时改这里
export LANGSMITH_PROJECT="my-langchain-app"                    # 不设则进 default 项目
```

**与旧变量名的关系：**

| 现代变量 | 旧变量（仍兼容） | 说明 |
| --- | --- | --- |
| `LANGSMITH_TRACING` | `LANGCHAIN_TRACING_V2` | 是否开启追踪 |
| `LANGSMITH_API_KEY` | `LANGCHAIN_API_KEY` | API Key |
| `LANGSMITH_ENDPOINT` | `LANGCHAIN_ENDPOINT` | 服务地址 |
| `LANGSMITH_PROJECT` | `LANGCHAIN_PROJECT` | 项目名 |

> 品牌从「LangChain Hub / LANGCHAIN_*」统一迁到「LangSmith / LANGSMITH_*」。**新代码一律用 `LANGSMITH_*`，旧变量作为兼容别名仍然有效**，面试说明这一点即可。

```python
# 也支持代码内设置（不推荐硬编码密钥，这里仅演示键名）
import os
os.environ["LANGSMITH_TRACING"] = "true"
os.environ["LANGSMITH_API_KEY"] = os.environ["LS_KEY"]  # 从密钥管理读取
```

**② 追踪粒度：自动 + 手动**

- **自动**：任何 Runnable 的 `invoke/stream/batch`、LangGraph 节点、工具调用都会自动生成 Run 树（父子嵌套、参数、耗时、token）。
- **手动**：给普通 Python 函数加 `@traceable`，即可纳入同一 Trace。

```python
from langsmith import traceable


@traceable(run_type="tool", name="clean_text")
def clean_text(raw: str) -> str:
    """非 LangChain 组件的函数，用 @traceable 手动接入追踪。"""
    return raw.strip().replace("\n\n", "\n")
```

**③ 评估：Dataset + evaluator + `evaluate()`**

流程固定三步：**建数据集 → 跑被试（target）→ 用 evaluator 打分**。

```python
from langsmith import Client, evaluate

client = Client()

# 1) 建数据集（也可以在 LangSmith 网页上创建后再拉取）
dataset = client.create_dataset(dataset_name="qa-eval-demo", description="FAQ 回归测试")
client.create_examples(
    dataset_id=dataset.id,
    examples=[
        {"inputs": {"question": "什么是 LCEL？"}, "outputs": {"answer": "LangChain 表达式语言"}},
        {"inputs": {"question": "什么是 RAG？"}, "outputs": {"answer": "检索增强生成"}},
    ],
)

# 2) 被试函数：输入 example.inputs，返回实际输出
def target(inputs: dict) -> dict:
    return {"answer": chain.invoke({"question": inputs["question"]}).content}


# 3) evaluator：可用规则（精确匹配），也可用 LLM-as-Judge
def exact_match(run, example) -> dict:
    return {"key": "exact_match", "score": float(run.outputs["answer"] == example.outputs["answer"])}


def llm_judge(run, example) -> dict:
    """用另一个模型当裁判，按 0~1 打分。"""
    judge = ChatOpenAI(model="gpt-4o-mini", temperature=0)
    prompt = (
        "请判断【回答】是否准确回答了【问题】，只输出 0 到 1 的数字：\n"
        f"问题：{example.inputs['question']}\n回答：{run.outputs['answer']}"
    )
    score = float(judge.invoke(prompt).content.strip())
    return {"key": "llm_judge", "score": score}


results = evaluate(
    target,
    data="qa-eval-demo",
    evaluators=[exact_match, llm_judge],
    experiment_prefix="prompt-v2",
)
```

**④ 生产监控：** 打开 Tracing 后，LangSmith 会自动统计**延迟、错误率、token 成本、调用量**，并支持按 `metadata`/`tags` 过滤（如按 `user_id`、`version` 切片对比），还能建在线 evaluator 对线上流量抽样打分。

**面试怎么答：** 「LangSmith = LangChain 的 DevTools：开发期用它看每次调用的完整 Run 树定位问题；上线后用它做数据集回归评估和线上质量监控；评估的核心是 Dataset + evaluator（规则或 LLM-as-Judge）」。**注意区分：LangSmith 是平台，RAGAS 是评估指标库（见第 10 题），两者可互补。**

**易错点：**

- 追踪是**异步上报**的：进程异常退出（如硬 kill）可能丢最后几个 Run；长驻服务正常退出时会刷盘。
- 别把 API Key 写进代码或提交到 Git；用环境变量或密钥服务。
- `evaluate` 里的 target 必须是**纯函数**（无副作用、确定性），否则实验结果不可复现。
- 数据敏感：企业数据上传到 SaaS 版 LangSmith 需要评估合规，可申请自建/私有化部署。

## 6. Callbacks 与回调机制

**Callbacks** 是 LangChain 的**事件钩子体系**：在链/模型/工具/检索器的生命周期节点上触发回调，让你做**日志、监控、Token 统计、流式转发、人工审核、异常捕获**，而不用侵入业务代码。

**核心类：**

| 类 | 说明 |
| --- | --- |
| `BaseCallbackHandler` | 同步回调基类，重写你关心的事件方法 |
| `AsyncCallbackHandler` | 异步版，`await` 友好；**异步链中混用同步 handler 会阻塞事件循环** |
| `BaseCallbackManager` | 事件分发器；`CallbackManager`（旧）/ `AsyncCallbackManager` |
| `RunnableConfig.callbacks` | 每次调用时传入的 handler 列表，支持继承/局部作用域 |

**常用事件钩子：**

| 事件 | 触发时机 | 典型用途 |
| --- | --- | --- |
| `on_chain_start` / `on_chain_end` / `on_chain_error` | 链开始/结束/出错 | 计时、埋点、错误上报 |
| `on_llm_start` / `on_chat_model_start` | 调模型前 | 记录输入、审计 prompt |
| `on_llm_new_token` | 流式收到一个 token | 转发给前端、实现打字机效果 |
| `on_llm_end` / `on_llm_error` | 模型返回/出错 | **统计 token 与成本**、重试逻辑 |
| `on_tool_start` / `on_tool_end` / `on_tool_error` | 工具调用前后 | 记录工具轨迹、权限审计 |
| `on_retriever_start` / `on_retriever_end` | 检索前后 | 记录召回了哪些文档 |
| `on_agent_action` | Agent 决定动作 | 观测决策过程 |
| `on_retry` | 重试发生 | 监控模型不稳定 |

**三种传入方式（作用域从大到小）：**

| 方式 | 写法 | 作用域 |
| --- | --- | --- |
| 构造时绑定 | `ChatOpenAI(callbacks=[handler])` | 该组件所有调用 |
| 调用时传入 | `chain.invoke(x, config={"callbacks": [handler]})` | 本次调用（含子链） |
| 全局隐式 | （LangSmith 通过环境变量开启，不走 callbacks 显式传递） | 全局 |

```python
# 统计每次 LLM 调用的 token 与成本，并打印耗时
import time
from langchain_core.callbacks import BaseCallbackHandler
from langchain_openai import ChatOpenAI
from langchain_core.prompts import ChatPromptTemplate


class UsageCostHandler(BaseCallbackHandler):
    """记录调用耗时、token 用量并估算成本。"""

    def __init__(self, price_in_per_1k: float = 0.00015, price_out_per_1k: float = 0.0006):
        self.price_in_per_1k = price_in_per_1k
        self.price_out_per_1k = price_out_per_1k
        self.total_cost = 0.0
        self._start = 0.0

    def on_chat_model_start(self, serialized, messages, **kwargs):
        self._start = time.perf_counter()

    def on_llm_end(self, response, **kwargs):
        elapsed = time.perf_counter() - self._start

        # 0.3.x 起 token 用量优先从消息的 usage_metadata 读取
        usage = None
        for gen_list in response.generations:
            for gen in gen_list:
                msg = getattr(gen, "message", None)
                usage = getattr(msg, "usage_metadata", None) or usage
        usage = usage or response.llm_output.get("token_usage", {})

        in_tok = usage.get("input_tokens") or usage.get("prompt_tokens", 0)
        out_tok = usage.get("output_tokens") or usage.get("completion_tokens", 0)

        cost = in_tok / 1000 * self.price_in_per_1k + out_tok / 1000 * self.price_out_per_1k
        self.total_cost += cost
        print(f"[LLM] 耗时 {elapsed:.2f}s | 输入 {in_tok} | 输出 {out_tok} | 本次成本 ${cost:.6f}")


handler = UsageCostHandler()
llm = ChatOpenAI(model="gpt-4o-mini")

chain = ChatPromptTemplate.from_template("{q}") | llm
# handler 通过 config 传入，本次调用链上所有子 Runnable 都会触发
print(chain.invoke({"q": "用一句话解释什么是回调"}, config={"callbacks": [handler]}).content)
print(f"累计成本：${handler.total_cost:.6f}")
```

**流式场景下的回调：**

```python
class PrintTokens(BaseCallbackHandler):
    def on_llm_new_token(self, token: str, **kwargs):
        print(token, end="", flush=True)


chain.invoke({"q": "讲个笑话"}, config={"callbacks": [PrintTokens()]})
```

**易错点：**

- **异步链里用同步 handler**：`on_llm_end` 里做阻塞 IO（同步写库、同步 HTTP）会拖慢甚至卡死事件循环 → 异步场景应继承 `AsyncCallbackHandler`。
- handler 必须**线程安全**：多线程/多协程共享同一 handler 时，像上面 `self._start` 这种实例状态会被覆盖，需用 `threading.local()` 或按 run_id 存字典。
- `on_llm_new_token` 只在**流式调用**（`stream`/`astream`）时触发，`invoke` 不会触发。
- 回调异常默认会**向上抛出**（`raise_error=True`），handler 内要自己 try/except，否则监控代码的 bug 会打断正常业务。
- Token 字段在不同厂商命名不一致（OpenAI 用 `prompt_tokens`/`completion_tokens`，统一层给的是 `input_tokens`/`output_tokens`），统计时要做兼容。

## 7. Token 统计与成本控制

**是什么：** LLM 按 token 计费，统计 token 是所有成本优化的前提。统计口径分**输入 token（prompt）**与**输出 token（completion）**，输出通常贵数倍。

**① 三种统计方式**

| 方式 | 做法 | 适用 |
| --- | --- | --- |
| 响应字段 | 读 `AIMessage.usage_metadata`（0.3.x 统一字段） | 单次调用后立即取数，最准 |
| Callback 累计 | `on_llm_end` 累加（见第 6 题） | 全链路汇总、监控上报 |
| 本地预估 | `tiktoken` 编码计数，或 `llm.get_num_tokens(text)` | **调用前**预算控制、裁剪判断 |

```python
from langchain_openai import ChatOpenAI

llm = ChatOpenAI(model="gpt-4o-mini")
resp = llm.invoke("用三句话介绍 RAG")

# 统一用量字段（0.3.x）
print(resp.usage_metadata)
# {'input_tokens': 12, 'output_tokens': 58, 'total_tokens': 70}

# 原始响应里还保留厂商字段，作兜底
print(resp.response_metadata.get("token_usage"))

# 调用前预估输入 token（用于裁剪与预算）
print(llm.get_num_tokens("这是一段待估算的文本"))
```

**② 成本控制的手段（按性价比排序）**

| 手段 | 说明 | 典型案例 |
| --- | --- | --- |
| **缓存** | 相同/相似请求直接命中缓存（第 8 题） | 重复 FAQ、开发期反复调试 |
| **模型分级路由** | 简单任务走小模型、复杂任务走大模型 | 意图分类用 `gpt-4o-mini`，推理用旗舰 |
| **裁剪与压缩上下文** | `trim_messages`、摘要压缩、只召回 Top-K | RAG 少塞无关文档 |
| **限制 `max_tokens`** | 给输出设上限，防「跑飞」 | 结构化抽取场景 |
| **批处理** | 多请求合并（`batch`、批量 embedding） | 离线批量打标 |
| **精简 Prompt** | 去掉冗余示例、压缩 System 指令 | Few-shot 示例数量收敛 |
| **监控告警** | 按日/按用户统计，设预算阈值 | 防止单用户刷爆账单 |
| **语义缓存** | 相似问题复用答案（成本换准确率） | 客服问答 |
| **Prompt Caching** | 厂商级前缀缓存（见第 8 题） | 长 System + 固定前缀场景 |

```python
# 分级路由 + 输出上限 + 预算预估的组合示例
from langchain_openai import ChatOpenAI
from langchain_core.prompts import ChatPromptTemplate

# 便宜模型做路由判断，贵模型做最终回答
router = ChatOpenAI(model="gpt-4o-mini", temperature=0, max_tokens=8)
solver = ChatOpenAI(model="gpt-4o", temperature=0, max_tokens=500)  # 输出设上限

route_prompt = ChatPromptTemplate.from_template(
    "判断下面问题是否需要复杂推理，只回答 simple 或 complex：{q}"
)


def smart_call(q: str):
    kind = router.invoke(route_prompt.format(q=q)).content.strip().lower()
    model = solver if kind.startswith("complex") else router
    answer = model.invoke(q)
    # 打印用量，便于按用户/接口维度统计成本
    print(kind, answer.usage_metadata)
    return answer.content


print(smart_call("1+1 等于几"))
print(smart_call("推导这个算法的时间复杂度并给出证明思路"))
```

**面试怎么答：** 「先说统计三种口径（响应字段最准、回调做聚合、本地估算做预算），再说控制手段按『缓存 > 路由 > 裁剪 > 限额 > 监控』排序，最后落到监控——没有监控的成本优化都是盲猜。」

**易错点：**

- `usage_metadata` 在**流式调用**时通常**只在最后一个合并 chunk 上完整**，中途 chunk 可能为空，别在中途就断言取不到。
- 本地 `tiktoken` 计数与厂商真实计费**不完全一致**（Chat 格式还有每条消息的固定开销），只适合做预算估算。
- 推理模型（o 系列）的 token 计费含**隐藏的 reasoning token**，`max_tokens` 语义也变为「可见输出」上限，成本模型要单独评估。
- 缓存/路由会引入**成本与准确率的权衡**，属于业务决策，不能只谈省钱。

## 8. 缓存机制与使用方式

**缓存的目的：** 命中缓存时**跳过 LLM 调用**，既省钱又降延迟，还能提高同一输入下输出的一致性。

**① 全局 LLM 缓存（`set_llm_cache`）**

```python
# 内存缓存：进程内有效，重启即失，适合开发与单实例
from langchain_core.caches import InMemoryCache
from langchain_core.globals import set_llm_cache

set_llm_cache(InMemoryCache())
```

```python
# SQLite 缓存：跨进程重启依然有效，适合单机/小规模
from langchain_community.cache import SQLiteCache
from langchain_core.globals import set_llm_cache

set_llm_cache(SQLiteCache(database_path=".langchain.db"))
```

```python
# Redis 缓存（精确匹配）；也可用 RedisSemanticCache 做语义相似命中
from langchain_community.cache import RedisCache
from langchain_core.globals import set_llm_cache
from redis import Redis

redis_client = Redis.from_url("redis://localhost:6379/0")
set_llm_cache(RedisCache(redis_client, ttl=3600))  # ttl 单位秒
```

设置后**代码无需改动**：同一模型 + 同一输入第二次调用直接返回缓存结果。

**② 缓存类型对比**

| 类型 | 实现 | 命中判定 | 持久化 | 适用 |
| --- | --- | --- | --- | --- |
| 内存缓存 | `InMemoryCache` | 精确匹配 | 否 | 开发、单实例 |
| SQLite 缓存 | `SQLiteCache` | 精确匹配 | 是（本地文件） | 单机、小规模 |
| Redis 缓存 | `RedisCache` | 精确匹配 | 是 | 多实例共享 |
| 语义缓存 | `RedisSemanticCache` / `GPTCache` 思路 | embedding 相似度 ≥ 阈值 | 是 | 客服、FAQ 类重复问题 |
| Prompt Caching | 厂商能力（Anthropic/OpenAI 等） | 前缀完全一致 | 服务端 | 长 System + 固定前缀 |
| 图内节点缓存 | LangGraph `CachePolicy`（按节点） | 按节点输入 | 视后端而定 | 昂贵节点的结果复用 |

> 提示：**精确缓存**与 **Prompt Caching 不是一回事**。前者按「模型 + 完整输入」做键值匹配；后者是厂商侧对「输入前缀」做的 KV 复用，两者可叠加。

**③ 生产用法：只缓存确定性请求**

```python
from langchain_core.caches import InMemoryCache
from langchain_core.globals import set_llm_cache
from langchain_openai import ChatOpenAI

set_llm_cache(InMemoryCache())
llm = ChatOpenAI(model="gpt-4o-mini", temperature=0)  # temperature>0 时缓存会掩盖随机性

# 场景一：结构化抽取（确定性任务，适合缓存）
print(llm.invoke("把『北京 25 度晴』抽成 JSON").content)  # 第一次：真实调用
print(llm.invoke("把『北京 25 度晴』抽成 JSON").content)  # 第二次：命中缓存，几乎瞬时
```

**④ 语义缓存的取舍（概念示例）**

语义缓存用 embedding 相似度决定是否复用答案：命中率高但**存在误命中风险**（把「可以退货吗」和「可以换货吗」判为同一问题会给错答案）。生产上通常会：

- 对阈值做保守设置（如 0.95 以上），并**只对非敏感、低风险问题**开启；
- 结合业务白名单（仅 FAQ 类）使用，不对长尾开放式问题生效。

**易错点：**

- 缓存的键包含 `temperature` 等参数吗？**键是「模型标识 + 完整输入（含消息序列） + 参数」**，参数变了不会命中；但 `temperature>0` 的随机性会被缓存吃掉，测试时要注意。
- `SQLiteCache` 在多进程/高并发下会**锁库**，高并发生产应换 Redis。
- 语义缓存误命中是**线上事故的常见来源**（答非所问），务必设阈值 + 灰度。
- 缓存不会自动失效：知识更新后需要 `clear()` 或按 TTL 过期，否则会持续返回旧答案。

## 9. 如何做流式响应到前端

**为什么流式：** LLM 首 token 延迟（TTFT）远小于完整生成时间，流式能显著改善体感，是现代 LLM 应用的默认交互方式。

**① 三条流式接口（LCEL）**

| 接口 | 产出 | 适用 |
| --- | --- | --- |
| `stream` / `astream` | 最终输出的**增量 chunk** | 最简单，纯打字机效果 |
| `astream_events` | 全链路**事件流**（含中间步骤、工具、检索） | 需要展示「思考过程/工具调用」 |
| LangGraph `astream(stream_mode=...)` | `values`/`updates`/`messages` 等多种模式 | 图/Agent 场景 |

```python
from langchain_openai import ChatOpenAI
from langchain_core.prompts import ChatPromptTemplate

chain = ChatPromptTemplate.from_template("{q}") | ChatOpenAI(model="gpt-4o-mini")

# 每个 chunk 是一个 AIMessageChunk，增量在 .content
for chunk in chain.stream({"q": "用三句话介绍流式响应"}):
    print(chunk.content, end="", flush=True)
```

**② FastAPI + SSE 推给前端（生产常用）**

```python
# app.py  依赖：fastapi uvicorn
import json
from fastapi import FastAPI
from fastapi.middleware.cors import CORSMiddleware
from fastapi.responses import StreamingResponse
from langchain_core.prompts import ChatPromptTemplate
from langchain_openai import ChatOpenAI

app = FastAPI()
app.add_middleware(
    CORSMiddleware,
    allow_origins=["https://your-frontend.com"],  # 生产务必收窄来源
    allow_methods=["POST"],
    allow_headers=["*"],
)

chain = ChatPromptTemplate.from_template("{q}") | ChatOpenAI(model="gpt-4o-mini", temperature=0)


@app.post("/chat/stream")
async def chat_stream(payload: dict):
    async def event_stream():
        try:
            # 关键：用 astream，不要用同步 stream，避免阻塞事件循环
            async for chunk in chain.astream({"q": payload["q"]}):
                if chunk.content:
                    data = json.dumps({"delta": chunk.content}, ensure_ascii=False)
                    yield f"data: {data}\n\n"
            yield "data: [DONE]\n\n"
        except Exception as exc:  # 出错也要给前端一个终止信号
            yield f"data: {json.dumps({'error': str(exc)}, ensure_ascii=False)}\n\n"

    return StreamingResponse(
        event_stream(),
        media_type="text/event-stream",
        headers={"Cache-Control": "no-cache", "X-Accel-Buffering": "no"},  # 关闭 Nginx 缓冲
    )
```

```javascript
// 前端：用 fetch + ReadableStream 解析 SSE（EventSource 不能发 POST，故手写解析）
const res = await fetch("/chat/stream", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ q: "用三句话介绍流式响应" }),
});

const reader = res.body.getReader();
const decoder = new TextDecoder("utf-8");
let buffer = "";

while (true) {
  const { value, done } = await reader.read();
  if (done) break;
  buffer += decoder.decode(value, { stream: true });

  // SSE 以空行分隔事件
  const parts = buffer.split("\n\n");
  buffer = parts.pop();

  for (const part of parts) {
    const line = part.trim();
    if (!line.startsWith("data:")) continue;
    const data = line.slice(5).trim();
    if (data === "[DONE]") return;
    console.log(JSON.parse(data).delta); // 逐段追加到界面
  }
}
```

**③ 想要「展示工具调用过程」→ 用 `astream_events`**

```python
async def run():
    async for event in chain.astream_events({"q": "北京今天天气如何"}, version="v2"):
        # 事件类型：on_chat_model_stream / on_llm_new_token / on_tool_start / on_chain_end ...
        if event["event"] == "on_chat_model_stream":
            chunk = event["data"]["chunk"]
            if chunk.content:
                print(chunk.content, end="", flush=True)
```

**面试怎么答：** 「流式要分两层讲：**后端**用 `astream`（异步、不阻塞事件循环）把 chunk 包成 SSE，用 `StreamingResponse` 返回；**前端**用 `fetch` + `ReadableStream`（或 `EventSource` 只读 GET）逐块解析渲染。要展示中间步骤就用 `astream_events`。**工程上必须处理 Nginx 缓冲（`X-Accel-Buffering: no`）、心跳保活、客户端断开与异常终止信号**。」

**易错点：**

- 后端用同步 `stream()` 塞进 `async def` 会**阻塞事件循环**，高并发下整体卡死 → 必须 `astream`。
- Nginx 默认会**缓冲**响应，导致前端「一次性收到全部内容」；需 `proxy_buffering off` 或加 `X-Accel-Buffering: no`。
- SSE 要求 `Content-Type: text/event-stream` 且消息以 `\n\n` 结尾，缺一不可。
- 客户端中途关闭连接时，要配合 `try/finally`（或 `asyncio.CancelledError`）释放 LLM 连接，否则会浪费算力。
- 不要在流式响应上再加「响应压缩」中间件（gzip 会破坏增量到达）。

## 10. 如何评估 RAG 与 Agent 效果

**为什么必须评估：** LLM 输出不固定，"看起来挺好"不能作为上线依据。评估要**分层**：检索层（有没有找对资料）、生成层（有没有用好资料）、端到端（用户是否满意）。

**① RAG 评估指标（RAGAS 核心）**

| 指标 | 层 | 含义 | 低了怎么优化 |
| --- | --- | --- | --- |
| **Faithfulness（忠实度）** | 生成 | 答案是否**完全依据**上下文，无编造 | 收紧 Prompt（「只依据资料作答」）、降低无关上下文 |
| **Answer Relevancy（答案相关性）** | 生成 | 答案与问题的相关程度，惩罚冗余/答非所问 | 优化 Prompt、提高检索精度 |
| **Context Precision（上下文精度）** | 检索 | 召回的上下文里，相关资料是否**排在前面** | 加 Rerank、调检索策略 |
| **Context Recall（上下文召回）** | 检索 | 参考答案需要的信息是否**都被召回** | 提高 `k`、混合检索、查询改写 |
| **Answer Correctness（答案正确性）** | 端到端 | 与标准答案的事实+语义一致度 | 综合优化 |

```python
# RAGAS 评估（经典用法；0.3+ 已改为 EvaluationDataset / PascalCase 指标类，思路一致）
# 依赖：pip install ragas datasets langchain-openai
from datasets import Dataset
from ragas import evaluate
from ragas.metrics import faithfulness, answer_relevancy, context_precision, context_recall

# 每条样本：问题、系统回答、召回的上下文列表、（可选）标准答案
data = {
    "question": ["LangChain 是什么？", "什么是 RAG？"],
    "answer": ["LangChain 是构建 LLM 应用的框架。", "RAG 是检索增强生成。"],
    "contexts": [["LangChain 是……的框架。", "它提供 Runnable 抽象。"], ["RAG 先检索再生成。"]],
    "ground_truth": ["LangChain 是构建 LLM 应用的框架。", "RAG 是先检索后生成的方法。"],
}

result = evaluate(
    Dataset.from_dict(data),
    metrics=[faithfulness, answer_relevancy, context_precision, context_recall],
)
print(result)          # 各指标 0~1 的得分
print(result.to_pandas())
```

> 提示：RAGAS 的 `faithfulness`/`context_precision` 等指标**依赖 LLM 判分**，需要配置裁判模型（`ChatOpenAI` 等）；评估本身也要花钱，建议用小数据集 + 便宜模型定期跑。

**② LLM-as-Judge（不依赖标准答案的通用做法）**

适合开放式问答：让裁判模型按**明确评分细则（rubric）**打分，比"像不像"更稳定。

```python
from langchain_openai import ChatOpenAI
import json

judge = ChatOpenAI(model="gpt-4o-mini", temperature=0)

JUDGE_TEMPLATE = """你是严格的技术答案评审。请按 0~5 给下面的回答打分，只输出 JSON。
评分维度：
- 正确性：事实是否准确
- 完整性：是否覆盖问题要点
- 简洁性：有无冗余废话

问题：{question}
回答：{answer}

输出格式：{{"正确性": 0-5, "完整性": 0-5, "简洁性": 0-5, "理由": "..."}}"""


def judge_answer(question: str, answer: str) -> dict:
    raw = judge.invoke(JUDGE_TEMPLATE.format(question=question, answer=answer)).content
    return json.loads(raw.strip().removeprefix("```json").removesuffix("```"))


print(judge_answer("什么是 RAG？", "RAG 是把检索和大模型结合起来的方法。"))
```

**③ Agent 评估：和 RAG 不一样**

Agent 的输出是**动作序列**，评估要看成败与轨迹：

| 维度 | 指标 | 说明 |
| --- | --- | --- |
| 任务结果 | 成功率 / 完成率 | 端到端是否能完成任务 |
| 工具调用 | 工具选择正确率、参数正确率 | 是否调对工具、传对参数 |
| 效率 | 步数 / 迭代次数 / 耗时 / 成本 | 是否绕远路（ReAct 打转） |
| 轨迹质量 | 动作序列与理想轨迹的匹配度 | 常用 LLM-as-Judge 评「轨迹是否合理」 |
| 鲁棒性 | 异常注入下的表现 | 工具报错、超时后能否自恢复 |
| 安全性 | 越权/危险操作拦截率 | 是否会被诱导执行破坏性动作 |

**LangSmith 侧的统一做法：** 把上面这些做成 evaluator，用第 5 题的 `evaluate(target, data, evaluators)` 跑数据集回归，做到「改了 Prompt 就能量化对比」。

**面试怎么答：** 「RAG 用 RAGAS 四件套（faithfulness / answer relevancy / context precision / context recall）分层定位问题：context recall 低是检索问题，faithfulness 低是幻觉问题；Agent 没有标准答案，用成功率 + 工具调用正确率 + 步数 + LLM-as-Judge 评轨迹；工程上都要挂到 LangSmith 做回归。」

**易错点：**

- 评估指标**必须绑定数据集**：没有标准集就没法比较版本优劣。
- 单看 overall 分数会掩盖问题，要**分维度看**（检索 vs 生成）。
- LLM-as-Judge 有**位置偏差/长度偏差**（偏爱长答案、偏爱先出现的选项），要随机化顺序、统一长度、给明确 rubric。
- RAGAS 指标本身也是 LLM 判分，**裁判模型换一次分数可能整体偏移**，跨版本比较要用同一裁判模型。

## 11. 版本兼容与依赖管理

**背景：LangChain 在 0.1 → 0.2 → 0.3 之间做了大规模「瘦身拆分」**，理解包结构是排查兼容问题的前提。

| 包 | 职责 | 稳定性 |
| --- | --- | --- |
| `langchain-core` | Runnable、Prompt、Message、OutputParser 等**抽象接口** | 最稳定，许多 partner 包依赖它的版本区间 |
| `langchain` | 元包，聚合常用组件（旧 Chain/Memory 已迁往 `langchain-classic`） | 版本演进快 |
| `langchain-community` | 社区集成（Loader/VectorStore/Tool/Cache） | 质量参差，接口可能变动 |
| `langchain-openai` / `langchain-anthropic` / … | 厂商 partner 包 | 与 `langchain-core` 强绑定版本区间 |
| `langgraph` + `langgraph-checkpoint-*` | 有状态编排与持久化 | 与 `langchain-core` 有兼容要求 |

**核心规则：**

1. **`langchain-core` 是版本兼容的锚点。** 各 partner 包在 `pyproject.toml` 里声明了 `langchain-core>=X,<Y`，装错了就会 `ImportError` 或运行时报 `AttributeError`。
2. **不要手写「精确版本」硬锁**，用**兼容版本号**（`~=`）并在 lock 文件里固定精确版本。
3. **升级要自底向上**：先升 `langchain-core`，再升 partner 包，最后升 `langchain`/`langgraph`；一次升一个。
4. **`langchain-classic` 承接旧 API**：还在用 `LLMChain`、`ConversationBufferMemory` 的老代码，要靠它运行，但应尽快迁移。

```text
# requirements.txt（推荐用兼容版本号，具体补丁版本交给 lock 文件）
langchain~=0.3.0
langchain-core~=0.3.0
langchain-community~=0.3.0
langchain-openai~=0.3.0
langgraph~=0.2.0
langgraph-checkpoint-sqlite~=2.0.0
langgraph-checkpoint-postgres~=2.0.0
langserve~=0.3.0
pydantic~=2.7.0
```

```bash
pip install -r requirements.txt
pip check                 # 报告不满足的依赖关系
pipdeptree -p langchain-core   # 看谁依赖了 core、各自要求的区间

# 生成确定性的锁文件（生产复现必备）
pip freeze > requirements.lock.txt   # 或使用 uv / poetry 的 lock
```

**升级到 LangChain v1 / LangGraph v1 的注意点（前瞻）：**

| 变化 | 说明 |
| --- | --- |
| `create_react_agent` → `create_agent` | LangGraph v1 弃用预置 `create_react_agent`，改用 LangChain 的 `create_agent`（中间件机制更灵活） |
| 旧 Chain / Memory | 整批移入 `langchain-classic`，主包不再导出 |
| 0.3 / 0.4 系列 | 进入 MAINTENANCE 模式（维护至 2026 年底），安全补丁仍提供 |
| 迁移策略 | 先补测试集（第 10 题），再小步升级，用 LangSmith 回归验证 |

**面试怎么答：** 「LangChain 拆包后兼容性问题的根因是 **`langchain-core` 的版本区间**——partner 包绑定了 core 的上下界，随意升降级就会 `ImportError`。所以：用兼容版本号 + lock 文件、升级自底向上、旧 API 迁到 `langchain-classic`、升级前先建评估集。」

**易错点：**

- 同时装 `langchain` 与 `langchain-classic` 时，注意两者导入路径不同，别混用。
- `pydantic` v1 → v2 是大坑：`langchain 0.3` 要求 pydantic v2，插件/自定义 Tool 若还在写 v1 的 `validator` 会直接报错。
- Python 版本也要对齐：0.3.x 需要 **Python ≥ 3.9**（多数新特性建议 3.10+），不少第三方库已放弃 3.8。
- 看到 `ModuleNotFoundError: No module named 'langchain.chains'` 之类报错，先想「是不是对象搬家了」，而不是重装。
- 不要盲目 `pip install -U langchain`，它会连带升级 core，可能打破 partner 包兼容区间。

## 12. 如何把 LangChain 部署上线

**三条部署路线：**

| 路线 | 做法 | 适用 |
| --- | --- | --- |
| **自建 FastAPI 服务** | 自己写 API，用 `StreamingResponse` 做 SSE，`uvicorn` 起服务 | 需要完全控制、自定义鉴权与业务逻辑 |
| **LangServe** | `add_routes(app, chain, path="/chat")` 快速暴露 | 无状态链、快速出原型/内部工具 |
| **托管平台（LangGraph Platform / LangSmith Deployment）** | 提交图代码，平台负责扩缩容、持久化、长任务 | 复杂 Agent、需要断点续跑与人工介入 |

**生产必做的工程事项：**

1. **无状态化**：Web 进程不保存会话；会话状态放 **`PostgresSaver` / `Redis`**，多副本才可水平扩展。
2. **配置与密钥**：模型 Key、LangSmith Key 走**环境变量/密钥服务**，绝不进镜像。
3. **并发模型**：`uvicorn` 多 worker + **全链路异步**（`ainvoke/astream`），I/O 密集场景不要用同步调用。
4. **超时与重试**：模型调用设 `timeout` 与 `max_retries`，对外接口设网关超时，避免请求悬挂。
5. **限流与配额**：按用户/IP 限流，按日内成本配额，防刷爆账单。
6. **健康检查与优雅停机**：`/healthz` 探针；SIGTERM 时等待在途请求结束（否则 SSE 连接与 LangSmith 上报会断）。
7. **可观测**：开启 LangSmith，输出结构化日志（含 `trace_id`），接 APM。
8. **CI/CD 与灰度**：镜像构建 → 评估集回归（第 10 题）→ 灰度发布。


```python
# app/server.py：无状态 + Postgres 持久化 + 健康检查的最小生产骨架
from contextlib import asynccontextmanager

from fastapi import FastAPI
from fastapi.responses import JSONResponse
from langgraph.checkpoint.postgres import PostgresSaver

from app.graph import build_graph  # 你自己的图构建入口

DB_URI = "postgresql://user:pass@db:5432/langgraph"

state = {}


@asynccontextmanager
async def lifespan(app: FastAPI):
    # 进程启动时建立持久化 checkpointer 与连接池，关闭时释放
    with PostgresSaver.from_conn_string(DB_URI) as saver:
        saver.setup()  # 首次运行需建表
        state["graph"] = build_graph().compile(checkpointer=saver)
        yield
    state.clear()


app = FastAPI(lifespan=lifespan)


@app.get("/healthz")
async def healthz():
    # 探针应轻量：只检查进程可用，不要在这里打模型
    return {"status": "ok"}


@app.post("/chat")
async def chat(payload: dict):
    cfg = {"configurable": {"thread_id": payload["thread_id"]}}
    result = await state["graph"].ainvoke(
        {"messages": [("user", payload["message"])]}, config=cfg
    )
    return JSONResponse({"reply": result["messages"][-1].content})
```

**面试怎么答：** 「部署分三档——无状态链用 LangServe/FastAPI 最快；有状态 Agent 必须把会话落到外部存储（PostgresSaver）才能多副本；再往上是托管平台。无论哪档，**密钥不进镜像、全链路异步、超时重试、限流、健康检查、LangSmith 可观测**这几件是底线。」

**易错点：**

- 镜像构建时 `COPY .` 会把 `.env`、本地测试数据一起打进去 → 用 `.dockerignore` 排除。
- 多 worker 下**内存型会话（`MemorySaver`/内存 dict）会导致"同一个用户在不同 worker 上丢失历史"**，生产必须用共享存储。
- 冷启动加载 embedding 模型/建连接池耗时较长，要做**预热**并调大就绪探针的初始延迟。
- SSE 长连接会占用 worker 的并发额度，`--workers` 与连接数要一起估算，必要时用非阻塞的 `uvicorn` + 反向代理。

## 13. 常见性能瓶颈与优化

**先定位瓶颈位置：** 一次请求耗时通常构成为 **网络/网关 → 检索（embedding + 向量查询）→ 模型首 token（TTFT）→ 模型生成**。可以用 LangSmith 的 Run 树按段看耗时，别凭感觉优化。

| 瓶颈 | 现象 | 根因 | 优化手段 |
| --- | --- | --- | --- |
| 串行 LLM 调用 | 总耗时≈各步之和 | 多路调用没并发 | `asyncio.gather` / `abatch` / `RunnableParallel` |
| 首 token 慢 | 用户等待久 | 未流式 / 上下文过长 | 流式输出、精简 Prompt、Prompt Caching |
| 检索慢 | embedding/向量库耗时占比高 | 逐条 embedding、没建索引 | 批量 embedding、HNSW/IVF 索引、加缓存 |
| 上下文过长 | 每次都很贵且慢 | 无非裁剪、召回太多 | `trim_messages`、Top-K 收敛、摘要压缩 |
| 同步阻塞事件循环 | 并发上不去、P99 飙升 | 在异步链里调同步 `invoke`/同步 IO | 全链路 `ainvoke`/`astream`，阻塞操作放线程池 |
| 重复劳动 | 同一输入反复算 | 无缓存 | LLM 缓存、检索结果缓存、embedding 缓存 |
| 模型选型不当 | 简单任务也走旗舰模型 | 没有分级 | 小模型做路由/分类，旗舰做难题 |
| 冷启动 | 首波请求超时 | 模型/连接池/索引加载 | 预热、保持常驻 worker、连接池复用 |
| 向量库膨胀 | 检索随数据量劣化 | 未分区/未量化 | 分片、量化（PQ/SQ）、元数据预过滤 |

```python
# 并行化：多条独立子任务用 gather 而不是顺序 await
import asyncio
from langchain_openai import ChatOpenAI
from langchain_core.prompts import ChatPromptTemplate

llm = ChatOpenAI(model="gpt-4o-mini")

# 三个互不依赖的子问题（例如对同一文档的三个方面做摘要）
sub_queries = ["总结背景", "总结方法", "总结结论"]
prompt = ChatPromptTemplate.from_template("针对给定主题，{task}，限两句。")


async def summarize_many(topic: str):
    tasks = [llm.ainvoke(prompt.format(task=q, topic=topic)) for q in sub_queries]
    results = await asyncio.gather(*tasks)  # 并发发起，总耗时≈最慢一个
    return [r.content for r in results]


print(asyncio.run(summarize_many("RAG 检索优化")))
```

```python
# LCEL 里并行跑多路，用 RunnableParallel 或 .assign（比手写线程池更简单）
from langchain_core.runnables import RunnableParallel, RunnablePassthrough

chain = RunnableParallel(
    summary=ChatPromptTemplate.from_template("一句话概括：{text}") | llm,
    keywords=ChatPromptTemplate.from_template("抽取 3 个关键词，逗号分隔：{text}") | llm,
)
print(chain.invoke({"text": "……一段长文……"}))  # 两路并发执行
```

```python
# 批量 embedding：一次请求打包多条，显著减少往返
from langchain_openai import OpenAIEmbeddings

emb = OpenAIEmbeddings(model="text-embedding-3-small")
vectors = emb.embed_documents(["文本一", "文本二", "文本三"])  # 一次调用返回多条向量
```

**优化优先级建议：** **先并发（收益最直接）→ 再流式（改善体感）→ 再缓存（省钱省时）→ 再裁剪上下文（降本）→ 最后换模型/换库（成本最高）**。

**面试怎么答：** 「按链路分段定位：检索段用批量 embedding + 索引 + 缓存；模型段用并发 + 流式 + 分级 + 裁剪；服务段保证全链路异步 + 连接池复用。给出的优化顺序是『并发 → 流式 → 缓存 → 裁剪 → 换件』。」

**易错点：**

- 在 `async def` 里调用同步 `llm.invoke()` → **阻塞整个事件循环**，并发一上来全卡住；统一用 `await llm.ainvoke()`。
- `asyncio.gather` 并发上百个请求会直接触发**限流 429**，要加 `Semaphore` 控制并发度。
- 只加缓存不失效，会长期返回旧结果；要在知识更新时清理。
- 优化前先用数据证明瓶颈位置（LangSmith 分段耗时），**凭直觉优化常优化错地方**。

## 14. 生产环境的常见问题排查

生产问题按「现象 → 根因 → 排查手段」建立排查手册，比逐个 debug 更高效。

| 问题 | 典型现象 | 根因 | 排查与处理 |
| --- | --- | --- | --- |
| **请求超时** | 报 `Timeout` / 504，长回答尤其多 | 模型慢、上下文长、未流式、`timeout` 设太小 | 开流式；调大 `timeout` 与网关超时；查 LangSmith 分段耗时定位是哪一段慢 |
| **限流 429** | `RateLimitError` / `429 Too Many Requests` | 并发过高、超配额、单账号共享 | 加并发上限（`Semaphore`）、指数退避重试、分账号/分 key、申请提额 |
| **JSON 解析失败** | `OutputParserException` / `json.decoder.JSONDecodeError` | 模型不遵循格式、带 Markdown 包裹、字段缺失 | 优先用 `with_structured_output`；给 `PydanticOutputParser` + `get_format_instructions`；`OutputFixingParser` 兜底修复；降 `temperature` |
| **上下文超长** | `context_length_exceeded` 或答案"忘了前面" | 历史/召回未裁剪，超模型窗口 | `trim_messages` 裁剪、摘要压缩、减少 Top-K；调用前用 `get_num_tokens` 预估 |
| **成本失控** | 账单飙升、单用户异常高 | 无缓存、无 `max_tokens`、Prompt 冗余、死循环 | 开缓存、设 `max_tokens`、限制 Agent 最大迭代、按用户设配额与告警 |
| **幻觉** | 答案貌似合理但事实错误 | 上下文不足/噪声、Prompt 未约束、模型能力不足 | 约束 Prompt（「只依据给定资料，无依据要说明」）、加 Rerank 提精度、要求引用来源、上线忠实度评估 |
| **并发线程安全问题** | 会话串号、状态互相污染、随机报错 | 全局共享可变对象（handler 状态、单例 chain 的 dict、同步 handler 配异步链） | 会话状态外部化（Checkpointer/Redis）；handler 用 `threading.local` 或按 run_id 存；异步链用 `AsyncCallbackHandler`；避免模块级可变全局 |
| **静默失败 / 空回复** | 返回空字符串、无异常 | 工具报错被吞、流式 chunk 未拼接、解析返回空 | 打日志到 trace 级；对流式做 chunk 聚合；对工具调用加超时与错误上报 |
| **版本/依赖错乱** | `ImportError` / `AttributeError: no attribute xxx` | 升级把 API 搬家/改签名 | `pip check`、`pipdeptree` 查 core 版本区间；按第 11 题自底向上升级 |
| **内存泄漏 / 连接耗尽** | 进程内存持续上涨、Too many open files | 会话全在内存、HTTP 客户端未复用/未关闭 | 会话落库、复用 `httpx` 连接池、及时关闭 checkpointer/store 上下文 |

```python
# 统一的重试与错误分类处理（生产模板）
import httpx
from langchain_openai import ChatOpenAI
from langchain_core.output_parsers import PydanticOutputParser
from pydantic import BaseModel, Field


class Answer(BaseModel):
    summary: str = Field(description="一句话总结")
    confidence: float = Field(description="置信度 0~1")


# 1) 客户端级：超时可控 + 自动重试（含指数退避）
llm = ChatOpenAI(
    model="gpt-4o-mini",
    timeout=httpx.Timeout(60.0, connect=5.0),  # 连接 5s，整体 60s
    max_retries=3,                             # 429/5xx 自动重试，内部带退避
)

# 2) 链级：结构化输出直接拿对象，避免手工 JSON 解析
parser = PydanticOutputParser(pydantic_object=Answer)
structured = llm.with_structured_output(Answer)

# 3) 链级重试：对自定义链上的非模型错误也可加退避重试
robust = structured.with_retry(stop_after_attempt=3, wait_exponential_jitter=True)

try:
    result = robust.invoke("把这段说明总结成一句话：……")
    print(result.summary, result.confidence)
except httpx.HTTPStatusError as exc:           # 明显的 HTTP 层错误
    print("HTTP 错误：", exc.response.status_code)
except Exception as exc:                        # 其余错误：上报到监控，别吞掉
    print("调用失败，已记录 trace：", repr(exc))
```

```bash
# 排查时常用的日志与自检手段
grep -n "trace_id" app.log | tail -20      # 按 trace 串起一次请求的全部耗时
# 在 LangSmith 里按 error / latency 排序，快速找到最慢与最常失败的 Run
# 用同一 thread_id 复现会话串号问题，确认是否命中共享内存状态
```

**面试怎么答：** 「生产排查我给一套**结构化清单**：分四类——**稳定性**（超时、429、限流）、**正确性**（JSON 解析、幻觉、空回复）、**成本**（超长上下文、成本失控）、**并发**（线程安全、会话串号、连接耗尽）。诊断靠 LangSmith 的 Run 树加结构化日志（带 `trace_id`），处理上统一走『重试退避 + 结构化输出 + 外部化会话 + 配额监控』这几条防线。」

**易错点：**

- 把异常 `except Exception: pass` 静默吞掉，是最难排查的根源——**任何被吞的异常都会变成"偶尔返回空"的幽灵 bug**。
- 429 时应**指数退避 + 抖动（jitter）**重试，立即重试会加剧限流；同时要限制总尝试次数，避免长尾请求拖死接口。
- `with_structured_output` 失败率与模型强相关：小模型更容易不遵循 schema，必要时降级为「先自由生成再解析」或换模型。
- 会话串号多半是**「内存型会话 + 多 worker」**导致，先检查 checkpointer/store 是不是落在进程内存里，再怀疑并发代码。
