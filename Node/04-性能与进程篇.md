## 1. Node 的内存结构与 V8 垃圾回收

**结论：** Node 的常驻内存由 **V8 堆、堆外内存（Buffer/ArrayBuffer）、C ++ 对象、栈** 四部分组成。V8 堆按代际分为**新生代**与**老生代**：新生代用 Scavenge（复制算法）快速回收短命对象，老生代用标记-清除 + 标记-整理，并配合增量标记、并发标记、惰性清扫降低停顿。**Buffer 不计入 `heapUsed`，它属于堆外内存**，这是排查「堆看着不大但 RSS 很高」的关键。

**V8 堆的分区：**

| 区域 | 存放内容 | 回收方式 | 大小控制 |
| --- | --- | --- | --- |
| 新生代（New Space） | 刚分配的对象、临时变量 | Scavenge，复制存活对象到另一半 semi-space | `--max-semi-space-size` |
| 老生代（Old Space） | 存活两轮以上的对象、大对象 | Mark-Sweep / Mark-Compact | `--max-old-space-size` |
| 大对象空间（Large Object Space） | 超过阈值的大对象，直接进老生代 | 标记-清除 | 无单独参数 |
| 代码空间（Code Space） | JIT 编译后的机器码 | 随老生代 | 较小 |
| Map 空间 | 隐藏类、对象形状 | 标记-清除 | 较小 |
| 只读空间 | 内置对象、常量 | 不回收 | 固定 |

**`process.memoryUsage()` 的五个字段（高频追问）：**

| 字段 | 含义 | 是否受 V8 堆上限约束 | 常见误判 |
| --- | --- | --- | --- |
| `rss` | 进程实际占用的物理内存 | 否 | 用它判断是否「堆泄漏」 |
| `heapTotal` | V8 已向系统申请的堆大小 | 是 | 以为等于实际使用量 |
| `heapUsed` | 当前存活对象占用 | 是 | 最常用的泄漏观察指标 |
| `external` | V8 管理的堆外内存（Buffer 等） | 否 | 忽略它导致 RSS 解释不通 |
| `arrayBuffers` | `ArrayBuffer` / `SharedArrayBuffer` 占用 | 否 | 与 `external` 混淆 |

**两代回收的流程：**

1. **Scavenge（新生代）**：把新生代分成 from/to 两块 semi-space；分配时只在 from 区推进指针，空间不足时把存活对象复制到 to 区，然后交换两块角色。复制算法只处理存活对象，适合「朝生夕死」的短命对象分布。
2. **晋升**：对象经历两轮 Scavenge 仍存活，或 to 区使用超过 25%，就晋升到老生代；大对象直接进大对象空间。
3. **Mark-Sweep（老生代）**：从根（全局对象、栈、寄存器）出发做三色标记，标记完成后清除不可达对象，会产生内存碎片。
4. **Mark-Compact**：碎片过多时把存活对象向一端移动，整理出连续空间，代价是移动成本。
5. **并发化**：增量标记把标记拆成小片与 JS 交替执行；并发标记让标记线程与主线程并行；惰性清扫把释放工作推迟到分配时。目标是缩短 Stop-The-World 时间。

**GC 的触发时机：** 新生代分配失败时触发 Scavenge；老生代使用量达到阈值（V8 根据存活率与分配速率动态调整）时触发 Major GC；长时间没有 GC 时 V8 也可能主动触发。**不要用 `global.gc()` 做业务逻辑**，它需要 `--expose-gc`，且会打乱 V8 的自适应策略。

```js
// Node 18+：观察内存构成与 GC 事件
const { PerformanceObserver, constants } = require('node:perf_hooks');
const v8 = require('node:v8');

const mb = (n) => `${(n / 1024 / 1024).toFixed(1)} MB`;

function printMemory(tag) {
  const m = process.memoryUsage();
  console.log(tag, {
    rss: mb(m.rss),
    heapTotal: mb(m.heapTotal),
    heapUsed: mb(m.heapUsed),
    external: mb(m.external),
    arrayBuffers: mb(m.arrayBuffers),
  });
}

printMemory('启动');

// 1) 堆外内存：16MB Buffer 只会体现在 external / arrayBuffers，不会进入 heapUsed
const buf = Buffer.alloc(16 * 1024 * 1024);
printMemory('分配 Buffer 后');

// 2) 观察各空间的容量与使用量
const spaces = v8.getHeapSpaceStatistics();
for (const s of spaces) {
  console.log(s.space_name, mb(s.space_size), mb(s.space_used_size));
}

// 3) 监听 GC：kind 区分新生代与老生代，duration 是停顿时间
const obs = new PerformanceObserver((list) => {
  for (const e of list.getEntries()) {
    const kind =
      e.kind === constants.NODE_PERFORMANCE_GC_MAJOR ? 'major' :
      e.kind === constants.NODE_PERFORMANCE_GC_MINOR ? 'minor' : 'other';
    console.log(`[gc] ${kind} ${e.duration.toFixed(2)}ms`);
  }
});
obs.observe({ entryTypes: ['gc'] });

// 4) 模拟短命对象：会产生大量 minor GC
let sink = 0;
for (let i = 0; i < 1e6; i++) {
  sink += { i }.i;
}
console.log('sink', sink);
```

**常用启动参数：**

| 参数 | 作用 | 建议 |
| --- | --- | --- |
| `--max-old-space-size=2048` | 限制老生代上限（MB） | 容器内按内存限制的 60%～75% 设置 |
| `--max-semi-space-size=64` | 调大新生代 | 短命对象多、minor GC 频繁时可试 |
| `--expose-gc` | 暴露 `global.gc` | 仅压测与排查时使用 |
| `--heapsnapshot-near-heap-limit=3` | 接近上限时自动生成快照 | 线上 OOM 取证 |
| `--trace-gc` | 打印每次 GC | 本地分析 GC 频率 |

**容器里的常见坑：** Node 18 之前的版本读取不到 cgroup 内存限制，会按宿主机内存设置默认堆上限，导致容器被 OOMKilled 而不是抛 JS 堆溢出。Node 18 已支持 cgroup v2，但仍建议显式设置 `--max-old-space-size`。**RSS 上限 = 堆 + 堆外 + 代码段 + 栈**，只限制堆并不等于限制进程内存。

**面试怎么答：** 先画内存分区（堆内两代 + 堆外 Buffer + 栈），再讲 Scavenge 的复制与晋升、老生代的标记-清除/整理、并发化如何缩短停顿，最后强调 `heapUsed` 与 `rss` 的差异以及 `--max-old-space-size` 的容器实践。

**易错点：**

- 认为 `heapUsed` 就是进程内存，看到 Buffer 导致 RSS 上涨却找不到堆泄漏。
- 认为新生代越大越好：过大会拉长单次 Scavenge 的停顿。
- 把 `global.gc()` 当成常规优化手段，频繁全量 GC 反而降低吞吐。
- 忽略 `external` 与 `arrayBuffers`，把 `Buffer.concat` 造成的内存增长误判为闭包泄漏。

## 2. 内存泄漏的排查（heap snapshot、--inspect）

**结论：** Node 的「泄漏」绝大多数不是 V8 的 Bug，而是**长生命周期对象持有了短生命周期对象**：全局缓存无上限、闭包捕获大对象、事件监听器只增不减、定时器未清理、连接/请求未释放、Promise 永久挂起。排查路径是「先确认趋势，再定位对象，最后看引用链」：用 `memoryUsage` 与 GC 曲线确认泄漏，用 **heap snapshot 三次对比**定位构造函数，用 **Retainers 引用链**找到持有者。

**先区分三种「内存上涨」：**

| 现象 | 原因 | 判断方法 |
| --- | --- | --- |
| 锯齿形上涨后回落 | 正常 GC 周期 | `heapUsed` 在 GC 后回到基线 |
| 阶梯式上涨不回落 | 真实泄漏 | 强制 GC 后基线持续抬高 |
| RSS 涨但 heap 平稳 | 堆外内存或碎片 | 看 `external` / `arrayBuffers` |

**排查流程：**

1. **确认趋势**：定时打印 `heapUsed`，或接入 `prom-client` 暴露指标；观察数小时，排除流量高峰造成的正常增长。
2. **区分堆内堆外**：`heapUsed` 平稳而 `rss` 上涨，优先查 Buffer、`ArrayBuffer`、原生插件、连接数。
3. **抓取快照**：本地 `node --inspect server.js` 后用 Chrome 打开 `chrome://inspect`；线上用 `--heapsnapshot-near-heap-limit` 或信号触发 `v8.writeHeapSnapshot()`。
4. **三次对比**：预热后抓 S1，压测 10 分钟后抓 S2，再压 10 分钟抓 S3；在 DevTools 的 Comparison 视图看「从 S1 到 S3 仍新增且未释放」的对象。
5. **看 Retainers**：选中可疑对象，展开引用链，找到「谁在持有它」——通常是某个 Map、数组、EventEmitter 或闭包。
6. **验证修复**：同样的压测脚本重跑，确认 `heapUsed` 基线回落。

**读快照的三个关键指标：**

| 指标 | 含义 | 用途 |
| --- | --- | --- |
| Shallow Size | 对象自身占用 | 判断对象本身大小 |
| Retained Size | 该对象被回收后能释放的总内存 | 优先看大 Retained Size |
| Distance | 到 GC 根的引用距离 | 距离异常大可能是意外持有 |
| Retainers | 谁引用了我 | 定位泄漏源头的核心 |

```js
// Node 18+：程序内主动抓取堆快照，便于线上按信号触发
const v8 = require('node:v8');
const fs = require('node:fs');
const path = require('node:path');

process.on('SIGUSR2', () => {
  const file = path.join('/tmp', `heap-${Date.now()}.heapsnapshot`);
  const ok = v8.writeHeapSnapshot(file); // 同步写盘，会短暂阻塞，线上谨慎
  console.log(ok ? `快照已写入 ${file}` : '快照写入失败');
});

// 用 inspector 抓快照（可配合 --inspect，更细粒度）
const inspector = require('node:inspector');
function snapshotViaInspector(file) {
  return new Promise((resolve, reject) => {
    const session = new inspector.Session();
    session.connect();
    const chunks = [];
    session.on('HeapProfiler.addHeapSnapshotChunk', (m) => chunks.push(m.params.chunk));
    session.post('HeapProfiler.takeHeapSnapshot', null, (err) => {
      session.disconnect();
      if (err) return reject(err);
      fs.writeFileSync(file, chunks.join(''));
      resolve(file);
    });
  });
}
```

```js
// 典型泄漏：无上限缓存 + 事件监听器累积
const EventEmitter = require('node:events');

const cache = new Map();          // 泄漏源 1：只写不删
const emitter = new EventEmitter();

function handleRequest(userId, payload) {
  cache.set(userId, payload);     // 用户越多，内存越大

  const onDone = () => {};        // 泄漏源 2：每次请求新增监听器，从不移除
  emitter.on('done', onDone);
}

// 修复：有界 + TTL，监听器用 once 或显式移除
const { LRUCache } = require('lru-cache'); // npm i lru-cache
const safeCache = new LRUCache({ max: 5000, ttl: 60_000 });

function handleRequestFixed(userId, payload) {
  safeCache.set(userId, payload);
  emitter.once('done', () => {}); // 触发一次后自动移除
}
```

**常见泄漏源清单：**

| 类型 | 具体表现 | 修复思路 |
| --- | --- | --- |
| 全局/模块级 Map | 以用户、租户、URL 为键只增不减 | LRU + TTL + 上限 |
| 闭包 | 回调持有大 Buffer、request 对象 | 缩小捕获范围，处理完置空 |
| 事件监听 | `on` 累积、`MaxListenersExceededWarning` | `once`、`off`、`removeAllListeners` |
| 定时器 | `setInterval` 引用了大对象且未 `clear` | 请求结束清理，或用 `unref` |
| Promise | 永不 resolve 的 Promise 持有上下文 | 加超时，避免悬挂 |
| 连接 | 数据库连接、socket 未 release/close | `finally` 释放，池化 |
| 中间件 | 每个请求往全局数组 push 日志/上下文 | 改为请求级对象 |
| 原生扩展 | C++ 侧未释放 | 升级依赖，隔离进程 |

**线上注意事项：** 抓快照会**暂停主线程**（几十 MB 堆可能停顿数百毫秒到数秒），必须在低峰期或单实例灰度执行；快照文件可能达到堆大小的数倍，注意磁盘；不要在生产环境长期开着 `--inspect=0.0.0.0`，它有远程代码执行风险，必须配合安全组与认证。

**面试怎么答：** 按「确认趋势 → 区分堆内堆外 → 三次快照对比 → Retainers 找持有者 → 修复后回归验证」五步讲，再举两个真实例子（无上限 Map、EventEmitter 累积），最后补一句线上抓快照会 STW，需低峰操作。

**易错点：**

- 只抓一张快照就下结论，无法区分「本来就该常驻」与「持续增长」。
- 看到 `heapUsed` 高就重启了事，没定位到持有链，问题会复发。
- 用 `delete` 删 Map 键但仍有其它引用，对象并不会被回收。
- 忽略 `MaxListenersExceededWarning`，它往往就是监听器泄漏的早期信号。

## 3. CPU 性能分析（--prof、火焰图、clinic）

**结论：** CPU 分析的本质是**采样调用栈**：按固定频率记录当前执行到哪个函数，聚合后得到「谁占了多少 CPU」。Node 内置的 `--cpu-prof` 生成 `.cpuprofile`，可直接在 Chrome DevTools 查看火焰图；`--prof` 生成 isolate 日志再 `--prof-process` 转文本；`clinic` 与 `0x` 在此之上做了可视化与诊断建议。排查顺序是「先看事件循环利用率，再抓火焰图，最后定位到具体函数」。

**工具对照：**

| 工具 | 产物 | 优点 | 适用 |
| --- | --- | --- | --- |
| `--cpu-prof` | `.cpuprofile` | 内置、Chrome 直接打开 | 首选，本地与预发 |
| `--prof` + `--prof-process` | 文本摘要 | 内置、含 C++ 栈 | 无 GUI 的服务器 |
| `clinic flame` | HTML 火焰图 | 开箱即用、可读性好 | 快速定位热点 |
| `clinic doctor` | HTML 诊断报告 | 自动提示事件循环/GC/内存问题 | 整体体检 |
| `0x` | HTML 火焰图 | 支持 `--on-port` 压测联动 | 本地复现 |
| `perf_hooks` | 指标 | 可常驻、可上报 | 线上持续观测 |

**两个常驻指标（比抓 profiler 更适合线上）：**

| 指标 | 获取方式 | 说明 |
| --- | --- | --- |
| 事件循环延迟 | `monitorEventLoopDelay()` | P99 延迟持续超过几十毫秒说明有长任务 |
| 事件循环利用率 | `performance.eventLoopUtilization()` | `utilization` 接近 1 表示 CPU 打满 |

```js
// Node 18+：事件循环延迟与利用率
const { monitorEventLoopDelay, performance } = require('node:perf_hooks');

const h = monitorEventLoopDelay({ resolution: 10 });
h.enable();

let last = performance.eventLoopUtilization();
setInterval(() => {
  const elu = performance.eventLoopUtilization(last); // 传入上一次快照得到区间值
  last = performance.eventLoopUtilization();
  console.log({
    elu: elu.utilization.toFixed(3),           // 0~1
    delayP99: (h.percentile(99) / 1e6).toFixed(1), // 纳秒转毫秒
    delayMax: (h.max / 1e6).toFixed(1),
  });
}, 5000).unref();
```

```js
// 一段可复现的 CPU 热点：同步 JSON 与正则回溯
const http = require('node:http');

// 灾难性回溯：输入越长耗时指数增长
const BAD_RE = /^(a+)+$/;

function hotRoute(body) {
  const data = JSON.parse(body);                 // 大 JSON 同步解析，阻塞
  if (BAD_RE.test(data.text)) return 'ok';       // 可能触发回溯
  return data.items.sort((a, b) => a - b);       // 大数组排序，阻塞
}

http.createServer((req, res) => {
  let body = '';
  req.on('data', (c) => { body += c; });
  req.on('end', () => {
    res.end(String(hotRoute(body)));
  });
}).listen(3000);
```

**火焰图怎么读：**

1. 横轴是**时间占比**（不是时间顺序），宽度越宽说明占用 CPU 越多。
2. 纵轴是**调用栈深度**，下面是调用者，上面是被调用者。
3. **自身耗时（self）**看最上层没有子调用的块；**总耗时（total）**包含其子调用。
4. 找「又宽又平」的块：通常是热点函数；找「底部很宽但上层很窄」：可能是框架开销。
5. 出现大量 `(idle)` 说明 CPU 没打满，瓶颈在 I/O 或下游；出现 `(garbage collector)` 说明 GC 压力大。

**常见 CPU 热点：**

| 场景 | 典型函数 | 优化方向 |
| --- | --- | --- |
| 大 JSON | `JSON.parse` / `JSON.stringify` | 分页、流式解析、限制 body 大小 |
| 同步加密 | `crypto.pbkdf2Sync`、`scryptSync` | 异步版本或 worker |
| 正则 | 灾难性回溯 | 改写正则、限制输入长度、用 RE2 |
| 大数组 | `sort`、`filter`、`reduce` | 分片、索引、下推数据库 |
| 模板渲染 | 字符串拼接 | 缓存编译结果、流式输出 |
| 日志 | 同步写文件 | 异步/批量、采样 |
| 压缩 | `zlib.gzipSync` | 异步或交给 Nginx |

**面试怎么答：** 先说「采样调用栈」的本质，再对比 `--cpu-prof`、`--prof`、`clinic` 的产物与场景，接着讲火焰图「宽度是占比、深度是调用栈、self 与 total 的区别」，最后补线上用 ELU 与事件循环延迟做常驻监控。

**易错点：**

- 把火焰图横轴当成时间顺序，误以为左边先执行。
- 只看热点函数不看调用链，优化了叶子却忽略了真正的大头。
- 在开发机空转时采样，得到一堆 `(idle)`，没有意义。
- 压测与采样不同步，火焰图里没有真实流量特征。
- 只优化 JS 层，忽略了同步 I/O、DNS、下游等待造成的「假 CPU 高」。

## 4. cluster 多进程与负载均衡

**结论：** Node 单进程只能用一个 CPU 核，`cluster` 通过 **primary 进程 fork 多个 worker** 并让它们**共享同一个监听端口**来铺满多核。默认的 `SCHED_RR` 由 primary 接受连接后分发给 worker；多个 worker 之间**不共享内存、不共享 session、不共享限流计数**，这些必须外置到 Redis 等共享存储。

**三种扩容方式对比：**

| 方式 | 隔离级别 | 端口共享 | 内存共享 | 适用 |
| --- | --- | --- | --- | --- |
| `cluster` | 多进程 | 是（primary 分发句柄） | 否 | 单机多核、传统部署 |
| 容器多副本 | 多进程/多机 | 由负载均衡器分发 | 否 | 云原生主流 |
| `worker_threads` | 多线程 | 同一进程内共享 | 部分（SAB） | CPU 密集计算 |

**调度策略：**

| 策略 | 行为 | 平台 |
| --- | --- | --- |
| `SCHED_RR` | primary 接受连接，按轮询交给 worker | Linux/macOS 默认 |
| `SCHED_NONE` | worker 各自 accept，由操作系统调度 | Windows 默认，或手动设置 |

`SCHED_RR` 的「轮询」是**按连接**而不是按请求：一个 keep-alive 连接上的多个请求都会落在同一个 worker，长连接场景下各 worker 的负载可能不均。这是「压测 QPS 上不去」的常见原因之一。

```js
// Node 18+：可自愈的 cluster 启动脚本
const cluster = require('node:cluster');
const http = require('node:http');
const os = require('node:os');

const WORKERS = Number(process.env.WEB_CONCURRENCY) ||
  (os.availableParallelism ? os.availableParallelism() : os.cpus().length);

if (cluster.isPrimary) {
  let shuttingDown = false;

  const fork = () => cluster.fork();

  for (let i = 0; i < WORKERS; i++) fork();

  cluster.on('exit', (worker, code, signal) => {
    console.error(`[primary] worker ${worker.process.pid} 退出 code=${code} signal=${signal}`);
    if (!shuttingDown) {
      setTimeout(fork, 1000);
    }
  });

  process.on('SIGTERM', () => {
    shuttingDown = true;
    for (const worker of Object.values(cluster.workers)) {
      worker.send('shutdown');            // 通知 worker 优雅退出
      setTimeout(() => worker.kill('SIGKILL'), 10_000).unref();
    }
  });
} else {
  const server = http.createServer((req, res) => {
    res.setHeader('content-type', 'application/json');
    res.end(JSON.stringify({ pid: process.pid, url: req.url }));
  });

  server.listen(3000, () => console.log(`[worker ${process.pid}] 已监听 3000`));

  process.on('message', (msg) => {
    if (msg === 'shutdown') {
      server.close(() => process.exit(0));       // 停止接收新连接，处理完存量再退出
      server.closeIdleConnections?.();            // Node 18.2+：关闭空闲 keep-alive 连接
      setTimeout(() => process.exit(1), 8000).unref();
    }
  });
}
```

**为什么多个 worker 能监听同一端口：** primary 创建 server 后，把底层 TCP handle 通过 IPC 传给各 worker；`SCHED_RR` 下由 primary 统一 accept，再把连接句柄分发出去，所以不会出现 `EADDRINUSE`。这不是操作系统的 `SO_REUSEPORT`。

**必须外置的状态：**

| 状态 | 放在进程内的问题 | 正确做法 |
| --- | --- | --- |
| Session | 用户请求落到其它 worker 就掉登录 | Redis / 数据库 / 签名 Cookie |
| 限流计数 | 实际配额被放大 N 倍 | Redis + Lua 原子计数 |
| 内存缓存 | 各 worker 不一致，命中率下降 | Redis，或 pub/sub 广播失效 |
| WebSocket 连接表 | 跨 worker 无法推送 | Redis Pub/Sub、专门网关 |
| 定时任务 | 每个 worker 都跑一遍 | 独立进程 / 分布式锁 |

**优雅重启（rolling restart）思路：** 逐个 worker 处理——先 fork 新 worker 预热，再向旧 worker 发送 shutdown，等它退出后处理下一个。这样任何时刻都有可用 worker，配合负载均衡器的健康检查可实现零停机。

**面试怎么答：** 先讲「primary + N worker 共享端口」的模型，再解释 `SCHED_RR` 由 primary accept 分发、Windows 退化为 OS 调度，然后强调状态必须外置（session/限流/缓存），最后补滚动重启与容器多副本的替代关系。

**易错点：**

- 用了 cluster 就把 session 放内存，登录状态随机丢失。
- 认为 `SCHED_RR` 是按请求轮询，实际按连接，长连接会倾斜。
- 忘记监听 `exit` 自动拉起，worker 崩溃后容量静默下降。
- 在容器里既开 cluster 又开多副本，进程数翻倍导致内存超限。
- 重启时直接 `SIGKILL`，正在处理的请求全部失败。

## 5. worker_threads 实战与数据传递

**结论：** `worker_threads` 是**同一进程内的多线程**：每个 worker 有独立的 V8 isolate、独立的堆和事件循环，适合卸载 **CPU 密集**任务（加解密、图像处理、大 JSON、复杂计算）；它**不解决 I/O 密集**问题，I/O 并发靠事件循环即可。线程间不共享普通对象，数据通过 `postMessage` 结构化克隆、`transferList` 转移所有权、`SharedArrayBuffer + Atomics` 真正共享。

**选型对照：**

| 方案 | 隔离 | 通信成本 | 启动成本 | 适用 |
| --- | --- | --- | --- | --- |
| `worker_threads` | 线程级（独立 isolate） | 中（克隆/转移） | 较低 | CPU 密集、可并行计算 |
| `child_process` | 进程级 | 高（IPC 序列化） | 高 | 外部命令、强隔离 |
| `cluster` | 进程级 | 高 | 高 | 横向扩容 HTTP 服务 |

**数据传递的三种方式：**

| 方式 | 是否复制 | 典型场景 | 注意 |
| --- | --- | --- | --- |
| `postMessage(obj)` | 结构化克隆（深拷贝） | 小对象、任务参数 | 不能传函数、Symbol、原型链 |
| `postMessage(obj, [buf])` | 转移所有权，零拷贝 | 大 `ArrayBuffer`、图像数据 | 转移后原线程 `byteLength` 变为 0 |
| `SharedArrayBuffer` + `Atomics` | 真正共享内存 | 计数器、共享缓冲区 | 需自己加锁/原子操作，主线程不能 `Atomics.wait` |

**worker 的关键 API：**

| API | 作用 |
| --- | --- |
| `new Worker(file, { workerData, resourceLimits })` | 创建 worker，`workerData` 在 worker 内同步可读 |
| `parentPort.postMessage()` | 向主线程发消息 |
| `worker.on('message' / 'error' / 'exit')` | 接收结果、捕获未处理异常、感知退出 |
| `worker.terminate()` | 强制终止，返回 Promise |
| `MessageChannel` | 建立专用双向通道，可传给其它 worker |
| `BroadcastChannel` | 同进程内多 worker 广播 |

```js
// Node 18+：一个带并发上限的 worker 池
const { Worker } = require('node:worker_threads');
const os = require('node:os');
const path = require('node:path');

class WorkerPool {
  constructor(size = os.availableParallelism?.() || os.cpus().length) {
    this.size = size;
    this.idle = [];
    this.queue = [];
    for (let i = 0; i < size; i++) this.idle.push(this.#spawn());
  }

  #spawn() {
    const worker = new Worker(path.join(__dirname, 'worker.js'));
    worker.on('message', (msg) => {
      const task = worker.currentTask;
      worker.currentTask = null;
      if (task) task.resolve(msg);
      this.#release(worker);
    });
    worker.on('error', (err) => {
      const task = worker.currentTask;
      worker.currentTask = null;
      if (task) task.reject(err);
      this.#release(worker);
    });
    worker.on('exit', (code) => {
      if (code !== 0) console.error(`worker 异常退出 code=${code}`);
    });
    return worker;
  }

  #release(worker) {
    const next = this.queue.shift();
    if (next) {
      worker.currentTask = next;
      worker.postMessage(next.payload);
    } else {
      this.idle.push(worker);
    }
  }

  run(payload) {
    return new Promise((resolve, reject) => {
      const task = { payload, resolve, reject };
      const worker = this.idle.pop();
      if (worker) {
        worker.currentTask = task;
        worker.postMessage(payload);
      } else {
        this.queue.push(task);          // 没有空闲 worker 时排队，形成背压
      }
    });
  }

  async close() {
    await Promise.all(this.idle.map((w) => w.terminate()));
  }
}
```

```js
// 转移所有权与共享内存
const { Worker, isMainThread, parentPort, workerData } = require('node:worker_threads');

if (isMainThread) {
  const big = new ArrayBuffer(64 * 1024 * 1024);
  const worker = new Worker(__filename, { workerData: { sab: new SharedArrayBuffer(8) } });

  worker.on('message', (msg) => {
    console.log('收到', msg, '原 buffer 长度', big.byteLength); // 0，已转移
  });

  worker.postMessage({ big }, [big]);   // 零拷贝转移
} else {
  const arr = new Int32Array(workerData.sab);
  parentPort.once('message', ({ big }) => {
    Atomics.add(arr, 0, 1);             // 原子累加，主线程可读
    parentPort.postMessage({ bytes: big.byteLength, count: Atomics.load(arr, 0) });
  });
}
```

**`resourceLimits` 的用途：** 可以限制 worker 的 `maxOldGenerationSizeMb`、`maxYoungGenerationSizeMb`、`stackSizeMb`，防止单个计算任务吃光内存；超限会导致 worker 以非零码退出，需要在 `exit` 事件里兜底。

**使用建议：**

1. 常驻 worker 池化复用，不要每个请求 `new Worker`（创建 isolate 有毫秒级成本）。
2. 任务要可中断、可超时：`Promise.race` + `worker.terminate()`，避免一个死循环拖住池子。
3. 大数据优先 `transferList`，避免结构化克隆的深拷贝成本。
4. 共享内存必须用 `Atomics`，否则会出现数据竞争与可见性问题。
5. worker 内不能直接操作主线程的 DOM/句柄，数据库连接不要跨线程传递。

**面试怎么答：** 先区分「线程共享进程、进程隔离」与 CPU/I/O 场景，再讲三种数据传递（克隆、转移、共享）的成本，接着说明池化与超时兜底，最后补 `resourceLimits` 与「worker 不解决 I/O 并发」。

**易错点：**

- 把 worker 当成「解决所有性能问题」的银弹，I/O 场景反而增加开销。
- 每请求创建一个 worker，创建与销毁成本吃掉收益。
- 传大 Buffer 不用 transferList，结构化克隆导致内存翻倍。
- 只监听 `message` 不监听 `error`，worker 抛错后 Promise 永久挂起。
- 直接读写 `SharedArrayBuffer` 不用 `Atomics`，出现脏读。
- 在主线程调用 `Atomics.wait`，直接抛错。

## 6. PM2 进程守护与部署

**结论：** PM2 是 Node 场景最常用的**进程管理器**：负责守护（崩溃拉起）、多进程（cluster 模式）、日志收集、开机自启与零停机 reload。它的核心价值在**传统虚拟机/物理机部署**；在 Kubernetes 等容器编排平台里，进程守护应交给编排系统，容器内只跑单进程，避免「PM2 再拉起一层」导致信号与资源管理混乱。

**两种运行模式：**

| 模式 | 行为 | 适用 |
| --- | --- | --- |
| `fork` | 每个 app 一个进程，可多实例但互相独立 | 定时任务、脚本、单进程服务 |
| `cluster` | 基于 `cluster` 模块共享端口，多 worker | HTTP 服务，铺满多核 |

**关键配置项：**

| 配置 | 含义 | 建议 |
| --- | --- | --- |
| `instances` | 实例数 | `max` 或等于核数 |
| `exec_mode` | `fork` / `cluster` | HTTP 服务用 `cluster` |
| `max_memory_restart` | 超过内存阈值自动重启 | 设为本容器上限的 70%～80% |
| `autorestart` | 崩溃自动拉起 | 保持 `true` |
| `max_restarts` | 短时间内最大重启次数 | 防崩溃循环 |
| `restart_delay` | 重启延迟 | 配合退避，避免打满 CPU |
| `kill_timeout` | 发送 SIGKILL 前的等待时间 | 要大于优雅退出耗时 |
| `wait_ready` | 等应用 `process.send('ready')` 后再算启动成功 | 避免流量打到未初始化实例 |
| `listen_timeout` | 等待 ready 的超时 | 与启动耗时匹配 |

```js
// ecosystem.config.js：生产配置示例
module.exports = {
  apps: [
    {
      name: 'api',
      script: './dist/server.js',
      instances: 'max',
      exec_mode: 'cluster',
      max_memory_restart: '700M',
      autorestart: true,
      max_restarts: 10,
      restart_delay: 2000,
      kill_timeout: 10_000,        // 留足优雅退出时间
      listen_timeout: 15_000,
      wait_ready: true,            // 应用需主动 process.send('ready')
      merge_logs: true,
      time: true,                  // 日志加时间戳
      out_file: './logs/out.log',
      error_file: './logs/err.log',
      env: { NODE_ENV: 'development', PORT: 3000 },
      env_production: { NODE_ENV: 'production', PORT: 3000 },
    },
    {
      name: 'cron',
      script: './dist/cron.js',
      instances: 1,                // 定时任务只能单实例，避免重复执行
      exec_mode: 'fork',
    },
  ],
};
```

```js
// server.js：配合 wait_ready，启动完成后再通知 PM2
const http = require('node:http');

const server = http.createServer((req, res) => res.end('ok'));

server.listen(process.env.PORT || 3000, () => {
  console.log('listening');
  if (process.send) process.send('ready');   // 在 cluster 模式下每个 worker 都要发
});

// 优雅退出：PM2 reload 会先发 SIGINT，再在 kill_timeout 后 SIGKILL
process.on('SIGINT', () => {
  server.close(() => process.exit(0));
  server.closeIdleConnections?.();
});
```

**常用命令：**

```bash
pm2 start ecosystem.config.js --env production   # 启动
pm2 reload api                                   # 零停机滚动重载（cluster）
pm2 restart api                                  # 直接重启，会中断连接
pm2 stop api && pm2 delete api                    # 停止并移除
pm2 logs api --lines 200                          # 查看日志
pm2 monit                                         # 实时 CPU/内存
pm2 save && pm2 startup                           # 保存进程列表并配置开机自启
pm2 install pm2-logrotate                         # 日志轮转
```

**`reload` 与 `restart` 的区别：** `reload` 在 cluster 模式下逐个替换 worker，先起新进程再杀旧进程，理论零停机；`restart` 直接杀掉全部再拉起，会有秒级不可用。**`reload` 依赖应用能优雅退出**，否则旧 worker 的存量请求仍会失败。

**PM2 的局限：**

1. 只做进程级守护，不做跨机器调度，不是编排系统。
2. 日志是本地文件，多实例需要额外采集（Filebeat/Fluent Bit）。
3. 集群内多实例的 session、限流、缓存仍需外置。
4. 容器内使用会与 `docker stop` 的信号链冲突，建议单进程 + 编排层重启策略。

**面试怎么答：** 先讲 PM2 的四个能力（守护、cluster、日志、自启），再说 `fork` 与 `cluster` 的适用差异，接着讲 `reload` 的滚动替换与 `wait_ready` 的作用，最后补「容器里交给 K8s，PM2 主要用于虚拟机部署」。

**易错点：**

- 用 `pm2 restart` 做发布，造成秒级 502。
- `max_memory_restart` 设得比容器上限还高，进程先被 OOMKilled。
- 定时任务开多实例，任务重复执行。
- 忘记 `pm2 save`，机器重启后进程不会恢复。
- 没有配置日志轮转，日志文件把磁盘写满。
- `wait_ready` 开了但应用从不 `process.send('ready')`，PM2 一直判定启动失败。

## 7. 日志与可观测性（结构化日志、traceId）

**结论：** 生产日志必须是**结构化 JSON**，而不是拼接字符串：只有结构化才能被采集、检索、聚合与告警。核心要素是「**时间、级别、服务名、环境、traceId、消息、上下文字段**」。可观测性由**日志（Logs）、指标（Metrics）、链路（Traces）** 三支柱组成，`traceId` 是把三者串起来的主键，通常通过 `AsyncLocalStorage` 在异步调用链中透传。

**日志级别约定：**

| 级别 | 用途 | 生产是否输出 |
| --- | --- | --- |
| `fatal` | 进程无法继续 | 是，触发告警 |
| `error` | 请求失败、依赖异常 | 是，触发告警 |
| `warn` | 可恢复的异常、降级、重试 | 是 |
| `info` | 关键业务事件、启动、发布 | 是 |
| `debug` | 调试细节 | 默认关闭，按需开启 |
| `trace` | 极细粒度 | 基本关闭 |

**一条标准日志应包含：**

| 字段 | 示例 | 说明 |
| --- | --- | --- |
| `ts` | `2026-10-24T10:00:00.000Z` | ISO 时间，统一 UTC |
| `level` | `info` | 级别 |
| `service` | `order-api` | 服务名 |
| `env` | `prod` | 环境 |
| `version` | `1.8.3` | 镜像/提交版本，便于定位发布引入的问题 |
| `traceId` | `4bf92f3577b34da6a3ce929d0e0e4736` | 全链路 ID |
| `spanId` | `00f067aa0ba902b7` | 当前片段 ID |
| `reqId` | `uuid` | 单请求 ID，无链路系统时也能串 |
| `userId` | `123` | 业务定位（注意脱敏） |
| `msg` | `order created` | 人类可读摘要 |
| `latencyMs` | `37` | 耗时 |
| `status` | `200` | 结果 |

**traceId 透传的两种方式：**

1. **显式传参**：把 `traceId` 挂在 `req` 上，逐层传进 service。缺点是侵入性强、容易漏。
2. **AsyncLocalStorage**：在中间件里 `als.run({ traceId }, next)`，之后任意异步调用都能 `als.getStore()` 拿到，无需改函数签名。Node 18 的异步资源追踪已覆盖 Promise、定时器、I/O。

**W3C Trace Context 的 `traceparent` 格式：**

```text
00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
版本(2) - traceId(32 hex) - parentSpanId(16 hex) - flags(2)
```

上游没有传时自己生成 32 位十六进制 traceId，并在响应头回传，方便前端与网关对齐。

```js
// Node 18+：AsyncLocalStorage + 结构化日志
const http = require('node:http');
const { AsyncLocalStorage } = require('node:async_hooks');
const { randomUUID, randomBytes } = require('node:crypto');

const als = new AsyncLocalStorage();

const SERVICE = 'demo-api';
const ENV = process.env.NODE_ENV || 'development';

function log(level, msg, extra = {}) {
  const store = als.getStore() || {};
  const line = {
    ts: new Date().toISOString(),
    level,
    service: SERVICE,
    env: ENV,
    traceId: store.traceId,
    reqId: store.reqId,
    userId: store.userId,
    msg,
    ...extra,
  };
  process.stdout.write(JSON.stringify(line) + '\n'); // 容器里写 stdout，由采集器收集
}

const TRACE_RE = /^00-([0-9a-f]{32})-([0-9a-f]{16})-[0-9a-f]{2}$/;

http.createServer((req, res) => {
  const incoming = req.headers.traceparent || '';
  const matched = TRACE_RE.exec(incoming);
  const traceId = matched ? matched[1] : randomBytes(16).toString('hex');
  const reqId = req.headers['x-request-id'] || randomUUID();

  const start = process.hrtime.bigint();
  res.setHeader('traceparent', `00-${traceId}-${randomBytes(8).toString('hex')}-01`);

  // 在 ALS 上下文中执行后续所有异步逻辑
  als.run({ traceId, reqId }, () => {
    log('info', 'request start', { method: req.method, url: req.url });

    res.on('finish', () => {
      const latencyMs = Number(process.hrtime.bigint() - start) / 1e6;
      log('info', 'request end', { status: res.statusCode, latencyMs: Math.round(latencyMs) });
    });

    route(req, res).catch((err) => {
      log('error', 'request failed', { err: err.message, stack: err.stack });
      if (!res.headersSent) res.statusCode = 500;
      res.end('internal error');
    });
  });
}).listen(3000);

async function route(req, res) {
  await new Promise((r) => setTimeout(r, 5));   // 模拟异步调用，ALS 依然有效
  log('debug', '处理业务');                      // 自动带上 traceId
```

**落地建议：**

1. 用成熟库：`pino` 性能最好，`winston` 生态更全；HTTP 层可用 `pino-http` 自动记录请求日志。
2. **日志写 stdout**，容器由 Fluent Bit / Filebeat 采集；不要在应用内做文件轮转。
3. **禁止记录密码、Token、身份证、银行卡**；对手机号、邮箱做掩码；用 `redact` 配置统一脱敏。
4. 高频日志要**采样**，避免日志成本超过计算成本；错误日志不采样。
5. 慢请求单独打点（`latencyMs > 阈值`），比全量日志更有价值。
6. 指标用 `prom-client` 暴露 `/metrics`：QPS、P95、错误率、事件循环延迟、GC 次数、连接池等待。

**三支柱的分工：**

| 支柱 | 回答的问题 | 典型工具 |
| --- | --- | --- |
| Metrics | 「现在是否异常、趋势如何」 | Prometheus + Grafana |
| Logs | 「这次请求具体发生了什么」 | Loki / ELK |
| Traces | 「慢在哪一段、跨服务调用链」 | OpenTelemetry + Jaeger/Tempo |

**面试怎么答：** 先讲结构化日志的必要性与必备字段，再讲 traceId 用 ALS 透传、W3C `traceparent` 格式，最后把日志/指标/链路三支柱与各自回答的问题说清楚，补一句脱敏与采样。

**易错点：**

- 拼接字符串日志，线上无法按字段检索与聚合。
- `traceId` 只放在 `req` 上，异步后丢失；应使用 ALS。
- 把 Token、密码、完整身份证写进日志。
- 用 `console.log` 打大对象，序列化成本高且阻塞。

## 8. 数据库连接池与并发控制

**结论：** 连接池的作用是**复用 TCP 连接、限制数据库并发、提供排队与超时**。池太小会让请求排队、P99 飙升；池太大反而压垮数据库（上下文切换、锁竞争、内存）。经验公式是 `连接数 ≈ CPU 核数 × 2 + 磁盘数`，但更重要的是**按压测结果调**。事务必须**在同一个连接上完成**，用完必须 `release`，否则池会被耗尽。

**池参数的含义（以 `mysql2` / `pg` 为例）：**

| 参数 | 含义 | 建议 |
| --- | --- | --- |
| `connectionLimit` | 单进程最大连接数 | 10～20 起步，压测调整 |
| `queueLimit` | 等待队列长度，0 表示不限制 | 建议限制，避免无限堆积 |
| `acquireTimeout` / `connectionTimeoutMillis` | 获取连接超时 | 2～5 秒，快速失败 |
| `idleTimeout` | 空闲连接回收 | 30～60 秒 |
| `maxLifetime` | 连接最大寿命 | 小于数据库/中间件的空闲断开时间 |
| `enableKeepAlive` | TCP 保活 | 长连接建议开启 |

**总连接数的全局账：** 单实例池 × 实例数 ≤ 数据库 `max_connections` 的 70%～80%，要给运维、迁移、备份留余量。连接数不是越大越好：PostgreSQL 官方建议从「核数 × 2 + 磁盘数」起步，超过后吞吐不再增长，延迟反而上升。

**并发控制的三层：**

| 层次 | 手段 | 作用 |
| --- | --- | --- |
| 入口 | 限流、队列、超时 | 控制进入系统的请求量 |
| 应用 | 信号量、`p-limit` | 限制在途的数据库/下游调用 |
| 数据库 | 连接池、事务隔离、索引 | 控制真实并发与锁竞争 |

```js
const pool = mysql.createPool({
  host: process.env.DB_HOST,
  user: process.env.DB_USER,
  password: process.env.DB_PASSWORD,
  database: process.env.DB_NAME,
  waitForConnections: true,     // 池满时排队而不是立即报错
  connectionLimit: 10,
  queueLimit: 100,              // 队列上限，超过直接失败，形成背压
  connectTimeout: 5000,
  enableKeepAlive: true,
  keepAliveInitialDelay: 0,
});

// 事务：begin/commit/rollback 必须使用同一个连接
async function withTransaction(fn, retries = 3) {
  for (let attempt = 1; ; attempt++) {
    const conn = await pool.getConnection();
    try {
      await conn.beginTransaction();
      const result = await fn(conn);
      await conn.commit();
      return result;
    } catch (err) {
      await conn.rollback().catch(() => {});
      // 死锁与锁等待超时可重试，其它错误直接抛出
      const retryable = err.code === 'ER_LOCK_DEADLOCK' || err.code === 'ER_LOCK_WAIT_TIMEOUT';
      if (!retryable || attempt >= retries) throw err;
      await new Promise((r) => setTimeout(r, 20 * attempt + Math.random() * 20));
    } finally {
      conn.release();           // 必须释放，位置放在 finally
    }
  }
}

async function transfer(fromId, toId, amount) {
  return withTransaction(async (conn) => {
    const [rows] = await conn.execute(
      'SELECT id, balance FROM accounts WHERE id IN (?, ?) FOR UPDATE',
      [fromId, toId],
    );
    if (rows.length !== 2) throw new Error('账户不存在');
    const from = rows.find((r) => r.id === fromId);
    if (from.balance < amount) throw new Error('余额不足');

    await conn.execute('UPDATE accounts SET balance = balance - ? WHERE id = ?', [amount, fromId]);
    await conn.execute('UPDATE accounts SET balance = balance + ? WHERE id = ?', [amount, toId]);
  });
}
```

```js
// 信号量：限制同时访问下游的并发数
class Semaphore {
  constructor(limit) {
    this.limit = limit;
    this.active = 0;
    this.queue = [];
  }

  async acquire() {
    if (this.active < this.limit) {
      this.active++;
      return;
    }
    await new Promise((resolve, reject) => {
      const entry = { resolve, timer: null };
      entry.timer = setTimeout(() => {
        const i = this.queue.indexOf(entry);
        if (i >= 0) this.queue.splice(i, 1);
        reject(new Error('等待信号量超时'));
      }, 3000);
      this.queue.push(entry);
    });
    // 槽位由 release 直接移交，这里不再自增，避免并发下超发
  }

  release() {
    const next = this.queue.shift();
    if (next) {
      clearTimeout(next.timer);
      next.resolve();            // 保持 active 不变，把槽位交给等待者
    } else {
      this.active--;
    }
  }

  async run(fn) {
    await this.acquire();
    try {
      return await fn();
    } finally {
      this.release();
    }
  }
}

const dbGate = new Semaphore(8);          // 最多 8 个并发查询
const query = (sql, args) => dbGate.run(() => pool.execute(sql, args));
```

**池耗尽的典型原因：**

| 原因 | 表现 | 修复 |
| --- | --- | --- |
| 忘记 `release` | 池连接数只增不减，最终超时 | `finally` 中释放 |
| 事务里做 HTTP 调用 | 连接被长时间占用 | 事务内只做数据库操作 |
| 慢查询 | 连接排队，P99 飙升 | 加索引、分页、限流 |
| 池太小 | `queueLimit` 频繁触发 | 压测后调大，或加副本 |

**面试怎么答：** 先讲连接池的三个作用（复用、限流、排队），再给容量公式与「池总和不超过数据库上限」的约束，接着强调事务必须同连接、`release` 必须在 `finally`，最后补信号量做应用层并发控制与超时快速失败。

**易错点：**

- 事务中途 `await` 了外部 HTTP 接口，连接被占住几十秒。
- 出错路径忘记 `release`，池逐渐枯竭。
- 每个实例都开 100 个连接，10 个副本直接把数据库打满。
- 认为连接池越大吞吐越高，忽略数据库侧的锁与上下文切换。
- 只给「获取连接」设超时，不给 SQL 执行设超时，慢查询永久占用连接。

## 9. Node 中的缓存设计（内存缓存与 Redis）

**结论：** 缓存要解决的是「**用可控的一致性换取延迟与数据库压力**」。进程内缓存最快但有**副本不一致**与**容量上限**问题；Redis 缓存可跨实例共享但有网络往返与序列化成本。选型上：**只读、变化少、可容忍短暂不一致**的数据放本地；**需要跨实例一致、共享会话/限流/锁**的放 Redis。必须处理**穿透、击穿、雪崩**三类问题。

**缓存模式对比：**

| 模式 | 读路径 | 写路径 | 一致性 | 适用 |
| --- | --- | --- | --- | --- |
| Cache-Aside | 先读缓存，未命中读库并回填 | 更新库后删缓存 | 最终一致 | 最常用 |
| Read-Through | 缓存层负责回源 | 同上 | 最终一致 | 封装度高的框架 |
| Write-Through | 读缓存 | 同时写缓存与库 | 较强 | 写少读多 |
| Write-Behind | 读缓存 | 先写缓存，异步刷库 | 弱，可能丢数据 | 计数、埋点 |

**三类经典问题：**

| 问题 | 现象 | 解法 |
| --- | --- | --- |
| 缓存穿透 | 查询不存在的数据，每次都打到库 | 缓存空值（短 TTL）、布隆过滤器、参数校验 |
| 缓存击穿 | 热点 key 过期瞬间大量请求回源 | 互斥重建（singleflight）、逻辑过期、永不过期 + 后台刷新 |
| 缓存雪崩 | 大量 key 同时过期或 Redis 宕机 | TTL 加随机抖动、多级缓存、熔断降级、集群高可用 |

**一致性策略：** 常用「**更新数据库 → 删除缓存**」，而不是更新缓存（避免并发写覆盖）。删除后仍可能有短暂旧值：读请求在删除前读到旧值并回填。进一步可用**延迟双删**（更新后延迟几百毫秒再删一次）或**订阅 binlog 删除**。强一致场景不要依赖缓存，直接读库。

```js
// Node 18+：带 TTL 与 LRU 的进程内缓存（无第三方依赖）
class TtlLruCache {
  constructor({ max = 1000, ttl = 60_000 } = {}) {
    this.max = max;
    this.ttl = ttl;
    this.map = new Map();          // Map 的插入顺序天然可做 LRU
  }

  get(key) {
    const entry = this.map.get(key);
    if (!entry) return undefined;
    if (entry.expireAt <= Date.now()) {
      this.map.delete(key);
      return undefined;
    }
    this.map.delete(key);          // 命中后移到队尾，表示最近使用
    this.map.set(key, entry);
    return entry.value;
  }

  set(key, value, ttl = this.ttl) {
    if (this.map.has(key)) this.map.delete(key);
    if (this.map.size >= this.max) {
      const oldest = this.map.keys().next().value;
      this.map.delete(oldest);       // 淘汰最久未使用
    }
    this.map.set(key, { value, expireAt: Date.now() + ttl });
  }

  delete(key) {
    this.map.delete(key);
  }

  get size() {
    return this.map.size;
  }
}

const local = new TtlLruCache({ max: 5000, ttl: 30_000 });
```

```js
// Node 18+：Cache-Aside + 互斥重建（singleflight），防止击穿
const inflight = new Map();

async function getOrLoad(key, loader, { ttl = 60_000, nullTtl = 10_000 } = {}) {
  const hit = local.get(key);
  if (hit !== undefined) return hit;

  // 同一个 key 的并发请求合并成一次回源
  if (inflight.has(key)) return inflight.get(key);

  const task = (async () => {
    try {
      const value = await loader();
      if (value === null || value === undefined) {
        local.set(key, null, nullTtl);   // 缓存空值，防穿透
        return null;
      }
      local.set(key, value, ttl);
      return value;
    } finally {
      inflight.delete(key);              // 无论成功失败都要清理
    }
  })();

  inflight.set(key, task);
  return task;
}

// 使用示例
async function getUser(id) {
  return getOrLoad(`user:${id}`, () => db.findUserById(id), { ttl: 60_000 });
}
```

```js
// Node 18+：Redis 版 Cache-Aside（npm i ioredis）
const Redis = require('ioredis');
const redis = new Redis({ host: '127.0.0.1', port: 6379, maxRetriesPerRequest: 2 });

async function getOrLoadRedis(key, loader, ttlSeconds = 60) {
  const cached = await redis.get(key);
  if (cached !== null) return JSON.parse(cached);

  const value = await loader();
  if (value == null) {
    await redis.set(key, 'null', 'EX', 10);   // 空值短 TTL
    return null;
  }
  // TTL 加随机抖动，避免同一时刻批量过期
  const ttl = ttlSeconds + Math.floor(Math.random() * 10);
  await redis.set(key, JSON.stringify(value), 'EX', ttl);
  return value;
}

async function invalidate(key) {
  await redis.del(key);
}
```

**多级缓存的失效传播：** 本地缓存不会因为 Redis 删除而自动失效。常见做法是更新后向 Redis 发布一条失效消息，各实例订阅后清理本地 key；或者本地缓存只设很短的 TTL（1～5 秒），用「短 TTL + Redis 长 TTL」容忍不一致。

**容量与淘汰：** 进程内缓存必须有上限，否则就是内存泄漏。`lru-cache` 库支持 `max`（条数）、`maxSize`（字节）、`ttl`、`staleWhileRevalidate`，比手写更可靠。缓存大对象时注意序列化成本，必要时缓存分片后的结果而不是整页。

**面试怎么答：** 先讲本地与 Redis 的取舍（速度 vs 一致性/共享），再说 Cache-Aside 与「更新库后删缓存」，重点展开穿透/击穿/雪崩三种问题及 singleflight、空值缓存、TTL 抖动，最后补多级缓存的失效广播。

**易错点：**

- 本地缓存无上限、无 TTL，最终变成内存泄漏。
- 更新数据库后「更新缓存」而不是删除，并发写导致旧值覆盖新值。
- 所有 key 用同一个过期时间，整点集体失效造成雪崩。
- 缓存空值不设 TTL，数据补录后永远读不到。
- 用 `JSON.parse` 反序列化超大对象，反序列化本身成为 CPU 热点。
- 认为 Redis 删除后本地缓存立即生效，多实例读到脏数据。

## 10. 限流、熔断与降级

**结论：** 限流解决「**入口流量超过系统能力**」，熔断解决「**下游持续故障拖垮自己**」，降级解决「**资源不足时保核心功能**」。三者配合「超时 + 重试 + 隔离」构成稳定性防线。单机限流用令牌桶/滑动窗口即可；多副本必须用 **Redis + Lua 原子操作**，否则实际配额被放大 N 倍。

**四种限流算法：**

| 算法 | 原理 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 固定窗口 | 每个周期一个计数器 | 实现最简单 | 窗口边界双倍流量 |
| 滑动窗口 | 按时间切片/日志统计 | 边界平滑 | 内存与计算成本高 |
| 令牌桶 | 匀速放令牌，请求取令牌 | 允许一定突发 | 参数需调优 |
| 漏桶 | 请求入桶，匀速流出 | 输出绝对平滑 | 不允许突发，排队延迟高 |

**熔断器的三个状态：**

| 状态 | 行为 | 迁移条件 |
| --- | --- | --- |
| Closed | 正常放行，统计失败率 | 失败率/慢调用比例超阈值 → Open |
| Open | 直接失败，快速返回降级结果 | 冷却时间到 → Half-Open |
| Half-Open | 放少量试探请求 | 成功 → Closed；失败 → Open |

**稳定性组合：** 超时要小于上游超时并逐层递减；重试只用于幂等请求，且必须指数退避 + 抖动；限流按用户/租户/IP/接口分别设限；隔离用独立连接池或信号量缩小故障面；熔断后返回缓存、默认值或静态兜底页。

```js
// Node 18+：单机令牌桶
class TokenBucket {
  constructor({ capacity, refillPerSecond }) {
    this.capacity = capacity;
    this.refillPerSecond = refillPerSecond;
    this.tokens = capacity;
    this.lastRefill = Date.now();
  }

  #refill() {
    const now = Date.now();
    const delta = ((now - this.lastRefill) / 1000) * this.refillPerSecond;
    if (delta > 0) {
      this.tokens = Math.min(this.capacity, this.tokens + delta);
      this.lastRefill = now;
    }
  }

  tryConsume(cost = 1) {
    this.#refill();
    if (this.tokens >= cost) {
      this.tokens -= cost;
      return true;
    }
    return false;
  }
}

const bucket = new TokenBucket({ capacity: 100, refillPerSecond: 20 });
```

```js
// Node 18+：熔断器实现
class CircuitBreaker {
  constructor({ failureThreshold = 5, cooldownMs = 10_000, halfOpenMax = 2 } = {}) {
    Object.assign(this, { failureThreshold, cooldownMs, halfOpenMax });
    this.state = 'closed';       // closed / open / half-open
    this.failures = 0;
    this.openedAt = 0;
    this.halfOpenCalls = 0;
  }

  async run(fn, fallback) {
    if (this.state === 'open') {
      if (Date.now() - this.openedAt < this.cooldownMs) return fallback(new Error('circuit open'));
      this.state = 'half-open';  // 冷却结束，放少量请求试探
      this.halfOpenCalls = 0;
    }
    if (this.state === 'half-open' && this.halfOpenCalls++ >= this.halfOpenMax) {
      return fallback(new Error('half-open limited'));
    }

    try {
      const result = await fn();
      this.state = 'closed';
      this.failures = 0;
      return result;
    } catch (err) {
      if (this.state === 'half-open' || ++this.failures >= this.failureThreshold) {
        this.state = 'open';
        this.openedAt = Date.now();
      }
      return fallback(err);
    }
  }
}

);
```

**工程细节：** 限流命中返回 `429` 并带 `Retry-After` 与 `RateLimit-*` 头，限流 key 按业务选择（登录用 IP + 账号，下单用用户 ID，开放接口用 API Key）。重试只用于幂等操作，指数退避 + 抖动，区分可重试错误（超时、503、429）与不可重试错误（400、401），且不要在链路每一层都重试。降级分功能级（关推荐位/评论）、数据级（返回缓存并标记 `degraded: true`）、页面级（静态兜底页）、流量级（排队/拒绝）。

**面试怎么答：** 先区分限流/熔断/降级各自解决的问题，再讲四种限流算法与令牌桶的突发优势，接着讲熔断三态与半开探测，最后补「多副本必须 Redis + Lua」「重试要退避+抖动+幂等」「降级要保核心」。

**易错点：**

- 限流计数放进程内，多副本后配额乘以副本数。
- 固定窗口在边界放行双倍流量。
- 熔断没有 Half-Open 探测，永久失败或永久放行。
- 所有层都加重试，重试风暴把下游彻底打挂。
- 重试非幂等请求，造成重复下单。
- 限流只按 IP，NAT 后大量用户共享一个出口被封。
- 降级返回 200 且不标记，前端把空数据当成真实结果。

## 11. 优雅退出与健康检查

**结论：** 优雅退出的目标是「**不再接新请求、把存量请求处理完、释放资源、限时强制退出**」。顺序是：收到 `SIGTERM` → 就绪探针置为不健康 → 停止 `listen` → 关闭空闲 keep-alive 连接 → 等待在途请求 → 关闭数据库/Redis/队列 → 刷新日志 → `exit(0)`；超过超时时间则强制退出。健康检查要区分 **liveness（要不要重启）** 与 **readiness（要不要接流量）**。

**退出信号：**

| 信号 | 来源 | 处理 |
| --- | --- | --- |
| `SIGTERM` | Docker stop、K8s、PM2 | 优雅退出，主信号 |
| `SIGINT` | Ctrl+C、PM2 reload | 优雅退出 |
| `SIGKILL` | 超时后强制 | 无法捕获，必须在此之前完成清理 |
| `SIGHUP` | 终端断开 | 通常忽略或重载配置 |

**三个探针的分工：**

| 探针 | 回答的问题 | 失败后果 | 检查内容 |
| --- | --- | --- | --- |
| `liveness` | 进程是否还活着 | 重启容器 | 只检查进程与事件循环，不查依赖 |
| `readiness` | 是否可以接流量 | 从 Service 摘除 | 数据库、Redis、必要下游 |
| `startup` | 是否启动完成 | 延迟 liveness 生效 | 初始化、预热 |

**常见错误：** 在 liveness 里检查数据库。数据库抖动时，所有实例被判定不健康并重启，故障被放大。liveness 应当尽量「轻」，只反映进程自身是否卡死。

```js
// Node 18+：HTTP 服务的优雅退出与健康检查
const http = require('node:http');
const { setTimeout: sleep } = require('node:timers/promises');

let ready = true;             // readiness 开关：退出时先置 false
let inFlight = 0;             // 在途请求计数
let shuttingDown = false;

const server = http.createServer(async (req, res) => {
  if (req.url === '/health/live') {
    return res.end(JSON.stringify({ status: 'ok' }));   // 不检查外部依赖
  }
  if (req.url === '/health/ready') {
    if (!ready) {
      res.statusCode = 503;
      return res.end(JSON.stringify({ status: 'draining' }));
    }
    try {
      await db.ping();                                    // 依赖可用才算就绪
      return res.end(JSON.stringify({ status: 'ready' }));
    } catch {
      res.statusCode = 503;
      return res.end(JSON.stringify({ status: 'dependency down' }));
    }
  }

  inFlight++;
  try {
    await sleep(100);
    res.end('ok');
  } finally {
    inFlight--;
  }
});

server.listen(3000);

async function shutdown(signal) {
  if (shuttingDown) return;
  shuttingDown = true;
  ready = false;                                   // 1) 先让 readiness 失败，摘流量
  console.log(`收到 ${signal}，开始优雅退出`);

  // 2) 停止接收新连接；回调在所有连接关闭后触发
  const closed = new Promise((resolve) => server.close(resolve));
  server.closeIdleConnections?.();                  // 3) 立刻关闭空闲 keep-alive 连接

  // 4) 兜底：超时后强制关闭所有连接并退出
  const timer = setTimeout(() => {
    console.error('优雅退出超时，强制关闭');
    server.closeAllConnections?.();
    process.exit(1);
  }, 10_000);
  timer.unref();

  try {
    // 5) 等待在途请求结束（简单轮询，生产中可配合 drain 事件）
    while (inFlight > 0) await sleep(50);
    await closed;
    await db.end();
    await redis.quit();
    clearTimeout(timer);
    console.log('清理完成，退出');
    process.exit(0);
  } catch (err) {
    console.error('清理失败', err);
    process.exit(1);
  }
}

process.on('SIGTERM', () => shutdown('SIGTERM'));
process.on('SIGINT', () => shutdown('SIGINT'));
```

**为什么必须处理 keep-alive：** `server.close()` 只停止 accept，不会断开已建立的 keep-alive 连接；这些连接可能空闲数十秒，导致进程迟迟不退出，最终被 `SIGKILL`。Node 18.2+ 提供 `closeIdleConnections()`（关闭空闲连接）与 `closeAllConnections()`（强制全部关闭）。

**容器与编排的配合：**

1. 设置 `terminationGracePeriodSeconds` 大于应用优雅退出超时（例如应用 10 秒，编排 30 秒）。
2. 配置 `preStop` 钩子先 `sleep 5`，等待 Service 摘流量的延迟，再让应用收到 SIGTERM。
3. 应用内超时必须小于编排宽限期，否则永远走到 `SIGKILL`。
4. 长连接（WebSocket、SSE）要单独处理：发送关闭帧、通知客户端重连。

**资源清理清单：**

| 资源 | 清理方式 |
| --- | --- |
| HTTP server | `close()` + `closeIdleConnections()` |
| 数据库连接池 | `pool.end()` |
| Redis | `quit()`（发送 QUIT 而不是直接断开） |
| 消息队列消费者 | `worker.close()`，等待当前任务完成 |
| 定时器 | `clearInterval` / `clearTimeout` |
| 日志 | `logger.flush()` |
| 临时文件 | 删除或标记可回收 |

**不要在 `uncaughtException` 里做优雅退出**：此时进程状态已不可信，正确做法是记录日志后立即退出，由外部拉起。`unhandledRejection` 同理，Node 15 起默认会升级为未捕获异常并退出。

**面试怎么答：** 先讲「摘流量 → 停 accept → 关空闲连接 → 等在途 → 释放资源 → 限时强杀」的顺序，再强调 `server.close()` 不处理 keep-alive、需要 `closeIdleConnections`，接着区分 liveness/readiness，最后补编排的宽限期与 preStop。

**易错点：**

- 只 `process.exit(0)`，在途请求全部中断。
- `server.close()` 后不关 keep-alive，进程卡住直到被 SIGKILL。
- liveness 检查数据库，数据库抖动引发全量重启。
- 应用超时 30 秒，编排宽限期 10 秒，永远来不及清理。
- 退出时忘记关闭消息队列消费者，任务执行到一半被中断。
- 退出过程中仍返回 readiness 200，流量继续打进来。

## 12. Node 服务性能优化清单

**结论：** 性能优化要按「**先度量、再定位、后优化、必回归**」的顺序，不能凭感觉。首要指标是 **P95/P99 延迟、吞吐、错误率、事件循环利用率、GC 停顿、内存水位、连接池等待**；优化优先级通常是「消除同步阻塞 > 减少下游往返 > 加缓存 > 扩容/多进程 > 调 V8 参数」。任何优化都要用压测对比，避免「优化了但更慢」。

**核心指标：**

| 指标 | 含义 | 健康信号 |
| --- | --- | --- |
| RPS/QPS | 每秒请求数 | 随并发上升后趋于平台 |
| P50/P95/P99 | 延迟分位 | P99 不应比 P50 高一个数量级 |
| 错误率 | 5xx/超时占比 | 小于 0.1%（按业务定） |
| ELU | 事件循环利用率 | 长期接近 1 说明 CPU 瓶颈 |
| 事件循环延迟 | P99 延迟 | 持续 > 50ms 需排查长任务 |
| GC | major GC 频率与停顿 | 停顿应远小于 P99 |
| 内存 | RSS/heapUsed 水位 | 有回落、无持续爬升 |
| 连接池 | 等待时间/排队数 | 等待接近 0 |

**分层优化清单：**

| 层次 | 检查项 | 典型收益 |
| --- | --- | --- |
| 代码 | 同步 `fs`/`crypto`/`zlib`、大 `JSON`、灾难性正则、大数组排序 | 高 |
| 代码 | 循环里 `await`、串行可并行的请求 | 高 |
| 架构 | 缓存热点数据、连接池、批量合并 | 高 |
| 架构 | CPU 密集任务移到 worker、HTTP 服务开 cluster/多副本 | 中高 |
| 协议 | 开启 gzip/br、HTTP/2、keep-alive | 中 |
| 运行时 | `--max-old-space-size`、`UV_THREADPOOL_SIZE`、`--max-semi-space-size` | 中 |
| 系统 | `ulimit -n`、TCP backlog、文件描述符、TIME_WAIT | 中 |
| 观测 | 日志采样、指标上报、慢请求追踪 | 长期 |

**最容易被忽略的「同步阻塞」：**

```js
// 反面清单
const fs = require('node:fs');
const crypto = require('node:crypto');

fs.readFileSync('big.log');                                  // 阻塞
crypto.pbkdf2Sync(password, salt, 100000, 64, 'sha512');    // 阻塞且昂贵
JSON.parse(hugeBody);                                        // 大对象阻塞
new Array(1e6).sort((a, b) => a - b);                        // 阻塞
for (const id of ids) await fetchOne(id);                    // 串行等待
```

```js
// Node 18+：串行改并行 + 限制并发
async function mapLimit(items, limit, fn) {
  const results = new Array(items.length);
  let cursor = 0;

  async function worker() {
    while (cursor < items.length) {
      const i = cursor++;
      results[i] = await fn(items[i], i);
    }
  }

  await Promise.all(Array.from({ length: Math.min(limit, items.length) }, worker));
  return results;
}

// 使用：最多 8 个并发，而不是串行 N 次往返
const users = await mapLimit(ids, 8, (id) => fetchUser(id));
```

```js
// Node 18+：一个简易压测脚本，测 P50/P95/P99 与 RPS（无第三方依赖）
const http = require('node:http');
const { performance } = require('node:perf_hooks');

const agent = new http.Agent({ keepAlive: true, maxSockets: 100 });

function once(url) {
  return new Promise((resolve, reject) => {
    const start = performance.now();
    const req = http.get(url, { agent }, (res) => {
      res.resume();
      res.on('end', () => resolve(performance.now() - start));
    });
    req.on('error', reject);
  });
}

async function run({ url, concurrency, total }) {
  const latencies = [];
  let issued = 0;
  const startedAt = performance.now();

  async function worker() {
    while (issued < total) {
      issued++;
      latencies.push(await once(url));
    }
  }

  await Promise.all(Array.from({ length: concurrency }, worker));
  const elapsed = (performance.now() - startedAt) / 1000;

  latencies.sort((a, b) => a - b);
  const p = (q) => latencies[Math.min(latencies.length - 1, Math.floor(latencies.length * q))];

  console.log({
    total,
    concurrency,
    rps: (total / elapsed).toFixed(1),
    p50: p(0.5).toFixed(1),
    p95: p(0.95).toFixed(1),
    p99: p(0.99).toFixed(1),
    max: latencies[latencies.length - 1].toFixed(1),
  });
}

run({ url: 'http://127.0.0.1:3000/', concurrency: 50, total: 2000 }).catch(console.error);
```

**压测方法论：**

1. 明确目标：目标 QPS、可接受 P99、错误率上限。
2. 固定环境：同机同网、预热 JIT、排除其它进程干扰。
3. 阶梯加压：10 → 50 → 100 → 200 并发，观察拐点，而不是一上来就打满。
4. 观察服务端：ELU、GC、内存、连接池、下游耗时，而不是只看客户端 RPS。
5. 定位瓶颈：CPU 满 → 火焰图；CPU 不满但延迟高 → 下游/连接池/锁；内存涨 → 快照。
6. 优化后回归：同一脚本、同一参数复测，记录对比数据。

**面试怎么答：** 先给指标体系（P99、ELU、GC、内存、连接池），再给优化优先级（去同步阻塞 → 减少往返 → 缓存 → 多进程/多副本 → 调参），接着举「串行 await 改并发」「大 JSON 分段」两个例子，最后强调压测阶梯加压与优化后回归。

**易错点：**

- 只看平均延迟，忽略 P99；平均值会被大量快请求拉低。
- 没有预热就开始压测，JIT 未优化导致数据失真。
- 压测客户端与服务端同机，争抢 CPU 得出错误结论。
- 盲目调大 `UV_THREADPOOL_SIZE`，文件/DNS 任务反而因上下文切换变慢。
- 只扩容不定位，横向扩容掩盖了同步阻塞与 N+1 查询。
- 优化后不做回归，把「把缓存命中率降低」当成性能提升。
