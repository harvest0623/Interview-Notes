## 1. Node 事件循环的六个阶段

**结论：** Node 的事件循环由 **libuv** 实现，一次循环（tick）按固定顺序经过 **timers → pending callbacks → idle/prepare → poll → check → close callbacks** 六个阶段。每个阶段维护一个 FIFO 回调队列；**每执行完一个回调，以及每两个阶段之间，都会清空 `process.nextTick` 队列和 Promise 微任务队列**。循环是否继续，取决于是否还有「被引用的 handle」或「未完成的请求」。

**六个阶段一览：**

| 阶段 | 处理内容 | 典型来源 |
| --- | --- | --- |
| timers | 执行已到期的 `setTimeout` / `setInterval` 回调 | 定时器 |
| pending callbacks | 执行上一轮被推迟的 I/O 错误回调 | TCP `ECONNREFUSED` 等 |
| idle, prepare | libuv 内部使用，业务代码不直接接触 | libuv 内部 |
| poll | 获取新的 I/O 事件并执行 I/O 回调；队列空时按规则阻塞等待 | `fs`、网络、`readFile` 回调 |
| check | 执行 `setImmediate` 回调 | `setImmediate` |
| close callbacks | 执行关闭类回调 | `socket.on('close')`、流销毁 |

**一次循环的推进顺序：**

```
┌───────────────────────────┐
│          timers           │  ← setTimeout / setInterval
├───────────────────────────┤
│     pending callbacks     │  ← 被推迟的 I/O 错误回调
├───────────────────────────┤
│       idle, prepare       │  ← libuv 内部
├───────────────────────────┤
│           poll            │  ← 等待并处理 I/O（可能阻塞）
├───────────────────────────┤
│           check           │  ← setImmediate
├───────────────────────────┤
│      close callbacks      │  ← close 事件
└───────────────────────────┘
        ↓ 循环，直到没有活跃的 handle
```

**poll 阶段的阻塞规则：**

1. poll 队列不为空：同步执行队列里的回调，直到队列清空或达到系统限制。
2. poll 队列为空且**有 `setImmediate`**：不阻塞，直接进入 check 阶段。
3. poll 队列为空且**有到期的 timer**：回到 timers 阶段执行。
4. 三者都没有：在 poll 阶段阻塞等待新的 I/O 事件，最长等到最近的 timer 到期。

**事件循环何时退出：**

事件循环不是「跑完一圈就结束」，而是由 libuv 判断 `uv_loop_alive`：还存在**被引用的 handle**（`ref` 的 timer、监听中的 server、打开的 socket）、**活跃的请求**（正在进行的文件读写、DNS 查询）、**正在关闭的 handle** 时继续循环。三者都没有时进程自然退出，这也解释了 `unref()` 的作用（见第 9 题）。

```js
// event-loop-order.js —— 运行：node event-loop-order.js
const fs = require('node:fs');

setTimeout(() => console.log('timers 阶段：setTimeout'), 0);

fs.readFile(__filename, () => {
  console.log('poll 阶段：readFile 回调');
  // 当前在 poll，下一次 check 先于下一轮 timers
  setTimeout(() => console.log('下一轮 timers：I/O 中的 setTimeout'), 0);
  setImmediate(() => console.log('check 阶段：I/O 中的 setImmediate'));
});

setImmediate(() => console.log('check 阶段：setImmediate'));
process.nextTick(() => console.log('nextTick 队列'));
Promise.resolve().then(() => console.log('Promise 微任务队列'));
console.log('同步代码：主模块执行完才开始循环');
```

**一种可能的输出：**

```
同步代码：主模块执行完才开始循环
nextTick 队列
Promise 微任务队列
timers 阶段：setTimeout          // 也可能是 check 阶段：setImmediate
check 阶段：setImmediate
poll 阶段：readFile 回调
check 阶段：I/O 中的 setImmediate
下一轮 timers：I/O 中的 setTimeout
```

同步代码先执行，随后清空 nextTick 与微任务；主模块顶层注册的 `setTimeout` 与 `setImmediate` 谁先谁后**不保证**（取决于进入 timers 阶段时 1ms 是否已过）；但 I/O 回调中注册的这一对顺序**固定**——当前在 poll，下一步就是 check。

**每个阶段都清空微任务：**

```js
// phase-microtask.js
const fs = require('node:fs');

setTimeout(() => {
  console.log('timer 回调');
  Promise.resolve().then(() => console.log('timer 内的微任务'));
}, 0);

setImmediate(() => {
  console.log('immediate 回调');
  Promise.resolve().then(() => console.log('immediate 内的微任务'));
});
```

输出中两个微任务总是紧跟各自回调，不会攒到循环末尾才执行。

**面试怎么答：** 先报六阶段名称，再补三句关键：①每个阶段一个 FIFO 队列；②阶段之间与每个回调之后都清空 nextTick 与微任务；③循环存活由 ref 的 handle 与活跃请求决定。最后用「I/O 回调里 `setImmediate` 一定早于 `setTimeout`」这个例子证明真的理解 poll 与 check 的相邻关系。

**易错点：**

- 六个阶段里没有「微任务阶段」，微任务在阶段之间穿插执行。
- `poll` 不是「处理所有异步」，Promise 回调、`nextTick`、timer 都不在 poll 里。
- `setTimeout(fn, 0)` 实际是 1ms 级，timers 阶段只执行**已到期**的定时器，没到期就跳过。
- 一次循环不等于「所有回调都执行完」，每轮只处理各阶段当前队列里的任务。

## 2. Node 与浏览器事件循环的差异

**结论：** 两者都遵循「同步代码 → 微任务 → 宏任务」的基本模型，但**规范来源、阶段划分、渲染步骤、定时器精度**不同。浏览器由 HTML 规范定义，围绕「任务队列 + 渲染」组织；Node 由 libuv 定义，围绕「六个阶段 + I/O」组织。面试时要能说出**三点相同**与**四点不同**。

**逐项对比：**

| 维度 | 浏览器 | Node.js |
| --- | --- | --- |
| 规范来源 | HTML Living Standard | libuv 实现（无统一规范） |
| 结构 | 多个任务队列（按 task source）+ 微任务检查点 | 六个阶段，每阶段一个 FIFO 队列 |
| 微任务时机 | 每个任务结束后、渲染前 | Node 11+ 每个回调后；旧版本在阶段之间 |
| nextTick | 无 | 有独立队列，优先级高于 Promise |
| `setImmediate` | 无（可用 `MessageChannel` 模拟） | 有，check 阶段 |
| 渲染 | 有样式计算、布局、绘制、`requestAnimationFrame` | 无渲染概念 |
| 定时器精度 | 嵌套超过 5 层后最小 4ms，后台标签页被节流 | 最小 1ms，不节流 |
| 循环退出 | 页面关闭前一直运行 | 无活跃 handle 时进程退出 |
| 长任务影响 | 掉帧、交互卡顿 | 请求堆积、健康检查超时 |
| 额外 API | `requestIdleCallback`、`MutationObserver` | `process.nextTick`、`unref`、`AsyncLocalStorage` |

**相同点（也要主动说）：**

1. `Promise.then`、`queueMicrotask` 都属于微任务，**先于下一个宏任务**。
2. 同步代码永远最先执行，`await` 之后的代码进入微任务。
3. 微任务可以无限递归，都会饿死宏任务，都需要业务侧避免。

```js
// loop-compare.js —— Node 18+ 运行；把同样的逻辑放进浏览器 <script> 对照
console.log('A 同步代码');

setTimeout(() => console.log('D setTimeout'), 0);        // 浏览器/Node 都是宏任务
queueMicrotask(() => console.log('C queueMicrotask'));    // 两端都是微任务
Promise.resolve().then(() => console.log('C2 Promise'));

if (typeof window === 'undefined') {
  // 浏览器没有 setImmediate，Node 用它填补 check 阶段
  setImmediate(() => console.log('E setImmediate'));
}

// Node 输出：A → C → C2 → D（或 E）→ E（或 D）
// 浏览器输出：A → C → C2 → D，且 D 之前可能插入一次渲染
```

**为什么渲染会改变浏览器的表现：**

浏览器在每个任务后可能执行「微任务检查点 → 更新渲染」：`requestAnimationFrame` 在渲染前调用，`setTimeout` 回调可能被排到下一帧。因此在浏览器里连续写 `setTimeout` 做动画会出现抖动；Node 没有渲染，定时器只受系统调度与事件循环影响。

**Node 中不要照搬浏览器经验的地方：**

1. 不要用 `setTimeout(fn, 0)` 当「让出主线程」的通用手段，Node 里更合适的让位方式是 `setImmediate` 或 `await new Promise(r => setImmediate(r))`。
2. 不要依赖 `requestAnimationFrame`、`MutationObserver`，Node 18 没有这些 API。
3. 浏览器里「微任务执行完一定渲染」的假设在 Node 不成立，Node 关心的是 I/O 是否被饿死。
4. 浏览器后台标签页的定时器节流不会发生在 Node，长定时器在 Node 里会照常触发。

**面试怎么答：** 用一句话概括「浏览器围着渲染转，Node 围着 I/O 转」；然后按「阶段结构、微任务检查点、setImmediate、定时器精度、退出条件」五点展开；最后补一句 Node 11 之后微任务时机已与浏览器对齐，但 nextTick 仍是 Node 独有。

**易错点：**

- 说「Node 没有宏任务」是错的，timer、I/O、immediate 都是宏任务级。
- 说「浏览器和 Node 的微任务完全一样」不严谨，Node 多了 nextTick 队列且优先级更高。
- `setTimeout` 的 4ms 是浏览器对嵌套调用的限制，不是 Node 的行为。
- Node 的 `setImmediate` 不是「立即执行」，它排在 poll 之后的 check 阶段。

## 3. process.nextTick 与微任务的优先级

**结论：** 优先级顺序是 **同步代码 > `process.nextTick` 队列 > Promise 微任务队列 > 宏任务（timer / I/O / immediate）**。nextTick 队列和微任务队列都会在**当前操作结束后立刻清空**，区别是 nextTick 队列**先被完整清空**，然后才轮到 Promise 微任务；两者递归都可能让事件循环「饿死」。

**两个队列的关系：**

| 对比项 | `process.nextTick` | Promise 微任务 |
| --- | --- | --- |
| 所属 | Node 独有，`process` 对象提供 | ECMAScript 标准，两端都有 |
| 队列 | nextTick 队列 | microtask 队列 |
| 优先级 | 更高，先清空 | 较低，后清空 |
| 清空时机 | 每个回调后、阶段切换时 | 每个回调后、阶段切换时 |
| 递归后果 | 饿死 I/O、定时器，甚至 Promise 回调 | 同样饿死宏任务 |
| 典型用途 | 保证回调异步、事件触发后置 | 通用异步链 |
| 抛错后果 | 未捕获则进程崩溃 | 未处理的 rejection，Node 15+ 默认崩溃 |

**执行模型：**

```
当前同步代码
   ↓
清空 nextTick 队列（新加入的 nextTick 也在本轮清空）
   ↓
清空 Promise 微任务队列（执行期间新加入的微任务也清空）
   ↓
下一个宏任务（timer / I/O / immediate）
   ↓
重复上面的清空过程
```

Node 11 起，这套清空逻辑发生在**每个宏任务回调之后**，而不是只在阶段之间；这也是 `await` 链在 Node 与浏览器表现一致的原因。

```js
// nexttick-priority.js —— 运行：node nexttick-priority.js
process.nextTick(() => console.log('nextTick 1'));
Promise.resolve().then(() => console.log('promise 1'));

process.nextTick(() => {
  console.log('nextTick 2');
  process.nextTick(() => console.log('nextTick 3')); // 仍在本轮 nextTick 队列中
  Promise.resolve().then(() => console.log('promise 2'));
});

// 输出固定为：nextTick 1 → nextTick 2 → nextTick 3 → promise 1 → promise 2

// 饥饿演示：递归 nextTick 期间，setImmediate 一直得不到执行
let count = 0;
function tick() {
  if (count++ < 3) process.nextTick(tick);
}
process.nextTick(tick);
setImmediate(() => console.log('setImmediate 只能等 nextTick 队列清空'));
```

`nextTick 3` 排在 `promise 1` 之前，说明 nextTick 队列是**整体优先**的，不是「插入一条执行一条、再和微任务交替」。

**什么时候该用 nextTick：**

1. 构造函数或同步 API 中触发事件时，用 `nextTick` 保证监听器在调用栈退出后才执行。
2. 让某个 API 的行为「始终异步」，避免调用方观察到同步返回（防止 Zalgo）。
3. 需要在当前操作彻底完成后、任何 I/O 之前做清理。

**什么时候不该用：**

1. 普通异步链优先 `queueMicrotask` 或 Promise，兼容性更好、语义更标准。
2. 递归调度绝对不要用 nextTick，会直接饿死事件循环；需要让位时用 `setImmediate`。

```js
// nexttick-starve.js —— 危险示例，不要在生产代码中这样写
let n = 0;
function loop() {
  if (n++ < 1_000_000) process.nextTick(loop);
}
loop();
setTimeout(() => console.log('timer 要等一百万次 nextTick 之后'), 0);
```

**面试怎么答：** 直接给优先级链条「同步 > nextTick > Promise 微任务 > 宏任务」，再解释「nextTick 队列先被完整清空，且新加入的 nextTick 仍在同一轮」，最后补一句 Node 11 之后两类微任务都在每个回调后清空，但 nextTick 的优先级不变。

**易错点：**

- `process.nextTick` 不是「下一轮循环」，而是「当前操作之后、本轮微任务之前」。
- 以为 nextTick 回调里的 Promise 会先执行——实际上 nextTick 队列清空前不会切到 Promise 队列。
- 在 nextTick 里 `throw`，错误不会变成 Promise rejection，而是走 `uncaughtException`。
- 大量使用 nextTick 做批处理容易造成 I/O 饥饿，应改用 `setImmediate` 分片。

## 4. setTimeout、setImmediate、Promise 的执行顺序

**结论：** 在**主模块顶层**，`setTimeout(fn, 0)` 与 `setImmediate(fn)` 的先后**不确定**；在**I/O 回调内部**，`setImmediate` **一定**先于 `setTimeout`。Promise 与 nextTick 永远排在它们之前。判断顺序的关键不是背结论，而是判断「当前代码运行在哪个阶段」。

**固定与不固定的部分：**

| 代码位置 | 顺序 | 原因 |
| --- | --- | --- |
| 主模块顶层 | 同步 → nextTick → Promise → `setTimeout` / `setImmediate`（后两者不定） | 进入 timers 时 1ms 是否已过不确定 |
| `fs.readFile` 等 I/O 回调内 | 同步 → nextTick → Promise → `setImmediate` → `setTimeout` | 当前在 poll，下一步固定是 check |
| timer 回调内 | 同步 → nextTick → Promise → 本轮回调内注册的 `setImmediate` 优先 | timer 在 timers 阶段，随后仍要经过 poll 到 check |
| immediate 回调内 | 同步 → nextTick → Promise → 下一轮的 timer | 新注册的 immediate 要等下一轮 check |

```js
// order-classic.js —— 运行：node order-classic.js
setTimeout(() => console.log('timeout'), 0);
setImmediate(() => console.log('immediate'));
Promise.resolve().then(() => console.log('promise'));
process.nextTick(() => console.log('nextTick'));
console.log('sync');

// 稳定输出：sync → nextTick → promise →（timeout / immediate 二者顺序不固定）
```

**为什么顶层不确定：**

1. `setTimeout(fn, 0)` 会被规范成最小 1ms。
2. 事件循环从 timers 阶段开始，如果主模块执行完到进入 timers 还没满 1ms，定时器未到期，本轮跳过。
3. 接着进入 poll，若没有待处理 I/O 且有 `setImmediate`，直接进 check，`immediate` 先输出。
4. 若进入 timers 时已超过 1ms，则 `timeout` 先输出。

**I/O 回调内为什么确定：**

```js
// order-io.js —— 运行：node order-io.js
const fs = require('node:fs');

fs.readFile(__filename, () => {
  setTimeout(() => console.log('timeout'), 0);
  setImmediate(() => console.log('immediate'));
  process.nextTick(() => console.log('nextTick'));
  Promise.resolve().then(() => console.log('promise'));
  console.log('sync（I/O 回调内）');
});

// 固定输出：sync → nextTick → promise → immediate → timeout
```

回调执行时正处于 poll 阶段，poll 之后紧邻 check，所以 `immediate` 必然先执行；`setTimeout` 要等到下一轮 timers。

**多层嵌套的行为：**

```js
// order-nested.js
setTimeout(() => {
  console.log('外层 timer');
  setTimeout(() => console.log('内层 timer：下一轮 timers'), 0);
  setImmediate(() => console.log('内层 immediate：本轮 check'));
}, 0);

setImmediate(() => {
  console.log('外层 immediate');
  setImmediate(() => console.log('内层 immediate：下一轮 check'));
  setTimeout(() => console.log('内层 timer：下一轮 timers'), 0);
});
```

内层回调都不会「插队」到当前阶段队列中间，而是进入下一轮对应阶段。这一点常被用来解释「为什么递归 `setTimeout` 不会栈溢出，但会累积延迟」。

**面试怎么答：** 先给「同步 → nextTick → 微任务 → 宏任务」大框架，再强调 `setTimeout` 与 `setImmediate` 的顺序取决于代码所处阶段：顶层不确定，I/O 回调内 `setImmediate` 必先。最后说明原因分别是 1ms 取整与 poll→check 的相邻关系。

**易错点：**

- 背成「setImmediate 永远先于 setTimeout」——只在 I/O 回调内成立。
- 把 `setTimeout(fn, 0)` 当成真正 0 延迟，实际最小 1ms，且受系统时钟影响。
- 认为 `setTimeout` 一定在 timers 阶段的第一顺位执行，实际只执行已到期的定时器。
- 在 immediate 回调里再注册 `setImmediate`，误以为还在本轮执行。

## 5. async/await 在 Node 中的执行与错误处理

**结论：** `async` 函数调用后**同步执行到第一个 `await`**，然后返回一个 Promise；`await` 等价于 `Promise.resolve(x).then(剩余代码)`，剩余代码进入**微任务**。`await` 只让出到微任务，不让出到宏任务，因此**一连串 `await` 不会给 I/O 执行机会**。错误处理的核心是：`async` 内的 `throw` 变成 rejection，必须用 `try/catch` 或 `.catch` 接住，漏接会触发 `unhandledRejection`。

**执行步骤：**

1. 调用 `async fn()`：函数体立即同步执行，直到遇到 `await`。
2. 遇到 `await`：先求值右侧表达式，然后 `await` 之后的代码被包装成回调放进微任务队列。
3. 函数立即返回一个 pending 的 Promise 给调用方，调用方继续执行同步代码。
4. 当前宏任务的微任务检查点到来时，`await` 后续代码恢复执行。
5. 全部执行完 resolve；抛错则 reject。

```js
// async-order.js —— 运行：node async-order.js
async function order() {
  console.log('1 async 函数体开始');   // 同步执行
  await null;                          // 即使不是 Promise，也让出一次微任务
  console.log('3 await 之后');          // 微任务
  return 'done';
}

console.log('0 before');
order().then((value) => console.log('4 then:', value));
console.log('2 after');

// 输出：0 before → 1 async 函数体开始 → 2 after → 3 await 之后 → 4 then: done
```

**`await` 不会让出到宏任务：**

```js
// async-starve.js
async function chain() {
  for (let i = 0; i < 3; i++) {
    await null; // 每次只是排一个微任务
    console.log('微任务', i);
  }
}
chain();
setTimeout(() => console.log('timer 排在所有 await 之后'), 0);
setImmediate(() => console.log('immediate 也排在所有 await 之后'));
```

所有 `await` 续体（包括新产生的）会在同一个微任务检查点内被清空，定时器只能等下一轮。这与递归 Promise 一样，会造成长任务。

**错误处理：**

```js
// async-error.js —— 运行：node async-error.js
const sleep = (ms) => new Promise((resolve) => setTimeout(resolve, ms));

async function loadUser(id) {
  await sleep(10);
  if (!id) throw new Error('id 不能为空'); // 等价于 return Promise.reject
  return { id };
}

async function main() {
  // 1. try/catch 能捕获 await 的 rejection
  try {
    await loadUser(0);
  } catch (err) {
    console.log('捕获:', err.message);
  }

  // 2. 串行：前一个完成才发下一个
  console.time('串行');
  await loadUser(1);
  await loadUser(2);
  console.timeEnd('串行'); // ≈ 20ms

  // 3. 并发：同时发起，总耗时取决于最慢的一个
  console.time('并发');
  await Promise.all([loadUser(1), loadUser(2)]);
  console.timeEnd('并发'); // ≈ 10ms

  // 4. 部分失败不中断
  const results = await Promise.allSettled([loadUser(1), loadUser(0)]);
  console.log(results.map((r) => r.status)); // [ 'fulfilled', 'rejected' ]
}

main();
```

**四个高频错误写法：**

```js
// 错误 1：忘记 await，rejection 逃逸成未处理拒绝
async function bad1() {
  loadUser(1).then((u) => console.log(u)); // 忘了 return/await，调用方无法感知失败
}

// 错误 2：在 forEach 中用 async，循环不会等待
[1, 2, 3].forEach(async (id) => {
  await loadUser(id); // 三个并发跑，外层早已返回
});
// 正确写法：for...of + await，或 Promise.all(array.map(...))

// 错误 3：try/catch 里 return 而不 return await，catch 抓不到
async function bad3() {
  try {
    return loadUser(0); // 直接返回 Promise，catch 失效
  } catch (err) {
    console.log('永远进不来');
  }
}
// 需要写成 return await loadUser(0)

// 错误 4：并发写入共享变量时没做顺序控制
async function bad4() {
  let seq = 0;
  await Promise.all([1, 2, 3].map(async () => {
    seq += await loadUser(seq); // 三个任务读到同一个 seq，结果不可预期
  }));
}
```

**`async` 函数的几个事实：**

| 说法 | 是否正确 | 说明 |
| --- | --- | --- |
| `async` 函数一定返回 Promise | 是 | 返回值被 `Promise.resolve` 包装 |
| `async` 函数内的 `throw` 会同步抛出 | 否 | 变成 rejected Promise |
| `await` 后面的代码是宏任务 | 否 | 是微任务 |
| `await` 一个非 Promise 值会立即同步继续 | 否 | 仍会让出一次微任务 |
| `Promise.all` 中一个失败其余取消 | 否 | 其余继续执行，只是结果被忽略 |

**面试怎么答：** 先讲「同步执行到第一个 await，之后进微任务」这条执行模型，再讲 `await` 等价于 `then`，因此不让出 I/O；错误处理按「try/catch、Promise.all/allSettled、unhandledRejection 兜底」三层回答；最后补 `return await` 与 `forEach` 两个坑。

**易错点：**

- 认为 `await` 会让出事件循环给 I/O——它只排微任务，密集 `await` 一样阻塞。
- 忘记 `await` 导致 rejection 逃逸，Node 15+ 默认让进程崩溃。
- 串行 `await` 写成本该并发的场景，接口耗时成倍增加。
- `try/catch` 只包住 `await` 表达式，外面 `.then` 里的错误仍需单独处理。
- `async` 函数中的同步异常也会变成 rejection，不要在外面用同步 try/catch 等它。

## 6. 阻塞事件循环的后果与排查

**结论：** Node 只有一个 JS 执行线程，**任何持续超过几十毫秒的同步计算都会让所有请求排队**。后果不是「变慢一点」，而是延迟毛刺、健康检查失败、心跳超时、连接堆积甚至雪崩。排查靠**事件循环延迟监控 + CPU profile**，解决靠**分片让出、流式处理、`worker_threads` 或拆服务**。

**常见阻塞源：**

| 类型 | 例子 | 处理方式 |
| --- | --- | --- |
| 同步文件 I/O | `fs.readFileSync`、`fs.statSync` | 改 `fs/promises`，启动阶段例外 |
| 同步加密 | `crypto.pbkdf2Sync`、`bcrypt.hashSync` | 异步版本或 worker |
| 大对象序列化 | 几十 MB 的 `JSON.parse` / `JSON.stringify` | 流式解析、分页、worker |
| 正则回溯 | 用户输入拼进复杂正则 | 限制长度、改用字符串方法、RE2 |
| 大数组计算 | 排序、去重、聚合百万级数据 | 分片 + 让出、worker |
| 同步压缩 | `zlib.gzipSync` | 异步 `zlib` 或流 |
| 日志与字符串拼接 | 循环内 `console.log`、超大模板串 | 采样、异步日志、批量写 |
| 同步 DNS | `dns.lookupSync`（不存在，但阻塞式调用常见于第三方库） | 使用异步 API |
| 原生扩展 | 同步 C++ addon | 放 worker 或改异步 |

**后果链条：**

```
同步长任务（300ms）
   → 本轮事件循环无法推进
   → 已到达的请求、定时器、心跳全部排队
   → 平均延迟上升、P99 毛刺
   → 负载均衡健康检查超时，实例被摘除
   → 请求重试打到剩余实例，压力放大
```

**监控事件循环延迟：**

```js
// loop-delay.js —— 运行：node loop-delay.js
const { monitorEventLoopDelay } = require('node:perf_hooks');

// resolution：采样间隔（毫秒）；统计值单位是纳秒
const histogram = monitorEventLoopDelay({ resolution: 20 });
histogram.enable();

setInterval(() => {
  const p99 = histogram.percentile(99) / 1e6;
  const max = histogram.max / 1e6;
  console.log(`事件循环延迟 p99=${p99.toFixed(1)}ms max=${max.toFixed(1)}ms`);
  histogram.reset();
}, 1000);

// 模拟一次 300ms 的同步阻塞
setTimeout(() => {
  const start = Date.now();
  while (Date.now() - start < 300) {
    // 空转，真实场景可能是大 JSON.parse 或同步读文件
  }
  console.log('同步阻塞结束');
}, 1500);
```

正常服务 p99 应在个位数毫秒；持续超过 50ms 就说明有阻塞或线程池排队；出现 200ms 以上的尖刺要能对应到具体请求。

**用 CPU profile 定位热点：**

```bash
# 1. 生成 CPU profile（Node 18+ 内置，无需额外依赖）
node --cpu-prof --cpu-prof-dir=./profiles app.js

# 2. 用 Chrome DevTools 打开 profiles 目录下的 .cpuprofile
#    Flame Chart 中最宽的同步栈就是阻塞点

# 3. 传统方式：采样日志 + 手动处理
node --prof app.js
node --prof-process isolate-*.log > profile.txt
```

线上不方便重启时，可以用 `--inspect` 连接 Chrome DevTools 抓 CPU Profile，或用 `clinic flame`、`0x` 这类工具生成火焰图。`perf_hooks` 只能告诉你「卡了多久」，火焰图才能告诉你「卡在哪一行」。

**分片让出：**

```js
// chunk-yield.js —— 把大任务拆成小批，批间让出事件循环
async function processInChunks(items, handler, chunkSize = 1000) {
  for (let i = 0; i < items.length; i += chunkSize) {
    const chunk = items.slice(i, i + chunkSize);
    for (const item of chunk) handler(item);
    // setImmediate 会让出到 check 阶段，I/O 与 timer 有机会执行
    await new Promise((resolve) => setImmediate(resolve));
  }
}

const data = Array.from({ length: 100_000 }, (_, i) => i);
processInChunks(data, (n) => n * 2).then(() => console.log('处理完成'));
setInterval(() => console.log('心跳仍然准时'), 100).unref();
```

**排查步骤（面试可直接背）：**

1. **确认现象**：看 P99 延迟、事件循环延迟直方图、健康检查失败率，而不是只看 CPU。
2. **定位时间点**：把毛刺时间与访问日志、慢查询日志对齐，找到触发请求。
3. **抓 CPU Profile**：找最宽的同步调用栈，确认是解析、正则、加密还是序列化。
4. **验证假设**：本地用同样入参复现，用 `monitorEventLoopDelay` 量出阻塞时长。
5. **修复**：小任务分片让出；大任务搬 `worker_threads`；I/O 改异步；正则限制输入；必要时水平拆服务。

**面试怎么答：** 按「现象 → 原因 → 定位 → 解决」四段答。现象说 P99 毛刺与请求堆积；原因列同步 I/O、大 JSON、正则回溯、同步加密；定位说 `monitorEventLoopDelay` 加 `--cpu-prof` 火焰图；解决说分片让出、worker、异步化、拆服务。

**易错点：**

- 只看 CPU 使用率，CPU 不高也可能是线程池打满或同步等待。
- 用 `setTimeout(fn, 0)` 做分片让出，精度差且优先级低，应该用 `setImmediate`。
- 把 `JSON.parse` 大报文当作「很快」，几十 MB 的解析足以造成百毫秒阻塞。
- 在日志里同步写文件（`appendFileSync`）放大阻塞。
- 认为 `async/await` 就不阻塞——同步计算放在 async 函数里照样阻塞。

## 7. 回调地狱与 Promise 化（util.promisify）

**结论：** 回调地狱的本质不是「缩进深」，而是**控制流被反转**：错误处理要在每一层重复、顺序与并发无法用统一语法表达、异常无法用 `try/catch` 捕获。Promise 化用 `util.promisify` 把 err-first 回调统一成返回 Promise 的函数，从而可以 `await`、可以 `Promise.all`、可以集中 `catch`。

**回调地狱的四个真实问题：**

| 问题 | 回调写法 | Promise 写法 |
| --- | --- | --- |
| 错误处理 | 每层判断 `if (err)` 并手动传递 | 一个 `try/catch` 或一个 `.catch` |
| 顺序执行 | 层层嵌套 | 顺序 `await` |
| 并发执行 | 手写计数器 | `Promise.all` / `allSettled` |
| 异常捕获 | 回调内 `throw` 无法被外层捕获 | rejection 可被 `await` 捕获 |

```js
// callback-hell.js —— 改造前的典型嵌套
const fs = require('node:fs');

fs.readFile('a.txt', 'utf8', (err, a) => {
  if (err) return console.error('读 a 失败', err);
  fs.readFile('b.txt', 'utf8', (err2, b) => {
    if (err2) return console.error('读 b 失败', err2);
    fs.writeFile('c.txt', a + b, (err3) => {
      if (err3) return console.error('写 c 失败', err3);
      console.log('完成');
    });
  });
});
```

**第一步：用命名函数拍平嵌套。** 命名函数把「回调金字塔」变成线性调用，但错误传递与并发问题仍在，只是可读性先恢复。

**第二步：`util.promisify` 统一 Promise 化。**

`util.promisify` 的契约非常明确：传入函数必须遵循 **Node 风格回调** `(err, value)`，返回一个新函数，调用后返回 Promise；`err` 非空则 reject，否则 resolve 第一个成功值。

```js
// promisify-demo.js —— 运行：node promisify-demo.js
const util = require('node:util');
const fs = require('node:fs');

// 1. 标准 Promise 化：fs.readFile 的回调是 (err, buffer)
const readFileAsync = util.promisify(fs.readFile);

// 2. 自定义 Promise 化：需要保留多个返回值时，挂在 custom 符号上
function query(sql, callback) {
  setTimeout(() => callback(null, { rows: [sql], count: 1 }), 10);
}
query[util.promisify.custom] = (sql) =>
  new Promise((resolve, reject) => {
    // 回调有多个成功值时，promisify 默认只保留第一个，这里手动返回完整对象
    query(sql, (err, result) => (err ? reject(err) : resolve(result)));
  });
const queryAsync = util.promisify(query);

// 3. 反向转换：Promise 函数转回调风格，便于兼容老接口
const callbackStyle = util.callbackify(async (id) => {
  if (!id) throw new Error('id 必填');
  return `user-${id}`;
});

(async () => {
  const source = await readFileAsync(__filename, 'utf8');
  console.log('源码长度:', source.length);

  const result = await queryAsync('select 1');
  console.log('自定义结果:', result); // { rows: [ 'select 1' ], count: 1 }

  callbackStyle(1, (err, value) => console.log('callbackify:', err, value));
  callbackStyle(0, (err) => console.log('callbackify 错误:', err.message));
})();
```

**第三步：用 `await` 重写流程。**

```js
// promisify-flat.js
const util = require('node:util');
const fs = require('node:fs');
const readFile = util.promisify(fs.readFile);
const writeFile = util.promisify(fs.writeFile);

async function merge() {
  try {
    const [a, b] = await Promise.all([
      readFile('a.txt', 'utf8'),
      readFile('b.txt', 'utf8'),
    ]);
    await writeFile('c.txt', a + b);
    console.log('完成');
  } catch (err) {
    // 所有失败集中在这里，err.code 可区分 ENOENT / EACCES
    console.error('失败:', err.code, err.message);
  }
}

merge();
```

**内置的 Promise 版本（优先使用，不用自己 promisify）：**

| 模块 | 引入方式 |
| --- | --- |
| 文件系统 | `require('node:fs/promises')` |
| 定时器 | `require('node:timers/promises')` |
| 流工具 | `require('node:stream/promises').pipeline` |
| DNS | `require('node:dns/promises')` |

**`util.promisify` 的边界：**

1. 只保留**第一个**成功值，多返回值要用 `promisify.custom`。
2. 回调被调用多次时，只有第一次生效（Promise 状态不可逆）。
3. 同步抛出的异常会变成 rejection（调用发生在 Promise 执行器内）。
4. 方法依赖 `this` 时，用 `promisify(obj.method).call(obj)` 调用。
5. 已经是 Promise 的函数不要再 promisify，会得到「Promise 套 Promise」的返回值。

**面试怎么答：** 先说回调地狱的三个本质问题（错误传递、并发表达、异常捕获），再说 Promise 化是把 err-first 回调适配成 Promise 的**适配器模式**；然后讲 `promisify` 的契约、多返回值用 `promisify.custom`、反向用 `callbackify`；最后补一句优先使用官方 `fs/promises` 等现成 Promise API。

**易错点：**

- 回调签名不是 `(err, value)`（比如事件风格 `(value)`）时直接 promisify，会永远 pending。
- 忘记在回调里 `return`，导致后续代码继续执行并重复回调。
- `promisify` 后仍用回调思维写代码，把 Promise 放进 `forEach` 而不 await。
- 认为 `callbackify` 会保留原始函数的同步行为，实际所有结果都异步回调。

## 8. EventEmitter 的原理与使用

**结论：** `EventEmitter` 是 Node 事件驱动模型的基石，本质是**「事件名 → 监听器列表」的同步发布订阅**。`emit` 会**同步**依次调用监听器，不做排队、不做异常隔离；`error` 事件没有监听器时会直接抛出并终止进程；默认监听器上限 10，超过只告警不禁止。

**核心 API：**

| API | 作用 | 备注 |
| --- | --- | --- |
| `on(type, fn)` / `addListener` | 注册监听器 | 可重复注册，按注册顺序调用 |
| `once(type, fn)` | 只触发一次 | 内部包一层 wrapper，触发后自动移除 |
| `prependListener` | 插到队首 | 用于内部框架优先处理 |
| `off(type, fn)` / `removeListener` | 移除监听器 | 对 `once` 需传原始函数 |
| `emit(type, ...args)` | 同步触发 | 有监听器返回 `true`，否则 `false` |
| `listeners` / `rawListeners` | 查看监听器 | `rawListeners` 能看到 once 的 wrapper |
| `setMaxListeners(n)` | 调整告警阈值 | `0` 表示不限制 |
| `removeAllListeners(type)` | 清空 | 不传参数清空全部 |
| `events.once(emitter, name)` | 把事件转成 Promise | 会监听 `error` 并 reject |

**内部结构（简化）：**

```js
// 单监听器时直接存函数，多监听器时存数组，减少数组开销
this._events = {
  data: fn,            // 一个监听器
  end: [fn1, fn2],     // 多个监听器
};
```

`emit` 在监听器多于一个时会**先复制数组再遍历**，所以监听器内部增删监听器不会影响本次分发；但这也意味着「移除后仍可能被本轮调用一次」。

**手写一个最小实现：**

```js
// mini-emitter.js —— 运行：node mini-emitter.js
class MiniEmitter {
  constructor() {
    this._events = Object.create(null);
  }

  on(type, fn) {
    (this._events[type] ||= []).push(fn);
    return this; // 支持链式调用
  }

  once(type, fn) {
    // wrapper 负责在执行后移除自己，同时保留原函数引用供 off 使用
    const wrapper = (...args) => {
      this.off(type, wrapper);
      fn.apply(this, args);
    };
    wrapper._origin = fn;
    return this.on(type, wrapper);
  }

  off(type, fn) {
    const list = this._events[type];
    if (!list) return this;
    this._events[type] = list.filter((item) => item !== fn && item._origin !== fn);
    return this;
  }

  emit(type, ...args) {
    const list = this._events[type];
    if (!list || list.length === 0) {
      if (type === 'error') {
        // 与 Node 行为一致：无监听器的 error 事件直接抛出
        throw args[0] instanceof Error ? args[0] : new Error('Unhandled error event');
      }
      return false;
    }
    for (const fn of [...list]) fn.apply(this, args); // 复制后遍历
    return true;
  }
}

const bus = new MiniEmitter();
bus.once('ready', (name) => console.log('once:', name));
bus.on('ready', (name) => console.log('on:', name));
bus.emit('ready', 'A');
bus.emit('ready', 'B');
// 输出：once: A → on: A → on: B
```

**真实场景下的用法：**

```js
// emitter-usage.js —— 运行：node emitter-usage.js
const { EventEmitter, once, errorMonitor } = require('node:events');

class TaskQueue extends EventEmitter {
  constructor() {
    // captureRejections：监听器返回 rejected Promise 时转成 'error' 事件
    super({ captureRejections: true });
    this.tasks = [];
  }

  add(task) {
    this.tasks.push(task);
    this.emit('add', task);
  }
}

const queue = new TaskQueue();

queue.on('add', (task) => console.log('监听器 1:', task));

// errorMonitor 在 'error' 事件之前收到错误，适合只做日志、不消费错误
queue.on(errorMonitor, (err) => console.log('errorMonitor:', err.message));
// 必须保留 'error' 监听器，否则进程会因未处理的 error 事件退出
queue.on('error', (err) => console.log('error 事件:', err.message));

async function main() {
  queue.add('task-1');

  queue.on('add', async () => {
    throw new Error('异步监听器失败'); // captureRejections 把它变成 'error'
  });
  queue.add('task-2');

  // 把一次性事件转成 Promise，失败会 reject
  setTimeout(() => queue.emit('done', 'ok'), 10);
  const args = await once(queue, 'done');
  console.log('once 拿到参数:', args); // [ 'ok' ]
}

main();
```

**与浏览器 `EventTarget` 的区别：**

| 维度 | Node `EventEmitter` | DOM `EventTarget` |
| --- | --- | --- |
| 事件对象 | 任意参数 `...args` | 必须是 `Event` 实例 |
| 冒泡/捕获 | 不支持 | 支持 |
| 默认行为 | 无 | 有 `preventDefault` |
| 异步监听器 | 默认不处理 rejection（可开 `captureRejections`） | 无此概念 |
| 一次性监听 | `once()` | `{ once: true }` |

**面试怎么答：** 先给「同步发布订阅」的定位，再讲内部用对象/数组存监听器、`once` 用 wrapper 自移除、`emit` 复制数组后同步调用；重点强调 `error` 事件的特殊语义与 `captureRejections`；最后说它在 Stream、HTTP、进程信号中的广泛应用。

**易错点：**

- `emit` 是同步的，监听器里的耗时逻辑会阻塞触发方。
- `error` 事件没有监听器会直接 throw，这是进程崩溃的常见原因。
- 监听器数量超过 10 只是告警，不是泄漏的证明；但持续增长通常意味着重复注册。
- `once` 后用原函数 `off` 无法移除 wrapper，Node 内部做了 `_origin` 映射，自定义实现要注意。
- 在监听器里 `removeAllListeners` 不会阻止本轮已复制的数组继续执行。

## 9. 定时器与 unref/ref

**结论：** Node 进程是否退出，取决于**是否还有被引用的活跃 handle**。定时器默认是 `ref` 状态，会阻止进程退出；调用 `unref()` 后不再阻止退出，但**只要进程还活着，回调仍然会按时触发**；`ref()` 可以恢复。`unref` 是「不拖住进程」，不是「取消定时器」。

**`Timeout` 对象的能力：**

| 方法/属性 | 作用 |
| --- | --- |
| `ref()` | 恢复引用，重新阻止进程退出 |
| `unref()` | 解除引用，不再阻止进程退出 |
| `hasRef()` | 当前是否处于 ref 状态 |
| `refresh()` | 重新开始计时（重置到期时间） |
| `close()` | 取消定时器，等价于 `clearTimeout` |
| `[Symbol.toPrimitive]()` | 可当作数字用于 `clearTimeout` |

`setImmediate` 返回的 `Immediate` 对象同样有 `ref()` 与 `unref()`。

**关键规则：**

1. `setTimeout` 的最小延迟是 **1ms**，传 0 会被当作 1。
2. 最大延迟是 **2147483647ms**（约 24.8 天），超过会告警并退化为 1ms，长周期任务应自己分段。
3. `setInterval` 不保证严格间隔，回调执行时间会累积成漂移；需要稳定节奏时用「递归 `setTimeout` 并按实际耗时补偿」。
4. `unref()` 只影响「是否阻止退出」，不影响「是否执行」；如果进程因没有其它 handle 而退出，回调不会执行。
5. `server.unref()`、`socket.unref()`、`child.unref()` 同理，常用于「不因这个句柄拖住进程」。

```js
// timer-unref.js —— 运行：node timer-unref.js
const http = require('node:http');

// 1. 默认 ref：这个定时器会拖住进程 60 秒
const keepAlive = setTimeout(() => console.log('60 秒后执行'), 60_000);
keepAlive.unref(); // 解除引用，进程不再等它

// 2. 有其它活跃 handle 时，unref 的定时器仍会正常触发
const server = http.createServer((req, res) => res.end('ok'));
server.listen(3000, () => {
  console.log('服务已启动；60 秒计时器不会阻止进程退出');

  const heartbeat = setInterval(() => {
    console.log('心跳');
  }, 1000);
  heartbeat.unref(); // 心跳不该决定进程生死
});
```

把 `server.listen` 注释掉再运行，进程会立刻退出，`60 秒后执行` 永远不会打印——这就是 `unref` 与 `clearTimeout` 的区别。

**优雅退出中的典型用法：**

```js
// graceful-shutdown.js
const server = require('node:http').createServer((req, res) => res.end('ok'));

server.listen(3000, () => console.log('启动'));

function shutdown() {
  server.close(() => {
    console.log('连接已排空，退出');
    process.exit(0);
  });
  // 兜底：10 秒还没关完就强制退出，这个定时器不能拖住进程
  setTimeout(() => {
    console.error('关闭超时，强制退出');
    process.exit(1);
  }, 10_000).unref();
}

process.on('SIGTERM', shutdown);
process.on('SIGINT', shutdown);
```

**`timers/promises`（Node 15+，推荐）：**

```js
// timer-promises.js —— 运行：node timer-promises.js
const { setTimeout: delay, setInterval: interval } = require('node:timers/promises');

(async () => {
  // ref: false 等价于 unref，不阻止进程退出
  await delay(100, undefined, { ref: false });

  // 异步迭代器：每次迭代返回一次时间点，必须手动 break
  for await (const _ of interval(50, undefined, { ref: false })) {
    console.log('每 50ms 一次');
    break;
  }

  // 可被 AbortSignal 中断，适合带超时的下游调用
  const controller = new AbortController();
  setTimeout(() => controller.abort(), 20);
  try {
    await delay(1000, undefined, { signal: controller.signal });
  } catch (err) {
    console.log('定时器被中断:', err.name); // AbortError
  }
})();
```

**长延迟任务的正确写法：**

```js
// long-delay.js —— 需要等待超过 24.8 天时，不要直接传超大值
async function sleepLong(totalMs) {
  const MAX = 2_147_483_647;
  let remaining = totalMs;
  while (remaining > 0) {
    const step = Math.min(remaining, MAX);
    await new Promise((resolve) => setTimeout(resolve, step));
    remaining -= step;
  }
}
```

**面试怎么答：** 先讲「进程退出由活跃 handle 决定」，再解释 `ref`/`unref` 只控制是否阻止退出、不控制是否执行；然后说 `refresh` 用于重置计时、`timers/promises` 的 `signal` 与异步迭代器；最后补长延迟溢出与 `server.close` 超时兜底的实践。

**易错点：**

- 认为 `unref()` 会取消定时器，实际上它照常触发，只是不阻止退出。
- 测试时用 `unref` 的定时器等结果，进程提前退出导致「代码没执行」。
- `setInterval` 做精确调度，长时间运行后漂移明显。
- `setTimeout` 传超过 2147483647 的值，行为退化为 1ms。
- 优雅关闭的兜底定时器忘了 `unref()`，导致进程多等 10 秒。

## 10. AsyncLocalStorage 与异步上下文

**结论：** `AsyncLocalStorage`（ALS）是 Node 官方提供的**异步上下文存储**：在一次调用链开始时 `run(store, callback)` 写入数据，之后无论经过多少层 Promise、定时器、I/O 回调，都能用 `getStore()` 取回同一份数据。它解决了「日志 traceId、租户信息、事务对象」在异步链路中必须层层传参的问题。

**API：**

| API | 作用 |
| --- | --- |
| `run(store, callback, ...args)` | 在指定 store 下执行回调，返回回调结果 |
| `getStore()` | 取当前异步上下文的 store，不存在返回 `undefined` |
| `enterWith(store)` | 让当前执行上下文及其后续异步操作使用该 store，影响范围较大 |
| `exit(callback, ...args)` | 在空上下文下执行回调 |
| `disable()` | 清空所有上下文并停止跟踪（一般只在测试中用） |

```js
// als-trace.js —— 运行：node als-trace.js，然后访问 http://localhost:3000
const { AsyncLocalStorage } = require('node:async_hooks');
const { randomUUID } = require('node:crypto');
const http = require('node:http');

const als = new AsyncLocalStorage();

// 日志函数不再需要显式传 requestId
function log(...args) {
  const store = als.getStore();
  console.log(`[${store?.requestId ?? '-'}]`, ...args);
}

const server = http.createServer((req, res) => {
  const requestId = req.headers['x-request-id'] || randomUUID();

  // run 之后的整条异步链都持有这份 store
  als.run({ requestId, userId: null }, async () => {
    log('收到请求', req.method, req.url);

    await new Promise((resolve) => setTimeout(resolve, 10));
    log('定时器之后仍能取到 requestId');

    await Promise.resolve().then(() => log('Promise 之后仍能取到'));

    res.setHeader('x-request-id', requestId);
    res.end('ok');
  });
});

server.listen(3000, () => log('服务启动（此时没有请求上下文）'));
```

请求 A 与请求 B 并发时，各自的日志不会串——ALS 按异步资源隔离，而不是按全局变量。

**原理（简化）：**

1. `async_hooks` 为每个异步资源（Promise、timer、TCP 连接、文件请求）分配 `asyncId`，并记录 `triggerAsyncId`。
2. ALS 维护「asyncId → store」的映射，异步资源创建时继承创建者的上下文。
3. 回调执行前，ALS 根据当前 asyncId 恢复对应 store；执行后还原。
4. 因此「在哪个上下文创建的回调」决定「回调执行时看到哪个 store」，而不是「在哪个上下文调用」。

**上下文丢失的常见场景：**

| 场景 | 是否会丢失 | 说明 |
| --- | --- | --- |
| `await`、`.then`、`queueMicrotask` | 不丢失 | 都属于可跟踪的异步资源 |
| `setTimeout` / `setInterval` | 不丢失 | 定时器创建时继承上下文 |
| `fs`、`http` 回调 | 不丢失 | I/O 异步资源可跟踪 |
| 在 `run` 之外创建的长生命周期回调 | 丢失 | 启动时注册的全局回调没有请求上下文 |
| 事件在 `run` 之外 `emit` | 丢失 | 监听器使用 emit 时的上下文 |
| `worker_threads` | 不共享 | 线程有独立上下文，需要手动传递 |
| 原生 addon 的裸回调 | 可能丢失 | 没有经过 Node 的异步资源封装 |

```js
// als-caveat.js —— 运行：node als-caveat.js
const { AsyncLocalStorage } = require('node:async_hooks');
const { EventEmitter } = require('node:events');

const als = new AsyncLocalStorage();
const bus = new EventEmitter();

// 在请求上下文之外注册，回调执行时取不到 store
bus.on('tick', () => {
  console.log('监听器 store:', als.getStore());
});

als.run({ requestId: 'req-1' }, () => {
  console.log('run 内 store:', als.getStore());
  setTimeout(() => {
    console.log('定时器内 store:', als.getStore());
    bus.emit('tick'); // 在 run 内 emit，监听器能看到 req-1
  }, 10);
});

bus.emit('tick'); // 在 run 外 emit，监听器看到 undefined
```

`emit` 发生在哪个上下文，监听器就在哪个上下文执行，所以「监听器注册位置」不影响结果，「触发位置」才影响。真正容易踩的是「启动时创建、循环复用的回调」：它们永远带着创建时的上下文。

**实践建议：**

1. 只在入口（HTTP 中间件、消息消费、定时任务）调用一次 `run`，不要在每个函数里嵌套。
2. store 里放轻量对象（id、租户、trace 上下文），不要放大 Buffer 或连接对象。
3. 优先用 `run`，慎用 `enterWith`，后者会污染当前同步执行流，容易把上下文泄漏到无关代码。
4. 跨 worker 或跨进程时，把 traceId 放进消息体或 HTTP Header 显式传递。
5. ALS 有一定开销，纯计算脚本没必要使用；Web 服务中的收益远大于成本。

**面试怎么答：** 先定位「异步上下文存储，解决异步链路传参」，再举例「一次 `run`，全链路 `getStore` 拿 traceId」；原理说 async_hooks 的 asyncId 继承；最后主动提上下文丢失场景（run 外创建的回调、worker、外部 emit）与 `enterWith` 的风险，体现深度。

**易错点：**

- 以为 `getStore()` 是全局变量，实际只在当前异步上下文有效，`run` 外是 `undefined`。
- 用 `enterWith` 代替 `run`，上下文泄漏到后续无关请求。
- 在 `run` 外注册的全局定时器里读 store，永远拿不到。
- store 里存大对象导致内存随请求生命周期延长。
- 认为 ALS 能跨 `worker_threads` 自动传递，实际需要 `workerData` 或消息显式携带。

## 11. worker_threads、child_process、cluster 的区别与选型

**结论：** 三者解决的是不同层面的问题：`worker_threads` 是**同进程多线程**，用来把 CPU 密集任务挪出主线程；`child_process` 是**独立进程**，用来执行外部程序或做故障隔离；`cluster` 是**多进程共享端口**，用来把 HTTP 服务铺满多核。**I/O 密集不需要它们，CPU 密集优先 worker，要多核跑 HTTP 才考虑 cluster。**

**对比表：**

| 维度 | `worker_threads` | `child_process` | `cluster` |
| --- | --- | --- | --- |
| 隔离级别 | 同进程，独立 V8 isolate 与事件循环 | 独立进程，独立内存空间 | 独立进程，多个实例 |
| 内存共享 | 可共享 `SharedArrayBuffer` | 不可共享，需序列化 | 不可共享 |
| 通信方式 | `postMessage` / `MessagePort` | stdin/stdout、IPC、`send` | 主进程与 worker 的 IPC |
| 启动成本 | 较低（毫秒级） | 较高（几十到几百毫秒） | 较高（每 worker 一个进程） |
| 适合任务 | 图像处理、压缩、加解密、大计算 | 调用外部命令、跑其他语言、隔离不可信任务 | 多核扩展 HTTP 服务 |
| 崩溃影响 | 可捕获 `error`，但共享进程资源 | 完全隔离，主进程不受影响 | 主进程可监听 `exit` 并重启 |
| 典型包 | 内置 `node:worker_threads` | 内置 `node:child_process` | 内置 `node:cluster` |

**选型步骤：**

1. 任务是 I/O 等待（数据库、HTTP、文件）→ 不需要多线程，异步 I/O 已经够用。
2. 任务是 CPU 计算且需要返回结果 → `worker_threads`，配合线程池复用。
3. 需要执行系统命令、跑 Python 脚本、隔离崩溃 → `child_process`。
4. 目标是让 HTTP 服务吃满多核 → `cluster`，或更现代的「多容器 + 负载均衡」。
5. 计算量巨大且要横向扩展 → 拆成独立计算服务，用消息队列通信。

**`worker_threads` 示例：**

```js
// worker-cpu.js —— 运行：node worker-cpu.js
const { Worker } = require('node:worker_threads');

// 用 eval 方式内联 worker 代码，方便单文件演示；生产中应放到独立文件
const workerCode = `
const { parentPort } = require('node:worker_threads');
function fib(n) { return n <= 1 ? n : fib(n - 1) + fib(n - 2); }
parentPort.on('message', ({ id, n }) => {
  parentPort.postMessage({ id, result: fib(n) });
});
`;

function runTask(n) {
  return new Promise((resolve, reject) => {
    const worker = new Worker(workerCode, { eval: true });
    worker.once('message', (msg) => {
      resolve(msg.result);
      worker.terminate(); // 任务结束主动回收，避免线程常驻
    });
    worker.once('error', reject);
    worker.postMessage({ id: 1, n });
  });
}

(async () => {
  console.log('主线程继续响应，不会被 fib 阻塞');
  const results = await Promise.all([35, 36, 37, 38].map(runTask));
  console.log('计算结果:', results);
})();
```

每任务新建线程只适合演示；生产应使用固定大小的线程池（`piscina`、`workerpool`），线程复用、任务排队，避免频繁创建 isolate 的开销。

**`cluster` 示例：**

```js
// cluster-server.js —— 运行：node cluster-server.js
const cluster = require('node:cluster');
const http = require('node:http');
const os = require('node:os');

// availableParallelism 在 Node 18.14+ 可用，比 os.cpus().length 更准确
const cpus = os.availableParallelism();

if (cluster.isPrimary) {
  console.log(`主进程 ${process.pid}：启动 ${cpus} 个 worker`);
  for (let i = 0; i < cpus; i++) cluster.fork();

  cluster.on('exit', (worker, code, signal) => {
    console.log(`worker ${worker.process.pid} 退出(${code || signal})，补一个`);
    cluster.fork();
  });
} else {
  http
    .createServer((req, res) => {
      res.end(`worker ${process.pid}`);
    })
    .listen(3000, () => console.log(`worker ${process.pid} 就绪`));
}
```

Linux/macOS 默认 `SCHED_RR`（主进程轮询分发连接），Windows 默认 `SCHED_NONE`（由操作系统调度），因此不同平台的连接分布可能不同。cluster 的多个 worker **不共享内存、定时器、缓存和 session**，登录态、限流计数必须放 Redis 等外部存储。

**现代部署的取舍：**

| 方案 | 适用 |
| --- | --- |
| 单进程 + 容器多副本 | 云原生默认，扩缩容与滚动发布更简单 |
| `cluster` | 单机多核、无法多副本的旧环境 |
| `worker_threads` | 单进程内的 CPU 任务卸载 |
| `child_process` | 外部命令、脚本、隔离运行 |

**面试怎么答：** 先用一句话区分「线程 / 进程 / 进程组」，再按「隔离、内存、通信、启动成本、适用场景」列表对比；选型时强调「I/O 不用多线程，CPU 用 worker，多核 HTTP 用 cluster 或多副本」；最后补 cluster 不共享状态、worker 要做线程池两个实践点。

**易错点：**

- 给每个请求 `new Worker`，线程创建与 isolate 初始化成本反而拖垮服务。
- 认为 `worker_threads` 与主线程共享普通变量，实际只能通过消息或 `SharedArrayBuffer` 共享。
- 用 cluster 后仍把 session 存在进程内存，导致请求落到不同 worker 时登录态丢失。
- 以为 `child_process.fork` 是开线程，实际是新进程，默认带 IPC 通道。
- worker 内 `require` 相对路径以 worker 文件为基准，路径写错会直接启动失败。

## 12. 在 Node 中实现并发控制与限流

**结论：** 并发控制有两个方向：**出站**限制「同时进行多少个任务」（信号量 / 队列），**入站**限制「单位时间允许多少请求」（限流算法）。核心要素是四个：并发上限或速率、排队策略与队列上限、超时与取消、拒绝时的响应（429 与 `Retry-After`）。单机限流用内存即可，多实例必须用 Redis 等共享存储。

**常见限流算法：**

| 算法 | 思路 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 固定窗口 | 每个时间窗计数，超限拒绝 | 实现最简单 | 窗口边界双倍流量 |
| 滑动日志 | 记录每次请求时间戳 | 精确 | 内存随请求量增长 |
| 滑动窗口计数 | 当前窗口 + 上一窗口加权 | 精度与内存平衡 | 仍是近似值 |
| 令牌桶 | 按速率生成令牌，请求取令牌 | 允许突发 | 需要处理桶容量 |
| 漏桶 | 请求入桶，按固定速率流出 | 输出平滑 | 突发时排队延迟高 |

**出站并发控制（可运行）：**

```js
// limiter.js —— 运行：node limiter.js
function createLimiter(max) {
  let active = 0;
  const queue = [];

  function next() {
    if (active >= max || queue.length === 0) return;
    active += 1;
    const { fn, resolve, reject } = queue.shift();

    // 用 Promise.resolve().then 包一层：同步异常也会变成 rejection
    Promise.resolve()
      .then(fn)
      .then(resolve, reject)
      .finally(() => {
        active -= 1;
        next(); // 腾出名额后立刻调度下一个
      });
  }

  return function limit(fn) {
    return new Promise((resolve, reject) => {
      queue.push({ fn, resolve, reject });
      next();
    });
  };
}

const limit = createLimiter(2);
const task = (id, ms) => () =>
  new Promise((resolve) => {
    console.log(`开始任务 ${id}`);
    setTimeout(() => {
      console.log(`完成任务 ${id}`);
      resolve(id);
    }, ms);
  });

(async () => {
  const start = Date.now();
  // 5 个任务、并发 2，约 3 批，总耗时约 300ms
  await Promise.all([1, 2, 3, 4, 5].map((id) => limit(task(id, 100))));
  console.log('总耗时:', Date.now() - start, 'ms');
})();
```

生产版本还需要补三件事：**队列上限**（超过直接拒绝，避免无限堆积）、**超时**（`AbortSignal.timeout` 或 `Promise.race`）、**任务优先级**（插队或分池）。

**入站限流：令牌桶中间件（可运行）：**

```js
// rate-limit.js —— 运行：node rate-limit.js
const buckets = new Map();

function allow(key, { capacity = 5, refillPerSec = 2 } = {}) {
  const now = Date.now();
  const bucket = buckets.get(key) || { tokens: capacity, updatedAt: now };

  // 按经过的时间补充令牌，最多补到容量
  const elapsedSec = (now - bucket.updatedAt) / 1000;
  bucket.tokens = Math.min(capacity, bucket.tokens + elapsedSec * refillPerSec);
  bucket.updatedAt = now;

  if (bucket.tokens < 1) {
    buckets.set(key, bucket);
    return {
      ok: false,
      retryAfter: Math.ceil((1 - bucket.tokens) / refillPerSec), // 秒
    };
  }

  bucket.tokens -= 1;
  buckets.set(key, bucket);
  return { ok: true, remaining: Math.floor(bucket.tokens) };
}

// 定期清理长时间未使用的桶，避免 Map 无限增长
setInterval(() => {
  const now = Date.now();
  for (const [key, bucket] of buckets) {
    if (now - bucket.updatedAt > 300_000) buckets.delete(key);
  }
}, 300_000).unref();

(async () => {
  for (let i = 0; i < 8; i++) {
    console.log(i, allow('user:1'));
    await new Promise((resolve) => setTimeout(resolve, 200)); // 每 200ms 补 0.4 个令牌
  }
})();
```

**多实例场景：Redis + Lua 保证原子性。** 单条 Lua 脚本在 Redis 内原子执行，避免「读-算-写」之间的竞态；固定窗口也可以用 `INCR` + `PEXPIRE` 实现，但要注意首次设置过期时间。

```lua
-- KEYS[1]=限流键，ARGV={容量, 每秒补充速率, 当前毫秒}
local b = redis.call('HMGET', KEYS[1], 'tokens', 'updated')
local tokens = tonumber(b[1]) or tonumber(ARGV[1])
local updated = tonumber(b[2]) or tonumber(ARGV[3])
local delta = math.max(0, ARGV[3] - updated) / 1000
tokens = math.min(tonumber(ARGV[1]), tokens + delta * tonumber(ARGV[2]))
local allowed = tokens >= 1 and 1 or 0
tokens = tokens - allowed
redis.call('HMSET', KEYS[1], 'tokens', tokens, 'updated', ARGV[3])
redis.call('PEXPIRE', KEYS[1], 60000)
return { allowed, math.floor(tokens) }
```

**限流设计的五个细节：**

1. **限流键要分维度**：用户 ID、IP、接口、租户，组合成 `rl:{scope}:{id}`，避免全站共用一个桶。
2. **白名单与分级**：内部服务、健康检查放行；付费用户更高配额。
3. **拒绝要可感知**：返回 429、`Retry-After`、`X-RateLimit-*`，让客户端退避而不是立即重试。
4. **不要只靠单机内存**：多副本部署时每个进程各算一份，实际配额是 N 倍。
5. **保护自己也要保护下游**：入站限流之外，出站并发控制与熔断、超时同样必要。

**面试怎么答：** 先区分「并发控制」与「限流」两个问题，再给出站用信号量 + 队列、入站用令牌桶/滑动窗口；实现层面讲清「补充速率、容量、原子性、拒绝响应」四个参数；最后补单机与分布式差异，以及队列上限、超时、Redis Lua 三个工程细节。

**易错点：**

- 只在单进程内存里限流，多副本后配额被放大 N 倍。
- 令牌桶补令牌时不做 `Math.min` 上限，长时间空闲后攒出巨大突发。
- 限流后返回 500 或直接断开连接，客户端无法区分「该退避」还是「服务故障」。
- 队列没有上限，下游变慢时内存持续增长直至 OOM。
- 用 `setInterval` 补充令牌而不是按时间差惰性计算，定时器抖动会造成速率不准。
- 把并发控制写成「固定 sleep」，吞吐下降且无法应对下游恢复。
