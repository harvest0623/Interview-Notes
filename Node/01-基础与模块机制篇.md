## 1. Node.js 是什么？与浏览器中的 JavaScript 有什么区别

**结论：** Node.js 是一个**基于 Chrome V8 引擎的 JavaScript 运行时（runtime）**，它把 V8 嵌入到一个由 C++ 实现的宿主进程中，并借助 **libuv** 提供事件循环、线程池与跨平台异步 I/O。JavaScript 语言本身在两端一致，但**宿主环境提供的能力、全局对象、模块系统、事件循环实现**完全不同。

一句话对比：**浏览器给 JS 的是 DOM、BOM 与沙箱；Node 给 JS 的是文件、网络、进程与操作系统能力。**

**运行时的组成：**

```
业务代码（JavaScript）
      ↓
Node 标准库（fs、http、path、stream……，大部分由 JS 实现）
      ↓
C++ Binding（把 JS 调用转成对底层能力的调用）
      ↓
V8（编译并执行 JS） + libuv（事件循环、线程池、epoll/kqueue/IOCP）
      ↓
操作系统（文件系统、网络协议栈、进程与信号）
```

**浏览器与 Node 的对比：**

| 维度 | 浏览器 | Node.js |
| --- | --- | --- |
| 宿主 | 浏览器内核（Chrome / Firefox / Safari） | 独立的操作系统进程 |
| 全局对象 | `window`（`globalThis` 指向它） | `global`（`globalThis` 指向它） |
| 内置能力 | DOM、BOM、`localStorage`、`fetch`、Canvas | 文件、网络、进程、`Buffer`、`crypto` |
| 模块系统 | 原生 ESM（`<script type="module">`），早期靠打包器 | CommonJS 为主，同时支持 ESM |
| 事件循环 | HTML 规范定义，任务队列 + 微任务 + 渲染 | libuv 定义，六个阶段 + 微任务 |
| 多线程 | Web Worker（受同源与 DOM 限制） | `worker_threads`、`child_process`、`cluster` |
| 生命周期 | 页面关闭即结束 | 由事件循环决定何时退出，有进程信号 |
| 安全模型 | 同源策略、沙箱 | 拥有进程权限，可直接读写文件 |
| 包管理 | 无统一标准（npm 也可用于前端构建） | npm / pnpm / yarn，`node_modules` |
| 典型用途 | 页面交互、渲染 | 服务端 API、CLI、构建工具、BFF |

**「Node 是单线程」这句话要怎么理解：**

1. **执行 JavaScript 的主线程只有一个**，同一时刻只有一段 JS 代码在跑，所以长同步计算会阻塞所有请求。
2. **libuv 维护一个线程池**（默认 4 个线程，可用环境变量 `UV_THREADPOOL_SIZE` 调整），负责文件读写、DNS 查询（`getaddrinfo`）、`crypto` 的部分算法、`zlib` 压缩等「没有异步系统调用」的任务。
3. **网络 I/O 不占线程池**：Linux 用 epoll、macOS 用 kqueue、Windows 用 IOCP，由内核通知事件循环。
4. 因此 Node 的高并发来自**事件驱动 + 非阻塞 I/O**，而不是「多线程并行计算」。

```js
// runtime-compare.js —— Node 18+ 直接运行：node runtime-compare.js
const fs = require('node:fs');

// 1. 全局对象：Node 是 global，浏览器是 window
console.log('global === globalThis:', global === globalThis); // true
console.log('typeof window:', typeof window);                 // undefined

// 2. Node 能拿到进程与操作系统信息，浏览器没有这些概念
console.log('Node 版本:', process.version);
console.log('平台/架构:', process.platform, process.arch);

// 3. 同样的回调风格，Node 的文件读取由 libuv 线程池完成，不阻塞 JS 主线程
fs.readFile(__filename, 'utf8', (err, source) => {
  if (err) throw err;
  console.log('读取到源码长度:', source.length);
});

// 4. 同步代码先执行完，回调要等文件读取完成后才进入事件循环
console.log('这一行先于 readFile 回调输出');
```

**两者的相同点（面试时也要提一句）：**

- 都遵循 ECMAScript 标准，`Promise`、`async/await`、`Proxy`、`Map` 等语义一致。
- 都有事件循环与微任务，但**调度细节不同**（见 02 分册）。
- 都能使用 `globalThis`、`URL`、`TextEncoder`、`AbortController` 等跨平台 API。

**面试怎么答：** 先给定义「基于 V8 的 JavaScript 运行时」，再按「宿主能力、全局对象、模块系统、事件循环、线程模型」五点对比，最后补一句「Node 的高并发靠事件驱动与非阻塞 I/O，而不是单线程跑得快」。

**易错点：**

- Node **不是语言、不是框架、也不是浏览器里的 JS**，它是运行时；`npm` 只是包管理器，不等于 Node。
- 「单线程」指的是 **JS 执行线程**，libuv 线程池、`worker_threads`、`cluster` 都可能引入多线程/多进程。
- 浏览器与 Node 都有 `fetch`，但 Node 18 的 `fetch` 默认开启且标注为实验性，Node 21 才转为稳定；不要假设所有 18.x 小版本行为完全一致。

## 2. Node.js 适合与不适合哪些场景

**结论：** Node 的优势是**大量并发连接 + 少量计算 + 高频 I/O**；劣势是**CPU 密集型任务**会阻塞唯一的事件循环。选型时先判断「瓶颈在 I/O 还是在 CPU」。

**适合的场景：**

| 场景 | 为什么适合 | 典型技术 |
| --- | --- | --- |
| Web API / BFF | 请求主要是转发与聚合，等待下游 I/O，天然非阻塞 | Express、Koa、NestJS、Fastify |
| 实时通信 | 长连接多、消息小而频繁，事件驱动模型开销低 | WebSocket、Socket.IO、SSE |
| 服务端渲染 | 与前端同语言，可复用模板与类型 | Next.js、Nuxt |
| CLI 与构建工具 | 启动快、生态全、跨平台 | Vite、webpack、ESLint、脚手架 |
| 微服务 / 网关 | 轻量、启动快、适合做协议转换与聚合 | gRPC、API Gateway |
| 流式处理 | `stream` 背压机制成熟，边读边写内存占用低 | 日志采集、文件转码管道 |
| I/O 密集型脚本 | 爬虫、同步任务、消息消费 | `undici`、`puppeteer`、定时任务 |

**不适合的场景：**

| 场景 | 原因 | 更合适的方案 |
| --- | --- | --- |
| 图像/视频转码 | 计算密集，会长时间占满主线程 | 独立服务（Go/C++/Rust）、FFmpeg 子进程 |
| 大规模数值计算、机器学习训练 | 缺少 SIMD 与成熟数值库，GC 压力大 | Python + NumPy、C++、GPU |
| 超高并发的纯内存计算 | 单线程无法利用多核 | Go、Java、Rust |
| 硬实时系统 | GC 与事件循环存在不可控延迟 | C/C++、Rust |
| 超大内存驻留应用 | 单进程内存与 GC 停顿受限 | JVM 系、分片部署 |

**判断流程：**

```
请求/任务的主要耗时在哪里？
   ├─ 等数据库、等 HTTP、等磁盘 → I/O 密集 → Node 合适
   ├─ 等锁、等第三方限流     → I/O 密集 → Node 合适（注意连接池）
   └─ 在本进程里算          → CPU 密集 → 不要放在主线程
                                ├─ 偶发、可切片 → worker_threads
                                ├─ 重任务、可独立部署 → 单独服务
                                └─ 可外置 → 交给专用工具/子进程
```

**CPU 密集任务的最小改造示例：**

```js
// cpu-offload.js —— Node 18+：把斐波那契计算放到 worker 线程
const { Worker, isMainThread, parentPort, workerData } = require('node:worker_threads');

if (isMainThread) {
  const start = Date.now();

  // 主线程继续处理定时器与 I/O，不被计算阻塞
  setTimeout(() => console.log('主线程定时器仍然准时:', Date.now() - start, 'ms'), 10);

  const worker = new Worker(__filename, { workerData: 40 });
  worker.on('message', (result) => {
    console.log('计算结果:', result, '总耗时:', Date.now() - start, 'ms');
  });
  worker.on('error', (err) => console.error('worker 出错:', err));
} else {
  // 子线程里执行真正的 CPU 计算
  const fib = (n) => (n < 2 ? n : fib(n - 1) + fib(n - 2));
  parentPort.postMessage(fib(workerData));
}
```

**面试怎么答：** 先说结论「I/O 密集型适合、CPU 密集型不适合」，再各举三类场景，最后给出改造手段（`worker_threads`、拆分服务、子进程），并补一句「Node 的价值是同一个语言覆盖前后端与高并发连接，而不是性能绝对值最高」。

**易错点：**

- 不要笼统说「Node 性能差」：**吞吐与延迟取决于场景**，I/O 密集场景下 Node 往往优于同步阻塞模型。
- 用了 `async` 不等于不阻塞：`await` 后面的同步计算、`JSON.parse` 大对象、同步 `fs` 都会阻塞事件循环。
- `worker_threads` 不是银弹：线程间通信有序列化成本，`SharedArrayBuffer` 才适合共享大块内存。

## 3. CommonJS 的模块机制（require 流程、缓存、循环依赖）

**结论：** CommonJS 模块在**首次 `require` 时同步执行**，执行结果挂在 `module.exports` 上，并按**解析后的绝对路径**缓存到 `require.cache`。循环依赖时，后加载的模块会拿到前一个模块**尚未执行完的半成品 `exports`**。

**每个模块都被包裹在一个函数里：**

```js
// Node 内部用 Module.wrapper 包装模块源码，等价于：
(function (exports, require, module, __filename, __dirname) {
  // 你写的模块代码
});
```

因此模块内的 `exports`、`require`、`module`、`__filename`、`__dirname` 都是**函数参数**，不是真正的全局变量。可以通过 `require('node:module').wrapper` 查看。

**require 的完整流程：**

| 步骤 | 内部动作 | 说明 |
| --- | --- | --- |
| 1 | `Module._resolveFilename` | 把 `./a`、`lodash` 解析成绝对路径 |
| 2 | 查 `Module._cache` | 命中则直接返回 `module.exports`，不重复执行 |
| 3 | `new Module(filename)` | 创建模块实例，记录 `parent` / `children` |
| 4 | 放入缓存 | **先缓存再执行**，这是循环依赖能拿到半成品的原因 |
| 5 | `module.load(filename)` | 按扩展名选择加载器 |
| 6 | `module._compile` | 包装成函数并执行，传入五个参数 |
| 7 | 返回 `module.exports` | 若执行抛错，则从缓存删除并向上抛 |

**路径解析顺序（简化）：**

```
require('fs')                    → 核心模块，直接返回
require('/abs/path/a')           → 绝对路径，按文件/目录加载
require('./a')                   → 相对当前模块
require('lodash')                → 逐级向上找 node_modules/lodash

LOAD_AS_FILE:      a.js → a.json → a.node
LOAD_AS_DIRECTORY: 读 package.json 的 main → index.js → index.json → index.node
```

**缓存示例：**

```js
// cache-demo.js —— 同一个路径只会执行一次
const counter = require('./counter');
const again = require('./counter');

console.log(counter === again); // true，拿到的是同一个 module.exports

// 缓存键是解析后的绝对路径，不是 require 时写的字符串
console.log(Object.keys(require.cache).some((k) => k.endsWith('counter.js'))); // true

// 想重新加载（例如热更新配置）必须手动删除缓存
delete require.cache[require.resolve('./counter')];
const fresh = require('./counter');
console.log(fresh === counter); // false，重新执行后是新对象
```

**循环依赖示例：**

```js
// a.js
exports.loaded = false;
const b = require('./b');          // 此时 a 还没执行完，b 拿到的是半成品
console.log('a 看到 b:', b.name);
exports.loaded = true;
exports.name = 'a';
```

```js
// b.js
const a = require('./a');          // 命中缓存，拿到 { loaded: false }
console.log('b 看到 a:', a);       // { loaded: false }，没有 name
module.exports = { name: 'b' };
```

```js
// main.js
const a = require('./a');
console.log('最终 a:', a);         // { loaded: true, name: 'a' }
```

执行 `node main.js` 的输出顺序是：`b 看到 a: { loaded: false }` → `a 看到 b: b` → `最终 a: { loaded: true, name: 'a' }`。**关键点：`b.js` 执行时 `a.js` 只完成了 `exports.loaded = false` 这一行。**

**为什么 CommonJS 是同步的：**

- 模块加载发生在**运行时**，`require` 必须立刻返回一个值，因此只能同步读文件、同步执行。
- 这也是 ESM 要引入「静态分析 + 异步链接」的原因：ESM 可以在执行前确定依赖关系，从而支持循环依赖的 live binding 与 tree shaking。

**面试怎么答：** 按「模块包装函数 → 解析路径 → 查缓存 → 先缓存后执行 → 编译执行 → 返回 `module.exports`」讲完整流程，再补缓存键是绝对路径、循环依赖拿到半成品、`delete require.cache` 可强制重载。

**易错点：**

- 缓存发生在**执行之前**，不是执行之后；否则循环依赖会无限递归。
- `require` 返回的是 `module.exports` 的**当前值**，模块内部后续再改 `module.exports` 不会影响已经取走的值。
- `.json` 文件走 `JSON.parse`，`.node` 是 C++ 扩展；不要假设所有文件都按 JS 编译。
- 热重载只删当前模块缓存不够，依赖它的模块仍持有旧引用；生产环境不要依赖这种做法。

## 4. CommonJS 与 ES Module 的互操作

**结论：** Node 同时支持两套模块系统。**ESM 可以 `import` CommonJS**（`default` 就是 `module.exports`，命名导出靠静态分析）；**CommonJS 在 Node 20.19+/22.12+ 可以同步 `require()` ESM**（前提是没有 top-level await），更早版本需要实验开关或改用动态 `import()`。

**两套系统的本质差异：**

| 维度 | CommonJS | ES Module |
| --- | --- | --- |
| 加载时机 | 运行时，`require` 同步执行 | 解析期静态分析，先链接后执行 |
| 导出值 | `module.exports` 的快照引用 | live binding，导出变量变化会同步 |
| 顶层 `this` | `module.exports` | `undefined` |
| 顶层 await | 不支持 | 支持（在 ESM 中） |
| 文件扩展名 | `.js` / `.cjs` 默认 CJS，可省略扩展名 | `.mjs`，或 `type: module` 下的 `.js`，**必须写扩展名** |
| `__dirname` / `__filename` | 直接可用 | 不存在，需用 `import.meta.url` 推导 |
| 严格模式 | 默认非严格 | 默认严格 |
| 循环依赖 | 返回半成品，容易拿到 `undefined` | 先建立绑定再执行，TDZ 内访问会报错 |
| Tree shaking | 困难（导出是运行时对象） | 容易（静态结构可分析） |
| 动态导入 | `require()` 同步 | `import()` 返回 Promise |

**方向一：ESM 导入 CommonJS**

```js
// math.cjs —— CommonJS 模块
module.exports = {
  add: (a, b) => a + b,
  version: '1.0.0',
};
```

```js
// use-esm.mjs —— 用 ESM 导入上面的 CJS
import math from './math.cjs';            // default 等于整个 module.exports
import { add, version } from './math.cjs'; // 命名导出由 cjs-module-lexer 静态探测
import * as ns from './math.cjs';

console.log(math.add(1, 2));      // 3
console.log(add(3, 4));           // 7
console.log(version);             // 1.0.0
console.log(ns.default === math); // true
```

命名导出不是运行时解构，而是 Node 用 `cjs-module-lexer` 对源码做静态分析得到的。**写成 `module.exports = someFunction` 或动态赋值时，往往只能拿到 `default`。**

**方向二：CommonJS 加载 ESM**

```js
// use-cjs.cjs
// Node 20.19+ / 22.12+：无 top-level await 的 ESM 可以被同步 require
const esm = require('./pure-esm.mjs');
console.log(esm.default, esm.named);

// 兼容旧版本的通用写法：动态 import() 返回 Promise
(async () => {
  const mod = await import('./pure-esm.mjs');
  console.log(mod.default, mod.named);
})();
```

如果 ESM 里存在 top-level await，同步 `require()` 会抛 `ERR_REQUIRE_ASYNC_MODULE`，只能走 `import()`。

**在 ESM 里补回 CJS 的便利能力：**

```js
// esm-compat.mjs
import { fileURLToPath } from 'node:url';
import { dirname } from 'node:path';
import { createRequire } from 'node:module';

const __filename = fileURLToPath(import.meta.url);
const __dirname = dirname(__filename);
const require = createRequire(import.meta.url); // 可以继续 require CJS 包

console.log(__dirname);
console.log(require('./math.cjs').add(2, 3));
```

**双包风险（dual package hazard）：**

同一个库同时提供 CJS 与 ESM 入口时，如果应用里既有 `require('lib')` 又有 `import 'lib'`，可能加载出**两份实例**：单例、缓存、`instanceof` 判断都会失效。解决办法：

1. 库只提供一种入口，另一种用 wrapper 转发到同一份实现；
2. 用 `package.json` 的 `exports` 条件导出，保证两条路径指向同一个文件；
3. 应用层统一模块系统，避免混用。

**面试怎么答：** 先讲两套系统的加载时机与导出语义差异，再分两个方向讲互操作：ESM 导入 CJS 的 `default` 与命名导出探测；CJS 加载 ESM 的版本门槛与 top-level await 限制；最后补 `createRequire`、`import.meta.url` 与双包风险。

**易错点：**

- ESM 里没有 `__dirname`、`__filename`、`require`，不要直接复制 CJS 代码。
- ESM 导入相对路径**必须带扩展名**，`import './utils'` 会报 `ERR_MODULE_NOT_FOUND`。
- `import { add } from './math.cjs'` 能否成功取决于 CJS 的导出写法，动态赋值时只能拿 `default`。
- `require()` ESM 的版本差异要记清：Node 20.17 需 `--experimental-require-module`，20.19+/22.12+ 默认可用；不要把 18.x 的行为当成通用行为。

## 5. module.exports 与 exports 的区别

**结论：** `exports` 只是 `module.exports` 的**初始引用**。给 `exports.foo` 赋值会同时反映到 `module.exports` 上；但一旦给 `exports` **重新赋值**，它就指向了新对象，与 `module.exports` 断开，`require` 拿到的仍是原来的对象。

**内存关系：**

```
初始状态：
  exports ─┐
           ├──> { }   ← module.exports 指向的对象
  module.exports ─┘

执行 exports = { a: 1 } 之后：
  exports ───────────> { a: 1 }     （新对象，require 看不到）
  module.exports ────> { }          （旧对象，require 返回它）
```

**四种写法对比：**

| 写法 | 是否生效 | 原因 |
| --- | --- | --- |
| `exports.a = 1` | 生效 | 修改的是 `module.exports` 指向的对象 |
| `module.exports.a = 1` | 生效 | 直接修改目标对象 |
| `module.exports = { a: 1 }` | 生效 | 把 `module.exports` 指向新对象 |
| `exports = { a: 1 }` | **不生效** | 只改了局部变量 `exports` 的指向 |

```js
// case-1.cjs
exports.a = 1;
// require 得到 { a: 1 }

// case-2.cjs
module.exports = { a: 1 };
// require 得到 { a: 1 }

// case-3.cjs
exports = { a: 1 };
// require 得到 {}，exports 的新对象被丢弃

// case-4.cjs
exports.a = 1;
module.exports = { b: 2 };
// require 得到 { b: 2 }，之前挂在旧对象上的 a 丢失
```

**常见正确写法：**

```js
// 导出多个成员
exports.add = (a, b) => a + b;
exports.sub = (a, b) => a - b;

// 导出一个函数/类，必须用 module.exports
module.exports = class User {
  constructor(name) {
    this.name = name;
  }
};

// 需要同时保留命名属性时，重新建立引用
module.exports = User;
module.exports.helper = () => 'helper';
```

**为什么 Node 要同时提供两个名字：**

- 历史原因：早期 CommonJS 规范只有 `exports`，后来为了支持「导出单个值」增加了 `module.exports`。
- `exports` 只是书写方便，**最终 `require` 只认 `module.exports`**。

**面试怎么答：** 一句话「`exports` 是 `module.exports` 的引用副本，改属性生效、重新赋值失效」，再用四种写法说明，最后补「导出函数/类时用 `module.exports =`，导出多个成员时用 `exports.foo =`」。

**易错点：**

- `exports = module.exports = {...}` 可以生效，因为它同时改了两个变量，但没必要写得这么绕。
- 混用 `exports.foo` 与 `module.exports = {...}` 时，先挂的属性会丢失。
- TypeScript 编译到 CommonJS 时会给 `exports` 加 `__esModule` 标记，这不是 Node 的行为，而是编译器的约定。

## 6. package.json 中的 main、module、exports、type 字段

**结论：** `main` 是传统的 CommonJS 入口；`module` 是打包器（webpack/Rollup）识别的 ESM 入口，**Node 本身不读它**；`exports` 是现代入口声明，支持条件导出与子路径封装；`type` 决定 `.js` 文件按 CommonJS 还是 ESM 解释。

**字段对比：**

| 字段 | 读取方 | 作用 | 备注 |
| --- | --- | --- | --- |
| `main` | Node、打包器 | 包的默认入口 | 缺省为 `index.js`；只在没有 `exports` 时对根导入生效 |
| `module` | 打包器 | 指向 ESM 版本，便于 tree shaking | 非 Node 标准字段，Node 直接忽略 |
| `exports` | Node、打包器 | 声明所有可被外部访问的入口 | 优先级高于 `main`；未列出的子路径无法导入 |
| `type` | Node | `"commonjs"`（默认）或 `"module"` | 影响 `.js` 的解释方式；`.cjs` / `.mjs` 永远覆盖它 |
| `imports` | Node | 以 `#` 开头的内部别名 | 只能包内使用，常用于 `#internal/*` |

**`type` 的作用范围：**

```
type 缺省 / "commonjs"：
  .js   → CommonJS
  .mjs  → ESM
  .cjs  → CommonJS

type: "module"：
  .js   → ESM
  .mjs  → ESM
  .cjs  → CommonJS
```

**`exports` 的三种写法：**

```json
{
  "name": "my-lib",
  "type": "module",
  "exports": "./dist/index.js"
}
```

```json
{
  "name": "my-lib",
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.mjs",
      "require": "./dist/index.cjs",
      "default": "./dist/index.js"
    },
    "./utils": "./dist/utils.js"
  }
}
```

```json
{
  "name": "my-lib",
  "exports": {
    "./features/*": "./src/features/*.js",
    "./features/private/*": null
  }
}
```

**条件导出的匹配规则：**

1. 条件对象按**书写顺序**从上到下匹配，命中即停，所以 `default` 必须放最后。
2. `types` 必须放在最前，否则 TypeScript 可能匹配不到声明文件。
3. 常见条件：`node`、`import`、`require`、`types`、`default`；还支持自定义条件（`--conditions=xxx`）。
4. `exports` 的 key 必须以 `./` 开头；`.` 表示包根。
5. `null` 用于显式封禁某个子路径。
6. `exports` 与 `main` 同时存在时，**根导入以 `exports` 为准**，`main` 只作为旧版工具的兜底。

```js
// 在 Node 中观察实际解析结果
console.log(require.resolve('my-lib'));        // CJS 条件
console.log(import.meta.resolve('my-lib'));    // ESM 条件（Node 20.6+ 同步可用）
```

**一个常见的发布结构：**

```
my-lib/
├─ package.json
├─ dist/
│  ├─ index.cjs      ← require 入口
│  ├─ index.mjs      ← import 入口
│  └─ index.d.ts
└─ src/
```

```json
{
  "name": "my-lib",
  "type": "module",
  "main": "./dist/index.cjs",
  "module": "./dist/index.mjs",
  "types": "./dist/index.d.ts",
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.mjs",
      "require": "./dist/index.cjs"
    }
  },
  "files": ["dist"]
}
```

**面试怎么答：** 按「`main` 传统入口、`module` 只给打包器、`exports` 现代条件导出与路径封装、`type` 决定 `.js` 语义」四点讲，再补 `exports` 的匹配顺序、`types` 放首位、未导出路径不可访问。

**易错点：**

- 加了 `exports` 之后，包内其他文件不再能被 `require('my-lib/xxx')` 直接访问，必须显式声明子路径。
- `module` 字段 Node 不认；只在 Node 里跑的话，写了也没用。
- 条件对象顺序敏感，`default` 写在前面会让后面的 `import`/`require` 永远匹配不到。
- 把 `type` 改成 `"module"` 会让所有 `.js` 变成 ESM，原来的 `require`、`__dirname` 立刻报错，迁移要逐步来。

## 7. Buffer 的原理与常见用法

**结论：** `Buffer` 是 Node 为**二进制数据**提供的固定长度字节数组，继承自 `Uint8Array`（Node 4 起），可以直接与 TypedArray、ArrayBuffer 互操作。它常用于文件、网络、加密、流式数据的中间表示。

**核心特征：**

| 特性 | 说明 |
| --- | --- |
| 定长 | 创建后长度不可变，不能 `push`/`pop` |
| 类数组 | 继承 `Uint8Array`，支持下标、`length`、`subarray` |
| 二进制 | 每个元素是 0-255 的字节，不是字符 |
| 编码转换 | `Buffer.from(str, encoding)` / `buf.toString(encoding)` |
| 共享内存 | `slice`/`subarray`、`Buffer.from(arrayBuffer)` 不拷贝 |
| 池化 | 小于 4KB 的 `allocUnsafe` 从 8KB 内存池切分 |

**三种创建方式：**

```js
// 1. 分配指定长度，内容全部为 0，安全但多一次清零
const zero = Buffer.alloc(4);
console.log(zero); // <Buffer 00 00 00 00>

// 2. 分配但不初始化，可能残留旧数据，性能更高但必须自己写满
const unsafe = Buffer.allocUnsafe(4);
unsafe.fill(0); // 演示：实际使用中要确保每个字节都被赋值

// 3. 从字符串/数组/ArrayBuffer 创建
const fromStr = Buffer.from('你好', 'utf8');
const fromArr = Buffer.from([0x68, 0x69]);
const fromAb = Buffer.from(new ArrayBuffer(8)); // 与 ArrayBuffer 共享内存
```

**常用 API：**

| API | 作用 |
| --- | --- |
| `Buffer.from(data, encoding)` | 从字符串、数组、ArrayBuffer 创建 |
| `Buffer.alloc(size)` | 分配并清零 |
| `Buffer.allocUnsafe(size)` | 分配不清零（可能含旧数据） |
| `Buffer.concat(list, totalLength)` | 拼接多个 Buffer |
| `Buffer.byteLength(str, encoding)` | 计算字符串按指定编码的字节数 |
| `Buffer.isBuffer(obj)` | 判断是否为 Buffer |
| `buf.toString(encoding)` | 转字符串，默认 `utf8` |
| `buf.subarray(start, end)` | 返回共享内存的视图 |
| `buf.readUInt32BE(offset)` | 按大端读取 32 位无符号整数 |
| `StringDecoder` | 按块解码，避免多字节字符被切断 |

**编码与长度的坑：**

```js
const text = '你好';
console.log(Buffer.byteLength(text, 'utf8')); // 6，每个汉字 3 字节
console.log(text.length);                     // 2，按 UTF-16 码元计数
console.log(Buffer.from(text).toString('base64')); // 5L2g5aW9
console.log(Buffer.from('5L2g5aW9', 'base64').toString('utf8')); // 你好
```

**共享内存示例（重要）：**

```js
const buf = Buffer.from('abcdef');
const view = buf.subarray(0, 3);

view[0] = 'z'.charCodeAt(0);
console.log(buf.toString());  // zbcdef，修改视图会影响原 Buffer
console.log(buf === view);    // false，但是同一块内存

// 需要独立副本时显式拷贝
const copy = Buffer.from(buf);
copy[0] = 'x'.charCodeAt(0);
console.log(buf.toString());  // zbcdef，原 Buffer 不变
```

**流式读取时的中文乱码问题：**

```js
// 直接对每个 chunk 调用 toString，汉字可能被切成两半，出现乱码
const { StringDecoder } = require('node:string_decoder');
const decoder = new StringDecoder('utf8');

process.stdin.on('data', (chunk) => {
  // StringDecoder 会缓存不完整的字节，等下一个 chunk 补齐后再输出
  process.stdout.write(decoder.write(chunk));
});

process.stdin.on('end', () => {
  process.stdout.write(decoder.end());
});
```

**面试怎么答：** 先定义「定长字节数组、Uint8Array 子类」，再讲三种分配方式的区别（清零与安全）、常用编码转换、`subarray` 共享内存、流式场景用 `StringDecoder` 处理断字，最后补 `allocUnsafe` 的内存池与安全风险。

**易错点：**

- `Buffer.allocUnsafe` 不保证内容为 0，直接返回给外部可能泄露内存旧数据。
- `buf.slice()` 已废弃，用 `buf.subarray()`；两者都共享内存，不是拷贝。
- `Buffer.from(arrayBuffer)` 共享内存，`Buffer.from(buffer)` 才是拷贝。
- 字符串的 `.length` 与字节长度不是一回事，中文、emoji 差异更大。

## 8. process 对象与 Node 的全局变量

**结论：** `process` 是 Node 的**进程级全局对象**，提供命令行参数、环境变量、标准输入输出、退出控制、信号监听、内存与运行时长等信息。Node 的全局变量比浏览器少，但多了 `Buffer`、`process`、`require`、`__dirname` 等运行时能力。

**Node 中的全局对象（部分）：**

| 名称 | 说明 | 备注 |
| --- | --- | --- |
| `global` | 全局对象本身 | `globalThis === global` |
| `process` | 当前进程信息与控制 | 见下表 |
| `Buffer` | 二进制数据构造器 | 全局可用，无需 require |
| `console` | 标准输出/错误 | 与浏览器类似，但支持 `console.table` 等 |
| `setTimeout` / `setInterval` / `setImmediate` | 定时器 | 返回 `Timeout` 对象，可 `unref` |
| `queueMicrotask` | 入队微任务 | 与 `Promise.then` 同队列 |
| `__dirname` / `__filename` | 当前模块目录/文件绝对路径 | **仅 CommonJS** |
| `require` / `module` / `exports` | 模块系统 | **仅 CommonJS** |
| `URL` / `URLSearchParams` | URL 解析 | 全局可用 |
| `TextEncoder` / `TextDecoder` | 文本编解码 | 全局可用 |
| `fetch` / `Headers` / `Request` / `Response` | HTTP 客户端 | Node 18 默认开启（实验性），21 稳定 |
| `AbortController` / `AbortSignal` | 取消异步任务 | 全局可用 |
| `structuredClone` | 深拷贝 | Node 17+ |
| `performance` | 高精度计时 | 来自 `perf_hooks`，全局暴露 |
| `atob` / `btoa` | Base64 编解码 | Node 16+ |

**`process` 常用成员：**

| 成员 | 作用 |
| --- | --- |
| `process.argv` | 命令行参数数组，`[nodePath, scriptPath, ...args]` |
| `process.env` | 环境变量对象，值都是字符串 |
| `process.cwd()` | 当前工作目录（不是脚本所在目录） |
| `process.exitCode` | 设置退出码，让进程自然退出 |
| `process.exit(code)` | 立即退出，可能丢失未完成的 I/O |
| `process.nextTick(fn)` | 当前操作结束后尽快执行 |
| `process.pid` / `process.ppid` | 当前/父进程 ID |
| `process.platform` / `process.arch` | 平台与架构 |
| `process.version` / `process.versions` | Node 与依赖库版本 |
| `process.memoryUsage()` | 堆、常驻内存等指标 |
| `process.uptime()` | 进程运行秒数 |
| `process.hrtime.bigint()` | 高精度单调时钟，适合计时 |
| `process.stdout` / `process.stderr` | 标准输出/错误流 |
| `process.on('SIGINT', fn)` | 监听中断信号，做优雅关闭 |

```js
// process-demo.js —— 运行：node process-demo.js --port 3000
console.log('参数:', process.argv.slice(2)); // [ '--port', '3000' ]
console.log('工作目录:', process.cwd());
console.log('脚本目录:', __dirname);

// 环境变量一定是字符串，需要数字要自己转换
const port = Number(process.env.PORT || 3000);
console.log('端口:', port, typeof port);

// 内存指标，单位字节
const mem = process.memoryUsage();
console.log('rss:', (mem.rss / 1024 / 1024).toFixed(1), 'MB');
console.log('heapUsed:', (mem.heapUsed / 1024 / 1024).toFixed(1), 'MB');

// 高精度计时
const start = process.hrtime.bigint();
setTimeout(() => {
  const ms = Number(process.hrtime.bigint() - start) / 1e6;
  console.log('定时器耗时:', ms.toFixed(2), 'ms');
}, 100);

// 优雅退出：先设置退出码，等事件循环自然清空
process.exitCode = 0;
```

**`process.exit()` 与 `process.exitCode` 的区别：**

- `process.exit(code)` 会**立即终止**进程，未写完的日志、未 flush 的流、未完成的数据库事务都可能丢失。
- 设置 `process.exitCode = 1` 只是告诉 Node「事件循环空了就以此码退出」，更安全。
- 需要主动退出时，先关闭服务器、等待连接排空，再调用 `process.exit()`。

**面试怎么答：** 先说明 `process` 是进程级全局对象，按「参数、环境变量、目录、退出、信号、内存、计时」分类讲常用 API，再补 `exit` 与 `exitCode` 的区别，以及 `__dirname` 在 ESM 中不存在。

**易错点：**

- `process.cwd()` 是**启动命令时的工作目录**，不是脚本文件所在目录；用 `__dirname` 或 `import.meta.url` 才可靠。
- `process.env` 的值永远是字符串，`process.env.DEBUG = false` 实际得到 `"false"`（真值）。
- `process.exit()` 不会触发 `beforeExit`，也不会等待异步清理；优雅关闭应监听信号并主动 `server.close()`。
- 不要往 `global` 上挂业务变量，模块间共享应通过显式导出。

## 9. path 与 fs 模块的常用 API

**结论：** `path` 负责**路径字符串的解析与拼接**，不访问文件系统；`fs` 负责**实际的文件读写**。服务端代码应优先使用 `fs.promises` 或流式 API，避免同步方法阻塞事件循环。

**path 常用 API：**

| API | 作用 | 示例结果 |
| --- | --- | --- |
| `path.join(...parts)` | 拼接并规范化，处理 `..` 与分隔符 | `join('a', 'b', '../c')` → `a/c` |
| `path.resolve(...parts)` | 从右往左拼接，直到得到绝对路径 | `resolve('a', 'b')` → `/当前工作目录/a/b` |
| `path.relative(from, to)` | 计算相对路径 | `relative('/a/b', '/a/c')` → `../c` |
| `path.basename(p, ext)` | 取文件名，可去扩展名 | `basename('/a/b.js', '.js')` → `b` |
| `path.dirname(p)` | 取目录名 | `dirname('/a/b.js')` → `/a` |
| `path.extname(p)` | 取扩展名 | `extname('b.tar.gz')` → `.gz` |
| `path.parse(p)` / `path.format(obj)` | 拆解/还原路径对象 | `{ root, dir, base, ext, name }` |
| `path.normalize(p)` | 规范化分隔符与 `..` | 处理多余斜杠 |
| `path.sep` / `path.delimiter` | 平台分隔符 | Windows `\` / `;`，POSIX `/` / `:` |
| `path.posix` / `path.win32` | 指定风格的实现 | 跨平台路径处理 |

**`join` 与 `resolve` 的关键区别：**

```js
const path = require('node:path');

console.log(path.join('src', '/utils', 'a.js'));    // src/utils/a.js
console.log(path.resolve('src', 'utils', 'a.js'));  // /当前工作目录/src/utils/a.js

// resolve 遇到绝对路径会丢弃前面的部分
console.log(path.resolve('/base', '/other'));        // /other

// 处理用户输入的相对路径时，先 resolve 再校验前缀，防止目录穿越
const safeJoin = (root, userPath) => {
  const target = path.resolve(root, userPath);
  if (!target.startsWith(path.resolve(root) + path.sep)) {
    throw new Error('路径越界');
  }
  return target;
};
```

**fs 的三套 API：**

| 风格 | 写法 | 适用场景 |
| --- | --- | --- |
| 同步 | `fs.readFileSync` | 启动脚本、CLI、构建工具 |
| 回调 | `fs.readFile(path, cb)` | 老代码、需要极致控制 |
| Promise | `fs.promises.readFile` / `require('node:fs/promises')` | 现代服务端代码首选 |

**常用文件操作：**

| 操作 | Promise API |
| --- | --- |
| 读整个文件 | `fs.promises.readFile(path, 'utf8')` |
| 写整个文件 | `fs.promises.writeFile(path, data)` |
| 追加 | `fs.promises.appendFile(path, data)` |
| 读目录 | `fs.promises.readdir(path, { withFileTypes: true })` |
| 创建目录 | `fs.promises.mkdir(path, { recursive: true })` |
| 删除 | `fs.promises.rm(path, { recursive: true, force: true })` |
| 重命名/移动 | `fs.promises.rename(oldPath, newPath)` |
| 复制 | `fs.promises.copyFile(src, dest)` / `fs.promises.cp(src, dest, { recursive: true })` |
| 元信息 | `fs.promises.stat(path)` / `lstat(path)` |
| 权限检查 | `fs.promises.access(path, fs.constants.R_OK)` |

```js
// fs-demo.js —— Node 18+：递归读取目录并统计文件大小
const fs = require('node:fs/promises');
const path = require('node:path');

async function walk(dir, files = []) {
  const entries = await fs.readdir(dir, { withFileTypes: true });
  for (const entry of entries) {
    const full = path.join(dir, entry.name);
    if (entry.isDirectory()) {
      await walk(full, files);       // 目录递归
    } else if (entry.isFile()) {
      const stat = await fs.stat(full);
      files.push({ path: full, size: stat.size });
    }
  }
  return files;
}

const files = await walk(process.cwd()); // ESM 顶层 await；CJS 需包在 async 函数里
console.log('文件数:', files.length);
console.log('总大小:', files.reduce((sum, f) => sum + f.size, 0), '字节');
```

> `fs.promises.readdir` 的 `recursive: true` 选项在 Node 18.17 / 20.1 起可用，可以直接递归返回路径；上面的手写递归兼容更早版本，也便于演示 `withFileTypes`。

**大文件不要用 `readFile`：**

```js
// 流式复制：内存占用与文件大小无关
const fs = require('node:fs');
const { pipeline } = require('node:stream/promises');

await pipeline(
  fs.createReadStream('big.log'),
  fs.createWriteStream('big.copy.log')
);
```

**面试怎么答：** 先区分 `path` 只处理字符串、`fs` 才碰文件；再讲 `join`/`resolve` 的差异与目录穿越校验；`fs` 按同步/回调/Promise 三套 API 分类，强调服务端用 Promise 与流，最后补 `readFile` 不适合大文件。

**易错点：**

- `path.join('/a', '/b')` 得到 `/a/b`，而 `path.resolve('/a', '/b')` 得到 `/b`，两者语义不同。
- `__dirname` 是模块所在目录，`process.cwd()` 是启动目录，拼接资源路径时不要混用。
- `fs.exists` 已废弃，用 `access` 或直接捕获 `ENOENT`。
- `fs.rmdir` 对非空目录会失败，删除目录树用 `fs.rm(..., { recursive: true })`。
- 同步 `fs` 方法在请求处理函数里会阻塞所有并发请求，只适合启动阶段。

## 10. 环境变量与多环境配置管理

**结论：** Node 通过 `process.env` 读取环境变量，值**永远是字符串**。多环境配置的核心是「**同一份代码 + 不同环境变量**」，而不是在代码里写 `if (env === 'prod')` 分散判断；敏感信息只放环境变量或密钥管理服务，不进仓库。

**常见的环境划分：**

| 环境 | `NODE_ENV` | 用途 | 典型差异 |
| --- | --- | --- | --- |
| 本地开发 | `development` | 本机调试 | 详细日志、热更新、Mock |
| 测试 | `test` | 自动化测试 | 内存数据库、固定随机种子 |
| 预发布 | `staging` | 上线前验证 | 与生产同构、独立数据 |
| 生产 | `production` | 线上 | 关闭调试、开启压缩与缓存 |

**读取与校验：**

```js
// config.js —— 集中读取、转换类型、缺失即报错
function required(name) {
  const value = process.env[name];
  if (!value) throw new Error(`缺少环境变量: ${name}`);
  return value;
}

const config = {
  env: process.env.NODE_ENV || 'development',
  port: Number(process.env.PORT || 3000),
  databaseUrl: required('DATABASE_URL'),
  redisUrl: process.env.REDIS_URL || 'redis://127.0.0.1:6379',
  logLevel: process.env.LOG_LEVEL || 'info',
  isProd: (process.env.NODE_ENV || 'development') === 'production',
};

// 启动时一次性打印（注意不要打印密钥）
console.log('配置加载完成:', {
  env: config.env,
  port: config.port,
  logLevel: config.logLevel,
});

module.exports = config;
```

**加载 `.env` 文件的三种方式：**

```bash
# 1. Node 20.6+ 内置参数，无需 dotenv
node --env-file=.env app.js

# 2. 多个文件依次加载，后者覆盖前者（Node 21.7+）
node --env-file=.env --env-file=.env.local app.js

# 3. 代码内加载（Node 20.12+）
node -e "process.loadEnvFile('.env'); console.log(process.env.PORT)"
```

```js
// 兼容旧版本的 dotenv 写法
require('dotenv').config({ path: `.env.${process.env.NODE_ENV || 'development'}` });
```

**优先级（从高到低）：**

```
命令行显式传入的环境变量
   ↓
--env-file / dotenv 加载的文件
   ↓
代码里的默认值
```

已经在 shell 中存在的变量**不会被 `.env` 覆盖**（dotenv 默认行为），这符合「外部注入优先」的原则。

**多环境文件组织：**

```
.env                 # 公共默认值，可提交
.env.development     # 本地开发，可提交
.env.local           # 个人覆盖，不提交
.env.production      # 生产模板，不提交真实密钥
```

```gitignore
.env.local
.env.*.local
.env.production
```

**为什么不在代码里区分环境：**

- 构建产物应该**一次构建、多处部署**，环境差异通过运行时变量注入。
- 配置散落在业务代码里会导致「改一个地址要重新发版」。
- 集中式 `config` 模块便于校验、打日志、做默认值。

**面试怎么答：** 先讲「代码与配置分离、环境变量注入」的原则，再给集中式 `config` 的写法与必填校验，补 `--env-file` / `dotenv` 的加载方式与优先级，最后强调密钥不入库、构建一次多环境部署。

**易错点：**

- `process.env` 只能存字符串，布尔值 `"false"` 是真值，必须显式比较。
- `NODE_ENV` 不是 Node 内置语义，只是社区约定；很多库（Express、React）会读取它来切换行为。
- `.env` 文件不要提交真实密钥；`NODE_ENV=production` 也不等于安全，仍需校验配置完整性。
- 修改环境变量后需要重启进程，运行中的 `process.env` 不会自动同步到子进程之外。

## 11. Node 的版本管理与 LTS 策略

**结论：** Node 采用「**偶数版本进 LTS、奇数版本只做短期尝鲜**」的策略。生产环境应使用 **Active LTS 或 Maintenance LTS**，并通过 `engines`、`.nvmrc`、锁文件把版本固定下来。

**发布节奏：**

| 阶段 | 时间 | 说明 |
| --- | --- | --- |
| Current | 每年 4 月/10 月发布新的大版本 | 新特性先进入 Current |
| Active LTS | 每年 10 月，偶数版本转为 LTS | 开始长期维护，推荐生产使用 |
| Maintenance LTS | LTS 约 12 个月后 | 只修 bug 与安全漏洞 |
| End-of-Life | LTS 开始约 30 个月后 | 停止维护，必须升级 |

**常见版本时间线（以官方计划为准）：**

| 版本 | 首次发布 | Active LTS | Maintenance | EOL |
| --- | --- | --- | --- | --- |
| Node 18 | 2022-04 | 2022-10 | 2023-10 | 2025-04 |
| Node 20 | 2023-04 | 2023-10 | 2024-10 | 2026-04 |
| Node 22 | 2024-04 | 2024-10 | 2025-10 | 2027-04 |
| Node 24 | 2025-04 | 2025-10 | 2026-10 | 2028-04 |

> 截至 2026 年，Node 18 已 EOL，Node 20 处于 Maintenance 阶段，Node 22/24 是生产主线。新项目优先选 Active LTS。

**版本管理工具对比：**

| 工具 | 平台 | 特点 |
| --- | --- | --- |
| `nvm` | macOS / Linux | 最常用，按 shell 切换 |
| `nvm-windows` | Windows | 独立实现，命令略有差异 |
| `fnm` | 跨平台 | Rust 编写，启动快，支持 `.node-version` |
| `volta` | 跨平台 | 按项目自动切换，锁定工具链 |
| `n` | macOS / Linux | 轻量，直接切换全局版本 |
| `asdf` | 跨平台 | 统一管理多语言运行时 |

```bash
# nvm 常用命令
nvm install 20
nvm use 20
nvm alias default 20
nvm ls

# fnm
fnm install 20
fnm use 20
```

**把版本写进项目：**

```json
{
  "engines": {
    "node": ">=20.0.0 <21",
    "npm": ">=10"
  },
  "packageManager": "pnpm@9.0.0"
}
```

```text
# .nvmrc
20
```

```ini
# .npmrc：让 npm 在版本不符时直接失败
engine-strict=true
```

**升级前的检查清单：**

1. 读官方 CHANGELOG 与 Breaking Changes。
2. 在 CI 中增加新版本矩阵，先跑测试再切生产。
3. 检查原生模块（`node-gyp`）是否有对应 ABI 的预编译包。
4. 检查依赖的 `engines` 范围，避免间接依赖不兼容。
5. 灰度发布，观察错误率与事件循环延迟。

**面试怎么答：** 先讲偶数版本 LTS、奇数版本短命的规则与四个阶段，再给版本时间线，说明生产选 Active/Maintenance LTS，最后补 `engines` + `.nvmrc` + CI 矩阵的落地方式。

**易错点：**

- LTS 不是「永不过期」，Node 18 已在 2025-04 EOL，继续使用会缺少安全补丁。
- `engines` 默认只是警告，不阻止安装；需要 `engine-strict=true` 才强制。
- 升级大版本时原生模块（`bcrypt`、`sharp` 等）需要重新编译，CI 与生产的基础镜像要同步。
- 不要把 `node` 版本与 `npm` 版本混为一谈，npm 随 Node 捆绑但可单独升级。

## 12. Node 中的错误处理（同步/异步/未捕获异常/进程退出）

**结论：** Node 的错误处理按调用方式分四类：**同步用 `try/catch`、回调用 error-first、Promise 用 `catch`/`await`、事件用 `error` 事件**。`uncaughtException` 与 `unhandledRejection` 是最后的安全网，正确做法是**记录日志、停止接收新请求、尽快退出**，而不是吞掉错误继续运行。

**错误分类：**

| 类型 | 例子 | 处理方式 |
| --- | --- | --- |
| 同步异常 | `JSON.parse` 失败、`fs.readFileSync` 找不到文件 | `try/catch` |
| 回调错误 | `fs.readFile(path, (err, data) => {})` | 判断 `err` 并 `return` |
| Promise 拒绝 | `await fetch()` 失败 | `try/catch` 或 `.catch()` |
| 事件错误 | `EventEmitter` 触发 `error` | 监听 `error`，否则进程崩溃 |
| 流错误 | `createReadStream` 的 `error` | `stream.pipeline` 统一处理 |
| 未捕获异常 | 回调里 `throw` | `process.on('uncaughtException')` |
| 未处理拒绝 | 没有 `catch` 的 Promise | `process.on('unhandledRejection')` |

**同步与回调：**

```js
const fs = require('node:fs');

// 同步：异常可以被 try/catch 捕获
try {
  const data = fs.readFileSync('not-exist.txt', 'utf8');
  console.log(data);
} catch (err) {
  if (err.code === 'ENOENT') {
    console.error('文件不存在:', err.path);
  } else {
    throw err; // 不认识的错误继续向上抛
  }
}

// 回调：错误作为第一个参数，处理完必须 return，避免继续执行
fs.readFile('not-exist.txt', 'utf8', (err, data) => {
  if (err) {
    console.error('读取失败:', err.message);
    return;
  }
  console.log(data);
});
```

**Promise 与 async/await：**

```js
// 串行：任一失败都会进入 catch
async function loadConfig() {
  try {
    const raw = await fs.promises.readFile('config.json', 'utf8');
    return JSON.parse(raw);
  } catch (err) {
    // 保留原始错误上下文
    throw new Error('配置加载失败', { cause: err });
  }
}

// 并发：Promise.all 快速失败，Promise.allSettled 收集全部结果
const results = await Promise.allSettled([
  loadConfig(),
  fs.promises.readFile('other.json', 'utf8'),
]);
for (const r of results) {
  if (r.status === 'rejected') console.error('失败:', r.reason.message);
}
```

**自定义错误与错误码：**

```js
class AppError extends Error {
  constructor(message, { code = 'APP_ERROR', status = 500, cause } = {}) {
    super(message, { cause });
    this.name = 'AppError';
    this.code = code;
    this.status = status;
  }
}

// 业务层抛错，框架层统一转成 HTTP 响应
throw new AppError('用户不存在', { code: 'USER_NOT_FOUND', status: 404 });
```

**未捕获异常与未处理拒绝：**

```js
process.on('uncaughtException', (err) => {
  // 只做同步的日志落盘，不要再执行复杂业务
  console.error('未捕获异常:', err);
  process.exitCode = 1;
  process.exit(1); // 进程状态可能已不可信，尽快退出让守护进程重启
});

process.on('unhandledRejection', (reason, promise) => {
  console.error('未处理的 Promise 拒绝:', reason);
  process.exitCode = 1;
});
```

> Node 15 起，未处理的 Promise 拒绝默认行为是抛出异常并终止进程（`--unhandled-rejections=throw`）。监听 `unhandledRejection` 只能作为兜底，不能替代在每个异步边界处理错误。

**优雅退出：**

```js
const http = require('node:http');

const server = http.createServer((req, res) => {
  res.end('ok');
});

server.listen(3000, () => console.log('启动'));

let shuttingDown = false;

async function shutdown(signal) {
  if (shuttingDown) return;
  shuttingDown = true;
  console.log('收到信号，开始关闭:', signal);

  // 1. 停止接收新连接，等待已有请求完成
  server.close(async () => {
    // 2. 关闭数据库、Redis 等资源
    // await db.end();
    console.log('资源已释放，退出');
    process.exit(0);
  });

  // 3. 超时强制退出，避免卡死
  setTimeout(() => process.exit(1), 10_000).unref();
}

process.on('SIGINT', () => shutdown('SIGINT'));
process.on('SIGTERM', () => shutdown('SIGTERM'));
```

**面试怎么答：** 先按「同步、回调、Promise、事件、未捕获」分类，给出各自的处理方式；再强调 `uncaughtException` 不是恢复手段而是退出前的最后记录；最后补 `cause`、`AggregateError`、`exitCode` 与优雅关闭的流程。

**易错点：**

- `try/catch` 捕获不到回调里的异步异常，也捕获不到没有 `await` 的 Promise。
- `EventEmitter` 触发 `error` 且没有监听器时会直接抛出，导致进程崩溃。
- 监听 `uncaughtException` 后继续提供服务是危险的，进程可能处于不一致状态。
- `process.exit()` 会跳过流 flush 与异步清理，优雅关闭应等 `server.close()` 回调。
- 只记录 `err.message` 会丢堆栈，日志里应输出完整 `err.stack` 与 `err.cause`。
