## 1. Express 与 Koa 的对比

**结论：** 两者都是「中间件 + 路由」的轻量框架，核心差异在**中间件模型与内置能力**：Express 是**回调式线性中间件**，内置路由、静态资源、`res.send` 等能力，生态最大；Koa 是**基于 async/await 的洋葱模型**，内核极薄，路由、body 解析、静态资源都要额外装包，但错误处理与异步流程更自然。新项目若没有历史包袱，Express 胜在生态与团队熟悉度，Koa 胜在中间件可控性与类型友好。

**核心对比：**

| 维度 | Express | Koa |
| --- | --- | --- |
| 中间件签名 | `(req, res, next)` | `async (ctx, next)` |
| 执行模型 | 线性，`next()` 后通常不再回到当前中间件 | 洋葱，`await next()` 后可继续执行 |
| 异步错误 | 4.x 需手动 `try/catch` 或包装；5.x 支持 Promise rejection | 原生 `try/catch`，冒泡到最外层 |
| 内置能力 | 路由、`express.static`、`res.json/send`、`express.json` | 仅核心，路由/body/static 需第三方 |
| 上下文 | `req` / `res` 两个对象 | `ctx` 聚合请求、响应、状态、throw |
| 生态 | 最大，几乎所有教程与中间件都支持 | 较小但质量高，多为 koa 官方维护 |
| 学习成本 | 低，回调模型直观 | 中，需要理解洋葱与 `ctx` 代理 |
| 适合 | 传统 REST、快速交付、团队熟悉 | 重视中间件流程、异步错误、轻量内核 |

**Express 5 的变化：** 5.x 已稳定，支持 async 中间件返回的 Promise 被 reject 时自动 `next(err)`；同时路由参数语法、`req.query` 解析、`res.status` 校验等有破坏性变更。面试时若提到 Express，最好说明版本，避免把 4.x 的行为套到 5.x。

```js
// Node 18+：Express 版本
const express = require('express'); // npm i express
const findUser = async (id) => (id === '1' ? { id: 1, name: '张三' } : null);

const app = express();
app.use(express.json({ limit: '1mb' }));

app.get('/users/:id', async (req, res, next) => {
  try {
    const user = await findUser(req.params.id);
    if (!user) return res.status(404).json({ code: 'NOT_FOUND' });
    res.json(user);
  } catch (err) {
    next(err);                       // Express 4 必须显式交给错误中间件
  }
});

app.use((err, req, res, next) => {   // 四个参数才是错误中间件
  if (res.headersSent) return next(err);
  res.status(err.status || 500).json({ code: err.code || 'INTERNAL' });
});

app.listen(3000);
```

```js
// Node 18+：Koa 版本
const Koa = require('koa'); // npm i koa
const findUser = async (id) => (id === '1' ? { id: 1, name: '张三' } : null);

const app = new Koa();

// 最外层统一捕获下游抛出的错误
app.use(async (ctx, next) => {
  try {
    await next();
  } catch (err) {
    ctx.status = err.status || 500;
    ctx.body = { code: err.code || 'INTERNAL' };
    ctx.app.emit('error', err, ctx);
  }
});

app.use(async (ctx, next) => {
  const start = Date.now();
  await next();                      // 先执行下游
  ctx.set('X-Response-Time', `${Date.now() - start}ms`); // 回到本层再执行
});

// Koa 不自带路由，这里用最简单的路径判断演示
app.use(async (ctx) => {
  const matched = /^\/users\/(\d+)$/.exec(ctx.path);
  if (ctx.method === 'GET' && matched) {
    const user = await findUser(matched[1]);
    if (!user) ctx.throw(404, '用户不存在', { code: 'NOT_FOUND' });
    ctx.body = user;
    return;
  }
  ctx.status = 404;
  ctx.body = { code: 'NOT_FOUND' };
});

app.listen(3000);
```

**选型建议：**

1. **团队与生态优先**：需要大量现成中间件、老项目迁移、招聘容易，选 Express。
2. **流程控制优先**：需要在 `next()` 之后做统计、事务提交、响应改写，Koa 的洋葱模型更自然。
3. **类型与工程化**：两者都能配 TypeScript；NestJS（默认 Express，可换 Fastify）适合大型团队，Fastify 适合极致性能与 schema 校验。
4. **不要只看 benchmark**：同量级框架的性能差异通常小于数据库与业务代码的影响，中间件模型与可维护性更重要。

**面试怎么答：** 先给一句话定位「Express 回调线性、Koa async 洋葱」，再从中间件签名、异步错误、内置能力、上下文、生态五个维度对比，最后补 Express 5 的 async 支持与选型建议。

**易错点：**

- 在 Express 4 的 async 路由里抛错却不 `next(err)`，请求悬挂直到超时。
- 认为 Koa 自带路由与 body 解析，实际都要额外安装。
- 把 Koa 的 `ctx.req` 当成 `ctx.request`：前者是原生 `IncomingMessage`，后者是 Koa 封装。

## 2. Koa 的洋葱模型与中间件原理

**结论：** Koa 用 `compose` 把中间件数组合成一个函数：每个中间件收到 `(ctx, next)`，`await next()` 会递归执行下一个中间件，**下游全部完成后，控制权沿着调用栈回到上游**，形成「先进后出」的洋葱结构。这个模型让「请求前」与「响应后」的逻辑写在同一个中间件里，天然适合耗时统计、事务、统一响应包装。

**执行顺序：**

```text
请求 →
  middleware A 前半段
    middleware B 前半段
      middleware C（业务）
    middleware B 后半段
  middleware A 后半段
→ 响应
```

**`compose` 的关键设计：**

| 设计点 | 作用 |
| --- | --- |
| `dispatch(i)` 递归 | 用下标控制当前执行到第几个中间件 |
| `index` 记录已执行位置 | 防止同一个中间件里 `next()` 被调用多次 |
| `Promise.resolve(fn(...))` | 统一把同步返回值包装成 Promise |
| `try/catch` 包住调用 | 同步抛错也能转成 rejected Promise |
| 末尾 `next` 参数 | 支持把 Koa 应用挂载为其它框架的中间件 |

```js
// Node 18+：手写 koa-compose，理解洋葱模型
function compose(middleware) {
  if (!Array.isArray(middleware)) throw new TypeError('中间件必须是数组');
  for (const fn of middleware) {
    if (typeof fn !== 'function') throw new TypeError('中间件必须是函数');
  }

  return function (context, next) {
    let index = -1;

    function dispatch(i) {
      if (i <= index) return Promise.reject(new Error('next() 被重复调用'));
      index = i;

      let fn = middleware[i];
      if (i === middleware.length) fn = next;   // 允许外部再串一个函数
      if (!fn) return Promise.resolve();

      try {
        return Promise.resolve(fn(context, dispatch.bind(null, i + 1)));
      } catch (err) {
        return Promise.reject(err);             // 同步异常也走 Promise 链
      }
    }

    return dispatch(0);
  };
}

// 验证洋葱顺序
const stack = [];
const mw = [
  async (ctx, next) => {
    stack.push('A-before');
    await next();
    stack.push('A-after');
  },
  async (ctx, next) => {
    stack.push('B-before');
    await next();
    stack.push('B-after');
  },
  async () => {
    stack.push('C');
  },
];

const run = compose(mw);
run({}).then(() => console.log(stack));
// [ 'A-before', 'B-before', 'C', 'B-after', 'A-after' ]
```

**`ctx` 是怎么来的：** 每个请求都会创建一个新对象，原型链指向应用级 `context`，并挂上 `request` 与 `response` 两个封装对象：

```js
// Koa 源码简化示意
const ctx = Object.create(this.context);
ctx.request = Object.create(this.request);
ctx.response = Object.create(this.response);
ctx.app = this;          // 指回应用实例
ctx.req = ctx.request.req = req;   // 原生 IncomingMessage
ctx.res = ctx.response.res = res;  // 原生 ServerResponse
```

Koa 通过 `delegate` 把 `ctx.request` / `ctx.response` 的属性和方法代理到 `ctx` 上，所以可以直接写 `ctx.path`、`ctx.body`、`ctx.status`，而不必写 `ctx.request.path`。

**常用上下文 API：** `ctx.body`（响应体，自动推断类型与状态码）、`ctx.status`、`ctx.set()`、`ctx.throw()`、`ctx.assert()`、`ctx.state`（请求级共享数据）、`ctx.cookies`。

```js
// Node 18+：一个最小 Koa 应用，观察洋葱与错误冒泡
const Koa = require('koa');
const findUser = async (id) => (id === '1' ? { id: 1, name: '张三' } : null);

const app = new Koa();

app.use(async (ctx, next) => {
  const start = process.hrtime.bigint();
  try {
    await next();
  } finally {
    const ms = Number(process.hrtime.bigint() - start) / 1e6;
    ctx.set('X-Response-Time', `${ms.toFixed(1)}ms`);
    console.log(`${ctx.method} ${ctx.url} ${ctx.status} ${ms.toFixed(1)}ms`);
  }
});

app.use(async (ctx, next) => {
  if (ctx.path === '/boom') ctx.throw(400, '演示错误', { code: 'DEMO_ERROR' });
  await next();
});

app.use(async (ctx) => {
  ctx.body = { ok: true, path: ctx.path };
});

app.on('error', (err) => {
  console.error('应用级错误', err.status, err.code, err.message); // ctx.throw 会触发
});

app.listen(3000);
```

**为什么 `next()` 不能调用两次：** `dispatch` 用闭包里的 `index` 记录已执行位置，第二次调用时 `i <= index` 直接 reject。否则同一个下游会被执行两次，可能造成重复写响应、重复扣款等严重后果。

**与 Express 的模型差异：** Express 的 `next()` 是「交棒」，调用后当前中间件通常不再持有控制权；Koa 的 `await next()` 是「调用」，下游返回后当前中间件继续执行。这决定了 Koa 可以在响应返回前统一改写 `ctx.body`、统一加头、统一提交事务。

**面试怎么答：** 先画洋葱顺序图，再手写 `compose` 的 `dispatch` 递归与 `index` 防重复，接着讲 `ctx` 的原型链与 delegate 代理，最后说明洋葱模型在耗时统计、统一响应、错误冒泡上的价值。

**易错点：**

- 忘记 `await next()`，下游中间件根本不执行。
- 在 `next()` 之后修改 `ctx.body` 却覆盖了业务结果。
- 认为 `ctx.body` 赋值后立刻发送，实际是在响应阶段统一处理。
- 调用两次 `next()`，被 compose 的 `index` 拦截并抛错。
- 把错误处理中间件放在最后，无法捕获上游抛出的异常。

## 3. 中间件的编写与错误处理

**结论：** 中间件要遵守三条规则：**只做一件事、必须调用或等待 `next()`、错误统一交给错误中间件**。Express 的错误中间件是**四个参数**的函数，必须注册在所有路由之后；Koa 则在最外层用 `try/catch` 包住 `await next()`。生产环境对外只返回**错误码与安全文案**，堆栈与内部细节只写日志。

**两类中间件：** 普通中间件注册在路由之前，负责解析、鉴权、日志、限流；错误中间件在 Express 中必须四个参数，注册在所有路由之后，负责统一响应与告警。

**错误分类：** 业务错误（参数不合法、余额不足、无权限）映射 4xx 并返回业务码；系统错误（数据库断开、第三方异常）映射 5xx，记录完整堆栈并对外隐藏细节；编程错误在进程级兜底，记录后退出并由外部拉起。

```js
// Node 18+：Express 的错误体系
const express = require('express');
const orderService = { find: async () => ({ id: '1', status: 'paid' }) };

class AppError extends Error {
  constructor(message, status = 500, code = 'INTERNAL', expose = status < 500) {
    super(message);
    this.name = 'AppError';
    this.status = status;
    this.code = code;
    this.expose = expose;
    Error.captureStackTrace?.(this, AppError);
  }
}

// 包装 async 路由，保证 rejection 一定进入错误中间件
const asyncHandler = (fn) => (req, res, next) => {
  Promise.resolve(fn(req, res, next)).catch(next);
};

const app = express();
app.use(express.json({ limit: '1mb' }));

app.get('/orders/:id', asyncHandler(async (req, res) => {
  const order = await orderService.find(req.params.id);
  if (!order) throw new AppError('订单不存在', 404, 'ORDER_NOT_FOUND');
  res.json(order);
}));

// 404 兜底：放在所有路由之后、错误中间件之前
app.use((req, res) => {
  res.status(404).json({ code: 'ROUTE_NOT_FOUND', message: '接口不存在' });
});

// 错误中间件：必须四个参数，且放在最后
app.use((err, req, res, next) => {
  if (res.headersSent) return next(err);       // 响应已开始，交给 Express 默认处理

  const status = err.status || 500;
  const code = err.code || 'INTERNAL';
  const log = status >= 500 ? console.error : console.warn;
  log('请求失败', { code, message: err.message, stack: err.stack, path: req.path });

  res.status(status).json({
    code,
    message: err.expose ? err.message : '服务器内部错误', // 不泄漏内部信息
    requestId: req.id || req.headers['x-request-id'],
  });
});
```

```js
// Node 18+：Koa 的等价写法
const Koa = require('koa');
const app = new Koa();

app.use(async (ctx, next) => {
  try {
    await next();
    if (ctx.status === 404 && !ctx.body) {
      ctx.status = 404;
      ctx.body = { code: 'ROUTE_NOT_FOUND', message: '接口不存在' };
    }
  } catch (err) {
    const status = err.status || 500;
    ctx.status = status;
    ctx.body = {
      code: err.code || 'INTERNAL',
      message: status < 500 ? err.message : '服务器内部错误',
    };
    if (status >= 500) ctx.app.emit('error', err, ctx); // 交给应用级日志
  }
});

app.use(async (ctx) => {
  if (ctx.path === '/orders/404') ctx.throw(404, '订单不存在', { code: 'ORDER_NOT_FOUND' });
  ctx.body = { ok: true };
});

app.on('error', (err, ctx) => {
  console.error('未处理错误', { path: ctx?.path, message: err.message, stack: err.stack });
});
```

**中间件编写规范：**

1. **单一职责**：鉴权、日志、限流、校验各自独立，便于复用与测试。
2. **总是结束响应或调用 `next()`**：既不 `next()` 也不返回响应，请求会挂起。
3. **异步必须 `await`**：`await next()` 才能保证洋葱顺序与错误冒泡。
4. **不要吞错**：`catch` 后要么处理并返回，要么 `throw` / `next(err)`，不能静默。
5. **不要重复发送响应**：`res.headersSent` 之后只能 `next(err)`。
6. **错误中间件放最后**，且 Express 必须保留四个参数，否则会被当成普通中间件。
7. **区分环境**：生产隐藏堆栈，开发可以返回 `stack` 方便调试。

**面试怎么答：** 先讲普通中间件与错误中间件的签名和注册顺序，再给「业务错误映射 4xx、系统错误 5xx、对外只暴露错误码」的分层策略，接着说明 Express 4 的 async 需要包装、Express 5 与 Koa 原生支持，最后补 `headersSent`、404 兜底与日志脱敏。

**易错点：**

- 错误中间件写成三个参数，Express 根本不会识别。
- 把错误中间件注册在路由之前，捕获不到后面的异常。
- `catch` 里只 `console.log` 不返回也不 `next`，请求一直挂起。
- 出错后已经 `res.json`，又调用 `next(err)` 造成 `ERR_HTTP_HEADERS_SENT`。
- 生产环境把 `err.stack` 返回给前端，泄漏文件路径与依赖版本。

## 4. 路由设计与版本管理

**结论：** 路由是 API 的契约。设计上遵循 **REST 资源化 + 正确的 HTTP 方法/状态码 + 稳定的错误结构**；版本管理优先选择 **URI 主版本（`/api/v1`）** 用于公开 API，内部服务可用 **Header 版本**避免 URL 膨胀。破坏性变更必须升版本，新增字段属于兼容变更，不应升版本。

**REST 设计要点：**

| 项 | 推荐 | 避免 |
| --- | --- | --- |
| 资源命名 | 复数名词 `/users`、`/orders` | 动词 `/getUser`、`/createOrder` |
| 层级 | 最多两层 `/users/:id/orders` | 过深嵌套 |
| 方法 | GET 查询、POST 创建、PUT 全量更新、PATCH 局部、DELETE 删除 | 全用 POST |
| 状态码 | 200/201/204/400/401/403/404/409/422/429/500 | 一律 200 + 业务码 |
| 幂等 | GET/PUT/DELETE 幂等，POST 用幂等键 | 重试导致重复创建 |
| 分页 | `?page=1&pageSize=20` 或游标 `?cursor=` | 一次返回全量 |
| 过滤排序 | `?status=paid&sort=-createdAt` | 把查询塞进 path |
| 错误体 | `{ code, message, requestId, details? }` | 纯文本或 HTML |

**版本策略对比：**

| 方式 | 示例 | 优点 | 缺点 |
| --- | --- | --- | --- |
| URI 版本 | `/api/v1/users` | 直观、易缓存、易网关路由 | URL 变化，HATEOAS 链接需改 |
| Header 版本 | `Accept: application/vnd.api.v2+json` | URL 稳定、语义清晰 | 调试不便，缓存需 Vary |
| Query 版本 | `?version=2` | 改动最小 | 污染查询参数，易漏 |
| 域名版本 | `v2.api.example.com` | 隔离彻底 | 证书与运维成本 |

**兼容与弃用：** 新增可选字段、新增枚举值通常兼容；删除字段、改类型、改语义、收紧校验属于破坏性变更。弃用接口时返回 `Deprecation`、`Sunset`、`Link` 响应头，并在文档与日志中标记调用方，给足迁移窗口。

```js
// Node 18+：Express Router + 版本隔离
const express = require('express');
const app = express();

// v1 与 v2 共享同一个 service，只在出参结构上不同
const userService = {
  async find(id) {
    if (!/^\d+$/.test(id)) return null;      // 先做参数格式校验
    return { id: Number(id), name: '张三', phone: '13800000000' };
  },
};

const v1 = express.Router();
v1.get('/users/:id', async (req, res, next) => {
  try {

    if (!user) return res.status(404).json({ code: 'USER_NOT_FOUND' });

  res.set('Deprecation', 'true');
  res.set('Sunset', 'Wed, 31 Dec 2026 23:59:59 GMT');
  res.set('Link', '</api/v2>; rel="successor-version"');
```

**路由注册顺序：** Express 按注册顺序匹配，具体路径要放在参数路径之前（如 `/users/me` 在 `/users/:id` 之前），否则 `/users/me` 会被 `:id` 捕获。`router.param()` 适合统一处理 `:id` 的校验与加载。

**版本管理的工程做法：**

1. 路由文件按版本分目录：`routes/v1/users.js`、`routes/v2/users.js`，共享 `services/`。
2. 网关按前缀转发到不同服务，避免应用内堆积多版本逻辑。
3. OpenAPI 文档分版本维护，CI 中做 schema diff 检测破坏性变更。
4. 用访问日志按 `apiVersion` 维度统计调用量，确认旧版本可以下线。
5. **不要在同一版本里悄悄改行为**，语义变更比字段变更更隐蔽。

**面试怎么答：** 先讲 REST 的资源命名、方法语义、状态码与幂等，再对比四种版本策略并给出「公开 API 用 URI、内部用 Header」的结论，接着说明破坏性变更的判定与弃用响应头，最后补路由顺序与 `router.param`。

**易错点：**

- 用动词命名接口，方法语义混乱，缓存与网关无法按语义处理。
- 所有响应都返回 200，错误靠业务码区分，监控无法按状态码告警。
- 删除字段不升版本，老客户端直接崩溃。
- 只新增一个可选字段就升大版本，版本数量失控。
- `/users/:id` 放在 `/users/me` 之前，`me` 被当成 id。

## 5. 参数校验与分层架构

**结论：** 校验必须发生在**系统边界**：HTTP 入参、消息队列消息、第三方回调都要校验，且校验后要**转换成内部 DTO**，不要把 `req` 透传到 service。分层上采用 **Router → Controller → Service → Repository**：Controller 只负责协议转换，Service 承载业务与事务，Repository 只做数据访问。这样业务逻辑可测试、可复用，不依赖框架。

**分层职责：**

| 层 | 职责 | 不该做的事 |
| --- | --- | --- |
| Router | 路径与方法映射、中间件编排 | 写业务逻辑 |
| Controller | 解析入参、调用 Service、组装响应 | 直接访问数据库 |
| Service | 业务规则、事务边界、领域错误 | 依赖 `req` / `res` |
| Repository | SQL/ORM、缓存、外部存储适配 | 决定业务流程 |
| Model/DTO | 数据结构与校验 | 承载流程控制 |

**校验方案对比：**

| 方案 | 特点 | 适用 |
| --- | --- | --- |
| `zod` | TypeScript 友好，schema 即类型 | 新项目首选 |
| `joi` | 功能全，生态成熟 | 传统 JS 项目 |
| `express-validator` | 与 Express 集成紧密 | Express 项目 |
| `class-validator` | 装饰器风格 | NestJS / TS |
| JSON Schema | 语言无关，可生成文档 | 开放 API、网关 |

```js
// Node 18+：zod 校验 + 分层（npm i express zod）
const express = require('express');
const { z } = require('zod');

const createUserSchema = z.object({
  email: z.string().email(),
  name: z.string().min(1).max(50),
  age: z.number().int().min(0).max(150).optional(),
}).strict();                       // 拒绝未定义字段，防参数污染

function validateBody(schema) {
  return (req, res, next) => {
    const result = schema.safeParse(req.body);
    if (!result.success) {
      return res.status(422).json({
        code: 'VALIDATION_FAILED',
        details: result.error.issues.map((i) => ({
          path: i.path.join('.'),
          message: i.message,
        })),
      });
    }
    req.validatedBody = result.data;   // 只传净化后的数据，不直接改 req.body
    next();
  };
}

// Repository：只关心数据
class UserRepository {
  constructor(db) { this.db = db; }
  findByEmail(email) { return this.db.user.findUnique({ where: { email } }); }
  create(data) { return this.db.user.create({ data }); }
}

// Service：业务规则与错误语义
class UserService {
  constructor(repo) { this.repo = repo; }

  async create(input) {
    const exists = await this.repo.findByEmail(input.email);
    if (exists) {
      const err = new Error('邮箱已被注册');
      err.status = 409;
      err.code = 'EMAIL_EXISTS';
      throw err;
    }
    return this.repo.create(input);
  }
}

// Controller：只做协议转换
function buildUserController(service) {
  return {
    create: async (req, res, next) => {
      try {
        const user = await service.create(req.validatedBody);
        res.status(201).json({ id: user.id, email: user.email, name: user.name });
      } catch (err) {
        next(err);
      }
    },
  };
}

const db = {
  user: { findUnique: async () => null, create: async (data) => ({ id: '1', ...data }) },
};

const app = express();
app.use(express.json({ limit: '1mb' }));
const controller = buildUserController(new UserService(new UserRepository(db)));
app.post('/api/v1/users', validateBody(createUserSchema), controller.create);
```

**校验的三个层次：**

1. **格式校验**：类型、长度、正则、枚举，放在边界。
2. **语义校验**：邮箱是否已注册、余额是否足够，放在 Service。
3. **数据库约束**：唯一索引、外键、非空，作为最后防线，不能省。

只做前两层而不建唯一索引，并发下仍会写入重复数据；只靠数据库约束而不做前置校验，错误信息不友好且浪费连接。

**DTO 的意义：** 入参 DTO 与实体分离，可以避免「前端多传一个 `role: admin` 就被写进数据库」的越权赋值。返回 DTO 同样重要，避免把 `passwordHash`、`internalStatus` 直接序列化给前端。

**面试怎么答：** 先讲「边界校验 + 净化后 DTO」的原则，再给 Router/Controller/Service/Repository 的职责表，接着说明格式校验、语义校验、数据库约束三层防线，最后补 DTO 防越权赋值与 Service 可测试性。

**易错点：**

- 把 `req` 传进 Service，业务逻辑与框架耦合，单测必须造 HTTP 对象。
- 校验失败返回 500 而不是 422/400。
- 用 `Object.assign(entity, req.body)`，攻击者可以覆盖 `role`、`balance`。
- 只做应用层校验不建唯一索引，并发下写入重复邮箱。
- 返回实体全字段，泄漏密码哈希与内部字段。
- 在 Controller 里直接开事务、写 SQL，分层形同虚设。

## 6. 鉴权方案（Session、JWT、OAuth2）

**结论：** 三者解决的问题不同：**Session 是「服务端保存会话状态」**，易撤销但需共享存储；**JWT 是「签名令牌」**，无状态易扩展但难撤销，适合短时效的访问令牌；**OAuth2 是「授权框架」**，解决第三方应用如何在不拿密码的前提下获得有限权限，常与 OIDC 一起做单点登录。工程上常见组合是「**OAuth2/OIDC 登录 → 颁发短效 JWT + 可撤销 Refresh Token**」。

**三种方案对比：**

| 维度 | Session | JWT | OAuth2 / OIDC |
| --- | --- | --- | --- |
| 状态存放 | 服务端（内存/Redis） | 客户端（令牌自包含） | 授权服务器 |
| 撤销 | 立即（删 session） | 困难（黑名单/短 TTL） | 撤销 refresh token |
| 横向扩展 | 需共享存储 | 天然支持 | 授权服务器集中 |
| 适用 | 同域 Web、管理后台 | API、移动端、服务间 | 第三方登录、SSO |
| 主要风险 | CSRF、会话固定 | XSS 窃取、算法混淆 | 回调劫持、PKCE 缺失 |

**Session 的关键点：**

1. Cookie 必须 `HttpOnly`（防 XSS 读取）、`Secure`（仅 HTTPS）、`SameSite=Lax/Strict`（防 CSRF）。
2. 登录成功后**重新生成 sessionId**，防会话固定攻击。
3. 服务端存 Redis，设置空闲超时与绝对超时；登出时删除。

```js
// Node 18+：最小 Session 实现（生产用 Redis 存储）
const crypto = require('node:crypto');

const sessions = new Map();          // 生产替换为 Redis：key=sessionId, value=JSON

function parseCookies(header = '') {
  return Object.fromEntries(
    header.split(';').filter(Boolean).map((pair) => {
      const i = pair.indexOf('=');
      return [pair.slice(0, i).trim(), decodeURIComponent(pair.slice(i + 1))];
    }),
  );
}

function sessionMiddleware(req, res, next) {
  const sid = parseCookies(req.headers.cookie).sid;
  if (sid && sessions.has(sid)) req.session = sessions.get(sid);

  req.login = (userId) => {
    const newSid = crypto.randomBytes(32).toString('base64url'); // 登录即换 ID
    sessions.set(newSid, { userId, createdAt: Date.now() });
    res.setHeader('Set-Cookie',
      `sid=${newSid}; HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=86400`);
  };

  req.logout = () => {
    const current = parseCookies(req.headers.cookie).sid;
    if (current) sessions.delete(current);
    res.setHeader('Set-Cookie', 'sid=; HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=0');
  };

  next();
}
```

**JWT 的关键点：**

1. Header、Payload 只是 **base64url 编码，不是加密**，不能放密码、身份证等敏感信息。
2. 必须校验**算法白名单**，防 `alg: none` 与 HS/RS 混淆攻击。
3. `exp` 要短（访问令牌 5～15 分钟），并校验 `iss`、`aud`、`nbf`；撤销靠短 TTL + Refresh Token 名单，不要指望删除已签发的 JWT。
4. 存储位置：`HttpOnly` Cookie 可防 XSS 读取但要防 CSRF；`localStorage` 易被 XSS 窃取。没有绝对安全，只有权衡。

```js
// Node 18+：HS256 JWT 签发与校验（依赖 node:crypto）
const crypto = require('node:crypto');

const SECRET = process.env.JWT_SECRET || 'dev-secret';
const b64 = (obj) => Buffer.from(JSON.stringify(obj)).toString('base64url');

function signJwt(payload, secret, ttlSeconds = 900) {
  const now = Math.floor(Date.now() / 1000);
  const header = b64({ alg: 'HS256', typ: 'JWT' });
  const body = b64({ ...payload, iat: now, exp: now + ttlSeconds });
  const data = `${header}.${body}`;
  const sig = crypto.createHmac('sha256', secret).update(data).digest('base64url');
  return `${data}.${sig}`;
}

function verifyJwt(token, secret, { issuer, audience } = {}) {
  const parts = token.split('.');
  if (parts.length !== 3) throw new Error('JWT 格式非法');
  const [h, p, s] = parts;

  const header = JSON.parse(Buffer.from(h, 'base64url').toString('utf8'));
  if (header.alg !== 'HS256') throw new Error('不支持的算法');   // 白名单

  const expected = crypto.createHmac('sha256', secret).update(`${h}.${p}`).digest('base64url');
  const a = Buffer.from(s);
  const b = Buffer.from(expected);
  if (a.length !== b.length || !crypto.timingSafeEqual(a, b)) throw new Error('签名无效');

  const payload = JSON.parse(Buffer.from(p, 'base64url').toString('utf8'));
  const now = Math.floor(Date.now() / 1000);
  if (payload.exp && now >= payload.exp) throw new Error('令牌已过期');
  if (payload.nbf && now < payload.nbf) throw new Error('令牌尚未生效');
  if ((issuer && payload.iss !== issuer) || (audience && payload.aud !== audience)) {
    throw new Error('签发方或受众不匹配');
  }
  return payload;
}

// Refresh Token 轮换：一次性使用，检测重放后吊销整个令牌族
const refreshStore = new Map(); // 生产用 Redis + 哈希存储

function revokeFamily(family) {
  for (const [id, record] of refreshStore) if (record.family === family) refreshStore.delete(id);
}

function issueRefresh(userId) {
  const jti = crypto.randomBytes(16).toString('hex');
  refreshStore.set(jti, { userId, used: false, family: jti });
  return { jti, token: signJwt({ sub: userId, jti, typ: 'refresh' }, SECRET, 7 * 86400) };
}

function rotateRefresh(token) {
  const payload = verifyJwt(token, SECRET);
  const record = refreshStore.get(payload.jti);
  if (!record || record.used) {
    if (record) revokeFamily(record.family);   // 检测到重放，整族吊销
    throw new Error('Refresh Token 已失效');
  }
  record.used = true;
  return issueRefresh(payload.sub);
}
```

**OAuth2 授权码 + PKCE 的流程：**

1. 客户端生成 `code_verifier`，计算 `code_challenge = base64url(sha256(verifier))`。
2. 跳转授权服务器，带 `client_id`、`redirect_uri`、`scope`、`state`、`code_challenge`。
3. 用户登录并同意后，回调地址收到 `code`；先校验 `state` 防 CSRF。
4. 客户端用 `code` + `code_verifier` 换 `access_token` 与 `refresh_token`。
5. 用 `access_token` 调资源服务器；`id_token`（OIDC）用于获取用户身份。

**必须校验：** `redirect_uri` 白名单精确匹配、`state`、PKCE、`scope` 最小化、令牌签名与 `iss/aud/exp`。公共客户端（SPA、移动端）**不能保存 client_secret**，必须用 PKCE。

**面试怎么答：** 先分别给三者定位（服务端状态、签名令牌、授权框架），再对比撤销能力与扩展性，接着讲 Session 的 Cookie 属性与 JWT 的算法白名单/短时效/刷新轮换，最后补 OAuth2 授权码 + PKCE 的步骤与 `state` 校验。

**易错点：**

- 把 JWT 当加密，往 payload 里塞手机号、身份证。
- 不校验 `alg`，接受 `none` 或把 RS256 当 HS256 验证。
- Access Token 设 7 天且无法撤销，泄露后长期可用。
- Session Cookie 缺 `HttpOnly` / `SameSite`，被 XSS 或 CSRF 利用。
- 登录后不换 sessionId，存在会话固定漏洞。
- OAuth2 不校验 `state` 与 `redirect_uri`，授权码被劫持。

## 7. 配置、日志、异常处理中间件

**结论：** 配置要**外置、分层、启动即校验**：环境变量优先，代码内只保留默认值与非敏感常量，缺少关键配置时**启动失败**而不是运行到一半才报错。日志与异常处理应做成**全局中间件**：请求进来分配 `requestId`，通过 `AsyncLocalStorage` 贯穿异步调用，错误统一在一个地方映射为响应并记录上下文。

**配置来源的优先级：** 环境变量 > 按环境拆分的配置文件 > 代码默认值；动态开关与灰度参数可放配置中心，敏感值一律走 Secret Manager。

```js
// Node 18+：启动即校验的配置模块（config.js）
function required(name) {
  const value = process.env[name];
  if (!value) throw new Error(`缺少必需的环境变量: ${name}`); // 快速失败
  return value;
}

function toInt(name, fallback, { min = 0, max = Number.MAX_SAFE_INTEGER } = {}) {
  const raw = process.env[name];
  const value = raw === undefined ? fallback : Number(raw);
  if (!Number.isInteger(value) || value < min || value > max) {
    throw new Error(`环境变量 ${name} 非法: ${raw}`);
  }
  return value;
}

const config = Object.freeze({
  env: process.env.NODE_ENV || 'development',
  port: toInt('PORT', 3000, { min: 1, max: 65535 }),
  db: Object.freeze({
    host: required('DB_HOST'),
    port: toInt('DB_PORT', 3306),
    user: required('DB_USER'),
    password: required('DB_PASSWORD'),
    database: required('DB_NAME'),
    poolSize: toInt('DB_POOL_SIZE', 10, { min: 1, max: 100 }),
  }),
  redisUrl: required('REDIS_URL'),
  logLevel: process.env.LOG_LEVEL || 'info',
});

module.exports = config;
```

```js
// Node 18+：请求上下文 + 结构化访问日志中间件
const { AsyncLocalStorage } = require('node:async_hooks');
const { randomUUID } = require('node:crypto');

const als = new AsyncLocalStorage();

function requestContext(req, res, next) {
  const requestId = req.headers['x-request-id'] || randomUUID();
  const traceId = req.headers['x-trace-id'] || requestId;

  res.setHeader('x-request-id', requestId);

  // 在 ALS 上下文中执行后续中间件与业务逻辑
  als.run({ requestId, traceId, userId: null }, () => {
    const start = process.hrtime.bigint();
    res.on('finish', () => {
      const latencyMs = Number(process.hrtime.bigint() - start) / 1e6;
      console.log(JSON.stringify({
        level: res.statusCode >= 500 ? 'error' : 'info',
        msg: 'http_request',
        requestId,
        traceId,
        userId: als.getStore()?.userId,
        method: req.method,
        path: req.originalUrl,
        status: res.statusCode,
        latencyMs: Math.round(latencyMs),
      }));
    });
    next();
  });
}

function currentContext() {
  return als.getStore() || {};
}
```

**异常处理中间件的职责：**

| 职责 | 做法 |
| --- | --- |
| 统一响应结构 | `{ code, message, requestId }` |
| 错误映射 | `AppError` / 校验错误 / 数据库唯一键 → 对应状态码 |
| 日志 | 5xx 记 `error` 并带堆栈，4xx 记 `warn` 不带堆栈 |
| 脱敏 | 不返回 SQL、堆栈、内部地址 |
| 兜底 | `headersSent` 时交给默认处理；未捕获异常记录后退出 |

```js
// Node 18+：统一的异常映射
function errorHandler(err, req, res, next) {
  if (res.headersSent) return next(err);

  let status = err.status || 500;
  let code = err.code || 'INTERNAL';

  if (err.name === 'ZodError') {                    // 校验错误
    status = 422;
    code = 'VALIDATION_FAILED';
  } else if (err.code === 'ER_DUP_ENTRY') {         // 数据库唯一键冲突
    status = 409;
    code = 'DUPLICATE_ENTRY';
  }

  const ctx = currentContext();
  const payload = {
    level: status >= 500 ? 'error' : 'warn',
    msg: 'request_error',
    requestId: ctx.requestId,
    traceId: ctx.traceId,
    code,
    err: err.message,
    stack: status >= 500 ? err.stack : undefined,
    path: req.originalUrl,
    method: req.method,
  };
  console.log(JSON.stringify(payload));

  res.status(status).json({
    code,
    message: status >= 500 ? '服务器内部错误' : err.message,
    requestId: ctx.requestId,
  });
}
```

**配置与密钥的工程规范：**

1. `.env` 只用于本地，必须进 `.gitignore`；仓库提供 `.env.example`。
2. 密钥放 Secret Manager / KMS，不写进镜像，不通过命令行参数传递（会出现在 `ps`）。
3. 配置变更要能触发滚动重启，避免半新半旧实例读到不同配置。
4. 打印配置时必须脱敏（`password: '***'`），不要整体 `console.log(config)`。
5. 特性开关（feature flag）与配置分离，支持按用户/百分比灰度。

**面试怎么答：** 先讲配置的四层来源与「启动即校验、缺失即失败」，再讲请求上下文用 ALS 透传 requestId/traceId，接着列出异常中间件的五件事（统一结构、映射、日志、脱敏、兜底），最后补密钥管理与脱敏。

**易错点：**

- 配置缺失时给一个「看起来能用」的默认值，上线后连错数据库。
- 把 `config` 整体打进日志，密码与密钥泄漏。
- 异常中间件把 `err.stack` 返回给前端。
- 只记录错误消息不记录 requestId，线上无法关联日志。
- `headersSent` 后仍尝试 `res.json`，抛 `ERR_HTTP_HEADERS_SENT`。

## 8. Web 安全实践（helmet、CORS、限流、注入防护）

**结论：** Web 安全的核心是「**不信任任何外部输入**」：所有入参校验与参数化、所有输出编码、所有跨域请求显式白名单、所有敏感操作限流与鉴权。Node 层能做的事情主要是**安全响应头、CORS 白名单、body 大小限制、限流、注入防护、依赖与密钥管理**；TLS、WAF、DDoS 防护通常交给网关与云厂商。

**常见威胁与防护：**

| 威胁 | 攻击方式 | 防护 |
| --- | --- | --- |
| XSS | 注入脚本到页面 | 输出编码、CSP、`HttpOnly` Cookie |
| CSRF | 借用已登录 Cookie 发请求 | `SameSite`、CSRF Token、校验 Origin |
| SQL 注入 | 拼接 SQL | 参数化查询、ORM 绑定、最小权限账号 |
| NoSQL 注入 | 传 `{ "$ne": null }` 绕过 | 强制类型校验、拒绝操作符对象 |
| 命令注入 | 拼接 shell 命令 | `execFile`/`spawn` 传数组，禁用 `shell: true` |
| 路径穿越 | `../../etc/passwd` | `path.resolve` 后校验前缀 |
| SSRF | 让服务端请求内网地址 | 白名单域名、禁内网 IP、限制协议 |
| 原型污染 | `__proto__` 合并 | 拒绝危险键、`Object.create(null)`、禁用深合并 |
| 暴力破解 | 撞库、验证码轰炸 | 限流、账号锁定、验证码、风控 |
| 依赖漏洞 | 老版本组件 | `npm audit`、锁文件、SCA 扫描 |

```js
// Node 18+：安全中间件组合（npm i express helmet cors express-rate-limit）
const express = require('express');
const helmet = require('helmet');
const cors = require('cors');

const app = express();

// 1) 安全响应头：CSP、HSTS、X-Content-Type-Options、Referrer-Policy、frame 防护
app.use(helmet({
  contentSecurityPolicy: {
    directives: {
      defaultSrc: ["'self'"],
      scriptSrc: ["'self'"],              // 避免 unsafe-inline，降低 XSS 影响
      objectSrc: ["'none'"],
      baseUri: ["'self'"],
      frameAncestors: ["'none'"],
    },
  },
  hsts: { maxAge: 31_536_000, includeSubDomains: true, preload: true },
}));

// 2) CORS 白名单：credentials 为 true 时绝不能配 '*'
const allowList = new Set(['https://app.example.com', 'https://admin.example.com']);
app.use(cors({
  origin(origin, callback) {
    if (!origin || allowList.has(origin)) return callback(null, true);
    callback(new Error('CORS 不允许的 Origin'));
  },
  credentials: true,
  methods: ['GET', 'POST', 'PUT', 'PATCH', 'DELETE'],
  allowedHeaders: ['Content-Type', 'Authorization', 'X-Request-Id'],
  maxAge: 600,
}));

// 3) body 大小限制，防止超大 JSON 拖垮内存与 CPU
app.use(express.json({ limit: '1mb' }));
app.use(express.urlencoded({ extended: false, limit: '1mb' }));

  max: 300,
  standardHeaders: true,
  legacyHeaders: false,

app.use('/auth/login', rateLimit({

  max: 10,
```

```js
// Node 18+：几类注入的防护写法
const path = require('node:path');
const { execFile } = require('node:child_process');

// 1) SQL：永远参数化，不拼接
async function findUser(db, email) {
  return db.query('SELECT id, email FROM users WHERE email = ?', [email]); // 绑定参数
}

// 2) NoSQL：拒绝对象/数组，只接受标量
function requireScalar(value, name) {
  if (typeof value !== 'string' && typeof value !== 'number') {
    const err = new Error(`${name} 类型非法`);
    err.status = 400;
    throw err;
  }
  return value;
}
// 攻击载荷 { "token": { "$ne": null } } 会被类型校验拦下

// 3) 命令：用 execFile 传数组，避免 shell 解析
function convertImage(input, output) {
  return new Promise((resolve, reject) => {
    execFile('convert', [input, output], { timeout: 10_000 }, (err, stdout) => {
      if (err) return reject(err);
      resolve(stdout);
    });
  });
}

// 4) 路径穿越：解析后必须仍在基目录内
const UPLOAD_DIR = path.resolve('/var/app/uploads');
function safeJoin(name) {
  const target = path.resolve(UPLOAD_DIR, name);
  if (!target.startsWith(UPLOAD_DIR + path.sep)) {
    const err = new Error('非法路径');
    err.status = 400;
    throw err;
  }
  return target;
}

// 5) 原型污染：拒绝危险键
function safeMerge(target, source) {
  for (const [key, value] of Object.entries(source)) {
    if (key === '__proto__' || key === 'constructor' || key === 'prototype') continue;
    target[key] = value;
  }
  return target;
}
```

**CORS 的三个易错配置：**

1. `origin: '*'` 与 `credentials: true` 不能共存，浏览器会直接拒绝。
2. 反射任意 `Origin`（`origin: true`）等价于允许所有来源，配合凭证就是漏洞。
3. 预检请求要允许 `OPTIONS`，并设置合理的 `Access-Control-Max-Age`，否则每个请求都多一次往返。

**其他必须做的事：** HTTPS + HSTS、Cookie 的 `HttpOnly/Secure/SameSite`、上传的类型与大小限制、日志脱敏、依赖审计与锁文件、密钥轮换、生产隐藏堆栈，以及每个接口的对象级鉴权（防 IDOR 越权）。

**面试怎么答：** 按「输入校验 → 参数化/命令数组化/路径校验 → 输出编码与 CSP → CORS 白名单 → 限流与鉴权 → 依赖与密钥」讲成一条链路，重点说清 NoSQL 操作符注入、命令注入、路径穿越三种具体写法与防护代码。

**易错点：**

- CORS 配 `origin: true` + `credentials: true`，等于对所有站点开放凭证。
- 用字符串拼接 SQL，参数化只做了一半。
- 用 `exec` 拼接用户输入，`; rm -rf` 直接执行。
- 只校验扩展名不校验内容类型，上传可执行脚本。
- 只在网关做鉴权，业务接口没有对象级权限校验，改个 id 就能越权。
- CSP 里加 `unsafe-inline` 图省事，XSS 防护形同虚设。

## 9. Node 服务的测试（Jest + supertest）

**结论：** 测试要分层：**单元测试**验证 Service 的业务规则（mock Repository），**集成测试**用 supertest 直接打 `app`（不监听端口）验证路由、中间件、校验与错误映射，**端到端测试**验证真实依赖。关键是把 `app` 与 `server.listen` 拆开，并让依赖可注入，否则测试只能连真数据库、又慢又不稳定。

**测试金字塔：**

| 层级 | 范围 | 速度 | 数量占比 | 工具 |
| --- | --- | --- | --- | --- |
| 单元 | 函数、Service、工具 | 毫秒 | 最多 | Jest / node:test |
| 集成 | 路由 + 中间件 + DB | 百毫秒 | 中等 | supertest + 测试库 |
| 端到端 | 完整链路、外部依赖 | 秒级 | 最少 | Playwright / 真实环境 |

**可测试性的三个改造：**

1. **导出 app，不导出 listen**：`app.js` 只创建并返回 app；`server.js` 负责 `listen`。supertest 传 app 即可，无需占用端口。
2. **依赖注入**：Service 的 Repository、时钟、ID 生成器通过构造函数传入，测试可替换为假实现。
3. **配置可覆盖**：测试环境用独立数据库与独立配置，避免污染开发数据。

```js
// Node 18+：app.js —— 只组装，不监听
const express = require('express');

function createApp({ userService }) {
  const app = express();
  app.use(express.json({ limit: '1mb' }));

  app.get('/health/live', (req, res) => res.json({ status: 'ok' }));

  app.post('/api/v1/users', async (req, res, next) => {
    try {
      const { email, name } = req.body;
      if (typeof email !== 'string' || typeof name !== 'string') {
        return res.status(422).json({ code: 'VALIDATION_FAILED' });
      }
      const user = await userService.create({ email, name });
      res.status(201).json({ id: user.id, email: user.email });
    } catch (err) {
      next(err);
    }
  });

  app.use((err, req, res, next) => {
    if (res.headersSent) return next(err);
    res.status(err.status || 500).json({ code: err.code || 'INTERNAL' });
  });

  return app;
}

module.exports = { createApp };
```

**测试规范：**

- 测试里 `app.listen()` 固定端口，用例并发时端口冲突。
- 每个测试连真实数据库且不清数据，结果依赖执行顺序。
- 只断言 200，不校验响应体，接口字段改了测试仍然通过。
- Mock 了被测对象本身，测试变成「验证 mock 调用」而没有验证逻辑。
- 用 `setTimeout` 真等 3 秒测超时，测试套件越来越慢。
- 覆盖率刷到 100%，但异常分支全是空断言。

## 10. 部署（Docker、Nginx 反向代理、PM2）

**结论：** 生产部署的标准形态是「**容器内单进程 + Nginx/网关反向代理 + 编排层负责扩缩与重启**」。容器要小而可复现（多阶段构建、`npm ci`、非 root、只带生产依赖），进程要能正确处理 `SIGTERM` 做优雅退出，Nginx 负责 TLS、静态资源、压缩、超时与真实 IP 透传。PM2 适合虚拟机部署，容器里应交给编排系统。

**Dockerfile 的关键点：**

| 项 | 做法 | 原因 |
| --- | --- | --- |
| 基础镜像 | `node:18-alpine` 或 `node:18-slim` | 体积小、攻击面小 |
| 多阶段 | deps 阶段装依赖，运行阶段只拷产物 | 镜像不含构建工具 |
| 依赖安装 | `npm ci --omit=dev` | 锁定版本、可复现 |
| 用户 | `USER node` | 不以 root 运行 |
| 信号 | `CMD ["node", "server.js"]`（exec 形式） | PID 1 能直接收到 SIGTERM |
| 健康检查 | `HEALTHCHECK` 打 `/health/live` | 编排可感知 |
| 缓存 | 先拷 `package*.json` 再 `npm ci` | 改代码不失效依赖层 |

```dockerfile
# 多阶段构建：依赖层与运行层分离
FROM node:18-alpine AS deps
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci --omit=dev

FROM node:18-alpine
ENV NODE_ENV=production
WORKDIR /app

# 只拷贝生产依赖与源码
COPY --from=deps /app/node_modules ./node_modules
COPY . .

# 不使用 root
USER node
EXPOSE 3000

# 容器内健康检查，Node 18 自带 fetch
HEALTHCHECK --interval=30s --timeout=3s --start-period=10s --retries=3 \
  CMD node -e "fetch('http://127.0.0.1:3000/health/live').then(r=>process.exit(r.ok?0:1)).catch(()=>process.exit(1))"

# exec 形式，node 作为 PID 1 直接接收 SIGTERM
CMD ["node", "server.js"]
```

```nginx
# Nginx 反向代理：TLS 终止、压缩、超时、真实 IP
upstream node_api {
    server 127.0.0.1:3000;

        proxy_pass http://node_api;
        proxy_http_version 1.1;
        proxy_set_header Connection "";                 # 启用 keepalive
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        proxy_connect_timeout 3s;

        proxy_read_timeout 30s;

        access_log off;
```

**Node 侧必须配合的两件事：**

1. **信任代理**：Express 默认不信任 `X-Forwarded-*`，需要 `app.set('trust proxy', 1)` 才能拿到真实 IP 与协议；否则限流、日志、`Secure` Cookie 判断都会错。
2. **优雅退出**：监听 `SIGTERM`，停止接收新连接，等待在途请求，关闭连接池，超时强杀。容器默认 `docker stop` 会先发 SIGTERM，宽限期后才 SIGKILL。

```js
// Node 18+：部署环境下的入口
const http = require('node:http');
const { createApp } = require('./app');

const app = createApp({ /* 注入依赖 */ });
app.set('trust proxy', 1);        // 位于 Nginx 之后

const server = http.createServer(app);
server.listen(process.env.PORT || 3000);

let closing = false;
function shutdown(signal) {
  if (closing) return;
  closing = true;
  console.log(`收到 ${signal}，开始退出`);

  const force = setTimeout(() => {
    server.closeAllConnections?.();
    process.exit(1);
  }, 10_000);
  force.unref();

  server.close(async () => {
    await app.locals.db?.end?.();
    await app.locals.redis?.quit?.();
    clearTimeout(force);
    process.exit(0);
  });
  server.closeIdleConnections?.();
}

process.on('SIGTERM', () => shutdown('SIGTERM'));
process.on('SIGINT', () => shutdown('SIGINT'));
```

**发布策略：** 滚动发布（K8s 默认，逐批替换）、蓝绿（两套环境切换，回滚快但成本高）、金丝雀（先放 1%～5% 流量）、虚拟机上的 PM2 reload（逐个替换 worker）。

**PM2 与容器的关系：** 虚拟机用 PM2 做守护、多进程、日志与开机自启；容器里 `PID 1` 应由 Node 直接担任（或加 `tini`/`--init`），重启交给 `restart: always` 或 K8s。容器内再套 PM2 会让信号链变复杂，且 PM2 的多进程与容器副本重复扩容。

**镜像与配置规范：**

1. 镜像 tag 用**版本号或 git sha**，禁止只用 `latest`。
2. 配置通过环境变量/Secret 注入，不打进镜像。
3. `.dockerignore` 排除 `node_modules`、`.git`、`.env`、测试与日志。
4. 镜像扫描（Trivy）与依赖审计纳入 CI。
5. 日志写 stdout/stderr，由运行时采集，不在容器内轮转。

**面试怎么答：** 先讲「单进程容器 + Nginx + 编排」的标准形态，再说 Dockerfile 的多阶段、非 root、`npm ci`、exec 形式与健康检查，接着讲 Nginx 的 keepalive、真实 IP、超时，最后补 `trust proxy`、优雅退出与滚动/蓝绿发布。

**易错点：**

- 用 shell 形式 `CMD node server.js`，信号收不到，`docker stop` 只能等超时。
- 镜像里以 root 运行，容器逃逸风险高。
- 改了代码但依赖层缓存失效，构建时间翻倍。
- Nginx 与 Express 的 body 大小限制不一致，大请求一边 413 一边 500。
- 不设 `trust proxy`，限流按 Nginx 的内网 IP 统计，所有用户共享一个桶。
- 容器内用 PM2 cluster，再开 10 个副本，连接数与内存成倍超限。
- 用 `latest` 发布，出问题无法确定回滚到哪个版本。

## 11. BFF 与 SSR

**结论：** **BFF（Backend For Frontend）** 是面向特定端的聚合层：为 Web、App、小程序分别裁剪接口，减少端上多次往返与过度取数；**SSR（服务端渲染）** 是在服务端生成 HTML，改善首屏与 SEO，代价是服务端渲染开销与 hydration 复杂度。两者都跑在 Node 上，但目标不同：BFF 解决「**数据聚合与协议适配**」，SSR 解决「**首屏内容与 SEO**」。

**BFF 的职责与边界：**

| 职责 | 说明 |
| --- | --- |
| 聚合 | 一次请求并发调用多个下游，合并结果 |
| 裁剪 | 只返回当前端需要的字段，减少流量 |
| 适配 | 把内部协议转换成端上友好的结构 |
| 鉴权 | 在 BFF 统一处理 Token 换取与注入 |
| 容错 | 单个下游失败时降级，不拖垮整页 |

**BFF 的风险：** 多一跳网络与故障点、聚合逻辑容易膨胀成「第二个后端」、团队边界不清导致谁都改。应对方式是**按端拆分、只做编排不做领域逻辑、设置超时与降级、明确 owner**。

```js
// Node 18+：BFF 聚合接口，带超时与部分失败降级
const express = require('express');
const app = express();

async function fetchJson(url, { timeoutMs = 800, headers = {} } = {}) {
  const res = await fetch(url, {
    headers,
    signal: AbortSignal.timeout(timeoutMs),   // Node 18 支持
  });
  if (!res.ok) throw new Error(`下游 ${url} 返回 ${res.status}`);
  return res.json();
}

app.get('/bff/home', async (req, res) => {
  const auth = { authorization: req.headers.authorization || '' };

  const [user, orders, coupons] = await Promise.allSettled([
    fetchJson('http://user-svc/users/me', { headers: auth }),
    fetchJson('http://order-svc/orders?limit=5', { headers: auth }),
    fetchJson('http://promo-svc/coupons/available', { headers: auth, timeoutMs: 300 }),
  ]);

  const pick = (result, fallback) =>
    result.status === 'fulfilled' ? result.value : fallback;

  res.json({
    user: pick(user, null),
    orders: pick(orders, []),
    coupons: pick(coupons, []),
    degraded: [user, orders, coupons].some((r) => r.status === 'rejected'), // 明确告知降级
  });
});
```

`Promise.allSettled` 是关键：用 `Promise.all` 时任何一个下游失败都会让整页 500，而首页聚合通常允许部分模块缺失。

**SSR 相关概念：** CSR 在浏览器执行 JS 后渲染，首屏慢、SEO 弱；SSR 每次请求服务端渲染，首屏快、SEO 强；SSG 构建时生成，最快；ISR 在 SSG 基础上定期增量再生，适合频繁更新但可容忍延迟的内容。

```js
// Node 18+：最小 SSR，注意 HTML 转义与初始状态注入
const http = require('node:http');

function escapeHtml(value) {
  return String(value).replace(/[&<>"']/g, (c) => ({
    '&': '&amp;', '<': '&lt;', '>': '&gt;', '"': '&quot;', "'": '&#39;',
  }[c]));
}

function renderPage({ title, user, items }) {
  const state = JSON.stringify({ user, items }).replace(/</g, '\\u003c'); // 防 </script> 注入
  return `<!doctype html>
<html lang="zh-CN">
<head>
  <meta charset="utf-8">
  <title>${escapeHtml(title)}</title>
</head>
<body>
  <div id="app">
    <h1>${escapeHtml(user.name)} 的订单</h1>
    <ul>${items.map((i) => `<li>${escapeHtml(i.title)}</li>`).join('')}</ul>
  </div>
  <script>window.__INITIAL_STATE__ = ${state};</script>
  <script src="/client.js" defer></script>
</body>
</html>`;
}

const loadHomeData = async () => ({
  title: '首页',
  user: { name: '张三' },
  items: [{ title: '订单 1' }],
});

http.createServer(async (req, res) => {
  if (req.url === '/') {
    const data = await loadHomeData();          // 服务端取数，避免端上瀑布
    res.setHeader('Content-Type', 'text/html; charset=utf-8');
    res.end(renderPage(data));
    return;
  }
  res.statusCode = 404;
  res.end('not found');
}).listen(3000);
```

**hydration 与常见不一致：** 浏览器接管 SSR 生成的 DOM 时，若两端渲染结果不同会报 hydration mismatch。常见来源是 `Date.now()`、`Math.random()`、`new Date().toLocaleString()`、`window` 判断、用户本地时区。解法是把这些值**由服务端计算并放入初始状态**，或延迟到 `useEffect` 中渲染。

**流式 SSR：** React 18 的 `renderToPipeableStream` 可以边渲染边发送，配合 `Suspense` 让慢模块后到，显著改善 TTFB 与首屏。代价是响应头一旦发送就无法改状态码，错误处理更复杂。

**性能与缓存：** 按「用户相关/无关」拆分页面，无关部分用 CDN 或 Redis 缓存 HTML；设置 `Cache-Control` 与 `Vary`；服务端取数并发化；渲染耗时纳入监控，超阈值降级为 CSR 骨架屏；BFF/SSR 进程同样要限流、超时、熔断与优雅退出。

**面试怎么答：** 先区分 BFF（聚合与适配）与 SSR（首屏与 SEO），再讲 BFF 的职责、`Promise.allSettled` 部分降级与「不做领域逻辑」的边界，接着对比 CSR/SSR/SSG/ISR，最后补 HTML 转义、初始状态注入、hydration mismatch 与流式渲染。

**易错点：**

- BFF 用 `Promise.all`，一个非核心下游超时导致整页失败。
- 聚合层越写越厚，把业务规则复制一遍，形成双份维护。
- SSR 拼接 HTML 不转义，直接引入 XSS。
- 初始状态用 `JSON.stringify` 直接注入 `<script>`，`</script>` 截断标签。
- 服务端渲染使用 `window`/`localStorage`，直接抛错。
- 两端时间/随机数不一致，hydration 报警并整树重渲染。

## 12. 微服务、消息队列与任务队列

**结论：** 微服务不是默认答案：**单体优先，按业务边界拆分**。拆分后必须面对分布式带来的问题：服务发现、超时重试、幂等、最终一致、链路追踪。**消息队列**用于解耦与削峰，**任务队列**用于异步执行可重试的后台任务；两者都要保证「至少一次投递 + 消费端幂等」，因为「恰好一次」在工程上几乎不可实现。

**单体与微服务：**

| 维度 | 单体 | 微服务 |
| --- | --- | --- |
| 部署 | 一个包 | 独立部署、独立扩容 |
| 事务 | 本地事务，强一致 | 分布式事务/Saga，最终一致 |
| 调用 | 进程内函数 | 网络调用，需超时/重试/熔断 |
| 排障 | 单一日志 | 需要 traceId 与链路追踪 |
| 团队 | 共享代码库 | 按边界划分 ownership |
| 适用 | 早期、团队小、领域未稳定 | 多团队、独立伸缩、领域清晰 |

**什么时候该拆：** 不同模块的伸缩需求差异大、发布节奏互相阻塞、团队规模大到沟通成本超过拆分成本、领域边界已经稳定。**不该拆**：领域还没想清楚、团队没有可观测性与自动化运维能力、只是「别人都拆了」。

**消息中间件对比：**

| 组件 | 模型 | 吞吐 | 顺序 | 典型场景 |
| --- | --- | --- | --- | --- |
| RabbitMQ | AMQP，队列 + 交换机 | 中 | 队列内近似有序 | 业务解耦、延时任务、复杂路由 |
| Kafka | 分区日志，拉模型 | 极高 | 分区内严格有序 | 日志、埋点、事件流、CDC |
| Redis Streams | 内存流 + 消费组 | 高 | 流内有序 | 轻量事件、实时通知 |
| BullMQ | Redis 任务队列 | 中高 | 按队列 | 邮件、导出、重试任务 |
| SQS | 托管队列 | 高 | 标准队列不保证 | 云上解耦 |

**投递语义：** At most once 可能丢消息；At least once 会重复但可重试；Exactly once 成本极高，工程上通常用「至少一次 + 消费端幂等」近似。

```js
// Node 18+：BullMQ 生产者与消费者（npm i bullmq ioredis）
const { Queue, Worker } = require('bullmq');
const Redis = require('ioredis');

const connection = { host: '127.0.0.1', port: 6379 };
const redis = new Redis(connection);

const emailQueue = new Queue('email', { connection });
const sendWelcomeMail = async (email) => { console.log('发送欢迎邮件', email); };

async function enqueueWelcome(userId, email) {
  await emailQueue.add(
    'welcome',
    { userId, email },
    {
      jobId: `welcome:${userId}`,            // 去重：同一用户只入队一次
      attempts: 5,
      backoff: { type: 'exponential', delay: 1000 },  // 1s, 2s, 4s...
      removeOnComplete: { age: 3600 },       // 保留 1 小时便于排查
      removeOnFail: { age: 7 * 86400 },
    },
  );
}

const worker = new Worker('email', async (job) => {
  // 消费端幂等：用业务唯一键或 Redis SET NX 占位
  const key = `job:done:${job.id}`;
  const first = await redis.set(key, '1', 'NX', 'EX', 86400);
  if (!first) return;                         // 已处理过，直接跳过

  if (job.name === 'welcome') {
    await sendWelcomeMail(job.data.email);   // 外部调用必须有超时
  }
}, {
  connection,
  concurrency: 10,                            // 并发消费数
  limiter: { max: 100, duration: 1000 },      // 每秒最多 100 个，保护下游
});

worker.on('failed', (job, err) => {
  console.error('任务失败', { id: job?.id, attempts: job?.attemptsMade, err: err.message });
});

worker.on('completed', (job) => {
  console.log('任务完成', job.id);
});

// 优雅退出：等待当前任务完成，不再取新任务
process.on('SIGTERM', async () => {
  await worker.close();
  await emailQueue.close();
});
```

**消费端幂等的三种做法：**

1. **数据库唯一约束**：业务表加 `(source, event_id)` 唯一索引，重复插入直接冲突。
2. **去重表/Redis 标记**：处理前 `SET NX` 占位，处理完写入结果；注意占位失败与处理失败的区分。
3. **状态机**：订单状态只能从 `PENDING → PAID`，重复消息因状态不满足而被忽略。

**分布式一致性的常用模式：**

| 模式 | 做法 | 适用 |
| --- | --- | --- |
| 本地消息表/Outbox | 业务与事件写同一事务，中继进程投递 | 避免「写库成功、发消息失败」 |
| Saga | 每步有补偿操作，失败反向执行 | 跨服务长事务 |
| TCC | Try-Confirm-Cancel 三阶段预留 | 资金、库存等强约束 |
| 幂等键 | 客户端生成唯一键，服务端去重 | 下单、支付 |

**Outbox 的核心：** 在同一个数据库事务里写业务数据和一条 outbox 记录，再由独立的中继进程轮询并投递到 MQ，投递成功标记已发送。这样不会出现「数据库提交了但消息没发出去」的丢事件问题。

**微服务的工程底线：**

1. 每个跨服务调用都要有**超时、重试上限、熔断与降级**。
2. 所有请求透传 `traceId`，日志、指标、链路三者可关联。
3. 消费端必须幂等，生产端尽量带业务唯一键。
4. 队列要配置**死信队列/失败重试上限**，避免毒消息无限循环。
5. 监控队列积压、消费延迟、失败率，积压是故障的最早信号。
6. 服务发现与配置中心选型要跟公司基础设施一致，不要自造。

**面试怎么答：** 先给「单体优先、按边界拆」的判断，再讲拆分后的分布式问题（超时、幂等、最终一致、追踪），接着对比 RabbitMQ/Kafka/BullMQ 的模型与场景，最后落到「至少一次 + 消费端幂等 + Outbox + 死信队列」。

**易错点：**

- 为了「架构先进」过早拆微服务，运维与排障能力跟不上。
- 认为消息队列能保证恰好一次，消费端不做幂等。
- 业务写库与发消息不在同一事务，出现丢事件或重复事件。
- 消费者没有重试上限与死信队列，毒消息无限重投。
- 任务队列没有 `jobId` 去重，用户重复点击就重复发邮件。
- 队列积压没有监控，直到磁盘/内存被打满才发现。
