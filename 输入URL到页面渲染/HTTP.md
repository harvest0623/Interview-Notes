# HTTP 协议

## 基础概念

1. HTTP（HyperText Transfer Protocol）是**基于 TCP 的应用层协议**，用来在互联网上传输数据。
2. 它定义了**客户端与服务器之间的通信规则**：请求 / 响应模型。
3. 报文使用**文本格式**通信（HTTP/2 起改为二进制分帧）。

**请求报文**：请求行（方法、路径、版本）+ 请求头 + 请求体。
**响应报文**：状态行（版本、状态码）+ 响应头 + 响应体。

**常见方法**：`GET`（获取）、`POST`（提交）、`PUT`（更新）、`DELETE`（删除）、`HEAD`、`OPTIONS`。

**常见状态码**：

| 分类 | 含义 | 例子 |
| --- | --- | --- |
| 1xx | 信息 | 101 Switching Protocols |
| 2xx | 成功 | 200 OK、204 No Content |
| 3xx | 重定向 / 缓存 | 301 永久、302 临时、304 Not Modified |
| 4xx | 客户端错误 | 400、401、403、404 |
| 5xx | 服务器错误 | 500、502、504 |

---

## HTTP/0.9 版本

1. 最初的简单版本，只用来传输**体积很小的 HTML 文件**。
2. 特点：
   - 只有**请求行**，没有请求头、请求体。
   - 服务端没有响应头、响应体。
   - 返回内容以 **ASCII 字符流**传输，只能传 HTML。

---

## HTTP/1.0 版本

1. 网景公司推出浏览器，万维网联盟（W3C）成立 HTTP 工作组。
2. 网络发展带来了**多种资源**的传输需求（图片、视频、音频、JS、CSS 等）。
3. 如何支持多种类型文件的下载？
   - 引入**请求头 / 响应头**（向服务器传递额外信息），例如：
     `Accept: text/html`、`Accept-Encoding: gzip, deflate`、`Accept-Charset: utf-8`、`Accept-Language: zh-CN,zh;q=0.9`、`Content-Encoding: br`、`Content-Type: text/html; charset=utf-8`
   - 引入**状态码**。
   - 引入 **Cache 机制**（缓存）。
   - 引入 **User-Agent** 字段（用户代理）。
4. 缺点：默认**短连接**，每个请求都要新建一次 TCP 连接，开销大。

---

## HTTP/1.1 版本

1. **持久连接（Keep-Alive）**：一次 TCP 连接可传输多个请求和响应（默认开启）。
2. 浏览器对**同一域名**通常只维持 **6 个** TCP 连接，超出的请求排队。
3. **队头阻塞（HOL Blocking）**：同一连接中前面的请求未返回，后面的请求会被阻塞。
4. **Host 字段**：用来指定请求的目标主机，使同一 IP 能托管多个网站（虚拟主机）。
5. **Chunk Transfer Encoding**：分块传输，服务器可以在不知道总长度时边生成边发送。
6. 支持更多缓存控制字段（如 `Cache-Control`）。

---

## HTTP/2.0 版本

**1.1 的性能问题**：请求越多越慢。理论上 100 个请求需要 `100 × n × RTT`，分成 6 条连接后为 `(100 × n × RTT) / 6`，带宽利用率低（如 100M 带宽实际只用到 12.5M）。

**带宽利用率低的原因**：

- 同时启用多条 TCP 连接，这些连接**相互竞争带宽**。
- **TCP 慢启动**：新连接会先从小窗口慢慢增大，起步阶段发送很慢。
- **队头阻塞**：一条 TCP 连接中某个请求的响应延迟，会阻塞其后的请求。

**HTTP/2 的解决手段**：

1. **一个域名只保留一个 TCP 连接**，所有请求都在这个连接上发送。
2. **多路复用**：把该连接中的多个请求切成**帧**打散传输，并给每个帧打上流标识；服务器可按优先级处理「加急」的请求。
3. **头部压缩（HPACK）**：压缩请求头和响应头，减少传输量（尤其对重复的 Cookie、User-Agent 效果明显）。
4. **服务器推送（Server Push）**：可主动把客户端将要用的资源推过去。
5. **二进制分帧**：相比 1.1 的文本格式，解析更高效。

> 局限：HTTP/2 解决了「应用层」的队头阻塞，但**底层仍是 TCP**，一旦丢包，TCP 层的队头阻塞依旧存在。

## HTTPS = HTTP + SSL/TLS

1. **TLS** 是一种加密协议，用来保护 HTTP 通信的安全（机密性、完整性、身份认证）。
2. **对称加密**：客户端和服务端持有同一个密钥，用它加密、也用它解密。速度快，但「如何安全地把密钥交给对方」是难题。
3. **非对称加密**：服务端生成一对公钥/私钥，把**公钥**发给客户端；客户端用公钥加密一个「对称密钥」传给服务端，服务端用**私钥**解密得到该密钥。
4. **实际做法（混合加密）**：用非对称加密安全地协商出对称密钥，之后的数据通信用对称加密传输——兼顾安全与性能。
5. 还需要**数字证书 + CA** 来验证服务端公钥的真实性，防止中间人攻击。

---

## HTTP/3.0 版本

1. **2.0 的问题**：底层 TCP 的**队头阻塞**依然存在。
2. 能直接改进 TCP 吗？很难——TCP 深植于操作系统内核，更新缓慢。
3. **TCP 协议僵化（Protocol Ossification）**：中间设备（防火墙、NAT 等）对 TCP 的行为做了大量假设，导致 TCP 难以演进。
4. **QUIC 协议**：于是把可靠传输、加密等能力**搬到 UDP 之上**，绕开 TCP 的僵化。
5. 基于 UDP 优化，取 TCP 之长、补 TCP 之短：
   - 可靠传输、流量控制。
   - **TLS 加密内建**（握手与加密合并，更快）。
   - **多路复用**，且**彻底解决队头阻塞**（流之间互不影响）。
   - **快速握手**（0/1 RTT 建立连接）。

## 附：HTTP 缓存

| 类型 | 相关字段 | 行为 |
| --- | --- | --- |
| 强缓存 | `Cache-Control: max-age`、`Expires` | 未过期则直接用本地缓存，**不发请求** |
| 协商缓存 | `ETag` / `If-None-Match`、`Last-Modified` / `If-Modified-Since` | 发请求校验，未变化返回 **304**，复用本地缓存 |

优先级：`Cache-Control` 高于 `Expires`；`ETag` 高于 `Last-Modified`。
