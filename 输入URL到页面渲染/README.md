# 从输入 URL 到页面渲染

> **经典面试题：在浏览器地址栏输入 `https://www.baidu.com` 并回车，到页面完整展示，中间发生了什么？**

这是一道串联网络与浏览器工作原理的综合题。回答时建议先给出**总览骨架**，再逐段展开，最后补充**渲染流程**与**性能优化**。

## 1. 总览流程

```
输入 URL
  → URL 解析
  → DNS 解析（域名 → IP）
  → 建立 TCP 连接（三次握手）
  → 发送 HTTP 请求
  → 服务器处理、返回 HTTP 响应
  → 浏览器解析并渲染页面
  → 断开 TCP 连接（四次挥手）
```

如果走 HTTPS，在「建立 TCP 连接」之后、发送请求之前，还要多一次 **TLS 握手**（见 [HTTP.md](HTTP.md) 中 HTTPS 部分）。

---

## 2. 第一步：URL 解析

浏览器先把地址栏里的字符串解析成结构化信息：协议（`https`）、主机（`www.baidu.com`）、端口（默认 443/80）、路径（`/`）、查询参数、hash 等。

- 如果输入的不是合法 URL，浏览器可能把它当作搜索词，交给默认搜索引擎。
- **优化点**：现代浏览器会在后台预解析、预连接（如 DNS 预取、`preconnect`），提前完成后续步骤。

> 手写 URL 解析器可参考同级目录 `解析URL`。

---

## 3. 第二步：DNS 解析（域名 → IP）

TCP/IP 通信需要知道对方的 **IP 地址**，而用户输入的是域名，因此要先把域名解析成 IP。

**查询顺序（就近优先）：**

1. **浏览器 DNS 缓存**
2. **操作系统 DNS 缓存**（含 hosts 文件）
3. **本地 DNS 服务器**（运营商/网关）
4. 本地 DNS 服务器依次向 **根域名服务器 → 顶级域名服务器（.com）→ 权威域名服务器（baidu.com）** 发起查询
5. 拿到 IP 后**逐级写入缓存**，并设置 TTL

**优化点：**

- **DNS 预取**：`<link rel="dns-prefetch" href="//cdn.example.com">`，提前解析第三方域名。
- DNS 查询本身也有耗时（通常几十毫秒），是首屏关键路径的一环。

---

## 4. 第三步：建立 TCP 连接（三次握手）

拿到 IP 后，通过**三次握手**建立可靠的 TCP 连接：

1. 客户端 → 服务器：`SYN`（请求建立连接）
2. 服务器 → 客户端：`SYN + ACK`（同意并确认）
3. 客户端 → 服务器：`ACK`（确认服务器的确认）

之后双方进入 `ESTABLISHED` 状态，可以开始传输数据。

> **为什么要三次？** 两次无法确认「客户端的接收能力」和「自己的发送请求是否已过期」，三次才能让双方都确认收发能力正常、并同步初始序列号。
>
> 详见 [TCP.md](TCP.md)。

**优化点**：`preconnect` 可以提前完成 DNS + TCP + TLS，减少真正的请求等待时间。

---

## 5. 第四步：发送 HTTP 请求

TCP 连接建立后，浏览器构造 **HTTP 请求报文**发送给服务器，包含：

- **请求行**：方法（GET/POST…）、路径、HTTP 版本
- **请求头**：`Host`、`User-Agent`、`Accept`、`Cookie`、`Referer` 等
- **请求体**：GET 一般为空，POST 等携带数据

**优化点：**

- **HTTP 缓存**：命中强缓存（`Cache-Control`/`Expires`）可直接使用本地副本，不发请求；协商缓存（`ETag`/`Last-Modified`）则发请求但可能返回 304 节省流量。
- **减少请求数**：合并资源、使用雪碧图、内联小资源。

---

## 6. 第五步：服务器处理并返回响应

服务器接收到请求后，可能经过负载均衡、反向代理（Nginx）、应用服务器处理，最终返回 **HTTP 响应报文**：

- **状态行**：状态码（200/301/304/404/500…）
- **响应头**：`Content-Type`、`Content-Encoding`、`Cache-Control` 等
- **响应体**：HTML 文本或其他资源

浏览器收到后：根据状态码处理（如 301/302 重定向会重新走一遍流程、304 使用本地缓存）。

**优化点**：`Content-Encoding: gzip/br` 压缩、CDN 就近分发。

---

## 7. 第六步：浏览器渲染

这是整道题最容易展开、也最能体现功底的部分。

**（1）构建 DOM 树**
解析 HTML 字节流 → 词法/语法分析生成节点 → 形成 **DOM 树**。
遇到 `<script>`（无 `async`/`defer`）会**阻塞 HTML 解析**，因此脚本通常放在底部或使用 `defer`/`async`。

**（2）构建 CSSOM 树**
解析 CSS（外链、内联、行内）生成 **CSSOM**。CSS 会阻塞渲染（但不阻塞 DOM 解析）。

**（3）构建渲染树（Render Tree）**
DOM + CSSOM 合并成渲染树，只包含**可见**节点（`display:none` 的元素不在其中）。

**（4）布局 / 回流（Layout / Reflow）**
计算每个节点的几何信息（位置、尺寸）。

**（5）绘制（Paint）**
把节点绘制成像素，生成绘制指令。

**（6）分层与合成（Layer / Composite）**
把页面分成多个图层，交给 **GPU** 合成，最终显示到屏幕。

**关键概念：回流（Reflow）与重绘（Repaint）**

- **回流**：几何属性变化（宽高、位置、字体大小…），需要重新布局，代价最大。
- **重绘**：外观变化（颜色、背景…），不改变布局，代价次之。
- `transform` / `opacity` 等属性的动画可只触发**合成**，性能最好。

**优化点**：减少回流重绘、把动画放在合成层、使用 `requestAnimationFrame`、避免频繁读写 DOM 触发强制同步布局。

---

## 8. 第七步：断开 TCP 连接（四次挥手）

数据传输完成后，通过**四次挥手**断开连接：

1. 客户端 → 服务器：`FIN`（我要关闭了）
2. 服务器 → 客户端：`ACK`
3. 服务器 → 客户端：`FIN`（我也关了）
4. 客户端 → 服务器：`ACK`

客户端在发出最后的 `ACK` 后会进入 **`TIME_WAIT`**，等待 **2MSL** 后才真正关闭。

> **为什么要四次？** TCP 是全双工的，双方都要各自关闭自己的发送通道；服务器收到 `FIN` 后可能还有数据要发，所以 `ACK` 和 `FIN` 不能合并。
>
> **为什么要等 2MSL？** 确保最后的 `ACK` 能到达服务器；若丢失，服务器会重发 `FIN`，此时客户端还能响应。
>
> 详见 [TCP.md](TCP.md)。

> 补充：HTTP/1.1 默认**持久连接**（Keep-Alive），多个请求会复用同一条 TCP 连接，不一定每个请求都经历「握手 → 挥手」。

## 10. 可能的追问

**Q：JS、CSS 的解析会互相阻塞吗？**
CSS 不阻塞 DOM 解析，但会阻塞渲染；JS 会阻塞 DOM 解析（`defer`/`async` 除外），且 JS 执行前必须等待其上方的 CSS 加载完成（因为 JS 可能读取样式）。

**Q：为什么把 CSS 放在头部、JS 放在底部？**
CSS 提前加载可以让渲染树尽早构建、避免闪屏；JS 会阻塞解析，放底部可让页面先渲染出结构。

**Q：`defer` 和 `async` 的区别？**
`async` 下载完立即执行、执行顺序不定；`defer` 在 HTML 解析完成后、`DOMContentLoaded` 前按顺序执行。

**Q：白屏时间如何优化？**
减少首屏关键资源、开启缓存与压缩、使用 CDN、SSR/预渲染、首屏内联关键 CSS、懒加载非首屏资源。
