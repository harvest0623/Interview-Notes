# TCP 协议

TCP（Transmission Control Protocol，传输控制协议）是**面向连接的、可靠的、基于字节流**的传输层协议，是 HTTP 等应用层协议的底层支撑。

---

## 1. TCP 数据包结构（关键字段）

TCP 把数据切分成**报文段（Segment）**传输，每个报文段的头部包含：

| 字段 | 作用 |
| --- | --- |
| Sequence Number（序列号） | 标识本报文段数据的顺序，用于接收端重组 |
| Acknowledgment Number（确认号） | 期望收到的下一个字节序号，用于确认已收到数据 |
| Window Size（窗口大小） | 接收端还能接收多少数据，用于**流量控制** |
| 标志位 | `SYN`（建立连接）、`ACK`（确认）、`FIN`（结束连接）、`RST`（重置）等 |

---

## 2. 三次握手（建立连接）

```
客户端                                    服务器
  |------------- SYN, seq=x ------------->|   客户端进入 SYN_SENT
  |<----- SYN, ACK, seq=y, ack=x+1 -------|   服务器进入 SYN_RECEIVED
  |------------- ACK, ack=y+1 ------------>|   双方进入 ESTABLISHED
```

1. 客户端发送 `SYN`，请求建立连接 → 客户端进入 `SYN_SENT` 状态。
2. 服务器返回 `SYN + ACK`，表示同意并确认 → 服务器进入 `SYN_RECEIVED` 状态。
3. 客户端发送 `ACK` 确认 → 双方进入 `ESTABLISHED`，连接建立成功。

### 为什么必须三次？两次行不行？

- **两次不够**：只有两次的话，服务器无法确认自己发出的报文对方是否收到，也无法确认客户端当前的接收能力是否正常。
- **防止历史连接**：网络中可能存在**延迟的旧 `SYN` 报文**。若只握手两次，旧的 `SYN` 到达后服务器会直接建立连接并等待数据，白白浪费资源；三次握手能让客户端用 `ACK` 拒绝这个过期请求。
- 三次是**双方都能确认「对方收发能力正常」且「序列号已同步」的最小次数**。

---

## 3. 四次挥手（断开连接）

TCP 是全双工的，双方需要各自关闭自己的发送通道，因此需要四次：

```
客户端                                    服务器
  |------------- FIN, seq=u ------------->|   客户端进入 FIN_WAIT_1
  |<------------ ACK, ack=u+1 ------------|   服务器进入 CLOSE_WAIT
  |<------------ FIN, seq=w ---------------|   服务器进入 LAST_ACK
  |------------- ACK, ack=w+1 ------------>|   客户端进入 TIME_WAIT
                                             服务器收到 ACK 后进入 CLOSED
```

1. 客户端发送 `FIN`，请求关闭 → 客户端进入 `FIN_WAIT_1`。
2. 服务器返回 `ACK` 确认 → 服务器进入 `CLOSE_WAIT`，客户端进入 `FIN_WAIT_2`。
3. 服务器把剩余数据发完后，发送 `FIN` → 服务器进入 `LAST_ACK`。
4. 客户端返回 `ACK` → 客户端进入 `TIME_WAIT`，服务器收到后进入 `CLOSED`。

> **注意**：真正先关闭的是客户端，`TIME_WAIT` 出现在**主动关闭方**（这里即客户端），等待 `2MSL` 后进入 `CLOSED`。

### 为什么要四次？

- 服务器收到 `FIN` 后，可能**还有数据没发完**，所以先回一个 `ACK`，等数据发完再单独发 `FIN`——`ACK` 和 `FIN` 不能合并，于是四次。
- 若服务器也没有数据要发，`ACK` 和 `FIN` 可以合并，退化成三次挥手。

### 为什么要等待 2MSL？

- **保证最后的 `ACK` 能到达服务器**：若该 `ACK` 丢失，服务器会超时重发 `FIN`，此时客户端仍能接收并重发 `ACK`。
- **让本次连接的旧报文在网络上彻底消失**，避免影响后续新连接。

## 4. TCP 的核心特点

- **可靠传输**：通过序列号、确认号、超时重传、校验和保证数据不丢、不错。
- **有序传输**：接收端按序列号重组数据，保证顺序。
- **面向连接**：通信前必须握手建立连接。
- **字节流**：不保留消息边界，需要应用层自己划分（如 HTTP 的内容长度/分块）。
- **流量控制**：通过接收方通告的**窗口大小**，防止发送过快导致接收端缓冲区溢出。
- **拥塞控制**：通过**拥塞窗口**避免网络过载，包含四个算法：
  - **慢启动（Slow Start）**：窗口从很小开始指数增长。
  - **拥塞避免（Congestion Avoidance）**：达到阈值后改为线性增长。
  - **快重传（Fast Retransmit）**：收到 3 个重复 ACK 立即重传，不必等超时。
  - **快恢复（Fast Recovery）**：配合快重传，将窗口降到一半后继续（不回到慢启动）。

---

## 5. 队头阻塞（Head-of-Line Blocking）

- TCP 保证**有序**，若前面的报文段丢失，后续已到达的报文段也只能在缓冲区等待，造成阻塞。
- 这是 HTTP/2 多路复用仍受制于 TCP 的根本原因；HTTP/3 改用 **QUIC（基于 UDP）**正是为了解决这一问题。
