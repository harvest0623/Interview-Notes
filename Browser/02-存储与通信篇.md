## 1. 浏览器存储全景对比（Cookie/localStorage/sessionStorage/IndexedDB/CacheStorage/OPFS）

**结论：** 六种存储解决的是不同问题：Cookie 是**随请求自动发送的会话凭证**，localStorage 与 sessionStorage 是**同步的字符串键值存储**，IndexedDB 是**异步的、可索引的结构化数据库**，CacheStorage 是**HTTP 请求与响应的缓存**，OPFS 是**源私有的文件系统**。选型的核心不是「谁容量大」，而是**是否要随请求发送、能否接受同步阻塞、数据是否结构化、是否需要离线**。

**全景对比：**

| 存储 | 容量（典型） | 生命周期 | 作用域 | API 形态 | 随请求发送 | 典型用途 |
| --- | --- | --- | --- | --- | --- | --- |
| Cookie | 单条约 4KB，单域数量有限 | 会话或 `Expires`/`Max-Age` | 域 + 路径，可跨子域 | `document.cookie`，同步 | 是 | 会话标识、灰度分流 |
| localStorage | 约 5MB/源 | 永久，除非主动清理 | 同源 | 同步 | 否 | 配置、轻量缓存、草稿 |
| sessionStorage | 约 5MB/源 | 标签页会话 | 同源 + 单个标签页 | 同步 | 否 | 表单暂存、一次性状态 |
| IndexedDB | 受配额限制，可达数百 MB 至 GB | 永久，可被浏览器清理 | 同源 | 异步，事件模型 | 否 | 大量结构化数据、离线数据库 |
| CacheStorage | 受配额限制 | 永久，可被清理 | 同源 | 异步 Promise | 否 | 静态资源、离线页面、接口缓存 |
| OPFS | 受配额限制 | 永久 | 同源 | 异步；Worker 内可同步 | 否 | 大文件、音视频、虚拟文件系统 |

**容量的真实含义：** 上表的「5MB」是各浏览器的实现上限而非规范承诺；`localStorage` 按 UTF-16 计费，存中文时一个字符可能占 2 字节，5MB 实际能放的字符数会减半。IndexedDB 与 CacheStorage 共享同一个「源配额」，配额由磁盘空间与浏览器策略决定，低磁盘时会收紧。

```js
// 查询当前源的配额与用量，并申请持久化（避免被自动清理）
const { usage, quota } = await navigator.storage.estimate();
console.log(`已用 ${(usage / 1024 / 1024).toFixed(1)}MB / 配额 ${(quota / 1024 / 1024).toFixed(1)}MB`);

const persisted = await navigator.storage.persist();
console.log('是否已持久化：', persisted);
```

**清理与逐出（eviction）：** 除 Cookie 外，其余存储都是「best-effort」。浏览器在磁盘紧张时会按「最近最少使用 + 是否持久化」清理整个源的数据，而不是逐条删除。申请 `persist()` 后仍需用户同意或满足站点参与度条件，Safari 的 ITP 还会对 7 天无交互的站点清除脚本可写存储。

**选型决策：**

| 需求 | 首选 | 理由 |
| --- | --- | --- |
| 登录态需要服务端自动识别 | Cookie（`HttpOnly`） | 唯一会自动随请求发送的存储 |
| 存一个主题、语言、开关 | localStorage | 同步、API 简单、量小 |
| 存未提交的表单，且希望每个标签页独立 | sessionStorage | 标签页隔离，刷新不丢 |
| 缓存上千条列表数据、支持按字段查询 | IndexedDB | 异步、索引、事务、容量大 |
| 离线访问页面与静态资源 | CacheStorage + Service Worker | 可拦截请求，按策略返回 |
| 在浏览器里处理大文件、断点续传 | OPFS | 文件语义、Worker 中可同步读写 |
| 敏感凭证 | 不下发到 JS 可读的位置 | localStorage 可被 XSS 读取 |

**同步与异步的分水岭：** localStorage 与 sessionStorage 的读写发生在主线程，且是同步 API。存 1MB JSON 时，`JSON.stringify` 与写入会占用主线程数十毫秒，直接表现为掉帧或交互延迟。IndexedDB、CacheStorage、OPFS 都是异步的，不会阻塞渲染，但代码复杂度更高。

**面试怎么答：** 不要背容量表，按「凭证、小配置、结构化数据、资源缓存、文件」五类需求各给一个方案，再补三个判断维度：是否随请求发送、同步还是异步、能否被浏览器清理。最后点出 Cookie 的自动携带是双刃剑（方便鉴权，也带来 CSRF），localStorage 的同步 API 是性能隐患。

**易错点：**

- Cookie 的限制是**单条约 4KB**，不是 4MB；数量上限各家不同，旧资料常写的「每域 50 条」已不适用于 Chrome。
- localStorage 只能存字符串，存对象必须序列化，`Date`、`Map`、`undefined` 会在序列化中丢失或变形。
- sessionStorage 不跨标签页共享，新标签页即使是同一 URL 也是独立副本。
- CacheStorage 只能存 `Request`/`Response`，不能直接存任意 JS 对象。
- OPFS 的同步文件句柄只在 Worker 中可用，主线程只能走异步 API。

## 2. Cookie 机制详解（Domain/Path/SameSite/HttpOnly/Secure/大小限制）

**结论：** Cookie 是服务器通过响应头 `Set-Cookie` 写入、浏览器按**域、路径、安全属性、SameSite** 自动附加到请求头 `Cookie` 的键值对。它本质上不是「存储 API」，而是**HTTP 状态载体**，因此容量小、每次请求都要带上、且前端无法设置 `HttpOnly`。理解 Cookie 的关键是「谁在什么时候会带上它」。

```http
HTTP/1.1 200 OK
Set-Cookie: sid=abc123; Domain=example.com; Path=/; Max-Age=604800; Secure; HttpOnly; SameSite=Lax
Set-Cookie: theme=dark; Path=/; Max-Age=31536000; SameSite=Lax
```

**核心属性：**

| 属性 | 作用 | 关键细节 |
| --- | --- | --- |
| `Domain` | 指定可接收该 Cookie 的域 | 不写则为 host-only（只发给当前主机）；写了则包含子域；必须是当前域的后缀，不能是公共后缀（如 `.com`） |
| `Path` | 指定路径前缀 | 请求路径以该前缀开头才发送；`/foo` 匹配 `/foo/bar`，不匹配 `/foobar`；默认是请求路径的目录 |
| `Expires` | 绝对过期时间 | 受客户端时钟影响 |
| `Max-Age` | 相对过期秒数 | 优先级高于 `Expires`；为 0 或负数表示删除 |
| `Secure` | 仅 HTTPS 发送 | 明文 HTTP 不发送；`localhost` 在 Chrome 中被视为安全上下文 |
| `HttpOnly` | 禁止 JS 读取 | 防 XSS 窃取会话 Cookie，但不能防「借用浏览器发请求」 |
| `SameSite` | 限制跨站发送 | `Strict`/`Lax`/`None`，`None` 必须同时有 `Secure` |
| `Partitioned` | 按顶层站点分区（CHIPS） | 第三方 Cookie 按「嵌入方站点」隔离，用于合规的嵌入式场景 |
| `Priority` | 清理优先级提示 | `Low`/`Medium`/`High`，浏览器在容量满时参考 |

**SameSite 的发送规则（面试高频）：**

| 值 | 跨站请求是否携带 | 典型影响 |
| --- | --- | --- |
| `Strict` | 完全不带 | 从外部链接进入站点时「看起来未登录」，需要再点一次 |
| `Lax` | 仅顶层导航且为安全方法（GET）时带 | 默认值，兼顾安全与体验；跨站 POST、iframe、img、fetch 不带 |
| `None` | 总是带（需 `Secure`） | 第三方嵌入、跨站单点登录需要；必须显式声明 |

补充两点：Chrome 的 `Lax` 对「跨站 POST 的顶层导航」有一个约 2 分钟的「Lax+POST」宽限（针对新写入的 Cookie），不要依赖它做安全设计；`SameSite` 只按**站点（eTLD+1）**判断，同一站点下的不同子域仍算同站。

**发送判定顺序（浏览器内部）：**

```text
请求 URL 与 Cookie 属性
  → 域匹配：host-only 精确匹配，或 Domain 后缀匹配且非公共后缀
  → 路径匹配：请求 path 以 Cookie Path 为前缀
  → Secure：HTTPS（或 localhost）
  → 未过期
  → SameSite：根据请求是否跨站、是否顶层导航、方法是否安全
  → 全部通过才写入 Cookie 请求头
```

注意：**端口不参与 Cookie 的域匹配**，`https://example.com:8080` 与 `:443` 共享 Cookie；协议只通过 `Secure` 间接影响。

**作用域与覆盖：**

| 场景 | 结果 |
| --- | --- |
| 同一 name，不同 Domain | 可以并存，请求时可能同时发送多个同名 Cookie |
| 同一 name，不同 Path | 更具体路径的 Cookie 排在前面，服务端通常取第一个 |
| 删除 Cookie | 必须让 `name`、`Domain`、`Path` 完全一致，并把 `Max-Age` 设为 0 |
| 子域读取父域 Cookie | 可以，父域 Cookie 会发送给子域 |
| 子域写父域 Cookie | 可以（`Domain=example.com`），但父域不能写子域的 host-only Cookie |

**Cookie 前缀（用命名约束属性）：**

| 前缀 | 要求 | 作用 |
| --- | --- | --- |
| `__Host-` | `Secure` + `Path=/` + 不带 `Domain` | 锁定到当前主机，防止子域覆盖 |
| `__Secure-` | 必须 `Secure` | 防止被明文覆盖 |

**大小与数量限制：**

| 限制 | 数值 | 说明 |
| --- | --- | --- |
| 单条 Cookie | 约 4096 字节 | 包含 name、value 与属性；超出会被截断或拒绝 |
| 单域数量 | 各家不同，Chrome 约 180 条 | 超出时按优先级与最近使用淘汰 |
| 请求头总大小 | 服务器通常 8KB 左右 | Cookie 过多会导致 431 或请求被拒 |

```js
// 跨域请求必须显式带上凭证，否则浏览器不会发送跨站 Cookie
await fetch('https://api.example.com/me', {
  credentials: 'include',
  headers: { 'Content-Type': 'application/json' },
});
```

**面试怎么答：** 先明确 Cookie 是「HTTP 状态」而非普通存储，再按「写入方式 → 六个核心属性 → 发送判定 → 作用域覆盖 → 容量限制」讲。加分点：`SameSite=Lax` 已是默认、`None` 必须 `Secure`、`__Host-` 前缀、端口不影响 Cookie、删除要三要素一致。

**易错点：**

- 认为 `HttpOnly` 能完全防 XSS；它只阻止 JS 读 Cookie，XSS 仍可发起同站请求。
- 设置 `SameSite=None` 却忘记 `Secure`，浏览器会直接丢弃该 Cookie。
- 删除 Cookie 时只改 `Max-Age=0`，但 `Path` 或 `Domain` 与写入时不一致，导致删不掉。
- 认为跨域 `fetch` 会自动带 Cookie；默认 `credentials` 是 `same-origin`。
- 把 `Domain` 写成 `localhost` 或公共后缀，导致 Cookie 被拒绝。
- 认为 Cookie 加密后前端就安全；Cookie 内容对客户端可见（除非 HttpOnly），加密不能替代传输层安全。

## 3. localStorage 与 sessionStorage 的细节与坑（同步阻塞、容量、跨标签页）

**结论：** 两者都是**同源的同步键值存储**，只能存字符串，容量约 5MB。localStorage 的生命周期是「直到主动清除」，sessionStorage 的生命周期是「单个标签页会话」。它们最大的价值是简单，最大的问题是**同步 API 占主线程**、**无过期与事务**、**可被 XSS 读取**。

**核心差异：**

| 维度 | localStorage | sessionStorage |
| --- | --- | --- |
| 生命周期 | 永久，除非用户或代码清除 | 标签页关闭即销毁，刷新与恢复页面仍在 |
| 作用域 | 同源的所有标签页、窗口共享 | 同源 + 单个标签页；新标签页有独立副本 |
| 复制行为 | 无 | 由 `window.open` 打开的新标签页会复制一份初始数据 |
| 容量 | 约 5MB/源 | 约 5MB/源（与 localStorage 独立计算） |
| 跨标签页事件 | `storage` 事件 | 不触发 `storage` 事件（因为不共享） |
| 典型用途 | 配置、主题、轻量缓存 | 表单草稿、多步流程的临时状态 |

**同步阻塞到底有多严重：** 读写本身是同步的，但真正的成本在**序列化与反序列化**。存一个 2MB 的对象，`JSON.stringify` 加写入可能占用主线程 30 至 100 毫秒；读出来再 `JSON.parse` 同样要花时间。主线程被占住期间，渲染、输入响应、动画全部排队。

```js
// 反例：每次滚动都读写大对象，造成明显掉帧
window.addEventListener('scroll', () => {
  const draft = JSON.parse(localStorage.getItem('draft') || '{}');
  draft.scrollTop = window.scrollY;
  localStorage.setItem('draft', JSON.stringify(draft));
});

// 正例：节流 + 只存必要字段，或改用 IndexedDB
const saveDraft = throttle((value) => {
  localStorage.setItem('draft', JSON.stringify({ title: value.title }));
}, 500);
```

**容量与异常：** 超出配额时抛出 `DOMException`，名称是 `QuotaExceededError`。不同浏览器对「字符」的计费方式不同，UTF-16 环境下中文占 2 字节，所以「5MB」并不意味着能存 500 万个汉字。写入前应做 try/catch，并给出降级方案。

```js
function safeSet(key, value) {
  try {
    localStorage.setItem(key, value);
    return true;
  } catch (err) {
    if (err.name === 'QuotaExceededError' || err.code === 22) {
      // 清理旧数据或提示用户
      localStorage.removeItem('old-cache');
    }
    return false;
  }
}
```

**storage 事件的细节（跨标签页同步的基础）：**

| 特性 | 说明 |
| --- | --- |
| 触发范围 | **同源的其他标签页/窗口**，当前标签页不触发 |
| 触发条件 | `setItem`、`removeItem`、`clear` 导致值真正变化时；写入相同值不触发 |
| 事件字段 | `key`、`oldValue`、`newValue`、`url`、`storageArea` |
| `clear()` | `key`、`oldValue`、`newValue` 均为 `null` |
| 新键 | `oldValue` 为 `null` |
| 删除键 | `newValue` 为 `null` |
| 触发时机 | 在写入操作完成后异步派发，不保证实时顺序用于强一致场景 |

```js
// 跨标签页同步登录态或主题
window.addEventListener('storage', (event) => {
  if (event.key === 'theme' && event.newValue) {
    document.documentElement.dataset.theme = event.newValue;
  }
  if (event.key === 'logout') {
    location.reload();
  }
});
```

**sessionStorage 的坑：**

- 刷新页面不丢，但**关闭标签页就丢**；浏览器「恢复上次会话」时可能恢复。
- `window.open` 打开的新标签页会复制 opener 的 sessionStorage，之后各写各的。
- 同源的两个标签页之间**不共享**，所以不能用它做跨标签页通信。
- 浏览器为了性能可能延迟恢复 sessionStorage，页面刚加载时读到空值是正常现象。

**其他坑：** 只能存字符串，`Date`、`Map` 会在序列化中变形；没有过期与事务，需要自己在值里存 `expireAt` 或合并成单 key；隐私模式下可能写入即抛异常；第三方 iframe 中的存储可能按顶层站点分区。

**面试怎么答：** 先给「同源同步字符串存储」的定位，再用一张表对比生命周期与作用域，重点讲三个点：同步 API 的序列化开销、`storage` 事件只在其他标签页触发、sessionStorage 的标签页隔离。最后补配额异常与 XSS 风险，体现工程意识。

**易错点：**

- 认为 sessionStorage 跨标签页共享；它恰恰是最标签页私有的。
- 认为 `storage` 事件会在当前标签页触发，从而写出重复处理逻辑。
- 认为 localStorage 有 5MB 就一定够用，忽略 UTF-16 计费与序列化膨胀。
- 把 token 放 localStorage 图方便，忽略 XSS 可直接读取。
- 认为 `clear()` 只清当前 key；它会清空整个源的所有 localStorage。

## 4. IndexedDB 的使用与封装（事务、游标、索引、版本升级）

**结论：** IndexedDB 是浏览器内置的**异步、事务型、面向对象**的数据库：数据以「对象仓库」为单位存储，支持主键、索引、游标与范围查询，能存结构化克隆支持的任何值（包括 `Blob`、`File`、`ArrayBuffer`）。它适合**大量数据、离线优先、需要按字段检索**的场景，不适合存几十字节的小配置。

**核心概念：**

| 概念 | 含义 | 对应 API |
| --- | --- | --- |
| database | 一个源下的数据库，有版本号 | `indexedDB.open(name, version)` |
| objectStore | 类似「表」，存放记录 | `db.createObjectStore()` |
| keyPath | 记录中作为主键的字段路径 | `{ keyPath: 'id' }` |
| autoIncrement | 自增主键 | `{ autoIncrement: true }` |
| index | 基于字段的辅助索引，可唯一 | `store.createIndex()` |
| transaction | 一组操作的原子单元 | `db.transaction([...], mode)` |
| request | 异步操作句柄，有 `onsuccess`/`onerror` | `store.get()`、`store.put()` |
| cursor | 逐条遍历结果 | `store.openCursor(range, direction)` |
| keyRange | 主键或索引的范围 | `IDBKeyRange.bound()` |

**打开与版本升级：** 版本号只能升不能降。首次创建或版本变化时触发 `onupgradeneeded`，这是唯一能修改对象仓库与索引结构的时机。升级过程中要做「按旧版本逐级迁移」，而不是假设用户总是从 0 开始。

```js
function openDB() {
  return new Promise((resolve, reject) => {
    const request = indexedDB.open('app-db', 3);

    request.onupgradeneeded = (event) => {
      const db = request.result;
      const oldVersion = event.oldVersion;

      if (oldVersion < 1) {
        const users = db.createObjectStore('users', { keyPath: 'id' });
        users.createIndex('by-email', 'email', { unique: true });
      }
      if (oldVersion < 2) {
        const orders = db.createObjectStore('orders', { keyPath: 'id', autoIncrement: true });
        orders.createIndex('by-user', 'userId');
        orders.createIndex('by-created', 'createdAt');
      }
      if (oldVersion < 3) {
        // 给已有仓库补索引
        const tx = request.transaction;
        const users = tx.objectStore('users');
        if (!users.indexNames.contains('by-name')) {
          users.createIndex('by-name', 'name');
        }
      }
    };

    request.onsuccess = () => resolve(request.result);
    request.onerror = () => reject(request.error);
    request.onblocked = () => {
      // 旧版本的连接没有关闭，升级被阻塞
      console.warn('请关闭其他标签页后重试');
    };
  });
}
```

**事务的生命周期（最容易踩的坑）：** 事务在「没有新的请求被加入且微任务队列清空」时自动提交。也就是说，**在事务里 `await` 一个非 IndexedDB 的 Promise（如 `fetch`、`setTimeout`）会导致事务提前提交**，后续操作报 `TransactionInactiveError`。

```js
// 错误：await fetch 会让事务提交
const tx = db.transaction('users', 'readwrite');
const store = tx.objectStore('users');
const user = await fetch('/api/user/1').then((r) => r.json());
await store.put(user); // 可能抛 TransactionInactiveError

// 正确：先取数据，再开事务
const user = await fetch('/api/user/1').then((r) => r.json());
const tx = db.transaction('users', 'readwrite');
await requestToPromise(tx.objectStore('users').put(user));
await transactionDone(tx);
```

**Promise 封装：** 原生 API 是事件式的，工程里通常封装成 Promise。关键是**不要吞掉事务的 `onerror`/`onabort`**，否则调用方无法感知失败。

```js
function requestToPromise(request) {
  return new Promise((resolve, reject) => {
    request.onsuccess = () => resolve(request.result);
    request.onerror = () => reject(request.error);
  });
}

function transactionDone(tx) {
  return new Promise((resolve, reject) => {
    tx.oncomplete = () => resolve();
    tx.onerror = () => reject(tx.error);
    tx.onabort = () => reject(tx.error || new DOMException('Aborted', 'AbortError'));
  });
}

async function addUser(db, user) {
  const tx = db.transaction('users', 'readwrite');
  const store = tx.objectStore('users');
  const id = await requestToPromise(store.add(user));
  await transactionDone(tx);
  return id;
}
```

**索引与范围查询：**

```js
// 按索引取单条
async function findByEmail(db, email) {
  const tx = db.transaction('users', 'readonly');
  const index = tx.objectStore('users').index('by-email');
  return requestToPromise(index.get(email));
}
```

**游标遍历：** 适合大数据量的分批处理，避免一次性 `getAll` 占内存。

```js
async function iterateAll(db) {
  const tx = db.transaction('orders', 'readonly');
  const store = tx.objectStore('orders');
  const request = store.openCursor(null, 'next');

  await new Promise((resolve, reject) => {
    request.onerror = () => reject(request.error);
    request.onsuccess = () => {
      const cursor = request.result;
      if (!cursor) return resolve();
      if (cursor.value.status === 'pending') {
        cursor.update({ ...cursor.value, status: 'archived' });
      }
      cursor.continue();
    };
  });
}
```

**兼容与清理：** 用户可在浏览器设置里清除站点数据，浏览器也会在配额紧张时清理整个源。Safari 的 ITP 对长期无交互站点有更激进的清除策略。重要数据应配合 `navigator.storage.persist()` 并做服务端同步。

**面试怎么答：** 按「为什么需要（异步、大容量、可索引）→ 核心对象模型 → 打开与升级 → 事务自动提交的坑 → 游标与索引 → 封装与降级」讲。最能体现深度的是两点：事务在 `await` 非 IDB Promise 后会提前提交；版本升级必须逐级兼容旧用户。

**易错点：**

- 在事务中 `await fetch`，导致事务提前提交。
- 忘记监听 `onblocked`，旧标签页占着连接时升级永远不完成。
- 认为 IndexedDB 是同步的；它全部是异步事件。
- 用 `getAll` 拉全表再过滤，数据量大时内存爆掉，应该用索引与游标。
- 认为删除数据库会立刻成功；有连接未关闭时会阻塞，需要监听 `versionchange` 并 `db.close()`。
- 存了函数或 DOM 节点；结构化克隆不支持，会抛 `DataCloneError`。

## 5. Cache API 与 Service Worker 离线缓存

**结论：** CacheStorage 是**以 `Request` 为键、`Response` 为值**的缓存仓库，Service Worker 是**位于页面与网络之间的可编程代理**。两者配合，可以在 `fetch` 事件里按策略返回缓存，实现离线访问、弱网加速与资源版本控制。它和 HTTP 缓存不是替代关系，而是「应用层可控的缓存层」。

**Service Worker 的生命周期：**

```text
register() → install（预缓存，失败则安装失败）
  → installed / waiting（已有旧 SW 在控制页面时进入等待）
  → activate（清理旧缓存、接管客户端）
  → fetch / message / sync / push（运行时）
  → 更新：浏览器定期检查脚本字节变化，重新走 install
```

| 阶段 | 能做什么 | 注意 |
| --- | --- | --- |
| `install` | 预缓存核心资源 | `cache.addAll` 任一失败则整体失败 |
| `waiting` | 等待旧页面关闭 | `skipWaiting()` 可强制跳过，但要处理页面版本错配 |
| `activate` | 删除旧版本缓存 | 需 `clients.claim()` 才能立即控制未受控页面 |
| `fetch` | 拦截同源与可控跨域请求 | 只对 scope 内、且已被控制的页面生效 |

```js
// main.js：注册 Service Worker
if ('serviceWorker' in navigator) {
  window.addEventListener('load', async () => {
    const registration = await navigator.serviceWorker.register('/sw.js', { scope: '/' });
    console.log('SW 注册成功：', registration.scope);
  });
}
```

```js
// sw.js：预缓存 + 清理旧版本 + 三种策略
const VERSION = 'v3';
const STATIC_CACHE = `static-${VERSION}`;
const RUNTIME_CACHE = `runtime-${VERSION}`;
const PRECACHE_URLS = ['/', '/index.html', '/assets/app.css', '/assets/app.js'];

self.addEventListener('install', (event) => {
  event.waitUntil(
    caches.open(STATIC_CACHE).then((cache) => cache.addAll(PRECACHE_URLS))
  );
  self.skipWaiting();
});

self.addEventListener('activate', (event) => {
  event.waitUntil(
    caches.keys().then((keys) =>
      Promise.all(
        keys
          .filter((key) => key !== STATIC_CACHE && key !== RUNTIME_CACHE)
          .map((key) => caches.delete(key))
      )
    ).then(() => self.clients.claim())
  );
});

self.addEventListener('fetch', (event) => {
  const { request } = event;
  if (request.method !== 'GET') return;

  const url = new URL(request.url);

  // 导航请求：网络优先，失败回退离线页
  if (request.mode === 'navigate') {
    event.respondWith(
      fetch(request).catch(() => caches.match('/index.html'))
    );
    return;
  }

  // 带 hash 的静态资源：缓存优先
  if (url.pathname.startsWith('/assets/')) {
    event.respondWith(
      caches.match(request).then((cached) => cached || fetchAndCache(request))
    );
    return;
  }
});

async function fetchAndCache(request) {
  const response = await fetch(request);
  if (response.ok) {
    const cache = await caches.open(RUNTIME_CACHE);
    cache.put(request, response.clone());
  }
  return response;
}
```

**四种常用缓存策略：**

| 策略 | 流程 | 适用 | 代价 |
| --- | --- | --- | --- |
| Cache First | 缓存优先，未命中再网络 | 带 hash 的静态资源、字体 | 更新不及时，需要换 URL 或版本 |
| Network First | 网络优先，失败回退缓存 | 导航页、时效性接口 | 弱网首屏慢 |
| Stale-While-Revalidate | 立刻返回缓存，同时后台更新 | 头像、列表、非关键数据 | 可能返回旧数据 |
| Network Only / Cache Only | 只走一边 | 支付、实时数据 / 离线包 | 无兜底 |

**Cache API 的关键细节：**

| 细节 | 说明 |
| --- | --- |
| 可用环境 | 安全上下文（HTTPS/localhost）；Window 与 Worker 都可用 |
| 键值类型 | 只能存 `Request`/`Response`，不能存 JS 对象 |
| 请求方法 | 只能缓存 `GET`；`POST` 等无法命中 |
| `addAll` | 原子性差：任一请求失败，整个调用 reject，但已成功的条目可能已写入 |
| 匹配 | `cache.match(request, { ignoreSearch: true })` 可忽略查询串 |
| 响应克隆 | 一个 `Response` body 只能读一次，缓存与返回必须 `clone()` |
| 跨域响应 | `no-cors` 响应是 opaque，状态码为 0，无法判断成功与否，且体积被填充 |
| 存储位置 | 与 IndexedDB 共享源配额；可能被浏览器清理 |

**版本化与更新：** 常见做法是「缓存名带版本号 + activate 时删除旧缓存」。若使用 `skipWaiting()`，旧页面可能仍在请求旧资源，新 SW 却返回新资源，出现「HTML 与 JS 版本错配」；稳妥方案是提示刷新，或让 HTML 网络优先、静态资源带 hash。SPA 还要单独处理 `mode === 'navigate'`，回退到 `index.html` 让前端路由接管。

**面试怎么答：** 先区分「HTTP 缓存由响应头控制、对前端不透明」与「Cache API 由代码控制、可编程返回」，再讲 SW 生命周期与四种策略。加分点：`Response` 只能读一次要 `clone`、`addAll` 的失败语义、`skipWaiting` 带来的版本错配、`no-cors` 的 opaque 响应。

**易错点：**

- 在 `fetch` 里 `respondWith` 一个已经被消费过的 `Response`，报 `body already used`。
- 缓存了 `POST` 请求或带用户身份的接口，造成数据串号或隐私泄露。
- 只注册 SW 不做更新策略，用户长期停留在旧版本。
- 认为 SW 能拦截所有请求；它只控制 scope 内、已被激活控制的页面。
- 在 HTTP 环境下调试 SW，注册直接失败，误以为是代码问题。
- 把大文件全塞进 CacheStorage，忽略配额与清理策略。

## 6. 同源策略到底限制了什么

**结论：** 同源策略（Same-Origin Policy）是浏览器最基础的安全边界，源由**协议 + 主机 + 端口**三元组决定。它限制的是**跨源读取**（读 DOM、读响应、读存储、读画布像素），而**不限制跨源发送请求、嵌入资源、跳转导航**。很多安全问题的根源，正是「请求能发出去，但响应读不到」这个不对称。

**源的判定：**

| URL | 与 `https://example.com/a` 是否同源 | 原因 |
| --- | --- | --- |
| `https://example.com/b` | 是 | 协议、主机、端口一致 |
| `https://example.com:443/b` | 是 | 443 是 https 默认端口 |
| `http://example.com/b` | 否 | 协议不同 |
| `https://api.example.com/b` | 否 | 主机不同 |
| `https://example.com:8443/b` | 否 | 端口不同 |
| `https://example.com.evil.com` | 否 | 主机是 suffix 攻击 |
| `https://192.168.1.10/b` | 否 | IP 与域名不同 |

**被限制的能力：**

| 能力 | 限制表现 |
| --- | --- |
| 读取跨源 `fetch`/`XHR` 响应 | 默认被 CORS 拦截，拿不到响应体 |
| 访问跨源 iframe 的 DOM | `contentWindow.document` 抛 `SecurityError` |
| 读取跨源窗口的 `location` | 只能写 `href`，读 `href` 被禁止 |
| 读取跨源 `localStorage`/IndexedDB | 存储本身按源隔离，根本无法访问 |
| Canvas 读取跨源图片像素 | 画布被「污染」，`getImageData` 抛异常 |
| 读取跨源 CSS 规则 | `cssRules` 不可读 |
| 跨源 Cookie | 由 Cookie 自己的 Domain/SameSite 规则决定，不完全等同同源 |

**不被限制的能力：**

| 能力 | 说明 |
| --- | --- |
| 嵌入 `<script>`、`<img>`、`<link>`、`<video>`、`<iframe>` | 资源可以跨源加载 |
| 提交表单到跨源地址 | 请求能发出，响应页面归目标源 |
| 顶层导航与链接跳转 | 可以把用户带到任意站点 |
| 写 `window.location.href` | 可以导航，但不能读回 |
| `postMessage` | 可以跨源通信，安全性由接收方校验 `origin` |
| WebSocket 连接 | 不受同源策略限制，靠服务端校验 `Origin` |
| 发送简单跨源请求 | 请求会到达服务端，只是响应可能读不到 |

**关键区分：同源策略不防 CSRF。** 因为表单、图片、`<script>` 都能发起跨源请求，Cookie 也可能被自动带上（取决于 SameSite）。同源策略保护的是「攻击者读不到你的数据」，而不是「攻击者不能替你发请求」。CSRF 的防御必须靠 CSRF Token、SameSite、Origin 校验。

**源与站点（site）不是一回事：** 站点按 eTLD+1 划分，`a.example.com` 与 `b.example.com` 是**同站不同源**。Cookie 的 `SameSite` 按站点判断，所以同站跨子域仍会发送；而 `fetch` 的 CORS 按源判断，所以同站跨子域仍需要 CORS。

**放宽同源的几种机制：**

| 机制 | 放宽的内容 | 风险 |
| --- | --- | --- |
| CORS | 允许跨源读取响应 | 配置过宽会泄露数据 |
| `document.domain` | 允许同主域的不同子域互访 | 已废弃，且会削弱隔离 |
| `postMessage` | 显式的跨源消息通道 | 校验不严会泄露或注入 |
| 代理 | 让请求变成同源 | 代理本身可能成为 SSRF 入口 |
| `Cross-Origin-Isolation` | 开启 `SharedArrayBuffer` 等能力 | 需要 COOP/COEP 配套 |

```js
// 跨源读取会被浏览器拦截，错误信息由 CORS 决定
try {
  const res = await fetch('https://api.other.com/data');
  const data = await res.json();
} catch (err) {
  console.error('跨源读取失败', err); // TypeError: Failed to fetch
}

// 跨源 iframe 的 DOM 访问会被拒绝
const frame = document.querySelector('iframe');
try {
  console.log(frame.contentWindow.document.title);
} catch (err) {
  console.error('SecurityError', err);
}
```

**面试怎么答：** 先给「协议 + 主机 + 端口」的定义，再明确「限制读、不限制写/发/嵌入」这条主线，用表格列出被限制与被允许的能力。加分点：同源策略不防 CSRF、源与站点的区别、`document.domain` 已废弃、Canvas 污染与 `postMessage` 是显式放宽。

**易错点：**

- 认为跨域请求「没有发出去」；请求通常已经到达服务端，只是响应被浏览器拦截。
- 认为同源策略能防 CSRF；它防不住跨源发请求。
- 把 `example.com` 与 `api.example.com` 当成同源；子域不同就是跨源。
- 忽略端口；`localhost:3000` 与 `localhost:8080` 是跨源。
- 认为 `http` 与 `https` 只是「安全与否」，在浏览器眼里它们是不同的源。
- 用 `document.domain` 做跨子域通信，忽略它已被废弃且破坏隔离。

## 7. 跨域解决方案总览（CORS/JSONP/代理/postMessage/WebSocket）

**结论：** 跨域的本质是「如何在同源策略下安全地拿到另一个源的数据」。方案可以归为四类：**服务端授权**（CORS）、**同源中转**（开发代理、网关反向代理）、**历史协议 hack**（JSONP）、**显式消息通道**（postMessage、WebSocket）。选型取决于「谁改得动」：能改服务端优先 CORS，只能改前端就用代理，跨窗口协作用 postMessage。

**方案对比：**

| 方案 | 原理 | 适用场景 | 限制 | 安全注意 |
| --- | --- | --- | --- | --- |
| CORS | 服务端返回 `Access-Control-Allow-*` 响应头 | 前后端分离、开放 API | 需要服务端配合；复杂请求触发预检 | 不要反射任意 Origin，不要与凭证通配 |
| JSONP | `<script>` 不受同源限制，加载返回 JS 回调的接口 | 老旧系统、只支持 GET | 仅 GET、无错误码、易受 XSS | 回调名要校验，响应必须是可信 JSON |
| 开发代理 | 开发服务器把 `/api` 转发到后端 | 本地开发 | 仅开发环境；生产需网关 | 代理不要开放任意目标，防 SSRF |
| 反向代理 / 网关 | 前后端同域，由 Nginx 转发 | 生产部署 | 需要运维配置 | 路径与头部要清洗 |
| postMessage | 跨窗口/iframe 显式消息 | 父子页面、微前端、OAuth 弹窗 | 需要双方约定协议 | 必须校验 `origin` 与 `source` |
| WebSocket | 独立协议，握手后双向通信 | 实时推送 | 不受同源限制，但需服务端校验 `Origin` | 鉴权不能只靠 Cookie |
| 修改 `document.domain` | 同主域子域互访 | 旧系统 | 已废弃，破坏隔离 | 不推荐 |

**JSONP 的最小实现与缺陷：**

```js
function jsonp(url, callbackName) {
  return new Promise((resolve, reject) => {
    const script = document.createElement('script');
    window[callbackName] = resolve;
    script.onerror = () => reject(new Error('network error'));
    script.src = `${url}?callback=${callbackName}`;
    document.head.appendChild(script);
  });
}
```

JSONP 的问题很明确：只能 GET、无法区分 HTTP 错误、回调名可被注入、响应被当作脚本执行（等于把数据源当成代码源）。现代项目不应再新增 JSONP。

**CORS 的最小配置（服务端）：**

```js
// Express

app.use(cors({
  origin: ['https://app.example.com'],
  methods: ['GET', 'POST', 'PUT', 'DELETE'],
  allowedHeaders: ['Content-Type', 'Authorization', 'X-Request-Id'],
  credentials: true,
  maxAge: 600,
}));
```

```nginx
# Nginx：同域反向代理，前端请求 /api 即可
location /api/ {
    proxy_pass https://backend.internal/;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
}
```

**postMessage 的最小用法：**

```js

// iframe 接收并校验来源
window.addEventListener('message', (event) => {

});
```

**WebSocket 的跨域问题：** 浏览器不会用同源策略阻止 WebSocket 连接，但握手请求会带 `Origin` 头，服务端必须自行校验。只靠 Cookie 鉴权时，恶意页面可以诱导用户浏览器建立连接（CSWSH），所以要在握手阶段校验 `Origin` 并使用不可预测的 token。

**选型路径：**

```text
能改服务端？
  ├─ 是 → 需要读响应 → CORS（带凭证时严格白名单）
  │        需要实时双向 → WebSocket / SSE
  └─ 否 → 开发阶段 → 本地代理
           生产阶段 → 同域网关反向代理
跨窗口/iframe？
  → postMessage（严格校验 origin）
只支持 GET 的老接口？
  → JSONP（仅兼容，不作为新方案）
```

**面试怎么答：** 不要只背「CORS、JSONP、代理」三个词，按「服务端授权、同源中转、协议 hack、消息通道」四类归纳，再给选型条件。重点说明：CORS 是标准且唯一能读响应的方案；JSONP 只适合遗留系统；代理解决的是「请求同源化」，不是浏览器安全机制。

**易错点：**

- 认为跨域是「前端配置一下就行」；CORS 必须服务端返回响应头。
- 用 `Access-Control-Allow-Origin: *` 又开 `credentials`，浏览器直接拒绝。
- 开发代理能跑通就以为生产也能跑通；生产需要网关配置。
- JSONP 用来传敏感数据；它会把响应当脚本执行。
- WebSocket 不校验 `Origin`，遭受跨站 WebSocket 劫持。
- 用 `postMessage` 不校验 `event.origin`，任意站点都能注入消息。

## 8. CORS 详解（简单请求、预检、凭证、响应头、常见报错）

**结论：** CORS 是浏览器实现的**跨源读取授权协议**：浏览器自动加 `Origin` 头，服务端用 `Access-Control-Allow-*` 响应头声明是否允许。请求分「简单请求」与「需要预检的请求」；带 Cookie 时必须同时满足「具体 Origin + `Allow-Credentials: true` + 前端 `credentials: include`」。CORS 只约束浏览器，不约束服务端之间的调用。

**简单请求的三个条件（必须同时满足）：**

| 条件 | 允许值 |
| --- | --- |
| 方法 | `GET`、`HEAD`、`POST` |
| 请求头 | 只能是 CORS 安全列表头：`Accept`、`Accept-Language`、`Content-Language`、`Content-Type`（受限值）、`Range` 等 |
| `Content-Type` | 只能是 `text/plain`、`multipart/form-data`、`application/x-www-form-urlencoded` |
| 其他 | 没有 `ReadableStream` 请求体，没有事件监听器附加到 `XMLHttpRequestUpload` |

注意：`application/json` **不属于**简单请求，会触发预检；带 `Authorization` 也会触发预检。

**预检流程：**

```text
浏览器判断需要预检
  → OPTIONS /resource
      Origin: https://app.example.com
      Access-Control-Request-Method: PUT
      Access-Control-Request-Headers: content-type, authorization
  ← 204 / 200
      Access-Control-Allow-Origin: https://app.example.com
      Access-Control-Allow-Methods: PUT, POST, GET
      Access-Control-Allow-Headers: Content-Type, Authorization
      Access-Control-Allow-Credentials: true
      Access-Control-Max-Age: 600
  → 预检通过后，才发送真正的 PUT 请求
  → 真正的响应仍需返回 Access-Control-Allow-Origin
```

**请求头与响应头：**

| 头 | 方向 | 作用 |
| --- | --- | --- |
| `Origin` | 请求 | 浏览器自动添加，页面无法伪造 |
| `Access-Control-Request-Method` | 预检请求 | 声明真正请求要用的方法 |
| `Access-Control-Request-Headers` | 预检请求 | 声明真正请求要用的自定义头 |
| `Access-Control-Allow-Origin` | 响应 | 允许的源，必须是具体值或 `*` |
| `Access-Control-Allow-Methods` | 预检响应 | 允许的方法 |
| `Access-Control-Allow-Headers` | 预检响应 | 允许的请求头 |
| `Access-Control-Allow-Credentials` | 响应 | 是否允许携带凭证，只能是 `true` |
| `Access-Control-Expose-Headers` | 响应 | 允许 JS 读取的响应头（默认只有安全列表头） |
| `Access-Control-Max-Age` | 预检响应 | 预检结果缓存秒数 |
| `Vary: Origin` | 响应 | 告诉缓存按 Origin 区分，避免缓存串源 |

**凭证模式的硬性规则：**

| 规则 | 说明 |
| --- | --- |
| 前端 | `fetch(url, { credentials: 'include' })` 或 `xhr.withCredentials = true` |
| `Allow-Origin` | 必须是**具体源**，不能是 `*` |
| `Allow-Credentials` | 必须是 `true` |
| Cookie | 跨站场景需要 `SameSite=None; Secure` |
| `Allow-Headers` | 不能是 `*`（凭证模式下通配无效） |
| `Expose-Headers` | 不能是 `*` |

**完整配置示例：**

```js
// Express：严格白名单 + 凭证
const ALLOWED = new Set(['https://app.example.com', 'https://admin.example.com']);

app.use((req, res, next) => {
  const origin = req.headers.origin;
  if (ALLOWED.has(origin)) {
    res.setHeader('Access-Control-Allow-Origin', origin);
    res.setHeader('Access-Control-Allow-Credentials', 'true');
    res.setHeader('Vary', 'Origin');
  }
  if (req.method === 'OPTIONS') {
    res.setHeader('Access-Control-Allow-Methods', 'GET,POST,PUT,DELETE,OPTIONS');
    res.setHeader('Access-Control-Allow-Headers', 'Content-Type,Authorization,X-Request-Id');
    res.setHeader('Access-Control-Max-Age', '600');
    return res.status(204).end();
  }
  next();
});
```

```js
// 前端：带 Cookie 的跨源请求
const res = await fetch('https://api.example.com/orders', {
  method: 'POST',
  credentials: 'include',
  headers: {
    'Content-Type': 'application/json',
    Authorization: `Bearer ${token}`,
  },
  body: JSON.stringify({ page: 1 }),
});
```

**常见报错与定位：**

| 报错 | 原因 | 修复 |
| --- | --- | --- |
| `No 'Access-Control-Allow-Origin' header is present` | 响应缺少 ACAO，或源不在白名单 | 服务端返回正确 ACAO |
| `The value of the 'Access-Control-Allow-Origin' header must not be '*' when credentials mode is 'include'` | 凭证模式用了通配 | 返回具体 Origin |
| `Request header field authorization is not allowed by Access-Control-Allow-Headers` | 预检未允许该头 | 补充 `Allow-Headers` |
| `Method PUT is not allowed by Access-Control-Allow-Methods` | 预检未允许方法 | 补充 `Allow-Methods` |
| `Response to preflight request doesn't pass access control check` | 预检本身失败（404/401/500） | 确保 OPTIONS 路由可访问且无需鉴权 |
| `Redirect is not allowed for a preflight request` | 预检遇到 3xx 重定向 | 预检直接返回 2xx |
| 浏览器控制台报错但 Network 显示 200 | 请求成功、响应被拦截 | 看响应头，不看状态码 |

**调试方法：** 在 Network 面板筛选 `OPTIONS` 检查预检请求与响应头，也可用 `curl -X OPTIONS -H "Origin: ..." -H "Access-Control-Request-Method: PUT" -i` 直接验证服务端；浏览器会缓存预检结果，改配置后要禁用缓存或换端口。另注意预检不带 Cookie（OPTIONS 路由不能要求登录）、302 重定向在预检中不被允许、CDN 层也要返回 CORS 头并配 `Vary: Origin`。

**面试怎么答：** 按「简单请求条件 → 预检流程 → 凭证规则 → 响应头 → 常见报错」这条线讲。加分点：`application/json` 一定触发预检、OPTIONS 不能要求鉴权、凭证模式不能用通配、实际响应也要 ACAO、`Vary: Origin` 防缓存串源。

**易错点：**

- 认为 CORS 是服务端安全机制；它只决定浏览器是否把响应交给 JS。
- 只给预检加 CORS 头，忘了实际响应也要加。
- 用 `*` 加 `credentials`，浏览器直接拒绝，且错误信息容易误导。
- 把 401/500 当成「CORS 配置问题」；预检失败往往是路由或鉴权拦截了 OPTIONS。
- 忘记 `Expose-Headers`，前端拿不到分页总数等自定义头。
- 在网关层重复添加 `Access-Control-Allow-Origin`，产生多个值导致浏览器拒绝。

## 9. 跨标签页通信（storage 事件、BroadcastChannel、SharedWorker）

**结论：** 同源标签页之间没有直接的 JS 对象共享，必须借助浏览器提供的中介：`storage` 事件、`BroadcastChannel`、`SharedWorker`、`Service Worker`、`window.postMessage`（配合 `opener`/`parent`）。其中 `BroadcastChannel` 是首选，`storage` 事件兼容性最好但只能传字符串，`SharedWorker` 适合需要共享状态或单飞请求的场景。

**方案对比：**

| 方案 | 通信范围 | 数据类型 | 实时性 | 生命周期 | 兼容性 | 适用 |
| --- | --- | --- | --- | --- | --- | --- |
| `storage` 事件 | 同源其他标签页/窗口 | 字符串（存 localStorage） | 异步，通常很快 | 无额外进程 | 极好 | 简单状态同步、兜底方案 |
| `BroadcastChannel` | 同源标签页、iframe、Worker | 结构化克隆（对象、`Blob` 等） | 快 | 随页面 | 现代浏览器，Safari 15.4+ | 首选的消息总线 |
| `SharedWorker` | 同源所有页面 | `postMessage` | 快 | 有连接就存活 | Safari 支持较晚 | 共享状态、单飞请求 |
| `Service Worker` | 其控制的所有页面 | `postMessage` | 快，但可能被终止 | 事件驱动，可休眠 | 现代浏览器 | 离线、消息中转、推送 |
| `postMessage` + `opener` | 有引用关系的窗口 | 结构化克隆 | 快 | 随窗口 | 极好 | 弹窗、父子页面 |
| Cookie 轮询 | 同源标签页 | 字符串 | 差（轮询间隔） | 随 Cookie | 极好 | 极旧浏览器兜底 |

**storage 事件：**

```js
// 发送方：写入 localStorage 触发其他标签页的 storage 事件
localStorage.setItem('app:event', JSON.stringify({
  type: 'logout',
  at: Date.now(),
  id: crypto.randomUUID(),
}));

// 接收方：注意当前标签页不会收到自己写入触发的事件
window.addEventListener('storage', (event) => {
  if (event.key !== 'app:event' || !event.newValue) return;
  const payload = JSON.parse(event.newValue);
  if (payload.type === 'logout') {
    location.href = '/login';
  }
});
```

细节：写入相同值不会触发；`clear()` 的事件里 `key` 为 `null`；事件在**其他**同源上下文派发，当前标签页要自己处理本地状态；`storageArea` 可用于区分 localStorage 与 sessionStorage（sessionStorage 不跨标签页，实际很少用）。

**BroadcastChannel：**

```js
// 任意同源标签页
const channel = new BroadcastChannel('app-events');

channel.onmessage = (event) => {
  const { type, payload } = event.data;
  if (type === 'theme-change') {
    document.documentElement.dataset.theme = payload.theme;
  }
};

channel.postMessage({ type: 'theme-change', payload: { theme: 'dark' } });

// 页面卸载时关闭，避免泄漏
window.addEventListener('pagehide', () => channel.close());
```

`BroadcastChannel` 使用结构化克隆，可以直接传对象；它**不会把消息回送给发送它的那个 channel 实例**，但同一标签页里另一个同名 channel 实例可以收到。它不能跨源，也不支持跨浏览器进程之外的系统。

**SharedWorker：**

```js
// shared-worker.js：所有同源页面共享同一个实例
const ports = new Set();
let state = { count: 0 };

self.onconnect = (event) => {
  const port = event.ports[0];
  ports.add(port);

  port.onmessage = (e) => {
    if (e.data.type === 'increment') {
      state.count += 1;
      ports.forEach((p) => p.postMessage({ type: 'state', state }));
    }
    if (e.data.type === 'get') {
      port.postMessage({ type: 'state', state });
    }
  };

  port.start();
};
```

```js
// 页面侧
const worker = new SharedWorker('/shared-worker.js');
worker.port.onmessage = (event) => {
  if (event.data.type === 'state') render(event.data.state);
};
worker.port.postMessage({ type: 'get' });
```

SharedWorker 的优势是「一个实例服务多个页面」，适合做**单飞请求**（多个标签页同时刷新 token，只发一次）与共享内存状态；缺点是调试麻烦、Safari 支持较晚、页面全部关闭后实例才销毁。

**Service Worker 作为消息中转：** 页面通过 `navigator.serviceWorker.controller.postMessage` 发给 SW，SW 再用 `self.clients.matchAll()` 广播给所有受控页面。但 SW 随时可能被终止，适合做广播与离线队列，不适合保存关键状态。

**面试怎么答：** 先说明「同源页面不共享 JS 运行时」，再列中介方案并对比数据类型、实时性、生命周期。重点讲 `storage` 事件的两个反直觉点（当前页不触发、只能传字符串），以及 `BroadcastChannel` 的结构化克隆与同源限制。最后给出「优先 BroadcastChannel、兜底 storage、共享状态用 SharedWorker」的选型。

**易错点：**

- 用 `storage` 事件做当前标签页的状态同步，发现根本不触发。
- 认为 `BroadcastChannel` 可以跨源；它严格限定同源。
- 在 `pagehide` 里忘记 `close()`，长时间运行后 channel 泄漏。
- 把 SharedWorker 当常驻数据库；页面全部关闭后它会被销毁。
- 依赖 SW 保存内存状态；SW 随时可能被终止。

## 10. Web Worker 与 Shared Worker、Service Worker 的区别

**结论：** 三者都运行在**独立于主线程的 Worker 全局环境**，都没有 DOM，都通过 `postMessage` 通信，但定位完全不同：Web Worker 是**页面的私有计算线程**，SharedWorker 是**同源页面共享的后台线程**，Service Worker 是**可拦截网络请求的事件驱动代理**。

**核心对比：**

| 维度 | Web Worker | SharedWorker | Service Worker |
| --- | --- | --- | --- |
| 归属 | 创建它的单个页面 | 同源的所有页面 | 注册它的源，控制 scope 内页面 |
| 生命周期 | 随页面销毁，可手动 `terminate()` | 只要还有端口连接就存活 | 事件驱动，空闲可被终止，可被唤醒 |
| DOM 访问 | 无 | 无 | 无 |
| 网络拦截 | 不能 | 不能 | 能（`fetch` 事件） |
| 通信方式 | `postMessage` | `port.postMessage` | `postMessage` + `clients` |
| 主要用途 | CPU 密集计算、数据处理 | 多标签页共享状态、单飞请求 | 离线缓存、推送、后台同步 |
| 安全上下文 | 普通页面即可 | 普通页面即可 | 必须 HTTPS（localhost 例外） |
| 调试 | DevTools 的 Workers 面板 | 较麻烦 | Application → Service Workers |
| 可访问存储 | IndexedDB、Cache、fetch | 同左 | IndexedDB、Cache（无 localStorage） |

**Web Worker：**

```js
// main.js
const worker = new Worker('/heavy-worker.js', { type: 'module' });

worker.postMessage({ type: 'parse', buffer }); // 默认结构化克隆，复制数据
worker.onmessage = (event) => {
  console.log('结果', event.data);
};

// 使用 Transferable 转移所有权，避免大数组复制开销
const buffer = new ArrayBuffer(1024 * 1024 * 64);
worker.postMessage({ type: 'parse', buffer }, [buffer]);
console.log(buffer.byteLength); // 0，已被转移
```

```js
// heavy-worker.js
self.onmessage = async (event) => {
  const { type, buffer } = event.data;
  if (type === 'parse') {
    const result = heavyParse(buffer);
    self.postMessage({ type: 'done', result });
  }
};
```

**SharedWorker：** 见上一题的代码。它的关键区别是「同一脚本、同一源只创建一个实例」，多个页面通过各自的 `port` 连接；因此它可以持有共享状态，也可以做请求合并。页面全部关闭后实例销毁，状态不持久。

**Service Worker：**

```js
// 注册
navigator.serviceWorker.register('/sw.js', { scope: '/' });

// sw.js
self.addEventListener('fetch', (event) => {
  event.respondWith(
    caches.match(event.request).then((cached) => cached || fetch(event.request))
  );
});
```

**能力边界：**

| 限制 | 说明 |
| --- | --- |
| 无 DOM | 不能操作 `document`、`window`、`alert` |
| 无 `localStorage` | Worker 环境不提供同步存储，改用 IndexedDB |
| 脚本同源 | Worker 脚本必须与页面同源（或通过 CORS 与 `importScripts` 受限加载） |
| 结构化克隆 | 传递函数、DOM 节点会抛 `DataCloneError` |
| 传输成本 | 大对象默认复制；`Transferable` 可转移 `ArrayBuffer`、`MessagePort`、`ImageBitmap` |
| 错误隔离 | Worker 内未捕获错误触发 `error` 事件，不会冒泡到页面 |

**选型：** 耗时计算用 Web Worker，跨标签页共享状态用 SharedWorker，离线与请求拦截用 Service Worker；纯广播优先 BroadcastChannel，不必引入 Worker。

**面试怎么答：** 用「私有计算线程 / 共享后台线程 / 网络代理」三个定位区分三者，再对比生命周期、网络拦截能力、安全上下文与通信方式。加分点：Web Worker 默认复制数据、Transferable 可转移所有权、Worker 里没有 `localStorage`、Service Worker 空闲会被终止。

**易错点：**

- 认为 Worker 里能操作 DOM；完全没有 `document`。
- 以为 `postMessage` 是共享内存；默认是结构化克隆的深拷贝。
- 转移 `ArrayBuffer` 后继续在主线程使用它，发现长度变成 0。
- 把 Service Worker 当成常驻后台进程；它随时可能被终止。
- 在 HTTP 页面注册 SW，注册失败。
- 用 SharedWorker 存关键数据，页面全关后状态丢失。

## 11. WebSocket、SSE 与长轮询的对比与选型

**结论：** 三者都是「服务端主动向客户端推送」的方案，但成本与能力不同：**WebSocket** 是全双工、独立协议，适合高频双向交互；**SSE** 是建立在 HTTP 上的单向文本流，自带重连与事件 ID，适合通知、进度、行情；**长轮询** 是兼容性兜底，适合无法升级协议的旧环境。选型要看「方向、频率、协议栈、运维成本」。

**核心对比：**

| 维度 | WebSocket | SSE | 长轮询 |
| --- | --- | --- | --- |
| 通信方向 | 双向 | 服务端 → 客户端 | 客户端请求 → 服务端响应后立即再请求 |
| 底层协议 | HTTP Upgrade 后转为独立协议 | HTTP/1.1 或 HTTP/2 的流式响应 | 普通 HTTP |
| 数据格式 | 文本或二进制帧 | 文本（`text/event-stream`） | 任意 |
| 自动重连 | 无，需要自己实现 | 有，浏览器内置并带 `Last-Event-ID` | 由客户端循环实现 |
| 消息顺序 | 同一连接内有序 | 有序 | 每次请求独立，需业务保证 |
| 代理/防火墙 | 需要支持 Upgrade，部分代理会断连 | 普通 HTTP，兼容性好 | 最好 |
| 浏览器连接数 | 不受 HTTP/1.1 六连接限制 | HTTP/1.1 下受每域六连接限制 | 受连接数限制 |
| 服务端成本 | 长连接、内存与心跳 | 长连接，实现简单 | 频繁建连，开销大 |
| 典型场景 | 聊天、协同编辑、游戏 | 通知、进度、日志、股票 | 兼容兜底、低频任务状态 |

**WebSocket 握手与心跳：**

```http
GET /chat HTTP/1.1
Host: example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13
Origin: https://app.example.com

HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=
```

```js
let ws;
let retry = 0;

function connect() {
  ws = new WebSocket('wss://api.example.com/ws');
  ws.onopen = () => { retry = 0; };
  ws.onmessage = (event) => handle(JSON.parse(event.data));
  ws.onerror = () => ws.close();
  ws.onclose = () => {
    // 指数退避 + 随机抖动，避免大量客户端同时重连
    const delay = Math.min(30000, 1000 * 2 ** retry++);
    setTimeout(connect, delay + Math.random() * 1000);
  };
}
connect();
```

**SSE 服务端与客户端：**

```js
// Express：SSE 响应
app.get('/events', (req, res) => {
  res.setHeader('Content-Type', 'text/event-stream');
  res.setHeader('Cache-Control', 'no-cache');
  res.setHeader('Connection', 'keep-alive');
  res.setHeader('X-Accel-Buffering', 'no'); // 关闭 Nginx 缓冲

  let id = 0;
  const timer = setInterval(() => {
    id += 1;
    res.write(`id: ${id}\n`);
    res.write('event: tick\n');
    res.write(`data: ${JSON.stringify({ id, at: Date.now() })}\n\n`);
  }, 1000);

  req.on('close', () => clearInterval(timer));
});
```

```js
// 浏览器：EventSource 自动重连
const source = new EventSource('/events', { withCredentials: true });

source.addEventListener('tick', (event) => {
  const data = JSON.parse(event.data);
  console.log('收到', data);
});

source.onerror = () => {
  // 浏览器会自动重连，这里只做状态展示
  console.warn('SSE 连接异常，等待重连');
};
```

SSE 的协议格式很严格：`data:` 行组成消息体，空行表示消息结束，`event:` 指定事件名，`id:` 用于断线续传，`retry:` 指定重连间隔。服务端可以通过 `Last-Event-ID` 请求头知道客户端最后收到的事件，从而补发。

**长轮询：**

```js
async function longPoll(cursor) {
  while (!stopped) {
    try {
      const res = await fetch(`/api/events?cursor=${cursor}`, { cache: 'no-store' });
      const { events, nextCursor } = await res.json();
      cursor = nextCursor;
      events.forEach(handleEvent);
    } catch (err) {
      await new Promise((r) => setTimeout(r, 3000));
    }
  }
}
```

长轮询的关键是「服务端在没有数据时挂起请求，直到超时或有数据再返回」，而不是客户端频繁空转；同时要用游标保证不丢消息、不重复消费。

**选型建议：** 聊天、协同编辑、在线游戏选 WebSocket；站内通知、任务进度、构建日志选 SSE；旧浏览器或代理限制严格时用长轮询兜底。

**面试怎么答：** 先给「全双工 / 单向流 / 兼容兜底」三个定位，再用表格对比协议、重连、连接数、代理兼容性。加分点：WebSocket 需要自己做心跳与指数退避重连；SSE 自带 `Last-Event-ID` 续传，但 HTTP/1.1 下受六连接限制、Nginx 要关缓冲；长轮询要用游标保证消息不丢不重。

**易错点：**

- 认为 WebSocket 会自动重连；原生 API 不会，必须自己实现。
- 用 SSE 传二进制；它只支持文本，二进制要走 WebSocket 或分片编码。
- 忘记给 SSE 关闭代理缓冲，消息被攒着一次性吐出。
- 在 HTTP/1.1 下开多个 SSE 连接，占满同域六连接，阻塞其他请求。
- 长轮询没有游标，断线后丢消息或重复消费。
- WebSocket 只靠 Cookie 鉴权且不校验 `Origin`，遭受跨站劫持。

## 12. 浏览器缓存的完整链路（memory cache、disk cache、HTTP 缓存、SW 缓存）

**结论：** 一次请求可能经过四层缓存：**Service Worker 缓存（代码可控）→ 内存缓存（memory cache）→ 磁盘缓存（disk cache，即 HTTP 缓存）→ 网络**。其中 HTTP 缓存由响应头决定，是首屏性能的主体；SW 缓存由代码决定，用于离线与精细控制；内存缓存是浏览器对同页资源的短期复用，开发者无法直接配置。

**请求链路：**

```text
发起请求
  → 是否被 Service Worker 控制？
      是 → fetch 事件 → 命中 CacheStorage 则直接返回
  → memory cache（同渲染进程、短期、通常不再校验）
  → disk cache（按 URL + Vary 查找，校验新鲜度）
      新鲜 → 直接返回（from disk cache）
      过期 → 带 If-None-Match / If-Modified-Since 请求
            → 304 则复用本地副本
  → 网络（DNS / TCP / TLS / HTTP）
  → 响应按 Cache-Control 写入 disk cache
```

**内存缓存与磁盘缓存：**

| 维度 | memory cache | disk cache |
| --- | --- | --- |
| 位置 | 渲染进程内存 | 磁盘，跨标签页共享 |
| 生命周期 | 页面会话内，进程退出即消失 | 可跨重启，直到过期或被清理 |
| 命中速度 | 最快，无网络与磁盘 IO | 较快，需读磁盘 |
| 是否遵守 HTTP 缓存头 | 部分遵守，通常直接复用 | 完整遵守 |
| 典型场景 | 同页重复图片、脚本、字体 | 二次访问、跨页面复用 |
| DevTools 显示 | `from memory cache` | `from disk cache` |
| 能否禁用 | DevTools 勾选 Disable cache 可绕过 | 同上 |

**HTTP 缓存响应头：**

| 指令 | 含义 | 常见误区 |
| --- | --- | --- |
| `no-store` | 完全不缓存 | 与 `no-cache` 不同 |
| `no-cache` | 可以存，但每次使用前必须校验 | 不是「不缓存」 |
| `max-age=N` | 相对新鲜期 N 秒 | 从响应生成时间算起，不是收到时间 |
| `s-maxage=N` | 仅共享缓存（CDN）使用 | 优先级高于 `max-age` |
| `must-revalidate` | 过期后必须校验，不能用陈旧副本 | 断网时直接失败 |
| `immutable` | 新鲜期内绝不校验 | 只适合内容永不变化的 URL |
| `stale-while-revalidate=N` | 过期后 N 秒内先返回旧副本并后台更新 | 需要 CDN/代理支持 |
| `private` / `public` | 是否允许共享缓存 | 带用户数据的响应应 `private` |
| `Vary` | 按指定请求头区分缓存 | 漏配会把 A 用户响应给 B 用户 |

**协商缓存与 304：**

```http
GET /app.js HTTP/1.1
If-None-Match: "abc123"
If-Modified-Since: Wed, 21 Oct 2025 07:28:00 GMT

HTTP/1.1 304 Not Modified
ETag: "abc123"
Cache-Control: max-age=0, must-revalidate
```

`ETag` 是强校验，优先级高于 `Last-Modified`；`Last-Modified` 只精确到秒，且文件内容未变但修改时间变化时会误判。304 不返回响应体，但仍消耗一次往返，所以「能被强缓存」比「每次 304」更快。

**推荐的缓存策略：**

```nginx
# HTML：始终校验，保证发版后能拿到新入口
location = /index.html {
    add_header Cache-Control "no-cache";
}

# 带 hash 的静态资源：一年强缓存 + immutable
location ~* \.(js|css|woff2|png|jpg|svg)$ {
    add_header Cache-Control "public, max-age=31536000, immutable";
}

# 接口：按业务决定，用户相关响应默认 private
location /api/ {
    add_header Cache-Control "private, no-cache";
}
```

**SW 缓存与 HTTP 缓存的关系：**

| 关系 | 说明 |
| --- | --- |
| 顺序 | 受控页面的请求先进入 SW 的 `fetch` 事件 |
| 独立性 | CacheStorage 不自动遵守 `Cache-Control`，是否缓存由代码决定 |
| 组合 | SW 内 `fetch(request)` 仍会走 HTTP 缓存，可用 `cache: 'no-store'` 绕过 |
| 风险 | SW 缓存了带用户信息的接口，可能跨用户复用 |
| 清理 | 两者共享源配额，都可能被浏览器清理 |

**DevTools 上怎么读：** `from memory cache` 与 `from disk cache` 表示未发请求；`304 Not Modified` 表示发了协商请求但复用本地副本；`200 (from service worker)` 表示由 SW 直接返回。

**面试怎么答：** 按「SW → memory → disk → network」讲链路，再区分「强缓存（不发请求）」与「协商缓存（发请求但 304）」。重点说清 `no-cache` 与 `no-store` 的区别、`max-age` 的起算点、`ETag` 优于 `Last-Modified`、HTML 与带 hash 静态资源应采用相反策略。

**易错点：**

- 把 `no-cache` 当成「不缓存」；它只是「用前必须校验」。
- 给 `index.html` 配长 `max-age`，发版后用户一直拿到旧入口。
- 给带 hash 的资源配 `no-cache`，浪费了强缓存的机会。
- 忘记 `Vary: Origin` 或 `Vary: Accept-Encoding`，导致缓存串源或压缩格式错乱。
- 认为 304 没有成本；它仍有一次网络往返。
- 把 bfcache 当成 HTTP 缓存；它是整页快照，逻辑完全不同。

## 13. iframe 通信与 postMessage 的用法

**结论：** 跨源 iframe 之间不能直接读写对方的 DOM 或变量，标准做法是 `postMessage`：发送方指定目标窗口与 `targetOrigin`，接收方校验 `event.origin`、`event.source` 与消息结构。`postMessage` 是**显式授权通道**，安全责任在接收方，任何一处校验缺失都可能变成 XSS 或数据泄露。

**API 与事件对象：**

```js
targetWindow.postMessage(message, targetOrigin, [transfer]);
```

| 参数/字段 | 含义 |
| --- | --- |
| `targetWindow` | `iframe.contentWindow`、`window.parent`、`window.opener` 等 |
| `message` | 结构化克隆的数据，不能是函数或 DOM 节点 |
| `targetOrigin` | 只向该源发送；`"*"` 表示任意源；`"/"` 表示与发送方同源 |
| `transfer` | 可转移对象列表，如 `MessagePort`、`ArrayBuffer` |
| `event.data` | 收到的数据 |
| `event.origin` | 发送方的源，**必须校验** |
| `event.source` | 发送方窗口引用，可用于回信 |

**父页面发给 iframe：**

```js
const iframe = document.querySelector('#child');
iframe.addEventListener('load', () => {
  iframe.contentWindow.postMessage(
    { type: 'init', payload: { locale: 'zh-CN' } },
    'https://child.example.com'
  );
});
```

**iframe 发给父页面：**

```js
window.parent.postMessage(
  { type: 'resize', payload: { height: document.body.scrollHeight } },
  'https://parent.example.com'
);
```

**接收与校验：**

```js
const ALLOWED = new Set(['https://parent.example.com']);

window.addEventListener('message', (event) => {
  if (!ALLOWED.has(event.origin)) return;
  if (event.source !== window.parent) return;

  const { type, payload } = event.data ?? {};
  if (type === 'theme') {
    applyTheme(String(payload?.theme ?? 'light'));
  }
});
```

校验三件事：**来源白名单**（不要用 `includes` 或前缀匹配）、**发送方窗口**（防止同源其他窗口伪造）、**数据结构与类型**（防止原型污染或注入）。只校验 `origin` 不校验 `source`，在同源多窗口场景仍有风险。

**targetOrigin 的选择：**

| 值 | 行为 | 风险 |
| --- | --- | --- |
| `"*"` | 发给任意当前源 | iframe 被导航到恶意站点时消息泄露 |
| 具体源 | 只在目标窗口当前源匹配时发送 | 推荐 |
| `"/"` | 仅同源发送 | 适合同源 iframe |

注意 `targetOrigin` 匹配的是**发送那一刻目标窗口的源**；如果 iframe 之后被导航到其他站点，消息不会发给它（用 `"*"` 则会）。

**sandbox 的常用组合：** 不写任何属性最严格（无脚本、唯一源）；`allow-scripts` 单独使用仍视为唯一源，较安全；`allow-forms` 会带来 CSRF 类风险；`allow-top-navigation` 可劫持整个页面。特别注意 `sandbox="allow-scripts allow-same-origin"` 同时存在时，iframe 里的脚本可以移除自己的 sandbox 属性，等于没有沙箱，除非内容完全可信。

**MessageChannel：建立私有通道**

```js
// 父页面
const channel = new MessageChannel();
iframe.contentWindow.postMessage({ type: 'port' }, 'https://child.example.com', [channel.port2]);

channel.port1.onmessage = (event) => {
  console.log('来自 iframe 的私有消息', event.data);
};

// iframe 内
window.addEventListener('message', (event) => {
  if (event.origin !== 'https://parent.example.com') return;
  if (event.data?.type === 'port') {
    const port = event.ports[0];
    port.onmessage = (e) => console.log(e.data);
    port.postMessage({ hello: 'parent' });
  }
});
```

`MessageChannel` 建立后，后续通信不再经过全局 `message` 事件，减少与其他监听器的冲突，也便于按通道做权限隔离，适合微前端与编辑器嵌入。

**嵌入限制：** 目标页面可以用 `X-Frame-Options: DENY/SAMEORIGIN` 或 CSP `frame-ancestors` 拒绝被嵌入；反过来，嵌入方也可以用 iframe 的 `csp` 属性限制子页面加载的资源。双向都存在策略，不要假设 iframe 一定能加载。

**面试怎么答：** 先说明跨源 iframe 不能直接互访，标准方案是 `postMessage`；再讲 API 三要素（目标窗口、消息、targetOrigin）与接收方三校验（origin、source、数据结构）。加分点：`targetOrigin="*"` 的泄露风险、`allow-scripts + allow-same-origin` 会破坏沙箱、MessageChannel 做私有通道、X-Frame-Options 与 frame-ancestors 的双向限制。

**易错点：**

- 发送时用 `"*"`，任意被导航后的 iframe 都能读到消息。
- 接收时只判断 `event.data.type`，不校验 `origin`。
- 用 `origin.includes('example.com')` 做白名单，被 `example.com.evil.com` 绕过。
- 认为 sandbox 加了就绝对安全，忽略 `allow-scripts` 与 `allow-same-origin` 的组合。
- 直接 `JSON.parse(event.data)` 后合并到全局对象，造成原型污染。
- 在 iframe 未加载完成时 `postMessage`，`contentWindow` 还是初始 `about:blank`。
