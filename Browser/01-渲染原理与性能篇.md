## 1. 浏览器的多进程架构（主进程/渲染进程/GPU/网络/插件进程）

**结论：** 现代浏览器是**多进程 + 多线程**的集合。浏览器主进程负责窗口与调度，渲染进程按站点隔离负责 DOM、CSS、JS 与布局绘制，GPU 进程负责合成与光栅化，网络进程负责所有网络请求，插件与工具进程各自独立。多进程带来**稳定性、安全性（沙箱）、并行性**，代价是**内存占用与 IPC 开销**。

**为什么不是单进程：** 单进程模型下，一个页面的死循环、内存越界或崩溃会拖垮整个浏览器；而且所有页面共享同一地址空间，恶意页面可以直接读取其他页面的数据。多进程把「故障域」和「权限域」拆开。

| 进程 | 核心职责 | 崩溃后的影响 | 备注 |
| --- | --- | --- | --- |
| 浏览器主进程（Browser） | 窗口、标签页、地址栏、前进后退、下载、权限弹窗、进程调度 | 整个浏览器退出 | 内含 UI 线程与 IO 线程 |
| 渲染进程（Renderer，可多个） | HTML 解析、DOM/CSSOM、样式计算、布局、绘制、JS 执行 | 单个标签页崩溃，显示「页面崩溃」 | 默认按站点隔离，一个站点一个进程 |
| GPU 进程 | 图层合成、纹理上传、光栅化、绘制到屏幕 | 页面花屏或整体卡顿 | 全浏览器共用一个（少数平台多个） |
| 网络进程（Network Service） | DNS、连接池、HTTP 缓存、Cookie 存取、代理 | 所有请求失败 | Chrome 曾把它放在主进程，后拆出 |
| 插件进程 | PPAPI 插件（Flash 等） | 插件失效 | Flash 已停止支持，基本退出历史 |
| 扩展进程 | 每个扩展独立运行 | 扩展失效 | 与页面进程隔离 |
| 工具进程（Utility） | 音频解码、视频捕获、数据解码、PDF | 功能失效 | 按需拉起 |

**渲染进程内部的线程（面试常追问）：**

| 线程 | 职责 |
| --- | --- |
| 主线程（Main Thread） | 解析、样式、布局、绘制指令生成、执行 JS；**单线程，所有长任务都在这里排队** |
| 合成线程（Compositor / Impl Thread） | 维护图层树、处理滚动与合成动画、协调光栅化 |
| 光栅线程池（Raster Workers） | 把绘制指令转成位图（tile） |
| Worker 线程 | `Web Worker` / `Service Worker`，独立于主线程 |

**站点隔离（Site Isolation）：** Chrome 以「site」为粒度分配渲染进程，site 取 scheme + eTLD+1（如 `https://a.example.com` 与 `https://b.example.com` 同 site）。跨站 iframe 会被放进独立进程，目的是防御 Spectre 这类「同进程可越权读内存」的侧信道攻击。因此「一个标签页一个进程」是近似说法，实际可能一个标签页对应多个渲染进程。

**沙箱（Sandbox）：** 渲染进程运行在受限环境，不能直接读写文件、不能直接创建网络连接，需要的能力都通过 IPC 向主进程/网络进程申请。这也是为什么渲染进程崩溃不会破坏系统。

**IPC 与 Mojo：** 进程间通过 Mojo 消息管道通信，例如渲染进程请求 Cookie 要走网络进程；导航请求由主进程发起，响应体经 Mojo 数据管道流式交给渲染进程。IPC 是异步的，所以「主线程卡住」时浏览器外壳仍然可响应。

```text
用户输入 URL
   │
Browser 进程（UI 线程）── 校验 URL、决定是否复用进程
   │  IPC
Network 进程 ── DNS → TCP/TLS → HTTP → 响应头/响应体
   │  IPC（流式）
Renderer 进程（主线程）── 解析 HTML → 构建 DOM → 子资源请求 → 渲染
   │  IPC（Commit）
GPU 进程 ── 合成、光栅化、上屏
```

**观察手段（不编造命令行工具，全部是浏览器自带页面）：**

```text
Shift + Esc         打开 Chrome 任务管理器，看每个标签页/GPU/网络服务的 PID 与内存
chrome://gpu        查看 GPU 加速与光栅化状态
chrome://histograms 查看内部指标（谨慎使用，项非常多）
```

**面试怎么答：** 先给「多进程 + 多线程」的总判断，再按「主进程 / 渲染进程 / GPU / 网络 / 插件与工具」逐个说职责，随后补三点加分项：站点隔离的动机（Spectre）、沙箱与 IPC、渲染进程内主线程与合成线程的分工。最后说明代价：内存与 IPC。

**易错点：**

- 「一个标签页一个进程」不准确，跨站 iframe、`site isolation` 会让一个页面占多个渲染进程。
- 渲染进程不是「只跑 JS」，它承担解析、样式、布局、绘制指令生成；JS 只是主线程任务之一。
- GPU 进程不等于「GPU 加速一定更快」，纹理上传和显存占用本身就是成本。

## 2. 从 HTML 到像素：完整的渲染流程

**结论：** 一次页面呈现可以拆成**导航、解析、样式、布局、绘制、合成**六段。前五段基本在主线程串行完成，最后一段（合成、光栅化、上屏）在合成线程与 GPU 进程完成。任何一段被 JS 长任务占住，后面的段都无法开始，用户看到的就是白屏或卡顿。

**导航阶段（不产生像素，但决定首字节时间）：**

| 步骤 | 发生位置 | 产物 |
| --- | --- | --- |
| URL 解析、检查缓存与 Service Worker | 主进程 / 渲染进程 | 命中缓存则直接复用响应 |
| DNS 查询、TCP、TLS | 网络进程 | 连接 |
| 发送请求、接收响应头 | 网络进程 | 状态码、`Content-Type`、缓存策略 |
| 决定进程模型、提交导航 | 主进程 | 新渲染进程与 `document` |

**渲染阶段（产生像素）：**

```text
HTML 字节流
  → 解码（charset）
  → 词法/语法分析，边下载边解析（Preload Scanner 并行预扫描资源）
  → DOM 树
CSS（link/style/@import）
  → CSSOM 树
DOM + CSSOM
  → 样式计算（Recalc Style）：每个可见节点拿到 computed style
  → 布局树 Layout Tree（几何信息：位置、尺寸）
  → 绘制 Paint：生成绘制指令列表（display list），记录「画什么、按什么顺序画」
  → 分层 Layer / 图层树
  → 提交（Commit）给合成线程
  → 分块（Tiling）→ 光栅化（Raster）→ 生成位图
  → 合成（Composite）：GPU 把各图层按变换拼成一张图
  → 上屏（Draw / Swap）
```

**每一段的产物与线程归属：**

| 阶段 | 线程 | 输入 | 输出 |
| --- | --- | --- | --- |
| 解析 HTML | 主线程 | 字节流 | DOM |
| 解析 CSS | 主线程 | CSS 文本 | CSSOM |
| 样式计算 | 主线程 | DOM + CSSOM | 每个节点的计算样式 |
| 布局 | 主线程 | 布局树 + 几何约束 | 每个盒子的坐标与大小 |
| 绘制 | 主线程 | 布局树 + 样式 | 绘制指令（display list） |
| 分层与提交 | 主线程 → 合成线程 | 绘制指令 + 变换 | 图层树、commit |
| 光栅化 | 光栅线程 / GPU | 绘制指令 + tile 范围 | 纹理位图 |
| 合成上屏 | 合成线程 + GPU | 图层纹理 | 屏幕像素 |

**关键细节：**

1. **解析是增量的。** HTML 解析器不会等整个文档下载完；遇到 `<script>` 会暂停解析（同步脚本），遇到 `<link rel="stylesheet">` 会继续解析但阻塞渲染。预加载扫描器（Preload Scanner）在解析器被脚本阻塞时仍会继续扫描后续资源标签并发起请求，这也是 `defer`/`async` 有价值的原因之一。
2. **样式计算不是「每个节点重新匹配所有选择器」。** 浏览器维护规则表与失效集合（invalidation set），只对受影响的节点重新计算；选择器匹配从右往左，右起选择器越具体，匹配越快。
3. **绘制产出的是指令，不是像素。** 真正画出来发生在光栅化阶段，所以「减少绘制面积」「把绘制放到合成阶段」都能省时间。
4. **首次绘制（FP）与首次内容绘制（FCP）不是同一件事。** FP 是首次有任何非白像素，FCP 是首次有文本/图片等内容。LCP 更晚，衡量的是「主要内容可见」。
5. **主线程的工作会被任务队列切分。** 一次渲染更新发生在「帧」的边界上，JS 改样式并不会立刻触发同步布局，除非你读取了会强制布局的属性（见第 4 题）。

**一个最小的时序（便于口述）：**

```text
TTFB（首字节）→ 下载 HTML → 解析出 <body> → 请求 CSS/JS/图片
→ CSSOM 就绪 → 首次布局 → 首次绘制（FP/FCP）
→ 主图/主文案加载完成 → LCP
→ 交互可用（INP 观测开始）
```

**面试怎么答：** 用「导航 → 解析 → 样式 → 布局 → 绘制 → 合成」这条主线讲，强调三点：解析是流式的、CSS 阻塞渲染不阻塞解析、绘制产出指令而像素在光栅化/合成阶段产生。能补出预加载扫描器与「主线程 vs 合成线程」的分工，基本就超过平均线。

**易错点：**

- 把「渲染树」当成 DOM + CSSOM 的简单合并，忽略 `display:none` 被剔除、伪元素被加入。
- 认为 CSS 会阻塞 HTML 解析；CSS 阻塞的是**渲染**与**后续脚本执行**（脚本可能要读样式）。
- 认为「绘制完成」就上屏了，漏掉分层、光栅化、合成三步。

## 3. DOM、CSSOM 与渲染树（Render Tree）的构建

**结论：** DOM 是 HTML 的结构化表示，CSSOM 是样式规则的结构化表示，二者结合后经**样式计算**得到每个可见节点的计算样式，再生成**布局树（Render Tree / Layout Tree）**。渲染树只包含会参与布局与绘制的节点：`display:none` 的子树被剔除，`visibility:hidden` 保留，伪元素会被加入，`<head>`、`<script>`、`<style>` 不参与。

**DOM 构建要点：**

| 现象 | 原因 |
| --- | --- |
| DOM 是增量构建的 | 解析器逐 token 建节点，用户可能看到「逐步出现」 |
| `<script>` 会阻塞解析 | 脚本可能 `document.write` 修改文档流，解析器必须停下来执行 |
| `innerHTML` 会重建子树 | 解析 HTML 字符串并替换子节点，原有节点引用与事件监听全部丢失 |
| 属性与 property 不同步 | `attribute` 是 HTML 层，`property` 是 JS 对象层，`value`/`checked` 有特殊行为 |

**CSSOM 构建要点：**

- 所有样式来源都进入 CSSOM：`<link>`、`<style>`、行内 `style`、`@import`、用户代理样式。
- `@import` 是串行阻塞：外层 CSS 下载并解析后才发现内层 CSS，形成请求链，生产环境应避免。
- 无法解析的规则会被丢弃，但不会中断整个样式表。
- CSSOM 完成前，浏览器不会进入布局，因为布局需要最终样式。

**渲染树（布局树）的筛选规则：**

| 节点情况 | 是否进入渲染树 | 说明 |
| --- | --- | --- |
| 普通可见元素 | 是 | 生成对应盒子 |
| `display: none` | 否（整棵子树） | 不占空间、不参与布局 |
| `visibility: hidden` | 是 | 占位，只是不绘制 |
| `opacity: 0` | 是 | 参与布局与命中测试 |
| `::before` / `::after` | 是 | 作为所属元素的子盒子 |
| `<head>`、`<script>`、`<style>`、`<template>` | 否 | 不产生盒子 |
| 文本节点 | 是（匿名文本盒） | 空白文本也可能生成盒子 |
| 浮动/绝对定位元素 | 是 | 脱离常规流但仍需布局 |

**样式计算做了什么：**

```text
1. 收集所有规则 → 按来源与重要性排序（UA < 用户 < 作者 < !important）
2. 对每个元素匹配选择器（从右向左）→ 得到声明集合
3. 处理层叠（cascade）：来源、重要性、特异性、源码顺序
4. 处理继承与初始值 → 得到 computed style
5. 处理相对单位（em/rem/%/vh）→ 得到 used value（部分在布局阶段才确定）
```

**易被追问的点：选择器为什么从右往左匹配？** 因为要判断「这个元素是否匹配」，从最右的选择器（key selector）入手可以先快速过滤掉大量元素，再向左验证祖先关系；从左往右会产生大量候选分支。

**失效集合（invalidation set）：** 修改一个类名时，浏览器不会重算整棵树，而是根据事先记录的「哪些规则依赖这个类/属性/伪类」定位受影响节点。这也是 `:has()` 这类选择器在早期实现中性能较差的原因（依赖关系更难界定）。

```js
// 结构变化与样式变化的代价不同
const box = document.querySelector('.box');

box.classList.add('active');        // 只影响匹配该类的节点，触发样式重算
box.style.width = '200px';          // 几何变化，后续会布局 + 绘制
box.innerHTML = '<span>hi</span>';  // 子树重建：解析 + 样式 + 布局 + 绘制 + 事件丢失

// 读取计算样式会触发样式解析（必要时强制布局）
const color = getComputedStyle(box).color;
```

**Shadow DOM 与扁平树：** 样式计算发生在「扁平树（flattened tree）」上，插槽（slot）内容会被分配到宿主中参与布局；外部样式无法穿透 shadow boundary（除继承属性与 CSS 自定义属性），这也是组件样式隔离的原理。

**面试怎么答：** 定义三棵树，重点讲渲染树的筛选规则（`display:none` 剔除、`visibility:hidden` 保留、伪元素加入），再讲样式计算的层叠与继承，最后补选择器匹配方向与失效集合，体现「不是每次改样式都全量重算」。

**易错点：**

- 说「渲染树 = DOM + CSSOM」而不提筛选，`display:none` 是必问点。
- 认为 `visibility:hidden` 不进渲染树；它进，只是不绘制。
- 把 `getComputedStyle` 读到的值当成最终布局值，百分比宽度在这里可能还是 `auto` 的解析结果。

## 4. 布局（Layout/Reflow）与绘制（Paint）

**结论：** 布局解决「盒子在哪、多大」，绘制解决「按什么顺序画什么」。布局的输出是每个盒子的几何信息，绘制的输出是绘制指令列表。布局是三者中最贵的（尤其深层依赖、表格、字体度量），绘制成本取决于**绘制面积**与**绘制复杂度**（阴影、模糊、圆角裁剪）。

**布局的输入与输出：**

| 输入 | 说明 |
| --- | --- |
| 布局树 | 可见节点及其父子关系 |
| 计算样式 | `display`、`position`、`width/height`、`margin/padding/border`、`font` 等 |
| 包含块（containing block） | 决定百分比参照与定位基准 |
| 可用空间 | 视口尺寸、父盒子内容区 |

输出：每个盒子的 `x/y/width/height`、基线位置、滚动区域尺寸。

**格式化上下文（Formatting Context）：** 布局按上下文分别计算，块级上下文、行内上下文、Flex、Grid、Table、绝对定位各有算法。这也是为什么「改一个 flex 子项的宽度」可能引起整条 flex 线重排，而 `contain: layout` 可以把影响限制在子树内。

**布局的类型与成本：**

| 类型 | 触发场景 | 成本特征 |
| --- | --- | --- |
| 全局布局 | 视口尺寸变化、根字号变化、`body` 几何变化 | 整棵树重算 |
| 局部布局（partial layout） | 某个子树独立变化 | 只重算脏子树，依赖布局边界 |
| 首次布局 | 文档初次渲染 | 必然全量 |
| 强制同步布局 | JS 在写样式后立即读几何属性 | 打断批处理，可能反复触发 |

**强制同步布局（layout thrashing）的机制：**

```js
// 反例：读-写-读-写交替，每一轮都强制布局
for (const el of items) {
  el.style.width = el.offsetWidth + 10 + 'px'; // 读 offsetWidth → 强制布局
}

// 正例：先批量读，再批量写
const widths = items.map((el) => el.offsetWidth);
items.forEach((el, i) => {
  el.style.width = widths[i] + 10 + 'px';
});
```

浏览器本来会把样式与布局推迟到帧边界统一处理，一旦 JS 读取 `offsetWidth`、`offsetHeight`、`getBoundingClientRect()`、`scrollTop`、`getComputedStyle()` 等「布局相关」的值，就必须立刻把之前累积的脏样式结算成布局结果，批处理被打断。

**绘制（Paint）做了什么：**

```text
1. 遍历布局树，按绘制顺序生成绘制指令（display list）
   顺序大致为：背景色 → 背景图 → 边框 → 子元素 → 轮廓/阴影
2. 记录绘制范围（paint bounds / cull rect）
3. 把指令交给分层与光栅化阶段
```

绘制阶段还没有像素，只有「在哪个矩形里画什么」。真正的像素生成在光栅化，因此「减少绘制面积」和「把变化转移到合成阶段」是两条主线。

**绘制成本的影响因素：**

| 因素 | 影响 |
| --- | --- |
| 绘制面积 | 面积越大，光栅化越慢；`box-shadow`、`filter: blur()` 会扩大绘制范围 |
| 绘制复杂度 | 圆角、渐变、遮罩、混合模式、文本渲染都更贵 |
| 重绘频率 | 每帧都重绘大面积区域会挤占帧预算 |
| 是否被提升为独立层 | 独立层重绘不影响其他层，但增加显存 |

**减少布局与绘制的引擎级手段：**

```css
/* 把布局影响限制在子树内，形成布局边界 */
.widget {
  contain: layout paint;
}

/* 视口外的内容跳过渲染（渲染 → 布局 → 绘制），需要占位尺寸避免滚动条跳动 */
.section {
  content-visibility: auto;
  contain-intrinsic-size: 800px;
}

/* 动画改用合成属性，避免每帧布局 */
.card {
  transform: translateX(0);
  transition: transform 0.2s;
}
```

**面试怎么答：** 先说两句定义，然后给出「布局产出几何、绘制产出指令、像素在光栅化产生」这条链。重点讲强制同步布局的成因与读写分离的修法，再补 `contain`、`content-visibility`、合成动画三个引擎级优化点。

**易错点：**

- 认为「改了颜色就是重绘、改了尺寸就是回流」就结束了，说不出为什么回流一定伴随重绘（几何变化导致绘制范围变化）。
- 认为 `requestAnimationFrame` 里读写混用没问题；在 rAF 回调里同样会强制布局，只是时机更接近帧边界。
- 把所有动画都交给 `transform`，忽略 `transform` 会改变包含块与命中测试范围。

## 5. 分层、合成与 GPU 加速（Layer、will-change、提升条件）

**结论：** 分层是把页面拆成若干张可独立变换的位图，合成是按图层树把位图拼成最终画面。被提升为独立层的元素，其 `transform` / `opacity` 动画可以**在合成线程完成**，不经过主线程的样式、布局、绘制，因此能稳定跑满帧率。但分层有显存与合成开销，**不是越多越好**。

**分层到上屏的完整链路：**

```text
主线程：绘制指令 → 按 stacking/定位/特效划分图层 → 图层树
   ↓ Commit（把图层树与绘制指令交给合成线程）
合成线程：分块（tile，通常 256×256 或 512×512）→ 分配光栅任务
   ↓
光栅线程/GPU：执行绘制指令 → 纹理（texture）
   ↓
合成线程：计算每个图层的变换矩阵 → 生成 draw quads
   ↓
GPU：按矩阵采样纹理、混合 → 帧缓冲 → 上屏
```

**图层提升（compositing layer）的常见条件（Chrome）：**

| 条件 | 示例 |
| --- | --- |
| 3D 变换 | `transform: translateZ(0)`、`translate3d()` |
| 明确的提升提示 | `will-change: transform` / `opacity` / `filter` |
| 变换或透明度动画 | 动画进行中的 `transform`、`opacity` |
| 视频、Canvas、iframe | `<video>`、`<canvas>`、跨站 iframe |
| 固定定位 | `position: fixed`（部分场景） |
| 滤镜与特效 | `filter`、`backdrop-filter`、`mix-blend-mode` |
| 与已合成层重叠且需要正确层叠 | overlap 场景 |
| `backface-visibility: hidden` | 常见于 3D 卡片 |

**属性与渲染流水线的关系（决定优化方向）：**

| 改动的属性 | 样式 | 布局 | 绘制 | 合成 |
| --- | --- | --- | --- | --- |
| `transform`、`opacity`（已在独立层） | 可能 | 否 | 否 | 是 |
| `transform`、`opacity`（未分层） | 可能 | 否 | 是 | 是 |
| `width`、`height`、`top`、`left`、`margin` | 是 | 是 | 是 | 是 |
| `color`、`background-color`、`box-shadow` | 是 | 否 | 是 | 是 |
| `filter`、`backdrop-filter` | 是 | 否 | 视情况 | 是 |

**`will-change` 的正确用法：**

```css
/* 动画前提示浏览器预留资源，动画结束后移除提示，避免长期占显存 */
.card {
  transition: transform 0.3s ease;
}
.card:hover {
  will-change: transform;
  transform: translateY(-4px);
}

/* 反例：给大量元素常驻 will-change，图层爆炸，显存与合成成本上升 */
.list-item {
  will-change: transform;
}
```

```js
// 需要精确控制生命周期时，在动画开始/结束时增删
el.style.willChange = 'transform';
el.addEventListener('transitionend', () => {
  el.style.willChange = 'auto';
}, { once: true });
```

**图层压缩（layer squashing）：** Chrome 会把「不需要独立」的小图层合并成一个，以减少显存与合成开销。设置 `will-change` 或 3D 变换会阻止合并（因为需要独立变换），所以「随手加 `translateZ(0)`」经常适得其反：图层数量上升、内存上升、光栅化任务变多，低端设备反而更卡。

**GPU 加速的真实收益与代价：**

| 收益 | 代价 |
| --- | --- |
| 合成动画不占主线程，主线程繁忙时仍流畅 | 每个独立层都要显存存纹理 |
| 滚动由合成线程处理，减少主线程滚动卡顿 | 首次提升需要额外光栅化 |
| 变换/透明度动画不触发布局与绘制 | 文本在独立层上可能失去子像素抗锯齿，出现轻微模糊 |
| 大图层可分块光栅化，只重绘脏区 | 图层过多时合成与内存带宽成为瓶颈 |

**面试怎么答：** 先区分「分层」与「合成」两个概念，再讲图层提升条件与「合成线程可独立完成的属性只有 transform/opacity」。核心结论是「提升的收益是绕开主线程，成本是显存与光栅化」，因此 `will-change` 要按需、短期使用。

**易错点：**

- 认为 `transform` 动画一定不触发绘制；未分层时仍会重绘，只是不布局。
- 把 `will-change` 当万能优化，忽略它会阻止图层压缩。
- 认为「GPU 加速」等于「更快」，忽略纹理上传、显存带宽与低端设备的实际表现。

## 6. 重排与重绘的触发与优化（与 CSS 篇的题目错开，重点讲浏览器内部机制）

**结论：** 重排（reflow/layout）是重新计算盒子的几何信息，重绘（repaint）是重新生成绘制指令，合成（composite）是重新拼图层。三者是**流水线上的不同阶段**：几何变了必然重排，重排后绘制范围变化必然重绘；颜色变了只重绘；独立的 `transform`/`opacity` 只合成。优化的核心不是「少改样式」，而是**缩小脏区、减少同步结算、把变化推到合成阶段**。

**三个阶段的判定：**

| 变化 | 样式计算 | 布局 | 绘制 | 合成 | 说明 |
| --- | --- | --- | --- | --- | --- |
| `width`、`height`、`margin`、`top` | 是 | 是 | 是 | 是 | 几何变化，影响兄弟与祖先 |
| `font-size`、`line-height` | 是 | 是 | 是 | 是 | 文本度量变化，可能整段重排 |
| `color`、`background-color` | 是 | 否 | 是 | 是 | 只影响绘制 |
| `box-shadow`、`border-radius` | 是 | 否 | 是 | 是 | 绘制复杂度与范围变化 |
| `visibility`、`opacity`（未分层） | 是 | 否 | 是 | 是 | 仍会重绘 |
| `transform`、`opacity`（已分层） | 可能 | 否 | 否 | 是 | 合成线程独立完成 |
| `filter`、`backdrop-filter` | 是 | 否 | 视情况 | 是 | 常被提升为独立层 |

**浏览器内部如何避免全量重算：**

| 机制 | 作用 |
| --- | --- |
| 脏位标记（dirty bits） | 节点被标记为「样式脏 / 布局脏 / 绘制脏」，只处理脏节点 |
| 失效集合（invalidation set） | 记录哪些规则依赖某个类、属性、伪类，改类名时只定位受影响节点 |
| 布局边界（layout boundary） | 独立格式化上下文（如 `contain: layout`、绝对定位）可把重排限制在子树 |
| 绘制失效矩形（paint invalidation rect） | 只重绘发生变化的最小矩形区域 |
| 图层压缩（squashing） | 合并无需独立变换的小层，降低合成与显存成本 |
| 帧边界批处理 | 同一任务内的多次样式修改合并到下一次渲染更新 |

**强制同步布局（layout thrashing）：** 浏览器本可以把写样式累积到帧边界统一布局，但一旦 JS 读取布局相关属性（`offsetWidth`、`offsetHeight`、`scrollTop`、`getBoundingClientRect()`、`getComputedStyle()` 的部分值），就必须立刻结算脏样式，导致「写 → 读 → 写 → 读」反复全量布局。

```js
// 反例：每次循环都读一次布局，强制同步布局 N 次
function growBad(items) {
  for (const el of items) {
    el.style.width = `${el.offsetWidth + 10}px`;
  }
}

// 正例：先批量读，再批量写，只触发一次布局
function growGood(items) {
  const widths = items.map((el) => el.offsetWidth);
  items.forEach((el, i) => {
    el.style.width = `${widths[i] + 10}px`;
  });
}

// 用 Performance API 观察强制布局的耗时
const items = [...document.querySelectorAll('.item')];
performance.mark('layout-start');
growGood(items);
performance.mark('layout-end');
performance.measure('batch-layout', 'layout-start', 'layout-end');
console.table(performance.getEntriesByName('batch-layout').map((e) => ({ duration: e.duration })));
```

**减少重排重绘的工程手段：**

| 手段 | 原理 |
| --- | --- |
| 读写分离 | 避免在一次循环里交替读写布局属性 |
| `DocumentFragment` / `cssText` | 批量插入或一次性设置样式，减少多次失效 |
| 离线 DOM（`display:none` 后操作再显示） | 操作期间不参与布局，但切换本身有成本，慎用 |
| `contain: layout paint` | 建立布局与绘制边界，限制影响范围 |
| `content-visibility: auto` | 视口外内容跳过渲染，需配 `contain-intrinsic-size` 占位 |
| 动画只用 `transform`/`opacity` | 已分层时在合成线程完成，不触发布局与绘制 |
| 避免表格与深嵌套 | 表格列宽联动、深层依赖会放大重排范围 |
| 固定尺寸占位 | 图片、广告位预留宽高，避免加载后连锁重排 |

```css
/* 建立布局边界，子树的几何变化不影响外部 */
.card {
  contain: layout paint;
}

/* 长列表：视口外跳过渲染，同时给出占位高度 */
.row {
  content-visibility: auto;
  contain-intrinsic-size: 64px;
}

/* 动画走合成，不触发主线程布局 */
.ball {
  transform: translateX(0);
  transition: transform 0.3s ease;
}
```

**面试怎么答：** 先用「几何 → 布局，像素外观 → 绘制，已分层 transform/opacity → 合成」三句话定性，再讲浏览器不是全量重算，而是靠脏位、失效集合、布局边界与绘制矩形缩小范围。重点展开强制同步布局：读布局属性会打断批处理，修法是读写分离与批量更新。最后补 `contain`、`content-visibility` 与合成动画。

**易错点：**

- 说「改颜色一定只重绘」；如果元素未分层且绘制范围扩大，仍可能触发更贵的绘制。
- 认为重排一定比重绘贵；小范围重排可能比大面积模糊重绘便宜，要看脏区。
- 在 `requestAnimationFrame` 里读写混用，仍会强制布局。
- 给所有元素加 `contain: layout`，忽略它会影响百分比尺寸与定位基准。
- 用 `display:none` 批量操作 DOM，忽略切换本身会触发两次布局。

## 7. 关键渲染路径（CRP）与阻塞渲染的资源

**结论：** 关键渲染路径是「从收到 HTML 到首次绘制」的最短链路：**HTML → DOM，CSS → CSSOM，二者合成渲染树 → 布局 → 绘制**。其中 **CSS 是渲染阻塞资源**，**同步 JS 既是解析阻塞也是渲染阻塞资源**。优化 CRP 的本质是缩短这条链上的**关键字节、往返次数与主线程工作量**。

**最小 CRP 流程：**

```text
HTML 响应
  → 解析并构建 DOM（遇到 <script> 同步脚本则暂停）
  → 下载并解析 CSS，构建 CSSOM
  → DOM + CSSOM → 渲染树 → 布局 → 绘制
  → 首次绘制（FP）/ 首次内容绘制（FCP）
```

**资源的阻塞属性：**

| 资源 | 阻塞解析 | 阻塞渲染 | 说明 |
| --- | --- | --- | --- |
| `<link rel="stylesheet">` | 否 | 是 | CSSOM 未就绪不进入布局 |
| `<style>` 内联样式 | 否 | 是 | 同样要进入 CSSOM |
| `@import` | 否 | 是 | 串行发现，形成请求链，应避免 |
| `<script>`（无属性） | 是 | 是 | 可能 `document.write`，必须暂停解析并执行 |
| `<script defer>` | 否 | 是（执行时） | 解析完成后、`DOMContentLoaded` 前按顺序执行 |
| `<script async>` | 否 | 是（执行时） | 下载完立即执行，顺序不保证 |
| `<script type="module">` | 否 | 是 | 默认 defer 语义，依赖图需先加载 |
| `<img>` | 否 | 否 | 不阻塞首绘，但影响 LCP |
| `<video>` / `<iframe>` | 否 | 否 | 可延迟加载 |
| 字体 | 否 | 视策略 | 默认 swap 前可能有不可见文本期 |

**为什么 CSS 阻塞脚本：** 同步脚本可能读取 `getComputedStyle` 或依赖样式计算结果，浏览器必须等 CSSOM 就绪才执行脚本，因此「CSS 后面的同步脚本」会被 CSS 间接拖慢。反过来，脚本也会阻塞后续 CSS 的发现（解析器暂停），所以把脚本放在 `<head>` 中间是最差的位置。

**关键路径长度与关键字节：**

| 指标 | 含义 | 优化方向 |
| --- | --- | --- |
| 关键资源数量 | 首绘前必须下载的文件数 | 内联关键 CSS、删除未使用样式 |
| 关键字节数 | 这些文件的压缩后大小 | 压缩、按路由拆分、移除死代码 |
| 关键路径深度 | 依赖链层数（如 `@import` 链） | 扁平化依赖、预加载 |
| 往返次数（RTT） | DNS、TCP、TLS、请求 | 预连接、HTTP/2 多路复用、CDN |

```html
<!-- 关键 CSS 内联，非关键样式异步加载 -->
<style>
  .hero { display: flex; min-height: 320px; }
  .hero__title { font-size: 32px; line-height: 1.2; }
</style>
<link rel="preload" href="/styles/non-critical.css" as="style" onload="this.rel='stylesheet'">
<noscript><link rel="stylesheet" href="/styles/non-critical.css"></noscript>

<!-- 预连接与预加载，减少后续 RTT -->
<link rel="preconnect" href="https://cdn.example.com" crossorigin>
<link rel="preload" href="/fonts/app.woff2" as="font" type="font/woff2" crossorigin>
```

```js
// 采集首绘与首次内容绘制，验证 CRP 优化是否生效
new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    console.log(entry.name, Math.round(entry.startTime));
  }
}).observe({ type: 'paint', buffered: true });
```

**常见优化清单：**

| 措施 | 收益 | 注意 |
| --- | --- | --- |
| 内联首屏关键 CSS | 少一次阻塞请求 | 控制体积，避免每页重复 |
| 非关键 CSS 异步化 | 缩短关键路径 | 需防 FOUC，保留 `<noscript>` 兜底 |
| 脚本 `defer` / 放 body 末尾 | 不阻塞解析 | `defer` 仍按顺序执行 |
| 预加载 LCP 图片与字体 | 提前发起请求 | `fetchpriority="high"` 可用于主图 |
| 拆分路由与代码 | 减少首屏字节 | 避免首屏依赖过大 chunk |
| 使用 CDN 与 HTTP/2+ | 降低 RTT | HTTP/2 下不宜过度合并文件 |
| 服务端渲染或静态化 | 首屏 HTML 自带内容 | 仍需处理水合成本 |

**面试怎么答：** 先画 CRP 的最短链路，再明确「CSS 阻塞渲染、同步 JS 阻塞解析并间接阻塞渲染」。解释 CSS 为什么阻塞脚本（脚本可能读样式），最后给优化顺序：减少关键资源与字节 → 扁平化依赖 → 内联关键 CSS、脚本 defer、预加载 LCP 资源。

**易错点：**

- 认为 CSS 会阻塞 HTML 解析；它阻塞渲染与后续脚本执行。
- 认为 `async` 脚本不阻塞渲染；下载时不阻塞，执行时仍占主线程。
- 把 `@import` 当成普通样式引入，忽略它串行发现、拉长关键路径。
- 内联了所有 CSS，导致 HTML 体积暴涨、无法缓存。
- 只优化文件大小，忽略请求链深度与 RTT。

## 8. JS 为什么阻塞渲染？defer 与 async 的执行时机

**结论：** JS 阻塞渲染的根本原因是**主线程只有一个**：解析、样式、布局、绘制与 JS 都在主线程排队执行。同步脚本还会**阻塞 HTML 解析**，因为脚本可能通过 `document.write` 改变文档流。`defer` 让脚本在解析完成后按顺序执行，`async` 让脚本下载完就执行、顺序不保证；两者都不解决「执行时占用主线程」的问题。

**三种加载方式的对比：**

| 属性 | 下载 | 执行时机 | 顺序 | 是否阻塞解析 | 是否阻塞 `DOMContentLoaded` |
| --- | --- | --- | --- | --- | --- |
| 无属性 | 立即，阻塞解析 | 下载完立即执行 | 文档顺序 | 是 | 是（执行完才触发） |
| `defer` | 并行下载 | 解析完成后、`DOMContentLoaded` 前 | 保证顺序 | 否 | 是（全部 defer 执行完） |
| `async` | 并行下载 | 下载完立即执行（可能打断解析） | 不保证 | 执行时短暂阻塞 | 不一定（可能早于或晚于） |
| `type="module"` | 并行下载依赖图 | 默认 defer | 保证顺序 | 否 | 是 |

**时间线（便于口述）：**

```text
同步脚本：
HTML 解析 ──遇到 script──> 停止解析 ──下载──> 执行 ──> 继续解析
                                    ↑ 白屏时间被拉长

defer：
HTML 解析 ──────────────────────────> 解析完成 ──> 按顺序执行 defer ──> DOMContentLoaded

async：
HTML 解析 ──────────────────────────> 解析完成 ──> DOMContentLoaded
             └──下载──> 执行（随时可能插入，打断解析）
```

**`DOMContentLoaded` 与 `load`：**

| 事件 | 触发条件 | 常见用途 |
| --- | --- | --- |
| `DOMContentLoaded` | DOM 解析完成，defer 脚本执行完毕；不等待图片、样式、iframe | DOM 初始化、绑定事件 |
| `load` | 页面所有资源（图片、样式、iframe）加载完成 | 统计、非关键资源 |
| `readystatechange` | `interactive` → `complete` | 兼容旧逻辑 |
| `pageshow` | 页面显示（含 bfcache 恢复） | 恢复状态 |

```html
<!-- 推荐：入口脚本 defer，保证 DOM 就绪且按顺序 -->
<script src="/js/vendor.js" defer></script>
<script src="/js/app.js" defer></script>

<!-- 独立统计脚本：async，不依赖其他脚本 -->
<script src="https://analytics.example.com/a.js" async></script>
```

```js
// 动态插入的脚本默认是 async，需要显式关闭以保持顺序
const script = document.createElement('script');
script.src = '/js/lazy-widget.js';
script.async = false; // 按插入顺序执行
document.head.appendChild(script);

// 用 PerformanceObserver 观察长任务对交互的影响
new PerformanceObserver((list) => {
  for (const task of list.getEntries()) {
    console.warn('长任务', Math.round(task.duration), 'ms');
  }
}).observe({ type: 'longtask', buffered: true });
```

**为什么「执行时仍阻塞」：** `defer`/`async` 只改变了下载与执行的调度，脚本执行仍要占用主线程。一个 200ms 的脚本，无论用哪种属性，都会让这一帧的渲染延后 200ms。真正的解法是**减少执行时间**：代码分割、延迟非关键逻辑、把计算移到 Worker、把大任务切片。

**脚本放置策略：**

| 场景 | 建议 |
| --- | --- |
| 依赖 DOM 的业务入口 | `<body>` 末尾或 `defer` |
| 有顺序依赖的多个脚本 | 全部 `defer`，保持顺序 |
| 独立第三方脚本 | `async`，并评估其执行成本 |
| 首屏不需要的模块 | 动态 `import()` 按需加载 |
| 必须尽早执行的埋点 | 内联小段代码，避免额外 RTT |

**面试怎么答：** 先给「单主线程」这个根因，再分「解析阻塞」与「渲染阻塞」两层。用时间线讲清同步、`defer`、`async` 的差异，补 `DOMContentLoaded` 与 `load` 的区别。最后强调 `defer`/`async` 不减少执行耗时，真正优化要靠拆分与卸载主线程。

**易错点：**

- 认为 `async` 完全不阻塞；执行阶段仍占用主线程，且可能打断解析。
- 认为 `defer` 脚本在 `DOMContentLoaded` 之后执行；实际是在它之前。
- 动态插入的脚本默认 `async`，忘记设 `async = false` 导致顺序错乱。
- 把 `load` 当成 DOM 就绪；图片未加载完时 `load` 不会触发。
- 用 `document.write` 动态插入脚本，在网络慢时可能清空文档。
- 认为把脚本放底部就不阻塞渲染；它仍会推迟后续绘制与交互。

## 9. 浏览器帧、60fps 与 requestAnimationFrame

**结论：** 浏览器按**垂直同步（vsync）**的节奏出帧，60Hz 屏幕每 **16.67ms** 一帧。一帧内要完成「输入事件 → rAF 回调 → 样式 → 布局 → 绘制 → 合成提交」，主线程超出预算就会**丢帧**。`requestAnimationFrame` 把回调对齐到下一帧的渲染开始前，是唯一与浏览器出帧节奏同步的动画 API。

**一帧内的执行顺序：**

```text
vsync 到来
  → 处理输入事件（pointerdown、click 等）
  → 执行 requestAnimationFrame 回调
  → 样式计算（Recalc Style）
  → 布局（Layout）
  → 绘制（Paint，生成指令）
  → 提交给合成线程（Commit）
  → 合成线程：光栅化 + 合成 → 上屏
```

注意：rAF 回调在**样式与布局之前**执行，所以在这里改样式可以被本帧统一处理；但如果在回调里读取布局属性，仍会强制同步布局。

**帧预算：**

| 刷新率 | 单帧预算 | 常见设备 |
| --- | --- | --- |
| 60Hz | 16.67ms | 主流显示器 |
| 90Hz | 11.11ms | 部分手机/平板 |
| 120Hz | 8.33ms | 高刷屏、ProMotion |
| 144Hz | 6.94ms | 电竞显示器 |

预算不只是 JS：样式、布局、绘制、光栅化都要在这十几毫秒内完成，因此留给 JS 的时间通常只有 **8–10ms**。

**rAF 与定时器的区别：**

| 维度 | `requestAnimationFrame` | `setTimeout` / `setInterval` |
| --- | --- | --- |
| 触发时机 | 下一帧渲染前，与 vsync 对齐 | 到达延迟后进入任务队列，不保证与帧对齐 |
| 回调参数 | `DOMHighResTimeStamp`（帧开始时间） | 无统一时间戳 |
| 后台标签页 | 暂停或大幅降频 | 被节流到约 1 次/秒（嵌套定时器更严格） |
| 掉帧表现 | 自动跳过，不会补执行 | 可能积压多个回调，造成「追赶式」卡顿 |
| 适用场景 | 动画、滚动联动、逐帧测量 | 延迟任务、轮询、非视觉逻辑 |

```js
// 一个可粘贴到控制台的 FPS 采样器
let frames = 0;
let last = performance.now();
let rafId;

function tick(now) {
  frames += 1;
  const elapsed = now - last;
  if (elapsed >= 1000) {
    const fps = Math.round((frames * 1000) / elapsed);
    console.log(`FPS: ${fps}，单帧均值 ${(elapsed / frames).toFixed(1)}ms`);
    frames = 0;
    last = now;
  }
  rafId = requestAnimationFrame(tick);
}

rafId = requestAnimationFrame(tick);
// 停止：cancelAnimationFrame(rafId);
```

```js
// 标准动画循环：用时间差计算位移，保证不同刷新率下速度一致
let start = null;
let x = 0;

function animate(timestamp) {
  if (start === null) start = timestamp;
  const progress = (timestamp - start) / 1000; // 秒
  x = Math.min(progress * 200, 600);
  box.style.transform = `translateX(${x}px)`;
  if (x < 600) requestAnimationFrame(animate);
}

requestAnimationFrame(animate);
```

**为什么不用 `setInterval(…, 16)` 做动画：** 定时器只保证「不早于」，不保证与屏幕刷新对齐；显示器是 60Hz 时可能一帧执行两次或两帧执行一次，表现为抖动。页面不可见时定时器被节流，动画会在后台「跳跃式」推进，回到前台时状态突变。

**掉帧的常见原因：**

| 原因 | 表现 | 对策 |
| --- | --- | --- |
| 长任务占用主线程 | 帧被跳过，动画一顿一顿 | 任务切片、移入 Worker |
| rAF 里读写混用 | 强制同步布局，单帧超预算 | 读写分离 |
| 每帧修改布局属性 | 每帧都布局 + 绘制 | 改用 `transform`/`opacity` |
| 大面积重绘/滤镜 | 光栅化超时 | 缩小绘制区域、减少模糊 |
| 图层过多 | 合成与显存压力 | 控制 `will-change` 与提升范围 |
| 频繁创建对象 | GC 停顿 | 复用对象、减少每帧分配 |

**后台标签页行为：** 页面不可见时，浏览器会把 rAF 暂停、定时器节流，以省电。依赖 rAF 的计时逻辑在后台会停住，需要配合 `visibilitychange` 做状态修正，或改用基于 `performance.now()` 的绝对时间计算。

**面试怎么答：** 先给「16.67ms 一帧、主线程串行」的预算模型，再讲 rAF 在帧中的位置（输入之后、样式布局之前）。对比 rAF 与定时器：对齐 vsync、后台暂停、不积压。最后说明掉帧根因是长任务与强制布局，优化要减少主线程工作并把动画交给合成。

**易错点：**

- 认为 rAF 一定每秒执行 60 次；高刷屏是 120 次，后台会暂停。
- 用固定步长（每帧 +5px）做动画，导致高刷屏上速度快一倍。
- 在 rAF 回调里读取 `offsetWidth`，造成强制同步布局。
- 用 `setInterval` 做动画，忽略它与刷新率不对齐。
- 认为 rAF 回调里的时间戳是「当前时间」，它其实是本帧开始时间。
- 忘记 `cancelAnimationFrame`，组件卸载后回调仍在跑。

## 10. Core Web Vitals（LCP/INP/CLS）及优化手段

**结论：** Core Web Vitals 是 Google 定义的**用户体验核心指标**：**LCP** 衡量加载速度（主要内容何时可见），**INP** 衡量交互响应（从交互到下一帧绘制的延迟），**CLS** 衡量视觉稳定性（意外布局偏移）。三者都按**真实用户数据（field data）**统计，取 75 分位作为达标线。

**指标与阈值：**

| 指标 | 含义 | 良好 | 需改进 | 差 |
| --- | --- | --- | --- | --- |
| LCP（Largest Contentful Paint） | 视口内最大内容元素（图片、视频封面、大块文本）的渲染时间 | ≤ 2.5s | 2.5–4.0s | > 4.0s |
| INP（Interaction to Next Paint） | 用户交互到下一次绘制完成的延迟，取接近最差的一次 | ≤ 200ms | 200–500ms | > 500ms |
| CLS（Cumulative Layout Shift） | 意外布局偏移的累积分数（按会话窗口计算） | ≤ 0.1 | 0.1–0.25 | > 0.25 |
| TTFB（辅助诊断） | 首字节时间 | ≤ 0.8s | 0.8–1.8s | > 1.8s |

补充：INP 于 2024 年 3 月取代 FID 成为正式指标；FID 只测「首次输入延迟」，INP 覆盖整个访问周期内的所有交互，更接近真实体验。

**LCP 的元素与阶段：**

| 阶段 | 内容 | 优化 |
| --- | --- | --- |
| TTFB | 服务器响应首字节 | CDN、缓存、服务端优化 |
| 资源加载延迟 | 发现并下载 LCP 资源 | 预加载、`fetchpriority="high"`、避免懒加载首图 |
| 资源加载时长 | 图片/字体体积 | 压缩、AVIF/WebP、响应式图片 |
| 元素渲染延迟 | 主线程被阻塞、CSS/JS 未就绪 | 减少阻塞资源、拆分长任务 |

**INP 的构成：**

| 部分 | 说明 |
| --- | --- |
| 输入延迟 | 从用户操作到事件回调开始，受主线程长任务影响 |
| 处理时间 | 事件回调自身执行耗时 |
| 呈现延迟 | 回调结束到下一帧绘制完成，受样式、布局、绘制影响 |

优化 INP 的核心是**让主线程尽快空闲**：拆分长任务、减少事件回调里的同步计算、避免在输入回调里强制布局、用 `scheduler.yield` 让出主线程。

**CLS 的常见来源：**

| 来源 | 示例 | 对策 |
| --- | --- | --- |
| 图片/视频无尺寸 | 加载后撑开布局 | 设置 `width`/`height` 或 `aspect-ratio` |
| 动态插入内容 | 广告、公告条、推荐位 | 预留占位空间 |
| 字体切换 | FOIT/FOUT 导致文本重排 | `font-display: swap` + 字体度量匹配 |
| 动画改布局属性 | 用 `top/left` 做动画 | 改用 `transform` |
| 异步组件 | 骨架屏与真实内容尺寸不一致 | 骨架屏尺寸对齐 |

```js
// 采集 LCP
new PerformanceObserver((list) => {
  const entries = list.getEntries();
  const last = entries[entries.length - 1];
  console.log('LCP', Math.round(last.startTime), last.element);
}).observe({ type: 'largest-contentful-paint', buffered: true });

// 采集 CLS：同一会话窗口内累加，窗口间隔 >1s 或总长 >5s 则切分
let cls = 0;
let sessionValue = 0;
let sessionEntries = [];
new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    if (!entry.hadRecentInput) {
      const first = sessionEntries[0];
      const last = sessionEntries[sessionEntries.length - 1];
      const gap = first && entry.startTime - last.startTime < 1000;
      const within = first && entry.startTime - first.startTime < 5000;
      if (sessionValue && gap && within) {
        sessionValue += entry.value;
        sessionEntries.push(entry);
      } else {
        sessionValue = entry.value;
        sessionEntries = [entry];
      }
      cls = Math.max(cls, sessionValue);
    }
  }
  console.log('CLS', cls.toFixed(4));
}).observe({ type: 'layout-shift', buffered: true });
```

```js
// 近似采集 INP：记录每次交互的最长持续时间
let worstINP = 0;
new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    if (entry.duration > worstINP) {
      worstINP = entry.duration;
      console.log('INP 候选', Math.round(worstINP), entry.name);
    }
  }
}).observe({ type: 'event', buffered: true, durationThreshold: 40 });
```

**优化优先级：**

| 优先级 | 措施 | 影响指标 |
| --- | --- | --- |
| 高 | 减少 TTFB（CDN、缓存、SSR） | LCP |
| 高 | 首图预加载 + 明确尺寸 | LCP、CLS |
| 高 | 拆分长任务、减少主线程阻塞 | INP、LCP |
| 中 | 字体 `swap` 与度量匹配 | CLS、LCP |
| 中 | 预留广告/推荐位占位 | CLS |
| 中 | 事件回调瘦身、避免同步布局 | INP |
| 低 | 图片格式升级（AVIF/WebP） | LCP |

**面试怎么答：** 先给三个指标各一句话定义与阈值，再分别展开：LCP 的四个阶段、INP 的三段构成、CLS 的常见来源。强调「field data、75 分位」与「INP 已取代 FID」。最后给优化顺序：TTFB → LCP 资源 → 主线程长任务 → 尺寸占位与字体。

**易错点：**

- 把实验室 Lighthouse 分数当成 CWV；正式评估用真实用户 75 分位数据。
- 认为 LCP 是「页面加载完成时间」；它是最大内容元素的渲染时间。
- 给首屏主图加 `loading="lazy"`，反而推迟 LCP。
- 认为 CLS 只统计首屏；整个访问周期的意外偏移都会计入。
- 只优化图片，忽略 TTFB 与主线程阻塞对 LCP 的影响。
- 仍以 FID 作为交互指标；自 2024 年起应使用 INP。

## 11. Performance API 与性能数据采集（PerformanceObserver、longtask）

**结论：** Performance API 把浏览器内部的时序暴露为**高精度、单调递增**的时间戳与结构化条目。`performance.now()` 用于打点，`mark`/`measure` 用于自定义区间，`PerformanceObserver` 用于**异步订阅** paint、LCP、layout-shift、longtask、resource 等条目。生产采集要注意**缓冲、采样、上报时机**，避免监控本身拖慢页面。

**常用 API：**

| API | 作用 | 典型用途 |
| --- | --- | --- |
| `performance.now()` | 相对 `timeOrigin` 的毫秒数，精度到微秒级 | 自定义耗时统计 |
| `performance.timeOrigin` | 页面时间原点（Unix 毫秒） | 与服务端日志对齐 |
| `performance.mark(name)` | 打一个命名时间点 | 业务阶段标记 |
| `performance.measure(name, start, end)` | 计算两个标记之间的时长 | 首屏、接口、渲染耗时 |
| `performance.getEntriesByType(type)` | 取已有条目 | 资源、导航、绘制 |
| `PerformanceObserver` | 异步监听新条目 | 长任务、LCP、CLS、INP |
| `performance.memory` | 堆内存概览（非标准，Chrome） | 粗查内存趋势 |

**条目类型：**

| `entryType` | 内容 | 注意 |
| --- | --- | --- |
| `navigation` | 导航各阶段（DNS、TLS、TTFB、DOMContentLoaded、load） | 每次导航一条 |
| `resource` | 每个资源的下载耗时、大小、协议 | 需注意跨域计时限制 |
| `paint` | `first-paint`、`first-contentful-paint` | 只有首屏两条 |
| `largest-contentful-paint` | LCP 候选，可能多次上报 | 取最后一条 |
| `layout-shift` | 布局偏移条目 | 需按会话窗口汇总 |
| `longtask` | 超过 50ms 的主线程任务 | 归因有限，但有 `attribution` |
| `event` | 交互事件的持续时间 | INP 数据来源 |
| `element` | 元素级渲染时间 | 需显式注册元素 |
| `mark` / `measure` | 自定义标记与区间 | 可被 DevTools 展示 |

```js
// 自定义阶段耗时：首屏关键流程
performance.mark('app-start');
await loadUserConfig();
performance.mark('config-ready');

performance.mark('data-start');
const data = await fetchDashboard();
performance.mark('data-end');

performance.measure('config', 'app-start', 'config-ready');
performance.measure('dashboard-data', 'data-start', 'data-end');

for (const m of performance.getEntriesByType('measure')) {
  console.log(m.name, m.duration.toFixed(1), 'ms');
}
```

```js
// 长任务监控：超过 50ms 的主线程任务
const longTasks = [];
new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    longTasks.push({
      start: Math.round(entry.startTime),
      duration: Math.round(entry.duration),
      attribution: entry.attribution?.[0]?.name || 'unknown',
    });
  }
}).observe({ type: 'longtask', buffered: true });

// 页面隐藏时统一上报，避免占用关键路径
document.addEventListener('visibilitychange', () => {
  if (document.visibilityState === 'hidden') {
    navigator.sendBeacon('/api/perf', JSON.stringify({ longTasks }));
  }
}, { once: true });
```

**导航时序的关键节点：**

| 字段 | 含义 |
| --- | --- |
| `redirectStart` / `redirectEnd` | 重定向耗时 |
| `domainLookupStart` / `domainLookupEnd` | DNS |
| `connectStart` / `connectEnd` | TCP 建连（含 TLS 前） |
| `secureConnectionStart` | TLS 开始 |
| `requestStart` / `responseStart` | 请求发出到首字节（TTFB 相关） |
| `responseEnd` | 响应体接收完成 |
| `domContentLoadedEventEnd` | DOM 就绪 |
| `loadEventEnd` | 全部资源加载完成 |

**采集原则：**

| 原则 | 说明 |
| --- | --- |
| 用 `buffered: true` | 订阅晚于事件发生时仍能拿到历史条目 |
| 采样上报 | 按用户或页面比例采样，控制成本 |
| 隐藏时上报 | `visibilitychange` + `sendBeacon`，不阻塞卸载 |
| 不上报原始大对象 | 只传数值与必要维度，避免 payload 过大 |
| 区分实验室与真实用户 | Lighthouse 是实验室数据，CWV 看 field data |
| 注意跨域限制 | 未配 `Timing-Allow-Origin` 时资源耗时被裁剪 |

**面试怎么答：** 先区分「打点三件套」`now`/`mark`/`measure` 与「订阅」`PerformanceObserver`，再列常用 entryType 与各自用途。重点说清 `buffered` 的意义、长任务 50ms 阈值、导航时序里的 TTFB 字段，以及生产环境用采样与 `sendBeacon` 上报。

**易错点：**

- 用 `Date.now()` 做性能打点；它受系统时钟调整影响，精度也不够。
- 订阅 LCP 后只取第一条；LCP 会随页面变化多次上报，应取最后一条。
- 忘记 `buffered: true`，订阅晚于首绘时拿不到 paint 条目。
- 在 `unload` 里同步上报，阻塞卸载且可能丢失。
- 认为 `longtask` 能精确归因到函数；它只提供有限的 attribution。
- 忽略跨域资源的 `Timing-Allow-Origin`，看到的时间全是 0。

## 12. 长任务拆分与调度（requestIdleCallback、scheduler、时间切片）

**结论：** 超过 **50ms** 的主线程任务被视为长任务，会推迟渲染与输入响应。解决思路不是「让任务变快」这一条，而是**把任务切成小块并主动让出主线程**：让浏览器有机会处理输入与渲染，然后再继续。可选工具包括 `setTimeout`、`MessageChannel`、`requestIdleCallback`、`scheduler.postTask` 与 `scheduler.yield`。

**为什么是 50ms：** 这是 RAIL 模型给出的阈值——100ms 内响应用户输入，其中约一半留给渲染与其他开销，因此单个任务控制在 50ms 以内。长任务会直接拉高 INP，并可能推迟 LCP。

**让出主线程的方式对比：**

| 方式 | 让出时机 | 优先级控制 | 兼容性 | 适用 |
| --- | --- | --- | --- | --- |
| `setTimeout(fn, 0)` | 下一个宏任务，实际常被钳制到约 4ms | 无 | 全部 | 简单分片，注意嵌套延迟 |
| `MessageChannel` | 下一个宏任务，无最小延迟 | 无 | 现代浏览器 | 尽快继续的分片 |
| `requestIdleCallback` | 帧末空闲时段，可能长时间不执行 | 无（idle 最低） | Safari 支持较晚 | 非关键后台任务 |
| `scheduler.postTask` | 按优先级调度（user-blocking/visible/background） | 有 | Chrome 系为主 | 需要优先级的任务 |
| `scheduler.yield` | 让出后以高优先级尽快恢复 | 有 | Chrome 129+ | 交互后的连续工作 |

**时间切片（time slicing）：**

```js
// 通用让出：优先 scheduler.yield，降级 MessageChannel
const yieldToMain = (() => {
  if (typeof scheduler !== 'undefined' && typeof scheduler.yield === 'function') {
    return () => scheduler.yield();
  }
  return () =>
    new Promise((resolve) => {
      const channel = new MessageChannel();
      channel.port1.onmessage = () => resolve();
      channel.port2.postMessage(null);
    });
})();

async function processInSlices(items, handleOne, budget = 8) {
  let sliceStart = performance.now();

  for (const item of items) {
    handleOne(item);

    // 每片最多占用约 8ms，随后让出，让输入与渲染插队
    if (performance.now() - sliceStart >= budget) {
      await yieldToMain();
      sliceStart = performance.now();
    }
  }
}

await processInSlices(bigList, renderRow);
```

**空闲调度（requestIdleCallback）：**

```js
function runWhenIdle(tasks) {
  let index = 0;

  const schedule = () => {
    requestIdleCallback((deadline) => {
      // 只要还有剩余时间且未到帧截止，就继续做
      while (index < tasks.length && deadline.timeRemaining() > 2) {
        tasks[index++]();
      }
      if (index < tasks.length) schedule();
    }, { timeout: 2000 }); // 超时兜底，避免永远不执行
  };

  schedule();
}

runWhenIdle([
  () => prefetchNextPage(),
  () => warmImageCache(),
  () => reportAnalytics(),
]);
```

`requestIdleCallback` 的回调可能在帧末只剩几毫秒，也可能因为持续有输入而长时间不执行；它适合「可延迟、可中断」的工作，不适合必须尽快完成的任务。Safari 长期不支持，生产环境要准备降级。

**`scheduler.postTask` 的优先级：**

| 优先级 | 用途 |
| --- | --- |
| `user-blocking` | 直接影响交互的任务，最高优先级 |
| `user-visible` | 可见但非阻塞的任务（默认） |
| `background` | 预取、日志、缓存预热 |

```js
// 高优先级任务插队，低优先级任务让路
scheduler.postTask(() => updateAutocomplete(), { priority: 'user-blocking' });
scheduler.postTask(() => prefetchSuggestions(), { priority: 'background' });
```

**切片的边界与代价：**

| 代价 | 说明 | 缓解 |
| --- | --- | --- |
| 让出本身有开销 | 每次让出都是一次任务调度 | 切片不要过碎，8ms 左右较合适 |
| 状态可能变化 | 让出期间用户可能操作、数据可能更新 | 记录版本号或取消标记 |
| 总耗时略增 | 调度与恢复有成本 | 只对长任务切片，短任务直接做完 |
| 顺序与并发 | 多个切片流程可能交叉 | 用队列或锁串行化 |

**框架里的时间切片：** React 的并发渲染用 Fiber 把渲染工作拆成可中断的小单元，借 `MessageChannel` 调度，在浏览器需要处理输入或渲染时暂停。它解决的是「渲染任务可中断」，与业务侧把大数组循环切片是同一类思路。

**面试怎么答：** 先给「50ms 长任务 → 阻塞输入与渲染」的因果，再列四种让出方式并对比时机、优先级、兼容性。重点讲时间切片的两条规则：按时间预算切、每片后主动让出；以及 `requestIdleCallback` 的「可能饿死」问题与 `timeout` 兜底。最后补 `scheduler.postTask` 的优先级与切片的状态一致性风险。

**易错点：**

- 把任务切成 1ms 一片，调度开销反而超过收益。
- 用 `setTimeout` 切片，忽略嵌套定时器的 4ms 钳制。
- 依赖 `requestIdleCallback` 做必须及时完成的工作，结果长时间不执行。
- 让出期间不校验状态，继续操作已经失效的 DOM 或数据。
- 认为时间切片能减少总耗时；它改善的是响应性，不是计算量。
- 在不支持 `scheduler` 的环境直接调用，未做特性检测与降级。

## 13. 页面生命周期与 bfcache（visibilitychange、freeze/resume、pageshow）

**结论：** 页面不是只有「打开 / 关闭」两种状态，而是经历 **active → passive → hidden → frozen → terminated** 的生命周期。`visibilitychange` 是保存状态与暂停任务的最佳时机；`pagehide` / `pageshow` 用于处理进入与退出 bfcache；`freeze` / `resume` 用于释放与恢复资源。`unload` 已不可靠，不应依赖它做清理或上报。

**状态与事件：**

| 状态 | 含义 | 相关事件 |
| --- | --- | --- |
| active | 页面可见且拥有焦点 | `focus`、`resume`（从 frozen 恢复） |
| passive | 可见但失去焦点（如切换到另一个窗口） | `blur` |
| hidden | 不可见（切换标签页、最小化） | `visibilitychange` |
| frozen | 被浏览器冻结，定时器与任务暂停，释放 CPU | `freeze` |
| terminated | 被丢弃（内存压力、长时间后台） | 无事件，直接销毁 |

| 事件 | 触发时机 | 可靠性 |
| --- | --- | --- |
| `visibilitychange` | 可见性变化 | 高，移动端切换应用也会触发 |
| `pagehide` | 页面即将离开（含进入 bfcache） | 高，推荐替代 `unload` |
| `pageshow` | 页面显示（首次加载或 bfcache 恢复） | 高，用 `event.persisted` 区分 |
| `freeze` | 页面被冻结前 | 中，Chrome 系为主 |
| `resume` | 页面从冻结恢复 | 中，Chrome 系为主 |
| `beforeunload` | 即将卸载，可弹确认框 | 低，移动端常被忽略，且影响 bfcache |
| `unload` | 卸载中 | 低，已废弃趋势，阻塞 bfcache |

**bfcache 是什么：** 前进/后退时，浏览器不重新加载页面，而是把整个页面（含 JS 堆、DOM、滚动位置）冻结后保存在内存中，返回时瞬间恢复。它极大改善返回导航的体验，但页面必须能在「冻结后恢复」时保持正确。

**常见的不符合 bfcache 条件：**

| 限制 | 说明 | 处理 |
| --- | --- | --- |
| 注册了 `unload` 监听 | 使页面无法安全冻结 | 删除，改用 `pagehide` |
| `Cache-Control: no-store` | 禁止页面进入缓存 | 改为 `no-cache` 或合理缓存 |
| `beforeunload` 确认框 | 部分浏览器因此拒绝缓存 | 仅在真正需要时注册 |
| 存在未关闭的连接/事务 | 如进行中的 IndexedDB 事务、WebSocket | 在 `pagehide` 中关闭 |
| 页面被其他页面引用 | 如仍被 iframe 嵌入 | 解除引用 |
| 使用某些旧 API | 如 `SharedWorker` 的特定状态 | 以实测为准 |

可在 DevTools 的 Application → Back-forward Cache 面板查看是否命中，或用前进/后退实测 `pageshow` 的 `persisted` 值。

```js
// 进入后台：保存草稿、暂停计时与轮询
document.addEventListener('visibilitychange', () => {
  if (document.visibilityState === 'hidden') {
    saveDraft();
    stopPolling();
    pauseAnimation();
  } else {
    resumeAnimation();
    refreshIfStale();
  }
});

// 离开页面：优先 pagehide，兼容 bfcache
window.addEventListener('pagehide', (event) => {
  if (event.persisted) {
    // 进入 bfcache，不要在这里做不可逆清理
    console.log('进入 bfcache');
  } else {
    // 真正卸载，可做最终上报
    navigator.sendBeacon('/api/leave', JSON.stringify({ at: Date.now() }));
  }
});

// 从 bfcache 恢复：刷新可能过期的状态
window.addEventListener('pageshow', (event) => {
  if (event.persisted) {
    console.log('从 bfcache 恢复');
    refreshAuthState();
    resumeTimers();
  }
});
```

**冻结与恢复：**

```js
// Chrome 系支持 freeze/resume；其他浏览器用 visibilitychange 兜底
document.addEventListener('freeze', () => {
  releaseHeavyResources(); // 释放大图、断开连接、停止 worker
});

document.addEventListener('resume', () => {
  reinitialize();
});
```

注意：`freeze` 触发后页面可能被直接销毁，不保证有 `resume`；因此不要在 `freeze` 中做「必须写回」的持久化，关键数据应在 `visibilitychange` 为 hidden 时就保存。

**不要依赖 `unload`：** 移动端切换应用、系统杀进程、崩溃等场景下 `unload` 不会触发；而且注册 `unload` 会让页面失去 bfcache 资格。替代方案是 `visibilitychange`（hidden）+ `pagehide` + `sendBeacon`。

**面试怎么答：** 先给五态生命周期，再讲三个关键事件的分工：`visibilitychange` 保存/暂停，`pagehide`/`pageshow` 处理 bfcache 进出，`freeze`/`resume` 释放/恢复重资源。重点说明 bfcache 的收益与「`unload` 会破坏 bfcache」，最后强调 `pageshow.persisted` 与恢复后的状态刷新。

**易错点：**

- 在 `unload` 里发上报；移动端不触发，且会破坏 bfcache。
- 只监听 `beforeunload`，忽略移动端与后台切换。
- 从 bfcache 恢复后不刷新登录态，页面显示过期数据。
- 在 `freeze` 里做关键持久化，忽略可能直接销毁。
- 把 `visibilitychange` 当成「页面关闭」，在 hidden 时做不可逆清理。
- 认为 bfcache 恢复会重新执行脚本；它复用原来的 JS 堆与 DOM。

## 14. 浏览器内存管理与常见内存泄漏（detached DOM、闭包、定时器、事件监听）

**结论：** 浏览器用**可达性（reachability）**判断对象是否可回收：从 GC Roots（全局对象、栈上引用、DOM 树等）出发，仍然可达的对象不会被回收。内存泄漏的本质是**不再需要的对象仍被强引用**。常见来源是 detached DOM、闭包、定时器、事件监听、全局缓存与未取消的订阅。

**垃圾回收的基本模型：**

| 概念 | 说明 |
| --- | --- |
| GC Roots | 全局对象、当前调用栈、DOM 树、活跃的定时器/回调等 |
| 标记清除（Mark-Sweep） | 从 Roots 遍历标记可达对象，未标记的回收 |
| 分代回收 | 新生代（Scavenge，频繁且快）+ 老生代（Mark-Compact，较少但慢） |
| 增量/并发标记 | 把标记拆成小步，减少主线程停顿 |
| 弱引用 | `WeakMap`、`WeakSet`、`WeakRef` 不阻止回收 |

**常见泄漏与修法：**

| 泄漏类型 | 成因 | 修法 |
| --- | --- | --- |
| detached DOM | JS 变量仍引用已从文档移除的节点 | 移除后置空引用；用 `WeakRef` 仅作缓存 |
| 闭包 | 长生命周期函数捕获了大对象 | 缩小捕获范围，必要时置空 |
| 定时器 | `setInterval` 未清除，回调引用外部对象 | 组件卸载时 `clearInterval`/`clearTimeout` |
| 事件监听 | 全局对象上的监听未移除 | 成对 `addEventListener`/`removeEventListener` |
| 全局变量 | 意外挂到 `window`，永不回收 | 使用块级作用域，避免隐式全局 |
| 未取消订阅 | WebSocket、`ResizeObserver`、Promise 链 | 卸载时 `unsubscribe`/`disconnect`/`abort` |
| 无界缓存 | Map 只增不减 | 设上限、LRU、`WeakMap` |
| iframe 泄漏 | 移除 iframe 后仍持有 `contentWindow` | 置空引用，先卸载再移除 |

```js
// 反例：detached DOM —— 节点已移除，但变量仍引用
let panel = document.querySelector('#panel');
document.body.removeChild(panel);
// panel 仍然可达，整棵子树无法回收

// 正例：移除后解除引用
panel.remove();
panel = null;
```

```js
// 反例：定时器捕获大对象
function start() {
  const huge = new Array(1e6).fill('x');
  setInterval(() => {
    console.log(huge.length); // 闭包让 huge 永远可达
  }, 1000);
}

// 正例：保存句柄并在卸载时清理
function startSafe() {
  const huge = new Array(1e6).fill('x');
  const timer = setInterval(() => {
    console.log(huge.length);
  }, 1000);
  return () => clearInterval(timer);
}
const stop = startSafe();
// 组件卸载时调用 stop()
```

```js
// 反例：全局监听 + 匿名函数，无法移除
window.addEventListener('resize', () => layout());

// 正例：具名函数 + 对应移除
function onResize() {
  layout();
}
window.addEventListener('resize', onResize);
// 卸载时：
window.removeEventListener('resize', onResize);
```

```js
// 反例：Map 缓存无上限
const cache = new Map();
function memo(key, value) {
  cache.set(key, value);
}

// 正例一：WeakMap，键不被外部引用时自动回收
const weakCache = new WeakMap();
function memoWeak(key, value) {
  weakCache.set(key, value);
}

// 正例二：需要保留强引用时，用带上限的 LRU 替代无界 Map
```

**观察与定位：**

| 工具 | 用途 |
| --- | --- |
| DevTools → Memory → Heap snapshot | 对比快照，查 detached 节点与增长对象 |
| Allocation instrumentation on timeline | 观察持续分配的对象 |
| `performance.memory`（Chrome） | 粗看 `usedJSHeapSize` 趋势 |
| `queryObjects(Constructor)` | 在控制台统计某构造函数的实例数 |
| Detached elements 面板 | 直接列出被保留的游离 DOM |

```js
// 控制台：粗看内存趋势（Chrome 专有字段）
console.table({
  used: (performance.memory.usedJSHeapSize / 1048576).toFixed(1) + 'MB',
  total: (performance.memory.totalJSHeapSize / 1048576).toFixed(1) + 'MB',
  limit: (performance.memory.jsHeapSizeLimit / 1048576).toFixed(1) + 'MB',
});

// 连续采样，观察是否持续增长
setInterval(() => {
  console.log('heap', (performance.memory.usedJSHeapSize / 1048576).toFixed(1));
}, 5000);
```

**一个排查流程：** 复现操作 → 拍第一次堆快照 → 重复操作多次 → 强制 GC 后拍第二次 → 对比「对象数量与 retained size 的增长」→ 沿 retainer 链找到持有者 → 修复引用。

**面试怎么答：** 先讲可达性与 GC Roots，说明泄漏是「意外的强引用」而不是「忘了 free」。再按 detached DOM、闭包、定时器、监听、缓存五类给例子与修法。最后讲定位方法：堆快照对比、retainer 链、`queryObjects`，并强调 `WeakMap` 只适合做缓存，不能解决业务对象本身的生命周期。

**易错点：**

- 认为 `removeChild` 后节点就被回收；JS 变量仍引用时不会。
- 用匿名函数注册监听，之后无法精确移除。
- 认为 `WeakMap` 能解决所有缓存泄漏；值对象之间仍可能互相引用。
- 只清定时器不清回调里持有的 DOM 引用，泄漏依旧。
- 把 `performance.memory` 当标准 API；它是 Chrome 专有且精度有限。
- 认为单页应用切换路由就会释放内存；未清理的订阅会一直累积。

## 15. 渲染性能排查实战（DevTools Performance/Layers/Rendering 面板与优化清单）

**结论：** 性能排查的顺序是**先量化、再定位、后优化、最后回归**。用 Performance 面板录一段包含交互的 trace，找主线程上的长任务与强制布局；用 Layers 与 Rendering 面板确认图层与重绘范围；用 Memory 面板排除泄漏。不要凭感觉改 CSS，每次只改一个变量并对比数据。

**面板分工：**

| 面板 | 看什么 | 典型用途 |
| --- | --- | --- |
| Performance | 火焰图、帧、主线程任务、布局/绘制、GPU | 定位长任务、强制布局、掉帧 |
| Performance Insights | 自动归因的洞察卡片 | 快速发现 LCP、CLS、长任务问题 |
| Layers | 图层数量、原因、显存估算 | 排查图层爆炸与提升是否合理 |
| Rendering | 重绘高亮、布局偏移区域、FPS 量表、图层边框 | 直观看到重绘与偏移 |
| Memory | 堆快照、分配时间线 | 排查 detached DOM 与泄漏 |
| Coverage | CSS/JS 未使用比例 | 减少首屏字节 |
| Network | 瀑布图、优先级、缓存 | 优化关键路径与 LCP 资源 |

**标准排查流程：**

```text
1. 明确问题：首屏慢 / 滚动卡 / 点击无响应 / 动画掉帧
2. 打开无痕窗口，禁用无关扩展，固定网络与 CPU 节流（如 4x）
3. Performance 面板录制 5–10 秒，覆盖问题操作
4. 看 Frames 条：红色/紫色帧对应掉帧；看主线程火焰图找 >50ms 任务
5. 展开任务：定位 Recalculate Style、Layout、Paint、Function Call
6. 若出现紫色 Layout 且紧跟 JS：检查强制同步布局（读写混用）
7. 若 Paint 面积大：Rendering 面板开 Paint flashing 确认重绘范围
8. 若图层多：Layers 面板看提升原因，清理不必要的 will-change
9. 改一处 → 重新录制 → 对比同一指标，记录前后数据
10. 用真实设备与真实网络复测，避免只在高配机器上验证
```

**Rendering 面板的开关：**

| 开关 | 作用 |
| --- | --- |
| Paint flashing | 绿色高亮重绘区域，面积越大越贵 |
| Layout Shift Regions | 蓝色高亮发生偏移的区域 |
| Frame Rendering Stats | 显示实时 FPS 与 GPU 内存 |
| Layer borders | 显示图层边界，判断是否意外分层 |
| Scrolling performance issues | 标出可能拖慢滚动的监听器 |
| Emulate CSS media feature prefers-reduced-motion | 验证无动画时的可用性 |

```js
// 在控制台快速定位长任务与强制布局的时间点
const observer = new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    console.log(
      `[longtask] ${Math.round(entry.startTime)}ms, 持续 ${Math.round(entry.duration)}ms`,
      entry.attribution
    );
  }
});
observer.observe({ type: 'longtask', buffered: true });

// 标记一次怀疑有强制布局的操作，随后在 Performance 面板对照
performance.mark('suspect-start');
document.querySelectorAll('.card').forEach((el) => {
  el.style.width = `${el.offsetWidth}px`; // 典型的读写混用
});
performance.mark('suspect-end');
performance.measure('suspect-layout', 'suspect-start', 'suspect-end');
console.log(performance.getEntriesByName('suspect-layout')[0].duration);
```

**火焰图怎么读：**

| 现象 | 可能原因 | 处理 |
| --- | --- | --- |
| 一大块黄色 Function Call | 长 JS 任务 | 拆分、移入 Worker、减少计算 |
| 紫色 Layout 反复出现 | 强制同步布局 | 读写分离、批量更新 |
| 绿色 Paint 面积大 | 大面积重绘、阴影/模糊 | 缩小区域、提升为独立层 |
| 灰色 Other / 空白 | 浏览器内部工作、GC | 减少分配、观察 GC 频率 |
| 帧条出现长红条 | 掉帧 | 对照主线程任务与合成耗时 |
| Composite Layers 很长 | 图层过多或过大 | 减少提升、控制图层面积 |

**优化清单（按收益排序）：**

| 优先级 | 检查项 | 验证方式 |
| --- | --- | --- |
| 高 | 主线程是否有 >50ms 长任务 | Performance 火焰图、longtask |
| 高 | 是否存在强制同步布局 | 紫色 Layout 紧跟 JS、`performance.measure` |
| 高 | LCP 资源是否被延迟发现 | Network 优先级、`fetchpriority` |
| 高 | 图片/广告是否预留尺寸 | Layout Shift Regions、CLS |
| 中 | 动画是否只改 `transform`/`opacity` | Layers、Paint flashing |
| 中 | 图层数量是否失控 | Layers 面板的 reasons 与内存 |
| 中 | 事件回调是否过重 | Performance 的 Event 段 |
| 中 | 是否存在未使用 CSS/JS | Coverage 面板 |
| 低 | 字体是否阻塞文本渲染 | Network、`font-display` |
| 低 | 缓存策略是否合理 | Network 的 Size 与 Headers |

**面试怎么答：** 按「量化 → 定位 → 优化 → 回归」四步讲，并说明每个面板的分工。重点讲两个高频定位手法：火焰图里找 >50ms 长任务；看到 Layout 紧跟 JS 就怀疑强制同步布局。最后强调固定网络/CPU 节流、一次只改一个变量、用真实设备回归。

**易错点：**

- 开着扩展、缓存与高配机器录性能，数据不可复现。
- 只看 Lighthouse 分数，不看具体火焰图与帧。
- 一次改十几处 CSS，无法判断哪项生效。
- 把 Paint flashing 的绿色面积当成唯一指标，忽略合成与布局成本。
- 认为图层越多越流畅，忽略显存与合成开销。
- 优化后不做回归，线上真实设备仍然卡顿。
