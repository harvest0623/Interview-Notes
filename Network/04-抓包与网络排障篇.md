## 1. 抓包工具与原理（tcpdump、Wireshark）

**现象：** 应用日志只有时间戳、状态码和一句「请求失败」，无法回答「包有没有到」「握手停在哪一步」「响应是不是被中间设备改了」。这时需要协议层证据，抓包是唯一能还原链路上真实交互的手段。

**原理：** Linux 上抓包依赖 libpcap（Windows 为 Npcap），核心机制是：

- 网卡驱动把报文交给内核，libpcap 通过 `AF_PACKET` 在协议栈旁路复制一份，不影响正常收发。
- 过滤器由 **BPF 字节码**在内核中执行，只有命中的包才复制到用户态，所以过滤越精确，开销越小。
- 默认只抓本机收发的包；开启混杂模式（`promisc`）后能抓到同一广播域内的其他主机流量，但在交换网络中仍需要镜像端口或 TAP。
- 抓包本身有成本：缓冲区不足会丢包，写盘太慢会丢包，过滤太宽会占满 CPU。

**抓包点的选择（比工具更重要）：**

| 位置 | 能看到什么 | 注意事项 |
| --- | --- | --- |
| 客户端网卡 | 请求发出、响应收到 | 看不到服务端内部处理 |
| 服务端网卡 | 请求到达、响应发出 | 看不到中间代理与 LB |
| 负载均衡 / 代理 | 两次连接的对应关系 | 需同时抓前后两段 |
| 容器内 eth0 | 容器视角的流量 | 与宿主机 veth 是一对 |
| 宿主机网桥 | 所有容器流量 | 流量大，必须精确过滤 |
| 交换机镜像口 | 整条链路的原始流量 | 需要网络设备权限 |

**工具定位：**

| 工具 | 用途 | 特点 |
| --- | --- | --- |
| tcpdump | 命令行抓包 | 服务器上最常用，资源占用低 |
| dumpcap | Wireshark 的抓包引擎 | 支持环形缓冲、多文件轮转 |
| Wireshark | 图形化分析 | 协议解析、时序图、专家信息 |
| tshark | 命令行版 Wireshark | 可脚本化、可字段提取 |
| ss | 查看套接字状态 | 看队列、RTT、重传，不抓包 |
| mitmproxy / Charles | 解密 HTTPS 抓包 | 需安装并信任代理证书 |

**抓包命令：**

```bash
    # 全量抓包，禁用名称解析，写到文件，缓冲区 64 MiB
    sudo tcpdump -i eth0 -nn -s 0 -B 65536 -w /tmp/cap.pcap 'host 10.0.0.5 and port 443'

    # 抓 200 个包并直接打印，适合快速确认流量是否到达
    sudo tcpdump -i any -nn -c 200 'tcp port 80'

    # 指定网卡抓 TLS，交给 Wireshark 分析
    sudo tshark -i eth0 -f 'tcp port 443' -w /tmp/tls.pcap

    # 查看抓包文件的基本信息与完整性
    capinfos /tmp/cap.pcap

    # 按时间窗口裁剪，便于交给他人分析
    editcap -A '2026-11-03 10:00:00' -B '2026-11-03 10:05:00' /tmp/cap.pcap /tmp/slice.pcap

    # 统计抓包文件中的 TCP 会话
    tshark -r /tmp/cap.pcap -q -z conv,tcp
```

**判读标准：**

| 信号 | 含义 | 处理 |
| --- | --- | --- |
| `packets captured` 与 `packets received` 差值大 | 内核丢包，缓冲区不足 | 增大 `-B`，缩小过滤范围 |
| `packets dropped by kernel` | 同上，抓包不完整 | 写文件、减少打印、提高优先级 |
| 文件里只有单向包 | 抓包点只看到一侧 | 改抓 `any` 或在对端同时抓 |
| 时间戳间隔异常 | 时钟不同步 | 统一 NTP 后再对比 |
| 看到超大 TCP 段 | 网卡 GRO/TSO 卸载 | 抓包侧关闭 offload 再看 |

**处置建议：**

1. 先在关键路径上用最小过滤确认「包到没到」，再决定是否全量抓包。
2. 生产环境优先写文件而不是打印，避免终端 IO 拖慢进程。
3. 抓包前估算体积：`带宽 × 时长`，必要时用 `-C` 做文件轮转。
4. 容器场景在宿主机抓 veth 或在容器内安装 tcpdump，注意命名空间差异。
5. 涉及 HTTPS 时先判断是「连接问题」还是「内容问题」，后者才需要代理解密。

**面试怎么答：** 先讲 libpcap 通过 BPF 在内核过滤、旁路复制的原理，再强调「抓包点比工具重要」，按客户端、服务端、代理、容器四类位置说明能看到什么；最后给出 `tcpdump -nn -s 0 -w` 的标准命令与丢包判读。

**易错点：**

- 在容器内抓 `eth0`，却拿宿主机的流量做对比，两边时间与网卡对不上。
- 只抓单向流量，看到「没有响应」其实是对端回包走了另一条路径。
- 生产环境开混杂模式抓全量，CPU 与磁盘被拖垮。
- 认为抓到 HTTPS 就能看到 URL 和 Body，未解密时只有 TLS 记录层。

## 2. 常用抓包过滤表达式

**现象：** 直接抓全量包，文件几个 GB，打开就卡死；或者加了过滤条件却一条都抓不到，怀疑「没有流量」，实际是表达式写错。

**原理：** 抓包过滤分两层，必须区分清楚：

- **捕获过滤器（BPF）**：在抓包时由内核执行，语法是 `tcpdump -f` 或 Wireshark 的 Capture Filter，只能识别到传输层，写 `http` 这类应用层关键字无效。
- **显示过滤器（Display Filter）**：在 Wireshark/tshark 解析后执行，语法是 `ip.addr == ...`，能引用 `http.request.method`、`tls.handshake.type` 等字段。
- `tshark` 中 `-f` 是捕获过滤，`-Y` 是显示过滤，混用会报语法错误。

**BPF 常用原语：**

| 原语 | 示例 | 说明 |
| --- | --- | --- |
| `host` | `host 10.0.0.5` | 源或目的地址 |
| `src` / `dst` | `src 10.0.0.5` | 限定方向 |
| `net` | `net 10.0.0.0/8` | 网段 |
| `port` | `port 443` | 源或目的端口 |
| `portrange` | `portrange 8000-9000` | 端口范围 |
| `tcp` / `udp` / `icmp` | `tcp and port 80` | 协议 |
| `and` / `or` / `not` | `tcp and not port 22` | 逻辑组合 |
| `greater` / `less` | `greater 1200` | 按报文长度过滤 |
| 标志位 | `tcp[tcpflags] & tcp-syn != 0` | 只看 SYN |

**捕获过滤命令：**

```bash
    # 指定主机与端口，最常用
    sudo tcpdump -i eth0 -nn 'host 10.0.0.5 and tcp port 443'

    # 只看 SYN 包，用于确认连接是否发起
    sudo tcpdump -i eth0 -nn 'tcp[tcpflags] & tcp-syn != 0 and host 10.0.0.5'

    # 排除 SSH 与 ARP，减少噪声
    sudo tcpdump -i eth0 -nn 'not port 22 and not arp'

    # 只看大于 1200 字节的包，排查 MTU 与分片
    sudo tcpdump -i eth0 -nn 'greater 1200 and host 10.0.0.5'

    # 端口范围
    sudo tcpdump -i eth0 -nn 'tcp portrange 8000-9000'

    # 抓 DNS 查询与响应
    sudo tcpdump -i eth0 -nn 'udp port 53'
```

**显示过滤命令：**

```bash
    # 指定地址与端口
    tshark -r /tmp/cap.pcap -Y 'ip.addr == 10.0.0.5 && tcp.port == 443'

    # 只看重传
    tshark -r /tmp/cap.pcap -Y 'tcp.analysis.retransmission'

    # 只看零窗口
    tshark -r /tmp/cap.pcap -Y 'tcp.analysis.zero_window'

    # 只看 HTTP POST 请求
    tshark -r /tmp/cap.pcap -Y 'http.request.method == "POST"'

    # 只看 TLS ClientHello
    tshark -r /tmp/cap.pcap -Y 'tls.handshake.type == 1'

    # 只看 DNS 查询某个域名
    tshark -r /tmp/cap.pcap -Y 'dns.qry.name contains "example.com"'

    # 只看 SYN 且非 ACK
    tshark -r /tmp/cap.pcap -Y 'tcp.flags.syn == 1 && tcp.flags.ack == 0'
```

**判读标准：**

| 过滤结果为空 | 可能原因 |
| --- | --- |
| 完全无包 | 网卡选错、流量不经过本机、VLAN 标签未被解析 |
| 有包但看不到 HTTP | 端口是 443 且未解密，或用了非标准端口 |
| BPF 报语法错误 | 把显示过滤语法写进了 `-f` |
| 过滤到大量重传 | 可能是乱序被误标，需要看 `tcp.analysis.out_of_order` |
| 看不到 DNS | 用了 DNS over HTTPS，走的是 443 而非 53 |

**处置建议：**

1. 抓包先用「主机 + 端口」缩小范围，再逐步加协议条件。
2. 分析阶段才用显示过滤，避免抓包时就漏掉关键包。
3. 过滤表达式先在小流量环境验证，再上生产。
4. 对加密流量，过滤到五元组即可，不要期待看到 URL。
5. 保留原始 pcap，显示过滤只影响视图，不影响证据。

**面试怎么答：** 先分清捕获过滤与显示过滤，说明 BPF 在内核执行、只能到传输层；再给三到四条高频表达式（host+port、SYN、重传、HTTP 方法），最后讲「先粗后细」的过滤策略与空结果的排查方向。

**易错点：**

- 在 `tcpdump` 里写 `http.request.method`，BPF 不认识应用层字段。
- `tshark -f` 与 `-Y` 混用，前者是捕获过滤，后者才是显示过滤。
- 过滤条件过窄，漏掉握手包，后续时序无法分析。
- 认为「没有抓到包」等于「没有流量」，忽略抓包点与 VLAN。

## 3. 分析一次完整的 HTTP 请求

**现象：** 用户反馈接口慢，但服务端日志显示处理只用了 20ms。说明时间花在了「到达服务端之前」或「响应回来之后」，必须把一次请求拆成可归因的几段。

**原理：** 一次 HTTPS 请求的时间可以拆成五段：

1. **DNS 解析**：域名到 IP，受缓存与递归影响。
2. **TCP 连接**：三次握手，跨地域时约 1 个 RTT。
3. **TLS 握手**：TLS 1.2 约 2 个 RTT，TLS 1.3 约 1 个 RTT，会话复用可再降。
4. **TTFB**：请求发出到首字节返回，包含服务端处理与网络往返。
5. **内容传输**：响应体下载，受带宽、压缩、分块影响。

**协议层还要看这些细节：**

- `Connection: keep-alive` 是否复用了连接；复用后没有握手开销。
- `Transfer-Encoding: chunked` 表示分块传输，首字节早但结束晚。
- `Expect: 100-continue` 会多一次往返，大 POST 常见。
- `Content-Encoding: gzip/br` 是否生效，未压缩会放大传输时间。
- HTTP/2 的多路复用让「连接数」不再等于「并发数」。

**量化命令：**

```bash
    # curl 内置计时变量，一次拿到各段耗时
    curl -o /dev/null -s \
        -w 'dns=%{time_namelookup} connect=%{time_connect} tls=%{time_appconnect} ttfb=%{time_starttransfer} total=%{time_total} size=%{size_download}\n' \
        https://api.example.com/v1/users

    # 查看请求与响应头、TLS 版本、证书、是否复用连接
    curl -v https://api.example.com/v1/users

    # 对比 HTTP/1.1 与 HTTP/2 的耗时差异
    curl --http1.1 -o /dev/null -s -w 'http1 total=%{time_total}\n' https://api.example.com/
    curl --http2   -o /dev/null -s -w 'http2 total=%{time_total}\n' https://api.example.com/

    # 开启压缩，确认传输时间是否下降
    curl --compressed -o /dev/null -s -w 'compressed total=%{time_total}\n' https://api.example.com/

    # 连接复用前后各测一次，冷连接包含完整握手
    curl -o /dev/null -s -w 'cold total=%{time_total}\n' https://api.example.com/
    curl -o /dev/null -s -w 'warm total=%{time_total}\n' https://api.example.com/

    # 抓明文 HTTP，直接看请求行与响应头
    sudo tcpdump -i eth0 -nn -A 'tcp port 80 and host 10.0.0.5'

    # 按时间顺序提取请求方法、状态码与服务端处理时间
    tshark -r /tmp/http.pcap -Y 'http.request or http.response' -T fields \
        -e frame.time_relative -e ip.src -e http.request.method \
        -e http.response.code -e http.time

    # 还原一次 TCP 会话的完整内容
    tshark -r /tmp/http.pcap -q -z follow,tcp,ascii,0
```

**判读标准：**

| 指标 | 正常范围 | 异常含义 |
| --- | --- | --- |
| `time_namelookup` | < 50ms | 偏大说明 DNS 慢或缓存未命中 |
| `time_connect - time_namelookup` | 同城 < 10ms，跨地域约 1 RTT | 偏大说明网络或握手排队 |
| `time_appconnect - time_connect` | TLS1.3 约 1 RTT | 偏大说明证书链、SNI 或加密套件问题 |
| `time_starttransfer - time_appconnect` | 取决于业务，通常 < 500ms | 偏大说明服务端慢或上游阻塞 |
| `time_total - time_starttransfer` | 与响应体大小成正比 | 偏大说明带宽不足或未压缩 |
| `time_connect` 接近 0 但 total 很大 | 连接被复用 | 重点看 TTFB 与传输 |
| 响应头带 `Connection: close` | 每次请求都重新握手 | 开启 keep-alive 复用 |
| `time_appconnect - time_connect` 超过 2 RTT | 证书链过长或会话未复用 | 精简证书链、开 session reuse |
| TCP 握手后立刻 RST | 服务端拒绝 | 端口未监听、安全组、限流 |

**处置建议：**

1. 先看哪一段占比最大，只优化最大的一段。
2. DNS 慢：加缓存、换就近解析、上 HTTPDNS。
3. 连接慢：检查跨地域 RTT、LB 排队、SYN backlog。
4. TLS 慢：升级 TLS 1.3、开启会话复用、精简证书链。
5. TTFB 慢：区分服务端处理与上游依赖，看链路追踪。
6. 传输慢：开压缩、上 CDN、减小响应体、启用 HTTP/2 或 HTTP/3。
7. 冷连接与热连接分开测，连接复用的收益要单独评估，不能被平均值掩盖。
8. 分块响应只看首字节时间会低估总耗时，要同时看 `time_total` 与响应体大小。

**面试怎么答：** 直接背五段拆分（DNS、连接、TLS、TTFB、传输），说明每段的正常值与常见根因，再给 `curl -w` 这条能一次量化全部指标的命令；最后强调「服务端日志只覆盖 TTFB 的一部分，不能代表用户耗时」。

**易错点：**

- 拿服务端处理时间当作端到端耗时，忽略 DNS 与握手。
- 只测一次就下结论，没有区分冷连接与连接复用。
- 忽略 `Content-Encoding`，把带宽问题误判为服务端慢。
- 在 HTTP/2 下按连接数评估并发，实际是多路复用。
- 只用 `time_total` 一个指标判断快慢，不拆分阶段，优化没有靶点。
- 忽略 `Connection: close`，把每次重新握手的时间算进服务端耗时。

## 4. 分析 TCP 重传与乱序

**现象：** 接口偶发变慢、下载速度上不去、长连接周期性卡顿。服务端 CPU 与内存都正常，但 `netstat -s` 里的重传计数持续增长。

**原理：** TCP 用「确认 + 重传」保证可靠传输：

- **RTO 超时重传**：发送方在 RTO 内没收到 ACK，重发报文，通常意味着真实丢包，对吞吐影响最大。
- **快速重传**：收到 3 个重复 ACK 立即重发，不必等 RTO，恢复更快。
- **乱序（out-of-order）**：报文到达顺序与发送顺序不同，接收方会等待缺失段，表现为重复 ACK，但不一定是丢包。
- **虚假重传（spurious retransmission）**：原报文其实已到达，只是 ACK 延迟或乱序触发了重传，属于误判。
- **零窗口（zero window）**：接收方缓冲区满，发送方暂停，问题在消费端而非网络。

**RTO 与重传的关系：** Linux 的最小 RTO 约为 200ms，连续丢包时按指数退避放大。因此抓包里看到「1s、2s、4s」这种间隔，说明已经进入 RTO 重传，而不是快速重传；快速重传的前提是后续报文仍在到达并产生至少 3 个重复 ACK。


**抓包与分析命令：**

```bash
    # 抓取与目标主机的全部 TCP 流量
    sudo tcpdump -i eth0 -nn -s 0 -w /tmp/retrans.pcap 'tcp and host 10.0.0.5'

    # 提取重传事件：时间、源、序号、长度
    tshark -r /tmp/retrans.pcap -Y 'tcp.analysis.retransmission' -T fields \
        -e frame.time -e ip.src -e tcp.seq -e tcp.len

    # 统计重传、乱序、重复 ACK 数量
    tshark -r /tmp/retrans.pcap -q -z expert

    # 查看套接字的 RTT、重传、拥塞窗口
    ss -ti dst 10.0.0.5

    # 内核累计计数（TcpRetransSegs / TcpOutSegs）
    nstat -az TcpRetransSegs TcpOutSegs TcpExtTCPLostRetransmit

    # 传统方式查看重传统计
    netstat -s | grep -Ei 'retrans|out-of-order'

    # 直接计算重传率
    nstat -az TcpRetransSegs TcpOutSegs | awk '$1=="TcpRetransSegs"{r=$2} $1=="TcpOutSegs"{o=$2} END{printf "retrans=%.3f%%\n", r/o*100}'
```

**判读标准：**

| 现象 | 说明 | 结论 |
| --- | --- | --- |
| 重传率 = 重传段 / 发出段 | < 0.1% 正常，> 1% 明显异常 | 先查链路丢包 |
| 大量 `TCP Dup ACK` + 少量重传 | 多为乱序，不一定是丢包 | 检查多路径、负载均衡 |
| `tcp.analysis.out_of_order` 集中出现 | 报文走了不同路径 | 多线接入或负载不均 |
| `zero_window` 持续 | 接收端读得太慢 | 查应用消费速度与缓冲区 |
| 重传集中在同一方向 | 该方向链路丢包 | 结合 mtr 定位跳数 |
| 重传间隔按 0.2s、0.4s、0.8s 递增 | RTO 指数退避 | 连续丢包，链路质量差 |
| 重传后紧跟重复 ACK | 乱序或 ACK 丢失 | 结合 out_of_order 判断 |
| `TCPLostRetransmit` 增长 | 重传包本身也丢了 | 链路质量严重恶化 |

**处置建议：**

1. 先用 `mtr` 确认丢包发生在哪一跳，区分端侧与链路。
2. 链路丢包：换线路、上专线或 CDN，必要时联系运营商。
3. 网卡大量 drop：检查环形缓冲区、队列与中断，调 `ethtool -S`。
4. MTU 问题：确认 PMTUD 是否被中间设备阻断，必要时收敛 MSS。
5. 应用侧：避免小包频繁发送，合并写入，减少交互次数。
6. 接收端零窗口：提升消费速度或增大缓冲区，而不是盲目调 TCP 参数。
7. 抓包分析前关闭抓包机的 GRO/TSO，避免把卸载后的巨包误判为异常。
8. 重传率要持续采样，结合业务高峰与运营商维度看，单次快照没有说服力。

**面试怎么答：** 先区分 RTO 重传、快速重传、乱序、虚假重传、零窗口五种现象，再给 `tshark -Y 'tcp.analysis.retransmission'` 与 `ss -ti` 两条命令，最后用「重传率 < 0.1% 正常、> 1% 需要定位」给出量化判断。

**易错点：**

- 看到重传就认定丢包，乱序也会表现为重复 ACK。
- 在抓包机开启 GRO/TSO，看到远超 MTU 的「巨包」，误判为分片。
- 只统计一次采样，忽略业务高峰与时段差异。
- 盲目调小 `tcp_retries2`，导致弱网下连接更早断开。
- 把「重传间隔呈指数增长」当成快速重传，混淆了 RTO 与三次重复 ACK 的触发条件。

## 5. 排查连接超时

**现象：** 客户端报 `connect timed out`、`Connection timed out`，或 Nginx 返回 504；请求根本到不了应用，服务端日志一片空白。

**原理：** 「连接超时」严格来说只指 TCP 握手没完成，常见断点在四处：

- **去程被丢**：安全组、防火墙 DROP、路由缺失，SYN 发出去没有回应。
- **回程被丢**：SYN/ACK 到达客户端但 ACK 回不去，表现为握手反复重试。
- **服务端不接**：端口未监听会立刻 RST（这是「拒绝」不是「超时」）；SYN 队列满则丢包，表现为超时。
- **中间设备**：NAT 会话超时、LB 后端健康检查失败、云厂商安全策略。

**排查命令（按顺序执行）：**

```bash
    # 1. 只测连接，限制 3 秒，区分超时与拒绝
    curl -v --connect-timeout 3 https://api.example.com/health

    # 2. 直接测端口，不涉及 HTTP
    nc -vz -w 3 api.example.com 443

    # 3. 没有 nc 时用 bash 内建的 TCP 连接
    timeout 3 bash -c '</dev/tcp/api.example.com/443' && echo open || echo fail

    # 4. 看逐跳路径与丢包位置
    mtr -n -c 50 api.example.com

    # 5. 确认本机监听与队列
    ss -lnt
    ss -s

    # 6. 连接跟踪表是否打满
    conntrack -S
    sysctl net.netfilter.nf_conntrack_count net.netfilter.nf_conntrack_max

    # 7. 防火墙规则与丢包计数
    sudo iptables -nvL
    sudo nft list ruleset

    # 8. 内核是否有 SYN 丢弃记录
    dmesg | grep -i 'SYN flooding\|table full'

    # 9. 抓包确认 SYN 是否发出、是否有 SYN/ACK
    sudo tcpdump -i eth0 -nn 'tcp port 443 and host 10.0.0.5'

    # 10. 查看握手重试次数与队列上限
    sysctl net.ipv4.tcp_syn_retries net.core.somaxconn net.ipv4.tcp_max_syn_backlog
```

**判读标准：**

| 抓包现象 | 含义 | 排查方向 |
| --- | --- | --- |
| 只有 SYN，无 SYN/ACK | 去程被丢或服务端未收到 | 安全组、路由、端口监听 |
| SYN 重试间隔 1s/2s/4s 递增 | 标准 TCP 重试 | 同上，属超时而非拒绝 |
| 立即 RST | 端口未监听或被拒绝 | 服务进程、监听地址 |
| SYN/ACK 有，客户端无 ACK | 回程被丢 | 客户端侧路由、NAT |
| 握手成功但无 HTTP 响应 | 应用层问题 | 不是连接超时，查 TTFB |
| `ss -lnt` 中 Recv-Q 接近上限 | backlog 已满 | 调 `somaxconn`、加快 accept |
| `curl` 立即返回 `Connection refused` | 端口未监听 | 不是超时，先查进程与监听地址 |
| `conntrack_count` 接近 max | NAT 表满，新连接被丢 | 扩大容量或缩短超时 |

**处置建议：**

1. 先确认是「超时」还是「拒绝」，两者的排查方向完全相反。
2. 用 `mtr` 判断是否在某一跳之后持续丢包，锁定运营商或机房。
3. 服务端确认监听地址是 `0.0.0.0` 而非 `127.0.0.1`。
4. 云环境依次检查安全组、网络 ACL、负载均衡健康检查。
5. backlog 满：提高 `net.core.somaxconn` 与 `tcp_max_syn_backlog`，同时优化 accept 速度。
6. NAT 超时：缩短客户端连接复用周期，或让 LB 保活。
7. 排查顺序固定为「DNS → SYN 出没出 → SYN/ACK 回没回 → 应用有无响应」，不要跳步。

**面试怎么答：** 先澄清「超时」与「拒绝」的区别，再按「DNS 是否解析 → SYN 是否发出 → 是否有 SYN/ACK → 是否握手完成」四步走，每步给一条命令；最后说明服务端侧要看监听地址、backlog、conntrack 三个点。

**易错点：**

- 把「端口未监听返回 RST」说成连接超时。
- 只从客户端排查，忽略回程路由与 NAT。
- 看到 `curl` 卡住就调大超时，掩盖了真正的丢包。
- 忘记容器与宿主机共享内核参数，改错命名空间。
- 把 `Connection refused` 也归为超时，忽略「拒绝」代表服务端明确回应。

## 6. 排查 DNS 解析失败

**现象：** 报错 `Could not resolve host`、`Name or service not known`、`Temporary failure in name resolution`，或解析时快时慢、偶发失败；容器里尤其常见。

**原理：** 解析失败有三类完全不同的原因：

- **NXDOMAIN**：域名或记录不存在，权威明确回答「没有」。
- **SERVFAIL**：递归解析器无法完成查询，常见于权威故障、DNSSEC 校验失败、上游超时。
- **超时**：53 端口被封锁、DNS 服务器不可达、查询量过大被限流。

**还要考虑解析器的行为：**

- `/etc/nsswitch.conf` 决定先查 `hosts` 还是 DNS。
- `resolv.conf` 的 `search` 会拼接域名，`ndots` 决定「先当完整域名还是先拼后缀」。
- Kubernetes 默认 `ndots:5`，`api.example.com` 这种带点的名字会先尝试 4 次 search 后缀，再查绝对域名，表现为「解析慢但不报错」。
- 同时返回 A 与 AAAA 时，若 IPv6 不可达，可能出现「解析成功但连接失败」。

**排查命令：**

```bash
    # 1. 直接查解析器，确认是否能拿到答案
    dig api.example.com A +noall +answer
    dig api.example.com AAAA +short

    # 2. 绕过本地配置，直连公共 DNS 对比
    dig @223.5.5.5 api.example.com A +short
    dig @8.8.8.8 api.example.com A +short

    # 3. 走系统解析链路（会受 nsswitch 与 search 影响）
    getent hosts api.example.com

    # 4. 查看当前生效的 DNS 配置
    cat /etc/resolv.conf
    resolvectl status

    # 5. 查看 hosts 是否覆盖
    cat /etc/hosts

    # 6. 观察完整查询过程与耗时
    dig +search api.example.com
    dig api.example.com +stats

    # 7. 确认 53 端口是否可达
    nc -vzu -w 3 223.5.5.5 53

    # 8. 容器内确认 DNS 与 ndots
    cat /etc/resolv.conf
    grep hosts /etc/nsswitch.conf
```

**判读标准：**

| 返回状态 | 含义 | 处置方向 |
| --- | --- | --- |
| `NXDOMAIN` | 域名或记录不存在 | 核对拼写、区域文件、是否漏配记录 |
| `SERVFAIL` | 解析器无法完成 | 查权威健康、DNSSEC、上游递归 |
| 查询超时无响应 | 53 被封或服务器不可达 | 换 DNS、检查安全组与防火墙 |
| `getent` 失败但 `dig` 成功 | 系统链路问题 | 查 nsswitch、search、ndots |
| 解析耗时不均匀 | search 拼接或缓存未命中 | 调 ndots、加缓存 |
| 只返回 AAAA 且不可达 | IPv6 优先但链路不通 | 关闭 AAAA 或修复 IPv6 |

**处置建议：**

1. 先用 `dig` 绕过系统链路，判断问题在 DNS 服务还是在客户端配置。
2. `NXDOMAIN` 优先核对权威记录与拼写，不要反复重启应用。
3. `SERVFAIL` 检查权威服务器可用性与 DNSSEC 配置。
4. 容器场景把 `ndots` 调到 2 左右，或直接用 FQDN（末尾加点）。
5. 内网服务用 ClusterIP 或服务发现，减少对公共 DNS 的依赖。
6. 关键链路配置两个以上 DNS，并加本地缓存，避免单点。

**面试怎么答：** 先区分 NXDOMAIN、SERVFAIL、超时三种失败语义，再按「dig 直连 → getent 走系统链路 → 看 resolv.conf/nsswitch」三步定位，最后补容器 `ndots:5` 这个高频坑。

**易错点：**

- 只用 `ping` 判断，`ping` 失败可能只是 ICMP 被禁。
- 改了 `/etc/resolv.conf` 却被 NetworkManager 或 systemd-resolved 覆盖。
- 忽略 search 域与 `ndots`，把「慢」误判为「失败」。
- 容器内只测 `dig`，没测 `getent`，漏掉 nsswitch 配置问题。

## 7. 排查 TLS 握手失败

**现象：** 浏览器报 `ERR_SSL_PROTOCOL_ERROR`、`ERR_CERT_AUTHORITY_INVALID`，curl 报 `error 35`，Java 客户端报 `PKIX path building failed`，或握手直接卡住直到超时。

**原理：** TLS 1.2 的握手要经过 ClientHello → ServerHello + Certificate → ClientKeyExchange → Finished 多个往返；TLS 1.3 精简为 1 个 RTT。失败点通常落在五处：

- **版本不匹配**：客户端只支持 TLS 1.3，服务端只开 TLS 1.0/1.1。
- **套件不匹配**：双方没有共同的加密套件，服务端返回 `handshake_failure`。
- **证书链不完整**：服务端只发叶子证书，客户端缺中间 CA，报 `unknown_ca`。
- **证书身份不符**：CN 或 SAN 不包含访问的域名，SNI 缺失时服务端可能返回默认证书。
- **时间与中间设备**：客户端时间偏差导致「证书未生效/已过期」；企业代理替换证书导致校验失败。

**排查命令：**

```bash
    # 完整握手并打印证书链，重点看最上面一行与 verify 结果
    openssl s_client -connect api.example.com:443 -servername api.example.com -showcerts </dev/null

    # 强制指定协议版本，判断是否版本不兼容
    openssl s_client -connect api.example.com:443 -servername api.example.com -tls1_2
    openssl s_client -connect api.example.com:443 -servername api.example.com -tls1_3

    # 校验证书链（需要先导出服务端证书）
    openssl s_client -connect api.example.com:443 -servername api.example.com \
        -showcerts </dev/null | openssl x509 -out /tmp/server.pem
    openssl verify -CAfile /etc/ssl/certs/ca-certificates.crt /tmp/server.pem

    # 查看有效期、签发者与 SAN
    openssl x509 -in /tmp/server.pem -noout -dates -issuer -subject -ext subjectAltName

    # 用 curl 看握手细节与 ALPN 协商结果
    curl -v https://api.example.com/ 2>&1 | grep -Ei 'SSL|TLS|ALPN|certificate'

    # 枚举服务端支持的协议与套件
    nmap --script ssl-enum-ciphers -p 443 api.example.com

    # 检查本机时间是否漂移
    date -u
    chronyc tracking

    # 抓包看握手停在哪一步，以及服务端返回的 alert
    sudo tcpdump -i eth0 -nn -s 0 -w /tmp/tls.pcap 'tcp port 443 and host 10.0.0.5'
    tshark -r /tmp/tls.pcap -Y 'tls.handshake.type == 1 || tls.alert_message'
```

**判读标准：**

| 现象 / alert | 含义 | 处置方向 |
| --- | --- | --- |
| `handshake_failure`（40） | 无共同加密套件 | 调整 `ssl_ciphers` 或升级客户端 |
| `unknown_ca`（48） | 客户端不信任签发者 | 补全中间证书链 |
| `certificate_expired`（45） | 证书已过期 | 续签并检查自动续期 |
| `protocol_version`（70） | 协议版本不支持 | 放开 TLS 1.2 或升级客户端 |
| `wrong version number` | 用 TLS 访问了明文端口 | 核对 80/443 与回源协议 |
| `bad_record_mac`（20） | 解密失败 | 查中间设备、代理、套件配置 |
| `no_application_protocol`（120） | ALPN 协商失败 | 核对 h2/http1.1 支持 |
| 握手在 ClientHello 后无响应 | 被拦截或服务端未处理 | 抓包看是否有 RST/超时 |

**处置建议：**

1. 先确认是「证书问题」还是「协议/套件问题」，`openssl s_client` 的输出会直接给出原因。
2. 证书链不全：在 Nginx 的 `ssl_certificate` 中拼接「站点证书 + 中间证书」，顺序不能反。
3. 时间偏差：部署 NTP/chrony，容器基础镜像也要同步。
4. 老客户端兼容：保留 TLS 1.2 与兼容套件，不要一刀切只开 1.3。
5. 回源场景：CDN 回源 HTTPS 时，回源 Host 与 SNI 必须与证书域名一致。
6. 企业代理：确认代理根证书是否已装入客户端信任库，否则会出现「只有办公网失败」。

**面试怎么答：** 先讲 TLS 握手的几个关键阶段，再把失败归为版本、套件、证书链、域名/SNI、时间/中间设备五类；然后给 `openssl s_client -servername -showcerts` 这条能一次性看清证书链与协商结果的命令，最后说明 `unknown_ca` 与 `handshake_failure` 的处置差异。

**易错点：**

- 只用浏览器看「证书无效」，不去确认是链不全、过期还是域名不符。
- 配了证书却漏了中间证书，桌面浏览器能自动补链，移动端与 Java 客户端失败。
- 用 IP 直连测试，导致 SNI 缺失，拿到默认站点证书后误判为证书错误。
- 服务器时间偏差，报错却是「证书未生效」，方向被带偏。

## 8. 排查高延迟与丢包

**现象：** 接口 P99 从 50ms 涨到 300ms，用户反馈「卡一下」，但服务端 CPU、内存、GC 都正常；或者 ping 平均值正常，抖动却很大。

**原理：** 端到端延迟由四部分组成：**传播延迟**（物理距离）、**传输延迟**（报文长度 / 带宽）、**排队延迟**（链路拥塞、缓冲区积压）、**处理延迟**（设备与应用）。丢包则分两类：链路真实丢包，以及设备对 ICMP/特定流量的限速丢弃。

**为什么「平均延迟正常」仍可能有问题：**

- 拥塞是突发的，均值被大量正常请求稀释，要看 P95/P99 与抖动。
- `bufferbloat`：缓冲区过大，排队延迟在拥塞时可达数百毫秒。
- 丢包会让 TCP 降窗，表现为「延迟不大但吞吐很低」。
- 无线侧的重传与切换，会带来周期性的尖刺。

**排查命令：**

```bash
    # 1. 基础连通与延迟抖动
    ping -c 100 -i 0.2 api.example.com

    # 2. 逐跳定位，观察从哪一跳开始丢包与延迟抬升
    mtr -n -c 100 api.example.com

    # 3. 路由路径（mtr 不可用时）
    traceroute -n api.example.com

    # 4. 看套接字层面的 RTT、重传、拥塞窗口
    ss -ti dst 10.0.0.5

    # 5. 查看本机队列的排队与丢弃
    tc -s qdisc show dev eth0

    # 6. 网卡层丢包与错误计数
    ip -s link show eth0
    ethtool -S eth0 | grep -Ei 'drop|err|miss'

    # 7. 抓 ICMP 与 TCP，确认是链路丢包还是限速
    sudo tcpdump -i eth0 -nn 'icmp or (tcp and host 10.0.0.5)'

    # 8. UDP 打流测丢包与抖动（需服务端配合）
    iperf3 -c 10.0.0.5 -u -b 100M -t 30
```

**判读标准：**

| 现象 | 含义 | 结论 |
| --- | --- | --- |
| 从第 N 跳开始持续丢包且后续跳也丢 | 该段链路问题 | 联系运营商或换线路 |
| 中间跳丢包但末跳正常 | 该设备对 ICMP 限速 | 不是真实丢包 |
| 平均 RTT 正常、P99 很高 | 抖动或突发拥塞 | 查队列、带宽与无线 |
| 延迟随流量上升而线性增长 | 排队延迟 | 缓冲区过大或带宽不足 |
| 丢包伴随 `ss` 中 retrans 增长 | 真实丢包 | 结合 mtr 定位 |
| 只有移动网络用户异常 | 无线侧切换/弱覆盖 | 弱网优化与超时策略 |

**处置建议：**

1. 用 `mtr` 找到「第一跳开始持续丢包」的位置，这是最有效的定位手段。
2. 中间跳单独丢包、末跳正常，先排除 ICMP 限速，不要误报障。
3. 延迟高但带宽未满：查排队与缓冲区，必要时启用 AQM（如 fq_codel）。
4. 跨地域延迟高：上专线、CDN 或全球加速，协议侧考虑 HTTP/3。
5. 无线场景：优化超时与重试，减少大包与串行请求。
6. 长期监控：按地域、运营商、接入方式分维度看 P95/P99，而不是只看均值。

**面试怎么答：** 先把延迟拆成传播、传输、排队、处理四段，说明「均值正常不代表没问题」；然后给 `mtr` 与 `ss -ti` 两条核心命令，强调「中间跳丢包但末跳正常多为 ICMP 限速」，最后按链路、带宽、无线三个方向给处置。

**易错点：**

- 只看 `ping` 平均值，忽略抖动与 P99。
- 把中间跳的 ICMP 丢包当成真实链路故障。
- 延迟高就加带宽，实际瓶颈是排队或应用处理。
- 用 ICMP 结论推断 TCP 行为，两者限速策略可能完全不同。

## 9. 排查带宽瓶颈

**现象：** 大文件下载只有几 MB/s，视频卡顿，多用户并发时整体变慢；但 CPU、内存、磁盘 IO 都不高，服务端日志也没有慢请求。

**原理：** 带宽瓶颈要看三个层次，别一上来就扩容：

- **物理带宽**：网卡、交换机、专线的上限，跑满就是硬瓶颈。
- **单流吞吐**：受 TCP 拥塞窗口与 RTT 限制，理论上限约为 `窗口 / RTT`。RTT 100ms、窗口 1MB 时，单流最多约 10MB/s，哪怕链路有 1Gbps。
- **应用层放大**：未压缩、重复下发、串行请求、大 Body，都会让「有效带宽」远低于物理带宽。

**单位换算先统一：** 带宽通常按 `Mbps`（兆比特每秒）标称，下载工具显示的是 `MB/s`。100Mbps ≈ 12.5MB/s，1Gbps ≈ 125MB/s，差 8 倍，很多「带宽不够」的误判源于此。

**排查命令：**

```bash
    # 1. 网卡实时吞吐（每列单位为 KB/s）
    sar -n DEV 1 10

    # 2. 按连接看实时流量，找出占用最高的会话
    sudo iftop -n -i eth0

    # 3. 更直观的实时曲线
    nload eth0

    # 4. 网卡累计字节、丢包、错误
    ip -s link show eth0
    ethtool -S eth0 | grep -Ei 'drop|err|miss'

    # 5. 单连接视角：RTT、cwnd、重传、发送队列
    ss -ti dst 10.0.0.5

    # 6. 多流打流，区分「链路带宽不足」与「单流受限」
    iperf3 -c 10.0.0.5 -P 4 -t 30
    iperf3 -c 10.0.0.5 -P 1 -t 30

    # 7. 查看限速与队列配置
    tc -s qdisc show dev eth0
    tc -s class show dev eth0

    # 8. 单次下载的实际速率
    curl -o /dev/null -s -w 'speed=%{speed_download} B/s total=%{time_total}\n' \
        https://static.example.com/bigfile.bin
```

**判读标准：**

| 现象 | 含义 | 处置 |
| --- | --- | --- |
| 网卡吞吐接近标称上限 | 物理带宽打满 | 升带宽、分流、上 CDN |
| 单流慢、多流正常 | 受 cwnd/RTT 限制 | 多流、调窗口、上 BBR |
| 多流也慢、网卡未满 | 链路限速或中间设备瓶颈 | 查 QoS、专线带宽、云带宽包 |
| `ss` 中 cwnd 很小且重传多 | 丢包导致降窗 | 先解决丢包 |
| 发送队列 `Send-Q` 持续堆积 | 出口拥塞 | 限流或扩容 |
| `ethtool` 中 drop/err 增长 | 网卡或驱动层丢包 | 查队列、缓冲区、硬件 |
| 带宽利用率周期性尖刺 | 突发流量 | 平滑发布、预加载、错峰 |

**处置建议：**

1. 先用 `sar`/`iftop` 确认是不是真的跑满，再谈扩容。
2. 单流受限优先考虑多流并发、增大窗口、启用 BBR，而不是直接升带宽。
3. 静态大文件上 CDN，源站只承担回源，避免边缘流量压垮出口。
4. 开启 gzip/br 压缩，减少响应体；图片转 WebP/AVIF。
5. 出口有突发：配置流量整形（`tbf`）或错峰任务。
6. 长期方案：按业务峰值规划带宽，保留 30% 余量，并监控 P95 利用率。

**面试怎么答：** 先强调单位换算与「物理带宽、单流吞吐、应用放大」三层，再给 `sar -n DEV`、`ss -ti`、`iperf3 -P` 三条命令区分瓶颈类型；最后说明「单流慢多流正常」是窗口与 RTT 的问题，不是带宽不够。

**易错点：**

- 把 Mbps 当 MB/s，误判带宽差 8 倍。
- 只测单流就断言链路带宽不足。
- 忽略重传导致的降窗，盲目扩容。
- 只盯服务器出口，忽略客户端接入带宽与 Wi-Fi。

## 10. 排查 502 与 504

**现象：** 网关或 Nginx 返回 `502 Bad Gateway` / `504 Gateway Timeout`，前端看到统一错误页，后端日志可能完全没有记录。

**原理：** 这两个状态码都属于「网关侧」错误，但根因完全不同：

- **502**：网关与上游通信失败或上游返回了无法解析的响应。典型是连接被拒、连接被提前关闭、上游返回非 HTTP 报文、回源 DNS 失败、TLS 握手失败。
- **504**：网关成功连上上游，但在超时时间内没等到响应。对应 `proxy_connect_timeout`、`proxy_read_timeout`、`proxy_send_timeout` 三个配置。
- **499**：Nginx 特有，客户端在服务端响应前主动断开，通常不是服务端故障，而是用户等不及或前端超时更短。
- **503**：服务不可用，常见于全部上游被摘除、限流或发布中。

**排查命令：**

```bash
    # 1. 实时看错误日志，重点看 upstream 相关行
    sudo tail -f /var/log/nginx/error.log

    # 2. 统计最近一段时间的错误类型
    sudo grep -E 'upstream|timed out|prematurely|no live' /var/log/nginx/error.log \
        | awk '{print $0}' | tail -n 50

    # 3. 看访问日志中的 upstream_status 与 upstream_response_time
    sudo tail -n 100 /var/log/nginx/access.log

    # 4. 确认后端端口是否真的在监听
    ss -lntp | grep -E ':8080|:8000'

    # 5. 绕过 DNS 与负载均衡，直连某一台上游
    curl -v --resolve api.example.com:443:10.0.0.11 https://api.example.com/health

    # 6. 查看当前生效的超时与重试配置
    nginx -T | grep -E 'proxy_(connect|read|send)_timeout|proxy_next_upstream|keepalive'

    # 7. 抓包看网关到上游的握手与响应
    sudo tcpdump -i eth0 -nn -A 'tcp port 8080 and host 10.0.0.11'

    # 8. 后端自身健康与资源
    curl -s -o /dev/null -w '%{http_code} %{time_total}\n' http://10.0.0.11:8080/health
    top -b -n 1 | head -n 15
```

**判读标准：**

| 错误日志关键字 | 含义 | 处置 |
| --- | --- | --- |
| `connect() failed (111: Connection refused)` | 上游未监听或已崩溃 | 拉起进程、查端口 |
| `upstream prematurely closed connection` | 上游处理中被关闭 | 查后端崩溃、超时、OOM |
| `no live upstreams` | 所有上游被健康检查摘除 | 查健康检查与后端状态 |
| `upstream timed out (110)` | 连接上游超时 | 网络、安全组、上游积压 |
| `read timeout` | 等响应超时 | 慢查询、下游阻塞、扩容 |
| `SSL_do_handshake() failed` | 回源 TLS 失败 | 证书、SNI、协议版本 |
| `client intended to send too large body` | 请求体超限 | 调 `client_max_body_size` |
| 大量 499 | 客户端提前断开 | 前端超时、首屏体验 |

**处置建议：**

1. 先区分 502 与 504，前者多是「连不上/被断开」，后者是「等太久」。
2. 502 优先查后端进程、端口监听、发布重启、OOM。
3. 504 先看慢在哪里：应用 CPU、下游依赖、数据库慢查询、锁等待。
4. 超时要分级：连接 1~3s、读 10~30s，按接口 SLA 设置，不要一律 60s。
5. 重试只对幂等请求开启，且限制次数，避免故障时流量放大。
6. 全站 5xx 突增时先限流与降级，再定位根因，避免雪崩。

**面试怎么答：** 先用一句话区分「502 是通信失败、504 是等待超时」，再按「看 error.log 关键字 → 确认端口 → 直连上游 → 查后端资源」四步排查；最后讲超时分级、幂等重试与限流降级三个工程手段。

**易错点：**

- 把 504 当成后端没启动，实际是慢查询或下游阻塞。
- 只调大 `proxy_read_timeout`，请求堆积更多，雪崩更严重。
- 对所有请求开重试，非幂等接口造成重复下单。
- 忽略 499，把用户主动断开误判为服务端 5xx。

## 11. 弱网模拟与移动网络

**现象：** 办公室与内网一切正常，用户在地铁、电梯、地下车库、演唱会现场频繁遇到超时、白屏、上传失败；日志里表现为连接超时、请求中断、重试。

**原理：** 移动网络的体验由四个因素决定：

- **RRC 状态机**：手机空闲时会释放无线承载，下一次请求需要先建立连接，首包延迟可达数百毫秒。
- **信号与切换**：弱覆盖导致丢包，基站切换带来瞬断，表现为周期性尖刺。
- **延迟与抖动**：4G/5G 的 RTT 波动大，丢包率远高于有线网络。
- **接入差异**：IPv6 优先、运营商代理、DNS 解析路径不同，都会引入额外耗时。

**弱网模拟命令（Linux 服务端或测试机）：**

```bash
    # 固定延迟 100ms，抖动 ±20ms，丢包 5%
    sudo tc qdisc add dev eth0 root netem delay 100ms 20ms loss 5%

    # 叠加乱序与重复包，更接近真实无线环境
    sudo tc qdisc add dev eth0 root netem delay 100ms 20ms loss 5% duplicate 1% reorder 25% 50%

    # 正态分布的延迟抖动
    sudo tc qdisc add dev eth0 root netem delay 200ms 50ms distribution normal

    # 限制带宽并设置排队上限，模拟弱网 + 缓冲
    sudo tc qdisc add dev eth0 root tbf rate 1mbit burst 32kbit latency 400ms

    # 查看当前规则与统计
    sudo tc qdisc show dev eth0
    sudo tc -s qdisc show dev eth0

    # 清除规则
    sudo tc qdisc del dev eth0 root
```

**移动端与浏览器侧：**

```bash
    # Android 模拟器限速与延迟
    emulator -avd Pixel_5 -netdelay gsm -netspeed gsm

    # 查看当前模拟器的网络参数
    adb emu network status
```

浏览器 DevTools 的 Network 面板内置预设（Slow 3G、Fast 3G）与自定义节流，适合验证首屏与请求瀑布；iOS 可用 Xcode 的 Network Link Conditioner，真机可用厂商的弱网测试工具。

**判读标准：**

| 现象 | 含义 | 处置 |
| --- | --- | --- |
| 首包耗时远大于后续请求 | RRC 建立或 DNS 冷启动 | 预连接、预解析、合并请求 |
| 请求瀑布串行且每步都慢 | 依赖链过长 | 并行化、减少跳数 |
| 上传失败但下载正常 | 上行带宽与丢包更差 | 分片上传、断点续传 |
| 只有特定运营商异常 | 运营商代理或 DNS | 多线路、HTTPDNS |
| 页面在 3G 下白屏 | 主包过大或超时太短 | 资源瘦身、分级加载 |
| 切换网络后请求全部失败 | 连接未重建 | 监听网络变化并重置连接池 |

**处置建议：**

1. 超时分级：连接 3s、读 10s，弱网下不要用同一套超时。
2. 重试采用指数退避 + 抖动，限制总次数，避免弱网下的重试风暴。
3. 资源瘦身：首屏只加载必要资源，图片按需与自适应分辨率。
4. 预连接与预解析：在关键路径前完成 DNS 与 TLS。
5. 支持断点续传与分片上传，避免一次失败全部重来。
6. 监控按网络类型分维度：Wi-Fi、4G、5G 的耗时与失败率要分开看。

**面试怎么答：** 先讲移动网络的四个特性（RRC、切换、抖动、接入差异），再给 `tc netem` 的完整命令与 DevTools 节流两种模拟方式；然后按「超时分级、退避重试、资源瘦身、预连接」给优化手段，最后强调监控要按网络类型拆分。

**易错点：**

- 只在办公室 Wi-Fi 下验证，忽略移动网络首包延迟。
- 重试次数不设上限，弱网下放大成倍流量。
- 用固定 30s 超时，弱网用户等待过久，体验与容量双输。
- 模拟只加延迟不加丢包，测不出重传与超时问题。

## 12. 线上网络问题案例复盘

**现象：** 某电商晚高峰 19:30 起，部分用户下单接口 504 比例从 0.2% 升至 8%，持续约 40 分钟；同一时间商品详情正常，客服收到「下单转圈」的集中反馈。

**时间线：**

| 时间 | 事件 |
| --- | --- |
| 19:28 | 促销活动开始，下单 QPS 由 800 升至 4200 |
| 19:30 | 监控出现 504，集中在华东与华南 |
| 19:33 | 504 比例到 8%，下单成功率下降到 91% |
| 19:35 | 值班先扩容应用实例，504 未明显下降 |
| 19:38 | 发现应用连接池耗尽，数据库慢查询堆积 |
| 19:42 | 限流 + 关闭非幂等重试 + 降级推荐，504 回落到 1% |
| 19:55 | 数据库慢查询优化上线，连接池恢复 |
| 20:10 | 指标恢复正常，活动继续 |

**排查命令（按实际执行顺序）：**

```bash
    # 1. 看错误分布：是 502 还是 504，集中在哪个上游
    sudo grep -E 'upstream|timed out' /var/log/nginx/error.log | tail -n 200

    # 2. 看上游响应时间与状态码
    sudo tail -n 500 /var/log/nginx/access.log | awk '{print $9, $11}'

    # 3. 确认应用端口与连接数
    ss -lnt | grep 8080
    ss -s

    # 4. 应用侧连接池与线程池指标（以实际监控平台为准）
    curl -s http://10.0.0.11:8080/actuator/metrics/hikaricp.connections.active

    # 5. 数据库当前慢查询与锁等待
    mysql -e 'SHOW PROCESSLIST;'
    mysql -e 'SHOW ENGINE INNODB STATUS\G' | head -n 60

    # 6. 抓包确认网关到应用是否出现提前关闭
    sudo tcpdump -i eth0 -nn -A 'tcp port 8080 and host 10.0.0.11' -c 200

    # 7. 确认扩容后的实例是否真的注册到上游
    curl -s http://127.0.0.1:8080/health
    nginx -T | grep -A 10 'upstream order_backend'
```

**判读标准：**

| 证据 | 结论 |
| --- | --- |
| 504 集中在 `POST /orders`，GET 正常 | 写链路问题，优先查数据库与连接池 |
| `upstream timed out` 大量出现 | 应用处理超过 `proxy_read_timeout` |
| 应用连接池 active 接近 max | 连接被占满，新请求排队 |
| 数据库 ProcessList 大量 `Sending data` | 慢查询堆积 |
| 扩容后无改善 | 瓶颈不在应用 CPU，而在下游 |
| 关闭重试后 504 明显下降 | 重试放大了流量 |

**根因：** 促销流量把下单 QPS 放大 5 倍，应用连接池（上限 200）被慢查询占满，请求排队超过 Nginx 的 30s 读超时，网关返回 504；同时客户端与服务端都对下单做了自动重试，非幂等重试进一步放大流量，形成正反馈。

**处置建议：**

1. 先止血：对下单接口限流、关闭非幂等重试、降级非核心推荐逻辑。
2. 再定位：沿「网关 → 应用连接池 → 数据库慢查询」逐层确认瓶颈。
3. 扩容要与瓶颈匹配，应用 CPU 不高时扩实例无用，应先解决下游。
4. 超时分级：下单接口读超时下调到 10s，快速失败并释放连接。
5. 事后优化慢查询、增加索引、拆分热点写、连接池按峰值重新评估。
6. 压测复现：用促销峰值 QPS 做全链路压测，验证扩容与限流阈值。

**复盘产出（要可执行，不要只写感受）：**

| 改进项 | 负责人 | 期限 |
| --- | --- | --- |
| 下单接口超时从 30s 调整为 10s | 后端 | 本周 |
| 非幂等接口禁用自动重试 | 后端 + 前端 | 本周 |
| 慢查询加索引并接入慢日志告警 | DBA | 两周 |
| 连接池上限按压测结果重算 | 后端 | 两周 |
| 5xx 告警按接口与状态码拆分 | SRE | 一周 |
| 大促前全链路压测纳入发布流程 | 测试 | 下次大促前 |

**面试怎么答：** 用 STAR 结构讲：现象与影响面 → 时间线 → 按「网关、应用、数据库」三层取证 → 根因（连接池耗尽 + 慢查询 + 重试放大）→ 止血与修复 → 复盘产出。重点体现「先止损再定位」和「扩容不等于解决瓶颈」。

**易错点：**

- 一上来就扩容，没确认瓶颈在下游，浪费扩容窗口。
- 只盯 504 数量，不看具体接口与状态码分布。
- 忽略重试放大，止血动作缺失，故障时间被拉长。
- 复盘只写「加强监控」，没有负责人、期限与验证标准。
