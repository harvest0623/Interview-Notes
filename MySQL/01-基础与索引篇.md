## 1. MySQL 的整体架构（连接层、Server 层、存储引擎层）

**MySQL 是「连接层 + Server 层 + 可插拔存储引擎层」的三层架构**：连接层负责网络、认证与线程管理；Server 层负责 SQL 解析、优化、执行以及跨引擎的通用能力；存储引擎层只负责数据的物理存取与事务、锁、索引等引擎特性。一条 SQL 的执行链路是「连接 → 解析 → 预处理 → 优化 → 执行 → 引擎接口 → 返回结果」。

**分层职责：**

| 层次 | 主要组件 | 核心职责 | 备注 |
| --- | --- | --- | --- |
| 连接层 | 连接管理、认证、权限校验、线程模型、SSL | 建立 TCP 连接、校验账号密码与库权限、为每个连接分配线程 | 社区版是「一连接一线程」，企业版才有线程池 |
| Server 层 | 解析器、预处理器、优化器、执行器、内置函数、存储过程/触发器/视图、binlog | 词法语法分析、语义检查、生成并选择执行计划、调用引擎接口、写 binlog | 与引擎无关，所有引擎共用 |
| 存储引擎层 | InnoDB、MyISAM、Memory、Archive、TempTable | 管理页、索引、事务、锁、MVCC、缓冲池、崩溃恢复 | 插件式，按表指定引擎 |

**一条查询的完整流程：**

1. **连接建立**：客户端与 `mysqld` 建 TCP 连接，服务端做认证；认证通过后从 `thread_cache` 取线程或新建线程，绑定会话变量。
2. **解析**：解析器做词法与语法分析，产出语法树。此阶段只校验 SQL 语法，不校验表是否存在。
3. **预处理**：检查表、列是否存在，展开 `*`，检查权限，把 `SELECT` 中的别名、视图、子查询做语义解析。
4. **优化**：逻辑改写（外连接转内连接、子查询物化/半连接、常量传播），基于成本模型选择索引、连接顺序、排序方式，生成执行计划。
5. **执行**：执行器按计划调用存储引擎的 `handler` 接口（`index_read`、`rnd_next`、`update_row` 等），逐行取数并做 Server 层过滤、排序、聚合。
6. **返回**：结果集按协议写给客户端；若开启 binlog，则在事务提交阶段写 binlog（两阶段提交）。
7. **清理**：释放表锁/MDL、归还连接线程。

**各层关键参数与查看方式：**

```sql
-- 1. 确认默认存储引擎与当前实例支持的引擎
SHOW VARIABLES LIKE 'default_storage_engine';
SHOW ENGINES;

-- 2. 连接层：连接数与线程情况
SHOW VARIABLES LIKE 'max_connections';
SHOW VARIABLES LIKE 'thread_cache_size';
SHOW STATUS LIKE 'Threads_connected';   -- 当前已建立连接
SHOW STATUS LIKE 'Threads_running';     -- 正在执行的连接（不含 Sleep）
SHOW STATUS LIKE 'Threads_created';     -- 累计创建线程数，增长快说明 thread_cache 偏小

-- 3. Server 层：优化器为什么选了这个索引
SET optimizer_trace = 'enabled=on';
SELECT id, name FROM users WHERE age = 20 AND city = '杭州';
SELECT TRACE FROM information_schema.OPTIMIZER_TRACE\G
SET optimizer_trace = 'enabled=off';

-- 4. Server 层各阶段耗时（performance_schema，需要相应 UPDATE 权限）
UPDATE performance_schema.setup_instruments
   SET ENABLED = 'YES' WHERE NAME LIKE 'stage/%';
UPDATE performance_schema.setup_consumers
   SET ENABLED = 'YES' WHERE NAME LIKE '%events_stages%';
SELECT EVENT_NAME, ROUND(TIMER_WAIT / 1e9, 3) AS ms
FROM performance_schema.events_stages_history_long
ORDER BY TIMER_START DESC LIMIT 10;
```

**8.0 与 5.7 的架构差异：**

- **查询缓存被移除**：8.0 彻底删除 `query_cache`，`SHOW VARIABLES LIKE 'query_cache%'` 为空；5.7 虽保留但默认关闭，且写多读少场景命中率极低。
- **数据字典**：5.7 用 `.frm` 文件 + MyISAM 系统表存元数据；8.0 改为 InnoDB 中的事务型数据字典，DDL 具备原子性。
- **临时表引擎**：8.0 引入 `TempTable` 引擎替代部分 `MEMORY` 临时表，支持变长与 BLOB，减少内存浪费。
- **binlog 默认格式**：5.7.7 起与 8.0 均为 `ROW`。

**面试怎么答：** 先给出「三层 + 插件式引擎」的总判断，再用一条 `SELECT` 串起「连接 → 解析 → 预处理 → 优化 → 执行 → 引擎 → 返回」，接着点出 Server 层与引擎层的边界（binlog、函数、跨表 JOIN 在 Server 层；索引、事务、锁在引擎层），最后补两个加分项：8.0 删除查询缓存与数据字典事务化。

**易错点：**

- 解析器不检查表是否存在，表/列校验在预处理阶段完成，所以「语法正确但表不存在」的报错发生在解析之后。
- 优化器只负责生成计划，真正的取数在执行器；`EXPLAIN` 看到的是优化器的估算，不是实际执行统计。
- binlog 属于 Server 层，与引擎无关；redo log 才是 InnoDB 独有的。
- 存储引擎不解析 SQL，它只接受 `handler` 接口的「按索引读一行 / 读下一行 / 更新一行」这类调用。
- 社区版没有真正的线程池，连接数过高时线程切换与内存开销会拖垮实例，不能只靠调大 `max_connections` 解决。

## 2. InnoDB 与 MyISAM 的区别与选型

**InnoDB 是支持事务、行级锁、MVCC、外键与崩溃恢复的通用引擎，MyISAM 是不支持事务、表级锁、以读为主的老式引擎**。MySQL 5.5 起默认引擎为 InnoDB，新项目除极特殊的只读归档场景外都应选 InnoDB。

**核心差异：**

| 维度 | InnoDB | MyISAM |
| --- | --- | --- |
| 事务 | 支持 ACID，redo/undo 保障 | 不支持，`ROLLBACK` 无效 |
| 锁粒度 | 行锁（基于索引）+ 意向锁，另有表锁 | 表级读写锁，并发写差 |
| 并发控制 | MVCC，读写不阻塞 | 无 MVCC，读写互斥 |
| 索引结构 | 聚簇索引，叶子存整行；二级索引存主键 | 非聚簇索引，索引与数据分离，叶子存行地址 |
| 主键 | 必须有（无则用隐藏 row_id） | 可以没有 |
| 外键 | 支持 | 不支持 |
| 崩溃恢复 | redo + doublewrite，可自动恢复 | 无 redo，崩溃后可能需 `REPAIR TABLE`，可能丢数据 |
| 行数统计 | `COUNT(*)` 需扫描最小的二级索引 | 元数据保存精确行数，`COUNT(*)` 无 `WHERE` 时 O(1) |
| 全文索引 | 5.6 起支持 | 支持 |
| 空间与压缩 | 支持表空间、页压缩、`COMPRESSED` | 支持 `myisampack` 只读压缩 |
| 缓存 | 缓冲池缓存数据页与索引页 | 只缓存索引，数据依赖 OS page cache |
| 典型场景 | OLTP、订单、账户、任何需要事务的表 | 只读日志归档、临时中间表（历史用法） |

**文件结构差异：**

- InnoDB：8.0 默认 `innodb_file_per_table=ON`，每表一个 `.ibd`；Undo 在 undo 表空间，Redo 在 `#innodb_redo`（8.0.30+）或 `ib_logfile*`。
- MyISAM：每表三个文件 `.frm`（8.0 已无）、`.MYD`（数据）、`.MYI`（索引）。

**动手验证差异：**

```sql
-- 建两张只有引擎不同的表
CREATE TABLE t_innodb (
  id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  memo VARCHAR(64) NOT NULL DEFAULT '',
  PRIMARY KEY (id)
) ENGINE=InnoDB;

CREATE TABLE t_myisam (
  id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  memo VARCHAR(64) NOT NULL DEFAULT '',
  PRIMARY KEY (id)
) ENGINE=MyISAM;

-- 1. 事务：MyISAM 的 ROLLBACK 不会回滚已插入的数据
START TRANSACTION;
INSERT INTO t_myisam (memo) VALUES ('myisam-row');
ROLLBACK;
SELECT COUNT(*) AS myisam_rows FROM t_myisam;   -- 结果为 1，回滚无效

START TRANSACTION;
INSERT INTO t_innodb (memo) VALUES ('innodb-row');
ROLLBACK;
SELECT COUNT(*) AS innodb_rows FROM t_innodb;   -- 结果为 0，回滚生效

-- 2. 计数：MyISAM 直接读元数据；InnoDB 需要扫描最小的二级索引
EXPLAIN SELECT COUNT(*) FROM t_myisam;
EXPLAIN SELECT COUNT(*) FROM t_innodb;          -- type=index，key 为最小的二级索引

-- 3. 表状态：Rows 是估算值，MyISAM 相对准确
SHOW TABLE STATUS LIKE 't_innodb'\G
SHOW TABLE STATUS LIKE 't_myisam'\G

-- 4. 崩溃修复（MyISAM 专用，可能丢数据，生产慎用）
CHECK TABLE t_myisam;
REPAIR TABLE t_myisam;

-- 5. 清理测试表
DROP TABLE t_innodb, t_myisam;
```

**选型结论：**

1. **默认选 InnoDB**：事务、行锁、崩溃恢复是业务底线，MyISAM 一旦掉电可能整表损坏。
2. **不要用 MyISAM 存流水/日志**：表锁会让写入串行化，且无事务无法保证多条记录一致。
3. **只读归档**可考虑 MyISAM 或更合适的列存/对象存储，但现代方案多选 InnoDB 压缩表或 OLAP 引擎。
4. **Memory 引擎**只适合会话级临时数据，重启即丢，且不支持 BLOB/TEXT。
5. 5.7 的系统表仍是 MyISAM，8.0 数据字典已改为 InnoDB，因此「系统表都是 MyISAM」的说法在 8.0 不再成立。

**面试怎么答：** 用「事务 / 锁 / 索引结构 / 崩溃恢复 / 计数」五个维度对比即可，重点讲清「InnoDB 行锁基于索引、MyISAM 只有表锁」和「MyISAM 的 `COUNT(*)` 快是因为元数据存了行数，而不是扫描更高效」，最后给出选型结论：OLTP 一律 InnoDB。

**易错点：**

- MyISAM 的表锁不是「完全不能并发读」：共享读锁可以并发，读写、写写才互斥。
- MyISAM 支持全文索引，InnoDB 从 5.6 起也支持，不能用「只有 MyISAM 有全文索引」作为选型理由。
- InnoDB 的 `COUNT(*)` 慢不是缺陷，而是 MVCC 下不同事务看到不同行数，无法缓存一个全局精确值。
- `SHOW TABLE STATUS` 的 `Rows` 是估算值，InnoDB 误差可能很大，不能用于精确对账。
- MyISAM 的 `REPAIR TABLE` 可能丢行，且修复期间表不可用；有备份优先用备份恢复。

## 3. 为什么用 B+ 树而不是 B 树、红黑树、哈希

**InnoDB 选 B+ 树，本质是为了「用最少的磁盘 IO 定位范围数据」**：B+ 树是非叶子节点只存键和页号的高扇出多叉树，树矮、每层一个 16KB 页、叶子节点用双向链表串联，因此等值查询稳定在 3~4 次 IO，范围查询和排序可以顺着叶子链表顺序扫描。

**先算一笔扇出账（InnoDB 页大小 16KB）：**

| 层级 | 每条记录大小构成 | 单页可存数量 | 累计可索引行数 |
| --- | --- | --- | --- |
| 非叶子（BIGINT 主键） | 8B 键 + 6B 页号 = 14B | 16384 / 14 ≈ 1170 | 1 层 ≈ 1170 |
| 非叶子 2 层 | 同上 | 1170 × 1170 | ≈ 137 万 |
| 叶子（假设每行 1KB） | 16 行/页 | 1170 × 1170 × 16 | ≈ 2190 万 |
| 叶子（假设每行 200B） | 80 行/页 | 1170 × 1170 × 80 | ≈ 1.1 亿 |

结论：**千万级表通常 3 层，十亿级表 4 层**，每次查询最多 3~4 次页访问，且根节点与热页常驻缓冲池，真实物理 IO 往往只有 0~1 次。

**四类结构对比：**

| 结构 | 等值查询 | 范围查询 | 排序 | 树高（2000 万行） | 磁盘友好度 | 结论 |
| --- | --- | --- | --- | --- | --- | --- |
| B+ 树 | O(log₁₁₇₀N)，稳定 | 叶子链表顺序扫描，极优 | 可直接复用索引顺序 | 3 | 极好，页对齐 | InnoDB 采用 |
| B 树 | O(log N)，非叶也存数据 | 需中序回溯，跨层跳转 | 较差 | 3~4 | 较好，但扇出小 | 范围查询与空间利用率差 |
| 红黑树 | O(log₂N) ≈ 25 次 | 中序遍历，随机跳转 | 一般 | 25 | 差，每层一次 IO | 内存结构，不适合磁盘 |
| 哈希 | O(1)，无冲突时 | 不支持 | 不支持 | — | 随机分布 | 只适合等值，且不支持最左前缀 |
| 跳表 | O(log N) | 有序链表，较优 | 支持 | 内存结构 | 差（多层指针） | Redis 等内存存储使用 |

**逐项说明：**

1. **为什么不是 B 树**：B 树的非叶子节点也存整行数据，单页能放的键更少，扇出下降、树更高；范围查询需要在树中反复中序回溯，无法像 B+ 树那样在叶子链表上顺序扫描。B+ 树还把「内部节点」与「数据节点」解耦，内部节点常驻内存后命中率极高。
2. **为什么不是红黑树**：红黑树是二叉结构，2000 万行高度约 25，最坏 25 次随机磁盘 IO；每次旋转/变色只解决平衡，不解决「一次 IO 只读一个键」的磁盘局部性问题。
3. **为什么不是哈希**：哈希只支持等值，`WHERE age > 20`、`ORDER BY`、`LIKE '张%'`、联合索引最左前缀都无法使用；且哈希冲突会退化。InnoDB 的「自适应哈希索引（AHI）」只是缓冲池热页的自动加速结构，不能显式创建，也不改变 SQL 层语义。
4. **为什么不是跳表**：跳表靠多层指针做二分，节点分散、指针跳转导致随机 IO，适合内存（Redis zset）；磁盘场景下 B+ 树的页内连续布局更优。

**验证索引规模与缓冲池命中率：**

```sql
-- 页大小：InnoDB 默认 16KB，建库后不可改
SHOW VARIABLES LIKE 'innodb_page_size';

-- 从统计表看索引占用的页数（估算值，需有权限）
SELECT table_name, index_name, stat_name, stat_value
FROM mysql.innodb_index_stats
WHERE database_name = 'demo'
  AND table_name = 'users'
  AND stat_name IN ('size', 'n_leaf_pages', 'n_diff_pfx01')
ORDER BY index_name, stat_name;

-- 缓冲池命中率：越接近 1 越好
SHOW STATUS LIKE 'Innodb_buffer_pool_read_requests';  -- 逻辑读次数
SHOW STATUS LIKE 'Innodb_buffer_pool_reads';          -- 落到磁盘的物理读次数
-- 命中率 = 1 - Innodb_buffer_pool_reads / Innodb_buffer_pool_read_requests

-- 自适应哈希索引的使用情况（SHOW ENGINE INNODB STATUS 的对应段落）
SHOW VARIABLES LIKE 'innodb_adaptive_hash_index';
SHOW ENGINE INNODB STATUS\G

-- 对比：等值、范围、排序三种访问方式
EXPLAIN SELECT * FROM users WHERE id = 100;              -- const，一次定位
EXPLAIN SELECT * FROM users WHERE id BETWEEN 100 AND 200; -- range，叶子链表扫描
EXPLAIN SELECT * FROM users ORDER BY id LIMIT 10;        -- 直接利用聚簇索引顺序，无 filesort
```

**面试怎么答：** 先给结论「B+ 树矮、扇出大、叶子有序」，再算扇出（1170 × 1170 × 16 ≈ 2000 万/3 层），然后逐个否定：B 树非叶存数据导致扇出小且范围查询要回溯；红黑树是二叉树、25 层、每层一次 IO；哈希不支持范围/排序/最左前缀，InnoDB 只有自适应哈希。最后补一句「索引高度不等于 IO 次数，根节点常驻缓冲池」。

**易错点：**

- 「B+ 树 3 层所以查一次要 3 次磁盘 IO」不准确：非叶节点通常已在缓冲池，真实物理读可能为 0。
- B+ 树叶子存整行只适用于**聚簇索引**；二级索引叶子存的是索引列 + 主键。
- InnoDB 不能像 Memory 引擎那样显式建 `USING HASH` 索引，`USING HASH` 会被忽略或报错。
- 哈希索引并非「一定更快」：高并发下哈希冲突、全表扫描、范围查询都吃亏，且无法利用最左前缀。
- 页大小不是越大越好：16KB 是 IO 与空间的折中，改 `innodb_page_size` 必须在初始化时指定。

## 4. 聚簇索引、二级索引与回表

**聚簇索引（clustered index）是按主键组织、叶子节点存放整行数据的索引；二级索引（secondary index）的叶子只存「索引列 + 主键值」，因此通过二级索引查非索引列时，必须再拿主键去聚簇索引查一次，这就是回表**。回表是随机 IO，次数多时优化器可能直接放弃二级索引改走全表扫描。

**两种索引的结构差异：**

| 维度 | 聚簇索引 | 二级索引（辅助索引） |
| --- | --- | --- |
| 组织键 | 主键 | 用户指定的索引列 |
| 叶子内容 | 完整行记录（含隐藏列） | 索引列 + 主键值（InnoDB 自动附加） |
| 数量 | 每表只有一个 | 可有多个 |
| 查询路径 | 一次 B+ 树即可拿到整行 | 先查二级索引拿主键，再回表 |
| 范围扫描 | 按主键顺序，天然有序 | 按索引列顺序，主键顺序被打乱 |
| 更新代价 | 主键变更代价极高（行迁移） | 主键变更需重建所有二级索引 |

**聚簇索引的选择规则：**

1. 有主键 → 用主键。
2. 无主键 → 选第一个「所有列都 `NOT NULL` 的唯一索引」。
3. 都没有 → InnoDB 生成 6 字节隐藏列 `DB_ROW_ID` 作为聚簇键，对用户不可见。
4. 因此「表可以没有主键」只是语法上成立，物理上一定有聚簇索引。

**回表的代价：**

- 二级索引按 `name` 有序，主键在叶子中是无序的，回表是**随机页访问**。
- 若命中 1 万行，最坏是 1 万次随机读；缓冲池命中时是内存访问，未命中则是磁盘 IO。
- 优化器会估算「回表成本 + 二级索引扫描成本」与「全表扫描成本」，当二级索引过滤后行数占比很高（经验上超过约 20%~30%）时，可能选择全表扫描。

**完整示例：**

```sql
CREATE TABLE users (
  id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  name VARCHAR(32) NOT NULL,
  age TINYINT UNSIGNED NOT NULL DEFAULT 0,
  city VARCHAR(32) NOT NULL DEFAULT '',
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  KEY idx_name (name)
) ENGINE=InnoDB;

-- 1. 走二级索引 + 回表：需要 name 之外的城市、年龄
EXPLAIN SELECT id, name, age, city FROM users WHERE name = '张三';
-- key=idx_name，Extra 无 Using index → 需要回表

-- 2. 只查索引列 + 主键：二级索引叶子已含主键，无需回表
EXPLAIN SELECT id, name FROM users WHERE name = '张三';
-- Extra: Using index

-- 3. 主键查询：直接走聚簇索引
EXPLAIN SELECT * FROM users WHERE id = 100;

-- 4. 看索引里到底有哪些列（二级索引会隐含主键）
SHOW INDEX FROM users;
-- idx_name 的 Column_name 只有 name，但叶子实际存储 (name, id)

-- 5. 强制走二级索引，观察回表成本（仅用于对比，生产慎用）
EXPLAIN SELECT * FROM users FORCE INDEX (idx_name) WHERE name = '张三';
EXPLAIN SELECT * FROM users IGNORE INDEX (idx_name) WHERE name = '张三';

-- 6. 范围扫描时二级索引的主键顺序是乱的
EXPLAIN SELECT id, name FROM users WHERE name BETWEEN '张' AND '赵' ORDER BY id;
-- 若 ORDER BY 主键，可能无法同时利用 idx_name 的顺序，出现 filesort
```

**主键设计对回表的影响：**

- **自增 BIGINT 主键**：插入总在聚簇索引最右侧，页分裂少，二级索引里的主键也短。
- **UUID 主键**：随机写入导致页分裂与碎片；16/36 字节让所有二级索引膨胀，缓冲池能缓存的页数下降，回表更慢。
- **业务字段做主键**：一旦业务键变更，需要迁移整行并重建全部二级索引，代价极高。

**面试怎么答：** 先画「聚簇索引叶子 = 整行，二级索引叶子 = 索引列 + 主键」，再说回表的定义与随机 IO 代价，接着讲优化器为什么会因为回表太多而放弃索引，最后落到主键选型：自增 BIGINT、避免 UUID、主键尽量短（二级索引都会带一份）。

**易错点：**

- 「二级索引查出主键再回表」是 InnoDB 的固定行为，不是优化器可选的；只有覆盖索引能避免。
- 没有主键时不是「没有聚簇索引」，而是用隐藏 `DB_ROW_ID` 建聚簇索引，无法被用户使用。
- `SELECT id FROM t WHERE name = ?` 通常是覆盖索引，因为二级索引叶子自带主键，不要再画蛇添足加 `id` 到索引里。
- 回表次数多不代表一定慢：命中缓冲池时是内存随机访问，真正致命的是磁盘随机 IO。
- 主键不要用 `VARCHAR(255)` 之类的大字段，它会被复制到每一个二级索引的叶子里。

## 5. 覆盖索引与索引下推

**覆盖索引解决「能不能不回表」，索引下推（ICP）解决「回表前能不能少回几行」**。覆盖索引指查询用到的所有列都包含在某个索引中（二级索引自动包含主键），执行计划出现 `Using index`；索引下推指 MySQL 5.6 起把索引列上的条件下推到存储引擎，在回表之前就用索引记录过滤，执行计划出现 `Using index condition`。

**两者的定位对比：**

| 维度 | 覆盖索引（Covering Index） | 索引下推（Index Condition Pushdown） |
| --- | --- | --- |
| 解决的问题 | 避免回表 | 减少无效回表次数 |
| 触发条件 | 查询列 ⊆ 索引列（含主键） | 条件列在索引中，但无法用于定位（如范围后的列、`LIKE '%x'`） |
| Extra 标志 | `Using index` | `Using index condition` |
| 版本 | 一直支持 | 5.6+，`optimizer_switch` 中 `index_condition_pushdown=on` |
| 适用索引 | 二级索引 / 聚簇索引均可 | 主要对二级索引有意义 |
| 效果 | 一次索引扫描即返回 | 索引扫描次数不变，回表次数下降 |

**索引下推的执行过程：**

假设索引 `idx_name_age (name, age)`，SQL 为：

```sql
SELECT * FROM users WHERE name LIKE '张%' AND age = 20;
```

1. **无 ICP**：引擎按 `name LIKE '张%'` 做范围扫描，把每条记录的整行返回给 Server 层；Server 层再判断 `age = 20`，不满足则丢弃。`age` 列明明在索引里，却要回表后才能过滤。
2. **有 ICP**：引擎在扫描索引时就判断 `age = 20`，只对满足两条条件的记录回表。扫描的索引条目数不变，但回表次数从「所有姓张的记录」降为「姓张且 20 岁」。

**可执行示例：**

```sql
-- 联合索引：name 用于前缀范围，age 无法用于定位但可用于 ICP
ALTER TABLE users ADD INDEX idx_name_age (name, age);

-- 1. 覆盖索引：只查索引列，Extra = Using index
EXPLAIN SELECT name, age FROM users WHERE name = '张三';

-- 2. 需要回表，但 age 条件下推，Extra = Using index condition
EXPLAIN SELECT id, name, age, city FROM users
WHERE name LIKE '张%' AND age = 20;

-- 3. 关闭 ICP 做对比（会话级，仅用于验证）
SET optimizer_switch = 'index_condition_pushdown=off';
EXPLAIN SELECT id, name, age, city FROM users
WHERE name LIKE '张%' AND age = 20;
SET optimizer_switch = 'index_condition_pushdown=on';

-- 4. 看优化器实际用了索引的哪几段（used_key_parts 能看出定位到哪一列）
EXPLAIN FORMAT=JSON
SELECT id, name, age, city FROM users
WHERE name LIKE '张%' AND age = 20\G

-- 5. 覆盖索引的典型误用：SELECT * 直接破坏覆盖
EXPLAIN SELECT * FROM users WHERE name = '张三';   -- 无 Using index
EXPLAIN SELECT id, name FROM users WHERE name = '张三'; -- Using index
```

**覆盖索引的常见构造方式：**

1. **只查业务需要的列**：把 `SELECT *` 改成明确列，是最简单的优化。
2. **扩展联合索引**：高频查询 `WHERE user_id = ? ORDER BY created_at` 且只返回 `status`，可建 `(user_id, created_at, status)`。
3. **利用二级索引自带主键**：`SELECT id FROM t WHERE name = ?` 天然覆盖。
4. **注意索引长度**：为了覆盖而把大字段（`VARCHAR(255)`、`TEXT` 前缀）加进索引，会让索引膨胀、写入变慢，需要权衡。

**面试怎么答：** 先区分两个概念：覆盖索引是「索引里有所有列，不用回表」，标志是 `Using index`；ICP 是「把索引列上的条件下推到引擎，在回表前过滤」，标志是 `Using index condition`，5.6 引入。再举 `(name, age)` 配 `name LIKE '张%' AND age = 20` 的例子说明 ICP 减少回表，最后补一句「ICP 不减少索引扫描量，只减少回表量；覆盖索引则连回表都不需要」。

**易错点：**

- `Using index` 与 `Using index condition` 不是一回事，前者表示覆盖，后者表示下推，二者可能同时出现。
- ICP 只对「索引中但无法用于定位」的条件有效；如果条件列不在索引里，仍然只能回表后由 Server 层过滤。
- `SELECT *` 几乎必然破坏覆盖索引，这是 ORM 框架最常见的性能坑。
- 覆盖索引仍要扫描索引页，范围很大时并不快；它不是「免 IO 金牌」。
- 为了覆盖而无限扩列会让索引变大，写入放大、缓冲池命中率下降，收益可能为负。

## 6. 最左前缀原则与索引失效场景

**联合索引 `(a, b, c)` 按 a→b→c 的顺序排序，B+ 树只能从最左列开始连续匹配，因此查询条件必须包含最左列才能用于定位，这就是最左前缀原则**；违反前缀、对列做运算、隐式类型转换、前导模糊等都会让索引「失效」——更准确地说，是无法用于定位，或只能部分使用。

**能用到哪几列：**

| 查询条件 | 能否定位 | 说明 |
| --- | --- | --- |
| `a = 1` | 用 a | 最左前缀 |
| `a = 1 AND b = 2` | 用 a、b | 连续前缀 |
| `a = 1 AND b = 2 AND c = 3` | 用 a、b、c | 全列命中 |
| `a = 1 AND c = 3` | 只用 a | c 无法定位，但可用于 ICP |
| `b = 2` | 不用 | 缺少最左列 |
| `b = 2 AND c = 3` | 不用 | 缺少最左列 |
| `a > 1 AND b = 2` | 用 a 定位，b 仅 ICP | 范围列之后的列不能继续定位 |
| `a = 1 AND b > 2 AND c = 3` | 用 a、b 定位，c 仅 ICP | 同上 |
| `a = 1 ORDER BY b` | 用 a 定位 + 索引顺序排序 | 无 filesort |
| `a = 1 ORDER BY c` | 只用 a | 排序无法利用索引，filesort |

**常见失效场景与可执行对比：**

```sql
CREATE TABLE orders (
  id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  user_id BIGINT UNSIGNED NOT NULL,
  order_no VARCHAR(32) NOT NULL,
  status TINYINT UNSIGNED NOT NULL DEFAULT 0,
  amount DECIMAL(10,2) NOT NULL DEFAULT 0.00,
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  remark VARCHAR(64) NOT NULL DEFAULT '',
  PRIMARY KEY (id),
  KEY idx_user_status_created (user_id, status, created_at)
) ENGINE=InnoDB;

-- 1. 函数/运算：索引列被包住，无法定位
EXPLAIN SELECT * FROM orders WHERE DATE(created_at) = '2026-10-01';   -- 失效
EXPLAIN SELECT * FROM orders
 WHERE created_at >= '2026-10-01' AND created_at < '2026-10-02';      -- 改写后可用

-- 2. 隐式类型转换：order_no 是 varchar，传数字会把列转成 double 比较
EXPLAIN SELECT * FROM orders WHERE order_no = 20261001001;            -- 失效
EXPLAIN SELECT * FROM orders WHERE order_no = '20261001001';          -- 可用

-- 3. 前导模糊：只有前缀匹配能定位
EXPLAIN SELECT * FROM orders WHERE order_no LIKE '%2026%';            -- 失效
EXPLAIN SELECT * FROM orders WHERE order_no LIKE '2026%';             -- range

-- 4. 违反最左前缀
EXPLAIN SELECT * FROM orders WHERE status = 1;                        -- 失效
EXPLAIN SELECT * FROM orders WHERE user_id = 1 AND status = 1;        -- 可用

-- 5. 范围列之后的列只能 ICP
EXPLAIN SELECT * FROM orders
 WHERE user_id = 1 AND status > 0 AND created_at > '2026-01-01';      -- created_at 仅 ICP

-- 6. OR 一侧无索引
EXPLAIN SELECT * FROM orders WHERE user_id = 1 OR remark = 'urgent';  -- 可能全表

-- 7. 排序方向与索引不一致（8.0 可用降序索引解决）
EXPLAIN SELECT * FROM orders WHERE user_id = 1 ORDER BY created_at DESC;      -- 可复用索引
EXPLAIN SELECT * FROM orders WHERE user_id = 1 ORDER BY status DESC, created_at ASC; -- 混合方向，可能 filesort
```

**为什么隐式转换会失效：**

- 列是 `VARCHAR`、常量是数字时，MySQL 会把**字符串列逐行转成 `DOUBLE`** 再比较，列上发生函数运算，索引失效。
- 列是 `INT`、常量是字符串时，MySQL 把**常量转成数字**，列本身不变，索引仍可用。
- 经验规则：**以列的类型为准**，让常量去适配列，而不是让列去适配常量。

**为什么 `OR` 会失效：**

- `WHERE a = 1 OR b = 2`，若 `b` 无索引，优化器只能全表扫描；若两侧都有索引，可能走 `index_merge`（`Using union`），但代价高、常不被选择。
- 改写为 `UNION ALL` 往往更稳定。

**面试怎么答：** 先用「联合索引是一本按 a、b、c 排序的字典」解释最左前缀，再列 5 类高频失效：列上函数/运算、隐式类型转换、前导模糊、违反最左前缀、范围列之后的列；补充 `OR` 与排序方向两个细节。最后强调「失效不等于完全不用索引」，很多情况是「只能用于 ICP 过滤」。

**易错点：**

- `WHERE b = 2 AND a = 1` 与 `WHERE a = 1 AND b = 2` 等价，优化器会自动调整等值条件顺序，不要把它当成最左前缀的反例。
- `LIKE '张%'` 可以用索引，`LIKE '%张'` 不行；`LIKE '%张%'` 若覆盖索引，仍可能走全索引扫描而非全表。
- `!=`、`NOT IN`、`IS NOT NULL` 不是绝对失效，低选择性时优化器会主动放弃，高选择性时仍可能走 range。
- 范围条件之后的列不是「完全没用」，`Using index condition` 表示它参与了引擎层过滤。
- 字符集/排序规则不一致（`utf8mb4` 列与 `utf8mb3` 常量）会触发隐式转换，是容易被忽略的失效原因。

## 7. 联合索引的字段顺序如何设计

**联合索引的顺序遵循「等值列在前、范围列在后、排序/分组列紧跟等值列、区分度高的列优先」**；等值条件之间的顺序对定位影响不大（优化器会调整），但会显著影响排序能力、覆盖能力与索引体积，因此不能只按「区分度从高到低」机械排列。

**设计步骤：**

1. **列出该索引要服务的所有 SQL**（同一张表通常 3~5 条高频查询共享一个联合索引）。
2. **把等值条件列放最左**：`tenant_id`、`user_id`、`status` 这类 `=` 或 `IN` 的列。
3. **把范围条件列放最后**：`created_at BETWEEN`、`amount >` 之后的列无法继续定位。
4. **排序/分组列紧跟在等值列之后**：`WHERE user_id = ? ORDER BY created_at DESC` → `(user_id, created_at)`；若排序前还有范围列，排序就用不上索引。
5. **在等值列内部按区分度排序**：区分度高的在前，能让范围扫描更早收敛；但若某列几乎总是等值且区分度低（如 `status`），放在等值列末尾也可接受。
6. **考虑覆盖**：把 `SELECT` 中的小字段追加到索引末尾，避免回表，但要评估索引膨胀。
7. **控制列数**：单索引不超过 5 列，单表索引不超过 5 个，避免写放大。

**顺序对排序的影响：**

| SQL | 推荐索引 | 原因 |
| --- | --- | --- |
| `WHERE user_id=? ORDER BY created_at DESC` | `(user_id, created_at)` | 等值 + 排序 |
| `WHERE user_id=? AND status=? ORDER BY created_at` | `(user_id, status, created_at)` | 两个等值 + 排序 |
| `WHERE user_id=? AND created_at>? ORDER BY created_at` | `(user_id, created_at)` | 范围列同时承担排序 |
| `WHERE user_id=? AND status=? ORDER BY amount` | `(user_id, status, amount)` | 排序字段必须在等值列之后 |
| `WHERE user_id=? ORDER BY status, created_at` | `(user_id, status, created_at)` | 排序字段顺序要与索引一致 |
| `WHERE user_id=? ORDER BY created_at DESC, id DESC` | `(user_id, created_at, id)` | 8.0 可建全降序索引 |

**8.0 降序索引：**

- 5.7 语法上接受 `INDEX (a DESC)`，但会被忽略，实际仍是升序。
- 8.0 真正支持降序索引，`ORDER BY a DESC, b ASC` 这种混合方向可以通过 `INDEX (a DESC, b ASC)` 消除 filesort。
- 若所有排序列方向一致，普通升序索引也能反向扫描，不必额外建降序索引。

**可执行示例：**

```sql
-- 目标 SQL：
-- SELECT id, status, amount FROM orders
--  WHERE tenant_id = ? AND status = ? AND created_at >= ?
--  ORDER BY created_at DESC LIMIT 20;

-- 方案 A：等值在前、范围在后
ALTER TABLE orders ADD INDEX idx_a (tenant_id, status, created_at);

-- 方案 B：再追加覆盖列（amount），避免回表
ALTER TABLE orders ADD INDEX idx_b (tenant_id, status, created_at, amount);

-- 对比执行计划
EXPLAIN SELECT id, status, amount FROM orders
 WHERE tenant_id = 1 AND status = 1 AND created_at >= '2026-01-01'
 ORDER BY created_at DESC LIMIT 20;

EXPLAIN FORMAT=JSON SELECT id, status, amount FROM orders
 WHERE tenant_id = 1 AND status = 1 AND created_at >= '2026-01-01'
 ORDER BY created_at DESC LIMIT 20\G
-- 关注 used_key_parts、key_length、是否出现 filesort

-- 错误顺序：范围列放在等值列前面，后面的等值列无法定位
ALTER TABLE orders ADD INDEX idx_bad (created_at, tenant_id, status);
EXPLAIN SELECT * FROM orders WHERE tenant_id = 1 AND status = 1 AND created_at >= '2026-01-01';
-- key 可能是 idx_bad，但只能用到 created_at 一段，tenant_id/status 退化为过滤

-- 删除错误索引，避免冗余
ALTER TABLE orders DROP INDEX idx_bad;
```

**区分度怎么量：**

```sql
-- 单列区分度：越接近 1 越适合做索引前缀
SELECT
  COUNT(DISTINCT tenant_id) / COUNT(*) AS tenant_sel,
  COUNT(DISTINCT status)    / COUNT(*) AS status_sel,
  COUNT(DISTINCT created_at)/ COUNT(*) AS created_sel
FROM orders;

-- 组合区分度：判断联合索引整体过滤能力
SELECT COUNT(*) AS total,
       COUNT(DISTINCT tenant_id, status, created_at) AS combos,
       COUNT(DISTINCT tenant_id, status, created_at) / COUNT(*) AS combo_sel
FROM orders;
```

**面试怎么答：** 按「等值 → 排序 → 范围 → 覆盖」四步说，强调「范围列之后无法定位」和「排序字段要与索引顺序、方向一致」；再补「等值列之间顺序影响不大，但区分度高的放前面能减少扫描」「不要为每条 SQL 建一个索引，要合并共用前缀」，最后提 8.0 降序索引。

**易错点：**

- 把区分度最高的列一律放最左是教条：若它总是范围条件，放最左会让后续等值列全部失效。
- `IN` 在 MySQL 里通常按多个等值处理，可以放在等值区，但 `IN (大量值)` 会膨胀成多次范围扫描。
- `ORDER BY` 的字段若在范围列之后，仍然无法利用索引排序。
- 索引 `(a, b)` 与 `(b, a)` 不是冗余关系，能否共用要看查询的最左前缀。
- 覆盖列追加太多会让索引页变宽，可能反而增加 IO，需用 `EXPLAIN` + 实际耗时验证。

## 8. 如何读懂 EXPLAIN 执行计划

**`EXPLAIN` 展示优化器选定的访问路径，核心看四件事：访问类型 `type`、实际使用的索引 `key` 与索引长度 `key_len`、预估扫描行数 `rows` 与过滤比例 `filtered`、以及 `Extra` 中的排序/临时表/覆盖/下推信息**。MySQL 8.0.18 起可用 `EXPLAIN ANALYZE` 看到真实执行耗时与循环次数。

**字段含义：**

| 字段 | 含义 | 重点关注 |
| --- | --- | --- |
| `id` | 查询序号 | 相同 id 从上往下执行；id 越大越先执行；`NULL` 表示 union 结果 |
| `select_type` | 查询类型 | `SIMPLE`、`PRIMARY`、`SUBQUERY`、`DERIVED`、`UNION` |
| `table` | 访问的表 | `<derivedN>`、`<unionM,N>` 表示临时结果 |
| `partitions` | 命中分区 | 分区裁剪是否生效 |
| `type` | 访问类型 | 性能等级核心指标 |
| `possible_keys` | 候选索引 | 仅作参考，可能包含用不上的索引 |
| `key` | 实际使用的索引 | `NULL` 表示未使用索引 |
| `key_len` | 使用到的索引字节数 | 反推用了联合索引的哪几列 |
| `ref` | 与索引比较的列/常量 | `const`、`func`、其他表的列 |
| `rows` | 预估扫描行数 | 估算值，不是精确值 |
| `filtered` | 剩余条件过滤后的行占比 | 与 `rows` 相乘估算最终行数 |
| `Extra` | 补充信息 | 覆盖、下推、排序、临时表、连接算法 |

**`type` 性能等级（从好到差）：**

| type | 含义 | 典型场景 |
| --- | --- | --- |
| `system` | 表只有一行（系统表） | 极少见 |
| `const` | 主键/唯一索引等值命中至多一行 | `WHERE id = 1` |
| `eq_ref` | 联表时被驱动表用主键/唯一索引等值匹配 | `JOIN ... ON a.id = b.id` |
| `ref` | 普通二级索引等值匹配 | `WHERE name = '张三'` |
| `fulltext` | 全文索引 | `MATCH ... AGAINST` |
| `ref_or_null` | `ref` 且包含 `IS NULL` | `WHERE name = 'x' OR name IS NULL` |
| `index_merge` | 合并多个索引 | `Using union/intersect` |
| `range` | 索引范围扫描 | `BETWEEN`、`>`、`IN`、前缀 `LIKE` |
| `index` | 扫描整棵索引树 | 覆盖索引但无过滤条件 |
| `ALL` | 全表扫描 | 无索引或优化器放弃索引 |

**`key_len` 反推联合索引用了几列：**

| 列类型 | 索引占字节 | 说明 |
| --- | --- | --- |
| `TINYINT` | 1 | — |
| `INT` | 4 | — |
| `BIGINT` | 8 | — |
| `DATETIME` | 5（5.6.4 起，含 5.7/8.0） | 带小数秒再加 0~3 字节 |
| `DATE` | 3 | — |
| `VARCHAR(32) utf8mb4` | 32×4 + 2 = 130 | 变长长度前缀 2 字节 |
| `CHAR(32) utf8mb4` | 32×4 = 128 | 定长 |
| 可空列 | 额外 +1 | NULL 标志位 |

例：索引 `(user_id BIGINT, status TINYINT, created_at DATETIME)`，`key_len = 8 + 1 + 5 = 14` 表示三列全用上；`key_len = 9` 表示只用了 `user_id + status`。

**`Extra` 常见值：**

| Extra | 含义 | 是否需优化 |
| --- | --- | --- |
| `Using index` | 覆盖索引，无回表 | 好 |
| `Using index condition` | 索引下推，回表前过滤 | 好 |
| `Using where` | Server 层还有过滤条件 | 视情况 |
| `Using filesort` | 无法用索引顺序排序 | 需关注 |
| `Using temporary` | 使用了临时表（GROUP BY、DISTINCT、UNION） | 需关注 |
| `Using join buffer` | 被驱动表无索引，用了 join buffer | 需优化 |
| `Using MRR` | 多范围读，二级索引回表排序优化 | 一般好 |
| `Using index for group-by` | 索引完成分组 | 好 |
| `Using index for skip scan` | 8.0.13+ 跳过最左列扫描 | 视情况 |

**可执行示例：**

```sql
-- 1. 基础 EXPLAIN
EXPLAIN SELECT id, user_id, status FROM orders
WHERE user_id = 1 AND status = 1
ORDER BY created_at DESC LIMIT 10;

-- 2. JSON 格式：能看到 used_key_parts、cost、是否覆盖
EXPLAIN FORMAT=JSON SELECT id, user_id, status FROM orders
WHERE user_id = 1 AND status = 1
ORDER BY created_at DESC LIMIT 10\G

-- 3. TREE 格式：8.0 支持，直观看连接与排序
EXPLAIN FORMAT=TREE SELECT * FROM orders WHERE user_id = 1;

-- 4. ANALYZE：8.0.18+ 真实执行，输出 actual time、rows、loops
EXPLAIN ANALYZE SELECT id, user_id, status FROM orders
WHERE user_id = 1 AND status = 1
ORDER BY created_at DESC LIMIT 10;

-- 5. 对比 const / range / ALL 三种 type
EXPLAIN SELECT * FROM orders WHERE id = 1;
EXPLAIN SELECT * FROM orders WHERE user_id BETWEEN 1 AND 100;
EXPLAIN SELECT * FROM orders WHERE remark = 'urgent';

-- 6. 联表看驱动顺序与 eq_ref
EXPLAIN SELECT o.id, u.name
FROM orders o JOIN users u ON u.id = o.user_id
WHERE o.user_id = 1;
```

**怎么读一条计划：**

1. 看 `type`：出现 `ALL` 且表大，优先处理。
2. 看 `key`：是否为预期索引；`possible_keys` 有但 `key` 为 `NULL`，说明优化器认为全表更便宜（统计信息、回表成本、选择性）。
3. 看 `key_len`：联合索引用了几列，是否被范围条件截断。
4. 看 `rows × filtered`：估算最终参与的行数，判断索引过滤能力。
5. 看 `Extra`：`filesort`、`temporary`、`join buffer` 是三大常见瓶颈。
6. 用 `EXPLAIN ANALYZE` 验证估算是否离谱，估算与实际差一个数量级时执行 `ANALYZE TABLE` 更新统计。

**面试怎么答：** 按「type → key/key_len → rows/filtered → Extra」的顺序讲，能背出 `const > eq_ref > ref > range > index > ALL`，说明 `key_len` 可以反推联合索引用了几列，`Using index` 是覆盖、`Using index condition` 是下推、`Using filesort/Using temporary` 要警惕，最后提 8.0 的 `EXPLAIN ANALYZE` 能看真实耗时。

**易错点：**

- `rows` 是优化器的估算值，统计信息过期时会严重失真，不能当作真实扫描行数。
- `type=index` 不是「用了索引就快」，它表示扫描整棵索引树，和 `ALL` 一样是「扫全部」。
- `Using filesort` 不一定落盘：数据量小于 `sort_buffer_size` 时在内存排序，但仍说明无法利用索引顺序。
- `possible_keys` 有值而 `key` 为 `NULL` 是正常现象，优化器基于成本放弃了索引。
- `EXPLAIN` 在 8.0.18 之前只做计划不执行；`EXPLAIN ANALYZE` 会真实执行 SQL，写操作不要随便加。

## 9. 慢查询的定位与优化流程

**慢查询治理是一条闭环：先确保慢日志采集完整，再按「总耗时占比」排序找出 Top SQL，用 `EXPLAIN`/`EXPLAIN ANALYZE` 定位瓶颈，最后从「索引 → SQL 改写 → 表结构 → 架构」逐层优化并回归验证**。不要一上来就加索引，先确认慢在扫描、锁等待、排序还是回表。

**采集配置：**

| 参数 | 作用 | 建议 |
| --- | --- | --- |
| `slow_query_log` | 是否开启慢日志 | 生产必开，8.0 支持动态开启 |
| `slow_query_log_file` | 日志路径 | 独立磁盘，避免与数据盘争 IO |
| `long_query_time` | 超过多少秒记录 | 一般 0.5~1 秒；核心接口可降到 0.1 |
| `log_queries_not_using_indexes` | 记录未走索引的语句 | 谨慎开启，小表也会刷屏 |
| `log_slow_admin_statements` | 记录 `ALTER`、`ANALYZE` 等管理语句 | 建议开 |
| `log_slow_replica_statements` | 记录从库回放的慢语句（8.0.26+，旧名 `log_slow_slave_statements`） | 排查复制延迟时开 |
| `min_examined_row_limit` | 扫描行数低于该值不记录 | 过滤小查询噪音 |
| `log_output` | `FILE` / `TABLE` / 两者 | 默认 `FILE`，写入 `mysql.slow_log` 会与业务争锁 |

```sql
-- 1. 动态开启慢日志（8.0 支持，无需重启）
SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 1;
SET GLOBAL log_slow_admin_statements = ON;
-- 仅短期排查使用，避免日志暴涨
SET GLOBAL log_queries_not_using_indexes = ON;

SHOW VARIABLES LIKE 'slow_query_log%';
SHOW VARIABLES LIKE 'long_query_time';
SHOW VARIABLES LIKE 'log_output';

-- 2. 若 log_output 含 TABLE，可直接查 mysql.slow_log
SELECT start_time, query_time, lock_time, rows_examined, rows_sent, db, sql_text
FROM mysql.slow_log
ORDER BY start_time DESC
LIMIT 20;

-- 3. 用 performance_schema 做聚合排序（推荐，开销小于全量日志解析）
SELECT
  SCHEMA_NAME,
  DIGEST_TEXT,
  COUNT_STAR AS exec_count,
  ROUND(SUM_TIMER_WAIT / 1e12, 2) AS total_sec,
  ROUND(AVG_TIMER_WAIT / 1e9, 2) AS avg_ms,
  SUM_ROWS_EXAMINED AS rows_examined,
  SUM_ROWS_SENT AS rows_sent,
  SUM_NO_INDEX_USED AS no_index_used
FROM performance_schema.events_statements_summary_by_digest
ORDER BY SUM_TIMER_WAIT DESC
LIMIT 10;

-- 4. sys 库现成视图：全表扫描、临时表、排序
SELECT * FROM sys.statements_with_full_table_scans LIMIT 10;
SELECT * FROM sys.statements_with_temp_tables LIMIT 10;

-- 5. 单条 SQL 的真实执行细节
EXPLAIN ANALYZE
SELECT id, user_id, amount FROM orders
WHERE user_id = 1 AND status = 1
ORDER BY created_at DESC
LIMIT 20;

-- 6. 更新统计信息（统计失真导致选错索引时）
ANALYZE TABLE orders;
```

**日志分析工具：**

```bash
# 按总耗时排序取前 10 条（mysqldumpslow 自带）
mysqldumpslow -s t -t 10 /var/lib/mysql/slow.log

# 按平均耗时排序，并过滤 SELECT
mysqldumpslow -s at -t 10 -g 'SELECT' /var/lib/mysql/slow.log

# pt-query-digest：输出指纹、总耗时占比、执行次数、样例 SQL
pt-query-digest /var/lib/mysql/slow.log > slow_report.txt
```

**标准优化流程：**

1. **确认现象**：是单条慢、周期性慢，还是整体抖动；区分「执行慢」与「等锁慢」（`lock_time` 高说明锁等待）。
2. **找 Top SQL**：按 `SUM_TIMER_WAIT` 排序，优先处理「总耗时占比高」的语句，而不是单次最慢的语句。
3. **看执行计划**：`type` 是否 `ALL`、`key` 是否符合预期、`rows` 是否远大于返回行数、`Extra` 是否有 `filesort`/`temporary`。
4. **定位瓶颈类型**：
   - 扫描行数大 → 索引缺失/失效/选择性差。
   - 回表多 → 覆盖索引、减少 `SELECT *`。
   - 排序/分组 → 调整索引顺序、减少结果集、分页。
   - 锁等待 → 缩短事务、调整加锁顺序、降隔离级别（谨慎）。
   - 临时表 → 优化 `GROUP BY`、避免 `DISTINCT` 大字段。
5. **改写 SQL**：去掉函数包裹、拆分 `OR`、大 `IN` 改 `JOIN`、深分页改游标、批量写改小批次。
6. **结构与架构**：加索引、拆表、归档冷数据、读写分离、缓存。
7. **回归验证**：对比 `EXPLAIN ANALYZE` 的 `actual time` 与 `rows`，观察 `Innodb_rows_read`、`Slow_queries` 指标。

**面试怎么答：** 按「采集 → 排序 → 解释计划 → 分类定位 → 优化 → 验证」六步讲，强调「按总耗时排序而不是单次最慢」「先看 `rows_examined` 与 `rows_sent` 的比值」「`lock_time` 高说明是锁问题不是索引问题」，最后给出常见手段：索引、覆盖、改写、分页、归档、读写分离。

**易错点：**

- `long_query_time` 只统计语句执行阶段，网络传输与客户端处理不计入；`lock_time` 单位是秒且精度有限。
- 慢日志只记录执行超过阈值的语句，**不会记录被锁等待卡住但最终很快的语句**的完整上下文。
- `log_queries_not_using_indexes` 在生产可能写出 GB 级日志，必须配合 `min_examined_row_limit`。
- 只优化单次最慢的 SQL 往往收益有限，应按「总耗时 = 单次耗时 × 调用次数」排序。
- `ANALYZE TABLE` 会更新统计信息但会短暂加锁，大表应在低峰执行（InnoDB 通常为轻量扫描）。

## 10. 深分页的性能问题与优化

**`LIMIT offset, size` 的代价与 offset 成正比**：MySQL 必须先扫描并丢弃前 `offset` 行，若查询需要回表，还要对每行做一次回表，最后只返回 `size` 行。翻到第 10 万页时，扫描量与回表量都是灾难性的。核心解法是「让数据库只定位起点，不数中间行」——游标（keyset）分页、延迟关联、覆盖索引预取主键。

**三种方案对比：**

| 方案 | 写法 | 优点 | 缺点 | 适用场景 |
| --- | --- | --- | --- | --- |
| 传统 `LIMIT offset` | `LIMIT 1000000, 20` | 简单、支持跳页 | 越翻越慢，回表量大 | 浅分页（前几百页） |
| 延迟关联 | 子查询先取主键再 JOIN | 不改接口语义，减少回表 | 仍需扫描 offset 行索引 | 必须支持跳页且要回表 |
| 游标/Keyset | `WHERE id > last_id LIMIT 20` | 稳定 O(size)，无 offset 扫描 | 不支持随机跳页 | 信息流、导出、滚动加载 |
| 覆盖索引预取 | 先查 id 再按 id 取详情 | 减少回表与数据传输 | 两次查询、需额外网络往返 | 列表页 + 详情补全 |

**为什么延迟关联有效：**

- 原 SQL `SELECT * FROM orders WHERE user_id = 1 ORDER BY id LIMIT 1000000, 20`：扫描 100 万行索引，再回表 100 万次（即使只返回 20 行）。
- 延迟关联：子查询只查 `id`（覆盖索引，不回表），扫描 100 万行索引后只对最终 20 个 id 回表。把「100 万次回表」降为「20 次回表」。
- 注意：如果 `ORDER BY` 列不在索引中，子查询本身也要 filesort，延迟关联救不了排序成本。

**可执行示例（先造 10 万行数据）：**

```sql
-- 允许递归 CTE 生成 10 万行（默认上限 1000）
SET SESSION cte_max_recursion_depth = 100000;

INSERT INTO orders (user_id, order_no, status, amount, created_at)
WITH RECURSIVE seq(n) AS (
  SELECT 1
  UNION ALL
  SELECT n + 1 FROM seq WHERE n < 100000
)
SELECT
  n % 1000,                                   -- 1000 个用户
  CONCAT('NO', LPAD(n, 10, '0')),             -- 订单号
  n % 4,                                      -- 状态 0~3
  ROUND(RAND() * 1000, 2),                    -- 金额
  NOW() - INTERVAL n MINUTE                    -- 时间递减
FROM seq;

-- 1. 传统深分页：扫描 + 丢弃 10 万行，回表 10 万次
EXPLAIN ANALYZE
SELECT * FROM orders ORDER BY id LIMIT 100000, 20;

-- 2. 延迟关联：子查询只取主键（覆盖索引），再回表 20 次
EXPLAIN ANALYZE
SELECT o.*
FROM orders o
JOIN (
  SELECT id FROM orders ORDER BY id LIMIT 100000, 20
) t ON o.id = t.id
ORDER BY o.id;

-- 3. 游标分页：从上一页最后一个 id 继续，扫描量恒定为 20 行
EXPLAIN ANALYZE
SELECT * FROM orders WHERE id > 100000 ORDER BY id LIMIT 20;

-- 4. 带业务条件的游标分页（要求 (user_id, id) 有索引）
EXPLAIN ANALYZE
SELECT * FROM orders
WHERE user_id = 1 AND id > 5000
ORDER BY id
LIMIT 20;

-- 5. 覆盖索引预取：先拿 id 列表，再按 id 批量查详情
SELECT id FROM orders WHERE user_id = 1 ORDER BY id LIMIT 100000, 20;
SELECT * FROM orders WHERE id IN (100001, 100002, 100003);
```

**游标分页的边界处理：**

- 排序键必须**唯一且稳定**：单列 `id` 最好；若按 `created_at` 排序，必须加 `id` 作为次级排序键，否则同一时间戳会漏行/重复。
- 对应的复合游标条件：`WHERE (created_at, id) < ('2026-10-01 10:00:00', 12345) ORDER BY created_at DESC, id DESC`，并建索引 `(created_at, id)`。
- 前端需要「上一页」时，可缓存每页的起止游标，或反向查询。

**面试怎么答：** 先解释 `LIMIT offset` 的成本模型「扫描 offset+size 行、回表 offset 次、丢弃 offset 行」，再给三档方案：浅分页直接 `LIMIT`；必须跳页用延迟关联把回表降到 size 次；信息流用游标分页把复杂度降为 O(size)。最后补一句「排序字段必须有索引，否则瓶颈是 filesort 而不是 offset」。

**易错点：**

- 延迟关联不是万能的：子查询若不能覆盖索引，仍要回表；若 `ORDER BY` 无索引，仍要 filesort。
- 游标分页不支持随机跳页，产品上要改成「下一页/加载更多」，或额外维护页码到游标的映射。
- `LIMIT 100000, 20` 与 `LIMIT 20 OFFSET 100000` 完全等价，换写法不解决问题。
- 只把 `SELECT *` 改成 `SELECT id` 而不改分页方式，仍需扫描 offset 行，只是省了回表。
- 导出场景不要用分页循环，改用主键区间批量拉取，避免长事务与重复扫描。

## 11. 索引选择性、基数与冗余索引

**选择性（selectivity）= 不重复值个数 / 总行数，越接近 1 过滤能力越强；基数（cardinality）是优化器对不重复值的估算，来自采样统计，不是精确值**。选择性决定「这个索引值不值得建」，基数决定「优化器会不会用」。冗余索引则是「前缀被其他索引覆盖或完全重复」的索引，只会增加写入与 DDL 成本。

**判断标准：**

| 指标 | 计算方式 | 经验阈值 | 说明 |
| --- | --- | --- | --- |
| 单列选择性 | `COUNT(DISTINCT col)/COUNT(*)` | > 0.1 值得考虑 | 性别、状态这类 < 0.01 的列不适合单列索引 |
| 平均匹配行数 | `COUNT(*)/COUNT(DISTINCT col)` | < 表行数的 10%~30% | 匹配行太多时优化器倾向全表扫描 |
| 联合选择性 | `COUNT(DISTINCT a,b)/COUNT(*)` | 越高越好 | 组合过滤能力的真实指标 |
| 基数 | `SHOW INDEX` 的 `Cardinality` | 与真实 distinct 接近 | 采样估算，可能严重偏差 |
| 前缀选择性 | `COUNT(DISTINCT LEFT(col,n))/COUNT(*)` | 接近全列选择性 | 用于长字符串前缀索引 |

**冗余与重复的判定：**

| 情况 | 是否冗余 | 处理 |
| --- | --- | --- |
| `(a)` 与 `(a, b)` | 是，前者被前缀覆盖 | 删除 `(a)`，除非它更短且高频 |
| `(a, b)` 与 `(b, a)` | 否 | 服务不同最左前缀 |
| `(a, b)` 与 `(a, b, c)` | 是 | 保留更长的，评估覆盖需求 |
| 两个完全相同的索引 | 是（重复） | 删除一个 |
| 主键 `(id)` 与 `(id, x)` | 否 | 后者可服务 `ORDER BY x` |
| 索引列已包含在主键中（联合主键前缀） | 视情况 | 聚簇索引已有序，二级索引可能仍需要 |

**可执行示例：**

```sql
-- 1. 单列与组合选择性
SELECT
  COUNT(*) AS total,
  COUNT(DISTINCT city) AS city_distinct,
  ROUND(COUNT(DISTINCT city) / COUNT(*), 4) AS city_sel,
  COUNT(DISTINCT city, age) AS city_age_distinct,
  ROUND(COUNT(DISTINCT city, age) / COUNT(*), 4) AS city_age_sel
FROM users;

-- 2. 优化器眼里的基数（估算值）
SHOW INDEX FROM users;
SELECT table_name, index_name, column_name, cardinality, seq_in_index
FROM information_schema.statistics
WHERE table_schema = 'demo' AND table_name = 'users'
ORDER BY index_name, seq_in_index;

-- 3. 手动刷新统计信息（会短暂加锁，低峰执行）
ANALYZE TABLE users;

-- 4. 长字符串前缀索引：找到区分度足够的最短前缀
SELECT
  ROUND(COUNT(DISTINCT LEFT(email, 8))  / COUNT(*), 4) AS sel_8,
  ROUND(COUNT(DISTINCT LEFT(email, 12)) / COUNT(*), 4) AS sel_12,
  ROUND(COUNT(DISTINCT LEFT(email, 16)) / COUNT(*), 4) AS sel_16,
  ROUND(COUNT(DISTINCT email) / COUNT(*), 4)           AS sel_full
FROM users;

ALTER TABLE users ADD INDEX idx_email_prefix (email(12));

-- 5. 冗余索引与未使用索引（sys 库，依赖 performance_schema 统计）
SELECT * FROM sys.schema_redundant_indexes;
SELECT * FROM sys.schema_unused_indexes
WHERE object_schema = 'demo';

-- 6. 删除索引前先确认没有查询依赖（示例）
ALTER TABLE users DROP INDEX idx_name_age;
```

**统计信息为什么会让优化器选错索引：**

- InnoDB 默认 `innodb_stats_persistent=ON`，统计信息持久化在 `mysql.innodb_index_stats`，采样页数由 `innodb_stats_persistent_sample_pages` 控制（默认 20）。
- 数据分布剧烈变化（批量导入、大量删除）后统计未更新，`rows` 估算可能差几个数量级。
- 表数据倾斜严重时，均匀采样会低估热点值的行数；可对热点列使用直方图（8.0 支持 `ANALYZE TABLE ... UPDATE HISTOGRAM ON col`）。

```sql
-- 8.0 直方图：帮助优化器识别数据倾斜
ANALYZE TABLE orders UPDATE HISTOGRAM ON status WITH 32 BUCKETS;
SELECT * FROM information_schema.COLUMN_STATISTICS
WHERE SCHEMA_NAME = 'demo' AND TABLE_NAME = 'orders';
```

**面试怎么答：** 先给定义与公式，说明「选择性看过滤能力、基数看优化器估算」，再讲冗余索引判定（前缀覆盖、完全重复），最后落到实践：低选择性列不做单列索引但可作为联合索引的过滤列；长字符串用前缀索引并验证区分度；索引数量控制在 5 个以内；用 `sys.schema_unused_indexes` 清理。

**易错点：**

- `Cardinality` 是采样估算，`SHOW INDEX` 的数字可能比真实 `COUNT(DISTINCT)` 小很多，不能直接当准确值。
- 选择性高不等于一定走索引：还要看回表成本、表大小、`ORDER BY` 需求。
- 前缀索引不能用于覆盖索引（除非查询只需要前缀列），也不能支持 `ORDER BY` 完整列。
- 删除「冗余」索引前要确认没有查询依赖它的长度优势（短索引可能更快）。
- 索引越多写越慢：每个二级索引都要维护 B+ 树、占用缓冲池，并放大 DDL 与迁移成本。

## 12. 表设计规范与字段类型选择

**表设计的核心是「主键短而有序、字段类型够用且精确、尽量避免 NULL 与大字段、索引数量可控」**。字段类型一旦上线再改代价很高（尤其是大表 DDL），因此建表阶段就要按「取值范围 + 精度 + 排序/比较需求」选型，而不是一律用 `VARCHAR(255)` 或 `BIGINT`。

**字段类型选择：**

| 场景 | 推荐类型 | 理由 | 避免 |
| --- | --- | --- | --- |
| 主键 | `BIGINT UNSIGNED` 自增 / 雪花 ID | 有序插入、8 字节、范围大 | `UUID`、`VARCHAR` 随机串 |
| 状态/枚举 | `TINYINT UNSIGNED` | 1 字节，配合字典表 | `VARCHAR(10)`、`ENUM`（改值需 DDL） |
| 金额 | `DECIMAL(18,2)` / `BIGINT` 存分 | 精确十进制，无浮点误差 | `FLOAT`、`DOUBLE` |
| 时间 | `DATETIME`（8.0 占 5 字节） | 范围到 9999 年，不带时区转换 | `TIMESTAMP`（2038 上限、受时区影响） |
| 布尔 | `TINYINT(1)` | 语义清晰、可扩展 | `ENUM('Y','N')` |
| 短字符串 | `VARCHAR(n)` 按实际长度 | 变长存储，避免浪费 | 一律 `VARCHAR(255)` |
| 长文本/JSON | `TEXT`/`JSON` 拆到扩展表 | 避免行溢出、减少主表 IO | 放主表高频查询 |
| IP | `INT UNSIGNED`（IPv4）/ `VARBINARY(16)`（IPv6） | 4/16 字节，可范围查询 | `VARCHAR(45)` |
| 手机号 | `VARCHAR(20)` | 保留前导 0、可含国际码 | `BIGINT`（丢失前导 0） |
| 性别/小集合 | 不单独建索引 | 选择性极低 | 单列索引 |

**建表规范清单：**

1. **必须有主键**，优先自增 `BIGINT UNSIGNED`；分布式场景用雪花 ID，但要注意时钟回拨与长度。
2. **所有字段尽量 `NOT NULL` + 默认值**：NULL 让索引统计、`COUNT`、比较语义复杂化，且每行多占 1 字节 NULL 标志。
3. **字符集统一 `utf8mb4`**，排序规则 8.0 默认 `utf8mb4_0900_ai_ci`；不要用 `utf8`（实为 `utf8mb3`，不支持 emoji）。
4. **单表字段数控制在 30 以内**，大字段（`TEXT`/`BLOB`）拆到扩展表，避免行溢出与主表页分裂。
5. **索引数量 ≤ 5**，联合索引优先，避免低选择性单列索引。
6. **适度反范式**：高频列表页可冗余 `user_name` 等字段，减少 JOIN，但要有同步机制。
7. **单表容量规划**：InnoDB 单表建议控制在千万级、容量 100GB 以内，超过后考虑归档、分区或分库分表。
8. **命名规范**：表名小写下划线、索引 `idx_列名`、唯一索引 `uk_列名`，布尔字段用 `is_` 前缀。
9. **避免用 `SELECT *`**：字段变更会影响覆盖索引与网络传输。
10. **DDL 预留扩展**：常用扩展属性放 `ext` JSON 或扩展表，避免频繁加列。

**可执行建表示例：**

```sql
CREATE TABLE `order_info` (
  `id`            BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '主键',
  `order_no`      VARCHAR(32)     NOT NULL                COMMENT '业务订单号，唯一',
  `user_id`       BIGINT UNSIGNED NOT NULL                COMMENT '用户 ID',
  `shop_id`       BIGINT UNSIGNED NOT NULL DEFAULT 0      COMMENT '店铺 ID',
  `status`        TINYINT UNSIGNED NOT NULL DEFAULT 0     COMMENT '0 待支付 1 已支付 2 已发货 3 已完成 4 已取消',
  `pay_amount`    DECIMAL(12,2)   NOT NULL DEFAULT 0.00   COMMENT '实付金额（元）',
  `currency`      CHAR(3)         NOT NULL DEFAULT 'CNY'  COMMENT '币种',
  `receiver_phone` VARCHAR(20)    NOT NULL DEFAULT ''     COMMENT '收货手机号',
  `remark`        VARCHAR(200)    NOT NULL DEFAULT ''     COMMENT '备注',
  `created_at`    DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  `updated_at`    DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
  `is_deleted`    TINYINT UNSIGNED NOT NULL DEFAULT 0     COMMENT '软删除标记',
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_order_no` (`order_no`),
  KEY `idx_user_created` (`user_id`, `created_at`),
  KEY `idx_shop_status_created` (`shop_id`, `status`, `created_at`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci COMMENT='订单主表';

-- 1. 看表结构、字符集、行格式
SHOW CREATE TABLE order_info\G
SHOW TABLE STATUS LIKE 'order_info'\G

-- 2. 字段长度是否被滥用（统计平均长度）
SELECT
  AVG(CHAR_LENGTH(remark)) AS avg_remark_len,
  MAX(CHAR_LENGTH(remark)) AS max_remark_len,
  COUNT(*) AS total
FROM order_info;

-- 3. 时间类型范围对比（8.0）
-- DATETIME  : 1000-01-01 ~ 9999-12-31，占 5 字节，不做时区转换
-- TIMESTAMP : 1970-01-01 ~ 2038-01-19，占 4 字节，写入/读取按会话时区转换
SELECT @@session.time_zone, @@global.time_zone;

-- 4. 字符集与排序规则检查
SELECT table_name, table_collation
FROM information_schema.tables
WHERE table_schema = 'demo' AND table_name = 'order_info';

-- 5. 金额不要用浮点：对比精度损失
SELECT CAST(0.1 AS DOUBLE) + CAST(0.2 AS DOUBLE) AS float_sum;  -- 0.30000000000000004
SELECT CAST(0.1 AS DECIMAL(10,2)) + CAST(0.2 AS DECIMAL(10,2)) AS dec_sum; -- 0.30
```

**为什么主键不建议用 UUID：**

- **页分裂**：UUID 随机，插入位置随机，16KB 页频繁分裂，产生碎片与空洞。
- **索引膨胀**：二级索引叶子要带主键，36 字节 UUID 让每个二级索引都变大，缓冲池可缓存的页数下降。
- **比较慢**：字符串比较比整数比较慢，且 UUID 无序，范围查询与分页效率低。
- 若必须用全局唯一 ID，用「雪花 ID（BIGINT）」或「有序 UUID（UUID v7 / 有序化改造）」。

**面试怎么答：** 按「主键 → 字段类型 → 约束 → 索引 → 容量」五块讲：主键自增 BIGINT、字段够用且精确（金额 DECIMAL、时间 DATETIME、状态 TINYINT）、尽量 NOT NULL、字符集 utf8mb4、索引不超过 5 个、大字段拆表、大表提前规划归档/分片。最后补一个反例：UUID 主键导致页分裂与二级索引膨胀。

**易错点：**

- `utf8` 在 MySQL 中是 `utf8mb3`（最多 3 字节），存不了 emoji，必须用 `utf8mb4`。
- `VARCHAR(255)` 不是「越大越安全」：排序、临时表、内存临时表会按最大长度分配，可能超出 `tmp_table_size`。
- `TIMESTAMP` 有 2038 年上限，且会随会话时区转换；跨时区业务优先 `DATETIME` 并在应用层统一时区。
- 金额用 `FLOAT/DOUBLE` 会出现精度误差，必须用 `DECIMAL` 或整数存分。
- 手机号、身份证等可能带前导 0 或字母的字段不要用整型。
- 软删除字段 `is_deleted` 会让所有查询都要带条件，且与唯一索引冲突（同一订单号无法二次创建），需要配合归档表或使用删除时间戳。

## 本篇小结

- **架构**决定边界：连接层管连接、Server 层管 SQL、引擎层管存取；binlog 在 Server 层，redo/undo 在 InnoDB。
- **索引**决定下限：B+ 树的高扇出与叶子链表是范围查询的基础；聚簇索引存整行、二级索引存主键，回表是二级索引的固有成本。
- **优化**要看证据：`EXPLAIN` 看路径、`EXPLAIN ANALYZE` 看真实耗时、慢日志按总耗时排序，不要凭感觉加索引。
- **设计**决定上限：主键短而有序、类型精确、索引克制，能避免绝大多数后期迁移与性能问题。
