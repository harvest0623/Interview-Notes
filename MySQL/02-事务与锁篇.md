## 1. 事务的 ACID 与实现原理

**ACID 是事务的四个承诺：原子性（Atomicity）靠 undo log 回滚，一致性（Consistency）靠约束、业务逻辑与 AID 共同保证，隔离性（Isolation）靠锁与 MVCC，持久性（Durability）靠 redo log 与刷盘机制**。其中「一致性」是目的，另外三个是手段，数据库并不能单独「实现」业务一致性。

**四个特性与实现手段：**

| 特性 | 含义 | InnoDB 的实现 | 关键日志/机制 |
| --- | --- | --- | --- |
| 原子性 A | 一组操作要么全成功，要么全失败 | 修改前记录 undo，回滚时反向执行 | undo log |
| 一致性 C | 事务前后满足约束与业务规则 | 主键/唯一/外键约束、触发器、应用校验 | 由 A、I、D 共同支撑 |
| 隔离性 I | 并发事务互不干扰 | 行锁、意向锁、MVCC 快照 | 锁 + Read View |
| 持久性 D | 提交后即使宕机也不丢 | 提交前写 redo 并刷盘，崩溃后重放 | redo log、doublewrite、binlog |

**原子性如何实现：**

1. 事务修改一行前，先把「旧值/反向操作」写入 undo log，并把 undo 页也纳入 redo 保护。
2. 事务回滚时，按 undo 记录逆序执行：插入变删除、删除变插入、更新恢复旧值。
3. 回滚本身也要写 redo，保证「回滚过程」崩溃后还能继续回滚。

**持久性如何实现：**

1. 修改先写 redo log buffer，事务提交时按 `innodb_flush_log_at_trx_commit` 策略刷盘。
2. 数据页可以延迟刷盘（WAL），崩溃后用 redo 重放已提交但未落盘的数据页修改。
3. `doublewrite buffer` 防止「页写一半」导致页损坏，保证 redo 重放时有完整页副本。
4. 主从架构下，binlog 的 `sync_binlog` 决定 binlog 落盘策略，影响「提交后备库能否恢复」。

**隔离性如何实现：**

- **写写冲突**：行锁（记录锁、间隙锁、Next-Key Lock）。
- **读写冲突**：MVCC，读操作读快照，不阻塞写；写操作不阻塞快照读。
- **跨表/跨行**：意向锁 + 表级锁，以及 MVCC 的一致性快照。

**关键参数与验证：**

```sql
-- 1. 事务隔离级别与自动提交
SELECT @@transaction_isolation;      -- 8.0；5.7 可用 @@tx_isolation
SELECT @@autocommit;

-- 2. 持久性相关：redo 刷盘策略与 binlog 刷盘策略
SHOW VARIABLES LIKE 'innodb_flush_log_at_trx_commit';  -- 1 最安全，0/2 有丢失窗口
SHOW VARIABLES LIKE 'sync_binlog';                      -- 1 每次提交刷盘
SHOW VARIABLES LIKE 'innodb_doublewrite';               -- 默认 ON

-- 3. 转账示例：原子性 + 一致性
CREATE TABLE account (
  id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  user_id BIGINT UNSIGNED NOT NULL,
  balance DECIMAL(12,2) NOT NULL DEFAULT 0.00,
  PRIMARY KEY (id),
  UNIQUE KEY uk_user (user_id),
  CONSTRAINT chk_balance CHECK (balance >= 0)
) ENGINE=InnoDB;

START TRANSACTION;
UPDATE account SET balance = balance - 100 WHERE user_id = 1;
UPDATE account SET balance = balance + 100 WHERE user_id = 2;
-- 若第二条失败（余额不足、行不存在），整个事务回滚，第一条的扣款也撤销
COMMIT;

-- 4. 显式回滚：观察 undo 生效
START TRANSACTION;
UPDATE account SET balance = balance - 1 WHERE user_id = 1;
SELECT balance FROM account WHERE user_id = 1;  -- 事务内可见扣减后的值
ROLLBACK;
SELECT balance FROM account WHERE user_id = 1;  -- 恢复原值

-- 5. 保存点：部分回滚
START TRANSACTION;
UPDATE account SET balance = balance - 10 WHERE user_id = 1;
SAVEPOINT sp1;
UPDATE account SET balance = balance - 10 WHERE user_id = 1;
ROLLBACK TO SAVEPOINT sp1;   -- 只回滚到保存点，第一次扣减保留
COMMIT;
```

**ACID 之间的张力：**

- 隔离级别越高，一致性越强，但并发越低；RR 通过 MVCC + 间隙锁在「一致性」与「并发」之间折中。
- 持久性越强，刷盘越频繁，TPS 越低；`innodb_flush_log_at_trx_commit=1` + `sync_binlog=1` 是最安全组合，也是性能最低组合。
- 原子性依赖 undo，undo 又依赖 redo 保护，因此「日志本身也是数据」，崩溃恢复要先恢复日志系统。

**面试怎么答：** 先逐个说实现：A→undo、D→redo + doublewrite、I→锁 + MVCC、C→约束与业务 + AID 共同保证。再强调「一致性不是单独机制，而是目标」，最后补两个工程点：`innodb_flush_log_at_trx_commit` 与 `sync_binlog` 如何权衡性能与安全。

**易错点：**

- 「一致性由 redo log 保证」不准确：redo 保证的是持久性，一致性靠约束、回滚与隔离共同达成。
- undo log 本身也是要写 redo 的，否则回滚过程中崩溃会丢失回滚信息。
- `COMMIT` 成功不等于数据页已落盘，只保证 redo 已按策略持久化。
- `innodb_flush_log_at_trx_commit=1` 也不是绝对零丢失，还受磁盘写缓存、文件系统与硬件故障影响。
- 保存点 `ROLLBACK TO SAVEPOINT` 不是回滚整个事务，释放保存点要用 `RELEASE SAVEPOINT`。

## 2. 四种隔离级别与并发问题

**SQL 标准定义四种隔离级别，MySQL InnoDB 支持全部四种，默认 `REPEATABLE READ`**。并发问题有三个：脏读（读到未提交数据）、不可重复读（同一事务两次读同一行结果不同）、幻读（同一查询两次返回行数不同）。隔离级别越高，问题越少，并发代价越大。

**级别与并发问题对照（SQL 标准）：**

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 实现要点 |
| --- | --- | --- | --- | --- |
| `READ UNCOMMITTED` | 可能 | 可能 | 可能 | 几乎不加读锁，直接读最新数据 |
| `READ COMMITTED` | 不会 | 可能 | 可能 | 每条语句新建 Read View；当前读只加记录锁 |
| `REPEATABLE READ` | 不会 | 不会 | 标准允许，InnoDB 基本避免 | 事务首次快照读建 Read View；当前读用 Next-Key Lock |
| `SERIALIZABLE` | 不会 | 不会 | 不会 | 读加共享锁，写加排他锁，等同串行 |

**MySQL 的实际行为（重点）：**

1. **RC 下每条语句一个新快照**：同一事务内两条 `SELECT` 之间若有其他事务提交，第二条能看到新数据，因此「不可重复读」。
2. **RR 下整个事务共用一个快照**：Read View 在第一次快照读时创建，后续快照读复用，因此可重复读。
3. **RR 下当前读用 Next-Key Lock**：`SELECT ... FOR UPDATE`、`UPDATE`、`DELETE` 会锁记录 + 间隙，阻止其他事务在范围内插入，从而避免当前读的幻读。
4. **SERIALIZABLE 下普通 `SELECT` 也会加共享锁**：当 `autocommit=0` 时，InnoDB 把普通 `SELECT` 隐式转成 `SELECT ... FOR SHARE`，读写互斥。
5. **RC 的「半一致性读」**：`UPDATE` 在 RC 下对不匹配的行会先释放锁再重新读取，减少锁等待；RR 不做这个优化。

**设置与查看：**

```sql
-- 查看当前会话与全局隔离级别（8.0 变量名是 transaction_isolation）
SELECT @@session.transaction_isolation, @@global.transaction_isolation;

-- 会话级设置（只影响当前连接）
SET SESSION transaction_isolation = 'READ-COMMITTED';
SET SESSION transaction_isolation = 'REPEATABLE-READ';

-- 全局设置（影响新连接，需谨慎）
SET GLOBAL transaction_isolation = 'READ-COMMITTED';

-- 5.7 兼容写法（8.0 已移除 tx_isolation）
-- SELECT @@tx_isolation;

-- 确认当前事务状态
SELECT trx_id, trx_state, trx_isolation_level, trx_started
FROM information_schema.innodb_trx;
```

**两会话演示「不可重复读」（RC）：**

```sql
-- 会话 A
SET SESSION transaction_isolation = 'READ-COMMITTED';
START TRANSACTION;
SELECT balance FROM account WHERE user_id = 1;   -- 1000

-- 会话 B
START TRANSACTION;
UPDATE account SET balance = 900 WHERE user_id = 1;
COMMIT;

-- 会话 A 再读：RC 下能看到 900（不可重复读）
SELECT balance FROM account WHERE user_id = 1;   -- 900
COMMIT;
```

**两会话演示「RR 可重复读」：**

```sql
-- 会话 A
SET SESSION transaction_isolation = 'REPEATABLE-READ';
START TRANSACTION;
SELECT balance FROM account WHERE user_id = 1;   -- 1000，建立 Read View

-- 会话 B
START TRANSACTION;
UPDATE account SET balance = 900 WHERE user_id = 1;
COMMIT;

-- 会话 A 再读：仍是 1000（快照读复用 Read View）
SELECT balance FROM account WHERE user_id = 1;   -- 1000

-- 但当前读能看到最新值
SELECT balance FROM account WHERE user_id = 1 FOR UPDATE;  -- 900
COMMIT;
```

**RC 与 RR 的工程取舍：**

| 维度 | RC | RR |
| --- | --- | --- |
| 快照 | 每语句一个 | 每事务一个 |
| 间隙锁 | 基本不加（外键/唯一性检查除外） | 当前读会加 |
| 并发度 | 更高，锁等待更少 | 较低，易死锁 |
| 幻读 | 当前读可能幻读 | 当前读由 Next-Key Lock 防 |
| 主从复制 | 必须 `ROW` 格式 | `ROW` 更安全 |
| 适用场景 | 互联网高并发读多写少 | 需要事务内稳定快照 |

**面试怎么答：** 先背表格「RU 全可能、RC 脏读解决、RR 不可重复读解决、Serializable 全解决」，再强调 MySQL 与标准的两点差异：RR 是默认级别、RR 通过 Next-Key Lock 在当前读下基本避免幻读；最后讲 RC 与 RR 的取舍（间隙锁、并发度、死锁概率、复制格式）。

**易错点：**

- MySQL 默认是 RR，不是 Oracle/PostgreSQL 常见的 RC，迁移时要注意语义差异。
- RR 的「可重复读」只对快照读成立，`FOR UPDATE` 等当前读永远读最新已提交数据。
- RC 不是「完全不加间隙锁」：外键检查、唯一性检查仍可能加间隙锁。
- `SERIALIZABLE` 不是「只给写加锁」，普通读也会被转成共享锁，极易阻塞。
- 修改隔离级别要评估复制格式：RC 下 `STATEMENT` 格式的 binlog 可能不一致，必须用 `ROW`。

## 3. MVCC 的原理（undo log、Read View、版本链）

**MVCC 通过「隐藏事务 ID + undo 版本链 + Read View 可见性判断」实现不加锁的一致性读**：每行有 `DB_TRX_ID`（最后修改它的事务 ID）和 `DB_ROLL_PTR`（指向 undo 中的上一个版本），事务读时用 Read View 判断某个版本是否对自己可见，不可见就顺着版本链找更老的版本。

**行记录的三个隐藏列：**

| 隐藏列 | 长度 | 作用 |
| --- | --- | --- |
| `DB_TRX_ID` | 6 字节 | 最近一次修改该行的事务 ID |
| `DB_ROLL_PTR` | 7 字节 | 指向 undo log 中的回滚指针（版本链） |
| `DB_ROW_ID` | 6 字节 | 无主键时生成的隐藏行 ID（有主键则不需要） |

**版本链的形成：**

1. 事务 T1 把 `balance` 从 1000 改成 900：旧值 1000 写入 undo，行上 `DB_TRX_ID = T1`，`DB_ROLL_PTR` 指向这条 undo。
2. 事务 T2 再改成 800：新 undo 记录旧值 900，`DB_ROLL_PTR` 指向 T2 的 undo，而 T2 的 undo 又指回 T1 的 undo。
3. 于是形成 `当前行 → T2 undo → T1 undo` 的链表，链上每个版本都带当时的事务 ID。

**Read View 的四个字段：**

| 字段 | 含义 |
| --- | --- |
| `m_ids` | 创建 Read View 时，所有「活跃但未提交」的事务 ID 列表 |
| `min_trx_id` | `m_ids` 中的最小值（最小活跃事务 ID） |
| `max_trx_id` | 创建 Read View 时系统下一个将要分配的事务 ID（不是当前最大已提交 ID） |
| `creator_trx_id` | 创建该 Read View 的事务 ID（自身修改总是可见） |

**可见性判断规则（按顺序）：**

1. 版本的 `trx_id` 等于 `creator_trx_id` → **可见**（自己改的）。
2. `trx_id < min_trx_id` → **可见**（在 Read View 创建前已提交）。
3. `trx_id >= max_trx_id` → **不可见**（Read View 创建后才开始的事务）。
4. `trx_id` 在 `m_ids` 中 → **不可见**（创建时还活跃，未提交）。
5. 其他情况（`min_trx_id <= trx_id < max_trx_id` 且不在 `m_ids`）→ **可见**（已提交）。

不可见时，沿 `DB_ROLL_PTR` 找上一个版本，重复判断，直到找到可见版本或链表结束。

**RC 与 RR 的关键差异：**

| 维度 | READ COMMITTED | REPEATABLE READ |
| --- | --- | --- |
| Read View 创建时机 | 每条 `SELECT` 都新建 | 事务第一次快照读时创建，之后复用 |
| 能否读到其他事务新提交的数据 | 能 | 不能（同一事务内） |
| 是否可重复读 | 否 | 是 |
| undo 版本保留需求 | 较短 | 较长（长事务会拖住 purge） |

**可执行验证：**

```sql
-- 1. 观察事务与版本链相关信息
SELECT trx_id, trx_state, trx_started, trx_isolation_level,
       trx_rows_locked, trx_rows_modified
FROM information_schema.innodb_trx;

-- 2. 查看当前事务的 Read View 信息（8.0 的 SHOW ENGINE INNODB STATUS 会输出）
SHOW ENGINE INNODB STATUS\G
-- 关注 TRANSACTIONS 段：ACTIVE 事务的 trx id、隔离级别、是否只读

-- 3. 构造版本链：同一行连续被两个事务修改
-- 会话 A（RR）
START TRANSACTION;
SELECT balance FROM account WHERE user_id = 1;   -- 1000，建立 Read View

-- 会话 B
START TRANSACTION;
UPDATE account SET balance = 900 WHERE user_id = 1;
COMMIT;

-- 会话 C
START TRANSACTION;
UPDATE account SET balance = 800 WHERE user_id = 1;
COMMIT;

-- 会话 A 仍读到 1000：沿版本链跳过 T_B、T_C 的版本
SELECT balance FROM account WHERE user_id = 1;   -- 1000
COMMIT;

-- 4. 长事务会阻止 undo purge，观察 History List Length
SHOW ENGINE INNODB STATUS\G
-- 关注 TRANSACTIONS 段的 History list length，持续增长说明有长事务
```

**为什么 MVCC 能实现「读写不阻塞」：**

- 读操作只读快照，不修改行，不需要加锁；写操作修改当前行并生成 undo，不需要等待读。
- 读写冲突被「版本链 + 可见性判断」消解，而不是靠锁。
- 但 MVCC 只解决快照读；当前读仍要加锁，且要读最新版本。

**面试怎么答：** 按「隐藏列 → 版本链 → Read View 四字段 → 五条可见性规则 → RC/RR 创建时机差异」讲，强调「MVCC 只对快照读生效」「Read View 是可见性判断，不是锁」「长事务导致 undo 无法 purge」。最后补一句：MVCC 减少读锁，但写写冲突仍靠行锁。

**易错点：**

- `max_trx_id` 是「下一个待分配的事务 ID」，不是当前最大事务 ID，边界判断容易写错。
- 事务自己的修改永远可见，即使它还没提交；这是 `creator_trx_id` 的作用。
- RC 下每次 `SELECT` 新建 Read View，所以同一事务内可能看到不同结果。
- MVCC 不能解决写写冲突，两个事务改同一行仍会锁等待。
- undo 不是永久保留：purge 线程会清理不再需要的版本，长事务会让 History List Length 持续增长。

## 4. 快照读与当前读

**快照读（consistent read）读取事务可见的历史版本，不加锁；当前读（locking read）读取最新已提交版本，并加锁**。普通 `SELECT` 是快照读；`SELECT ... FOR UPDATE`、`SELECT ... FOR SHARE`、`UPDATE`、`DELETE`、`INSERT` 都是当前读。两者混用是 RR 下「看起来幻读」的根源。

**语句归类：**

| 语句 | 读类型 | 加锁情况 |
| --- | --- | --- |
| `SELECT ...` | 快照读 | 不加锁（MVCC） |
| `SELECT ... FOR UPDATE` | 当前读 | 排他 Next-Key Lock（RC 下为记录锁） |
| `SELECT ... FOR SHARE`（8.0）/ `LOCK IN SHARE MODE`（5.7） | 当前读 | 共享 Next-Key Lock |
| `UPDATE ...` | 当前读 | 先读最新版本，再加排他锁 |
| `DELETE ...` | 当前读 | 排他锁 |
| `INSERT ...` | 当前读 | 插入意向锁 + 唯一性检查 |
| `INSERT ... ON DUPLICATE KEY UPDATE` | 当前读 | 唯一键冲突时加锁 |

**RR 下两种读的差异（经典现象）：**

```sql
-- 会话 A：RR
START TRANSACTION;
SELECT COUNT(*) FROM orders WHERE user_id = 1;   -- 10，建立 Read View

-- 会话 B：插入并提交
START TRANSACTION;
INSERT INTO orders (user_id, order_no, status, amount, created_at)
VALUES (1, 'NO-NEW', 1, 10.00, NOW());
COMMIT;

-- 会话 A：快照读仍看不到新行
SELECT COUNT(*) FROM orders WHERE user_id = 1;   -- 10

-- 会话 A：当前读能看到新行（并加锁）
SELECT COUNT(*) FROM orders WHERE user_id = 1 FOR UPDATE;  -- 11

-- 会话 A：再快照读，仍看不到（Read View 未变）
SELECT COUNT(*) FROM orders WHERE user_id = 1;   -- 10
COMMIT;
```

这个例子说明：**RR 的快照读与当前读看到的是两个「世界」**。业务上如果先 `SELECT` 判断再 `UPDATE`，可能基于旧快照做决策，而 `UPDATE` 又作用在新数据上，产生逻辑不一致。解决办法是统一使用当前读（`FOR UPDATE`），或接受最终一致并在应用层做幂等。

**RC 下的差异：**

```sql
-- 会话 A：RC
SET SESSION transaction_isolation = 'READ-COMMITTED';
START TRANSACTION;
SELECT COUNT(*) FROM orders WHERE user_id = 1;   -- 10

-- 会话 B 插入并提交后
SELECT COUNT(*) FROM orders WHERE user_id = 1;   -- 11（每条语句新快照）
SELECT COUNT(*) FROM orders WHERE user_id = 1 FOR UPDATE;  -- 11
COMMIT;
```

**当前读的加锁范围：**

- RR：`FOR UPDATE` 在二级索引上通常加 Next-Key Lock（记录 + 间隙）；唯一索引等值命中时退化为记录锁。
- RC：只加记录锁，不加间隙锁（外键/唯一性检查除外），因此并发更高但可能出现幻读。
- 若 `WHERE` 无索引，当前读会退化为全表扫描并锁定大量记录，表现为接近表锁。

**可执行验证锁信息：**

```sql
-- 1. 查看当前锁（8.0 用 performance_schema，5.7 用 information_schema.innodb_locks）
SELECT ENGINE_TRANSACTION_ID, OBJECT_NAME, INDEX_NAME, LOCK_TYPE,
       LOCK_MODE, LOCK_STATUS, LOCK_DATA
FROM performance_schema.data_locks;

-- 2. 查看锁等待关系
SELECT * FROM performance_schema.data_lock_waits;

-- 3. 查看阻塞链（8.0 sys 视图）
SELECT * FROM sys.innodb_lock_waits\G

-- 4. 当前读加锁演示（会话 A 执行后，在会话 B 用 data_locks 观察）
START TRANSACTION;
SELECT * FROM orders WHERE user_id = 1 FOR UPDATE;
-- 此时 data_locks 中能看到 X,REC_NOT_GAP 或 X 等锁模式
ROLLBACK;
```

**面试怎么答：** 先定义两种读：快照读走 MVCC 不加锁，当前读读最新版本并加锁；再列语句归类；重点讲 RR 下「快照读看不到、当前读看得到」导致的语义不一致，说明这不是 bug 而是隔离级别设计；最后给工程建议：需要「读最新再判断」的场景统一用当前读，或把判断与更新合并为一条原子 SQL。

**易错点：**

- `SELECT ... FOR UPDATE` 必须在事务内才有意义，autocommit=1 时语句结束锁就释放。
- 当前读不是「读已提交的最新版本」那么简单，它还要加锁，可能阻塞或被阻塞。
- RR 下当前读看到新行后，后续快照读仍看不到，因为 Read View 没有重建。
- `UPDATE` 的 `WHERE` 条件也是当前读，可能读到快照读看不到的行并修改它。
- 无索引的当前读会锁全表扫描路径上的所有记录，极易造成大范围阻塞。

## 5. 行锁、表锁、意向锁

**InnoDB 的行锁加在索引记录上，不是加在「行」上**：有索引才能精确锁住目标记录；没有索引时，`UPDATE`/`DELETE` 会锁住扫描路径上的所有记录，表现为接近表锁。表级锁主要包括意向锁（IS/IX）、`AUTO-INC` 锁和 Server 层的 MDL（元数据锁），其中意向锁是为了让表锁能快速判断「表内是否已有行锁」。

**锁的层次与类型：**

| 层次 | 锁类型 | 作用 | 获取方式 |
| --- | --- | --- | --- |
| 表级 | 意向共享锁 `IS` | 表示事务准备给某些行加 S 锁 | 执行 `SELECT ... FOR SHARE` 时自动加 |
| 表级 | 意向排他锁 `IX` | 表示事务准备给某些行加 X 锁 | 执行 `UPDATE`/`DELETE`/`FOR UPDATE` 时自动加 |
| 表级 | `AUTO-INC` 锁 | 保证自增列连续分配 | 插入自增列时自动加，受 `innodb_autoinc_lock_mode` 控制 |
| 表级 | MDL 共享/排他锁 | 保护表结构，防止 DDL 与 DML 并发 | 访问表时自动加，DDL 时升级为排他 |
| 行级 | 记录锁 `REC_NOT_GAP` | 锁住某条索引记录 | 唯一索引等值命中 |
| 行级 | 间隙锁 `GAP` | 锁住两条记录之间的间隙 | RR 下范围扫描/唯一索引未命中 |
| 行级 | Next-Key Lock `ORDINARY` | 记录锁 + 前面的间隙（前开后闭） | RR 下默认加锁单位 |
| 行级 | 插入意向锁 `INSERT_INTENTION` | 插入前声明「我要在某间隙插入」 | `INSERT` 时自动加 |

**意向锁的兼容矩阵：**

| 已持有 \ 请求 | `IS` | `IX` | `S`（表） | `X`（表） |
| --- | --- | --- | --- | --- |
| `IS` | 兼容 | 兼容 | 兼容 | 冲突 |
| `IX` | 兼容 | 兼容 | 冲突 | 冲突 |
| `S` | 兼容 | 冲突 | 兼容 | 冲突 |
| `X` | 冲突 | 冲突 | 冲突 | 冲突 |

意向锁之间互相兼容，只与表级 S/X 冲突。这样 `LOCK TABLES ... WRITE` 或 DDL 只需检查表上的意向锁，不必逐行扫描判断是否有行锁。

**为什么「行锁锁索引」：**

- InnoDB 在 B+ 树叶子记录上加锁，锁对象是「索引项」。
- 若 `WHERE` 条件没有可用索引，执行器只能全表扫描，并对扫描到的每条记录加锁（RR 下还包括间隙），效果接近锁表。
- 若索引选择性差，扫描范围大，同样会锁很多记录。
- 因此「加索引」不仅是查询优化，也是**减少锁冲突**的手段。

**MDL（元数据锁）：**

- 任何 DML 都会对表加 MDL 读锁，DDL 需要 MDL 写锁；读写互斥。
- 长事务持有 MDL 读锁时，DDL 会阻塞；DDL 排队又会阻塞后续所有 DML，形成「MDL 等待雪崩」。
- 排查：8.0 查 `performance_schema.metadata_locks`；5.7 只能看 `SHOW PROCESSLIST` 中的 `Waiting for table metadata lock`。

**自增锁模式：**

| `innodb_autoinc_lock_mode` | 行为 | 版本默认 | 特点 |
| --- | --- | --- | --- |
| `0` | 语句级 `AUTO-INC` 表锁，直到语句结束 | 5.7 之前 | 自增连续，并发最差 |
| `1` | 简单插入用轻量互斥量，批量插入用表锁 | 5.7 默认 | 连续、并发较好 |
| `2` | 全部用轻量互斥量，不保证连续 | 8.0 默认 | 并发最好，自增值可能不连续 |

**可执行验证：**

```sql
-- 1. 行锁是否存在，取决于 WHERE 是否走索引
CREATE TABLE lock_demo (
  id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  uid BIGINT UNSIGNED NOT NULL,
  remark VARCHAR(32) NOT NULL DEFAULT '',
  PRIMARY KEY (id),
  KEY idx_uid (uid)
) ENGINE=InnoDB;

INSERT INTO lock_demo (uid, remark) VALUES (1,'a'),(2,'b'),(3,'c');

-- 会话 A：走 idx_uid，只锁 uid=1 的索引记录及主键记录
START TRANSACTION;
SELECT * FROM lock_demo WHERE uid = 1 FOR UPDATE;

-- 会话 B：观察锁
SELECT OBJECT_NAME, INDEX_NAME, LOCK_TYPE, LOCK_MODE, LOCK_DATA
FROM performance_schema.data_locks;

-- 会话 A：不走索引，扫描并锁定全部记录（RR 下还有间隙）
ROLLBACK;
START TRANSACTION;
SELECT * FROM lock_demo WHERE remark = 'a' FOR UPDATE;
-- 此时 data_locks 中几乎能看到全表的 X 锁

-- 2. 表级意向锁
SELECT LOCK_TYPE, LOCK_MODE, COUNT(*) AS cnt
FROM performance_schema.data_locks
GROUP BY LOCK_TYPE, LOCK_MODE;

-- 3. MDL 锁：另开会话执行 DDL，再回来观察
SELECT OBJECT_TYPE, OBJECT_SCHEMA, OBJECT_NAME, LOCK_TYPE, LOCK_DURATION, LOCK_STATUS
FROM performance_schema.metadata_locks
WHERE OBJECT_SCHEMA = 'demo';

-- 4. 自增锁模式
SHOW VARIABLES LIKE 'innodb_autoinc_lock_mode';

-- 5. 显式表锁（Server 层，会隐式提交当前事务，慎用）
LOCK TABLES lock_demo READ;
SHOW OPEN TABLES WHERE In_use > 0;
UNLOCK TABLES;
```

**面试怎么答：** 先给结论「InnoDB 行锁锁索引」，再讲三种行锁（记录/间隙/Next-Key）与两种意向锁（IS/IX），说明意向锁的作用是「让表锁快速判断有无行锁」，最后补充 MDL 与自增锁。落到线上：没有索引的 `UPDATE` 会锁大量行甚至全表，加索引既提速又降锁冲突。

**易错点：**

- 「行锁锁行」是简化说法，实际锁的是索引记录；同一行通过不同索引访问会加不同的锁。
- 意向锁不是「给行加的锁」，它是表级锁，且只与表级 S/X 冲突。
- RC 下普通查询不加间隙锁，但外键检查和唯一性检查仍可能加。
- `LOCK TABLES` 是 Server 层表锁，会隐式提交当前事务，且与 InnoDB 行锁机制并存，生产很少使用。
- MDL 等待不会因为 `innodb_lock_wait_timeout` 超时而结束，它受 `lock_wait_timeout` 控制，默认 31536000 秒（一年）。

## 6. 间隙锁与 Next-Key Lock

**间隙锁（Gap Lock）锁住索引记录之间的「空隙」，Next-Key Lock 是「记录锁 + 该记录前面的间隙」，加锁单位在 RR 下默认是 Next-Key，区间为左开右闭 `(prev, current]`**。它们的目的不是阻止其他事务读，而是阻止其他事务在间隙中**插入**，从而避免当前读的幻读。

**三种行锁的关系：**

```
假设索引中有记录 5、10、15：
  (-∞, 5)   (5, 10)   (10, 15)   (15, +∞)
间隙锁 GAP：锁住开区间，如 (5,10)
记录锁 REC_NOT_GAP：只锁 10 这一条
Next-Key：锁住 (5,10]，即「10 前面的间隙 + 10 本身」
```

**加锁规则（丁奇总结，适用于 RR）：**

1. **基本原则**：加锁单位是 Next-Key Lock，区间左开右闭。
2. **查找过程中访问到的对象才会加锁**：没扫到的记录不加锁。
3. **唯一索引等值查询，命中记录**：Next-Key 退化为记录锁（只锁该行）。
4. **唯一索引等值查询，未命中**：Next-Key 退化为间隙锁（锁住「值应该所在」的间隙）。
5. **非唯一索引等值查询**：命中记录加 Next-Key；继续向右扫描，直到第一个不满足条件的记录，该记录的 Next-Key 退化为间隙锁。
6. **唯一索引范围查询**：会访问到第一个不满足条件的值，并对它加间隙锁（或 Next-Key 退化）。

**具体例子（表 `t`，主键 id 有 5、10、15、20、25）：**

| SQL（RR） | 加锁范围 | 说明 |
| --- | --- | --- |
| `WHERE id = 10 FOR UPDATE` | `(5,10]` 退化为 `10` | 唯一索引命中，仅记录锁 |
| `WHERE id = 12 FOR UPDATE` | `(10,15)` | 未命中，间隙锁 |
| `WHERE id > 10 AND id <= 15 FOR UPDATE` | `(10,15]` + `(15,20)` | 扫描到 20 确认范围结束 |
| `WHERE id BETWEEN 10 AND 20 FOR UPDATE` | `(5,10]`、`(10,15]`、`(15,20]`、`(20,25)` | 20 后的间隙也被锁 |
| `WHERE id > 100 FOR UPDATE` | `(25,+∞)` | 锁住最大值之后的间隙 |
| `WHERE uid = 1 FOR UPDATE`（uid 非唯一） | 命中记录的 Next-Key + 右侧第一个不满足值的间隙 | 非唯一索引需向右多扫一条 |

**插入意向锁与间隙锁的冲突：**

- `INSERT` 前会先加「插入意向锁」，它表示「我要在某个间隙插入」。
- 插入意向锁之间互相兼容（不同位置可并发插入），但**与间隙锁冲突**。
- 因此间隙锁能有效阻止插入，是防幻读的关键；代价是并发插入容易被阻塞，甚至死锁。

**RC 下的差异：**

- RC 下普通 `SELECT ... FOR UPDATE` 只加记录锁，不加间隙锁，因此并发更高，但当前读可能出现幻读。
- 例外：外键约束检查、唯一键冲突检查会加间隙锁。
- 5.7 的 `innodb_locks_unsafe_for_binlog` 已被移除，8.0 只能用隔离级别控制。

**可执行验证：**

```sql
-- 准备数据
CREATE TABLE gap_demo (
  id INT NOT NULL,
  uid INT NOT NULL,
  PRIMARY KEY (id),
  KEY idx_uid (uid)
) ENGINE=InnoDB;
INSERT INTO gap_demo VALUES (5,1),(10,2),(15,3),(20,4),(25,5);

-- 会话 A：唯一索引等值命中 → 只锁 id=10
START TRANSACTION;
SELECT * FROM gap_demo WHERE id = 10 FOR UPDATE;
-- 会话 B：观察锁模式与 LOCK_DATA
SELECT INDEX_NAME, LOCK_MODE, LOCK_DATA FROM performance_schema.data_locks;
-- 预期看到 X,REC_NOT_GAP 与 10

-- 会话 A：唯一索引等值未命中 → 锁 (10,15)
ROLLBACK;
START TRANSACTION;
SELECT * FROM gap_demo WHERE id = 12 FOR UPDATE;
-- 预期看到 X,GAP 与 15（LOCK_DATA 表示间隙右边界）

-- 会话 A：范围查询 → Next-Key
ROLLBACK;
START TRANSACTION;
SELECT * FROM gap_demo WHERE id BETWEEN 10 AND 20 FOR UPDATE;
-- 预期看到 X 与 10/15/20/25（25 为间隙）

-- 会话 B：在锁住的间隙插入会被阻塞
INSERT INTO gap_demo VALUES (12, 9);
-- 阻塞，直到会话 A COMMIT/ROLLBACK

-- 会话 A
ROLLBACK;

-- 对比 RC：同样的范围当前读只加记录锁
SET SESSION transaction_isolation = 'READ-COMMITTED';
START TRANSACTION;
SELECT * FROM gap_demo WHERE id BETWEEN 10 AND 20 FOR UPDATE;
-- 会话 B 此时可插入 id=12，说明没有间隙锁
```

**面试怎么答：** 先画「5、10、15」的间隙图，说明 Gap 锁间隙、Next-Key = 间隙 + 记录、插入意向锁与 Gap 冲突；再背四条规则：单位是 Next-Key、只锁访问到的对象、唯一索引等值命中退化记录锁、未命中退化间隙锁；最后说明只在 RR 生效、RC 不加间隙锁，以及它的代价（阻塞插入、增加死锁）。

**易错点：**

- 间隙锁之间互相兼容，两个事务可以同时持有同一间隙的 Gap 锁，真正冲突的是「Gap 锁 vs 插入意向锁」。
- 间隙锁不阻止快照读，只阻止插入；它锁的是「位置」不是「数据」。
- 唯一索引等值命中时没有间隙锁，所以 `WHERE id = 10` 不会阻止插入 `id = 11`。
- `WHERE id = 12` 未命中时，锁的是 `(10,15)` 这个间隙，而不是「12 这一行」。
- 无索引的当前读会把所有记录和间隙都锁住，效果接近锁表，这是线上最危险的情况之一。

## 7. MySQL 的幻读到底怎么解决

**准确说法是：RR 下「快照读」通过 MVCC 让幻读不可见，「当前读」通过 Next-Key Lock 阻止范围内插入；两者组合后，业务上大多数幻读被规避，但同一事务混用两种读时仍会出现「看起来幻读」的语义不一致**。不要回答「RR 完全消灭幻读」。

**幻读的定义：**

- 同一事务内，同一查询条件执行两次，第二次返回了第一次没有的行（或行数变化）。
- 与「不可重复读」的区别：不可重复读针对**同一行**的值变化；幻读针对**结果集行数**变化。

**两层机制：**

| 读类型 | 机制 | 效果 | 局限 |
| --- | --- | --- | --- |
| 快照读 | Read View + undo 版本链 | 看不到事务开始后其他事务插入的行 | 只是「看不见」，数据实际已存在 |
| 当前读 | Next-Key Lock / 间隙锁 | 阻止其他事务在锁定范围内插入 | 只对加锁范围有效；RC 下没有 |

**混用两种读导致「幻读」的经典例子：**

```sql
-- 会话 A：RR
START TRANSACTION;
SELECT COUNT(*) FROM gap_demo WHERE id > 100;          -- 0，快照读
-- 会话 B：插入 id=101 并提交
-- INSERT INTO gap_demo VALUES (101, 9); COMMIT;

-- 会话 A：当前读，看到新行并修改它
UPDATE gap_demo SET uid = 99 WHERE id > 100;           -- 影响 1 行
SELECT COUNT(*) FROM gap_demo WHERE id > 100;          -- 仍为 0（旧 Read View）
SELECT COUNT(*) FROM gap_demo WHERE id > 100 FOR UPDATE; -- 1（当前读）
COMMIT;
```

对会话 A 来说：第一次查是 0，`UPDATE` 却改到了 1 行，再查又是 0，加锁读又是 1。这不是 bug，而是「快照读看历史、当前读看现在」的必然结果。

**RR 到底防住了什么：**

1. **快照读的幻读**：Read View 固定，看不到新插入的行 → 表现为「没有幻读」。
2. **当前读的幻读**：`SELECT ... FOR UPDATE` 在范围内加 Next-Key Lock，其他事务无法插入 → 真正阻止。
3. **同一事务内先快照读、再当前读**：两者看到不同版本 → 语义不一致仍然存在。

**四种解决思路：**

| 方案 | 做法 | 适用场景 | 代价 |
| --- | --- | --- | --- |
| 统一当前读 | 事务内所有相关查询都用 `FOR UPDATE`/`FOR SHARE` | 先查后改、库存扣减 | 锁范围大，并发下降 |
| 提高隔离级别 | `SERIALIZABLE`，读也加共享锁 | 强一致、低并发 | 并发最差 |
| 唯一约束兜底 | 用唯一索引阻止重复插入 | 幂等、防重复提交 | 只能防特定模式 |
| 应用层幂等/乐观锁 | 版本号、状态机、分布式锁 | 高并发业务 | 复杂度转移到应用层 |

**可执行验证：**

```sql
-- 1. 快照读：看不到新插入
-- 会话 A
START TRANSACTION;
SELECT * FROM gap_demo WHERE id > 100;   -- 空

-- 会话 B
INSERT INTO gap_demo VALUES (101, 9);
COMMIT;

-- 会话 A
SELECT * FROM gap_demo WHERE id > 100;   -- 仍为空（MVCC）
COMMIT;

-- 2. 当前读：加 Next-Key Lock 阻止插入
-- 会话 A
START TRANSACTION;
SELECT * FROM gap_demo WHERE id > 100 FOR UPDATE;  -- 空，但锁住 (25,+∞)

-- 会话 B
INSERT INTO gap_demo VALUES (102, 9);              -- 阻塞
-- 会话 A COMMIT 后才能插入

-- 3. 唯一约束兜底
ALTER TABLE gap_demo ADD UNIQUE KEY uk_uid (uid);
-- 会话 B 插入重复 uid 会报 Duplicate entry，而不是产生幻行
INSERT INTO gap_demo VALUES (103, 9);
-- ERROR 1062 (23000): Duplicate entry '9' for key 'gap_demo.uk_uid'
```

**面试怎么答：** 先区分快照读与当前读，说清「MVCC 让快照读看不见幻行、Next-Key Lock 让当前读插不进来」；再主动指出「混用时仍可能语义不一致」，并举 `SELECT COUNT(*)` 后 `UPDATE` 的例子；最后给方案：统一当前读、SERIALIZABLE、唯一约束、应用层幂等。这样回答比一句「RR 解决了幻读」更有深度。

**易错点：**

- 标准 SQL 允许 RR 出现幻读，InnoDB 是在「当前读」层面用间隙锁额外规避，不要说成「RR 定义上就没有幻读」。
- 快照读「看不到」不等于「不存在」，`UPDATE` 仍可能改到它，这是很多线上逻辑 bug 的来源。
- 间隙锁只在 RR 生效；RC 下当前读可能幻读，需要应用层或唯一约束兜底。
- 唯一索引能防「重复插入」，但防不了「范围内新增不同值」的幻读。
- `SERIALIZABLE` 会把普通 `SELECT` 转成共享锁读，性能下降明显，不适合高并发核心链路。

## 8. 死锁的产生、排查与避免

**死锁是「两个或多个事务互相持有对方需要的锁并无限等待」**。InnoDB 默认开启死锁检测（`innodb_deadlock_detect=ON`），发现环后回滚「代价最小」的事务作为牺牲者；没有检测到的锁等待则由 `innodb_lock_wait_timeout`（默认 50 秒）兜底超时。

**死锁的四个必要条件（操作系统通用）：**

1. **互斥**：锁资源同一时刻只能被一个事务持有。
2. **持有并等待**：持有锁的同时请求新锁。
3. **不可剥夺**：锁只能由持有者释放，不能被强行抢走。
4. **循环等待**：存在事务 → 锁 → 事务的环形等待链。

数据库无法消除前三个（否则就不需要锁），只能通过「破坏循环等待」来避免死锁。

**常见死锁场景：**

| 场景 | 例子 | 原因 |
| --- | --- | --- |
| 加锁顺序相反 | T1 改 A 再改 B，T2 改 B 再改 A | 循环等待 |
| 间隙锁 + 插入 | 两个事务各锁一个间隙，再互相插入 | Gap 锁与插入意向锁冲突 |
| 唯一键冲突 | 并发 `INSERT ... ON DUPLICATE KEY UPDATE` | 唯一性检查加锁顺序不同 |
| 索引缺失 | `UPDATE` 无索引，锁全表扫描路径 | 锁范围扩大，交叉等待 |
| 批量更新顺序不一致 | 批量按不同顺序更新同一批行 | 顺序不一致 |
| 二级索引 + 主键 | 先锁二级索引再锁聚簇索引，方向相反 | 锁升级路径交叉 |

**排查手段：**

```sql
-- 1. 最近一次死锁的完整现场（最常用）
SHOW ENGINE INNODB STATUS\G
-- 关注 LATEST DETECTED DEADLOCK 段：
--   TRANSACTION 1 / TRANSACTION 2 的 SQL、持有的锁、等待的锁
--   WE ROLL BACK TRANSACTION (1) 表示回滚了哪个事务

-- 2. 让所有死锁都写入错误日志（默认只保留最近一次）
SET GLOBAL innodb_print_all_deadlocks = ON;
-- 之后可在 error log 中检索 "Deadlock found"

-- 3. 当前锁等待关系
SELECT * FROM performance_schema.data_lock_waits;
SELECT * FROM sys.innodb_lock_waits\G

-- 4. 当前事务与阻塞者
SELECT trx_id, trx_state, trx_started, trx_mysql_thread_id,
       trx_query, trx_rows_locked, trx_rows_modified
FROM information_schema.innodb_trx
ORDER BY trx_started;

-- 5. 死锁相关参数
SHOW VARIABLES LIKE 'innodb_deadlock_detect';       -- 默认 ON
SHOW VARIABLES LIKE 'innodb_lock_wait_timeout';     -- 默认 50 秒

-- 6. 必要时终止事务（先确认业务影响）
KILL <thread_id>;
```

**手动构造一次死锁（两会话）：**

```sql
-- 准备
CREATE TABLE dead_demo (
  id INT PRIMARY KEY,
  v INT NOT NULL
) ENGINE=InnoDB;
INSERT INTO dead_demo VALUES (1, 0), (2, 0);

-- 会话 A
START TRANSACTION;
UPDATE dead_demo SET v = v + 1 WHERE id = 1;   -- 持有 id=1 的 X 锁

-- 会话 B
START TRANSACTION;
UPDATE dead_demo SET v = v + 1 WHERE id = 2;   -- 持有 id=2 的 X 锁

-- 会话 A
UPDATE dead_demo SET v = v + 1 WHERE id = 2;   -- 等待 B

-- 会话 B
UPDATE dead_demo SET v = v + 1 WHERE id = 1;   -- 形成环，InnoDB 立即检测并回滚其中一个
-- ERROR 1213 (40001): Deadlock found when trying to get lock; try restarting transaction

-- 查看现场
SHOW ENGINE INNODB STATUS\G
```

**避免死锁的工程手段：**

1. **固定加锁顺序**：所有事务按「主键升序」或「业务约定的顺序」访问资源；批量更新先排序。
2. **缩短事务**：把非数据库操作（RPC、发消息、文件 IO）移出事务，减少持锁时间。
3. **减少锁范围**：保证 `WHERE` 走索引，避免无索引 `UPDATE` 锁全表；能用记录锁就不用间隙锁。
4. **降低隔离级别**：RC 下没有间隙锁，死锁概率显著下降（需评估幻读与复制格式）。
5. **拆分大事务**：大批量更新分批次提交，每批行数可控。
6. **唯一约束 + 幂等**：用 `INSERT ... ON DUPLICATE KEY UPDATE` 或幂等表替代「先查后插」。
7. **应用层重试**：捕获 1213/1205 错误后做有限次退避重试，并保证业务幂等。
8. **监控告警**：对 `Innodb_deadlocks` 指标与错误日志中的死锁做告警，定期分析 Top 死锁 SQL。

```sql
-- 死锁与锁等待相关状态指标
SHOW GLOBAL STATUS LIKE 'Innodb_deadlocks';
SHOW GLOBAL STATUS LIKE 'Innodb_row_lock_waits';
SHOW GLOBAL STATUS LIKE 'Innodb_row_lock_time_avg';
```

**面试怎么答：** 先给定义与四个必要条件，说明 InnoDB 用等待图检测、回滚代价最小的事务；再讲排查三板斧：`SHOW ENGINE INNODB STATUS` 看 `LATEST DETECTED DEADLOCK`、`data_lock_waits` 看等待关系、`innodb_trx` 看长事务；最后给避免手段：固定顺序、短事务、走索引、降隔离级别、批量拆分、应用重试。最好能口述一个「相反顺序更新两行」的例子。

**易错点：**

- 死锁不是「锁等待超时」：死锁由检测机制立即发现并回滚；`innodb_lock_wait_timeout` 只处理没有形成环的普通等待。
- `innodb_deadlock_detect=ON` 有 CPU 开销，超高并发下可能成为瓶颈，但关掉后只能靠超时，风险更大。
- 回滚的是「权重最小」的事务（修改行数少、undo 少），不一定是后发起的事务。
- 死锁被回滚后，事务已全部回滚，应用必须重试整个事务，不能只重试最后一条 SQL。
- 间隙锁会显著增加死锁概率：两个事务各锁相邻间隙再插入，很容易形成环。

## 9. redo log 与 WAL 机制

**redo log 是 InnoDB 的物理日志，记录「哪个页做了什么修改」，采用 WAL（Write-Ahead Logging）先写日志再刷数据页，从而把随机写变成顺序写，并在崩溃后用日志重放保证持久性**。它是循环写的固定空间日志，不是无限增长的归档日志。

**WAL 的核心流程：**

1. 事务修改数据页前，先在内存中修改，并把「页号 + 偏移 + 修改内容」写入 redo log buffer。
2. 事务提交时，按 `innodb_flush_log_at_trx_commit` 策略把 redo 从 log buffer 刷到磁盘。
3. 数据页（脏页）不立即刷盘，由后台线程在 checkpoint 时批量刷，减少随机 IO。
4. 崩溃恢复时，从最近一次 checkpoint 的 LSN 开始重放 redo，把已提交但未落盘的页修改补上。
5. redo 空间循环复用：checkpoint 推进后，旧的 redo 可以被覆盖。

**为什么 WAL 快：**

| 方式 | IO 模式 | 每次提交的写量 | 说明 |
| --- | --- | --- | --- |
| 直接改数据页 | 随机写，页分散 | 至少 16KB/页 | 事务涉及多页时随机 IO 放大 |
| WAL | 顺序追加 redo | 几十到几百字节 | 顺序写 + 组提交，吞吐高 |

**刷盘策略：**

| `innodb_flush_log_at_trx_commit` | 提交时行为 | 崩溃丢失窗口 | 性能 |
| --- | --- | --- | --- |
| `0` | 写入 log buffer，由后台每秒刷 | 最多 1 秒（实例崩溃即丢） | 最高 |
| `1` | 写入 log buffer 并 `fsync` 到磁盘 | 理论上不丢（受硬件缓存影响） | 最低，最安全 |
| `2` | 写入 OS page cache，不 `fsync` | 实例崩溃不丢，机器断电可能丢 | 中等 |

**组提交（group commit）：**

- 多个事务同时提交时，由一个 leader 把大家的 redo 一起 `fsync`，其他事务等待结果，把多次 `fsync` 合并为一次。
- 组提交分三段：`flush`（写盘）、`sync`（fsync）、`commit`（引擎提交），对应 binlog 的 `binlog_group_commit_sync_delay` 等参数。
- 高并发下组提交能显著提升 TPS，低并发时收益有限。

**LSN 与 checkpoint：**

- **LSN（Log Sequence Number）** 是 redo 的全局递增序号，标记日志位置。
- **checkpoint LSN** 表示「这个位置之前的脏页都已刷盘」，恢复时从这里开始重放。
- `SHOW ENGINE INNODB STATUS` 的 `LOG` 段会显示 `Log sequence number`、`Log flushed up to`、`Last checkpoint at`。

**8.0 的变化：**

- 5.7 用 `innodb_log_file_size` + `innodb_log_files_in_group` 控制 redo 大小；8.0.30 起改为 `innodb_redo_log_capacity`（默认 100MB），并放在 `#innodb_redo` 目录，支持在线调整。
- 8.0 支持 redo 归档（`innodb_redo_log_archive`），用于备份期间的日志保留。

**doublewrite：**

- 数据页刷盘时先写到 doublewrite buffer，再写到真实数据文件，防止「页写一半」导致页损坏。
- 崩溃恢复时，若数据页损坏，可从 doublewrite 中恢复完整页，再用 redo 重放。
- 8.0 的 doublewrite 文件位于独立表空间，`innodb_doublewrite=ON` 默认开启。

**可执行验证：**

```sql
-- 1. 刷盘策略与日志大小
SHOW VARIABLES LIKE 'innodb_flush_log_at_trx_commit';
SHOW VARIABLES LIKE 'innodb_log_buffer_size';
SHOW VARIABLES LIKE 'innodb_redo_log_capacity';       -- 8.0.30+
SHOW VARIABLES LIKE 'innodb_log_file_size';           -- 5.7 / 8.0.30 之前
SHOW VARIABLES LIKE 'innodb_doublewrite';

-- 2. 查看 LSN 与 checkpoint（LOG 段）
SHOW ENGINE INNODB STATUS\G
-- Log sequence number      : 已写入 redo 的位置
-- Log flushed up to        : 已 fsync 的位置
-- Pages flushed up to      : 已刷数据页的位置
-- Last checkpoint at       : 最近 checkpoint 位置

-- 3. 脏页比例（接近 100% 会触发强制刷脏，性能抖动）
SHOW STATUS LIKE 'Innodb_buffer_pool_pages_dirty';
SHOW STATUS LIKE 'Innodb_buffer_pool_pages_total';

-- 4. 观察组提交效果（高并发压测时）
SHOW GLOBAL STATUS LIKE 'Innodb_log_write_requests';
SHOW GLOBAL STATUS LIKE 'Innodb_log_writes';
SHOW GLOBAL STATUS LIKE 'Innodb_os_log_fsyncs';

-- 5. 修改刷盘策略（会话级无效，必须 GLOBAL；生产评估后再改）
SET GLOBAL innodb_flush_log_at_trx_commit = 1;
```

**面试怎么答：** 先讲 WAL 的两个收益「顺序写替代随机写、日志先行使提交只需刷日志」；再说 redo 是物理日志、循环写、用 LSN 与 checkpoint 管理；接着讲 `innodb_flush_log_at_trx_commit` 三档与组提交；最后补 doublewrite 解决「页断裂」，以及 8.0.30 的 `innodb_redo_log_capacity`。

**易错点：**

- redo log 不是 binlog：redo 是 InnoDB 物理日志、循环写、用于崩溃恢复；binlog 是 Server 层逻辑日志、追加写、用于复制与备份。
- WAL 不是「不刷数据页」，而是「延迟批量刷」，checkpoint 与脏页阈值会触发刷盘。
- `innodb_flush_log_at_trx_commit=1` 也只保证「日志到了磁盘」，不保证数据页已落盘。
- redo 太小会导致频繁 checkpoint、刷脏抖动；太大则崩溃恢复时间长。
- 组提交是「并发提交合并 fsync」，单线程低并发时看不出效果。

## 10. undo log 与事务回滚

**undo log 是 InnoDB 的逻辑日志，记录「如何撤销这次修改」，承担两个职责：事务回滚与 MVCC 版本链**。它与 redo 相反：redo 记录「做了什么」，undo 记录「怎么撤销」；undo 本身也受 redo 保护，保证回滚过程可恢复。

**undo 记录的内容：**

| 操作 | undo 记录 | 回滚动作 |
| --- | --- | --- |
| `INSERT` | 记录新插入行的主键 | 删除该行（标记删除） |
| `DELETE` | 记录被删除行的完整内容 | 重新插入该行 |
| `UPDATE` | 记录被修改列的前值 | 把列恢复为前值 |

**undo 的两大用途：**

1. **事务回滚**：`ROLLBACK` 或语句失败时，按 undo 链逆序执行反向操作。
2. **MVCC**：`DB_ROLL_PTR` 指向 undo 中的旧版本，快照读沿版本链找到可见版本。

**undo 的生命周期：**

1. 事务修改数据时生成 undo 记录，挂在对应行的版本链上。
2. 事务提交后，undo 不会立即删除，因为可能还有更早的 Read View 需要读旧版本。
3. **purge 线程**判断「没有 Read View 需要这个版本」后，才清理 undo 并释放空间。
4. 长事务会持有旧 Read View，导致 purge 无法推进，`History list length` 持续增长。

**undo 表空间：**

- 8.0 默认 `innodb_undo_tablespaces=2`（只读参数，初始化时确定），undo 文件位于 `undo_001`、`undo_002`。
- `innodb_max_undo_log_size` 控制单个 undo 表空间上限（默认 1GB），超过后可截断。
- `innodb_undo_log_truncate=ON` 允许在线截断 undo 表空间，需要至少两个 undo 表空间轮换。
- 5.7 的 `innodb_undo_logs` 在 8.0 已移除。

**可执行验证：**

```sql
-- 1. undo 相关参数
SHOW VARIABLES LIKE 'innodb_undo%';
SHOW VARIABLES LIKE 'innodb_max_undo_log_size';
SHOW VARIABLES LIKE 'innodb_purge_threads';

-- 2. 观察事务修改行数与 undo 压力
START TRANSACTION;
UPDATE account SET balance = balance - 10 WHERE user_id = 1;

SELECT trx_id, trx_state, trx_rows_modified, trx_rows_locked
FROM information_schema.innodb_trx;

ROLLBACK;   -- undo 反向执行，余额恢复

-- 3. History list length：purge 是否被长事务拖住
SHOW ENGINE INNODB STATUS\G
-- TRANSACTIONS 段：History list length 持续增长说明旧版本堆积

-- 4. 查看 undo 表空间文件与大小
SELECT NAME, SPACE_TYPE, FILE_SIZE
FROM information_schema.INNODB_TABLESPACES
WHERE NAME LIKE 'undo%';

-- 5. 保存点回滚只撤销部分 undo
START TRANSACTION;
UPDATE account SET balance = balance - 10 WHERE user_id = 1;
SAVEPOINT sp1;
UPDATE account SET balance = balance - 10 WHERE user_id = 1;
ROLLBACK TO SAVEPOINT sp1;
COMMIT;
```

**undo 与 redo 的配合：**

- 修改数据页 → 写 undo（记录前值）→ 写 redo（记录数据页与 undo 页的修改）。
- 回滚时读 undo → 修改数据页 → 再写 redo。
- 崩溃恢复时先重放 redo，把数据页与 undo 页恢复到崩溃前状态，再决定是否需要回滚未提交事务。

**面试怎么答：** 先给定义「逻辑日志、记录前值」，再讲两个用途「回滚 + MVCC」，然后讲生命周期「提交后不立即删、purge 判断无 Read View 需要才清理」，最后落到长事务导致 undo 膨胀、History list length 增长、磁盘告警。

**易错点：**

- undo 不是「备份」，它记录的是反向操作，不能用来做数据恢复。
- 事务提交后 undo 仍可能保留很久，用于 MVCC，不要以为提交就释放。
- `History list length` 是「未 purge 的 undo 版本数」，不是事务数，但能反映长事务。
- purge 是后台异步的，即使没有长事务，指标也可能短时波动。
- undo 表空间被撑大后，即使 purge 完，磁盘文件也不一定立即缩小，需要 truncate。

## 11. binlog 的三种格式与两阶段提交

**binlog 是 Server 层的逻辑日志，记录所有修改数据的语句或行变更，用于主从复制、备份恢复与审计**。它有三种格式 `STATEMENT`、`ROW`、`MIXED`，8.0 默认 `ROW`；为保证「binlog 与 redo 一致」，InnoDB 采用两阶段提交（2PC）。

**三种格式对比：**

| 格式 | 记录内容 | 优点 | 缺点 | 适用 |
| --- | --- | --- | --- | --- |
| `STATEMENT` | 原始 SQL 语句 | 日志小、可读 | 非确定性函数（`NOW()`、`RAND()`、`UUID()`）、RC 隔离级别下可能主从不一致 | 少用 |
| `ROW` | 每行变更的前后值 | 精确、可逆、支持 RC 与 MGR | 日志大、批量更新膨胀 | 8.0 默认，生产首选 |
| `MIXED` | 自动在两者间切换 | 兼顾体积与安全 | 行为依赖优化器，排查复杂 | 历史兼容 |

**ROW 格式的关键参数：**

- `binlog_row_image=FULL|MINIMAL|NOBLOB`：记录完整行、仅变更列、或排除 BLOB。`MINIMAL` 减少日志量，但部分工具与恢复场景需要 `FULL`。
- `binlog_row_metadata=MINIMAL|FULL`：控制是否记录列名等元数据，CDC 工具常需要 `FULL`。
- `binlog_format` 是全局/会话参数，修改只影响新会话；MGR 要求 `ROW`。

**两阶段提交流程：**

1. **Prepare 阶段**：事务修改完成，InnoDB 写 redo 并标记为 `prepare`，把 XID 写入 redo。
2. **写 binlog**：Server 层把事务的 binlog 事件写入 binlog 文件并 `fsync`（受 `sync_binlog` 控制）。
3. **Commit 阶段**：InnoDB 把 redo 标记为 `commit`，事务真正提交。
4. **崩溃恢复规则**：
   - redo 是 `prepare` 且 binlog 完整（XID 存在）→ 提交。
   - redo 是 `prepare` 但 binlog 不完整 → 回滚。
   - redo 已是 `commit` → 提交。

这样保证「主库提交的事务，从库一定能通过 binlog 重放」，不会出现「主库有、从库没有」或反之。

**为什么需要 2PC：**

- 如果先写 binlog 再提交 redo：binlog 写了但 redo 未提交，崩溃后主库回滚，从库却已重放 → 主从不一致。
- 如果先提交 redo 再写 binlog：主库提交成功但 binlog 丢失，从库缺数据 → 主从不一致。
- 2PC 用 XID 关联两份日志，让崩溃恢复能判断「该提交还是回滚」。

**组提交与刷盘：**

| 参数 | 作用 | 建议 |
| --- | --- | --- |
| `sync_binlog=1` | 每次提交都 `fsync` binlog | 金融级必须；`0` 由系统决定，`N` 每 N 次提交刷一次 |
| `binlog_cache_size` | 单个事务的 binlog 缓存 | 大事务会落临时文件，观察 `Binlog_cache_disk_use` |
| `max_binlog_size` | 单个 binlog 文件上限 | 默认 1GB，事务跨文件不影响一致性 |
| `binlog_expire_logs_seconds` | 日志保留时长 | 8.0 用秒，替代 5.7 的 `expire_logs_days` |
| `binlog_group_commit_sync_delay` | 组提交延迟，合并 fsync | 微秒级，吞吐优先时可调 |

**可执行验证：**

```sql
-- 1. 当前格式与行镜像策略
SHOW VARIABLES LIKE 'binlog_format';
SHOW VARIABLES LIKE 'binlog_row_image';
SHOW VARIABLES LIKE 'sync_binlog';
SHOW VARIABLES LIKE 'binlog_expire_logs_seconds';

-- 2. 查看 binlog 列表与当前写入位置
SHOW BINARY LOGS;
SHOW MASTER STATUS;      -- 8.0 可用；8.2+ 改为 SHOW BINARY LOG STATUS

-- 3. 观察 binlog 缓存是否落盘（大事务指标）
SHOW GLOBAL STATUS LIKE 'Binlog_cache_use';
SHOW GLOBAL STATUS LIKE 'Binlog_cache_disk_use';

-- 4. 用 mysqlbinlog 解析（ROW 格式需 --base64-output=DECODE-ROWS -v）
-- mysqlbinlog --base64-output=DECODE-ROWS -v /var/lib/mysql/binlog.000001 | less
-- mysqlbinlog --start-datetime='2026-10-01 00:00:00' binlog.000001 > replay.sql

-- 5. 事务提交与 2PC 的关系（概念验证）
START TRANSACTION;
UPDATE account SET balance = balance - 1 WHERE user_id = 1;
COMMIT;
-- 提交后：redo 有 prepare/commit 标记，binlog 有对应 XID 的事件

-- 6. GTID 模式（复制常用）
SHOW VARIABLES LIKE 'gtid_mode';
SHOW VARIABLES LIKE 'enforce_gtid_consistency';
```

**GTID 与 binlog：**

- GTID（Global Transaction Identifier）格式为 `server_uuid:transaction_id`，每个事务全局唯一。
- 开启 `gtid_mode=ON` 后，从库用 `SOURCE_AUTO_POSITION=1` 自动定位，不再依赖文件名 + 偏移量。
- GTID 要求 `binlog_format=ROW`、`enforce_gtid_consistency=ON`，并禁止部分不安全语句。

**面试怎么答：** 先讲三种格式与 8.0 默认 `ROW`，说明 `STATEMENT` 在非确定性函数与 RC 下的不一致风险；再讲 2PC 三步「prepare redo → 写 binlog → commit redo」与崩溃恢复的三种判断；最后补 `sync_binlog=1` 与组提交的权衡，以及 GTID 的作用。

**易错点：**

- binlog 不是 InnoDB 的日志，它属于 Server 层；关闭 binlog 不影响 InnoDB 崩溃恢复。
- 两阶段提交的「两阶段」指 redo 的 prepare/commit，不是「先写 binlog 再写 redo」。
- `sync_binlog=1` 与 `innodb_flush_log_at_trx_commit=1` 都开才接近「提交不丢」，只开一个仍有窗口。
- `STATEMENT` 格式下 `NOW()`、`RAND()`、`UUID()`、`LIMIT` 无 `ORDER BY` 都可能导致主从不一致。
- `max_binlog_size` 不是硬上限：一个大事务可能跨越多个文件，从库仍按事务整体重放。

## 12. 长事务的危害与治理

**长事务是「开启后长时间不提交的事务」，它最大的危害不是占连接，而是持有旧 Read View 与锁，导致 undo 无法 purge、锁等待扩散、主从延迟放大、回滚极慢**。治理的核心是「缩短事务边界 + 监控 + 兜底」。

**危害清单：**

| 危害 | 机制 | 表现 |
| --- | --- | --- |
| undo 膨胀 | 旧 Read View 阻止 purge | `History list length` 持续增长，undo 表空间暴涨 |
| 锁持有时间长 | 行锁/间隙锁不释放 | 其他事务锁等待、超时、死锁概率上升 |
| MDL 阻塞 DDL | 长事务持有 MDL 读锁 | DDL 排队，后续 DML 全部阻塞 |
| 主从延迟 | 大事务在从库回放耗时长 | `Seconds_Behind_Master` 上升 |
| 回滚慢 | 需要按 undo 逆序执行 | `KILL` 后长时间处于 rollback 状态 |
| 临时表/内存 | 大查询、排序、临时表 | 磁盘临时表增长、IO 抖动 |
| 连接占用 | 事务期间连接不能复用 | 连接池耗尽 |

**排查 SQL：**

```sql
-- 1. 按开始时间找出长事务（最关键）
SELECT trx_id, trx_state, trx_started,
       TIMESTAMPDIFF(SECOND, trx_started, NOW()) AS seconds,
       trx_mysql_thread_id, trx_query,
       trx_rows_locked, trx_rows_modified, trx_isolation_level
FROM information_schema.innodb_trx
ORDER BY trx_started
LIMIT 20;

-- 2. 只看超过 60 秒的事务
SELECT trx_id, trx_mysql_thread_id,
       TIMESTAMPDIFF(SECOND, trx_started, NOW()) AS seconds,
       trx_rows_modified, trx_query
FROM information_schema.innodb_trx
WHERE TIMESTAMPDIFF(SECOND, trx_started, NOW()) > 60
ORDER BY seconds DESC;

-- 3. 长事务是否阻塞了别人
SELECT * FROM sys.innodb_lock_waits\G

-- 4. 当前连接在做什么（区分 Sleep 与真正执行）
SELECT ID, USER, HOST, DB, COMMAND, TIME, STATE, INFO
FROM information_schema.PROCESSLIST
WHERE COMMAND <> 'Sleep'
ORDER BY TIME DESC;

-- 5. undo 堆积情况
SHOW ENGINE INNODB STATUS\G
-- 关注 History list length

-- 6. 是否存在未提交的只读事务（也可能是长事务）
SELECT trx_id, trx_state, trx_started, trx_query
FROM information_schema.innodb_trx
WHERE trx_state = 'RUNNING' AND trx_query IS NULL;
```

**治理手段：**

1. **关闭自动提交的误用**：应用连接池初始化时确认 `autocommit=1`，只在需要时显式 `START TRANSACTION`。
2. **缩短事务边界**：事务内只放数据库操作，RPC、消息、文件 IO、循环查询全部移出。
3. **拆分大批量操作**：`UPDATE ... LIMIT 1000` 循环，或按主键区间分批提交。
4. **设置语句超时**：`SET SESSION max_execution_time = 5000;`（仅对 `SELECT` 生效，单位毫秒）。
5. **设置锁等待超时**：`innodb_lock_wait_timeout` 按业务调小（如 5~10 秒），避免无限等待。
6. **连接空闲超时**：`wait_timeout`、`interactive_timeout` 控制空闲连接，避免「开了事务却忘了提交」的连接长期挂起。
7. **监控告警**：对 `innodb_trx` 中超过阈值的事务、`History list length`、`Innodb_row_lock_time` 做告警。
8. **兜底 Kill**：确认业务影响后 `KILL <thread_id>`；注意大事务回滚可能持续很久，必要时评估重启或从库切换。
9. **代码规范**：禁止在事务中调用外部服务、禁止 `for` 循环里逐条 SQL、禁止无界批量更新。

**可执行示例：**

```sql
-- 会话 A：模拟长事务（事务内休眠 120 秒）
START TRANSACTION;
UPDATE account SET balance = balance - 1 WHERE user_id = 1;
SELECT SLEEP(120);
COMMIT;

-- 会话 B：观察长事务
SELECT trx_id, trx_mysql_thread_id,
       TIMESTAMPDIFF(SECOND, trx_started, NOW()) AS seconds,
       trx_rows_modified, trx_state
FROM information_schema.innodb_trx
ORDER BY trx_started;

-- 会话 B：查看它持有的锁
SELECT ENGINE_TRANSACTION_ID, OBJECT_NAME, INDEX_NAME, LOCK_MODE, LOCK_DATA
FROM performance_schema.data_locks
WHERE ENGINE_TRANSACTION_ID = <trx_id>;

-- 会话 B：确认影响后终止（KILL 后事务进入回滚，连接可能仍显示 rollback）
KILL <trx_mysql_thread_id>;

-- 会话 B：观察回滚进度
SELECT trx_id, trx_state, trx_rows_modified
FROM information_schema.innodb_trx
WHERE trx_id = <trx_id>;

-- 应用侧：语句级超时与事务内禁止外部调用（示意）
SET SESSION max_execution_time = 3000;
SET SESSION innodb_lock_wait_timeout = 5;
```

**面试怎么答：** 先列危害「undo 不能 purge、锁不释放、MDL 阻塞 DDL、主从延迟、回滚慢」，再给排查 SQL（`innodb_trx` 按 `trx_started` 排序、`History list length`、`sys.innodb_lock_waits`），最后讲治理：缩短事务、拆分批量、设置超时、监控告警、必要时 Kill。强调「长事务往往不是慢 SQL，而是事务边界设计错误」。

**易错点：**

- 长事务不一定是「执行很久的 SQL」，也可能是「开着事务但连接在 Sleep」，要看 `trx_started` 而不是 `PROCESSLIST.TIME`。
- `max_execution_time` 只对只读 `SELECT` 生效，不能终止 `UPDATE`/`DELETE`。
- `KILL` 只是发起终止，大事务回滚需要时间，期间仍占资源，不能假设立刻释放。
- 只读事务在某些驱动/框架中也会开启（如 `@Transactional(readOnly=true)`），同样会持有 Read View。
- 把 `wait_timeout` 调得过大并不能解决长事务，反而让「忘记提交」的连接存活更久。

## 本篇小结

- **事务**：A 靠 undo、D 靠 redo + doublewrite、I 靠锁 + MVCC、C 是目标而非单一机制。
- **隔离**：RC 每条语句一个快照、RR 每个事务一个快照；RR 的当前读用 Next-Key Lock 防幻读，但混用快照读与当前读仍有语义差。
- **锁**：行锁锁索引，间隙锁只在 RR 生效；无索引的当前读接近锁表。
- **日志**：redo 物理、循环写、用于崩溃恢复；undo 逻辑、用于回滚与 MVCC；binlog 逻辑、用于复制；2PC 保证 redo 与 binlog 一致。
- **工程**：短事务、固定加锁顺序、走索引、监控 `innodb_trx` 与 `History list length`，比任何参数调优都重要。
