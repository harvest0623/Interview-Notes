## 1. 主从复制的原理与复制模式

**MySQL 主从复制是「主库写 binlog、从库拉取并重放」的异步日志复制**：主库的 `binlog dump` 线程把 binlog 发给从库，从库的 IO 线程写入 relay log，SQL（回放）线程按顺序执行 relay log，从而在从库重放出相同的数据变更。

**三个线程与两个日志：**

| 角色 | 所在节点 | 职责 |
| --- | --- | --- |
| `binlog dump` 线程 | 主库 | 每个从库连接一个，读取 binlog 并发送 |
| IO 线程 | 从库 | 连接主库、接收 binlog、写入 relay log |
| SQL 线程（回放线程） | 从库 | 读取 relay log 并在从库执行 |
| binlog | 主库 | 记录所有数据变更，复制的数据源 |
| relay log | 从库 | 本地缓存的待回放日志，回放后可清理 |

**复制流程：**

1. 从库执行 `CHANGE REPLICATION SOURCE TO ...` 配置主库地址、账号、起始位点或 GTID。
2. 从库 IO 线程连接主库，主库为它创建 `binlog dump` 线程。
3. 主库把 binlog 事件按位点发送；从库 IO 线程写入本地 relay log，并更新 `Relay_Master_Log_File` 与 `Read_Master_Log_Pos`。
4. 从库 SQL 线程读取 relay log，按事务顺序回放，更新 `Exec_Master_Log_Pos` / `Executed_Gtid_Set`。
5. 回放完成后，relay log 可被清理；复制延迟通过位点差或 GTID 差衡量。

**复制模式：**

| 模式 | 机制 | 数据安全 | 性能 | 适用 |
| --- | --- | --- | --- | --- |
| 异步复制 | 主库提交后立即返回，不等待从库 | 主库宕机可能丢未传送事务 | 最高 | 普通业务、允许少量丢失 |
| 半同步（AFTER_COMMIT） | 等至少一个从库收到 binlog 并写 relay log 后再返回 | 比异步好，但主库已提交仍可能丢 | 中等 | 5.6 传统半同步 |
| 半同步（AFTER_SYNC，增强） | 先等从库 ACK 再提交，主库崩溃不丢已 ACK 事务 | 更好，5.7+ 推荐 | 中等 | 金融、订单核心 |
| 组复制 MGR | Paxos 多数派确认 | 强一致、自动选主 | 较低 | 核心系统、高可用 |

**半同步的关键参数（8.0.26+ 命名）：**

```sql
-- 主库
INSTALL PLUGIN rpl_semi_sync_source SONAME 'semisync_source.so';
SET GLOBAL rpl_semi_sync_source_enabled = ON;
SET GLOBAL rpl_semi_sync_source_timeout = 1000;          -- 毫秒，超时后退化为异步
SET GLOBAL rpl_semi_sync_source_wait_point = AFTER_SYNC; -- 5.7+ 默认，增强半同步

-- 从库
INSTALL PLUGIN rpl_semi_sync_replica SONAME 'semisync_replica.so';
SET GLOBAL rpl_semi_sync_replica_enabled = ON;

-- 5.7 旧命名：rpl_semi_sync_master_* / rpl_semi_sync_slave_*
```

**GTID 复制（推荐）：**

- GTID 形如 `3E11FA47-71CA-11E1-9E33-C80AA9429562:1-100`，每个事务有全局唯一 ID。
- 从库用 `SOURCE_AUTO_POSITION=1` 自动向主库请求缺失事务，不再手工算 binlog 位点。
- 主库故障切换后，新主库的 GTID 集合可判断哪些事务已执行，避免重复或遗漏。

**8.0 复制命令（5.7 用 `MASTER`/`SLAVE` 旧语法）：**

```sql
-- 主库：查看当前 binlog 位点与 GTID
SHOW MASTER STATUS;
SELECT @@gtid_mode, @@server_uuid;

-- 从库：8.0.22+ 推荐语法
CHANGE REPLICATION SOURCE TO
  SOURCE_HOST = '10.0.0.11',
  SOURCE_PORT = 3306,
  SOURCE_USER = 'repl',
  SOURCE_PASSWORD = '***',
  SOURCE_AUTO_POSITION = 1,
  SOURCE_CONNECT_RETRY = 10,
  SOURCE_RETRY_COUNT = 86400;

START REPLICA;
SHOW REPLICA STATUS\G

-- 5.7 / 8.0.22 之前的旧语法
-- CHANGE MASTER TO MASTER_HOST='10.0.0.11', MASTER_AUTO_POSITION=1;
-- START SLAVE;
-- SHOW SLAVE STATUS\G

-- 关键字段
-- Replica_IO_Running / Replica_SQL_Running 必须都为 Yes
-- Seconds_Behind_Source：延迟秒数（估算，见下一题）
-- Retrieved_Gtid_Set / Executed_Gtid_Set：已拉取 / 已回放的 GTID
-- Last_IO_Error / Last_SQL_Error：复制错误
```

**并行复制：**

- 5.7 起支持基于组提交的并行回放：`replica_parallel_type=LOGICAL_CLOCK`，`replica_parallel_workers=N`。
- 8.0 增加 `WRITESET` 依赖追踪（`binlog_transaction_dependency_tracking=WRITESET`），无冲突事务可并行回放。
- 并行度不是越大越好：受主库组提交并发度、从库 CPU 与磁盘限制，通常设为 CPU 核数的 2~4 倍并压测验证。

**面试怎么答：** 先讲「三个线程 + 两个日志」和完整流程，再对比异步/半同步/MGR 的安全性与性能，重点说清 `AFTER_SYNC` 与 `AFTER_COMMIT` 的差别（主库何时返回、是否会丢已 ACK 事务），最后补 GTID 与并行复制如何降低运维复杂度与延迟。

**易错点：**

- 半同步不是「强同步」：超时后会退化为异步，仍可能丢数据；要配合 `rpl_semi_sync_source_timeout` 与监控。
- `AFTER_COMMIT` 下主库已经提交才等 ACK，主库崩溃时已提交事务可能未传到从库；`AFTER_SYNC` 先等 ACK 再提交，更安全。
- `Seconds_Behind_Source` 不是精确延迟，见下一题。
- 从库的 SQL 线程是单线程还是并行，取决于 `replica_parallel_workers` 与依赖追踪，不是「从库永远单线程」。
- 复制过滤规则（`replicate-do-table` 等）配置错误会导致从库缺表，且 GTID 模式下部分过滤不被允许。

## 2. 读写分离与主从延迟

**读写分离把写请求发主库、读请求发从库，以提升读吞吐，但引入「主从延迟」导致读到旧数据**。延迟的根因通常是「主库并发写入速度 > 从库单线程/并行回放速度」，典型放大因素是大事、无主键表的行复制、从库额外压力与 DDL。

**延迟的常见原因：**

| 原因 | 机制 | 处理 |
| --- | --- | --- |
| 大事务 | 一个事务在从库整体回放，期间位点不推进 | 拆分事务、控制批量大小 |
| 无主键/无索引表 | ROW 格式下每行变更需全表扫描定位 | 所有表必须有主键 |
| 从库压力大 | 从库承担大量读、备份、报表 | 读流量分摊、报表走专用从库 |
| 并行度不足 | 单 SQL 线程回放，主库多线程写入 | 开 `LOGICAL_CLOCK`/`WRITESET` 并行复制 |
| 主库写入突增 | 批量导入、活动峰值 | 限流、削峰、错峰 |
| DDL | 大表 DDL 在从库重放耗时长 | gh-ost/pt-osc、低峰执行 |
| 网络/IO | binlog 传输慢、relay log 落盘慢 | 检查带宽、磁盘 IO |

**延迟的度量：**

- `Seconds_Behind_Source`（5.7 名为 `Seconds_Behind_Master`）：从库当前回放时间与主库 binlog 事件时间戳之差。**它为 0 不代表无延迟**：relay log 可能还有未回放事务；大事务执行期间该值可能突然跳变。
- **位点差**：`Read_Master_Log_Pos - Exec_Master_Log_Pos`，反映已拉取未回放量，但不同 binlog 文件不可直接相减。
- **GTID 差**：`Retrieved_Gtid_Set - Executed_Gtid_Set`，最直观。
- **心跳表**：`pt-heartbeat` 每秒在主库更新时间戳，从库读该时间戳计算真实延迟，是最可靠的方式。

```sql
-- 1. 复制状态关键字段
SHOW REPLICA STATUS\G
-- Replica_IO_Running / Replica_SQL_Running
-- Seconds_Behind_Source
-- Relay_Log_Space
-- Retrieved_Gtid_Set / Executed_Gtid_Set

-- 2. 用 GTID 差判断还有多少事务未回放（8.0）
SELECT
  @@global.gtid_executed AS executed_on_this_node;

-- 3. 等待从库追平到指定 GTID（读己之写兜底，超时返回 NULL）
SELECT WAIT_FOR_EXECUTED_GTID_SET('3E11FA47-71CA-11E1-9E33-C80AA9429562:1-1000', 2);

-- 4. 心跳表方案（pt-heartbeat 会在主库创建）
-- 主库写入心跳
-- pt-heartbeat --host=master --daemonize --update --interval=1
-- 从库计算延迟
-- pt-heartbeat --host=replica --monitor --interval=1

-- 5. 观察从库回放线程与并行度
SHOW VARIABLES LIKE 'replica_parallel_workers';
SHOW VARIABLES LIKE 'replica_parallel_type';
SHOW PROCESSLIST;   -- 可见 system user 的回放线程
```

**解决「读到旧数据」的工程手段：**

1. **写后读主**：同一请求内写完立即读，强制路由到主库；或按业务标记（下单、支付）短时间走主库。
2. **会话粘滞**：同一用户会话在 N 秒内读请求都走主库。
3. **GTID 等待**：事务提交后拿到 GTID，读从库前 `WAIT_FOR_EXECUTED_GTID_SET` 等待追平。
4. **半同步 + 并行复制**：降低延迟到毫秒级，但仍不是零。
5. **缓存补偿**：写后更新缓存，读走缓存而不是从库。
6. **业务容忍**：商品列表、评论等场景可接受最终一致，核心链路（余额、库存）必须走主库。

**读写分离的架构位置：**

| 方案 | 说明 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 应用层多数据源 | 代码中配置主/从数据源，AOP 或注解路由 | 简单、可控 | 侵入业务、易漏配 |
| 中间件代理 | ProxySQL、MaxScale、MyCat | 统一路由、支持读写分离与故障转移 | 多一跳、需运维 |
| 云数据库代理 | RDS 读写分离地址 | 免运维、自动权重 | 受云厂商能力限制 |

**面试怎么答：** 先讲「为什么延迟」：从库回放速度跟不上主库写入，列出大事务、无主键表、从库压力、并行度不足；再讲「怎么度量」：`Seconds_Behind_Source` 不可靠，用 GTID 差或 `pt-heartbeat`；最后讲「怎么解决」：并行复制、拆大事务、写后读主、GTID 等待、缓存兜底。

**易错点：**

- `Seconds_Behind_Source=0` 不代表从库已追平：relay log 可能还有未执行事务，且该值在大事务期间会跳变。
- 读写分离不是「读全部走从库」：写后读、事务内读、强一致读必须走主库。
- 半同步只能降低「主库崩溃丢数据」的风险，不能消除延迟。
- 从库并行复制受主库事务依赖限制，主库单线程写入时从库也快不起来。
- 主从延迟会放大「缓存与数据库不一致」的窗口，缓存方案要按最终一致设计。

## 3. 分库分表的策略与问题

**分库分表是「单库单表容量/并发达到瓶颈后，把数据按规则拆分到多个库或表」的架构手段**，分为垂直拆分（按业务/字段）与水平拆分（按行）。它能提升容量与并发，但会引入跨库 JOIN、分布式事务、全局 ID、跨分片分页、扩容迁移等一整套复杂度，应作为索引与架构优化后的最后手段。

**拆分方式：**

| 类型 | 说明 | 例子 | 解决的问题 | 新问题 |
| --- | --- | --- | --- | --- |
| 垂直分库 | 按业务拆到不同库 | 订单库、用户库、商品库 | 业务解耦、单库压力 | 跨库 JOIN、分布式事务 |
| 垂直分表 | 冷热字段拆表 | 主表 + 扩展表（大字段） | 单表宽度、IO | 关联查询 |
| 水平分表 | 同库内按行拆多表 | `order_0` ~ `order_3` | 单表行数 | 跨表查询、路由 |
| 水平分库 | 按行拆到多库多表 | `db0.order_0` ~ `db3.order_3` | 容量与并发 | 全局 ID、跨库事务、扩容 |

**分片键与算法：**

| 算法 | 规则 | 优点 | 缺点 |
| --- | --- | --- | --- |
| `HASH` 取模 | `MOD(user_id, N)` | 数据均匀、实现简单 | 扩容需重新分布 |
| `RANGE` | 按时间/ID 区间 | 扩容方便、范围查询友好 | 热点集中（如最新月份） |
| 一致性哈希 | 哈希环 + 虚拟节点 | 扩容只迁移少量数据 | 实现复杂、可能不均 |
| 基因法 | 把分片键基因写入订单号 | 可用非分片键反查 | 需要 ID 生成配合 |

**分片键选择原则：**

1. **高基数、分布均匀**：`user_id` 优于 `status`。
2. **覆盖大多数查询**：分片键要出现在高频查询条件中，否则每次都要广播所有分片。
3. **避免跨分片事务**：同一业务聚合根（如一个用户的订单）落在同一分片。
4. **考虑扩容**：优先能「成倍扩容」的算法，或预留分片位。
5. **不要用可变字段**：分片键变更意味着数据迁移。

**可执行示例：**

```sql
-- 1. 分片计算：4 库 × 4 表
SELECT
  MOD(user_id, 4) AS db_index,
  MOD(user_id, 16) AS table_index;

-- 2. 每个分片表结构一致，仅后缀不同
CREATE TABLE order_0 LIKE order_info;
CREATE TABLE order_1 LIKE order_info;
CREATE TABLE order_2 LIKE order_info;
CREATE TABLE order_3 LIKE order_info;

-- 3. 按用户查询：能精确定位一个分片
SELECT * FROM order_2 WHERE user_id = 6 ORDER BY created_at DESC LIMIT 20;

-- 4. 按订单号查询：若订单号不含分片基因，只能广播所有分片
-- SELECT * FROM order_0 WHERE order_no = 'NO...'
-- UNION ALL SELECT * FROM order_1 WHERE order_no = 'NO...'
-- UNION ALL SELECT * FROM order_2 WHERE order_no = 'NO...'
-- UNION ALL SELECT * FROM order_3 WHERE order_no = 'NO...';

-- 5. 跨分片分页：各分片取 offset+size，再在应用层归并排序
SELECT id, user_id, created_at FROM order_0 ORDER BY created_at DESC LIMIT 1020;
SELECT id, user_id, created_at FROM order_1 ORDER BY created_at DESC LIMIT 1020;
SELECT id, user_id, created_at FROM order_2 ORDER BY created_at DESC LIMIT 1020;
SELECT id, user_id, created_at FROM order_3 ORDER BY created_at DESC LIMIT 1020;
-- 应用层合并 4 份结果，排序后取第 1001~1020 条

-- 6. 全局统计：需要并行查询各分片再汇总
SELECT SUM(cnt) AS total FROM (
  SELECT COUNT(*) AS cnt FROM order_0
  UNION ALL SELECT COUNT(*) FROM order_1
  UNION ALL SELECT COUNT(*) FROM order_2
  UNION ALL SELECT COUNT(*) FROM order_3
) t;
```

**分库分表后的典型问题：**

| 问题 | 表现 | 方案 |
| --- | --- | --- |
| 跨分片 JOIN | 无法用单库 JOIN | 冗余字段、宽表、应用层拼装、ES |
| 分布式事务 | 跨库更新无法用本地事务 | 最终一致、TCC、Saga、事务消息 |
| 跨分片分页/排序 | 每片取 N 条再归并，深分页放大 | 游标分页、搜索引、限制页数 |
| 全局唯一 ID | 自增主键冲突 | 雪花 ID、号段、Redis |
| 唯一约束 | 分片内唯一，全局不唯一 | 全局唯一表、布隆过滤器、基因法 |
| 扩容 | 取模分片需全量迁移 | 成倍扩容、一致性哈希、双写迁移 |
| 聚合统计 | 需扫全部分片 | 汇总表、离线数仓、ClickHouse |
| 运维复杂度 | 多库备份、监控、DDL | 中间件、自动化平台 |

**扩容思路（成倍扩容）：**

- 从 4 片扩到 8 片时，每个旧分片的数据按「新分片 = 旧分片 + 4」拆成两半，只需迁移一半数据。
- 迁移期间双写 + 数据校验 + 灰度读，确认一致后切写。
- 避免「4 扩 5」这种非成倍扩容，否则几乎所有数据都要重分布。

**基因法（订单号带分片信息）：**

- 生成订单 ID 时，把 `user_id` 的低 N 位嵌入订单 ID 的低位，使 `order_id % 16 == user_id % 16`。
- 这样按订单号查询也能定位到用户所在分片，避免广播。
- 代价是订单 ID 不再连续，且分片数变化时基因位要重新设计。

**面试怎么答：** 先区分垂直/水平、分库/分表，再讲分片键与算法（HASH、RANGE、一致性哈希、基因法），重点说清「分片键要覆盖高频查询」；然后主动列问题：跨库 JOIN、分布式事务、跨分片分页、全局 ID、唯一约束、扩容；最后给结论：优先索引/缓存/归档，分库分表是最后手段。

**易错点：**

- 分库分表不是「性能银弹」：单表 2000 万行但查询都能走索引时，未必需要拆分。
- 只按 `status`、`created_at` 分片会导致热点或广播查询。
- 取模分片扩容成本极高，设计时就要考虑成倍扩容或一致性哈希。
- 跨分片分页在深分页时会把 `offset` 放大到每个分片，比单表更慢。
- 分片后仍要遵守索引规范：每个分片表都要有合适索引，否则只是把慢查询复制了 N 份。

## 4. 分布式 ID 的生成方案

**分布式 ID 的核心要求是「全局唯一、趋势递增、高可用、低延迟、不易被猜测」**。常见方案有数据库自增/号段、Redis `INCR`、雪花算法、UUID，以及美团 Leaf、百度 UidGenerator 等工程化实现；没有一种方案同时满足所有要求，要按业务取舍。

**方案对比：**

| 方案 | 唯一性 | 有序性 | 性能 | 依赖 | 缺点 |
| --- | --- | --- | --- | --- | --- |
| 数据库自增 | 单库唯一 | 严格递增 | 受单库写入限制 | MySQL | 单点、分库冲突、扩容难 |
| 数据库多主步长 | 多库唯一 | 趋势递增 | 中等 | MySQL | 扩容需改步长、ID 有空洞 |
| 号段模式 | 唯一 | 趋势递增 | 高（批量取号） | MySQL + 本地缓存 | 服务重启可能浪费号段 |
| Redis `INCR` | 唯一 | 递增 | 高 | Redis | 依赖 Redis 可用性、持久化风险 |
| 雪花算法 | 唯一 | 趋势递增 | 极高（本地生成） | 机器号分配 | 时钟回拨、机器号管理 |
| UUID | 唯一 | 无序 | 高（本地生成） | 无 | 太长、索引不友好、不可读 |

**雪花算法（Snowflake）的 64 位布局：**

| 位段 | 位数 | 作用 |
| --- | --- | --- |
| 符号位 | 1 | 恒为 0，保证正数 |
| 时间戳 | 41 | 毫秒级，可用约 69 年 |
| 机器 ID | 10 | 最多 1024 个节点（可拆 5 位机房 + 5 位机器） |
| 序列号 | 12 | 同一毫秒同一节点最多 4096 个 ID |

- 单节点理论峰值：4096 ID/毫秒，约 409 万 ID/秒。
- 时间戳左移 22 位、机器号左移 12 位、序列号占低 12 位。
- 时钟回拨处理：小幅回拨等待追平；大幅回拨拒绝服务并告警；或改用「逻辑时间」保证单调。

**号段模式（Leaf-segment）：**

1. 数据库维护 `sequence` 表，记录业务名与当前最大值。
2. 服务一次取一个号段（如 1000 个），在本地内存分配，用完再取。
3. 双 buffer：当前号段消耗到 10% 时异步预取下一段，避免取号停顿。
4. 服务重启会丢弃未用完的号段，ID 出现空洞，但保证唯一与趋势递增。

**可执行示例：**

```sql
-- 1. 数据库自增：8.0 起自增计数器持久化，重启不回退（5.7 可能回退）
CREATE TABLE id_auto (
  id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  biz_tag VARCHAR(32) NOT NULL,
  PRIMARY KEY (id)
) ENGINE=InnoDB;

-- 2. 多主步长：两台实例分别用 offset 1/2、increment 2
SET GLOBAL auto_increment_increment = 2;
SET GLOBAL auto_increment_offset = 1;   -- 另一台设为 2
-- 生成序列：1,3,5,7... 与 2,4,6,8...

-- 3. 号段模式：一次取 1000 个，返回起始值
CREATE TABLE sequence (
  biz_tag VARCHAR(32) NOT NULL,
  max_id BIGINT UNSIGNED NOT NULL DEFAULT 0,
  step INT UNSIGNED NOT NULL DEFAULT 1000,
  updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (biz_tag)
) ENGINE=InnoDB;
INSERT INTO sequence (biz_tag, max_id, step) VALUES ('order', 0, 1000);

START TRANSACTION;
UPDATE sequence SET max_id = LAST_INSERT_ID(max_id + step)
WHERE biz_tag = 'order';
SELECT LAST_INSERT_ID() AS segment_start;   -- 本次号段起点
COMMIT;
-- 应用拿到 [segment_start, segment_start + step) 在本地分配

-- 4. Redis 方案（命令示例，非 SQL）
-- INCR order:id
-- INCRBY order:id 1000

-- 5. 雪花 ID 的位运算演示（用 SQL 模拟，仅用于理解）
SELECT
  (1717171717171 << 22)                    -- 时间戳部分
  | (12 << 12)                              -- 机器号 12
  | 345 AS snowflake_like_id;

-- 6. 查看当前自增相关参数
SHOW VARIABLES LIKE 'auto_increment%';
```

**选型建议：**

1. **单体/小规模**：数据库自增足够，简单可靠。
2. **分库分表但 QPS 中等**：号段模式，数据库压力小、ID 趋势递增。
3. **高并发、多机房**：雪花算法 + 统一机器号分配（ZooKeeper/配置中心），做好时钟同步。
4. **绝对不重复、可接受无序**：UUID（建议 v7 或二进制存储），但不要做主键。
5. **已有 Redis 且能容忍持久化风险**：`INCR` 简单，但要配置 AOF 与主从。

**面试怎么答：** 先给五个要求「唯一、有序、高可用、低延迟、安全」，再对比四类方案，重点讲雪花 64 位布局与时钟回拨处理、号段模式的双 buffer；最后给选型：小规模自增、分库分表号段、高并发雪花、UUID 只做业务标识不做主键。

**易错点：**

- UUID 做主键会导致聚簇索引随机插入、页分裂、二级索引膨胀，性能很差。
- 雪花算法依赖机器号唯一，机器号重复会直接产生重复 ID。
- 时钟回拨不是小概率事件：NTP 校时、虚拟机迁移都可能触发，必须有兜底策略。
- 号段模式重启会浪费未用完的号段，ID 不连续但唯一，不要拿它做「无空洞」假设。
- MySQL 8.0 才持久化自增计数器；5.7 重启后可能复用已删除的最大值附近 ID。

## 5. 高可用方案（MHA、MGR、云数据库）

**MySQL 高可用的核心是「故障检测 + 选主 + 流量切换 + 防脑裂」**。常见方案有 MHA（外部管理、成熟但需自建）、MGR（原生 Paxos 组复制、自动选主）、InnoDB Cluster（MGR + Shell + Router）、Orchestrator（拓扑管理）以及云数据库的多可用区自动切换。

**方案对比：**

| 方案 | 原理 | 节点要求 | 切换时间 | 数据安全 | 运维成本 | 适用 |
| --- | --- | --- | --- | --- | --- | --- |
| MHA | Manager 监控 + 补 relay log + 提升新主 + VIP | 1 主 2 从 + 管理节点 | 约 10~60 秒 | 依赖 relay log 完整性，可能丢少量 | 中，需 SSH 与脚本 | 传统自建机房 |
| MGR | Paxos 多数派确认，自动选主 | 至少 3 节点 | 秒级~数十秒 | 多数派确认，强一致 | 高，对网络敏感 | 核心系统、云原生 |
| InnoDB Cluster | MGR + MySQL Shell + Router | 3 节点起 | 秒级 | 同 MGR | 中，官方工具链 | 新建集群 |
| Orchestrator | 拓扑发现 + 故障切换 + 钩子 | 任意复制拓扑 | 秒级~分钟 | 取决于复制模式 | 中 | 已有主从架构 |
| 云 RDS 多可用区 | 主备半同步 + 自动切换 | 云托管 | 约 30~60 秒 | 半同步，通常不丢 | 低 | 大多数业务 |

**MHA 的工作流程：**

1. Manager 节点定期探测主库，同时从各从库采集 binlog 位点。
2. 主库不可达后，Manager 选出「relay log 最全」的从库，补拉未接收的 binlog。
3. 提升该从库为新主，其他从库 `CHANGE MASTER TO` 新主。
4. 通过 VIP 漂移或 DNS 切换把写流量引到新主。
5. 原主恢复后作为新从库重新加入。

```bash
# MHA 常用命令（需安装 mha4mysql-manager）
masterha_check_repl --conf=/etc/mha/app.cnf      # 检查复制状态
masterha_check_status --conf=/etc/mha/app.cnf    # 查看 Manager 状态
masterha_manager --conf=/etc/mha/app.cnf         # 启动监控
masterha_master_switch --conf=/etc/mha/app.cnf --master_state=dead --dead_master_host=10.0.0.11
masterha_master_switch --conf=/etc/mha/app.cnf --master_state=alive --new_master_host=10.0.0.12
```

**MGR 的关键约束：**

- 必须使用 InnoDB、`binlog_format=ROW`、开启 GTID、每张表有主键。
- 建议 3~9 个节点，多数派存活才能继续写入；2 节点没有容错能力。
- 默认单主模式（`group_replication_single_primary_mode=ON`），也可多主，但多主冲突处理复杂。
- 对网络延迟敏感，跨机房部署要评估 RTT；流控（flow control）会限制快节点等待慢节点。
- 不支持 `SERIALIZABLE` 隔离级别、不支持部分 DDL 与超大事务。

```sql
-- 1. 安装并启动组复制（每个节点执行，server_id 必须唯一）
INSTALL PLUGIN group_replication SONAME 'group_replication.so';

SET GLOBAL group_replication_group_name = 'aaaaaaaa-bbbb-cccc-dddd-eeeeeeeeeeee';
SET GLOBAL group_replication_start_on_boot = OFF;
SET GLOBAL group_replication_local_address = '10.0.0.11:33061';
SET GLOBAL group_replication_group_seeds = '10.0.0.11:33061,10.0.0.12:33061,10.0.0.13:33061';
SET GLOBAL group_replication_single_primary_mode = ON;

START GROUP_REPLICATION;

-- 2. 查看成员状态（ONLINE / RECOVERING / ERROR）
SELECT MEMBER_ID, MEMBER_HOST, MEMBER_PORT, MEMBER_STATE, MEMBER_ROLE
FROM performance_schema.replication_group_members;

-- 3. 查看当前主节点
SELECT MEMBER_ID, MEMBER_HOST
FROM performance_schema.replication_group_members
WHERE MEMBER_ROLE = 'PRIMARY';

-- 4. 手动切换主节点（MySQL Shell AdminAPI）
-- dba.setPrimaryInstance('10.0.0.12:3306')

-- 5. 查看组复制统计与流控
SELECT * FROM performance_schema.replication_group_stats\G
```

**防脑裂：**

- 脑裂是「两个节点都认为自己是主」，同时接受写入，导致数据分叉。
- MGR 用多数派投票避免：少数派自动变为只读，无法提交。
- MHA/主从方案需要额外机制：VIP 仲裁、网关只允许一个写入点、STONITH（ fencing）、监控脚本双检。
- 云 RDS 由控制面统一仲裁，用户侧通常无需处理，但要避免自行搭建双写。

**切换后的收尾：**

1. 确认新主 `read_only=OFF`、旧主 `read_only=ON` 并指向新主。
2. 校验复制链路与 GTID 集合，确认没有事务缺口。
3. 清理旧主未发送的 binlog，避免误重放。
4. 更新连接池/中间件/ DNS，验证写入与读取。
5. 复盘切换耗时、数据丢失量、告警是否及时。

**面试怎么答：** 先给高可用四要素「检测、选主、切流、防脑裂」，再对比 MHA/MGR/云 RDS 的切换时间与数据安全，重点讲 MGR 的多数派与三节点要求、MHA 依赖 relay log 补数据，最后补「切换后要校验 GTID 与只读状态」。

**易错点：**

- MHA 不是官方组件，依赖 SSH 与脚本，且 Manager 自身可能成为单点。
- MGR 两节点没有容错：任意一个挂掉就失去多数派，无法写入。
- 半同步/组复制只能降低丢数据概率，不能替代备份。
- 切换后旧主若未设置 `read_only`，可能被应用继续写入，造成双写分叉。
- 高可用不仅是「主库挂了怎么办」，还包括网络分区、磁盘满、DDL 阻塞等场景。

## 6. 连接池的原理与配置

**连接池通过复用 TCP 连接与认证会话，避免每次请求都经历「建连 → 认证 → 分配线程」的开销**。核心不是「池越大越好」，而是「池大小与数据库并发承载能力匹配」，同时保证 `maxLifetime` 小于数据库的 `wait_timeout`，避免拿到已被服务端关闭的死连接。

**连接的生命周期成本：**

| 阶段 | 成本 | 说明 |
| --- | --- | --- |
| TCP 三次握手 | 毫秒级 | 跨机房更明显 |
| 认证与权限校验 | 毫秒级 | 涉及系统表/缓存 |
| 会话初始化 | 中 | 字符集、时区、`sql_mode`、会话变量 |
| 服务端线程分配 | 中 | 一连接一线程，占用栈与内存 |
| 连接销毁 | 低 | 但频繁建连会放大以上成本 |

**HikariCP 关键参数：**

| 参数 | 默认值 | 作用 | 建议 |
| --- | --- | --- | --- |
| `maximumPoolSize` | 10 | 最大连接数 | 按 DB 承载与压测结果定，不是越大越好 |
| `minimumIdle` | 等于最大值 | 最小空闲连接 | 核心服务可等于最大值，避免扩缩抖动 |
| `connectionTimeout` | 30s | 获取连接超时 | 应小于接口超时，快速失败 |
| `idleTimeout` | 10min | 空闲连接回收 | 仅当 `minimumIdle < maximumPoolSize` 生效 |
| `maxLifetime` | 30min | 连接最大存活 | 必须小于 MySQL `wait_timeout` |
| `keepaliveTime` | 0（关闭） | 定期探活 | 跨网络设备/NAT 时建议开启 |
| `validationTimeout` | 5s | 连接有效性检测 | 配合 `connectionTestQuery` 或 JDBC4 的 `isValid` |
| `leakDetectionThreshold` | 0（关闭） | 连接泄漏检测 | 测试环境设 10~30s，生产慎用 |

**池大小怎么算：**

- PostgreSQL 社区的经验公式：`connections = ((core_count * 2) + effective_spindle_count)`，MySQL 同样适用。
- 4 核 + SSD 的实例，池大小 8~10 往往比 100 更好：过多连接会增加上下文切换、锁竞争与缓冲池争用。
- 最终以压测为准：逐步增加并发，观察 QPS、`Threads_running`、`Innodb_row_lock_time`、CPU，找到拐点。

**MySQL 服务端相关参数：**

```sql
-- 1. 连接上限与当前使用
SHOW VARIABLES LIKE 'max_connections';          -- 默认 151
SHOW STATUS LIKE 'Threads_connected';           -- 当前连接
SHOW STATUS LIKE 'Threads_running';             -- 正在执行
SHOW STATUS LIKE 'Max_used_connections';        -- 历史峰值
SHOW STATUS LIKE 'Aborted_connects';            -- 建连失败次数
SHOW STATUS LIKE 'Connection_errors%';

-- 2. 空闲超时：连接池 maxLifetime 必须小于它
SHOW VARIABLES LIKE 'wait_timeout';             -- 默认 28800 秒（8 小时）
SHOW VARIABLES LIKE 'interactive_timeout';      -- 交互式客户端超时
SHOW VARIABLES LIKE 'thread_cache_size';

-- 3. 连接按来源聚合，定位连接泄漏
SELECT SUBSTRING_INDEX(HOST, ':', 1) AS client_ip, COUNT(*) AS conns
FROM information_schema.PROCESSLIST
GROUP BY client_ip
ORDER BY conns DESC;

-- 4. 查看连接状态与最后一条 SQL
SELECT ID, USER, HOST, DB, COMMAND, TIME, STATE, LEFT(INFO, 80) AS sql_head
FROM information_schema.PROCESSLIST
WHERE COMMAND <> 'Sleep'
ORDER BY TIME DESC;

-- 5. performance_schema 线程视角（能看到后台线程）
SELECT THREAD_ID, NAME, TYPE, PROCESSLIST_STATE, PROCESSLIST_TIME
FROM performance_schema.threads
WHERE TYPE = 'FOREGROUND'
ORDER BY PROCESSLIST_TIME DESC
LIMIT 20;

-- 6. 调整连接上限（需评估内存：每连接约 256KB~数 MB）
SET GLOBAL max_connections = 500;
```

**连接池常见故障：**

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| `Communications link failure` | 连接被服务端 `wait_timeout` 关闭，池里是死连接 | `maxLifetime < wait_timeout`，开启 `keepaliveTime` |
| 获取连接超时 | 池太小或连接泄漏 | 查 `leakDetectionThreshold`、慢 SQL、未关闭的 `ResultSet` |
| 连接数打满 | 池总和超过 `max_connections`，或连接未归还 | 统一池配置、加监控、限流 |
| 短连接风暴 | 每次请求新建连接 | 启用池、预热、`minimumIdle` |
| 连接空闲但不释放 | 事务未提交、连接未 close | 检查代码与框架事务边界 |

**面试怎么答：** 先讲连接池的价值「复用建连与认证成本、控制并发」，再给关键参数与两条硬约束「`maxLifetime < wait_timeout`」「池大小按 DB 承载而非越大越好」，最后讲公式与压测方法、连接泄漏排查（`PROCESSLIST` 按 IP 聚合、`leakDetectionThreshold`）。

**易错点：**

- 池越大并不代表吞吐越高：超过 DB 承载后只会增加上下文切换与锁竞争。
- `maxLifetime` 大于 `wait_timeout` 时，池可能拿到已被服务端关闭的连接，报通信异常。
- `minimumIdle=maximumPoolSize` 是 Hikari 的默认行为，不是「固定池」的额外配置。
- 连接泄漏通常来自未关闭的 `Connection`/`ResultSet` 或长事务，调大池只是拖延故障。
- MySQL 的 `wait_timeout` 与 `interactive_timeout` 要一起看，交互式客户端取后者。

## 7. 缓存与 MySQL 的数据一致性

**缓存与数据库的经典方案是 Cache Aside：读时「缓存未命中查库并回填」，写时「先更新数据库，再删除缓存」**。这套方案保证最终一致，但在并发读写下仍有短暂不一致窗口；强一致需要牺牲性能或用锁/串行化，通常不应把缓存当唯一数据源。

**三种常见模式：**

| 模式 | 读 | 写 | 问题 |
| --- | --- | --- | --- |
| Cache Aside | 先读缓存，未命中查库回填 | 更新库后删缓存 | 并发下可能回填旧值 |
| Read/Write Through | 缓存层代理读写 | 缓存层同步写库 | 实现复杂，缓存层要可靠 |
| Write Behind | 读缓存 | 写缓存后异步批量落库 | 宕机丢数据，一致性最弱 |

**为什么是「删除缓存」而不是「更新缓存」：**

- 更新缓存需要写入完整值，并发写时后写的可能覆盖先写的。
- 删除是幂等的，下次读自然回填最新值。
- 若缓存结构复杂（多表拼装），更新成本高且容易漏字段。

**为什么是「先更新库、再删缓存」：**

- 若先删缓存再更新库：删后、更新前有读请求，会把旧值回填，之后库更新，缓存长期是旧值。
- 先更新库再删缓存：即使删缓存失败，也有重试/订阅 binlog 兜底；窗口更小。
- 仍存在经典并发问题：读请求未命中 → 查库得到旧值 → 写请求更新库并删缓存 → 读请求把旧值写回缓存。解决办法是「延迟双删」或「版本号/逻辑过期」。

**延迟双删：**

```
1. 更新数据库
2. 删除缓存
3. 延迟 500ms~1s（大于一次读请求的查库+回填耗时）
4. 再删除一次缓存
```

延迟时间要覆盖「并发读回填」的窗口，不能拍脑袋；更可靠的做法是订阅 binlog（Canal/Debezium）异步删除，失败重试。

**可执行示例（SQL + Redis 命令）：**

```sql
-- 1. 更新数据库
UPDATE user_profile
SET nickname = '新昵称', updated_at = NOW()
WHERE user_id = 100;

-- 2. 删除缓存（应用侧执行，伪代码）
-- DEL user:profile:100
```

```bash
# 用 redis-cli 演示缓存回填与删除
redis-cli GET user:profile:100
redis-cli SET user:profile:100 '{"nickname":"旧昵称"}' EX 300
redis-cli DEL user:profile:100
redis-cli TTL user:profile:100
```

```sql
-- 3. 用数据库版本号辅助判断缓存新旧（可选）
SELECT user_id, nickname, version, updated_at
FROM user_profile
WHERE user_id = 100;
-- 缓存 value 中带 version，回填时若发现 version 更旧则丢弃

-- 4. 订阅 binlog 的兜底思路（Canal 配置，非 SQL）
-- 监听 user_profile 表的 UPDATE/INSERT/DELETE，异步删除对应缓存 key
-- 失败进入重试队列，保证最终删除成功
```

**缓存三大问题：**

| 问题 | 现象 | 方案 |
| --- | --- | --- |
| 缓存穿透 | 查询不存在的数据，每次都打到 DB | 缓存空值（短 TTL）、布隆过滤器、参数校验 |
| 缓存击穿 | 热点 key 过期瞬间大量请求打到 DB | 互斥锁重建、逻辑过期、热点永不过期 |
| 缓存雪崩 | 大量 key 同时过期或缓存集群故障 | TTL 加随机值、多级缓存、熔断降级、集群高可用 |

**强一致方案（谨慎使用）：**

- 读写都加分布式锁，串行化同一 key 的读写；性能差，仅用于极核心字段。
- 写请求更新库后同步更新缓存，并用版本号做 CAS。
- 关键读走主库，不用缓存（如余额、库存扣减的最终判断）。

**面试怎么答：** 先给 Cache Aside 的标准流程与「为什么删而不是更新」「为什么先更库再删缓存」，再主动指出并发下仍会脏读，给延迟双删、版本号、binlog 订阅三种兜底；最后补穿透/击穿/雪崩与强一致取舍。结论：缓存追求最终一致，强一致不要依赖缓存。

**易错点：**

- 「先删缓存再更新库」在并发读下更容易长期脏数据，不是推荐顺序。
- 延迟双删的延迟时间不是固定值，要按读请求耗时估算，且仍不是 100% 一致。
- 删除缓存失败必须有重试或 binlog 补偿，不能假设一次 `DEL` 一定成功。
- 缓存空值要设置较短 TTL，否则新增数据后仍会长时间返回空。
- 缓存雪崩不仅是「同时过期」，还包括 Redis 主从切换、网络分区、集群扩容等故障。

## 8. 大表 DDL 的平滑方案

**大表 DDL 的核心矛盾是「变更表结构需要持有 MDL 排他锁，而长事务/大表复制会让锁等待无限放大」**。优先用 `ALGORITHM=INSTANT` 或 `INPLACE` 的在线 DDL；无法在线完成时，用 gh-ost / pt-osc 做「影子表 + 增量同步 + 原子切换」，把风险从业务阻塞转移到磁盘、主从延迟与运维复杂度。

**DDL 的三种算法：**

| 算法 | 行为 | 是否阻塞 DML | 空间需求 | 适用 |
| --- | --- | --- | --- | --- |
| `INSTANT` | 只改数据字典元数据 | 不阻塞 | 几乎无 | 8.0 加列/删列（见版本限制） |
| `INPLACE` | 原地重建/修改，期间允许 DML | 大部分时间不阻塞 | 可能需额外空间 | 加索引、改索引、部分列变更 |
| `COPY` | 建新表、逐行拷贝、再替换 | 全程阻塞写 | 约 2 倍表空间 | 复杂类型变更、老版本 |

**8.0 的 INSTANT 能力：**

- 8.0.12 起支持 `INSTANT` 在表末尾加列，只改元数据。
- 8.0.29 起支持任意位置加列、删列（`INSTANT`），但仍有限制（如不能与全文索引、压缩表等组合）。
- `RENAME COLUMN`、修改列默认值等部分操作也可 INSTANT。
- 修改列类型、字符集、`NULL` 约束通常需要 `INPLACE` 重建，不能 INSTANT。

**在线 DDL 的三个阶段：**

1. **Prepare**：申请 MDL 排他锁，检查表结构、磁盘空间、算法兼容性；此阶段可能被长事务阻塞。
2. **Execute**：允许并发 DML，DDL 线程扫描/重建数据，同时把并发 DML 记录到 row log 并在最后应用。
3. **Commit**：再次申请 MDL 排他锁（短暂），替换表定义/文件，释放锁。此阶段会短暂阻塞读写。

**可执行示例：**

```sql
-- 1. 先看表大小、行数，评估耗时与空间
SELECT table_name, table_rows,
       ROUND(data_length / 1024 / 1024, 2) AS data_mb,
       ROUND(index_length / 1024 / 1024, 2) AS index_mb
FROM information_schema.tables
WHERE table_schema = 'demo' AND table_name = 'order_info';

-- 2. 设置锁等待上限，避免 DDL 无限排队拖垮业务
SET SESSION lock_wait_timeout = 10;

-- 3. 显式指定算法与并发级别（不满足会直接报错，而不是偷偷降级）
ALTER TABLE order_info
  ADD COLUMN channel VARCHAR(16) NOT NULL DEFAULT '' COMMENT '渠道',
  ALGORITHM=INSTANT;

-- 4. 加索引：INPLACE + 允许并发 DML
ALTER TABLE order_info
  ADD INDEX idx_channel_created (channel, created_at),
  ALGORITHM=INPLACE, LOCK=NONE;

-- 5. 观察 DDL 是否在等 MDL
SELECT OBJECT_NAME, LOCK_TYPE, LOCK_DURATION, LOCK_STATUS
FROM performance_schema.metadata_locks
WHERE OBJECT_SCHEMA = 'demo' AND OBJECT_NAME = 'order_info';

-- 6. 查看当前 DDL 进度（8.0）
SELECT * FROM performance_schema.events_stages_current
WHERE EVENT_NAME LIKE '%alter%';

-- 7. 回滚 DDL（若已提交则只能再改回去）
ALTER TABLE order_info DROP INDEX idx_channel_created, ALGORITHM=INPLACE, LOCK=NONE;
```

**gh-ost 与 pt-osc 对比：**

| 维度 | gh-ost | pt-online-schema-change |
| --- | --- | --- |
| 增量同步 | 读 binlog（无触发器） | 在源表建触发器 |
| 对业务影响 | 较低，可限流、暂停 | 触发器增加源表写入开销 |
| 切换方式 | 原子 `RENAME TABLE` | 原子 `RENAME TABLE` |
| 前置要求 | `ROW` 格式 binlog、主键 | 主键/唯一索引、触发器权限 |
| 空间 | 约 2 倍表空间 | 约 2 倍表空间 |
| 复制延迟 | 可控制写入节奏 | 触发器与拷贝可能放大延迟 |

```bash
# gh-ost 示例：在影子表上执行 DDL，再原子切换
gh-ost \
  --host=10.0.0.11 --database=demo --table=order_info \
  --alter="ADD INDEX idx_channel_created (channel, created_at)" \
  --allow-on-master --execute \
  --max-load='Threads_running=50' \
  --critical-load='Threads_running=100' \
  --chunk-size=1000

# pt-online-schema-change 示例
pt-online-schema-change \
  --alter="ADD INDEX idx_channel_created (channel, created_at)" \
  --host=10.0.0.11 --user=dba --password='***' \
  D=demo,t=order_info --execute \
  --max-load='Threads_running=50' \
  --critical-load='Threads_running=100'
```

**降风险的执行规范：**

1. **低峰执行**，并提前确认无长事务、无大查询、无未提交事务。
2. **先在从库/预发验证**，确认算法、耗时、空间与复制延迟。
3. **设置 `lock_wait_timeout`**，拿不到 MDL 就失败重试，不要无限排队。
4. **监控 `Threads_running`、复制延迟、磁盘空间**，异常立即暂停 gh-ost。
5. **准备回滚方案**：DDL 前备份、保留旧表、确认反向 DDL 可执行。
6. **避免一次性改多列**：拆成多次小 DDL，降低单次风险。

**面试怎么答：** 先讲三种算法与「INSTANT 只改元数据、INPLACE 允许并发 DML、COPY 全程锁写」，再讲在线 DDL 三阶段的 MDL 风险；然后给 gh-ost/pt-osc 的「影子表 + 增量 + 原子切换」流程与对比；最后补执行规范：低峰、`lock_wait_timeout`、监控复制延迟、准备回滚。

**易错点：**

- `ALGORITHM=INPLACE` 不等于「完全不锁表」：开始与结束仍需要短暂 MDL 排他锁。
- `INSTANT` 有版本与表结构限制，不是所有 `ADD COLUMN` 都能瞬时完成。
- 大表 DDL 的直接风险往往不是主库，而是「从库回放 DDL 期间延迟暴涨」。
- pt-osc 的触发器会增加源表写入开销，高写入表优先 gh-ost。
- DDL 期间磁盘空间要按「原表 + 影子表 + binlog」估算，空间不足会直接失败。

## 9. 数据迁移与双写方案

**数据迁移的目标是「不停机、不丢数据、可回滚」**，标准流程是「评估 → 建目标 → 全量迁移 → 增量追平 → 双写 → 校验 → 灰度读 → 切写 → 下线旧库」。双写是过渡期的核心手段，但必须解决顺序、失败补偿、幂等与一致性校验四个问题。

**迁移阶段：**

| 阶段 | 动作 | 退出条件 |
| --- | --- | --- |
| 评估 | 表结构、数据量、写入 QPS、依赖关系、停机窗口 | 迁移方案与回滚方案评审通过 |
| 建目标 | 新库/新分片建表、索引、账号、监控 | 结构与旧库一致（或符合新规范） |
| 全量 | `mysqldump --single-transaction`、mydumper、clone plugin | 全量数据导入完成，行数核对通过 |
| 增量 | 解析 binlog（Canal/Debezium）持续追平 | 延迟稳定在秒级以内 |
| 双写 | 应用同时写旧库与新库 | 双写成功率、差异率达标 |
| 校验 | 行数、checksum、抽样、业务对账 | 差异为 0 或有明确解释 |
| 灰度读 | 按用户/比例读新库 | 错误率、耗时无异常 |
| 切写 | 写流量切到新库，旧库停写 | 观察期无回滚 |
| 下线 | 停止双写、备份旧库、回收资源 | 保留回滚窗口后清理 |

**全量与增量工具：**

```bash
# 1. 逻辑备份：单事务一致性快照，不锁表；--master-data=2 记录 binlog 位点
mysqldump --single-transaction --master-data=2 --set-gtid-purged=ON \
  --databases demo > demo_full.sql

# 2. 多线程逻辑备份/恢复（大数据量更快）
mydumper -h 10.0.0.11 -u dba -p '***' -B demo -o /backup/demo -t 8
myloader -h 10.0.0.12 -u dba -p '***' -B demo -d /backup/demo -t 8

# 3. 物理克隆（8.0 clone plugin，适合大库全量）
# 目标库执行：
# INSTALL PLUGIN clone SONAME 'mysql_clone.so';
# CLONE INSTANCE FROM 'dba'@'10.0.0.11':3306 IDENTIFIED BY '***';
```

```sql
-- 4. 记录迁移起点（全量时刻的 binlog 位点/GTID）
SHOW MASTER STATUS;
SELECT @@global.gtid_executed;

-- 5. 行数与关键指标核对
SELECT COUNT(*) AS cnt, SUM(pay_amount) AS amount_sum, MAX(id) AS max_id
FROM order_info;

-- 6. 分片/分表后的逐片核对
SELECT 'order_0' AS shard, COUNT(*) AS cnt, SUM(pay_amount) AS amt FROM order_0
UNION ALL SELECT 'order_1', COUNT(*), SUM(pay_amount) FROM order_1
UNION ALL SELECT 'order_2', COUNT(*), SUM(pay_amount) FROM order_2
UNION ALL SELECT 'order_3', COUNT(*), SUM(pay_amount) FROM order_3;
```

```bash
# 7. 逐行校验（pt-table-checksum，主从/双库差异）
pt-table-checksum --host=10.0.0.11 --user=dba --password='***' \
  --databases=demo --tables=order_info --replicate=demo.checksum

# 8. 找出差异行（pt-table-sync 只打印不执行）
pt-table-sync --host=10.0.0.11 --user=dba --password='***' \
  --databases=demo --tables=order_info --print
```

**双写的四种顺序与取舍：**

| 顺序 | 一致性 | 性能 | 风险 |
| --- | --- | --- | --- |
| 先旧库后新库 | 旧库为准，新库失败可补偿 | 串行，RT 增加 | 新库短时缺失 |
| 先新库后旧库 | 新库为准，旧库失败可补偿 | 串行 | 旧库短时缺失，回滚困难 |
| 并发双写 | 快，但失败处理复杂 | 并行 | 部分成功，需对账修复 |
| 异步双写（消息） | 最终一致 | 最好 | 消息丢失/重复，需幂等 |

**工程建议：**

1. **以旧库为主**：迁移期旧库仍是权威数据源，新库失败只记录补偿，不回滚旧库。
2. **双写必须幂等**：用业务唯一键 + `INSERT ... ON DUPLICATE KEY UPDATE`，避免重试产生重复。
3. **失败落补偿表/消息**：记录失败的主键与操作，异步重试，达到阈值告警。
4. **不要引入强分布式事务**：双写 + 对账 + 补偿通常比 XA/TCC 更可控。
5. **灰度读按用户维度**：同一用户固定读一侧，避免同一请求跨库读到不同版本。
6. **保留回滚窗口**：切写后至少观察一个业务周期，旧库只读但可快速切回。

**双写幂等示例：**

```sql
-- 新库写入使用唯一键幂等
INSERT INTO order_info (order_no, user_id, status, pay_amount, created_at)
VALUES ('NO20261001001', 100, 1, 99.00, NOW())
ON DUPLICATE KEY UPDATE
  status = VALUES(status),
  pay_amount = VALUES(pay_amount),
  updated_at = NOW();

-- 补偿表：记录双写失败，异步重试
CREATE TABLE migration_retry (
  id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  biz_type VARCHAR(32) NOT NULL,
  biz_key VARCHAR(64) NOT NULL,
  payload JSON NOT NULL,
  retry_count INT UNSIGNED NOT NULL DEFAULT 0,
  next_retry_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  status TINYINT UNSIGNED NOT NULL DEFAULT 0,
  PRIMARY KEY (id),
  KEY idx_status_retry (status, next_retry_at),
  UNIQUE KEY uk_biz (biz_type, biz_key)
) ENGINE=InnoDB;

-- 取出待重试任务
SELECT id, biz_type, biz_key, payload
FROM migration_retry
WHERE status = 0 AND next_retry_at <= NOW()
ORDER BY next_retry_at
LIMIT 100;
```

**面试怎么答：** 按「全量 + 增量 + 双写 + 校验 + 灰度切流」讲完整链路，强调「旧库为权威、双写幂等、失败补偿、逐行校验、可回滚」；再对比双写顺序的取舍，说明为什么不用强分布式事务；最后补工具：mysqldump/mydumper、clone plugin、Canal、pt-table-checksum。

**易错点：**

- 全量迁移必须用一致性快照（`--single-transaction`），否则边迁边变会导致行数对不上。
- 增量追平要以「全量时刻的位点/GTID」为起点，起点选错会丢数据或重复。
- 双写「并发写」看似快，但部分成功时若无补偿，差异会长期存在。
- 只核对行数不够：金额、状态、更新时间等字段同样要校验。
- 切写后立即下线旧库风险很高，必须保留只读回滚窗口。

## 10. 慢查询监控与告警体系

**监控体系的目标是「先发现、再定位、可回溯」**：用 Prometheus + mysqld_exporter 采集指标，Grafana 展示，Alertmanager 分级告警；慢查询则靠慢日志 + `performance_schema` 聚合 + 定期 Top SQL 报告。指标要覆盖「可用性、性能、容量、复制、错误」五类。

**核心指标：**

| 类别 | 指标 | 说明 | 告警建议 |
| --- | --- | --- | --- |
| 可用性 | `mysql_up` | 实例是否可连接 | 1 分钟为 0 即 P0 |
| 性能 | QPS / TPS |  `Questions`、`Com_commit`+`Com_rollback` 速率 | 突增/突降 50% 告警 |
| 性能 | `Threads_running` | 正在执行的线程数 | 持续 > CPU 核数 × 2 |
| 性能 | 慢查询数 | `Slow_queries` 速率 | 连续 5 分钟 > 阈值 |
| 连接 | `Threads_connected` | 当前连接数 | > `max_connections` 的 80% |
| 连接 | `Aborted_connects` | 建连失败 | 速率突增 |
| 缓冲池 | 命中率 | `1 - reads/read_requests` | < 95%（OLTP） |
| 锁 | `Innodb_row_lock_waits` | 行锁等待次数 | 速率突增 |
| 锁 | `Innodb_row_lock_time_avg` | 平均等待毫秒 | > 100ms |
| 复制 | 延迟 | `Seconds_Behind_Source` 或心跳 | > 5 秒告警，> 30 秒 P1 |
| 复制 | 线程状态 | `Replica_IO/SQL_Running` | 非 Yes 即 P0 |
| 容量 | 磁盘使用率 | 数据盘/日志盘 | > 80% 预警，> 90% P1 |
| 容量 | binlog 增长 | 每小时增量 | 异常增长排查大事务 |
| 错误 | `Innodb_deadlocks` | 死锁次数 | 突增告警 |
| 临时表 | `Created_tmp_disk_tables` | 磁盘临时表 | 占比 > 10% |

**采集 SQL：**

```sql
-- 1. QPS / TPS（两次采样差值除以秒数）
SHOW GLOBAL STATUS LIKE 'Questions';
SHOW GLOBAL STATUS LIKE 'Com_commit';
SHOW GLOBAL STATUS LIKE 'Com_rollback';
SHOW GLOBAL STATUS LIKE 'Uptime';

-- 2. 连接与线程
SHOW GLOBAL STATUS LIKE 'Threads_connected';
SHOW GLOBAL STATUS LIKE 'Threads_running';
SHOW GLOBAL STATUS LIKE 'Max_used_connections';
SHOW VARIABLES LIKE 'max_connections';

-- 3. 缓冲池命中率
SHOW GLOBAL STATUS LIKE 'Innodb_buffer_pool_read_requests';
SHOW GLOBAL STATUS LIKE 'Innodb_buffer_pool_reads';

-- 4. 锁与死锁
SHOW GLOBAL STATUS LIKE 'Innodb_row_lock_waits';
SHOW GLOBAL STATUS LIKE 'Innodb_row_lock_time_avg';
SHOW GLOBAL STATUS LIKE 'Innodb_deadlocks';

-- 5. 临时表与排序
SHOW GLOBAL STATUS LIKE 'Created_tmp_tables';
SHOW GLOBAL STATUS LIKE 'Created_tmp_disk_tables';
SHOW GLOBAL STATUS LIKE 'Sort_merge_passes';

-- 6. 慢查询总量
SHOW GLOBAL STATUS LIKE 'Slow_queries';

-- 7. 复制状态（从库）
SHOW REPLICA STATUS\G

-- 8. 磁盘与表空间
SELECT table_schema,
       ROUND(SUM(data_length + index_length) / 1024 / 1024 / 1024, 2) AS size_gb
FROM information_schema.tables
GROUP BY table_schema
ORDER BY size_gb DESC;
```

**慢查询监控闭环：**

1. **采集**：慢日志 + `performance_schema.events_statements_summary_by_digest`，按指纹聚合。
2. **聚合**：每天输出 Top 20（按总耗时、平均耗时、扫描行数），对比上周变化。
3. **告警**：单条 SQL 平均耗时、慢查询速率、全表扫描次数超阈值。
4. **归因**：`EXPLAIN`、`EXPLAIN ANALYZE`、`rows_examined/rows_sent` 比值、`lock_time`。
5. **治理**：索引、SQL 改写、归档、限流；治理后回归对比指标。
6. **防回归**：上线前 SQL 审核（`soar`、`pt-query-digest` 静态检查），禁止无索引大表查询。

**告警分级：**

| 级别 | 定义 | 通知方式 | 例子 |
| --- | --- | --- | --- |
| P0 | 业务不可用 | 电话 + 群 + 工单 | 主库不可连、复制全断、磁盘满 |
| P1 | 性能严重下降 | 电话/短信 + 群 | 连接数 90%、延迟 > 30 秒、CPU 95% |
| P2 | 需要关注 | 群 + 邮件 | 慢查询突增、死锁增加、磁盘 80% |
| P3 | 趋势预警 | 日报 | 表容量增长、索引冗余 |

**面试怎么答：** 按「指标分类 → 采集 → 展示 → 告警分级 → 慢查询闭环」讲，强调「黄金指标」：可用性、QPS/TPS、延迟、错误率；再补 MySQL 特有指标：连接数、缓冲池命中率、锁等待、复制延迟、磁盘；最后说告警要分级、可抑制、能定位到 SQL 与主机。

**易错点：**

- 只监控 `Seconds_Behind_Source` 不够，它可能为 0 但 relay log 仍有积压。
- 缓冲池命中率要看长期趋势，短时低可能是冷启动或大查询。
- `Threads_running` 高不一定是 CPU 问题，也可能是锁等待或磁盘 IO。
- 告警阈值不能照搬：不同规格、不同业务基线不同，要用历史分位数动态调整。
- 只告警不治理会迅速疲劳，必须有 Top SQL 日报与责任人。

## 11. 统计与报表查询的优化

**报表查询的特点是「扫描行数大、聚合多、SQL 复杂」，直接跑在 OLTP 主库上会拖垮在线业务**。优化方向是「隔离（从库/专用库/OLAP）、预聚合（汇总表）、减少扫描（覆盖索引/分区）、控制资源（资源组/超时）、异步化（离线任务）」。

**优化手段：**

| 手段 | 做法 | 收益 | 代价 |
| --- | --- | --- | --- |
| 读写隔离 | 报表走只读从库/专用实例 | 保护主库 | 需处理延迟 |
| 预聚合 | 按天/小时生成汇总表 | 查询从扫明细变扫汇总 | 实时性下降、需调度 |
| 覆盖索引 | 索引包含聚合列 | 避免回表 | 索引变大 |
| 分区表 | 按时间分区 | 分区裁剪，只扫目标区间 | 分区管理、跨分区查询 |
| 分批查询 | 按主键/时间分片拉取 | 降低单次锁与内存 | 应用层聚合 |
| 资源组 | 限制报表线程 CPU 与优先级 | 防止抢占 OLTP | 8.0 才支持 |
| 列式存储 | 同步到 ClickHouse/Doris | 聚合快 10~100 倍 | 架构复杂、数据同步 |
| 异步任务 | 报表预生成、缓存结果 | 前端秒开 | 数据非实时 |

**预聚合示例：**

```sql
-- 1. 明细表按天汇总（离线任务，低峰执行）
CREATE TABLE order_daily_summary (
  stat_date DATE NOT NULL,
  shop_id BIGINT UNSIGNED NOT NULL,
  order_cnt BIGINT UNSIGNED NOT NULL DEFAULT 0,
  pay_cnt BIGINT UNSIGNED NOT NULL DEFAULT 0,
  pay_amount DECIMAL(18,2) NOT NULL DEFAULT 0.00,
  PRIMARY KEY (stat_date, shop_id),
  KEY idx_shop_date (shop_id, stat_date)
) ENGINE=InnoDB;

INSERT INTO order_daily_summary (stat_date, shop_id, order_cnt, pay_cnt, pay_amount)
SELECT DATE(created_at) AS stat_date,
       shop_id,
       COUNT(*) AS order_cnt,
       SUM(status >= 1) AS pay_cnt,
       SUM(CASE WHEN status >= 1 THEN pay_amount ELSE 0 END) AS pay_amount
FROM order_info
WHERE created_at >= '2026-10-01' AND created_at < '2026-10-02'
GROUP BY DATE(created_at), shop_id
ON DUPLICATE KEY UPDATE
  order_cnt = VALUES(order_cnt),
  pay_cnt = VALUES(pay_cnt),
  pay_amount = VALUES(pay_amount);

-- 2. 报表查询只扫汇总表
SELECT stat_date, order_cnt, pay_amount
FROM order_daily_summary
WHERE shop_id = 100 AND stat_date BETWEEN '2026-09-01' AND '2026-09-30'
ORDER BY stat_date;

-- 3. 8.0 窗口函数：排名、环比（避免自连接）
SELECT stat_date, pay_amount,
       RANK() OVER (ORDER BY pay_amount DESC) AS amount_rank,
       LAG(pay_amount) OVER (ORDER BY stat_date) AS prev_amount,
       ROUND(pay_amount - LAG(pay_amount) OVER (ORDER BY stat_date), 2) AS diff
FROM order_daily_summary
WHERE shop_id = 100
ORDER BY stat_date;

-- 4. 分区裁剪：只扫目标月份
EXPLAIN SELECT SUM(pay_amount)
FROM order_info
WHERE created_at >= '2026-10-01' AND created_at < '2026-11-01';
-- 若按 RANGE(TO_DAYS(created_at)) 分区，partitions 列只显示 p202610

-- 5. 资源组限制报表查询（8.0）
CREATE RESOURCE GROUP rg_report
  TYPE = USER
  VCPU = 2
  THREAD_PRIORITY = 19;
SET RESOURCE GROUP rg_report;
SELECT /* 报表 SQL */ COUNT(*) FROM order_info;
SET RESOURCE GROUP default;

-- 6. 语句超时，避免报表拖死连接
SET SESSION max_execution_time = 30000;   -- 30 秒
```

**报表 SQL 的写法建议：**

1. **只查需要的列**，避免 `SELECT *` 与大字段。
2. **先过滤再聚合**，把时间范围、店铺等条件下推到最内层。
3. **避免在 `WHERE` 中对列做函数**，用范围条件替代 `DATE()`。
4. **大表 `COUNT(DISTINCT)` 代价高**，可用预聚合或近似算法（业务允许时）。
5. **多维度报表拆成多个汇总表**，不要一条 SQL 里堆十几个 `CASE WHEN`。
6. **分页导出用游标**，不要 `LIMIT` 深偏移。

**面试怎么答：** 先讲「隔离」：报表不要跑主库，走只读从库或专用 OLAP；再讲「预聚合」：明细 → 日汇总 → 月汇总，报表查汇总；然后讲「减少扫描」：覆盖索引、分区裁剪、先过滤后聚合；最后讲「控资源」：资源组、超时、异步任务、列式存储。

**易错点：**

- 报表走从库要接受主从延迟，T+1 报表无所谓，实时报表要单独设计。
- 预聚合的实时性下降，要明确「T+1 还是小时级」，并做补偿重算。
- 分区表不是「建了分区就快」，查询条件必须能命中分区键，否则全分区扫描。
- 资源组只限制 CPU 与优先级，不能解决磁盘 IO 与锁竞争。
- 把 OLTP 明细表直接同步到 ClickHouse 时，要处理更新与删除（CDC + 折叠）。

## 12. 线上常见故障排查（CPU 打满、连接数耗尽、主从延迟）

**线上 MySQL 故障排查遵循「先止血、再定位、后复盘」**：先保证业务可用（限流、kill、切主、扩容），再收集现场（`PROCESSLIST`、`innodb_trx`、`data_locks`、慢日志、系统指标），最后定位根因并补监控与规范。

**一、CPU 打满**

| 步骤 | 命令/动作 | 关注点 |
| --- | --- | --- |
| 确认 | `top`、`pidstat -p <pid> 1` | 是 mysqld 还是其他进程；用户态还是内核态 |
| 看 SQL | `SHOW FULL PROCESSLIST`、`performance_schema.events_statements_current` | 是否有大量同一条慢 SQL |
| 看执行计划 | `EXPLAIN`、`EXPLAIN ANALYZE` | 全表扫描、filesort、临时表 |
| 看锁 | `data_lock_waits`、`innodb_trx` | 锁等待导致线程空转 |
| 看并发 | `Threads_running`、QPS 曲线 | 流量突增还是单条 SQL 退化 |
| 止血 | Kill 慢 SQL、限流、降级、加索引 | 先恢复，再根因 |

```sql
-- 1. 正在执行的 SQL（按耗时排序）
SELECT ID, USER, HOST, DB, COMMAND, TIME, STATE, LEFT(INFO, 200) AS sql_text
FROM information_schema.PROCESSLIST
WHERE COMMAND <> 'Sleep'
ORDER BY TIME DESC
LIMIT 20;

-- 2. 当前语句的等待事件（区分 CPU、IO、锁）
SELECT THREAD_ID, EVENT_NAME, SOURCE, TIMER_WAIT / 1e9 AS ms
FROM performance_schema.events_waits_current
ORDER BY TIMER_WAIT DESC
LIMIT 20;

-- 3. 按指纹聚合，找出消耗 CPU 的 SQL
SELECT DIGEST_TEXT, COUNT_STAR,
       ROUND(SUM_TIMER_WAIT / 1e12, 2) AS total_sec,
       SUM_ROWS_EXAMINED, SUM_ROWS_SENT
FROM performance_schema.events_statements_summary_by_digest
ORDER BY SUM_TIMER_WAIT DESC
LIMIT 10;

-- 4. 锁等待
SELECT * FROM sys.innodb_lock_waits\G

-- 5. 终止失控查询（确认业务影响）
KILL QUERY <thread_id>;   -- 只终止语句
KILL <thread_id>;         -- 终止连接（可能触发事务回滚）
```

```bash
# 系统层定位
top -Hp $(pidof mysqld)          # 找出占用高的线程
pidstat -p $(pidof mysqld) 1 10  # 用户态/内核态、上下文切换
iostat -x 1 5                    # 磁盘 IO 是否打满
vmstat 1 5                       # 运行队列、swap
```

**二、连接数耗尽**

- 现象：应用报 `ERROR 1040 (HY000): Too many connections`，连管理员都连不上。
- 排查：`Threads_connected` 接近 `max_connections`；`PROCESSLIST` 大量 `Sleep` 或同一条慢 SQL；`Aborted_connects` 增长说明建连失败。
- 常见原因：连接池配置过大/泄漏、慢 SQL 堆积、事务未提交、`wait_timeout` 过大、短连接风暴。
- 止血：保留管理员连接（`max_connections + 1` 特权）、Kill 空闲/慢连接、临时调大 `max_connections`、重启连接池、限流。
- 根治：统一池大小、修慢 SQL、修连接泄漏、设置合理 `wait_timeout`、加监控。

```sql
-- 1. 连接使用情况
SHOW STATUS LIKE 'Threads_connected';
SHOW STATUS LIKE 'Threads_running';
SHOW VARIABLES LIKE 'max_connections';
SHOW STATUS LIKE 'Connection_errors_max_connections';

-- 2. 按来源统计连接
SELECT SUBSTRING_INDEX(HOST, ':', 1) AS ip, COMMAND, COUNT(*) AS cnt
FROM information_schema.PROCESSLIST
GROUP BY ip, COMMAND
ORDER BY cnt DESC;

-- 3. 找空闲最久的连接
SELECT ID, USER, HOST, DB, COMMAND, TIME, STATE
FROM information_schema.PROCESSLIST
WHERE COMMAND = 'Sleep'
ORDER BY TIME DESC
LIMIT 20;

-- 4. 批量 Kill 空闲连接（示例，需谨慎，先确认不是连接池预热）
SELECT CONCAT('KILL ', ID, ';')
FROM information_schema.PROCESSLIST
WHERE COMMAND = 'Sleep' AND TIME > 600;

-- 5. 临时调大上限（评估内存后）
SET GLOBAL max_connections = 1000;
```

**三、主从延迟**

- 排查顺序：`SHOW REPLICA STATUS` 看 IO/SQL 线程是否 Yes、`Seconds_Behind_Source`、`Retrieved/Executed_Gtid_Set`、`Relay_Log_Space`；再看主库是否有大事务、从库是否有大查询/备份/DDL。
- 常见根因：大事务、无主键表、从库规格低、单线程回放、从库承担大量读、网络带宽、磁盘 IO。
- 止血：读流量切主库或其它从库、暂停备份/报表、提升从库规格、临时提高并行度。
- 根治：拆大事务、所有表加主键、开 `LOGICAL_CLOCK`/`WRITESET` 并行复制、读写分离按权重、DDL 用 gh-ost。

```sql
-- 1. 复制状态
SHOW REPLICA STATUS\G
-- Replica_IO_Running / Replica_SQL_Running
-- Seconds_Behind_Source
-- Relay_Log_Space
-- Retrieved_Gtid_Set / Executed_Gtid_Set

-- 2. 计算未回放事务（GTID 差，需人工比对集合）
SELECT @@global.gtid_executed;

-- 3. 并行复制配置
SHOW VARIABLES LIKE 'replica_parallel_workers';
SHOW VARIABLES LIKE 'replica_parallel_type';
SHOW VARIABLES LIKE 'binlog_transaction_dependency_tracking';

-- 4. 临时提升并行度（需评估从库 CPU）
SET GLOBAL replica_parallel_workers = 8;
STOP REPLICA SQL_THREAD;
START REPLICA SQL_THREAD;
```

**故障复盘模板：**

1. **时间线**：何时告警、何时止血、何时恢复。
2. **影响面**：受影响业务、请求量、错误率、数据是否丢失。
3. **根因与处置**：直接原因（慢 SQL/大事务/连接泄漏）、深层原因（缺索引、缺规范、缺监控），以及临时止血与最终修复。
4. **改进项**：监控、告警、SQL 审核、容量规划、演练，每项有责任人与截止时间。

**面试怎么答：** 按「CPU、连接、延迟」三类分别讲「现象 → 排查命令 → 止血 → 根因 → 预防」。CPU 重点说 `PROCESSLIST` + `performance_schema` 找 Top SQL；连接重点说 `Threads_connected`、按 IP 聚合、Kill 空闲连接、池配置；延迟重点说 `SHOW REPLICA STATUS`、GTID 差、大事务与并行复制。最后补「先止血再定位」和复盘机制。

**易错点：**

- CPU 打满不一定是慢 SQL：也可能是锁自旋、备份、全表扫描、并发突增，先看 `Threads_running` 与等待事件。
- `KILL` 大事务会触发回滚，可能持续数分钟甚至更久，期间资源不会立刻释放。
- 连接数打满时不要只调大 `max_connections`，每连接都占内存，可能把实例拖入 OOM。
- 主从延迟时不要只看 `Seconds_Behind_Source`，它可能为 0 但 relay log 仍有积压。
- 从库延迟时直接把读流量切回主库可能压垮主库，要评估主库余量并逐步切换。

## 本篇小结

- **复制**：三个线程 + relay log；异步/半同步/MGR 按数据安全与性能取舍，GTID 降低运维复杂度。
- **读写分离**：延迟不可避免，用 GTID 差或心跳表度量；写后读主、缓存兜底、核心链路不走从库。
- **拆分**：分库分表解决容量与并发，但引入跨库 JOIN、分布式事务、全局 ID、扩容与分页问题，是最后手段。
- **ID**：自增简单、号段均衡、雪花高性能、UUID 只做业务标识；机器号与时钟回拨是雪花的关键风险。
- **高可用**：检测、选主、切流、防脑裂四件事；切换后必须校验只读状态与 GTID。
- **工程**：连接池按承载配置、缓存追求最终一致、大表 DDL 用在线工具、迁移靠双写 + 校验 + 灰度。
- **排障**：先止血再定位，CPU/连接/延迟三类问题各有固定的排查路径与复盘模板。
